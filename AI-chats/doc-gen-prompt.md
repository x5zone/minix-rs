# 文档生成与分阶段 review（可复用 prompt）

> 用途：为某个 stage 生成一篇正式技术文档，并按「正确性 review → 卓越性 review → 测试 → 提交」的顺序做完整保障。
> 用法：填好下面的参数，整段发给 agent（Claude Code / Codex / OpenCode / Qoder 等）。
> 边界依据：`prompt/review-rules/review-cmds.md` §一b 决策树、§二 full-review（不做边界 line 88）、§四 code-excellence（不做边界 line 137）、§八 序列（line 243）。

## 参数

```
stage = 01-stage-kernel      # rewrite-notes 下的 stage 目录名（去 stage 化时替换此值）
num   = 01                   # 本次生成的正式文档序号（去文档号化时用 {DOC_NN}）
tool  = qoder   # claude / codex / trae / qoder，决定 .review 状态目录（值必须与 `.review/` 下实际目录名一致，写错会开错状态树）
tree  = rewrite-notes
```

**目标**：为 stage 生成第 `{num}` 篇正式技术文档，再按「正确性 review → 卓越性 review → 测试」的顺序做完整保障。真值优先序恒为：`Minix3 C 源码行为 > 设计契约 > Rust 实现 > 文档 > AI 分析`。

> **为什么正确性和卓越性必须分两轮**（规则硬边界，不许合并）：
> - `full-review` 只管正确性（bug、覆盖度、与 C 源行为一致），**明确不做卓越性重构**，发现卓越性问题只记进 todo；
> - `code-excellence` / `style-fix` 只管卓越性，**明确不修正确性 bug**（卓越建立在正确之上）。
>
> 于是两轮必须**先跑正确性、把 P0 清零，再跑卓越性**——否则卓越性阶段会踩在未修的正确性缺陷上，且违反各自"不做边界"。

## 第 -1 步 · 并发隔离前置（worktree，动任何文件前先做）

本仓库可能有多个 agent 并发操作同一份工作树。直接在共享主树里开工是 `C-35` 事故判例——一次 `checkout`/`reset` 就会销毁其它会话未提交的在制品。**用现成机制 `tools/claim.sh`，别手搓 `git worktree`**（依据：`rewrite-notes/coordination/CONCURRENT-WORK-PROTOCOL.md` §4、§11）：

- **领取**：`tools/claim.sh claim <条目ID> <owner>`（`<条目ID>` 用文档号如 `doc01`）——建排他锁分支 `claim/<ID>-<owner>` + 自动建专属工作树 `.wt/<id>-<owner>/`。分支名全局唯一，第二人领同一条目会直接失败，天然防双领。
- **只在自己那棵树里干**：`cd .wt/<id>-<owner>/` 后再读改文档；**共享主树内禁止 `checkout` 与 `reset --force`**。
- **换任务前自检**：`tools/claim.sh verify`——站在主树会告警，报出的未提交文件数是"在制品即提交"约定的自查信号。
- **归属线自查**（协议 §2 所有权分线）：本任务属**一线（内核面）**，领地含 `rewrite-notes/01-stage-kernel/`、`os/kernel/`、`os/arch/`、`os/qemu-tests/`；越界碰别人的文件先在编排板 `new_edge4.md` 登记一行"跨界改点"再动。
- **QEMU 必须串行**：真机门共用同一块串口，两个 QEMU 同跑互相污染读数。跑 qemu 前先 `tools/claim.sh list` 加直接问，确认无人占用。
- **台账/共享文件是写热点**：`coordination/TODO-LEDGER-OPEN.md`、`TODO-LEDGER-DONE.md`、`new_edge4.md` 多写者共用。各树各分支改，合回 `rewrite` 时会变成一次**显式 git merge 冲突**（优于同树静默覆盖），按"状态以台账为准"手工并解。
- **收尾合回**：改动在自己树里"一个逻辑单元一笔提交"，合入 `rewrite` 后 `tools/claim.sh release <条目ID> <owner>` 删树 + 销锁（树里仍有未提交改动会被拒绝）。

## 第 0 步 · 强制预加载（不许凭记忆动手，技能必须真调用）

按序完整读取规范源：`prompt/review-rules/` 下 `review.md` → `review-process.md` → `fix-guard.md` → `review-cmds.md` §一b 决策树 **与 §一 通用强制门 #9「教学构件承载门」、§六 第 9–10 条（反膨胀 ≠ 砍教学）** → `review-patterns.md` → `review-doc-checklist.md` §4 → `review-core-semantics.md` §1.6 → `review-doc-excellence.md` 末尾「承载性 vs 讲法质量」分界段。

先跑 `tools/review-init.sh` 拿到本文的 `.review/{tool}/{stage}/{doc-stem}/` 制品清单与状态目录（后续所有中间产物都落这里）。

所有技能必须通过 **Skill 工具真正调用**并记入 Skill Invocation Log，"读过/我记得"不算调用。

## 第 1 步 · 选题与衔接（检查点 A：先汇报再动手）

- 文档序真源：`{tree}/{stage}/doc_rerank_*.md`（各 AI 的重建蓝图）+ `checklist.md`。**注：`01-stage-kernel` 无 `plan.md`**（plan.md 只在 02–18 stage 存在），有则参考，无则以上两者为准。
- `doc_rerank_*.md` 应都读取并参考，这就是多AI bagging的意义。
- `{tree}/{stage}/draft/` 是旧文档，**仅作思路参考、不作事实来源**；正式文档禁止引用 `draft/`、`.design/`、`tmp_design_and_todo/`（引用即 P0-process-violation）。**旧文档的章节大纲也同样过期**（它派生自旧正文），只作参考、不许继承复用——新大纲按第 1.5 步现推。
- 结合 `minix3/` C 码与 `os/` Rust 实现，定 `{num}` 的主题边界，说明与前后文档的知识衔接（哪些概念首次在此出现、哪些留后续）。
- 汇报「选题范围 + 覆盖的 C 文件/函数 + 与相邻文档衔接」，用户确认后进第 1.3 步（人工资产对账），再到第 1.5 步写大纲；**未得到确认不得直接写正文**。

## 第 1.3 步 · 人工资产对账（收割 draft，写大纲前必做）

上面那句「draft 只作思路参考」只说了**不许抄什么**，没说**哪些东西必须有人接手**——不固定这一步，人工审阅轮沉淀下来的高价值资产会随 draft 无声蒸发（多模型 bagging 的交集：ds T-4 / glm 提案 E / mimo G-6 都指向此处）。

通读 `draft/{num}-*.md`，按下面八类逐类盘点，列成三列台账（资产 | 类型 | 处置）：

1. 机制图与框图（画法、层次）　2. 表格与对照表（C↔Rust、架构↔架构、位域/常量）　3. 源码节选块与逐行走查讲解　4. 非显然行为的辨析与坑　5. 可复制命令与调试/复现配方　6. 可核对读数与量化基线（测试数、符号数、口径）　7. 诚实披露（测试妥协、覆盖率低、诊断盲区）　8. 认知减负声明与查表入口

**处置只许三档**：继承（按正式版文风**重写**，不是搬运）/ 有意不继承（写**可被第三人复核**的理由：事实过期、归属他篇、历史专题）/ 遗漏（列入本轮补写或 todo）。⛔ 禁止写"简化起见"这类无法复核的理由。台账随检查点 A 一并交用户确认，并写进 `scan.md`。

可选但建议：从 draft 摘 3–5 处**合规**的教学片段当正例锚，让"技术博客文风"从一句口号变成有样品的标准（避开它的过程痕迹与迭代叙事段落）。

## 第 1.5 步 · 追问本质 + 写大纲（正文前必做，检查点 A2）

**先破一个误解**：不能直接拿 `draft/` 旧文档的章节结构当大纲。旧大纲是从旧正文里长出来的，既然正文已按 rerank 重新选题重生成，旧大纲就同样只能参考、不许继承复用。新结构必须从「C 源码本质机制 + Rust 实现 + `doc_rerank_*.md` 选题」**现推**，而不是照旧目录复习一遍。

1. **追问本质**（先问后写）：这篇要讲清的核心矛盾是什么？读者不懂它会卡在哪？按 WHY→WHAT→HOW 排出知识点的因果链——先有哪个矛盾，才逼出哪个机制。这条链决定章节次序，而不是旧文档的次序。
2. **写结构大纲 + 代码清单 + 讲法资产**（一节一行，先不写正文）：每节列出——
   - 该节要讲的本质机制（一句话）；
   - 该节的**章型**：承载章（C 源码分析章 / 实现章 / 诊断章）还是排除型（测试/概念/参见/附录/概述/目录/术语/导航/小结/总览）——承载门 #9 按此判定；
   - 预定贴哪个 C 函数（`minix3/...:func`）、哪段 Rust 实现（`os/...:fn`）；贴几行、贴整函数还是片段、目的是"对照行为"还是"对照结构"；
   - 该节的**讲法资产**：用图、用表、逐行走查、可复制命令、还是反例推演（大纲写了图，正文就必须有图；写了走查，正文就必须有走查——Gate H.6 要同时对齐"知识点覆盖"与"讲法资产兑现"）；
   - 第 1.3 步判为"继承"的资产，在此标出落到哪一节；
   - 与相邻节的衔接（承接上一节的什么、为下一节铺垫什么）。
3. **大纲自审**（过了才准写正文）：逐条问——次序是否贴合因果链、有没有把"属于后续文档的细节"提前展开（细节深度归位）、知识点是否悬空（用了却没前置讲）、代码清单是否每节都有 C 与 Rust 两侧锚点、是否有节只堆坐标而不讲机制；**承载门预检**：每个承载章是否都排了 C/Rust 节选码、诊断章是否排了可复制命令（这一步就能挡住干巴稿，不用等 R1 报 P1-docStyle）；第 1.3 步的继承项是否**每一条都有落点**。体量按文档长度分档：短文（<300 行）只强制客观可判的阻断项，中长文档按全清单。
4. **检查点 A2**：把大纲（含代码清单）交用户确认；确认后进第 2 步。大纲是中间产物，放 `.review/{tool}/{stage}/{doc-stem}/`，正文不复述它。

## 第 2 步 · 按确认的大纲生成正式文档 `{num}-{topic}.md`（`style-bible` 全程强制）

- 逐节对照第 1.5 步大纲的代码清单与讲法资产落笔：贴的每段 C/Rust、每张图表都对应大纲预定项；需偏离则回第 1.5 步改大纲并重新自审，不在正文里临时加节。**大纲是编号契约**：正文小节编号与大纲保持一致；若因教学顺序必须调整，改完大纲要重扫正文内部引用（`tools/doc-ref-check.sh`，需 `AWK=gawk`），不允许留下按旧编号写的"第 N.M 节"。

**写作底线（与下面的文风禁令同权；多模型 bagging 交集：glm 提案 A + ds §11.4 + mimo G-3/G-7）**——生成时就按契约写，评审门的命中量自然下降：

1. **被整段分析的每个函数** → 源码节选 + 逐行/逐段讲解（或显式写豁免理由：教学节奏、归属他篇）。判据是"读者能否只凭本篇复现这个函数的行为"，不是"提及过"。
2. **非显然行为逐条辨析**，四类触发器：顺序敏感的序列、位组合不对称、哨兵/魔数、看似多余的步骤。每一类在其出现处自查是否配了辨析段。
3. **每个关键设计决策** → 取舍与否决表（列"选什么/否掉什么/代价"）。
4. **契约类型** → 结构体骨架视图（字段表代替不了"整体长什么样"）。
5. **第 1 章至少一张机制图**（用无语言围栏块画：链路图/状态迁移图/角色关系图均可），并在章末用同一框架复述一次。
6. **凡"C 行为 → Rust 重表达"必有表**：列出保留 / 改型 / 淘汰 / 新增中的适用项。
7. **凡"不能这样做"的取舍给反例推演**："若 X 会 Y（后果具体到会坏掉什么），所以用 Z"。
8. **诊断/复现/验证类章节给可复制命令**，并写出预期输出的关键行。
9. **数量声称必须给读数**：测试数、符号数、步数都要能复算（写清命令或分解表），严禁抄表上的数字。
10. **至少一处认知减负声明**：明写"本章不必深究 X，因为它属于 Y（后续文档/外部资料）"，让读者知道可以安全跳过什么。
11. **保留过程知识，不要把"走一遍"压成"结论"**（反过度压缩，多模型 bagging 会集体过拟合到"干净"，此条对冲它）：机制类文档要按**四层认知序**搭：①概念骨架（问题/矛盾）→ ②C 源码导读（真实代码+为什么+顺序+调用图，几乎不可压缩）→ ③设计演化故事（为何 32→i64 不能直搬/新字段/新 trait，含被哪个真实故障逼出）→ ④**当前代码实地导览**（实现章必有一节：从入口函数顺着调用链走，每跳挑一个最关键真实片段讲透，配里程碑日志/调用图）。抽象结论句（"本质语义是…""这正是…的落点""这条约束钉死…"）密度若高过"带读者走一遍"的段落 = 过度压缩 → P1。目标不是字数少而是**认知保真**；体量随内容（机制文档常见 700–1000 行，不是越短越好）。

**教学构件承载门 #9（属正确性，不是卓越性）**：非排除型的分析章/实现章必须有 **C/Rust 语言围栏的节选码**（ASCII 图与表不算码），诊断章必须有**可复制命令围栏**，否则 `P1-docStyle` 阻断收敛。机器读数 `tools/doc-code-density-check.sh`。

- 技术博客文风：讲本质机制（WHY→WHAT→HOW），深入浅出；Ch1 主语 = CPU/OS/机制/矛盾，不是函数名。
- 禁黑话/缩写/文言文/压缩简写；禁开发文档味（用"若 X 会有 Y 问题，所以 Z"的假设性推理）。
- **读者体验优先于审查便利**：纯坐标（如行尾 `/* 33 */`、工具行号提示）移出正文，落 `.review/{tool}/{stage}/{doc-stem}.anchors.md`（用 `tools/anchor-resolve.sh --extract`）；符号锚点与块级区间题注保留。
- 每条事实断言带符号/来源锚点；行号只允许工具派生；给不出标 `[待验证]`，禁静默写成事实。过程痕迹（review 编号/日期/修复史）禁入正文。
- KERNEL 约束：SMP+BKL，共享数据 `Arc`+`Mutex`/`Atomic`，禁 `Rc`/`RefCell` 跨 CPU；抽象语义而非暴露 CR3/PTE。三档术语 Rewrite/Refactor/[ARCH] 一致标注。

## 第 3 步 · R1 正确性 REVIEW（`full-review`，scope=doc）——先把 P0 清零

只判对错与覆盖度，**不改设计、不改文风**。

- Step 0 预检：`tools/design-coverage-check.sh {stage}`、`ls {tree}/{stage}/.design/{num}-*.v*.md`；`tools/doc-code-map.sh {num}-{topic}.md` 得关联 Rust 代码清单。
- Blocker Gates（0/A/B/C/D/D-6/E/G/H）逐门附**命令+输出证据**（L1）；无证据的"✅ 通过"作废，L3 推断视为 FAIL（除非写 `MANUAL_FALLBACK`）。
- **教学构件承载门 #9（属正确性 Layer 1，不是卓越性）**：`tools/doc-code-density-check.sh --check {num}-{topic}.md` 命中即 `P1-docStyle`，**计入 STATE Open P1 并阻断 CONVERGED**（旧流程把贴码/图/对照归入不阻断的 grade，导致零代码干巴稿全绿通过——这条分界已修）。`report` 模式恒 exit0 只作读数，`--check` 才阻断；排除型章型与逐章豁免见 `review-cmds.md` §一 #9（豁免章数过半会报泛滥 WARN，不得拿豁免当默认出路）。
- Doc Code Sync 七项（`review-doc-checklist.md` §4）必跑；覆盖率穷举产 `SYMBOLS.md`；对照 C 源查遗漏。
- **发现的设计/文风/卓越性问题 → 只登记进 `{num}-todo.md`，本轮不动**（交 R2）。
- `VERIFY-CHECK.md`（独立验证，标"同 agent + 已重放 grep"）。
- **检查点 B1**：P0（六类：fact/code-bug/design-deviation/design-missing/design-wrong/test-missing）全部修完才可继续；可延后的移 `rewrite-notes/coordination/`。

## 第 3.5 步 · R1 修复的反向验证（防"修了个寂寞"）

每一条当场修复都要做反证：**回退该修改 → 门应变红 → 复原 → 变绿**，退出码写进 `scan.md`。只说"已修"而不展示门在回退态下会拦截，等于未验证（bagging 已实证"修复收敛必须串行"，本步是它在生成端的对应物）。一次只修一条，修完用同一批 grep/工具命令复验。

## 第 4 步 · R2 卓越性 REVIEW（消费 R1 todo，建立在正确代码之上）

分文档侧与代码侧，各自通过 Skill 工具调用：

- **文档卓越 → `style-fix`**（前置 `style-bible`）：章节组织、逐节开发文档味、细节深度归位；裸概念复述自检（把 Ch1 函数名换 `[XXX]` 是否仍可读）。
- **第四项审计：教学资产完备性**（`review-cmds.md` §三 第 4 条）：逐节按第 2 步十条写作底线勾对——贴码/调用图/辨析/三架构对照/诊断命令/取舍表/机制图。**⛔ 不得以"审计通过、无改动"掩盖"本轮未做教学增益"**：必须以"本处已有（在哪）/ 仍缺为何可不补"逐构件作答，并写"本次新增了哪些教学资产（逐条列）"。
- **零发现反证探针**（多模型交集：glm 提案 F）：从 `draft/` 随机抽三个内容形态项（一个代码块、一段辨析、一张图），逐项问"新文档对应物在哪"；判"无需改"的每个维度必须写两句：检查了什么范围、证据是什么命令或对照物。
- **代码块逐块分类**：`tools/doc-snippet-extract.sh {num}-{topic}.md` 输出围栏清单，逐块标为逐字引用 / 教学简化 / 反面示例 / 签名示意，判定它们是否符合最佳实践。
- **反膨胀 ≠ 砍教学（仲裁规则）**：反膨胀条款（拆分阈值、Ch1 节拍上限、示例最小化、注册表元规则）针对的是**重复内容、过程痕迹、越界内容**；贴码/图/辨析/对照/诊断不属膨胀。**删减只删重复与越界，不删教学对象**；体量是"构件齐备"的结果、不是目标——不为凑短砍掉血肉，也不为显教学堆重复。两者冲突时以保留教学性为准。
- **代码卓越 → `code-excellence`**：分层审视（整体→模块→trait→函数）+ 再三比对 Redox/Linux/OS 理论/Rust 社区；**§16.7 跨架构判定栏强制**；死代码消除子轮（每项写"为何死+消除影响"，拿不准标 OQ 上交，不擅自删）；非法态封堵清单（§16.6）；发现正确性 bug 退回 `full-review`，不在本轮修。
- 产物：设计对比表（旧 vs 新 vs Redox 参照）+ 死代码清单 + 文档同步记录。
- **检查点 B2**：与用户确认哪些卓越性改动当场落地、哪些进 `{num}-todo.md` / `coordination/`。

## 第 4.6 步 · 学生型走查（教学质量门，与机器门正交）

机器门（承载/锚点/文风）测的是"承载存在与合规"，测不出"读者能否顺着走一遍"。补一个**不同工种**的 reviewer：

- 派一个**只能凭本文档回答、不得调用自身 OS 常识补全**的"第一次接触 Minix3 的学生"角色（可用子代理并显式禁外部知识），对它抛出 5–8 个机制型问题（如"为什么恒等映射先于内核映射？""这个契约字段是谁生产的？""为什么 C 有 pg_alloc_page 而 Rust 换成 bump 分配器？""为什么 aarch64 需要方案 A？"）。
- **逐题判**：答案能否**仅凭本文**给出。任一题只能靠"常识脑补"或跳步回答 → **教学链断点**，计 P1、回 §1.5 补回该处"走一遍"的推导/实地导览，不得靠加抽象结论句蒙混。
- 这是比"多 AI 整体评价"更有效的教学质量探针：bagging 会把文风往"干净现代"收，只有"学生只凭本文答题"能量化"教材感"。

## 第 5 步 · 测试回归（有代码改动必做）

- 加载 `test-audit`：5 维度——完备性、测试自身正确性（防"测试代码就是错的"）、冗余、无效、虚构（文档测试描述与代码双向对账）。
- 单元：`cargo test -p {crate}`（工作区根 `os/`）；lint `cargo clippy`。
- 真机门：按 `os/qemu-tests/README.md` 跑 `run_qemu.sh` 三架构回归；权威编译门配方见 `AGENTS.md`（docker `minix-ci:1.94` + `-m 2g -j 1`）。
- 思考并补上后续保障测试，缺口记进 `{num}-todo.md`。

## 第 6 步 · todo 归档与执行轨迹

- 未当场修复项写 `{num}-todo.md`（清晰详细，标准是"换个 AI 也能看明白"，禁速记黑话）。
- （可选，建议开）记 `REVIEW-TRACE` 存档（命令/输出/技能调用/各 Gate 判定），供优化流程。

## 第 7 步 · 提交

- 全部 Gate 通过、P0 清零后，将本次所有改动（新文档 + 代码 + `draft/` 移动 + `.review` 外的产物）提交；正文降噪与锚点底账**同一笔提交**落地。
- **受审正文与交付物绑定**（`review-process.md` 0.13，防"过了门的版本 ≠ 入库的版本"）：把 `sha256sum {num}-{topic}.md` 写进 `STATE.md`；提交前复算，与记录不一致（评审后正文被改过）→ **重跑承载门 + 文风门 + anchor 复解析**后再提交。`git diff --stat {doc}` 必须为空才允许收笔。
- **提交前的增量门清单**（五条全绿才提交）：`tools/anchor-resolve.sh --check`、`tools/doc-code-map.sh --check`、`tools/doc-style-lint.sh --diff`（零 error）、`tools/doc-ref-check.sh`（需 `AWK=gawk`）、`tools/doc-code-density-check.sh --check`。
- **人工修改回炉**：已评审文档若被人工改动超过阈值（建议 50 行以上，或触碰事实断言），触发轻量回炉：`anchor-resolve.sh --check` + `doc-style-lint.sh --diff` + 新增事实断抽样对账，产物进 `.review/`。不受门的修改与不受门的生成一样会产出超出真值的断言。
- 提交信息按项目既有风格；**不跳过任何 hook**；如任一门 FAIL 或未确认，则**先回报、不提交**。
