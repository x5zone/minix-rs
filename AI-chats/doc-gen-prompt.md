# 文档生成与分阶段 review（可复用 prompt）

> 用途：为某个 stage 生成一篇正式技术文档，并按「正确性 review → 卓越性 review → 测试 → 提交」的顺序做完整保障。
> 用法：填好下面的参数，整段发给 agent（Claude Code / Codex / OpenCode / Qoder 等）。
> 边界依据：`prompt/review-rules/review-cmds.md` §一b 决策树、§二 full-review（不做边界 line 88）、§四 code-excellence（不做边界 line 137）、§八 序列（line 243）。

## 参数

```
stage = 01-stage-kernel      # rewrite-notes 下的 stage 目录名（去 stage 化时替换此值）
num   = 01                   # 本次生成的正式文档序号（去文档号化时用 {DOC_NN}）
tool  = qoder   # claude / codex / trae / qoder，决定 .review 状态目录（值必须与 `.review/` 下实际目录名一致，写错会开错状态树）
tree  = rewrite-notes
```

**目标**：为 stage 生成第 `{num}` 篇正式技术文档，再按「正确性 review → 卓越性 review → 测试」的顺序做完整保障。真值优先序恒为：`Minix3 C 源码行为 > 设计契约 > Rust 实现 > 文档 > AI 分析`。

## ⛔ 两条总则（优先于下面一切步骤与门禁；第 1 轮两次返工后确立）

**一、章节结构属教学架构，不属可优化对象。** 规范源固定的章级骨架（`prompt/review-rules/review-doc-checklist.md` §1–§4：概述 → C 源码分析 → Rust 设计决策 → 实现详解 → 测试要点 → 诊断/专题 → 参见）本身就是教学模型：先知道它是什么 → 再读 C 怎么做 → 再理解 Rust 为何改 → 再看如何落地 → 再看测试如何证明 → 最后看出问题怎么查。**除非发现实质性错误，任何 review/迭代不得以"更优叙事""认知主线""局部闭环"为由重排、合并或拆分章。**跳章造成的阅读断开用回指与就地最小解释修复，不用重构骨架。

**二、不得以篇幅或密度为理由删教学内容。** 以下全部不是合法删除理由：“旧版重复”“可以交叉引用”“前文已解释”“属实现细节”“可归下一篇”“读者不需要这么多”“更紧凑”“信息密度更高”。合法删除只有三种：内容错、与本篇主题无关、他篇已有更合适的教学位置。**“可以引用他篇”不等于“本篇不需要解释”**：一个概念在本篇首次出现时，必须给足上下文让读者不用跳文档就能读下去。真实代码片段、具体地址例子、寄存器位、调用顺序、失败场景、一次手算、一次对照、“如果改成这样会怎样”——这些都是**教学对象**，不得归入“实现细节”而删。

**篇幅由教学内容决定**：一个概念需要“源码 + 解释 + 反例 + 具体例子 + 架构对照”就写这么长；一句话已经够了就不人为扩写。**禁止把“还能不能再删 20%”当优化标准。**

> **为什么正确性和卓越性必须分两轮**（规则硬边界，不许合并）：
> - `full-review` 只管正确性（bug、覆盖度、与 C 源行为一致），**明确不做卓越性重构**，发现卓越性问题只记进 todo；
> - `code-excellence` / `style-fix` 只管卓越性，**明确不修正确性 bug**（卓越建立在正确之上）。
>
> 于是两轮必须**先跑正确性、把 P0 清零，再跑卓越性**——否则卓越性阶段会踩在未修的正确性缺陷上，且违反各自"不做边界"。

## 第 -1 步 · 并发隔离前置（worktree，动任何文件前先做）

本仓库可能有多个 agent 并发操作同一份工作树。直接在共享主树里开工是 `C-35` 事故判例——一次 `checkout`/`reset` 就会销毁其它会话未提交的在制品。**用现成机制 `tools/claim.sh`，别手搓 `git worktree`**（依据：`rewrite-notes/coordination/CONCURRENT-WORK-PROTOCOL.md` §4、§11）：

- **领取**：`tools/claim.sh claim <条目ID> <owner>`（`<条目ID>` 用文档号如 `doc01`）——建排他锁分支 `claim/<ID>-<owner>` + 自动建专属工作树 `.wt/<id>-<owner>/`。分支名全局唯一，第二人领同一条目会直接失败，天然防双领。
- **只在自己那棵树里干**：`cd .wt/<id>-<owner>/` 后再读改文档；**共享主树内禁止 `checkout` 与 `reset --force`**。
- **换任务前自检**：`tools/claim.sh verify`——站在主树会告警，报出的未提交文件数是"在制品即提交"约定的自查信号。
- **归属线自查**（协议 §2 所有权分线）：本任务属**一线（内核面）**，领地含 `rewrite-notes/01-stage-kernel/`、`os/kernel/`、`os/arch/`、`os/qemu-tests/`；越界碰别人的文件先在编排板 `new_edge4.md` 登记一行"跨界改点"再动。
- **QEMU 必须串行**：真机门共用同一块串口，两个 QEMU 同跑互相污染读数。跑 qemu 前先 `tools/claim.sh list` 加直接问，确认无人占用。
- **台账/共享文件是写热点**：`coordination/TODO-LEDGER-OPEN.md`、`TODO-LEDGER-DONE.md`、`new_edge4.md` 多写者共用。各树各分支改，合回 `rewrite` 时会变成一次**显式 git merge 冲突**（优于同树静默覆盖），按"状态以台账为准"手工并解。
- **收尾合回**：改动在自己树里"一个逻辑单元一笔提交"，合入 `rewrite` 后 `tools/claim.sh release <条目ID> <owner>` 删树 + 销锁（树里仍有未提交改动会被拒绝）。

## 第 0 步 · 强制预加载（不许凭记忆动手，技能必须真调用）

按序完整读取规范源：`prompt/review-rules/` 下 `review.md` → `review-process.md` → `fix-guard.md` → `review-cmds.md` §一b 决策树 **与 §一 通用强制门 #9「教学构件承载门」、§六 第 9–10 条（反膨胀 ≠ 砍教学）** → `review-patterns.md` → `review-doc-checklist.md` §4 → `review-core-semantics.md` §1.6 → `review-doc-excellence.md` 末尾「承载性 vs 讲法质量」分界段。

先跑 `tools/review-init.sh` 拿到本文的 `.review/{tool}/{stage}/{doc-stem}/` 制品清单与状态目录（后续所有中间产物都落这里）。

所有技能必须通过 **Skill 工具真正调用**并记入 Skill Invocation Log，"读过/我记得"不算调用。

## 第 1 步 · 选题与衔接（检查点 A：先汇报再动手）

- 文档序真源：`{tree}/{stage}/doc_rerank_*.md`（各 AI 的重建蓝图）+ `checklist.md`。**注：`01-stage-kernel` 无 `plan.md`**（plan.md 只在 02–18 stage 存在），有则参考，无则以上两者为准。
- `doc_rerank_*.md` 应都读取并参考，这就是多AI bagging的意义。
- `{tree}/{stage}/draft/` 是旧文档，**仅作思路参考、不作事实来源**；正式文档禁止引用 `draft/`、`.design/`、`tmp_design_and_todo/`（引用即 P0-process-violation）。**指向尚未重生成的篇目时，写成 `NN-篇名`（篇题，尚未重生成）的形式、不给路径**（v3 第 5 轮实测：03/05 两篇共 27 处写成了 `rewrite-notes/…/draft/NN-*.md`，而本轮之前五篇正稿里这个数字是 0——是相对既有基线的回归）。**旧文档的章节大纲也同样过期**（它派生自旧正文），只作参考、不许继承复用——新大纲按第 1.5 步现推。
- 结合 `minix3/` C 码与 `os/` Rust 实现，定 `{num}` 的主题边界，说明与前后文档的知识衔接（哪些概念首次在此出现、哪些留后续）。
- 汇报「选题范围 + 覆盖的 C 文件/函数 + 与相邻文档衔接」，用户确认后进第 1.3 步（人工资产对账），再到第 1.5 步写大纲；**未得到确认不得直接写正文**。

## 第 1.3 步 · 人工资产对账（收割 draft，写大纲前必做）

上面那句「draft 只作思路参考」只说了**不许抄什么**，没说**哪些东西必须有人接手**——不固定这一步，人工审阅轮沉淀下来的高价值资产会随 draft 无声蒸发（多模型 bagging 的交集：ds T-4 / glm 提案 E / mimo G-6 都指向此处）。

通读 `draft/{num}-*.md`，用下面八类镜头逐处扫过（**这是读稿时的检查视角，不是要另交的一张台账**）。**两类最容易漏，必须逐张点名核对**（v3 第 1 轮实测）：① **常量 / 位域 / 地址宏的查表表**（PDE/PTE 权限位与地址掩码、CR0/CR4 位号表这类）——它们读起来不像"教学"，但正是读者后面自己回查的入口；② **逐字段处置表**（某一结构体的字段逐个"保留/改型/淘汰/新增"的去向），旧版有而新稿只给分组说明时，属于典型漏收。旧版有、本篇没有的，要么补，要么写明可复核理由：

1. 机制图与框图（画法、层次）　2. 表格与对照表（C↔Rust、架构↔架构、位域/常量）　3. 源码节选块与逐行走查讲解　4. 非显然行为的辨析与坑　5. 可复制命令与调试/复现配方　6. 可核对读数与量化基线（测试数、符号数、口径）　7. 诚实披露（测试妥协、覆盖率低、诊断盲区）　8. 认知减负声明与查表入口

**处置只许三档**：继承（按正式版文风**重写**，不是搬运）/ 有意不继承（写**可被第三人复核**的理由：事实过期、归属他篇、历史专题）/ 遗漏（列入本轮补写或 todo）。⛔ 禁止写"简化起见"这类无法复核的理由。

**每条收割只有一处落点：第 1.5 步大纲对应节的「讲法资产 / 继承项落点」栏**（连同处置档位与那句理由一起写进栏内）。不再单列三列台账、不再单独走一次用户确认——它在检查点 A2 随大纲一并交审。理由：大纲每节本就有「讲法资产」与「继承项落点」两栏，另立台账等于把同一信息写两遍，两遍必然漂不一致（第 0 轮减法 S1）。

可选但建议：从 draft 摘 3–5 处**合规**的教学片段当正例锚，让"技术博客文风"从一句口号变成有样品的标准（避开它的过程痕迹与迭代叙事段落）。

## 第 1.5 步 · 追问本质 + 写大纲（正文前必做，检查点 A2）

**先破一个误解**：不能直接拿 `draft/` 旧文档的章节结构当大纲。旧大纲是从旧正文里长出来的，既然正文已按 rerank 重新选题重生成，旧大纲就同样只能参考、不许继承复用。新结构必须从「C 源码本质机制 + Rust 实现 + `doc_rerank_*.md` 选题」**现推**。

> **⚙ 大纲是"认知事件的规格"，不是"正文的样子"。** 只列"讲什么/知识点/章型"的 outline 会生成一篇"完整、正确、干净、却不教"的架构说明书——它只保证知识都在，没规定"读者按什么顺序、经历哪些证据才能自己得到这些知识"。但**大纲同样不许提前写成教学文案**：一旦里面出现比喻、结论句、悬念安排或"这里值得停下来"，正文就只能围着这些预设的漂亮句子去找证据，方向就倒转成"设计目标→模板→叙事包装"（第 0 轮元组契约落地后首次暴露的失效形态）。大纲只描述**认知事件是什么、要哪些证据**；"怎么写得让人读下去"属正文阶段，而且要靠证据本身产生重量。

1. **追问本质**（先问后写）：这篇要讲清的核心矛盾是什么？读者不懂它会卡在哪？按 WHY→WHAT→HOW 排出知识点的因果链——先有哪个矛盾，才逼出哪个机制。这条链决定章节次序，而不是旧文档的次序。
2. **写大纲：每节 = 知识字段 + 认知四段 + 两条约束**（结构化字段，不写成段落散文）：
   - 知识字段：该节讲的本质机制（一句话）、**章型**（承载/排除）、预定贴哪个 C 函数（`minix3/...:func`）与哪段 Rust（`os/...:fn`）、讲法资产（图/表/逐行走查/命令/反例——写了正文就必须有）、第 1.3 步继承项落点。
   - **认知四段（必答，写成字段名 + 一句要点，不写成文案）**：
     ① **Input**：读者进本节时已知什么（前文哪一节给的）；
     ② **Question**：本节要他回答的问题（必须是一个能被源码回答的真问题，不是修辞性悬念）；
     ③ **Evidence**：给他看的真实代码/数据（具体到 `path:fn`；没有证据能引出这个问题，就不该有这一节）；
     ④ **Output**：读完本节读者能自己解释什么（写"能解释什么"，**不写正文结论句的原话**）。
   - **两条约束**：ⓐ **必须暴露的非显然事实**（本节里"不看代码就想不到、看了代码能自己发现"的那一条）；ⓑ **必须引用的源码锚点**（每条事实断言的出处）。
   - ⛔ **大纲禁则（绝对，无例外）**：**大纲里不得出现任何比喻、拟人、中心意象**——这一条不因正文允许谨慎使用比喻而放宽。大纲是结构与认知依赖的中间表示，比喻属于正文层的表达手段；在大纲里写比喻，等于把措辞提前锁死，正文就只能围着这句现成的漂亮话找证据。同样禁：正文结论句（"契约的形状由…决定"这类漂亮抽象）；写作指示（"先制造悬念""这里值得强调""章末复述"）；"本节兜现落差 D#"式标记。**落差清单是校验项（进 outline-review 与第 4.6 步），不是内容，不得出现在大纲的正文档位。**
   > 判据不变：**任何一个代码片段，如果不能回答"读者为什么此刻必须看它"，就不要放；任何一个结论，如果没有配"读者如何自己得到它"的证据链，就不许只给结论。**
3. **大纲自审**（过了才准写正文）：除原有的次序/覆盖/承载门预检外，**必须加一条读者转移审计**——逐节检查认知四段与两条约束是否填全、相邻节的 Output→Input 是否首尾咬合（上一节的"读者读完能解释什么"＝下一节的"已知"）；**凡预定了代码节选的分析节与每个设计决策节，每一节都要问三遍**（不再随机抽三处——抽样式自检等于给未抽中的小节开了"可以压成结论"的后门）：**①"这里是不是把'看代码→发现→推理'压成了一句结论？"** 是→恢复成过程；**②"这一节让读者能自己回答'为什么不能反过来做'吗？"**——本节的机制若反过来写、次序颠倒或缺掉这一步，**具体坏到哪里**（要坏到某个状态、某一位、某根线、某个地址或某一步次序，依据能在源码里指出），只写"为了保证正确性/否则会出错"＝没写，须在正文里把推演展开；**③"本节自列了清单吗（需要三样东西/四条观察/N 个问题）？"**——清单的每一项都要在本文内有实质展开（贴码、解码或推演），不许只出现一次名词就再也不见；做不到就删掉该项或把该节扩到能兑现。**再加一道禁则复扫**：对大纲本身 grep 比喻词与"值得/注意/这就是/唯一"类宣布句，命中即删（大纲里就不该有这些，否则正文一定长出来）。**反压缩硬纪律**：对任何准备删/准备简写的地方先问"删了以后，读者是不是少了一次自己发现某个东西的机会？"——是→**不许删**（这与"反膨胀"相对置，冲突时保教学；反膨胀只删重复结论/纯实现目录/过程痕迹，不删认知跃迁）。
4. **检查点 A2**：把大纲（含每节认知四段与两条约束）交用户确认；确认后进第 2 步。大纲是中间产物，放 `.review/{tool}/{stage}/{doc-stem}/`，正文不复述它。

## 第 2 步 · 按确认的大纲生成正式文档 `{num}-{topic}.md`（`style-bible` 全程强制）

- 逐节对照第 1.5 步大纲的代码清单与讲法资产落笔：贴的每段 C/Rust、每张图表都对应大纲预定项；需偏离则回第 1.5 步改大纲并重新自审，不在正文里临时加节。**正文要让证据产生重量，而不是替读者完成思考。**两条硬判据（本条重写第 0 轮 T2：原"先观察、空一行、再归纳"被执行成了悬念式戏剧节拍，反而催生元话语，此处软化）：（a）**顺序必须是"证据在前、结论在后"**——读者先看到代码/数据，再被要求回答；不许先给结论再补一段码当装饰；（b）**一个非显然事实不许当别的句子的从句**（一句话塞两个发现，读者眼睛会滑过去），它要单独成句或单独成项。**同时禁止"作者宣布这里很重要"的元话语**："这一点值得停下来看""最典型的一例""现在你能自己回答了""这里能看到一种重要模式"一类句子大面积删——**判据：删掉这句后读者仍然能从代码里发现那个事实，那它本来就不需要**。重点靠代码 + 一个真问题自己显出重量。**大纲是编号契约**：正文小节编号与大纲保持一致；若因教学顺序必须调整，改完大纲要重扫正文内部引用（`tools/doc-ref-check.sh`，需 `AWK=gawk`），不允许留下按旧编号写的"第 N.M 节"。

**写作底线（与下面的文风禁令同权；多模型 bagging 交集：glm 提案 A + ds §11.4 + mimo G-3/G-7）**——生成时就按契约写，评审门的命中量自然下降：

1. **被整段分析的每个函数** → 源码节选 + 逐行/逐段讲解（或显式写豁免理由：教学节奏、归属他篇）。判据是"读者能否只凭本篇复现这个函数的行为"，不是"提及过"。
2. **非显然行为逐条辨析**，四类触发器：顺序敏感的序列、位组合不对称、哨兵/魔数、看似多余的步骤。每一类在其出现处自查是否配了辨析段。
3. **每个关键设计决策** → 取舍与否决表（列"选什么/否掉什么/代价"）。
4. **契约类型** → 结构体骨架视图（字段表代替不了"整体长什么样"）。
5. **第 1 章至少一张机制图**（用无语言围栏块画：链路图/状态迁移图/角色关系图均可），并在章末用同一框架复述一次。
6. **凡"C 行为 → Rust 重表达"必有表**：列出保留 / 改型 / 淘汰 / 新增中的适用项。
7. **反向推演是每个分析节与每个设计决策节的必答项，不是可选装饰**（v3 从"凡取舍得给反例"升级为逐节必答——依据：v2 五轮的学生读数里，残留缺口几乎全部落在这同一类上，"为什么不能反过来做"最常被压成作者一句结论）：把本节机制反过来做、次序颠倒、或缺掉这一步会怎样——**后果必须落到具体对象**（哪个状态、哪一位、哪根线、哪个地址、哪一步次序），且依据能在源码里指出（C 注释、位定义、值域检查、调用顺序都算）。写成"若 X 会 Y，所以用 Z"或"若 X 会 Y（会坏掉什么），所以不允许 X"。读者读完应当能**自己**回答"为什么不能反过来"，而不是复述作者给的理由。
8. **诊断/复现/验证类章节给可复制命令**，并写出预期输出的关键行。
9. **数量声称必须给读数**：测试数、符号数、步数都要能复算（写清命令或分解表），严禁抄表上的数字。**两条 v3 加的硬判据**（第 2 轮实测：一篇给了"复算命令"但那条命令实际输出 53 与 47、而非文中写的 3 与 2；另一篇把"三行/两个/三个"这类计数写错了四处）：
   - **复算命令必须实跑过**——写进正文之前先在终端里跑一遍，确认输出就是你写的那个数；只给一条"看起来能算"的命令 = 未复算。
   - **写"唯一/只有 N 个/第一个/三种"这类计数或排序断言前，必须先把被省略号、被表格分行、被 `cfg` 分支、被代码块边界挡住的成员全核一遍**，并写清计数口径（行还是条、含不含注释/构造点/兜底分支）。凡同一对象在本篇出现在两张表里（如一张取舍表 + 一张字段去向表），两表必须互相一致。
10. **"grep 找不到"不等于"不存在"**（v3 第 2 轮：一句"`LABEL` 宏在本仓没有定义"被 `#define	LABEL` 里的**制表符**证伪）：用检索给出"本仓没有 / 无法确定"这类否定结论前，检索模式要覆盖空白变体（制表符与空格）、注释形态与被宏包裹的名字；否证不了就写成"在本篇检索范围内未命中"，不要写成"本仓库没有"。
11. **至少一处认知减负声明**：明写"本章不必深究 X，因为它属于 Y（后续文档/外部资料）"，让读者知道可以安全跳过什么。
12. **保留过程知识，不要把"走一遍"压成"结论"**（反过度压缩，多模型 bagging 会集体过拟合到"干净"，此条对冲它）。**章级骨架沿用规范源，不得自创**：`prompt/review-rules/review-doc-checklist.md` §1–§4 规定为 ①概述/概念 → ②C 源码分析 → ③Rust 设计决策 → ④实现详解 → ⑤测试要点 → ⑥诊断/过渡/参见；同文件两条硬要求一并适用——**第 1、2 章不得包含 Rust 相关内容**，**第 4 章每个实现必须对应第 3 章的某条设计决策**。本条只规定**章内怎么写**与**章间怎么接**（它于第 1 轮被改写过一次、那次把骨架改成"按概念成章"、与规范源直接冲突，已回退）：
   - **概念章只建立心智模型并提出问题，不得提前给出后续章的结论**。否则第 2 章会退化成"看看 C 怎么证明我刚才说的对"，读者经历史上没有经历"理解生成"。这是"先宣布后证明"的真确修复方式——**改的是概念的交付时机，不是章级骨架**。
   - **C 源码分析章：看真实代码 → 指出从码上才能发现的事实 → 让读者自己归纳**。被整段分析的每个函数贴真实节选 + 逐段讲；**流程图/地图 ≠ 走查**；实现章从入口顺调用链走，每跳给一个最关键真实片段（带 `path:fn`），**节选里的省略号不得吞掉承载语义的行**（尤其不得吞掉"先把当前值读回来"这类机制核心行）。
   - **Rust 设计章每个决策的第一句必须是"C 里真实存在的某个语义或负担"，并回指 C 章的具体小节**。跳章因果靠这条回指闭合，不靠把 C 与 Rust 混写在一章（后者违反规范源）；第 4 章每个实现反过来对应第 3 章的某条决策。
   - **比喻分两层对待：大纲绝对禁止（见第 1.5 步禁则），正文不禁但要格外慎重。**精妙的比喻很难，而且模型不会自己剪自己的比喻（旧版那几个能留下，是因为**有人在剪**：它们旁边同样有一堆被剪掉的环比喻）。因此下笔时的默认值是**不用**；决定要用时，只允许"事后命名"型：好比喻都是**给已经摆在读者眼前的那个动作换个名字**，不引入新实体（正例：`get_parameters` 的代码先看完，再叫它"情报收集官"；`add_memmap/cut_memmap/alloc_lowest` 的登记-冲销-余额形状先看完，再叫它"清单/账本"）；环比喻都是**先于证据出现、还要跨章承担论证**的（反例："递梯子的人会消失""自己脚下的地址""交棒"——一个场景被要求同时承载生命周期 + 地址映射 + 当前执行点）。
     三个硬判据（不靠审美，靠可检查项）：**⓪顺序**——机制先用代码/数据展示过，比喻才能出现；先比喻后码→不合格。**①可删**——删掉比喻后，那一段的机制句仍然完整成立（只删比喻就读不通，说明比喻在替论证干活）；**②不追问**——读者不会问"那梯子到底是谁？固件算不算梯子？跳镜像时梯子又是什么？"这类**映射边界问题**（一旦要追问，比喻就从降低成本变成制造成本）。
     **另外两条：以能数得过来为限（这不是配额，是慎重程度的代理指标），且不得把同一个比喻当母题跨章回收（主题句、章首题词、篇末呼应都不算豁免）；真正值得留下的那一个，应落在"数据结构形状与操作同名"那种天然对位上**（如"切一刀、左右两段补回去"），而不是人为发明的场景。
   - **禁"作者宣布这里很重要"的元话语**："这一点值得停下来看""最典型的一例""现在你能自己回答了""这里能看到一种重要模式"一类句子大面积删——**判据：删掉这句后读者仍然能从代码里发现那个事实，那它本来就不需要**。重点靠代码 + 一个真问题自己显出重量。
   - **禁过度断言**：不写"唯一可能的形状""这不是偏好""必然如此"。改写为两句话："存在 X 依赖，因此 A 不能早于 B（这是不变量）"与"这是当前实现的选择，可以不同（这是选择）"。**区分不变量与实现选择本身就是本项目重视的事，文风必须比它更克制。**
   - 抽象结论句（"本质语义是…""这正是…的落点""这一条钉死了…"）密度若高于"证据 + 真问题"段落 = 过度压缩 → P1。目标不是字数少而是**认知保真**；体量随内容，不为显得厚而堆（机制文档常见 700–1000 行，不是越短越好）。

**教学构件承载门 #9（属正确性，不是卓越性）**：非排除型的分析章/实现章必须有 **C/Rust 语言围栏的节选码**（ASCII 图与表不算码），诊断章必须有**可复制命令围栏**，否则 `P1-docStyle` 阻断收敛。机器读数 `tools/doc-code-density-check.sh`。

- 技术博客文风：讲本质机制（WHY→WHAT→HOW），深入浅出；Ch1 主语 = CPU/OS/机制/矛盾，不是函数名。
- 禁黑话/缩写/文言文/压缩简写；禁开发文档味（用"若 X 会有 Y 问题，所以 Z"的假设性推理）。
- **读者体验优先于审查便利**：纯坐标（如行尾 `/* 33 */`、工具行号提示）移出正文，落 `.review/{tool}/{stage}/{doc-stem}.anchors.md`（用 `tools/anchor-resolve.sh --extract`）；符号锚点与块级区间题注保留。
- 每条事实断言带符号/来源锚点；行号只允许工具派生；给不出标 `[待验证]`，禁静默写成事实。过程痕迹（review 编号/日期/修复史）禁入正文。**锚点必须落在围栏之外的正文里**（v3 第 1 轮实测：本篇 44 条符号锚点写在代码块注释里、只有 19 条落在围栏外，而 `anchor-resolve.sh` 只扫围栏外——写在注释里等于未受锚点门保护）：每个被整段分析的函数，正文里至少要有它的一条符号锚点（C 用 `minix3/…c:func`，Rust 用 `os/…rs:fn NAME` 这类带类型前缀的形式）。
- **动机也要有依据，不许自造合理故事**（v3 第 3 轮实测：初稿把"为什么要做那两处 `memcpy`"讲成了一个听起来很顺的动机——"把启动信息搬进内核自己的存储"——而源码里那两处其实是**全局对象自拷贝**，叙事整段作废）：凡写"为什么要有这一步""这样做是为了…"，必须能指出源码依据（哪一行、哪条注释、哪个调用关系、哪个值域检查）；指不出就写"源码未说明动机"，**不许替它编一个因果通顺的解释**。判据：把这句话拿掉，读者从贴出的代码里还能不能得到同一个结论？得不到就说明依据不足。
- **代码块必须分类标注**（逐字引用 / 节选 / 教学简化 / 签名示意）：删行要留 `...`，改写注释或删去声明就**必须标明是简化**，不得自称"完整"而实际删了承载行。**注释也是引用内容**（v3 第 1 轮实测：6 处"逐字引用"块的注释被改写或删节，其中一处把源码注释里的 `C: protect.c:450-451` 换成了"参见本篇 2.4.1"）——注释被删节/改写，要么恢复原文，要么把该块标注降到"节选（注释有删节）"。**节选块上面那句"省略号处为 X"的注解，必须在块写完之后对着块核一遍再写**（v3 第 3 轮实测：一篇里 6 处此类注解与块内实际省略的内容不符——有的说"省略号处为循环体"而块内根本没有省略号，有的只说省了注释而实际还省了操作数；注解是照记忆写的，读者按它去找会找不到）。
- **教学完整性终检（不止于正确性/覆盖度/设计对齐/代码同步）**：从章标题开始逐节能回答“这里发生了什么、为什么这样做、源码在哪里、改错会怎样、Rust 为何不同”吗？**只看到结论而看不到证据或推导的，判为教学缺失**，不得当成“信息已存在”放行。
- KERNEL 约束：SMP+BKL，共享数据 `Arc`+`Mutex`/`Atomic`，禁 `Rc`/`RefCell` 跨 CPU；抽象语义而非暴露 CR3/PTE。三档术语 Rewrite/Refactor/[ARCH] 一致标注。

## 第 3 步 · R1 正确性 REVIEW（`full-review`，scope=doc）——先把 P0 清零

只判对错与覆盖度，**不改设计、不改文风**。

- Step 0 预检：`tools/design-coverage-check.sh {stage}`、`ls {tree}/{stage}/.design/{num}-*.v*.md`；`tools/doc-code-map.sh {num}-{topic}.md` 得关联 Rust 代码清单。
- Blocker Gates（0/A/B/C/D/D-6/E/G/H）逐门附**命令+输出证据**（L1）；无证据的"✅ 通过"作废，L3 推断视为 FAIL（除非写 `MANUAL_FALLBACK`）。
- **教学构件承载门 #9（属正确性 Layer 1，不是卓越性）**：`tools/doc-code-density-check.sh --check {num}-{topic}.md` 命中即 `P1-docStyle`，**计入 STATE Open P1 并阻断 CONVERGED**（旧流程把贴码/图/对照归入不阻断的 grade，导致零代码干巴稿全绿通过——这条分界已修）。`report` 模式恒 exit0 只作读数，`--check` 才阻断；排除型章型与逐章豁免见 `review-cmds.md` §一 #9（豁免章数过半会报泛滥 WARN，不得拿豁免当默认出路）。
- Doc Code Sync 七项（`review-doc-checklist.md` §4）必跑；覆盖率穷举产 `SYMBOLS.md`；对照 C 源查遗漏。
- **发现的设计/文风/卓越性问题 → 只登记进 `{num}-todo.md`，本轮不动**（交 R2）。
- `VERIFY-CHECK.md`（独立验证，标"同 agent + 已重放 grep"）。
- **检查点 B1**：P0（六类：fact/code-bug/design-deviation/design-missing/design-wrong/test-missing）全部修完才可继续；可延后的移 `rewrite-notes/coordination/`。

## 第 3.5 步 · R1 修复的反向验证（防"修了个寂寞"）

每一条当场修复都要做反证：**回退该修改 → 门应变红 → 复原 → 变绿**，退出码写进 `scan.md`。只说"已修"而不展示门在回退态下会拦截，等于未验证（bagging 已实证"修复收敛必须串行"，本步是它在生成端的对应物）。**外部 review 的结论也要复核**（v3 第 3 轮判例：核查员报"`sp0+4` 那个 CPU 号没有任何读者"，作者复跑证据发现 `minix3/minix/kernel/arch/i386/include/arch_smp.h:cpuid` 宏正是用边界算术读走它——`X86_STACK_TOP_RESERVED = 2*sizeof(reg_t)`，`((frame + K_STACK_SIZE-1) & ~(K_STACK_SIZE-1))[-1]` 就是 `sp0+4`；照核查结论改会把对的说成错的）：**review 报的每一条，动手前先用它给的证据命令自己跑一遍**；与核查不一致时以源码为准，并把偏离项单独列出交编排者仲裁，不许默默照改也不许默默不改。**适用边界（第 0 轮减法 S3）**：本步的反证只适用于**客观门报红后被修掉的项**（anchor / density / style-lint / ref-check / code-map）。**教学性重写没有可回退的红色态**——把一句结论展回"看代码→观察→推理"不会让任何门变红，因此这类改动改为：改完立即用第 4.6 步的同一判据复跑一次（旧版四步是否仍被替读者做），并把它当"跃迁清单由非空变空"的前后对照写进 `scan.md`。

一次只修一条，修完用同一批 grep/工具命令复验。

## 第 4 步 · R2 卓越性 REVIEW（消费 R1 todo，建立在正确代码之上）

分文档侧与代码侧，各自通过 Skill 工具调用：

- **文档卓越 → `style-fix`**（前置 `style-bible`）：章节组织、逐节开发文档味、细节深度归位；裸概念复述自检（把 Ch1 函数名换 `[XXX]` 是否仍可读）。
- **第四项审计：教学资产完备性**（`review-cmds.md` §三 第 4 条）——**分级勾对，不再逐条平铺**（第 0 轮减法 S2：presence 式逐条打勾正是 v1 "干巴稿全绿通过"的共谋）：
  - **第一层（跃迁质量，归第 4.6 步判）**：底线 #1（源码节选+逐段讲解）、#2（非显然行为逐条辨析）、#12（走查真实行与回指闭合）——**由第 4.6 步按评判标尺 M2/M3/M4/M7 判，本轮不再重复逐条勾对**；勾对结果直接引用 4.6 的跃迁清单条目号。
  - **第二层（承载存在性，归机器读数）**：#3~#11（取舍表/结构体骨架/机制图/C↔Rust 表/反向推演/命令带预期输出/数量现算/否定式断言有据/认知减负）——以 `tools/doc-code-density-check.sh` 的 `report` 读数为入口，只对读数缺失处作答，已有一句话登记"本处已有（在第几节）"即可，不逐条复述。
  - **⛔ 不得以"审计通过、无改动"掩盖"本轮未做教学增益"**：必须写"本次新增/恢复了哪几处认知跃迁（逐条，指到节）"；一条都写不出时，要写清检查了什么范围、证据是哪条命令或哪次对照。
- **零发现反证探针**（多模型交集：glm 提案 F）：从 `draft/` 随机抽三个内容形态项（一个代码块、一段辨析、一张图），逐项问"新文档对应物在哪"；判"无需改"的每个维度必须写两句：检查了什么范围、证据是什么命令或对照物。
- **代码块逐块分类**：`tools/doc-snippet-extract.sh {num}-{topic}.md` 输出围栏清单，逐块标为逐字引用 / 教学简化 / 反面示例 / 签名示意，判定它们是否符合最佳实践。
- **反膨胀 ≠ 砍教学（仲裁规则）**：反膨胀条款（拆分阈值、Ch1 节拍上限、示例最小化、注册表元规则）针对的是**重复内容、过程痕迹、越界内容**；贴码/图/辨析/对照/诊断不属膨胀。**删减只删重复与越界，不删教学对象**；体量是"构件齐备"的结果、不是目标——不为凑短砍掉血肉，也不为显教学堆重复。两者冲突时以保留教学性为准。
- **代码卓越 → `code-excellence`**：分层审视（整体→模块→trait→函数）+ 再三比对 Redox/Linux/OS 理论/Rust 社区；**§16.7 跨架构判定栏强制**；死代码消除子轮（每项写"为何死+消除影响"，拿不准标 OQ 上交，不擅自删）；非法态封堵清单（§16.6）；发现正确性 bug 退回 `full-review`，不在本轮修。
- 产物：设计对比表（旧 vs 新 vs Redox 参照）+ 死代码清单 + 文档同步记录。
- **检查点 B2**：与用户确认哪些卓越性改动当场落地、哪些进 `{num}-todo.md` / `coordination/`。

## 第 4.6 步 · 学生型走查（教学质量门，与机器门正交）

机器门（承载/锚点/文风）测的是"承载存在与合规"，测不出"读者能否顺着走一遍"。补一个**不同工种**的 reviewer：

- 派一个**只能凭本文档回答、不得调用自身 OS 常识补全**的"第一次接触 Minix3 的学生"角色（可用子代理并显式禁外部知识），对它抛出 5–8 个机制型问题。
- **主判据（不是"能答对"而是"认知动作有没有被替做"）**：对每个被整段分析的 C 函数，问——旧版会带读者做的四步：**看到真实代码 → 逐条解码 → 发现一个不明显事实 → 自己归纳出机制**，新版是不是直接给了一句结论（"X 初始化了 Y"）就把这四步替读者做完了？凡是新版用结论替代了其中任一步 = **认知跃迁被压缩**，计 P1、回 §1.5 把该处恢复成"看代码→观察→推理"。这是比"能答对题"更严的判据——新版常常“题答得出但发现被略过”。
- **逐节穷举，不抽样**（v3 加；依据：v2 的走查是"报出若干条"式的抽样，未被抽中的小节因此长期免检，而 v2 收尾自己证明"误差恰好集中在没被问到的地方"）：对**每一个**分析节与设计决策节给出三态判定——① **读者能自己推出**（码与解码俱在，反面推演也在）／② **只能靠结论**（读者拿到了结论，拿不到过程）／③ **文中没提**。凡出现 ② 或 ③ 的节，本轮不通过，回 §1.5 把该节恢复成"看代码→观察→推理"。判定表按节号逐行列出，节号不得缺项（缺项 = 本轮未完成，不是"未发现问题"）。
- **自列清单兑现检查**（v3 加）：正文里凡自列清单（"需要三样东西""四条观察""N 个问题"），逐项核对本文是否有实质展开；只出现一次名词的项按 ② 计。
- **范围外的留白不算丢**：若本节明确声明某内容属他篇并给了"继续学去哪"，按该处只判指引是否给足，不判"本篇没写"。**"可以引用他篇"与"本篇必须自己解释"的分界见第 2 步总则二**——首次出现的概念本篇要给足上下文。
- 任一题只能靠"常识脑补"或跳步回答 → 教学链断点，计 P1。
- **反向判据（第 1 轮加，防"教学被形式化"）**：若一篇文档每节都齐备"机制图/辨析/落差/读者问题/章末收束"，读起来却是"作者不断告诉我这里有重点"，计 `P1-teaching-formalized`——它说明闸门被当成**节拍**执行而不是当成**认知事件**执行。修法不是再补构件，也不是改章级骨架（那是规范源定的，不得自创），而是三件事：**删元话语、把结论后移到证据之后（概念章不提前宣布后续章的结论）、把跳章拼接补成回指（第 3 章每个决策回指第 2 章的具体观察，第 4 章每个实现回指第 3 章的决策）。**
- 有旧版时：拿旧版当 pedagogical exemplar，比对"旧版在这节让读者做了什么认知动作，新版把它压成了什么"；无旧版时：靠本判据自身生成。
- 这是比"多 AI 整体评价"更有效的教学质量探针：bagging 会把文风往"干净现代"收，只有"学生只凭本文答题"能量化"教材感"。

- **提交前的增量门清单**（五条全绿才提交）：`tools/anchor-resolve.sh --check`、`tools/doc-code-map.sh --check`、`tools/doc-style-lint.sh --diff`（零 error）、`tools/doc-ref-check.sh --check`（需 `AWK=gawk`；**必须带 `--check`**——不带时它只报告不阻断，第 4 轮就是在报告模式下放过了 5 处悬空引用），`tools/doc-code-density-check.sh --check`。**另加两条本门查不到、必须人工做的引用对账**（第 5 轮发现）：① `doc-ref-check` 只按**本文标题**判定 `§N.M` 与`第 N`，所以跨文档引用只要撞上同号小节就会假通过（写法上无从区分，要逐条开目标文件核对标题真的对得上）；② `第 N` 这个形式会误伤自然语言（"第 0 根线"、"第 2 段"），遇到时改成不撞号的写法（"0 号线"、"第二段"），不得靠删引用过关；③ **跨文档引用要写成 `[目标.md](目标.md) §N.M` 的形式**（同一行里出现 `.md`，检查器才会按"外部引用"跳过）——只写"01 篇 §3.8"会被判成**本文**的悬空小节（v3 第 3 轮实测 4 处）；引用不属于本仓文档体系的编号（外部工作记录之类）时，**不要用 `§` 号形式**，写成"某记录里的编号 X"。**这三条都要在提交前实跑一遍 `--check` 看它是否全绿，不能只凭"我写的时候是对的"。****再加一条元话语与比喻的复扫（它是收笔判据，不是建议）**：`grep -nE '值得(单独|完整|注意|记下|说清|带走|想清|逐字)|本篇[^。，]{0,12}值得|最值得|值得留下|值得花一节|就把人问住|结论有点意外|反直觉|唯一可能的|这不是偏好|地基|洁癖|老路|伸手' {doc}.md` 与 `grep -nE '梯子|脚下|交棒|盖章|账本|名片|送人' {doc}.md`——**后一条命中不等于必须删**：命中后逐条按第 2 步里比喻的三个硬判据（⓪顺序 ①可删 ②不追问）判，删掉或**在提交信息里点名保留哪几个、为什么**（不写这条，同一个词会在五篇里得出不一样结论，下轮无法对账）；梯子/脚下/交棒/送人这四个是已判坏的，命中即删。改法不是删掉这句，而是把它换成**机制层的陈述**：判据是"这句评的是稿子自己（值不值得写、为何单独成节），还是评代码与硬件"。前者必删，后者可留（"读一个具体控制器的 `init` 时这一行必须实地核对"是允许的指导，因为它指向读者下次能重复的动作）。**另加一条"编辑口吻"复扫**（v3 第 1 轮实测：19 个节里"最需要理解/最重要/最容易"式措辞密集出现，属编辑口吻而非机制陈述）：`grep -nE '最需要理解|最重要的一条|最容易在改动|容易被忽略|这条区分很重要|本篇要教|需要看清' {doc}.md`——命中同样逐条判：**评稿子的改写为平实陈述（把"三行里最需要理解的是 X"改成直接讲 X），评机制的保留**。

**再加一条"过程编号"复扫**（v3 第 4 轮实测：`S-2b`/`S-6.2（D-41）`/`NK4-C 1.114`/`D-59` 这类仓库内部阶段编号进了正文，而 `doc-style-lint` 的 SL-11 词表只覆盖 fixNN/续-N/首尾一类的形态、拦不住它们）：`grep -nE '\bS-[0-9]+[a-z]?\b|\bD-[0-9]{1,3}\b|NK4-[A-Z]|\bFIX-[0-9]+' {doc}.md`——命中逐条判两类：**文档自己的叙述里**出现（"这个写法在 S-4 之前存在""由 D-64① 补上"）→ 改写成不带编号的陈述（"早期版本里""由一处补充动作接上"）；**属被引用源码注释或程序输出的原文**（逐字引用块、`### TEST_RESULT` 横幅）→ 原样保留，但要在该块标注里写明"内含仓库内部阶段编号，按原文引用"。判据同元话语：**这句是给读者看的，还是给仓库记账看的？**
- **数字必须可复算**（第 5 轮 CodeReview 报的 P0：正文写"变体分支有 27 行"，实为 25 条——`rg -c` 命中的行数与两处构造点被混在一个口径数）：正文里每一个**自己算出来的数字**（分支条数、测试个数、表项数、行数）都要就地给出复算命令或给出逐项拆解，只给数字 = 未经真值的断言；而**口径要写清**（行还是条、含不含构造点/兜底分支）。挂入 R1：拿不准的先跑一遍再写。
- **人工修改回炉**：已评审文档若被人工改动超过阈值（建议 50 行以上，或触碰事实断言），触发轻量回炉：`anchor-resolve.sh --check` + `doc-style-lint.sh --diff` + 新增事实断抽样对账，产物进 `.review/`。不受门的修改与不受门的生成一样会产出超出真值的断言。
- 提交信息按项目既有风格；**不跳过任何 hook**；如任一门 FAIL 或未确认，则**先回报、不提交**。
