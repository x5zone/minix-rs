# 【文档重写/优化标准工作流】

> 本工作流用于已有初稿或已有 design doc 时，对 Minix-RS 阶段文档进行结构化重写或质量优化。每次执行必须严格按顺序走完所有步骤，**不准跳过、不准压缩、不准在没列完知识点前直接写正文**。
> 
> 核心原则：C 源码是 ground truth；文档是教学材料，不是开发迭代记录；rewrite 不是 translate，必须讲清本质机制。

---

## Step 0：前置阅读（不读不准写）

必须全部读完并交叉理解，方可进入下一步：

1. **Minix3 C 源码**：本阶段涉及的全部 C 文件（如 `*.c` / `*.h` / `arch/*`，具体文件依阶段而定）。
2. **现有文档**：`{NN}-{stage-title}.md`（阶段主文档）的当前版本；若存在 `.bak` 旧版则一并阅读。重写前建议手动备份当前版本为 `.bak`，重写完成后用 `.bak` 做二次检查，确保关键知识点未被误删。
3. **设计文档**：`{NN}-design.md` 或 `{NN}-design-final.md`（若经过多 AI bagging）。
4. **Rust 实现**：对应模块的当前代码（kernel 阶段在 `os/kernel/src/*`、`os/arch/src/*`；VM/PM/VFS 等 server 阶段在 `os/servers/xxx/src/*`；具体路径依阶段而定）。
5. **相邻文档**：前一阶段（`{NN-1}`）和后一阶段（`{NN+1}`）的概述，确保衔接。

> ⚠️ **强制**：未读完源码就下结论 = P0 流程违规。

- **设计约束**：零堆 / no_std / SMP / BKL / 启动期自举 / 安全类型等

  - 类型安全设计（newtype / enum / bitflags / Option 替代 flag）

  - 零堆 / const fn / no_std 约束

- Ch1 小节数是否过多？（建议 5-8 个概念节拍）
- 统一框架是否提前出现，后续章节是否挂在这个框架下？
- 范围边界是否清晰（哪些讲、哪些见后续文档、哪些是预留）？

### 3.5 输出

Review 结论写入 `{NN}-outline-review.md` 或直接在对话中输出：
- 强项
- 问题清单（P0/P1/P2）
- 具体修改建议
- 是否批准进入 Step 4

> ⚠️ **强制**：P0 问题未解决前，禁止进入 Step 4。

## Step 4：重写正文 `{NN}-{stage-title}.md`

基于批准的 outline.md 写正文。

### 4.1 写作纪律

- **C 源码是 ground truth**：每个事实性断言必须带 `file:line` 锚点。
- **Ch1 不讲函数名**：函数/结构体名只能作为 Ch2/Ch3/Ch4 的脚注或引用。
- **没有开发迭代史**：禁止"旧版""最初""后来""我们改成"。用假设性推理替代。
- **架构范围标注**：x86-only / aarch64 / riscv64 / 三架构统一，每处明确。
- **因果链必须正确**："因为 X 所以 Y" 中的 X 必须是真实机制，不能编造。
- **纵向链路完整**：Ch3 每个决策在 Ch1/Ch2 有依据；Ch4 每个实现对应 Ch3 决策；Ch5 每个测试覆盖 Ch3+Ch4。

### 4.2 质量检查

写完后必须跑一遍：
- 裸概念复述测试（把 Ch1 函数名换成 [XXX]，是否仍可读）
- 覆盖矩阵复核（structure.md 的每个知识点是否被正文覆盖）
- 断链检查（Ch3→Ch1&2 / Ch4→Ch3 / Ch5→Ch3+Ch4）
- C 引用逐行验证

## 通用禁令

1. **禁止在列完知识点前写正文**。
2. **禁止 Ch1 以函数名/结构体名为主语**。
3. **禁止"旧版/最初/后来/我们改成"等迭代叙事**。
4. **禁止遗漏 C 源码核心符号**（函数、结构体、行为宏、标志位）。
5. **禁止架构特有机制当共性讲**（必须标注 x86/aarch64/riscv64 范围）。
6. **禁止因果链编造**（解释必须能从 C 语义/ISA 规范推导）。
7. **禁止测试覆盖缺失**（Ch3 每个决策在 Ch5 有对应测试或明确标注为何不可测）。
