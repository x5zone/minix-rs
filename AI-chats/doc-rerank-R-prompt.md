# 文档重建蓝图提示词（R 相·重建蓝图）v1.0

> 本提示词用于对某一个 stage 目录做"文档重建"的第一阶段：只产出重建蓝图，不修改任何
> 正文。第二阶段（B 相·重建）再按蓝图逐篇重写，旧文档归档不删，锚点全部迁移。
>
> 本任务由多个 AI 各自独立执行（bagging）：每个 AI 独立完成一份蓝图，全部产出之后再
> 汇总收敛出一份共识蓝图，共识蓝图才允许开工重建。任何 AI 都不许读取其它 AI 的
> `doc_rerank_*` 产物；任何写入仓库的产物都必须以执行者名字作为文件名后缀。
>
> 本提示词是自包含的。执行者不需要理解整个项目，只需严格按下面的步骤执行。

---

## 执行头部（每次执行前填写；这段文字直接作为报告的第一节）

```text
your_name(AI agent name) = 填写执行者名称
target_dir(关注的工作目录) = 填写目标目录，例如 01-stage-kernel
repo_root(仓库根目录) = /home/xzhao/github/minix-rs

任务 = R 相·重建蓝图：输出 target_dir/doc_rerank_<your_name>.md，不改任何正文。
       只读 C 代码不够，还必须读：本目录全部文档的头部声明、os/ 目录对应入口、
       00-*-overview.md 的导航表。
约束 = 不得引用 .design/ 与 tmp_design_and_todo/；任何落盘产物必须带
       _<your_name> 后缀；不得读取或照抄其它 AI 的 doc_rerank_* 产物。
```

## 一、任务是什么

对一个 stage 目录做文档重建的蓝图设计。蓝图要回答四个问题：

1. **这个 stage 的运行时真序是什么？** 直接从 C 源码重建，不从现有文档转述。
2. **现有文档一共承载了哪些知识点？** 去重之后形成整个 stage 的知识点池。
3. **重建后的新目录是什么？** 每一篇的编号、标题、定位、边界、知识点清单。
4. **从旧到新怎么变？** 重排、拆分、合并、新建、归档逐项列清，并给出锚点迁移表。

交付物只有一个：`target_dir/doc_rerank_<your_name>.md`。它是一份可以直接执行的
重建规格，不是意见清单、不是补丁单。所谓"可以直接执行"，意思是 B 相拿到它之后，不需要
再做任何取舍判断，按每一篇的契约取料、写正文即可。

报告写成能独立阅读的正式文档：不假设读者看过对话过程，不引用"上面说过"的上下文。

---

## 二、为什么是重建，而不是在旧文档之间搬移

这是本任务的方法论前提，执行者必须先理解，否则会把蓝图写成补丁单。

- **搬移的代价**：现有目录是一张三十多个节点的关系网。重排意味着每动一篇，都要重新平衡
  它与前后篇的边界、前置声明、交叉引用、代码注释里的引用，改动互相牵制，最后往往退化成
  "每一篇都动了一点，但每一篇都没有真正变好"。
- **重建的代价更低**：重建以新目录为坐标。设计好新目录之后，每一篇只需要做一件事——
  从"全 stage 知识点池 + C 源码 + 非 C 制品"里，把属于自己契约的知识点找出来、剪贴过来、
  按新的教学顺序重新写。旧文档只作为知识来源，不作为搬移对象。
- **蓝图的形态**：参考 `01-stage-kernel/06-todo.md` 的写法。它不是论证"旧文档哪里错了"，
  而是定义"新文档讲什么、不讲什么、下放给谁、验收是什么"。本报告只借它的写法，
  不搬它的内容。
- **历史教训**：这个项目曾经在"重编号断链风险大于收益"的裁决下停在原地
  （`01-stage-kernel/todo.md` 的 I-14 条目）。所以 R 相必须先把断链成本算清楚——把旧文档
  每一节的去向、每一处引用的迁移全部列成表，再谈重建。看不清成本的重建不做。

## 三、允许做什么、禁止做什么

允许：

- 读取仓库内任何文件：C 源码、头文件、Rust 代码、脚本、配置、构建文件、现有文档。
- 运行只读命令收集证据（`rg`、`sed -n`、`git log`、`wc -l`、`git grep` 等）。
- 在蓝图中提出：重排、拆分、合并、新建、归档、重编号，包括为 C 之外的主题新建篇章。
- 引用文件路径与符号作为证据。

禁止：

- 修改、重命名、移动、删除任何现有文件。
- 提交任何代码或文档变更。
- 读取其它 AI 的 `doc_rerank_*` 报告或任何以他人名字为后缀的中间产物。
- 引用 `.design/` 与 `tmp_design_and_todo/` 目录下的任何内容（项目规范：这两个目录视为
  中间产物，正式文档引用即违规）。
- 直接照抄现有 `00-*-overview.md`、`plan.md`、`todo.md` 里的顺序结论。可以引用它们作为
  线索，但必须在蓝图中给出你自己的证据与判断。
- 编造事实。任何关于 C 源码、Rust 代码、构建制品的断言都必须带锚点；给不出锚点的判断
  必须显式标注为"推测"或"待验证"。

落盘规则（重要，防止多个 AI 互相误读中间产物）：

- 只允许写一个文件：`target_dir/doc_rerank_<your_name>.md`。
- 执行过程中的中间结果（知识点草表、依赖关系图、命令输出摘录）一律放进这个文件；
  除非文件过大，确实需要分文件，分文件名必须带 `_<your_name>` 后缀。
- 仓库里任何无后缀的新文件都会污染其它 AI 的读取，视为违规。

## 四、必读输入（只读 C 代码是不够的）

必须读完下面七类输入再开始下结论。C 代码只能回答"有哪些主题、按什么顺序执行"，回答不了
"读者按什么顺序才学得会"和"哪些主题不在 C 代码里"。

1. **目标目录全部文档**：编号文档的头部声明（讲什么、不讲什么、前置、边界）全部要读；
   正文按需精读，用于建立知识点池。
2. **本 stage 对应的 Minix3 C 源码与头文件全量**。清单来源：`00-*-overview.md` 的文档
   映射表、`plan.md`，再用检索按目录名核对一遍，逐文件确认，不只看映射表。
3. **非 C 语言的构建与引导制品**（最容易漏，逐项检查并在蓝图中回答）：
   链接脚本、汇编入口与陷阱入口、引导链与引导协议、镜像布局、用户态启动与运行时装载、
   跨模块接口与线格式、构建脚本与工具链、测试基建与模拟器脚本。
4. **阶段边界材料**：`notes/rewrite/fork-syscall-rewrite/00-master-plan/README.md`
   （阶段划分与启动因果链）、`edge_todo.md`（跨阶段条目）、目标目录的 `plan.md` 与
   `todo.md`（含已声明不做的事项）。
5. **前一个 stage 的 `00-*-overview.md`**：确认哪些概念前面已经讲过，本 stage 不许重复
   展开；这决定新目录第一篇的起点。
6. **对应 Rust 实现入口**：`os/` 下与本 stage 相关的 crate 与模块入口。用途是核对
   "机制在代码里是否存在、是否有代码已实现但文档没讲的机制"；Rust 代码不是顺序权威，
   Minix3 C 源码才是行为底线。
7. **写法范例（可选）**：`01-stage-kernel/06-todo.md`。只学它如何写"新文档契约"
   （讲什么、不讲什么、下放给谁、验收是什么），不搬它的任何结论。

## 五、判断标准：什么叫"对读者最友好的讲述顺序"

沿用四条可度量硬标准与并行体的组织规则。

### 5.1 四条硬标准（不满足就是错误，不是偏好）

1. **无前向引用**：新目录中任意一篇，读者只用它之前的篇章加开头声明的前置知识，就能完整
   读懂；任何术语、概念、机制都不允许引用尚未出现的篇章。
2. **执行与因果序优先**：本 stage 如果是线性启动链或线性调用链，讲述顺序尽量与运行时序
   一致；不一致的地方必须记录在《序差表》里，写清运行时序事实（带锚点）、教学序选择的
   理由、以及回指补偿的位置。
3. **首次出现即完整**：一个概念第一次出现时把"是什么、为什么需要、解决什么问题"讲完整；
   后面只引用，不再重新解释。
4. **单篇单语义**：每一篇只承载一个可独立阅读的语义单元；一篇不允许同时既是概念教学、
   又是实现手册、又是测试清单。

### 5.2 并行体的组织规则（不许伪造线性序）

当一组主题是并行的（几十个系统调用、几十个设备驱动、多种文件系统、大量命令），不要强行
排成一条线，按"汇聚点加触发时机"组织：

- 先给统一框架篇（共同的消息格式、分派机制、生命周期、注册方式）；
- 再按场景或角色分组成篇（例如进程生命周期类、内存类、信号类、设备类）；
- 组内选一个代表性成员讲透，其余按差异表收束；
- 主线路径、支线路径、可跳读路径分开声明。

### 5.3 软目标（在多条可行顺序之间择优）

- 认知递进：先具体后抽象，先现象后机制，先局部后整体。
- 主题聚簇：同类主题相邻成组，组内按使用频率与最小惊讶排序。
- 主线与支线分离：启动链、核心数据流、核心协议是主线；调试工具、性能采样、历史演进、
  已声明不做（WONTFIX）的内容是支线，集中成组，允许跳读。

### 5.4 验收方式（机械检查，不靠感觉）

1. 前向引用扫描：按新目录顺序逐篇检查契约里的"前置"，确认只指向更早的篇章。
2. 依赖关系图检查：由契约的前置关系构图，验证无环；有环必须给出拆解方案。
3. 覆盖率检查：知识点池每一条都必须有去向（新篇章编号加小节）或被明确标记删除并给理由。
4. 断链成本统计：统计旧文档被引用次数（文档之间加代码注释），给出总量与热点。

## 六、执行步骤

### 步骤 0：范围与清单

先声明范围：哪些算文档（编号文档、`99` 总概念篇），哪些算参考材料（`plan.md`、
`todo.md`、`draft/`、`checklist.md`），哪些算范围外。然后收集四份清单：

- 文档清单：编号、标题、行数、头部声明的前置与边界；
- C 源码清单：文件与对应的现有文档编号；
- 非 C 制品清单：第四部分第 3 类逐项记录实际找到的文件与位置；
- 引用关系清单：用检索统计文档之间、代码注释里对现有文档编号或文件名的引用。

范围要写进报告元数据一节。末尾发现的范围外重要主题，单列"范围外发现"。

### 步骤 1：C 真序（运行时真序重建）

直接从 C 源码重建运行时序，不允许从现有文档转述。按阶段类型采取不同形态：

- 启动链型：从入口函数开始，沿调用关系列到本 stage 结束，逐步带锚点。
- 服务事件循环型：分两段——启动段（进程诞生、初始化、进入循环）与循环段（消息接收、
  分派、处理、回复）。
- 系统调用集合型：给出分派表结构与按主题的分组，以及触发时机（谁在什么时候发起）。
- 驱动与命令集合型：给出注册机制、发现机制、参考使用路径。

输出一张"真序表"：步骤编号、动作、C 函数与文件锚点、说明。这张表是后续《序差表》的
事实来源，必须逐条可核对。

### 步骤 2：知识点全集（存量池初建）

对现有每一篇文档提取知识点，然后全 stage 去重，形成知识点池的存量部分。每个知识点记录：

| 编号 | 名称 | 类型 | 来源类型 | 现有位置（文档与小节） | 锚点（C 源码或制品或文档） | 读者收益（学会它能回答什么问题） |

知识点类型建议：概念、机制、数据结构、接口与协议、约束与不变量、架构演进、工具与工程、
测试性质。编号使用 stage 内唯一编号（例如 `K-001`），多 AI 汇总时以"名称加锚点"作为对齐
键。同一知识点在多个文档重复出现的，合并成一条并记录全部现有位置，标注哪个是主讲述点。

来源类型有两种，池内平等对待，只是后续要回答的问题不同：

- **存量**：来自现有文档，后续要回答"搬到哪里去"（受步骤 4 的去向规则约束）；
- **新增**：现有文档没有，但 C 源码、非 C 制品或操作系统理论承载，由步骤 3 的覆盖审计
  发现并追加入池；后续要回答"证据锚点在哪里"（不受去向规则约束）。

这是重建不丢知识的底线，也是新增知识有据可查的底线：池子建不完整，后面所有结论都不可信。

### 步骤 3：覆盖审计（防遗漏、防重复、防越界）

先建立**主题全集**，来源四路：

1. C 源码符号：函数、结构体、宏、常量、状态机、错误路径、按架构分支的部分；
2. 这些机制对应的操作系统通用概念（不依赖具体代码，例如进程状态机、地址空间、权限模型）；
3. 非 C 制品承载的主题（第四部分第 3 类）；
4. 阶段边界契约里属于本 stage 的主题。

再与知识点池、现有文档逐一对账，得到三张表：

- **覆盖缺口表**：主题在全集里但没有任何一篇讲。每条给出建议（新建篇章、并入某篇、
  判定属于其它 stage、或明确不做并给理由）。
- 凡是建议新建篇章或并入某篇的缺口，逐条落实为"新增知识点"追加入池（来源类型标新增，
  锚点填 C 源码位置、非 C 制品路径或操作系统理论出处），供步骤 5 的契约引用。旧文档
  没讲过的知识点由此获得合法身份，不会因为"找不到去向"而卡住。
- **重复主题表**：同一主题在多个文档重复展开。每条给出"新目录中保留哪一篇作为主讲述点，
  其余改为引用"。
- **越界主题表**：某篇讲了声明边界之外的主题。每条给出正确归属。

非 C 主题必须逐项显式回答"在哪里讲"或"为什么不在本 stage"，清单固定为：
链接与加载、镜像与内存布局、汇编入口与陷阱进入、启动装配、构建与工具链、跨模块接口与
线格式、错误路径、关闭与退出、并发与同步、测试基建。

### 步骤 4：设计新目录

设计新的篇章结构。允许五类操作：

1. **重排**：整篇或整节换位置；
2. **拆分**：一篇拆成多篇；
3. **合并**：多篇并成一篇；
4. **新建**：为现有文档没有覆盖的主题新建篇章，特别是 C 之外的主题；
5. **归档**：内容被吸收后旧篇退出正式目录（B 相归档不删）。

硬规则：

- 每处操作必须写 `旧 → 新`、为什么、涉及的知识点编号，并按下面的双方向规则写清经手
  知识点的去向或来源。
- **双方向规则**（互相独立，不要混用）：
  - **存量方向看去向**：拆分与合并涉及的旧文档知识点，逐条给出新位置（新篇章加小节）；
    确实要丢弃的写"删除加理由"。**写不出去向的不许拆**——这条只约束旧知识的搬迁，
    不约束新知识。
  - **新增方向看来源**：现有文档没有、但 C 源码或非 C 制品或操作系统理论承载的知识点，
    不受去向规则约束，直接作为新增知识点进入契约；必须给证据锚点，禁止凭空出现。
- 新建篇章必须写清原料来源（从哪些旧文档取、从哪些 C 文件取、从哪些非 C 制品取）。
- 新目录给出编号、标题、一句话定位；如果分若干部分或阶段，给出分组；并行主题给出
  主线、支线、可跳读路径。

### 步骤 5：每篇新文档的契约（强制，缺一篇不许交付）

新目录里每一篇都要有契约。契约是 B 相写正文的任务书，也是防止重建回潮成百科的闸门
（`06-todo.md` 的体检教训：文档坏在概念混杂和职责越界，不坏在篇幅）。

```markdown
### <新编号>-<标题>

- 一句话定位：这篇解决读者的什么问题。
- 讲什么：逐条列出本篇承担的知识点（引用步骤 2 的编号）。
- 不讲什么：逐条列出明确不讲的邻近主题，并写去向（交给哪一篇，或为什么不在本 stage）。
- 前置：读懂本篇需要先读的新篇章（只允许指向更早的编号）。
- 后置：哪几篇会引用本篇的结论。
- 事实底线（ground truth）：
  - C 文件与函数、宏、结构体（带锚点）；
  - 非 C 制品（链接脚本、汇编、构建文件、协议、线格式，带路径）。
- 知识点清单（每条一行）：
  | 知识点编号 | 名称 | 类型 | 锚点 | 为什么归本篇 | 来源（存量填旧文档位置；新增填 C 源码锚点、非 C 制品路径或操作系统理论出处） |
- 验收标准：怎样算讲透，给出可验证的检查（例如关键问题清单、必须出现的对比、必须画出的
  关系图）。
```

### 步骤 6：缺漏新篇

把步骤 3 里发现的缺口，按固定清单逐项落实为新建篇章或明确否决。每一项写：主题是什么、
为什么重要、原料在哪里、归哪一篇、验收标准是什么。此节不允许留空，不允许写"待定"。

### 步骤 7：锚点迁移表与断链成本

重建的最大成本是断链。先把账算清楚再谈重建。

锚点迁移表覆盖所有发生变化的旧文档，逐节列出：

| 旧位置（文档与小节） | 旧内容（一句话） | 新位置（新篇章与小节） | 迁移类型（原样搬移/改写/合并/拆分/删除） | 备注（断链风险） |

另外单列"引用迁移表"：用检索找出所有引用旧编号或旧文件名的地方，包括文档之间的交叉引用
与代码注释里的引用（例如 `covered in NN`、`see XX-doc.md`），每条写旧引用、新目标、
验证方式。最后给出断链成本摘要：受影响引用总数、热点文件、建议的批量修改方式。

### 步骤 8：验证与自检

按第五部分第 4 条的四种机械检查执行，并把结果写进报告。任何一项不通过，结论必须写成
"未完成"并列出还缺什么。

## 九、按阶段类型的补充提示

- **启动链型**（内核、用户态运行时、初始化进程）：以启动时序为骨架；非启动路径的机制
  （调试、采样、已声明不做）归入支线。
- **服务事件循环型**（存储管理、进程管理、文件系统、注册服务、调度、信息库）：
  按"服务为什么存在 → 诞生与初始化 → 消息接口 → 核心数据结构 → 按场景分组的请求处理 →
  查询与杂项 → 与邻接服务的协议"组织；一次请求的生命周期通常比源码调用顺序更适合
  作主线。
- **库与框架型**（文件系统框架库、网络框架库）：先讲抽象层与接口契约，再讲框架骨架，
  最后按实现族展开；不要一上来逐文件讲实现。
- **集合型**（几十个驱动、大量命令）：先总览与分类框架，再按设备族或命令族分组，组内给
  代表性成员精讲加差异表；必须给出阅读路径。

同一个 stage 同时具备多种特征时，说明按哪一类处理以及为什么。

## 十、与 B 相（重建相）的衔接（执行者了解即可，不必写进报告）

- R 相全部 AI 的蓝图汇总收敛为一份共识蓝图，共识蓝图就是新目录的施工图。
- B 相按共识蓝图逐篇写正文：对每一篇，从知识点池取料——存量条目按契约的"来源"一列定位
  旧文档段落，新增条目按证据锚点直接从 C 源码或非 C 制品取料；一律按事实底线核对，
  再按新目录的教学顺序重写，不保留旧文档的叙述结构。
- 旧文档整体归档，不删除；所有交叉引用与代码注释引用按锚点迁移表批量迁移。
- B 相每一篇完成后，按本项目的文档规范做正式审查；验收标准用契约里写好的那一条，不再
  另立标准。
