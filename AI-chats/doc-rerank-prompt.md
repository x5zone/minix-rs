# 文档顺序重排审查提示词（doc_rerank）v0.1

> 用途：对某一个 stage 目录内的文档做"讲述顺序"审查，产出一份《文档顺序重排建议》
> 报告。该报告只做分析与建议，不修改任何现有文档、不重命名任何现有文件。
>
> 本任务会由多个 AI 各自独立执行（bagging）。每个 AI 必须独立完成，禁止阅读其它 AI 的
> 中间产物或最终报告；所有写入仓库的中间产物与最终报告都必须以执行者的名字作为后缀。
>
> 本提示词是自包含的。执行者不需要理解整个项目，只需要严格按下面步骤执行。

---

## 执行头部（每次执行前填写；这三行是报告的第一段内容）

```text
your_name(AI agent name) = 填写执行者名称
target_dir(关注的工作目录) = 填写目标目录，例如 01-stage-kernel
repo_root(仓库根目录) = /home/xzhao/github/minix-rs

现在需要关注目标目录内文档的讲述顺序。
```

---

## 一、任务是什么

关注 `target_dir` 目录内所有编号文档的**讲述顺序**，回答四个问题：

1. **现在每篇文档讲了哪些知识点？** 逐篇穷举，列出完整清单。
2. **这些知识点为什么放在这一篇、这一个位置？** 给出位置理由；讲不出的，就是位置可疑项。
3. **对读者最友好的讲述顺序是什么？** 给出推荐顺序，并说明每条推荐的理由。
4. **有没有主题被漏掉或讲重复？** 列出覆盖缺口表与重复主题表，并判定归属。

"讲述顺序"并不等于文件编号顺序。文件编号是目录顺序；讲述顺序是读者实际阅读时的推进
顺序。两者可以建议保持一致（重编号方案），也可以建议分离（保留编号，只提供阅读路径）。
两种方案都要给出。

本报告的目的不是立刻动手改文档，而是为后续的文档重排、拆分、合并、新增提供一份经过
论证的执行依据。因此"讲清楚为什么"比"给出一个顺序"更重要。

## 二、允许做什么、禁止做什么

允许：

- 读取仓库内任何文件（C 源码、Rust 代码、文档、脚本、配置）。
- 在报告中引用文件与符号作为证据。
- 建议新增文档、拆分文档、合并文档、调整编号、调整章节内容归属。
- 运行只读命令（`rg`、`sed -n`、`git log`、`wc -l` 等）收集证据。

禁止：

- 修改、重命名、移动、删除任何现有文件。
- 提交任何代码或文档变更。
- 阅读其它 AI 的 `doc_rerank_*` 报告或中间产物。
- 直接照抄现有 `00-*-overview.md`、`plan.md`、`todo.md` 里的顺序结论而不做独立验证。
  （可以引用它们作为线索，但必须在报告中给出你自己的证据与判断。）
- 编造事实。任何一条关于 C 源码、Rust 代码、构建制品的断言都必须带锚点；给不出锚点的
  判断必须显式标注为"推测"或"待验证"。

写入仓库的产物只有一个：`target_dir/doc_rerank_{your_name}.md`。
如果执行过程中需要落盘中间产物（知识点清单、依赖图等），也一律放进同一个文件，或用
`{your_name}` 作为文件名后缀，禁止产生无后缀的中间文件。

## 三、必读输入（只读 C 代码是不够的）

必须把下面六类输入都读完，再开始下结论。只读 C 代码只能回答"有哪些主题、按什么顺序
执行"，回答不了"读者按什么顺序才学得会"和"哪些主题不属于 C 代码"。

1. **目标目录内的全部文档**（00 到最后一篇，含 `99` 与 `plan.md`、`todo.md`）。
   重点读每篇开头声明的"本篇讲什么 / 本篇不讲什么 / 前置 / 边界 / 与相邻文档的关系"，
   以及正文里的交叉引用（`详见某某篇`）。
2. **本 stage 对应的 Minix3 C 源码与头文件全量**。
   C 源码清单的来源：目标目录 `00-*-overview.md` 的文档映射表、`plan.md`、以及按目录名
   到 `minix3/` 的实际检索。逐文件确认，不要只看映射表。
3. **非 C 语言的构建与引导制品**。这一段最容易漏，必须逐项检查：
   - 链接脚本（`*.ld`、`*.lds`）；
   - 汇编入口与陷阱入口（`*.S`、`arch/` 下的汇编、Rust `naked_asm!`）；
   - 引导链与引导协议（boot-shim、multiboot、设备树、U-Boot、EFI）；
   - 用户态启动与运行时装载（`crt0`、`minix-rt`、动态装载、服务加载）；
   - 跨模块接口与线格式（`minix-types`、`minix-boot`、系统调用应用二进制接口）；
   - 构建与工具链（`build.rs`、`xtask`、`Cargo.toml`、生成脚本、QEMU 测试脚本）。
4. **阶段规划与阶段边界**：
   - `notes/rewrite/fork-syscall-rewrite/00-master-plan/README.md`（阶段划分与启动因果链）；
   - `notes/rewrite/fork-syscall-rewrite/edge_todo.md`（跨阶段条目）；
   - 目标目录的 `plan.md`（如果有）与 `todo.md`（含已声明不做的项）。
5. **前一个 stage 的 `00-*-overview.md`**：确认哪些概念前面已经讲过，本 stage 不许重复
   展开；这决定了本 stage 第一篇文档的起点。
6. **本 stage 对应的 Rust 实现目录**：只用于核对"文档讲到的机制在代码里是否存在、是否
   有文档没讲但代码已实现的机制"。Rust 实现不是顺序的权威来源，C 源码才是行为底线。

特别提醒：本项目的"主题集"从来不只等于 C 代码。链接与加载、内核镜像布局、引导协议、
装配与启动、构建与工具链、线格式、错误路径、关闭与重启、并发与锁、测试基建，这些主题
在 C 代码里往往没有对等物，但读者必须学到。**每一个 stage 都要显式回答这些主题在哪里讲；
如果没有任何一篇讲，就是覆盖缺口。**

## 四、什么叫"对读者最友好的讲述顺序"

这是本任务的判断标准。先给定义，再给仲裁规则；报告中每一条顺序建议都要能对上这里的
某一条。

### 4.1 硬门槛（不满足就是错误，不是偏好）

1. **依赖闭合**：推荐顺序中的任意一篇 P，读者只用 P 之前的文档加上开头声明的前置知识，
   就能完整读懂 P。P 不允许引用尚未出现的术语、概念、章节、文档编号。
2. **概念首次出现即讲透**：一个概念第一次出现时把"是什么、为什么需要、解决什么问题"
   讲完整；后面只引用，不再重新解释。
3. **因果连续**：每一篇开篇要回答的问题，由上一篇收尾留下的问题自然导出（问题链），
   不允许跳步，不允许凭空开始一个新主题而没有过渡。
4. **单篇独立可读**：任意一篇都能单独读懂（有前置声明、边界声明、术语指向）。
5. **无编造**：所有事实性断言都有锚点。

### 4.2 软目标（用于在多条可行顺序之间择优）

1. **时序一致**：当本 stage 是一条线性启动链或线性调用链时，讲述顺序尽量与运行时序
   一致，读者可以边读边在心里模拟系统启动。这是最省认知成本的顺序。
2. **认知递进**：先具体后抽象，先现象后机制，先局部后整体，先问题后方案。
3. **主题聚簇**：同一类主题相邻成组，组内按"使用频率 + 最小惊讶"排序；不要让读者在
   两个不相关的主题之间来回跳。
4. **主线与支线分离**：启动链、核心数据流、核心协议是主线；调试工具、性能采样、历史
   演进、已声明不做（WONTFIX）的内容是支线。支线不插进主线的推进节奏，集中成组，允许
   跳读，并给出明确的阅读路径。
5. **并行主题不强行线性化**：当一组主题其实是并行的（例如几十个系统调用、几十个驱动、
   多种文件系统），先给统一框架，再按场景或角色分组，给出"主线路径 + 支线路径 + 可跳读
   路径"。强行排成一条线会让读者抓不住结构。

### 4.3 冲突仲裁规则（顺序是多个目标妥协的产物，必须写清妥协方法）

优先顺序从高到低：

1. 硬门槛永远优先。
2. 硬门槛之间若紧张（例如严格依赖闭合要求先讲一个平时序上靠后的概念），按"依赖闭合"
   优先，并在《序差表》里记录这次偏离。
3. 线性启动或调用链的 stage，用"时序一致"作为骨架。
4. 其余情况下用"认知递进 + 主题聚簇"决定次序。
5. "主线与支线分离"决定哪些内容放最后或放附录，不参与主线排序。

**凡是与运行时序不一致的地方，必须逐条进入《序差表》**，写清运行时序的事实（带锚点）、
教学顺序选择的理由、以及在哪里做回指补偿。

### 4.4 可检验的验收方式

推荐顺序不是靠感觉验收，而是用四个机械检查：

1. **前向引用扫描**：按推荐顺序逐篇检查交叉引用，确认所有引用都指向更靠前的文档或章节。
2. **依赖边抽样**：从依赖关系图里随机抽十条边，逐条验证顺序满足依赖。
3. **读者走查**：模拟一个只读过前一个 stage 概述的读者，按推荐顺序逐篇走查，记录在哪一
   篇开始卡住、卡在哪个术语或哪个机制上。
4. **序差表核对**：每一条与运行时序不一致的地方都能在《序差表》里找到。

## 五、执行步骤

### 步骤 0：范围声明与清单收集

先声明这次审查的范围（哪些文档算在内、哪些算在范围外，例如非编号的 `plan.md`、
`todo.md`、`draft/` 目录如何处理），然后收集三份清单：

- 文档清单：编号、标题、行数、头部声明的前置与边界。
- C 源码清单：文件、对应的文档编号（先照映射表，再用检索核对）。
- 非 C 制品清单：第三部分第 3 类里的每一项，逐一记录实际找到的文件与位置。

范围要写进报告的元信息一节。末尾发现范围外的重要主题，单列"范围外发现"。

### 步骤 1：知识点穷举（逐篇文档）

对每一篇文档，列出一张"文档卡片"：

- 文档编号与标题；
- 一句话定位（这篇文档解决读者的什么问题）；
- 知识点清单，逐条包含：编号、名称、类型、证据锚点、读者收益、前置知识点；
- 这篇文档声明的前置与边界；
- 这篇文档实际越界讲了什么、缺了什么（与声明对照）。

知识点类型建议分为：概念、机制、数据结构、接口与协议、约束与不变量、架构演进、工具与
工程、测试性质。编号使用"文档编号-序号"，例如 `06-12`，全报告唯一，供多个 AI 的结果
互相对比。

要求：

- 讲过的都要列，不许挑重点列。
- 每条都要有锚点（C 源码用 `文件:符号`，Rust 用 `文件:符号`，文档用 `文件#小节`）。
- "读者收益"要写成一句话，说明读者学到它之后能回答什么问题；写不出的条目，说明它可能
  只是实现细节，要标注出来供后续判断。

### 步骤 2：覆盖审计（防遗漏、防重复）

1. 先建立**主题全集**，来源四路：
   - C 源码的符号（函数、结构体、宏、常量、状态机、错误路径、按架构分支的部分）；
   - 这些机制对应的操作系统通用概念（是机制本身，不依赖具体代码）；
   - 非 C 制品里承载的主题（第三部分第 3 类）；
   - 阶段边界契约里属于本 stage 的主题（阶段规划、跨阶段条目）。
2. 再与现有文档逐一对账，得到三张表：
   - **覆盖缺口表**：主题在全集里但没有任何一篇讲；每条给出建议（新增文档、并入某篇、
     判定属于其它 stage、或明确不做并给理由）。
   - **重复主题表**：同一主题在多篇重复展开；每条给出"保留哪一篇为主文档，其余改为引用"。
   - **越界主题表**：某篇讲了声明边界之外的主题；每条给出正确的归属文档。
3. 对每个 stage 必须显式回答的非 C 主题清单（回答"在哪里讲"或"为什么不在本 stage"）：
   链接与加载、镜像布局、汇编入口、装配与启动、构建与工具链、线格式与接口、
   错误路径、关闭与退出、并发与同步、测试基建。

### 步骤 3：依赖关系图

- 节点：步骤 1 的知识点（可以先聚合成概念组再画图，但聚合规则要说明）。
- 边：X 是 Y 的前置（不先懂 X 就无法懂 Y）；每条边给出证据或理由。
- 输出一张有向无环图（缩进列表或文本图均可），并标注：哪些组之间是强依赖、哪些只是
  建议阅读顺序、哪些可以互换。
- 如果发现环（互为基础），必须显式指出并给出打破方法（通常是拆出更小的基础概念）。

### 步骤 4：推荐讲述顺序

给出两个方案，都要写：

**方案 A（最小改动）**：保留现有文件编号，只调整每篇内部的主题取舍与章节顺序，另加一份
"建议阅读路径"（哪篇先读、哪篇可跳、并行主题的支线怎么走）。适合编号变更成本高的情况。

**方案 B（完全重排）**：给出新的编号顺序与篇章划分（含新增、拆分、合并、删除），并附
"重编号影响清单"：用检索统计每个被移动文档被引用的次数与位置（代码注释里的
`covered in NN`、其它文档的交叉引用、review 记录路径等）。

两个方案里，每一篇的推荐位置都要写"为什么在这里"，理由必须能对应第四部分的硬门槛或
软目标编号。还要写"为什么不选另一种排法"（至少给出你考虑过、但否决的两个备选顺序）。

### 步骤 5：序差表

逐条记录教学顺序与运行时序不一致的地方：

| 编号 | 运行时序事实（锚点） | 教学序位置 | 偏离原因 | 回指补偿 | 风险 |
|------|---------------------|-----------|---------|---------|------|

### 步骤 6：重复主题与被重复文档的去向

把步骤 2 的重复主题表展开成可执行建议：哪个文档降级为引用、哪个文档吸收内容、引用时
指向哪一小节。

### 步骤 7：自检门

逐条回答，不许跳过：

| 门 | 检查内容 |
|----|---------|
| G1 | 知识点穷举是否完整：每个 C 文件、每个非 C 制品，在报告里都有归属或"明确排除 + 理由" |
| G2 | 推荐顺序是否满足全部依赖边（随机抽十条验证并列出验证过程） |
| G3 | 前向引用扫描是否通过（随机抽十处交叉引用验证） |
| G4 | 每一条与运行时序的偏离是否都进了序差表 |
| G5 | 每个覆盖缺口是否都判定了归属并给出处置建议 |
| G6 | 事实断言是否都有锚点（随机抽十条核对；推测项是否已标注） |
| G7 | 读者走查是否执行（列出卡点清单） |

任何一门不通过，报告结论必须写成"未完成"，并列出还缺什么。

### 步骤 8：结论与待裁决问题

最后写一页以内的结论：现状顺序的最大三个问题、推荐方案、以及需要用户裁决的问题
（例如是否接受重编号、是否新增文档、是否把某主题登记为跨阶段条目）。

- 不写开发迭代史（"旧版怎样、后来改成怎样"）；写"如果不这样安排，读者会在哪里卡住，
  所以建议怎样安排"。
- 报告是给读者看的正式产出，不写过程痕迹（review 编号、修复日期、内部工具术语）。

## 八、按阶段类型的补充提示（选择与目标目录最接近的一类）

- **启动链型（例如内核、运行时、用户态初始进程）**：以启动时序为骨架，硬门槛优先；
  非启动路径的机制（调试、采样、WONTFIX）归入支线。
- **服务事件循环型（例如存储管理、进程管理、文件系统、注册服务、调度、信息库）**：
  建议按"服务为什么存在 → 诞生与初始化 → 消息接口 → 核心数据结构 → 按场景分组的
  请求处理 → 查询与杂项 → 与邻接服务的协议"组织；一次请求的生命周期通常比源码调用
  顺序更适合作主线。
- **库与框架型（例如文件系统框架库、网络框架库）**：先讲抽象层与接口契约，再讲框架
  骨架，最后按实现族展开；避免一上来就逐文件讲实现。
- **集合型（例如几十个驱动、大量命令）**：先总览与分类框架，再按设备族或命令族分组，
  组内给代表性顺序；必须给出阅读路径，避免平铺几十篇。

如果目标目录同时具备多种特征，说明你按哪一类处理以及为什么。
