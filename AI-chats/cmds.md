# 命令手册（cmds.md）

> 本文档汇集所有日常发给 AI（Claude Code / OpenCode / dsh / zcode 等）的指令，按**目的**分类组织。
>
> **来源**：[daily.todo.md](./daily.todo.md) 全文扫描抽取（行 22-487）。
>
> **使用约定**：
> - 每条命令有唯一 ID（`cmd-XX`），方便对话和文档互相引用
> - 标题后括号内为命令**形态**：`[单段]`（一段一段段落）/ `[多段]`（多个段落块）/ `[工作流]`（Step 0-5 类）
> - **muse 警告**：含 `> [!muse]` 标记的段落，是为 OpenCode 中的 muse 子模型专设的纠偏指令；其他模型可忽略
> - 命令正文保留 daily.todo.md 中的**原始段落**形态（你每次手动微调后整段粘贴）
> - 末尾 `[锚点]` 标注 daily.todo.md 源行号；`[关联]` 列出同主题其他命令
> - **去 stage 化**：命令表达"模式/目标"，不绑定具体 stage（如 02-stage-vm、03-stage-rs）。替换 `{STAGE_DIR}` 占位符即可应用到任意 stage
> - **去文档号化**：命令不绑定具体文档号（如"06 号文档"、"14 文档"）。所有具体文档号都用 `{DOC_NN}` 占位符

## 〇、决策树（模式导向卡片）

按**用户工作流时间线**组织 7 个阶段：从启动到收尾的全流程。每张卡片对应一个具体场景，按"场景描述 → 推荐命令 → 期望产出 → 配套使用"的格式。

**重要**：命令表达"模式/目标"，不绑定具体 stage 或文档号。决策时只问"我现在处于什么阶段、要做什么"，不问"我在哪个 stage、处理哪个文档号"。

### 工作流阶段总览

| 阶段 | 含义 | 何时使用 |
|---|---|---|
| **P0 准备** | 规划、搭骨架 | 接手新任务 / 准备开始一项工作 |
| **P1 启动** | 选定方向、开始干 | 知道要做什么但还没动手 |
| **P2 review** | 找错误/找问题 | 文档+代码完成后做质量检查 |
| **P3 修复** | 改代码/改文档 | 知道要改什么 |
| **P4 重构** | 提升设计质量 | 正确性已过，要卓越化 |
| **P5 收尾** | 补全+回归 | 主体工作完成，要做最后清理 |
| **P6 异常** | 跑偏时纠正 | AI 行为异常时强制约束 |

### P0 准备

#### 卡片 1：准备一个全新的任务 / 阶段
- **场景**：我要开始一项新工作（如新增一个 stage，或接手一个空目录）
- **触发条件**：目录里没有 plan.md，或现有 plan.md 已不适用
- **推荐命令**：**cmd-06**（重建 stage 的 plan.md）
- **期望产出**：新的 plan.md（含主线/次主线/拆分方案）+ 旧内容归档到 `draft/` + 最小化文档骨架
- **配套使用**：完成后用 cmd-12 按 plan.md 逐个生成文档

### P1 启动

#### 卡片 2：从 todo.md 选一个具体任务开始
- **场景**：todo.md 里有若干待办，我想开始干一项
- **触发条件**：已知要做什么（来自 todo.md / 用户指令）
- **推荐命令**：**cmd-08**（修一个 TODO，3 个变体）
  - 变体 A：实现 stage 内 stub/deferred
  - 变体 B：在某 stage 中随机选一个修
  - 变体 C：跨任务随机选 + 加载 4 个 review skill + 汇报进度
- **期望产出**：修复后的代码 + 文档 + todo.md 标注
- **配套使用**：修完后回 cmd-08 选下一个；或转 P2 review

#### 卡片 3：拿到一份 plan.md，要按它逐个生成文档
- **场景**：plan.md 已经规划好一组文档，要按它实现
- **触发条件**：plan.md 已存在且拆分方案明确
- **推荐命令**：**cmd-12**（按 plan.md 逐文档生成）
- **期望产出**：每个 little 文档（含完整正文 + Rust 实现 + 测试）+ 回归 review 报告
- **配套使用**：配合 cmd-11（先逐个 review 计划中的文档）效果更佳

### P2 review

#### 卡片 4：单文档+其代码做一次彻底检查
- **场景**：某个文档和其 Rust 实现需要质量检查
- **触发条件**：有 1 个具体文档要审
- **推荐命令**：**cmd-01**（单文档 + 关联 Rust 实现的 deep review）
- **期望产出**：P0/P1/P2 问题清单；若属于重写级则给出 outline.md
- **配套使用**：发现重写级问题后转 cmd-17 走完整重写流程

#### 卡片 5：单文档从零审视（不依赖历史中间结果）
- **场景**：文档改来改去不知对不对，想抛弃历史重新判断
- **触发条件**：文档或关联代码被反复修改，现状混乱
- **推荐命令**：**cmd-03**（单文档 deep review，从零）
- **期望产出**：基于权威源的 review-todo 列表，追加到 todo.md（`oc-review` 小标题）
- **配套使用**：与 cmd-01 互补——cmd-01 看现状，cmd-03 从零看

#### 卡片 6：一次审多个文档（区间/逐个）
- **场景**：有一组文档要批量审
- **触发条件**：文档数量 N 个，需统一处理
- **推荐命令**：
  - **cmd-02**（区间 review + 全修）—— 一次性全审全修，含 scan.md 标注
  - **cmd-11**（区间逐个 review）—— 每次一个 x.md，分多轮
  - **cmd-20**（区间四步收尾）—— /plan /goal 形式：找遗漏+找改进+补覆盖+回归
- **期望产出**：
  - cmd-02：全量问题清单 + 全部修复 + scan.md
  - cmd-11：每文档的 full-review 报告
  - cmd-20：补足的新文档 + 全部修复 + 收尾报告
- **选择指引**：
  - 想"一次到位" → cmd-02
  - 想"细致审" → cmd-11
  - 想"做 4 步收尾" → cmd-20

#### 卡片 7：审视整个 stage 的代码（架构级）
- **场景**：一个 stage 的所有代码，从架构层面看是否最优
- **触发条件**：要对一个 stage 做整体审视（不限定某文档）
- **推荐命令**：**cmd-04**（Stage 架构级审视 + 修复）
- **期望产出**：架构级改进建议（写入 stage 的 todo.md）+ 修复后的代码
- **配套使用**：可联网参考 Redox 实现；修复阶段可转 cmd-21 做设计清理

#### 卡片 8：执行 todo.md 中已规划好的某节决策
- **场景**：todo.md 里有 §X 已经写好要做的事，要按它执行
- **触发条件**：todo.md 已有 §X 子章节（待办/决策/计划）
- **推荐命令**：**cmd-05**（按 todo.md §X 决策执行）
- **期望产出**：跳过的项及原因 + 执行的项及验证结果
- **配套使用**：执行后更新 todo.md 标注

### P3 修复

#### 卡片 9：审计单文档的章节/文风/细节
- **场景**：单文档写完后，从读者视角看章节组织和文风
- **触发条件**：单文档内容已写，想提升教学性/可读性
- **推荐命令**：**cmd-10**（单文档审计：章节组织 + 开发文档味 + 细节深度）
- **期望产出**：三类审计结果（组织/文档味/细节深度），追加到 todo.md
- **配套使用**：审计通过后转 cmd-17 走重写流程

#### 卡片 10：单文档要重写，先列大纲
- **场景**：单文档要彻底重写，需先穷举知识点
- **触发条件**：单文档需要重写或大幅修改
- **推荐命令**：**cmd-17**（单文档：先列大纲 → 再写正文）
- **期望产出**：`{DOC_NN}-structure.md`（含全部知识点 + 章节组织 + 教学要点）
- **配套使用**：完成后走 cmd-19 完整工作流（含 review）

#### 卡片 11：单文档大纲由另一 AI 生成，需做质量审查
- **场景**：另一 AI 生成了 outline.md，要评估其质量
- **触发条件**：已收到 outline.md，但需独立判断是否可用
- **推荐命令**：**cmd-18**（单文档大纲 review：教学性/概念覆盖/组织合理性）
- **期望产出**：5 维度评估 + P0/P1/P2 清单 + 修改建议 + 是否批准进入写正文
- **配套使用**：批准后走 cmd-17 / cmd-19

#### 卡片 12：完整文档重写流程（Step 0-5）
- **场景**：已有初稿或 design doc，要做结构化重写或质量优化
- **触发条件**：需要走完整重写流程
- **推荐命令**：**cmd-19**（文档重写标准工作流 Step 0-5）
- **期望产出**：structure.md + outline.md + 重写后文档 + scan.md + VERIFY-CHECK.md
- **配套使用**：完整流程，**不准跳过不准压缩**

### P4 重构

#### 卡片 13：arch 重构后做设计级清理 + 死代码消除
- **场景**：架构层面已重构（cmd-04 之后），现在要扫尾
- **触发条件**：通过正确性 gate 后，要让代码达到 textbook + redox 级卓越
- **推荐命令**：**cmd-21**（设计级清理 + 死代码消除）
- **期望产出**：删除的死代码清单 + 设计对比表 + 同步更新的文档
- **配套使用**：与 cmd-04 配对——cmd-04 找问题，cmd-21 扫尾

#### 卡片 14：文件被改得面目全非，从零重生成
- **场景**：一个文件/文档被反复修改，逻辑已不连贯
- **触发条件**：现状不知道对不对，或多轮迭代后偏离原始设计
- **推荐命令**：**cmd-22**（从零重生成，避免历史干扰）
- **期望产出**：重写后的文件 + 与权威源的对应关系表
- **配套使用**：与 cmd-03 互补——cmd-03 审文档，cmd-22 审/重写任意文件

#### 卡片 15：阶段目录有 N 个文档要生成
- **场景**：一个阶段要批量生成 N 个文档 + 配套实现
- **触发条件**：阶段 plan.md 已规划好，文档尚未生成或需要重做
- **推荐命令**：**cmd-07**（生成 stage 内 N 个文档 + 实现 + 回归）
- **期望产出**：N 个文档 + Rust 实现 + 测试代码 + 回归 full-review 报告
- **配套使用**：可与 cmd-04（架构审视）配对

### P5 收尾

#### 卡片 16：按 plan.md 逐个实现文档
- **场景**：已审查过文档区间（cmd-11），现在按 plan 实现
- **触发条件**：plan.md 已就绪，要执行实现
- **推荐命令**：**cmd-12**（按 plan.md 逐文档生成）
- **期望产出**：每个文档 + 配套实现 + 测试 + 回归 review 报告
- **配套使用**：通常接在 cmd-11 之后

#### 卡片 17：测试代码质量专项审查
- **场景**：要审计测试本身的完备性/正确性/真实性
- **触发条件**：担心测试测不到真东西，或文档中的测试描述与代码不符
- **推荐命令**：**cmd-23**（测试专项审查：完备/正确/冗余/无效/虚构）
- **期望产出**：5 维度审查报告 + 文档-代码一致性矩阵
- **配套使用**：作为其他 review 类 cmd 的辅助审计

#### 卡片 18：阶段内 N 个文档+实现统一收尾
- **场景**：阶段内已有部分文档/实现，要补全+统一收尾
- **触发条件**：阶段工作进入收尾阶段
- **推荐命令**：**cmd-20**（文档区间四步收尾）
- **期望产出**：补足的新文档 + 全部修复 + 收尾 review 报告
- **配套使用**：与 cmd-15 配对做"硬性约束"——避免收尾时糊弄

### P6 异常

#### 卡片 19：目标模型是 muse，需强制约束文风
- **场景**：用 OpenCode 中的 muse 子模型，担心输出黑话/缩写/文言文
- **触发条件**：目标模型是 muse
- **推荐命令**：**cmd-14**（禁止缩写/黑话/文言文/压缩简写）
- **期望产出**：详细完整的文档和中间结果
- **配套使用**：作为前缀或后缀追加到其他 cmd

#### 卡片 20：AI 在循环中修修补补或糊弄
- **场景**：观察到 AI 把 TODO 改成 DEFERRED 充数，或越修越多问题
- **触发条件**：AI 行为出现糊弄迹象
- **推荐命令**：**cmd-15**（拒绝修修补补糊弄行为）
- **期望产出**：AI 真正修一个 TODO 而非"伪修复"
- **配套使用**：作为硬性提醒追加到其他 cmd

#### 卡片 21：讨论规则集本身或项目长期目标
- **场景**：要讨论 review 规则集的目标/优先级/术语
- **触发条件**：讨论"为什么用这套规则"或"优先级如何"
- **推荐命令**：**cmd-16**（正确性 + 卓越性双目标 + C 源码 ground truth）
- **期望产出**：对规则集本身的讨论/改进建议
- **配套使用**：作为前缀说明项目长期目标

## 一、文档级 cmd（作用于文档，含文档本身的 review/审计/重写/区间收尾/plan 重建）

### cmd-01 [单段] 单文档 + 关联 Rust 实现的深度全面 review

**摘要**：对单个文档及对应 Rust 代码做深度全面 review；若属于重写级（文档和实现质量均不佳），需彻底重写，并遵循 review 规范（含 outline 流程）。额外关注点：(a) 与前序文档衔接自然无跳步；(b) Rust 实现是否仅为 C 代码的 translate，是否有更好的 Rust 设计。

**占位符**：
- `{DOC_NN}` = 目标文档号（默认 14）
- `{DOC_RANGE_PREV}` = 前序文档区间（默认 01~13）

**命令正文**：

> 【上下文】
> 这是 Minix-RS 阶段文档重写工作流的一环。当前已存在前序文档（`{DOC_RANGE_PREV}`），现要处理目标文档 `{DOC_NN}` 及其关联的 Rust 实现。这是单文档级 review，不是全量扫描。
>
> 【任务】
> 1. 深度全面 review `{DOC_NN}` 文档和它关联的 Rust 实现。
> 2. 这个文档是**重写级**的 review 吗？
>    - 若是（即文档和关联的实现质量不佳，需要彻底重写），则进入重写流程；重写也必须遵守 review 规范，含 outline 流程
>    - 若否，则按标准 review 流程输出问题清单
> 3. 额外的两个 review 关注点：
>    - 衔接：`{DOC_NN}` 文档关注的内容和 `{DOC_RANGE_PREV}`，衔接是否自然，是否无跳步无遗漏？
>    - 设计：`{DOC_NN}` 的 Rust 实现，是否为 C 代码的 translate？是否有更好的 Rust 设计来改进？**谨防 translate！**
> 4. 若进入重写或修复：设计实现应思考多种方案，优中选优，最终选择最佳的 Rust 设计与实现。
>
> 【交付物】
> - review 问题清单（按 P0/P1/P2 分级）
> - 若属于重写级：先给出 outline.md，再写正文
> - 若属于修复级：列出每项改动 + 对应的 Rust 设计依据

**通用要求**（所有 cmd 适用）：
- 文风：技术博客风格，详细清晰透彻，避免说明书/开发文档味
- 代码：避免 translate，对比 Redox/OS/Rust 社区最佳实践，文档与代码同步修改
- 测试：完备且正确
- 流程：遵循 review 规范（含 outline、纵向链路检查、因果链验证）

**可定制点**：替换 `{DOC_NN}` 和 `{DOC_RANGE_PREV}` 为实际值；如要加特定关注点，在【任务】3 之后追加。

**[关联]** cmd-02（区间 review 同模板）、cmd-11（区间逐个 review）、cmd-20（区间收尾）
**[锚点]** daily.todo.md:23

### cmd-02 [单段] {DOC_RANGE_ALL} 文档及 Rust 实现的 review 并全量修复

**摘要**：检查指定范围内全部文档关联的 Rust 实现，对照 Redox 实现和 Rust 社区最佳实践找改进点；按 review 意见全部修复，文档同步更新，每修一项在 scan 文档中标注。

**占位符**：
- `{DOC_RANGE_ALL}` = 文档号区间（默认 01~14）

**命令正文**：

> 【上下文】
> Minix-RS 阶段文档的 Rust 实现已部分沉淀到 `{DOC_RANGE_ALL}` 区间。本次任务是该区间的全量 review + 全量修复，不是新增功能也不是单点修改。
>
> 【任务】
> 1. 检查 `{DOC_RANGE_ALL}` 文档关联和涉及的 Rust 实现。
> 2. 从 Rust 代码的角度出发，对照 Redox 的实现和 Rust 社区的最佳实践。找出：
>    - 任何可改进的点
>    - 任何可重构的设计
> 3. 按上述意见**全部修复**：
>    - 关联的文档也需要一并修复，以避免代码和文档不一致
>    - 修复时遵守 review 相关规范，以免引入新问题
>    - 修复一项，就在 scan 文档中标注一项
>

### cmd-23 [多段] 测试专项审查：完备性 + 正确性 + 真实性

**摘要**：对测试代码做专项审查，覆盖 5 个维度：(1) **完备性**——核心逻辑、边界条件、错误路径是否都有测试；(2) **测试自身正确性**——测试代码是否真在测被测对象，曾犯过"测试代码就是错的，啥都测不出来"的错；(3) **冗余测试**——重复测同一行为、互相覆盖；(4) **无效测试**——空测试、被 disable 的测试、永远 assert!(true) 的测试；(5) **虚构测试**——文档中声称存在但实际不存在的测试，或反之。本命令是其他 cmd 的辅助 cmd，配合其他 cmd 使用以做深度审计。

**占位符**：
- `{TARGET}` = 审查目标：`测试代码文件` / `文档中的测试描述` / `两者`
- `{TEST_FILES}` = 测试代码文件列表
- `{DOC_FILES}` = 相关文档文件列表
- `{STAGE_DIR}` = 阶段目录（用于关联 src 和 tests）

**命令正文**：

> 【上下文】
> 测试是正确性的另一支柱（与 C 源码 ground truth 互补）。但测试本身可能存在问题：
> - 测试代码本身就是错的（曾犯过，测试全过但其实啥都没测）
> - 文档描述的测试在代码中找不到（虚构测试）
> - 代码中有测试但文档不描述（文档缺失）
> - 测试之间互相覆盖或重复（冗余）
> - 大量空测试、skip、#[ignore]（无效）
> - 核心逻辑、错误路径、边界条件无测试（不完备）
>
> 【任务】按 5 个维度审查：
>
> 1. **完备性**（是否测了所有该测的）：
>    - 核心逻辑分支
>    - 边界条件（空、最大、最小、边界值）
>    - 错误路径（panic、Err 变体、错误码）
>    - 资源管理（init/cleanup、leak 防护）
>    - 并发场景（若适用）
>
> 2. **测试自身正确性**（测试代码是否真在测被测对象）：
>    - 断言是否对应被测行为
>    - mock/fixture 是否正确
>    - 是否存在"测试代码就是错的"——assert 永远 true、测试函数调用与描述不符
>    - **曾犯过此类错误，需特别警惕**
>

### cmd-16 [单段] 正确性 → 卓越性 双目标 + C 源码 ground truth

**摘要**：建立两层目标关系：**正确性**（catching errors）和**卓越性**（textbook + redox 级 Rust）。卓越性建立在正确性之上；二者非冲突而是嵌套。C 源码是 ground truth（正确性核心来源），确保核心语义对齐几乎能保证正确性。**Rust 重写后核心语义对齐，整个 OS 设计上不会出现大 bug；自由发挥反而会乱麻**。测试 = 正确性的另一支柱（防止生成代码中的幻觉），与语义对齐互补。

**命令正文**：

> 【上下文】
> Minix-RS 项目的目标体系由两层组成：当前规则集优化的是**正确性**（catching errors），但终极目标是**卓越性**（textbook + redox 级 Rust）。这两者是嵌套关系，不是替代关系。
>
> 【任务】
> 1. 明确两层目标：
>    - 正确性 = catching errors
>    - 卓越性 = textbook + redox 级 Rust
> 2. 关键约束：**卓越性建立在正确性之上**。如果没有正确性，卓越性也无从谈起。
> 3. **C 源码是 ground truth**：
>    - 这是正确性的核心来源
>    - 确保核心语义保持一致，几乎就能确保正确性
> 4. **当前阶段**：rewrite（保持外部可观察行为不变，内部用 Rust 类型系统重新表达）
> 5. 核心语义的对齐是 rewrite 容易成功的保证。
> 6. 测试 = 正确性的另一支柱（防止生成代码中的幻觉），与语义对齐互补。
>
> ## 核心术语定义
>
> | 术语 | 英文 | 定义 |
> |---|---|---|
> | **代码迁移** | Translate | 直接 1:1 翻译 C 代码到 Rust，保持代码结构、命名、逻辑完全一致。仅做语法转换，不做语义改变。 |
> | **语义重建** | Rewrite | 保持外部可观察行为不变，内部使用 Rust 类型系统重新表达。将隐式编码显式化（如 flag → enum、int → newtype）。 |
> | **系统重构** | Redesign | 改变系统架构、机制或协议。修改 IPC 协议、合并服务、改变调度策略等都属于此范畴。 |
>
> > 💡 Translate 是"翻译"，Rewrite 是"重写"，Redesign 是"重设计"
>
> 【交付物】
> - 对规则集本身的讨论 / 改进建议
> - 决策依据（哪个目标是当前瓶颈）
