# Review Rules 改进建议（Kimi 独立版）

> **来源任务**：分析 `03-kmain-cstart.md` 重构前后版本（`03-kmain-cstart-bak.md` 旧稿、`03-todo.md` 改进记录、`AI-chats/comments.md` GPT 评审），思考 prompt/review-rules 的可改进之处。
> **独立性声明**：本文件基于对上述文档的直接阅读独立完成，未参考 `prompt/review-improve-*.md` 中其他 AI 的输出。

---

## 1. 核心发现：当前规则在"概念层教学质量"上存在系统性缺口

`03-kmain-cstart-bak.md` 的旧稿问题不是简单的"引用错误"或"Rust 泄漏"，而是**叙事方向反了**：它从 `prot_init()` 源码出发总结概念，导致初学者读完后仍不知道"保护结构到底是什么"（comments.md L1-L1981 中反复强调）。新稿通过"CPU 视角三问"把 Ch1 从实现驱动改为概念驱动，这是质变。

但现有 review-rules 对这类问题只有间接约束（如 §3.5 教学性、§2.1 概念准确性），**缺少可直接执行的检查项**。以下建议旨在把这次重构中暴露的"概念层教学质量问题"固化为规则。

---

## 2. 对 `review-doc-checklist.md` 的改进建议

### 2.1 在 §2.1「概念准确性」增加「概念来源层级」子项

**问题**：旧稿 Ch1 把 `ProtectionArch` / `TrapEntryArch` 这两个 **Rust trait** 当作概念层术语引入（bak.md §1.5），混淆了"CPU/架构概念"与"Rust 实现抽象"。

**建议新增检查项**：

```markdown
### 2.1.x 概念来源层级检查

Ch1（概念章）的术语必须来自 CPU/操作系统/协议层，不得把实现层抽象（Rust trait、函数名、类型别名）当作概念定义。

**执行步骤**：
1. 提取 Ch1 所有加粗术语、关键名词。
2. 逐术语判定其来源层级：
   - L0 硬件/CPU 层：ring、EL、IDT、VBAR、stvec、TSS、sscratch
   - L1 OS 概念层：保护结构、特权级、异常入口、内核栈、信任边界
   - L2 实现抽象层：ProtectionArch、TrapEntryArch、`init_protection()`、`tss_init()`
3. Ch1 允许出现 L0/L1 术语；L2 术语在 Ch1 首次出现必须仅用于"预告"，且不能替代概念定义。

**判定**：
- Ch1 用 L2 术语作为概念定义 → P1（概念层级泄漏）
- Ch1 用 L2 术语且无 L0/L1 定义 → P0（概念地基缺失）
```

**依据**：bak.md §1.5 直接把 trait 表格放在 Ch1，违反 review-doc-checklist.md §1「第1/2章不得包含 Rust」的精神，但现有规则只检查"是否含 Rust 代码"，不检查"是否把 Rust 抽象当作概念"。

---

### 2.2 在 §3.5「教学性质量」增加「叙事驱动方向」子项

**问题**：旧稿 Ch1 是"实现驱动"——从 `prot_init()` 源码出发，努力总结概念；新稿是"概念驱动"——从 CPU 为什么需要保护出发，再落地到 `prot_init()`。

**建议新增检查项**：

```markdown
### 3.5.x 叙事驱动方向检查（Ch1 专项）

Ch1 必须采用「问题 → 概念 → 实现」的驱动方向，禁止采用「实现 → 总结概念」的反向叙事。

**退化信号**：
- [ ] Ch1 开篇即引用具体函数（如 `prot_init()`、`tss_init()`）并以其为骨架组织概念。
- [ ] Ch1 章节标题以函数/文件命名（如 "1.2 prot_init() 详解"）。
- [ ] Ch1 在解释"是什么"之前，先贴出源码片段或 Rust trait 定义。
- [ ] 读完 Ch1 后，读者能复述实现步骤，但无法回答"为什么需要这个机制"。

**推荐结构**（以 03 文档为例）：
1.1 WHY：什么是保护，为什么要保护
1.2 WHAT：特权级是什么（三架构对照）
1.3 HOW：跨特权级流程（统一抽象）
1.4 CPU 三问：prot_init 到底在填哪三个答案
1.5 三架构对照表
1.6 为什么不能用固件
1.7 x86 历史包袱 GDT

**判定**：
- 实现驱动叙事 → P1（必须重构 Ch1 结构）
- 导致 Ch1 含 Rust / 函数细节 → 同时触发 §1 结构违规，按 P0 处理
```

**依据**：comments.md 中 GPT 反复强调"从 prot_init() 出发解释概念，方向反了"，并给出重构后大纲（comments.md 多处）。03-todo.md 也把"Ch1 驱动方向：概念驱动"列为首个已确认决策。

---

### 2.3 在 §3.5「教学性质量」增加「章节边界声明」子项

**问题**：旧稿没有告诉读者"本章讲到什么程度、不讲什么"，读者会一直想知道 IDT Gate 格式、TSS 结构体长什么样，偏离主线。

**建议新增检查项**：

```markdown
### 3.5.y 章节边界声明检查

Ch1 必须在早期（1.0 引言或 1.1 之前）显式声明「本章不讲什么」，帮助读者建立正确预期。

**检查项**：
- [ ] 是否有"本章不讲什么"或"本章边界"段落/引用块？
- [ ] 列出的延后内容是否确实在后续文档中覆盖？
- [ ] 延后内容是否不是本章核心概念所必需的？（不能把地基内容也延后）

**判定**：
- 无边界声明 → P2（读者体验问题）
- 边界声明把核心概念也延后 → P1（叙事骨架缺失）
```

**依据**：03-todo.md 明确把"1.0 末尾加框：本章不讲什么"列为已确认决策，并给出具体内容。

---

### 2.4 在 §3.5「教学性质量」增加「跨架构共性抽象」子项

**问题**：旧稿 Ch1 虽然提到 IDT/VBAR/stvec，但没有把它们统一抽象为"异常入口"这一共性概念，读者难以建立"三架构其实是一回事"的心智模型。

**建议新增检查项**：

```markdown
### 3.5.z 跨架构共性抽象检查

对于涉及多架构（x86/aarch64/riscv64）的文档，Ch1 必须先用一个统一的抽象层概括三架构共性，再展开各架构差异。

**退化信号**：
- [ ] 直接罗列各架构专有名词，无统一抽象术语。
- [ ] 表格只有"x86 / ARM / RISC-V"三列，没有"共同概念"列。
- [ ] 读者读完后能背出各架构名词，但说不出它们回答的共同问题。

**推荐表达**：
```text
CPU 三问
├── 当前什么特权级？   → ring/EL/mode
├── 异常跳到哪里？     → IDT / VBAR_EL1 / stvec
└── 陷入内核用哪个栈？ → TSS.sp0 / SP_EL1 / sscratch
```

**判定**：
- 无统一抽象层 → P1（教学性不足）
- 把架构差异放在共性之前讲 → P2（顺序可优化）
```

**依据**：comments.md 指出"真正的架构抽象应该是 CPU保护机制 → 特权级/切换/异常入口/内存权限，再映射到三架构"；03-todo.md 把"三架构统一对照表"和"CPU 视角三问"作为核心框架。

---

### 2.5 在 §3.5「教学性质量」增加「双向机制叙事闭环」子项

**问题**：旧稿只讲"用户态 → 内核态"，没讲"内核态 → 用户态"返回。保护结构是双向门，只讲一半会导致读者误以为保护结构只是"进入内核的机制"。

**建议新增检查项**：

```markdown
### 3.5.w 双向机制叙事闭环检查

对于保护结构、系统调用、异常处理等涉及"进入+返回"双向转移的机制，Ch1 必须同时建立"进入"和"返回"的心智模型。

**检查项**：
- [ ] 是否明确指出保护结构是双向门（进入 + 返回）？
- [ ] 是否给出返回指令/返回路径的对照（如 iretq/eret/sret）？
- [ ] 返回部分是否仅建立概念模型、不展开实现细节？

**判定**：
- 只讲进入不讲返回 → P1（叙事闭环缺失）
```

**依据**：comments.md 第四轮评审把"加内核→用户返回闭环"列为"最有价值的改进"之一；03-todo.md 也明确加入返回闭环。

---

### 2.6 在 §3.1「文本流畅性」增加「章内概念重复」检查

**问题**：旧稿 1.2 和 1.4a 都讲了"页表权限位/访问控制"，只是角度不同，造成重复。

**建议新增检查项**：

```markdown
### 3.1.x 章内概念重复检查

同一概念在同一章节内重复讲解超过 2 次时，必须检查是否必要。若重复内容可在另一处统一讲清，应合并或改为引用。

**执行步骤**：
1. 提取各小节主题句。
2. 检查不同小节是否用不同措辞讲解同一机制。
3. 判定重复是否服务于不同抽象层次（如 1.2 讲定义、1.4 讲落地）——若是，应显式说明层次差异。

**判定**：
- 同层次重复且无显式层次分工 → P2（建议合并）
- 重复导致读者困惑"我刚看过这个" → P1（需要重写）
```

**依据**：comments.md 第二轮第一点明确指出"1.2 和 1.4a 有内容重叠"，并建议 1.2 只讲特权级、1.4a 再讲特权级如何落实到内存保护。

## 3. 对 `review-patterns.md` 的改进建议

新增以下 5 个文档错误模式，与已有 15 个模式编号衔接。

### 模式 16：实现驱动叙事（Implementation-first narrative）

```markdown
### 模式16：实现驱动叙事

❌ 错误：
## 1. 概念：保护结构
### 1.1 prot_init() 入口
`prot_init()` 初始化 GDT、IDT、TSS...
### 1.2 从 prot_init 总结出的概念
保护结构包括异常入口、特权级、内核栈...

✅ 正确：
## 1. 概念：保护结构
### 1.1 什么是保护？
### 1.2 CPU 需要什么才能保护内核？
### 1.3 这些需求如何映射到 prot_init()

判定：Ch1 以函数/源码为骨架 → P1；导致 Ch1 含 Rust → P0
```

---

### 模式 17：视角漂移（Perspective drift）

```markdown
### 模式17：视角漂移

❌ 错误：
> "CPU 发现异常 → 查向量表 → 找到 handler"
> "保护结构负责用户态可访问的内存范围"

问题：前一句是 CPU 视角，后一句变成 OS 资源视角。混用视角会让读者困惑。

✅ 正确：
统一采用 CPU 视角：
> "CPU 发现异常 → 查向量表 → 跳 handler"
> "CPU 在当前特权级下发起访问 → 页表权限位决定是否允许"

判定：同一章节内视角不统一 → P2；导致核心框架模糊 → P1
```

**依据**：comments.md 第三轮指出"1.4 三问其实还是有一点 OS 视角"，建议把第一问从"能访问哪些内存"改为"当前执行者是谁"。

---

### 模式 18：单向门叙事（One-way narrative）

```markdown
### 模式18：单向门叙事

❌ 错误：
只讲用户态 → 异常 → 内核态，不讲返回。

✅ 正确：
用户态 → 异常/syscall → 内核态 → 返回指令 → 用户态
并给出返回指令对照表（iretq/eret/sret）。

判定：涉及双向转移的机制只讲进入 → P1
```

---

### 模式 19：跨架构共性未提取（Missing cross-arch abstraction）

```markdown
### 模式19：跨架构共性未提取

❌ 错误：
| x86 | ARM | RISC-V |
| IDT | VBAR_EL1 | stvec |

只列名词，没有共同问题。

✅ 正确：
| CPU 问题 | x86 | ARM | RISC-V |
| 异常入口 | IDT | VBAR_EL1 | stvec |

先抽象问题，再填架构答案。

判定：多架构文档无统一抽象层 → P1
```

---

### 模式 20：章内概念重复（Intra-chapter redundancy）

```markdown
### 模式20：章内概念重复

❌ 错误：
1.2 讲"特权级 → 页表权限位 → 访问控制"
1.4a 又讲"用户态可访问范围 → 页表权限位 → 访问控制"

✅ 正确：
1.2 只讲"特权级是什么"
1.4a 讲"特权级如何落实到内存保护"
层次分工明确。

判定：同层次重复 → P2；重复造成困惑 → P1
```

## 4. 对 `review-doc-excellence.md` 的改进建议

### 4.1 在 §4.1「叙事结构卓越性」增加「概念骨架可见性」

```markdown
### 2.1.x 概念骨架可见性

Ch1 必须让读者在 30 秒内识别出本章的核心概念骨架（如"CPU 三问"）。

检查项：
- [ ] 是否有显式的核心框架/问题列表/三问？
- [ ] 章末小结是否用同一框架收束？
- [ ] 后续章节（Ch2-Ch4）是否引用该框架？

判定：无可见概念骨架 → 卓越性 P1
```

**依据**：03-todo.md 新增 1.10「本章小结」用三问框架收束，并计划在 Ch3 加 CPU 问题→Trait 映射表。

---

### 4.2 在 §4.3「教学深度卓越性」增加「抽象层次一致性」

```markdown
### 4.1.y 抽象层次一致性

流程图、表格、代码引用必须在同一抽象层次上，避免低层细节破坏高层统一性。

反例：
- 流程图写"CPU 自动切栈"，但 RISC-V 是软件切栈。
- 流程图写"保存现场"，但三架构保存现场方式不同。

正例：
- "切换到可信内核栈（x86/aarch64 硬件自动；riscv64 软件交换）"
- "保存现场（由硬件、软件或两者协作完成）"

判定：抽象层次不一致 → 卓越性 P1
```

**依据**：comments.md 第三轮指出"1.3 流程图有一个隐藏问题"——对 x86 成立、对 riscv 不成立；03-todo.md 明确修正流程图用统一抽象层。

## 5. 对 `review-process.md` 的改进建议

### 5.1 在 Step 3「Sanity Check」增加 Ch1 叙事方向快速扫描

```markdown
### Step 3.x Ch1 叙事方向快速扫描

在 Step 3 的一致性检查中，对 Ch1 额外执行：
1. 提取 Ch1 前三个小节标题和首段主题句。
2. 判定是否以 WHY/WHAT 开头，还是以函数/源码开头。
3. 若发现实现驱动叙事，标记 P1 并建议重构。

执行命令：
```bash
rg "^## 1\." {doc} -A 3
rg "prot_init\|tss_init\|idt_init" {doc} -n | head -20
```
```

---

### 5.2 在 Step 4「Cross-Document Check」增加跨架构抽象检查

```markdown
### Step 4.x 跨架构抽象检查

若文档涉及 x86/aarch64/riscv64 多架构：
1. 检查 Ch1 是否先给出统一抽象术语（如"异常入口"、"内核栈切换"）。
2. 检查是否把架构差异作为"答案"而非"问题"呈现。
3. 检查对照表是否有"共同问题/概念"列。

输出：
| 抽象概念 | x86 载体 | aarch64 载体 | riscv64 载体 | 文档位置 |
|---------|---------|-------------|-------------|---------|
| 异常入口 | IDT | VBAR_EL1 | stvec | §1.4b |
```
