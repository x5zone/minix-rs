# review-rules 改进建议（Qwen 独立分析）

> **分析依据**：阅读 03-todo.md（改进 TODO）、03-kmain-cstart.md（新文档）、03-kmain-cstart-bak.md（旧文档）、comments.md（GPT 四轮评审），对比 review-rules 现有规则，识别改进空间。
> **核心发现**：review-rules 在"正确性"维度已经很强，但在"概念教学性"维度存在系统性缺口。GPT 评审中揭示的多个关键问题（概念驱动 vs 实现驱动、跨架构统一抽象、心智模型完整性），在现有规则中要么缺失、要么 buried 在低优先级检查项中。

---

## 一、核心发现：review-rules 的结构性盲区

### 1.1 最大盲区：缺少"概念驱动 vs 实现驱动"检查

GPT 评审中最核心的判断是：

> 旧 Ch1 从 `prot_init()` 源码出发总结概念（实现驱动），方向反了。应该从 CPU 为什么需要这些东西出发解释 prot_init()（概念驱动）。

现有 review-rules **没有任何检查项**能捕获这个问题。

- §3.5 教学性质量检查的是"有没有引导语""有没有注释"，不检查"概念引入顺序"。
- §4.1 叙事弧检查的是"问题→分析→决策→实现"的章节级弧线，不检查单个概念的引入方式。
- §2.1 概念准确性检查的是"概念是否与源码一致"，不检查"概念是否以正确顺序引入"。

**结果**：一篇"每一句话都正确、但教学方向完全反了"的文档，可以通过现有全部检查。

### 1.2 第二个盲区：缺少"跨架构统一抽象"检查

GPT 评审中反复强调：

> 真正的架构抽象应该是：CPU保护机制 → 特权级 / 特权级切换 / 异常入口 / 内存访问权限。然后再映射到三架构。

> 目前文档一上来就 `trait ProtectionArch` / `trait TrapEntryArch`，这是代码抽象，不是架构抽象。

现有 review-rules 有"硬件抽象为 trait"的检查（模式14），但没有"概念层跨架构统一抽象"的检查。对于 Ch1 这种概念章节，读者需要的是"三架构其实是一回事"的统一心智模型，而不是代码层的 trait 拆分。

### 1.3 第三个盲区：缺少"心智模型完整性"检查

GPT 评审中发现：

> 保护结构不是单向门，而是双向门（用户→内核 + 内核→用户）。旧文档只讲了"进入内核"，没讲"返回用户态"。

这种"只讲一个方向、遗漏另一个方向"的问题，在现有规则中没有对应检查项。§2.8 检查 C 源码覆盖完整性（函数/结构体/宏是否遗漏），但不检查"概念模型的对称性/完整性"。

## 二、具体改进建议

### 改进 1：新增 §2.12 "概念驱动检查"（review-doc-checklist.md）

**优先级**：P0（结构性缺口）

**新增内容**：

```markdown
### 2.12 概念驱动检查（强制，不可跳过）

> **核心原则**：Ch1（概述/概念章）必须从"为什么需要"出发引入概念，而非从"实现代码怎么写的"出发总结概念。
> 判定标准：如果去掉所有代码引用后，概念讲解仍然成立且有条理，则是概念驱动；如果去掉代码引用后概念讲解崩塌，则是实现驱动。

**执行步骤**：

**Step 2.12.1：概念引入顺序检查**
对 Ch1 中每个核心概念，检查引入顺序：
1. 是否先解释了"为什么需要这个概念"？（WHY）
2. 然后才解释"这个概念是什么"？（WHAT）
3. 最后才展示"代码中如何实现"？（HOW）

如果顺序是 HOW→WHAT→WHY 或 HOW→WHY→WHAT，标记为 P0（实现驱动）。

**Step 2.12.2：代码依赖度检查**
对 Ch1 中每个概念讲解段落，检查：
- 如果删除所有代码片段和代码引用，这段讲解是否仍然自洽？
- 如果删除后不自洽 → 概念讲解依赖代码，是"实现驱动"的信号

**Step 2.12.3：读者先验知识检查**
- Ch1 是否在引入术语前假设读者已经知道这些术语？
- 例如：直接使用 Ring0/Ring3/EL0/EL1/S-mode/U-mode 而不解释"什么是特权级"
- 如果假设过多 → P1

**必须输出以下表格**（不可省略）：
| 概念 | 引入位置 | WHY→WHAT→HOW 顺序? | 删除代码后自洽? | 先验知识假设合理? | 判定 |
|------|---------|-------------------|--------------|----------------|------|
| 保护 | §1.1 | ✅ WHY→WHAT→HOW | ✅ 自洽 | ✅ 无假设 | OK |
| 特权级 | §1.2 | ❌ 直接 WHAT | ⚠️ 部分自洽 | ❌ 假设已知 Ring/EL | P1 |
| ... | ... | ... | ... | ... | ... |

**判定标准**：
- Ch1 核心概念以 HOW 开头（先展示代码再解释概念）→ P0
- Ch1 核心概念无 WHY 直接 WHAT → P1
- Ch1 假设读者已知核心术语（特权级、异常、系统调用）→ P1
```

**理由**：这是 GPT 评审中识别的最大问题，现有规则完全无法捕获。03-todo.md 的核心重构方向（"从实现驱动改成概念驱动"）正是因为缺少这个检查才导致的。

### 改进 2：新增 §2.13 "跨架构统一抽象检查"（review-doc-checklist.md）

**优先级**：P1（对多架构文档重要）

**新增内容**：

```markdown
### 2.13 跨架构统一抽象检查（多架构文档适用）

> **核心原则**：当文档覆盖多个硬件架构（如 x86/ARM/RISC-V）时，必须先建立跨架构的统一概念模型，再分架构展示实现差异。
> 反模式：一上来就分架构讲解，读者看完不知道"三架构其实是一回事"。

**适用条件**：文档涉及 ≥2 个硬件架构的实现。

**执行步骤**：

**Step 2.13.1：统一抽象检查**
- 文档是否在分架构讲解前，先建立了跨架构的统一概念框架？
- 例如：先讲"CPU 需要回答三个问题"，再讲"三架构分别如何回答"
- 如果直接分架构 → P1

**Step 2.13.2：对照表检查**
- 文档是否提供了跨架构对照表，让读者看到"三架构一回事"？
- 对照表是否以"概念问题"为行（而非"实现机制"为行）？
- 如果对照表以实现机制为行 → P2（应改为概念问题为行）

**Step 2.13.3：代码抽象 vs 架构抽象检查**
- Ch1 是否使用代码层抽象（如 trait 名）代替架构层抽象？
- 如果 Ch1 出现 trait 名/代码结构名作为核心组织框架 → P1
- Ch1 应使用概念框架（如"CPU 三问"），Ch3 才引入代码框架（如 trait 拆分）

**必须输出**：
| 检查项 | 状态 | 问题 |
|--------|------|------|
| 统一抽象框架 | ✅/❌ | |
| 跨架构对照表 | ✅/❌ | |
| 概念抽象 vs 代码抽象 | ✅/❌ | |

**判定标准**：
- 多架构文档无统一抽象框架 → P1
- Ch1 使用代码抽象（trait/struct 名）作为核心框架 → P1
- 无跨架构对照表 → P2
```

**理由**：GPT 评审反复强调"缺少真正的统一抽象""代码抽象不是架构抽象"。03-todo.md 最终新增了 §1.5 三架构对照表来解决这个问题。这个检查项确保未来文档不会重蹈覆辙。

### 改进 3：新增 §2.14 "心智模型完整性检查"（review-doc-checklist.md）

**优先级**：P1

**新增内容**：

```markdown
### 2.14 心智模型完整性检查（强制，不可跳过）

> **核心原则**：概念章节必须建立完整的心智模型。如果机制是双向的（如进入内核+返回用户态），文档必须覆盖两个方向。
> 反模式：只讲一个方向，读者形成不完整的心智模型。

**执行步骤**：

**Step 2.14.1：对称性检查**
对 Ch1 中每个核心机制，检查是否存在"对称的另一半"：
- 进入内核 → 返回用户态？
- 分配 → 释放？
- 注册 → 注销？
- 建立 → 销毁？

如果文档只讲了一半 → P1

**Step 2.14.2：边界声明检查**
- Ch1 是否有"本章不讲什么"的显式声明？
- 声明是否列出了被延后到后续章节的概念？
- 如果没有 → P2

**必须输出**：
| 机制 | 方向1 | 方向2 | 覆盖完整? |
|------|-------|-------|----------|
| 特权级切换 | 用户→内核 ✅ | 内核→用户 ✅/❌ | |
| 异常向量 | 注册 ✅ | 查询 ✅/❌ | |
| ... | ... | ... | |

**判定标准**：
- 核心机制只讲一个方向 → P1
- Ch1 无"本章不讲什么"声明 → P2
```

**理由**：GPT 评审指出旧文档"缺一个非常重要的东西：内核→用户的返回闭环"。这种遗漏不是"事实错误"（§2.1 查不出），也不是"覆盖不足"（§2.8 查不出，因为没有对应的 C 函数遗漏），而是"心智模型不完整"。现有规则没有维度能捕获这类问题。

### 改进 4：强化 §3.5 教学性质量（review-doc-checklist.md）

**优先级**：P1

**现状**：§3.5 已经有"教学性质量"检查，但存在三个问题：
1. 判定标准偏低（P1/P2），对 Ch1 概念驱动这种根本性问题约束力不够
2. 缺少"WHY 优先"的显式检查
3. 缺少"概念引入顺序"的检查

**建议修改**：

在 §3.5 开头增加：

```markdown
> **Ch1 特别规则**：Ch1 的教学性问题是 P1 级别（不是 P2）。Ch1 是读者建立心智模型的关键章节，教学性缺陷会导致后续所有章节的理解成本增加。

**Ch1 专项检查**：
- [ ] 每个概念引入时是否先解释 WHY（为什么需要），再解释 WHAT（是什么）？
- [ ] 是否存在"先展示代码再解释概念"的实现驱动模式？→ P1
- [ ] 是否有"CPU 视角"或"系统视角"的统一框架，而非罗列术语？
- [ ] 是否在引入术语前假设读者已知？（如直接用 Ring0 不解释）→ P1
```

**理由**：GPT 评审给旧 Ch1 打 6/10，新 TODO 打 9/10，差距主要在教学性。现有 §3.5 的判定标准（"代码块超过 15 行无注释 → P1"）太关注表面形式，不关注概念引入方式。

### 改进 5：新增"概念正交性检查"到 §3.3 冗余控制

**优先级**：P2

**建议增加**：

```markdown
### 概念正交性检查

> **核心原则**：如果两个章节讲解的概念存在包含关系（A 是 B 的特殊情况/后果），不应作为并列概念分别讲解。

**检查项**：
- [ ] 是否存在"概念 A 和概念 B 并列讲解，但 A 实际上是 B 的后果/特殊情况"？
  - 例：特权级 和 页表权限位 并列讲解，但页表权限位是特权级的落地手段
  - 如果发现 → P2（应调整为层次关系：先讲 B，再讲 A 作为 B 的后果）
- [ ] 是否存在"两个问题看似独立，实际是同一个问题的两个方面"？
  - 例："异常跳哪"和"用哪个栈"看似两个问题，实际都是"如何安全进入内核"
  - 如果发现 → P2（可考虑合并或显式说明关系）
```

**理由**：GPT 评审指出"1.2 和 1.4a 有内容重叠"（特权级和页表权限位被讲了两次），以及"三问其实是两问半"。这类问题不是简单的"冗余"（§3.3 当前只检查文字重复），而是"概念层次不清"导致的结构性重复。

```markdown
### 概念抽象原则

**核心原则：概念章节（Ch1）必须从架构视角组织，而非从代码视角组织。**

| 维度 | ❌ 代码视角 | ✅ 架构视角 |

**Review 检查点**：
- ❌ Ch1 以 trait/函数/结构体名作为核心组织框架 → 应改为概念框架
- ❌ Ch1 先展示代码再解释概念 → 应先解释 WHY
- ❌ Ch1 分架构讲解而不建立统一抽象 → 应先建立统一框架
- ✅ Ch1 从 CPU/系统视角组织概念
- ✅ Ch1 先 WHY 再 WHAT 再 HOW
- ✅ Ch1 先统一抽象再分架构实现

**与硬件抽象原则的关系**：
- 硬件抽象原则约束代码层（trait 抽象机制而非描述硬件）
- 概念抽象原则约束文档层（概念框架而非代码框架）
- 两者互补：概念层用架构视角，代码层用 trait 抽象
```

## 四、额外观察

### 4.1 review-rules 的"正确性偏好"

现有 review-rules 在正确性维度已经非常强：
- §2.0 Claims-Evidence Tracing（论文级）
- §2.1 概念准确性（逐概念溯源）
- §2.2 C 代码引用验证（逐引用核对）
- §2.8 C 源码覆盖完整性（机器穷举 + AI 判断）
- Gate D P0 必检清单（5 项机械化检查）

但 GPT 评审揭示的最大问题不是正确性，而是**教学方向**。旧 Ch1 的每个事实陈述都是正确的，但组织方式（实现驱动）导致教学效果差。这说明 review-rules 需要一个独立的"教学性"维度，而不是把教学性作为正确性的附属。

### 4.2 "多 AI bagging" 视角下的独特贡献

本次分析独立于 GPT 评审，聚焦于 review-rules 本身的结构性缺口。GPT 聚焦于"这篇文档怎么改"，本分析聚焦于"规则集怎么改才能在未来自动捕获这类问题"。两者的互补性在于：
- GPT 提供了具体的教学洞察（CPU 三问、统一抽象、返回闭环）
- 本分析将这些洞察转化为可执行的检查项（§2.12/§2.13/§2.14/模式 46-48）

### 4.3 实施建议

1. **第一批（P0）**：改进 1（§2.12 概念驱动检查）。这是最大的结构性缺口，应立即加入。
2. **第二批（P1）**：改进 2-4, 6-7, 9-10。这些改进相互独立，可并行实施。
3. **第三批（P2）**：改进 5, 8。这些是精细化改进，可在前两批稳定后加入。

### 4.4 对 Agent Prompt 的影响

新增的检查项会增加 review-doc-skill 的体积。当前 review-doc-skill 为 8,908 字符。建议：
- §2.12（概念驱动检查）必须加入 skill（P0 级）
- §2.13/§2.14 可加入 skill 或保留在 checklist 中按需加载
- 模式 46-48 加入 review-patterns-skill（当前 13,269 字符，需注意 skill 体积）
