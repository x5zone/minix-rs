## 0. 核心诊断（合成）

现有 `prompt/review-rules/` 是一套**"以 claim 校验为中心的正确性验证机"**——grep 源码、验证 claim、检查覆盖率、Gate A-E 把关实现层完整性。但 03 案例暴露的失败模式中，**有一半不是事实层错误，而是心智层/叙事层错误**：

| 失败类型 | 案例 | 现有规则能否捕获 |
|---------|------|----------------|
| 因果链编造（P0） | `local_cbi` "栈帧被覆盖"解释 | ❌ §2.0 只验单点 claim，不验 claim 间因果 |
| 实现驱动伪装概念驱动 | Ch1 从 `prot_init()` 出发总结概念 | ❌ §3.5 是软判断 |
| 作者元注释泄漏 | "本节只回答…避免重复" 等 13+ 处 | ❌ §2.11 只管进度标记 |
| 架构范围隐含 | "段寄存器依赖 GDT" 未标注 x86 特有 | ❌ 模式 4 只管 32/64 位字段差异 |
| 单向心智模型 | 只讲 user→kernel，不讲返回 | ❌ §2.8 只查 C 函数遗漏 |
| 缺跨架构统一抽象 | 直接堆 GDT/VBAR/stvec 无共性 | ❌ 无对应检查 |

**根本结论**：规则集需要从"校验事实"扩展到"暴露作者心智 + 验证读者心智模型"。本次改进围绕三个层次展开：
1. **事实层**（已有，强化）：因果链验证
2. **叙事层**（新增，统一为 structure.md 产物）：概念驱动、统一抽象、双向闭环、架构范围
3. **心智层**（新增，统一为 structure.md 产物）：作者意图透明性、读者模拟、文档设计哲学

> **关键创新**：用户提议的 `structure.md` 产物把叙事层和心智层的分散检查统一为一个结构化输出（§5），先评审骨架再验证细节，避免 reviewer"逐项打勾"而不做整体判断。

## 1. review.md 改进（核心原则层）

### 1.1 新增"概念抽象原则"（与"硬件抽象原则"互补）`[来源: Qwen]`

在现有"硬件抽象原则"之后增加：

```markdown
### 概念抽象原则

**核心原则：概念章节（Ch1）必须从架构视角组织，而非从代码视角组织。**

| 维度 | ❌ 代码视角 | ✅ 架构视角 |
|------|-----------|-----------|
| 组织框架 | trait 名 / 函数名 / 结构体名 | CPU 需要回答的问题 / 系统机制 |
| 引入顺序 | 先展示代码，再总结概念 | 先解释 WHY，再展示 WHAT |
| 跨架构 | 分架构讲解实现差异 | 先建立统一抽象，再分架构展示 |
| 读者收获 | "代码做了这些事" | "为什么需要这些机制" |

- 硬件抽象原则约束代码层（trait 抽象机制而非描述硬件）
- 概念抽象原则约束文档层（概念框架而非代码框架）
- 两者互补：概念层用架构视角，代码层用 trait 抽象
```

### 1.2 新增"规则演化机制" `[来源: M3]`

```markdown
### 规则演化机制（Rule Evolution）

规则集本身不是真理，是"在 Minix-RS Review 历史中反复出现的失败模式的归纳"。

演化步骤：
1. 触发：用户/AI 在 review 中发现 ≥2 次同类新模式
2. 提案：AI 生成新模式提案（含案例、判定、归类）
3. 评审：用户确认是否纳入
4. 落地：写入对应 rules 文件，附"来源：xxx 案例"
5. 验证：下一轮 review 验证新规则是否生效
```

### 2.2 §2.0 Claims-Evidence：新增"解释因果链验证" `[来源: GLM(主) + M3]`

在 Step 2.0.2 后新增 **Step 2.0.3：解释因果链验证（强制，P0）**：

```markdown
> 核心原则：claim 有 evidence 不够，解释 claim 的 BECAUSE 部分必须技术上正确。
> "因为 X 所以 Y" 中的 X 必须是真实机制，不是听起来合理的编造。

对每个带因果解释的 claim（含"因为/所以/由于/为了"的断言）：
1. 提取因果链：claim + 因为 M1 所以 M2
2. 验证 M1 是否是真实机制（用 C 语言语义/ISA 规范/源码逻辑推断，非"听起来对"）
3. 若 M1 无法直接验证，必须标注"推测，待验证"

判定：
- 因果链机制技术上错误 → P0（解释编造，即使 claim 本身正确）
- 因果链含未验证环节且未标注 → P1
- 因果链可由 C 语义/ISA 规范直接验证 → ✅
```

**典型反例**（03 案例）：claim "memcpy(&kinfo, local_cbi, ...) 是必要的" ✅；编造解释"调用链推进后栈帧被覆盖" ❌（C 语义上 kmain 没返回前栈帧一直在）；正确解释"local_cbi 作用域限于 kmain 调用链，非 kmain 链代码访问不到" ✅。

> **与模式 34 的边界**：模式 34 是"代码注释的理由虚假"，本规则是"文档正文的因果链编造"。两者不重叠。

### 2.3 §2.1 概念准确性：新增三项 `[来源: GLM + M3 + Seed + Kimi]`

**Step 2.1.5：架构范围标注验证**（多架构文档强制）`[来源: GLM(主) + M3 + DS]`
- 叙述中出现 x86 特有机制（GDT/段描述符/TSS/IDT 门/CPL）→ 必须标注"x86 特有"
- aarch64 特有（EL/SP_EL/VBAR/PSTATE）、riscv64 特有（S/U-mode/sscratch/stvec/SPP）同理
- 未标注 → P1；ISA 寄存器角色描述错误（如 RISC-V SPP 当作"当前特权级"）→ P0
- 标注格式：`> 架构范围：x86-64` / `> 架构范围：三架构共性` / 行内 `(x86-64 特有)` `[来源: M3]`

**Step 2.1.6：过度简化检查（"A 就是 B" 反读法）** `[来源: Seed]`
- 对每处"A 就是 B / A 等于 B / A 即 B"定义性表述，反读"反过来 B 就是 A"是否成立
- 不成立 → 过度简化。涉及核心术语首次定义 → P1；其他 → P2
- 例："GDT 就是保护结构"反读"保护结构就是 GDT"不成立 → 应修正

**Step 2.1.7：概念来源层级检查** `[来源: Kimi]`
- Ch1 术语来源分层：L0 硬件/CPU 层（ring/EL/IDT/VBAR）、L1 OS 概念层（保护/特权级/异常入口）、L2 实现抽象层（ProtectionArch trait/函数名）
- Ch1 用 L2 术语作为概念定义 → P1（概念层级泄漏）；Ch1 用 L2 且无 L0/L1 定义 → P0

### 2.4 §3.1 文本流畅性：新增"开篇第一句"检查 `[来源: DS]`

- Ch1 开篇第一句实质性内容是否包含 2+ 个未定义术语？→ P2（读者第一句就卡住）
- 反例："prot_init() 让内核从借用固件的运行上下文变成拥有自己的运行上下文"（3 个未定义术语）
- 正例："信任边界：内核可信，用户进程不可信"（0 个未定义术语）

### 2.5 §3.3 冗余控制：新增"概念正交性 / 因果链重复" `[来源: Qwen + GLM + Kimi]`

- **概念正交性**：两个"并列"概念实际有因果/包含关系（如特权级 vs 页表权限位）→ P2，应调整为层次关系 `[来源: Qwen]`
- **因果链重复**：同一套因果关系（A→B→C）在 2+ 节完整重讲 → P2，应拆分层次 `[来源: GLM]`

### 2.6 §3.4 读者体验：新增"示例最小化" `[来源: DS + Seed]`

- 概念引入示例是否避免引入与核心机制无关的细节？
- 示例引入额外问题（读者会问"为什么 X"但 X 与核心无关）→ P2
- 反例：`*(0xffffffff80000000)=0` → 读者问"为什么这地址是内核地址"
- 正例：`*((int*)0)=0` → 读者只关心"为什么空指针写失败"

### 2.7 §3.5 教学性质量：新增"教学模式检查" `[来源: GLM(主) + DS + Kimi + Qwen]`

```markdown
### 教学模式检查（多架构/保护结构类文档强制）

- [ ] 统一抽象层先行（见 §1.Ch1 1.5）
- [ ] 双向流完整性（见 §1.Ch1 1.6）
- [ ] 历史包袱降级：架构特有遗留机制降级为补充章节，标题用疑问式（"x86 为什么还保留 GDT"）→ 违反 P2
```

### 2.8 §3.7（新增）：作者意图透明性 `[来源: M3(主) + GLM + Seed]`

```markdown
### §3.7 作者意图透明性（Author Intention Transparency）

> 检查"作者元注释"——暴露作者写作过程而非读者接收结果的文字。

判别口诀："删掉这段后，读者对主题的理解是否减少？"
- 减少 → 是正文，保留
- 不变 → 是元注释，删除或改写

六类元注释 `[来源: GLM]`：
1. 过渡类："引出 §1.4"
2. 范围声明类："本节只回答…避免重复"
3. 深度策略类："一句话带过"、"不展开，只建模型"
4. 作者自我强调类："必须加"、"本节最难理解"
5. 历史修正叙述类："早期文档曾表述…这不准确"
6. 自问自答修辞类："为什么需要？因为…"

判定：单处 → P2；>5 处 → P1（系统性风格问题）
与模式 15 区别：模式 15 是"已实现/待实现"进度追踪；本规则是"作者 narrate 写作策略"。
```

```markdown
### §3.6 文档设计哲学（Document Design Philosophy）

Step 3.6.1 哲学选择：抽取 Ch1 开头、Ch1 总结、Ch3 引言，判定属于：
- 概念驱动（Concept-first）：以"为什么需要 X"为起点
- 实现驱动（Implementation-first）：以"Minix3 C 源码"为起点

同一文档内部要保持哲学一致。

Step 3.6.2 主线检验（主语分析）：抽取 Ch1 主线陈述，判定主语是
prot_init() / CPU / 读者 / OS 中的哪一个。主语是函数名 → 实现驱动 → P1。
```

### 模式 40：因果链编造（解释正确性，P0）`[来源: GLM(主) + M3]`

```markdown
❌ 错误：claim 正确，但 BECAUSE 解释编造看似合理的技术机制
        "memcpy(&kinfo, local_cbi, ...) 是必要的，因为调用链推进后原栈帧会被覆盖"
        → claim 对（源码有），但"栈帧被覆盖"是编造的（kmain 没返回前栈帧一直在）

✅ 正确：用 C 语义/ISA 规范可验证的因果链
        "因为 local_cbi 是 kmain 的局部参数，作用域限于 kmain 调用链，非 kmain 链代码访问不到"

> 原因：grep 能验 claim 有无 evidence，验不了 BECAUSE 是否技术上正确。
> 编造的因果链比"无证据"更危险——读者会信以为真并据此推理。
> 判定：BECAUSE 部分机制技术上错误 → P0，即使 claim 本身正确。
> 与模式 34 边界：模式 34 是代码注释理由虚假，本模式是文档正文因果链编造。
```

### 模式 41：写作策略元注释泄漏（P2，>5 处 P1）`[来源: GLM(主) + M3 + Seed]`

```markdown
❌ 错误：作者对自己写作策略的注释进入读者正文（六类见 §3.7）
✅ 正确：教科书直接"做"过渡、"做"范围控制，不"说"自己在做

> 判定标准：删掉这段后，读者对主题的理解是否减少？不变 → 元注释。
> 与模式 15 区别：模式 15 是进度追踪（已实现/待实现）；本模式是写作策略自述。
```

### 模式 42：架构范围未标注（P1）`[来源: GLM(主) + M3 + DS]`

```markdown
✅ 正确：显式标注架构范围，三架构分别说明强制点
```

### 模式 43：实现驱动概念章（P1）`[来源: 全员, GLM/Seed/Qwen 最系统]`

```markdown
❌ 错误：Ch1 从源码函数出发反向总结概念
        Ch1 开篇："prot_init() 让内核从借用固件变成拥有自己运行上下文"
❌ 错误：Ch1 以 trait ProtectionArch / TrapEntryArch 作为核心组织框架（代码抽象非架构抽象）

✅ 正确：Ch1 从 CPU/系统视角的 WHY 出发，落到实现定位
        "什么是保护？为什么需要？→ 特权级 → CPU 运行时三问 → prot_init 是给 CPU 填三个答案"
```

### 模式 44：单向心智模型（P1）`[来源: GLM/DS/Kimi/Qwen/Seed]`

```markdown
❌ 错误：保护结构只讲"用户→内核"（进入），不讲"内核→用户"（返回）
❌ 错误：内存管理只讲"分配"不讲"释放"；异常处理只讲"触发"不讲"恢复"

✅ 正确：保护结构讲完整闭环
        用户态 → 进入内核（syscall/exception）→ 内核态 → 返回用户态（iretq/eret/sret）
        附返回指令对照表

> 判定：涉及双向转移的机制只讲单向 → P1
> 返回路径即使不展开，也必须至少提一句"如何返回"并附返回指令表。
```

### 模式 46：视角漂移（P2）`[来源: Kimi]`

```markdown
❌ 错误：同一章节内视角不统一
```

## 5. structure.md：新增结构分析产物（统一叙事层检查）`[来源: 用户提议 + DS/Seed/M3 合成]`

### 5.1 动机

03 案例暴露的核心问题是：**每个 claim 都对，但整体叙事失败**。现有 review 产物中：

| 产物 | 导向 | 检查的是 |
|------|------|---------|
| scan.md | 问题导向 | 哪里有 P0/P1/P2 |
| SYMBOLS.md | 符号导向 | C 源码覆盖率 |
| VERIFY-CHECK.md | 收敛导向 | 是否达标 |

**缺一个"结构导向"的产物**——没有人把文档的骨架单独提取出来评审。本提案的 §2.1 Ch1 骨架检查、§5.1 Step 0.5 读者模拟、§2.9 文档设计哲学虽然方向对，但散落在 checklist 的不同 §里，reviewer 容易"逐项打勾"而不做整体判断。

**structure.md 的价值**：强制 reviewer 先"提取骨架"再"评审骨架"，把宏观叙事质量从分散检查项提升为一个独立产物。它合并了 DS 的读者模拟 Step 0.5 + Seed 的 Ch1 骨架 + M3 的文档设计哲学三个提案，统一为一个结构化输出。

### 5.2 structure.md 模板

```markdown
# structure.md — {文档名} 结构分析

## 1. 主题思想（一句话）
> 例：prot_init() 给 CPU 配置回答"特权级/异常入口/内核栈"三问的数据结构
> 说不出 → P1（读者无法建立概念模型）

## 2. 目标读者
> 初学者/中级/高级 + 前置知识
> 未声明 → P1（无法验证教学性是否匹配读者）[来源: DS]

## 3. 叙事主语
> prot_init() / CPU / 读者 / OS —— 选一个，附证据（Ch1 开篇第一句主语）
> 主语是函数名 → P1（实现驱动）[来源: M3/Seed]

## 4. 驱动方向
> 概念驱动 / 实现驱动 / 混合 —— 附判定证据
> 实现驱动 → P1（模式43）[来源: 全员]

## 5. 文档大纲（每章核心命题）
| 章节 | 核心命题（一句话） | 回答的问题 | 叙事弧角色 |
|------|------------------|-----------|-----------|
| Ch1 | 保护结构是 CPU 三问的答案 | WHAT/WHY | 起(问题) |
| Ch2 | Minix3 C 如何回答三问 | HOW(C) | 承(证据) |
| Ch3 | Rust trait 如何抽象三问 | HOW(抽象) | 转(设计) |
| Ch4 | 具体实现如何落地 | HOW(代码) | 合(落地) |
| Ch5 | 测试如何验证 | VERIFY | 合(验证) |
> 叙事弧缺环节 → P1；章节核心命题说不出 → P1 [来源: DS/Seed]

## 6. 核心概念清单（按引入顺序）
| 顺序 | 概念 | 来源层级(L0/L1/L2) | 依赖的概念 | 依赖已引入? | 文字行数 | 占比 |
|------|------|-------------------|-----------|-----------|---------|------|
| 1 | 保护 | L1 | 无 | — | 15 | 10% |
| 2 | 特权级 | L1 | 保护 | ✅ | 20 | 13% |
| 3 | GDT | L0 | 特权级 | ✅ | 40 | 27% |

## 7. 跨架构统一抽象（多架构文档）

> 无统一抽象层 → P1（模式45）[来源: 全员]

## 8. 双向闭环完整性
| 机制 | 进入 | 返回 | 完整? |
|------|------|------|-------|
| 特权级切换 | user→kernel ✅ | kernel→user ✅/❌ | |
> 只单向 → P1（模式44）[来源: 全员]

## 9. 起承转合（叙事弧）
> 起(问题) → 承(概念) → 转(证据/抽象) → 合(落地/验证)
> 缺失环节标注 ❌ → P1 [来源: DS]

## 10. 元注释位置标记
| 位置 | 类型(六类之一) | 判定 |
|------|--------------|------|
| §1.2 L39 | 过渡类 | 删除 |
| §1.4 L106 | 深度策略类 | 删除 |
> >5 处 → P1（模式41）[来源: GLM/M3/Seed]

## 11. 裸概念复述测试 [来源: Seed]
> 把 Ch1 正文中所有函数名/结构体名/trait 名用 [XXX] 替换后，
> 核心概念是否仍能被理解？
> 不能 → P1

## 12. 纵向链路映射 [来源: Seed]
```

## 7. review-socratic-skill.md 改进（新增场景 9-12）`[来源: GLM + M3 + 用户强化]`

> **核心原则**：苏格拉底提问应多问偏本质向、触及读者灵魂、触及本质的问题。
> 不是"这里有没有错"，而是"删掉这一章，读者对整个系统的理解缺了什么？"

### 场景 9：叙事架构追问（本质向） `[来源: GLM(主) + M3 + 用户强化]`

触发：文档正确性通过，但读完后"不知道在讲什么"或"抓不住主线"。

话术（本质向）：
- {核心概念}到底是什么？为什么需要它？删掉它，系统能运转吗？
- {Ch1}是从"为什么需要 X"出发，还是从"X 函数做 Y"出发？
- {核心抽象}是否被低知识量内容淹没？读者读完能记住什么？
- {多架构内容}是否先给统一抽象，还是直接堆三架构细节？
- **删掉这一章，读者对整个系统的理解缺了什么？**（灵魂之问）
- **如果只能让读者记住一句话，那句话是什么？**（本质之问）

判定路径：实现驱动→P1（模式43）；核心抽象被淹没→P1（模式48）；多架构无统一抽象→P1（模式45）。

### 场景 10：解释正确性追问（因果链是否编造） `[来源: GLM(主) + M3]`

触发：claim 有 evidence，但 BECAUSE 听起来"太顺"或"想当然"。

话术：
- 文档 §X 说 "{claim}"，源码确实如此。但解释是"因为 {M1}"。{M1} 是 C 语义/ISA 规范保证的，还是推测的？
- 能否用源码逻辑或语言规范验证 {M1}？
- 如果 {M1} 无法验证，是否应标注"推测，待验证"？
- **这个"因为"是机制层面的因果，还是叙事层面的"听起来合理"？**（本质之问）

判定路径：M1 可验证→✅；无法验证且未标注→P1；技术上错误→P0（模式40）。

### 场景 11：心智模型 / 哲学层追问 `[来源: M3 + 用户强化]`

触发：文档技术正确但教学性可疑。

话术（心智模型）：
- 读者读完这个 section，心里能回答什么问题？
- 如果只能让读者记住一句话，那句话是什么？
- 这个 section 的存在，让读者多建立了什么心智模型？
- **读者合上文档后，能用三句话向同事解释这个机制吗？**（灵魂之问）
- **这个 section 是在教读者"理解"，还是在教读者"记住"？**（本质之问）

话术（哲学层）：
- 这篇文档的主语是谁？prot_init() / CPU / 读者 / OS？
- 作者想要读者带走什么？一句话能说出来吗？
- 文档的骨架是什么？按时间/空间/问题/架构分块？
- **文档是在回答"是什么"，还是在回答"为什么"？如果只回答"是什么"，读者能自己推出"为什么"吗？**（本质之问）

### 场景 12：结构骨架追问（基于 structure.md） `[来源: 用户提议]`

触发：structure.md 评审发现骨架问题，但需要作者澄清意图。

话术：
- structure.md 第 1 节"主题思想"写不出一句话——作者自己能说出来吗？
- structure.md 第 3 节"叙事主语"是函数名——这是有意的（实现驱动文档）还是无意的？
- structure.md 第 5 节"大纲"某章核心命题说不出——这一章存在的理由是什么？
- structure.md 第 6 节"概念依赖"有倒置——为什么先引入 A 再引入 B？
- structure.md 第 9 节"叙事弧"缺环节——这个缺失是有意的（延后到后续章节）还是遗漏？

判定路径：作者能澄清且有依据→✅；无法澄清→P1（结构缺陷）。

## 11. 总结与建议

### 11.1 总结

6 份独立分析 + 用户 structure.md 提议高度收敛于一个核心判断：**现有 review-rules 是"正确性验证机"，但 03 案例暴露的是"心智层/叙事层失败"**。规则集需要从"校验事实"扩展到"暴露作者心智 + 验证读者心智模型"。

最高价值的改进集中在四处：
1. **因果链验证**（P0，GLM/M3）——填补 §2.0 只验单点不验链式的盲区
2. **Ch1 强制骨架**（P1，Seed 主导）——把"Ch1 主语对了吗"从自由裁量提升为结构化标准
3. **作者意图透明性 + 架构范围标注**（P1，GLM/M3/DS）——暴露作者写作过程与架构偏见
4. **structure.md 结构分析产物**（P0，用户提议）——把分散的叙事层检查统一为一个结构化产物，先评审骨架再验证细节

### 11.2 建议

1. **立即落地第一阶段 5 项**（P0）：因果链验证 + Ch1 骨架 + Gate D-6 + 概念抽象原则 + **structure.md**。其中 structure.md 是用户提议的核心创新，它把 DS 的读者模拟、Seed 的 Ch1 骨架、M3 的文档设计哲学三个分散提案统一为一个产物，投入产出比最高。
2. **建立 Rule Discovery 机制**（M3）：规则集本身需要自演化。每次 review 强制填写"是否发现新模式"，避免"这次发现下次又重蹈"。
3. **注意 skill 体积**（Qwen 提醒）：新增检查项会增加 review-doc-skill 体积。建议 §2.0.3（因果链）+ §1.Ch1（骨架）+ §5（structure.md 模板）必须进 skill；其余按需加载。
4. **多 AI bagging + 用户裁决验证有效**：6 份独立分析中，P0 因果链被 2/6 识别、Ch1 骨架被 6/6 识别、元注释被 4/6 识别——bagging 显著提升了覆盖率（单 AI 最高 85%，合成后覆盖全部案例问题）。用户在 bagging 基础上提出的 structure.md 进一步把分散检查统一为结构化产物，证明了"多 AI bagging + 人类裁决"模式的有效性。建议未来类似任务继续采用此模式。
5. **下一步**：用户确认本提案后，按第一阶段修改 `review-doc-checklist.md` / `review-patterns.md` / `review-process.md` / `review.md`，新增 `structure.md` 产物模板，并在下一轮 03 文档 review 中验证新规则生效。
