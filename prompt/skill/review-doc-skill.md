# Minix-RS 文档 Review 检查清单

## 1. 文档结构规范

每篇文档应遵循以下结构：

```
# XX-title: 标题
> **分类**: 模块库 / 模块私有 / 全局基建
> **源码**: `minix3/minix/servers/模块/xxx.c`
> **说明**: 一句话功能描述
---

## 1. 概述
### 1.1 概念定义/作用
### 1.2 与 Minix3 的对应关系
### 1.3 关键状态/机制说明
### 1.4 行为规则

## 2. C 源码分析
### 2.1 相关定义（常量、调用号、配置等）
### 2.2 核心数据结构
### 2.3 关键函数分析
### 2.4 调用关系/调用点分析
### 2.5 设计要点/特殊处理

## 3. Rust 设计决策
> 高层设计选择，解释"为什么这样设计"

## 4. 实现详解
> Rust 实现的具体展开，解释"如何实现"

## N. 测试要点（倒数第二章）
## N+1. 参见（最后一章）
```

**关键约束**：第1/2章不得含 Rust；Ch3 聚焦"为什么"且可追溯 Ch1&2；Ch4 聚焦"怎么做"且对应 Ch3；测试章基于 Ch3+Ch4；C 源码分析完整覆盖所有核心数据结构/关键函数/调用关系；Ch3 有更好替代方案应写 TODO。

### 1.Ch1 Ch1 强制骨架（概念章专项，强制）

> **背景**：03-kmain-cstart 重构案例暴露 Ch1 最常见的失败模式是"主语错了"——从函数名出发总结概念，而非从"为什么需要"出发建立心智模型。
> **详见**：[review-rules/review.md §概念抽象原则](../review-rules/review.md)、[review-rules/review-patterns.md](../review-rules/review-patterns.md) 模式 51-53。

| # | 检查项 | 通过标准 | 优先级 |
|---|--------|---------|--------|
| 1.1 | **目标读者声明** | Ch1 引言声明目标读者与前置知识。未声明 → P1 | P1 |
| 1.2 | **"本章不讲什么"框** | Ch1 引言列出延后到后续章节的细节。无 → P2 | P2 |
| 1.3 | **裸概念复述测试** | 把 Ch1 正文中所有函数名/结构体名/trait 名用 `[XXX]` 替换后，读者是否仍能理解核心概念？不能 → P1 | P1 |
| 1.4 | **概念驱动方向** | Ch1 遵循 WHY→WHAT→HOW。开篇主语是函数名 → P1（实现驱动，模式 51）| P1 |
| 1.5 | **统一抽象先行** | 多架构文档先给统一框架（如"CPU 三问"），再分架构展开。无 → P1（模式 53）| P1 |
| 1.6 | **双向闭环** | 进入类机制（trap/syscall/IPC）必须同时覆盖"进入"和"返回"。只单向 → P1（模式 52）| P1 |
| 1.7 | **核心流程图** | Ch1 至少一张流程/关系图建立心智模型。无 → P2 | P2 |
| 1.8 | **核心 vs 历史包袱区分** | 架构特有机制（如 GDT）标注为"实现细节/历史包袱"，不当核心讲。违反 → P2 | P2 |
| 1.9 | **本章小结** | Ch1 末尾用核心框架收束并预告后续章节。无 → P2 | P2 |

**裸概念复述测试执行方法**（1.3）：
1. 提取 Ch1 正文中所有函数名/结构体名/trait 名
2. 用 `[XXX]` 替换后重读 Ch1
3. 如果核心概念仍能被理解 → ✅
4. 如果替换后 Ch1 变成"调用 [XXX] 然后 [YYY]"的无意义流水账 → P1（实现驱动）

## 2. 文档 Review 维度

### 2.0 Claims-Evidence Tracing（论文级文档质量，强制）

> 将文档中每个事实性断言视为学术论文的 claim，必须有可追溯的 evidence 支撑。这是论文级文档质量的核心方法论。

**执行步骤**：

**Step 2.0.1：提取所有断言**
从文档各章节中提取所有**事实性断言**（不含过渡句、不含设计决策的理由说明）：
- 行为描述：「X 函数从高地址向低地址扫描」
- 数值断言：「Y 结构体包含 N 个字段」
- 常量断言：「Z 常量在所有构建配置下都等于 K」
- 调用关系：「A 函数调用 B 函数完成某项工作」

**Step 2.0.2：逐 claim 分类与验证**
对每个 claim：
- **Claim 类型**：行为描述 / 数值断言 / 结构断言 / 调用关系 / 设计推断
- **Evidence 来源**：源码位置（精确到行号）/ 配置推导 / 文档链路上游
- **Evidence 强度**：直接可 grep（强）/ 需阅读逻辑推断（中）/ 无源码依据仅推理（弱）
- **可复现性**：他人能否仅凭文档+源码独立验证此 claim？

**必须输出表格**：
```markdown
### 2.0 Claims-Evidence Tracing 验证结果

| Claim | 类型 | 文档位置 | Evidence 来源 | 强度 | 可复现? | 判定 |
|-------|------|---------|-------------|------|---------|------|
| alloc_pages 从高到低扫描 | 行为 | Ch2§2.3 L45 | alloc.c:123-156 | 强 | ✅ | ✅ |
| phys_block 有 4 个字段 | 结构 | Ch2§2.2 L30 | region.h:23-35 | 强 | ✅ | ✅ |
| ... | ... | ... | ... | ... | ... | ... |
```

**额外质量维度（论文级要求）**：
- [ ] **先验假设显式化**：文档是否说明"本文档假设读者已经理解 X"？
- [ ] **结论 vs 证据的区分**：读者能否区分"这是事实行为"vs"这是设计者的判断"？
- [ ] **反面案例覆盖**：文档是否讨论了 edge case？是否说明"在什么条件下这个行为不成立"？
- [ ] **不确定性的诚实表达**：对无法确认的 claim 是否标注了"待确认"？

**判定标准**：
- claim 证据强度为"弱"且不可复现 → P0（文档不可信，需补充源码引用）
- claim 证据强度为"中" → P1（需补充更精确的源码引用）
- claim 证据强度为"强"且可复现 → ✅

**Step 2.0.3：解释因果链验证（强制，P0）**

> **核心原则**：claim 有 evidence 不够，解释 claim 的 BECAUSE 部分必须技术上正确。
> "因为 X 所以 Y" 中的 X 必须是真实机制，不是听起来合理的编造。
> 来源：03-kmain-cstart

对每个带因果解释的 claim（含"因为/所以/由于/为了"的断言）：
1. **提取因果链**：claim + 因为 M1 所以 M2
2. **验证 M1 是否是真实机制**（用 C 语言语义/ISA 规范/源码逻辑推断，非"听起来对"）
3. 若 M1 无法直接验证，必须标注"推测，待验证"

**判定**：
- 因果链机制技术上错误 → **P0**（解释编造，即使 claim 本身正确）
- 因果链含未验证环节且未标注 → P1
- 因果链可由 C 语义/ISA 规范直接验证 → ✅

**典型反例**（03 案例）：
- claim "memcpy(&kinfo, local_cbi, ...) 是必要的" ✅
- 编造解释"调用链推进后栈帧被覆盖" ❌（C 语义上 kmain 没返回前栈帧一直在）
- 正确解释"local_cbi 作用域限于 kmain 调用链，非 kmain 链代码访问不到" ✅

> **详见**：[review-rules/review-patterns.md](../review-rules/review-patterns.md) 模式 48（因果链编造）。

### §2.0.5 Design 引用规范

> **目的**：文档中引用 design 时统一格式，便于审稿人快速溯源。

文档中引用 design 时，应使用以下格式：

| 引用类型 | 格式 | 示例 |
|---------|------|------|
| design 决策 | `design.md §X.Y`（非 bagging）/ `design-final.md §X.Y`（bagging） | design.md §3.3 |
| design vs code 一致性 | `design.md §X.Y ↔ file:line` | design.md §3.3 ↔ vm.rs:243 |
| design 缺失 | `design.md §X.Y（缺失）` | design.md §3.3（缺失） |
| design Refactor 触发 | `design Refactor: design.md §X.Y 错` | design Refactor: design.md §3.3 漏进程表 |

**判定**：
- ✅ 文档引用 design 且 design 存在 → 强证据
- ⚠️ 文档引用 design 但 design 缺失 → **P0-design-missing**
- ❌ 文档不引用 design 但属于 design 范围 → P1
- ❌ 文档引用格式错误（无 §X.Y） → P1-process-violation

> **配套机制**：[review.md §Design First 原则](../review-rules/review.md) + [review-process.md §Step 1.6 设计对齐检查](../review-rules/review-process.md) + [review-patterns.md §模式 63 Design-Missing](../review-rules/review-patterns.md)。

### 2.1 概念准确性检查（强制，不可跳过）

> 禁止虚构、禁止幻觉、以 Minix3 源码为唯一真理来源。

**执行步骤**：
1. 从 Ch1 提取加粗术语/类型名/关键名词，从 Ch2 提取结构体/函数/宏名，汇总为「核心概念清单」
2. 逐概念 grep 验证：`rg "CONCEPT" minix3/minix/servers/{module}/ --type c -n` + kernel/ + include/
3. 数值常量验证：`rg "#define CONSTANT" minix3/minix/servers/{module}/ -n`
4. 算法描述验证：读 C 函数源码，逐行对比算法行为

**必须输出**：
```markdown
### 2.1 概念准确性验证结果

| 概念/术语 | 文档位置 | grep 结果 | 源码行号 | 一致性 | 问题 |
|----------|---------|----------|---------|--------|------|

**数值常量验证**：
| 常量 | 文档值 | 源码值 | 源码位置 | 一致? |

**算法描述验证**：
| 算法 | 文档描述 | 源码行为 | 一致? |
```

**判定**：概念在源码中找不到→P0 虚构概念；解释与源码不一致→P0 概念错误；数值不一致→P0 数据错误；算法不一致→P0 行为错误。

**Step 2.1.5：架构范围标注验证**（多架构文档强制）

> 来源：03-kmain-cstart

- 叙述中出现 x86 特有机制（GDT/段描述符/TSS/IDT 门/CPL）→ 必须标注"x86 特有"
- aarch64 特有（EL/SP_EL/VBAR/PSTATE）、riscv64 特有（S/U-mode/sscratch/stvec/SPP）同理
- 未标注 → P1；ISA 寄存器角色描述错误（如 RISC-V SPP 当作"当前特权级"）→ P0
- 标注格式：`> 架构范围：x86-64` / `> 架构范围：三架构共性` / 行内 `(x86-64 特有)`

**Step 2.1.6：过度简化检查（"A 就是 B" 反读法）**

- 对每处"A 就是 B / A 等于 B / A 即 B"定义性表述，反读"反过来 B 就是 A"是否成立
- 不成立 → 过度简化。涉及核心术语首次定义 → P1；其他 → P2
- 例："GDT 就是保护结构"反读"保护结构就是 GDT"不成立 → 应修正

**Step 2.1.7：概念来源层级检查**

> 来源：Kimi 提案

Ch1 术语来源分层：
- **L0 硬件/CPU 层**：ring/EL/IDT/VBAR（CPU 规范定义）
- **L1 OS 概念层**：保护/特权级/异常入口（OS 抽象）
- **L2 实现抽象层**：ProtectionArch trait/函数名（Rust 代码）

- Ch1 用 L2 术语作为概念定义 → P1（概念层级泄漏）
- Ch1 用 L2 且无 L0/L1 定义 → P0

### 2.2 C 代码引用验证（强制，不可跳过）

> 引用的代码必须正确，讲解必须准确。

**执行步骤**：
1. 提取文档中所有 C 代码引用（文件路径+行号）。
2. **逐引用验证**：对每个引用执行 `Read` 或 `rg -n` 读取对应源码行，确认文件是否存在、行号是否准确、片段是否完整。
3. 检查路径格式：禁止 `file:///home/user/...` 绝对路径。
4. 对比文档讲解与源码实际行为。

**严格禁止**：
- 不允许在 scan.md 中使用 **"未逐行验证" / "未全部验证" / "抽样验证" / "行号未核对"** 等表述。
- 如果引用行数过多无法在当前轮次全部验证，必须明确说明：
  - 已验证的引用范围和结果；
  - 未验证的范围；
  - 未验证部分标记为 **"P1 待验证"** 或 **"to confirm"**，并给出下一轮验证计划。
- 不得以"大体一致"、"基本正确"、"看起来没问题"替代逐行验证结论。

**必须输出**：
```markdown
### 2.2 C 代码引用验证结果

| 引用位置 | 文件路径 | 行号 | 文件存在? | 行号准确? | 片段完整? | 讲解一致? | 路径格式? | 问题 |
|---------|---------|------|----------|----------|----------|----------|----------|------|
```

**判定**：文件不存在→P0；行号偏差超5行→P1；片段截断改语义→P0；讲解与源码不一致→P0；过度解读→P1；绝对路径→P1；**出现"未逐行验证"等模糊结论→P1（流程违规）**。

### 2.3 数据结构覆盖完整性（强制，不可跳过）

**执行步骤**：
1. 从 Ch2 提取所有分析的结构体名称
2. grep 提取 C 源码结构体：`rg "^struct \w+" minix3/minix/servers/{module}/ --type c -n`
3. 逐结构体对比字段覆盖

**必须输出**：
```markdown
### 2.3 数据结构覆盖验证结果

| 结构体 | 源码位置 | 总字段数 | 文档覆盖字段数 | 遗漏字段 | 判定 |
|--------|---------|---------|--------------|---------|------|
```

**判定**：核心结构体完全未分析→P0；遗漏关键字段→P1；非核心遗漏→P2。

### 2.4 文档与代码一致性

- [ ] Rust 函数签名/参数类型/返回值是否与真实代码一致？
- [ ] 文档描述的行为与代码实现是否一致？示例代码是否可编译？

### 2.4b 代码示例 Rust 习惯用法同步检查（NEW 2026-07-30）

> **目的**：检测文档代码示例是否反映当前 idiomatic Rust 写法（特别是 Rust 2024 edition 兼容）。
> **触发条件**：文档 §3 / §4 含 Rust 代码块（` ```rust ... ``` `）。
> **模式参考**：[review-patterns-skill 模式 73](../skill/review-patterns-skill.md#模式-73-文档代码示例-rust-2024-edition-driftnew-2026-07-30)。

**检查命令**：
```bash
# Doc-side 静态扫描
rg "static mut" {doc}.md  # 命中非"说明性注释"位置 → P1

# Rust-side 实际状态（应 0 hits）
rg "static mut" os/ -t rust

# 路径一致性
rg "arch/src/(pt_alloc|paging\.rs|paging_ext)" {doc}.md  # 命中但路径已重组 → P1
find os/arch/src -name "pt_alloc.rs" -o -name "paging.rs" -o -name "paging_ext.rs"
```

**判定**：
- 文档示例含 `static mut` 而实际代码已迁移至 `Atomic*` / `UnsafeCell` → **P1**（模式 73）
- 文档路径引用 vs 实际 `find` 结果不一致（目录重组）→ **P1**（模式 73 子类型 b）
- 文档示例签名/API 名称与实际不符（`fetch_add` vs `compare_exchange`）→ **P2**（模式 73 子类型 c）

**修复**：
1. 复制实际代码到文档代码块
2. 加注释说明 Rust 2024 edition 兼容性选择
3. 路径错误按 `find` 结果更新

### 2.4c 文档路径约定一致性检查（NEW 2026-07-30, 模式 #74）

> **目的**：检测文档 Rust crate 路径引用是否漏 `os/` workspace 根前缀（典型：`kernel/src/...` 应为 `os/kernel/src/...`）。
> **触发条件**：任何 doc review（路径引用是文档基础约定）。
> **模式参考**：[review-patterns-skill 模式 74](../skill/review-patterns-skill.md#模式-74-文档路径约定漂移doc-path-convention-drift-new-2026-07-30)。

**检查命令**：
```bash
# 裸路径扫描（应仅命中 minix3/... 上下文）
rg "kernel/src/|boot-shim/src/|arch/src/|servers/vm/" {doc}.md | grep -v "minix3"

# 正确路径统计
rg "os/(kernel|boot-shim|arch|servers|libs)" {doc}.md | wc -l

# 双重前缀（sed 副作用）
rg "os/os/" {doc}.md  # 必须 0 hits

# 跨文档一致性
rg "os/kernel/src/" notes/rewrite/{module}/{stage}/01-*.md | wc -l
rg "os/kernel/src/" notes/rewrite/{module}/{stage}/02-*.md | wc -l
# 同一 stage 内所有 doc 的 `os/` 前缀使用率应一致
```

**判定**：
- doc 漏 `os/` 前缀（裸 `kernel/src/` 等） → **P1**（模式 74 默认）
- doc 仅个别遗漏（<5 处） → **P2**
- `os/os/` 双重前缀 → **P1**（sed 副作用，必须修）
- 跨 doc 路径风格不一致（doc 01 用 `os/`，doc 02 不用） → **P1**（模式 74b）

**修复**（≤10 分钟）：
```bash
# 1. 批量加 os/ 前缀
sed -i 's|kernel/src/|os/kernel/src/|g' {doc}.md

# 2. 修双重前缀
sed -i 's|os/os/|os/|g' {doc}.md

# 3. 验证 minix3 C 源路径未受影响
rg "minix3/.*kernel/src/" {doc}.md  # 应保留
```

### 2.4d 文档行号引用准确性检查（NEW 2026-07-31, Proposal #7）

> **目的**：检测 doc 中 `file:line` / `file:line-line` 引用与实际代码位置是否一致。
> **触发条件**：任何 doc review（行号引用是文档基础锚点）。
> **模式参考**：[review-process-skill Step 1.0a-自动](review-process-skill.md)。

**检查命令**（自动化脚本）：
```bash
# 1. 抽取 doc 中所有 file:line 引用
rg -o "(?:os/|minix3/)?[a-z_/0-9]+\.(?:rs|c|h|ld|sh|asm|S):\d+(?:-?\d+)?" {doc}.md | sort -u > /tmp/doc_lines.txt
```

### 2.4g const 权威位置检查（NEW 2026-07-31, Proposal #12）

> **目的**：doc 描述的 `pub const` 类型可能在多个 crate 中重复定义（如 DEFAULT_HZ 在 os/arch + os/kernel 两处独立定义）。doc 应显式说明**权威定义位置** + **同步约束**。
> **背景**：本次 05 doc review 发现 DEFAULT_HZ 在 `os/arch/src/arch/clock.rs:32` 和 `os/kernel/src/clock.rs:148` 各定义一次。Rust 不同 crate 独立 const 不会编译错误（不同 module），所以测试不会发现。doc §3.2 应显式说明权威位置 + 修改顺序。
> **触发条件**：任何 doc 描述跨 crate 共享的常量（HZ, PAGE_SIZE, NR_*, MAX_* 等）。
> **模式参考**：[Pattern #76 关联](review-patterns-skill.md) + [Proposal #12 design.md §X-Y "权威位置"段](review-process-skill.md)。

**检查命令**：
```bash
# 1. 提取 doc 中描述的 const 名
rg "pub const \w+" {doc}.md | rg -o "\w+" | sort -u

# 2. 对每个 const，验证是否跨 crate 重复定义
for c in DEFAULT_HZ PAGE_SIZE NR_PROCS; do
    matches=$(rg "pub const $c" os/ -t rust -l 2>&1 | wc -l)
    if [ "$matches" -gt 1 ]; then
        echo "⚠️ $c defined in $matches crates"
    fi
done
```

**判定**：
- 单一 crate 定义 → ✅ 不记录
- 多 crate 重复定义 + doc 显式说明权威位置 → ✅ 接受
- 多 crate 重复定义 + doc **未**说明权威位置 → **P1 doc 缺说明**

**修复**（≤5 分钟）：
```rust

/// **权威定义位置**：`os/<crate>/src/<module>.rs:NN`
/// （`<other_crate>` crate 内的同值 `const` 是独立副本，避免跨 crate 依赖）
/// 修改时**先改权威位置**，再 sync 到其他副本。
pub const DEFAULT_HZ: u32 = 100;
```

**关联**：

**必须输出**：
```markdown
### 2.11 文档风格验证结果

| 问题文本 | 位置 | 问题类型 | 建议改写 |
|---------|------|---------|---------|
```

**禁止**（TODO 允许保留，TODO 标记待做事项与进度标记不同）：

| 禁止 | 推荐 |
|------|------|
| "已实现：X" / "待实现：Z" / "未实现：W" | "X 函数负责 Y" / "Z 功能处理 W 场景" |

| 按完成状态分组 | 按功能分组 |

**判定**：进度标记/状态 emoji/进度标题 → P1；>5处 → 需系统性重写相关章节。

## 3. 可读性与表达质量

### 3.1 文本流畅性
- [ ] 语病/错句？长句超40字？代词指代清晰？被动语态滥用？术语一致？标点混用？
- [ ] **开篇第一句检查** ：Ch1 开篇第一句实质性内容是否包含 2+ 个未定义术语？→ P2（读者第一句就卡住）
  - 反例："prot_init() 让内核从借用固件的运行上下文变成拥有自己的运行上下文"（3 个未定义术语）
  - 正例："信任边界：内核可信，用户进程不可信"（0 个未定义术语）

### 3.2 逻辑组织
- [ ] 段落有逻辑衔接？有"跳跃"？遵循"先总后分"？信息密度不均？标题准确？

### 3.3 冗余控制
- [ ] 单文档内重复>2次？跨文档重复>3行应改引用？代码注释和文字说同一件事？
- [ ] **概念正交性**：两个"并列"概念实际有因果/包含关系（如特权级 vs 页表权限位）→ P2，应调整为层次关系
- [ ] **因果链重复**：同一套因果关系（A→B→C）在 2+ 节完整重讲 → P2，应拆分层次
- **判定**：同一概念同文档重复超2次→检查是否必要；跨文档重复超3行→简介+引用

### 3.4 读者体验
- [ ] 新概念有上下文？术语首次出现有定义？假设读者已知什么？复杂流程有"结论先行"？
- [ ] 长文档有目录？代码块和文字比例合理？**代码块注释用中文**（文档注释用中文）；类比恰当？
- **判定**：新概念3行内无解释→P2；连续20行纯文字→P2；连续30行纯代码→P2

**示例最小化检查**（§3.4 补充）：
- 概念引入示例是否避免引入与核心机制无关的细节？
- 示例引入额外问题（读者会问"为什么 X"但 X 与核心无关）→ P2
- 反例：`*(0xffffffff80000000)=0` → 读者问"为什么这地址是内核地址"
- 正例：`*((int*)0)=0` → 读者只关心"为什么空指针写失败"
- 本章开门第一个例子就有此问题 → P1

### 3.5 教学性质量（强制）

> 文档面向开源社区，是教学材料而非内部开发笔记。

**说明书 vs 教学文档**：

| 维度 | 说明书（退化） | 教学文档（目标） |
|------|--------------|----------------|
| Ch2 | 逐函数翻译注释 | 解释函数在整体流程中的角色 |
| Ch3 | 只写结论 | 推理过程+替代方案 |
| Ch4 | 贴裸代码 | 引导语+代码注释+设计决策引用 |
| 语义对应 | 无 | 与 Minix3 C 源码的语义对应 |
| 概念引入 | 直接使用不解释 | 给出定义、动机和上下文 |

**各章节要求**：Ch1 每个概念解释"为什么需要它"；Ch2 每个函数解释"它的角色"；Ch3 每个决策解释"为什么选A非B"；Ch4 每个类型有引导语解释核心思路+代码有注释。

**退化信号**：
- [ ] Ch2 只有代码片段+一行说明，无"为什么这样设计"的分析？
- [ ] Ch3 只罗列决策，无"为什么选A非B"？
- [ ] Ch4 变成 API 文档——列函数签名和功能说明？
- [ ] 缺少反例论证？缺少对比分析？缺少迭代过程记录？
- [ ] **开发记录退化**：出现"已实现/待实现/未实现"、✅❌🚧 状态标记、"实现清单"等进度追踪式表述？（详见 §2.11）

**详细检查项**：
- [ ] 每个章节/小节有引导语解释核心思路？
- [ ] 代码块内非自解释行有注释？特别是与 C 对应的注释？
- [ ] 代码块上方有 `> 设计决策：§3.x（xxx）` 引用？
- [ ] 核心概念/类型有 C 行为 vs Rust 行为对照？
- [ ] 代码块超15行无注释→P1；类型/模块小节无引导语→P1
- [ ] 新概念首次出现无定义→P1；代码块无设计决策引用→P2；无语义对应→P2

**教学模式检查**（多架构/保护结构类文档强制）：

- [ ] 统一抽象层先行（见 §1.Ch1 1.5）
- [ ] 双向流完整性（见 §1.Ch1 1.6）
- [ ] 历史包袱降级：架构特有遗留机制降级为补充章节，标题用疑问式（"x86 为什么还保留 GDT"）→ 违反 P2
- [ ] 附录化深度展开：WHY 完整论证会打断概念流时，主文一句话建模型 + 文末附录展开（含威胁模型/前提+机制+防御对应+总结）→ 违反 P2
- [ ] 概念骨架可见性：Ch1 有显式核心框架（如"三问"），章末用同框架收束，后续章节引用该框架 → 违反 P2

**判定**：3个以上退化信号→需要重构；1-2个→P1；0个→良好。

### 3.6 文档设计哲学（强制）

> 来源：M3 提案
> **背景**：03 案例暴露文档"哲学不一致"——Ch1 声称概念驱动，实际从函数名出发。

**Step 3.6.1 哲学选择**：抽取 Ch1 开头、Ch1 总结、Ch3 引言，判定属于：
- **概念驱动**（Concept-first）：以"为什么需要 X"为起点
- **实现驱动**（Implementation-first）：以"Minix3 C 源码"为起点
- **混合**（Hybrid）：问题驱动的实现分析

同一文档内部要保持哲学一致。Ch1 声称概念驱动但实际实现驱动 → P1。

**Step 3.6.2 主线检验（主语分析）**：抽取 Ch1 主线陈述，判定主语是 `prot_init()` / CPU / 读者 / OS 中的哪一个。
- 主语是函数名 → 实现驱动 → P1（模式 51）
- 主语是 CPU → 概念驱动 → ✅

### 3.7 作者意图透明性（强制）

> 来源：多 AI 提案
> **背景**：03 案例正文出现 13+ 处"作者元注释"——暴露作者写作过程而非读者接收结果的文字。

**判别口诀**："删掉这段后，读者对主题的理解是否减少？"
- 减少 → 是正文，保留
- 不变 → 是元注释，删除或改写

**六类元注释**：
1. **过渡类**："引出 §1.4"
2. **范围声明类**："本节只回答…避免重复"
3. **深度策略类**："一句话带过"、"不展开，只建模型"
4. **作者自我强调类**："必须加"、"本节最难理解"
5. **历史修正叙述类**："早期文档曾表述…这不准确"
6. **自问自答修辞类**："为什么需要？因为…"

**判定**：单处 → P2；>5 处 → P1（系统性风格问题）

> **详见**：[review-rules/review-patterns.md](../review-rules/review-patterns.md) 模式 49（元注释泄漏）。

### 3.8 P2 可读性检查的执行策略

1. **先粗筛**：30秒快速浏览，感觉良好标注「无明显问题」跳过
2. **抽样检查**：感觉有问题，抽3处（首段、中段、尾段）逐项检查
3. **聚焦高频**：术语不一致、信息跳跃、纯代码无讲解（超30行）
4. **极简化输出**：仅输出实际发现的问题
5. **批量处理**：超500行按章节切分

**输出格式**：
```
### 可读性检查（P2）
- 术语：✅一致 / ⚠️X处不一致
- 逻辑：✅通顺 / ⚠️X处跳跃
- 冗余：✅无 / ⚠️X处重复
- 读者体验：✅良好 / ⚠️X个问题
```
