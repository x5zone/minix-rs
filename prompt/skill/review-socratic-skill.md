# Minix-RS Review 苏格拉底追问话术

> **原则**：不直接下结论，而是通过提问让用户自己发现问题。
> **核心原则**：苏格拉底提问应多问偏本质向、触及读者灵魂、触及本质的问题。
> 不是"这里有没有错"，而是"删掉这一章，读者对整个系统的理解缺了什么？"
> **触发**：Agent 发现可疑点但无法立即判定时，加载本 Skill 选择对应场景话术。
> **目标**：避免误判（P0 误报或漏报），通过用户澄清获得准确证据。

---

## 场景 1：文档声明与源码疑似矛盾

**触发条件**：文档 §X 的声明与 minix3 源码 FILE.c:LINE 的行为不一致。

**话术模板**：
```
我注意到文档 §X 说 "{声明}"，但我在 minix3/.../FILE.c:LINE 看到的是 "{源码行为}"。
这两者似乎不一致。能否帮我确认：
1. 我对源码的理解是否正确？
2. 如果正确，这是文档错误，还是有其他上下文我没看到？
```

**判定路径**：
- 用户确认源码理解正确 + 无其他上下文 → 文档错误，标 P0
- 用户指出其他上下文 → 重新评估，可能降级
- 用户无法确认 → 标注 "待确认"，继续 Review

---

## 场景 2：设计决策缺乏依据

**触发条件**：Ch3 §X 的设计决策在 Ch1&2 找不到对应概念或源码分析依据。

**话术模板**：
```
Ch3 §X 设计了 "{决策}"，但我在 Ch1&2 没找到对应的依据。
这个设计是为了解决什么问题？能否追溯到 Ch1&2 的某个概念或 Ch2 的某个源码分析？
如果没有依据，可能需要补充 Ch1&2 或在 Ch3 说明动机。
```

**判定路径**：
- 用户能追溯到 Ch1&2 依据 → 补充文档链路，标 P1（链路断裂）
- 用户承认无依据 → 设计无依据，标 P1
- 用户说明是架构演进 → 检查是否标注 ARCH

---

## 场景 3：代码与文档设计不一致

**触发条件**：文档 Ch3 §X 的设计与代码 FILE.rs:LINE 的实现不一致。

**话术模板**：
```
文档 Ch3 §X 设计了 "{设计}"，但代码 FILE.rs:LINE 实现的是 "{实现}"。
这两者不一致。请问：
1. 是代码还没更新到匹配设计？
2. 还是设计已变更但文档未同步？
3. 或者有其他原因？
```

**判定路径**：
- 代码未更新 → 标 P1（代码-设计不匹配），建议更新代码
- 设计已变更文档未同步 → 标 P1，建议同步文档
- 其他原因 → 重新评估

---

## 场景 4：核心语义疑似违反

**触发条件**：对比 C 和 Rust 行为契约时，发现 errno 与 Error 变体语义不同。

**话术模板**：
```
我在对比 C 和 Rust 的 {函数名} 行为契约时发现：
- C 在 {条件} 下返回 {errno}
- Rust 在相同条件下返回 {Error 变体}
这两者语义不同（{errno} 表示 X，{Error 变体} 表示 Y）。
这是有意为之的架构演进，还是语义偏移？如果是演进，需要在文档中标注 ARCH。
```

**判定路径**：
- 有意演进 → 检查 ARCH 标注，未标注则 P1
- 语义偏移 → 标 P0（核心语义违反）
- 无法确认 → 标注 "待确认"，加载 core-semantics-skill 深入分析

---

## 场景 5：覆盖率缺口

**触发条件**：覆盖率穷举显示 C 符号在文档和 Rust 中均未覆盖。

**话术模板**：
```
覆盖率穷举显示 {符号} 在 C 源码中存在，但：
- 文档未覆盖（{符号} 不在任何 .md 中）
- Rust 未实现（{符号} 不在任何 .rs 中）
这个符号是否在语义范围内？如果是，需要补充文档和实现；如果否，需要说明排除理由。
```

**判定路径**：
- 在语义范围内 → 标 P0（覆盖率缺口），建议补全
- 不在语义范围内 → 要求标注 ARCH 排除理由
- 无法确认 → 标注 "待确认"，继续 Review

---

## 场景 6：卓越性问题（正确性已通过）

**触发条件**：正确性检查已通过，发现可提升的卓越性改进点。

**话术模板**：
```
正确性检查已通过，但我注意到一个卓越性改进点：
{位置} 的 {代码/文档} 可以 {改进方案}，这样能 {收益}。
这不是必须修复的问题，但能提升 {可读性/可维护性/可测试性}。
是否需要现在改进，还是记录到 FINDINGS.md 供后续处理？
```

**判定路径**：
- 用户选择现在改进 → 标 Excellence-P1/P2，给出改进项
- 用户选择后续处理 → 记录到 FINDINGS.md，标 Excellence-P2
- 用户认为不需要 → 不记录

---

## 场景 7：证据不足无法判定

**触发条件**：grep 验证未找到匹配，或匹配结果不足以判定声明的真伪。

**话术模板**：
```
我尝试验证 "{声明}"，但：
- grep "{pattern}" 在 {路径} 未找到匹配
- 或匹配结果不足以判定
能否提供更多上下文，或确认这个声明是否有源码支撑？
如果无法确认，我会标注 "待确认" 并继续。
```

**判定路径**：
- 用户提供上下文/证据 → 重新评估
- 用户确认无源码支撑 → 标 P0（Claims-Evidence 违反）
- 用户无法确认 → 标注 "待确认"，继续 Review

---

## 场景 8：跳过检查的正当性

**触发条件**：Agent 准备跳过某检查项，需确认跳过理由是否合理。

**话术模板**：
```
我准备跳过 {检查项}，因为 {理由}。
但根据规则，跳过需要确认。请问：
1. 这个跳过理由是否合理？
2. 是否有其他方式可以部分验证？
如果确认合理，我会标注 "跳过: {理由}" 继续。
```

**判定路径**：
- 用户确认合理 → 标注 "跳过: {理由}"，继续
- 用户认为不合理 → 执行该检查项
- 用户建议部分验证 → 执行部分验证，标注剩余跳过

## 场景 9：叙事架构追问（本质向）

**触发条件**：文档正确性通过，但读完后"不知道在讲什么"或"抓不住主线"。

**话术模板**（本质向）：
```
文档正确性检查通过了，但我读完后抓不住主线。想追问几个本质问题：
1. {核心概念}到底是什么？为什么需要它？删掉它，系统能运转吗？
2. {Ch1}是从"为什么需要 X"出发，还是从"X 函数做 Y"出发？
3. {核心抽象}是否被低知识量内容淹没？读者读完能记住什么？
4. {多架构内容}是否先给统一抽象，还是直接堆三架构细节？
5. **删掉这一章，读者对整个系统的理解缺了什么？**（灵魂之问）
6. **如果只能让读者记住一句话，那句话是什么？**（本质之问）
```

**判定路径**：
- 实现驱动（主语是函数名）→ P1（模式 51）
- 核心抽象被淹没 → P1（模式 55）
- 多架构无统一抽象 → P1（模式 53）
- 作者能澄清且有依据 → ✅
- 无法澄清 → P1（结构缺陷）

---

## 场景 10：解释正确性追问（因果链是否编造）

**触发条件**：claim 有 evidence，但 BECAUSE 听起来"太顺"或"想当然"。

**话术模板**：
```
文档 §X 说 "{claim}"，源码确实如此。但解释是"因为 {M1}"。
想追问：
1. {M1} 是 C 语义/ISA 规范保证的，还是推测的？
2. 能否用源码逻辑或语言规范验证 {M1}？
3. 如果 {M1} 无法验证，是否应标注"推测，待验证"？
4. **这个"因为"是机制层面的因果，还是叙事层面的"听起来合理"？**（本质之问）
```

**判定路径**：
- M1 可验证 → ✅
- 无法验证且未标注 → P1
- 技术上错误 → P0（模式 48 因果链编造）

---

## 场景 11：心智模型 / 哲学层追问 

**触发条件**：文档技术正确但教学性可疑。

**话术模板**（心智模型）：
```
文档技术正确，但我对教学性有疑问。想追问：
1. 读者读完这个 section，心里能回答什么问题？
2. 如果只能让读者记住一句话，那句话是什么？
3. 这个 section 的存在，让读者多建立了什么心智模型？
4. **读者合上文档后，能用三句话向同事解释这个机制吗？**（灵魂之问）
5. **这个 section 是在教读者"理解"，还是在教读者"记住"？**（本质之问）
```

**话术模板**（哲学层）：
```
想追问几个哲学层问题：
1. 这篇文档的主语是谁？prot_init() / CPU / 读者 / OS？
2. 作者想要读者带走什么？一句话能说出来吗？
3. 文档的骨架是什么？按时间/空间/问题/架构分块？
4. **文档是在回答"是什么"，还是在回答"为什么"？如果只回答"是什么"，读者能自己推出"为什么"吗？**（本质之问）
```

**判定路径**：
- 主语是函数名 → P1（模式 51 实现驱动）
- 读者无法三句话复述 → P1（心智模型不完整）
- 只回答"是什么"无"为什么" → P1（教学性缺失）

## 场景 13：Design-Missing 追问

**触发条件**：Review 发现 design doc 缺少关键决策（如 trait 方法签名、错误码策略、不变量）。

**话术模板**：
```
我在 review design doc (e.g. 06-design.md / 06-design-final.md) 时发现：
- §3 的 trait 定义了 X 接口但未给出方法签名
- §4 的错误码策略只列出了 Y 和 Z，缺少 W 的处理
- §5 的不变量只说"资源 A 必须先释放"，但没说"何时检查"

这些缺失是设计有意延后（到 §X.Y 详述），还是 design 漏写？
能否指出 design 中的具体章节，或者允许我标记为 P0-design-missing？
```

**判定路径**：
- Design 有具体章节延后 → 补充文档链路，标 P1（链路断裂）
- Design 无对应章节 → P0-design-missing（必须在 Final Review 前补 design）
- 用户说明是架构演进 → 检查 ARCH 标注

详见 [review-patterns-skill.md §X.5 Pattern 63 Design-Missing](../skill/review-patterns-skill.md)。

## 场景 12：结构骨架追问（基于 structure.md）

**触发条件**：structure.md 评审发现骨架问题，但需要作者澄清意图。

**话术模板**：
```
structure.md 评审发现几个骨架问题，想请作者澄清：
1. structure.md 第 1 节"主题思想"写不出一句话——作者自己能说出来吗？
2. structure.md 第 3 节"叙事主语"是函数名——这是有意的（实现驱动文档）还是无意的？
3. structure.md 第 5 节"大纲"某章核心命题说不出——这一章存在的理由是什么？
4. structure.md 第 6 节"概念依赖"有倒置——为什么先引入 A 再引入 B？
5. structure.md 第 9 节"叙事弧"缺环节——这个缺失是有意的（延后到后续章节）还是遗漏？
```

**判定路径**：
- 作者能澄清且有依据 → ✅
- 无法澄清 → P1（结构缺陷）
- 有意为之但未在文档说明 → P2（应补充说明）

## 使用指南

### Agent 调用时机
1. **发现可疑点时**：选择最匹配的场景，使用对应话术
2. **不强制使用**：如果证据充分可直接判定，无需追问
3. **组合使用**：一个可疑点可能涉及多个场景，可组合话术
4. **记录结果**：追问后必须记录判定结果和用户回应

### 话术定制
- 模板中的 `{占位符}` 必须替换为具体内容
- 可根据上下文调整措辞，但保留"提问而非下结论"的核心风格
- 避免引导性提问（如"这是不是错的？"），应开放性提问

### 与其他 Skill 的协作
- 追问后如需深入分析 → 加载 core-semantics-skill（行为契约表）
- 追问后如需覆盖率验证 → 加载 coverage-skill
- 追问后如需卓越性评估 → 加载 excellence-skill
