# Minix-RS Review 文档卓越性检查

> 本文件定义文档卓越性检查标准，追求"教科书级"文档质量。
> **前置条件**：正确性 gate（[review-doc-checklist.md](review-doc-checklist.md)）已通过。
> **强制规则**：每个判定标注 evidence [DIRECT/MEDIUM/INFERRED]。

---

## 一、卓越性 vs 正确性

| 维度 | 正确性（gate） | 卓越性（grade） |
|------|--------------|---------------|
| 目标 | 文档不错 | 文档好读、好学、好维护 |
| 判定 | P0/P1/P2 | 卓越性 P1/P2（不降级为正确性 P1） |
| 时机 | 先执行 | 正确性通过后执行 |
| 修复 | 必须修复 | 建议修复 |

**⛔ 卓越性问题不降级为正确性问题。卓越性 P1 是"可以更好"，正确性 P1 是"必须修复"。**

---

## 二、§4.1 叙事结构卓越性

### 2.1 检查项

| 检查项 | 说明 | Evidence 级别 |
|--------|------|-------------|
| 叙事弧完整 | 问题→分析→决策→实现 | [MEDIUM] |
| 动机说明 | 每章有"为什么"而非仅"是什么" | [DIRECT] |
| 逻辑过渡 | 章节间有过渡而非堆砌 | [MEDIUM] |
| 层次清晰 | 章节层次不超过 4 级 | [DIRECT] |
| 主题聚焦 | 每章一个主题，不混杂 | [MEDIUM] |
| **概念骨架可见性** | Ch1 有显式核心框架（如"三问"），章末用同框架收束，后续章节引用该框架 | [DIRECT] |
| **统一抽象先行** | 多架构文档先给统一框架再分架构展开（见 [review-doc-checklist.md §1.Ch1 1.5](review-doc-checklist.md#1ch1-ch1-强制骨架)） | [DIRECT] |
| **双向闭环** | 进入类机制覆盖"进入"+"返回"（见 [review-doc-checklist.md §1.Ch1 1.6](review-doc-checklist.md#1ch1-ch1-强制骨架)） | [DIRECT] |

### 2.2 Execute

1. 阅读文档目录结构，检查叙事弧：
   - Ch1 是否提出问题？
   - Ch2 是否分析现状（C 源码）？
   - Ch3 是否给出设计决策？
   - Ch4 是否描述实现？
   - 测试章是否验证设计+实现？

2. 检查每章开头是否有动机段落（"本章解决什么问题"）。

3. 检查章节间是否有过渡（"上一章分析了 X，本章将设计 Y"）。

4. **概念骨架可见性检查**（新增）：
   - Ch1 是否有显式核心框架（如"CPU 三问"、"保护结构两要素"）？
   - Ch1 章末是否用同一框架收束？
   - Ch3/Ch4 是否引用该框架（如"对应 Ch1 三问中的第 1 问"）？
   - 无显式框架 → 降级为 B（良好）；有框架但后续章节未引用 → 降级为 C（合格）

### 2.3 Output

| 章节 | 叙事弧完整? | 动机说明? | 逻辑过渡? | 层次清晰? | 主题聚焦? | 概念骨架? | 统一抽象? | 双向闭环? | Issue |
|------|------------|----------|----------|----------|----------|----------|----------|----------|-------|

### 2.4 卓越性标准

- **A（优秀）**：叙事弧完整，每章有动机，过渡自然，Ch1 有显式概念骨架且后续章节引用
- **B（良好）**：叙事弧基本完整，多数章节有动机，Ch1 有概念骨架但后续未充分引用
- **C（合格）**：叙事弧有缺失，但可读，Ch1 无显式概念骨架
- **D（不合格）**：堆砌式，无叙事弧，无概念骨架

## 三、§4.2 读者体验卓越性

### 3.1 检查项

| 检查项 | 说明 | Evidence 级别 |
|--------|------|-------------|
| 目标读者明确 | 文档说明面向谁 | [DIRECT] |
| 术语定义 | 术语首次出现有定义 | [DIRECT] |
| 复杂概念图解 | 复杂概念有图或类比 | [MEDIUM] |
| 前置知识声明 | 显式声明读者需知 | [DIRECT] |
| 导航辅助 | 有目录、索引、交叉引用 | [DIRECT] |
| 可读性 | 句子简洁，段落适中 | [MEDIUM] |
| **边界声明** | Ch1 声明"本章不讲什么"，列出延后到后续章节的细节  | [DIRECT] |

### 3.2 Execute

1. 检查文档开头是否声明目标读者和前置知识。

2. 提取所有粗体术语，检查首次出现是否有定义：
   ```bash
   rg "\*\*[A-Z_]+\*\*" FILE.md -n
   ```

3. 检查复杂概念（如页表映射、IPC 协议）是否有图解或类比。

4. 检查是否有目录和交叉引用。

5. **边界声明检查**（新增）：Ch1 引言是否有"本章不讲什么"框，列出延后到后续章节的细节？无 → 降级为 B。

### 3.3 Output

| 位置 | 读者体验问题 | 卓越性 P? | Suggested Fix |
|------|------------|----------|---------------|

### 3.4 卓越性标准

- **A**：目标读者明确，术语全定义，复杂概念有图解，Ch1 有边界声明
- **B**：多数术语有定义，关键概念有图解，但 Ch1 无边界声明
- **C**：术语定义不全，但可推断
- **D**：术语未定义，无图解，难读

## 四、§4.3 教学深度卓越性

### 4.1 检查项

| 检查项 | 说明 | Evidence 级别 |
|--------|------|-------------|
| 设计取舍 | 解释为什么选 A 不选 B | [MEDIUM] |
| 边界情况 | 讨论行为不成立的条件 | [MEDIUM] |
| 失败模式 | 讨论错误场景和恢复 | [MEDIUM] |
| 系统图景 | 连接到更大的系统 | [INFERRED] |
| 可运行示例 | 提供可运行代码示例 | [DIRECT] |
| 历史背景 | 解释 C 设计的历史原因 | [MEDIUM] |
| **概念→抽象→实现三层闭环** | Ch1 概念通过 Ch3 trait 抽象落到 Ch4 实现，且有映射表  | [MEDIUM] |
| **运行时视角三问可泛化性** | 框架从"一个运行时实体的运行时问题"出发，能被后续章节反复引用形成闭环，能让读者闭眼复述状态机。反模式：框架是名词列表 | [MEDIUM] |
| **抽象层次一致性** | 流程图/表格/代码引用在同一抽象层次，低层细节不破坏高层统一性（如不写"CPU 自动切栈"当 RISC-V 是软件切栈）| [MEDIUM] |

### 4.2 Execute

1. 检查 Ch3 设计决策是否有"替代方案"段落。

2. 检查 Ch2 是否讨论了 C 代码的边界情况（如空指针、零长度、溢出）。

3. 检查 Ch3 是否讨论了设计决策的失败模式。

4. 检查文档是否连接到更大的系统图景（如 VM 文档是否提到与 PM/VFS 的交互）。

5. 检查 Ch4 是否有可运行的代码示例。

6. **三层闭环检查**（新增）：Ch1 概念 → Ch3 trait → Ch4 实现 是否有映射表？无 → 降级为 B。
7. **框架可泛化性检查**（新增）：Ch1 框架是"运行时实体的问题"还是"名词列表"？后者 → 降级为 C。
8. **抽象层次一致性检查**（新增）：流程图/表格/代码是否在同一抽象层次？低层细节破坏高层统一性 → 降级为 B。

### 4.3 Output

| 位置 | 教学深度问题 | 卓越性 P? | Suggested Fix |
|------|------------|----------|---------------|

### 4.4 卓越性标准

- **A**：有设计取舍、边界情况、失败模式、系统图景、可运行示例、三层闭环映射表、框架可泛化、抽象层次一致
- **B**：有设计取舍和边界情况，但缺三层闭环或框架可泛化性
- **C**：仅描述"是什么"，无"为什么"，框架是名词列表
- **D**：纯描述，无教学价值

---

### §4.3.5 Design 视角的教学深度

> **核心思想**：文档不应只解释"实现如何"，还应解释"为什么这样 design"。如果 Ch3 只有"决策结论"而无"决策依据"，是教科书级文档的关键缺口。

| 检查项 | 期望 | 示例 |
|--------|------|------|
| 设计决策的依据 | 必须有"因为 X 所以 Y" | "用 `enum` 替代裸 int，因为类型安全" |
| 设计的本质表达 | 必须有"灵魂本质"（一句话击中本质）| "进程是 CPU 时间的断点续传" |
| 设计的取舍说明 | 必须有"为什么不选 B" | "不选 `Box<dyn>`，因为 boot 阶段零堆" |
| design vs Minix3 的演进 | 必须说明 | "32 位临时窗口 → 64 位 direct_map" |

**判定**：
- ✅ 4 项全有 → A 级卓越
- ⚠️ 缺 1 项 → B 级可接受
- ❌ 缺 ≥2 项 → **P1-design-perspective-missing**（需补充 design 视角）

**详见**：[review.md §Design First 原则](review.md) + [review-patterns.md §模式 56 决策日志体](review-patterns.md)。

## 五、§4.4 可维护性卓越性

### 5.1 检查项

| 检查项 | 说明 | Evidence 级别 |
|--------|------|-------------|
| 变更日志 | 有变更日志或修订记录 | [DIRECT] |
| TODO 标记 | 未完成项有 TODO 标记 | [DIRECT] |
| 外部引用 | 引用外部资料有链接 | [DIRECT] |
| 一致性 | 术语、命名、风格一致 | [MEDIUM] |

### 5.2 Execute

1. 检查是否有变更日志段落。

2. 检查 TODO 标记：
   ```bash
   rg "TODO|FIXME|XXX" FILE.md -n
   ```

3. 检查外部引用是否有链接。

4. 检查术语和命名的一致性（同一概念是否用同一术语）。

### 5.3 Output

| 位置 | 可维护性问题 | 卓越性 P? | Suggested Fix |
|------|------------|----------|---------------|

### §4.4 补充：文档组织合理性检查矩阵（13 项）

> 教训回顾：再次列出大纲，思考整体组织、思考教学性、概念全面覆盖。
> **引用**：文档重写工作流 Step 2.1 章节结构作为组织标准（见 [review-process.md §Step 0.3.2 生成 outline.md](review-process.md)）。

**组织合理性检查矩阵**：

| # | 检查项 | 期望 | 引用依据 |
|---|--------|------|---------|
| 1 | Ch1 小节数 | 5-8 个概念节拍 | 工作流 Step 2.3 |
| 2 | Ch1 主语 | CPU/OS/机制/矛盾，**禁止函数名** | 工作流 Step 2.3 |
| 3 | Ch1 顺序 | WHY → WHAT → HOW | 工作流 Step 3.1 |
| 4 | Ch1 灵魂本质 | 每个核心概念必须有"灵魂本质一句话" | 工作流 Step 2.3 |
| 5 | Ch1 统一框架 | 多架构文档必须先给统一框架，再分架构 | 工作流 Step 2.3 |
| 6 | Ch1 进入类机制 | trap/syscall/IPC/boot 必须覆盖双向流 | 工作流 Step 2.3 |
| 7 | Ch2 C 源码引用 | 每节标注 `file:line` 锚点 | 工作流 Step 2.1 |
| 8 | Ch3 设计决策 | 必须用"如果 X 设计会有 Y 问题，所以用 Z"假设性推理 | 工作流 Step 2.4 |
| 9 | Ch3 禁止叙事 | 禁止"旧版/最初/后来/我们改成"（模式 64）| §通用禁令 |
| 10 | Ch5 测试 | 每个 Ch3 决策在 Ch5 有对应测试 | 工作流 Step 2.5 |
| 11 | 跨文档衔接 | 与前后文档有明确衔接（前一阶段/后一阶段）| 工作流 Step 0 |
| 12 | 范围边界 | 本章讲什么/不讲什么/见后续文档/预留 | 工作流 Step 2.1 |
| 13 | **核心概念完整性** | **Ch1 提到的每个核心概念必须在 Ch3 有设计对应** | design §3 trait 列表 |

**判定**（13 项）：
- ✅ 13 项全有 → A 级组织
- ⚠️ 缺 1-2 项 → B 级可接受
- ❌ 缺 ≥3 项 → **P1-organization-incomplete**（需重构章节）
- ❌ 违反"禁止函数名作主语" → **P0-narrative-violation**
- ❌ "核心概念完整性"未通过 → **P0-concept-incomplete**（教训）

**章节结构模板**：
```
# {NN}-{stage-title}.md

## Ch1. 概述（概念导向，建立心智模型）
### 1.0 本章讲什么
### 1.1 核心概念 1
### 1.2 核心概念 2
### 1.N 本章小结

## Ch2. C 源码分析（Ground Truth）
## Ch3. Rust 设计决策（本质机制）
## Ch4. 实现详解（HOW）
## Ch5. 测试要点
## Ch6. 参见
```

**文档拆分判定阈值**：

| 触发条件 | 阈值 | 处置 |
|---------|------|------|
| 文档总行数 | > 2500 行 | 拆分为 2 个文档（07 顺延） |
| Ch1 概念节拍 | > 8 个核心概念 | 拆分为 Ch1 + Ch1.b（背景） |
| Ch2 文件引用 | > 5 个 C 文件 | 拆分为 Ch2（核心）+ Ch2.b（次要） |
| 知识点覆盖矩阵 | 单概念组跨 3+ 章核心内容 | 拆分为独立文档（每文档 1 主概念组） |
| 实施 Phase | 跨 2 个独立实施阶段 | 文档拆分必须与 phase 拆分的 commit 对齐 |

**判定流程**：
1. 列出 §4.4 矩阵判定结果
2. 任意 1 项超阈值 → **P1-suggest-split**（建议拆分）
3. 任意 2 项超阈值 → **P0-require-split**（必须拆分，可触发文档重组流程：拆分后原文档归档为 `.bak`，新文档重新走 §1-2 流程）

## 六、§4.5 概念教学卓越性（Ch1 专项）

> **前置条件**：§1.Ch1 概念驱动检查已通过（见 [review-doc-checklist.md §1.Ch1](review-doc-checklist.md#1ch1-ch1-强制骨架)）。
> **背景**：Ch1 是概念章，需要专门评估其教学卓越性，而非仅评估正确性。

### 6.1 检查项

| 检查项 | 说明 | Evidence 级别 |
|--------|------|-------------|
| CPU/系统视角（非 OS 代码角度） | Ch1 从 CPU/系统视角组织，而非从 OS 代码角度 | [MEDIUM] |
| 统一抽象先于分架构实现 | 多架构文档先给统一框架再分架构展开 | [MEDIUM] |
| 心智模型完整（双向机制两方向都覆盖） | 进入类机制覆盖"进入"+"返回" | [DIRECT] |
| 认知负荷（新概念不引入不必要额外问题） | 示例最小化，不引入与核心机制无关的细节 | [MEDIUM] |
| 预期管理（"本章不讲什么"显式声明） | Ch1 声明边界，列出延后到后续章节的细节 | [DIRECT] |
| 概念收束（章末用框架收束，预告后续） | Ch1 章末用核心框架收束并预告后续章节 | [MEDIUM] |

### 6.2 Execute

1. 抽取 Ch1 开篇第一句，判定主语是 CPU/系统 还是 OS 代码/函数名。后者 → 降级。
2. 检查多架构内容是否有统一抽象层先行。无 → 降级。
3. 检查进入类机制（trap/syscall/IPC）是否双向闭环。只单向 → 降级。
4. 检查 Ch1 示例是否最小化（不引入额外问题）。违反 → 降级。
5. 检查 Ch1 是否有"本章不讲什么"声明。无 → 降级。
6. 检查 Ch1 章末是否用核心框架收束并预告后续。无 → 降级。

### 6.3 Output

| 检查项 | 判定 | 证据 | Issue |
|--------|------|------|-------|

### 6.4 卓越性标准

- **A（优秀）**：CPU 视角 + 统一框架 + 心智完整 + 预期管理 + 框架收束
- **B（良好）**：概念驱动 + 统一抽象 + 心智基本完整
- **C（合格）**：概念驱动但缺统一抽象或心智不完整
- **D（不合格）**：实现驱动

## 七、Pass condition

- §4.1 叙事结构：至少 B 级
- §4.2 读者体验：至少 B 级
- §4.3 教学深度：至少 B 级
- §4.4 可维护性：至少 B 级
- §4.5 概念教学（Ch1 专项）：概念文档至少 B 级

**⛔ 卓越性问题不阻塞 Review 收敛。但应在 FINDINGS.md 中记录，供后续改进。**
