# 代码 Review 检查清单

> 本文档定义对 Minix-RS 项目 Rust 代码进行 Review 时的检查维度。
> 适用：所有 Rust 源代码（`.rs` 文件）

---

## 1. Rewrite 质量检查

> 这是最核心的维度。发现 Translate 味道必须指出。

- [ ] 是否存在裸整数表达语义（应用 newtype/enum 替代）？
- [ ] 是否存在 C 式空指针/哨兵值（裸 `0`、`-1` 表示"无值"）？应改用 `Option<T>`
- [ ] 是否存在未命名的魔术数字（应抽象为命名常量）？
- [ ] 是否存在 C 式 flag 组合（应用 bitflags/enum/typestate 替代）？
- [ ] 是否存在 C 式错误码传递（应用 Result + ? 替代）？
- [ ] 是否将 C 宏直接翻译成 Rust 宏（应用 trait/泛型替代）？
- [ ] 是否保留了 C 式数据结构而未用 Rust 所有权重构？
- [ ] 是否存在"为了 Rust 而 Rust"的过度设计（偏离 Minix 语义）？
- [ ] 是否做到了"非法状态不可表达"（invalid states unrepresentable）？
- [ ] **错误码是否对齐**：Rust 的 `Result<T, Error>` 中封装的错误码，是否与 Minix3 原始定义的 errno 严格对应？禁止为了"优雅"而合并或创造新的错误语义
- [ ] **内存所有权是否清晰**：C 源码中的内存分配/释放点，在 Rust 中是否有对应的 `Owner`？是否存在 C 中"借用"但在 Rust 中被误用为"所有权"的情况？
- [ ] **代码是否实现了文档 Ch3 的设计决策**：如果 Ch3 说用 typestate，代码是否真的用了？如果 Ch3 说用 enum，代码是否用了裸整数？
- [ ] **代码是否与文档 Ch4 的实现描述一致**：函数签名、类型定义、行为语义是否匹配？

### §1.5 Design 对齐检查

> **核心**：如果 design 不抓本质（如漏掉核心概念），仅 review 代码实现无意义。这种情况应触发 Refactor（Gate H 阻断）。

| 检查项 | 期望 | 实际 | 状态 |
|--------|------|------|------|
| design ↔ code 一致性 | ≥80%（Step 1.6.2）| _% | ⚠️/✅ |
| design 是否定义核心 trait | 是 | 是/否 | ✅/❌ |
| code 是否实现 design 中所有决策 | 是 | 是/否 | ✅/❌ |
| design 是否抓到 Minix3 本质 | 是 | 是/否 | ✅/❌ |
| 错误码策略 | 严格对齐 Minix3 | check | ✅/❌ |
| `as` 截断阈值规则 | design 明文 | check | ✅/❌ |

> **关键判定**：
> - 一致性 ≥ 80% + design 本质正确 → ✅ 继续 review
> - 一致性 < 80% 但 design 正确 → **code Refactor**（修 code）
> - design 漏概念（design-missing）→ **design Refactor**（先补 design）
> - design 抓错本质（design-wrong）→ **design Refactor 必须**（先 redesign）

**配套机制**：[review.md §Design First 原则](review.md) + [review-process.md §Step 1.6 设计对齐检查](review-process.md) + [review-process.md §Gate H design 门控](review-process.md#gate-h-design-门控) + [review-patterns.md §模式 65 Translate 倾向](review-patterns.md)。

## 2. 硬件抽象检查

> **强制规则：所有硬件都必须被抽象为 trait。**
> 核心原则：抽象机制，而非描述硬件。描述"做什么"，而非"怎么做"。

- [ ] 是否出现了具体硬件语义（CR3、TSS、MSR、I/O 端口等）？❌ 必须拒绝
- [ ] 硬件交互是否全部通过 trait 抽象完成？（无例外）
- [ ] trait 是否描述"OS 需要什么机制"而非"硬件怎么做"？
- [ ] 上层代码是否仅依赖 trait 接口，不感知底层硬件布局？
- [ ] 数据结构中是否包含架构特定的硬件字段（如 `pde` 数组）？❌ 应由 trait 实现内部管理
- [ ] 是否使用 `#[cfg(target_arch)]` 条件编译选择硬件行为？❌ 应通过 trait 静态分派
- [ ] OS 语义类型（如 `PageFlags`）是否与硬件编码分离？
- [ ] mock 硬件是否实现了所有必需的 trait？
- [ ] trait 定义是否在使用方附近（分散定义）？
- [ ] trait 实现是否集中在 arch crate（集中实现）？
- [ ] trait 设计是否考虑了 x86-64/arm64/RISC-V 64 的共性？

### 2.5 trait 设计质量评估

> **核心原则**：trait 是抽象机制的工具，不是装饰品。每个 trait 必须有其存在的理由。
> §2 要求"该抽象的必须抽象"，本节要求"抽象了的必须抽象得合理"。

- [ ] **多态必要性**：该 trait 是否有 ≥2 个**行为不同**的实现？
  - 如果所有实现的行为完全相同（如都调用同一个 syscall），trait 不提供多态价值 → P1
- [ ] **trait bound 使用**：该 trait 是否被用作泛型约束（`where T: Trait` 或 `impl Trait`）？
  - 如果从未作为 bound 使用，说明不需要多态分派 → P1（考虑改为固有方法或自由函数）
- [ ] **单方法 trait 评估**：如果 trait 只有 1 个方法，是否真的需要独立存在？
  - 能否合并到已有 trait？
  - 能否改为各实现者的固有方法 + enum 分发？
- [ ] **机制 vs 策略分离**：trait 是否混淆了"硬件机制"和"OS 策略"？
  - 机制（如页表映射）→ 属于 trait，各架构实现不同
  - 策略（如绑定进程地址空间）→ 属于上层，所有架构相同，不应放在 trait 中
- [ ] **跨架构差异验证**：trait 的每个方法，在不同架构上的实现是否真的不同？
  - 如果完全相同 → 考虑改为自由函数或固有方法
  - 如果仅标志位不同 → 考虑用关联常量而非 trait 方法

**判定标准**：
- trait 有 ≥2 个行为不同的实现 + 被用作 trait bound → ✅ 合理的 trait
- trait 所有实现相同 + 从未作为 bound → ❌ 不必要的 trait（P1）
- trait 方法在所有架构上实现相同 → ❌ 该方法不应在 trait 中（P1）

## 3. 类型系统与安全

- [ ] typestate 是否真正约束了状态？是否存在绕过 typestate 的路径？
- [ ] typestate 和 flags 之间是否严格一致？能否构造出"逻辑非法但类型合法"的状态？
- [ ] 是否可能同时持有同一对象的多个 view（aliasing 问题）？
- [ ] `unsafe` 是否最小化？每个 `unsafe` 块是否有明确的安全契约？
- [ ] 是否存在"逻辑正确但在 Rust 内存模型下是 UB"的代码？
- [ ] `MaybeUninit` / `UnsafeCell` / 裸指针使用是否正确且必要？
- [ ] 是否手动实现了 `unsafe Send` / `unsafe Sync`？其安全性是否经过论证？
- [ ] Drop 语义是否清晰？是否存在隐式 drop 风险？

## 4. 执行模型与并发假设

> 用户态服务器假设单线程执行；内核模块必须考虑 SMP + BKL。

### 4.1 用户态服务器检查项

- [ ] 模块是否明确声明了单线程假设？
- [ ] 是否存在 `Sync` / `Send` 的不当实现？
- [ ] 是否使用 `UnsafeCell` 绕过借用检查？其前提是否被明确保证？
- [ ] 是否存在潜在的 aliasing UB，即使在单线程下？
- [ ] 如果未来扩展为多线程，该设计是否会失效？
- [ ] 是否使用了 `lazy_static` / `OnceCell`？初始化顺序是否正确？
- [ ] IPC 消息传递的指针是否通过 `Send` 约束或 Safe Wrapper 保证安全？

### 4.2 内核 SMP/BKL 检查项（Kernel 模块专用）

> Minix3 kernel 有 `CONFIG_SMP` + `spinlock_t big_kernel_lock`（`BKL_LOCK()`/`BKL_UNLOCK()`）。BKL 是 spinlock（busy-wait），临界区内禁止睡眠/调度。

**BKL 持有完整性**：
- [ ] 进入内核空间的每条路径是否持有 BKL？调用链上是否有对应的 `BKL_LOCK()`？
- [ ] 是否存在 BKL 未持有的间隙（如 `BKL_UNLOCK()` 后 `BKL_LOCK()` 前）允许其他 CPU 修改共享状态？
- [ ] BKL 临界区内是否存在睡眠、调度、等待 IPC 的操作？→ ❌ P0（spinlock 内不能 sleep/deadlock）
- [ ] 是否存在因提前 return 或错误路径导致的 BKL 未释放？

**CPU-local 数据**：
- [ ] per-CPU 数据是否通过 `get_cpu_var()`/`put_cpu_var()` 成对访问？
- [ ] 是否存在跨 CPU 读取 local 数据的路径？
- [ ] per-CPU 数据是否有非 BKL 保护的并发修改？

**共享状态保护**：
- [ ] 内核全局变量/`static` 是否有明确的并发保护策略并文档说明？
- [ ] 是否存在"宣称 BKL 保护但实际访问时未持有"的路径？
- [ ] `static mut` 在 Rust 中是 unsafe——如何保证不产生 data race？

**Rust 类型系统与 SMP 约束**：
- [ ] `Rc<T>` 在内核中能否跨 CPU 共享？（`!Send + !Sync` → 不能）
- [ ] `RefCell<T>` 能否跨 CPU 共享？（`!Sync` → 不能）
- [ ] `UnsafeCell` 的安全论证是否从"单线程"改为"BKL 保护"或"per-CPU 隔离"或"Atomic 操作"？
- [ ] 跨 CPU 共享是否需要 `Arc` + `Mutex`/`RwLock` 或 `Atomic*` 类型？

## 5. 内存模型与状态表达

- [ ] 是否在未初始化内存上读取字段（UB）？
- [ ] `MaybeUninit` 是否仅为表达"空槽位"（通常是误用）？
- [ ] Drop 是否用于资源释放，而不是状态管理？

## 6. 公开接口与模块设计

- [ ] `pub` 是否克制？是否遵守最小权限原则？
- [ ] 模块是否高内聚？是否存在职责不清的模块？
- [ ] 是否有逻辑应该拆分出去？
- [ ] 是否有本应 private 却暴露的 API？
- [ ] 模块间依赖是否清晰且合理？

### 6.1 模块可见性分层原则

> **核心思想**：模块内部可以宽松，但对外必须严格通过 API 访问。

**实现模式**：
```
module/
├── mod.rs          # 不导出内部类型（如 VmProc）
├── internal.rs     # pub(crate) 字段，模块内可访问
└── view.rs         # typestate views，对外公开

external_module.rs  # 只能通过 view.rs 的 API 访问
```

**目的**：将 bug 消灭在设计中，而非代码审计时。

### 6.2 最小可见性原则

> **核心思想**：每个类型的可见性应该是"必须暴露的最小范围"。

**判断口诀**：
> **"这个 pub 是因为外部需要，还是因为内部懒得组织？"**
> 如果是后者，需要收紧可见性。

> **"这个类型导出后，外部能做什么？如果答案是不应该做的东西，就不该导出。"**

## 8. 测试

- [ ] 测试是否覆盖：正常路径、边界条件、状态转换（含非法路径）？
- [ ] 对于每个 `unsafe` 函数/块，是否有测试验证安全契约？

- [ ] 跨模块测试是否存在冗余？

## 9. 注释与文档

> 参考 Redox OS 风格：英文注释、清晰、简洁、解释"为什么"。

### 9.1 注释覆盖率（强制）

- [ ] **每个 `pub` 函数/方法/类型必须有文档注释**（`///`）？
- [ ] **每个 `pub(crate)` 函数如果语义非自解释，必须有注释**？
- [ ] **每个模块（`mod.rs`）必须有模块级文档注释**（`//!`）说明模块职责？
- [ ] **复杂算法或非常规实现必须有行内注释**解释"为什么"？
- [ ] **文件级注释**：如果文件职责不显然，是否有文件头注释说明？

> **判定标准**：如果 Reviewer 需要读代码才能理解一个 `pub` 接口的用途，则缺少文档注释。

### 9.2 注释质量

- [ ] **注释必须使用英文**（这是原则，不是建议）？
- [ ] 文档注释是否描述了公开接口的契约和前置条件？
- [ ] 是否存在显而易见的冗余注释？
- [ ] 是否有过多的空行影响紧凑性？
- [ ] `unsafe` 代码是否有 safety 注释？
- [ ] 关键设计决策是否解释了"为什么不用另一种常见方案"？

## 10. 64 位假设

- [ ] 代码是否基于 64 位假设编写？
- [ ] 是否存在不必要的 32 位残留（如 `u32` 用于地址/大小）？
- [ ] 是否存在用 `as` 进行有损截断（如 `u64 as u32`）且无注释说明安全性？

## 11. 复杂度与工程性

> 防止过度设计的刹车系统。

- [ ] 当前设计是否明显复杂于问题本身？
- [ ] 是否存在"理论优雅但工程不必要"的设计？
- [ ] 是否为了类型安全引入过高复杂度？
- [ ] 是否可以用更简单的模型表达相同语义？
- [ ] **trait 是否过度抽象**：是否存在"为了 trait 而 trait"的设计？参考 [§2.5 trait 设计质量评估](#25-trait-设计质量评估) 的判定标准

## 12. no_std 约束检查

> **核心原则**：除 mock 和 test 外，所有代码必须在 `no_std` 环境下运行。

- [ ] 是否存在 `use std::` （非 `#[cfg(test)]` 代码中）？→ P0
- [ ] `Cargo.toml` 中是否正确设置了 `#![no_std]`？
- [ ] 是否使用了需要 `std` 的第三方 crate？
- [ ] `alloc` 的使用是否提供了全局分配器实现？
- [ ] mock/test 代码是否正确使用 `#[cfg(test)]` 隔离？
- [ ] 是否存在隐式依赖 `std` 的模式（如 `println!`、`Vec::new` 在非 test 中）？

**允许的例外**：
- `#[cfg(test)]` 模块中可以使用 `std`
- mock 实现中可以使用 `std`（但必须通过 feature gate 隔离）
- build.rs 中可以使用 `std`

## 13. 设计-代码一致性检查

> **核心原则**：代码必须实现文档中描述的设计，不能设计与代码各写各的。

- [ ] **Ch3 设计→代码实现**：文档 Ch3 中的每个设计决策，代码中是否都有对应的实现？
  - 如果 Ch3 设计了 typestate 但代码用裸整数 → P0（设计未实现）
  - 如果 Ch3 设计了 enum 但代码用常量 → P1（设计意图未体现）
- [ ] **Ch4 描述→代码实现**：文档 Ch4 中的实现描述，代码是否与之匹配？
  - 函数签名是否一致？
  - 类型定义是否一致？
  - 行为语义是否一致？
- [ ] **代码→Ch3/Ch4 追溯**：代码中的每个关键实现，是否能在文档 Ch3 或 Ch4 中找到对应描述？
  - 如果代码实现了文档未描述的功能 → P1（实现超出设计）
  - 如果代码使用了文档未提及的类型/模式 → P1（可能偏离设计意图）

## 14. C-Rust 语义对齐检查

> **核心原则**：Rust 实现必须与 Minix3 C 源码语义对齐。不对齐的地方必须注释说明原因。
> 这是"行为语义优先原则"（review.md §行为语义优先原则）在代码层面的具体执行规则。

### 14.1 对齐分级

| 级别 | 定义 | 对齐要求 | 不对齐时的处理 |
|------|------|---------|--------------|
| **架构层** | 涉及整体架构变化的函数/模块 | 允许不对齐（架构演进） | 文档 §2.5 标注演进理由 |
| **叶函数** | 不依赖其他内部函数、直接操作数据的函数 | **必须对齐** | 代码注释说明原因（P1） |
| **修正性** | C 源码存在已知 bug，Rust 修正了行为 | 允许不对齐 | 代码注释说明 C 的 bug 和 Rust 的修正（P1） |

### 14.2 叶函数语义对齐（强制）

- [ ] 每个叶函数的 Rust 实现，其行为是否与对应 C 函数一致？
  - 返回值语义是否一致？
  - 错误码是否对齐？
  - 副作用是否等价？
- [ ] 如果叶函数行为不对齐，是否注释说明了原因？
  - C 源码 bug → 注释引用 C 源码位置和 bug 描述
  - Rust 类型系统约束 → 注释说明 Rust 为什么不能直接对应
  - 架构演进影响 → 注释说明演进如何改变了叶函数语义

### 14.3 C 有实现但 Rust 缺失（强制）

> 文档 §2.8 检查"C 源码覆盖完整性"（文档层面），本节检查代码层面的对应实现。
> 典型场景：C 的 `mem_type_t` 函数指针表中设置了某个回调，但 Rust 的 trait impl 中没有覆盖该方法。

当 C 源码中某个类型实现了某个回调/函数，但 Rust 对应类型的 trait impl 中没有覆盖该方法时：
- [ ] 是否确认缺失是合理的（使用默认实现即可）？
- [ ] 默认实现的行为是否与 C 中该回调的行为一致？
  - 如果不一致 → P1（应覆盖为与 C 一致的行为）
  - 如果一致 → 无需覆盖，但建议注释说明"使用默认实现，与 C 的 xxx 行为一致"
- [ ] 如果缺失不合理（C 有特化行为但 Rust 依赖默认），是否添加了覆盖实现？

**示例**：
```rust
// C 中 mem_type_anon_contig 设置了 .ev_split = anon_contig_split（空操作）。
// Rust 的 ContiguousAnonymous 必须覆盖 ev_split → Ok(())，
// 而不能依赖默认的 Err(NotSupported)（C 中 NULL → EINVAL，语义不同）。
```

### 14.4 Rust 代码注释中的 C 源码引用验证（强制）

> 文档 §2.2 检查"文档中的 C 代码引用"，本节检查 Rust 代码注释中的 C 源码引用。
> Rust 代码注释经常引用 C 源码函数名（如 "Minix3's anon_split"）来解释对齐关系，
> 如果引用错误，会误导后续开发者。

- [ ] Rust 代码注释中引用的 C 函数名是否正确？
  - 如注释写 "Minix3's anon_contig_split" 但实际对应的是 `mem_type_directphys`（NULL）→ P1
- [ ] 注释中描述的 C 行为是否与源码一致？
  - 如注释写 "C 中 NULL → 跳过" 但实际 C 中 NULL → EINVAL → P1
- [ ] 注释中引用的 C 源码位置（文件名、行号）是否准确？

**判定标准**：
- 注释引用了错误的 C 函数名 → P1（误导开发者）
- 注释描述的 C 行为与源码不符 → P1（语义对齐判断可能基于错误信息）
- 注释引用的源码位置不准确 → P2（不影响语义判断，但影响可追溯性）

### 14.5 架构演进导致的函数消失（允许）

当架构演进使整类 C 函数不再需要时（如 direct map 使物理地址转换函数消失）：
- [ ] 文档中是否说明了为什么这些函数不需要 Rust 对应？
- [ ] 代码中是否在相关位置注释了"Minix3 有 xxx 函数，但因 [演进原因] 不再需要"？

### 14.6 修正性不对齐（允许，但必须注释）

当 C 源码存在 bug 或设计缺陷，Rust 版本修正了行为时：
- [ ] 注释是否说明了 C 源码的 bug 是什么？
- [ ] 注释是否说明了 Rust 的修正方案？
- [ ] 注释是否引用了 C 源码位置？

**注释模板**：
```rust
// Minix3 bug: anon_contig_reference() returns ENOMEM but region.c ignores
// the return value (line 841). Rust fix: ev_copy returns NotSupported to
// correctly reject fork for contiguous memory regions.
```

### 14.7 Review 执行策略

> 逐函数对齐检查成本高，以下策略确保检查有实际产出而非形式主义。

1. **优先检查叶函数**：架构层函数的对齐由文档 §2.5 覆盖，代码 review 优先检查叶函数
2. **抽样验证**：如果叶函数数量多，优先检查以下高风险函数：
   - 返回错误码的函数（错误码不对齐 = 行为偏移）
   - 涉及内存分配/释放的函数（语义偏移 = 内存安全风险）
   - 涉及并发/锁的函数（语义偏移 = 死锁/竞态风险）

## 15. 细节精确性检查

> 本维度是"大方向正确"之后的第二层检查。5 个元规则跨阶段复用，适用于 Boot/VM/PM/VFS 等所有模块。
> Agent 策略：标记可疑点，不要求 100% 自动判定正确性，输出待人工确认的标记列表。

### 15.1 外部知识可验证

- [ ] 代码注释中是否引用了外部知识（硬件规范、协议条款、API 行为、标准约定）？
- [ ] 引用的外部知识是否可被独立验证？（寄存器手册、UEFI 规范、RISC-V Privileged Spec 等）
- [ ] 外部知识在当前上下文中是否仍然成立？（如 legacy 特性在新模式下是否仍适用）

**判定**：注释描述的硬件行为与规范不符 → P1（误导后续维护者）

### 15.2 通用接口纯度

- [ ] 共享结构体、trait、公共 API 中的每个字段/方法，是否对所有消费者上下文都有语义意义？
- [ ] 如果某字段/方法只对特定上下文有意义（特定架构、特定模块、特定进程类型），是否明确标注？
- [ ] 可选方案：① `Option<T>` 标注可选性；② 移至架构/模块特定的扩展结构；③ 注释明确标注"X 专用，其他忽略"

**判定**：通用接口包含未标注的上下文特定元素 → P1

### 15.3 返回值完整性

- [ ] 所有外部调用（固件、系统调用、库函数、硬件抽象 trait 方法）的返回值是否被处理？
- [ ] 返回值被忽略时，是否有显式注释说明"可安全丢弃"的理由？
- [ ] 如果返回值包含关键信息（如内存映射、状态码），丢弃后是否有替代来源？

**判定**：关键返回值被无说明地忽略 → P1

### 15.4 资源生命周期闭环

- [ ] 每个资源（内存、句柄、映射、缓冲区）的获取是否有对应的释放路径？
- [ ] 如果"不释放"，是否有显式声明的理由？（如 boot 一次性、静态全局、移交内核）
- [ ] 资源的释放责任方是否明确？（谁分配谁释放？还是由上层统一管理？）

**判定**：资源获取后无释放路径且无说明 → P1

### 15.5 理由可质疑性

- [ ] 代码/文档注释中给出的"为什么"解释，是否经得起"这个理由在上下文中成立吗？"的质疑？
- [ ] 理由是否是唯一/最真实的原因？有没有更诚实的说法？
- [ ] 涉及性能、安全、大小限制的理由，是否有量化依据？

**判定**：注释理由与实际情况明显不符 → P1（轻微）/ P0（严重误导设计决策）
