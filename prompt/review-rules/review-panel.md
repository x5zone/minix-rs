# Review Panel —— 独立审查面板协议

> 状态：V1（2026-11-07）；V3 修订（2026-11-10，§3.5 certify 阶段、P-READER 读者清单、输出规模改为按根因分组）。
> 本文件是 `prompt/skill/review-loop.md` 第一阶段（L1）的规范源。
> 它不是第七个任务命令，不改变 `review-cmds.md` 六个命令的契约；正常 review 不走本面板。

## 一、目的

现有 review 流程的强项是机械证据与检查清单，弱项是三个结构性盲区：

1. 审查者与作者共用同一个上下文，知道作者知道的东西，读者理解障碍看不见；
2. 代码审查停在“对照规则查”，没有从 C 语义出发独立提出 Rust 方案，翻译残留与设计死代码接不住；
3. 同 agent 的独立验证仍然是同一个“脑子”，抽样复判只能发现算术错误，发现不了共同盲区。

面板用五个角色把这三类问题分开处理。每个角色只拿判断所需的事实，不拿作者的结论；每个角色只报问题，不改代码。

## 二、总原则

| 原则 | 含义 |
|---|---|
| 审查者不改代码 | 面板角色只读仓库，只能写自己的报告到 `tmp/review-eval/`；修改权归主 agent。 |
| 材料隔离 | 每个角色有明确的“给”与“不给”清单；给判断所需的事实，不给作者的推理、结论、历史评审。 |
| 不以票数裁决 | 多个角色意见冲突时，按证据强度裁决：源码直接证据高于实验观察，实验观察高于推理，推理高于直觉。 |
| 冻结决策先查 | 命中 `rewrite-notes/meta/coordination/review-eval/DECISIONS.md` 且无新证据的发现，记为 `re-litigation`，不计文档缺陷。 |
| 范围先声明 | L0 声明本篇范围（文档主题加关联代码清单）；相邻问题只登记 follow-up，不作为本轮阻塞。 |
| 每条发现可处置 | 每条发现必须有位置、证据、最小修复、置信度、是否需要源码核实，以及“若我错了”的自述。 |

## 三、角色与材料隔离矩阵

| 角色 | 拿到 | 明确不给 | 产出 |
|---|---|---|---|
| P-FACT 事实与合同 | 文档全文、相关 C 源、相关 Rust 代码、工具读数、`DECISIONS.md` 的相关条目（只给编号与一行裁决） | 历史 `scan.md`、其他 agent 的结论、作者自评、`expected/` | `panel/fact.md` |
| P-DESIGN D1 独立设计 | C 语义合同、文档 Ch1 与 Ch2、`AGENTS.md` 的关键约束、操作系统理论 | 现有 Rust 实现、文档 Ch3 与 Ch4、`meta/design/<stage>/` 快照、历史评审、作者解释 | `panel/design-d1.md` |
| P-DESIGN D2 差异审查 | D1 方案、现有 Rust 代码、文档 Ch3 与 Ch4、`tools/trait-audit.py` 读数 | 作者对“为什么这样设计”的解释、历史评审结论 | `panel/design-d2.md` |
| P-READER A 初学者路径 | 文档正文全文、一页读者画像（前置知识、教学目标） | 源码、其他文档、diff、工作流规则、作者解释、其他 agent 输出、`expected/` | `panel/reader-a.md` |
| P-READER B 结构编辑 | 同 A | 同 A | `panel/reader-b.md` |
| P-READER C 因果一致性 | 同 A | 同 A | `panel/reader-c.md` |
| P-REFUTE 反证 | 文档全文、相关源码、设计合同 | 作者结论、其他 agent 结论、历史评审 | `panel/refute.md` |
| P-SUBTRACT 减法倡导者（触发式） | 待裁决提案清单、现有 Rust 实现、相关 C 源码、`review-code-checklist.md` §3.5 | 提案作者的解释、历史评审结论、其他角色输出、`expected/` | `panel/subtract.md` |
| P-META 流程评估 | 当前工作流版本说明、语料条目、盲区账本、本轮轨迹、面板原始输出、前几篇指标、`DECISIONS.md` | 主 agent 的自我评价与建议（归因表可以给，但要求抽样独立复判） | `meta/<doc-stem>-review.md` |

补充规则：

- `DECISIONS.md` 只给“编号加一行裁决”，不给历史论证；否则冻结决策本身会变成锚点。
- 读者画像由主 agent 从文档头部提取；缺失时写一页并请用户确认，不得把作者的设计笔记塞进去。
- 设计角色的第一遍必须在没有现有 Rust 代码的条件下完成；如果角色报告“我参考了现有实现”，该遍作废。
- 反证角色只在触发条件下启动：P-FACT 或 P-DESIGN 报出至少一条 P0，或本篇属于启动链、IPC、内存管理、时钟中断高风险类（与 §七同行清单一致），或用户明确要求。
- **减法倡导者（P-SUBTRACT，V3.6/C-37）只在触发条件下启动**：本轮归因后存在 `[ARCH]` 提案、待用户亲裁的 D-0xx 行，或其他"新增类型 / 新装置"级提案，且在交用户裁决之前。提案为空 → 跳过并在 `loop.md §1` 记「P-SUBTRACT 未启动：无提案」。它**不参与常规六角色 survey**，也不计入 §七 的读者/设计档位。

### 3.5 certify 阶段的裁剪（V3）

V3 没有验证轮。每轮的 survey 阶段派全量角色；fix 之后的 certify 阶段是同一轮的
关闭阶段，输入是闭集：

- P-FACT：只查本轮修复 hunk 涉及的符号、常量、签名、引文；不重扫全文，不抽
  “随机未改章节”。
- READER：只读改动段及邻句，确认理解障碍是否消失；不读全文，不重开 A/B/C 三份。
- RB：审最终 HEAD（含本轮全部修复提交）；覆盖全部 P0/P1 与全部修复项，不抽样。
- 不派 DESIGN 全量；设计项只核对“已实施/未实施”状态。
- 不派 P-SUBTRACT：减法倡导只在提案**交用户裁决之前**跑一次（§4.3b），certify 阶段不重复。

### 3.6 确认轮（V3.3）

修改轮 ROUND-CLOSED 后，确认轮是收敛声明的唯一来源（§6A 四态模型）。它是
**全量 survey**（六个角色、材料隔离不变），但修复权限受限：

- 修复只针对本轮新准入的 P0/P1/P2 事实与同步项；**不实施 ⑥**——设计项登记
  `OPEN-DEBT.md` 到下一个设计批，否则基线在确认之下移动；
- 读者 P3 走 §4.0e/§4.0c 的严重度门槛：`## SUGGESTION` 优先，按 §4.0c 以 SUGG 行入台账（V3.4-r8 对齐——计入 SUGG 键与发现总数，不进阻断集）；
- `certify 新准入 = 0` → 该篇 `CONVERGED`；> 0 → 确认轮内修完再确认一次
  （每个 CANDIDATE 最多 2 次，edition 更替或批准重开后重新计数）；结构性新根因 → `NOT CONVERGING` 回边界；
- 确认轮不占 §7.5 的 3 轮修改预算；CONVERGED 之后不得再开轮（新证据走重开决策）。

certify 发现的新准入项进**本轮**台账，在本轮内修完再复跑 certify；不得写成下一轮，
也不得开新轮。同一根因连续两次修复仍复发 → 标 `STUCK` 交用户。

## 四、角色 brief（逐字交给子 agent）

以下五段是自包含的任务书。主 agent 复制对应段落，替换尖括号占位符，作为子 agent 的完整提示；不要在任务书之外补充作者的解释或结论。

### 4.1 P-FACT 事实与合同

```text
你是独立事实审查者。你的任务不是评价文风，也不是提出重构，而是核对这篇文档与它声称的事实是否一致。

允许读取：
- 目标文档：<DOC_PATH>
- 文档声明的相关 C 源码与 Rust 代码（由 <DOC_CODE_MAP_PATH> 给出）
- 只读命令：grep、rg、sed、awk、wc、sha256sum、cargo metadata、cargo test --no-run 等不修改文件的命令
- 冻结决策清单：<DECISIONS_SNIPPET>
- 前几轮未修核销清单（如有；只确认状态，不重新推导）：<PREVIOUS_FOLLOWUPS_PATH>

禁止读取：
- 任何历史 scan.md、review 报告、todo 台账中的评审结论
- 其他面板角色的输出
- 任何 expected/ 目录

任务：
0. **先跑机械门**：`anchor-resolve.sh`、`doc-code-map.sh`、`doc-structure-check.py`、
   `doc-ref-check.sh`、`doc-style-lint.sh`、`doc-citation-check.py`。工具能判定的，
   直接引用读数；你的任务是补工具不能判定的语义核对，不要用手工重做已机械化的项。
1. 锚点与路径：文档中的每个事实断言是否有可解析的符号锚点或来源锚点；相关代码路径是否存在。
2. 文档-代码同步七项：静态可变、路径、常量、内部 TODO、符号锚点、工作区前缀、测试计数。
3. 测试名对账：文档声称的每个测试函数是否真实存在；测试数量与实测是否一致。
4. 常量、签名、行为合同：函数参数个数、返回类型、错误码、结构体字段是否与源码一致。
5. 引文块：声明逐字引用的代码块是否与现行源码逐字一致；节选是否标注了省略。
6. 覆盖率缺口：文档声称覆盖的 C 函数与 Rust 实现中，哪些没有对应说明。
7. 反事实前提：文档中的“如果反过来想”或类似反事实，前提是否真实存在。
8. 阴性声明：每个检查写“扫了什么、发现数、N=0 时不覆盖什么”。

输出格式（写到 <PANEL_PATH>/fact.md）：
## FINDING FACT-<NN>（P<N>）
- 位置：<文档路径与节号；必要时给源码路径与符号>
- 严重度：P0/P1/P2/P3
- 问题：<一句话>
- 影响：<读者会因此误解什么，或哪个结论失去依据>
- 证据或推理：<命令与输出摘要，或源码位置；证据强度标 E1/E2/E3>
- 最小修复：<改哪一句、补哪个锚点、重跑哪个命令>
- 置信度：高/中/低
- 是否需源码核实：是/否
- 若我错了：<最可能的反例或我可能误读的地方>

纪律：
- 只读，不修改任何仓库文件。
- 没有证据的怀疑写”证据不足”，不要写成事实。
- 每条发现必须有位置；没有位置的发现直接删除。
- 每条发现必须写“对应判据”（规则/检查清单项）；纯偏好不报，或单独放在
  `## SUGGESTION` 下，不混入 `## FINDING`。
- 输出：按根因分组报全部准入项，不设固定条数；同一根因合并为一条；超过 40 个根因时
  在末尾给“未展开根因”清单（ID + 一句话），不丢弃。
```

### 4.3 P-DESIGN 第二遍：差异审查

> **单元级档位（V3.9）**：本次派发按 `review-units.py next` 的单元行数选档；首 edition 的整篇
> survey 仍按整篇行数。T2 的读者 C 必须读整篇，A/B 只读被派单元；高风险篇的 P-REFUTE 在章级触发。
>
> **D1 缺席时的回退（V3.4-r8，D-024 停跑 / <500 行档）**：D2 把基线换为「文档主张
> ↔ 源码事实」的独立第二遍（D02 R1 实践形态），并在 `loop §1` 记 VARIANCE。

```text
你是独立设计审查者。第一遍已经给出一版从 C 语义出发的设计；现在把它与现有 Rust 实现对照。

允许读取：
- 第一遍方案：<PANEL_PATH>/design-d1.md
- 现有 Rust 实现：<RELATED_RUST_PATHS>
- 目标文档的 Ch3 与 Ch4
- tools/trait-audit.py 的输出：<TRAIT_AUDIT_PATH>
- 项目关键约束：<AGENTS_CONSTRAINTS>

禁止读取：
- 作者对“为什么这样设计”的解释
- 任何历史评审结论、其他面板角色输出
- 任何 expected/ 目录

任务：
1. 差异表：第一遍方案与现有实现，在状态表达、身份、所有权、错误、并发、抽象边界、可测试性七个维度逐项对比。
2. 翻译残留：现有实现里哪些结构只是因为 C 这样写才存在；按“单实现依赖注入 trait、无状态 Manager、布尔或字符串状态机、哨兵返回值、clone 到能编译、对象图共享”分类。
3. 死抽象：哪些 trait、结构体、中间层今天已经不承担语义职责；用 trait-audit 的读数作事实，但要自己核实，不要机械判决。
4. 非法状态：哪些状态组合在类型上可表示、在语义上不可能。
5. 最小化机会：现有实现能否删掉整个层次、合并两个状态、去掉一个 trait，而不改变外部行为。
6. 每条结论给“接受 / 拒绝 / 需用户裁决”，并说明理由与代价。
7. 每条 FINDING 必须标分类（D-047）：`[MODERN]`（C 有此语义，换现代表达）/ `[DEL]`（C 没有此物，删翻译残留）/ `[ARCH]`（改变 boot 是什么：机制替换、新责任/字段/检查/策略）。`[ARCH]` 不是缺陷提案：写入 `## ARCH-PROPOSAL` 段（内容=扩张内容、[ARCH] 三处一致计划、不做会坏在哪、代价），主 agent 转记判决账（状态=待用户裁决，P0/P1/P2 阻断关轮、P3 不阻断）——不要写成 `## FINDING`，不要建议直接实施。

**减法优先（V3.6，C-32；本节第 5 项的可执行化）**：第 5 项不是可选小节。报告必须**先**给出
减法方案，再列加法方案，顺序不可颠倒（先看加法会被先入为主锚定）：

1. 对**每一个**你想新增的类型 / 字段 / trait / 层，先写它在「更少概念的替代方案」里的对应物——
   闭包、fn 参数、现有类型的既有能力、borrow checker 可拦住的约束，或干脆不做；
2. 减法方案与加法方案并列成表，两列都写清「保障强度」与「新增概念数」；
3. 只有当减法方案**确实拦不住**该故障时，才允许在 FINDING 里报加法提案，且必须写明
   「减法方案 X 为什么拦不住」——**填不出这一句的加法提案，视为报告不完整**。

**新增类型的准入（V3.6，C-31/C-33）**：你提出的任何类型级防御（newtype / token / 守卫字段 /
值对象），必须在 FINDING 里逐条回答 `review-code-checklist.md` §3.5 的三问（威胁模型 /
borrow checker 是否已拦住 / 最坏后果与理解成本计数），并核对该节的可判边界（静默性 + 可混淆面、
接反是否静默）。**可信链（本仓其他模块 → 内核）上的不变量用 `assert!`（fail-fast）是正确形态，不要提案改成类型或
`Result`；`debug_assert!` 在 release 被编译掉，只是开发期辅助，不算可信链保证**；只有外部 / 不可信输入才用
`Result` + 完整校验。

**教学概念账（V3.6，C-35）**：每个加法提案必须带一行成本账——新概念引入数 / 讲解增量（行） /
与既有叙事冲突。同等保障下「能让读者少记一个概念」的方案优先。

输出格式（写到 <PANEL_PATH>/design-d2.md）：
## DIFF-TABLE
| 维度 | 第一遍方案 | 现有实现 | 差异 | 判断 |

## SUBTRACTION-TABLE（V3.6，C-32）
| 加法提案 | 减法替代（闭包 / fn 参数 / 现有类型 / 不做） | 减法拦不住的理由 | 保障强度对比 | 新增概念数 | 采纳 |
> 最后一列只填 `是` 或 `否`（整格精确值）。`metrics.md` 的 `减法: 采纳` 必须等于本列 `是`
> 的行数——门会交叉校验（V3.6-r6）。填 `不是`/`未采纳` 一律按 `否` 处理。

## FINDING DESIGN-<NN>（P<N>）
- 位置：
- 严重度：P0/P1/P2/P3
```

### 4.3b P-SUBTRACT 减法倡导者（触发式；V3.6，C-37）

- 全 0 = 可关闭；任一非 0 = 该轮不得判 CONVERGED/ROUND-CLOSED；

- V3.5 及更早的回执不追溯（已封存，门保留旧启发式只求不误伤）。

## 六、只读纪律与违规判定

- 面板角色不得修改 `os/`、`minix3/`、`rewrite-notes/`、`prompt/` 下的任何文件；只能写自己的 `tmp/review-eval/<stage>/<doc-stem>/panel/<role>.md`。
- 面板运行前后，主 agent 各跑一次 `git status --porcelain`。如果出现面板运行前没有的改动，判该角色违规：丢弃它的输出，检查 diff，必要时重跑。
- 面板角色读取了禁止材料并在报告中承认的，该角色本轮输出作废；如果它没有承认，但报告里出现只有禁止材料才可能知道的内容，同样作废。
- 读者角色读到了 `expected/` 或源码，本轮读者结论不计入独立性指标。

## 七、成本分级

| 条件 | 配置 |
|---|---|
| 文档少于 500 行 | 读者合并为 A+B 一次，C 一次；设计只跑第二遍（D2） |
| 文档 500 行及以上 | **读者 A、B、C 各自独立全文**；关联代码少于 2000 行时设计只跑 D2，2000 行及以上跑 D1+D2 |
| 关联代码少于 500 行且文档少于 500 行 | 可以只跑 P-FACT 与一个合并读者角色；但必须在 `loop.md §1` 写明缩编理由与风险 |
| 高风险篇目（启动链、IPC、内存管理、时钟中断） | 全角色；反证角色强制启动；读者三角色强制独立 |

缩编不是默认选项；每次缩编都要在轨迹里写明“本轮没跑哪个角色、因此可能漏什么”。

**判据优先级（V3.4-r7）**：读者档只按文档行数判；设计档按关联代码行数判（≥2000
→ D1+D2，<2000 → 只 D2）——但档位表第一行（文档 <500 行）优先于设计档判据：
<500 行的篇目无论代码量只跑 D2；高风险行覆盖其余行。本表是档位唯一源
（`review-loop.md` L1 只引用不重抄数值）。

**读者合并的硬边界（2026-11-17 用户裁决）**：500 行及以上的文档，读者 A/B/C 不得合并。
2026-11-12 前后 D02–D04 曾按 `review-loop.md` L1 的旧档位把 500–1500 行文档的
A/B/C 合并成一个 agent，并在报告里只标 `VARIANCE`；这是**降档**，不是等价配置：
合并后三角色共享同一上下文，B 的结构视角与 C 的因果视角互相锚定，A 的“卡在哪”
也不再是独立信号。D04 R2 的 14 条读者项全部来自合并角色、且主 agent 只能靠机械门复核，
就是这条降档的代价。此后 500 行及以上一律分角色；如果确实要合并，必须在
`loop.md §1` 写 `VARIANCE + 降档理由 + 用户批准日期`，否则该轮 `轮结果` 最多
`NOT CONVERGED`。

## 九、禁止事项

- 禁止把面板当成“多找几个人投票”；冲突按证据裁决，不按人数。
- 禁止把面板发现直接当修复清单；必须先归因、查冻结决策、判范围。
- 禁止让读者角色读源码后再自称“读者”。
- 禁止让设计角色在看过现有实现后自称“独立设计”。
- 禁止用面板替代机械门；面板是补充，不是 Gate 的替代品。
- 禁止把面板输出原样贴进正式文档或提交信息；先归因，再决定哪些进入轨迹、哪些进入修复。
