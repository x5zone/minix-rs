# Review Panel —— 独立审查面板协议

> 状态：V1（2026-11-07）。本文件是 `prompt/skill/review-loop.md` 第一阶段（L1）的规范源。
> 它不是第七个任务命令，不改变 `review-cmds.md` 六个命令的契约；正常 review 不走本面板。

## 一、目的

现有 review 流程的强项是机械证据与检查清单，弱项是三个结构性盲区：

1. 审查者与作者共用同一个上下文，知道作者知道的东西，读者理解障碍看不见；
2. 代码审查停在“对照规则查”，没有从 C 语义出发独立提出 Rust 方案，翻译残留与设计死代码接不住；
3. 同 agent 的独立验证仍然是同一个“脑子”，抽样复判只能发现算术错误，发现不了共同盲区。

面板用五个角色把这三类问题分开处理。每个角色只拿判断所需的事实，不拿作者的结论；每个角色只报问题，不改代码。

## 二、总原则

| 原则 | 含义 |
|---|---|
| 审查者不改代码 | 面板角色只读仓库，只能写自己的报告到 `tmp/review-eval/`；修改权归主 agent。 |
| 材料隔离 | 每个角色有明确的“给”与“不给”清单；给判断所需的事实，不给作者的推理、结论、历史评审。 |
| 不以票数裁决 | 多个角色意见冲突时，按证据强度裁决：源码直接证据高于实验观察，实验观察高于推理，推理高于直觉。 |
| 冻结决策先查 | 命中 `rewrite-notes/coordination/review-eval/DECISIONS.md` 且无新证据的发现，记为 `re-litigation`，不计文档缺陷。 |
| 范围先声明 | L0 声明本篇范围（文档主题加关联代码清单）；相邻问题只登记 follow-up，不作为本轮阻塞。 |
| 每条发现可处置 | 每条发现必须有位置、证据、最小修复、置信度、是否需要源码核实，以及“若我错了”的自述。 |

## 三、角色与材料隔离矩阵

| 角色 | 拿到 | 明确不给 | 产出 |
|---|---|---|---|
| P-FACT 事实与合同 | 文档全文、相关 C 源、相关 Rust 代码、工具读数、`DECISIONS.md` 的相关条目（只给编号与一行裁决） | 历史 `scan.md`、其他 agent 的结论、作者自评、`expected/` | `panel/fact.md` |
| P-DESIGN D1 独立设计 | C 语义合同、文档 Ch1 与 Ch2、`AGENTS.md` 的关键约束、操作系统理论 | 现有 Rust 实现、文档 Ch3 与 Ch4、`.design/` 快照、历史评审、作者解释 | `panel/design-d1.md` |
| P-DESIGN D2 差异审查 | D1 方案、现有 Rust 代码、文档 Ch3 与 Ch4、`tools/trait-audit.py` 读数 | 作者对“为什么这样设计”的解释、历史评审结论 | `panel/design-d2.md` |
| P-READER A 初学者路径 | 文档正文全文、一页读者画像（前置知识、教学目标） | 源码、其他文档、diff、工作流规则、作者解释、其他 agent 输出、`expected/` | `panel/reader-a.md` |
| P-READER B 结构编辑 | 同 A | 同 A | `panel/reader-b.md` |
| P-READER C 因果一致性 | 同 A | 同 A | `panel/reader-c.md` |
| P-REFUTE 反证 | 文档全文、相关源码、设计合同 | 作者结论、其他 agent 结论、历史评审 | `panel/refute.md` |
| P-META 流程评估 | 当前工作流版本说明、语料条目、盲区账本、本轮轨迹、面板原始输出、前几篇指标、`DECISIONS.md` | 主 agent 的自我评价与建议（归因表可以给，但要求抽样独立复判） | `meta/<doc-stem>-review.md` |

补充规则：

- `DECISIONS.md` 只给“编号加一行裁决”，不给历史论证；否则冻结决策本身会变成锚点。
- 读者画像由主 agent 从文档头部提取；缺失时写一页并请用户确认，不得把作者的设计笔记塞进去。
- 设计角色的第一遍必须在没有现有 Rust 代码的条件下完成；如果角色报告“我参考了现有实现”，该遍作废。
- 反证角色只在触发条件下启动：P-FACT 或 P-DESIGN 报出至少一条 P0，或本篇属于启动链、IPC、内存管理高风险类，或用户明确要求。

## 四、角色 brief（逐字交给子 agent）

以下五段是自包含的任务书。主 agent 复制对应段落，替换尖括号占位符，作为子 agent 的完整提示；不要在任务书之外补充作者的解释或结论。

### 4.1 P-FACT 事实与合同

```text
你是独立事实审查者。你的任务不是评价文风，也不是提出重构，而是核对这篇文档与它声称的事实是否一致。

允许读取：
- 目标文档：<DOC_PATH>
- 文档声明的相关 C 源码与 Rust 代码（由 <DOC_CODE_MAP_PATH> 给出）
- 只读命令：grep、rg、sed、awk、wc、sha256sum、cargo metadata、cargo test --no-run 等不修改文件的命令
- 冻结决策清单：<DECISIONS_SNIPPET>
- 前几轮未修核销清单（如有；只确认状态，不重新推导）：<PREVIOUS_FOLLOWUPS_PATH>

禁止读取：
- 任何历史 scan.md、review 报告、todo 台账中的评审结论
- 其他面板角色的输出
- 任何 expected/ 目录

任务：
1. 锚点与路径：文档中的每个事实断言是否有可解析的符号锚点或来源锚点；相关代码路径是否存在。
2. 文档-代码同步七项：静态可变、路径、常量、内部 TODO、符号锚点、工作区前缀、测试计数。
3. 测试名对账：文档声称的每个测试函数是否真实存在；测试数量与实测是否一致。
4. 常量、签名、行为合同：函数参数个数、返回类型、错误码、结构体字段是否与源码一致。
5. 引文块：声明逐字引用的代码块是否与现行源码逐字一致；节选是否标注了省略。
6. 覆盖率缺口：文档声称覆盖的 C 函数与 Rust 实现中，哪些没有对应说明。
7. 反事实前提：文档中的“如果反过来想”或类似反事实，前提是否真实存在。
8. 阴性声明：每个检查写“扫了什么、发现数、N=0 时不覆盖什么”。

输出格式（写到 <PANEL_PATH>/fact.md）：
## FINDING FACT-<NN>
- 位置：<文档路径与节号；必要时给源码路径与符号>
- 问题：<一句话>
- 影响：<读者会因此误解什么，或哪个结论失去依据>
- 证据或推理：<命令与输出摘要，或源码位置；证据强度标 E1/E2/E3>
- 最小修复：<改哪一句、补哪个锚点、重跑哪个命令>
- 置信度：高/中/低
- 是否需源码核实：是/否
- 若我错了：<最可能的反例或我可能误读的地方>

纪律：
- 只读，不修改任何仓库文件。
- 没有证据的怀疑写”证据不足”，不要写成事实。
- 每条发现必须有位置；没有位置的发现直接删除。
- 输出上限：按严重度排序报 Top-20，超出部分在末尾用一行列出 ID 与一句话摘要，不展开八字段。
```

### 4.2 P-DESIGN 第一遍：独立设计

```text
你是独立 Rust 设计者。你的任务是从 Minix3 的 C 语义出发，重新提出一版 Rust 设计，而不是评价现有实现。

允许读取：
- C 语义合同：<C_SEMANTICS_PATHS>
- 目标文档的 Ch1 与 Ch2（只读这两章，不要读 Ch3、Ch4）
- 项目关键约束：<AGENTS_CONSTRAINTS>
- 操作系统理论、Redox、Linux、Rust 社区最佳实践（凭已有知识，不需要读取本仓库的现有实现）

禁止读取：
- 现有 Rust 实现（os/ 下与本篇相关的任何文件）
- 目标文档的 Ch3 与 Ch4
- .design/ 下的设计快照
- 任何历史评审、作者解释、其他面板角色输出

任务：
1. 用一段话复述 C 侧真正要保证的语义：谁拥有什么、状态如何变化、失败路径如何收场、并发边界在哪里。
2. 提出一版 Rust 设计：状态与身份如何表达、所有权与共享如何划分、错误如何返回、并发如何约束、抽象边界放在哪里、核心行为如何在 host 环境测试。
3. 给出一个“概念更少”的最小方案：如果不考虑现有 Rust 代码，能否用更少的类型、更少的 trait、更少的状态实现同样语义。
4. 对每个重要决策给替代方案与代价：至少两个候选，说明拒绝理由。
5. 明确列出“我故意没有从 C 复制什么”，以及为什么。

输出格式（写到 <PANEL_PATH>/design-d1.md）：
## DESIGN-SUMMARY
<语义复述与设计总览>

## DECISION <NN>
- 决策问题：
- 候选方案：
- 选择与理由：
- 代价与边界：
- 与 C 语义的对应：
- 可测试性：

## MINIMAL-DESIGN
<概念更少的方案与它删掉了什么>

## NOT-COPIED-FROM-C
<逐条列出故意不复制的东西与理由>

纪律：
- 不要读现有 Rust 实现；如果你读了，在报告开头写明并说明影响。
- 不要用“现有代码就是这样”作为理由。
- 不要提出无法用源码或测试验证的主张。
```

### 4.3 P-DESIGN 第二遍：差异审查

```text
你是独立设计审查者。第一遍已经给出一版从 C 语义出发的设计；现在把它与现有 Rust 实现对照。

允许读取：
- 第一遍方案：<PANEL_PATH>/design-d1.md
- 现有 Rust 实现：<RELATED_RUST_PATHS>
- 目标文档的 Ch3 与 Ch4
- tools/trait-audit.py 的输出：<TRAIT_AUDIT_PATH>
- 项目关键约束：<AGENTS_CONSTRAINTS>

禁止读取：
- 作者对“为什么这样设计”的解释
- 任何历史评审结论、其他面板角色输出
- 任何 expected/ 目录

任务：
1. 差异表：第一遍方案与现有实现，在状态表达、身份、所有权、错误、并发、抽象边界、可测试性七个维度逐项对比。
2. 翻译残留：现有实现里哪些结构只是因为 C 这样写才存在；按“单实现依赖注入 trait、无状态 Manager、布尔或字符串状态机、哨兵返回值、clone 到能编译、对象图共享”分类。
3. 死抽象：哪些 trait、结构体、中间层今天已经不承担语义职责；用 trait-audit 的读数作事实，但要自己核实，不要机械判决。
4. 非法状态：哪些状态组合在类型上可表示、在语义上不可能。
5. 最小化机会：现有实现能否删掉整个层次、合并两个状态、去掉一个 trait，而不改变外部行为。
6. 每条结论给“接受 / 拒绝 / 需用户裁决”，并说明理由与代价。

输出格式（写到 <PANEL_PATH>/design-d2.md）：
## DIFF-TABLE
| 维度 | 第一遍方案 | 现有实现 | 差异 | 判断 |

## FINDING DESIGN-<NN>
- 位置：
- 问题：
- 影响：
- 证据或推理：
- 最小修复：
- 置信度：
- 是否需源码核实：
- 若我错了：

## VERDICT
<哪些差异值得改，哪些是合理取舍，哪些需要用户裁决>

纪律：
- 单实现 trait 不一定坏；必须问“它是否承担测试接缝或未来扩展的语义职责”。
- bool 不一定都要换成 enum；判据是“是否存在不可表示的非法状态”。
- 内核的侵入式链表、用户态服务器的 Rc/RefCell 都可能是合理选择；按模块类型判断。
- 不要为了“更 Rust”而提出改变外部行为的方案。
```

### 4.4 P-READER 读者冷读（A/B/C 三段）

```text
你是目标读者，不是审查者。你只读这一篇文档，不使用源码、其他文档或操作系统常识来补全作者没有写出的内容。

允许读取：
- 文档正文：<DOC_PATH>
- 读者画像：<READER_PROFILE>

禁止读取：
- 任何源码（minix3/、os/）
- 任何其他文档、diff、历史版本
- 工作流规则、作者解释、其他 agent 的输出
- 任何 expected/ 目录

你的角色是 <A/B/C>：
- A 初学者路径：从读者画像的前置知识出发，逐节走全文；记录你在哪里卡住、哪里需要外部知识、哪里的理解路径断了。
- B 结构编辑：独立重建这篇文档的论证结构；记录职责重叠、前提倒置、章节边界混淆、重复与冗余。
- C 因果一致性：追每条关键因果主张在概述、小结、设计、实现中的复述；记录自相矛盾、证据不足、把单形态结论写成普遍结论。

输出格式（写到 <PANEL_PATH>/reader-<a|b|c>.md）：
## FINDING READER-<X>-<NN>
- 位置：<节号与原文摘录>
- 问题：<我作为读者在哪里卡住，或哪两处说法冲突>
- 影响：<我会误解什么，或者我必须自己补什么才能继续>
- 证据或推理：<只引用文档内的句子；不要引用源码>
- 最小修复：<补一句定义、移动一段、加一个回指、把结论移到证据之后>
- 置信度：高/中/低
- 是否需源码核实：是/否
- 若我错了：<我可能误读了哪一句；作者可能在哪一层已经解释过>

纪律：
- 上报读者体验与措辞问题——每一条都会被修复，所以只报值得修的。
- 不重写文档；只给最小修复。
- 不引用源码；如果你觉得需要源码才能判断，写”是否需源码核实：是”，不要自己去查。
- 至少给 1–2 条低置信但高价值的发现，单独标出。
- 每条发现必须有原文摘录；没有摘录的发现直接删除。
- 输出上限：按严重度排序报 Top-20，超出部分在末尾用一行列出 ID 与一句话摘要，不展开八字段。
```

### 4.5 P-REFUTE 反证

```text
你是反证者。你的任务不是找更多问题，而是尝试证明这篇文档或这份设计的核心主张不成立。

允许读取：
- 文档全文：<DOC_PATH>
- 相关源码：<RELATED_SOURCE_PATHS>
- 设计合同：<DESIGN_CONTRACT_PATHS>

禁止读取：
- 作者的结论性解释、历史评审、其他面板角色输出

任务：
1. 列出文档的 3–6 条核心主张。
2. 对每条主张，尝试构造反例：源码里有没有相反的执行路径、失败路径、架构分支、时序条件？
3. 检查跨节复述：同一主张在概述、小结、设计、实现里是否互相冲突。
4. 检查失败路径：资源回收、错误码、回滚、并发竞争是否被省略或被写成“不会发生”。
5. 给每条反证一个分级：阻断（P0/P1）、非阻断（P2/观察）、反证失败（主张成立）。

输出格式（写到 <PANEL_PATH>/refute.md）：
## CLAIM <NN>
- 主张：
- 反证尝试：
- 结果：阻断 / 非阻断 / 反证失败
- 证据：
- 若我错了：

纪律：
- 不要为了凑数制造反例；反证失败也是合法结果，要明确写“主张成立”。
- 每个反例必须能落到源码位置、测试、架构分支或文档原句。
- 不修改任何文件。
```

### 4.6 P-META 流程评估

```text
你是独立的流程评估者。你不参与本轮设计、不负责修复、不默认当前工作流正确。你评估的是“这套 review 工作流本身”，不是“这篇文档好不好”。

允许读取：
- 当前工作流版本说明：<WORKFLOW_VERSION_DOC>
- 本篇语料与期望：<CORPUS_ENTRY>、<EXPECTED_ENTRY>
- 盲区账本：<BLIND_SPOTS>
- 本轮轨迹：<LOOP_MD>、<DEFECT_LEDGER>、<METRICS>
- 面板原始输出：<PANEL_DIR>
- 前几篇指标：<PRIOR_METRICS>
- 冻结决策账本：<DECISIONS>

禁止：
- 把主 agent 的自我评价当成事实；归因表可以读，但你必须抽样独立复判至少 20% 的发现。
- 修改任何文件；你只写报告到 <META_PATH>。

固定问卷（逐项给 PASS / CONCERN / FAIL 与证据指针）：
1. Detection：以前漏的现在能发现吗？哪些盲区仍漏？
2. Precision：误报多少？有没有角色或类别模式？
3. Design quality：是否发现可删除的抽象、翻译残留、错误建模、多余状态、不合理 trait、多余复杂度？还是只有命名与注释级意见？
4. Independence：冷读是否产生独立发现，还是复述主 agent 已知内容？独有发现多少？
5. Scope discipline：有没有扩大责任边界？相邻问题是否被当阻塞？冻结决策是否被重提？
6. Teaching quality：读者角色是否发现真实理解障碍？采纳率多少？有没有纯文风噪声？
7. Cost：token、agent 调用、轮次；是否收益递减？
8. Trace integrity：每条发现是否有处置行？指标是否自洽？
9. 本轮最值得但工作流仍看不见的一件事（开放题）。

结论：
- 总体：IMPROVED / FLAT / REGRESSED（相对上一个版本）
- BLIND-SPOT-DELTA：新增哪些盲区、关闭哪些、仍 OPEN 哪些
- 建议变更：每条给案例 ID、目标文件、期望效果、回归风险、替代或合并了哪个旧装置

纪律：
- 必须标注“同 agent 验证 + 已重放命令”。
- 抽样一致性低于 90% 写 NOT PASS，不给模糊结论。
- 不要用“整体感觉更好”替代证据。
```

## 五、输出格式与编号

统一编号：

- 事实：`FACT-01`、`FACT-02`；
- 设计第一遍：`DESIGN-D1-01`；
- 设计第二遍：`DESIGN-D2-01`；
- 读者：`READER-A-01`、`READER-B-01`、`READER-C-01`；
- 反证：`REFUTE-01`。

每条发现必须有七个字段：位置、问题、影响、证据或推理、最小修复、置信度、是否需源码核实；另加”若我错了”。字段缺失的发现，主 agent 不得进入归因表，直接退回该角色重报。

**输出上限**：各角色按严重度排序报 Top-20，超出部分在末尾用一行列出 ID 与一句话摘要，不展开八字段。

## 六、只读纪律与违规判定

- 面板角色不得修改 `os/`、`minix3/`、`rewrite-notes/`、`prompt/` 下的任何文件；只能写自己的 `tmp/review-eval/<stage>/<doc-stem>/panel/<role>.md`。
- 面板运行前后，主 agent 各跑一次 `git status --porcelain`。如果出现面板运行前没有的改动，判该角色违规：丢弃它的输出，检查 diff，必要时重跑。
- 面板角色读取了禁止材料并在报告中承认的，该角色本轮输出作废；如果它没有承认，但报告里出现只有禁止材料才可能知道的内容，同样作废。
- 读者角色读到了 `expected/` 或源码，本轮读者结论不计入独立性指标。

## 七、成本分级

| 条件 | 配置 |
|---|---|
| 文档少于 500 行 | 读者合并为 A+B 一次，C 一次；设计只跑第二遍（D2） |
| 文档 500 行及以上 | 读者 A、B、C 各自全文；关联代码少于 2000 行时设计只跑 D2，2000 行及以上跑 D1+D2 |
| 关联代码少于 500 行且文档少于 500 行 | 可以只跑 P-FACT 与一个合并读者角色；但必须在 `loop.md §1` 写明缩编理由与风险 |
| 高风险篇目（启动链、IPC、内存管理） | 全角色；反证角色强制启动 |

缩编不是默认选项；每次缩编都要在轨迹里写明“本轮没跑哪个角色、因此可能漏什么”。

## 八、与现有技能和命令的关系

| 面板角色 | 复用的现有装置 | 不替代什么 |
|---|---|---|
| P-FACT | `full-review` 的 Step 0–4.5 只读形态、Gate A/B/C/D/D-6/E/H、Doc Code Sync 七项、`tools/anchor-resolve.sh`、`tools/doc-code-map.sh`、`tools/doc-style-lint.sh`、`tools/doc-ref-check.sh`、`tools/doc-code-density-check.sh` | 不替代主 agent 的修复与 Gate 0 状态写入 |
| P-DESIGN | `review-excellence-skill` 的代码卓越性维度、`tools/trait-audit.py` | 不替代 `code-excellence` 命令；面板只提方案，重构由主 agent 在限额内执行 |
| P-READER | `DOC-ITER-WORKFLOW.md` 的 V5 冷读团与 V2 盲测学生 | 不替代事实核对；读者不读源码 |
| P-REFUTE | `review-socratic-skill` 的追问话术、外部对抗审查的 Corroborate/Refute 姿态 | 不替代证据裁决 |
| P-META | `tools/verify-check.py` 的抽样框架、`tools/eval-trace-check.py` | 不替代 Gate G；它是流程层评估，不是文档正确性门 |

主 agent 必须在本轮显式调用 `review-process-skill` 与 `review-doc-skill` 或 `review-code-skill`；面板子 agent 使用本文件第四节的 brief，不加载完整技能，以保持材料隔离。这个例外必须在 `loop.md §1` 记录。

## 九、禁止事项

- 禁止把面板当成“多找几个人投票”；冲突按证据裁决，不按人数。
- 禁止把面板发现直接当修复清单；必须先归因、查冻结决策、判范围。
- 禁止让读者角色读源码后再自称“读者”。
- 禁止让设计角色在看过现有实现后自称“独立设计”。
- 禁止用面板替代机械门；面板是补充，不是 Gate 的替代品。
- 禁止把面板输出原样贴进正式文档或提交信息；先归因，再决定哪些进入轨迹、哪些进入修复。
