# Review Evals —— 语料、轨迹、指标与收敛

> 状态：V1（2026-11-07）；V3 修订（2026-11-10，§4.0b–§4.0e 轮次交易/缺陷身份/批次复验/读者清单，§6A 收敛判据，§7 edition 纪律）。
> 本文件是 `prompt/skill/review-loop.md` 的评测规范，也是 `rewrite-notes/meta/coordination/review-eval/` 的数据契约。
> 它不改变六个任务命令的现有规则；它规定“怎么判断工作流本身有没有进步”。

## 一、目的

“这一轮评审感觉更认真了”不是进步证据。可验证的进步至少需要三样东西：

1. 固定语料：同一批案例反复跑，避免用更简单的文档制造进步；
2. 完整轨迹：每条发现都有来源、证据、处置与复验，不能只留下“已修复”三个字；
3. 独立评估：由一个不参与本轮设计和修复的冷启动评估者，按固定问卷判断。

本文件定义这三样东西的格式与判据。

## 二、语料契约

### 2.1 条目类型

| 类型 | 前缀 | 用途 | 运行时机 |
|---|---|---|---|
| 真实篇目 | `D` | 文档加关联代码的完整循环 | 每篇一次 |
| 回归切片 | `R` | 历史缺陷的定向复现 | 每个版本边界 |
| 对抗样本 | `T` | 合成阳性、阴性、范围陷阱 | 每个版本边界 |

### 2.2 每条必填字段

- `ID`：唯一编号；
- `制品路径`：文档或样本文件；
- `形态`：启动链、服务事件循环、库、集合等；
- `关联代码`：由 `tools/doc-code-map.sh` 产出的路径清单，或明确写“无”；
- `期望发现`：引用 `BLIND-SPOTS.md` 的盲区编号与期望探测器；
- `负期望`：明确写出“不许报什么”，用于测误报与范围纪律；
- `成本预算`：允许的面板角色数、修复轮数、agent 调用数；
- `上次结果`：命中、漏报、误报三项计数。

### 2.3 语料不可静默修改

新增条目可以随时加。修改已有条目的期望发现或负期望，必须在 `WORKFLOW-VERSIONS.md` 的版本表里写明“为什么原来的期望不成立”，否则视为为了让本轮好看而改题。

## 三、轨迹契约

### 3.1 目录

每轮轨迹必须含**判决与收口记录**（2026-11-09 用户裁决 P-1 晋升）：

- `### L6` 小节：meta 结论与 BLIND-SPOT-DELTA；
- `### L6.5` 小节：资源重读三问三去处（检测模式 → BLIND-SPOTS；流程改进 → 候选规则表，不当轮实施；立即可用清单 → 下一轮修复批）；
- **判决字段**（8 字段，`reviewer_verdict` 与 `user_decision` 分列，不得覆盖独立回读的 NOT PASS）：`decision_id` / `reviewer_verdict` / `user_decision` / `decision_reason` / `scope` / `implementation_status` / `evidence` / `reopen_condition`。

### 3.2 目录（历史格式）

每篇一份：

```
rewrite-notes/meta/coordination/review-eval/runs/<stage>/<doc-stem>/
  loop.md
  metrics.md
  defect-ledger.md
  follow-ups.md
```

原始输出：

```
tmp/review-eval/<stage>/<doc-stem>/panel/<role>.md
tmp/review-eval/<stage>/<doc-stem>/logs/
```

**V3.5 制品链（`schema: V3.4` 起的新篇目，以及 V3.3+ 且尚未 FREEZE 的文档）**：面板原始输出与 certify 独立回执不再是
一次性 tmp 产物，必须**入库**并在轮关闭时由门校验：

- 面板：`runs/<stage>/<doc-stem>/panel/round<N>/*.md` + `INDEX.md`（由
  `python3 tools/panel-index.py <dir>` 生成，逐文件 sha256 + FINDING/SUGGESTION/CLAIM
  计数）；`--check` 不一致即门 FAIL。tmp 只作工作副本。
- 回执：`runs/<stage>/<doc-stem>/certify/round<N>-*.md`（独立冷读输出原文）。
- 伪造因此需要伪造**完整且哈希自洽**的制品链，且任何不一致（改动未重生成索引、
  新增未入索引、回执缺失）可机械发现。01–04 已 FREEZE 的历史轮不追溯。

### 3.2 `loop.md` 固定九节

标题必须逐字包含以下九个二级标题，供 `tools/eval-trace-check.py` 解析：

```markdown
## §0 基线
## §1 面板
## §2 发现
## §3 归因
## §4 修复
## §5 复验
## §6 指标
## §7 状态
## §8 给 meta-review 的不确定点
```

各节最小内容：

| 节 | 必须写什么 |
|---|---|
| §0 | commit、文档 sha256、行数、范围声明、关联代码清单路径、语料条目 ID |
| §1 | 角色清单、每个角色拿到与没拿到什么、模型、起止时间、原始输出路径；缩编时写缩编理由与风险 |
| §2 | 每条发现的 ID、来源角色、严重度、类别、位置、证据、建议；可以引用面板原文，但必须保留 ID |
| §3 | 每条发现的处置类、理由、证据强度、冻结决策检查结果、范围类（in-scope / adjacent） |
| §4 | 每条修复的 ID、文件、diff 摘要、测试证据、fix-guard 记录 |
| §5 | 修复段回读、台账重放、机械门读数、回归扫描、QEMU 结果（如适用） |
| §6 | 指标摘要，与 `metrics.md` 一致 |
| §7 | `CONVERGED` 或 `NOT CONVERGED`；未收敛时列 design-debt 与 carry-over |
| §8 | 本轮自己也不确定的地方，供 meta-review 重点检查 |

### 3.3 `defect-ledger.md` 表格式

表头必须包含以下列名：

```markdown
| 发现 ID | 来源角色 | 严重度 | 类别 | 处置类 | 处置 | 证据 | 复验 |
```

规则：

- `发现 ID` 必须与面板报告里的 `## FINDING <ID>` 完全一致；一行可以放多个 ID，用顿号或逗号分隔；
- `严重度` 必须与面板 `## FINDING <ID>（P<N>…）` 标题机械同步（V3.3）：R30 曾把面板的
  P0 记成台账 P1/P2 且整轮无 P0 行——列分叉即 `severity-sync` FAIL；
- `处置类` 只能是 `①` / `②` / `④` / `⑤` / `⑥` / `FP` / `SUGG`（V3.3 起，见下条），或对应的英文标记 `fix` / `transfer` / `wording` / `insufficient` / `refactor` / `false-positive`；
- **`③` 已删除，不再接受**。误报只能写 `FP`，且 `证据` 列必须给出源码、测试或文档原文的反证；没有反证的“误报”按 `⑤` 未闭环处理，不得当作已处置。**`SUGG`（V3.3 起）为合法处置类**（**形状契约，V3.4-r11**：面板标头必须是
`##/### SUGGESTION <ASCII-ID>`（ID 字符集与 FINDING 同，含下划线）——与 FINDING 同规则；
无 ID 的聚合段落是散文，不计入 INDEX/发现总数/覆盖率）：限读者/设计角色的 P3 建议与准入判据不全的读者/设计项——以 SUGG 行入台账、计入 metrics 的 `SUGG` 键与发现总数（七项之和），不参与 G1–G9；FACT/DESIGN 事实类证据不足写 `⑤`（V3.4-r8 与工具对齐）；
- `处置类` 为 `①` / `④` / `⑥` 的行，`复验` 必须非空，且不能是 `TBD`、`待定`、`-`；
- `处置类` 为 `②` 的行，`处置` 必须含“用户批准”和 `YYYY-MM-DD` 日期、去向批次/篇目；缺一项即按未批准计，阻断本轮关闭；
- `处置类` 为 `⑤` 的行，`处置` 必须写“还缺什么证据、去哪里取、谁负责”，且本轮不得判 `CONVERGED`；
- 没有处置行的发现，`eval-trace-check.py` 判 FAIL，L2 不允许进入 L3。

### 3.4 `metrics.md` 固定键

V3 固定键：

```markdown
- 发现总数: <整数>
- 唯一根因数: <整数>
- 本轮新准入: <整数>
- certify 新准入: <整数>
- 重复合并: <整数>
- 自引入: <整数>
- 处置: ① <整数> / ② <整数> / ④ <整数> / ⑤ <整数> / ⑥ <整数> / FP <整数> / SUGG <整数>
- 未闭环: <整数>
- 轮型: full | structural | confirmation
- 轮结果: ROUND-CLOSED | CONVERGED | NOT CONVERGED | NOT CONVERGING | FREEZE-WITH-BACKLOG | BLOCKED
- 代裁决: <整数>（V3.3 治理仪表）
- ARCH 提案: <整数>（V3.3 治理仪表；待用户裁决，不阻断）
- 用户否决: <整数>（V3.3 治理仪表；否决派生常规工作项）
- edition: V3.x
- re-litigation: <整数>
- adjacent 阻塞: <整数>
- 重构: 提出 <整数> / 接受 <整数> / 实施 <整数> / 登记 <整数>
- 减法: 提案 <整数> / 采纳 <整数>（V3.6，C-34：提案数 = design-d2 的 SUBTRACTION-TABLE 数据行数；采纳数 = 实际改掉的数量）
- 成本: agent <整数> / token <整数> / 耗时 <文本>
```

V2.5 过渡键（仅 R25 及以前）：`轮型: discovery | verification`、`新 in-scope 真缺陷`；
R25 收口时必须额外写 `- certify 新准入: 0`。

规则：

- `发现总数` 必须等于 `处置` 列出的**全部**计数项之和（V3.3 起含 SUGG 共七项——与工具 `check_metrics` 口径一致，V3.4-r7 废除本文件内五项/六项旧口径）；
- `发现总数` = 本轮原始发现 ID 数；`唯一根因数` = 本轮出现的不同 `根因 ID` 数；
  `本轮新准入` = 本轮 `origin` 首次出现的根因数；`certify 新准入` = certify 阶段首次
  出现的准入根因数。三个数分开报，禁止用一个数冒充另一个；
- `未闭环` 必须等于台账本轮逐行实际未闭环数（`⑤` + 未获用户批准的 `②` + 复验写“未修/待修/未实施”的 `①/④/⑥`）；`eval-trace-check.py` 会把声明值与台账聚合值交叉校验，手填 0 掩盖未修行直接 FAIL。本轮关闭时必须为 0；
- 轮次关账命令是 `eval-trace-check.py <run-dir> --round R<N>`：只检查该轮的覆盖、收口与未闭环。不带 `--round` 是全历史归档审计，历史轮次的旧格式/stale 面板不阻断当前轮，但不得删除历史证据来“变绿”；
- V3 的 `轮型` 只能是 `full` / `structural` / `confirmation`；出现 `discovery`/`verification` 即 FAIL。V2.5 过渡轮按旧键检查；
- `re-litigation` 是命中冻结决策且无新证据的发现数；
- `adjacent 阻塞` 是相邻问题被当成当前阻塞的发现数，目标为 0；
- `重构` 四项分别记录提出、接受、实施、登记的数量；
- `减法` 两键（V3.6，C-34）是反奖励回路：`提案` 来自 D2 的 `## SUBTRACTION-TABLE` 数据行数，
  `采纳` 必须等于 D2 `SUBTRACTION-TABLE` 的「采纳」列填 `是` 的行数（V3.6-r6：
  门做交叉校验，自报数与 D2 实物不符即 FAIL）。**有新增抽象提案（FINDING 带 `- 三问：` 字段）却
  `减法: 提案` 为 0 → 报告不完整（§4.3 纪律），按流程缺陷记入 `BLIND-SPOTS.md`**；
  **D2 显式声明「本轮无新增抽象提案」时 0 是合法零，不算缺陷**（V3.6-r4 修正：原口径把
  诚实零报告也记成流程缺陷，正好复刻 F1 惩罚诚实报告的错误）。连续两篇出现同一形态即按 §7.4 回退评估。
- 成本不能只写“若干”；没有 token 读数时写“未采集”，不要编造。

### 3.5 判决账（decision ledger，P-1）

用户裁决与审查者的独立结论必须分列，不能压成“某几条已修”。凡是用户裁决过的
事项（采纳、否决、接受风险、要求继续修），都要在
`rewrite-notes/meta/coordination/review-eval/DECISIONS.md` 的判决账表里落一行，
表头固定八列：

```markdown
| decision_id | reviewer_verdict | user_decision | decision_reason | scope | implementation_status | evidence | reopen_condition |
```

规则：

- `decision_id`：稳定编号（`D-01` 起；一轮内不复用）；
- `reviewer_verdict`：审查者/独立回读的原始结论（`PASS`、`NOT PASS`、具体异议），
  **用户裁决不得覆盖它**——用户接受风险时写 `user_decision: 接受（风险自留）`，
  `reviewer_verdict` 仍保留 `NOT PASS`；
- `user_decision`：用户最终裁决（采纳的选项、否决、搁置），与上一列分列；
- `decision_reason`：裁决理由（不是审查者理由）；
- `scope`：`in-scope` / `adjacent` / `cross-crate` / `workflow`；
- `implementation_status`：`待实施` / `已实施` / `移入 code-excellence` / `不实施`；
- `evidence`：可重放的命令、提交号或测试名；没有证据就写缺什么；
- `reopen_condition`：什么新证据可以重开；没有就写“无”。

账本同时保留历史散文条目（`D-001` 起）；新增条目一律用八列表格。PR 或轮次
收尾时，`implementation_status` 从“待实施”变为“已实施”必须同时填 `evidence`。

### 3.6 表结构与内部链接门（P-2 第一版）

文档 review 的机械门在原有五门之外，增加：

```bash
python3 tools/doc-structure-check.py <doc.md>
```

判据（第一版范围）：

- 表块连续性：每个表块以「表头 + 分隔行」开始，表体不得被空行劈开；表头与
  每一行的列数一致；
- 转义竖线（`\|`）与行内代码里的竖线不算分隔符；
- fenced code block（``` / ~~~）整块排除；
- 内部 `.md` 相对链接按**文档目录**解析；外链、纯锚点、代码块与行内代码里的
  示例不查；`#fragment` 剥掉后只解析文件；
- 第一版**不做**标题锚点校验与外部链接存活检查（锚点仍由 `anchor-resolve.sh`
  负责）。

检查器自身由 `--self-test` 的正负 fixture 驱动（合法表、空行劈表、列数不符、
转义竖线、fenced 排除、断链、代码内链接、锚点剥离）；fixture 失败视为门故障，
不是文档缺陷。CI 在 `rules-consistency.yml` 常驻执行自测与受审文档的正式检查。

## 四、归因契约

### 4.0 全修原则

范围内确认为真缺陷的发现——不论严重度是 P0、P1、P2 还是读者体验项——**一律本轮修**。不允许无档期转出。P-DESIGN 发现的可实施代码改进标 ⑥ 本轮实施（见 4.1）；确需跨 crate 协调的，在 `OPEN-DEBT.md` 立独立项目（带负责人与截止轮次），不得留评审欠账。每篇文档必须在收敛门通过后才进入下一篇；收敛门的第一条就是 `in-scope 待修 = 0`。`OPEN-DEBT.md` 只登记跨 crate 独立项目；`adjacent` 项登记在 `follow-ups.md` 并按 §4.2 不阻塞收敛——不得把相邻项写成 `OPEN-DEBT` 来阻塞本篇。

**架构级实施会使旧轮次的收敛结论失效。** 一旦本轮以 ⑥ 实施了跨 crate 的设计变更（`wire` 版本、所有权/借用模型、ABI 布局、分配器分区等），此前轮次的“零新增”只对**旧基线**成立：代码已经大改，旧结论不能拿来给新代码背书。此时必须重新固定基线（提交、文档行数/sha256、测试计数）、重跑受影响的文档门/宿主测试/QEMU，再判断 G8/G9；不允许用旧轮次结论宣告当前基线收敛，也不允许为了保留“已收敛”而推迟设计实施。

### 4.0a 轮型与收敛状态机（V2.5 历史；R25 及以前）

> 以下为 V2.5 历史条款，仅用于 R25 及以前已存在的轨迹；V3 起由 §4.0b 取代，
> 新文档和 01 的 R26 起不得再使用 discovery/verification 轮型。

每篇文档的循环只有两种轮型，**不允许无限重复全量发现轮**：

| 轮型 | 输入 | 角色 | 出口 |
|---|---|---|---|
| 发现轮（discovery） | 全文 + 关联代码 | 全角色（P-FACT A/B、READER A/B/C、REFUTE、DESIGN-D2；D1 按 D-024 停跑） | 全部 `①/④/⑥` 已修、`②` 有用户批准、`FP` 有反证、`⑤`=0、`未闭环=0`；然后**只能**进入验证轮 |
| 验证轮（verification） | 上轮修复 hunk、上轮未闭环项、随机 20% 未改章节、最终 HEAD 的 RB | P-FACT 定点、READER 定点（只读修改段及邻句）、RB；不跑全量 A/B/C、不跑全量 DESIGN | 新 in-scope 真缺陷=0 → `CONVERGED`； >0 → 在同一验证轮内修完并复跑 delta 验证；**不得开新轮**，也不得用 R(n+1) 承接 |

硬规则：

1. **发现轮之后不得再开第二个全量发现轮**。验证轮发现的新问题只修该问题；修完继续验证，不重开全量面板。
2. 验证轮最多在同一轮内跑 2 次 delta；第 2 次仍出现新的 P0/P1/P2/P3 真缺陷，写 `STUCK-REPORT.md` 并交用户裁决，不得新开一轮。**上一轮未闭环 >0 时，禁止出现下一轮小节；这条由 `eval-trace-check.py` 机械检查。**
3. 验证轮必须审**最终 HEAD**（含本轮所有修复提交）；审旧 sha 的回读不算。
4. RB/commit 回归的发现必须写入同一 `defect-ledger.md` 并计入 `未闭环`；只写在 loop 或 RB 报告里不算入账。
5. 收敛后写 `FREEZE.md`（文档 sha、HEAD、未闭环=0、验证轮证据）；之后只有用户明确要求或出现新证据才允许重开，不自动进入下一轮。
6. `meta PASS` 只表示流程运行质量，不等于文档 `CONVERGED`；`CONVERGED` 只能由验证轮出口给出。
7. **轮次收口必须可机械判定**：`## R<N>` 与旧 `# Round N` 两种标题都受 `### L6` / `### L6.5` 合同约束；`eval-trace-check.py --round R<N>` 必须为 0。收口检查不得只认旧标题，也不得让历史轮次的 stale 面板永久阻断当前轮。
8. **schema 标记从第一轮生效**：每篇 `loop.md §0` 必须写 `schema: V2.5 from R<N>`；01 写 `from R25`，02 及以后写 `from R1`。没有标记时 `--round` 直接 FAIL，防止新文档的 R1 落回旧 schema（允许 ③、无 `未闭环`、无限全量轮）。

### 4.0b 轮次交易模型（V3，2026-11-10 用户裁决）

V3 删除 `discovery` / `verification` 两种轮型。**一轮 = 一次完整的 review 交易**，在同一个
`edition`（规则版本）下完成四个阶段：

| 阶段 | 输入 | 产出 | 退出条件 |
|---|---|---|---|
| survey | 全文 + 关联代码 | 面板原始发现 | 所有角色报告已落盘 |
| inventory | 面板发现 | 去重后的根因台账 | 每条发现都有 `根因 ID`、`origin`、准入判据 |
| fix | 根因台账 | 分批修复 + 每批证据 | 每个根因有修复证据；每批 ≤20 个根因 |
| certify | 本轮全部修复 | 100% 复验 + 改动段冷读 + 机械门 | `open=0` 且 `certify 新准入=0` |

硬规则：

1. **下一轮只能在上一轮关闭后开**。上一轮 `open>0` 时禁止出现下一轮小节；这条由
   `eval-trace-check.py` 机械检查。
2. **每轮覆盖 = 未冻结单元 + 依赖闭包**（`review-units.md` §五）。首个 edition 的 full survey
   仍读整篇；后续轮只读未冻结单元；确认轮读未冻结单元 + ≥20% 冻结样本 + 骨架。脏单元 >30%
   或 T1 发现跨章结构问题时回退整篇。不存在“只查修复 hunk”的缩减轮；认证是同一轮的 certify
   阶段，不是新轮。R26 如果存在，就是新一轮完整 review。
3. **轮内可以多次 fix→certify**，但不得重开全量面板；certify 只读本轮改动段、
   未闭环项与受影响章节。第 2 次 certify 仍有新准入缺陷 → 继续在本轮修，不新开轮；
   同一根因连续两次修复后仍复发 → 该根因升级为设计问题，按 ⑥ 处理并记录原因。
   **第 3 次 certify 仍有新准入根因** → 该轮标 `BLOCKED`，写 `STUCK-REPORT.md`；
   不得用第 4 次 certify 自动循环，也不得开下一轮。
   **certify 型 BLOCKED 的解除——两级分流（V3.4 最小内核，R6-c 判例：解除协议此前
   缺位，BLOCKED 是单向死锁）**：
   - 第一级·独立冷读仲裁者：派一个未参与本轮修复的冷启动子 agent，只读 BLOCKED
     涉及的段与根因清单。仲裁通过 → 该根因按 certify 证据计入（仲裁回执落 §5），
     轮次可按正常出口关闭；
   - 第二级·用户病因讨论：仲裁不通过、或判定属规则/设计病 → 产出「病因讨论包」
     （复发段清单、自引入链、edition 史、候选病因假设、干预选项）交用户；**结论必须
     落 `DECISIONS.md` 八字段判决行后才能变更轮状态**——门不认识聊天（D-047 原则）。
     两级分流同时是升级配给：agent 可自解的 BLOCKED 不打扰用户。
   **BLOCKED 三型一览（V3.4-r7）**：① certify 三振（本条两级分流解除）；② `[ARCH]`
   P0/P1/P2（§4.1b——解除只认判决账行）；③ 同篇待裁决无授权（§4.1a——出路是当轮
   ⑥ 代裁或用户判决行）。三型解除的共同凭据 = `DECISIONS.md` 判决行或独立仲裁回执；
   解除后按原出口路径收口（certify 继续 / ⑥ 实施 / 判决改 FP），`轮结果` 的变更必须
   伴随 `--round` 门重跑通过——不得手改闭合态而不过门。
   **B 类根因（读者/设计/矛盾类）第二次出现时，修复必须是结构性重写**（整段/整小节），
   台账写 `rewrite` + 冷读 `CLOSED`；不得再用一句/一个指针的线级补丁。A 类事实项仍可线级修。
4. **轮关闭条件**：`未闭环=0`、`certify 新准入=0`、`### L6`/`### L6.5` 收口小节齐全、
   `eval-trace-check.py --round R<N>` 退出码 0。
5. **R25 过渡**：R25 在 `schema: V2.5 from R25` 下收口，不中途换规则；V3 从
   01 的 R26 或 02 的 R1 起生效。R25 的收口同样按本节的 certify 阶段执行（不另开 verification
   轮），这是唯一的一次性过渡条款。

**轮种（V3.3）**：`full`（完整 survey 交易）、`structural`（survey 输入 = 上一轮
已落盘的完整报告，主体是结构重写 + 机械再对账，不重开面板）、`confirmation`
（确认轮）。前两种是修改事务，占用 §7.5 的 3 轮预算；确认轮是收口阶段，不占修改
预算、每个 CONVERGENCE-CANDIDATE 最多 2 次（edition 更替或用户批准重开后重新计数），进入条件与退出条件见 §6A 四态模型。修改轮没有收敛声明权
（§6A）。

### 4.0c 缺陷身份与准入（V3）

**一行一个根因。** 台账行必须放在 `## R<N>` 编号节下（V3.4-r8 判例：无编号标题的
行对轮次作用域不可见——`--round` 的 coverage/未闭环/分档聚合全部跳过，等于阴影
账）。台账必须有以下列（V3 起）：

```markdown
| 根因 ID | 发现 ID | origin | 来源角色 | 严重度 | 类别 | 处置类 | 处置 | 证据 | 复验 |
```

- `根因 ID`：稳定编号（`RD-001` 起），跨轮不变；同一根因的多个面板发现共用一行，
  在 `发现 ID` 列用顿号列出。
- `origin`：根因首次出现的轮次（`R<N>` 或 `E<N>/R<N>`）；复发时写
  `origin: R<首见>；last_seen: R<本轮>`。**自引入缺陷的 origin 记引入轮，不是
  发现轮**（V3.3）：本轮修复引入、本轮 survey 抓到的同步债，origin 写引入它的
  那一轮（`自引入明细` 已点名引入轮，回填到 origin 列）——否则"本轮新准入"永远
  等于全部发现，跨轮身份失真（R30 判例：3 条 R29 自引入债全部记 origin R30）。
- 同一根因只保留一行；如果出于历史原因保留逐发现行，必须在 `处置` 列写
  `dup-of: RD-xxx`，且该行不计入 `唯一根因数`。没有 `dup-of` 的独立行必须能说明为什么
  是不同根因。`eval-trace-check.py` 对 V3 检查根因 ID 唯一性与 `origin` 完整性。
- 复发不产生新行、不计入“新准入”；只更新 `last_seen` 与复验证据。
- `metrics.md` 每轮块：`发现总数` = 本轮原始发现 ID 数；`唯一根因数` = 本轮出现的不同
  `根因 ID` 数；`本轮新准入` = 本轮 `origin` 首次出现的根因数。三个数分开报，禁止用
  一个数冒充另一个。

**准入判据**（四条全满足才进台账）：

1. **位置**：能落到文档节号、源码符号、测试名或命令输出；
2. **判据**：能映射到一条规则、检查清单项或读者验收清单项
   （`review-doc-checklist.md`、`review-code-checklist.md`、§4.0e 或 `DECISIONS.md`）；
3. **证据**：E1/E2 级证据，或 E3 级完整推理链；纯“我觉得可以更好”不满足；
4. **反证**：写了“若我错了”的具体反例或检索路径。

不满足四条的，面板可以照报，但主 agent 记入
`runs/<stage>/<doc-stem>/suggestions.md`。**SUGG 行的适用范围（V3.4-r8，与工具
`check_v33_admission` 一致）**：读者/设计角色的 P3 建议，或读者/设计项准入判据
不全者——以 SUGG 行入台账登记、计入 metrics 的 `SUGG` 键与发现总数，不进阻断集、
不阻塞收敛。FACT/DESIGN 的事实类证据不足写 `⑤`（不得用 SUGG 逃避未闭环）。
`suggestions.md` 每条给位置、建议、为什么暂不修；下一次 edition 边界可以
把其中反复出现的模式晋升为规则或读者验收清单项。这是“读者偏好”的合法出口，不是
`③` 桶的复活：suggestions 不声称是缺陷，也不参与 G1–G9。

**读者/设计项的严重度门槛（V3.3）**：READER 与 DESIGN 角色的 P3 发现默认不满足准入判据第 2 条——
"措辞/指针/计数枚举可以更好"不等于"读者卡住无法继续"。只有读者明确**卡住无法继续**
（理解路径断裂、必须外部知识才能往下读）的 P3 才准入台账，且按非阻断 backlog 处理、
不参与 G1–G8；其余一律 `suggestions.md`。R30 的台账 70% 是 P3、R31 仍产出约 28 条
P3，而 §6A 旧 G3 要求"准入 P3 = 0"——这是不可达判据，本条取代它。

### 4.0d 修复批次与 100% 复验（V3）

- 每批最多 **20 个根因**；同一根因的多条发现算一个。批内不混无关改动，批与批之间
  commit。
- **B 类/复发根因按“段”成批**：同一段/小节被报 ≥2 个根因，或同一根因第二次出现，
  该批必须重写整段/整小节（`rewrite`），不是把若干句分别打补丁；A 类事实项可线级修。
- **100% 复验**：每个根因都要有可重放的复验（旧串全篇 grep 归零 / 测试名 + 输出 /
  源码逐字对照 / 冷读回执），不抽样。R24 的 114 条只抽 29 条、R25 的 98 条只抽 46 条
  是 V3 明确禁止的做法。
- 代码改动触及 pub 签名/结构体字段/常量时，必须跑 `tools/doc-symbol-drift.sh`；
  文档引文块改动必须跑 `tools/doc-citation-check.py`。两者是 commit 门，不是下一轮
  面板的发现项。
- **代码批→文档同步清单（V3.2 硬步骤，FACT-B-01/02 判例）**：代码批触及行为/签名/
  常量时（无论是否删符号），certify 必须跑
  `doc-symbol-drift.sh <doc> --stale-lines <批前 rev> --strict`——`let _ =`→`match`
  这类行为改动不删任何符号，`--from-diff` 的标识符粒度扫不到；任一命中 = 本轮
  同步债，修完才许关轮。`节选` 引文块只允许省略、不允许改写
  （`doc-citation-check.py` V3.2 起逐行对账；显式声明 改写/示意/反例 的块豁免）。
- 修复引入新缺陷：该批回退，按 20 个根因上限重做；同一根因连续两次修复仍复发，
  升级为设计问题（⑥），不再用措辞修复打补丁。

### 4.0e 读者验收清单（V3，固定清单）

每个 edition 固定一份读者验收清单；P-READER 只按清单报，清单内全部本轮修，清单外
记 `suggestions.md`。首版清单（V3.0）：

1. 术语首次使用前有定义或可回指的首次定义；
2. 每个因果主张能在同节或回指节找到证据；
3. 每个“因为/所以/因此”有前提，不把单形态结论写成普遍结论；
4. 计数、编号、版本号只有一个权威口径，跨节引用同一口径；
5. 指针（节号/符号/表号）不落空、不反向、不自指；
6. 每节标题与内容一致，节边界不混装两类以上主题；
7. 改动段不引入“过程词”（本轮/上一轮/待修/已修）作为正文事实；
8. 引文块的省略、编注、改写都有显式标记；
9. 读者按画像前置知识能回答本节的三问：**不变量是什么、它的前提是什么、它的证据在哪**；
   三问答不出才是 FINDING，答得出但“更喜欢另一种写法”进 `suggestions.md`；
10. 同一事实不在三处以上重复展开；重复处至少两处是指针。

清单本身在 edition 边界可增删；清单变更必须写明替代/合并了哪一条，且用上一版的
文档做回归（至少 3 个历史发现）。清单内项目全部修完并由冷读者复读改动段，才算
`G4` 通过。

### 4.0f 单一未闭环口径：OPEN-DEBT 入门（V3.3，2026-11-10 用户裁决）

**V3.6-r4 状态 token（结构性修复，替代散文启发式）**：`OPEN-DEBT.md` 的每一行必须在处置格
以 `[CLOSED]` 或 `[OPEN]` 开头，其后才写理由与证据：

```markdown
| I-40 | P2 | [OPEN] 待 I-39 mini review 的 ghost 注释；截止 R40 |
| F-R17-02 | P2 | [CLOSED] ✅ `os/kernel/src/lib.rs:88` 的 `PhaseCell` 已落地；测试 `cell::phase` 通过 |
```

- 判据只读 token：`[CLOSED]` → 销账；`[OPEN]` → 保持打开；**无 token → FAIL**
  （V3.6+ 文档；V3.5 及更早文档按旧启发式判定，不追溯）。
- 为什么：三轮对抗证明散文状态不可靠——`✅ 完成度 40%` / `✅ 已修，但复验 FAIL` /
  `无需额外分配，应新增 newtype` 每次都击穿词表补丁。可判定的字面契约优于不断扩张的正则。

`OPEN-DEBT.md` 是未闭环的一部分，**不是账外债**（adjacent 行在 `follow-ups.md`，按 §4.2 不阻断）：
`eval-trace-check.py` 逐行核对该表，没有销账证据的行计入 `未闭环`，本轮不得关闭、
不得派下一轮面板。债务行只有两个合法出口：

1. **已实施**：附代码位置与测试证据；或 `dup-of: RD-xxx` 指向已覆盖它的根因行；
2. **判决账行**：`DECISIONS.md` 八字段记录的用户裁决——实施 / 有反证的拒绝 /
   明确批准的延期（批准须带日期与去向）。

**没有第三个状态。** 带 `截止 R<N>` 的行在 N 轮之后仍打开 = 逾期，门逐条点名 FAIL。
代裁决的授权范围必须写明是**批准实施**还是**批准转出**：只批准转出的授权不构成
实施授权（D-043 判例：批准转入 design batch 的 11 条，R27–R31 五轮之间无任何
执行器，R31 仍开着）。V3.2 禁止同篇 ② 转出堵住了**新增**逃逸；本条堵住的是
**存量**逃逸——债务在阴影账里不消灭，只会换一个名字回来（受影响章节的下轮重报）。

### 4.1 处置类

| 类 | 含义 | 必须写什么 |
|---|---|---|
| ① | 范围内真缺陷，本轮修（P0/P1/P2 一律） | 修复文件、修复方法、回归测试、反向验证、复验命令、fix-scope（点名位置逐处回读） |
| ② | 相邻范围转出（V3.2 收紧：仅此一种） | **只允许真正的相邻范围**（其他篇目/其他模块/其他 edition 范围）。**必须带批准**：`② 相邻：目标 <篇名/模块>；修于 <哪一轮/L0 清债>；用户批准 YYYY-MM-DD；理由 <为什么不在本轮>`。缺批准或缺日期即按未批准计，阻断本轮关闭。同篇内的待裁决项不得写 ②（见 §4.1a） |
| ④ | 读者验收清单内的体验项 | **本轮修**——只接收 §4.0e 清单内的项；措辞、结构、教学载体缺失、读者理解障碍按清单逐条验收。清单外偏好记 `suggestions.md`，并以 SUGG 行入台账（计入 SUGG 键与发现总数，不参与 G1–G9） |
| ⑤ | 证据不足 | 还缺什么证据、去哪里取、谁负责；本轮不得关闭 |
| ⑥ | 设计/代码重构——本轮实施 | **P-DESIGN 发现的可实施改进**：改哪些文件、设计取舍、测试计划、与文档的同步点。改完后同步 Ch3/Ch4/§5。未实施不得记 `FP` 或 `②` |
| FP | 反证成立（不是缺陷） | 必须写源码、测试或文档原文的反证；无证据按 `⑤` 未闭环处理。`FP` 不计入修复数，也不得用来承接“作者取舍/待裁决/未实施” |

### 4.1a ② 的唯一形态与同篇待裁决项（V3.2 收紧）

② 只允许**相邻范围**一种写法，且必须带日期（原“② 裁决”形态自 V3.2 删除）：

1. **相邻范围**：属于其他篇目或模块的条目。格式：`② 相邻：目标 <篇名/模块>；修于 <哪一轮/L0 清债>；用户批准 YYYY-MM-DD；理由 <为什么不在本轮>`。

**同篇内的待裁决设计项**只有两条路：

- 用户已授予代裁决授权（如“待裁决项可由 agent 代为裁决”）→ **当轮裁决并 ⑥ 实施**，不得转出；
- 没有授权 → 该轮标 `BLOCKED`（§4.0b 第 3 条），写裁决请求（等什么、选项、影响面），**轮次不关闭，绝不进入下一轮**——下一轮小节的出现会被 `eval-trace-check.py` 的轮序门当场拦截。

机械检查：`eval-trace-check.py` 对声明 V3.2 及以后的轮次强制 ② 行以 `② 相邻` 开头；`② 裁决` 形态一律 FAIL（历史轮次不受追溯影响）。

### 4.1b 代裁决授权边界与 ARCH 硬阻断（V3.3，D-047）

**授权边界 = Minix3 语义锚**（用户准则：锚定 C 语义、现代化表达 = 自动同意的代裁；
偏离 C 语义 = 必须用户纠结与裁决，无论大小）。设计类决策（DESIGN 角色的 ⑥ 行）
必须在台账标注分类标记，agent 按标记执行：

| 标记 | 判据 | 处置 |
|---|---|---|
| `[MODERN]` | C 有此语义，Rust 换现代表达（所有权/类型/结构），可观察行为逐点保持 | 代裁，当轮 ⑥ 实施 |
| `[DEL]` | C 没有此物——删除翻译残留/死抽象/多余一层，删除即回归 Minix3 对齐 | 代裁，当轮 ⑥ 实施 |
| `[ARCH]` | 改变 boot 是什么（机制替换如借槽→directMap、新责任/字段/检查/策略） | **不得实施** |

**ARCH 类的载体与解除（硬阻断）**：

- `[ARCH]` 且 P0/P1/P2 → 台账 `⑤`（取证路径=等待用户 ARCH 裁决）+ `轮结果: BLOCKED`。
  **即便用户口头说"继续"，解除的唯一方式也是 `DECISIONS.md` 判决账行**：批准 → 该行
  改 ⑥ 实施（引用 D-xxx）；拒绝 → 改 FP 附反证；延期 → **保留 ⑤ 行并补「用户批准 YYYY-MM-DD + D-xxx 判决行引用」三要素**
  （工具对带三要素的 ARCH ⑤ 行不触发 BLOCKED，V3.4-r8 修复回归判例；缺任一要素
  仍按 ARCH 硬阻断）。P0/P1 的批准须含「用户接受风险」。门不认识聊天，只认识行
  ——口头继续不解锁。
- `[ARCH]` 且 P3 → ARCH 提案记入判决账（状态=待用户裁决），**不阻断、不实施**——
  阻断的是"实施"，不是"存在"；提案随用户读文档时集合级审阅（防累积漂移：
  十条局部合理的小扩 = 小 OS，单项看不出、集合一眼可见）。
- **未分类**（无标记的设计 ⑥ 行）= 按 ARCH 阻断处理——举证责任在代裁侧：
  `[MODERN]`/`[DEL]` 必须能锚定 C 语义；给不出锚 = 偏离。
- 机械检查：`design-class`（未分类 FAIL；`[ARCH]` 实施缺 `D-xxx` 判决行引用 FAIL）；
  `lifecycle-v33`（存在 ARCH ⑤ 行而 `轮结果` ≠ `BLOCKED` FAIL）。

代裁决（`[MODERN]`/`[DEL]`）与 ARCH 提案均落判决账行并计数进 metrics
（`代裁决` / `ARCH 提案` / `用户否决`）——治理仪表：否决率持续 <20% 维持授权，
飙升则收紧。用户否决 = `user_decision: 否决` → 派生常规工作项（origin 指向该
判决行），走既有重做机制，不设时限。

### 4.2 证据强度

沿用 DOC-ITER 的分级：

- E1：源码直接确认，锚点到符号，引文块逐字对账；
- E2：实验观察，记录命令、环境、时间；只支持现象，不支持原因；
- E3：由证据推出，必须写全推理链；
- E4：未验证假设，只能作为假设登记；
- E5：风险约束型设计决策，必须写风险场景与代价。

裁决冲突时按 E1 高于 E2、E2 高于 E3、E3 高于直觉；不以角色人数投票。

### 4.3 冻结决策检查

每条发现进入处置前，先查 `DECISIONS.md`：

- 命中且没有新证据：记为 `re-litigation`；只有能给出源码/测试/文档原文反证时写 `FP`，否则写 `④`（读者仍会被误导）或 `⑤`（证据不足），并在 `处置` 里引用决策编号；不得写 `③`；
- 命中但有新证据：按正常发现处理，证据里必须写明”新证据是什么、为什么旧裁决不覆盖它”；
- 没有命中：正常处理。

### 4.4 范围门

L0 已经声明范围。每条发现再标一次：

- `in-scope`：属于本篇主题、关联代码或本轮修复触碰的文件；
- `adjacent`：真实但属于相邻模块或后续篇目；标 ② 并写明目标轮次。

`adjacent` 被写成阻塞，计入 `adjacent 阻塞` 指标，目标为 0。

### 4d. 测试充分性门

每个代码修复必须：

1. **带回归测试**：新增或修改至少一个 `#[test]`，覆盖修复前的失败场景；
2. **做反向验证**：还原修复 → 测试变红 → 恢复修复 → 测试变绿，两步记录在台账的 `复验` 列；
3. **受影响 crate 全量绿**：`cargo test -p <crate> --features <mock>` 通过；提交前 `cargo test -p minix-arch` 也必须通过（含 minix-arch，不允许带病提交）；
4. **QEMU 触发条件**：改动 `os/arch/`、`os/boot-shim/`、`os/kernel/src/boot` 或 `os/kernel/src/arch` 时，跑受影响架构的 QEMU 测试内核（至少编译检查 `cargo check -p <test-kernel>`；能跑则 `run_qemu.sh`）。

文档修复必须：触发它的那个检查（如 `anchor-resolve.sh`、`doc-style-lint.sh --diff`）重跑并通过。

### 4e. commit 级回归 review

每个逻辑 commit 提交后，派一个小型 review（不是全量面板），只看该 commit 的改动范围：

**文档 commit**（只改了 `.md` 文件）：

- `tools/anchor-resolve.sh --check <doc>` 重跑；
- `tools/doc-code-map.sh <doc> --check` 重跑；
- 改动段的 fact 抽查（改动节内每个事实断言逐个核对源码）；
- 改动节的 reader 抽查（改动段能否被目标读者理解）。

**代码 commit**（只改了 `.rs` 或构建文件）：

- 规范轴：错误处理（是否有 `unwrap`/`expect` 在不该出现的位置）、锁（跨 await / 持锁调用）、资源（泄漏/双重释放）、风格（clippy 新警告）；
- 设计意图轴：diff 是否偏离设计合同（`meta/design/<stage>/*.md` 中的对应决策）；不改外部行为；
- 契约（函数签名/前置条件/后置条件是否与文档/注释一致）、并发（数据竞争/死锁风险）、失败路径（每个 `Err` 分支是否被处理）。

**混合 commit**（同时改了 `.md` 和 `.rs`）：两个子集都跑。

**发现问题当场修复，修完才允许下一个 commit**（2026-11-09 用户裁决 §4e-1，替代“回 L2 归因”的旧口径——旧口径实测导致修复自引入再生）。回归按 commit 类型**分级**：

- **代码 commit**：双轴 + 相关 crate 测试 + 触面匹配的门（arch/boot → 三架构）；
- **文档-重 commit**（涉及表格/锚点/计数/跨节指针/代码引文之一）：五门全量 + 改动节 fact/reader 抽查；
- **文档-轻 commit**（错字/文风/单句措辞）：轻回归——改动 hunk 的锚点解析 + 文风 lint（diff 范围）+ ±5 行回读（数字/术语/指针）。拿不准按重处理。

**修复后复验与递归终止**：修复 diff 本身做复验（证据 = 旧串全篇 grep 归零，或测试输出）；复验通过则该 commit 的回归闭环终止。复验再发现新问题，同层级再修再验；**递归上限 2 层**——第 3 层起停止自动循环，剩余问题记台账带档期交下一轮（实测“修 A 坏 B”两层内收敛；第三层以上说明改动面理解有误，升级人工）。

### 4f. 轮转闸（2026-11-09 用户裁决）：无证据不进下一轮

进入下一轮面板之前，本轮全部发现（面板 + RBn + commit 级回归的再生项）必须满足：**所有可修项（①/④/⑥）已修且附证据；所有 `②` 有用户批准与日期；所有 `FP` 有源码/测试/文档原文反证；`⑤` 与未批准 `②` 一律视为未闭环，禁止派下一轮面板。**

- 文档类证据 = “旧串全篇 grep 归零”的命令与输出；
- 代码类证据 = 测试运行输出；
- 证据缺失 = **不得派下一轮面板**（`eval-trace-check.py` 对 ①/④ 行的复验列同样要求非空，空白即 FAIL）。

没有例外：`⑤` 不是“合法延期”，而是“本轮不能关闭”的标记；`②` 只有经 §4g 用户批准才不影响收敛。

### 4g. 拖欠须人工批准（2026-11-09 用户裁决）

② 转出/拖欠必须获得**用户明确批准**并落账（批准时间、去向批次、理由），才成为“不影响收敛的拖欠”（不阻断 G8/G9）；**未经批准的拖欠按未修计，阻断收敛**。`adjacent` 项仍不阻塞（§4.2），但同样适用本条：跨篇延期须用户批准。

### 4h. FREEZE 后回归审计与回归轮入账（V3.4 最小内核，R6-b/P1-5/R6-f 判例；V3.4-r7 由 4g-2 改号移位）

每篇 FREEZE 后、下一篇 L0 前，按 D-055 两墙派**独立**回归审查（实践自 2026-11-13
存在但一直挂在状态机外，本条收编）：

1. **载体**：`REGRESSION.md`（结论 PASS/FAIL + REOPEN/FINDING 清单 + 局限声明）+
   FREEZE 追加「回归 review」节。**FREEZE 文件 append-only**：只允许追加回归节与
   更新 sha256 行，不得改写原记录。
2. **回归轮必须入账（R6-b；V3.4-r8 补归属定义）**：回归/重做轮的全部发现必须在
   `defect-ledger.md` 建 **行级账**（逐 ID、处置类、含可重放 token 的修复证据——
   裸哈希不够，写 `commit <hash>` 或 `path:line`/grep），并在 `loop.md` 追加非编号
   索引节。**归属规则**：回归行放 `## REG-<date>` 节——该节不参与 `--round` 作用域

## 五、meta-review 契约

### 5.0 分级

| 轮次 | 深度 | 问卷 |
|---|---|---|
| 1–2 | 全量 | 九问全问 + P0/P1/未闭环 100% 复判 + P2/P3 抽 20% |
| 3+ | 轻量 | 问 1（Detection）、问 8（Trace integrity）、问 9（开放题）；P0/P1/未闭环 100% + P2/P3 抽 10 条；查上轮 fix-scope 完成率 |
| 文档收敛时 | 全量收口 | 九问全问 + P0/P1/未闭环 100% 复判 + P2/P3 抽 20% + 给流程质量结论（**不判文档 `CONVERGED`**；文档出口只看 §6A） |

轻量轮的输出仍写到 `meta/<doc-stem>-review.md`，但只包含问卷 1/8/9 三项 + 抽样表 + fix-scope 完成率 + 局限声明。

**meta 修约（V3.4 最小内核，P0-3 判例：契约要求逐轮、实践自 R27 起停摆，状态就此
结束）**：轮次级独立 meta 不再逐轮要求——**每篇收敛时（FREEZE 前）必须有一次独立
冷启动 meta**（全量收口问卷，输出 `meta/<doc-stem>-review.md`）；其余轮次由主 agent
在 `### L6` 写同 agent 收口并如实标注「同 agent 收口」；每 2 篇另做一次跨篇 meta
（执行定义，V3.4-r8：两篇 FREEZE 后由主 agent 写 `meta/cross-<a>-<b>.md`，输入为
两篇 L6/L6.5 收口与 BLIND-SPOT-DELTA，输出「供给结构对比 + 盲区账本动向 + 候选
规则」，同 agent 标注，不需独立冷启动）。
上表「1–2 全量 / 3+ 轻量」分级仅适用于被独立 meta 覆盖的轮次。

### 5.1 输入

- 当前工作流版本说明与 `WORKFLOW-VERSIONS.md`；
- 本篇语料条目与 `expected/` 对应条目；
- `BLIND-SPOTS.md` 的 OPEN 项；
- 本轮 `loop.md`、`defect-ledger.md`、`metrics.md`；
- 面板原始输出；
- 前几篇指标；
- `DECISIONS.md`。

### 5.2 不给什么

- 主 agent 的自我评价与建议（归因表可以给，但要求抽样独立复判）；
- 其他轮的 meta-review 结论（避免互相锚定）；
- 用户对本轮的即时评价（避免迎合）。

### 5.3 固定问卷

逐项给 `PASS` / `CONCERN` / `FAIL`，每项至少一个证据指针：

1. Detection：以前漏的现在能发现吗？哪些盲区仍漏？
2. Precision：误报多少？有没有角色或类别模式？
3. Design quality：是否发现可删除的抽象、翻译残留、错误建模、多余状态、不合理 trait、多余复杂度？还是只有命名与注释级意见？
4. Independence：冷读是否产生独立发现，还是复述主 agent 已知内容？独有发现多少？
5. Scope discipline：有没有扩大责任边界？相邻问题是否被当阻塞？冻结决策是否被重提？
6. Teaching quality：读者角色是否发现真实理解障碍？采纳率多少？有没有纯文风噪声？
7. Cost：token、agent 调用、轮次；是否收益递减？
8. Trace integrity：每条发现是否有处置行？指标是否自洽？
9. 本轮最值得但工作流仍看不见的一件事（开放题）。

### 5.4 输出

写到 `meta/<doc-stem>-review.md`，固定包含：

- 总体结论：`IMPROVED` / `FLAT` / `REGRESSED`（这是**流程质量**结论，不是文档
  `CONVERGED`/`NOT CONVERGED`；文档出口只看 §6A）；
- 四个流程数：`唯一根因数`、`自引入数`、`重复合并数`、`edition 是否稳定`；
- 问卷九项逐项结论；
- `BLIND-SPOT-DELTA`：新增、关闭、仍 OPEN 的盲区；
- 建议变更：每条给案例 ID、目标文件、期望效果、回归风险、替代或合并了哪个旧装置；
- 局限声明：必须写“同 agent 验证 + 已重放命令”；抽样一致性低于 90% 写 `NOT PASS`。

**V3.7 出版标准（2026-11-21 用户裁决）**：G10/G11 与 `prompt/review-rules/review-publication.md`

当轮修完，唯一例外是 `DECISIONS.md` 的 `defer-approved` 判决行（日期 + 具体条目 + 到期条件 +
不做后果）。`CONVERGED` 自此表示**出版就绪**，不是「本轮发现清零」。

V3 不再要求“连续两轮零新增”，也不再把 meta 抽样一致性作为收敛门。meta 的
`PASS`/`NOT PASS` 是流程质量指标；它 FAIL 时记录流程缺陷并在 edition 边界处理，
不阻止文档关闭。G7 的“100% 复验”取代原来的“meta 抽样 ≥90%”作为收敛证据。

**四态模型（V3.3，2026-11-10 用户裁决）**：R26 与 R30 两次假阳性（修改轮自判
`CONVERGED`，均被下一轮完整 survey 推翻，其中 R30 借"代理口径 A"越权）证明
"本轮交易成功关闭"与"文档已稳定"必须分成两个状态、由不同的轮种宣告：

| 状态 | 含义 | 谁能宣告 |
|---|---|---|
| `ROUND-CLOSED` | 本轮准入根因全部处置，100% 复验与机械门通过（G1–G9 的 open 部分） | 修改轮（full/structural）的 certify |
| `CONVERGENCE-CANDIDATE` | 最近一个修改轮 ROUND-CLOSED，等待确认轮 | 修改轮关闭时自动进入，无动作 |
| `CONVERGED` | 确认轮在最终工作树上 `certify 新准入 = 0`，G1–G14 全过（含全部单元 frozen），且 OPEN-DEBT 无未销账行 | **只由确认轮出口给出** |
| `FREEZE-WITH-BACKLOG` | 预算用尽或决定停止，仍有未解决事项或证据缺口 | 用户裁决 |

- **修改轮没有收敛声明权**：full/structural 轮的 agent 不得宣告 CONVERGED，最多
  ROUND-CLOSED / CONVERGENCE-CANDIDATE（`eval-trace-check.py` 机械检查）。
- **确认轮**：覆盖未冻结单元 + ≥20% 冻结单元（seed = 最终 commit）+ 骨架；首个 edition 或
  未冻结单元 >30% 时按整篇 survey。修复权限 = 本轮新准入的 P0/P1/P2 事实与
  同步项；不实施 ⑥、不扩大重构范围；P3 走 §4.0c 严重度门槛。每个 CONVERGENCE-CANDIDATE 最多 2 次（跨 edition 重开不累计）：
  第 1 次新准入 > 0 时在确认轮内修完再确认一次；仍 > 0 或出现结构性新根因 →
  `NOT CONVERGING` 回 edition 边界。确认轮不占 §7.5 的修改预算。
- **CONVERGED 的含义**仍是"确认轮口径下没有 open 项 + 无未销账债务"，不是
  "文档绝对无缺陷"；这条限制必须写进 `FREEZE.md`，禁止宣传成零缺陷保证。
  后续 edition 或新证据可以重开；重开不是上一轮失败，而是新尺度的认证。

**V2.5 历史（R25 及以前）**：仍按旧 G1–G9 收口（G7 为 meta 抽样 ≥90%，G8 为验证轮
新 in-scope 真缺陷=0）；V3 从 01 的 R26 或 02 的 R1 起生效。R25 的收口按 §4.0b 的 certify
阶段执行，不另开 verification 轮。

**R25 过渡的 G7**：R25 的收口按 V3 的 G7（台账/100% 复验）执行；meta25 的抽样一致性
只作流程质量记录，不作为 R25 的关闭门。其余 G1–G6/G8/G9 仍按 V2.5 口径。

**同一根因连续两次修复仍复发** → 生成 `STUCK-REPORT.md`（列出根因、已尝试的修复、
为什么没修好、建议的人工介入方向）→ 标记该根因 `STUCK` → 交用户裁决；不得用第 3 次
措辞修复继续打补丁，也不得把复发计成“新发现”。

### 6B-2. 门自身的收敛判据与威胁模型（V3.5，2026-11-18 用户裁决）

r6–r8 三轮对抗审查每轮都在门层发现新 P0（轮序断链 → 自报键伪造 → 空目录伪造），
说明「文本匹配门 + 自报数据」存在结构性上限。V3.5 明确两件事：

1. **威胁模型（写死，不许再靠加词表逼近）**：
   - 门防的是**事故与诚实执行者犯错**：漏交账、错归属、数字漂移、伪造一行文本；
   - 门**不防蓄意伪造完整制品链**（全套假面板 + 假台账 + 假回执且哈希自洽）——
     这类只能靠 meta/回归审计与人工复核发现。不得再把「全伪造」列为待修 P0；
     它是声明的边界，不是缺陷。**V3.4-r15 追加**：FREEZE.md 的状态以**标题契约**
     （`# … FREEZE …（CONVERGED|FREEZE-WITH-BACKLOG）`，无否定/未定标记）为准；
     正文叙述性否定（如历史段「NOT CONVERGED 保留为历史」）不毒化——伪造含肯定式
     标题的整个 FREEZE 文档属「伪造制品文件」，在本边界内。
2. **门自身的收敛判据**：连续两轮独立对抗审查，新增 P0/P1 **均为 0**（威胁模型
   边界类除外），且每个历史 P0 都有判别夹具（删除对应逻辑必红）。r9 是第一个
   正式考场；r9 若只出边界类问题，判「在声明的威胁模型内收敛」。

### 6B. 工作流收敛（全部篇目完成后才判）

“没有新问题”不是收敛。只有在全部篇目上同时满足以下八条，才判工作流收敛：

1. **盲区召回**：OPEN 的 Critical 盲区 100%、High 盲区至少 90% 在最近两次回归中被当前版本发现；未发现的必须有用户签字的”不可检测”或”超出范围”裁决。
2. **无新Critical/High 盲区**：最近 3 篇没有出现”工作流结构性看不见、事后由人或外部评审发现”的缺陷。
3. **精度**：误报率不高于 20% 且不上升；`re-litigation` 每篇不超过 1 条，目标为 0。
4. **范围**：`adjacent 阻塞` 为 0；每篇 ② 均有日期。
5. **设计质量**：每 2 篇至少 1 个被接受的结构性简化或重构；如果连续 3 篇设计角色只出命名与注释级意见，判设计能力未成立。
6. **教学**：读者角色每篇有真实理解障碍发现，采纳率至少 50%；纯文风偏好噪声不超过 20%。
7. **成本**：每篇 token 与 agent 调用不超过前 3 篇均值的 1.2 倍，或有”新增采纳发现”的明确证据。
8. **跨形态**：02 与 03 阶段的 01–10 篇上，第 1 至第 4 条不退化；退化则判过拟合，回到版本边界修正。

冻结时写 `FREEZE.md`，内容包括：最终版本、语料、盲区账本、收敛证据、维护规则。维护规则必须写明”什么时候可以重开”：出现新的真实盲区，而不是”某次评审又提了建议”。

## 七、升版纪律（V3）

### 7.1 边界

V3 的版本边界**不依赖文档收敛**，只在以下时点评估升版：

- 每一轮关闭后（`open=0` 且 certify 通过）可以评估一次；
- 每篇 FREEZE 之后；
- 同一 edition 在同一篇上连续 3 轮未收敛 → 强制 edition 评估（§7.5）；
- 出现被证实的 Critical/High 盲区。

完整 survey 之前，先在**最终 HEAD** 跑 `doc-citation-check.py` / `anchor-resolve.sh` /
`doc-symbol-drift.sh` 机械再对账；上一批修复引入的引文/符号漂移必须在 survey 前清零，
不能留给面板当“新发现”。

### 7.2 每次最多两条

一次升版最多晋升 2 条**增量**规则。每条必须带：

- 真实案例 ID（来自 `CORPUS.md` 或本轮轨迹）；
- 检测器（机械门、检查清单项或面板问题），不能只写“加强注意”；
- 期望效果（哪个盲区应该被接住，哪个指标应下降）；
- 回归风险（可能误伤什么）；
- 替代或合并了哪个旧装置；没有替代对象的，写“净增”与“为什么旧装置接不住”。

优先晋升降低 `r` 或 `M` 的候选（机械门、去重、身份键、读者清单收窄），
不优先晋升“加约束”类候选。

**MAJOR edition 例外**：一次重构核心模型（删除轮型、引入缺陷身份等）可以在一个边界
一次性定义，但必须在版本表标 `MAJOR`、逐条列出替代/合并的旧装置，并在下一个边界
接受效果读数。增量规则仍每次 ≤2 条；V3.0 就是一次 MAJOR edition。

### 7.3 同步门

升版后必须实际运行并贴出读数：

```bash
tools/generate-derived-skills.sh
tools/check-review-rules.sh
tools/lint-review-rules.sh
tools/diff-trae-skills.sh --only-diff
python3 tools/eval-trace-check.py --self-test
python3 tools/trait-audit.py --self-test
python3 tools/doc-citation-check.py --self-test
bash tools/doc-symbol-drift.sh --self-test
```

四项规则同步门与四个工具自测全绿才提交。只写“已通过”不算。

### 7.4 回退

连续两篇证明某条新规无效果或制造误报，回退。版本记录保留，写清回退原因、证据、
回退到哪个版本。

### 7.5 3 轮修改窗口与确认轮（V3.3 修订）

每个 edition 在同一篇文档上最多跑 **3 轮修改事务**（full / structural）。**确认轮
不占修改预算**：最后一个修改事务 ROUND-CLOSED 后，edition 进入
CONVERGENCE-CANDIDATE，由确认轮收口（§6A 四态模型），每个 CANDIDATE 最多 2 次。第 3 轮必须
是**结构轮**：按 `EDITION-RETRO.md` 重写被反复报的段/小节，并在最终 HEAD 跑
citation/anchor/symbol-drift 机械再对账；不得继续线级补丁。第 3 轮结束仍 `open>0`，
或第 3 轮本身仍是线级补丁：

1. 判该 edition `NOT CONVERGING`；
2. 写 `EDITION-RETRO.md`：唯一新增根因数、自引入数、重复率、修复批量、机械门命中、
   哪些规则从未命中；
3. 下一个边界必须处理最大阻塞项，或回退到上一 edition；
4. 不得在第 4 个修改事务继续用同一 edition 跑同一篇。

**单元预算（V3.9，与 edition 预算并行）**：每个 `###`/`##` 单元每轨最多 2 个修改轮
（`review-units.md` §三）；第 3 轮需用户批准或整节重写。单元预算耗尽不等于 edition
预算耗尽，反之亦然：篇级仍受本条 3 轮与 K=3 约束。冻结单元不占后续轮的面板输入。

**同篇 edition 上限（K=3，V3.3）**：同一篇文档最多经历 3 个 edition（软上限）。
超出后继续迭代必须在 `DECISIONS.md` 判决账落一行（理由 + 范围 + 日期），把
"无限换规则重试"从默认行为变成显式决定——它不是硬停（新盲区理应开新版本），
但必须留痕。V3.1 已在第 4 轮（R31，用户要求的追加轮）突破过一次：当时的追加轮
事实上就是确认轮，本条把这类轮次合法化并纳入上限管理。

这不是“放弃文档”：文档在下一个 edition 下继续，目标仍是收敛；被淘汰的是**不能
收敛的规则版本**，不是文档。

**V3.8 硬上限与强制重写（2026-11-21 用户裁决）**：

- **同一篇最多 3 个修改轮，跨 edition 累计。** 不再按 edition 分开计；换 edition 不是绕过
  上限的方式。第 4 个修改轮**禁止**；唯一例外是用户 `DECISIONS.md` 的 `rewrite-exception`
  判决行，且必须写明「为什么重写不可行」。
- **第 3 轮结束仍未收敛 → 强制重写**：不再开第 4 轮，转入 Manuscript 阶段，按
  `review-tutorial-rubric.md` 与 `review-publication.md` **整节重写**失败章节（不是线级补丁）。
- **重写后只允许 1 次确认轮**（不占修改轮预算）；确认轮仍不收敛 → 停止，交用户裁决，
  不得自动开轮。
- **代码冻结**：Review 期间关联代码冻结（见 `review-publication.md` §四.6）；重写期间落地的
  设计批必须在重写开始前完成，重写开始后任何 `os/` 改动 = 中止并重设基线。

### 7.6 中途变更

规则变更不得发生在轮次中途。确需中途变更：当前轮标 `INVALIDATED`，在新 edition 下
重开；旧轮结论不作数，不得静默继承。变更必须写入 `DECISIONS.md`（八字段）与
`WORKFLOW-VERSIONS.md`，并列出作废了哪些轮次。

### 7.7 强制减法

减法账本行数必须 ≥ 版本表行数——口径 = `WORKFLOW-VERSIONS.md` **第三节与各版本节下的
`### Vx.y 减法账本` 子表合计**（V3.6-r3 修正：原文只写「第三节」，而 V3.4/V3.5/V3.6 的账本
在各自版本节下，按字面读会误判违规）；每个新装置必须写明它替代、合并或删除了什么。没有替代对象的“净增”必须给出旧装置接不住的具体证据，
并在下一个边界接受效果读数；连续两篇无效果即回退。该行数由
`tools/check-review-rules.sh` 机械校验。

### 7.8 设计快照的历史定位

审查合同 = 文档 + 源码 + `DECISIONS.md`；`meta/design/<stage>/*.md` 是**历史设计输入**，不是现行合同。
快照与文档/源码冲突时以文档/源码为准；快照头部必须标“历史定位”或 `superseded`，
审查角色不得把旧条款当作“文档偏离合同”的依据。R27 REFUTE 的“合同与文档相反”判例
即此条的来源。

## 八、轨迹完整性检查

`tools/eval-trace-check.py` 检查：

1. `loop.md` 的九个二级标题是否齐全；
2. 每个 `panel/*.md` 的 `## FINDING <ID>` 是否在 `defect-ledger.md` 有处置行；
3. 台账是否有孤儿行（处置了但面板里没有）；
4. 每条处置是否有处置类；
5. 处置类为 ① 的行是否有复验；
6. `metrics.md` 的 `发现总数` 是否等于列出的全部处置项之和（V3.3 起含 SUGG，与 §3.4 单一口径一致）；
7. 必需键是否齐全；
8. 是否存在 `TBD`、`待定` 这类占位；
9. 每个 `panel/*.md` 要么至少一条 `## FINDING`，要么在 `loop.md §1` 写“无发现面板：<file>（理由）”；只报 WARN 不再是可接受状态（V2/C-20）；
10. P-REFUTE 的主张进 `defect-ledger.md` 的 `## P-REFUTE 附加` 表，每行给 claim ID、结果、处置；设计提案的 DECISION 在 `loop.md §1` 标“参考”，不进缺陷计数（V2/C-20）；
11. 同一处缺陷被多个角色报出时，台账用 `dup-of: <ID>` 合并；原始发现数与去重缺陷数分开报（V2/C-20）；
12. 每条 ② 转出必须给目的地文件、命令、测试或验收判据；只写“code batch”“闭环轮”不合格（V2/C-23）。
13. 每条 ① 必须在台账里列出发现点名的全部位置，修完逐处 grep 回读；缺一处即降级为 ②（V2.1/C-25）。
14. 暂存 diff 的每个 hunk 必须能回指台账行（含 `MAINT`）；无对应行的 hunk 要么补行，要么撤回（V2.1/C-25）。

**诚实性标注（V3.4-r7/r8，P2-9 判例：规则不得宣称不存在的机器检查）**：上列第
10–14 条是**人工合同**——`eval-trace-check.py` 未实现对应检查（grep 工具源码可证：
dup-of 目标存在性、② 目的地枚举、① 全位置回读、hunk 回指均为人工执行）。**第 10
条有部分机械面（r8 更正）**：工具会把 `## CLAIM N` 提取为 `CLAIM-NN` 并要求主台账
有处置行——但 §八.10 规定的三列附加表形状不被解析；只写附加表 = coverage FAIL。
机械化的其余部分登记为 V3.5 候选；落地前不得当作完整门引用。

退出码 0 表示轨迹完整；1 表示有缺口。缺口不修完，不允许进入下一阶段。

## 九、同 agent 局限声明

本项目的 meta-review 使用同一个模型的冷启动子 agent。它共享模型级盲区，不能替代真正的异构评审。因此：

- 必须标注“同 agent 验证 + 已重放命令”；
- 必须给出抽样比例与一致性；低于 90% 写 `NOT PASS`；
- 有条件时，优先把脱敏后的轨迹包交给外部模型做一次全量复核；
- 不把“同 agent 评估通过”写成“工作流已被独立证明”。

## 十、过拟合护栏

### 10.1 收敛信号（正面）

面板连续 2 轮的发现里，`FP`（有反证的误报）+ 重复项（`dup-of`）占比 > 50% 时，这不是"面板退化了"，而是**该篇已经收敛的信号**：面板找不到新的 in-scope 真缺陷了，只能报误报和重复。此时应触发收敛检查（§6A），而不是继续修。

### 10.2 陷阱套件复跑

每 2 轮复跑一次 `traps/T01–T08`。复跑结果与上次比较：

- 全 PASS → 正常，继续；
- 有陷阱从 PASS 翻转为 FAIL → **过拟合警报**：说明工作流改版后反而丢掉了之前能检测到的问题。此时必须回退到上一个版本，或明确写出"为什么这个翻转是预期的"。
- 有阴性样本（T07/T08）从 PASS 翻转为 FAIL → 同上，说明面板开始越界或重提冻结决策。

### 10.3 跨轮缺陷账本

V3 起 `origin` 与 `根因 ID` 是台账必填列（§4.0c），不再只是候选。每条缺陷有稳定
身份：同一根因第二次出现只更新 `last_seen`，不产生新行、不计入“新准入”。收敛检查
用三个数分开报：`发现总数`（原始 ID 数）、`唯一根因数`、`本轮新准入`。这样
“新问题”和“老问题没修干净”在账本上可区分，G8 的“零新增”才有机械含义。

历史轮次（V2.5 及以前）没有 `origin` 列的，保留原样，不回填、不追溯改账。
