# Review Evals —— 语料、轨迹、指标与收敛

> 状态：V1（2026-11-07）。本文件是 `prompt/skill/review-loop.md` 的评测规范，也是 `rewrite-notes/coordination/review-eval/` 的数据契约。
> 它不改变任何现有 review 规则；它规定“怎么判断工作流本身有没有进步”。

## 一、目的

“这一轮评审感觉更认真了”不是进步证据。可验证的进步至少需要三样东西：

1. 固定语料：同一批案例反复跑，避免用更简单的文档制造进步；
2. 完整轨迹：每条发现都有来源、证据、处置与复验，不能只留下“已修复”三个字；
3. 独立评估：由一个不参与本轮设计和修复的冷启动评估者，按固定问卷判断。

本文件定义这三样东西的格式与判据。

## 二、语料契约

### 2.1 条目类型

| 类型 | 前缀 | 用途 | 运行时机 |
|---|---|---|---|
| 真实篇目 | `D` | 文档加关联代码的完整循环 | 每篇一次 |
| 回归切片 | `R` | 历史缺陷的定向复现 | 每个版本边界 |
| 对抗样本 | `T` | 合成阳性、阴性、范围陷阱 | 每个版本边界 |

### 2.2 每条必填字段

- `ID`：唯一编号；
- `制品路径`：文档或样本文件；
- `形态`：启动链、服务事件循环、库、集合等；
- `关联代码`：由 `tools/doc-code-map.sh` 产出的路径清单，或明确写“无”；
- `期望发现`：引用 `BLIND-SPOTS.md` 的盲区编号与期望探测器；
- `负期望`：明确写出“不许报什么”，用于测误报与范围纪律；
- `成本预算`：允许的面板角色数、修复轮数、agent 调用数；
- `上次结果`：命中、漏报、误报三项计数。

### 2.3 语料不可静默修改

新增条目可以随时加。修改已有条目的期望发现或负期望，必须在 `WORKFLOW-VERSIONS.md` 的版本表里写明“为什么原来的期望不成立”，否则视为为了让本轮好看而改题。

## 三、轨迹契约

### 3.1 目录

每篇一份：

```
rewrite-notes/coordination/review-eval/runs/<stage>/<doc-stem>/
  loop.md
  metrics.md
  defect-ledger.md
  follow-ups.md
```

原始输出：

```
tmp/review-eval/<stage>/<doc-stem>/panel/<role>.md
tmp/review-eval/<stage>/<doc-stem>/logs/
```

### 3.2 `loop.md` 固定九节

标题必须逐字包含以下九个二级标题，供 `tools/eval-trace-check.py` 解析：

```markdown
## §0 基线
## §1 面板
## §2 发现
## §3 归因
## §4 修复
## §5 复验
## §6 指标
## §7 状态
## §8 给 meta-review 的不确定点
```

各节最小内容：

| 节 | 必须写什么 |
|---|---|
| §0 | commit、文档 sha256、行数、范围声明、关联代码清单路径、语料条目 ID |
| §1 | 角色清单、每个角色拿到与没拿到什么、模型、起止时间、原始输出路径；缩编时写缩编理由与风险 |
| §2 | 每条发现的 ID、来源角色、严重度、类别、位置、证据、建议；可以引用面板原文，但必须保留 ID |
| §3 | 每条发现的处置类、理由、证据强度、冻结决策检查结果、范围类（in-scope / adjacent） |
| §4 | 每条修复的 ID、文件、diff 摘要、测试证据、fix-guard 记录 |
| §5 | 修复段回读、台账重放、机械门读数、回归扫描、QEMU 结果（如适用） |
| §6 | 指标摘要，与 `metrics.md` 一致 |
| §7 | `CONVERGED` 或 `NOT CONVERGED`；未收敛时列 design-debt 与 carry-over |
| §8 | 本轮自己也不确定的地方，供 meta-review 重点检查 |

### 3.3 `defect-ledger.md` 表格式

表头必须包含以下列名：

```markdown
| 发现 ID | 来源角色 | 严重度 | 类别 | 处置类 | 处置 | 证据 | 复验 |
```

规则：

- `发现 ID` 必须与面板报告里的 `## FINDING <ID>` 完全一致；一行可以放多个 ID，用顿号或逗号分隔；
- `处置类` 只能是 `①` 到 `⑤`，或对应的英文标记 `fix` / `transfer` / `fp` / `wording` / `insufficient`；
- `处置类` 为 ① 或 `fix` 的行，`复验` 必须非空，且不能是 `TBD`、`待定`、`-`；
- `处置类` 为 ⑤ 或 `insufficient` 的行，`处置` 必须写“还缺什么证据、去哪里取”，不能只写“证据不足”；
- 没有处置行的发现，`eval-trace-check.py` 判 FAIL，L2 不允许进入 L3。

### 3.4 `metrics.md` 固定键

```markdown
- 发现总数: <整数>
- 处置: ① <整数> / ② <整数> / ③ <整数> / ④ <整数> / ⑤ <整数>
- re-litigation: <整数>
- adjacent 阻塞: <整数>
- 重构: 提出 <整数> / 接受 <整数> / 实施 <整数> / 登记 <整数>
- 成本: agent <整数> / token <整数> / 耗时 <文本>
```

规则：

- `发现总数` 必须等于 `处置` 五项之和；
- `re-litigation` 是命中冻结决策且无新证据的发现数；
- `adjacent 阻塞` 是相邻问题被当成当前阻塞的发现数，目标为 0；
- `重构` 四项分别记录提出、接受、实施、登记的数量；
- 成本不能只写“若干”；没有 token 读数时写“未采集”，不要编造。

## 四、归因契约

### 4.0 全修原则

范围内确认为真缺陷的发现——不论严重度是 P0、P1、P2 还是读者体验项——**一律本轮修**。不允许无档期转出。每篇文档必须在收敛门通过后才进入下一篇；收敛门的第一条就是 `in-scope 待修 = 0`。

### 4.1 处置类

| 类 | 含义 | 必须写什么 |
|---|---|---|
| ① | 范围内真缺陷，本轮修（P0/P1/P2 一律） | 修复文件、修复方法、回归测试、反向验证、复验命令、fix-scope（点名位置逐处回读） |
| ② | 相邻范围 | **必须带日期**：(a) 写明属于哪个模块/篇，在哪一轮修；(b) 用户裁决项写明等什么裁决。不允许”以后再说” |
| ③ | 误报 | 反证：源码、测试或文档原文说明为什么不是问题 |
| ④ | 读者体验 | **本轮修**——措辞、结构、教学载体缺失、读者理解障碍都是验收项，不是可选项 |
| ⑤ | 证据不足 | 还缺什么证据、去哪里取、谁负责 |

### 4.1a ② 的两种合法形态

② 只允许以下两种写法，且必须带日期：

1. **相邻范围**：属于其他模块或后续篇目的条目。格式：`② 相邻：目标 <篇名/模块>；修于 <哪一轮/L0 清债>；理由 <为什么不在本轮>`。
2. **用户裁决**：需要用户决定的条目。格式：`② 裁决：<等什么裁决>；选项 <A/B/…>；截止 <哪一轮之前必须裁决>`。

### 4.2 证据强度

沿用 DOC-ITER 的分级：

- E1：源码直接确认，锚点到符号，引文块逐字对账；
- E2：实验观察，记录命令、环境、时间；只支持现象，不支持原因；
- E3：由证据推出，必须写全推理链；
- E4：未验证假设，只能作为假设登记；
- E5：风险约束型设计决策，必须写风险场景与代价。

裁决冲突时按 E1 高于 E2、E2 高于 E3、E3 高于直觉；不以角色人数投票。

### 4.3 冻结决策检查

每条发现进入处置前，先查 `DECISIONS.md`：

- 命中且没有新证据：记为 `re-litigation`，处置类写 ③ 或 ④，并在 `处置` 里引用决策编号；
- 命中但有新证据：按正常发现处理，证据里必须写明”新证据是什么、为什么旧裁决不覆盖它”；
- 没有命中：正常处理。

### 4.4 范围门

L0 已经声明范围。每条发现再标一次：

- `in-scope`：属于本篇主题、关联代码或本轮修复触碰的文件；
- `adjacent`：真实但属于相邻模块或后续篇目；标 ② 并写明目标轮次。

`adjacent` 被写成阻塞，计入 `adjacent 阻塞` 指标，目标为 0。

### 4d. 测试充分性门

每个代码修复必须：

1. **带回归测试**：新增或修改至少一个 `#[test]`，覆盖修复前的失败场景；
2. **做反向验证**：还原修复 → 测试变红 → 恢复修复 → 测试变绿，两步记录在台账的 `复验` 列；
3. **受影响 crate 全量绿**：`cargo test -p <crate> --features <mock>` 通过；提交前 `cargo test -p minix-arch` 也必须通过（含 minix-arch，不允许带病提交）；
4. **QEMU 触发条件**：改动 `os/arch/`、`os/boot-shim/`、`os/kernel/src/boot` 或 `os/kernel/src/arch` 时，跑受影响架构的 QEMU 测试内核（至少编译检查 `cargo check -p <test-kernel>`；能跑则 `run_qemu.sh`）。

文档修复必须：触发它的那个检查（如 `anchor-resolve.sh`、`doc-style-lint.sh --diff`）重跑并通过。

### 4e. commit 级回归 review

每个逻辑 commit 提交后，派一个小型 review（不是全量面板），只看该 commit 的改动范围：

**文档 commit**（只改了 `.md` 文件）：

- `tools/anchor-resolve.sh --check <doc>` 重跑；
- `tools/doc-code-map.sh <doc> --check` 重跑；
- 改动段的 fact 抽查（改动节内每个事实断言逐个核对源码）；
- 改动节的 reader 抽查（改动段能否被目标读者理解）。

**代码 commit**（只改了 `.rs` 或构建文件）：

- 规范轴：错误处理（是否有 `unwrap`/`expect` 在不该出现的位置）、锁（跨 await / 持锁调用）、资源（泄漏/双重释放）、风格（clippy 新警告）；
- 设计意图轴：diff 是否偏离设计合同（`.design/*.md` 中的对应决策）；不改外部行为；
- 契约（函数签名/前置条件/后置条件是否与文档/注释一致）、并发（数据竞争/死锁风险）、失败路径（每个 `Err` 分支是否被处理）。

**混合 commit**（同时改了 `.md` 和 `.rs`）：两个子集都跑。

commit 级 review 发现的问题回 L2 归因（不是直接修），按 ①–⑤ 正常处置。

## 五、meta-review 契约

### 5.0 分级

| 轮次 | 深度 | 问卷 |
|---|---|---|
| 1–2 | 全量 | 九问全问 + 抽样 ≥20% |
| 3+ | 轻量 | 问 1（Detection）、问 8（Trace integrity）、问 9（开放题）；抽 10 条；查上轮 fix-scope 完成率 |
| 文档收敛时 | 全量收口 | 九问全问 + 抽样 ≥20% + 判 `CONVERGED` 或 `NOT PASS` |

轻量轮的输出仍写到 `meta/<doc-stem>-review.md`，但只包含问卷 1/8/9 三项 + 抽样表 + fix-scope 完成率 + 局限声明。

### 5.1 输入

- 当前工作流版本说明与 `WORKFLOW-VERSIONS.md`；
- 本篇语料条目与 `expected/` 对应条目；
- `BLIND-SPOTS.md` 的 OPEN 项；
- 本轮 `loop.md`、`defect-ledger.md`、`metrics.md`；
- 面板原始输出；
- 前几篇指标；
- `DECISIONS.md`。

### 5.2 不给什么

- 主 agent 的自我评价与建议（归因表可以给，但要求抽样独立复判）；
- 其他轮的 meta-review 结论（避免互相锚定）；
- 用户对本轮的即时评价（避免迎合）。

### 5.3 固定问卷

逐项给 `PASS` / `CONCERN` / `FAIL`，每项至少一个证据指针：

1. Detection：以前漏的现在能发现吗？哪些盲区仍漏？
2. Precision：误报多少？有没有角色或类别模式？
3. Design quality：是否发现可删除的抽象、翻译残留、错误建模、多余状态、不合理 trait、多余复杂度？还是只有命名与注释级意见？
4. Independence：冷读是否产生独立发现，还是复述主 agent 已知内容？独有发现多少？
5. Scope discipline：有没有扩大责任边界？相邻问题是否被当阻塞？冻结决策是否被重提？
6. Teaching quality：读者角色是否发现真实理解障碍？采纳率多少？有没有纯文风噪声？
7. Cost：token、agent 调用、轮次；是否收益递减？
8. Trace integrity：每条发现是否有处置行？指标是否自洽？
9. 本轮最值得但工作流仍看不见的一件事（开放题）。

### 5.4 输出

写到 `meta/<doc-stem>-review.md`，固定包含：

- 总体结论：`IMPROVED` / `FLAT` / `REGRESSED`；
- 问卷九项逐项结论；
- `BLIND-SPOT-DELTA`：新增、关闭、仍 OPEN 的盲区；
- 建议变更：每条给案例 ID、目标文件、期望效果、回归风险、替代或合并了哪个旧装置；
- 局限声明：必须写“同 agent 验证 + 已重放命令”；抽样一致性低于 90% 写 `NOT PASS`。

## 六、收敛标准（双层）

### 6A. 文档收敛（每篇的出口门）

一篇文档判 `CONVERGED` 需同时满足以下八条。全满足才进下一篇；不过就继续修。

```
G1  in-scope P0 = 0
G2  in-scope P1 = 0
G3  in-scope P2 = 0
G4  ④ 读者体验项 = 0 待修
G5  ③ 有反证、⑤ 有取证路径、② 有日期
G6  五门 + cargo test（含 minix-arch）+ 必要 QEMU 全绿
G7  meta-review 抽样一致性 ≥ 90% 且判 PASS
G8  连续 2 轮无新 in-scope 发现
```

**第 5 轮结束时 G1–G4 仍有未清项** → 生成 `STUCK-REPORT.md`（列出仍存在的问题、已尝试的修复、为什么没修好、建议的人工介入方向）→ 标记该篇为 `STUCK` → 终止该篇循环 → 进下一篇。

### 6B. 工作流收敛（全部篇目完成后才判）

“没有新问题”不是收敛。只有在全部篇目上同时满足以下八条，才判工作流收敛：

1. **盲区召回**：OPEN 的 Critical 盲区 100%、High 盲区至少 90% 在最近两次回归中被当前版本发现；未发现的必须有用户签字的”不可检测”或”超出范围”裁决。
2. **无新Critical/High 盲区**：最近 3 篇没有出现”工作流结构性看不见、事后由人或外部评审发现”的缺陷。
3. **精度**：误报率不高于 20% 且不上升；`re-litigation` 每篇不超过 1 条，目标为 0。
4. **范围**：`adjacent 阻塞` 为 0；每篇 ② 均有日期。
5. **设计质量**：每 2 篇至少 1 个被接受的结构性简化或重构；如果连续 3 篇设计角色只出命名与注释级意见，判设计能力未成立。
6. **教学**：读者角色每篇有真实理解障碍发现，采纳率至少 50%；纯文风偏好噪声不超过 20%。
7. **成本**：每篇 token 与 agent 调用不超过前 3 篇均值的 1.2 倍，或有”新增采纳发现”的明确证据。
8. **跨形态**：02 与 03 阶段的 01–10 篇上，第 1 至第 4 条不退化；退化则判过拟合，回到版本边界修正。

冻结时写 `FREEZE.md`，内容包括：最终版本、语料、盲区账本、收敛证据、维护规则。维护规则必须写明”什么时候可以重开”：出现新的真实盲区，而不是”某次评审又提了建议”。

## 七、升版纪律

### 7.1 边界

只在以下时点升版：

- 01 篇首跑之后；
- 之后每 2 篇（03、05、07、09 之后）；
- 10 篇之后做最终评估；
- 或者出现被证实的 Critical/High 盲区，必须立即升版。

### 7.2 每次最多两条

一次升版最多晋升 2 条规则。每条必须带：

- 真实案例 ID（来自 `CORPUS.md` 或本轮轨迹）；
- 目标文件与具体改动；
- 期望效果（哪个盲区应该被接住）；
- 回归风险（可能误伤什么）；
- 替代或合并了哪个旧装置；没有替代对象的，写“净增”与“为什么旧装置接不住”。

### 7.3 同步门

升版后必须实际运行并贴出读数：

```bash
tools/generate-derived-skills.sh
tools/check-review-rules.sh
tools/lint-review-rules.sh
tools/diff-trae-skills.sh --only-diff
python3 tools/eval-trace-check.py --self-test
python3 tools/trait-audit.py --self-test
```

四项规则同步门与两个新工具自测全绿才提交。只写“已通过”不算。

### 7.4 回退

连续两篇证明某条新规无效果或制造误报，回退。版本记录保留，写清回退原因、证据、回退到哪个版本。

## 八、轨迹完整性检查

`tools/eval-trace-check.py` 检查：

1. `loop.md` 的九个二级标题是否齐全；
2. 每个 `panel/*.md` 的 `## FINDING <ID>` 是否在 `defect-ledger.md` 有处置行；
3. 台账是否有孤儿行（处置了但面板里没有）；
4. 每条处置是否有处置类；
5. 处置类为 ① 的行是否有复验；
6. `metrics.md` 的 `发现总数` 是否等于五项处置之和；
7. 必需键是否齐全；
8. 是否存在 `TBD`、`待定` 这类占位；
9. 每个 `panel/*.md` 要么至少一条 `## FINDING`，要么在 `loop.md §1` 写“无发现面板：<file>（理由）”；只报 WARN 不再是可接受状态（V2/C-20）；
10. P-REFUTE 的主张进 `defect-ledger.md` 的 `## P-REFUTE 附加` 表，每行给 claim ID、结果、处置；设计提案的 DECISION 在 `loop.md §1` 标“参考”，不进缺陷计数（V2/C-20）；
11. 同一处缺陷被多个角色报出时，台账用 `dup-of: <ID>` 合并；原始发现数与去重缺陷数分开报（V2/C-20）；
12. 每条 ② 转出必须给目的地文件、命令、测试或验收判据；只写“code batch”“闭环轮”不合格（V2/C-23）。
13. 每条 ① 必须在台账里列出发现点名的全部位置，修完逐处 grep 回读；缺一处即降级为 ②（V2.1/C-25）。
14. 暂存 diff 的每个 hunk 必须能回指台账行（含 `MAINT`）；无对应行的 hunk 要么补行，要么撤回（V2.1/C-25）。

退出码 0 表示轨迹完整；1 表示有缺口。缺口不修完，不允许进入下一阶段。

## 九、同 agent 局限声明

本项目的 meta-review 使用同一个模型的冷启动子 agent。它共享模型级盲区，不能替代真正的异构评审。因此：

- 必须标注“同 agent 验证 + 已重放命令”；
- 必须给出抽样比例与一致性；低于 90% 写 `NOT PASS`；
- 有条件时，优先把脱敏后的轨迹包交给外部模型做一次全量复核；
- 不把“同 agent 评估通过”写成“工作流已被独立证明”。

## 十、过拟合护栏

### 10.1 收敛信号（正面）

面板连续 2 轮的发现里，③（误报）+ 重复项（`dup-of`）占比 > 50% 时，这不是"面板退化了"，而是**该篇已经收敛的信号**：面板找不到新的 in-scope 真缺陷了，只能报误报和重复。此时应触发收敛检查（§6A），而不是继续修。

### 10.2 陷阱套件复跑

每 2 轮复跑一次 `traps/T01–T08`。复跑结果与上次比较：

- 全 PASS → 正常，继续；
- 有陷阱从 PASS 翻转为 FAIL → **过拟合警报**：说明工作流改版后反而丢掉了之前能检测到的问题。此时必须回退到上一个版本，或明确写出"为什么这个翻转是预期的"。
- 有阴性样本（T07/T08）从 PASS 翻转为 FAIL → 同上，说明面板开始越界或重提冻结决策。

### 10.3 跨轮缺陷账本

工作流目前只有"本轮 ID"，没有"同一条缺陷的生命周期"。D06 起在 `defect-ledger.md` 加 `origin` 列：如果一条缺陷在之前的轮次出现过，写 `origin: <前一轮的 ID>`。这样在收敛检查时可以区分"新问题"和"老问题没修干净"。
