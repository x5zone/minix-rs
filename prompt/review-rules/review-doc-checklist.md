# 文档 Review 检查清单

> 本文档定义对 Minix-RS 项目文档进行 Review 时的检查维度。
> 适用：所有技术文档（`.md` 文件）

---

## 1. 文档结构规范

每篇文档应遵循以下**灵活结构**：

```
# XX-title: 标题

> **分类**: 模块库 / 模块私有 / 全局基建
> **源码**: `minix3/minix/servers/模块/xxx.c`
> **说明**: 一句话功能描述
> **状态**: 可选，标注 Rust 实现状态

---

## 1. 概述
### 1.1 概念定义/作用
### 1.2 与 Minix3 的对应关系
### 1.3 关键状态/机制说明
### 1.4 行为规则

## 2. C 源码分析
### 2.1 相关定义（常量、调用号、配置等）
### 2.2 核心数据结构
### 2.3 关键函数分析
### 2.4 调用关系/调用点分析
### 2.5 设计要点/特殊处理

## 3. Rust 设计决策
> 高层设计选择，解释"为什么这样设计"

## 4. 实现详解
> Rust 实现的具体展开，解释"如何实现"

## 5. 专题分析（如适用）
> 根据文档主题灵活安排

## N. 测试要点  （倒数第二章）
> 需要测试什么，而非罗列测试代码

## N+1. 参见  （最后一章）
- [相关文档1](xxx.md)

## 附录（可选）
```

**关键约束**：
- **第1章（概述）和第2章（C 源码分析）不得包含 Rust 相关内容**
- **第3章（设计决策）** 聚焦"为什么这样设计"，每个决策必须可追溯到 Ch1&2
- **第4章（实现详解）** 聚焦"怎么做"，每个实现必须对应 Ch3 的设计决策
- **倒数第二章（测试要点）** 必须基于 Ch3 的设计决策和 Ch4 的实现细节推导
- **最后一章是参见**
- **C 源码分析应完整覆盖**：所有核心数据结构、所有关键函数、调用关系
- **Ch3 如有更好的替代方案，应以 TODO 段落记录**

### §1.5 Design 对齐维度

> **目的**：让"文档是否真的反映了 design"成为独立检查维度，而不仅是隐含假设。
> **触发**：所有 review 模式执行；快速/构造模式可裁剪具体内容，但不能跳过 Step 0 或 Gate H。

| 检查项 | 期望 | 判定 |
|--------|------|------|
| 文档是否引用 design.md（非 bagging）/ design-final.md（bagging）| 是（按 §2.0.5 格式）| ✅/❌ |
| 文档 Ch3 设计决策 vs design.md §X.Y | 一致 | ✅/❌ |
| 文档 Ch4 实现 vs design.md §X.Y | 一致 | ✅/❌ |
| Minix3 核心概念在 design.md 中 | 有对应章节 | ✅/❌ |
| design-missing/wrong 触发 design Refactor | 已记录 | ✅/❌ |

> **配套机制**：[review.md §Design First 原则](review.md) + [review-process.md §Step 1.6](review-process.md) + §2.0.5 Design 引用规范。

### 1.Ch1 Ch1 强制骨架（概念章专项，强制）

> **背景**：03-kmain-cstart 重构案例暴露 Ch1 最常见的失败模式是"主语错了"——从函数名出发总结概念，而非从"为什么需要"出发建立心智模型。以下检查项把"Ch1 主语对了吗"从自由裁量提升为结构化标准。
> **详见**：[review.md §概念抽象原则](review.md#概念抽象原则)、[review-patterns.md](review-patterns.md) 模式 51-53。

| # | 检查项 | 通过标准 | 优先级 |
|---|--------|---------|--------|
| 1.1 | **目标读者声明** | Ch1 引言声明目标读者与前置知识。未声明 → P1 | P1 |
| 1.2 | **"本章不讲什么"框** | Ch1 引言列出延后到后续章节的细节。无 → P2 | P2 |
| 1.3 | **裸概念复述测试** | 把 Ch1 正文中所有函数名/结构体名/trait 名用 `[XXX]` 替换后，读者是否仍能理解核心概念？不能 → P1 | P1 |
| 1.4 | **概念驱动方向** | Ch1 遵循 WHY→WHAT→HOW。开篇主语是函数名 → P1（实现驱动，模式 51）| P1 |
| 1.5 | **统一抽象先行** | 多架构文档先给统一框架（如"CPU 三问"），再分架构展开。无 → P1（模式 53）| P1 |
| 1.6 | **双向闭环** | 进入类机制（trap/syscall/IPC）必须同时覆盖"进入"和"返回"。只单向 → P1（模式 52）| P1 |
| 1.7 | **核心流程图** | Ch1 至少一张流程/关系图建立心智模型。无 → P2 | P2 |
| 1.8 | **核心 vs 历史包袱区分** | 架构特有机制（如 GDT）标注为"实现细节/历史包袱"，不当核心讲。违反 → P2 | P2 |
| 1.9 | **本章小结** | Ch1 末尾用核心框架收束并预告后续章节。无 → P2 | P2 |

**裸概念复述测试执行方法**（1.3）：
1. 提取 Ch1 正文中所有函数名/结构体名/trait 名
2. 用 `[XXX]` 替换后重读 Ch1
3. 如果核心概念仍能被理解 → ✅
4. 如果替换后 Ch1 变成"调用 [XXX] 然后 [YYY]"的无意义流水账 → P1（实现驱动）

## 2. 文档 Review 维度

### 2.0 Claims-Evidence Tracing（论文级文档质量，强制，不可跳过）

> **核心原则**：将文档中每个事实性断言视为学术论文的 claim，必须有可追溯的 evidence 支撑。
> 论文审稿的核心方法论——审稿人不说"我觉得不对"，而是说"表 3 的数据不支持第 4 节的 claim"。

**执行步骤**（必须逐条执行，不可跳过）：

**Step 2.0.1：提取所有事实性断言**
从文档各章节中提取所有事实性断言（不含过渡句、不含设计决策的「为什么」理由说明）：

| 断言类型 | 示例 |
|---------|------|
| 行为描述 | 「X 函数从高地址向低地址扫描」 |
| 数值断言 | 「Y 结构体包含 N 个字段」「Z 常量等于 K」 |
| 结构断言 | 「结构体 A 的字段 B 指向 C」 |
| 调用关系 | 「A 函数调用 B 函数完成某项工作」 |
| 设计推断 | 「因为 C 做了 X，所以 Rust 应该做 Y」|

**Step 2.0.2：逐 claim 分类与验证**
对每个 claim：
- **Claim 类型**：行为描述 / 数值断言 / 结构断言 / 调用关系 / 设计推断
- **Evidence 来源**：源码位置（精确到行号）/ 配置推导 / 文档链路上游
- **Evidence 强度**：直接可 grep 验证（强）/ 需阅读逻辑推段（中）/ 无源码依据仅推理（弱）
- **可复现性**：他人能否仅凭文档+源码独立验证此 claim？

**必须输出以下表格**（不可省略）：
```markdown
### 2.0 Claims-Evidence Tracing 验证结果

| Claim | 类型 | 文档位置 | Evidence 来源 | 强度 | 可复现? | 判定 |
|-------|------|---------|-------------|------|---------|------|
| alloc_pages 从高向低扫描 | 行为 | Ch2§2.3 L45 | alloc.c:123-156 | 强 | ✅ | ✅ |
| phys_block 有 4 个字段 | 结构 | Ch2§2.2 L30 | region.h:23-35 | 强 | ✅ | ✅ |
| refcount 永远等于链表长度 | 设计推断 | Ch2§2.3 L80 | pb.c:44 初始化+pb.c:64 link | 中 | ⚠️ 需阅读 | P1 |
| ... | ... | ... | ... | ... | ... | ... |
```

**额外质量维度（论文级要求）**：
- [ ] **先验假设显式化**：文档是否说明"本文档假设读者已经理解 X"？
- [ ] **结论与证据的区分**：读者能否区分"这是事实行为"vs"这是设计者的判断"？
- [ ] **反面案例覆盖**：文档是否讨论了 edge case？是否说明"在什么条件下这个行为不成立"？
- [ ] **不确定性的诚实表达**：对无法确认的 claim 是否标注了"待确认"？

**判定标准**：
- claim 证据强度为「弱」且不可复现 → P0（文档不可信，必须补充源码引用）
- claim 证据强度为「中」→ P1（需补充更精确的源码引用或标注「待确认」）
- claim 证据强度为「强」且可复现 → ✅

**Step 2.0.3：解释因果链验证（强制，P0）**

> **核心原则**：claim 有 evidence 不够，解释 claim 的 BECAUSE 部分必须技术上正确。
> "因为 X 所以 Y" 中的 X 必须是真实机制，不是听起来合理的编造。
> 来源：03-kmain-cstart

对每个带因果解释的 claim（含"因为/所以/由于/为了"的断言）：
1. **提取因果链**：claim + 因为 M1 所以 M2
2. **验证 M1 是否是真实机制**（用 C 语言语义/ISA 规范/源码逻辑推断，非"听起来对"）
3. 若 M1 无法直接验证，必须标注"推测，待验证"

**判定**：
- 因果链机制技术上错误 → **P0**（解释编造，即使 claim 本身正确）
- 因果链含未验证环节且未标注 → P1
- 因果链可由 C 语义/ISA 规范直接验证 → ✅

**典型反例**（03 案例）：
- claim "memcpy(&kinfo, local_cbi, ...) 是必要的" ✅
- 编造解释"调用链推进后栈帧被覆盖" ❌（C 语义上 kmain 没返回前栈帧一直在）
- 正确解释"local_cbi 作用域限于 kmain 调用链，非 kmain 链代码访问不到" ✅

> **与模式 34 的边界**：模式 34 是"代码注释的理由虚假"，本规则是"文档正文的因果链编造"。两者不重叠。
> **详见**：[review-patterns.md](review-patterns.md) 模式 48（因果链编造）。

### §2.0.5 Design 引用规范

> **目的**：文档中引用 design 时统一格式，便于审稿人快速溯源。

文档中引用 design 时，应使用以下格式：

| 引用类型 | 格式 | 示例 |
|---------|------|------|
| design 决策 | `design.md §X.Y`（非 bagging）/ `design-final.md §X.Y`（bagging）| design.md §3.3 |
| design vs code 一致性 | `design.md §X.Y ↔ file:line` | design.md §3.3 ↔ vm.rs:243 |
| design 缺失 | `design.md §X.Y（缺失）` | design.md §3.3（缺失） |
| design Refactor 触发 | `design Refactor: design.md §X.Y 错` | design Refactor: design.md §3.3 漏进程表 |

**判定**：
- ✅ 文档引用 design 且 design 存在 → 强证据
- ⚠️ 文档引用 design 但 design 缺失 → **P0-design-missing**
- ❌ 文档不引用 design 但属于 design 范围 → P1
- ❌ 文档引用格式错误（无 §X.Y） → P1-process-violation

> **配套机制**：[review.md §Design First 原则](review.md) + [review-process.md §Step 1.6 设计对齐检查](review-process.md) + [review-patterns.md §模式 63 Design-Missing](review-patterns.md)。

### 2.1 概念准确性检查（强制，不可跳过）

> **核心原则**：禁止虚构、禁止幻觉、必须以 Minix3 源码为唯一真理来源

**执行步骤**（必须逐条执行，不可跳过）：

**Step 2.1.1：提取核心概念**
1. 从文档 Ch1（概述）中提取所有**加粗术语**、**代码块中的类型名**、**关键名词**
2. 从文档 Ch2（C 源码分析）中提取所有分析的结构体名、函数名、宏名
3. 汇总为「核心概念清单」

**Step 2.1.2：逐概念溯源验证**
对清单中的每个概念，执行以下 grep 命令：
```bash
rg "CONCEPT_NAME" minix3/minix/servers/{module}/ --type c -n
rg "CONCEPT_NAME" minix3/minix/kernel/ --type c -n
rg "CONCEPT_NAME" minix3/minix/include/ --type h -n
```

**Step 2.1.3：数值常量验证**
对文档中出现的所有数值常量（数组大小、阈值、魔数），执行：
```bash
rg "#define CONSTANT_NAME" minix3/minix/servers/{module}/ -n
rg "#define CONSTANT_NAME" minix3/minix/include/ -n
```

**Step 2.1.4：算法描述验证**
对文档中描述的算法行为（扫描方向、分配策略等），读取对应 C 函数源码，逐行对比。

**必须输出以下表格**（不可省略）：
```markdown
### 2.1 概念准确性验证结果

| 概念/术语 | 文档位置 | grep 结果 | 源码行号 | 一致性 | 问题 |
|----------|---------|----------|---------|--------|------|
| phys_block | Ch2§2.2 | ✅ 找到 | region.h:23 | ✅ 一致 | - |
| refcount=0 初始化 | Ch2§2.3 | ✅ 找到 | pb.c:44 | ✅ 一致 | - |
| ... | ... | ... | ... | ... | ... |

**数值常量验证**：
| 常量 | 文档值 | 源码值 | 源码位置 | 一致? |
|------|--------|--------|---------|-------|
| VM_PAGE_SIZE | 4096 | 4096 | config.h:xx | ✅ |
| ... | ... | ... | ... | ... |

**算法描述验证**：
| 算法 | 文档描述 | 源码行为 | 一致? |
|------|---------|---------|-------|
| alloc_pages 扫描方向 | 高→低 | 高→低 (alloc.c:xxx) | ✅ |
| ... | ... | ... | ... |
```

**判定标准**：
- 概念在源码中找不到 → P0（虚构概念）
- 概念解释与源码不一致 → P0（概念错误）
- 数值常量不一致 → P0（数据错误）
- 算法描述不一致 → P0（行为错误）

**Step 2.1.5：架构范围标注验证**（多架构文档强制）

> 来源：03-kmain-cstart

- 叙述中出现 x86 特有机制（GDT/段描述符/TSS/IDT 门/CPL）→ 必须标注"x86 特有"
- aarch64 特有（EL/SP_EL/VBAR/PSTATE）、riscv64 特有（S/U-mode/sscratch/stvec/SPP）同理
- 未标注 → P1；ISA 寄存器角色描述错误（如 RISC-V SPP 当作"当前特权级"）→ P0
- 标注格式：`> 架构范围：x86-64` / `> 架构范围：三架构共性` / 行内 `(x86-64 特有)`

**Step 2.1.6：过度简化检查（"A 就是 B" 反读法）**

- 对每处"A 就是 B / A 等于 B / A 即 B"定义性表述，反读"反过来 B 就是 A"是否成立
- 不成立 → 过度简化。涉及核心术语首次定义 → P1；其他 → P2
- 例："GDT 就是保护结构"反读"保护结构就是 GDT"不成立 → 应修正

**Step 2.1.7：概念来源层级检查**

> 来源：Kimi 提案

Ch1 术语来源分层：
- **L0 硬件/CPU 层**：ring/EL/IDT/VBAR（CPU 规范定义）
- **L1 OS 概念层**：保护/特权级/异常入口（OS 抽象）
- **L2 实现抽象层**：ProtectionArch trait/函数名（Rust 代码）

- Ch1 用 L2 术语作为概念定义 → P1（概念层级泄漏）
- Ch1 用 L2 且无 L0/L1 定义 → P0

### 2.2 C 代码引用验证（强制，不可跳过）

> **核心原则**：引用的代码必须正确，代码的讲解必须准确

**执行步骤**（必须逐条执行，不可跳过）：

**Step 2.2.1：提取所有代码引用**
从文档中提取所有 C 代码引用（文件路径 + 行号），汇总为清单。

**Step 2.2.2：逐引用验证**
对每个引用，执行：
1. 验证文件是否存在：`ls minix3/minix/servers/{module}/REFERENCED_FILE.c`
2. **读取引用行号附近的源码**（使用 `Read` 或 `rg -n`），对比文档中的代码片段
3. 检查路径格式：禁止 `file:///home/user/...` 绝对路径

> **严格禁止**：在输出中使用 **"未逐行验证" / "未全部验证" / "抽样验证" / "行号未核对"** 等模糊表述。如果引用数量过大无法一次性验证完，必须明确列出已验证范围、未验证范围，并将未验证部分标记为 **"P1 待验证"** 或 **"to confirm"**，给出下一轮验证计划。

**Step 2.2.3：讲解一致性验证**
对每个代码引用，对比文档的讲解文字与源码实际行为。

**必须输出以下表格**（不可省略）：
```markdown
### 2.2 C 代码引用验证结果

| 引用位置 | 文件路径 | 行号 | 文件存在? | 行号准确? | 片段完整? | 讲解一致? | 路径格式? | 问题 |
|---------|---------|------|----------|----------|----------|----------|----------|------|
| Ch2§2.2 L45 | region.h | 23-35 | ✅ | ✅ | ✅ | ✅ | ✅ 相对路径 | - |
| Ch2§2.3 L78 | pb.c | 36-50 | ✅ | ✅ | ⚠️ 缺上下文 | ✅ | ✅ 相对路径 | P2: 补充上下文 |
| ... | ... | ... | ... | ... | ... | ... | ... | ... |
```

**判定标准**：
- 文件不存在 → P0（引用错误）
- 行号偏差超过 5 行（函数定义位置）→ P1
- 代码片段截断导致语义改变 → P0
- 讲解与源码不一致 → P0
- 过度解读（讲解超出代码实际表达）→ P1
- 使用绝对路径 → P1
- **输出中出现"未逐行验证"等模糊结论 → P1（流程违规）**

### 2.3 数据结构覆盖完整性（强制，不可跳过）

**执行步骤**（必须逐条执行，不可跳过）：

**Step 2.3.1：提取文档分析的结构体**
从文档 Ch2 中提取所有分析的结构体名称。

**Step 2.3.2：提取 C 源码中的结构体**
```bash
rg "^struct \w+" minix3/minix/servers/{module}/ --type c -n
rg "^typedef struct" minix3/minix/servers/{module}/ --type c -n
```

**Step 2.3.3：逐结构体验证字段覆盖**
对每个结构体，读取源码定义，对比文档是否分析了所有字段。

**必须输出以下表格**（不可省略）：
```markdown
### 2.3 数据结构覆盖验证结果

| 结构体 | 源码位置 | 总字段数 | 文档覆盖字段数 | 遗漏字段 | 判定 |
|--------|---------|---------|--------------|---------|------|
| phys_block | region.h:23 | 4 (+1 debug) | 4 | - | ✅ |
| vir_region | region.h:42 | 12 | 10 | param.file.clearend, remaps | P1 |
| ... | ... | ... | ... | ... | ... |
```

**判定标准**：
- 核心结构体完全未分析 → P0
- 核心结构体遗漏关键字段 → P1

### 2.4e "参见" 范围引用扫描（NEW 2026-07-31, 模式 #75）

> **目的**：检测 doc 中"参见 X.rs:Y-Z"形式的范围引用是否覆盖到 impl 结束、行号是否偏移。
> **背景**：Step 1.0a 行号主动抽样**只检查**单行引用（`// path:line`），**漏检**范围引用（`参见 path:line-line`）。
> **触发条件**：任何 doc review（含"参见"型引用时强制）。

```

**判定标准**：
- 语义范围内的核心函数未覆盖 → P0
- 语义范围内的核心结构体未覆盖 → P0
- 语义范围内的行为宏/标志位宏未覆盖 → P1
- 覆盖率 < 80% → 整体评为 P0（覆盖严重不足）

**关于宏的分类**：
- **常量宏**（如 `#define PAGE_SIZE 4096`）：在数值常量验证中覆盖，不要求在 §2.8 表格中列出
- **行为宏**（如 `#define IS_LOWMEM(v) ((v) < KERNEL_LOAD_BASE)`）：承载判断逻辑，必须在 §2.8 表格中列出
- **标志位宏**（如 `#define PBF_INCACHE 0x01`）：定义标志位，必须在 §2.8 表格中列出
- **条件编译宏**（如 `#if SANITYCHECKS`）：影响代码路径，需要在 §2.8 表格中列出或说明

> **核心原则**：设计决策必须合理、完整、可追溯。Review 不能只检查"文档写得对不对"，还必须检查"设计好不好"。

**执行步骤**（必须逐条执行，不可跳过）：

**Step 2.9.1：提取 Ch3 所有设计决策**

对每个设计决策，在 Ch1&2 中搜索依据：

```

**Step 2.9.3：验证场景覆盖完整性**

### 2.10 章节链路验证（强制，不可跳过）

> **核心原则**：文档各章节之间必须形成完整的推导链路。链路断裂 = 设计或实现有问题。
> 链路验证的原则定义见 [review.md §文档链路模型](review.md)，执行步骤见 [review-process.md §Step 2.5](review-process.md)。本节定义具体的检查项（维度层）。

**执行步骤**（必须逐条执行，不可跳过）：

**Step 2.10.1：Ch3→Ch1&2 追溯**
1. 列出 Ch3 的所有设计决策（复用 §2.9 Step 2.9.1 的结果）
2. 逐一检查每个决策在 Ch1 或 Ch2 中是否有依据
3. 如果 Ch3 引入了 Ch1&2 未提及的概念 → P1

**Step 2.10.2：Ch4→Ch3 追溯**
1. 列出 Ch4 的所有实现描述（函数签名、类型定义、行为描述）
2. 逐一检查每个实现是否对应 Ch3 的某个设计决策
3. 如果 Ch4 实现了 Ch3 未设计的功能 → P1
4. 如果 Ch3 设计了但 Ch4 未实现 → P1（应标注 TODO）

**Step 2.10.3：测试→Ch3+Ch4 追溯**
1. 列出倒数第二章的所有测试要点
2. 逐一检查每个测试要点是否覆盖了 Ch3 的设计决策或 Ch4 的实现细节
3. 检查 Ch2 中分析的错误路径和边界条件是否有对应测试

**Step 2.10.4：代码→Ch4 一致性**（仅在完整 Review 时执行）
1. 对照 Rust 代码，检查 Ch4 描述的函数签名、类型定义、行为语义是否与实际代码一致

## 3. 可读性与表达质量

> **核心原则**：技术准确但读起来痛苦的文档，价值会大打折扣。文档是给人读的。

### 3.1 文本流畅性

- [ ] 是否存在语病、错句、歧义句？
- [ ] 长句是否过多（超过 40 字）？是否可拆分？
- [ ] 代词指代是否清晰（"它""这""上述"是否明确）？
- [ ] 被动语态是否滥用？技术文档优先主动语态
- [ ] 同一概念是否使用一致的术语（不混用"页目录/PD/页表根"等）？
- [ ] 标点使用是否规范？中英文标点是否混用？
- [ ] **开篇第一句检查** ：Ch1 开篇第一句实质性内容是否包含 2+ 个未定义术语？→ P2（读者第一句就卡住）
  - 反例："prot_init() 让内核从借用固件的运行上下文变成拥有自己的运行上下文"（3 个未定义术语）
  - 正例："信任边界：内核可信，用户进程不可信"（0 个未定义术语）

### 3.2 逻辑组织与信息流动

- [ ] 段落之间是否有明确的逻辑衔接？（因果、递进、对比、转折）
- [ ] 是否存在"跳跃"——读者需要自行脑补中间步骤？
- [ ] 复杂概念是否遵循"先总后分"或"先简单后复杂"的顺序？
- [ ] 代码讲解是否遵循"先展示全貌，再逐行解释"或"先提出问题，再展示解决"？
- [ ] 是否存在信息密度不均——某段落过于密集，某段落过于空洞？
- [ ] 章节标题是否准确概括内容？是否存在"标题党"？

### 3.3 冗余控制

- [ ] **单文档内**：同一概念是否在多个地方重复讲解？重复是否必要？
- [ ] **跨文档间**：概念 A 在文档 X 中已详细讲解，文档 Y 中是否只需简介+引用？
- [ ] 是否存在"为了完整性而复制粘贴"的大段重复？
- [ ] 代码注释和文档文字是否说同一件事？（优先保留一处详细，另一处引用）
- [ ] 是否可以用"详见 [xxx.md](xxx.md)"替代大段展开？
- [ ] **概念正交性** ：两个"并列"概念实际有因果/包含关系（如特权级 vs 页表权限位）→ P2，应调整为层次关系
- [ ] **因果链重复**：同一套因果关系（A→B→C）在 2+ 节完整重讲 → P2，应拆分层次

**判定标准**：
- 同一概念在同一文档中重复超过 2 次 → 检查是否必要
- 跨文档重复超过 3 行 → 应改为简介+引用
- 代码块和对应文字讲解说同一件事 → 保留文字，代码加简要注释即可

### 3.4 读者体验

- [ ] 新概念引入时是否给出了足够的上下文？
- [ ] 专业术语首次出现时是否给出了定义或解释？
- [ ] 是否假设了读者已知的知识？这些假设是否合理？
- [ ] 复杂流程是否有"先给结论，再给细节"的引导？
- [ ] 长文档是否有目录或锚点，方便跳转到特定章节？
- [ ] 关键结论是否有视觉突出（加粗、引用块、表格）？
- [ ] 代码块和文字的比例是否合理？（纯代码无讲解 = 不好；纯文字无代码 = 也不好）
- [ ] **文档中代码块的注释使用中文**（因为是中文文档，中文注释有利于读者理解）；Rust 源码中的注释使用英文（与社区规范一致，见 [review-code-checklist.md §9.2](review-code-checklist.md#92-注释质量)）
- [ ] 抽象概念是否有具体示例或类比辅助理解？
- [ ] 类比是否恰当？不会引入新的误解？

**判定标准**：
- 一个新概念首次出现，3 行内没有解释 → P2（应补充定义）
- 一个复杂流程没有" TL;DR "或"结论先行" → P2（建议加引导）
- 连续 20 行纯文字无代码/表格/列表 → P2（建议拆分或加可视化）
- 连续 30 行纯代码无讲解 → P2（建议加文字说明）

**示例最小化检查**（§3.4 补充）：
- 概念引入示例是否避免引入与核心机制无关的细节？
- 示例引入额外问题（读者会问"为什么 X"但 X 与核心无关）→ P2
- 反例：`*(0xffffffff80000000)=0` → 读者问"为什么这地址是内核地址"
- 正例：`*((int*)0)=0` → 读者只关心"为什么空指针写失败"
- 本章开门第一个例子就有此问题 → P1

### 3.5 教学性质量（强制）

> **背景**：这些文档面向开源社区，是教学材料而非内部开发笔记。最常见的退化模式是变成"说明书"——贴一段代码、列出函数签名、罗列事实、结束。读者学不到东西。

**教学文档的角色**：不是让读者知道"有这些函数"，而是让读者理解"为什么这样设计、如何落地、有哪些关键细节和容易踩的坑"。每个章节都应该**带路**，而不是**罗列**。

**说明书 vs 教学文档的判定标准**：

| 维度 | 说明书（❌） | 教学文档（✅） |
|------|-----------|-------------|
| 章节引导 | 无，直接开始罗列 | 每个章节/小节开头有引导语，解释核心思路 |
| 代码块 | 裸代码，无注释 | 关键行有注释，解释"这行在做什么"和"为什么这样做" |
| 设计关联 | 不提设计决策 | 代码块/实现引用对应的设计决策编号 |
| 语义对应 | 无 | 与 Minix3 C 源码的语义对应（关键函数的行为对照） |
| 读者收获 | 知道了"有这些东西" | 理解了"为什么这样做"、"和 C 源码的对应关系" |
| 概念引入 | 直接使用，不解释 | 新概念首次出现时给出定义、动机和上下文 |

**各章节的教学性要求**：

| 章节 | 教学性要求 | 常见退化模式 |
|------|-----------|------------|
| Ch1 概述 | 每个概念引入时解释"为什么需要它" | 罗列术语定义，不解释动机 |
| Ch2 C 源码分析 | 分析每个函数时解释"它在整体流程中的角色" | 逐函数翻译注释，不解释调用关系和设计意图 |
| Ch3 设计决策 | 每个决策解释"为什么选 A 而非 B" | 只写结论，不写推理过程和替代方案 |
| Ch4 实现详解 | 每个类型/模块有引导语解释核心设计思路；代码块有注释 | 贴裸代码，无引导语无注释，变成 API 说明书 |

**退化信号**：
- [ ] Ch2 只有代码片段+一行说明，无"为什么这样设计"的分析？
- [ ] Ch3 只罗列决策，无"为什么选A非B"？
- [ ] Ch4 变成 API 文档——列函数签名和功能说明？
- [ ] 缺少反例论证？缺少对比分析？缺少迭代过程记录？
- [ ] **开发记录退化**：出现"已实现/待实现/未实现"、✅❌🚧 状态标记、"实现清单"等进度追踪式表述？（详见 §2.11）

**检查项**：

- [ ] 每个章节/小节是否有引导语，解释**核心思路**？
  - 引导语应回答：这一节讲什么？核心要点是什么？和前后文的关系是什么？
  - 示例："匿名内存是最核心的内存类型，覆盖 malloc/mmap(MAP_ANON) 等场景。它有两个关键行为：CoW 和 per-page 可写判定。"
- [ ] 代码块内是否有注释解释关键行？
  - 不是每行都要注释，但**非自解释的行**必须有注释
  - 特别是：与 C 源码行为对应的注释、解释"为什么这样做"的注释
- [ ] 代码块是否引用了对应的设计决策？
  - 每个代码块上方应有 `> 设计决策：§3.x（xxx）` 格式的引用
- [ ] 是否有与 Minix3 C 源码的语义对应？
  - 对于核心概念/类型，应有表格或文字对照 C 行为 vs Rust 行为
- [ ] 是否存在"纯代码无讲解"的代码块（超过 15 行代码无任何注释或引导语）？
- [ ] 新概念首次出现时是否有定义和动机说明？

**判定标准**：
- 代码块超过 15 行无注释且无引导语 → P1（教学性缺失）
- 类型/模块小节无引导语 → P1（读者无法快速理解核心思路）
- 新概念首次出现无定义/动机 → P1（读者迷失）
- 代码块无设计决策引用 → P2（链路不完整）
- 核心概念/类型无 C 源码语义对应 → P2（读者无法对照 C 源码理解）

**教学模式检查**（多架构/保护结构类文档强制）：

- [ ] 统一抽象层先行（见 §1.Ch1 1.5）
- [ ] 双向流完整性（见 §1.Ch1 1.6）
- [ ] 历史包袱降级：架构特有遗留机制降级为补充章节，标题用疑问式（"x86 为什么还保留 GDT"）→ 违反 P2
- [ ] 附录化深度展开：WHY 完整论证会打断概念流时，主文一句话建模型 + 文末附录展开（含威胁模型/前提+机制+防御对应+总结）→ 违反 P2
- [ ] 概念骨架可见性：Ch1 有显式核心框架（如"三问"），章末用同框架收束，后续章节引用该框架 → 违反 P2

### 3.6 文档设计哲学（强制）

> 来源：M3 提案
> **背景**：03 案例暴露文档"哲学不一致"——Ch1 声称概念驱动，实际从函数名出发。

**Step 3.6.1 哲学选择**：抽取 Ch1 开头、Ch1 总结、Ch3 引言，判定属于：
- **概念驱动**（Concept-first）：以"为什么需要 X"为起点
- **实现驱动**（Implementation-first）：以"Minix3 C 源码"为起点
- **混合**（Hybrid）：问题驱动的实现分析

同一文档内部要保持哲学一致。Ch1 声称概念驱动但实际实现驱动 → P1。

**Step 3.6.2 主线检验（主语分析）**：抽取 Ch1 主线陈述，判定主语是 `prot_init()` / CPU / 读者 / OS 中的哪一个。
- 主语是函数名 → 实现驱动 → P1（模式 51）
- 主语是 CPU → 概念驱动 → ✅

### 3.7 作者意图透明性（强制）

> 来源：多 AI 提案
> **背景**：03 案例正文出现 13+ 处"作者元注释"——暴露作者写作过程而非读者接收结果的文字。

**判别口诀**："删掉这段后，读者对主题的理解是否减少？"
- 减少 → 是正文，保留
- 不变 → 是元注释，删除或改写

**六类元注释**：
1. **过渡类**："引出 §1.4"
2. **范围声明类**："本节只回答…避免重复"
3. **深度策略类**："一句话带过"、"不展开，只建模型"
4. **作者自我强调类**："必须加"、"本节最难理解"
5. **历史修正叙述类**："早期文档曾表述…这不准确"
6. **自问自答修辞类**："为什么需要？因为…"

**判定**：单处 → P2；>5 处 → P1（系统性风格问题）

> **与模式 15 区别**：模式 15 是"已实现/待实现"进度追踪；本规则是"作者 narrate 写作策略"。
> **详见**：[review-patterns.md](review-patterns.md) 模式 49（元注释泄漏）。

### 3.8 P2 可读性检查的执行策略

> **背景**：§3.1~3.4 的检查项数量多且判定主观，AI 容易全部跳过或过度执行。以下策略确保 P2 检查有实际产出。

**执行规则**：
1. **先粗筛，再精查**：先快速浏览文档全文，凭第一印象判断是否有明显的可读性问题（约 30 秒）。如果感觉良好，标注「可读性无明显问题」并跳过逐项检查
2. **抽样检查**：如果感觉有问题，抽样 3 处（首段、中段、尾段），逐项检查 §3.1~3.4
3. **聚焦高频问题**：P2 检查的重点是以下 3 类最常见且最影响阅读的问题：
   - **术语不一致**（同一个东西换 3 个名字）
   - **信息跳跃**（读者需要自行脑补中间步骤）
   - **纯代码无讲解**（代码块超过 15 行无文字说明，→ P1 教学性缺失）
4. **P2 输出极简化**：仅输出实际发现的问题，不要求逐项输出「通过/不通过」
5. **批量处理**：如果文档超过 500 行，按章节切分，每章只抽样 1~2 段检查

**输出格式**（P2 部分）：
```
### 可读性检查（P2）
- 术语使用：✅ 一致 / ⚠️ 发现 X 处不一致（列出）
- 逻辑组织：✅ 通顺 / ⚠️ 发现 X 处跳跃（列出）
- 冗余：✅ 无冗余 / ⚠️ 发现 X 处重复（列出）
- 读者体验：✅ 良好 / ⚠️ 发现 X 个问题（列出）
```
