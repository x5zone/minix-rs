# review-improve-m3.md — MiniMax-M3 独立改进建议

> **任务**：基于 `03-todo.md` / `03-kmain-cstart.md` / `03-kmain-cstart-bak.md` / `comments.md` 这一组 Ch1 重构案例，独立分析现有 `prompt/review-rules/` 在该案例中暴露的覆盖缺口，并提出改进建议。
>
> **方法**：读完 03 案例后，先用 03 案例作为"试金石"去逐项核对现有规则（不预先假设有哪些缺口），再独立归纳。本报告与其它 AI 的 review-improve-*.md 完全独立撰写。
>
> **重要原则**：本报告不重复 `03-todo.md §5.4/§5.6` 中已提出的规则草案（元注释六类、因果链编造、x86 偏向叙述、附录化展开），而是在此基础上**从规则集的系统性视角**审视：现有规则集为什么会遗漏这些模式？还有哪些更深层的问题？

## 0. 一句话诊断

> 现有 `prompt/review-rules/` 是一个**"以 claim 校验为中心"**的规则集，但 03 案例暴露的真正问题是：文档质量失败模式中有相当一部分**不是 claim 错误**，而是**作者没有意识到自己在"做某事"**——作者元注释、因果链编造、架构范围隐含、概念驱动 vs 实现驱动方向反了——这些都是**心智层失败**而非**事实层失败**。规则集需要从"校验事实"扩展到"暴露作者心智"。

下面分六块展开。

## 1. 关键发现 1 — "散文质量"作为独立维度缺失

### 1.1 现象

03 案例在第五轮 §5.1、§5.6 反复清理的"作者元注释"问题，分布在原文档 10+ 处：

- `L16` `"**本章不讲什么**（边界声明，避免读者偏离主线）:"`
- `L39` `"**过渡**：这种保护靠 CPU 硬件特权级实现。引出 1.2。"`
- `L43` `"本节只回答…（后者移到 §1.4a，避免重复）"`
- `L57` `"（概念点到，细节延后）"`
- `L68` `"用一张图建立…这是真正的架构抽象。"`
- `L106` `"（不展开，只建模型）"`
- `L143` `"（本节最难理解，必须加）"`
- `L161` `"是本节核心教学价值"`
- `L163` `"（必须点明）"`
- `L195` `"**RISC-V 特色必须强调**"`
- `L253` `"**历史遗留一句话带过**"`
- `L300` `"**修正"正交"表述**：早期文档曾表述…"`
- `L363-372` 四处 `"为什么需要？因为…"`

这些都不是"事实错误"——每一句元注释拿出来单独看都"没问题"。但它们累积起来，让文档读起来像"开发者的写作笔记"而不是"读者的学习材料"。

### 1.2 现有规则的覆盖盲区

逐条核对现有规则：

| 现有规则 | 是否覆盖元注释？ | 备注 |
|---------|----------------|------|
| `review-doc-checklist.md §2.11 文档风格` | **部分**：只覆盖进度标记（"已实现/待实现"、✅❌🚧） | 缺元注释 |
| `review-doc-checklist.md §3.1 文本流畅性` | **否**：只覆盖语病、长句、被动语态 | 缺元注释 |
| `review-doc-checklist.md §3.2 逻辑组织` | **部分**：提到"段落之间是否有明确的逻辑衔接" | 但没定义"作者自述"是元注释 |
| `review-doc-checklist.md §3.3 冗余控制` | **否**：聚焦内容重复 | 缺元注释 |
| `review-doc-checklist.md §3.4 读者体验` | **否**：聚焦读者侧体验 | 缺作者侧 |
| `review-patterns.md 模式15` | **否**：只覆盖"开发记录风格" | 缺元注释 |
| `review.md §审查优先级矩阵` | **否**：没有"作者元注释"分类 | 缺 |

**核心盲区**：现有规则检查"读者读到什么"，但**不检查"作者在做什么"**。作者元注释暴露的是"作者的写作过程"（"我现在要过渡"、"这节有重复"），不是"读者的接收结果"。

### 1.3 改进建议

**1.3.1** 在 `review-doc-checklist.md` 新增 **§3.7 作者意图透明性（Author Intention Transparency）**，专门检查"作者元注释"。

判定口诀（建议规则化）：
> **"删掉这段后，读者对主题（保护结构、内存分配等）的理解是否减少？"**
> - 减少 → 是正文，保留
> - 不变 → 是元注释/导航，删除或改写
> - 减少一点点但增加大量元信息 → 折中：保留核心信息，元注释删

**1.3.2** 该维度初始分类为 P2（可读性），>5 处 → P1（系统性风格问题）。未来如果反复出现，可升级为 P1 默认。

**1.3.3** 不在主清单里展开"作者元注释六分类"——那是 review-patterns.md 的事。主清单只引用：
> 详见 `review-patterns.md` 模式 P（作者意图透明性六类）。

**1.3.4** 在 `review.md §审查优先级矩阵` 加一行：

| 维度 | 优先级 | 说明 |
|------|-------|------|
| §3.7 作者意图透明性 | P2/P1 | 暴露作者写作过程的元注释。>5 处 → P1 |

## 2. 关键发现 2 — "因果链验证"作为独立 Step 缺失

### 2.1 现象

03 案例 §5.6.2 暴露了一个 P0 错误：

> §2.1 第 2 条解释 `memcpy(&kinfo, local_cbi, sizeof(kinfo))` 时，原版写：
> > `local_cbi` 是 `kmain` 的参数，位于调用者的栈帧中。`kmain` 调用 `cstart()`，`cstart()` 再调用 `proc_init()` 等一系列函数，原调用者的栈帧最终会被覆盖。如果不把启动信息拷贝到全局变量 `kinfo`，后续代码访问 `local_cbi` 时读到的是被覆盖后的垃圾值。

技术上是错误的：嵌套调用链中，只要 `kmain` 还在栈上没返回，它的栈帧一直存在，`local_cbi` 指向的内容不会被覆盖。"调用链推进后栈帧被覆盖"是想当然的因果链。

这个错误的特殊性在于：
1. **每一个底层事实都是真的**：`local_cbi` 确实是参数，确实在调用者栈帧里，确实可能被覆盖（如果 kmain 返回的话）
2. **因果链是假的**：当前没有 kmain 返回，所以不会被覆盖
3. **"未被覆盖" 才是正确的因果链**：因为非 kmain 调用链的代码需要访问 kinfo

### 2.2 现有规则的覆盖盲区

| 现有规则 | 是否覆盖因果链？ | 备注 |
|---------|----------------|------|
| `review-doc-checklist.md §2.0 Claims-Evidence Tracing` | **部分**：要求"每条 claim 都有 evidence" | 但**只验证单个 claim 的真实性**，不验证多个 claim 之间的因果链 |
| `review-doc-checklist.md §2.1 概念准确性` | **部分**：要求"概念解释与源码一致" | 概念解释中的因果链可能正确也可能错 |
| `review-patterns.md 模式34 注释理由虚假或牵强` | **部分**：覆盖代码注释中的理由 | **不覆盖文档正文中的因果链**（这是个真正的盲区） |

**核心盲区**：`§2.0 Claims-Evidence` 是**静态的**——每条 claim 独立验证。但解释（"为什么这样设计"、"为什么需要这个操作"）是**动态的**——多条 claim 通过因果关系组合成解释，因果链本身可能错。

### 2.3 改进建议

**2.3.1** 在 `review-doc-checklist.md §2.0` 末尾新增 **Step 2.0.4：因果链验证（Causal Chain Validation）**：

执行规则：
- 对文档中所有"为什么 X" / "X 的原因是 Y" / "X 是因为 Y" / "X 由 Y 决定" 类型的解释，识别其因果链
- 对每条因果链，验证：去掉中间环节后，结论是否仍然成立？
- 如果结论"显然错误"或"中间环节可证伪"→ P0

```
示例验证（03 案例）：
claim A: local_cbi 在调用者栈帧中 ✅
claim B: kmain 调用 cstart(), cstart() 调用 proc_init() 等 ✅
claim C: 调用链推进后，调用者栈帧被覆盖 ❌（在 kmain 返回前不会）
因果链: A → B → C → 结论
     去除 C: 结论不成立 → 因果链断裂 → P0
```

**2.3.2** 在 `review-patterns.md` 新增 **模式 Q：因果链编造（Causal Chain Fabrication）**：

> 特征：为了解释某个操作的目的，编造看似合理但技术上错误的因果链。  
> 检测：每个解释里出现"因为…会被覆盖/失效/丢失"，**必须用 C 语言语义可验证**（如"局部变量作用域限于函数内"是 C 标准保证的）。  
> 判定：违反 → P0（正确性问题）。  
> 根因：§2.0 Claims-Evidence 没区分"单个 claim 验证"与"claim 间因果链验证"。

**2.3.3** 在 `review-process.md §Step 3` 中加一个子步骤：

```
Step 3.5a（NEW）：因果链抽样验证
- 从 Ch2 抽取 5-10 个"为什么这样设计"的解释
- 对每个解释，识别其因果链（A→B→C→结论）
- 验证因果链每一步是否成立
- 失败 → P0
```

**2.3.4** 与模式 34 的关系：模式 34 是"代码注释的理由虚假"，本规则是"文档正文的因果链编造"。两者**不重叠**——一个是代码侧，一个是文档侧。规则集中应明确划分。

## 3. 关键发现 3 — "架构范围标注"作为独立检查项缺失

### 3.1 现象

03 案例 §5.6.3 暴露：

> §1.8 "为什么 cstart 必须先于后续所有阶段"段，原版只讲 x86 的 GDT 约束（"段寄存器依赖 GDT 描述符"），未点明这是 x86 特有。读者会误以为是三架构统一约束。

03 案例的整个 Ch1 重构核心就是**三架构对照**——x86 / aarch64 / riscv64 各自不同的保护结构实现。但旧文档的叙述自然倾向 x86 视角，因为 Minix3 主线是 x86，aarch64/riscv64 是 minix-rs 扩展。

### 3.2 现有规则的覆盖盲区

| 现有规则 | 是否覆盖架构范围标注？ | 备注 |
|---------|--------------------|------|
| `review-doc-checklist.md §2.5 架构演进说明` | **部分**：只覆盖"Minix3 vs minix-rs"差异 | 不覆盖"本文档描述的是哪个架构" |
| `review-patterns.md 模式4 架构差异未说明` | **否**：只覆盖"Minix3 32位 vs minix-rs 64位"的字段级差异 | 不覆盖"x86 vs aarch64 vs riscv64 的描述范围" |
| `review.md §核心原则` | **部分**：提到"行为语义优先" | 不显式要求标注架构范围 |

**核心盲区**：现有规则假设读者能区分"x86-32 Minix3"和"x86-64 minix-rs"两种语境，但不显式要求**作者**标注"这段描述适用于哪个架构子集"。当描述跨架构的"共性"或"x86 特有"时，需要显式标记。

### 3.3 改进建议

**3.3.1** 在 `review-doc-checklist.md §2.1` 末尾新增 **Step 2.1.5：架构范围标注**：

执行规则：
- 抽取 Ch1/Ch2/Ch3 所有提到具体架构机制（GDT/IDT/TSS/VBAR/stvec/SP_EL1/sscratch/PTE.U/AP 等）的句子
- 检查每句是否标注了架构范围
- 未标注 → P1（读者默认理解为"三架构统一"或"通用" → 误导）

**3.3.2** 标注格式建议（写入 review-doc-skill.md）：

| 标注方式 | 适用 |
|---------|------|
| `> 架构范围：x86-64`（引用块） | 单架构段落开头 |
| `> 架构范围：三架构共性` | 通用段落 |
| `> 架构范围：x86-64 特有 / aarch64 特有 / riscv64 特有` | 特有机制 |
| 行内括号 `(x86-64 特有)` | 段落内个别句子 |

**3.3.3** 在 `review-patterns.md` 新增 **模式 R：架构范围隐含（Architecture Scope Implicit）**：

> 特征：描述某个架构机制时未标注架构范围，读者默认理解为三架构统一。  
> 检测：`rg "GDT|段描述符|TSS|IST|swapgs|MSR_LSTAR|stvec|sscratch|VBAR|SP_EL" doc.md` 每条匹配必须相邻位置有架构范围标注。  
> 判定：未标注 → P1。  
> 根因：现有规则检查"差异是否说明"（Minix3 vs minix-rs），不检查"描述的架构范围是否明确"（x86 vs aarch64 vs riscv64）。

**3.3.4** 该规则与模式 4 的关系：模式 4 是"数据结构的字段级差异"，本规则是"叙述的架构范围"。**两者不重叠**——一个是数据层，一个是叙述层。

## 4. 关键发现 4 — "文档设计哲学"作为独立维度缺失

### 4.1 现象

03 案例的 Ch1 重构本质是**设计哲学的转变**：

| 维度 | 重构前（实现驱动） | 重构后（概念驱动） |
|------|------------------|------------------|
| 起点 | `prot_init()` 源码 | "什么是保护"WHY 地基 |
| 主线 | GDT/IDT/TSS 三个名词 | CPU 视角三问 |
| 节奏 | 列名词 → 总结 | 提问题 → 找答案 |
| 读者收获 | "有这些东西" | "三架构其实是一回事" |
| 教学角色 | 说明书 | 教科书 |

03 案例的 §1.4 引入"CPU 视角三问"是这个转变的核心：把"prot_init 给 CPU 填三个答案"作为主线，让所有 GDT/IDT/TSS/VBAR/stvec 都成为"回答三问的具体实现"。

### 4.2 现有规则的覆盖盲区

| 现有规则 | 是否覆盖文档设计哲学？ | 备注 |
|---------|--------------------|------|
| `review-doc-checklist.md §3.5 教学性质量` | **部分**：有"说明书 vs 教学文档"二分 | 但没要求作者**主动选择**哲学 |
| `review.md §核心原则` | **否**：聚焦"Rewrite vs Translate vs Redesign" | 不关注"概念驱动 vs 实现驱动" |
| `review-patterns.md 模式15` | **否**：只覆盖开发记录风格 | 缺文档设计哲学 |

**核心盲区**：现有规则检查"文档写得对不对"（事实层），但**不检查"作者选的设计哲学对不对"**。03 案例显示：错误的哲学（"实现驱动"）可以让整篇文档技术正确但教学失败。

### 4.3 改进建议

**4.3.1** 在 `review-doc-checklist.md` 新增 **§3.6 文档设计哲学（Document Design Philosophy）**：

执行规则（Step 3.6.1 哲学选择）：
- 抽取 Ch1 的开头、Ch1 总结、Ch3 引言
- 判定该文档属于以下哪种：
  - **概念驱动（Concept-first）**：以"为什么需要 X"为起点，以"X 的设计哲学"为骨架
  - **实现驱动（Implementation-first）**：以"Minix3 C 源码"为起点，以"实现细节"为骨架
  - **混合（Hybrid）**：以"问题"为起点，问题驱动的实现分析
- 同一份文档内部要保持哲学一致

执行规则（Step 3.6.2 主线检验）：
- 抽取 Ch1 的所有"主线"陈述（加粗、表格标题、H2 标题）
- 验证：这些陈述是否构成一个**统一骨架**？
- 例如 03 案例的重构后，Ch1 骨架是"三问"——三问→三架构对照→三问的实现定位。读者读完应该能复述这个骨架。

**4.3.2** 在 `review-patterns.md` 新增 **模式 S：实现驱动伪装概念驱动（Implementation-Driven Masquerading as Concept-Driven）**：

> 特征：作者声称写"概念文档"，但实际主线是源码实现。  
> 检测：从 Ch1 抽取 5 个加粗概念句，验证每个是否能在 Ch2/Ch3 找到对应源码？还是只是"概念化的实现描述"？  
> 判定：>50% 概念句本质是"实现描述的抽象化重写" → P1（哲学错位）。  
> 案例：03 旧 Ch1 的"三个问题"实际是 GDT/IDT/TSS 的抽象重写。

**4.3.3** 该规则与 `§3.5 教学性质量` 的关系：§3.5 检查"教学性表现"（有没有引导语、有没有注释、有没有 C 源码对照），§3.6 检查"教学性的根基"（设计哲学对不对）。**§3.6 是更基础的检查**——哲学错了，§3.5 做得再好也只是把实现驱动伪装成概念驱动。

## 5. 关键发现 5 — Rule Evolution 机制完全缺失

### 5.1 现象

03 案例本身是 Rule Evolution 的极好示例：

| 轮次 | 用户/AI 新发现的模式 | 规则的响应 |
|------|------------------|----------|
| 1 | 缺少 WHY 地基 | （无对应规则）|
| 2 | 缺少 CPU 视角统一抽象 | （无对应规则）|
| 3 | 1.2/1.4a 内容重叠 | （无对应规则）|
| 4 | 三问还是 OS 视角、1.3 流程图 RISC-V 不对 | （无对应规则）|
| 5 | 元注释、Ch3 决策日志 | 部分（"开发记录风格"模式 15 接近）|
| 6 | 元注释六类、因果链编造、x86 偏向、附录化展开 | **完全无对应规则**（需要新增）|

这个过程本身是**用户驱动 + AI 辅助**的——用户粗读发现新模式，AI 归纳成规则。但**没有自动化机制**。03 案例的 §5.4 明确说"待用户确认后正式写入 skill"——这意味着规则集的更新是**手动**的、**滞后的**。

### 5.2 现有规则的问题

| 现有规则 | 是否支持 Rule Evolution？ | 备注 |
|---------|----------------------|------|
| `review-process.md` 整个 | **否**：执行步骤是"应用现有规则"，不是"发现新规则" | 缺"rule discovery" |
| `review-socratic-skill.md` | **部分**：苏格拉底追问有 8 个场景 | 缺"在 review 中发现新模式时的追问" |
| `review.md` 整个 | **否**：核心原则是"以 Minix3 源码为真理" | 缺"规则集本身的真理" |

**核心盲区**：规则集是**静态的**，没有"rule discovery"或"rule evolution"机制。这意味着：
1. 新模式必须被用户粗读发现
2. 规则集更新需要用户 + AI 多轮交互
3. 容易出现"这次发现但下次又重蹈"的情况

### 5.3 改进建议

**5.3.1** 在 `review-process.md` 新增 **Step 7.5：Rule Discovery（规则发现）**：

执行规则：
- Review 完成后，AI 必须自问：
  - "本次 Review 中我标记的 P0/P1 中，是否有 ≥2 条属于同一类**新**模式？"
  - "新模式**在现有 rules/patterns/profiles 中都没有**？"
  - "新模式**可以泛化到其他文档/模块**？"
- 三条都满足 → AI 主动生成"新模式提案"，写入 scan.md 的"§Rule Discovery"小节
- 提案包含：模式名、模式定义、案例、判定标准、建议归入哪个文件
- 用户在下一轮 review 中确认 → 正式加入规则集

**5.3.2** 在 `review-socratic-skill.md` 新增 **场景 9：Rule Discovery 追问**：

```
场景 9：Rule Discovery 追问

触发条件：AI 在 Review 中标记了一条 P0/P1，但不确定它属于现有哪一类模式。

追问话术：
- "这个错误是**第一次出现**还是**已有先例**？"
- "如果是已有先例，现有规则是否覆盖？"
- "如果不覆盖，**为什么过去没发现**？是规则盲区还是场景罕见？"
- "这个错误能否被**预防**？如果能，需要什么规则？"
- "这个规则应该归入 review-patterns.md / review-doc-checklist.md / review-process.md / 新文件？"
```

**5.3.3** 在 `review.md` 新增 **§规则演化机制（Rule Evolution）**：

```
规则集本身不是真理。

规则集是"在 Minix-RS Review 历史中反复出现的失败模式的归纳"。

规则集的真理来源：
1. 历史 review 中被反复标记的 P0/P1 模式
2. 用户/AI 在 review 中发现的新模式（Rule Discovery）
3. 跨模块复用：模块 A 的失败模式是否在模块 B 出现？

规则集的演化步骤：
1. 触发：用户/AI 在 review 中发现 ≥2 次同类新模式
2. 提案：AI 生成新模式提案（含案例、判定、归类）
3. 评审：用户确认是否纳入
4. 落地：写入对应 rules 文件，附"来源：xxx 案例"
5. 验证：下一轮 review 验证新规则是否生效
```

**5.3.4** 在每个 review 完成后强制填写：

```markdown
### Rule Discovery（强制）
- 本次 Review 是否发现新模式？[✅ / ❌]
- 如果 ✅，新模式名：[名称]
- 新模式案例：[file:line + 简要]
- 新模式归类：[patterns / doc-checklist / process / 新文件]
- 建议规则草案：[一段话]
```

## 6. 关键发现 6 — 苏格拉底追问应该触及"本质向"问题

### 6.1 现象

03 案例 §5.4 末尾用户原话：

> 苏格拉底提问（review-socratic-skill）也应该多问这些偏本质向、触及读者灵魂、触及本质的问题。

这句话点出了一个独立的关键问题：现有 `review-socratic-skill.md` 的 8 个场景主要聚焦"事实层"（"这个 claim 对不对？"），不聚焦"本质层"（"为什么读者需要这个 section？" / "删掉这个 section 整篇文档还成立吗？" / "读者读完这个 section 心里建立了什么心智模型？"）。

### 6.2 现有规则的覆盖盲区

读 `prompt/skill/review-socratic-skill.md` 8 个场景（粗扫）：

| 场景 | 类型 | 缺什么 |
|------|------|-------|
| 文档与源码矛盾 | 事实层 | OK |
| 设计缺乏依据 | 概念层 | 部分 |
| 代码与设计不一致 | 事实层 | OK |
| 核心语义疑似违反 | 事实层 | OK |
| 覆盖率缺口 | 事实层 | OK |
| 卓越性改进 | 形式层 | 部分（缺"哲学层"）|
| 证据不足 | 事实层 | OK |
| 跳过检查 | 元层 | OK |

**核心盲区**：缺"心智层"和"哲学层"追问。

### 6.3 改进建议

**6.3.1** 在 `review-socratic-skill.md` 新增 **场景 10：心智模型追问（Mental Model Inquiry）**：

```
场景 10：心智模型追问

触发条件：AI 完成 Ch1/概念章节 Review 后，发现文档技术正确但教学性可疑。

追问话术：
- "读者读完这个 section，**心里能回答什么问题**？"
- "如果只能让读者记住一句话，**那句话是什么**？"
- "三架构对照表中，**三列的'共性'是哪一列**？还是说其实没有共性？"
- "这个 section 的存在，**让读者多建立了什么心智模型**？"
- "如果删掉这个 section，整篇文档的'故事线'还成立吗？"
- "作者想表达的'那个东西'，**有没有用更短的话说出来**？"
```

**6.3.2** 新增 **场景 11：哲学层追问（Philosophical Layer Inquiry）**：

```
场景 11：哲学层追问

触发条件：AI 发现文档的"设计哲学"可疑（实现驱动伪装概念驱动、概念驱动但缺哲学骨架等）。

追问话术：
- "这篇文档的**主语**是谁？prot_init() / CPU / 读者 / OS？"
- "如果主语是 prot_init()，那读者学完**能独立设计**一个保护结构吗？"
- "如果主语是 CPU，那读者学完**能解释**为什么三架构是同一回事吗？"
- "作者**想要读者带走什么**？一句话能说出来吗？"
- "如果只能让读者带走三样东西，**是哪三样**？"
- "文档的**骨架**是什么？是按时间、按空间、按问题、还是按架构分块？"
```

**6.3.3** 这两个场景是 `review-excellence-skill.md` 的"卓越性"维度的**前置**——卓越性检查"形式"，心智模型追问检查"内容"。**心智模型是卓越性的基础**。

## 7. 其他次要建议

### 7.1 优先级矩阵未覆盖新维度

`review.md §审查优先级矩阵` 现有：

| 维度 | 优先级 | 说明 |

| ... | ... | ... |

建议补：

| 维度 | 优先级 | 说明 |
|------|-------|------|
| 文档 | 因果链编造（解释错） | P0 |
| 文档 | 架构范围未标注 | P1 |
| 文档 | 实现驱动伪装概念驱动 | P1 |
| 文档 | 作者元注释（>5 处）| P1 |
| 文档 | 作者元注释（<5 处）| P2 |
| 文档 | 附录缺失但需展开 | P2 |

### 7.2 §2.0 Claims-Evidence 应增加"解释链"维度

`review-doc-checklist.md §2.0` 现有 Step 2.0.1-2.0.3 聚焦单个 claim。建议增加：

**Step 2.0.4（NEW）：解释链验证**

> 文档中所有"为什么 X" / "X 的理由是 Y" 类型的解释，构成"解释链"。  
> 对每条解释链：  
> 1. 列出所有中间 claim（链节点）  
> 2. 验证每个节点是否可独立验证（强/中/弱）  
> 3. 验证节点间的因果关系是否成立  
> 4. 弱节点 ≥ 1 个或因果断裂 → P0  

### 7.3 review-patterns.md 应建立"模式分组"目录

现有 patterns.md 是 35 个模式的扁平列表。03 案例暴露的几类新模式有共同主题（散文质量），建议分组：
