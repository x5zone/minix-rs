## 0. 核心诊断：现有规则的三个盲区

通读 03 案例后，我把暴露的问题归为三类盲区：

| 盲区 | 现有规则覆盖 | 案例证据 | 后果 |
|------|------------|---------|------|
| **A. 解释正确性** | §2.0 只验"claim 有无 evidence"，不验"explanation 的因果机制是否技术上正确" | §5.6.2 `local_cbi` 因果链编造（P0） | 文档"看起来都对"，但 BECAUSE 部分是编的 |
| **B. 叙事架构** | §1 只规定章节骨架（Ch1/Ch2/...），不规定 Ch1 内部"概念驱动 vs 实现驱动"的方向 | 整个 Ch1 从 prot_init() 出发总结概念，方向反了 | 读者读完不知道"为什么需要这些机制" |
| **C. 作者自省泄露** | §2.11 只管"开发记录风格"（已实现/待实现），不管"写作策略元注释" | §5.6.1 六类元注释泄露进正文 | 读者读到"本节只回答…避免重复"会出戏 |

这三个盲区下，我提出 14 项具体改进，按"规则文件 → 新增/修订条目 → 优先级 → 证据"组织。

## 1. review-doc-checklist.md 改进建议

### 1.1 §2.0 Claims-Evidence：新增"解释正确性"子检查（P0，必加）

**问题**：现有 §2.0 把所有事实性断言当 claim，验"有无 evidence"。但 03 案例的 P0 错误是：claim 本身对（`memcpy(&kinfo, local_cbi, ...)` 确实在源码里），但作者给的 BECAUSE 解释（"调用链推进后栈帧被覆盖"）是编造的——实际机制是作用域可见性。grep 验证 claim 会判"强证据 ✅"，漏掉解释错误。

**改进**：在 §2.0 Step 2.0.2 后新增 Step 2.0.3：

```markdown
### Step 2.0.3：解释因果链验证（强制，不可跳过）

> **核心原则**：claim 有 evidence 不够，解释 claim 的 BECAUSE 部分必须技术上正确。
> "因为 X 所以 Y" 中的 X 必须是真实机制，不是听起来合理的编造。

对每个带因果解释的 claim（含"因为/所以/由于/为了"的断言）：
1. 提取因果链：claim + 因为 M1 所以 M2
2. 验证 M1 是否是真实机制（用 C 语言语义/ISA 规范/源码逻辑推断，非"听起来对"）
3. 若 M1 无法直接验证，必须标注"推测，待验证"

**判定**：
- 因果链机制技术上错误 → P0（解释编造，即使 claim 本身正确）
- 因果链含未验证环节且未标注 → P1
- 因果链可由 C 语义/ISA 规范直接验证 → ✅

**典型反例**（来自 03 案例）：
- claim: "memcpy(&kinfo, local_cbi, ...) 是必要的" ✅（源码有）
- 编造解释: "因为调用链推进后原栈帧会被覆盖" ❌（C 语义上 kmain 没返回前栈帧一直在）
- 正确解释: "因为 local_cbi 作用域限于 kmain 调用链，非 kmain 链的代码（中断 handler）访问不到" ✅
```

**证据**: 03-todo.md §5.6.2 明确标 P0；这类错误 grep 抓不到，必须靠"C 语义推断"。

### 1.2 §2.1 概念准确性：新增"架构范围标注"检查（P1）

**问题**：03 §1.8 讲"cstart 必须先于后续阶段"，只讲 x86 的 GDT 约束，未标注是 x86 特有。读者误以为是三架构统一约束。现有 §2.1 验"概念是否虚构"，不验"概念适用范围是否标注"。

**改进**：§2.1 Step 2.1.4 后新增：

```markdown
### Step 2.1.5：架构范围标注验证（多架构文档强制）

对涉及 x86/aarch64/riscv64 多架构的文档：
- 叙述中出现 x86 特有机制（GDT/段描述符/TSS/IDT 门描述符/CPL）→ 必须标注"x86 特有"
- 叙述中出现 aarch64 特有机制（EL/SP_EL/VBAR/PSTATE）→ 必须标注"aarch64 特有"
- 叙述中出现 riscv64 特有机制（S/U-mode/sscratch/stvec/SPP）→ 必须标注"riscv64 特有"
- 未标注架构范围的机制描述 → 读者默认理解为三架构统一

**判定**：
- x86 特有机制未标注，文档声称覆盖三架构 → P1（误导读者以为统一约束）
- 架构特有机制标注但解释错误（如 RISC-V SPP 当作"当前特权级"）→ P0（概念错误）
```

**证据**: 03-todo.md §5.6.3；comments.md 第三轮第三处 RISC-V SPP 严谨（必改）。

### 1.3 §1 文档结构规范：新增"Ch1 概念驱动方向"约束（P1）

**问题**：现有 §1 规定 Ch1 是"概述"，但不规定 Ch1 内部叙事方向。03 原 Ch1 从 `prot_init()` 源码出发总结概念（实现驱动），重构后从 CPU 三问出发解释 prot_init（概念驱动）。这是 Ch1 质量的分水岭，但规则没约束。

**改进**：§1 "关键约束"末尾新增：

```markdown
- **Ch1 必须概念驱动，非实现驱动**：Ch1 从 WHY/WHAT（为什么需要、是什么）出发，
  落到 HOW（怎么实现）的定位，不能从源码函数出发反向总结概念。
  - ✅ 概念驱动：为什么需要保护 → 特权级是什么 → CPU 运行时三问 → prot_init 是给 CPU 填答案
  - ❌ 实现驱动：prot_init() 源码 → 总结出"保护结构"概念 → 提到特权级
  - 判定：Ch1 开篇若是"X 函数做 Y"，属实现驱动 → P1；开篇若是"为什么需要 X"，属概念驱动 → ✅
```

**证据**: 03-todo.md §1 决策表"Ch1 驱动方向"；comments.md "把第一章从实现驱动改成概念驱动"。

### 1.4 §3.5 教学性质量：新增 5 个具体教学模式（P1/P2）

**问题**：现有 §3.5 是"教学性质量"框架，但只给"引导语/注释/设计引用"等通用检查项，没有 03 案例暴露的具体教学模式。这些模式是可机械判定的，应入规则。

**改进**：§3.5 "检查项"末尾新增：

```markdown
### 教学模式检查（多架构/保护结构类文档强制）

- [ ] **统一抽象层先行**：多架构文档是否先给出三架构统一抽象（如"CPU 三问"），
      再分架构展开？流程图是否用统一抽象表述（不写"CPU 自动切栈"当 RISC-V 是软件切栈）？
      - 违反 → P1（流程图对部分架构无效，后续章节被迫推翻）
- [ ] **双向流完整性**：保护结构/trap 类文档是否同时覆盖"进入"（user→kernel）和"返回"（kernel→user）？
      - 只讲进入不讲返回 → P1（保护结构是双向门，单向叙述误导）
- [ ] **历史包袱降级**：架构特有遗留机制（如 x86 GDT）是否降级为补充章节，
      标题用疑问式（"x86 为什么还保留 GDT"）而非陈述式？
      - 遗留机制当核心讲 → P2（读者误以为是 OS 概念核心）
- [ ] **本章不讲什么框**：Ch1 引言是否有"本章不讲什么"边界声明，列出延后到后续章节的细节？
      - 无边界声明 → P2（读者偏离主线，纠结位级格式等细节）
- [ ] **附录化深度展开**：当 WHY 完整论证会打断概念流时，主文一句话建模型 + 文末附录展开？
      附录须含：威胁模型/前提 + 具体机制 + 防御对应 + 总结。
      - WHY 论证打断概念流且无附录 → P2（想深入的读者无归宿）
```

**证据**: 03-todo.md §2 决策表（统一抽象/返回闭环/GDT 降级/本章不讲什么）；§5.6.4（附录化）。

### 1.5 §3.3 冗余控制：新增"因果链重复"检查（P2）

**问题**：03 原 Ch1 §1.2 和 §1.4a 都讲了"特权级 → 页表权限位 → 访问控制"，读者产生"我刚看过这个"的 deja-vu。现有 §3.3 查"概念重复"，但不查"因果链重复"——同一套因果关系在多节展开。

**改进**：§3.3 新增：

```markdown
- [ ] **因果链重复**：同一套因果关系（如 A→B→C）是否在多个章节完整重讲？
      - 同一因果链在 2+ 节完整展开 → P2（应拆分：A 节讲 A，B 节只讲 B 作为 A 的后果）
      - 03 案例：§1.2 讲"特权级→页表权限"，§1.4a 又讲一遍 → 应 §1.2 只讲特权级是什么，§1.4a 讲特权级如何落地为权限
```

**证据**: 03-todo.md §1 决策表"1.2/1.4a 去重"；comments.md 第一处。

## 2. review-patterns.md 改进建议

### 2.1 新增模式48：因果链编造（P0）

```markdown
### 模式 48：因果链编造（解释正确性，P0）

❌ 错误：claim 正确，但 BECAUSE 解释编造看似合理的技术机制
        文档："memcpy(&kinfo, local_cbi, ...) 是必要的，因为 kmain→cstart→proc_init
        调用链推进后，原调用者栈帧会被覆盖。"
        → claim 对（源码有 memcpy），但"栈帧被覆盖"是编造的（kmain 没返回前栈帧一直在）

✅ 正确：用 C 语义/ISA 规范可验证的因果链
        文档："memcpy(&kinfo, local_cbi, ...) 是必要的，因为 local_cbi 是 kmain 的局部参数，
        作用域限于 kmain 调用链。非 kmain 链的代码（中断 handler）访问不到，需拷贝到全局。"

> 原因：grep 能验 claim 有无 evidence，验不了 BECAUSE 是否技术上正确。
> 编造的因果链比"无证据"更危险——读者会信以为真并据此推理。
> 判定：BECAUSE 部分机制技术上错误 → P0，即使 claim 本身正确。
```

**证据**: 03-todo.md §5.6.2；这是案例中唯一的 P0 级新错误类型。

### 2.2 新增模式49：写作策略元注释泄露（P2，>5处 P1）

```markdown
### 模式 49：写作策略元注释泄露（作者自省进正文，P2）

❌ 错误：作者对自己写作策略的注释进入读者正文
        - 过渡类："引出 §1.4"、"**过渡**：…引出 1.2"
        - 范围声明类："本节只回答…避免重复"、"概念点到，细节延后"
        - 深度策略类："一句话带过"、"不展开，只建模型"
        - 作者自我强调类："必须加"、"本节最难理解"、"是本节核心教学价值"
        - 历史修正叙述类："早期文档曾表述…这不准确"、"修正…表述"
        - 自问自答修辞类："为什么需要？因为…"

✅ 正确：教科书直接"做"过渡、"做"范围控制，不"说"自己在做
        - 删过渡类（自然过渡即可）
        - 范围声明改为"细节见 [X.md]"
        - 删自我强调（内容本身证明重要性）
        - 历史修正直接正面陈述
        - 自问自答改为直接陈述

> 判定标准：删掉这段后，读者对主题的理解是否减少？
>   减少 → 是正文，保留
>   不变 → 是元注释，删除或改写
> 单处 → P2；>5 处 → P1（系统性风格问题）
> 与模式15（开发记录风格）的区别：模式15 是"已实现/待实现"进度追踪；
> 模式49 是"作者 narrate 写作策略"。两者都是作者视角入侵读者视角，但内容不同。
```

**证据**: 03-todo.md §5.6.1 六类完整分类。

### 4.1 新增场景9：叙事架构追问（本质向提问）

**改进**：新增场景9：

```markdown
## 场景 9：叙事架构追问（本质向，触及读者心智模型）

**触发条件**：文档正确性通过，但读完后"不知道到底在讲什么"或"抓不住主线"。

**话术模板**：
```
这篇文档每句话似乎都对，但我读完后无法回答：
1. {核心概念}到底是什么？为什么需要它？
2. {章节}的主线是什么？读者读完应该建立什么心智模型？
3. {Ch1}是从"为什么需要 X"出发，还是从"X 函数做 Y"出发？
4. {核心抽象}是否被低知识量内容淹没？
5. {多架构内容}是否先给统一抽象，还是直接堆三架构细节？

能否帮我确认：这篇文档的叙事架构是否概念驱动？核心主线是否清晰？
```

**判定路径**：
- 实现驱动 → 标 P1（模式52），建议重构为概念驱动
- 核心抽象被淹没 → 标 P1（模式51），建议重组 Ch3
- 多架构无统一抽象 → 标 P1（§3.5 教学模式），建议加统一抽象层
- 叙事架构清晰 → 记录为卓越性观察，不标问题
```

**证据**: 03-todo.md §5.4 "苏格拉底提问也应该多问这些偏本质向、触及读者灵魂、触及本质的问题"。

### 4.2 新增场景10：解释正确性追问

**问题**：场景7（证据不足）问"claim 有无 evidence"，但不问"BECAUSE 是否技术上正确"。因果链编造需要独立追问。

**改进**：新增场景10：

```markdown
## 场景 10：解释正确性追问（因果链是否编造）

**触发条件**：文档 claim 有 evidence，但 BECAUSE 解释听起来"太顺"或"想当然"。

**话术模板**：
```
文档 §X 说 "{claim}"，源码确实如此。但解释是"因为 {M1} 所以 {M2}"。
我对 {M1} 这个机制有点不确定：
1. {M1} 是 C 语言语义/ISA 规范保证的，还是推测的？
2. 能否用源码逻辑或语言规范验证 {M1}？
3. 如果 {M1} 无法验证，是否应标注"推测，待验证"？
```

**判定路径**：
- M1 可由 C 语义/ISA 规范验证 → ✅
- M1 无法验证且未标注 → 标 P1，要求标注"推测"
- M1 技术上错误 → 标 P0（模式48 因果链编造）
```

**证据**: 03-todo.md §5.6.2 `local_cbi` 案例。

## 5. review-process.md 改进建议

### 5.1 新增"大纲收敛判断"（防止过度迭代）

**问题**：03 案例经历 6 轮重构。GPT 第四轮判定"进入设计收益<设计成本阶段"，建议"不要再继续收集意见，直接开写"。现有 review-process.md 的收敛判断针对"review 轮次"，不针对"大纲设计轮次"。

**改进**：在收敛判断后新增：

```markdown
### 大纲设计收敛判断（针对文档重构 TODO）

当文档重构经历多轮设计评审时，判断是否该停止大纲迭代、开始写作：
- 最后一轮评审无结构性提升（只有措辞优化）→ 该开写
- 评审意见开始重复或互相矛盾 → 该开写
- 核心架构决策已收敛（如 03 的"CPU 三问"框架确定）→ 该开写

**反信号**（不该停）：
- 评审发现新的 P0/P1 错误类型 → 继续迭代

```

## 7. 我独立观察到的、TODO/comments 未明确提及的点

以下是我在分析中独立发现的，TODO 和 comments 没有直接提出但隐含的问题：

### 7.1 "流程图架构有效性"应作为独立检查

03 §1.3 流程图写"CPU 自动切栈"对 RISC-V 无效。这不是"架构范围未标注"（模式50），而是"流程图本身对部分架构无效"。建议 §3.5 教学模式里"统一抽象层先行"检查项明确包含：**流程图表述必须对所有覆盖架构有效，否则加注架构差异**。

### 7.2 "问题式标题"作为微教学技巧

GPT 建议 "x86 为什么还保留 GDT"（疑问式）优于 "GDT：x86 的实现载体"（陈述式）。疑问式标题天然回答读者疑问。这可作为一个卓越性 P2 模式：**补充性章节讲遗留/特殊机制时，标题用疑问式**。

### 7.3 "示例选择"对概念引入的影响

03 把 `*(0xffffffff80000000)=0` 改为 `*((int*)0)=0`，避免初学者分心"为什么这个地址是内核地址"。现有规则不检查"概念引入示例是否最小化认知负担"。建议 §3.4 读者体验新增：**概念引入示例是否避免引入与核心机制无关的细节**。

### 7.4 "保存/恢复对称性"作为领域特定完整性检查

保护结构/trap 类文档，讲 entry（保存现场）必须讲 return（恢复现场）。这是领域特定的完整性，类似"双向流完整性"但更具体。可归入 §3.5 教学模式的"双向流完整性"项。

### 7.5 现有 §2.11 与新模式49 的边界需明确

§2.11 管"开发记录风格"（已实现/待实现/✅❌），新模式49 管"写作策略元注释"。两者都是"作者视角入侵读者视角"，但内容不同。建议在模式49 末尾显式标注与模式15（§2.11）的区别，避免 reviewer 混淆。

## 8. 总结

03 文档案例是一块好的"试金石"——它暴露了现有 review-rules 的核心盲区：**能抓"claim 错"和"无 evidence"，抓不了"解释编造"和"叙事方向反了"**。

我的 14 项改进建议聚焦三个盲区：
1. **解释正确性**（§2.0.3 + 模式48）——防 grep 抓不到的 P0
2. **叙事架构**（§1 概念驱动 + 模式51/52 + §3.5 教学模式）——防"每句都对但读完不懂"
3. **作者自省泄露**（模式49）——防"作者 narrate 写作策略进正文"

这三类问题的共同特征是：**grep 抓不到，需要 reviewer 理解文档叙事后才能判定**。因此它们在现有"机械化检查"框架下系统性漏检。加入这些规则后，reviewer 会在"正确性 gate"之外多一层"叙事性 gate"，覆盖 03 案例中靠 GPT 评审 + 用户粗读才发现的问题。

最小可行改进集：只加 §2.0.3（解释正确性）+ 模式48/52/51/50 + §1 概念驱动约束，即可覆盖 03 案例的 P0 和主要 P1。其余为质量提升项，可分批加入。
