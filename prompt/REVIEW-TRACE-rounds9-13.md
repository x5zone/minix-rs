## 一、串行循环的价值：暴露"修了但没修透"

这是本批最重要的方法论结论。前 8 轮（含并行那批）都是"修完就往下走"，本批每轮带**上一轮修复验证**作业，于是连续抓到：

| 上轮修复 | 本轮验证结论 |
|---|---|
| R9-D1 C 目录单一真相源 | R10 ✅ 完全生效（fs/ipc/drivers 三案例 `--c-dir` 均真实存在） |
| R9-D2 跨行签名 | R10 ⚠️ 只覆盖无嵌套括号形态 → **R10-D2**；修完 R11 ⚠️ 主症状修、幻影 `UNUSED` 复现 → **R11-D1**；再修 R12 ⚠️ 收尾行回喂单行正则仍复现 → **R12-D1**；三修后 R13 ✅ 六目录重放全 0 |
| R9-D3 中文数字坐标 | R10 ⚠️ 标签不进 stdout → **R10-D3**；修完 R11 ✅ |
| R9-D4 SL-4 头部豁免 | R10 ❌ **补到了不存在的形态**（全仓 0 篇 `> **已改写**`；真实形态是 `> **状态**: 已改写`，26 篇受影响）→ **R10-D1**；修完 R11 ✅（正对照：正文日期仍报） |
| R11-D2 卫生项标签 | R12 ❌ **修复本身引入新缺陷**：散文坐标双打印、`--side rust` 仍输出 C 侧 → **R12-D2**；修完 R13 ✅ |
| R12-D4 STATE 孤儿检查兜底 | R13 ⚠️ 主症状修，但 `### Open 项（Round N）` 子段不可见 → **R13-D1**；修完提取到 9 条 |

**结论**：一次修复的"形态覆盖"平均要 2–3 轮才能收敛。**并行跑法结构上不可能发现这一点**（同一批里没有"修复后的下一轮"）。用户要求的串行修复循环是发现这类问题的唯一途径，这条应写进流程规范。

## 三、串行五轮对"流程正确性与健壮性"的总结论

1. **正确性**：五轮再挖出 **4 处真实代码语义偏移**（IPC 信号量掩码、驱动随机源的错号门与 AES 密钥、输入事件打包步幅、PM 收养子进程的 trace 选项），全部由"文档 ↔ C 源 ↔ Rust 实现"三方对账逼出，修复后测试数字均上升且反向验证通过。累计 13 轮已挖出 7 处真实代码 bug。
2. **健壮性**：本批 20 条流程缺陷里，**12 条是"修复的形态覆盖不足"**——即"改一处、漏一处"的同族问题（跨行签名的三种形态、坐标形态的四次迭代、SL-4 的四种头部形态、STATE 的三层结构）。这说明**流程修复本身也需要"反向验证"**：改完必须用真实语料（全仓 grep 该形态）确认覆盖面，而不是只验证手头那一个案例。
3. **串行 vs 并行**：并行能更快铺开 stage 覆盖（R4–8 五轮并跑约 35 分钟），但**结构上无法发现"修复未修透"**；串行慢但每轮都在检验上一轮。二者互补：**广度用并行、修复收敛必须串行**。这条已写入检查项注册表。
4. **仍未根治**：行号门的 AMBIG 存量与字段级坐标进底账两条，需要一个专门的工具轮次（不宜夹在文档 review 里做）。
