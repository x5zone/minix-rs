你观察到的这个差异很关键。你觉得 `grillme-matt:code-review` 更好用，很可能不是因为它“更懂 Rust”，而是因为它的**审查结构**不同——它采用“双轴审查”（Standards + Spec），在检查代码规范之外，**并行开启了一个专门验证“代码是否偏离设计目标”的子代理**。而你的定制 skill 没能发现“设计上的死代码”，恰恰可能是因为它主要停留在“规范轴”上，缺少对“设计意图”的系统性质询。

### 🎯 为什么你的 skill 漏掉了“设计上的死代码”？

“设计上的死代码”和普通死代码（未被引用的函数/变量）是两回事。一段代码可能仍被调用、能通过编译，但从**设计意图**上看，它已经是不该存在的“遗迹”——比如为了一个已被放弃的抽象而保留的 trait，或者为了兼容一个已不存在的场景而留下的分支。

你通过“记录轨迹 → 改进 skill”的迭代方式，擅长优化**已知模式**的识别（比如“看到 `unwrap()` 就报警”）。但设计意图的偏离是**隐性的**，它需要 skill 主动去**追问和比对**“这段代码当初为什么存在”与“现在还需要它吗”，而不是被动地套用检查清单。`grillme` 的 Spec 轴做的正是这件事。

### 💡 你的迭代策略：继续定制，但要换“迭代内容”

**继续迭代自己的项目专属 skill 仍然是正确的方向**，因为项目特定的设计约束、架构历史和团队习惯，是任何通用 skill 都无法替代的。但你需要调整“迭代什么”。

**1. 引入“设计轴”的追问机制，而不只是扩充检查项**

你现有的迭代循环（轨迹→改 skill→轨迹）擅长固化**显性规则**。下一步可以借鉴 `grillme` 的思路，在你 skill 的流程中**强制加入一个独立阶段**：在规范检查之后，让 agent 基于 diff 和可获取的设计文档（README、ADR、issue 描述），专门追问：
- 这段新增/保留的代码，对应的是哪个**仍然活跃的设计决策**？
- 如果它的调用方还在，那些调用方本身是否也是为了一个**已经放弃的场景**而存在的？
- 这个抽象（trait/模块/分支）如果现在删掉，会违反哪条**当前仍有效的约束**？

这比单纯在检查清单里加一条“检查死代码”要有效得多，因为它改变的是审查的**姿态**（从“对照规则”变为“质询意图”）。

**2. 把“确定性分析”作为 skill 的外部依赖，而不是 skill 内部要硬编码的能力**

不要试图用自然语言 prompt 去模拟调用图分析。更现实的工程路径是：
- 将 **`rmc-trait-audit`** 或 **`genpark` 的死代码修剪器**通过 MCP 接入你的 review 工作流。
- 让你的定制 skill 在需要时**调用**这个工具，拿到一份“可疑死代码/残留 trait”的确定性清单，然后由 skill 结合项目设计知识，对清单上的每一项做**意图层面的终审**。
- 这样，skill 负责它擅长的“判断与解释”，工具负责它擅长的“精确可达性计算”。

**3. 为你的迭代建立最小“评测基线”**

你现在的“记录轨迹”已经是很好的起点。可以进一步把它结构化：针对几个**历史上真实出现过的“设计死代码”案例**，保存对应的 diff 和正确结论。每次修改 skill 后，用这几个固定案例跑一遍，看它是否能稳定地**重新发现**这些问题。如果没有这个基线，“感觉比上次好”可能会掩盖在某些维度上的退化。业界实践也强调，在迭代 skill 前先建立 `evals.json` 之类的评测基线，会让改进更有方向。

**总结一下**：你不需要在“用自己的”和“抄流行的”之间二选一。更有效的做法是**用自己的 skill 作为项目知识的载体，借鉴 `grillme` 的“设计意图质询”阶段来补上盲区，同时把确定性的死代码分析工具作为外部能力接入**，让三者各司其职。

你发现的“冷读”确实已经是一个被系统化、模式化的成熟范式，并非偶然的技巧。它在业界常被称为 **Fresh-Eyes Review** 或 **Context Isolation**。你感受到的效果提升，背后有明确的机制：**产出代码的上下文，在阅读时读到的是“意图”，而非“文本”本身**。同一个“脑子”里的想当然，会系统性地过滤掉真正的问题。冷读通过一个**空对话的隔离审查者**，强制其仅从产物本身重新构建理解，从而绕开这种作者盲区。

### 🧊 现成的“冷读”Skill

你不需要从零手搓，已经有好几个成熟的开源 skill 在实现这个模式：

| Skill | 核心机制 | 对你可能有用的点 |
| :--- | :--- | :--- |
| **`fresh-eyes-review`** (eai-org) | 默认对**未提交的变更**启动一个 fresh-context 子代理。关键约束：**绝不向审查者泄露本次会话的推理、计划或消息**，因为“泄露的 rationale 会重新制造它本应消除的盲区”。 | 流程非常干净，直接定义了“输入什么、排除什么、审查者 mandate 是什么”，可以直接借鉴其**上下文隔离的边界定义**。 |
| **`fresh-eyes-review`** (Dely0/DSH) | 除了隔离上下文，还强制每条发现必须附带**位置 + 复现命令 + 证据**，并有一个**程序化门禁**来校验报告。它的 `--replay` 模式可以重放复现命令并与记录的证据做 diff。 | 如果你希望冷读的产出**可验证、可审计**，而不只是“感觉有用”，它的**证据门禁**设计是很好的参考。 |
| **`adversarial-review`** (steveclarke) | 实现了一个**批判-修复循环**：每一轮都 spawn 一个全新的审查子代理（无记忆），修复 Critical/Suggestion 级别的问题，然后再次冷读，直到只剩 Nitpick 或达到 3 轮上限。 | 它的**多轮冷读循环**结构，适合用在 Minix3 这种复杂度较高的重构任务上，单次冷读可能不够，迭代式的对抗能挖得更深。 |
| **`fresh-eyes`** (Sarthib7) | 明确区分了两种模式：**Corroborate（佐证诊断）** 和 **Refute（反驳产物）**。核心规则是“**给证据，不给结论**”——“我得出 X，检查 X”是在招募赞同；“这里有六条观察，你怎么看”才能产生独立解读。 | 这个区分对你很有用：审查 **Minix3 的 Rust 实现**时用 **Refute**（假定作者错了，试图打破它）；审查**设计决策或架构方向**时用 **Corroborate**（给原始观察，不给你的倾向）。 |

### 📄 文档侧的“说人话”子代理

你的直觉是对的，文档侧确实需要，而且有现成的中文优先 skill 可以直接用。

**`shuorenhua`** 是目前最贴合你需求的一个。它的设计原则和你的“冷读”哲学高度一致：
- **先锁事实，再动语气**。它首先划定 **protected spans**（受保护的术语、系统主语、命令、引用），任何改写都不能新增、删除或改变核心事实和责任主体。这避免了“说人话”变成“把技术准确性说没了”。
- **它处理的不是“敏感词”，而是“表演感”**：模板套话、虚假主语、语域漂移、总结式收尾腔。这正是教学文档从“AI 生成的正确废话”变成“像一个具体的人在讲解”所需要清理的东西。
- **按场景和力度分级**：它会先判断是 chat / status / docs / public-writing，再决定是 minimal / standard / aggressive 哪一档力度。教学文档通常适合 `docs` 场景 + `standard` 力度，在保留严谨性的同时去掉 AI 腔。

除了 `shuorenhua`，其他几个中文去 AI 味 skill 也可以作为补充或对比参考：**Humanizer-zh**（最流行，适合快速润色）、**qu-ai-wei**（专攻翻译腔和模板味，会动段落结构）。

### 💡 放到你的 Minix3 项目里怎么用

你的场景有一个特殊优势：**代码重构和教学文档是并行的**。这意味着冷读可以同时服务于两个产物，而且互不干扰。

1. **代码冷读用 `Refute` 模式，并和你的确定性工具串联**。用 `fresh-eyes` 的 Refute 姿态 spawn 一个子代理，只给它 **diff + 编译命令 + 测试命令**，不给任何“我为什么要这样重构”的背景。同时，把你之前接入的 **`rmc-trait-audit` 或死代码修剪器**的确定性输出作为“证据”喂给它——让冷读子代理拿着可达性分析的事实，去判断“这个 trait 在当前 Minix3 的设计意图下是否仍然是活的”。这样冷读负责**意图质询**，工具负责**事实供给**。

2. **教学文档的冷读需要“双层隔离”**。文档的“作者盲区”比代码更隐蔽：你作为重构者，知道太多“读者不需要知道”的实现细节。建议：
   - **第一层：`shuorenhua` 做语言清理**，去掉 AI 腔和模板感。
   - **第二层：再 spawn 一个完全隔离的子代理**，只给它**清理后的文档 + 一个明确的读者画像**（例如：“你是熟悉 C 和操作系统概念、但没读过 Minix3 源码的开发者”），让它**冷读并标记出**：哪里需要回读、哪里术语未定义、哪里的讲解假设了它不该有的背景。这个子代理不接触你的任何重构笔记或设计讨论。

3. **利用你已经验证过的“费 token”换效果的模式**。冷读的成本本质上是**用独立的上下文重建理解**的代价。对于 Minix3 这种系统级项目，关键 diff 和关键教学章节值得付出这个成本。你可以在流程中把冷读**门禁化**：只有通过了冷读子代理“零 Critical 发现”或“零理解阻塞点”的产物，才进入下一阶段。`fresh-eyes-review` 的证据门禁和 `adversarial-review` 的多轮循环，都可以作为你设计这个门禁的参考。

你之前发现 `grillme-matt` 的 Spec 轴补上了“设计意图质询”的盲区，冷读则是从**信息通路**上系统性地消除作者盲区。两者结合，再加上确定性的可达性工具，你的 review 工作流在“规范、意图、事实、独立性”四个维度上就基本完整了。

### 🎯 为什么“强调rewrite”不够，而`adversarial-rust`能补上

你之前反复强调“要rewrite不要translate”，本质上是在要求模型做一次**意图声明**。但模型很容易在声明层面“过关”：它可以说“我是在rewrite”，同时写出带着C影子的Rust代码，因为**翻译残留往往以“看似合理的架构选择”出现**，而不是以明显的语法错误出现。

`adversarial-rust` 的切入点完全不同：它不问你“是不是在rewrite”，而是**直接命名代码背叛了哪个“异质心智模型”**，然后 prescribe 一次**深度重构来把它折叠回去，甚至可以删除整个层次**。它内置的判据正是从C/Minix3这类代码库翻译过来时最典型的残留形态：

- **单实现的 DI trait**：C里没有trait，翻译时容易为每个“接口”造一个只有一个实现的trait，看起来像抽象，实际上只是函数指针的Rust外衣。
- **`Manager`/`Service`式无状态结构体**：C里的模块被机械地映射成“一个struct + 一堆方法”，而不是让数据和方法真正住在一起。
- **布尔/字符串状态机、哨兵返回值**：C里用`int`或特殊返回值表示状态，翻译过来就变成`bool`字段或`String`模式，而不是用`enum`让非法状态不可表示。
- **`clone`到能编译为止、`Rc<RefCell>`对象图**：所有权模型被当成障碍而不是设计工具，翻译残留的典型症状。

这些恰恰是“设计不够聪明”的具体形态。你可以把 `adversarial-rust` 作为你 review 流程中**专门负责“架构翻译残留”的对抗性子代理**，和你的 `grillme` 设计轴并行，但职责更聚焦：`grillme` 问“这段代码是否还服务于活跃的设计意图”，`adversarial-rust` 问“**这段代码的架构形态本身，是不是从C范式里继承来的**”。

### 🏛️ 正向参照：OS代码的“品味”有可操作的定义

“设计不够聪明”的另一半问题，是你需要一套**正面标准**来替代“聪明”这个模糊感受。Minix3 的 Rust 重构有一个天然优势：已经有一个成熟项目把“Rust OS代码品味”写成了可审查的规则。

**openKylin x-kernel 的 Rust OS 风格指南**直接给出了几条对 Minix3 重构极具针对性的判据：

- **用类型系统编码状态和不变量**：`enum` 替代整数模式开关，`newtype` 替代裸 `usize` 标识符，专用配置/描述符结构体替代长位置参数列表。
- **优先 traits + 组合，而不是继承形状的分层或大的 god object**。
- **优先所有权和借用，而不是共享可变全局状态**；全局状态不可避免时，保持最小、封装、绑定到清晰的子系统边界。
- **让 `unsafe` 小而可控**，把 unsafe 边界放在靠近硬件/寄存器访问点的位置。
- **用 `Option`/`Result` 和显式错误传播替代哨兵值、魔法返回码和静默回退**。
- **用模式匹配和小辅助类型替代深层嵌套条件和布尔参数组合**。

这几乎就是对你“设计不够聪明”问题的正面回答。你可以把这些条目**内嵌到你 review skill 的“设计轴”检查清单**中，让“聪明”变成“类型系统是否承载了不变量”“状态是否被编码为不可表示的非法状态”这类可逐条追问的问题。

**Asterinas 的 persona 化指南**则提供了另一种组织方式：把审查按**角色**拆分——Project maintainer 问“代码是否形状良好且可理解”，Kernel developer 问“是否正确且高效”，Security expert 问“是否安全”，Hardware expert 问“是否符合硬件契约”。对于 Minix3 这种横跨机制与策略的项目，这种 persona 拆分比单一“review清单”更能覆盖不同维度的设计品味。

### 🔧 Review中能重构吗？什么skill能做

**能，但要有安全网。** 纯 review 和“审查中直接重构”是两种模式，你已有的流程更适合**先审查、再基于审查结论执行重构**，而不是让 review 子代理边看边改。

如果你希望 review 阶段就能产出可执行的重构，有两个 skill 是直接可用的：

- **`adversarial-rust`**：它的定位就是 **“review-and-refactor pass”**，不只是给发现，而是**prescribe 深度重构**，包括删除整个层次。你可以让它在冷读子代理中运行，输出“翻译残留清单 + 每一条的深度重构处方”，然后由主代理在验证编译和测试后执行。
- **`rust-refactoring-specialist`**：仓库级重构专家，强调 **behavior-aware、evidence-based**，核心规则是“执行完整、连贯的变更集”，不留半迁移的符号或推测性抽象。它把**public API shape、错误、顺序、副作用、panic 条件、drop 时机、锁作用域、`.await` 边界**都视为可观察行为来保持。这适合你在 review 确认问题后，**用它来安全地执行架构级重构**，而不是让 review 本身变成不可控的大改。

**安全网的最低要求**：Minix3 重构项目必须有可运行的测试基线（至少关键子系统的回归测试），以及 `cargo check` / `cargo clippy` 作为每次重构后的硬门禁。`adversarial-rust` 的处方再“深”，也要在“行为保持”的约束下执行；没有测试基线的深度重构，风险不在“改错”，而在“无法证明没改错”。

### 📚 文档侧还有什么能帮到你

你已有的“冷读 + 说人话”组合在**语言清理和读者盲区消除**上已经比较完整。文档侧还能补的是**教学结构本身**。`Systems Programming Course Builder` 提供的是**系统编程教学内容的结构化框架**，包括为C/Rust/Zig等语言标准化课程 profile，以及设计大学级别系统/OS课程作业的参考。你可以把它作为教学文档的**骨架参照**：哪些概念应该先于代码出现，每个子系统需要多少前置知识，实验/练习如何与重构阶段对齐。它不替代你的冷读，但它能让冷读子代理有一个“**这条讲解在课程结构中的位置是否正确**”的额外判据。

### 💎 调整后的工作流骨架

你现在缺的不是更多 skill，而是**把“意图追问”替换为“架构证据追问”**。一个可行的调整是：

1. **冷读子代理 A（架构对抗）**：加载 `adversarial-rust`，只给 diff + 编译/测试命令，要求它**命名每一个“异质心智模型残留”**，并给出深度重构处方。不给你的重构笔记。
2. **冷读子代理 B（品味门禁）**：加载 `thermo-nuclear-code-quality-review`，做一次极严格的 maintainability/abstraction 审查，重点抓**抽象质量、巨型文件、面条式条件增长**——这是“设计不够聪明”在可维护性层面的下限保障。
3. **正向参照内嵌**：把 x-kernel 的 OS 风格指南和 Asterinas 的 persona 清单作为你**定制 skill 的设计轴检查项**，让每次 review 都对照“类型是否承载不变量”“状态是否可表示非法”“unsafe 边界是否最小”这些具体条目。
4. **重构执行**：只有通过 A 和 B 的发现，再交给 `rust-refactoring-specialist` 在测试门禁下执行；review 阶段本身不直接改代码。

这样，你的流程就从“反复追问是否rewrite”，变成“**用架构判据识别翻译残留，用正向标准定义好设计，用安全网执行深度重构**”。“聪明”不再是期待模型自发产生的品质，而是被**可审查的架构证据**逼出来的结果。

- 「请找出当前 Rust 实现继承了哪些 C 的结构性限制」是一个审查任务。

## 一、先明确你的工作流究竟要优化什么

你的项目有四种不同的质量目标：

| 目标           | 真正要回答的问题                       |
| ------------ | ------------------------------ |
| Minix3 语义忠实性 | 是否正确理解并保留了原系统的语义？              |
| Rust 设计质量    | 是否充分利用 Rust，而不是把 C 的结构换一种语法表达？ |
| 实现质量         | 是否正确、安全、简洁，且符合架构约束？            |
| 教学文档质量       | 读者能否从文档中真正理解机制，而不是只看懂代码表面？     |

这四者有关联，但不能让同一个审查者用同一套检查清单解决。

尤其要区分：

语义忠实不等于结构忠实。

你要保留的是 Minix3 的操作系统语义，而不是它在 C 语言中的数据结构、函数组织和控制流。

因此，Rust 重写有时应该保留行为，却删除原有结构；有时甚至应该重新组织状态表达和模块边界。

这才是你想要的 rewrite。

## 二、我最推荐的工作流：五个独立视角

我会采用下面的结构。这里的关键不是有五个 agent，而是每个 agent 有自己的问题、证据要求和信息边界。

阶段 1 · 语义基准

Minix3 C 语义研究者

输入：Minix3 C 源码、相关数据结构、调用链。

输出：原始机制的行为、状态变化、不变量、失败路径、架构约束。

不负责：决定 Rust 应该长什么样。

阶段 2 · 设计探索

Rust 架构设计者

输入：阶段 1 的语义合同，以及项目的长期架构原则。

输出：至少一个合理的 Rust 设计，有必要时提出多个方案并比较。

核心问题：能否利用类型、所有权、生命周期、状态建模，消除原 C 实现中的复杂性？

阶段 3 · 实现

Rust 实现者

输入：已裁决的设计方案。

输出：代码、测试、验证记录。

核心要求：不得擅自把设计降级成方便编译的 C 式实现。

阶段 4 · 独立对抗

冷读审查者

输入：代码、必要的 C 源码和测试证据；按任务决定是否提供设计合同。

输出：独立发现、反例、失败路径、可简化的结构。

不继承作者的推理过程，不默认原设计正确。

阶段 5 · 教学表达

技术教师与普通读者

输入：已经验证的 C 语义、Rust 实现和测试证据。

输出：教学内容、概念解释、阅读路径、独立读者的理解障碍。

核心要求：能讲清楚原理，而不是替代码写一份说明书。

其中有一个重要变化：

阶段 2 不能由阶段 1 的作者直接跳过。

你过去的流程可能是：

C 源码分析 → Rust 设计 → Rust 实现 → review。

但这中间容易发生一个问题：模型对 C 形成的理解，会直接限制它想象 Rust 设计的方式。

所以我建议把 Rust 设计探索独立出来，专门要求它回答：

1. 原 C 结构中哪些是语义必需的？
2. 哪些只是 C 语言表达能力的限制？
3. 哪些是 Minix3 的历史实现选择，而不是不可改变的操作系统契约？
4. Rust 是否有更合适的表达方式？
5. 能否删除整个状态、包装层、trait 或中间对象，而不是仅仅换一种写法？

这比再强调十遍 `rewrite != translate` 更有价值。

### 4. Asterinas 的真正宝藏：它的 skill 实现方式

## 四、我认为你最需要增加的：设计探索，而不是更严格的 Review

这里有一个重要区别。

我建议你保留两种不同的评审模式：

A. 代码设计 Review

这是开放问题域的设计探索。

允许：

- 重新审视已经实现的代码。
- 推翻此前的设计决定。
- 讨论其他架构方案。
- 删除原有模块、trait 和数据结构。
- 大幅重构，只要更符合操作系统语义和项目原则。

它不应该只审查 diff。

B. 代码实现 Review

这是有明确准入范围的质量审查。

重点是：

- 当前变更是否正确。
- 是否破坏既有合同。
- 是否有安全、并发、资源管理缺陷。
- 是否违反已经确立的设计原则。
- 是否存在本次变更引入的结构性问题。

它必须控制责任边界。相邻的设计改进可以登记为后续事项，但不能无限扩展成当前变更的阻塞条件。

这正好呼应你已经建立的两种评审分类。

为什么我强调这个？

因为你目前最有价值的需求，并不是每次写完代码都找出更多问题，而是有时能够停下来问：

我们是不是从一开始就选错了 Rust 的设计方式？

这种问题需要一场真正的设计评审，而不是把代码 Review 加强到极限。

## 五、如何真正逼出更好的 Rust 设计？

这是我认为整个工作流中最值得投入的一部分。

我建议给 Rust 设计者一个独立的 `Alternative Design Challenge` 任务。

不是让它检查有没有 `unwrap()`，而是要求它拿到 C 的语义之后，独立提出 Rust 方案。

每个重要设计至少比较：

| 比较维度 | 具体问题                        |
| ---- | --------------------------- |
| 语义   | 是否完整保留 Minix3 的操作系统行为？      |
| 类型设计 | 能否让类型承载不变量？                 |
| 所有权  | 是否存在不必要的共享可变状态？             |
| 状态表达 | 是否存在重复、矛盾或非法状态？             |
| 抽象边界 | trait 是否表达 OS 语义，而不是包装硬件机制？ |
| 复杂度  | 是否可以删掉整个层次？                 |
| 可测试性 | 是否能在 host 环境验证核心行为？         |
| 可教学性 | 是否能够清晰地解释为什么这样设计？           |

但我想特别提醒你，不要把这张表变成新的机械规则。

例如：

- 单实现 trait 不一定就是坏设计。
- `bool` 不一定都应该替换成 enum。
- 内核 intrusive list 不一定应该改成普通集合。
- 所有权也不意味着应该强行消除所有共享状态。

关键是判断当前机制是否有必要，以及 Rust 是否能更准确地表达它。

我还会额外要求设计者提供一个最小化方案：假如不考虑兼容当前 Rust 代码，我们能否用更少的概念实现同样的语义？

这就是你真正想要的 code taste。

## 六、冷读工作流需要一个重要修正

我很赞同你采用冷读，但不建议把「完全不给背景」设成固定规则。

真正要隔离的是作者的解释和结论，而不是判断问题所必需的事实。

比如：

| 冷读任务        | 应提供                   | 应隐藏                 |
| ----------- | --------------------- | ------------------- |
| 检查 Rust 正确性 | C 语义合同、相关源码、Rust diff | 作者的推理过程             |
| 独立 Rust 设计  | C 机制、OS 语义、三架构原则      | 现有 Rust 方案及作者倾向     |
| 设计反驳        | 当前设计合同、候选方案、相关事实      | 作者希望得到的结论           |
| 教学文档阅读      | 教学文档、读者背景             | 源码、作者的解释、设计笔记       |
| 技术事实核对      | C 源码、Rust 实现、测试证据     | 不需要隐藏技术依据，但不能预设文档正确 |

这里特别推荐 `fresh-eyes-review` 的实现方式。

它会给审查者一份简短的任务意图，却不传递作者自己的推理、计划和会话消息。审查者还可以读取必要的项目材料。每个发现必须有位置和具体失败场景。

### 文档的冷读应该怎么做？

我会单独设计一个 `reader-reviewer`，甚至不加载你的项目专属 skill。

给它的指令大致是：

Reader persona

你是一名具备 C、Rust 基础，但没有阅读过 Minix3 源码的系统程序员。

你只能根据提供的教学文档理解内容。不要假设作者已经在其他地方解释了概念。

你的任务

1. 找出无法独立理解的术语和概念。
2. 找出讲解中突然出现、但尚未建立的知识。
3. 找出只能看懂代码、却不明白设计动机的段落。
4. 找出前后概念顺序不合理的地方。
5. 尝试复述这一章节的核心机制，暴露理解偏差。

输出

只报告读者障碍、具体位置和产生障碍的原因。不要直接重写整篇文章，也不要因为个人文风偏好提出问题。

之后再让另一个技术事实核对者拿 C 源码和 Rust 实现，检查文档有没有讲错。

这是两个完全不同的工作：

- 冷读者判断能否理解。
- 技术核对者判断理解是否正确。

不要混为一谈。

## 八、我会怎样重新组织你的项目专属 Skills

不建议把所有规则复制进每个子 agent。

我会分成三个层次。

第一层：项目宪法

所有 agent 按需读取

- Minix3 语义优先于 C 结构。
- Rust rewrite，不是语法翻译。
- RISC-V、ARM/AArch64、x86 三架构统一。
- 抽象 OS 语义，不抽象硬件机制。
- trait 必须有明确的语义职责。
- 代码和教学文档都要达到长期维护与出版标准。

第二层：专项能力

独立维护，避免主 skill 膨胀

C Semantic Audit

还原原始机制

Rust Redesign

独立设计挑战

Architecture Review

三架构统一性

Code Quality

结构简化与重构

Reader Review

教学冷读

Technical Fact Check

技术事实核验

第三层：确定性工具

不让自然语言 prompt 冒充工具

- 编译、Clippy、单元测试。
- 多架构交叉编译。
- QEMU / Bochs 集成验证。
- 静态分析和符号使用分析。
- 文档链接、代码引用和示例检查。

这里有一个重要的成本控制策略：

不是每次都启动全部 agent。

| 任务         | 推荐组合                      |
| ---------- | ------------------------- |
| 小型实现修改     | 实现者 + correctness 冷读 + 测试 |

## 九、我的最终建议：先做三个改动

如果是我负责改造你现在的工作流，我不会立刻重写所有 skill。

我会按照这个顺序：

第一优先级：设计探索 skill。

这是当前最大的能力缺口。

它必须能够从 C 语义出发，暂时忘掉现有 Rust 实现，重新提出方案。尤其要检查有没有可以整体删除的抽象、状态和中间层。

第二优先级：借鉴 Asterinas 的审查架构。

把 persona、独立上下文、反证和 benchmark 引入项目专属 review。你已经有 review 轨迹，现在要把它转化为可重复的评测案例。

第三优先级：文档 Reader Agent。

先让它阅读，不要让它改写。只有确定了读者理解障碍，再由技术作者修改。语言润色最后进行。

我认为还有一个原则值得贯穿整个项目：

不要把每一次评审都变成寻找违规项的过程。要让评审者寻找更好的方案。

你要的不是一个越来越擅长说「这里不符合规则」的 AI，而是一个能够提出：

「保留 Minix3 的这个语义，但我们不应该继续采用原来的这种数据结构和控制流。这里有一种更自然、更简单的 Rust 表达方式。」

而且它能够拿出代码、反例和测试证明自己的方案。

这才是 Minix3 Rust 重写项目值得长期投资的 AI 工作流。

我建议下一步拿一个已经完成、但你对设计品味不太满意的实际子系统做试点，先建立一份 `Rust Redesign Challenge` 和最小 Review Evals，而不是动现有主 skill 的全部结构。
