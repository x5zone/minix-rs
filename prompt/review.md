# Minix-RS Review 指南

> 本指南用于对 Minix-RS 项目的**文档**和**代码**进行深度 Review。
> 
> 适用范围：**所有 Minix3 模块**（VM、PM、VFS、Kernel、Drivers 等）
> 
> 参考原始 C 代码：`/home/xzhao/github/minix-rs/minix3/`（这是 ground truth）

---

## 项目背景

本项目是对 Minix3 内核模块的 **语义重建（Rewrite）**，不是翻译，不是重设计。

| 术语 | 定义 |
|---|---|
| **Translate** | 1:1 翻译 C 代码，仅做语法转换，不做语义改变。❌ 禁止 |
| **Rewrite** | 保持外部可观察行为不变，内部用 Rust 类型系统重新表达。✅ 目标 |
| **Redesign** | 改变系统架构、机制或协议。❌ 当前禁止 |

核心原则：**外部语义不变，内部表达可以改变。把"隐式编码"变成"显式协议"。**

### 当前执行模型

当前 VM / PM / VFS 等服务器默认假设：

- **单线程事件循环**：每个服务器是独立的单线程进程
- **无共享内存并发修改**：服务器间通过 IPC 通信，不共享内存
- **无 SMP 并行访问**：不存在多核同时访问同一数据结构的情况

因此以下设计是合理的：
- `Rc` 可替代 `Arc`（无跨线程共享）
- `RefCell` 可替代 `Mutex`（无并发访问）
- `!Send` / `!Sync` 是合理的（数据不跨线程）
- `UnsafeCell` 在单线程前提下是安全的

> ⚠️ 如果未来扩展为多线程，需重构状态管理。

### Allowed Evolution（允许的架构演进）

以下变化被视为**架构演进**，而非 Redesign：

| 演进类型 | Minix3 (C/32位) | minix-rs (Rust/64位) | 说明 |
|---------|----------------|---------------------|------|
| 架构位宽 | x86-32 | x86-64 | 利用 64 位地址空间 |
| 页表层级 | 2级 (PD+PT) | 4级 (PML4+PDPT+PD+PT) | 64位需要更多层级 |
| 页表项大小 | 32位 (u32) | 64位 (u64) | 支持更大物理地址 |
| 状态表达 | `int state` + 宏 | `enum` / `typestate` | 非法状态不可表达 |
| 错误处理 | 返回 `OK` / `errno` | `Result<T, Error>` | 错误码需严格对应 |
| 资源管理 | 手动 `free()` | RAII / `Drop` | 自动释放，避免泄漏 |
| 权限控制 | `bitchunk_t` 数组 | `bitflags` / `enum` | 类型安全 |
| 内存分配 | VM 私有 slab | Rust `alloc` | 利用标准库 |

**判定标准**：只要满足以下四点，即属于 Rewrite 范畴：
1. **外部可观察行为不变**（IPC 接口、返回值、副作用相同）
2. **IPC 协议不变**（消息格式、调用号、权限检查相同）
3. **生命周期语义不变**（创建、使用、释放的顺序相同）
4. **调度/权限/地址空间语义不变**（进程隔离、内存保护相同）

### 行为语义优先原则

Review 的核心目标是：**验证 Rust 实现是否保持了 Minix3 的行为语义**，而不是要求数据结构或代码组织形式与 C 源码一致。

**允许**：
- 数据结构重组（如将相关字段提取为子结构）
- 状态拆分（如将 `int flags` 拆分为多个 `enum`）
- 生命周期显式化（如用 `typestate` 替代状态字段）
- trait 抽象（如用 `trait PageTable` 替代具体实现）

**不允许**：
- 改变外部行为（如改变 `alloc_mem` 的分配策略）
- 改变 IPC 协议（如改变消息格式或调用号）
- 改变生命周期语义（如提前或延迟释放资源）
- 改变错误恢复语义（如改变错误码含义或重试策略）

### 不要过度模拟 C

Rewrite 的目标不是复刻 Minix3 的历史实现细节。如果某个设计仅仅是以下限制的结果，则应优先使用现代 Rust 表达：

- **C 语言限制**（如缺乏泛型、模式匹配、trait）
- **32 位限制**（如固定大小数组、地址空间假设）
- **无类型系统限制**（如裸指针、魔术数字、隐式转换）
- **无 RAII 限制**（如手动内存管理、错误码传递）

**反例**：
```rust
// ❌ 错误：为了对应 C 源码而手写 intrusive linked list
struct ListNode { next: *mut ListNode, ... }

// ✅ 正确：使用 Rust 标准库或安全抽象
struct FreeList { head: Option<Box<Node>> }
```

### Ground Truth 优先级

当以下三者冲突时，优先级为：

```
Minix3 源码行为  >  文档描述  >  Rust 实现  >  AI 分析
```

**永远以 Minix3 源码行为为最终真理来源**。文档写错、AI 分析错误、Rust 实现有 bug 都是可能的，但 Minix3 源码的行为是确定的。

### 3. 常见文档错误模式

#### 模式1：概念混淆
```markdown
❌ 错误：Slab 最大对象大小为 200 字节
✅ 正确：Slab 支持 200 种尺寸（SLABSIZES=200），
        最大对象大小为 207 字节（MAXSIZE = SLABSIZES-1+MINSIZE = 207）
```

#### 模式2：条件编译遗漏
```markdown
❌ 错误：SPAREPAGES = 200
✅ 正确：SPAREPAGES 根据构建配置不同：
        - SANITYCHECKS 构建：200
        - ARM 生产构建：150
        - x86 生产构建：20
```

#### 模式3：行为简化误导
```markdown
❌ 错误：alloc_pages 从高地址向低地址扫描
✅ 正确：alloc_pages 使用循环扫描策略：
        1. 从 lastscan 位置开始向低地址扫描
        2. 如果失败，从 maxpage 重新开始扫描
        3. 更新 lastscan 为本次分配位置
```

#### 模式4：架构差异未说明
```markdown
❌ 错误：pt_t 结构体包含 pt_pt[1024] 数组
✅ 正确：pt_t.pt_pt[1024] 是 Minix3 x86-32 设计。
        minix-rs 使用 x86-64，页表层级更多，采用动态分配策略。
```

#### 模式5：代码与文档不一致
```markdown
❌ 错误：文档描述 `alloc_virt(phys, clicks)` 分配虚拟地址并映射到 phys
✅ 正确：实际代码中 `alloc_virt` 忽略 phys 参数，仅分配虚拟地址槽位，
        不建立映射。应重命名为 `alloc_virt_slot` 以明确语义。
```

## 第二部分：代码 Review

### 1. Rewrite 质量检查

> 这是最核心的维度。发现 Translate 味道必须指出。

- [ ] 是否存在裸整数表达语义（应用 newtype/enum 替代）？
- [ ] 是否存在 C 式空指针/哨兵值（裸 `0`、`-1` 表示"无值"）？应改用 `Option<T>`
- [ ] 是否存在未命名的魔术数字（应抽象为命名常量）？
- [ ] 是否存在 C 式 flag 组合（应用 bitflags/enum/typestate 替代）？
- [ ] 是否存在 C 式错误码传递（应用 Result + ? 替代）？
- [ ] 是否将 C 宏直接翻译成 Rust 宏（应用 trait/泛型替代）？
- [ ] 是否保留了 C 式数据结构而未用 Rust 所有权重构？
- [ ] 是否存在"为了 Rust 而 Rust"的过度设计（偏离 Minix 语义）？
- [ ] 是否做到了"非法状态不可表达"（invalid states unrepresentable）？
- [ ] **错误码是否对齐**：Rust 的 `Result<T, Error>` 中封装的错误码，是否与 Minix3 原始定义的 errno 严格对应？禁止为了"优雅"而合并或创造新的错误语义
- [ ] **内存所有权是否清晰**：C 源码中的内存分配/释放点，在 Rust 中是否有对应的 `Owner`？是否存在 C 中"借用"但在 Rust 中被误用为"所有权"的情况？

### 2. 硬件抽象检查

> 当前阶段严禁实现任何真实硬件代码。

- [ ] 是否出现了具体硬件语义（CR3、TSS、MSR、I/O 端口等）？❌ 必须拒绝
- [ ] 硬件交互是否全部通过 trait 抽象完成？
- [ ] trait 是否描述"OS 需要什么机制"而非"硬件怎么做"？
- [ ] mock 硬件是否实现了所有必需的 trait？
- [ ] trait 定义是否在使用方附近（分散定义）？
- [ ] trait 实现是否集中在 arch crate（集中实现）？
- [ ] trait 设计是否考虑了 x86-64/arm64/RISC-V 64 的共性？

### 3. 类型系统与安全

- [ ] typestate 是否真正约束了状态？是否存在绕过 typestate 的路径？
- [ ] typestate 和 flags 之间是否严格一致？能否构造出"逻辑非法但类型合法"的状态？
- [ ] 是否可能同时持有同一对象的多个 view（aliasing 问题）？
- [ ] `unsafe` 是否最小化？每个 `unsafe` 块是否有明确的安全契约？
- [ ] 是否存在"逻辑正确但在 Rust 内存模型下是 UB"的代码？
- [ ] `MaybeUninit` / `UnsafeCell` / 裸指针使用是否正确且必要？
- [ ] 是否手动实现了 `unsafe Send` / `unsafe Sync`？其安全性是否经过论证？
- [ ] Drop 语义是否清晰？是否存在隐式 drop 风险？

### 4. 执行模型与并发假设

> 当前 VM server 假设单线程执行，但必须显式确认。

- [ ] 模块是否明确声明了单线程假设？

### 5. 内存模型与状态表达

### 6. 公开接口与模块设计

- [ ] `pub` 是否克制？是否遵守最小权限原则？
- [ ] 模块是否高内聚？是否存在职责不清的模块？
- [ ] 是否有逻辑应该拆分出去？
- [ ] 是否有本应 private 却暴露的 API？
- [ ] 模块间依赖是否清晰且合理？

#### 6.1 模块可见性分层原则

> **核心思想**：模块内部可以宽松，但对外必须严格通过 API 访问。

**实现模式**：
```
module/
├── mod.rs          # 不导出内部类型（如 VmProc）
├── internal.rs     # pub(crate) 字段，模块内可访问
└── view.rs         # typestate views，对外公开

external_module.rs  # 只能通过 view.rs 的 API 访问
```

**目的**：将 bug 消灭在设计中，而非代码审计时。

#### 6.2 最小可见性原则

> **核心思想**：每个类型的可见性应该是"必须暴露的最小范围"。

**判断口诀**：
> **"这个 pub 是因为外部需要，还是因为内部懒得组织？"**
> 如果是后者，需要收紧可见性。

> **"这个类型导出后，外部能做什么？如果答案是不应该做的东西，就不该导出。"**

- [ ] 是否存在显而易见的冗余注释？
- [ ] 是否有过多的空行影响紧凑性？
- [ ] `unsafe` 代码是否有 safety 注释？
- [ ] 关键设计决策是否解释了"为什么不用另一种常见方案"？

### 10. 64 位假设

- [ ] 代码是否基于 64 位假设编写？
- [ ] 是否存在不必要的 32 位残留（如 `u32` 用于地址/大小）？
- [ ] 是否存在用 `as` 进行有损截断（如 `u64 as u32`）且无注释说明安全性？
- [ ] 是否利用了 64 位的优势（如更大的地址空间）？

### 11. 复杂度与工程性

> 防止过度设计的刹车系统。

- [ ] 当前设计是否明显复杂于问题本身？
- [ ] 是否存在"理论优雅但工程不必要"的设计？
- [ ] 是否为了类型安全引入过高复杂度？
- [ ] 是否可以用更简单的模型表达相同语义？

## 第三部分：审查优先级矩阵

> 按以下优先级执行 Review。

### P0 - 阻塞性检查（必须修复，阻断合并）

| 维度 | 检查项 | 说明 |
|------|--------|------|
| 文档 | 概念错误、虚构事实 | 与 Minix3 源码不符的论述 |
| 文档 | C 代码引用错误 | 引用的代码不存在或行号错误 |
| 代码 | UB、内存安全漏洞 | 未定义行为、use-after-free、数据竞争 |
| 代码 | 语义偏移 | 外部可观察行为与 Minix3 不一致 |
| 代码 | 硬件语义泄漏 | 出现 CR3/TSS/MSR 等具体硬件代码 |
| 代码 | 错误码不对齐 | Rust 错误码与 Minix3 errno 语义不同 |

### P1 - 设计问题（建议修复，影响质量）

| 维度 | 检查项 | 说明 |
|------|--------|------|
| 文档 | 架构差异未说明 | 32→64位差异未标注 |
| 文档 | 覆盖不完整 | 遗漏核心数据结构或关键函数 |
| 代码 | typestate 无效 | 可以构造"逻辑非法但类型合法"的状态 |
| 代码 | pub 滥用 | 过度暴露内部实现 |
| 代码 | 模块职责不清 | 高内聚低耦合被破坏 |
| 代码 | 所有权混乱 | C 的借用被误用为 Rust 的所有权 |

### P2 - 改善性检查（可选修复，提升体验）

| 维度 | 检查项 | 说明 |
|------|--------|------|
| 文档 | 表述清晰度 | 章节组织、段落衔接 |
| 文档 | 交叉引用完整性 | 缺少前置文档引用 |
| 代码 | 命名规范 | 不符合 Rust 规范或与 Minix3 不一致 |
| 代码 | 注释质量 | 缺少 safety 注释、冗余注释 |
| 代码 | 测试覆盖 | 缺少边界条件或状态转换测试 |

## 第五部分：AI 执行 Review 的强制步骤

> 为防止 AI 在 Review 过程中"浮躁"或遗漏关键验证，必须按以下步骤执行。

### Step 1: Ground Truth Lookup（源码定位）

- 识别文档中提到的所有 Minix3 源文件
- 使用 `rg` 命令验证这些文件是否存在于 `minix3/` 目录
- 记录每个引用的**文件路径**和**行号范围**

### Step 2: Diff Extraction（差异提取）

- 列出 **3 个**你认为文档/代码中最背离 Minix3 原始语义的地方
- 对每个差异，说明：
  - Minix3 源码的实际行为
  - 文档/代码中的描述/实现
  - 差异的性质（概念错误、语义偏移、过度简化等）

### Step 3: Sanity Check（ sanity 检查）

- 验证文档第 2 章引用的**所有行号**是否真实存在于本地文件
- 验证文档中的**所有数值常量**是否与 Minix3 源码一致
- 验证文档中的**所有函数签名**是否与 Minix3 源码一致

### Step 4: Cross-Document Check（跨文档联动）

- 检查本文档涉及的概念/类型/函数是否在其他文档中已有定义
- 如果其他文档已有完整设计和实现，检查本文档是否：
  - 正确引用了那些文档？
  - 与那些文档的描述一致？
  - 没有重复定义或矛盾？
- 特别关注：
  - 共享的数据结构（如 `vmproc`、`vir_region`）
  - 共享的常量/配置（如 `CLICK_SIZE`、`VM_RQ_BASE`）
  - 跨模块调用（如 PM → VM 的 IPC 接口）

### Step 5: Final Review Output（最终输出）

- 按"Review 输出格式"整理所有发现
- 每个问题必须标注优先级（P0/P1/P2）
- 每个问题必须提供明确的修改方向

## 第六部分：Review 快速判断口诀

### 通用口诀

> **"我是在表达 Minix，还是在炫 Rust？"**
> 如果是后者，基本就该砍。

> **"这段 unsafe 是为了解决问题，还是为了逃避问题？"**
> 如果是后者，需要重新设计。

### 文档 Review 口诀

> **"这个概念在 Minix3 源码中有对应吗？"**
> 如果没有，可能是虚构的。

> **"引用的代码我能在源码中找到吗？"**
> 如果不能，引用可能错误。

> **"讲解的内容是否超出了代码实际表达的？"**
> 如果是，可能是过度解读。

> **"32位和64位的差异我说清楚了吗？"**
> 如果没有，读者会困惑。

> **"文档描述的 Rust 代码和真实代码一致吗？"**
> 如果不一致，需要同步。

### 代码 Review 口诀

> **"这个 pub 是因为外部需要，还是因为内部懒得组织？"**

> **"这个类型导出后，外部能做什么？如果答案是不应该做的东西，就不该导出。"**

> **"这段代码是在解决问题，还是在复刻 C 的历史包袱？"**

## 第七部分：跨文档联动检查

> 模块间存在大量共享概念和依赖关系，Review 时必须检查一致性。

### 检查清单

- [ ] **共享数据结构**：本文档使用的结构体（如 `vmproc`、`vir_region`）是否在其他文档中有更权威的定义？本文档的描述是否与之一致？
- [ ] **共享常量/配置**：本文档引用的常量（如 `CLICK_SIZE`、`VM_RQ_BASE`）是否与其他文档一致？是否有重复定义？
- [ ] **跨模块调用**：本文档描述的 IPC 接口（如 PM → VM）是否与其他模块的文档匹配？
- [ ] **前置依赖**：本文档假设读者已了解的概念，是否有对应的文档？是否正确引用？
- [ ] **后置引用**：其他文档是否依赖本文档的内容？本文档的变更是否会破坏那些文档？

### 常见跨文档错误

#### 模式 A：重复定义
```markdown
# 文档 04-physical-memory.md
#define CLICK_SIZE 4096

# 文档 05-vm-allocpage.md  
#define CLICK_SIZE 4096  // ❌ 重复定义，应引用 04 文档
```

#### 模式 B：定义矛盾
```markdown
# 文档 03-acl.md
vm_acl 取值：-1 (NO_ACL), 0 (USER_ACL), 1~31 (系统 ACL)

# 文档 01-vmproc-struct.md
vm_acl 取值：-1, 0, 1~32  // ❌ 与 03 文档矛盾（32 vs 31）
```

#### 模式 C：遗漏引用
```markdown
# 文档 05-vm-allocpage.md
vm_allocpage 使用 pt_init_done 标志...

# 缺少引用：pt_init_done 在 07-pagetable-ops.md 中详细定义
# 应添加：参见 [07-pagetable-ops.md](07-pagetable-ops.md)
```

### 验证方法

```bash
# 1. 检查常量是否多处定义
rg "CLICK_SIZE\s*=" notes/rewrite/ --type md -n

# 2. 检查结构体是否多处描述
rg "struct vmproc" notes/rewrite/ --type md -n

# 3. 检查 IPC 调用号是否一致
rg "VM_RQ_BASE" notes/rewrite/ --type md -n

# 4. 检查文档间交叉引用
rg "\[.*\]\(.*\.md\)" notes/rewrite/ --type md -n
```
