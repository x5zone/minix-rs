# 文档 Review 检查清单

> 本文档定义对 Minix-RS 项目文档进行 Review 时的检查维度。
> 适用：所有技术文档（`.md` 文件）

---

## 1. 文档结构规范

每篇文档应遵循以下**灵活结构**：

```
# XX-title: 标题

> **分类**: 模块库 / 模块私有 / 全局基建
> **源码**: `minix3/minix/servers/模块/xxx.c`
> **说明**: 一句话功能描述
> **状态**: 可选，标注 Rust 实现状态

---

## 1. 概述
### 1.1 概念定义/作用
### 1.2 与 Minix3 的对应关系
### 1.3 关键状态/机制说明
### 1.4 行为规则

## 2. C 源码分析
### 2.1 相关定义（常量、调用号、配置等）
### 2.2 核心数据结构
### 2.3 关键函数分析
### 2.4 调用关系/调用点分析
### 2.5 设计要点/特殊处理

## 3. Rust 设计决策
> 高层设计选择，解释"为什么这样设计"

## 4. 实现详解
> Rust 实现的具体展开，解释"如何实现"

## 5. 专题分析（如适用）
> 根据文档主题灵活安排

## N. 测试要点  （倒数第二章）
> 需要测试什么，而非罗列测试代码

## N+1. 参见  （最后一章）
- [相关文档1](xxx.md)

## 附录（可选）
```

**关键约束**：
- **第1章（概述）和第2章（C 源码分析）不得包含 Rust 相关内容**
- **第3章（设计决策）** 聚焦"为什么这样设计"，每个决策必须可追溯到 Ch1&2
- **第4章（实现详解）** 聚焦"怎么做"，每个实现必须对应 Ch3 的设计决策
- **倒数第二章（测试要点）** 必须基于 Ch3 的设计决策和 Ch4 的实现细节推导
- **最后一章是参见**
- **C 源码分析应完整覆盖**：所有核心数据结构、所有关键函数、调用关系
- **Ch3 如有更好的替代方案，应以 TODO 段落记录**

## 2. 文档 Review 维度

### 2.1 概念准确性检查

> **核心原则**：禁止虚构、禁止幻觉、必须以 Minix3 源码为唯一真理来源

- [ ] 每个核心概念是否有明确的 Minix3 源码对应？
- [ ] 概念解释是否与源码实现一致，而非作者臆测？
- [ ] 是否存在"听起来合理但源码中没有"的论述？
- [ ] 术语使用是否与 Minix3 源码保持一致（如 click vs page）？
- [ ] 所有数值常量（数组大小、阈值、魔数等）是否与源码一致？
- [ ] 是否存在条件编译（`#if SANITYCHECKS` 等）导致的多个可能值？
- [ ] 算法描述（扫描方向、分配策略等）是否与源码一致？

**验证方法**：
```bash
rg "TERM" minix3/minix/servers/{module}/ --type c
rg "TERM" minix3/minix/kernel/ --type c
rg "TERM" minix3/minix/include/ --type h
```

### 2.2 C 代码引用验证

> **核心原则**：引用的代码必须正确，代码的讲解必须准确

- [ ] 每个代码引用是否标注了准确的文件路径和行号？
- [ ] 引用的代码在 Minix3 源码中是否真实存在？
- [ ] 行号是否精确（允许小幅偏移，但函数定义位置必须准确）？
- [ ] 引用的代码片段是否完整（包含关键上下文）？
- [ ] 是否存在截断导致的语义改变？
- [ ] 讲解是否与引用的代码一致？
- [ ] 是否存在"过度解读"（讲解内容超出代码实际表达）？
- [ ] **路径是否以项目根为基准**？禁止使用 `file:///home/user/...` 等绝对路径

### 2.3 数据结构覆盖完整性

- [ ] 模块的所有核心数据结构是否都被分析？
- [ ] 结构体的每个字段是否有解释？
- [ ] 字段间的关联关系是否被说明？

### 2.4 文档与代码一致性

- [ ] 文档中的 Rust 函数签名是否与真实代码一致？
- [ ] 参数类型、返回值类型是否匹配？
- [ ] 文档描述的行为是否与代码实现一致？
- [ ] 文档中的示例代码是否可编译？

### 2.5 架构演进说明

- [ ] 文档描述的架构（如 x86-32 两级页表）是否与 Rust 实现（x86-64 四级页表）一致？
- [ ] 如果不一致，是否明确标注了差异？
- [ ] 是否解释了演进的理由？

**必须标注的差异**：

| 方面 | Minix3 (32位) | minix-rs (64位) | 说明 |
|------|---------------|-----------------|------|
| 页表层级 | 2级 (PD+PT) | 4级 (PML4+PDPT+PD+PT) | 64位需要更多层级 |
| 页表项大小 | 32位 (u32) | 64位 (u64) | 支持更大物理地址 |
| 地址划分 | 10+10+12 | 9+9+9+9+12 | 64位地址空间 |
| 页表指针数组 | pt_pt[1024] | 动态分配 | 64位无法预分配 |

### 2.6 文档间交叉引用

- [ ] 文档是否引用了所有相关的前置知识文档？
- [ ] "参见"章节是否完整？
- [ ] 引用的文档路径是否正确？

### 2.7 图表与可视化质量

> ASCII 图滥用或粗制滥造会严重降低文档质量。

- [ ] **必要性**：这个图是否传达了纯文字无法高效表达的信息？
- [ ] **对齐精度**：ASCII 图的边框、箭头、文字是否严格对齐？
- [ ] **可维护性**：ASCII 图是否过于复杂，导致后续修改困难？
- [ ] **信息密度**：图是否承载了足够的信息量？
- [ ] **替代方案**：是否可以用更简单的列表、表格或文字描述替代？

**判定标准**：
- 能用文字说清楚的，不要用图
- 图必须严格对齐（右边界、箭头、连接线）
- 图必须承载足够的信息量，不能为了"有图"而画图
- 复杂图应拆分为多个简单图

### 2.8 C 源码覆盖完整性检查

> **目的**：该文档**语义范围**内引用的 C 源码（函数 + 数据结构 + 宏），必须被完整覆盖。

**核心原则**：文档想讲解什么概念，就应该完整覆盖相关的 C 源码实现。漏掉函数/结构体/宏 = 实现缺功能或缺类型。

**检查方法**：
```bash
# 1. 列出模块的所有 C 源码文件
ls minix3/minix/servers/{module}/*.c

# 2. 列出所有函数定义
rg "^void \w+\(" minix3/minix/servers/{module}/ --type c -n
rg "^int \w+\(" minix3/minix/servers/{module}/ --type c -n
rg "^static int \w+\(" minix3/minix/servers/{module}/ --type c -n

# 3. 列出所有结构体定义
rg "^struct \w+" minix3/minix/servers/{module}/ --type c -n
rg "^typedef struct" minix3/minix/servers/{module}/ --type c -n

# 4. 列出所有宏定义
rg "^#define \w+" minix3/minix/servers/{module}/ --type c -n

# 5. 对照文档，检查是否所有核心函数、结构体、宏都有章节分析
```

**关于宏的说明**：
- **常量宏**（如 `#define PAGE_SIZE 4096`）：在"常量定义"小节覆盖即可
- **行为宏**（如 `#define IS_LOWMEM(v) ((v) < KERNEL_LOAD_BASE)`）：承载判断逻辑，需要分析
- **标志位宏**（如 `#define VM_PTE_PRESENT 0x001`）：定义页表项标志位，需要分析
- **条件编译宏**（如 `#if SANITYCHECKS`）：影响代码路径，需要说明

**判定标准**：
- 该文档**语义范围**内的所有核心函数，是否都有独立的分析小节？
- 该文档**语义范围**内的所有核心数据结构，是否都有完整分析？
- 该文档**语义范围**内的所有**行为宏/标志位宏**，是否都有分析说明？
- 是否有函数、结构体或宏被遗漏或错误归类到其他文档？

**示例问题**：
- `vm_mappages` 是页表映射操作，语义上属于 `07-pagetable-ops.md`
- `pt_t` 是页表核心结构体，语义上属于 `06-pagetable-struct.md`
- `ARCH_VM_PTE_PRESENT` 是页表项标志位宏，语义上属于 `06-pagetable-struct.md` 或 `07-pagetable-ops.md`

### 2.9 设计决策质量检查（Ch3 专项）

> **核心原则**：设计决策必须合理、完整、可追溯。Review 不能只检查"文档写得对不对"，还必须检查"设计好不好"。

- [ ] **合理性**：每个设计决策是否有充分的理由？是否考虑了替代方案？
- [ ] **完整性**：设计是否覆盖了 Ch2 中分析的所有场景（正常路径、边界条件、错误处理）？
- [ ] **缺陷检查**：设计是否存在遗漏？例如：
  - 错误处理路径是否完整？
  - 并发/重入场景是否考虑（即使当前单线程）？
  - 资源泄漏路径是否分析？
  - 初始化/清理顺序是否正确？
- [ ] **替代方案**：是否存在更好的设计？如果有，是否以 TODO 段落记录？
- [ ] **no_std 兼容**：设计是否在 `no_std` 环境下可行？是否依赖了 `std` 的功能？
- [ ] **可追溯性**：每个设计决策是否能追溯到 Ch1&2 的具体分析？

**判定标准**：
- 如果设计决策没有理由 → P1（缺乏依据）
- 如果设计遗漏了 Ch2 分析的场景 → P0（语义偏移风险）
- 如果有更好的替代方案但未记录 → P1（应写 TODO）
- 如果设计依赖 `std` → P0（不可实现）

**验证方法**：
```bash
# 1. 提取 Ch3 的所有设计决策关键词
rg "^###|^####" {doc_file} | grep "3\."

# 2. 对每个设计决策，在 Ch1&2 中搜索依据
rg "KEYWORD" {doc_file} | head -20

# 3. 检查 Ch2 中分析的错误路径，Ch3 是否都有对应设计
rg "error|fail|EPERM|EINVAL|ENOMEM" {doc_file} -i
```

### 2.10 章节链路验证

> **核心原则**：文档各章节之间必须形成完整的推导链路。链路断裂 = 设计或实现有问题。
> 链路验证的原则定义见 [review.md §文档链路模型](review.md)，执行步骤见 [review-process.md §Step 2.5](review-process.md)。本节定义具体的检查项（维度层）。

- [ ] **Ch3→Ch1&2 追溯**：Ch3 的每个设计决策是否在 Ch1 或 Ch2 中有依据？
  - 如果 Ch3 引入了 Ch1&2 未提及的概念 → P1（设计缺乏依据）
- [ ] **Ch4→Ch3 追溯**：Ch4 的每个实现细节是否对应 Ch3 的某个设计决策？
  - 如果 Ch4 实现了 Ch3 未设计的功能 → P1（实现超出设计）
  - 如果 Ch3 设计了但 Ch4 未实现 → P1（设计悬空，应标注 TODO）
- [ ] **测试→Ch3+Ch4 追溯**：倒数第二章的测试要点是否覆盖了：
  - Ch3 的每个关键设计决策？
  - Ch4 的每个关键实现细节？
  - Ch2 中分析的错误路径和边界条件？
- [ ] **代码→Ch4 一致性**：Rust 代码是否与 Ch4 描述的实现一致？
  - 函数签名是否匹配？
  - 类型定义是否匹配？
  - 行为语义是否匹配？

**验证方法**：
1. 列出 Ch3 的所有设计决策，逐一检查 Ch1&2 是否有对应分析
2. 列出 Ch4 的所有实现描述，逐一检查 Ch3 是否有对应设计
3. 列出测试章节的所有测试要点，逐一检查 Ch3/Ch4 是否有对应内容
4. 对照 Rust 代码，检查 Ch4 描述是否与实际代码一致

**链路断裂示例**：
```markdown
❌ Ch3 说"使用 typestate 模式管理 ACL 状态"
   但 Ch1&2 从未分析 ACL 的状态转换 → 设计缺乏依据

❌ Ch4 代码中用 int flags 实现 ACL
   但 Ch3 设计了 typestate → 实现与设计不一致

❌ 测试章节只测了"权限检查是否正确"
   但 Ch3 设计了 NO_ACL→USER_ACL 的状态转换 → 测试未覆盖设计决策
```

## 3. 可读性与表达质量

> **核心原则**：技术准确但读起来痛苦的文档，价值会大打折扣。文档是给人读的。

### 3.1 文本流畅性

- [ ] 是否存在语病、错句、歧义句？
- [ ] 长句是否过多（超过 40 字）？是否可拆分？
- [ ] 代词指代是否清晰（"它""这""上述"是否明确）？
- [ ] 被动语态是否滥用？技术文档优先主动语态
- [ ] 同一概念是否使用一致的术语（不混用"页目录/PD/页表根"等）？
- [ ] 标点使用是否规范？中英文标点是否混用？

### 3.2 逻辑组织与信息流动

- [ ] 段落之间是否有明确的逻辑衔接？（因果、递进、对比、转折）
- [ ] 是否存在"跳跃"——读者需要自行脑补中间步骤？
- [ ] 复杂概念是否遵循"先总后分"或"先简单后复杂"的顺序？
- [ ] 代码讲解是否遵循"先展示全貌，再逐行解释"或"先提出问题，再展示解决"？
- [ ] 是否存在信息密度不均——某段落过于密集，某段落过于空洞？
- [ ] 章节标题是否准确概括内容？是否存在"标题党"？

### 3.3 冗余控制

- [ ] **单文档内**：同一概念是否在多个地方重复讲解？重复是否必要？
- [ ] **跨文档间**：概念 A 在文档 X 中已详细讲解，文档 Y 中是否只需简介+引用？
- [ ] 是否存在"为了完整性而复制粘贴"的大段重复？
- [ ] 代码注释和文档文字是否说同一件事？（优先保留一处详细，另一处引用）
- [ ] 是否可以用"详见 [xxx.md](xxx.md)"替代大段展开？

**判定标准**：
- 同一概念在同一文档中重复超过 2 次 → 检查是否必要
- 跨文档重复超过 3 行 → 应改为简介+引用
- 代码块和对应文字讲解说同一件事 → 保留文字，代码加简要注释即可

### 3.4 读者体验

- [ ] 新概念引入时是否给出了足够的上下文？
- [ ] 专业术语首次出现时是否给出了定义或解释？
- [ ] 是否假设了读者已知的知识？这些假设是否合理？
- [ ] 复杂流程是否有"先给结论，再给细节"的引导？
- [ ] 长文档是否有目录或锚点，方便跳转到特定章节？
- [ ] 关键结论是否有视觉突出（加粗、引用块、表格）？
- [ ] 代码块和文字的比例是否合理？（纯代码无讲解 = 不好；纯文字无代码 = 也不好）
- [ ] 抽象概念是否有具体示例或类比辅助理解？
- [ ] 类比是否恰当？不会引入新的误解？

**判定标准**：
- 一个新概念首次出现，3 行内没有解释 → P2（应补充定义）
- 一个复杂流程没有" TL;DR "或"结论先行" → P2（建议加引导）
- 连续 20 行纯文字无代码/表格/列表 → P2（建议拆分或加可视化）
- 连续 30 行纯代码无讲解 → P2（建议加文字说明）

### 3.5 P2 可读性检查的执行策略

> **背景**：§3.1~3.4 的检查项数量多且判定主观，AI 容易全部跳过或过度执行。以下策略确保 P2 检查有实际产出。

**执行规则**：
1. **先粗筛，再精查**：先快速浏览文档全文，凭第一印象判断是否有明显的可读性问题（约 30 秒）。如果感觉良好，标注「可读性无明显问题」并跳过逐项检查
2. **抽样检查**：如果感觉有问题，抽样 3 处（首段、中段、尾段），逐项检查 §3.1~3.4
3. **聚焦高频问题**：P2 检查的重点是以下 3 类最常见且最影响阅读的问题：
   - **术语不一致**（同一个东西换 3 个名字）
   - **信息跳跃**（读者需要自行脑补中间步骤）
   - **纯代码无讲解**（代码块超过 30 行无文字说明）
4. **P2 输出极简化**：仅输出实际发现的问题，不要求逐项输出「通过/不通过」
5. **批量处理**：如果文档超过 500 行，按章节切分，每章只抽样 1~2 段检查

**输出格式**（P2 部分）：
```
### 可读性检查（P2）
- 术语使用：✅ 一致 / ⚠️ 发现 X 处不一致（列出）
- 逻辑组织：✅ 通顺 / ⚠️ 发现 X 处跳跃（列出）
- 冗余：✅ 无冗余 / ⚠️ 发现 X 处重复（列出）
- 读者体验：✅ 良好 / ⚠️ 发现 X 个问题（列出）
```
