## 0. 本案例的核心发现：Ch1 "主语错了"

在进入具体改进之前，先提炼本案例的一个**最根本性判断**——这个判断在 review-rules 中应当上升为 **Ch1 强制骨架检查**。

**原始 Ch1 的主语错了**：

| 原始文档的叙述主语 | 重构后的叙述主语 |
|---|---|
| `prot_init()` 做了什么 | CPU 需要回答哪些问题 |
| Minix3 怎么实现保护结构 | 保护结构是什么、为什么需要 |
| GDT / IDT / TSS 分别是什么 | 特权级 → 异常向量 → 内核栈 三问框架 |

这个"主语错了"不是个别措辞问题，而是**整章逻辑方向错了**——文档从"实现函数出发往上总结概念"，而正确的教学文档应该是"从读者需要理解的概念出发，再往下落到实现"。

**更严重的问题是**：现有 review-rules 的 checklist（`review-doc-checklist.md`）和 patterns（`review-patterns.md`）对这个问题的检测不够锐利。
- `review-doc-checklist.md §3.5 教学性` 存在，但它是"软判断"，reviewer 可以说"教学性尚可"就打勾。
- 没有**结构化的强制检查**——例如"Ch1 能否在不出现任何函数名的前提下完成对核心概念的解释"。

结果就是：**类似 `03-kmain-cstart-bak.md` 的文档在 review 中可能得到"通过"或"轻度改进"，但实际上它的 Ch1 从根本上不适合作为读者入门材料**。

**改进的核心理念**：把"主语对了吗"这个判断从"reviewer 自由裁量"提升为"可检查的结构化标准"。

## 1. Ch1 强制骨架（新增检查项）

**适用文件**：`review-doc-checklist.md §1 结构规范` + `review-doc-excellence.md §4.1 叙事结构`

**问题**：现有 `§1 结构规范` 对 Ch1 的要求只有"1/2章不得含Rust"和"章节顺序合理"，没有对"Ch1 应该讲什么、怎么讲"的结构性约束。

本案例表明——没有约束的 Ch1 很容易退化为"源码导读式 Ch1"（函数名堆、实现细节前置、概念地基薄弱）。

**提案：在 `review-doc-checklist.md` 中新增一组 Ch1 强制骨架检查**，reviewer 必须逐项确认：

| # | 检查项 | 通过标准 | 本案例对应 |
|---|---|---|---|
| 1.1 | **Ch1 是否有"本章不讲什么"框** | 在 Ch1 引言位置明确列出本章节不覆盖的内容（由后续章节覆盖的具体项），避免读者偏离主线。**建议定位**：Ch1 开头，紧接"本章目标"之后。 | 03-todo §2.67，03-kmain-cstart §1.0 有此框，bak 版没有 |
| 1.2 | **Ch1 核心概念能否在不出现任何函数名/结构体名/trait 名的前提下完整解释** | 把 Ch1 正文（不含引用/示例代码块）中的所有函数名/结构体名/trait 名全部用 `[XXX]` 替换后，读者是否仍能理解核心概念的"是什么+为什么+怎么用"。**测试方法**：在脑中完成一次"裸概念"复述——能复述 = 通过。 | bak 版 Ch1 大量出现 `prot_init()` / `ProtectionArch` / `TSS`，移除后就几乎什么也不剩；重构后 Ch1 概念层与实现层已解耦 |
| 1.3 | **Ch1 开头是否有一个"读者心智模型"的统一框架** | 读者读完 Ch1 前 20%（即引言 + 第一个核心概念小节）后，应当能用"三问"或类似形式清晰回答：这个模块解决什么问题？对操作系统状态机的哪几个运行时问题给出答案？不是一个名词列表，而是一个**状态机/问题清单**。 | 重构版的"CPU 视角三问"就是这样的框架；bak 版是名词列表 |
| 1.4 | **Ch1 是否遵循 WHY → WHAT → HOW 的叙事顺序** | WHY（为什么需要这个机制）→ WHAT（这个机制的定义/状态机）→ HOW（该机制如何落地/被其他子系统调用）。**反向标志**（P1 级警示）：Ch1 第一节就是函数签名/位域表格，或先讲实现后补动机。 | bak 版 WHY 薄弱；重构版 §1.1 就是"什么是保护——为什么要保护" |
| 1.5 | **Ch1 是否有统一的"统一抽象层"表述，区别于"架构具体实现"** | 对多架构文档，Ch1 应当先用一段"统一的 x86/aarch64/riscv64 抽象"讲清共性（如"异常→更高特权→可信栈→handler→返回"），再在后续小节展开具体架构的差异。**反向标志**：Ch1 就把 GDT/TTBR0/stvec 混在一起堆给读者。 | bak 版"GDT 权重过高"是典型；重构版三问框架在架构无关层建立 |
| 1.6 | **Ch1 是否有"返回路径/闭环"** | 对任何"进入"类主题（陷入内核、IPC 请求、中断进入、系统调用），Ch1 必须同时覆盖"进入"和"返回/恢复"两个方向，至少以表格或流程图形式点到返回指令、恢复顺序。**反向标志**（P1）：只画了单向箭头 `用户 → 内核` 就结束。 | bak 版缺返回路径；重构版 §1.3 有返回指令对照表 |
| 1.7 | **Ch1 是否有一张流程图（ASCII art 即可）表达核心机制** | 至少一张流程/关系图（非列表、非表格）用于建立"先发生什么、后发生什么、谁依赖谁"的心智模型。**最低标准**：ASCII art。"我们用文字描述清楚了"不算通过。 | 重构版 §1.3 有统一流程图；§1.4a 有"特权级→页表权限→异常"三层关系图 |
| 1.8 | **Ch1 中是否区分了"核心知识"与"实现细节/历史包袱"** | 对每个被引入的架构特有机制（如 x86 GDT、特定 ARM 寄存器），文档必须明确标注它是"核心知识"（三问直接答案）还是"实现细节/历史包袱"。**反向标志**（P2）：Ch1 就出现位域表格（如 GDT 描述符位格式）。 | bak 版 GDT 位格式出现在 Ch1；重构版 GDT 是"x86 为什么还保留 GDT"的补充小节 |
| 1.9 | **Ch1 是否有本章小结** | Ch1 末尾用一个小节（简短，约 1~2 个段落）复盘核心框架，并预告 Ch2/Ch3/Ch4/Ch5 将分别展开实现层/抽象层/代码层/测试层。 | bak 版缺小结；重构版 §1.10 有小结 |

**以上 9 项应加入 `review-doc-checklist.md §1` 或作为独立的 `§1.Ch1 Ch1 骨架检查`**，与"1/2章不得含Rust"平级或更高（因为"含 Rust"只是泄漏症状，Ch1 主语错了才是病根）。

## 2. 元注释泄漏检测（新增 Pattern）

**适用文件**：`review-patterns.md` 文档模式组（文档 15 模式的新增候选）

**案例来源**：03-todo §5.1 "元注释清理"——文档正文中出现诸如"本节只回答…避免重复"、"概念点到，细节延后 ch13"、"引出 §1.3"这类作者自言自语的写作策略，泄漏到了正文。

**问题本质**：元注释本身有价值（它暴露了作者的写作策略，能帮读者理解结构），但它的正确位置在**作者的写作笔记/todo** 中，不在正文。正文的读者是"第一次读这份文档的人"，他们不应看到作者在"说自己在做什么"。

**提案：在 `review-patterns.md` 中新增一条文档模式**——

> **模式 D-NEW-1（文档模式 16）：元注释泄漏进正文**
> - **特征**：正文出现作者对写作策略的自述，包括但不限于：
>   - "本节只回答…避免重复" / "本小节聚焦…"
>   - "引出 §X.X" / "详见后续章节"（不含正常的"详见 §X.X 的 YYY 小节"这种引用型句子）
>   - "概念点到，细节延后" / "点到为止" / "简化模型"
>   - "下面换一个角度看" / "让我们换一个方式" 这类纯叙述策略过渡
> - **判定**：把这句话从正文中删除后，如果正文仍然完整、流畅、不自相矛盾 → 这句话就是元注释。
> - **严重性**：P2（少量出现）；若整段/整节都是作者写作策略自述 → P1。
> - **修复建议**：隐藏为作者私注；或改写为真正面向读者的叙述（直接讲概念，不告诉读者"我正要讲概念"）。

**为什么这个模式值得加入**：在 03-todo 中有专门一小节（§5.1）处理这个问题，说明它在 Minix-RS 的文档中不是孤例——当作者长期写技术文档，很容易把"对读者说"和"对自己说"混在一起。一个 review 系统如果没有显式把它列为错误模式，reviewer 大概率会漏检。

## 3. CPU 视角三问框架的可泛化性（新增 Excellence 检查）

**适用文件**：`review-doc-excellence.md §4.3 教学深度`

**案例来源**：03-kmain-cstart 的"CPU 视角三问"（当前什么特权级？异常/syscall 跳哪？用哪个栈？）在本章节是极其有效的教学骨架，但它不是"保护结构专属"——它可以被泛化到很多模块：

| 模块 | "执行者视角三问"的泛化 |
|---|---|
| 03-kmain-cstart（保护结构） | CPU 运行时视角三问：当前特权级 / 跳哪 / 用哪个栈 |
| 04-clock-interrupt | 时钟中断处理视角三问：什么源触发 / 跳到哪个 handler / 处理完后返回到什么状态 |
| 05-process-table | 调度器视角三问：下一个选谁 / 切栈怎么切 / 返回时恢复什么 |
| 06-vm | 缺页处理视角三问：谁触发 / 查什么页表 / 填什么页框 |
| 12-syscall | 系统调用视角三问：用户请求编号 / 路由到哪个内核 handler / 返回值怎么传递 |
| 13-exception-interrupt | 异常视角三问：什么向量号 / 嵌套栈用 IST 还是当前栈 / eret 时恢复什么 |

共同点：**从"某个运行时实体的视角"出发，提出 2~4 个核心运行时问题，整章就是在回答这几个问题**。

**提案：在 `review-doc-excellence.md §4.3 教学深度` 中新增一项卓越性判定**——

> **判定 4.3.6（新增）：统一框架是否具备可泛化的"运行时视角三问"**
>
> - 如果该模块文档的 Ch1 有一个统一框架（如"CPU 视角三问"），检查：
>   1. 这个框架是从"一个运行时实体（CPU、调度器、IPC handler、缺页处理程序…）的运行时问题"出发的吗？还是从"函数列表/trait 列表"出发的？
>   2. 这个框架能否被同模块的后续章节（Ch2 C 分析 → Ch3 Rust 抽象 → Ch4 实现 → Ch5 测试）反复引用、形成闭环？
>   3. 这个框架能否让读者读完后"闭上眼睛能复述出整个状态机"？
> - **卓越性评分影响**：满足以上 3 点 → 4.3 项从"良好"升级为"优秀"。
> - **典型反模式**（会直接扣分）：Ch1 的"框架"是一个名词列表（GDT、IDT、TSS、trapframe…）而不是一组问题。

**为什么这条值得加入**：整个 review-doc-excellence 目前强调的是"章节之间链路的完整性"（Ch1→Ch2→Ch3 引用是否到位），但对"Ch1 本身内部用什么结构建立心智模型"缺乏正向引导。03 案例表明——一旦有"运行时视角三问"这种结构，整章的教学深度会显著上一个台阶。

## 4. 架构特有机制权重管理（新增 Pattern + Checklist 项）

**适用文件**：`review-patterns.md`（新增跨文档/跨章节模式）+ `review-doc-checklist.md §2.11 架构演进`

**案例来源**：03 案例中"GDT 权重过高"被反复提到（comments.md 多处、03-todo §1 决策点第 3 项、03-kmain-cstart §1.7 改写为"x86 为什么还保留 GDT"）。

**问题本质**：文档作者往往会"按照自己写代码时接触到的顺序"来组织内容——写 x86 保护模式时第一个碰到的就是 GDT，于是 GDT 自然成为文档的"第一个主角"。但从读者视角看，GDT 是 x86 的历史包袱，ARM/RISC-V 根本不需要这个概念。如果把 GDT 放在 Ch1 主线，读者会误以为"理解 GDT 是理解保护结构的前提"。

**提案：新增两条规则**——

### 4.a Pattern（`review-patterns.md` 文档模式新增）

> **模式 D-NEW-2：架构特有机制喧宾夺主**
> - **特征**：文档 Ch1 的主线叙述中，某个架构（通常是作者最熟悉的那个架构，一般是 x86）的特有机制（如 GDT、特定 MSR、特定 CSR 位）被作为"核心知识"展示给所有读者，而实际上它只是该架构的实现载体/历史包袱，对其他架构不存在。
> - **判定方法**（结构化，非主观）：
>   1. 列出 Ch1 中出现的所有"非通用术语"（即：在至少一个目标架构上不存在对应物的术语）。
>   2. 对每个术语，判断：如果把这个术语从 Ch1 主线移除（降级到"××× 为什么还保留它"的补充小节），Ch1 的核心概念是否仍完整？
>   3. 如果移除后 Ch1 核心概念仍然完整 → 该术语就属于"喧宾夺主的架构特有机制"。
> - **严重性**：P2。如果该术语占据了 Ch1 15% 以上篇幅或被作为首个核心概念引入 → P1。
> - **修复建议**：降级为"××× 为什么还保留 XXX"的补充小节；或移入 Ch2 C 代码分析。

### 4.b Checklist 项（`review-doc-checklist.md §2.11 架构演进` 新增）

> **2.11.6（新增）：架构特有机制权重检查**
> - 对每个在 Ch1 主线出现的架构特有术语（见 4.a 的判定方法），确认它是否真的属于"读者理解该模块的核心机制所必须"。
> - 对被判定为"实现细节/历史包袱"的术语，确认它在文档中被明确标注为"仅对 x86 有意义"或"ARM/RISC-V 无此机制"。
> - **反向标志**：某个架构特有术语在 Ch1 首次出现时，没有一句话说明"它在其他架构上的对应物是什么/不存在"。

## 5. 跨章节链路闭环：三问 → C 分析 → trait 抽象 → 实现 → 测试（新增 Process 步骤）

**适用文件**：`review-process.md`（Step 3/4 之间的跨章节检查）+ `review-doc-checklist.md §2.10 链路验证`

**案例来源**：03-todo §1 决策点第 9 项（Ch3 trait 映射表："CPU 问题 → trait → 架构实现"三层闭环）、§4.1/4.2/4.3/4.4/4.5 都提到的"Ch1 三问 → Ch2 C 分析 → Ch3 trait → Ch4 实现 → Ch5 测试"的纵向对齐要求。

**问题本质**：现有 `§2.10 链路验证` 关注的是"横向链接"——"文中引用的 §X.X 是否存在？引用的外部文件是否在磁盘上可找到？"——这是**存在性检查**。但是一个更关键的"纵向链路"——"Ch1 的概念在 Ch2/3/4/5 是否真的被落地成对应的实现、并被测试验证"——缺乏结构化检查。

03 案例表明：缺乏这个检查时，可能出现"Ch1 讲得很精彩，Ch3 trait 抽象设计合理，但两者之间没有明确的映射关系，读者无法把概念和代码对上"。

**提案**：在 `review-process.md` 的 Step 3（Diff 抽取/Sanity Check）之后、Step 4（Precision Check）之前，**新增一个 Step 3.5 "纵向链路检查"**，对每篇文档强制检查：

> **Step 3.5 纵向链路检查（新增）**
>
> 对目标文档，确认以下 5 层映射关系至少存在**显式的一段文字或一张表格**（不在 review 时临时推断，而是文档正文中已有此映射说明）：
>
> 1. **Ch1（概念） → Ch2（C 源码分析）**：Ch1 提出的核心问题/框架（如"CPU 三问"）在 Ch2 中是否有对应函数/数据结构的定位说明？（如"Ch1 的'内核栈'对应 Ch2 的 `tss_init()`"）
> 2. **Ch2（C 源码分析） → Ch3（Rust trait 抽象）**：Ch2 分析的每个 C 函数/结构体在 Ch3 是否有对应的 trait/struct 抽象？反之，Ch3 引入的每个 trait 在 Ch2 是否有对应的动机分析？
> 3. **Ch3（Rust trait 抽象） → Ch4（Rust 实现详解）**：Ch3 的每个 trait 在 Ch4 是否展开了具体实现（至少一个架构的实现）？
> 4. **Ch1（概念） → Ch4（Rust 实现）**：Ch1 的核心问题（如三问）在 Ch4 的代码中能否被读者清晰地"落地到具体函数"？（03 案例中"三问 → ProtectionArch/TrapEntryArch"的映射表就是这个检查的具体形式。）
> 5. **Ch1（概念） → Ch5（测试）**：Ch1 的核心概念是否在 Ch5 有对应的测试覆盖声明？（如"特权级切换"对应 Ch5 中哪些测试、"异常向量"对应哪些测试）
>
> **不满足时的处理**：不是直接判 FAIL，而是在 scan.md 的 Open P2 列表中加入"文档缺少纵向链路映射"，并要求作者补上 1 张类似"CPU 问题 → C 函数 → Rust trait → Rust 实现 → 测试"的映射表或对应小节。
>
> **为何放在 Step 3.5**：它不需要"先读完所有代码再判断"，只需要"知道每章讲了什么、能否对齐"——与 Step 3 Sanity Check 的深度相同，但方向不同（横向存在性 → 纵向链路）。

## 6. 例子选择的读者视角检查（新增 Pattern）

**适用文件**：`review-patterns.md`（文档模式新增）

**案例来源**：03-todo §1 决策点第 49 项（"1.1 例子简化：`*(0xffffffff80000000)=0` 改为 `*((int*)0)=0`，避免初学者分心'为什么这个地址是内核地址'"），comments.md 中 GPT 反复强调例子的"认知负担"问题。

**问题本质**：作者在选例子时，往往选"自己最熟悉的场景"（如写内核的人最熟悉写 `0xffffffff80000000` 这个高半区地址），但对第一次读文档的人来说，这个例子自带了额外的前置知识（"什么是高半区？为什么它是内核地址？"），这些前置知识与文档当前要讲的核心概念无关。

**提案**：新增一个文档模式——

> **模式 D-NEW-3：例子选择有"读者前置知识泄漏"**
> - **特征**：正文中为说明某个核心概念而举的代码示例/数字示例，隐含了超出本章当前进度的前置知识。典型症：
>   - 用 `0xffffffff80000000` 说明"写非法地址"——要求读者已经理解"高半区 = 内核"，而本章可能尚未讲页表布局。
>   - 用尚未在本文定义的结构体名/函数名作为例子（"类似 `foo_bar()`" 但 `foo_bar()` 在另一文档定义、本章节未前向引用）。
>   - 用"读者应已了解 XXX"这类语句为前提（未在本章建立，就假设读者已知）。
> - **判定方法**：假设你是"第一次接触该主题的读者"，读完这个例子后，是否会产生至少一个与本章当前主题无关的疑问？如果会 → 本例属于"读者前置知识泄漏"。
> - **严重性**：P2（普通例子）；如果本章开门第一个例子就有此问题 → P1（因为它直接影响读者是否能进入正文）。
> - **修复建议**：用"最小的、不依赖未建立知识的例子"替代——本例中 `*((int*)0)=0`（空指针写入）就比高半区地址更好，因为所有读者对"空指针不可写"都有直觉。

## 7. 概念表述的严格性：避免"××× 就是 yyy"（新增 Checklist 项）

**适用文件**：`review-doc-checklist.md §2.1 概念准确性`

**案例来源**：03-todo §1 决策点第 50 项（RISC-V SPP 表述修正：SPP 只在 trap 时记来源，当前特权级不是 SPP 表示）；comments.md 中 GPT 强调"术语定义要严格"。

**问题本质**：作者在简化概念时，有时会过度简化成"实际上不正确"的表述。例如：

| 过度简化（不正确） | 正确表述（更严格） |
|---|---|
| "RISC-V 当前特权级存在 sstatus.SPP 中" | "RISC-V 当前运行级别由 CPU 当前状态维护（S-mode vs U-mode）；SPP 只在 trap 发生时记录'上一个特权级来自哪里'，供 sret 返回时降回使用。" |
| "GDT 是保护结构" | "GDT 是 x86 上承载特权级描述符和 TSS 指针的表格；它是实现载体，不是保护结构本身。" |
| "异常向量 = IDT" | "IDT 是 x86 上的异常向量表；ARM 用 VBAR，RISC-V 用 stvec。异常向量是概念，IDT/VBAR/stvec 是各架构实现。" |

**提案：在 `review-doc-checklist.md §2.1 概念准确性` 中新增一项**——

> **2.1.6（新增）：××× 就是 yyy 的过度简化检查**
> - 对正文每一处出现"A 就是 B"、"A 等于 B"、"A 即 B"（以及英文的 "A is B"、"A == B"）的定义性表述，reviewer 必须核查：
>   1. 这个"就是"是否忽略了架构差异？（例如，A 是通用概念，B 是某架构实现，不能划等号）
>   2. 是否忽略了状态机差异？（例如，A 是"当前状态"，B 是"上一个状态的记录位"）
>   3. 是否把"实现载体"误写成了"概念本身"？（GDT 是载体，不是保护结构）
> - **测试方法**：把该表述"反过来读"——如果"反过来读"不成立 → 原表述就可能是过度简化。例如"GDT 就是保护结构"反过来读"保护结构就是 GDT"显然不对 → 原表述应修正。
> - **严重性**：P2 通常；如果涉及核心术语的首次定义（Ch1 第一次出现时）→ P1。

## 8. 执行模型分层的扩展：从"并发模型"到"状态机模型"（现有 §的补充）

**适用文件**：`review.md §执行模型` + prompt/README.md §"执行模型分层"

**现状**：review 系统的"执行模型"仅关注"单线程事件循环 vs SMP+BKL"的并发模型差异——这是代码层的执行模型。

**本案例暴露的缺口**：文档层也有"执行模型"问题——Ch1 应当建立一个**运行时状态机视角**（CPU 在每个异常前后处于什么状态、切换什么资源），而不是"源码组织视角"。这个状态机视角的缺失，就是"Ch1 主语错了"的根本原因。

**提案**：在 `review.md` 中现有"执行模型"小节末尾，**新增一段"文档层的执行模型"说明**（不影响已有的代码执行模型内容，仅是补充）：

> **文档层的执行模型（新增）**
>
> 除了代码层面的"单线程事件循环 vs SMP+BKL"，review 文档时还需关注文档的"叙述执行模型"：
>
> 1. **Ch1 是否从"运行时实体的视角"出发**（如 CPU 视角、调度器视角、缺页处理程序视角）？
> 2. **Ch1 是否先建立状态机，再落到实现**？理想顺序：状态机 → 三问 → 数据结构 → 函数。
> 3. **反向标志**：Ch1 的第一个小节就开始讲具体函数签名/结构体字段；或先讲实现再补动机。
>
> 这三点不是 review 的 Blocker Gate，但在 excellence review（§4）时作为"教学深度"的加分项来评估。

## 9. Blocker Gates A-E 的潜在强化：增加 Gate F "Ch1 骨架"

**适用文件**：`review-process-skill.md` 的 Blocker Gates 部分

**当前 Blocker Gates**（A-E）：

- **A**：coverage-extract.py 运行 + SYMBOLS.md 路径
- **B**：Top 5 行为契约表
- **C**：Precision Check 表
- **D**：P0 checklist 5 项（严格通过）
- **E**：§5 测试名 grep 验证

**本案例的反思**：A-E 全部聚焦在"实现层的完整性/正确性"——覆盖率、行为契约、精度、P0 检查、测试名验证。它们都是"这篇文档/代码的实现是否正确"问题。但**没有一个 Gate 检查"这篇文档 Ch1 的骨架是否对了"**——如 03-kmain-cstart-bak.md 这样的文档，在 A-E 上可能全部通过（引用有 file:line、覆盖率够、测试名正确），但 Ch1 从教学角度是不合格的。

**提案**：考虑新增 **Gate F "Ch1 骨架检查"**（或放在 Gate D 内部作为 D 的一个子项，不新增独立 Gate 以避免 Gate 过多）：

> **方案一（较轻）：Gate D 中新增一个子项 D-6 "Ch1 核心概念能否在不出现任何函数名/结构体名/trait 名的前提下完整解释"**（见本提案第 1 节 1.2 项）。reviewer 在 Gate D 中必须执行此项并附上"裸概念复述"的简短证据（scan.md 的 Gate D 证据段中加入 1~2 句复述）。
>
> **方案二（较重，不推荐本轮落地，但记录为长期目标）：新增 Gate F "Ch1 骨架"**，要求检查本文第 1 节的 1.1~1.9 全部项目，并在 scan.md 中附上每项的通过证据。风险：Gate 总数过多，reviewer 负担增加。建议先试点方案一（作为 Gate D 的一个子项）。

**推荐**：本轮采用方案一。如果试点后发现大量文档在该子项上 FAIL，再考虑升级为独立 Gate。

## 10. 文档卓越性的"收敛成本"警告（Process 改进）

**适用文件**：`review-process.md` 的"结束条件/再评审"部分

**案例来源**：03-todo 中反复出现"本轮 GPT 判定进入'设计收益 < 设计成本'阶段，改完即写"。这是一个非常有价值的信号——**文档改进不是无限的，超过某个点后 reviewer 的投入产出比会急剧下降**。

**现有规则的缺口**：review-rules 没有给 reviewer 明确信号——"当文档已经处于什么状态时，应当停止继续要求结构性修改、转向局部打磨或直接通过"。结果是：reviewer 可能在"已经 90 分的文档"上继续提出 10 个结构性改进建议，作者疲于奔命但实际教学收益有限。

**提案**：在 `review-process.md` 的 Step 7（报告/收敛阶段）中加入一段"收敛成本警告"——

> **Step 7.1 收敛成本警告（新增）**
>
> 在输出最终 review 报告前，reviewer 需自问以下三个问题，三个都回答"是"时，才应继续提出结构性修改建议；否则应将剩余建议降级为"可选改进项/P3"：
>
> 1. **这篇文档的 Ch1 已经满足本提案第 1 节的 Ch1 骨架检查吗？**（即核心概念驱动、三问框架、闭环、边界声明、本章小结等都已到位）
> 2. **上一轮提出的改进建议已经被作者实质吸收了吗？**（不是"作者又改了一版"，而是"核心问题已解决"——例如 03 案例中"主语从 `prot_init()` 换成 CPU"这一步完成后，文档就从 60 分升到 90 分了）
> 3. **我本轮新提出的建议是否会导致作者重写超过 20% 的现有正文？**（如果是 → 大概率属于"过度打磨"，应降级为可选改进。除非发现了 P0 级概念错误。）
>
> 当三个问题答案为"是/是/否"时，review 应**收敛**——剩余改进建议作为"可选优化项（P3）"列出，不作为阻塞项。

## 附：本提案的"自检"（苏格拉底追问 8 场景中的第 1 项："我是否在做过度推断？"）

最后自问一个关键问题以避免提案自身的"过度推断"风险：

> **问**：03-kmain-cstart 这个重构案例有多大代表性？能保证这些规则对 04-clock-interrupt、05-process、12-syscall、13-exception 等文档同样有用吗？
>
> **答**：
> 1. **代表性分析**：03-kmain-cstart 的核心问题——"Ch1 主语从 `prot_init()` 出发而非从概念出发"、"GDT 权重过高"、"缺少返回路径"、"例子用高半区地址有前置知识泄漏"——**每一条都是"作者按照自己写代码的顺序组织内容"的通用现象**，在任何需要"从 C 代码出发解释操作系统概念"的文档中都会重复出现。因此本案例的问题结构有高泛化性。
> 2. **可验证性**：提案中的每条规则都设计了**结构化判定方法**（如 #1.2 的"函数名替换测试"、#4.a 的"非通用术语清单 + 移除后是否仍完整"、#7 的"反过来读法"）——不是 reviewer 主观判断，而是可以被任何 reviewer 按同一步骤执行的检查。
> 3. **副作用评估**：提案新增的主要是"Ch1 层"的检查（因为本案例的问题集中在 Ch1），对 review 系统的其他部分（覆盖率穷举、P0 checklist、Gate A-E）几乎没有侵入性。最坏情况——如果某文档的 Ch1 确实不适合用"三问框架"（例如纯概念性章节，没有运行时视角）——reviewer 可以在检查项上标注"不适用（N/A）"并附理由，不会被强制套入错误框架。
> 4. **结论**：代表性高，判定可结构化，副作用低。提案可采纳。
