# REVIEW 流程优化提案（qwen 份）—— 让流程自足地产出"有血肉的技术博客"

> **性质**：多 AI bagging 中本会话的独立提案份（对齐 `rewrite-notes/*/doc_rerank_*.md` 的"各 AI 各写一份"约定）。
> **问题域**：`prompt/review-rules/` 这套文档生成 + 分阶段 review 流程。
> **一句话主张**：现行流程只约束"负面项 + 一致性"，不约束"正文必须承载哪些教学构件"，因而能全绿产出一篇**合规但没血肉**的干巴稿；必须把"血肉"从"靠 draft 侥幸"升级为"流程强制产物"，使 **draft / 旧快照不可用时流程仍自足**。
> **本会话实证**见 §2，落地映射与尺度决策见 §4–§6。

---

## 1. 病根：流程约束的是"别犯错"，不是"要有货"

现行流程对一篇机制类文档的硬约束，全部落在两类：

| 类别 | 出处 | 管什么 |
|---|---|---|
| 负面项 | `style-bible`、模式 64 | 禁黑话/缩写/文言文/压缩简写、禁开发文档味、禁过程痕迹入正文 |
| 一致性 | Doc Code Sync 七项、Gate B/C/D/E、锚点纪律（模式 83） | 文档说的和代码/ C 源**对不对**、锚点可解析、测试不虚构 |

**没有任何一条问："这一章有没有把被分析的 C 函数、被实现的关键 Rust 贴出来？有没有把控制流、纵深辨析、跨架构语义、失败路径讲出来？"**

后果是一个**结构性的漏判面**：一篇纯散文、零贴码、无调用图、无辨析、无三架构对照、无诊断的文档，只要不违禁、锚点齐、与代码一致，就能通过全部 Gate——它"合规"，却没有技术博客该有的血肉。

---

## 2. 本会话实证（这就是"没血肉也能全绿"的活证据）

- **draft/01**（`rewrite-notes/01-stage-kernel/draft/01-boot-shim-bootstrap.md`，经人工审阅）：**2019 行、19 个 Rust 块 + 7 个 C 块**，含每函数贴码 + "角色"框定、ASCII 调用树、PWT|PCD 与 USER 位不对称等源码级辨析、独立"启动失败与诊断"章。
- **流程首次产出的新 01**：**295 行、仅 3 个 Rust 块（全在 Ch3），Ch2 零 C 码、Ch4 零 Rust 码**。
- 而这版干巴稿**通过了全部正确性门**：`anchor-resolve` 9/9、`doc-style-lint` error=0、Gate G 一致性 100%、Gate A–H 全绿。
- **R2 的 `style-fix` 当时判"文风/章节/深度全通过、无需改动"**——它根本没有"代码密度/教学构件"这一维，所以拦不住干巴。这是流程盲区，不是执行者侥幸。
- 用户人工指出"太干巴、不像技术博客"后，才被要求补齐血肉（贴码 + 调用树 + 辨析 + 三架构对照 + 诊断章），增强到 ~470 行 / 15 个代码块。

**若 draft 不存在，或旧 `.design` 快照不存在，流程没有任何一环会提醒补这些** → 会原样交付那篇 295 行干巴稿并判它合格。用户的核心担忧正是此点。

## 3. 连带病根：outline-first 被"历史快照"顶替

现行 `review-process.md` Step 0.3 有"design-structure → outline → outline-review → design"的大纲优先链，Gate H 校验"快照齐全"。但存在一个**判据错误**：

- 我这次以"`.design/01-outline.v1.md` / `01-design.v1.md` 存在且标 PASS"为由，**跳过为"新文档"重出大纲**，直接写正文。
- 而那套 v1 快照是**围绕 draft/01 那一代**起草的，且**早于代码演进**——R1 当场证伪：`param_buf` 判"移除"实则保留、`reserved_regions` 没列、方案 A `BootHandoff` 根本没有。
- 一个连当前代码都不反映、且为**另一篇文档**起草的快照，**不能当新文档的结构契约**；其地位应等同 `draft/`——**只能作思路参考**。

这条链的失败与 §1 是同源的：规划层没有一次"为新文档独立出大纲、且大纲里登记了每节贴什么码"的动作，正文从一开始就没有代码放置的蓝图，自然塌成散文。**"缺血肉"是"缺 outline-first"的下游症状。**

## 4. 改进 A：把"血肉清单"写成正面产物约束（进 `style-bible`）

机制类文档（讲 WHY→WHAT→HOW 的那类）生成时**照单产**，而非事后补。每篇至少含五类构件：

| 构件 | 最低要求 | 为什么必须有（不可由"文风合规"替代） |
|---|---|---|
| **贴码** | C 源码分析章：每个核心函数一段真实节选代码 + "角色"框定 + 逐条件讲解；实现章：若干段关键 Rust | 技术博客靠"代码 + 讲解"双轨；读者要能对着代码看推理 |
| **调用/数据流图** | 跨函数控制流或数据流，用一张 ASCII 树/图承载 | 纯散文讲不清"谁在什么时刻动了什么" |
| **纵深辨析 aside** | ≥ 数条"这个位为何这么设 / 不 X 会怎样"、追到 C/Rust 源码注释的 blockquote | 讲本质而非复述接口，正是"触及灵魂的一针见血" |
| **三架构"机制各异·语义同一"对照** | 凡涉跨架构机制：一张三架构表 + 一句 §1.6 式"本质语义是什么"收口 | 落实"抽象语义、不描述机制"，让读者看见形状 vs 语义的分界 |
| **失败/边界诊断** | 一段"这条链炸了长什么样、怎么定位" | 机制文档若只讲成功路径，读者遇到故障无从下手 |

**定义来源是"技术博客的形态"本身（写进文风宪法），不引用任何既有文档** → 这正是让流程在 draft 缺席时仍自足的关键。

## 5. 改进 B：outline-first 加"代码放置清单"（进 `review-process.md` Step 0.3 + 生成 prompt 第 1.5 步）

新机制文档写正文**前**，必须产出它自己的结构大纲，其中每节登记一栏代码放置计划：

```
| 章节 | 讲什么 | 预定贴码（C 函数 / Rust 实体 + 节选行数 + 目的） | 调用图/辨析/三架构/诊断（勾选） |
```

大纲经自审（outline-review）通过后，正文按此放置代码与构件。**Gate H 对"新生成文档"的判据相应改为**：
- 旧判据（错）："存在 `.design/{num}` 历史快照即 PASS"。
- 新判据："**该文档自带新 outline（含代码放置清单）且经自审**"；旧 `draft/*`、旧 `.design` 快照**一律标注为'仅供参考、非本篇契约'，不得据以跳过本步**。

## 6. 改进 C：review 门补"血肉/代码密度"这一维（进 `style-fix` + 新工具 + CI）

- **`style-fix` 增第四维"教学构件完备性"**：逐条勾 §4 清单，缺哪类报哪类。修复本会话 R2 style-fix 的漏判。
- **新增机械门 `tools/doc-code-density-check.sh`**（尺度取**中等**）：按二级章节统计代码块数与行数占比——
  - **分析章 / 实现章为纯散文（该章 0 代码块）→ 判 P1-docStyle**（阻断 CONVERGED，非 P0，避免"逐函数必须贴码"的过死）；
  - 有码但疏密不均 / 缺调用图 / 缺三架构表 → 报告项，提醒不阻断。
- 纳入 `review-cmds.md` 通用强制门 + `.github/workflows/rules-consistency.yml` 那套 CI（改规范源须跑的四道同步门：`generate-derived-skills.sh` → `check-review-rules.sh` → `lint-review-rules.sh` → `diff-trae-skills.sh --only-diff`）。
- 可选 **Sync-8**：Doc Code Sync 增一项"分析章引用的每个 C 函数是否贴了节选码"，把"文档↔代码"从"一致性"扩到"承载性"。

## 8. 非目标（划清边界）

- **不是**要求把文档写回 draft 那种 2019 行的体量——draft 自身有过程痕迹、手工行号、落后于代码等纪律问题，血肉 ≠ 冗长。目标是"该贴的码贴上、该画的图画上、该追的辨析追到底"，体量随内容。
- **不是**削弱任何真值校验：符号锚点解析、覆盖率穷举、测试名对账照旧。贴码走"符号锚点 + 块级题注"，纯坐标仍外移底账。
- **不是**为漂亮提前改抽象契约：三架构对照表讲的是"语义同一、形状各异"，不为统一而伪造统一（公理三）。

## 9. 一句话验收标准（给后续 bagging）

**把 draft/01 和 `.design/01` 全部删除，重跑这套流程，产出的 01 文档仍应自动带上：C/Rust 节选码、调用树、源码级辨析、三架构语义对照、失败诊断。** 做到，就说明流程不再依赖 draft 兜底质量；做不到，说明"血肉"仍是靠人补而非靠流程产。
