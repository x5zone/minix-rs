# DOC-ITER-WORKFLOW — 文档迭代工作流（统一规格，v0.1）

> **版本**：v0.1（2026-10-13 建立）
> **性质**：本文件是「逐篇迭代优化 + GPT 第三方审阅闭环」的统一工作流规格，同时服务两个入口——
> 入口 A（新生成，文档不存在）与入口 B（存量优化，文档已存在）。两者共享同一套规则表与验收标准。
> **规格源与包内嵌**：每轮轮次包（§五）把本文件的「规格主体」（§一~§九）逐字内嵌，供外部审阅者
> 分别评估「文档质量」与「workflow 有效性」。本文件是唯一规格源；轮次包是它的当轮快照。
> **配套**：既有 review 规则源（`prompt/review-rules/`）、文风宪法（`prompt/skill/cmds/style-bible/SKILL.md`）、
> 开放项台账（`prompt/WORKFLOW-OPEN-ITEMS.md` 的 W-1/W-6/W-7/W-8/W-9 与 R5）——全部并入本规格的规则表，
> 不另立一套。若其中的纪律后续要并入规范源，按 `prompt/README.md` 三端同步流程执行。
> **落盘**：轮次包与过程产物进 `tmp/doc-iter/`（F-C 纪律：仓库根不散落文件）。

## 〇、开工前必读（执行会话照单读，不凭记忆）

1. 本文件全文（尤其 §四 规则表与 §七 反模式清单）。
2. `prompt/review-rules/review.md`（核心不变量：执行模型、真值优先序、P0 六分类）。
3. `prompt/review-rules/fix-guard.md`（动手前 5 件事、一次一条、修后留痕）。
4. `prompt/WORKFLOW-OPEN-ITEMS.md` 的 W-1（增量阻断+存量报告口径）、W-6（读者视角装置）、
   W-7/W-9（中文惯用法与受控比喻）、W-8（反事实构件纪律）。
5. 目标文档及其头部字段列出的 C 真值源与 Rust 实现（真值优先序：C 源码 > 设计契约 > Rust 实现 > 文档）。

## 一、定位：两个入口，同一套纪律

**入口 A · 新生成**（文档不存在）：沿用 doc-gen v3 装置——事实先修（fact-priors）→ 设计快照 →
大纲 → 生成 → 四路验证（编排自审 / 盲测学生 / CodeReview / 五门）。本规格在其上叠加编辑层：
S2 的「读者路径 + 决策卡」前移到大纲阶段作为输入；S2 的「标注式编辑审查」在初稿后执行一次。

**入口 B · 存量优化**（文档已存在）：本文件主体——§三 执行手册 S0~S5。

**共同纪律**：§四 规则表全适用；§六 六维验收全适用；§七 反模式清单全适用。

## 二、迭代结构（内循环 × 外循环）

**内循环（一篇文档，同一会话，3~5 轮）**：

```
第 i 轮（i = 1..3~5）：
① 优化：按当前 workflow 版本跑 S0~S4（第 1 轮全量审计；后续轮聚焦上轮 GPT 反馈与残余缺口）
② 打包：按 §五 装配 tmp/doc-iter/<doc-slug>/round-NN.md（单文件：规则集 + 新版全文 + diff）
③ 审阅：用户把包交给 GPT（建议每轮新开对话，保持审阅者独立；反馈可贴回对话，
   也可落成 tmp/doc-iter/<doc-slug>/gpt-feedback-round-NN.md 供执行会话读取）
④ 归因：取回反馈 → §八 归因表（workflow 缺陷 / 执行偏差 / 局部问题 / 事实错误）
   → 只把「有证据且可推广」的项写回本文件（版本 +1）→ 用户裁决
⑤ 提交：目标文档与本文件按具名路径提交（纪律见 S5）
⑥ 收敛判定（§九）：达标或触停止条件 → 结束内循环
```

**外循环（换篇，新会话）**：另选一篇文档，以当前 workflow 版本重跑内循环。
换篇是防过拟合的检验：规则必须在第二篇形态不同的文档上仍然成立，才算通用规则；
只服务单篇特征的项不上升（§八 裁决规则）。

**冻结**：连续两轮（可跨篇）没有「值得纳入全局 workflow」的新缺陷 → 冻结版本；
其后各篇按冻结版本执行，GPT 审阅降频为抽检（首轮包或疑难篇），不再逐轮送审。

**会话模型**：任一步骤可冷启动。状态全部在文件里：本文件（workflow 版本）+ 轮次包 +
`tmp/doc-iter/LEDGER.md`（轮次账：目标文档 / 基线 commit / 包路径 / 版本 / 审阅状态）+ git 提交。

**轮次对象**：任意文档路径（stage-agnostic）。首批：`rewrite-notes/01-stage-kernel/` 的 01~14
（全量重审计）。其他 stage 的文档随时可按同一规格加入队列（其教学性差异是同一问题域）。

## 三、每轮执行手册（入口 B）

### S0 基线冻结与存量盘点

1. 确认目标文档在工作树无未提交改动（有则先提交或记录）；记录基线 `git rev-parse HEAD`。
2. 规模读数：`wc -lc <doc>`。
3. 存量盘点（对目标文档 grep；读数进轮次包 §5）：
   - 套路句（W-8）：`grep -n '如果反过来想' <doc>`；同类套路句「少了这道防线会怎样」「次序错了会怎样」「破坏约定会怎样」。
   - 受控比喻「腿」（W-7/W-9）：`grep -n 腿 <doc>`——逐处判断（有真实语义的保留并确保首现有定义；
     纯比喻换通行说法），**禁全局替换**。
   - 「端口」移植义（W-9）：`grep -n 端口 <doc>`——逐处词义分流（网络端口 / I-O 端口义保留；
     架构移植义换「各架构 / x86 这一侧」）。
   - 引号主导风格（W-6①）：`grep -o '[“”]' <doc> | wc -l`——与文件主导风格比对，新引入的弯引号清零。
   - 含糊尾巴（W-6②）：`grep -n '及邻近\|相关部分\|等字段' <doc>`。
   - 压缩简写抽查（W-6）：抽 3~5 处最密段落人工读一遍。
4. 产出存量清单，S2 审计表里逐项落位。

### S1 事实层复核（对将动刀区域）

先事实后编辑——事实错会在改写中被掩盖。三条人审缺陷类逐条查（规则 F1~F3）：
- **F1 反事实先证伪**：每个反事实段展开前，先 grep 验证「被改动的对象/退路」在代码里真实存在
  （跨架构同名函数不得互相套用；签名/定义 grep 不过就删段，不是改措辞）。
- **F2 收益/理由指认到机制**：每条「收益/优点/理由」必须指认到机制本身提供的证据；
  冒领项（如把 feature gate 的功劳算给 trait）剔除。
- **F3 结论与依据配对**：每条次序/依赖/因果结论复核依据是否真正支撑它（防错配、防注释搬家）。
- **F4 锚点纪律**（既有）：引文逐字 + 区间复算；断言带锚点。

### S2 编辑审计（先标注，不直接改写）

1. **读者路径表**：逐节填「本节回答什么问题 / 依赖前文什么 / 为后文提供什么」；
   标出前提晚于需要（倒置）与跨章重复职责。
2. **决策卡（审计版，设计章）**：对每个设计决策核对八字段是否可寻——原始事实 / 新约束 /
   决策问题 / 候选方案 / 选择与理由 / 代价与边界 / 实现落点 / 可迁移原则；缺什么补什么，不硬套模板。
3. **逐段标注**：每段标 保留 / 压缩 / 移位 / 重写 + 理由 + 命中规则编号；产出审计表。判据：
   - 保留：核心推理或必要证据；删了读者会失去机制、因果链、设计理由或可验证结论。
   - 压缩：同一结论反复解释、措辞过密、无新增信息的过渡句。
   - 移位：内容有价值但属于其他章节（设计章里的实现细节、实现章里的设计辩论、附录级排障细节）。
   - 重写：概念堆叠、主语动作不清、顺序不合读者理解路径。
4. **四位置职责检查（E6）**：概念讲解 / 章节小结 / 下章开头 / 跨章总表——同一结论出现多次时，
   每次必须承担不同任务（允许重复结论，不允许重复整段推理）。
5. **卡点预演（预审版）**：编排者自问「读者在此会卡在哪」，列候选卡点清单，供 S4 盲测对照。

### S3 改写执行

1. 按审计表执行；逐条记录改动台账（节号 / 类型 / 命中规则 / 一句话理由）——S5 的 diff 标注与统计直接取用。
2. 纪律：E 系列（编辑）+ C 系列（承载保护）+ L 系列（语言）+ §七 反模式清单。
3. **结构冻结（E7）**：除非发现实质错误，不得以「更优叙事」为由重构章节结构。
4. 反事实段按 F1+C2 逐段过；过不了的删，不改成「委婉版」。

### S4 分项验收

1. **V2 盲测学生**（保留并升级——本工作流的固定装置，解决「教学性不足」痛点的核心）：
   - 闭卷：新读者 agent 只读目标文档，不读源码与其他文档。
   - 题组：8~11 题，全部要求沿机制链推理（不是背事实）；覆盖主路径与关键边界。
   - 卡点清单：逐节记录「我在哪里卡住 / 回读 / 需要外部知识」——W-6「预判读者卡点」的实证版。
   - 整段复述：抽 2~3 个核心机制段，学生用自己的话复述。
   - 输出：题分 + 卡点清单 + 复述结果；缺口进修复批次。
2. **V3 CodeReview**：独立 agent 核查文档断言 vs C 源 / Rust 代码；分级 P0/P1/P2；附命令与输出证据。
3. **V1 六维自评**：编排者按 §六 逐维给证据（供包 §5 与 GPT 对照）。
4. **V4 五门**：anchor-resolve / doc-code-map / doc-style-lint / doc-ref-check / doc-code-density 全绿。
5. 修复批次 → 复跑至 §九 收敛判据。

### S5 打包与提交

按 §五 模板装配 `tmp/doc-iter/<doc-slug>/round-NN.md`；更新 `tmp/doc-iter/LEDGER.md`。

提交纪律（仓库可能同时有其它会话的改动在制——并发现场）：

- 只按具名路径 `git add` 本轮涉及的文件（目标文档、本规格文件；包与过程产物在 tmp/ 不入库）；
- 提交前 `git status --short` 核对，不碰与本轮无关的在制文件；
- 禁 `git add -A` / `git commit -a`；commit message 记录轮次号、workflow 版本、包路径。

**diff 标注规范**：命中规则引用 §四 编号（如 `【命中：E3·E6】`）；一个改动块可并列多条规则；
纯机械清理（引号/尾巴/套路句）标 L 系列编号；删除类改动必须能对上规则理由（C1 保护的承载物除外——
删除承载物属违规，须在 §1 变更记录里说明为何不违反）。

## 六、验收标准（固定六维，每轮相同）

| 维度 | 判据 |
|---|---|
| 教学完整性 | 机制、因果链、设计理由讲透；没有「只有结论没有推导」处；未因精简退回大纲 |
| 语言清晰度 | 读者能自然理解谁做了什么、为什么、结果如何；无名词堆叠、无审计腔模板句 |
| 信息密度 | 无重复解释、无空泛过渡；重复出现的结论每次承担新任务 |
| 阅读路径 | 前提先于需要；节间依赖顺读者理解顺序；无职责倒置 |
| 章节职责 | 四章边界（概述=机制、C 源码=事实、设计决策=判断、实现=落地）不被混淆 |
| 技术准确性 | 结论有源码依据；改写未损失事实与关键约束 |

**硬规则**：技术准确性与教学完整性不得由语言流畅度抵偿（更短更自然但丢了推理链 ≠ 改进；
更详细但重复三次同一结论 ≠ 完美）。

## 七、反模式清单（违反即退回）

1. 不以缩短篇幅为目标；篇幅由教学内容决定（E5）。
2. 不删教学承载物（C1）；「可引用」≠「不必解释」（E8）。
3. 不复述已讲结论（E3）；不机械复用论证模板（审计腔）。
4. 反事实不仪式化：只在证明关键不变量、解释非显然故障或澄清边界时展开（C2），且先证伪前提（F1）。
5. 不以「更优叙事」重构章节结构（E7）。
6. 不全局替换直译词（L1 逐处词义分流）。
7. 不用套路句当反事实默认标签（W-8：引导句必须点明本段真正改动的对象）。

## 八、归因与 workflow 演化（元循环 ①）

GPT 反馈回来后，逐条填归因表：

| 字段 | 内容 |
|---|---|
| 本轮发现 | 审阅证据与具体问题（引用包内位置） |
| 根因判断 | workflow 缺陷 / 执行偏差 / 局部问题 / 事实错误 |
| 是否修改 workflow | 是 / 否 |
| 修改内容 | 新增、删除或调整了哪条规则（编号） |
| 预期效果 | 下一轮应该改善哪种问题 |
| 回归风险 | 这次修改可能损害什么已有优点 |

裁决规则（防规则膨胀）：只把「有证据 + 可推广」的项上升为规则；只在一处出现的建议谨慎上升；
新增规则必须证明改善超过额外复杂度；用户对上升项有最终裁决权。

## 九、收敛与停止条件

**每轮收敛**（可交付）：盲测题分全对或缺口全部修复且判定为范围外；卡点清单清零或确认全部范围外；
CodeReview P0/P1 清零；五门全绿；六维自评无系统性缺陷。

**内循环停止**（借鉴 review Step 7.1 + 用户设定）：同篇 ≥5 轮强制换篇；连续两轮新增 P1 ≤ 1；
本轮成本 > 上轮 80% 而新发现 < 20% 停止；首轮零发现触漏检自检（随机抽 3 项重跑）。

**外循环与冻结**：换篇检验规则可迁移性；连续两轮（可跨篇）无「值得纳入全局 workflow」的
新缺陷 → 冻结；冻结后其余篇目按冻结版本执行、GPT 审阅降频为抽检；再开新版本须有真实案例证明必要。
