# DOC-ITER-WORKFLOW — 文档迭代工作流（统一规格，v0.2）

> **版本**：v0.3（2026-10-14；Round 02 实证 + 外部评审后修订）
> **性质**：本文件是「逐篇迭代优化 + 第三方审阅闭环」的统一工作流规格，同时服务两个入口——
> 入口 A（新生成，文档不存在）与入口 B（存量优化，文档已存在）。两者共享同一套规则与验收标准。
> **修订原则（v0.2 起）**：优先改进缺陷发现、证据验证、效果归因与停止判据，**不扩大规则表**；
> 新条目必须来自真实案例（Round 01/02 的缺陷清单与外部评审）。
> **规格源与包内嵌**：每轮轮次包（§五）把本文件的「规格主体」（§一~§九）逐字内嵌一次，供外部
> 审阅者分别评估「文档质量」与「workflow 有效性」。本文件是唯一规格源；轮次包是它的当轮快照。
> **配套**：既有 review 规则源（`prompt/review-rules/`）、文风宪法（`prompt/skill/cmds/style-bible/SKILL.md`）、
> 开放项台账（`prompt/WORKFLOW-OPEN-ITEMS.md` 的 W-1/W-6/W-7/W-8/W-9 与 R5）——全部并入本规格的规则表，
> 不另立一套。若其中的纪律后续要并入规范源，按 `prompt/README.md` 三端同步流程执行。
> **落盘**：轮次包与过程产物进 `tmp/doc-iter/`（F-C 纪律：仓库根不散落文件）。
> **可恢复的最小记录**：`rewrite-notes/coordination/DOC-ITER-LEDGER.md`（入库，见 §五·5.1）。

## 〇、开工前必读（执行会话照单读，不凭记忆）

1. 本文件全文（尤其 §三 S1 证据盘点、§四 规则表、§七 反模式清单、§八 归因记录）。
2. `prompt/review-rules/review.md`（核心不变量：执行模型、真值优先序、P0 六分类）。
3. `prompt/review-rules/fix-guard.md`（动手前 5 件事、一次一条、修后留痕）。
4. `prompt/WORKFLOW-OPEN-ITEMS.md` 的 W-1（增量阻断+存量报告口径）、W-6（读者视角装置）、
   W-7/W-9（中文惯用法与受控比喻）、W-8（反事实构件纪律）。
5. 目标文档及其头部字段列出的 C 真值源与 Rust 实现（真值优先序：C 源码 > 设计契约 > Rust 实现 > 文档）。
6. `rewrite-notes/coordination/DOC-ITER-LEDGER.md`（本工作流的跨会话状态：上一轮基线/结果 commit、
   审阅状态、已接受的规则变更、轮次包定位）。

## 一、定位：两个入口，一套规则，两套执行流程

**共享层**：§四 规则表（F/E/C/L/V）+ §六 六维验收 + §七 反模式清单 + §八 归因记录——两入口同用。

**入口 B · 存量优化**（文档已存在）：本文件主体——§三 执行手册 S0~S5。
**入口 A · 新生成**（文档不存在）：沿用 doc-gen v3 装置——事实先修（fact-priors）→ 设计快照 →
大纲 → 生成 → 四路验证（编排自审 / 盲测学生 / CodeReview / 五门），叠加编辑层：S2 的「结构审阅 +
读者路径 + 决策卡」前移到大纲阶段作为输入。**入口 A 的完整重做不在 v0.2 射程内**：先让入口 B 经
真实案例（Round 01 起）验证，再把稳定规则回流到入口 A（见 §十 未决）。

## 二、迭代结构（内循环 × 外循环）

**内循环（一篇文档，同一会话，3~5 轮）**：

```
第 i 轮（i = 1..3~5）：
① 优化：按当前 workflow 版本跑 S0~S4（第 1 轮全量；后续轮聚焦上轮反馈与残余缺口）
② 打包：按 §五 装配 tmp/doc-iter/<doc-slug>/round-NN.md（单文件：规则集 + 新版全文 + 标注 diff）
③ 审阅：用户把包交给 GPT（建议每轮新开对话，保持审阅者独立；反馈可贴回对话，
   也可落成 tmp/doc-iter/<doc-slug>/gpt-feedback-round-NN.md 供执行会话读取）
④ 归因：取回反馈（含独立结构审阅结论）→ 填 §八 归因记录（每轮必填，不只写原则）
   → 只把「有证据且可推广」的项登记为候选规则；用户裁决后写入本文件（版本 +1）
⑤ 提交：目标文档、本文件、可提交台账按具名路径提交（纪律见 S5）
⑥ 收敛判定（§九 三道理门）：文档可交付？本轮有实质改进？workflow 可冻结？
```

**外循环（换篇，新会话）**：另选一篇**形态尽量不同**的文档，以当前 workflow 版本重跑内循环。
换篇是防过拟合的检验：规则必须在第二篇形态不同的文档上仍然成立，才算已验证规则；
只服务单篇特征的项不上升（§八 裁决规则）。

**冻结**：按 §九 第三道理门判定；冻结后其余篇目按冻结版本执行、GPT 审阅降频为抽检。

**会话模型**：任一步骤可冷启动。状态全部在文件里：本文件（workflow 版本）+ 轮次包 +
`rewrite-notes/coordination/DOC-ITER-LEDGER.md`（入库的最小记录）+ `tmp/doc-iter/LEDGER.md`
（进程细节）+ git 提交。

**轮次对象**：任意文档路径（stage-agnostic）。首批：`rewrite-notes/01-stage-kernel/` 的 01~14
（全量重审计）。其他 stage 的文档随时可按同一规格加入队列（其教学性差异是同一问题域）。

## 三、每轮执行手册（入口 B）

### S0 基线冻结与存量盘点

1. 确认目标文档在工作树无未提交改动（有则先提交或记录）；记录基线 `git rev-parse HEAD`。
2. 规模读数：`wc -lc <doc>`。
3. 存量盘点（对目标文档 grep；读数进轮次包 §5）：
   - 套路句（W-8）：`grep -n '如果反过来想' <doc>`；同类 fallback 套路句「少了这道防线会怎样」
     「次序错了会怎样」「破坏约定会怎样」。
   - 受控比喻「腿」（W-7/W-9）：`grep -n 腿 <doc>`——逐处判断（有真实语义的保留并确保首现有定义；
     纯比喻换通行说法），**禁全局替换**。
   - 「端口」移植义（W-9）：`grep -n 端口 <doc>`——逐处词义分流（网络端口 / I-O 端口义保留；
     架构移植义换「各架构 / x86 这一侧」）。
   - 引号主导风格（W-6①）：`grep -o '[“”]' <doc> | wc -l`——与文件主导风格比对，新引入的弯引号清零。
   - 含糊尾巴（W-6②）：`grep -n '及邻近\|相关部分\|等字段' <doc>`。
   - 压缩简写抽查（W-6）：抽 3~5 处最密段落人工读一遍。
4. 产出存量清单，S2 审计表里逐项落位。

### S1 证据盘点与事实复核（v0.2 重写：从"只查将动刀区"升级为"全篇证据盘点 + 重点复核"）

先事实后编辑——证据漂移会在改写中被掩盖。本步分两层，**不论本轮改哪一节，第一层都全篇执行**。

#### S1.0 证据分类登记（先说明性质，再决定怎么核）

把文档中容易随代码/测试/构建演进失效的内容按类型登记，并**先标注每一处的性质**：

| 性质 | 含义 | 核验方式 |
|---|---|---|
| 可复现命令 | 声称"现在跑能得到这个结果" | **重跑**；读数与正文比对 |
| 历史记录 | 某次真机/某日期的观测记录 | 不重跑；标注时间与版本来源（记录在案的证据） |
| 展示示例 | 讲解用的示例命令/伪命令 | 只查语法与语义正确性，不要求可跑 |
| 源码引用块 | 引用 C/Rust 源码（逐字引用 / 教学简化 / 反面示例 / 签名示意） | 逐块比对原文件（见 S1.2） |
| 数量/字段/对账表 | 计数、字段对照、"N 个字段的去向" | 有全集时做集合校验（计数一致、无漏项/重复/错列） |
| 路径与位置锚点 | `path:fn/struct/…`、文件路径、章节引用 | 机器扫描（anchor-resolve / doc-code-map / doc-ref-check），再按引用类型复核 |
| 规范/实现/设计结论 | 关于 ISA、硬件、C 行为、Rust 行为、设计动机的断言 | 按 S1.4 主张类型表选真值源核对 |

#### S1.1 全篇低成本扫描（机械可做，全部执行）

- 锚点：`bash tools/anchor-resolve.sh <doc>`；正文出现 `path.rs:NN` 形态的行号引用列表（本篇约定
  见文档头；有约定即报清单）。
- 关联代码：`bash tools/doc-code-map.sh <doc>`。
- 内部引用：`bash tools/doc-ref-check.sh <doc>`（报告级误报须逐条人工分诊并留证）。
- 数量/对账表：对每个"N 个 X"做计数复算；对字段/常量对照表，凡有全集（头文件、结构体、枚举）
  即做集合与唯一性检查。
- 可复现命令：**全部重跑**（历史记录与展示示例除外，按 S1.0 标注）。

#### S1.2 引文块逐块对账（Round 01 缺陷 #2 的装置化）

对每个 `逐字引用 / 节选 / 教学简化 / 反面示例 / 签名示意` 块：

1. 按块头标注的路径取出源文件对应区域，**逐行比对**（含缩进/制表符；可用脚本做"文档各内容行
   在源文件中按序逐字存在"的子序列校验，再人工处理注释与省略号）。
2. 核对**标签与实际的一致性**：标"逐字引用"的，块内不得有未声明的注释删节或省略号；
   标"节选"的，省略号/删节说明必须与事实相符。
3. 源函数在文档成稿后发生过演进（新增分支、新参数、新步骤）时，引文块与其解码必须同步——
   "引文仍停留在旧实现"按 P0-fact 处置（Doc Code Sync）。

#### S1.3 针对性复核

重做本轮改动涉及的事实，并优先复核 S1.0 中标注为"可复现命令"与"源码引用块"的全部条目
（它们是最易随代码演进失效的两类）。读数过期一律按 P0-fact 处理。

#### S1.4 按主张类型选真值源（F5，冲突保留）

| 要证明的主张 | 优先核对的依据 |
|---|---|
| 现有 C 代码实际做了什么 | C 源码、调用链及相关数据流 |
| Rust 版本实际如何实现 | Rust 代码、类型约束、测试结果 |
| 某项设计为什么存在 | 决策记录、契约及其推导依据 |
| CPU / ISA 规定了什么 | 对应架构规范或技术手册（如 RISC-V Privileged Spec） |
| 文档是否准确描述当前实现 | 文档断言与当前代码逐项对照 |

**冲突处理**：当代码注释、设计文档与硬件规范冲突时，**保留冲突记录**（文档按更高优先级的真值源
陈述，并注明冲突所在），分别报告实现现状与规范要求——不得简单二选一后把问题藏起来。
（案例：Round 01 的 `os/kernel/src/lib.rs` Step 1 注释与 RISC-V 规范对 `SUM` 的相反陈述。）

#### S1.5 关键因果主张核对（v0.3 新增）

不逐句审；每章挑**少量最重要的因果/依赖主张**（一般全篇 3~6 条，列进轮次包 §5），逐条核对四问：

| 问题 | 判据 |
|---|---|
| 结论依赖哪个**直接机制**？ | 写出成立所需的最近一环，不写"总体上" |
| 引用的证据是否真的证明了它？ | 证据指向的机制与结论依赖的机制是否同一个（防"结论对、解释错"） |
| 适用范围（架构/执行阶段）？ | 该结论对哪些形态成立；跨形态表述有没有被写成"普遍情况" |
| 重述是否失真？ | 该主张在概述、小结、设计章、实现章重述时，有没有被简化到与源节不一致 |

案例（Round 03）："内存清单先于建表"在 §1.2/§2.8 被写成"页表页要在这份清单里领"，而 §2.6 的实际
机制分三层（`mem_high_phys` 硬依赖 / 链接期常量 / 后续 4KB 路径动态取页）——"结论对、解释不精确"
叠加跨章节重述失真。凡此类主张，修正时必须把依赖拆到具体一环，并让各处重述收敛到同一解释。

#### S1.6 运行阶段边界检查（v0.3 新增；操作系统文档通用装置）

对会改变系统状态或资源归属的操作，逐项列出操作前后各自成立的约束。检查对象至少包括：
`ExitBootServices`、切换地址空间（CR3/satp/TTBR）、开启分页/MMU、跨镜像跳转、分配器注册/换手、
内存归还与回收。四问：

| 问题 | 案例（Round 03） |
|---|---|
| 此阶段之后，哪些 API / 协议失效？ | EBS 之后仍调 `uefi::println!`（ConOut 是 Boot Services 协议）——源码级违规，修复并同步文档 |
| 取得数据快照后，是否又有操作会使它失效？ | `build_memmaps()` 的列表存储在快照之后从同一池分配——证明安全性并记录不变量（内核入口先深拷） |
| 数据的所有权是否已变化？ | 跨镜像交接载荷、页表页池换手——交接后谁负责回收 |
| 后续机制真正依赖的输入是什么？ | `pg_identity()` 依赖 `mem_high_phys`；动态取页依赖记录——把"依赖"拆到具体一环 |

产出：一张"阶段 × 约束"表进轮次包 §5；凡发现**阶段越界**（后阶段还在用前阶段已失效的设施/数据）
按 P0 处置；源码侧越界（如未过 EBS 的调用）同样按 P0 修复或登记，不得只改文案。

### S2 结构审阅与编辑审计（v0.2：结构审阅升为 S2 的第一件事）

#### S2.0 结构审阅（独立还原论证结构；G-A 门的一部分）

在执行任何编辑之前，**先独立还原文章的教学论证结构**，回答五个问题（结论进轮次包 §5）：

1. 文章整体的教学路径是否合理，为什么？（读者从哪来、到哪去、靠什么走通）
2. 各章是否承担了不同且必要的职责？（四章边界：概述=机制 / C 源码=事实 / 设计=判断 / 实现=落地）
3. 有无前提出现过晚、跨章节依赖倒置（后文才讲的前提被前文论证依赖）、过早引入实现细节、
   局部范围越界（出了本章声明的射程而未声明）？
4. 哪些重复是有意的教学收束（结论重复、任务不同），哪些是无新增信息的重复（整段推理重复）？
5. 每个具体结构问题应修正文档，还是需要新增通用 workflow 规则？

审阅者（编排者）先提交自己的结构判断；第三方（GPT / 独立 agent）的结构审阅独立进行（见 S4.5），
两者结论都进包——**不得用六维自评、盲测或 CodeReview 替代这一项**。

#### S2.1 读者路径表与决策卡

1. **读者路径表**：逐节填「本节回答什么问题 / 依赖前文什么 / 为后文提供什么」；
   标出前提晚于需要（倒置）与跨章重复职责。
2. **决策卡（审计版，设计章）**：对每个设计决策核对八字段是否可寻——原始事实 / 新约束 /
   决策问题 / 候选方案 / 选择与理由 / 代价与边界 / 实现落点 / 可迁移原则；缺什么补什么，不硬套模板。
3. **逐段标注**：每段标 保留 / 压缩 / 移位 / 重写 + 理由 + 命中规则编号；产出审计表。判据：
   - 保留：核心推理或必要证据；删了读者会失去机制、因果链、设计理由或可验证结论。
   - 压缩：同一结论反复解释、措辞过密、无新增信息的过渡句。（保护对象是教学功能与关键承载物，
     **不是包裹它们的每一句解释**——源码片段的重复说明、同义过渡、复述式收尾都可压缩，见 C1。）
   - 移位：内容有价值但属于其他章节（设计章里的实现细节、实现章里的设计辩论、附录级排障细节）。
   - 重写：概念堆叠、主语动作不清、顺序不合读者理解路径。
4. **四位置职责检查（E6）**：概念讲解 / 章节小结 / 下章开头 / 跨章总表——同一结论出现多次时，
   每次必须承担不同任务（允许重复结论，不允许重复整段推理）。
5. **卡点预演（预审版）**：编排者自问「读者在此会卡在哪」，列候选卡点清单，供 S4 盲测对照。
6. **小节职责漂移检查（v0.3 新增）**：为每个小节留一条很短的定位记录——「本节主问题 / 回答它
   必需的材料 / 哪些是必要前提或下游延伸」。材料不再服务主问题的即漂移：能移的移位；留在本篇的
   下游内容必须**显式标为扩展**（独立子节标题，或"下游延伸"声明），避免读者把它当主路径。
   案例（Round 03）：§2.1 的 panic/reset 机制（归 Ch6）→ 收成结论 + 回指；§2.4/§2.6 的消费者
   材料 → 独立子节分组。
   两处机械对账（v0.3 追加，Round 03 冷读教训）：① **读者面声明清单 ↔ 正文自称集合**——凡
   "本篇边界/例外/归别篇"的清单，必须与正文里自称"下游/例外/范围外"的小节做集合校验，并随
   重编号同步；② **回指不得承载被删结论**——删内容改成"归 §X"时，必须核对 §X 处真的包含被删的
   结论（案例：Round 03 的 §2.1→§6.3 回指，而目标行本身是错的、旧错被回指曝光）。

### S3 改写执行

1. 按审计表执行；逐条记录改动台账（节号 / 类型 / 命中规则 / 一句话理由）——S5 的 diff 标注与统计直接取用。
2. 纪律：E 系列（编辑）+ C 系列（承载保护）+ L 系列（语言）+ §七 反模式清单。
3. **结构改动按 E7 三级执行**（见 §四）；章节内部顺序调整须记录：原顺序的问题、移动后的收益、
   对交叉引用的影响。
4. 反事实段按 F1+C2 逐段过；过不了的删，不改成「委婉版」。

### S4 分项验收

1. **V2 盲测学生**（固定装置；v0.2 增加目标映射与缺口三分）：
   - 闭卷：新读者 agent 只读目标文档，不读源码与其他文档。
   - **学习目标映射**：每题标注「对应哪个学习目标 / 希望读者能推导出什么 / 哪些内容明确不要求掌握」。
   - 题组：8~11 题，全部要求沿机制链推理（不是背事实）；覆盖主路径与关键边界。
   - 卡点清单：逐节记录「我在哪里卡住 / 回读 / 需要外部知识」。
   - 整段复述：抽 2~3 个核心机制段，学生用自己的话复述。
   - **缺口三分**（判定纪律，见 §九 G-A）：① 文档教学缺口——读者理解本篇核心机制确实需要这部分
     解释 → 必须补讲解，或明确写出"目前为何尚未解释"；② 证据缺口——事实/机制尚无可靠依据 →
     登记待核实，不得用措辞包装成已解决；③ 真范围外——**教学目标明确排除**的内容，记录理由后可
     不计入教学失败。**只有第③类才算"范围外"**；不得因"当前引用范围里找不到解释"就把读者疑问
     排除在评分外。
2. **V3 CodeReview**：独立 agent 核查文档断言 vs C 源 / Rust 代码；分级 P0/P1/P2；附命令与输出证据。
   重点关注：本轮改动区域、S1 标为"可复现命令/源码引用块"的条目、以及现行源码近期演进过的函数。
   （同 agent 验证局限与跨工具复核纪律按 review 规则集的既有要求执行。）
3. **V5 独立结构审阅**（v0.2 新增；v0.3 明确**分阶段冷读**）：独立 agent 按三段进行——
   ① 冷读：只凭新版正文记录读者会遇到的因果断裂、职责重叠、表达问题；② 再看 diff，区分
   "旧问题"与"本轮引入"；③ 最后才看规则与过程读数，判断为什么没发现（或发现了）。不得先看
   diff 与过程读数，以免被作者自评带偏；结论与编排者的 S2.0 结论并列进包。
4. **V1 六维自评**：编排者按 §六 逐维给证据（供包 §5 与 GPT 对照）。
5. **V4 五门**：anchor-resolve / doc-code-map / doc-style-lint / doc-ref-check / doc-code-density 全绿。
6. 修复批次 → 复跑至 §九 收敛判据。**首次检查结果与最终验收结果分开保存**（见 §八 发现阶段字段）。

### S5 打包与提交

按 §五 模板装配 `tmp/doc-iter/<doc-slug>/round-NN.md`；更新 `tmp/doc-iter/LEDGER.md` 与
入库台账 `rewrite-notes/coordination/DOC-ITER-LEDGER.md`（最小可恢复记录）。

提交纪律（仓库可能同时有其它会话的改动在制——并发现场）：

- 只按具名路径 `git add` 本轮涉及的文件（目标文档、本规格文件、入库台账；包与过程产物在 tmp/ 不入库）；
- 结构重排牵动**其他文档**的交叉引用时，被牵动的文档一并列入具名路径（改动限于引用编号本身）；
- 提交前 `git status --short` 核对，不碰与本轮无关的在制文件；
- 禁 `git add -A` / `git commit -a`；commit message 记录轮次号、workflow 版本、包路径。

**发布前扫描（v0.3 新增）**：提交前对目标文档跑一遍残留扫描——编辑标签、占位符、错字、失效交叉
引用、未闭合的文稿标记；另加两项机械检查：**同句重复**（同节/相邻的长句逐字重复）与**位置指称
有落点**（"第 N 行注释""上面的注释"等指称在节选块内是否真的存在）。可复用
`tools/doc-style-lint.sh` 加一份人工清单。注意：`[ARCH: ...]`是项目硬规则要求的**三处一致性标注**
（doc + design + code），不属于编辑残留——扫描时按"标注是否存在、是否与 design/code 对应"处理，
不按"清除"处理。

**台账重放（v0.3 追加）**：修复台账里每条"已修"必须带一条可重放的验证命令（grep 命中新文本），
终审时逐条重放——防"台账记了、正文没改"（Round 03 实例：两条 Round 02 修复记了台账但正文
未落地，靠下一轮冷读的交叉引用才发现）。

## 六、验收标准（固定六维，每轮相同）

| 维度 | 判据 |
|---|---|
| 教学完整性 | 机制、因果链、设计理由讲透；没有「只有结论没有推导」处；未因精简退回大纲 |
| 语言清晰度 | 读者能自然理解谁做了什么、为什么、结果如何；无名词堆叠、无审计腔模板句 |
| 信息密度 | 无重复解释、无空泛过渡；重复出现的结论每次承担新任务 |
| 阅读路径 | 前提先于需要；节间依赖顺读者理解顺序；无职责倒置 |
| 章节职责 | 四章边界（概述=机制、C 源码=事实、设计决策=判断、实现=落地）不被混淆 |
| 技术准确性 | 结论有源码依据；改写未损失事实与关键约束 |

**硬规则**：技术准确性与教学完整性不得由语言流畅度抵偿（更短更自然但丢了推理链 ≠ 改进；
更详细但重复三次同一结论 ≠ 完美）。

## 七、反模式清单（违反即退回）

1. 不以缩短篇幅为目标；篇幅由教学内容决定（E5）。
2. 不删教学承载物（C1）；「可引用」≠「不必解释」（E8）。
3. 不复述已讲结论（E3）；不机械复用论证模板（审计腔）。
4. 反事实不仪式化：只在证明关键不变量、解释非显然故障或澄清边界时展开（C2），且先证伪前提（F1）。
5. 不以「更优叙事」重构章节教学架构（E7①）；章节内部顺序调整必须按 E7② 留痕。
6. 不全局替换直译词（L1 逐处词义分流）。
7. 不用套路句当反事实默认标签（W-8：引导句必须点明本段真正改动的对象）。
8. **不以「范围外」回避缺口**（v0.2）：只有教学目标明确排除的疑问可判范围外；教学缺口要补、
   证据缺口要登记待核实——不得因为「当前引用里找不到依据」就把读者疑问排除在评分之外。
9. **不用六维自评、盲测或 CodeReview 替代独立结构审阅**（v0.2；S2.0/V5 是固定步骤）。

## 八、归因与 workflow 演化（元循环 ①；v0.2 起每轮必填）

每轮结束后、写回规则之前，逐条填归因记录（不只写原则）：

| 字段 | 内容 |
|---|---|
| 本轮发现 | 审阅证据与具体问题（引用包内位置） |
| **首次发现阶段/发现者** | 如「文档自审未发现 → 盲测发现 → 修复 → 复测通过」或「五门通过 → CodeReview 发现」 |
| 根因判断 | workflow 缺陷（规则覆盖不足 / 检测阶段缺口）/ 执行偏差 / 局部问题 / 事实错误 |
| 是否修改 workflow | 是 / 否 |
| 修改内容 | 新增、删除或调整了哪条规则（编号）或哪一步执行装置 |
| **规则状态** | 候选规则（已被真实案例支持，通用性未验证）/ 已验证规则（不同形态文档上重复有效，或有明确判据可直接验证） |
| **差异归因**（与独立审阅/冷读结论的差异） | 四类之一：① 从未被工作流识别；② 已识别但没有修对；③ 修复过、被后续改写重新引入；④ 被某个测试判为通过，但测试实际没测到该属性 |
| 预期效果 | 下一轮应该改善哪种问题 |
| 回归风险 | 这次修改可能损害什么已有优点 |

**裁决规则（防规则膨胀）**：只把「有证据 + 可推广」的项登记为**候选规则**；只在一处出现的建议
谨慎上升；新增规则必须证明改善超过额外复杂度；**除严重事实错误、明显安全问题或可确定的机械遗漏
外，不凭一篇文档把候选升级为全局纪律**——候选规则进入下一轮观察，跨篇复现后才升级为已验证规则；
用户对上升项有最终裁决权。

**每轮随记录一并报告两个统计**（比"改了多少行"更有参考价值）：
- **规则触发的实际改进数**：因某条规则/装置而发现并真实修掉的问题数；
- **发现但未定位根因的缺陷数**：报了问题但归因落到"待观察"的数量。

## 九、收敛与停止条件（v0.2：拆成三道理门）

**第一道理门 G-A · 文档可交付**（本轮产物能否交给下一环节）：

- 未解决的重大的事实错误为零（含过期读数、引文漂移、对账缺口的未决项）；
- 应修复的 P0/P1 已清理，或有明确、可审计的例外裁决（写明理由与证据）；
- 必需的检测装置均已完成（S1 证据盘点 / S2 结构审阅 / V1~V5）；
- 工具误报有证据与处置记录——不以「全绿」代替解释；
- 盲测缺口按 §四 V2 的三分处理：教学缺口已补（或写明未解释的原因）、证据缺口已登记、范围外有理由。

**第二道理门 G-B · 本轮是否真有改进**（与上一轮比较）：

- 各阶段发现了什么、首次发现出现在哪个阶段、修复后是否复现、是否损失了原有教学内容；
- **首次检查结果与最终验收结果分开保存**（G-B 读两份，不拿最终全绿掩盖首检表现）；
- 重复出现同类缺陷 = 上一轮修复无效或装置未生效的信号；
- 成本/发现量变化（沿用旧口径：本轮成本 > 上轮 80% 而加权新发现 < 上轮 20% = 参考信号）——
  仅作参考信号，不作机械停止开关（工作量、缺陷严重性与文档复杂度并不同步）。

**第三道理门 G-C · workflow 能否冻结**（跨篇判定）：

- 沿用「连续两轮（可跨篇）没有值得全局推广的新缺陷」原则，并增加三条判断：
  新出现的 P0 或重复同类缺陷 → 流程尚有值得调查的盲区；
  连续两轮 P1 很少 ≠ 成熟（可能两轮处理的是相似问题，须换形态验证）；
  只有在**不同形态的文档**上得到相近的质量结果、且无系统性回归，才能说明规则具有迁移性。

**内循环停止**：同篇 ≥5 轮强制换篇；首轮零发现触漏检自检（随机抽 3 项重跑）。
**外循环与冻结**：换篇检验规则可迁移性；按 G-C 判定冻结；再开新版本须有真实案例证明必要。
