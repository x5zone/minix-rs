# Minix-RS Review 卓越性检查

> 本 Skill 定义卓越性检查标准，追求"教科书级"文档和"redox 级"代码质量。
> **前置条件**：正确性 gate（doc/code/coverage/patterns）已通过。
> **详见**：[review-doc-excellence.md](../review-rules/review-doc-excellence.md) + [review-code-excellence.md](../review-rules/review-code-excellence.md)

---

## 卓越性 vs 正确性

| 维度 | 正确性（gate） | 卓越性（grade） |
|------|--------------|---------------|
| 目标 | 文档/代码不错 | 文档好读、好学、好维护；代码好读、好维护、好扩展 |
| 判定 | P0/P1/P2 | 卓越性 P1/P2（不降级为正确性 P1） |
| 时机 | 先执行 | 正确性通过后执行 |
| 修复 | 必须修复 | 建议修复 |

**⛔ 卓越性问题不降级为正确性问题。卓越性 P1 是"可以更好"，正确性 P1 是"必须修复"。**

## 一、文档卓越性（§4.1-§4.4）

### §2.0 架构演进作为独立知识点维度

> 配合 [review.md §2.0 架构演进](../review-rules/review.md) 使用。

**架构演进 5 类型**（必须在文档中显式标注）：
1. **FPU 上下文处理演进**（如 `FpuState` newtype 替代裸 `u32`）
2. **中断/异常处理演进**（如 APIC trait 抽象 PIC）
3. **分页模型演进**（2→4 级页表）
4. **地址空间布局演进**（32→64 位，KERNEL_BASE 等常量）
5. **启动链演进**（多架构启动路径统一抽象）

**降级条件**：
- 演进未标注 → P0-design-wrong 或 P0-doc-deviation
- 演进标注但未论证 → P1

### §4.1 叙事结构卓越性

**检查项**：叙事弧完整 / 动机说明 / 逻辑过渡 / 层次清晰 / 主题聚焦 / 概念骨架可见性 / 统一抽象先行 / 双向闭环

**Execute**:
1. 阅读文档目录结构，检查叙事弧：Ch1 提出问题？Ch2 分析现状？Ch3 设计决策？Ch4 实现？测试验证？
2. 检查每章开头是否有动机段落（"本章解决什么问题"）
3. 检查章节间是否有过渡（"上一章分析了 X，本章将设计 Y"）
4. **概念骨架可见性检查**（新增）：Ch1 是否有显式核心框架（如"CPU 三问"）？章末是否用同框架收束？后续章节是否引用该框架？
5. **统一抽象先行检查**：多架构文档是否先给统一框架再分架构展开？
6. **双向闭环检查**：进入类机制（trap/syscall/IPC）是否同时覆盖"进入"和"返回"？

**Output**:
| 章节 | 叙事弧完整? | 动机说明? | 逻辑过渡? | 层次清晰? | 主题聚焦? | 概念骨架? | 统一抽象? | 双向闭环? | Issue |
|------|------------|----------|----------|----------|----------|----------|----------|----------|-------|

**标准**：
- **A（优秀）**：叙事弧完整，每章有动机，过渡自然，Ch1 有显式概念骨架且后续章节引用
- **B（良好）**：叙事弧基本完整，多数章节有动机，Ch1 有概念骨架但后续未充分引用
- **C（合格）**：叙事弧有缺失，但可读，Ch1 无显式概念骨架
- **D（不合格）**：堆砌式，无叙事弧，无概念骨架

### §4.2 读者体验卓越性

**检查项**：目标读者明确 / 术语定义 / 复杂概念图解 / 前置知识声明 / 导航辅助 / 可读性

**Execute**:
1. 检查文档开头是否声明目标读者和前置知识
2. 提取所有粗体术语，检查首次出现是否有定义：`rg "\*\*[A-Z_]+\*\*" FILE.md -n`
3. 检查复杂概念是否有图解或类比

**Output**:
| 位置 | 读者体验问题 | 卓越性 P? | Suggested Fix |
|------|------------|----------|---------------|

### §4.3 教学深度卓越性

**检查项**：设计取舍 / 边界情况 / 失败模式 / 系统图景 / 可运行示例 / 历史背景

**Execute**:
1. 检查 Ch3 设计决策是否有"替代方案"段落
2. 检查 Ch2 是否讨论了 C 代码的边界情况
3. 检查 Ch3 是否讨论了设计决策的失败模式
4. 检查文档是否连接到更大的系统图景
5. 检查 Ch4 是否有可运行的代码示例

#### §4.3.5 Design 视角的教学深度

> 配合 [review-doc-excellence.md §4.3.5](../review-rules/review-doc-excellence.md) 使用。

**检查项**：
1. **决策依据**：每个设计决策是否有 design doc 引用？（或引用 Minix3 源码？）
2. **本质表达**：是否先讲"为什么这样设计"再讲"怎么实现"？
3. **取舍揭示**：是否说明替代方案及拒绝理由？
4. **架构演进标记**：对 Minix3 行为的偏离是否标注 ARCH？

**降级条件**：
- 决策无依据（无论证、无论文）→ P1
- 先讲实现后讲概念（实现驱动）→ P1（模式 51）
- 取舍缺失 → P1
- ARCH 未标注 → P0（Claims-Evidence）

**Output**:
| 位置 | 教学深度问题 | 卓越性 P? | Suggested Fix |
|------|------------|----------|---------------|

### §4.4 可维护性卓越性

**检查项**：变更日志 / TODO 标记 / 外部引用 / 一致性

**Execute**:
1. 检查是否有变更日志段落
2. 检查 TODO 标记：`rg "TODO|FIXME|XXX" FILE.md -n`
3. 检查外部引用是否有链接
4. 检查术语和命名的一致性

**Output**:
| 位置 | 可维护性问题 | 卓越性 P? | Suggested Fix |
|------|------------|----------|---------------|

#### §4.4 补充: 文档组织合理性检查矩阵

> 配合 [review-doc-excellence.md §4.4](../review-rules/review-doc-excellence.md) 使用。

**13 项组织检查**（每项独立判定）：

| # | 检查项 | 判定 |
|---|--------|------|
| 1 | 核心概念完整性 | 是否覆盖模块所有核心概念？ |
| 2 | Ch1&2/Ch3&4 平衡 | 概念章与实现章比例是否合理（理想 3:7 或 4:6）？ |
| 3 | 设计决策集中度 | Ch3 设计决策是否集中而非散落？ |
| 4 | 章节依赖单向性 | 后置章节是否只依赖前置章节？ |
| 5 | 文档拆分判定 | 单章 >500 行是否应拆分？ |
| 6 | 跨文档引用一致性 | 同名概念在不同 doc 描述是否一致？ |
| 7 | 索引完整性 | 有无目录或索引？ |
| 8 | 术语首次定义 | 术语首次出现位置是否给出定义？ |
| 9 | 摘要/总结 | Ch1/Ch4 是否有摘要？ |
| 10 | 代码示例最小化 | 示例是否引入无关细节？ |
| 11 | 引用 Minix3 源码 | 是否标注 `FILE.c:LINE` 证据？ |
| 12 | Design 引用 | 设计决策是否引用 `06-design.md`（非 bagging）/ `06-design-final.md`（bagging）等？ |
| 13 | 架构演进标注 | 演进是否标注 ARCH？ |

**章节拆分判定阈值**：
- 单章 >500 行 → 强烈建议拆分
- 单章 >300 行且有 2 个独立主题 → 建议拆分
- 章节 H1 数 > 7 → 考虑拆分为独立 doc

**章节结构模板**：
```
1. 动机（本章解决什么问题）
2. 核心概念（先讲"为什么"再讲"是什么"）
3. 设计决策（取舍 + 替代方案 + 拒绝理由）
4. 实现要点（伪代码 / 代码片段）
5. 验证 / 测试
6. 与其他模块的关系
7. 本章未讲什么（预期管理）
```

### §4.5 概念教学卓越性（Ch1 专项）

> **前置条件**：[review-doc-checklist.md §1.Ch1](../skill/review-doc-skill.md) 概念驱动检查已通过。
> **背景**：Ch1 是概念章，需要专门评估其教学卓越性，而非仅评估正确性。03-kmain-cstart 案例暴露的"每个 claim 都对但整体叙事失败"是典型问题。

**检查项**（6 项 + 卓越性标准）：

| # | 检查项 | 说明 | Evidence 级别 |
|---|--------|------|-------------|
| 1 | **CPU/系统视角**（非 OS 代码角度） | Ch1 从 CPU/系统视角组织，而非从 OS 代码/函数名角度 | [MEDIUM] |
| 2 | **统一抽象先于分架构实现** | 多架构文档先给统一框架（如"CPU 三问"）再分架构展开 | [MEDIUM] |
| 3 | **心智模型完整**（双向机制两方向都覆盖） | 进入类机制（trap/syscall/IPC）覆盖"进入"+"返回" | [DIRECT] |
| 4 | **认知负荷**（新概念不引入不必要额外问题） | 示例最小化，不引入与核心机制无关的细节 | [MEDIUM] |
| 5 | **预期管理**（"本章不讲什么"显式声明） | Ch1 声明边界，列出延后到后续章节的细节 | [DIRECT] |
| 6 | **概念收束**（章末用框架收束，预告后续） | Ch1 章末用核心框架收束并预告后续章节 | [MEDIUM] |

**Execute**:
1. 抽取 Ch1 开篇第一句，判定主语是 CPU/系统 还是 OS 代码/函数名。后者 → 降级。
2. 检查多架构内容是否有统一抽象层先行。无 → 降级。
3. 检查进入类机制（trap/syscall/IPC）是否双向闭环。只单向 → 降级。
4. 检查 Ch1 示例是否最小化（不引入额外问题）。违反 → 降级。
5. 检查 Ch1 是否有"本章不讲什么"声明。无 → 降级。
6. 检查 Ch1 章末是否用核心框架收束并预告后续。无 → 降级。

**Output**:
| # | 检查项 | 判定 (✅/降级) | 证据 (file:line) | Issue |
|---|--------|--------------|------------------|-------|
| 1 | CPU/系统视角 | | | |
| 2 | 统一抽象先行 | | | |
| 3 | 心智模型完整（双向） | | | |
| 4 | 认知负荷（示例最小化） | | | |
| 5 | 预期管理（本章不讲什么） | | | |
| 6 | 概念收束（章末框架收束） | | | |

**卓越性标准**：
- **A（优秀）**：CPU 视角 + 统一框架 + 心智完整 + 预期管理 + 框架收束
- **B（良好）**：概念驱动 + 统一抽象 + 心智基本完整
- **C（合格）**：概念驱动但缺统一抽象或心智不完整
- **D（不合格）**：实现驱动（Ch1 主语是函数名/结构体名/trait 名）

**关联模式**（与 [review-patterns-skill.md 模式 51-53、55-57](../skill/review-patterns-skill.md) 对应）：
- 模式 51 实现驱动概念章 ↔ 检查项 1（CPU/系统视角）
- 模式 52 单向心智模型 ↔ 检查项 3（双向闭环）
- 模式 53 跨架构共性未提取 ↔ 检查项 2（统一抽象先行）
- 模式 55 架构特有机制喧宾夺主 ↔ 检查项 4（认知负荷）
- 模式 57 例子前置知识泄漏 ↔ 检查项 4（认知负荷）

## 二、代码卓越性（§15-20）

### §15.5 design-first API 设计原则

> 配合 [review-code-excellence.md §15.5](../review-rules/review-code-excellence.md) 使用。

**6 维度检查**：
1. **命名**：是否与 design doc 一致？是否有"我用了更合理的命名"现象？
2. **参数**：是否严格匹配 design 中的 trait 方法签名？
3. **错误**：Error 变体是否与 design 中的错误码策略一致？
4. **可见性**：pub 接口是否与 design 中的"公共 API"列表一致？
5. **unsafe**：unsafe 边界是否与 design 中的安全论证一致？
6. **trait**：trait 方法是否与 design 中的 trait 抽象一致？

**降级条件**：
- 命名偏离 design 无显式标注 → P0-design-deviation
- 错误变体与 design 不一致 → P0-core-semantics
- unsafe 边界超出 design 论证 → P0-safety

### §15 API 设计卓越性

**检查项**：难以误用 / Rust 惯用法 / 错误类型精确 / 层次清晰 / 最小接口

**Execute**:
1. 检查 API 是否难以误用（无效状态可表达？调用顺序依赖未用 typestate？）
2. 检查错误类型：`rg "Box<dyn Error|Box<dyn std::error::Error>" FILE.rs -n` → 滥用 = 卓越性 P1
3. 检查 API 层次（low/mid/high level）
4. 检查 pub 接口是否最小化

**Output**:
| 位置 | API 设计问题 | 卓越性 P? | Suggested Fix |
|------|------------|----------|---------------|

### §16 表达力卓越性

**检查项**：类型系统利用 / 编译时保证 / 命名表达意图 / 迭代器组合子 / 模式匹配

**Execute**:
1. 检查 newtype：`rg "struct \w+\(\w+\);" FILE.rs -n` → 裸整数应有 newtype
2. 检查运行时检查可否改为编译时：`rg "if.*== 0|if.*is_none|panic!" FILE.rs -n`
3. 检查显式循环：`rg "for .* in |while " FILE.rs -n` → 可用迭代器替代 = 卓越性 P2
4. 检查 if-else 链：`rg "else if" FILE.rs -n` → 可用 match 替代 = 卓越性 P2

**Output**:
| 位置 | 表达力问题 | 卓越性 P? | Suggested Fix |
|------|----------|----------|---------------|

### §17 性能卓越性

**检查项**：无不必要分配 / 零成本抽象 / 热路径无抽象 / 缓存友好 / 批量操作

**Execute**:
1. 检查热路径分配：`rg "Vec::new|Box::new|String::from" FILE.rs -n` → 热路径中 = 卓越性 P1
2. 检查动态分派：`rg "dyn " FILE.rs -n` → 热路径中 = 卓越性 P2
3. 检查逐个操作：`rg "for .* in .*\.iter\(\)" FILE.rs -n` → 可批量化 = 卓越性 P2

**Output**:
| 位置 | 性能问题 | 卓越性 P? | Suggested Fix |
|------|---------|----------|---------------|

**⚠️ 性能优化必须论证，不能泄漏硬件细节。**

### §18 代码即文档卓越性

**检查项**：自解释 / 注释解释为什么 / 无冗余注释 / 模块文档 / 使用示例

**Execute**:
1. 检查模块文档：`rg "^//!" FILE.rs -n` → 无模块文档 = 卓越性 P1
2. 检查"是什么"注释（冗余）：`rg "// .* = |// .* is |// .* the " FILE.rs -n`
3. 检查 doctest：`rg "/// ```" FILE.rs -n` → pub 函数无 doctest = 卓越性 P2
4. 检查命名是否表达意图

**Output**:
| 位置 | 代码即文档问题 | 卓越性 P? | Suggested Fix |
|------|-------------|----------|---------------|

### §19 可测试性卓越性

**检查项**：依赖注入 / 纯函数 / 副作用显式 / 不变量测试 / Property-based

**Execute**:
1. 检查全局依赖：`rg "static|lazy_static|OnceCell" FILE.rs -n` → 可注入的依赖用全局 = 卓越性 P1
2. 检查副作用隐藏：`rg "fn .*-> .* \{" FILE.rs -n` → 返回值函数不应有隐藏副作用 = 卓越性 P1
3. 检查测试是否覆盖不变量

**Output**:
| 位置 | 可测试性问题 | 卓越性 P? | Suggested Fix |
|------|------------|----------|---------------|

### §20 测试质量卓越性

**测试三重标准**：
| 级别 | 类型 | 说明 |
|------|------|------|
| L1 | C-Rust 对偶测试 | 验证 Rust 实现与 C 行为一致 |
| L2 | Trait 契约测试 | 验证 trait 实现满足契约 |
| L3 | doctest | 文档中的代码示例可运行 |

**Execute**:
1. 统计测试数：`rg "#\[test\]" FILE.rs -n | wc -l`
2. 检查 L1 对偶测试：`rg "fn test_.*c_rust|fn test_.*parity|fn test_.*dual" FILE.rs -n`
3. 检查 L2 契约测试：`rg "fn test_.*contract|fn test_.*trait" FILE.rs -n`
4. 检查 L3 doctest：`rg "/// ```" FILE.rs -n`
5. 检查测试命名：`rg "fn test_\w+" FILE.rs -n` → `test_it_works` = 卓越性 P2

**Output**:
| 位置 | 测试质量问题 | 卓越性 P? | Suggested Fix |
|------|------------|----------|---------------|

**测试覆盖统计**:
| 核心函数 | L1 对偶 | L2 契约 | L3 doctest | 总覆盖 |
|---------|---------|---------|-----------|--------|

---

## Pass condition

- 文档卓越性：§4.1-4.4 至少 B 级
- 代码卓越性：§15-20 至少 B 级
- 测试三重标准：核心函数至少 L1/L2/L3 一项覆盖

**⛔ 卓越性问题不阻塞 Review 收敛。但应在 FINDINGS.md 中记录，供后续改进。**
