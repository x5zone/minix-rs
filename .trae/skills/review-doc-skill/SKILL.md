# Minix-RS 文档 Review 检查清单

## 1. 文档结构规范

每篇文档应遵循以下结构：

```
# XX-title: 标题
> **分类**: 模块库 / 模块私有 / 全局基建
> **源码**: `minix3/minix/servers/模块/xxx.c`
> **说明**: 一句话功能描述
---

## 1. 概述
### 1.1 概念定义/作用
### 1.2 与 Minix3 的对应关系
### 1.3 关键状态/机制说明
### 1.4 行为规则

## 2. C 源码分析
### 2.1 相关定义（常量、调用号、配置等）
### 2.2 核心数据结构
### 2.3 关键函数分析
### 2.4 调用关系/调用点分析
### 2.5 设计要点/特殊处理

## 3. Rust 设计决策
> 高层设计选择，解释"为什么这样设计"

## 4. 实现详解
> Rust 实现的具体展开，解释"如何实现"

## N. 测试要点（倒数第二章）
## N+1. 参见（最后一章）
```

**关键约束**：第1/2章不得含 Rust；Ch3 聚焦"为什么"且可追溯 Ch1&2；Ch4 聚焦"怎么做"且对应 Ch3；测试章基于 Ch3+Ch4；C 源码分析完整覆盖所有核心数据结构/关键函数/调用关系；Ch3 有更好替代方案应写 TODO。

---

## 2. 文档 Review 维度

### 2.1 概念准确性检查（强制，不可跳过）

> 禁止虚构、禁止幻觉、以 Minix3 源码为唯一真理来源。

**执行步骤**：
1. 从 Ch1 提取加粗术语/类型名/关键名词，从 Ch2 提取结构体/函数/宏名，汇总为「核心概念清单」
2. 逐概念 grep 验证：`rg "CONCEPT" minix3/minix/servers/{module}/ --type c -n` + kernel/ + include/
3. 数值常量验证：`rg "#define CONSTANT" minix3/minix/servers/{module}/ -n`
4. 算法描述验证：读 C 函数源码，逐行对比算法行为

**必须输出**：
```markdown
### 2.1 概念准确性验证结果

| 概念/术语 | 文档位置 | grep 结果 | 源码行号 | 一致性 | 问题 |
|----------|---------|----------|---------|--------|------|

**数值常量验证**：
| 常量 | 文档值 | 源码值 | 源码位置 | 一致? |

**算法描述验证**：
| 算法 | 文档描述 | 源码行为 | 一致? |
```

**判定**：概念在源码中找不到→P0 虚构概念；解释与源码不一致→P0 概念错误；数值不一致→P0 数据错误；算法不一致→P0 行为错误。

### 2.2 C 代码引用验证（强制，不可跳过）

> 引用的代码必须正确，讲解必须准确。

**执行步骤**：
1. 提取文档中所有 C 代码引用（文件路径+行号）
2. 逐引用验证：文件是否存在、行号是否准确、片段是否完整
3. 检查路径格式：禁止 `file:///home/user/...` 绝对路径
4. 对比文档讲解与源码实际行为

**必须输出**：
```markdown
### 2.2 C 代码引用验证结果

| 引用位置 | 文件路径 | 行号 | 文件存在? | 行号准确? | 片段完整? | 讲解一致? | 路径格式? | 问题 |
|---------|---------|------|----------|----------|----------|----------|----------|------|
```

**判定**：文件不存在→P0；行号偏差超5行→P1；片段截断改语义→P0；讲解与源码不一致→P0；过度解读→P1；绝对路径→P1。

### 2.3 数据结构覆盖完整性（强制，不可跳过）

**执行步骤**：
1. 从 Ch2 提取所有分析的结构体名称
2. grep 提取 C 源码结构体：`rg "^struct \w+" minix3/minix/servers/{module}/ --type c -n`
3. 逐结构体对比字段覆盖

**必须输出**：
```markdown
### 2.3 数据结构覆盖验证结果

| 结构体 | 源码位置 | 总字段数 | 文档覆盖字段数 | 遗漏字段 | 判定 |
|--------|---------|---------|--------------|---------|------|
```

**判定**：核心结构体完全未分析→P0；遗漏关键字段→P1；非核心遗漏→P2。

### 2.4 文档与代码一致性

- [ ] Rust 函数签名/参数类型/返回值是否与真实代码一致？
- [ ] 文档描述的行为与代码实现是否一致？示例代码是否可编译？

### 2.5 架构演进说明

- [ ] 32位 vs 64位差异是否标注？是否解释演进理由？

| 方面 | Minix3 (32位) | minix-rs (64位) | 说明 |
|------|---------------|-----------------|------|
| 页表层级 | 2级(PD+PT) | 4级(PML4+PDPT+PD+PT) | 64位需要更多层级 |
| 页表项大小 | u32 | u64 | 支持更大物理地址 |
| 地址划分 | 10+10+12 | 9+9+9+9+12 | 64位地址空间 |
| 页表指针 | pt_pt[1024] | 动态分配 | 64位无法预分配 |

### 2.6 文档间交叉引用

- [ ] "参见"章节是否完整？引用路径是否正确？

### 2.7 图表与可视化质量

- [ ] 必要性：能否用文字说清？对齐精度：严格对齐？可维护性：过于复杂？
- **判定**：能文字说清别画图；图必须严格对齐；复杂图拆分为多个简单图

### 2.8 C 源码覆盖完整性检查（强制，不可跳过）

> 语义范围内的 C 源码（函数+数据结构+宏）必须被完整覆盖。

**执行步骤**：
1. 从标题和 Ch1 提取语义范围（一句话）
2. 列出模块所有 C 源文件：`ls minix3/minix/servers/{module}/*.c *.h`
3. 提取所有 C 符号：
   - 函数：`rg "^[a-z_].*\w+\(.*\)\s*$" minix3/minix/servers/{module}/FILE.c -n`
   - 结构体：`rg "^struct \w+" minix3/minix/servers/{module}/FILE.h -n`
   - 宏（行为宏+标志位宏）：`rg "^#define \w+" minix3/minix/servers/{module}/FILE.h -n`
4. 语义归属判定+覆盖检查

**必须输出**：
```markdown
### 2.8 C 源码覆盖完整性验证结果

**语义范围**：[一句话]

| 符号 | 类型 | 源码位置 | 在语义范围内? | 文档覆盖? | 文档位置 | 判定 |
|------|------|---------|-------------|-----------|---------|------|

**覆盖统计**：总符号数 N / 已覆盖 M / 覆盖率 M/N%
```

**宏分类**：常量宏（`#define PAGE_SIZE 4096`）在 §2.1 数值验证中覆盖；行为宏（含判断逻辑）、标志位宏（定义标志位）、条件编译宏（影响代码路径）必须在表格中列出。

**判定**：核心函数未覆盖→P0；核心结构体未覆盖→P0；行为宏/标志位宏未覆盖→P1；覆盖率<80%→整体 P0。

### 2.9 设计决策质量检查（Ch3 专项，强制）

> Review 必须检查"设计好不好"，而非仅"写得对不对"。

**执行步骤**：
1. 提取 Ch3 所有设计决策：`rg "^###|^####" {doc} | grep -E "3\.|设计决策"`
2. 逐决策验证可追溯性（在 Ch1&2 搜索依据）
3. 验证场景覆盖（Ch2 的每个错误场景 Ch3 是否有对应设计）
4. 验证 no_std 兼容性

**必须输出**：
```markdown
### 2.9 设计决策质量验证结果

| 设计决策 | Ch3 | Ch1&2依据 | 可追溯? | 场景覆盖? | no_std? | 替代方案? | 判定 |
|---------|-----|----------|---------|----------|---------|----------|------|

**错误路径覆盖检查**：
| Ch2 错误场景 | Ch2 位置 | Ch3 是否有对应设计? | 判定 |
|-------------|---------|-------------------|------|
```

**判定**：设计无 Ch1&2 依据→P1；遗漏 Ch2 错误场景→P0；更好替代方案未记录→P1（应写 TODO）；依赖 `std`→P0。

### 2.10 章节链路验证（强制）

> 链路断裂=设计或实现有问题。

**执行步骤**：
1. Ch3→Ch1&2 追溯：每个决策在 Ch1/Ch2 是否有依据
2. Ch4→Ch3 追溯：每个实现是否对应 Ch3 决策
3. 测试→Ch3+Ch4 追溯：每个测试要点是否覆盖设计/实现
4. 代码→Ch4 一致性：Rust 代码是否匹配 Ch4 描述

**必须输出**：
```markdown
### 2.10 章节链路验证

**Ch3→Ch1&2**：
| Ch3 设计决策 | Ch3 位置 | Ch1&2 依据 | 链路状态 |

**Ch4→Ch3**：
| Ch4 实现 | Ch4 位置 | Ch3 设计依据 | 链路状态 |

**测试→Ch3+Ch4**：
| 测试要点 | 位置 | 覆盖的设计/实现 | 链路状态 |

**代码→Ch4**（如适用）：
| Ch4 描述 | Ch4 位置 | 代码位置 | 一致? |

**链路总结**：Ch3→Ch1&2：✅全部 / ❌N处断裂；Ch4→Ch3：✅全部 / ❌N处断裂；测试→Ch3+Ch4：✅全部 / ❌N处缺失；代码→Ch4：✅一致 / ❌N处不一致
```

**判定**：Ch3 引入 Ch1&2 未提及概念→P1；Ch4 实现 Ch3 未设计功能→P1；Ch3 设计 Ch4 未实现→P1；测试未覆盖关键决策→P1；代码与 Ch4 不一致→P1。

### 2.11 文档风格检查：面向读者知识讲解（强制）

> 文档面向读者讲解系统行为，不是开发进度追踪表。

**执行步骤**：
```bash
rg "已实现|待实现|未实现|WIP" {doc} -n
rg "[✅❌🚧⏳🔧]" {doc} -n
rg "^#+\s*(实现清单|代码状态|现有代码|进度|开发记录|完成情况)" {doc} -n
```

**必须输出**：
```markdown
### 2.11 文档风格验证结果

| 问题文本 | 位置 | 问题类型 | 建议改写 |
|---------|------|---------|---------|
```

**禁止**（TODO 允许保留，TODO 标记待做事项与进度标记不同）：

| 禁止 | 推荐 |
|------|------|
| "已实现：X" / "待实现：Z" / "未实现：W" | "X 函数负责 Y" / "Z 功能处理 W 场景" |
| ✅❌🚧 状态 emoji | 去掉状态标记，纯文字描述 |
| "实现清单""代码状态"等进度标题 | "模块组成与测试""组件一览" |
| 按完成状态分组 | 按功能分组 |

**判定**：进度标记/状态 emoji/进度标题 → P1；>5处 → 需系统性重写相关章节。

## 3. 可读性与表达质量

### 3.1 文本流畅性
- [ ] 语病/错句？长句超40字？代词指代清晰？被动语态滥用？术语一致？标点混用？

### 3.2 逻辑组织
- [ ] 段落有逻辑衔接？有"跳跃"？遵循"先总后分"？信息密度不均？标题准确？

### 3.3 冗余控制
- [ ] 单文档内重复>2次？跨文档重复>3行应改引用？代码注释和文字说同一件事？
- **判定**：同一概念同文档重复超2次→检查是否必要；跨文档重复超3行→简介+引用

### 3.4 读者体验
- [ ] 新概念有上下文？术语首次出现有定义？假设读者已知什么？复杂流程有"结论先行"？
- [ ] 长文档有目录？代码块和文字比例合理？**代码块注释用中文**（文档注释用中文）；类比恰当？
- **判定**：新概念3行内无解释→P2；连续20行纯文字→P2；连续30行纯代码→P2

### 3.5 教学性质量（强制）

> 文档面向开源社区，是教学材料而非内部开发笔记。

**说明书 vs 教学文档**：

| 维度 | 说明书（退化） | 教学文档（目标） |
|------|--------------|----------------|
| Ch2 | 逐函数翻译注释 | 解释函数在整体流程中的角色 |
| Ch3 | 只写结论 | 推理过程+替代方案 |
| Ch4 | 贴裸代码 | 引导语+代码注释+设计决策引用 |
| 语义对应 | 无 | 与 Minix3 C 源码的语义对应 |
| 概念引入 | 直接使用不解释 | 给出定义、动机和上下文 |

**各章节要求**：Ch1 每个概念解释"为什么需要它"；Ch2 每个函数解释"它的角色"；Ch3 每个决策解释"为什么选A非B"；Ch4 每个类型有引导语解释核心思路+代码有注释。

**退化信号**：
- [ ] Ch2 只有代码片段+一行说明，无"为什么这样设计"的分析？
- [ ] Ch3 只罗列决策，无"为什么选A非B"？
- [ ] Ch4 变成 API 文档——列函数签名和功能说明？
- [ ] 缺少反例论证？缺少对比分析？缺少迭代过程记录？
- [ ] **开发记录退化**：出现"已实现/待实现/未实现"、✅❌🚧 状态标记、"实现清单"等进度追踪式表述？（详见 §2.11）

**详细检查项**：
- [ ] 每个章节/小节有引导语解释核心思路？
- [ ] 代码块内非自解释行有注释？特别是与 C 对应的注释？
- [ ] 代码块上方有 `> 设计决策：§3.x（xxx）` 引用？
- [ ] 核心概念/类型有 C 行为 vs Rust 行为对照？
- [ ] 代码块超15行无注释→P1；类型/模块小节无引导语→P1
- [ ] 新概念首次出现无定义→P1；代码块无设计决策引用→P2；无语义对应→P2

**判定**：3个以上退化信号→需要重构；1-2个→P1；0个→良好。

### 3.6 P2 可读性检查的执行策略

1. **先粗筛**：30秒快速浏览，感觉良好标注「无明显问题」跳过
2. **抽样检查**：感觉有问题，抽3处（首段、中段、尾段）逐项检查
3. **聚焦高频**：术语不一致、信息跳跃、纯代码无讲解（超30行）
4. **极简化输出**：仅输出实际发现的问题
5. **批量处理**：超500行按章节切分

**输出格式**：
```
### 可读性检查（P2）
- 术语：✅一致 / ⚠️X处不一致
- 逻辑：✅通顺 / ⚠️X处跳跃
- 冗余：✅无 / ⚠️X处重复
- 读者体验：✅良好 / ⚠️X个问题
```
