## 1. C 真序

### 1.1 阶段类型判定

`13-stage-ipc` 是**服务事件循环型**（不是启动链型、不是集合型）。理由：IPC server 的 C 代码里没有"启动链"式的阶段推进（`main` 只有三段：`env_setargs` → `sef_local_startup` → `for(;;)`），全部语义负载落在"一次消息进门之后走哪条路"。因此按 prompt §九的"服务事件循环型"处理：分启动段与循环段两段重建真序。

**同一 stage 具备的次要特征**：`sem` 与 `shm` 是**并行的两类对象**（各有一张表、一组命令、一套生命周期），不是线性序。这一点决定了 §4 的平行体组织方式（先共同骨架篇，再按对象族分组）。

| 建议的批量修改方式 | ①先按"新文件名唯一映射"跑一次 sed（9 条规则），覆盖 90 处；②再对旧 06 / 旧 08 的 14 处残留逐个判流；③以 `rg "0[0-9]-ipc-|99-ipc-" os/ notes/` 归零为验收 |

**结论**：断链成本低且可控——104 处引用全部落在"本目录内 + 本 crate 内"，无一处跨 stage 文档引用，不存在历史 I-14 那种"重编号断链风险大于收益"的局面。重建可以开工。

### 9.3 结论

**蓝图完成**，可以作为 B 相的施工图。

**待用户裁决的三个问题**：

1. **F-1 的处置口径**：现有 08 篇与 `todo.md` 的 IPC-P1-6 把"u8 环绕"写成契约。本次实测确认 C 侧是"int 提升后存入 `unsigned int`"（`shm.h:97`），数值为 `0xFFFFFFFF` 而非 255。建议：**保留契约结论（零引用段存活、禁止改为饱和减），改正机制描述与数值**。是否接受这个"改机制、留结论"的口径？
2. **C-05 的归属变更**：plan §7 的 D-2 曾裁决"组装函数归 05/08、03 只覆盖注册/分派"。本蓝图改为"组装本体归 12（对外查询面）"，理由是消除 plan 自己承认的 D-4 前向引用，且"恒定长度数组"是 ipcs 侧的外部契约而非表内部语义。是否接受推翻 D-2？
3. **14 篇的取舍**：新建 Rust 工程面篇会把六篇里的"模块结构/边界缝/测试统计"段抽走。若倾向"每篇自包含、不依赖 14"，则 14 篇可降级为"可选支线、只在改代码时读"，但各篇仍保留精简后的实现段。是否接受"抽走 + 14 统一承载"？

**范围外发现**（不属于本 stage，但重建时值得登记）：

- `minix3/minix/lib/libsys/rmib.c` 的协议半（1089 行）在 Rust 侧长期缺位，13-stage-ipc 是首个深度消费者；相关接线登记在 `edge_todo.md` 的 E-RMIBWIRE。
- `minix3/minix/servers/mib/kern.c` 也出现 `KERN_SYSVIPC` 字样——MIB 服务侧可能有本 stage 的另一半契约，建议 B 相在写 12 篇时顺带核一次该文件的归属。
