# 10 — 服务生死簿：干净才走，不干净就留

> **状态**: 已改写（2026-09-05，依据 plan.md 阶段 5 生命周期边界从零写作）

## 1 概念

### 1.1 目标读者与前置知识

面向已经读过 01、03、05、08 篇的读者。前置知识：01 篇的信号回调登记，03 篇的树摘除，05 与 08 篇的空表判断。重生服务器是什么在用到时用一句话解释（负责拉起与重启系统服务的管理服务）。

### 1.2 本篇不讲什么

- 信号量与共享内存表内部怎么管——那是 05 与 07 的事情（本篇只调空表判断）。
- 管理信息库子树的结构——那是 03 的事情（本篇只调摘除）。
- 订阅掩码的开关——那是 09 的事情（退出时订阅状态随进程消失，无需专门退订）。
- 进程事件的送达——那是 09 的事情。

### 1.3 为什么退出要查两张表

一个刚接触实现的读者最容易犯的错误，是把"退出"理解成"信号来了就走"。其实终止信号只是一个"请你看看能不能走"的请求：服务先查信号量表空不空、再查共享内存表空不空，两张都空才走——摘除子树、零码退出。任一张非空则警告一句"带着不干净状态退出"然后留下（注意：留下，不是稍后重试——这次信号就这么过去了，下次信号再查）。

两道检查缺一不可的原因：信号量集合的等待者可能还挂着（走了就没人叫醒），共享内存段的映射可能还有人用着（走了物理页归属就乱了）。干净退出的本质是"本服务名下无任何活对象"——两张表的高水位都归零（05 篇 2.4 节与 08 篇 2.2 节的水位语义在这里收口）。Redox 操作系统的服务退出同样要先排空名下资源（方案注销前关闭打开的句柄）——"无活对象才注销"是通用规矩。

### 1.4 一次终止信号的完整旅程（以表已空为例）

```
1. 重生服务器：向本服务发终止信号
  → 2. 信号回调：先看是不是终止信号（不是则直接返回，别的信号一律忽略）
  → 3. 查两张表：信号量高水位为零且共享内存高水位为零
  → 4. 摘除子树（03 篇的摘除函数），零码退出
```

表非空的旅程：第 3 步不过则打印"带着不干净状态退出"，回调返回，服务继续跑——下次终止信号再查。没有"稍后自动再查"的机制，每次检查都由新信号触发。

### 1.5 小结

生命周期由四部分组成：信号过滤（只认终止）、双表检查、干净路（摘除加退出）、不干净路（警告加留下），外加重启语义（重挂载、状态全丢）。记住这四部分加重启，全阶段收口。

## 2 C 源码分析

### 2.1 信号回调逐项核对（`sef_cb_signal_handler`，第 101 行到第 122 行）

| 步骤 | C 位置 | 行为 |
|---|------|--------|
| 信号过滤 | 第 105 行 | 非终止信号直接返回（别的信号一律忽略） |
| 双表检查 | 第 111 行 | 信号量表空且共享内存表空（05 的 `is_sem_nil`、08 的 `is_shm_nil`，都是高水位为零） |
| 干净路 | 第 112 行到第 114 行 | 摘除子树（03 的 `rmib_deregister`），零码退出（`sef_exit(0)`） |
| 不干净路 | 第 117 行 | 打印"带着不干净状态退出"，回调返回（留下） |

退出码零表示正常——能走到这里说明两张表都干净，零码名副其实。不干净路不调退出函数：进程继续服务，下次信号重查。

### 2.2 重启语义（`sef_local_startup` 登记的另一半）

启动登记（第 128 行到第 129 行）把全新启动与重启挂到同一个函数（01 篇 2.2 节）：重启即重新执行注册（03 篇的挂载）。重启不保留任何动态状态：信号量集合表与共享内存段表都是进程静态内存，重生服务器重启本服务即重跑进程，表天然全空——"状态全丢"不是某行代码干的，是重启机制自带的。干净退出判定的前提（"表空才能走"）与重启语义（"走了表就空"）首尾相接：正常停机保证无活对象，重启保证从空表开始。

### 2.3 与重生服务器的契约

本服务不在启动映像里（01 篇 2.6 节），由重生服务器运行时拉起。拉起、发信号、重启三件事都归它：本篇只讲服务这一侧（收到信号怎么办、重启登记什么），拉起侧是 `03-stage-rs` 的事情。两侧在"终止信号"与"重启重跑"两个动作上握手。

## 3 Rust 设计决策

| 编号 | 决策 | C 做法 | Rust 做法 | 为什么这样做 |
|---|------|--------|-----------|--------|
| D1 | 信号过滤变类型 | 整数比较后返回（第 105 行） | `Signal::{Terminate, Other}` 加 `from_raw`（`lifecycle.rs`） | 非终止信号不可表达成"要处理"：枚举让"忽略"分支天然存在；信号号常量具名 |
| D2 | 退出判决变纯函数 | 检查与摘除退出混写（第 111 行到第 114 行） | `shutdown_check(sem_empty: bool, shm_empty: bool) -> ShutdownVerdict`（`lifecycle.rs`） | 判决（走哪条路）与执行（摘除、退出）分离：摘除与退出是边界效应，服务层执行；判决可单测 |
| D3 | 两条路变枚举 | 一路退出一路打印（第 112 行到第 117 行） | `ShutdownVerdict::{ExitClean, StayDirty}`（`lifecycle.rs`） | 与 06 篇 `TryOutcome` 同款三出口枚举化思想：两条路各有名字，漏分支编译不过 |
| D4 | 重启变注记 | 同函数登记（第 128 行到第 129 行） | `RESTART_LOSES_STATE` 常量注记加 `restart_registers()` 文档函数（`lifecycle.rs`） | 重启无代码可写（机制自带）；注记进代码审查视野，防止后人"优化"成保留状态 |

微内核对照（类比，不是移植依据）：Redox 的服务注销前同样要求名下无活对象（关句柄、卸挂载），否则注销失败——与本篇双表检查同构。seL4 的 capabilities 撤销是内核代收（ killed 进程的资源内核回收），形状不同，不适用这里（用户态服务自己管表）。

替代方案及否决：不干净时自动重试退出（定时重查）——否决，因为 C 语义是"查一次、留下等下次信号"，加定时器是行为级变更；且留下的服务继续正常服务请求，重试退出无必要。

## 4 实现详解

### 4.1 模块结构

```
os/servers/ipc-server/src/
  lifecycle.rs    — 信号类型、退出判决、重启注记（本篇 D1 到 D4 的落地）
```

摘除子树调 03 的库、退出调系统事件框架——两者都是边界效应，由服务层在判决之后执行（本模块只判走哪条路）。

### 4.2 关键类型与函数

**信号与判决**（`lifecycle.rs`）：

- `Signal::{Terminate, Other}`：`from_raw(signo: i32)` 只有终止号算终止（C 的 `SIGTERM`）。
- `ShutdownVerdict::{ExitClean, StayDirty}`：干净走、不干净留。
- `shutdown_check(sem_empty: bool, shm_empty: bool) -> ShutdownVerdict`：双表都空则干净，否则留下（第 111 行语义）。

**重启**（`lifecycle.rs`）：

- `RESTART_LOSES_STATE: bool`（真）：重启丢全部动态状态（2.2 节语义的注记）。
- `restart_registers() -> bool`（真）：重启重新执行注册（与全新启动同函数，01 篇 2.2 节）。

### 4.3 关键不变量

- 双表缺一不可：任一非空即留下（测试三组合钉住：空空走、非空空留、空非空留、非空非空留）。
- 非终止信号无动作：判决函数不收非终止输入（类型层面：调用者先过滤，`from_raw` 分流）。
- 重启不保留：注记为真，无代码路径能绕过（构造即全空表）。
