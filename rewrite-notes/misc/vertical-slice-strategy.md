# 纵向切片重写策略

## 按模块重写的问题

重写 Minix 这样的操作系统时，一个直观的想法是按模块逐个重写：

```
Phase 1: 完整重写 PM
Phase 2: 完整重写 VFS
Phase 3: 完整重写 VM
...
```

**这种方法会失败，原因如下：**

1. **概念爆炸**：每个模块（如 PM）包含太多概念：
   - 进程语义
   - 信号语义
   - fork/exec/exit/wait
   - 与内核的交互
   - 与 VM 的交互
   - 与 VFS 的交互
   - 历史包袱

2. **无限上下文追踪**：
   - 一行代码背后有一大串上下文
   - 上下文又牵出其他模块
   - 最终陷入无限递归的解释链

3. **无法闭环**：在所有模块完成之前，永远得不到一个"可运行的系统"

> **如果试图搞清楚每行代码的上下文，那意味着一定搞不清楚。**

---

## 解决方案：纵向切片策略

不要横向重写（按模块），而是纵向重写（按功能）：

```
Phase 1: fork 切片
Phase 2: exec 切片
Phase 3: exit 切片
Phase 4: signal 切片
...
```

**每个切片都是一条穿过所有模块的完整闭环路径。**

### 示例：exec 切片

```
用户 exec("hello")
       │
       ▼
┌─────────────────────────────────────────────────────────┐
│  kernel/                                                │
│    ├─ 最简调度器                                        │
│    ├─ 最简地址空间                                      │
│    └─ IPC（即使是假的也行）                             │
│                                                         │
│  pm/                                                    │
│    └─ 只实现 exec handler                               │
│       （不实现 signal、fork、wait）                     │
│                                                         │
│  vfs/                                                   │
│    ├─ open("/bin/hello")                                │
│    └─ read ELF                                          │
│                                                         │
│  vm/                                                    │
│    └─ 映射 ELF 段                                       │
│                                                         │
│  ipc/                                                   │
│    └─ 消息传递                                          │
└─────────────────────────────────────────────────────────┘
```

### 你实际要写的代码

不是写一个巨大的 `exec.rs`，而是：

```
pm/exec.rs      ← PM 的 exec 处理
vfs/elf.rs      ← VFS 的 ELF 加载
vm/map.rs       ← VM 的段映射
kernel/sched.rs ← 内核的最简调度器
```

**exec 流程穿过所有这些模块。**

---

## 核心原则：切片闭环，模块不完整

> **每个切片必须闭环，但每个模块不必完整。**

这是关键约束。

### 具体含义

实现 fork 切片时：

```rust
// pm/fork.rs - 只实现 fork 相关的入口
pub fn sys_fork() -> Result<Pid, Error> {
    // 最简 fork 逻辑
}

// kernel/process.rs - 只实现 fork 需要的支持
pub fn copy_process(proc: &Process) -> Process {
    // 最简进程复制
}

// vm/cow.rs - 只实现写时复制或最简地址空间复制
pub fn copy_address_space(as: &AddressSpace) -> AddressSpace {
    // 最简 VM 支持
}

// vfs/ - 暂不触碰，或留空接口
```

---

## 这种方法的优势

### 1. 防止概念爆炸

每个切片的范围有界。你只需要理解一条因果链。

### 2. 可验证的结果

每个切片完成后，你都有可工作的东西：

```
fork 切片完成后：  fork() 可用
exec 切片完成后：  exec() 可用
exit 切片完成后：  exit() 可用
```

### 3. 强制依赖分析

你会自然学会区分：

| 类别 | 说明 |
|------|------|
| **核心依赖** | 必须现在实现 |
| **可延后依赖** | 可以先 stub，后面再补 |
| **历史包袱** | 可以完全忽略 |

---

## 必须避免的反模式

**不要这样做：**

```
exec.rs  ← 所有逻辑都写在这里
```

这会变成**单体内核 demo**，丢失微内核的精髓。

**应该这样做：**

```
pm/exec.rs
vfs/elf.rs
vm/map.rs
kernel/sched.rs
```

**模块边界保留，即使每个模块都是最小实现。**

---

## 项目阶段

```
Phase 1: 扫描 Minix
         └─ 阅读并理解现有代码库
         
Phase 2: exec 纵向切片
         └─ 实现穿过所有模块的最简 exec 路径
         
Phase 3: fork + exec
         └─ 添加 fork，启用进程创建
         
Phase 4: IPC 优化
         └─ 现在可以思考 per-CPU 内核、
            共享内存 IPC、去中心化等问题
```

## 你将获得什么

完成几个切片后，你将能够回答：

1. **设计问题：**
   - 为什么 exec 必须经过 PM？
   - 为什么 VFS 不能直接加载？
   - 为什么 VM 必须参与？

2. **权衡理解：**
   - 为什么 IPC 昂贵？
   - 为什么 grant 机制存在？
   - 为什么 Linux 的设计不同？

3. **优化机会：**
   - Per-CPU 内核？
   - 共享内存 IPC？
   - 去中心化？

**这才是真正的操作系统设计阶段。**

---

## 总结

| 方法 | 问题 |
|------|------|
| 按模块重写 | 概念爆炸，无法闭环 |
| 单体切片重写 | 丢失模块边界 |
| **纵向切片 + 模块边界** | **正确方法** |

策略很简单：

> **按因果链（切片）重写，而不是按模块。**
> **保持模块边界，但只实现最小子集。**

这就是如何在复杂度中重建微内核而不被淹没。
