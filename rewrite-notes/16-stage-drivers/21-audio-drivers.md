## 1. 概念：乐队的指挥与七种乐器

### 1.0 章节引言

目标读者是读完帧缓冲的读者。前置知识只需要一条：字符驱动靠打开关闭读写与输入输出控制服务。本章解释音频为什么比显示多一层框架：七种声卡寄存器各不相同，得有个中间层把统一请求翻译成各卡方言。

### 1.1 框架是指挥，声卡是乐器

想象乐队指挥：指挥只打拍子（统一的十四钩子：初始化、复位、启动、停止、设直接存取、暂停、继续、输入输出控制等），七种乐器各按各的指法演奏（每种声卡填自己的寄存器）。听众点歌（声音控制请求：设采样率、设声道、设位宽、暂停、继续等十一项），指挥翻成各乐器能懂的手势。

### 1.2 采样率是乐队谈好的节拍

节拍必须先谈好：参考实现只认四千到四万四千一百赫兹，默认四万四千一百。谈不拢直接拒绝（超限检查）。三条通道各走各的转换器（采集走模数转换器基址，合成走合成器基址，回放走数模转换器基址），转换器内部固定四万八千赫兹跑，谈好的节拍靠换算公式折进去。

### 1.3 老声卡是只能听命令的老乐手

老声卡像只能听短命令的老乐手：复位先举手再放下（拉高再拉低复位线），等回音（读到十六进制的 AA 才算醒了），问版本发十六进制的 E1，设速率先发方向命令（输入六十六还是输出六十五）再发高低两字节。喇叭开关、停播续播各一字节，错一字节乐手就不理人。

### 1.4 七兄弟是同门不同指法

七兄弟同门（都挂字符框架加音频框架），指法各异：参考实现管转换器与编解码器，老卡管数字信号处理器，其余五家各管各的混音器（五份同构的混音器文件，各二百七十二行）。变体差异只在三处：初始化填什么寄存器、速率怎么谈、混音器有几路。

### 1.5 本章小结

音频三件事：指挥定十四钩子，节拍谈四千到四万四，命令一字节不错。下一章进入 C 语言源码验证。

### 2.8 与 C 约九千行的差异说明

| 差异 | C 做法 | Rust 做法 | 分类 |
|------|--------|-----------|------|
| 寄存器写入 | 七家全实现 | 参考实现与老卡只定范围（写入在服务层），第三卡按寄存器时序建模（`device.rs`） | 设计决策：能测的时序留在卡内 |
| 混音器 | 六份全实现 | 参考实现与老卡在服务层，第三卡按寄存器对与音量表建模（`mixer.rs`） | 设计决策：同上 |
| 直接存取搬运 | 边播边搬 | 服务层 | 设计决策：搬运在服务层 |

### 2.9 C 源的缺陷与两处忠实性勘误

第三卡带来三件需要写明的读数。

第一件是 C 源自身的缺陷：混音器的线路输入支（`minix3/minix/drivers/audio/cmi8738/mixer.c` 第一百一十三行到第一百一十四行）把左声道寄存器变量连赋两次，第二行赋的是右声道常量。后果是线路输入的音量请求左右两声道都打到右寄存器，左寄存器从不被写。这显然是笔误（同族八个设备支都是一左一右），但它是 C 的既成行为；重写按观测行为保留，并在此具名，免得后来者顺手"修好"它。

第七张卡带来两条缺陷读数，都在读路径上。第一条：当前地址读取算出了值却恒返零（`minix3/minix/drivers/audio/trident/trident.c` 第一百七十九行），于是"缓冲里有多少采样"这个请求只剩额外缓冲计数。第二条：编解码器读把端口按**字**读（同文件第八十行）再右移十六位（第八十五行），移位之后恒为零——连混音器的掉电探测都因此永远等不到回音（`mixer.c` 第二百三十六行的循环跑满五万次，打印警告后照写十一项默认值）。两条都按观测行为保留，并在门里钉住。另有一处有意差异：采样率的第二笔写入是 `(48000<<12)/rate`（同文件第一百一十五行），没有零除保护，零速率会让 C 的驱动进程收到除零异常；重写拒绝零速率。

第六张卡的端口宏走的是内存映射分支（`cs4281.h:5` 定义 `DMA_BASE_IOMAP`），于是它的读写**没有错误通道**：映射后的易失读写要么完成要么缺页，这正是缝上声明不可失败的理由（对照第四卡：`pci_helper.c` 的读宏在系统调用失败时返回未初始化局部量，那条路径既不安全也不可复现，重写不复制它）。

第五张卡带来两条缺陷读数。第一条是混音器线路输入支的连赋两次（`minix3/minix/drivers/audio/als4000/mixer.c` 第一百零四行到第一百零五行），与第三卡的副本同源，重写按观测行为保留。第二条在格式设置里：有符号单声道一支写的是**立体声**命令字节（`minix3/minix/drivers/audio/als4000/als4000.c` 第一百五十三行到第一百五十四行：另外三支都取对应常量，只有这一支取 `CMD_SIGN_STEREO`）。同样保留并在此具名。

第四张卡带来一条端口读的缺陷读数：`pci_helper.c` 的六个读写宏里，读宏在系统调用失败时打印一行警告，然后**返回一个从未写入的局部量**（`minix3/minix/drivers/audio/es1370/pci_helper.c` 第十九行到第二十四行）。重写不复制这条路径：端口读失败会报给调用方，卡的面把失败变成错误而不是拿着一个未定义的值继续配置寄存器。这是有意差异，记在此处。

第二件与第三件是两处分片大小的读数，两张卡都必须取三十二千字节。参考实现的 DMA 缓冲是六十四千字节对两片，故分片大小为三十二千字节（`es1371.c` 第一百六十四行到第一百六十五行按缓冲除以片数播种）；老卡同法（`sb16.c` 第一百一十行写 `DspFragmentSize`）。这个读数之所以要紧，原因在框架侧：框架的读写闸门按 C 的做法每次请求现读卡的分片大小（`audio_fw.c` 第四百一十二行与第四百六十二行调 `drv_get_frag_size`），再与请求长度比较（同两处的下一行）；尺寸读数错了，合法请求就会被闸门拒掉。

## 3. Rust 设计决策

> 本章解释为什么这样设计。每个决策先给依据，再给替代方案与取舍。

### 3.1 范围做成守卫函数（依据：第 1.2 节、第 2.4 节）

上下限写死（四千到四万四千一百），守卫纯函数一判就是全部。替代方案是守卫散落在分发入口，不选的理由是：纯函数让三路通道共用一套判法。

### 3.2 路由做成枚举（依据：第 1.2 节、第 2.4 节）

三通道各一变体，基址查表（模数七十八、合成七十、数模七十四）。替代方案是裸数字传基址，不选的理由是：枚举让传错基址编译不过。

### 3.3 命令做成常量（依据：第 1.3 节、第 2.5 节）

方向命令、喇叭开关、版本号、复位回音全写死，错一字节一眼看出。替代方案是运行时读配置，不选的理由是：命令字节是硬件写死的，读配置多一次错的机会。

### 3.4 分字节做成纯函数（依据：第 1.3 节、第 2.5 节）

方向加高低两字节一次算出，超限返回空（调用方拒绝）。替代方案是分字节散落在发送函数里，不选的理由是：纯函数一测就是全部边界。

### 3.5 设计决策汇总

| 决策 | 依据 | 替代方案 | 为何不选 |
|------|------|----------|----------|
| 范围守卫 | 第 1.2、2.4 节 | 守卫散落入口 | 三路不能共用 |
| 路由枚举 | 第 1.2、2.4 节 | 裸数字传基址 | 传错不响 |
| 命令常量 | 第 1.3、2.5 节 | 运行时读配置 | 硬件写死 |
| 分字节纯函数 | 第 1.3、2.5 节 | 分字节散落发送 | 边界测不全 |

## 4. 错误处理

| 场景 | C 行为 | Rust 表达 | 说明 |
|------|--------|-----------|------|
| 速率超上限 | 拒绝 | 守卫返回假 | 节拍谈不拢 |
