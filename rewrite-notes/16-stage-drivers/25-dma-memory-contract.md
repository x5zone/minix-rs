# 25 DMA 内存契约：驱动库与服务端之间的连续页边界

> **目标读者**：要给驱动库接真实设备的人。前置知识只需要一样：设备不认识虚拟地址，它只按总线上的物理地址读写内存。

## 1 概念：为什么设备内存不能问操作系统要

用户态进程眼里的内存是连续的虚拟地址，背后的物理页东一块西一块。CPU 访问时页表把这些碎片缝起来，程序毫无察觉。设备没有页表：总线主控发起一次传输，给出的地址必须原样命中物理内存。virto 环是设备与驱动共享的环形队列，设备异步地写它的游标字段——环要是被页表拆成了碎片，设备就会把游标写进不知谁家的一页里。所以共享环、命令表、大块缓冲这类内存有一个硬约束：物理上连续，地址让设备可见。

C 语言时代这件事不构成边界问题：驱动跑在内核里，`alloc_contig`（`minix3/minix/drivers/lib/libvirtio/virtio.c:319` 一带）直接从内核页分配器拿连续页，拿到的虚拟地址转成物理地址填进描述符就完事。分配器、地址翻译、驱动三者在同一个地址空间里，没有"边界"可言。

minix-rs 把驱动搬进了用户态服务器，这三样东西从此分了家：物理页在 VM 服务器手里，地址翻译靠页表（也是 VM 的领地），驱动库只认识字节数组。驱动库如果自己伸手够页表或者 CR3，就违反了本仓库"硬件藏到 trait 后面"的铁律；如果干脆不分配，第 14 篇搬进库的环布局就成了没有燃料的引擎。边界必须显式地画出来，画在双方都认可的形状上。

这里有三个贯穿全文的心智模型。第一个是**燃料站模型**：驱动库是发动机，物理分配器是油库，本契约是加油管的口径——发动机不关心油从哪儿炼出来，油库不关心发动机怎么烧，双方只认管口。第二个是**地址双簿模型**：一块 DMA 内存在驱动眼里是虚拟地址，在设备眼里是物理地址，契约把两个地址绑在同一张凭据上发出去，驱动不需要自己算换算。第三个是**单一权威模型**：契约的定义只有一份，住所有驱动库都依赖的共享类型库；服务端提供实现，库的测试提供替身——同一段驱动代码，生产环境吃真内存，测试环境吃假窗口。

## 2 契约：四件操作和一张凭据

契约定义在 `os/libs/minix-types/src/types/dma.rs`，一共四件操作加一张凭据，全部围绕"申请、归还、两个方向的地址翻译"。

凭据是 `DmaRegion`：三个字段，物理首址（填进设备描述符的 `addr` 栏）、CPU 侧首址（驱动读写缓冲用的地址）、可用长度。三者绑在一张凭据上是一次设计裁决：如果只发物理地址，驱动就得自己维护虚拟到物理的换算表；如果只发虚拟地址，设备描述符就没有内容可填。绑定发出，双方各取所需，谁也不用反向推算。长度字段记录的是**可用**字节数——实现方可以把底层分配向上取整到页界，但凭据上必须如实写调用者能用的部分，这是"凭据即事实"的原则。

四件操作挂在 `DmaMemory` 行为下。`dma_alloc(size, align)` 申请物理连续、设备相干的内存，穷尽或者对齐给不起时报 `ENOMEM`——C 的分配器拿不到页时返回 NULL，两者是同一个裁决的两种表达。`dma_free(region)` 归还凭据，无返回值：归还一个凭据不可能"失败"，重复归还或者归还外来的凭据是实现方自己的簿记错误，由实现方自查。`virtual_to_physical` 与 `physical_to_virtual` 互为逆运算，出界或来历不明的地址报"无"——这不算错误，翻译不了就是翻译不了，调用者检查空值即可。

两个值得展开的形状裁决。其一，申请失败报 errno 而不是空值：rcore 的 `virtio-drivers` `Hal` 用 `Option`，这里的共享契约用 `Result<_, Errno>`，因为共享类型库的纪律是错误必须落在 Minix 的错误号上，穷尽就是 `ENOMEM`（值 12），调用者能区分"没内存"和"参数荒唐"。其二，归还无返回值：Linux 的 `dma_free_coherent` 同样不报错，错误通道留给真正可行动的失败。

## 3 Rust 设计决策：契约为什么住共享类型库

契约的定义住在 `minix-types`（`types/dma.rs`），不在任何一个驱动库或服务端里。这不是随手一放：驱动库（virtio、ahci、usb_storage）和实现方（VM 服务器）分属两条工作线，契约放谁家，另一家就得反向依赖。放共享类型库，两家依赖它，箭头都朝下，没有环。

virtio 库经 `hal.rs` 以别名再导出消费这份契约：公开路径保持 rcore `virtio-drivers` 约定俗成的 `Hal` 名字，定义却只有共享类型库那一份，库内调用点引用的就是共享行为。ahci 和 usb_storage 将来长出服务缝时，直接拿同一个行为当参数，不需要再发明第二种说法。

库内测试怎么吃这个契约，规定了替身的形状：一个定长簿记的阶梯分配器（对齐向上取整、预算穷尽报 `ENOMEM`、翻译按凭据区间内查表），再加一个故意"永远没内存"的实现凑足两个行为不同的实现体——trait 只有一个实现体的抽象是装饰，两个起才算数。生产端的实现是 VM 服务器的事（edge3 S37），它拿连续页分配器把四个方法填实，驱动库一行不改。

## 4 错误处理：失败的三种形状

| Rust 情形 | 处理 | 对应的 Minix 语义 | 选择理由 |
|-----------|------|-------------------|----------|
| 申请穷尽或对齐给不起 | `Err(ENOMEM)`（值 12） | C 分配器返回 NULL | 同一裁决，错误号可区分可传播 |
| 翻译查无此址 | `None` | 无对应（翻译本来就可能不覆盖） | 不覆盖不算错误，空值即答案 |
| 归还凭据 | 无返回值 | C `free` 同样不报错 | 可行动的失败不存在，簿记错误由实现方自查 |

## 5 测试：契约自身的六条断言

契约模块自带三组测试（`cargo test -p minix-types`，其中本模块 3 个；连同 virtio 库经别名跑的替身测试，`cargo test -p minix-virtio` 本模块 1 个）。断言覆盖：申请的对齐承诺与长度如实性（第二次申请被顶到第一块之后的对齐边界）；穷尽路径返回 `ENOMEM` 而非恐慌或空凭据；翻译的往返对称性（虚拟加偏移到物理、再翻译回来逐字节吻合）与出界空值；归还后翻译立即失效。替身实现用确定性的阶梯地址，测试可以精确断言到字节，不依赖任何真内存。

端到端的验证——VM 服务器实现方把真连续页填进契约、virtio 环架在上面被设备真实读写——挂 edge4 E5 联调族，那是通电以后的事，本篇的断言面到契约为止。

## 6 过渡：从契约到服务端实现

本篇解决的是"驱动库如何开口要内存"。下一个问题是"VM 服务器如何兑现承诺"：连续物理页从哪个池子里出，地址翻译怎么在服务端的页表上做，设备写入之后 CPU 的缓存视角要不要维护。这些属于 VM 服务器的工作线（edge3 S37），在那边落地时直接拿本篇的 `DmaMemory` 行为当接口，不再另立名目。
