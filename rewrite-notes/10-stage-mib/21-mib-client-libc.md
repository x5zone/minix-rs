# 21 — 用户态 C 库：调服务之前，先看是不是自家的事

> **分类**: 客户端契约 / 外部文档（不实现）
> **源码**: `minix3/lib/libc/gen/sysctl.c`（391 行，用户态入口和本地子树）、`minix3/lib/libc/gen/sysctlbyname.c`、`minix3/lib/libc/gen/sysctlnametomib.c`、`minix3/lib/libc/gen/sysctlgetmibinfo.c`（611 行）、`minix3/minix/lib/libc/sys/__sysctl.c`（真正发消息）
> **说明**: 进程信息五篇讲完，视角换到调用的人。用户态程序调系统信息查询，先过 C 库这一层：自家的事本地办，别家的事发消息。本篇是外部契约文档，minix-rs 不重写 C 库，只把两边的约定写清楚，保证 C 库那边不用改。

---

## 1 概念

### 1.1 目标读者与前置知识

面向要保证 C 库兼容的人。前置知识：02（消息面和交换格式）、01（收尾换算和 ENOMEM 的特殊含义）。"本地子树"指用户配置那棵树，它住在 C 库里面，不进服务。

### 1.2 本章不讲什么

- 服务内部怎么查——01 到 20。
- 远端挂载的客户端——22。
- C 库重写——不做（架构演进 A-10，外部契约）。

### 1.3 先分流，再办事

用户态程序调 `sysctl`，C 库先看名字的第一个数。第一个数是用户配置，直接走本地表，不出进程。否则调 `__sysctl` 发消息给服务。分流的理由很实在：用户配置全是编译期常量（几个工具的上限、POSIX 版本号、能不能用某某功能），为查个常量跑一次跨服务消息不值得。本地表是静态数组，一行一个节点，整数用宏批量生成，字符串就一个（默认 PATH）。

本地办和发消息，两边的长度规矩是一样的：旧缓冲区装不下，报缓冲区太小，同时告诉调用的人完整长度，调用的人带大缓冲区再来一次。这条规矩两边必须一致，不然调用的人在本地能跑通的代码，发到服务就行为两样。01 篇讲的收尾换算，在这里是第二次出现：第一次是服务的事，这次是 C 库的事。

### 1.4 五个函数的分工

最底下是 `__sysctl`：填消息（旧地址、旧长度、新地址、新长度、名字长度、名字指针，短名字直接塞消息里），调系统调用发给服务，回来把旧长度抄回去。抄回去这一步有 NetBSD 传下来的怪规矩：**调用失败也抄**（注释原话，没文档，但 sysctl 命令行工具靠它，`__sysctl.c` 尾部）。消息层面失败抄回来的是垃圾，调用的人不该用，但成功和"缓冲区太小"这两种情况，抄回来的长度是准的，值得依赖。

`sysctl` 是包了一层的入口：本地子树自己办，别人的转交，回来统一算账。缓冲区太小的判断在这一层做，错误码按 C 库规矩走（返回负一，错误码放 errno）。

`sysctlbyname` 是给懒人用的：名字符串进来，转成编号数组，再调 `sysctl`。真正的活是 `sysctlnametomib` 干的，它又是 `sysctlgetmibinfo` 的薄包装。`sysctlgetmibinfo` 是最重的一个（六百多行）：用查询和描述两个元标识符把树走一遍，把名字排好序，返回编号数组。排序值得注意：服务返回的顺序不保证，C 库这边排完再交出去，调用的人拿到的总是排好的。

### 1.5 小结

C 库是服务的第一个消费者，也是规矩最多的消费者：本地子树、长度规矩、失败也抄长度、名字排序，四条约定服务侧都要守住。本篇是契约，服务实现（01 到 20）是履约，改任何一边都要看另一边。

## 2 C 源码分析

### 2.1 入口分流（`sysctl.c:78-109`）

第一个数是用户配置，走本地。否则走 `__sysctl`。旧长度空指针按零算，办完写回，装不下报缓冲区太小（`:78-109`，和 01 的收尾换算是同一条规矩的 C 库侧）。

### 2.2 本地表（`sysctl.c:112-240` 附近）

静态节点数组：一个字符串（默认 PATH，系统找标准工具用的 PATH 值），二十来个整数。整数都是"上限"和"版本号"两类：上限类管 bc 计算器、正则表达式、输入行长、能打开的流数、时区名长度、退出函数个数；版本类管 POSIX 两个版本的号；开关类管 C 语言开发、Fortran、本地化、软件开发、用户可移植性支不支持（支持填一，不支持填零，编译时按宏定）。整数用宏批量生成，标志是立即数加永久。查名字走数组，读写走通用读写（和 09 同语义，C 库侧复刻）。注意本地表不接受写：带新数据来直接报不允许（`sysctl.c` 写路径第一行），因为全是编译期常量，写它没有意义。本地表同样回答查询和描述（查编号信息要走它）。

### 2.3 发消息（`__sysctl.c` 全文）

填消息六件套，短名字（不超过八个）直接塞消息里（和 01 的名字取用路径选择对应：短名字服务侧直接用，长的服务侧再拷）。调系统调用。回来抄旧长度，失败也抄（NetBSD 怪规矩，见 §1.4）。

### 2.4 名字工具（`sysctlbyname.c`、`sysctlnametomib.c`、`sysctlgetmibinfo.c`）

按名查是薄层：字符串进来，转成编号数组，再调 `sysctl`，懒人专用。名转编号是更薄的包装，里面调查编号信息，注释还吐槽了一句"第三个参数用长度类型是错的，但能拿它怎么办"（`sysctlnametomib.c` 原话，FreeBSD 兼容包袱）。最重的是查编号信息（六百多行）：用查询元标识符把树从根走一遍，遇到名字对上的记下来，再用描述元标识符补全信息，最后按名字排序返回。排序保证调用的人每次拿到的顺序一样。走树用的是 10、11 的元标识符语义，所以查询和描述两边必须能走完一棵树，这是服务侧的履约点。

## 3 Rust 设计决策（契约侧，无实现）

| # | 约定 | 服务侧现状 | C 库侧现状 | 为什么能对上 |
|---|------|-----------|-----------|--------------|
| D1 | 本地子树不进服务 | 用户配置编号服务侧没有表 | C 库静态数组自办 | 编号空间是 NetBSD 传下来的，用户配置号服务侧查不到，查到了也是错 |
| D2 | 长度规矩两边一致 | 01 收尾换算 | 入口统一算账 | 调用的人不用分本地还是远端 |
| D3 | 失败也抄长度 | 01 附带长度返回 | `__sysctl` 照做 | 命令行工具靠它重试，改任何一边都断 |
| D4 | 名字排序 C 库做 | 服务不保证顺序 | 查编号信息排完再交 | 排序是表现层的事，不进服务 |

替代方案及否决：minix-rs 重写 C 库——否决。C 库是外部契约（A-10），重写它没有收益，只有兼容风险。本地子树搬进服务——否决，搬进去每次查常量都要跑消息，亏。

## 4 实现详解（契约清单，无代码）

本篇无 Rust 实现。履约点在 01（分发和收尾）、02（消息和交换格式）、10（查询终点）、11（查询和描述）。C 库侧五个函数的行为约定见 §2，改服务侧任何一点，先对这张表：

- 用户配置号服务侧必须查不到（查到就是 bug）。
- 缓冲区太小必须附完整长度（两边一样）。
- 失败必须抄旧长度（命令行工具靠它）。
- 查询和描述必须能遍历整棵树（查编号信息靠它）。
