## 独立判定

### T01 — translation-residue.rs（阳性：翻译残留 / 单实现 trait / 非法状态）

1. **裸整型状态，C `int` 直译** — 位置：L5 `pub state: i32`、L13/L25 `set_state(state: i32)`。
   问题：Minix3 C 真值中进程运行态是 `p_rts_flags` 位标志组合（`proc.h` L142–166：`RTS_SENDING|RTS_RECEIVING` 可并存等 16+ 位），这里把状态降格为无约束 `i32`：任何整数（包括 C 真值中从未定义的值）都能写入，类型系统对状态空间零约束。`flags: u32` 与 `state: i32` 的分工也未定义（两字段都是"状态"，谁管什么没说），且 u32/i32 混用是 C int 直译痕迹。属翻译残留，违背"语义重写不是翻译"。
   最小修复：状态改语义类型——位标志 newtype（`RtsFlags(u32)` + 命名常量）或受约束的 enum；`set_state` 签名随之收窄；`flags`/`state` 二者择一或明确分工。
   严重度：P1（形态 P0-design-deviation）。

2. **`ProcessManager` 单实现 trait，接缝职责无证据** — 位置：L11–14。
   问题：仅 `ProcTable` 一个实现，fixture 内无任何 `#[cfg(test)]`、无第二实现。按"先问职责"判据：它不承担语义收窄（`get`/`set_state` 是薄透传），测试接缝职责在样本内无证据。但不断言必删：若内核 host-mock 测试计划需要注入假进程表，trait 是合理接缝——那样应有 mock 实现或注释声明接缝意图，样本内两者皆无。
   最小修复：默认内联为 `ProcTable` 固有方法；若确有 mock 计划，补一条 mock 实现或注释声明接缝用途。
   严重度：P2。

3. **空槽无表示 + `get`/`set_state` 越界语义不对称（非法状态可表示）** — 位置：L16–28。
   问题：`procs: [Proc; 64]` 每槽都是"满" `Proc`，没有空槽表示——C 真值里"槽空闲"是 `RTS_SLOT_FREE` 位（状态空间内的事实），这里既无该位也无 `Option`，`get` 对未占用槽照样返回 `Some(&Proc)`，调用方无法区分真进程与陈旧数据，"空槽却像真进程"这一非法状态可表示。同时 `get(nr)` 返回 `Option` 承认越界、`set_state` 却直接索引 panic：同一 trait 对同一索引两种越界策略，行为不对称。
   最小修复：槽位改 `[Option<Proc>; 64]`（空 = `None`，单一事实源）；`set_state` 返回 `Option`/`Result` 与 `get` 对齐。
   严重度：P1。

### T02 — dead-abstraction.rs（阳性：死抽象，但必须问测试接缝）

1. **`now_ms(c: &Hpet)` 锁死具体类型，trait 接缝失效** — 位置：L16–18。
   问题：本样本的核心不是"单实现 trait 该删"。`ClockSource` 有明确语义职责：时钟源是典型测试接缝（host 测试注入假时钟）与多源扩展点（HPET/TSC/LAPIC timer），trait 应保留。真正的缺陷是 `now_ms` 参数类型是具体 `&Hpet` 而非 `&impl ClockSource`：抽象建了却被唯一调用点绕过，接缝失效——`MockClock` 永远注不进 `now_ms`。这是死抽象的精确形态（抽象存在但未被使用），而非"单实现即删"。
   最小修复：`pub fn now_ms(c: &impl ClockSource) -> u64`，trait 保留。
   严重度：P1。

2. **`Hpet::read_ns` 恒返 0 且无 MMIO 状态** — 位置：L8–14。
   问题：unit struct `Hpet` 无任何字段（HPET 读取需要 MMIO 基址），`read_ns` 返回常量 0——占位实现未以任何方式标注（无 TODO/`todo!`），调用方无从知道这是 stub；`now_ms(&Hpet)` 因此恒 0，时间语义静默丢失。
   最小修复：补 MMIO 基址字段与真实读取；短期至少 `todo!()` 或注释显式标注占位。
   严重度：P2。

### T03 — arch-leak.rs（阳性：硬件机制泄漏到共享层）

1. **共享层内嵌 x86-64 内联汇编，破坏三架构契约与硬件抽象边界** — 位置：L4–14（全部）。
   问题：模块声称位于共享层，但 `asm!("mov cr3, …")`/`invlpg` 是 x86-64 专属机制：ARM64/RISC-V 下直接无法编译，三架构契约当场破裂；CR3/invlpg 机制名直接暴露给 OS 语义层调用者，违反"硬件通过 trait 抽象，不把 CR3/PTE 位暴露给 OS 语义层"与"抽象语义不描述机制"第一原则（arch trait 自身可谈硬件名，共享层不行）。
   最小修复：下移到 x86-64 后端（如 `arch/x86_64/`），共享层定义语义接口（`AddressSpace::activate` / `Tlb::flush_page(addr)` 之类），三架构各自实现。
   严重度：P1（形态 P0-design-deviation / 架构边界破坏）。

2. **`init_tss` 名实不符，把 CPU 编号写进 CR3** — 位置：L4–8。
   问题：函数名说"初始化 TSS"（x86 任务状态段，应操作 GDT/TR），函数体却是 `mov cr3, cpu`——CR3 是页表物理基址寄存器，应写入页表基址，而这里把 `cpu: usize`（CPU 编号）当 CR3 值写入。名字与行为、参数与寄存器语义双重错位：要么名字错（实际是 per-CPU 页表激活），要么值错。参数类型也不对：CR3 值是物理地址，不是 CPU 编号。
   最小修复：拆分语义——`load_tr()`（真 TSS 初始化）与 `activate_page_table(cr3: PhysAddr)` 分立，地址用物理地址类型。
   严重度：P1。

3. **`flush_tlb` 固定只刷虚拟地址 0 的一页** — 位置：L10–13。
   问题：`invlpg [0]` 只失效地址 0 处单个页的 TLB 项，而函数名 `flush_tlb()` 无参数，承诺整体/通用 TLB 失效。调用者会误以为全 TLB 已刷新，实际只有一页——静默语义错位（全量做法是 CR3 读回重载）。
   最小修复：改为两个语义明确的接口：`flush_page(addr: Va)`（invlpg addr）与 `flush_all()`（CR3 读回）。
   严重度：P1。

### T04 — duplicate-state.rs（阳性：重复状态 / 非法组合可表示）

1. **`present: bool` 与 `SlotState::Empty` 重复表达同一事实** — 位置：L11–14。
   问题："槽是否占用"被表达两次：`present` 与 `state == Empty`。二者应恒一致的不变量无类型保证，非法组合可构造：`(present: true, state: Empty)`（占用却空）与 `(present: false, state: Running)`（空槽却在运行）都能轻松构建，矛盾时无权威字段仲裁。C 真值中"槽空闲"就是 `RTS_SLOT_FREE` 一个位——单一事实源；这里把一个事实拆成两个可矛盾的字段，是 C 风格 bool+enum 并存的直译。`pub` 字段还允许外部绕过任何约定。
   最小修复：删 `present`，以 `state == SlotState::Empty` 判空并提供 `Slot::is_empty()`；或删 `Empty` 变体改 `state: Option<ProcState>`。字段私有化。
   严重度：P1。

2. **（观察）互斥三值 enum 装不下真值状态空间** — 位置：L4–9。
   问题：对照 `minix3/minix/kernel/proc.h` L142–166：Minix3 进程态是可组合位集（`RTS_SENDING` 与 `RTS_SIG_PENDING` 可同时置位、多原因阻塞并存），`Empty/Ready/Running` 互斥单值 enum 既缺 PROC_STOP/PREEMPTED/NO_QUANTUM 等语义，也根本无法表达组合态。若本类型承载内核进程槽，接入 IPC/调度时会暴露。
   最小修复：确认本槽语义归属；若对应内核 proc，按 C 真值改位标志集（见 T01 修复 1，两处应一致）。
   严重度：P2（样本语境下登记，归属待定）。

### T05 — sentinel-error.rs（阳性：哨兵返回值）

1. **查找失败返回 -1 哨兵** — 位置：L9–16。
   问题：`lookup` 返回 `i32`，失败路径用 `-1` 表达——C 惯用哨兵直译。调用方必须记得手判 `idx < 0`，编译器不帮忙；`index as i32` 在大表下还有理论截断风险。注意这不是 errno 映射问题（-1 不是 errno 值，且"没找到"不是错误语义），Rust 语义应是 `Option<usize>`。
   最小修复：签名改 `fn lookup(table: &[Entry], key: u32) -> Option<usize>`，未找到返回 `None`。
   严重度：P1（修复一行，形态明确）。

### T06 — doc-incomprehensible.md（阳性：读者理解障碍与证据缺失）

1. **"页表已经就绪，所以不需要额外处理"——无证据的关键因果断言** — 位置：L5。
   问题："就绪"无定义（谁在切换前保证了什么？），"不需要额外处理"是无锚点全称断言：真实地址空间切换后 TLB 陈旧项、内核栈、每 CPU 状态都是待处理项；这句要么隐含未说明的前提（如内核映射在所有地址空间对称），要么就是错的。项目文风规则要求事实断言带锚点——此处零锚点（无 C 源路径、无代码引用）。
   最小修复：写明"就绪"的来源与责任方（如：activate 时已写 CR3 并 flush，引用对应函数与 `minix3/` 源位置），把全称否定改为可验证的具体陈述。
   严重度：P1。

2. **切换动作无主语无对象，读者无法建立场景** — 位置：L3–5。
   问题：整节三句话没说谁在切换（调度器？VM？）、切换什么（CR3？mm 结构？）、入口在哪。"切换之后内核继续执行"对未知读者是零信息（任何切换之后都如此）。教学文档开节必须建立场景。
   最小修复：补一句触发点与对象（"当调度器从 A 换到 B 时，……"级别即可）。
   严重度：P1（读者理解障碍是本样本主目标）。

3. **"后续的收尾工作由下一节说明"——悬置指代、零信息过渡** — 位置：L7。
   问题："收尾工作"与"下一节"都未命名，读者此刻无从核对；下一节移动/改名后这句即成断链。
   最小修复：改具体引用（"TLB 收尾见 §锚点"）或删除。
   严重度：P2。

4. **整节无码无锚，不满足机制文档承载门** — 位置：整节。
   问题：按项目教学构件承载门（机制文档的分析/实现章无码 = P1），本节谈论地址空间切换机制却零代码引用、零 C 源对照，信息密度近零。
   最小修复：挂上关键函数/源码锚点，或并入相邻节。
   严重度：P1。
