## FINDING READER-A-01（P1）

- 位置：§3.4.3（`BOOT_HANDOFF_V1_VERSION` 的定义段）与 §3.4.1（v10 删除说明）。
  - §3.4.3：「**信封版本号**（`BOOT_HANDOFF_V1_VERSION`，当前 9）随信封内布局变更递增、收发双方精确比对——本文出现的"版本 8→9"都是后者」
  - §3.4.1：「`BOOT_HANDOFF_V1_VERSION` 9 → 10，收发两侧精确比较，v9 与 v10 互相拒收。」
  - 另有两处同向陈述：§3.4.3「因此尺寸与信封版本 9 不变」；§4.6「旧生产者写 0 仍可读，信封版本仍为 9（见 §3.4.3）」。
- 严重度：P1
- 问题：同一个计数器在同一篇里同时被说成"当前 9"和"9 → 10、v9 与 v10 互相拒收"。读者无法判断当前信封版本到底是 9 还是 10，也无法判断 §3.4.3 关于"本文出现的 8→9 都是它"的枚举是否还完整。另有一层同源歧义：`v9`/`v10` 这组裸标签同时被用于两个独立计数器——wire 信封版本与 `VmBootHandoff` 版本；全文只有 §2.4.1.4 的一处括号加了限定词，§3.4.1 的「v9 已删除 `kern_ident`」与 §3.4.5 的「v9 把两件事分开」指的不是同一个 v9，读者只能按符号名猜。
- 影响：这是跨镜像 ABI 的二进制兼容判据。若读者按"当前 9"理解，会把 v10 发送侧/接收侧的拒收行为当成文档笔误；若按"当前 10"理解，则 §3.4.3 的"当前 9"和 §4.6 的"仍为 9"都是错值。后续照文档核对 `magic`/`version` 校验时，无法确定该比对 9 还是 10；遇到裸 `v9` 时也无法确定该查哪个常量。
- 证据或推理：只据文档内两句直接冲突：一句写「当前 9」，另一句写「9 → 10 ... v9 与 v10 互相拒收」。两处都点名 `BOOT_HANDOFF_V1_VERSION`，不是两个计数器。计数器重名则由 §2.4.1.4 的「它与 §3.4.3 的 arena 信封版本 `BOOT_HANDOFF_V1_VERSION` 是两个独立计数器」与后文两处裸 `v9` 的不同指代共同证明。
- 最小修复：指定一个权威值并全篇改齐。若 D-062 的 v10 已落地：把 §3.4.3 的「当前 9」改成「当前 10」，把「本文出现的"版本 8→9"都是后者」改成「8→9 与 9→10 都是后者」，把 §4.6 的「仍为 9」改成「仍为 10」，并在 §3.4.3 加一句「全文凡写'信封版本'处均指此值」。若 v10 未落地：删掉 §3.4.1 的 9→10 陈述及所有 v10 措辞。无论哪一侧，都把裸 `vN` 改成带限定词的写法（`wire vN` / `VM handoff vN`），至少在 §3.4.1 的 `v9 已删除 kern_ident` 与 §3.4.5 的 `v9 把两件事分开` 两处。
- 置信度：高
- 是否需源码核实：是（文档冲突已足以判缺陷；定值需看 `BOOT_HANDOFF_V1_VERSION` 的实际取值）
- 若我错了：除非「当前 9」指的是另一个未点名的计数器——但它与 §3.4.1 的 `BOOT_HANDOFF_V1_VERSION` 同名，且 §3.4.3 自己称其为"信封版本号"。
- 读者验收清单条目：4（版本号只有一个权威口径，跨节引用同一口径）

## FINDING READER-A-03（P2）

- 位置：§3.4.3 的 arena 注释（信封 + wire + source 的合计）。
  - 原文：「信封与各组分区合计 30624 B（信封 256 B + wire 分区 7616 B + source 分区 21312 B）≤ 32768，余 3584 B。」
  - 下一行同段：「v10 再减 1440 B，已用 29184 B（= `WIRE_SOURCES_END`）。……余量 3584 是 `ARENA_CAP` 与 29184 的差」。
- 严重度：P2
- 问题：同一段里，括号内三项相加是 256 + 7616 + 21312 = 29184，而句首写"合计 30624 B"；32768 − 30624 = 2144，也不是同句写的"余 3584 B"。30624 是 v9 的合计（含 1440 B startup 分区），29184 才是 v10 的合计；这句话把 v9 的总数、v10 的分项和 v10 的余量拼在了一起。
- 影响：读者按括号逐项验算会得到 29184，与句首 30624 和"余 3584"三方不一致；若读者相信 30624，会认为余量只有 2144 B，与下一行和 §3.4.1 的 3584 B 矛盾。arena 预算余量是后续新增分区时的硬上限，这个数不能有歧义。
- 证据或推理：纯算术：256 + 7616 + 21312 = 29184；32768 − 29184 = 3584；32768 − 30624 = 2144。§3.4.1 也写「八页 arena 的设计余量从 2144 B 变成 3584 B」，可交叉确认 v10 余量是 3584。
- 最小修复：把句首「合计 30624 B」改成「合计 29184 B」（保留括号与"余 3584 B"），或在句首明确标注"v9 合计 30624 B / v10 合计 29184 B"并分两句写。
- 置信度：高
- 是否需源码核实：否
- 若我错了：除非"信封 256 B"不是 256 而是 1696，或 wire 分区不是 7616——但同一行与 §3.4.3 的分区注释都给出 256/7616/21312，且下一行明写 29184 与 3584。
- 读者验收清单条目：4（计数只有一个权威口径）
