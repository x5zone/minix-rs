## SUGGESTION

- §1.1 的“框 1 = 可用内存清单（最终形态已排除内核与模块占用区）”与 §3.2.1 的“`memmap`……列表**不保证已扣除全部占用区**”同名不同阶段；且 §3.2.1 又把 `reserved_regions` 定义为“可用但不可分配”，它并不属于 C 框 1 那个可分配 free list。建议在 §1.1 表第一行补一句“交接时是 `memmap`（可分配，尚未扣尽）+ `reserved_regions`（可访问、不可分配）两张表；扣完占用区后才等价于 C 的框 1”，并把“框 1”限定为 C 侧最终 free list。
- §3.2.1 的 `memmap` 单元格约四百字，且同句重复“内核不保留可变 memmap 副本”两次；建议拆成“表里有什么 / 哪些腿已扣 / 消费前还要做什么”三条 bullet。
- §4.2.1 动作 ID 与时间拍两套编号并存，动作 2 占两拍，九动作对十拍；建议在表头加一句“按时间读只看第二列”，或把时间列改成 1–10 的单调序号。
- §4.4 的直核面门链“strict → pre-table → postconditions → boot_validate”漏掉了 `store_kernel_info`（§3.6 的 `arch_boot_finish` 代码与 §3.7 都把它放在 postconditions 与 boot_validate 之间）。这条正是 §3.7“两条腿的 store 与 boot_validate 次序相反”的关键对比，建议补上，否则初学者看不到直核面先存后校验。
- §3.2.1 的 `RamAuthority::DTB`、§4.4 的 `DtbBootInput`、§4.2 的 `InputObjectId::UefiMemoryMap` 在同一语义位上出现三个名字；读者无法判断它们是同一值的三层名字还是三个不同对象。建议加一句“三者是同一权威来源在结构体、构造参数、wire 标签三层上的名字”，或统一命名。
- §2 约九百行，而读者目标在 Rust 交接；建议在 §1.0 导读加一条“只关心 Rust 设计可先读 §1.3 + §2.8，再进第 3 章”，让初学者有可执行的跳过路径。

## RETOLD

核心矛盾：引导器知道“哪些物理内存可用”和“内核被装在哪里”，但内核不能直接使用引导器给的指针——跨镜像时两边地址空间不同，同镜像时指针的生命周期也不保证。于是交接必须把事实按值搬过边界：三份数据（可用内存清单及其来源、内核位置记录、交接结构），四条不变量（值不指针、来源可追、所有权单一、校验先于消费）。

状态转移：收集（读内核与模块、取内存图、分成可用与保留两张表并记来源）→ 记账（把内核与模块占用的区间从可用清单里切掉；C 侧把内核临时当成第 M+1 个模块，用同一套检查与切除）→ 构造载荷（发送侧自有存储一次装好六类载荷；跨镜像序列化进 arena 的信封与分区，直核面直接给借用视图）→ 交付（跨镜像只递 arena 物理基址，直核面同镜像直接调用）→ 接收（先过来源覆盖、后置条件与建表前校验门——各腿门集不同，再深拷进内核 `.bss` 的六个落地区，之后才建表、开分页、进 `kmain`）→ 换手（引导期页表页分配器注册一次，VM 起来后换 VM 的；bump 区间整段算内核保留；C 的可回收引导段在 Rust 侧不存在，字段删除）。

边界：本篇到“字节送进内核入口”为止；链接布局、ELF 摆放、运行期映射、换栈归 02 篇；同一段 `pre_init` 里取参数属本篇、建表属 02 篇；arena 的生命周期到解码为止；bump 的游标用三元组 resume 交接。以上能说出；说不出的是 Direct Map 的具体建立过程与页表布局（文档明确划给 02 篇），以及 ELF 段语义（文档没有从零讲，见 READER-A-01）。
