# READER-A 冷读报告（D01 · R31 基线）

## 读法与边界

- 输入只有两个文件：目标文档 `rewrite-notes/01-stage-kernel/01-boot-shim-bootstrap.md`（3554 行）与读者画像 `reader-profile.md`。
- 按画像从头通读到尾，一次到底；不查源码、不看 diff、不看其他文档与历史评审。
- 读者设定：懂 OS 基本概念（特权级、分页、进程切换）与 Rust 基本语法，能读 C 与 `mov`/`push`/`call` 一级汇编；不需要预先了解 Minix3 与 UEFI。
- 判定口径就是任务给的 10 条读者验收清单。凡是"读者会停一下、回翻、或者按文中步骤复算得到不同结果"的地方都算障碍；纯偏好放 `## SUGGESTION`。
- 局限：不能读源码意味着所有"这条断言对不对"只能做文内自洽检查与可复算推演；下面每条都给了反证路径，交给有源码权限的角色复核。

## 总体判断

主线是可以跟着走完的：§2 的 C 链条（设栈 → 拷参数 → 记账 → 切占用 → 建表 → 开分页）每一步都有"不变量 + 前提 + 证据"三件套，§3 的设计取舍大多给了可复核的反事实推演，§4 的代码引文与 §5 的覆盖表能对上号。冷读过程中没有出现"读不下去"的段落。

本次共 12 条发现：**0 条 P1、3 条 P2、9 条 P3**。三条 P2 分别是：§1.1 开头对 boot2 分页状态的事实断言与同节阶段表自相矛盾；§2.3 的 `xboard=2` 例子漏了"它不是首条记录"这个前提，按字面复算得不到文中结论；§3.4.3 的 arena 字节账在 v8→v9 之间对不上（30624 + 6144 > 32768）。其余 P3 集中在术语首次使用、跨节引用清单不一致、重复叙述与一处引文行号。

## FINDING READER-A-02

**位置**：§2.3，第 464 行。

**原文摘录**：

> 「例如 `param_buf` 里先有 `xboard=2`，内核再写 `board=` 时，中段 `board=2` 会被删掉，后一条 `arch=i386` 的前半截被补进原位，留下伪记录 `xarch=i386`。」

**问题**：这个例子要成立，`xboard=2` 必须是**第二条或更后**的记录。按 §2.3 自己推出来的删除扫描行为：扫描从 `bigbuf` 开始，第一条记录按 `name=` 前缀从记录起点比较（`xboard` 对 `board` 不匹配）；只有离开一条记录时那个 off-by-one 才会把指针推到**下一条记录的第二字节**。所以如果缓冲区里只有 `xboard=2` 一条，中段匹配根本不会发生，`xarch=i386` 也不会出现。文中只写"先有 `xboard=2`"，没有写"它不是首条"，按字面复算的读者会得到与文中不同的结果，进而怀疑整段"第二种表现"的推演。建议补上"`xboard=2` 之前还有别的键"这个前提（一行即可）。

**命中清单**：第 3 条（结论有前提）。

**严重度**：P2。

**反证路径**：用 `param_buf = "xboard=2\0\0"` 逐行走一遍 `mb_set_param` 的删除扫描：外层 `while (*p)` 在 p=0 比较 `xboard` 与 `board` 不匹配，`while (*p++)` 越过 NUL 后 p 落在末尾之后，独立 `p++` 再走一步，扫描结束，无删除。再把 `param_buf` 改成 `A=1\0xboard=2\0arch=i386\0\0` 重放，才能得到文中的 `xarch=i386`。

## SUGGESTION

以下不是缺陷，是冷读时觉得可以少花读者力气的写法。

- **§1.2 的图注把三套约定叠在一起**（竖向排列 = 布局、主链 = 阅读顺序、箭头 = 依赖方向），用两段文字才讲清。若在框表里加一列"依赖谁"，图注可以缩到一句"竖排只是布局"。
- **§3.4 标题的"四个附节"与子节编号错位**：3.4.1 是正文，3.4.2–3.4.5 才是那四个附节，但读者看到的编号是 3.4.1–3.4.5，第一反应会数出五个。改成"（附节 3.4.2–3.4.5）"更省一次回读。
- **§2.4.1 的"消费者"一词两用**：小节标题里的"两个消费者"指两个从记录取址的函数，小节末"各有其消费者"又指这些函数的调用者。建议后者改成"调用者"。
- **§3.7 的计数表里"生产腿 5"与"架构×链五行 5"成员完全相同**，读者会花时间找它们的差别；合成一行、在备注里说明"§4.8 的表按此五行排"即可。
- **§4.2 的信封时序有一个未交代的缝**：动作 5 说"标量信封先定稿"，但信封里有 `memmap_byte_len`/`reserved_regions_byte_len` 两个载荷长度，而 memmap/reserved 的载荷要到动作 6 配对循环才写。读者会问这两条长度由谁回填。若确实由分类器回填，建议在动作 6 的约束里加半句；若在省略段里，至少点一句"长度回填见省略段"。
- **§3.4.1 的 `reserved_regions` 语义写成"可用但不可分配"**，容易与 `memmap` 的"可用"混。它实际收的是 `LOADER_*`/`BOOT_SERVICES_*`/`ACPI_RECLAIM` 这类"运行期可经 Direct Map 访问、但不得再分配"的区间；改成"固件占用但可在 DM 下访问、不得分配"更贴近下文。
