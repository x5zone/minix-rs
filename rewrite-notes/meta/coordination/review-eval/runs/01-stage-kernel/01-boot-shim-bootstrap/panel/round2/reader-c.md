## 二、条目

### C2-01 source 分区例外的适用范围被写成无条件

- **位置**：§3.2.3 第 1315 行（“source 分区例外，只写 wire，`BootStorage` 的 source 切片为空（见 §3.7）”）；对照 §3.7 第 1837 行、§4.5 第 2478 行、§3.2 术语第 1062 行。
- **严重度**：高（直接推翻 R1 C-4 想修的“例外只限 UEFI 腿”）。
- **问题**：§3.2.3 的句子主语是“发送侧”，没有限定 UEFI。按字面读，三条 v1 发送腿的 source 分区都只写 wire、`BootStorage` 的 source 切片都为空。但 §3.7 说“**UEFI 腿**的 source 分区由分类器直写 wire，storage 的 source 切片为空”；§4.5 说“发送侧 `BootStorage` 的 source 槽是 40（DTB 收集器输入上限，超过 fail-closed）”；§3.2 术语又说“它拥有实际走 `fill_*` 的腿上的六类载荷（**UEFI 腿**的 source 分区由分类器直写 wire）”。三处都把例外限定在 UEFI 腿，只有 §3.2.3 写成无条件。
- **影响**：实现者若照 §3.2.3 做，会让 U-Boot shim 的 DTB source 收集器不写 `BootStorage` 的 40 槽，或者反过来认为 §4.5 的 40 槽是陈旧数字；两者都会破坏“语义表住 `BootStorage`、arena 只有一份 wire 表示”这条 I3 论证。审阅者也会在“例外到底覆盖哪条腿”上得到两个答案。
- **证据**：§3.2.3 第 1315 行 vs §3.7 第 1837 行 vs §4.5 第 2478 行 vs §3.2 第 1062 行；四处的限定词只在 §3.2.3 缺失。
- **最小修复**：把 §3.2.3 那句改成“**UEFI 腿**的 source 分区例外，只写 wire、`BootStorage` 的 source 切片为空；U-Boot shim 的 DTB source 记录仍经 `fill_source_records` 写 `BootStorage` 的 40 槽，再序列化进 wire”。一句话即可，其他节不动。
- **置信度**：高（内部交叉引用直接冲突，不依赖源码）。
- **若我错了**：若 U-Boot shim 的 source 记录也确实绕过 `BootStorage`、§4.5 的“发送侧 40 槽”只是别的东西，那么应改 §4.5 与 §3.7，而不是改 §3.2.3；两种读法必有一处要改。

### C2-02 aarch64 UEFI 的“走到 kmain”证据与 §5.4 判据不一致

- **位置**：§5.1 I3 行第 2639 行；对照 §5.4 第 2661 行、§5.5 第 2670 行、§6.1 第 2759 行。
- **严重度**：中高（门覆盖结论被夸大，属于 R1 C-8 的同一类问题）。
- **问题**：§5.1 I3 的“真机证据”列说“走到 `kmain` 的证据覆盖 x86 UEFI、**aarch64 UEFI 正常形态**与 riscv64 U-Boot shim”。但 §5.4 的 aarch64 UEFI 判据是“前两条固定标记 + 第三条变体（`memmap source`，或无 DTB 配置下的 `DTB preflight failed` fail-closed 路径）”，其中前两条是 `kernel loaded (entry staged)`、`12 boot modules loaded`，第三条 `memmap source` 按 §6.1 也是**发送侧**在 EBS 之后打印的行；整行没有 `resuming high-half boot` 或 `entering scheduler`。§5.5 又写“不把 fail-closed 形态算成走到 `kmain`”。于是 aarch64 UEFI 的正常形态（`memmap source`）按 §5.4 的字面判据也只证明到发送侧，不证明接收侧已起。
- **影响**：I3 的证据矩阵把“有门覆盖”升级成“走到 `kmain`”，而 §5.4 的判据不支持；aarch64 UEFI 的真实成功路径可能其实未被门锁住。这会影响“五条腿都有门覆盖”这一整段结论的可信度。
- **证据**：§5.4 第 2661 行的判据列只有前两条固定标记 + 第三条变体；§6.1 第 2759 行说明 `### minix-rs kernel-image: resuming high-half boot…` 才是“接收端已进入 Rust 面”的标记，而 §5.4 的 aarch64 行没有它；§5.5 第 2670 行的“不把 fail-closed 形态算成走到 `kmain`”进一步排除了把 fail-closed 分支当作成功路径。
- **最小修复**：二选一。(a) 在 §5.4 的 aarch64 判据里补上接收侧标记（至少 `resuming high-half boot`，若要“走到 `kmain`”再加 `entering scheduler`），并同步 §6.4 的注释；(b) 若脚本确实只查三条，把 §5.1 I3 改成“aarch64 UEFI 正常形态只证明到发送侧/分类点，未证明 `kmain`”，并把“走到 `kmain` 的证据”限定为 x86 UEFI 与 riscv64 U-Boot shim。
- **置信度**：高（判据列与结论列的直接对账，不需要脚本）。
- **若我错了**：若 `test-shim-bootmarks-aarch64.sh` 内部其实还查了 `resuming high-half`/`entering scheduler`，只是 §5.4 的判据单元格漏写，那么错在 §5.4 的判据列，修法仍是把标记补进该单元格；结论列不用改。

### C2-03 §4.8 的 Direct Map 链把直核面与 v1 接收面混成一条

- **位置**：§4.8 第 2571 行；对照 §3.6 第 1784–1792 行的 `resume_additive` 文档注释、§3.6 第 1805 行、§4.4.1 第 2362 行。
- **严重度**：中（会误导读者以为 v1 接收面重建 bootstrap 根）。
- **问题**：§4.8 写“在本篇的启动路径里，Direct Map 覆盖建立发生在启动信息存储之后、进入 `kmain` 之前：`store_kernel_info` → `arch_boot_impl`（其中的 Direct Map 相关步骤是 `build_bootstrap_root_and_enable` → `establish_boot_dm`）→ `jump_to_kmain`”。这条链只对**直核面**成立：§3.6 说 `arch_boot_finish` 是直核家族共用尾部，跨镜像的发送/接收两端都不经它；v1 接收面走 `resume_additive`，其文档注释明确说它只做 additive 阶段，且“must NOT rebuild the tables: calling `build_bootstrap_root_and_enable` here would `new_from_page(root_page)` and zero-fill the *active* root”。v1 接收面的实际链是 `… → resume_additive（store → establish_boot_dm）→ jump_to_kmain`，没有 `arch_boot_impl`，也不能有 `build_bootstrap_root_and_enable`。
- **影响**：§4.8 是读者理解“Direct Map 在交接中的位置”的概念入口；把它写成通用链，会让读者把直核面的“建根→开分页→建 DM”套到 v1 接收面，正好撞上 §3.6 用整段反向推演禁止的“重建活动根”。这也会掩盖“接收侧只做 additive 阶段”这条关键约束。
- **证据**：§3.6 第 1784–1792 行的引文（“validate/register allocators, land the KernelInfo into this .bss, establish the direct map, then enter kmain. It must NOT rebuild the tables…”）；§3.6 第 1805 行的“接收侧按干净启动重建 bootstrap 根会清掉活动根”的反向推演；§4.4.1 第 2362 行把 v1 接收面写成 `resume_additive` 链，不含 `arch_boot_impl`。
- **最小修复**：在 §4.8 这句前加“直核面”限定，并补一行 v1 接收面：“v1 接收面的对应链是 `resume_additive` 内 `store_kernel_info` → `establish_boot_dm` → `jump_to_kmain`，不调用 `arch_boot_impl`/`build_bootstrap_root_and_enable`（活动根只做加法）”。或者改成两行小表。
- **置信度**：高（§3.6 的禁止语句是本文最强硬的约束之一，§4.8 的通用链与它直接冲突）。
- **若我错了**：若 `resume_additive` 内部也调用一个同名 `arch_boot_impl` 且该分支不建根，那么 §4.8 的链可能只是省略了分派；但即便如此，§4.8 仍需说明“接收面不走建根分支”，否则读者无法从文字上排除重建活动根。

### C2-04 DTB preflight 变体有三种叫法，`DTB_CFGTABLE=1` 未定义

- **位置**：§5.4 第 2661 行（“无 DTB 配置下的 `DTB preflight failed` fail-closed 路径”）；§6.4 第 2860 行（“`DTB_CFGTABLE=1` 形态则是 DTB preflight 拒绝行”）；§5.1 I3 第 2639 行（“aarch64 UEFI 的 `DTB_CFGTABLE` 形态”）。
- **严重度**：低中（同一门的两处说明不能直接对上）。
- **问题**：同一段判据在三处被叫成三个名字。`DTB_CFGTABLE=1` 在本文没有定义，读者无法判断它是不是“无 DTB 配置”的那个固件配置；§5.4 说“无 DTB 配置”，§6.4 说“`DTB_CFGTABLE=1` 形态”，§5.1 又说“`DTB_CFGTABLE` 形态”。如果 `DTB_CFGTABLE=1` 是“DTB 通过 Configuration Table 提供”的构建/运行配置，那么它字面上不是“无 DTB”，两处描述就可能指不同变体；如果它其实是“该固件配置已声明无 DTB”的脚本变量，则三处应统一用同一个名字。
- **影响**：§5.4 是判据权威表，§6.4 是操作入口；操作者按 §6.4 找“`DTB_CFGTABLE=1` 形态”时，无法从 §5.4 确认这个形态的 PASS 条件（尤其是“前两条固定标记同时出现且该固件配置已声明无 DTB”这个额外前提）。这会直接影响 aarch64 UEFI 门的判读。
- **证据**：三处文本本身；本文没有 `DTB_CFGTABLE` 的定义段，§5.4 的“无 DTB 配置”与 §6.4 的“`DTB_CFGTABLE=1` 形态”之间没有等价声明。
- **最小修复**：在 §5.4 或 §6.1 的术语处加一句“`DTB_CFGTABLE=1` 指该固件配置不提供 DTB（脚本变量名），对应本节所说的‘无 DTB 配置’”；然后把 §5.1/§5.4/§6.4 三处统一成同一个名字（建议都用“无 DTB 配置（`DTB_CFGTABLE=1`）”）。若实际是两个变体，则在 §5.4 分成两行并各给 PASS 条件。
- **置信度**：中高（命名不一致确定；两处是否指同一变体需要脚本才能最终确认，但本文没有给出可对上的定义）。
- **若我错了**：若 `DTB_CFGTABLE=1` 在脚本里就是“无 DTB”的开关名，那么问题只是措辞，修法不变；若它是另一个变体，则 §5.4 漏了一个变体，修法是在表中补行。

- **严重度**：低（排版/可读性，但影响证据矩阵的读法）。
- **问题**：第 2633 行是表头与分隔行，第 2635 行是 I1 行，第 2636 行是一段不带 `|` 的普通段落，第 2638 行起才是 I2/I3/I4 行。按 GFM，表格在第 2636 行结束；I2–I4 行不再属于这张表，可能被渲染成普通文本或另一张无表头的表。

### C2-06 “一条依赖”与“两条依赖”对不上

- **位置**：§1.1 第 63 行（“两者只有一条依赖：框 2 的区间用于裁剪框 1，框 1 不进入框 2”）；§2.3 第 340 行（“这正是 §1.1 那两条依赖的根据：框 2……不接收框 1，反过来倒是框 2 的区间要拿去把框 1 裁短”）。
- **严重度**：低（术语/计数不一致，不影响主论证）。
- **问题**：§1.1 明确说“只有一条依赖”，并把“框 1 不进入框 2”作为同一条依赖的否定边界；§2.3 回指时称“那两条依赖”。按 §1.1 的写法，“框 2 裁剪框 1”是一条正依赖，“框 1 不进入框 2”是一条边界条件，不是第二条依赖。两处对“依赖”的计数不同。
- **影响**：读者若按 §2.3 回查 §1.1，会找不到“两条”中的第二条；这会影响“框 1/框 2 只有一条依赖”这一小结论的可信度。它不影响 D1–D5，但属于同一段的因果表述。
- **证据**：两处原文；§1.1 用“只有一条”，§2.3 用“那两条”。
- **最小修复**：把 §2.3 改成“这正是 §1.1 那条依赖（外加一条否定边界：框 1 不进入框 2）的根据”，或把 §1.1 改成“一条正依赖、一条边界：……”。统一成一种计数即可。
- **置信度**：高（文本直接对照）。
- **若我错了**：若作者把“框 1 不进入框 2”也算作一条依赖，那么 §1.1 的“只有一条”是错的；无论哪种，两处必须统一。

### C2-07 U-Boot arena 的“same bump pool”与“两个独立游标”需要一句合并说明

- **位置**：§3.5.1 第 1554–1557 行（`BootPrepareResult.bump` 注释“allocated from the same bump pool after the module landings”）；§3.6 第 1776 行（“由 `bump_alloc_pages`……另行分配（它与 `BootAlloc` 是两个独立游标）”）；§4.6 第 2535 行（“两个实例不共享游标……shim 的游标跨过子区间末尾（模块与 arena 在子区间之外）”）。
- **严重度**：低（语义可通过合并三处得到，但单看任一处会误读）。
- **问题**：`BootPrepareResult` 的注释说 arena 从“same bump pool”分配，§3.6 说它“另行分配”且与 `BootAlloc` 是两个独立游标，§4.6 说 shim 的游标跨过页表子区间末尾。三处可以相容：同一个物理池/区间，两个分配器（shim 的 `bump_alloc_pages` 与接收镜像的 `BootAlloc`），arena 在模块之后、`bump_end` 之外。但本文没有一句话把“same pool”与“two cursors”同时说清。
- **影响**：读者可能把“same bump pool”理解成 arena 也在 `boot_alloc_region()` 的 1024 页里，从而与 §3.6 的“其起点不低于 `bump_end`，因此在 1024 页 `boot_alloc_region()` 区间之外”冲突；也可能把“两个独立游标”理解成两个不同的物理池，从而与“same pool”冲突。这会影响对 U-Boot 腿 arena 归属与扣除的读法。
- **证据**：三处原文；§3.6 的“另行分配”与 §3.5.1 的“same bump pool”之间没有桥接句。
- **最小修复**：在 §3.6 那句后加“（‘same pool’指同一物理区间，不是同一个游标；shim 用 `bump_alloc_pages` 从模块落点之后发 arena，接收镜像的 `BootAlloc` 只续用页表子区间，两者游标独立）”，或在 §3.5.1 的注释后加同义一句。
- **置信度**：高（三处文字本身足以支持这种读法；缺的只是合并句）。
- **若我错了**：若 `BootPrepareResult.bump` 的“bump pool”在类型上就是 shim 的模块放置池、与 `BootAlloc` 的页表子区间不是同一区间，那么“same pool”与“两个独立游标”并不冲突，但仍应写明“arena 在 `bump_end` 之外”，否则读者无法从 §3.5.1 单独得到 §3.6 的结论。

### C2-08 wire 8→9 的版本定义与所述变更不完全对齐（低置信，供作者判断）

- **位置**：§3.2.3 第 1274 行（“信封版本号……随**信封内布局变更**递增……本篇出现的‘版本 8→9’与‘9→10’都是后者”）；同节第 1301–1311 行的 arena 注释（“v9 删掉了 v8 的 6144 B（6 KiB）语义工作分区”）。
- **严重度**：低（版本纪律的表述问题，不影响当前 v10 的收发拒收）。
- **问题**：本文把信封版本号定义为“随信封内布局变更递增”，但唯一描述的 8→9 变更是删掉 arena 里的 6144 B 语义工作分区——这是 arena 分区布局，不是信封字段。若 8→9 确实只改了 arena，那么“信封版本号”这个定义就太窄；若 8→9 还改了信封字段，本文没有写出是哪个字段。
- **影响**：读者无法从本文判断“什么变更必须 bump 信封版本、什么变更只需改 arena 偏移”；未来增删分区时容易把版本纪律用错。它不影响 v10 的“收发精确比较、v9/v10 互相拒收”这一结论。
- **证据**：第 1274 行的定义只提“信封内布局”；第 1301–1311 行把 8→9 的变更写成“删掉 6144 B 语义工作分区”；全文没有 8→9 的信封字段变更清单。
- **最小修复**：把定义改成“随信封或 arena 的 wire 布局变更递增”，或在 8→9 处补一句“同时删除了信封字段 X/Y”（若确实有）；若 8→9 只是 arena 变更，则在定义处加“arena 分区布局也算 wire 布局”这一句。
- **置信度**：中低（取决于 8→9 是否还有本文未写的信封字段变更；但“定义只写信封、例子只写 arena”这一不对齐是确定的）。
- **若我错了**：若 8→9 另有信封字段变更只是本文省略，那么定义本身没错，错在变更清单不完整；修法仍是补清单或补“arena 也算 wire 布局”的说明。

## 三、未展开的低置信观察

- §3.1.1/§5.1/§5.4 的“五条腿”与“五条门链”成员不同，本文已在 §3.6 末尾明确警告，不另报。只提醒：§5.1 I3 的“五条腿都有门覆盖”与 §5.4 的五条脚本不是同一组五条，读者容易把“有门”读成“每条生产腿都有对应的成功门”；本文没有在 §5.1 行内重复这条换算，建议在 I3 行加一句“门链成员见 §3.6 末尾的换算表”。（低）
- §6.1 的 `kernel: v0 enter` 行“适用腿”写“两个直核面 + 三条 v1 发送腿 + v1 接收腿”，而 §4.4.1 写“三条 v1 接收腿”。若“v1 接收腿”是类别名而非计数，建议写成“三条 v1 接收腿”以免被读成一条。（低）
- §3.2.2.2 说 `KinfoStruct.user_sp` 不是语义消费者，§4.4 又说 `GET_KINFO` 的 `user_sp` 读 `USER_STACK_TOP`。两者可并存（字段被填但无消费者），但建议在 §4.4 那行补“仅布局位，无 Rust 读者”，否则容易被读成“`GET_KINFO.user_sp` 是活读者”。（低）

## 四、结论

R1 的六项主题里，“统一存储去向”“D1–D5 范畴”“U-Boot arena”基本自洽；“source 分区例外”与“门覆盖”各有一处仍未收敛的跨节矛盾（C2-01、C2-02）；“DTB preflight 变体”是命名不一致（C2-04）。新发现里最值得先修的是 C2-03（§4.8 把 v1 接收面写成会走建根链），因为它与 §3.6 的“禁止重建活动根”直接冲突。其余为低严重度的结构/措辞问题，可随本轮一并处理。
