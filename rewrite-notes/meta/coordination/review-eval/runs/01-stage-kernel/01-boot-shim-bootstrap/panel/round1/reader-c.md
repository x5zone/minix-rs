## FINDING C-1（medium）：I1/I3 的“五条腿统一消费次序”与 §3.7 的“两条腿次序相反”直接冲突

- 节号+原文：§1.1 第 3 行“两个直核腿同镜像但仍走同一落地区（统一消费次序）”；§1.3“两个直核腿同镜像，仍用同一套落地区深拷（统一消费次序）”。
- 对照：§3.7“直核面由 `arch_boot_finish` 先 `store_kernel_info`、再进 `arch_boot_impl` 的 `boot_validate_and_prepare`；v1 接收面在 `resume_additive` 里先 `boot_validate_and_prepare`、后 `store_kernel_info`。**两条腿的 store 与 boot_validate 次序相反**。”§4.4.1 的逐腿链同样把 store 放在直核链中段、v1 链末段。
- 问题：概述两次把“统一消费次序”当作三份数据必须按值深拷的理由之一，读者会由此推断两族腿的门/落地顺序一致；实现章明确说相反。若“统一消费次序”仅指“最终都从私有副本消费”，措辞与 §3.7 的“次序”撞词，且没有限定语。
- 影响：读者按概述判断 I4“校验先于消费”时，会把两族腿当成同一套门链，无法解释为什么 v1 面不经过 `validate_before_tables`；也削弱“统一落地区”这一设计理由的可信度。
- 证据：§1.1 表格第 3 行；§1.3 第二条；§3.7 第一段；§4.4.1 开头两行。四处均在同一文档内，无需源码。
- 最小修复：把 §1.1/§1.3 的“统一消费次序”改成“统一存储去向（都在 `.bss` 落地区），但校验与落地的先后按腿不同，见 §3.7/§4.4.1”。
- 置信度：高（文本对照；若作者原意是“消费点统一在 kmain”，那也应换成这个词）。
- 若我错了：若“消费”在作者术语中专指 `kmain` 读取，而 `store/validate` 不算“消费”，则两句可并存；但 §3.7 自己用“消费前不等于发布前”把消费定义为建表/映射/分配，此时 store 也不算消费，冲突仍在措辞层。

## FINDING C-2（medium）：§2.8 把 D1–D5 统称“三份交接对象之间的次序约束”，与五条的实际对象不符

- 节号+原文：§2.8“三份交接对象之间的次序约束共五条（D1–D5）”。
- 对照：§1.4 定义 D1=内存清单先于建表输入、D2=内核位置先于清单裁剪、D3=页表先于开分页、D4=交接结构先于 `kmain`、D5=恒等映射先于内核映射。
- 问题：三份交接对象是 memmap、内核位置记录、`KernelInfo`（§1.1 表）。D1 的另一端是“建表”，D3/D5 的两端都是页表动作，D4 的另一端是 `kmain`，都不是三份数据之一。只有 D2 是两份数据之间的关系。把五条统称“三份交接对象之间”是范畴错误，读者会去找“第三份数据与谁排序”，找不到。
- 影响：读者无法建立 D1–D5 的分类轴（哪些是数据依赖、哪些是动作依赖），而 §1.2 又说“用 I1–I4 判断交接是否成立”、§1.4 说 D1–D5 是本篇的次序约束，概述与归纳因此对不上。
- 证据：§1.1 三行表；§1.4 D1–D5 定义；§2.8 该句与随后五条 bullet。
- 最小修复：改为“启动期的五条次序约束（跨三份交接数据与建表/进入动作）”，或在五条前加一行“D1/D3/D5 约束动作，D2/D4 跨数据与动作”。
- 置信度：高。
- 若我错了：若“交接对象”被作者扩展为包含页表与入口，则 §1.1“只有三份数据”需改；两处必有一处用词失配。

## FINDING C-3（medium）：U-Boot shim arena 归属自相矛盾——“同一物理区间”与“不在该区间”

- 节号+原文：§3.6“U-Boot shim 腿的 arena 由 `bump_alloc_pages` 从同一物理区间另行分配……它排在 1024 页的 `boot_alloc_region()` 区间之后（起点不低于 `bump_end`），因此**不在**该区间的整段扣除内”。
- 问题：同一句先说是“同一物理区间”，后说“不在该区间”。两个“区间”的指代没有名字：前者可能指 U-Boot 可用内存/模块落点所在区间，后者指 `boot_alloc_region()` 的 1024 页区间；但字面读是同一对象。读者无法判断 arena 是否落在 VM 扣除表覆盖的范围内。
- 影响：这是“arena 帧可在解码后重新发给 VM”这条因果链的前提。前提读不清，§4.6 的 poison 测试到底钉住了哪个区间就无法核对；也影响读者判断“为什么扣除表没有单独排除 arena”。
- 证据：§3.6 该 bullet；§3.4 扣除表与 §4.6 的游标说明（未逐行展开，但本句自身已构成指代冲突）。
- 最小修复：给两个区间命名，例如“从 U-Boot 可用内存中模块落点之后的区域分配（与 `BootAlloc` 是两个游标），其起点不低于 `bump_end`，因此在 1024 页 `boot_alloc_region()` 区间之外”。
- 置信度：中高（指代冲突确定；“同一物理区间”可能只是笔误）。
- 若我错了：若“同一物理区间”指“同一片 U-Boot 可用物理内存”，而“该区间”明确指 1024 页区间，则语义可通，但需要读者自行补两套指代，仍建议改写。

## FINDING C-4（medium）：§4.1 说分类结果“同时写进 wire 与 BootStorage”，§3.7/§4.2.1 说 UEFI 的 source 只写 wire

- 节号+原文：§4.1 总览表“再在配对循环里把分类结果同时写进 wire 与 shim 自己的 `BootStorage`（§4.2、§4.4）”；§3.2 也有“发送侧的分类结果同时写进它自己的 `BootStorage`……和 wire”。
- 对照：§3.7“UEFI 腿的 source 分区由分类器直写 wire，storage 的 source 切片为空，不在这句的覆盖范围内”；§4.2.1 代码注释“UEFI 腿的 source 记录由分类器直写 wire；storage 的 source 切片为空”；§5.1 I2“不证明什么”列同义。
- 问题：“分类结果”在本文中正是 source 记录的来源（按字节分类）。§4.1/§3.2 的无条件“同时写进两处”与三处“source 只写 wire”冲突。若“分类结果”只指 memmap/reserved 两张表，则应限定；否则 I2 的“storage 的 source 切片为空”就没有落脚点。
- 影响：读者会以为发送侧 `BootStorage` 也持有 source 记录，从而高估 `fill_source_records` 的覆盖面，也会误读 §3.7“第二次 fill 只对实际走 `fill_*` 的腿成立”的适用范围。
- 证据：§3.2 段末；§3.7 所有权段；§4.1 表“内存与参数准备”行；§4.2.1 动作 6/7 注释；§5.1 I2 行。
- 最小修复：在 §3.2 与 §4.1 的“同时写进 wire 与 `BootStorage`”后加“（source 分区例外：仅写 wire，storage 的 source 切片为空，见 §3.7）”。
- 置信度：中高。
- 若我错了：若“分类结果”是作者对 memmap/reserved 分类的专名、source 记录另算，则只需在首次出现处定义该专名；目前没有这层定义。

## FINDING C-5（medium）：§5.4 把失败标记 `DTB preflight failed` 列为 aarch64 UEFI 的通过变体，判据未交代前提

- 节号+原文：§5.4 aarch64 UEFI 行“前两条固定标记 + 第三条变体（`memmap source` 或 `DTB preflight failed`）”；§6.4 同义复述“aarch64 UEFI 看前两条固定标记 + 第三变体之一（见 §5.4）”。
- 问题：表头是“判据（关键路标）”，即看到这些行就判 PASS。把一条失败信息与成功信息并列为“第三变体”，却没有说明哪种固件/部署下 `DTB preflight failed` 是预期且可判 PASS 的。读者无法区分“已知无 DTB 配置的合法降级”与“真的 preflight 失败”。
- 影响：这是 I3/I4 真机证据的判据；若一条链实际走到失败路径也被算作 PASS，则 §5.1“五条腿都有门覆盖”与 §5.5“没有未闭环测试缺口”的证据强度被高估。作为第一次读的读者，我在这里卡住，无法判断该门到底证明什么。
- 证据：§5.4 表；§6.4 注释第 2859–2861 行；§5.1 I3 行只说 aarch64 UEFI“正常形态”走到 `kmain`，未解释该变体。
- 最小修复：在该行判据后加一句“`DTB preflight failed` 变体只在无 DTB 的 aarch64 固件配置下判 PASS，且必须同时出现前两条固定标记；其含义是 fail-closed 后走回退路径，不是启动成功”，或把该变体从 PASS 判据移到“允许的诊断输出”。
- 置信度：中（可能是作者已在前文解释而我漏读；但 §5.4 作为权威表自身不闭合）。
- 若我错了：若 §4.2 已定义该固件配置下的预期 fail-closed 路径，则这是交叉引用缺失而非判据错误，仍建议在 §5.4 就地补一句。

## SUGGESTION C-6：“五条腿都有门覆盖”与“只有三条腿有走到 kmain 的证据”并置，易读成前者已足够

## SUGGESTION C-7：“形态 3”的分类轴不单一，直核与同镜像的关系未交代

- 节号+原文：§3.6 换算表“形态 | 3 | 同镜像内调用 / 跨镜像跳转 / 直核自引导；同镜像是测试/历史形态，当前生产腿只有跨镜像与直核两类”。
- 问题：“同镜像内调用”与“跨镜像跳转”按镜像边界分，“直核自引导”按引导面位置分，三者不在同一轴上；而 §1.1/§3.6 又说“两个直核腿同镜像”。读者会问：直核腿既然同镜像，为什么不算“同镜像内调用”？区别到底是“内核是否独立 ELF”还是“谁建根”（§4.1 表说按“谁建根”归类）。

- 最小修复：在该行加括注“直核自引导也是同镜像，但与‘同镜像内调用’的区别是内核镜像自带引导面、自己建根；旧形态是内核被链进 shim 镜像内联执行”。

## 总评（因果链视角）

- 主链可追：引导器 → 三份数据 → `KernelInfo`/wire → 六个落地区 → I1–I4 → 五条腿 → 门链 → 证据。概述、设计、实现、测试四层都有复述，且多数复述带锚点，这是本文最强的地方。
- 主要风险集中在“复述时的限定语丢失”：C-1（统一消费次序）、C-4（分类结果同时写两处）、C-6（门覆盖 vs 成功路径）都是实现章说清了、概述/总览表把限定语删掉。C-2 是归纳句的范畴错误，C-3 是指代冲突，C-5 是判据表自不闭合。
- 未发现因果方向写反的硬错误；未发现单形态被无条件写成三架构普遍结论（§3.6/§2.7 对架构差异有显式限定）。C-5 是唯一可能把失败路径算成通过的点，建议优先处理。
