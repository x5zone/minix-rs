## 二、四类问题复核结论

### 1. 重复编号

基本解决，但未收干净。

- 章节编号已有统一规则：`x.y` 为二级节，`x.y.z` 为三级，`x.y.z.w` 为四级；第 3 章内部（3.1.1、3.2.1、3.2.2、3.2.2.1–4、3.4.1–3、3.5.1–2、4.2.1–2、4.4.1）是自洽的。
- 残留一处结构性编号错误：`### 2.4.2`（第 608 行）与 `### 2.4` 同级，且 `2.4.1` 缺失。这不是“重复编号”，而是“编号层级与标题层级错位 + 序号断档”，比重复编号更容易误导目录重建。
- 另有一类“编号过载”不是重复，但读者要维护多套序号：§4.1 的 Step 0–4、§4.2.1 的动作 ID 1–9、§4.2.1 的时间拍 1–10、§4.2.2 的五步判定。文本已显式提醒“三套编号要分清”，说明作者知道成本；§4.2.1 的时间拍表确实解决了执行序，但也把“动作 2”拆到拍 1 与拍 3，读者需要来回对照。

### 2. 职责膨胀

有改善，但两个旧肿块仍在。

- 改善明显的：§3.2 开头“本节的交付形状与另外四节分工”把 16 条截断、扣除表、六个落地区、VM 换手分别指向 §2.4.2/§3.4/§4.5/§4.6；§4.7 与 §7.5 用“源码 > 定义节 > 速查表”的优先序把两张 C↔Rust 表分开；§3.6 末尾的“启动路径计数换算基准”把五种计数口径收在一张表里，是有效的去膨胀。
- 仍在的肿块之一：§3.2.2 标题“旧字段去向、GET_KINFO 外部面、控制台与 param_buf”已经自己承认是四件事，下面又挂 3.2.2.1–4；其中 3.2.2.3“两种控制台”与“旧字段去向”没有直接关系，3.2.2.4“十条可观察分歧”是另一条产品线。四件事共用三级标题，导致第 3 章出现全文唯一的 `#####` 深度。
- 仍在的肿块之二：§2.4.2.5“模块内存与 unpaged 段的归属变更”被放进“从记录里取址：两个消费者、两条取整规则与移交截断”之下。标题承诺的是取址与截断，2.4.2.5 讲的是 C 侧清单生命周期（还 VM 镜像、还引导段、其余模块不归还的代价），并顺带讲 Rust 去向。它既超出标题，也把 §2.5 的“切占用”拉进来做对照。
- 第三处较轻的膨胀：§4.4 的“字段表”把 `user_sp`、`kern_stack_top`、`syscall_entry` 三个“v10 起不再是字段”的成员继续列为表格行。构造表应只列现字段；退场成员应回到 §3.2.1 的删除台账。

### 3. 边界混淆

比 R1 前应更清楚，但仍有两处硬边界与正文对不上。

- §1.4 的“栈顶名字拆开”写死：`load_stack_start`、`user_sp` 归 01；`k_initial_stktop`、`kernel_boot_stack_top`、`kern_stack_top` 归 02。但 §4.4 有“`kern_stack_top` 的三条展开”，逐条讲镜像尾、64 KiB 引导栈顶、收口填充与清零语义；§7.5 也专门解释 `kern_stack_top` 与 `kernel_boot_stack_top` 的区别。读者按 §1.4 会以为这些名字只在 02 篇出现，按 §4.4 又会认为 01 篇就是权威。
- §1.3 说“Rust 把数据半留在 boot-shim/自引导面的载荷构造里，把镜像半留给 02 篇的建表与进入”；§1.4 说“01 管取到字节、校验、记账、构造载荷、发送；02 管把字节解释成镜像、摆放、映射、进入”。但 §4.2 的九动作表里，动作 2 拷贝 ELF 段与加载模块（摆放），动作 9 建根、开分页、跳转（映射与进入）都写在 01 篇的实现详解里。这里需要把“动作编排在 01、机制展开在 02”说清楚，否则“02 管摆放/映射/进入”与 §4.2 直接冲突。
- 反过来，§3.6 的“接缝定义”、§4.7 的落点表、§7.5 的速查表都在努力守边界；问题集中在 §1.3/§1.4 的两句绝对化措辞，而不是全篇失控。

### 4. 执行序

R1 的主要成果在这里，仍有一处实质遗漏。

- 做得好的：§4.2.1 用“时间拍”表给出真实执行顺序，再用“动作 ID（非时序）”表给约束，明确“动作 ID 只是稳定标签”；§4.4.1 用“门列 bug 类、不按时间排序”的表，把“防线”与“执行序”分开；§2.8 明确“D1–D5 是约束名，不是执行序”。
- 实质遗漏：§3.7 与 §3.6 的直核链是 `validate_requiring_sources → validate_before_tables → check_boot_postconditions → store_kernel_info → boot_validate_and_prepare → kmain 的 validate`；§4.4.1 的直核链写成 `strict → pre-table → postconditions → boot_validate → kmain validate`，**漏掉 `store_kernel_info`**。两处都自称权威/执行序，读者会得到两条不同的链。
- 另一处轻微不一致：§3.7 说“直核面由 `arch_boot_finish` 先 `store_kernel_info`、再进 `arch_boot_impl` 的 `boot_validate_and_prepare`”；§4.4.1 的直核链没有这个动作，等于把“先存后验”这个与 v1 接收面相反的关键差异抹掉了。

## 五、R1 改动有效性总评

- **重复编号**：大部分收敛，但 §2.4.2 是硬残留；它不是“重复”，而是“层级错位 + 断档”，比重复更伤目录。R1 若只做了编号替换而没有做标题层级对齐，这一处就是证据。
- **职责膨胀**：§3.2/§3.6/§4.7 的分工声明是有效改进；但 §3.2.2 四主题、§2.4.2.5 下游延伸、§4.4 退场字段三处仍在膨胀。R1 解决的是“把大节切开并加指针”，没有解决“切开后每个节的标题是否覆盖内容”。
- **边界混淆**：§1.4 的接缝声明、§3.6 的计数表、§4.7/§7.5 的优先序都是有效改进；但 §1.4 的“栈顶名字归 02”与 §4.4 的 `kern_stack_top` 三条展开、§1.3 的“镜像半留给 02”与 §4.2 动作 9 的建根/开分页/跳转直接冲突。边界声明写得越绝对，正文越容易破。
- **执行序**：§4.2.1 的时间拍表是 R1 最成功的结构改动；§4.4.1 的门表也基本清楚。唯一实质遗漏是直核链漏 `store_kernel_info`，它恰好破坏了 §3.7“两条腿次序相反”的核心对比。

**建议处理顺序**（若只做最小改动）：

1. 修 §5.1 表格（B-F2，纯机械，收益最大）。
2. 修 §2.4.2 编号/层级（B-F1，影响目录与 12 处引用）。
