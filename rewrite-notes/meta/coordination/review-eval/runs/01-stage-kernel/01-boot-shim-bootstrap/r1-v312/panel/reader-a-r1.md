**问题**：这三处都是“核心结论压在一个长句/一段里”：§3.7 的 I3 段落同时列六类载荷、五个 `fill_*` 入口、UEFI source 两阶段直写、`resv_claims`/`push_dtb_sources`/`finish_sources` 三个未定义函数、strict 审计过滤；§4.4.1 的执行序用箭头和括号编号把两条腿的门顺序压成一段；§2.3 的 `board=` 遮蔽条件用两层括号嵌套。我每读一句都要回看前半句的主语，读完仍不能在脑内画出一张“腿 × 载荷 × 校验点”的表。

**影响**：I3/I4 是本章的两条核心不变量；如果读者无法从 §3.7 复述“哪条腿、哪类载荷、走哪个入口、在 wire 还是在 storage”，就无法用这两条不变量判断一次交接是否成立。§4.4.1 的门顺序同理：读者只能记住“有五个门”，记不住哪条腿先哪个。

**证据或推理**：L1837 是一段约 500 字的单段，包含至少 10 个内部标识符，其中 `resv_claims`/`push_dtb_sources`/`finish_sources` 在本篇此前没有定义；L2362 是一段约 300 字的单段，括号里的数字（1/2/3）与门名交错；L345 的条件分支用括号嵌套，读者需要做布尔化简。三处的共同点是“结论正确但信息密度超过一次阅读的工作记忆”。

**最小修复**：§3.7 改成一张表：行 = 腿（UEFI/U-Boot/直核），列 = 载荷类别、写入入口（`fill_*` 或直写 wire）、存储位置（`BootStorage`/wire/`.bss`）、提交点；表后只保留 UEFI source 例外的两句话。§4.4.1 改成两行有序列表（直核面 / v1 接收面），每行一个门一个箭头，编号放在括号外。§2.3 的 `board=` 改成三步：正常情况 → 首条记录 → 非首条记录，每步一句。

## SUGGESTION

- **章首问题陈述**：§1.0 的学习目标只有“说出三份数据”“用 I1–I4 判断一次交接”，而首行引用块是术语索引（`KernelInfo`、两张内存表、bootstrap 区间、校验门链、五条生产腿）。建议在“学习目标”前加 2–3 句白话：“本章回答：引导器交给内核的信息如何跨镜像安全到达？答案是三份数据、四条不变量、五条路径；第 2 章看 C 怎么做，第 3 章看 Rust 为什么这样设计，第 4 章看实现，第 5/6 章看证据与诊断。”这样读者能先拿到问题，再读术语。
- **§1.0 内部顺序**：L39 的小结已经使用“框 1/框 2”，而定义在 L48 的术语表（在小结之后）。建议把术语表移到小结之前，或在小结首次出现时加一句“见本节术语”。
- **§4.2.1 动作编号与时间拍**：L2038–L2049 的表里“时间拍 1 = 动作 2a、时间拍 2 = 动作 1”，虽然正文说明“动作 ID 只是稳定标签”，但初读仍会以为表印错了。建议要么按执行序重编号，要么把动作 ID 换成动词名（“读 ELF/预订跨度”“分配 root/bump”），只在需要回查旧编号时才保留数字。
