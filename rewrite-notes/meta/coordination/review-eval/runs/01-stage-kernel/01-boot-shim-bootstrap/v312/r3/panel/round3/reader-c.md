## FINDING READER-C-01（P2）

- 位置：§2.3“同一个 off-by-one 的第二种表现”段；§3.2.2.4“其一，重复键”段与节首“十条”声明。命中清单第 2、3、4 条。
- 严重度：P2
- 问题：§2.3 明确推出删除扫描能在**非首条记录的中部**命中，并把 `xboard=2` 的中段 `board=2` 删掉、留下伪记录 `xarch=i386`；§3.2.2.4 却把 C 的行为概括成“已存在先删只对首条记录生效”，并给出“首条副本 → 后写胜出；非首条 → 旧条留在原位”的两支模型。这个两支模型没有包含 §2.3 的中段误删：按 §2.3，非首条记录也会被改写。于是我读到这里无法判断：写 `board=` 时，非首条的 `xboard=2` 到底会不会被改坏；“十条可观察分歧”是否已经把这个分支算进去。
- 影响：我会把 §3.2.2.4 的两支模型当作 C 的完整行为，从而在审计 `param_buf` 内容时漏掉 `xboard` 一类伪记录；同时无法信任“共十条”是穷举。Rust 侧拒绝外部 `board=`（其二）掩盖了这个分支，所以它不是 Rust 需要实现的路径，但它是 C 行为复述的一部分。
- 证据或推理：
  - §2.3：“当 `p` 被推到记录中部时，前缀匹配可能从记录中部命中。例如 `param_buf` 里先有 `xboard=2`（它不是首条记录，前面还有别的键），内核再写 `board=` 时，中段 `board=2` 会被删掉，后一条 `arch=i386` 的前半截被补进原位，留下伪记录 `xarch=i386`。”
  - §3.2.2.4：“C 的"已存在先删"只对首条记录生效（§2.3 的源码推演），但结果分两支：若重复键的首个副本是第一条记录，旧条被删、新值追加，**后写胜出、只剩一条**；若首个副本不是第一条，旧条留在原位、新值追加到缓冲末尾，账上两条而读取返回第一条。”
  - §3.2.2.4 节首：“与 C 的可观察分歧共十条”。
- 最小修复：在“其一”的两支之后补一句：“同名键的整条删除只对首条记录成立；非首条记录还可能被中段匹配误删（§2.3 的 `xboard=2` → `xarch=i386`），这是另一条可观察差异。”若它算独立分歧，把“十条”改成十一条或明确说明十条只覆盖同名键；若不算，明确写“中段误删不改变本条两支结论，故不单列”。
- 置信度：高（两段文字直接冲突）；中（作者是否把中段误删视为独立分歧）。
- 是否需源码核实：否（§2.3 的字节级推演已足够判断冲突；源码只用于最终确认 C 行为，不用于发现这处复述不一致）。
- 若我错了：我可能把“已存在先删”窄化成“同名键整条删除”，而作者的两支模型本来就只谈同名键；中段误删是另一个匹配路径，作者有意留在 §2.3 的 C 缺陷段而不放进“Rust 分歧表”。即便如此，§3.2.2.4 的“只对首条记录生效”仍需要限定语，否则会被读成“非首条记录不受影响”。

## FINDING READER-C-02（P2）

- 位置：§1.1“内核位置记录”行；§3.2.1“升为字段”行与“两个直核面是例外”段；§4.4 字段表 `kern_virt_base`/`kern_phys_base`/`kern_size` 行。命中清单第 3 条（并涉第 2 条）。
- 严重度：P2
- 问题：§1.1 把“接收侧没有 ELF 头可读，镜像跨度只能由发送侧解析后交来”写成三字段必须跨边界的原因；§3.2.1“升为字段”行也写“来源改为 boot-shim 解析内核 ELF 的 PT_LOAD 段”。但两个直核腿并不解析 ELF，而是用自己文件里的 `KERN_VIRT_BASE`/`KERN_PHYS_BASE`/`KERN_SIZE` 常量；§3.2.1 后文自己称它们为“例外”，§4.4 字段表也写“直核面由 `KERN_*` 常量提供”。概述里的“只能”是单形态结论写成普遍结论：五条腿里只有三条 v1 发送腿符合这个理由。
- 影响：我在 §1.1 建立的模型是“五条腿的布局跨度都来自发送侧解析镜像”；读到 §3.2.1 的例外时必须回头修正。这个“为什么必须交接”的因果链对 2/5 条腿不成立，读者会误以为直核腿也依赖 shim 的 ELF 解析。
- 证据或推理：
  - §1.1：“接收侧没有 ELF 头可读，镜像跨度只能由发送侧解析后交来；C 侧则由链接期常量本地可得。”
  - §3.2.1：“Rust 把它们放进交接结构，来源改为 boot-shim 解析内核 ELF 的 PT_LOAD 段（§4.4 的字段表）。”
  - §3.2.1：“**两个直核面是例外**：`bootface`/`bootface_a64` 用自己文件里的 `KERN_VIRT_BASE`/`KERN_PHYS_BASE`/`KERN_SIZE` 常量，不从 ELF 头解析”。
  - §4.4：“直核面由 `KERN_*` 常量提供”。
- 最小修复：把 §1.1 那句限定为“三条 v1 腿的接收侧没有 ELF 头可读，跨度只能由发送侧解析后交来；两个直核腿同镜像，用自身 `KERN_*` 常量（见 §3.2.1）”，并把 §3.2.1“升为字段”行的“来源改为”改成“三条 v1 腿的来源改为；两个直核面用常量（例外见下段）”。
- 置信度：高。
- 是否需源码核实：否（文档内部的“只能”与“例外”已经足以判断矛盾，不需要看源码）。
- 若我错了：我可能把“发送侧”理解得太窄——直核腿的 `KERN_*` 常量也在“发送侧”（同一镜像的引导面）本地产生，作者可能认为“发送侧解析后交来”包括同镜像常量。但“解析 ELF”与“常量”是两种来源，§3.2.1 自己把它们对照为“例外”，所以 §1.1 的“只能”仍然过强。

## SUGGESTION

### SUGGESTION READER-C-S01（清单第 2 条）

- 位置：§2.4.2.3 前提三。
- 问题：“跳板约 2212 B（`trampoline.S` 的 16 位代码 + 固定 IDT 2048 B + GDT 表），`roundup` 为 `0x1000`…… 按当前 `C = 1` 计算总量约 2212 B”是“第三行常态”的关键前提，但文档没有给出 2212 的算术分解或可核对的区间上限；读者只能接受这个数。若它其实超过 4096，`len ≤ lowest` 就不成立，结论要重推。
- 影响：四前提被称作“核对过的事实”，但其中一条的数字无法在文档内复核；这削弱了“第三行常态”的证据强度。
- 证据或推理：原文只给“约 2212 B”和三个组成部分的名字，没有给 `trampoline.S` 的字节数、GDT 的 7×8=56 的求和过程或区间上界。
- 最小修复：补一行算术：“16 位代码 ~108 B + IDT 2048 B + GDT 56 B = 2212 B，且 < 4096”；或给出 `trampoline.S` 的符号区间与两个常量的出处。
- 置信度：高（缺口明确）；中（2212 是否准确）。
- 是否需源码核实：是。

### SUGGESTION READER-C-S02（清单第 2/9 条）

- 位置：§2.7“ARM32 的 `get_parameters` 第一件事……”段。
- 问题：原文说“ARM32 的 `get_parameters` 第一件事不是读引导器结构体，而是**造一个**”，紧接着给出的代码却是独立函数 `void setup_mbi(...)`。读者看不出 `setup_mbi` 是由 `pre_init` 在调用 `get_parameters` 之前调用，还是由 `get_parameters` 内部调用。
- 影响：ARM 侧的调用序（谁造 `mbi`、`get_parameters` 读什么）不清楚；这会影响对“两侧 `get_parameters` 同构”的理解。
- 证据或推理：原文：“ARM32 的 `get_parameters` 第一件事不是读引导器结构体，而是**造一个**：”，代码块标题是 `minix3/minix/kernel/arch/earm/pre_init.c:setup_mbi`。
- 最小修复：改成“ARM 的 `pre_init` 先调 `setup_mbi` 造一个 `mbi`，再调 `get_parameters` 读它”，或明确 `setup_mbi` 的调用点。
- 置信度：中（文字与代码块标题的错位清楚；调用点需源码确认）。
- 是否需源码核实：是。

### SUGGESTION READER-C-S04（清单第 1/9 条）

- 位置：§4.0 术语“落地区”与 §4.5 末段。
- 问题：§4.0 写“`store_kernel_info` 只做同址包装”，读起来像“调用它没有副作用、总是 no-op”；§4.5 说“`store_kernel_info` 顶部的一次性守卫会让第二次调用直接 panic，不是同址 no-op”。第一次调用同址跳过、第二次调用 panic，这两个事实只在后一处出现。
- 影响：我可能低估重复调用 `store_kernel_info` 的后果；这是启动期“唯一副本”不变量的一部分。
- 证据或推理：§4.0 术语与 §4.5 末段原文。
- 最小修复：把 §4.0 术语改成“首次同址跳过复制；带一次性守卫，第二次调用 panic”。
- 置信度：高。
- 是否需源码核实：否。

### SUGGESTION READER-C-S05（清单第 2/3 条）

- 位置：§2.4.1.1 与 §3.2.2.1 的 `mmap_size` 行。
- 问题：§2.4.1.1 说 C 的 `mmap_size` 是“当前遍历边界（切除不回缩，因此可能高于实际最高占用下标；中间可有零长空洞）”；§3.2.2.1 说“C 的‘遍历边界（最高占用下标加一）’由切片长度 `.len()` 直接承载”。切片 `.len()` 是元素个数（若 Rust 的列表是紧凑的，就是条目数），并不承载 C 的“高水位 + 空洞”语义；“承载”会被读成等值。
- 影响：我可能以为 Rust 保留了 C 的高水位/空洞行为，而 §4.5 的 `FreeRangeSet`（有序不相交页对齐集合）已说明 Rust 用有序不相交集合取代了它。
- 证据或推理：§2.4.1.1 的边界/空洞说明；§3.2.2.1 的“由切片长度直接承载”；§4.5 的 `FreeRangeSet` 描述。
- 最小修复：改成“C 的边界标量与空洞是定长数组布局的产物；Rust 的切片是紧凑条目列表，`.len()` 只是条目数，不需要边界标量”。
- 置信度：中/高。
- 是否需源码核实：是（确认 `KernelInfo.memmap` 的切片是否紧凑、无空洞）。

### SUGGESTION READER-C-S06（清单第 5/10 条）

- 位置：§7.5 `get_parameters` 与 `add_memmap` 行。
- 问题：`get_parameters` 行的 Rust 侧只列 `prepare_and_enter_kernel_image + ebs_pair + arch_boot`，漏掉 U-Boot shim 与直核腿的 `prepare_boot`/DTB 路径；`add_memmap` 行只列 `ebs_pair::pair_and_classify`（生产）/`build_memmaps`（测试），漏掉 U-Boot shim/直核腿的 DTB 解析路径。§7.5 虽声明“不保证穷举”，但这两处是系统性的腿覆盖缺口，不只是零散漏项。
- 影响：读者按速查表给 U-Boot 或直核腿找 `get_parameters`/`add_memmap` 对应物时，会得到“只有 UEFI 路径”的错误印象。
- 证据或推理：§7.5 表格行；§3.2 的“三条 UEFI 链 / U-Boot / 两个直核面”来源说明；§4.7 的同一对照。
