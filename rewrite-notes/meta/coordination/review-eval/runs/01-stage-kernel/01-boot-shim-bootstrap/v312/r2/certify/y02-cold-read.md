# 冷读报告：01-boot-shim-bootstrap

读者画像：能读 C；知道引导器把控制权交给内核、实模式/保护模式、页表的基本概念；Rust 基础（所有权、切片、trait、`unsafe` 的用途）；不熟悉本项目的内部类型。只读本文，未读源码、其它文档、diff 或评审报告。

### 1. 交接的形状（什么数据跨边界、以什么形式、为什么）

材料位置：§1.1 的三份数据表；§1.2 的 I1–I4；§1.0 的术语；§3.2/§3.2.1 的 `KernelInfo` 字段台账；§3.2.3 的 wire 与 arena；§4.4 的发送视图字段表；§4.5 的六个落地区与容量表。

能学到的：三份必须带走的数据（可用内存清单、内核位置记录、交接结构）；两张表加来源记录的基本分工；`KernelInfo` 按值交接、三条跨镜像腿走 wire、两个直核腿也深拷；六个 `.bss` 落地区；八页 arena 的概念；I1–I4 各自的失败面。

不够的地方：

- 字段台账的写法是“删除账本”，不是“现役字段指南”。读者要先消化 `16 → 13 → 14 → 10`、22 个被删字段、`7→8`、`8→9`、`9→10` 这些历史数字，才能拼出当前的 10 个字段。对第一次读的人，这些数字不是知识，是噪声。
- wire 的确切形状没有给出。§3.2.3 只给分区顺序（信封、内存图、保留区、模块、平台源、参数、source），§3.4.3 明确说“信封字段的完整偏移表在 `handoff_v1.rs` 的 `envelope_offsets`，本篇不复制”。于是我知道“有 wire”，但不知道每个字段的偏移、宽度、字节序和对齐，无法真正理解“固定宽度标量加字节分区”是什么样。
- `BootReport`、`BootStorage`、`land_and_store` 这三个核心名字在§1–§3 被反复使用，但它们的形状分散在 §1.2 的白话替换、§3.0 术语、§3.7 的所有权段、§4.4 的字段表和 §4.5 的代码里。读第一遍时，句子里的主语是陌生的。
- 我能回答“哪些数据跨边界”的高层问题；回答不了“每个字段为什么必须存在、少一个会在哪一步坏掉”的完整问题，因为后者被拆在字段去向表、失败对照和 02 篇的接缝声明里。

结论：概念骨架在，但“形状”的细节不完整，且被历史叙述遮住。部分够用。

### 2. C 基线

材料位置：§2.1 引导器契约与 `mbi`；§2.2 `head.S` 入口与栈；§2.3 `get_parameters` 与 `mb_set_param`；§2.4 内存账的两档来源、`add_memmap`/`cut_memmap`；§2.5 `overlaps` 与内核当第 M+1 个模块；§2.6 三层检查表；§2.7 ARM32 `setup_mbi`；§2.8 调用树与 D1–D5。

够用。这是全文最像“教材”的部分：引了真实 C 代码，逐行解释，给了字节图、手算切除、`load_mods` 与 `multiboot` 的次序推演、`overlaps` 去掉 `-1` 的反例、ARM32 的闭区间差异。一个能读 C 的人可以沿着 `boot.cfg` → `head.S` → `pre_init` → `get_parameters` → `add_memmap`/`cut_memmap` → `overlaps` 走完整个 C 侧交接，并知道每一步的失败现场。

不足的地方主要是比例：`mb_set_param` 的删除扫描缺陷、`alloc_lowest` 把长度当结束地址、`bootstrap_len` 的过度回收险情，都是很有价值的案例，但篇幅接近甚至超过主线本身。第一次读的人容易以为“C 基线就是一堆 bug”，而不是“先有一条正常路径，再有几个边界缺陷”。另外，`objcopy --prefix-symbols`、paged/unpaged 两份副本、`.usermapped` 拷贝这些构建细节，对只懂基本启动的读者来说偏深，虽然文中给了链际关系，仍需要额外背景。

结论：够用。建议把 C 缺陷考证标成“可选案例”，让主线更清楚。

### 3. Rust 设计

材料位置：§3.1 协议换代与备选方案；§3.2 `KernelInfo` 与字段台账；§3.3 两张表与 `SourceRecord`；§3.4 bootstrap 区间与分配器换手；§3.5 `FileLoader` 与 crate 依赖方向；§3.6 五条生产腿与发送侧；§3.7 所有权与校验门链。

不够。设计的主要结论都在：为什么不用 Multiboot2、为什么三个架构共用按值交接、为什么内存图是两张表加来源记录、为什么页表分配器要换手、为什么 `FileLoader` 是唯一的取件接缝、为什么内核不依赖 boot-shim、五条腿如何在形状上收敛、I3/I4 如何落地。这些结论本身是有说服力的。

但读起来不像一条设计讲解，而像一组“权威节”：

- 每讲一个点，句子就把读者送到另一节：“见 §3.2 的权威表”“本节只保留构造入口”“完整定义见 §4.2.1 动作 2”。读者必须一边读一边维护一张交叉引用图。
- 关键术语的定义是“路过式”的。`A+D`、`ReservedMapped`、`Side` 在 §3.2.1 的一个句子里被塞进三个括号；`BootReport`、`BootStorage`、`land_and_store`、`FreeRangeSet` 分散在 §1.2、§3.0、§3.7、§4.4、§4.5；`Excluded`/`DevicePath` 到 §4.2.2 才有完整判定。对“不熟悉内部类型”的读者，这层术语负担很重。
- 字段设计的理由被埋在删除账本里。读者想知道“为什么 `authority` 要放进结构体”“为什么 `kern_size` 用 `u64`”“为什么 `user_sp` 被删掉”，得在 §3.2.1 的表格、§3.2.2.1 的 22 行去向表、§3.2.2.3 的展开段之间来回找。
- 启动路径的计数有多个维度。§3.6 自己说“本篇用多个不同维度描述同一组启动路径”，并给了一张换算表。换算表能救急，但救不了第一遍读时的困惑：到底有几种形态、几条腿、几条链、几个交接面？哪些“五”是同一批成员，哪些不是？
- 版本历史混在现役设计里。§3.2.1 的“16 → 13 → 14 → 10”、§3.4.1 的“先写死 `(0,0)` 再删除、wire 7→8、envelope 184→160”、§3.2.3 的“7→8、8→9、9→10 都指信封版本”，这些是设计演化记录，不是当前设计的组成部分。第一次读的人无法判断哪一句是现状、哪一句是“曾经”。

结论：设计结论够，学习路径不够。一个没有内部类型背景的人能记住“按值交接、两张表、五条腿、门链”这些口号，但难以复述每个选择的边界条件。

### 4. 实现路径

材料位置：§4.1 入口与调用链；§4.2 九个动作与产出归属；§4.2.2 描述符分类五步；§4.3 两种文件来源共用的取件函数；§4.4 `BootReport` 与 `KernelInfo` 构造；§4.5 六个落地区；§4.6 arena 与分配器换手；§4.7 C 函数落点对照；§4.8 Direct Map 概念入口。

不够。§4.1 的入口骨架、§4.2 的九动作表、§4.2.2 的五步判定表、§4.4.1 的门链表、§4.5 的容量表、§4.7 的 C→Rust 对照，都是有用的材料；尤其 §4.7 能让人快速知道一个 C 函数在 Rust 侧大体落在哪。

但“实现路径”要求读者能沿着一条腿从固件走到 `kmain`，这份材料做不到：

- 主代码是节选，而且明确不是逐字、顺序也按语义重排。§4.2 的注释直接列出未展开段：参数统计、`system_table`/`boot_services`/`ops` 构造、`assert_range_clear_of_kernel`、`NeedBiggerBuffer` 分支、`dumpdtb_blob` 的 `#[cfg]` 构造、入口与首段 VMA 的断言。读者拿到的是一张“路标图”，不是可跟随的路径。
- 同一段路有三套编号：动作 ID、时间拍、§4.1 的 Step 0–4，再加上 §4.2.2 的判定五步。文中自己说“三套编号要分清”。分清之后仍然要不停换算。
- `ebs_pair`、`Serializer`、`ops`、`shim_windows`、`bootstrap_alloc_limit` 这些名字出现了，但只给了一两句话；读者不知道它们的输入输出和失败面，无法在脑中执行这段代码。
- 没有一条“x86_64 UEFI 从 `main` 到 `kmain`”的完整叙事。九动作表是表格，§4.2 的代码是节选，§4.4/§4.5 又跳到接收侧；读者需要自己把三节拼起来。
- §4.8 的 Direct Map 只给概念入口，完整机制在 02 篇；这对“实现路径”的完整性是合理的边界，但意味着这条路径在本文里本来就是断的。

结论：能学到“有哪些步骤、每步的约束是什么”，学不到“这条腿实际怎么跑起来”。不够。

### 5. 测试与诊断

材料位置：§5.1 四条不变量的证据矩阵；§5.2 宿主测试边界；§5.3 机制到证据的映射；§5.4 五条真机门链；§5.5 测试缺口；§6.1 里程碑清单；§6.2 panic 路径；§6.3 失败模式表；§6.4 可复制命令。

基本够用。§6 是全文第二好读的部分：按 `ExitBootServices` 分界讲两条输出通道，给出 `raw_serial`/`raw_serial_line` 的差别，给出里程碑表（含“适用腿”列），给出三层排查法（串口、`-d int`、GDB），最后给可复制命令。失败模式表把“信号 → 下一步确认”写得很实用，尤其是 `load_mods` 次序、模块缺失、信封无效、发送侧走完接收端未起、`assert_bootstrap_outside_memmap` 这几行。

不足的地方：

- 里程碑表很长，且每一行的“适用腿”不同。第一次读的人容易把某条腿的标记套到另一条腿上；表后的“阶段标签对照”段就是在补这个坑。
- §5.4 的判据依赖仓库里的脚本与 QEMU 环境；单读文档只能知道“看哪一行”，不能验证脚本本身。对“测试与诊断”的学习来说，这已经够定位，但不够独立复现。
- §5.2 的测试读数是快照（188/0、136/0、866/0/8、27/0），没有说明这些数字对应哪个提交或哪个配置；读者无法判断自己跑出来的数是不是同一件事。
- §5.1 的“不证明什么”列写得很好，但它也提醒读者：这些证据不能证明任意畸形输入会被拒绝。对学习者来说，这是一条重要的边界，但会让“我学会了测试”这个感觉打折扣。

结论：够用，尤其是诊断路径。测试证据部分更像“查证索引”，不是“测试教学”。

## Blockers

### Blocker 1 — 实现路径的代码不是可跟随的路径

位置：§4.2（同类问题见 §3.6、§4.1）

引文：

> “代码表达式也按语义重排、非逐字；source-symbol: prepare_and_enter_kernel_image；未展开段：参数统计的 `println`、`system_table`/`boot_services`/`ops` 构造、arena 的 `assert_range_clear_of_kernel`、`NeedBiggerBuffer` 扩容断言分支、`dumpdtb_blob` 的 `#[cfg]` 构造、入口与首段 VMA 的 `assert_eq!(layout.entry_point, layout.kern_virt_base.0, …)`”

以及 §3.6 的：

> “// ……（riscv64 cfg 别名、x86 cli、Step 0、policy 选择见源文件）……”

为什么这是硬阻断：这不是少了一两个注释，而是把“实现路径”变成了“实现路径的摘要”。读者被告知代码顺序不是真实顺序、若干分支没展开、关键调用要去看源文件。对一个不读源码的目标读者，§4 无法完成“沿着一条腿走完”的任务；他只能记住九动作的名字和若干约束。任务 4 因此不成立，任务 3 的“设计如何落地”也失去了一半证据。

### Blocker 2 — 当前设计与版本历史混在一起

位置：§3.2.1、§3.4.1、§3.2.3、§4.4.1

引文：

> “字段计数的完整链条是 16 → 13（去掉 `free_upper_idx`、`bootstrap_start`、`bootstrap_len` 三个，见 §3.4.1 与 §3.4.3）→ 14（加入 `authority`）；wire v10（设计裁决）再删掉 `startup_objects`（当时既是 `KernelInfo` 字段、也是 wire 分区与 builder 参数）、`user_sp`、`kern_stack_top`、`syscall_entry` 四个，落到 10。”

以及 §3.4.1 的：

> “这个字段对在 Rust 侧的处置走过两个阶段，最后停在**删除**：先是把 `(0, 0)` 写死并配一条硬断言（“必须为 0”），字段删除后离开 `KernelInfo`，wire 版本 7→8：本字段对释放 16 字节，同版本删除的 `free_upper_idx` 再释放 8 字节，合计 24 字节，envelope 从 184 缩到 160”

为什么这是硬阻断：读者要学的是“现在的交接结构是什么、为什么是这样”。文中给出的却是一条变更日志：16→13→14→10、7→8、8→9、9→10、184→160→128、startup 分区 1440 B、余量 2144→3584 B。没有读过前几版的人，无法把这些数字映射到任何具体结构；更糟的是，当前事实（10 个字段、没有 `bootstrap_start/len`、没有 `startup_objects`）总是和“曾经有过什么”写在同一个句子里，读者必须自己拆出“现状”。任务 1 的“形状”和任务 3 的“设计理由”都被这层历史遮住。

### Blocker 3 — 同一组路径有多套互不兼容的编号与计数

位置：§3.6、§4.2.1

引文：

> “三套编号要分清：本节的“动作 ID”、本节的“时间拍”、§4.2.2 的描述符判定五步；§4.1 的 Step 0–4 只作概览，不参与本节计数。”

以及 §3.6 的：

> “本篇用多个不同维度描述同一组启动路径。本表是全文启动路径计数的换算基准；各节可以在服务上下文时复述成员名单，但跨节比较与换算是以本表为准，不另立计数。”

为什么这是硬阻断：读者需要在脑中同时持有：三种形态、五条生产腿、四个协议段/交接面、六条三类链、五行架构×链、五条真机门链；其中两个“五”的成员不同（一个含 aarch64 直核面，一个含直载测试链），并且“腿”“链”“形态”“产线”“面”在正文里经常互换。§3.6 的换算表证明作者知道这件事，但表格是补丁，不是教学顺序。读者每读一节都要先问“这里的‘五’是哪五个”，这直接破坏任务 1、3、4 的连贯性。

### Blocker 4 — 权威表式交叉引用与“本篇不复制”

位置：§4.4、§3.4.3、§3.2.2

引文：

> “`reserved_regions` 的取值按腿的细目以 §3.2 为权威（UEFI `ReservedMapped`、U-Boot/riscv 直核 DTB 保留段、aarch64 直核 `fw_end=0`）；本节只保留构造入口，不逐腿复述。”

以及 §3.4.3 的：

> “信封字段的完整偏移表在 `handoff_v1.rs` 的 `envelope_offsets`，本篇不复制”

为什么这是硬阻断：本文的组织方式是“每节只保留自己那一块，其余去别的节看”。这对避免重复有好处，对第一次学习是灾难：读者无法在一个地方读完一个主题，必须不断跳转；而有些关键事实根本不在本文里（wire 的完整偏移表）。任务 1 需要 wire 的形状，任务 4 需要实现路径的细节，两者都被“不复制”和“以 §X 为权威”推到了本文之外。读者最后得到的是许多“结论的索引”，不是一条可以走通的路。

## 可选改进（不是阻断项）

1. 加一张端到端图：x86_64 UEFI 从固件到 `kmain`，每个箭头标注“谁写什么数据、过哪道门、失败落在哪个路标”；再给一张直核腿的简版。这一张图能同时缓解 Blocker 1 和 Blocker 3。
2. 加一份统一术语表：一行一个内部名字，覆盖 `BootReport`、`BootStorage`、`land_and_store`、`FreeRangeSet`、`A+D`、`ReservedMapped`、`Side`、`Excluded`、`DevicePath`、`arena`、`wire`、`leg`、`chain`、`form`。各章现有的术语小节可以保留，但需要一个地方能一次查到。
3. 把“22 个被删字段 + 版本字节数”移到附录；正文换成一张现役 `KernelInfo` 字段表：字段、类型、谁填、谁读、为什么必须跨边界。这样任务 1 就有了单一入口。
4. 加一张 wire 字节布局表：信封字段的偏移/宽度/字节序/对齐，各分区的偏移与长度。如果确实超出本篇范围，就在 §1.4 明确写“wire 的字节布局不在本篇”，并指向一个自包含的附录，而不是指向源码。
5. 修 §3.5.1 的签名展示：`prepare_boot(&mut BootStorage, bump_pages) -> BootPrepareResult<'a>` 里的 `'a` 没有声明。按 Rust 语法，这里要么写出 `<'a>` 和 `&'a mut`，要么说明是省略写法；一个 Rust 学习者会在这里停下来怀疑自己。
6. 把 C 缺陷考证与 C 基线分开：`mb_set_param` 的删除扫描、`alloc_lowest` 的参数错位、`bootstrap_len` 的过度回收，都是好案例，但应在小节标题或段首标“可选：一个真实缺陷”，让读者知道主线在哪里。
7. 减少“以 §X 为权威 / 本节不重复”的密度。每个事实保留一处完整陈述，其余地方用链接；现在的写法让正文读起来像交叉引用索引。
8. §4.4.1 的门链表是全文最好的表之一；在它旁边加一张“门 × 腿”的矩阵，读者就能一眼看出哪条腿跑哪些门，不必从句子里推。
9. “最小示例”目前多是 `grep` 或 `cargo test` 命令，需要仓库才能执行。给每条命令补一句“预期输出长什么样”，或者换成一个不依赖源码的概念小例子；否则冷读的人只能跳过。

## 总评

这份文档有大量真实知识。C 基线和诊断章是可以学的；Rust 设计章和实现章，对一个具备所述背景、且不读源码的读者来说，学不动。原因不是事实缺失，而是呈现方式：当前设计与版本历史混在一起，实现以“重排 + 节选 + 见源文件”的形式出现，读者还要在权威表和多套计数之间导航。上面列出的改进里，只要先做“一张端到端图 + 一份现役字段表 + 一张 wire 布局表”，本文的可学性就会有实质变化。按现在的状态，我不能从这份文本单独学会 Rust 交接设计或实现路径，因此判 NOT-READY。
