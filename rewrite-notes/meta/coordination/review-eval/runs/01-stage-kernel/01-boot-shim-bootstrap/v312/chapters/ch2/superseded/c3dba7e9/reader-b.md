## 我重建的结构

本章的 S2 学习要求是：按 `boot.cfg` 指令次序、`head.S` 入口与 `pre_init` 调用树复述 C 侧从引导器到 `kinfo` 的交接路径；解释 `add_memmap`/`cut_memmap`/`overlaps` 如何把引导器数据变成内核记录；指出 D1/D2/D4 的 C 证据锚点，并说明 D3/D5 归 02 篇。按“后一节需要前一节提供什么”重建，本章的因果链是：

1. **契约输入**（2.1）：引导器交出什么——识别头、两个魔术值、`mbi`、`boot.cfg` 指令次序与模块表。模块数上限与 `load_mods` 必须先于 `multiboot` 的约定也在这里，它们是 2.5/2.6 的前置。
2. **入口**（2.2）：控制权怎么进来——`head.S:multiboot_init` 设栈、清帧指针、按 i386 调用约定把 `magic`/`ebx` 交给 `pre_init`。
3. **收集**（2.3）：`get_parameters` 怎么把外来数据变成自己的记录——整份拷贝 `mbi`、链接期常量写 `kinfo`、命令行逐词扫描进 `mb_set_param`、`param_buf` 的格式与删除扫描。
4. **账本建造**（2.4.1 + 2.4.1.1）：可用内存记录从哪来——细表/粗档两档来源，`add_memmap` 追加、`cut_memmap` 切除及其取整规则。
5. **占用切除**（2.5）：账本怎么排除内核与模块——`overlaps` 半开区间检查、内核当第 M+1 个模块、逐条 `cut_memmap`。依赖第 4 步的 `cut_memmap` 与第 1 步的模块数/次序。
6. **账本消费与生命周期**（2.4.2）：账本建完并切完占用之后，谁从里面取址——`pg_alloc_page`、`alloc_lowest`、取整推演、移交 VM 的 16 条截断、模块与 unpaged 段的归属变更。依赖第 5 步（账本完成）。
7. **检查综合**（2.6）：模块装载三层检查（次序/条数/区间）的汇总表。依赖第 1 步与第 5 步。
8. **架构对照**（2.7）：ARM32 同名入口、`setup_mbi`、闭区间 `overlaps` 的差异。依赖第 1–5 步的 C 行为。
9. **归纳与证据**（2.8）：`pre_init` 调用树、D1–D5 的陈述与锚点、本章小结/术语/失败对照/最小示例。依赖前面全部。

2.0 是导读，放在链首；章末的失败对照、最小示例、小结、术语是教程构件，放在链尾。依赖图排出的顺序是：2.0 → 2.1 → 2.2 → 2.3 → 2.4.1 → 2.4.1.1 → **2.5 → 2.4.2** → 2.6 → 2.7 → 2.8 → 章末构件。

关键判断只有一条：**2.4.2 作为“消费者与生命周期”整体，应排在 2.5 之后**。2.4.1 的结算自己写明“内核与各模块占用的区间将在 §2.5 从里面切掉（到这里尚未切）”（466 行）；2.4.2.5 的表格第一行就是 §2.5 的“切占用”，并且注明“第一行属 §2.5，只作对照，不是本节主体”（589–595 行）。2.4.2.1–2.4.2.3 可以勉强读成 2.4.1 的延伸，但 2.4.2.4/2.4.2.5 明确是下游，整块放在 2.5 之前会让账本的生命周期倒着讲。

## 本章越界

### 硬性契约

Ch2 只允许 Minix3 C 行为、源码锚点、C 侧判据；禁止 Rust 设计、项目类型、代码走读。逐项核对：

- **项目类型/Rust 标识符**：无。命令 `grep -nE 'KernelInfo|BootReport|BootStorage|RamAuthority|SourceRecord|KernelInfoView|BOOT_HANDOFF|KERNEL_INFO|\bv1\b|\bv9\b|\bv10\b|wire'` 在切片上无命中。
- **Rust 设计**：11 行命中 `Rust`（122、123、201、267、470、582、585、629、631、714、834 行），全部是跨章指针，没有展开 Rust 设计、类型或协议内容。不构成禁止项。
- **代码走读**：本章大量“逐条解码”C 源码（2.2–2.7）。如果把这句禁止读成“任何逐行走读”，本章整体越界；但该读法会让“2. C 源码分析”的章名与 outline Ch2 知识点 2/3 的函数级要求自相矛盾，且机械检查只禁项目 Rust 类型/函数名。按后一种读法，C 逐段解码属于允许的 C 行为/判据。建议章契约把“代码走读”明确限定为“项目 Rust 代码走读”，消掉这个歧义。

### 边界扩张（outline/S2 未列，非硬性禁止，需作者确认）

1. **2.3 的 `rootdevname` 读者链（272–297 行）**。S2 只要求“从引导器到 `kinfo` 的交接路径”；这里写到 PM 的 `GET_MONPARAMS`、`PMGETPARAM`、RAMDS 的 `rc` 与 mib 的 `kern.root_device`，已越过 `kinfo` 进入用户态读者。它是 C 行为、有锚点，并用来证明“内核只当搬运工”，但属于下游扩张。后果：2.3 从“记录构造”扩成“记录消费”，与用户态章节的边界模糊。若保留，建议在节首标明“下游读者链，只作判据”。
2. **2.4.2.4 的 VM 16 条截断（583–586 行）**。outline Ch2 未列，S2 未要求。它是 C 行为，但主题是“清单怎么传下去”，属于 Ch3/Ch4；585 行自己指向“第三章与 §4.5”。后果：Ch2 提前消费 Ch3 的容量/落地区话题。
3. **2.4.2.5 的模块与 unpaged 段归属变更（587–631 行）**。标题自认“下游延伸”；outline Ch2 未列；内容包括 `arch_boot_proc`、`kmain` 后段、VM 的 `exec_bootproc`/`free_mem`，都在 `pre_init` 之后。2.2 的 123 行已把 `kmain`/`k_initial_stktop` 判给 02 篇 §2.3/§2.4，这里再写一遍“还引导段”会与 02 篇形成双重边界。后果：本章主路径被生命周期表打断，且表首行前向引用 2.5。
4. **2.4.2.3 的 `alloc_lowest` 参数错位长推演（553–580 行）**。它依赖 `arch_init`/SMP 路径，已在 `pre_init` 之后；outline Ch2 知识点 3 的函数清单只列 `get_parameters`、`mb_set_param`、`add_memmap`/`cut_memmap`、`overlaps`，没有这一项。它是 C 侧判据（允许），但深度超出 S2 的“解释三个函数如何把引导器数据变成内核记录”。后果：S2 读者要穿过 28 行 bug 证明才能回到 2.5。若保留，建议标成“C 侧判据旁支”或移到 2.5 之后。
5. **2.2 的构建/链接布局链（118–122 行）**。`Makefile.inc` 的对象次序、`kernel.lds` 的收段规则、`objcopy --prefix-symbols` 与 SysV 栈对齐风险，都是 C/build 判据，允许；但它把 2.2 的入口叙事拉长，且结论是“风险提示，不是设计选择”，与本章其他确定判据的语气不同。后果：2.2 的三个教学点里，栈对齐这一条落到“本项目没有保存反汇编证据”，读者拿不到可执行结论。若保留，建议降为脚注或把构建链移到 2.8 的 D2 附近。

### 漏项与跨章指针

1. **12 行的前置概念引用了旧版 Ch1 的实现名**。原文说“第 1 章 §1.3 的 `struct kinfo`、`get_parameters`、`add_memmap`/`cut_memmap` 三个名字；本章展开它们的实现”。Ch1 摘要的“下游可以引用什么”只列三类数据的抽象定义、I1–I4、声明者/转交者/所有者三角色与承重接缝，并明确“不得把 Ch1 的概念改写成类型名”；outline 的“上一章回顾”也说 Ch1 已重写为概念级章。故这行很可能引用的是 V3.13 重写前的 Ch1。后果：前置链断裂，读者按指针找不到这些 C 名字。建议改为“Ch1 的三类数据与 I1–I4；本章首次给出它们的 C 侧名字与实现”。
2. **863 行的 D1–D5 定义锚点不可由 Ch1 摘要复核**。原文说“D1–D5 ... 定义在 §1.4”。Ch1 摘要只列 I1–I4，没有列 D1–D5；§1.4 在摘要里作为接缝/边界锚点出现。无法由摘要证实 §1.4 含 D1–D5 定义。后果：D1–D5 的定义锚点可能落空。建议作者用 Ch1 原文核对；若 §1.4 不含 D1–D5，就在 2.8 给出一句话定义再引证据，或改指正确小节。
3. **718 行的 2.6 综合表丢了 2.1 的一条分支**。2.1 的 86 行明确有两条反序路径：正常分配下 `HAS_MODS` 已置位、停在 `assert(mi_mods_count > 0)`；模块表分配失败时 `HAS_MODS` 未置位、停在查标志的断言。2.6 的“次序”行只写“失败现场：`assert(mi_mods_count > 0)`，不是查 `HAS_MODS` 的那条”，把分配失败分支压掉了。后果：按 2.6 诊断分配失败路径会找错断言。建议在表里补半句“模块表分配失败时先停在 `HAS_MODS` 断言”，或直接指向 2.1 的两条路径。
4. **867/869 行的 D3/D5 只写“在 02 篇 J3”，没有一句“为什么”**。S2 明确要求“说明 D3/D5 为何归 02 篇”；834 行有概括理由（五步属 02 篇的镜像半），但 D3/D5 行本身没有。后果：S2 的掌握声明在 D3/D5 处只能靠读者自己拼。建议各加一句“建表/开分页的机制与证据属 02 篇，本篇只保留调用位置与约束名”。
5. **2.8 的调用树（836–861 行）是 outline Ch2 知识点 2 的交付物，却首次出现在归纳节**。这不是漏项，是位置分叉的后果：2.2 结束时读者没有调用树，2.8 既要归纳又要首次合成。建议在 2.2 末尾给一张只含 `pre_init` 直接调用的最小树（`get_parameters` 加五步 `pg_*`），2.8 再给带 D1–D5 标注的完整版；或者更新 outline，把“调用树”明确写成 2.8 的合成交付物，2.2 只负责入口。二者选一，不要让 outline 与正文各说一套。
