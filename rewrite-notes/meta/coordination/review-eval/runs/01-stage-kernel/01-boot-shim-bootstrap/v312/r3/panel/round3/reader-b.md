# READER-B · R3 结构编辑报告

## 我的结构重建（背景，不计入准入项）

全文的论证链是：§1 用「三份数据 + I1–I4 + 框 1/框 2 + D1–D5」把「交接成立」定义成一个可检查的问题，并把 `pre_init` 切成 01/02 的接缝；§2 以 C 侧 boot2/GRUB 契约、`head.S`、`get_parameters`、内存账、`overlaps`、模块三层检查、ARM32 对照和 D1–D5 证据建立真值基线；§3 依次回答协议为什么换代、`KernelInfo` 为什么按值、两张表为什么带 `SourceRecord`、bootstrap 区间与页表分配器为什么换手、取件为什么只抽 `FileLoader`、五条生产腿怎样收敛、I3/I4 怎样落成所有权与门链；§4 把设计压到入口链、九动作、取件、`BootReport`/`KernelInfo` 构造、六个落地区、arena/分配器换手、C→Rust 映射与 Direct Map 概念入口；§5 按 I1–I4 给宿主/真机证据并逐条写「不证明什么」；§6 按 EBS 分界、panic、失败模式与命令给诊断路径；§7 是索引。

结构上最稳定的装置是「主张 → 反事实 → 证据锚点」：几乎每个设计选择都配一个「如果不这样做会怎样」，每个 C 行为都尽量给 `file:line`。这也是全文很长却不散的原因。最重的结构负担是「五条生产腿 / 三条 v1 腿 / 两个直核面 / 四种交接面 / 六条三类链 / 五个真机门」这套多口径计数：§3.6 节末给了换算表并声明为权威，但读者在到达那张表之前就要能区分两个「五」，这是全文最容易掉线的地方。

我按角色记录四类结构问题：职责重叠（同一机制在 C/Rust/测试三层各展开一次）、前提倒置（少数结论先于其定义或证据出现）、章节边界（§3.2.2 与 §4.1 最明显）、重复与冗余（计数、删除账、注册故事）。下面先列我在阅读中真正停下来的准入项，再列改进机会。
