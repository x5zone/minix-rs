## 1. 专项：2.5 → 2.5.1 是否解决“先消费后切账”

### 1.1 结论

**在 2.5/2.5.1 边界上，解决了。** 新顺序是“先切占用（§2.5），再讲 `pre_init` 返回之后的两处加回（§2.5.1）”；这与 C 的时间序一致：`pre_init → get_parameters` 里切 → `arch_boot_proc` 里还 VM 镜像 → `kmain` 后段还引导段。若反排（2.5.1 在前），读者会先看到 VM 模块的字节被 `add_memmap` 加回，却还不知道这段字节在 `pre_init` 里被切过；“还”失去前提，“先消费后切账”的倒置就出现。新顺序消除了这个倒置。

### 1.2 证据

1. §2.5 开头把“切”定为建账之后的第一步：“内存账建好后，要从中切掉两块东西：模块占用的区间与内核自己占用的区间。”（619 行）
2. §2.5 末尾用框 1 的完成收口：“到这里，§2.4 的‘原材料已就位’加上本节的 `overlaps`/`cut_memmap`，框 1（可用物理内存清单）才真正完成——§2.4 的结算只承诺原材料。”（698 行）
3. §2.5.1 开头以切占用为既成前提：“`cut_memmap` 在 `pre_init` 里被调用时只覆盖引导期占用，切除本身不会在 `pre_init` 返回前撤销；这份账在 VM 接手后由 VM 的空闲位图取代，只有内核 unpaged 段会在 `kmain` 后段被加回。”（702 行）
4. §2.5.1 表第一行明确标注“**切占用**（§2.5 执行，不是 §2.4）”，把“切”与“还”分开；表按动作时间排序：切占用 → 还 VM 镜像 → 还引导段（704–708 行）。
5. “三条容易混的口径”把三个动作的对象分清：切占用处的是“模块字节连同内核镜像自己那一块”，还 VM 镜像处的是“模块字节”，还引导段处的是“unpaged 段”（710 行）。
6. §2.5.1 结算再把三处动作收成一句：“三处改账动作……把 VM 模块的字节交回系统（其余模块不归还，见本节末）、把内核镜像排除在可用清单之外、并在 `kmain` 后段归还 unpaged 段。”（748 行）

### 1.3 反排的后果（为什么新顺序是必要的）

如果 2.5.1 排在 2.5 前面，读者会先读“还 VM 镜像”的 `add_memmap(&kinfo, mod->mod_start, mod->mod_end-mod->mod_start)`（723 行），却不知道 `mod` 这段区间在 `get_parameters` 里已经被 `cut_memmap` 切走。此时“还”是一个没有前因的动作；读者要么把它误读成“模块内存一直在账上”，要么被迫跳到后面补看切占用。新顺序把“切”作为“还”的前提先立起来，这是正确的。

### 1.4 残留：2.4.2 的消费者仍先于 2.5 的切占用

新顺序只解决了 2.5/2.5.1 这个边界。**2.4.2 的取址消费者（`pg_alloc_page`、`alloc_lowest`）仍然排在 2.5 的切占用之前**：读者先学“怎么从账里取页”，后学“账里哪些段要先切掉”。本章对这一点有缓解：

- §2.4.1 结算说“到这里尚未切；这是 §1.1 框 1 的原材料，框 1 要到 §2.5 的 `cut_memmap` 之后才完成”（494 行）。
- §2.5 开头再说一次“内存账建好后，要从中切掉两块东西”（619 行）。
- §2.4.2.3 的四前提里，前提二已经包含 `arch_init` 的两条 `cut_memmap`（600 行）。

但第二级结论里“跳板所在的低条目在第三行常态下不是最高条目”（606 行）这一布局观察，以切占用之后的账为前提；正文没有回指 §2.5。读者在 2.4.2.3 无法验证这个观察，只能先接受 `[观测]` 标签。建议在第二级结论加一句“该布局观察以 §2.5 的切占用为前提”，或把第二级结论移到 §2.5.1 末。这是 P2，不是阻断项：本章的状态标记已经把“账还没切完”说清楚了，缺的是一句前向指针。

另外，§2.5.1 表第一行的“谁做”列写的是 `cut_memmap`（本篇 2.4），行首又写“§2.5 执行，不是 §2.4”；这两个括号一个指函数定义、一个指动作执行，读者容易混。建议把“谁做”改成“`cut_memmap`（定义见 §2.4.1.1）”，与“执行在 §2.5”分开。

### 1.5 另一个可选的节序改动

把 **2.4.2.4（清单移交 VM 时的 16 条截断）从 2.4.2 移到 2.5.1**（或新设 2.5.2“移交给 VM”）。本章自己也承认“它不属于‘取址’，但属于同一份清单的生命周期，紧接 `mmap_size` 的边界讨论放在这里”（615 行）。这句话是自认的例外：既然它是生命周期话题，就该和 2.5.1 的“还 VM 镜像/还引导段”放在一起。移过去之后，所有“账的后期生命”集中在一处，“先消费后切账”的散布感会进一步降低。这是本次复核里价值最高的节序建议之一（见第 10 节第 1 条）。

## 5. 示例与失败对照

### 5.1 正文里的示例与失败对照（强）

本章的示例密度很高，而且大多是“可手算/可对照”的：

- §2.2 的“三处教学点”先预告、再逐行、再回收（95、139 行）。这是全章最好的教学模板：**预告 → 展开 → 回收**。
- §2.3 的 `param_buf` 字节图（275–281 行）：`A=1\0B=2\0\0`，三行表格把“删除扫描只对首条生效”的 off-by-one 讲成可手算的事实。
- §2.3 的 `board` 五场景表（319–325 行）：把“删掉删除循环”的后果逐行对照。
- §2.4.1.1 的 `cut_memmap` 手算（477–492 行）：一条 `[0x100000, 0x1000000)` 被 `[0x400123, 0x401F00)` 切成两段，长度和校验 `0x300000 + 0xBFE000 + 0x2000 = 0xF00000`。这是全章最好的 worked example。
- §2.5 的“去掉 `-1`”对照（689–696 行）：A `[0x100000,0x200000)`、B `[0x200000,0x300000)` 相切，误报 `panic`。一步一步算出 `INRANGE(B, A.mod_end=0x200000) = 真`。
- §2.5 的“去掉 `overlaps` 整个函数”对照（698 行）：账不会坏，坏的是模块字节。这个反直觉结论讲得很清楚。
- §2.4.1 的“只给粗档”对照（366 行）：保留区被记成可用，`pg_alloc_page` 迟早撞上，症状是静默丢写/随机挂死。这是“失败现象离原因很远”的好例子。

这些示例覆盖了本章的两个半边（参数/文本半边与内存账半边），质量高。**P2 建议**：§2.3 的 `board` 表把“现状四行”和“反事实一行”混在同一张表里，第五行“删掉循环”的“后果”是反事实，前四行是现状。建议加一列“现状/反事实”，或在表前一句话说明“前四行是当前代码行为，第五行是删循环后的反事实”。否则读者会把第五行也当成现状。

### 5.2 章末“失败对照”（覆盖偏窄）

章末失败对照（919–921 行）只讲了一件事：`load_mods` 写在 `multiboot` 之后，内核停在 `assert(mbi->mi_mods_count > 0)`，不是查 `HAS_MODS` 的那条；另一条路是模块表分配失败。这个对照很好，有断言名、有诊断方向、有 §6.3 的现场输出指针。

但它只覆盖 §2.1 的模块装载，没有覆盖本章的另一半——内存账。**P2 建议**：加一条内存账侧的章末对照，例如“把 `overlaps` 整个去掉 → 账不错，但两个模块的字节互相覆盖，内核一声不响”（§2.5），或“把 `alloc_lowest` 的 `cut_memmap` 参数写成 `len` → 当前调用序下落第三行常态，跳板页仍挂在空闲账上”（§2.4.2.3）。这样章末对照才代表全章，而不是只代表开头。

### 5.3 章末“最小示例”（是自查命令，不是机制示例）

最小示例（923–934 行）是三条 `grep`：

1. `grep -rn rootdevname minix3/minix/kernel/` → 无输出，证明内核不解释 `rootdevname`。
2. `grep -n 'assert(magic == MULTIBOOT_INFO_MAGIC)' ...` → 一行，给出 `pre_init` 的第一道门。
3. `grep -n 'add_memmap\|cut_memmap\|mb_set_param' ...` → 三个入口。

这三条是**可运行的**，也确实是“最小”的，但它们验证的是“代码里有没有这个东西”，不是“机制怎么走”。本章的真正最小示例是 §2.4.1.1 的手算和 §2.3 的字节图。**P2 建议**：把这一节改名为“自查命令”，另加一条端到端微走读，例如：

```
boot.cfg: rootdevname=c0d0p0
  → cmdline: "... rootdevname=c0d0p0 ..."
  → param_buf: "rootdevname=c0d0p0\0\0"
  → sysenv rootdevname → c0d0p0
```

这条微走读把 §2.1 的指令、§2.3 的逐词扫描与 `mb_set_param` 的追加格式串起来，才是“最小机制示例”。现在的三条 grep 可以保留为“自查”。

### 5.4 §2.5.1 的“其余模块不归还”代价分析（过长）

§2.5.1 的 736–744 行是一段很长的代价分析：12 个模块、11 个不归还、17 项 `image[]`、5 项内核任务、两本账、残差三项（`arch_init` 的 `0x10C00`、`add_memmap` 的尾页取整、`alloc_lowest` 的空操作一页）。结论是“这段代价不该被夸大成病根；它真正的坏处是安静；残差不是单因”。这个结论很重要，但数字密度很高，读者容易在第三行就丢失主线。**P2 建议**：拆成“结论段（三句话）+ 对账细节（折叠/选读）”。结论段只说：内核账不收回其余模块；VM 接手后回收；在 VM 接手前这段内存不可用；它不是 OOM 的根因。对账细节留给排障时读。

## 6. 节序依赖（除 2.5 专项）

### 6.1 §2.4.1 先用 `mmap_size`，§2.4.1.1 才定义

### 6.2 §2.4.2.3 的论证是非线性的（P1）

这是本章最需要修的一处节序。§2.4.2.3 的顺序是：

1. **判决**（585 行）：`alloc_lowest` 参数错位；四前提成立时落在“第三行常态”；“调用序落在**上表** `len ≤ lowest` 那一行”。
2. **反事实 B**（587 行）：“若 `cut_memmap` 不把 `start` 向下、`end` 向上取整”。
3. **解释 A**（589–595 行）：“若 `alloc_lowest` 的切除参数写错会怎样”，三行表。
4. **四前提**（597–602 行）。
5. **第一级结论**（604 行）、**第二级结论**（606 行）。

问题有三层：

- **“上表”指向下方**：585 行说“上表”，但三行表在 591 行，是下表。读者会先往上找，找不到。
- **反事实 B 插在判决 A 与解释 A 之间**：读者刚读到“参数错位”的判决，就被拉到 `cut_memmap` 取整的反事实，再回到 `alloc_lowest` 的解释。论证的主线被打断。
- **2.4.2.2 把参数错误推迟到 2.4.2.3**（563 行：“参数错误本身……放到 2.4.2.3 一次推完”），制造了一个前向依赖；读者读完 2.4.2.2 的“校验缺口”，手里悬着一个“参数错误是什么”的问题，再进入 2.4.2.3 的判决。这是有意的悬念，但代价是工作记忆。

本章用“读法”（498 行）承认了这个非线性：“第一次读先读 2.4.2.3 的判决与 2.4.2.1 的‘下标序与地址序’，排障时再回来读四前提与第二级结论。”这是一条缓解措施，但它本身证明自然阅读顺序不成立。**P1 建议**：把 2.4.2.3 线性化为：

1. `alloc_lowest` 参数错位的解释 + 三行表（`lowest == 0` / `0 < lowest < len` / `len ≤ lowest`）；
2. 四前提；
3. 第一级结论（第三行常态）；
4. 第二级结论（布局 + 生命周期）；
5. `cut_memmap` 取整的反事实——移到 §2.4.1.1 的取整解码之后（471 行“取整在非退化请求上不改变净账本，真正改变净可用区间的是退化请求，见 §2.4.2.3”正好是它的位置），或放在 2.4.2.3 结论之后作为“另一条防线”。

这样“判决 → 解释 → 前提 → 结论”是一条直线，读者不需要“读法”覆盖。§2.2 的“预告 → 展开 → 回收”模板可以直接套用到这里。

1. 引导器契约由识别头、寄存器约定与 `mbi` 三样东西对接。
2. `get_parameters` 整份拷贝 `mbi`，再把命令行、模块表、内存图变成 `kinfo` 的记录。
3. `add_memmap` 建清单，`overlaps`/`cut_memmap` 逐条切除内核与模块占用区。
4. D1–D5 是约束名，不是执行序；证据都在本章与 02 篇的建表节。

**修法**：把小结改成与 S2 一一对应的六条（或三条，每条带分句）：

1. `boot.cfg` 三条指令各自送到哪、内核哪一段读它；`load_mods` 必须写在 `multiboot` 前面，反序停在 `assert(mi_mods_count > 0)`。
2. `head.S` 入口三件事（设栈、清帧指针与标志、按调用约定传参）；栈从 4096 对齐的 `load_stack_start` 起，入口 `%esp ≡ 0` 而非 SysV 的 `≡ 12`，是风险提示不是设计选择。
3. `get_parameters` 的三次转换：整份 `memcpy` `mbi`；命令行逐词 → `param_buf`；`mmap`/`mem_lower`/`mem_upper` → `memmap[]`；然后 `overlaps`/`cut_memmap` 逐条切占用。
4. D1/D2/D4 的 C 证据在本章（§2.3/§2.4/§2.5/§2.8）；D3/D5 的语义与证据在 02 篇 J3，因为建表与开分页属于“内核怎么走到高半去跑”那个主题。
5. 账的后续：VM 模块的字节在 `arch_boot_proc` 加回，unpaged 段在 `kmain` 后段加回，其余模块不归还（VM 接手后另行回收）。
6. ARM32 复用同名入口与函数名；差异在参数来源（`setup_mbi`）与 MMU 寄存器；`overlaps` 的闭区间差异是另一处对照。

**P2 补充**：小结完全没有提 §2.4.2 的 `alloc_lowest` 参数错位/第三行常态，也没有提 §2.5.1 的三处改账动作。前者是本章最长的一段分析（585–610 行），后者是本章的下游收口（700–748 行）。如果它们是核心，小结应该各给一条；如果它们是选读，§2.0 的路线图应该标“选读”。现在的状态是“正文很重、小结不提”，读者无法判断该不该掌握。建议二选一，不要悬着。

### 9.3 “第三行常态”与“上表”

“第三行常态”在 585 行先于它的三行表（591 行）使用，并说“上表”；术语（952 行）有定义，小结没有。这三件事指向同一个问题：**这个术语的引入顺序是“先用后定义，且指向错位”**。如果采纳 6.2 的线性化建议，把三行表放在判决之前，问题自然消失；否则至少把“上表”改成“下表”，并在首次使用时给一句“三行表见下”。
