## 1. FINDING

### F1 · IST 单写者：§3.7 的表格行与同节正文互相否定

- **位置**：§3.7 L1076（正文）与 L1082（"IST 恢复"行）；对照 §4.4 L1322、§5.4 M1（L1523）、M3（L1525）。
- **严重度**：P1（本节的中心不变量被表格反写成相反设计）。
- **问题**：正文说"`set_handler` 是唯一写者……IST 取自 NMI/#DF 表（2→IST1、8→IST2）"；表格"选择"列却写"`set_handler` 写 IST=0 后由安装器恢复 NMI/#DF"，并把"让 `set_handler` 自己记得 IST"放进"否掉什么"列。按表格读，选中方案是**两个写者**（`set_handler` 写 0，安装器再写 1/2），正是正文与 §4.4 断言不存在的第二来源。
- **影响**：读者若按表格实现，会引入第二次写门动作；§3.7"安装后立即断言 IST"的检查点也会落空（断言前 IST 已被安装器改过，`set_handler` 的 IST 逻辑等于死代码）。这是本篇唯一的"单写者"论证，写反了等于论证自毁。
- **证据**：L1076 与 L1082 字面冲突；L1322 明说"仓内没有 `set_gate_ist`"，排除"安装器恢复"的实现可能；§5.4 M1 把"41 门 DPL/IST/type 断言"归给 `install_idt_handlers`。三处都指向单写者。
- **最小修复**：把该行改为"选择：`set_handler` 内部按 NMI/#DF 表写 IST（唯一写者）；否掉：`set_handler` 只写 handler/DPL、由安装器二次恢复 IST（多一个写者与一次簿记，且与 §4.4 的断言时机冲突）"。
- **置信度**：0.9（仅凭文档内三处互证即可判定，无需源码）。
- **若我错了**：若代码实际是"`set_handler` 写 0、`install_idt_handlers` 调另一个内部函数恢复 1/2"，则 L1322 的"唯一写者/没有 `set_gate_ist`"两句是错的，应改正文与 §4.4，而不是改表格。两种修法互斥，文档必须二选一。

### F2 · §2.3 LDT 占位槽的"必须存在"论证不成立

- **位置**：§2.3 L462（"它为什么必须存在：`lldt` 要求选择子指向一个 LDT 类型的描述符，槽里没有描述符就没法执行这条装载"）。
- **严重度**：P2（因果前提错误，结论靠它支撑）。
- **问题**：`lldt` 接受**空选择子**（selector 0）并把 LDTR 标为 invalid，不需要任何描述符存在。所以"槽里没有描述符就没法执行这条装载"是错的：`lldt $0` 同样是合法装载。C 代码选择装一条**非空**的 bogus 描述符，需要槽里有一条 LDT 类型描述符；这是"选了非空选择子"的后果，不是 `lldt` 指令的硬性要求。
- **影响**：读者会得出"GDT 第 5 槽是架构必需"的结论，而文档自己在同一段只说源码注释叫它 `unusable LDT`/`Load bogus ldt`——注释支持"bogus"，不支持"必需"。这也会误导 Rust 侧"淘汰 LDT"的正当性论证（§3.1 L888 说长模式不使用 LDT，本来是对的；若第 5 槽真"必须存在"，淘汰就需额外解释）。
- **证据**：本段引用的两条源码注释（`unusable LDT`、`Load bogus ldt`）本身只证明"故意装一条不可用的"；`lldt` 空选择子的语义属 x86 规范常识（外部资料，文档 §1.4 已把 SDM 列为外部资料）。
- **最小修复**：改成"`lldt` 允许空选择子；C 选择装一条**非空**的占位描述符（注释自称 bogus），这条路径要求槽里有一条 LDT 类型描述符。源码没有给出选择非空而非空选择子的理由，本段不替它编动机。"
- **置信度**：0.85（规范层面确定；不确定的是 C 作者是否有未写出的理由）。
- **若我错了**：若本项目的 `x86_lldt` 包装对选择子 0 有额外断言（文档未提），则"必须存在"对**这份代码**成立，但仍应写成"本实现的封装不接受空选择子"，而不是"`lldt` 要求"。

### F3 · 第二次 `tss_init` 会清掉 busy 位，与 §2.5 的 busy 叙述未对账

- **位置**：§2.4 L588（`arch_init` 第二次 `tss_init`，参数换成 `get_k_stack_top(0)`）与 §2.5 L619（"`ltr` 成功后 CPU 把描述符 type 从 1001 置为 1011，改的是内存里的 GDT 表项……同一个实例第二次调 `load()` 会在 `ltr` 处撞上 busy 描述符而 #GP"）。
- **严重度**：P2（跨节因果链断点，读者无法判断第二次 `tss_init` 是否安全）。
- **问题**：`tss_init` 每次都会重写 `tssgdt->access = PRESENT | (DPL<<…) | TSS_TYPE`（§2.4 L486），即把 type 写回"可用"。`arch_init` 的第二次调用发生在 `prot_load_selectors` 的 `ltr` **之后**，所以它会把 CPU 刚置上的 busy 位在内存里清掉。§2.5 的 busy 叙述没有提这件事，读者顺着读会以为 busy 位一旦置上就一直在，进而怀疑"第二次 `tss_init` 会不会撞 busy / 是否必须重新 `ltr`"。
- **影响**：两个具体误读——(a) 以为换栈（`k_boot_stack` → `k_stacks`）必须重新 `ltr` 才生效（实际只需改 TSS 结构体里的 `sp0`，CPU 每次转场按 TR 缓存的基址读 TSS 内存；描述符基址 `&tss[cpu]` 两次相同）；(b) 以为 Rust 的 busy 检查能覆盖 C 的这条路径（它只覆盖"同一实例重复 `load`"，不覆盖"重写描述符后再 `load`"）。
- **证据**：L486（access 被整个赋值，type 回到 available）、L588（第二次调用在 `cstart` 的 `arch_init`，晚于 `prot_load_selectors`）、L619（busy 叙述未提重写）。三者都是文档内文本。
- **最小修复**：在 §2.4 末尾补三句：第二次 `tss_init` 重写描述符 access 会把 busy 位清回 available；TR 已缓存基址，重写描述符不改变已装载的 TR，`sp0` 是 TSS 结构体字段、每次转场现读，所以换栈无需重新 `ltr`；Rust 的 busy 检查只针对 `load` 路径。
- **置信度**：0.8（"access 整个赋值 = 清 busy"由 L486 字面推出；"TR 缓存基址、sp0 现读"是长模式转场语义，属外部规范）。
- **若我错了**：若 `TSS_TYPE` 展开后恰好含 busy 位（文档 L541 说是 `AVL_286_TSS | DESC_386_BIT`，AVL 即 available，不含 busy），则 F3 不成立。文档自身的展开说明支持我。

### F5 · §3.3"暴露面为零"与 §3.6 的无门窗口自相矛盾

- **位置**：§3.3 L975（"当前形状的搬移-重建窗口在 CLI 关闭、IDT 未装载的直线代码里，暴露面为零"）对照 §3.6 L1072（"控制器编程期间若发生异常或 NMI……IDTR 仍是引导方的值，门指向固件代码"）。
- **严重度**：P2（安全论证的结论方向相反，读者会据此认为该窗口无风险）。
- **问题**：搬移-重建窗口在 `init_protection` 内部，此时内核 IDT 尚未 `load`，CPU 用的仍是**引导方的 IDT**——不是"没有 IDT"。CLI 只挡可屏蔽中断，挡不住 NMI/#MC。所以该窗口的暴露面与 §3.6 描述的窗口**同源**，不是零。若作者本意是"不新增暴露面"（整个 `init_protection` 都在既有无门窗口内），这句话必须这么写；现在的三个理由（CLI、IDT 未装载、直线代码）都不支持"零"。
- **影响**：读者会跳过对该窗口的防御性推理；更糟的是与 §3.6 对照时无法判断哪句是真的。这是本轮唯一一处**结论级**矛盾（不是措辞）。
- **证据**：L975 与 L1072 的直接对立；L623 也承认 `lgdt` 之后的窗口"异常递送轴不设防"。
- **最小修复**：改为"该窗口完全落在内核 IDT 装载之前的既有无门窗口内，不新增暴露面；NMI/#MC 仍按引导方 IDT 递送，与 §3.6 同源"。
- **置信度**：0.85。
- **若我错了**：若 `store_protection`/`refresh_descriptors` 之间确实存在一条独立的"内核 IDT 已装载"前提（文档没有），则"零"可能成立；但 §4.2 的次序明确 `prot.load()` 在 `trap.load()` 之前，且 `refresh_descriptors` 紧跟在 `prot.load()` 之前——IDT 一定还没装。

### F6 · 向量 33 被叫作"IPC 门"，与 §1.2/§5.2 的选择子命名冲突

- **位置**：§5.1 L1479（"IPC 门（向量 33）由 `install_trap_stubs` 装 stub"）；对照 §1.2 L89（"`int $0x20/$0x21` 软中断门（十进制 32/33；libc 主路径，后者是 IDT 门）"）与 §5.2 L1503（`test-user-trap` 以 `int $0x21`（十进制 33）进门）。
- **严重度**：P2（诊断/测试名对账会指错向量；读者无法从文档判断 32 与 33 各是什么）。
- **问题**：按文档自己的写法，0x20=32 在前、0x21=33 在后，且测试用 33 进"系统调用"路径；那么 33 应是 SYS 向量，IPC 应是 32。§5.1 却把 33 标成 IPC。§1.2 的"后者是 IDT 门"也语义不明（两者都是 IDT 门）。
- **影响**：读者按"IPC 门（33）"去找门表会找错；§6.1 的诊断没有给向量号，无法自纠。
- **证据**：L89、L1479、L1503 三处对同一向量的称呼不一致。
- **最小修复**：统一为"IPC 门（向量 32，0x20）/ 系统调用门（向量 33，0x21）"，并把 §1.2 的"后者是 IDT 门"改成"两者都是 IDT 门，0x21 是 libc 主路径"。
- **置信度**：0.75（命名约定是 Minix3 常识；文档内三处互证足以判定不一致，但哪一个是笔误需源码确认）。
- **若我错了**：若 Minix3 的 IPC 向量确实是 0x21、系统调用是 0x20，则 §5.1 对而 §1.2/§5.2 的读法要改；无论哪种，现文本不自洽。

### F7 · `#GP(0x28)` 与 SYSRET 的 `|3` 规则对不上

- **位置**：§4.3 L1211（"选择子 `5*8 = 0x28`……`#GP(0x28)`"）、同段引用的常量注释 L1198（"`CS ← (STAR[63:48] + 16) | 3`"）、§6.1 L1592（"#GP(0x28)"）。
- **严重度**：P3（机制对、数字对账会卡住；但会污染诊断表的搜索串）。
- **问题**：按 L1198 的规则，`STAR[63:48]=0x18` 时 CS = `(0x18+16)|3 = 0x2B`（槽 5、RPL=3），不是 0x28。0x28 是去掉 RPL 的槽基址。若实测日志确实打印 0x28，那是因为 QEMU 在 #GP 错误码里掩掉了低两位（外部工具行为），文档必须说明；否则读者用 `|3` 复算会得到 0x2B，认为注释记错。
- **影响**：诊断表让读者在日志里搜 `#GP(0x28)`，真机/其他模拟器可能给 0x2B。
- **证据**：L1198 与 L1211/L1592 的同段自相矛盾。
- **最小修复**：加一句"0x28 是槽基址（5×8），实际装载的选择子是 `0x28|3 = 0x2B`；日志里的 0x28 是错误码掩掉 RPL 低两位后的读数"。
- **置信度**：0.7（|3 规则确定；QEMU 掩码行为是回忆，不确定）。
- **若我错了**：若硬件在 SYSRET 的 CS 装载里不做 `|3`（某些文档版本的伪代码只写 +16），则 0x28 直接成立，本条降为"请注明依据"。

### F8 · §3.7 表格行与正文的另外半处冲突：`set_handler` 是否"记得 IST"

- **位置**：§3.7 L1082（同 F1 的行）"代价：多一次簿记"。
- **严重度**：P3（与 F1 同源，合并修）。
- **问题**：若选中方案是单写者（`set_handler` 自己按表写 IST），代价不是"多一次簿记"，而是"`set_handler` 必须内置向量→IST 映射，DPL 走参数、IST 走内置，两个来源不对称"。表格的代价描述只对两写者方案成立。

- **证据**：L1082"代价"列与 L1076 的实现描述。
- **最小修复**：随 F1 一并改代价列为"`set_handler` 内置向量→IST 映射，DPL 与 IST 的来源不对称"。
- **置信度**：0.85。
- **若我错了**：若实际是两写者，则 F1 反过来成立，本行保留。

## 2. SUGGESTION

### S1 · §2.0"只有该槽残留一条可用 TSS 描述符时"是不可能分支

- **位置**：§2.0 L167。
- **问题**：同一函数在 L389–L390 先 `memset(gdt, 0, …)`，槽 6 必为全零；"残留一条可用 TSS 描述符"在 `memset` 在场时不可能出现。
- **影响**：读者会以为存在一条真实的潜伏路径而多查一步。
- **最小修复**：删掉该分句，或写成"除非同时也去掉 `memset`"。
- **置信度**：0.95。**若我错了**：若 `memset` 只清部分槽（文档写的是 `sizeof(gdt)`，全表），则不成立。

### S2 · `program_gs` 与 `program_entry_base` 两个名字之间没有桥

- **位置**：§3.2 L945（`ProtectionArch::program_entry_base`）、§3.4 L1017（`program_gs`）、§4.5 L1343（`program_gs`）、§5.2 L1489（载体调 `program_entry_base`）。
- **问题**：读者无法判断这两个名字是同一动作的两层（trait 方法转发到自由函数）还是两件不同的事；§4.2 的节选又把 `program_entry_base` 省略在 `...` 里。
- **影响**：追"GS 区在 `load` 之后编程"这条因果链时断一环。
- **最小修复**：在 §3.2 的映射表行或 §4.5 首句加"`program_entry_base` 的 x86-64 实现调用 `trap_stub.rs` 的 `program_gs`"。
- **置信度**：0.8。**若我错了**：若两者确实不同（前者写入口基址、后者写 GS 区），则应各给一行映射。

### S3 · §4.5 的失败证据是 `gs:0x10`，正文说的却是 `gs:0x0`

- **位置**：§4.5 L1345（"入口汇编读 `gs:0x0` 取内核栈顶……`gs:0x10` 读回 IVT 字节"）。
- **问题**：`GsArea` 的 `kernel_stack_top` 在偏移 0，`cpu_id` 在偏移 0x10（§3.4 L1008–L1013）。两处读的是不同字段，"基址 0 → 读到 IVT"对两者都成立，但读者会问为什么证据偏移变了。
- **影响**：小；诊断时不知道该看哪个偏移。
- **最小修复**：写成"入口读 `gs:0x0`（栈顶）或 `gs:0x10`（cpu_id）都会落到基址 0 附近；记录里的现场是 `gs:0x10` 读回 IVT 字节"。
- **置信度**：0.85。**若我错了**：若 `GsArea` 的字段顺序在源码里不同，则以源码为准，但文档内的偏移自述仍是 0/8/16。

### S4 · §2.8"`prot_init_done` 的唯一读者"与前一句不衔接

- **位置**：§2.8 L823（"读者在 `i386/arch_smp.c` 的 AP 启动路径里（`assert(prot_init_done)`）"）与 L830（"唯一读者 `copy_trampoline`"）。
- **问题**：前句说读者是"AP 启动路径里的 assert"，后句说唯一读者是 `copy_trampoline`；读者要自己推断 `copy_trampoline` 就是包含该 assert 的函数。
- **最小修复**：前句直接写"唯一读点是 `copy_trampoline` 里的 `assert(prot_init_done)`"。
- **置信度**：0.9。**若我错了**：若 `copy_trampoline` 不含该 assert，则两句各指一处，文档需给两个位置。

### S5 · §3.6 的"理由落在中断源而不是中断处理"与随后的理由相反

- **位置**：§3.6 L1070。
- **问题**：句首说次序的理由在"中断源"，句末给的理由却是"控制器编程期间的总线异常也有可用的栈与门"——那是中断/异常**处理**。两句都可成立，但被"而不是"连成对立。
- **最小修复**：拆成两条：(a) 源侧：`init` 结束时全部线已屏蔽，所以次序不承担"丢中断"的风险；(b) 处理侧：控制器编程期间的 NMI/总线异常仍需要内核门，所以保护结构必须在前。
- **置信度**：0.8。**若我错了**：若作者本意是"因为源被屏蔽，所以这个次序不是关于源的"，则只需改写连接词。

### S6 · §5.2"实例留在栈上"的解释少了一半

- **位置**：§5.2 L1491。
- **问题**：载体不调 `store_protection`，所以既没覆盖搬移也没覆盖 `refresh_descriptors`；原文只说"不覆盖 store_protection + refresh_descriptors 的搬迁收尾"，把两件事并成一个"收尾"，但 `store_protection` 本身是搬移动作，不是收尾。
- **最小修复**：写成"载体不调 `store_protection`，因此搬移与随后的 `refresh_descriptors` 两步都不覆盖；这两步由 `test-user-trap` 的生产 `init_protection` 覆盖"。
- **置信度**：0.9。

### S7 · §2.5 busy 检查的覆盖范围需要一句限定

- **位置**：§2.5 L619。
- **问题**：同段已说"换一个实例装载会静默换掉 GDTR/TR"，紧接着说 Rust"把'每个 CPU 的常驻实例只装载一次'写进 trait 契约；`load_with_tss` 在 `lgdt` 之前读目标槽的 access 字节"。读者容易把后半句读成"检查覆盖了整条契约"，实际只覆盖同实例重复 `load`（跨实例时新实例的槽是 available，检查必过）。
- **最小修复**：补"busy 检查只覆盖同一实例的第二次 `load`；跨实例替换仍只由 trait 契约约束"。
- **置信度**：0.85。

### S8 · §1.2"后者是 IDT 门"语义不明

- **位置**：§1.2 L89。
- **问题**：`int $0x20` 与 `int $0x21` 都是 IDT 门，"后者是 IDT 门"没有区分力；读者会以为前者是 MSR 路径。与 F6 同源，一起修。
- **置信度**：0.85。
