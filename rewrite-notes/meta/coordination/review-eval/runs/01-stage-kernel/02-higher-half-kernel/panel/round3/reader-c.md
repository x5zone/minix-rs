## FINDING RD3-READER-C-01（P2）

**位置**：§4.4「跳转完成时系统处在什么状态」状态表，第 1072 行。

**原文摘录**：

> `| 程序计数器 | v1 send/receive 与 aarch64 跨镜像：kmain 的高半 VMA；aarch64 direct-core：低地址进入（ldr 取高半绝对值跳）；riscv64 自引导 direct leg：加 delta 后的高半 VMA；测试载体：x86_64/aarch64 低地址、riscv64 高半 VMA（§4.3/§4.4） |`

**严重度**：P2。

**问题**：这一列的列头是「跳转完成时的值」，但 aarch64 direct-core 这一格填的是进入条件「低地址进入」，不是跳转完成时的程序计数器值。同一篇文档另外两处都明确写的是高半虚拟地址：§3.1 登记表第 371 行写「aarch64 direct-core（`bootface_a64` → `arch_boot`） | 低地址进入、物理视图 | 高半 VMA（`ldr` 取绝对值）」；§4.4 装载路径表第 1033 行写「跳转完成时 PC | 高半 VMA（`ldr` 取绝对值）」。三处对同一件事给出了两种表述。

**影响**：读者在建立「进入 `kmain` 时 CPU 状态」这张表时，会把 aarch64 direct-core 误读成跳转后仍停在低地址，与紧邻的两张表冲突；做 GDB 或串口诊断时也无法判断 `$rip` 该读高半还是低半。这不是措辞小病，它落在本篇用来收束全章的状态表上。

**证据或推理**：同一文档内三处对照即可成立，不需要源码。§3.1 的「进入/执行视图」与「跳转完成时 PC」是两列，aarch64 direct-core 分别是「低地址进入、物理视图」和「高半 VMA」；§4.4 状态表把前一列的内容写进了后一列。

**最小修复**：把该格改成「高半 VMA（低地址进入后由 `ldr` 取高半绝对值跳）」。这样既保留「低地址进入」这个事实，又明确回答列头问的「跳转完成时的值」。

**置信度**：0.9。

**是否需源码核实**：否，文档内部三处对照已经足够。

**若我错了**：如果作者的本意是「aarch64 direct-core 跳转完成后 PC 仍在低地址，`ldr` 只是把高半绝对值取进寄存器但未生效」，那么 §3.1 与 §4.4 的另两张表都错了，而状态表是对的；即便如此，三处仍需统一，不能三处三说。

**命中清单**：自相矛盾（同一文档三张表对同一状态给出两种值）；关键因果主张的复述不一致。

## FINDING RD3-READER-C-02（P2）

**位置**：§3.1「生产交接形态（v1 handoff）」段末，第 362 行。

**原文摘录**：

> 「测试载体走 inline `arch_boot`，是低地址执行视图，不是生产路径。」

**严重度**：P2。

**影响**：这正是读者画像要防的「把单形态结论写成普遍结论」。读者若只读 §3.1 的散文，会以为三个测试载体都停在低地址，从而在 riscv64 上把高半 VMA 误判成异常；反过来，若先读表再读散文，会不知道该信哪一处。

**证据或推理**：§3.1 散文（第 362 行）说「测试载体……低地址执行视图」；§3.1 表（第 370 行）把 riscv64 测试载体列为「物理视图 / 高半 VMA」；§4.3（第 990 行）明确把 riscv64 测试载体排除在「x86_64/aarch64 的内联测试载体」之外。三处证据在同一文件内。

**最小修复**：把散文限定为「x86_64/aarch64 测试载体走 inline `arch_boot`，是低地址执行视图」，并补一句「riscv64 测试载体低装高进，跳转后 PC 在高半」。

**置信度**：0.95。

**是否需源码核实**：否，文档内部对照即可。

**若我错了**：如果「inline `arch_boot`」在这里被当作与「低地址执行视图」并列的另一个分类标签（即句子在说「测试载体走 inline 路径，而这个路径属于低地址执行视图」），那么 riscv64 测试载体也走 inline 路径这一点仍会让句子覆盖它；除非作者能指出 riscv64 测试载体不算「inline `arch_boot`」，但 §4.4 第 1022 行写的正是「riscv64 测试载体 → 直接 `arch_boot`」。

**命中清单**：单形态结论写成普遍结论；自相矛盾（散文与表、与后文说明）。

## FINDING RD3-READER-C-03（P2）

**位置**：§3.4「再算一次对齐这笔账（x86_64）」段末，第 589 行。

**原文摘录**：

> 「`and rsp, -16` 与 `sub rsp, 8` 一起把这条不变量钉在本地，而不是修补上游。真正会坏的是"断言、`and`、`sub` 都去掉"：一个非 16 对齐的 `stack_top` 会一路传到 `kmain`，入口栈指针不再满足 psABI，落到入口处需要 16 字节对齐的指令上。」

**严重度**：P2。

**问题**：这句话把失败条件写成「三者都去掉」，暗示只去掉 `sub rsp, 8` 不会坏。按同一段自己给出的算式，只去掉 `sub` 就会坏：`mov rsp, stack_top`（已 16 字节对齐）→ `and rsp, -16` 空操作 → `push 0` 后 RSP = `stack_top − 8`（8 mod 16）→ `call` 压返回地址后入口 RSP = `stack_top − 16`，即 0 mod 16；而 System V 要求入口 `(RSP + 8)` 为 16 的倍数，也就是入口 RSP 必须 8 mod 16。少一条 `sub rsp, 8` 恰好把入口从 8 mod 16 变成 0 mod 16，与 `stack_top` 是否对齐无关。

**影响**：读者会以为 `sub rsp, 8` 只是配合「非对齐的 `stack_top`」的补丁，而实际上它是 psABI 垫片，独立于对齐断言。§5.4 的 M13 与 R02-T04 又说明 `sp_aligned` 断言只在 qemu_test 载体执行、生产入口没有这条断言；在这种前提下，把 `sub` 的独立作用说成「三者都去掉才坏」会直接误导排障：生产上只删 `sub` 就可能静默违反 ABI。

**证据或推理**：不需要源码，只需按同一段的算式复算。原文自己写「`push 0` 减 8，`sub rsp, 8` 再减 8，使 `call` 前的 RSP 回到 16 字节边界；`call` 压返回地址再减 8，进入 `kmain` 时 RSP = `stack_top − 24`，即 8 mod 16」。把 `sub rsp, 8` 一项拿掉，这个算式立刻变成 `stack_top − 16`，即 0 mod 16，结论与「入口必须 8 mod 16」冲突。

**最小修复**：拆成两种失败形态分别写：其一，只去掉 `sub rsp, 8`，入口 RSP 变成 0 mod 16，违反 System V 的 `(RSP + 8)` 对齐；其二，去掉断言与 `and rsp, -16`，非 16 字节对齐的 `stack_top` 会原样传到 `kmain`。不要把两种形态合并成「三者都去掉」。

**置信度**：0.95。

**是否需源码核实**：否，文档自身的算式已经足够判定。

**若我错了**：如果 `kmain` 的序言在第一条指令前又做了一次 `push` 或 `sub rsp, 8` 把 RSP 调回 8 mod 16，那么只删 `sub` 可能被下游补回来；但原文明确写「生产 `kmain` 是普通 Rust 函数」，普通函数序言不会替调用者补 psABI 垫片，而且原文把 `sub rsp, 8` 的作用定义为「`call` 前回到 16 字节边界」，这正说明它是调用点自己的责任。

**命中清单**：自相矛盾（结论与同段算式冲突）；因果条件写错（充分条件写成必要条件）。

## FINDING RD3-READER-C-04（P2）

**位置**：§2.4「假设栈定义落在 `.unpaged_bss`（低一侧）会怎样」段，第 310 行。

**原文摘录**：

> 「还有第二重后果：`.unpaged_bss` 覆盖的那段物理内存在引导阶段结束后会被交回空闲内存——`kernel/main.c` 的 `kmain` 在 `system_init()` 之后调用 `add_memmap(&kinfo, kinfo.bootstrap_start, kinfo.bootstrap_len)`，源码注释写明 `The bootstrap phase is over, so we can add the physical memory used for it to the free list.`。栈所在的页会进入空闲链，被下一次分配拿走」

**严重度**：P2。

**问题**：从「`.unpaged_bss` 覆盖的物理内存」到「`[bootstrap_start, bootstrap_start + bootstrap_len)` 区间」缺一个环节。文档只引了一句泛泛的注释「the physical memory used for it」，没有给出 `bootstrap_start` 与 `bootstrap_len` 的取值，也没有说明 `.unpaged_bss` 的物理区间落在这个范围内。读者无法判断「栈所在的页会进入空闲链」是事实还是推断。

**影响**：这是本节反向推演的第二重后果，也是它比「只切栈不跳」更严重的地方。如果这个环节不成立，读者会把一个未经证明的后果当成已证结论；如果这个环节成立，读者又需要知道 `bootstrap_start`/`bootstrap_len` 到底覆盖哪一段，才能在真实故障里对照。更棘手的是：高半段的段体也放在同一块低物理装载区（`AT()` 只改 `p_paddr`），如果 `bootstrap` 区间覆盖 `.unpaged_bss`，它是否也覆盖高半段的物理字节？文档没有回答，而这个回答会决定「交回空闲内存」到底只影响低侧栈，还是会影响整个内核镜像。

**证据或推理**：文档给出的全部证据是第 310 行的一句源码注释。注释里的「the physical memory used for it」指代的是「引导阶段用过的内存」，没有说「内核镜像的低侧段」。`add_memmap` 的调用本身也不能证明区间包含 `.unpaged_bss`。这是典型的因果链缺环：前提（调用 `add_memmap`）成立，结论（栈页进入空闲链）需要中间项（区间包含关系），而中间项没有出现。

**最小修复**：补出 `kinfo.bootstrap_start` 与 `bootstrap_len` 的取值或相对关系，至少写成「`.unpaged_bss` 的物理区间落在 `[bootstrap_start, bootstrap_start + bootstrap_len)` 内」；如果无法从文档现有材料确认，就把这句话降级为「若该区间覆盖 `.unpaged_bss`，则……」并标注待核实。顺带说明高半段物理字节是否在同一区间内、为何不受同一后果影响。

**置信度**：0.7。

**是否需源码核实**：是。需要核对 `kinfo.bootstrap_start`/`bootstrap_len` 的赋值处与 `add_memmap` 的语义，才能确认区间包含关系。

**若我错了**：如果 Minix3 的 `bootstrap_start`/`bootstrap_len` 本来就定义为内核低侧装载区（而不是引导监视器自身占用的内存），并且高半段体的物理地址被显式排除在外，那么结论成立；此时只需把这两个值和排除关系写出来，问题就从「证据不足」变成「证据未展示」。

**命中清单**：证据不足（因果链缺中间项）；单形态结论（把「调用 `add_memmap`」直接推成「栈页必然进入空闲链」）。

## SUGGESTION RD3-RC-S03

**位置**：§4.4「两条生产路径在 `kmain` 处合流」段，第 1064 行。

**原文摘录**：

> 「早先版本把 shim 栈上的 `&KernelInfo` 经 `noreturn` asm 的 `in("rdi")` 直传给 `kmain`，RDI 是 caller-saved、被调用方覆写后 `kmain` 拿到的是 .rdata 字符串地址（早期版本的读数：`kmain` 收到的指针 `0x1ddda2ee` 与 `.rdata` 里一个字符串常量的地址相合）」

**严重度**：P3。

**问题**：「RDI 是 caller-saved、被调用方覆写后 `kmain` 拿到的是 .rdata 字符串地址」这句话没有闭合因果链。`kmain` 是被调用方，它在入口收到的 RDI 就是调用方在 `call` 前设置的值；「被调用方覆写后」不能解释「入口收到的是另一个地址」。观测到的 `.rdata` 字符串地址更像来自栈槽复用、参数溢出后从被覆写的栈槽读回，或 `&KernelInfo` 指向的临时对象被销毁，而不是 RDI 作为 caller-saved 寄存器被 callee 覆写。

**影响**：读者能记住「后来改成 `.bss` 副本」这个结论，但无法从这段描述复现或解释早期故障；如果把「caller-saved」当成根因，会得出「只要换个寄存器就能修」的错误推论，而真正的修法是改变生命周期与存放位置。

**证据或推理**：同一段后文自己给出了另一条更具体的根因：「`kmain` 实现注释里的第二次根因：形参曾被编译器溢出到内核栈、从被覆写的栈槽读回」。这条与「RDI 被 callee 覆写」不是同一机制，两句话并列会让读者分不清哪条是主因。

**最小修复**：把机制写成一条可复述的链：旧版本传的是 shim 栈上对象的引用，切栈后该栈区不再有效/被复用，`kmain` 序言把形参溢出到内核栈后从被覆写的槽读回，于是得到 `.rdata` 字符串地址。若无法确认具体机制，就删掉「RDI 是 caller-saved」这句解释，只保留观测读数与修复结论。

**置信度**：0.7。

**是否需源码核实**：是，需要核对旧版本 asm 与 `kmain` 序言的实际溢出行为。

**若我错了**：如果旧版本的 asm 块在 `call kmain` 之前还有一段使用 RDI 的指令（例如把 RDI 当临时寄存器），那么「被调用方覆写」可能指 asm 块内部的某条指令；但正文没有给出这段指令，读者仍然无法复述。

**命中清单**：机制解释不闭合；两条根因并列但未分层。

## SUGGESTION RD3-RC-S04

**位置**：§3.1 字段对应表第 393 行；对照 §3.3 第 526 行与 §4.2 第 824 行。

**原文摘录**：

> §3.1：「镜像跨距（末段 `paddr + memsz` − 首段 `paddr`；平移一致时等于按 `vaddr` 算的差）」
>
> §3.3：「`kern_end_phys` 是所有段 `paddr + memsz` 的最大值」
>

**原文摘录**：

## SUGGESTION RD3-RC-S08

**位置**：§4.1 riscv64 基址段，第 751 行。

**原文摘录**：

> 「把基址换成 `0xFFFFFC0000000000` 或 `0xFFFFC00000000000`，同一条命令输出 `0x0`。后两个地址看起来像高地址，但 bit 38 是 0，符号扩展后落在低半——它们的 VPN[2] 与恒等映射（覆盖低 4GiB，即 VPN[2] = 0..3）共用同一个顶层槽位。」

**严重度**：P3。

**问题**：这两个 64 位常量并不是「符号扩展后落在低半」的合法地址：按 Sv39 的 canonical 规则，bits[63:39] 必须全部等于 bit 38。它们的 bit 38 是 0，但 bits[63:39] 不全为 0，因此它们是非 canonical 地址，硬件会直接报页错误，而不是把它们符号扩展成低半地址。文档紧接着自己引用了 `riscv64.ld` 头注释的「不是合法的 Sv39 canonical high」，说明作者知道这一点；但「符号扩展后落在低半」这句话仍会让读者以为它们是合法的低半地址。

**影响**：读者会混淆「VPN[2] 计算出来是 0」与「地址本身可以当低半地址使用」。反向推演里真正要论证的是「写高半映射时落到 VPN[2]=0 的槽位、覆盖恒等映射的顶层叶子」，而不是「这两个常量是低地址」。表述不精确会让读者在排障时把 non-canonical 故障误判成映射覆盖故障。

**证据或推理**：`VPN[2] = (vaddr >> 30) & 0x1FF` 只取 39 位有效位；对 `0xFFFFFC0000000000`，低 39 位的 bit 38 是 0，所以 VPN[2]=0。但完整 64 位地址的 bits[63:39] 不是全 0，违背 canonical 规则。文档的第 745 至 749 行给出了索引公式，第 753 行引用了「不是合法的 Sv39 canonical high」，两处合起来足以支持这个判断。

**最小修复**：把「符号扩展后落在低半」改成「按 39 位有效位截断后 bit 38=0，因此 VPN[2]=0；这两个 64 位常量本身是非 canonical，不能当作可执行的高半地址」。这样既保留 VPN[2] 的结论，又不把 non-canonical 说成合法低半。

**置信度**：0.75。

**是否需源码核实**：否，RISC-V Sv39 的 canonical 规则与文档给出的公式已经足够。

**若我错了**：如果作者说的「符号扩展」是指「软件在计算 VPN[2] 前先按 39 位截断再符号扩展」，那么这句话在计算语境下成立；但字面写的是「地址……符号扩展后落在低半」，读者会理解成硬件行为。

**命中清单**：机制表述不精确；把「索引为 0」与「地址落在低半」混为一谈。
