## FINDING

### F1 §2.3 其二 / §2.5 假设推演：低侧栈页“被回收”的前提未成立，且同一段内对恒等映射状态自相矛盾

- 位置：§2.3 “其二，只跳不切”（约 331 行）、§2.5 “假设栈定义落在 `.unpaged_bss`”（约 595 行）。
- 严重度：中。
- 问题：两处推演都把结论建立在“低侧镜像页属于引导段、引导后被交回空闲链”这一前提上。但 §2.4 对 `pg_mapkernel` 的描述是：从 `kern_phys_start`（= `_kern_phys_base` = 0x00400000，镜像起点）起映射 `kern_kernlen`，即低侧段所在的物理页同时是内核高半映射的背书存储；若这些页被释放并复用，高半别名会指向被复用的内存，整个内核（而不只是栈）都会失去背书。文档没有给出任何证据说明 `bootstrap_start/bootstrap_len` 覆盖的正是镜像低侧段；唯一引用只是“The bootstrap phase is over…”这句注释，它并没有说范围包括内核镜像。更直接的矛盾在 §2.5 同一段：前一句“映射本身还在（`pg_identity` 铺满 4 GiB）”，后一句“栈的可用性既依赖一张会被丢弃的映射”。
- 影响：读者按 §2.3/§2.5 会得出“只跳不切 = 等一会儿栈被复用 → 静默损坏”的因果链；若前提不成立，这条链断在第一环，读者无法判断真实症状（是页错误、还是根本不会坏）。这是本篇“失败对照”教学法最依赖的一类推演。
- 证据（仅篇内）：§2.4 `pg_mapkernel` 摘录从 `kern_phys = kern_phys_start` 起循环；§2.4 明说三个静态量来自链接脚本的 `_kern_phys_base`/`_kern_size`；§2.5 同段“映射还在”与“会被丢弃”并存。
- 最小修复：二选一。(a) 补出 `bootstrap_start/len` 的确切覆盖范围（引 C 侧赋值处的一句话即可），并解释为何低侧镜像页被回收不会破坏 §2.4 的高半映射；(b) 删掉“被回收”这条因果，把后果改成“栈仍指向内核镜像低侧别名，短期可读写；真正的失效点是恒等映射消失或该别名被其他用途覆盖时”，并统一“映射还在/会被丢弃”的时间点。
- 置信度：中高（矛盾本身高；`bootstrap_start` 的实际语义未能核实，故“回收不成立”只到“未证明且与 §2.4 冲突”）。
- 若我错了：若 Minix3 的 bootstrap 区间确实只覆盖且应当覆盖低侧镜像页，并且高半别名在引导后不再被任何代码访问，那么“回收”可以成立；此时只需在 §2.4/§2.5 补一句“高半别名虽在页表里但无读者”，矛盾即消。

### F2 §2.3 其二 与 §6.1 第 4 行：同一故障（栈未切换）给出相反的现场症状

- 位置：§2.3 “其二，只跳不切”（约 331 行）；§6.1 症状表第 4 行（约 2001 行）。
- 严重度：中。
- 问题：§2.3 明确说“映射还在（`pg_identity` 铺满 4 GiB），所以这里不是页错误，而是静默损坏”；§6.1 第 4 行却把“进入 `kmain` 后第一次压栈/中断失败”描述为“故障地址是低地址”，并把原因列为“栈指针未切换（§2.3 的‘只跳不切’）或栈顶值算错（§3.3）”。前者说无页错误，后者说低地址故障，二者不能同时成立。§6.1 该行还把两个不同原因的现场合并：栈顶值算错（SP 落进未映射洞）确实可能低地址页错误，栈未切换则不是。
- 影响：诊断章是读者排障的第一入口；按 §6.1 去等“低地址故障地址”，在“只跳不切”这一因上会等不到，转而怀疑映射代码。因果方向被症状表反向覆盖。
- 证据（仅篇内）：§2.3 “不是页错误，而是静默损坏”；§6.1 “故障地址是低地址”；§6.1 同一行两个原因并列。
- 最小修复：把 §6.1 第 4 行拆成两行或加时间窗：栈未切换 → “初期无异常，数据静默损坏；恒等映射消失后才出现低地址取指/访存错误”；栈顶算错 → “立即低地址页错误”。并与 §2.3 互引。
- 置信度：高（纯篇内矛盾）。
- 若我错了：若 §6.1 的“失败”不是指页错误而是泛称“出问题”，且“故障地址”一项只对“栈顶算错”成立，那么应把该行拆开写清，矛盾同样消失——结论不变，只是措辞问题。

### F3 §4.0 小结：“自举根在活动根上建立”与 §3.1/§3.6/§3.8 的“不重建根”相反

- 位置：§4.0 小结（约 1144 行）；对照 §3.1（约 691 行）、§3.6（约 1039 行）、§3.8（约 1099 行）、§4.0 术语“additive 阶段”（约 1151 行）。
- 严重度：中。
- 问题：小结写“自举根在活动根上建立并开启分页，Direct Map 随后追加，不替换根”。字面意思是“在活动根上建立自举根”，正是全文反复警告的“重建根”动作。§3.1/§3.6/§3.8 的因果是：v1 面 shim 已建根并开启，接收侧只做 additive，重建会用 `new_from_page` 清零活动根；direct 面才由镜像自己建新根。小结把两种形态的“建根”与“追加”压成一句，方向正好落在被禁止的一侧。
- 影响：§4.0 是“实现详解”的入口小结，读者若记住这句，会把“重建根”当成正常步骤，正好踩中 §3.8 称为“J3/J4 交界处最贵的错误”的那条。
- 证据（仅篇内）：上述四处原文；§3.6“重建会 `new_from_page` 清零正在使用的活动根，下一次取指立即 fault”。
- 最小修复：改为“自举根由建根者建立并开启分页；接收侧只在活动根上追加 Direct Map，不替换根”，并注明“建根者在 v1 是 boot-shim、在直核是内核镜像”。
- 置信度：高（措辞与多处原文直接冲突）。
- 若我错了：若“在活动根上建立”原意是“Direct Map 在活动根上建立（追加）”，那是句子歧义而非事实错误；改成上面的显式主语即可，不影响结论。

## SUGGESTION

### S1 §1.1 四时刻表把 v1/C 不成立的“谁决定”写成普遍结论

- 位置：§1.1 表“映射”行（约 60 行）。
- 严重度：低中。
- 问题：该行“谁决定”写“内核自己的建表代码”，但 §3.6/§4.5 明确 v1 生产腿的根由 boot-shim 在 `enter_kernel_image_v1` 内建立并开启，接收侧不建根；测试载体也不是“内核自己”建根（inline 载体在进程内调 `arch_boot`，尚可算内核侧，但 v1 不算）。同一表的“产物”列还写了“设备窗口”，C 侧没有这个对象（只有 4 GiB 恒等映射里的 `PWT|PCD` 区分）；“摆放”列的“末段 memsz 收口”也只对 Rust 生产镜像成立（§1.2 J2 自己承认）。
- 影响：读者在第一章会形成“映射总是内核镜像自己建”的模型，与后文“v1 不重建根”冲突；到 §3.1 才被纠正。
- 证据（仅篇内）：§1.1 表；§3.6 “v1 发送/接收腿：boot-shim … 建 bootstrap 根并开启分页”；§1.2 J2 “2 MiB 收口只对 Rust 生产镜像成立”。
- 最小修复：在该表加一行口径说明“本表按生产镜像描述；v1 的建根者是 boot-shim，C 无设备窗口，收口仅 Rust”，或把“谁决定”改成“按形态：C/直核是内核建表代码，v1 是 boot-shim”。
- 置信度：高。
- 若我错了：若该表本意只描述 Rust 直核形态，那应把标题/首句的范围写明；目前首句是“同一份内核镜像”，读者会当成通用模型。

### S2 §1.2 “J3 与 J4 只能在真机链上观测”与后文证据边界不一致

- 位置：§1.2（约 76 行）；对照 §5 开头表（约 1802 行）、§3.7（约 1081 行）、§5.4 M13（约 1943 行）。
- 严重度：低中。
- 问题：J3 被说成“只能在真机链上观测”，但 §5 明说“没有‘映射先于进入’的独立断言”，真机链尾只证明“到达 `kmain`”，不证明次序；也就是说 J3 的次序在真机上同样不可观测，只有代码审查。J4 的“不返回”由 `-> !` 在编译期保证（§3.7），入口对齐还有生产路径静态断言（M13），并非“只能在真机链上观测”。J3/J4 被并成同一观测类别，掩盖了二者证据性质的差异。
- 影响：读者会以为“上真机就能验证 J3”，与 §5 的教学目标（不要把链尾当整条链）冲突。
- 证据（仅篇内）：§1.2 原句；§5 表 J3 行；§3.7 “`-> !` 让‘返回’在编译期不成立”；§5.4 M13 静态断言。
- 最小修复：改为“J1/J2 可静态检查；J3 仅有代码审查与链尾证据；J4 的成对/对齐在真机可观测，‘不返回’由类型在编译期保证”。
- 置信度：高。
- 若我错了：若作者把“运行期性质”定义为“描述运行期行为”，而非“只能在运行期观测”，那应换词；读者按字面理解仍会得到错误印象。

### S3 §3.8 “接收侧的次序由 J4 约束”把 J3 的次序归给了 J4

- 位置：§3.8（约 1101 行）。
- 严重度：低。
- 问题：紧接的句子是“先完成映射与 `.bss` 落地，再换栈跳转”，这是 J3（映射先于进入）的内容；J4 管的是“换栈与跳转成对且不返回”。§3.6 已把建根次序归 J3，§3.8 又把它归 J4，读者会对四条不变量的分工产生混淆。
- 影响：四条不变量是全文的判据骨架；J3/J4 边界模糊会让 §5 的证据表对不上号。
- 证据（仅篇内）：§1.2 J3/J4 定义；§3.6 标题“自举根与映射建立的设计（J3）”；§3.8 原句。
- 最小修复：改为“接收侧的映射/BSS 次序由 J3 约束；J4 约束换栈与跳转的成对与不返回”。
- 置信度：高。
- 若我错了：若作者有意用 J4 涵盖“进入前的全部准备”，那与 §1.2 的 J4 定义不符，仍需统一。

### S4 §5.2 “L0–L10 唯一权威清单”未列出文中使用的 L3b/L3c/L6a/L6b

- 位置：§5.2 标题与表（约 1869–1893 行）；使用处 §3.1（L3c）、§4.1（L3b/L6a/L6b）、§6.1（L3b）。
- 严重度：低。
- 问题：§1.3 声明“L0–L10 的权威清单只在本篇 §5.2”，§5.2 自称“唯一权威清单”，但表里只有 L3、L6，没有 L3b/L3c/L6a/L6b 的定义。读者按 §3.1 的“L3c 会先红”去查清单，查不到。
- 影响：诊断/验证章节的可执行性下降；读者无法确认 L3c 与 L3 的关系（是子断言还是别名）。
- 证据（仅篇内）：上述使用处与 §5.2 表。
- 最小修复：在 L3/L6 行内列出子断言（L3a/L3b/L3c、L6a/L6b）及各自检查对象，或删掉“唯一权威”并指向脚本头部注释。
- 置信度：高。
- 若我错了：若 L3b/L3c 是脚本内部编号、不属于“L0–L10”公开契约，那应在 §3.1/§4.1 改用公开编号，避免读者跨章查找。

### S5 J1 的证据行把“解析/布局测试”列为证据，但这些测试不断言平移一致

- 位置：§5 开头表 J1 行（约 1800 行）；对照 §5.1（解析器/装载器测试族）、§5.2 L4、§5.4 M1。
- 严重度：低中。
- 问题：J1 是“同一组段 `vaddr − paddr` 相等”。§5.1 的 `compute_kernel_layout` 只取 `min(paddr)`/`min(vaddr)`/`max(paddr+memsz)`，不检查各段平移是否相等；`validate` 检查的是段间重叠，也不是 J1。真正断言 J1 的只有 §5.2 的 L4（Rust 生产镜像）。把 §5.1 列为 J1 证据会让读者以为宿主测试覆盖了 J1。
- 影响：证据强度被高估；与 §5.0“J1 有宿主测试或布局断言”的表述叠加，读者可能跳过 L4 的必要性。
- 证据（仅篇内）：§4.2 `compute_kernel_layout` 摘录；§5.1 测试族描述；§5.2 L4；§5.4 M1“C 侧静态阅读，无机器断言”。
- 最小修复：J1 证据改为“§5.2 L4（Rust 生产镜像）+ §2.1 C 侧手工分组核对”；若要保留 §5.1，补一条断言平移一致的测试或删掉该引用。
- 置信度：中高（按文中摘录判断；未读源码）。
- 若我错了：若 §5.1 的某个“布局测试”实际包含平移一致断言而文中未列出，则只需在 §5.1 点名该测试；结论从“证据不足”降为“引用不精确”。

### S6 同一符号 `delta` 在 §4.4 与 §6.2 取两个不同值，未标形态

- 位置：§4.4（约 1604 行）；§6.2 第五组（约 2051–2068 行）。
- 严重度：低。
- 问题：§4.4 用 `kern_virt_base − kern_phys_base = 0xffffffbf7fe00000` 复算源码注释的故障地址，隐含 `kern_phys_base = 0x80200000`（生产自引导镜像）；§6.2 的 `test-higher-half-riscv64` 用 `kern_phys_base = 0x80000000`，`delta = 0xffffffbf80000000`。两处都只写“delta”，差值 0x200000。读者按 §6.2 的数值代入 §4.4 的算式会得到不同结果。
- 影响：跨章复算对不上，读者会怀疑 §4.4 的算式或 §6.2 的读数。
- 证据（仅篇内）：两处数值与各自的 `kern_phys_base` 说明。
- 最小修复：§4.4 的复算注明“生产自引导镜像（phys base 0x80200000）；测试载体的 delta 不同，见 §6.2”，§6.2 也回指 §4.4。
- 置信度：高。
- 若我错了：若作者认为两处语境足够明显（一处讲源码注释、一处讲测试载体），则只需各加半句标签，结论不变。

### S7 §3.0 小结“三个消费者”与 §3.2“五个 crate / 五类调用点”计数不一致

- 位置：§3.0 小结（约 646 行）；§3.2（约 734 行）。
- 严重度：低。
- 问题：§3.2 明确“被五个 crate 依赖”“用途按调用点分五类”；§3.0 小结写“宿主测试与三个消费者共用同一套错误集”。读者无法判断“三个”是笔误还是只算主要消费者。
- 影响：共享 crate 的动机论证（“同一份语义被多个调用方共用”）依赖这个计数；计数不一致会削弱论证。
- 证据（仅篇内）：两处原文。
- 最小修复：统一为“五个依赖 crate（其中 vfs 只用常量）”，或说明“三个主要消费者”的筛选标准。
- 置信度：高。
- 若我错了：若“三个”指 boot-shim/boot.rs/vm_server 三个真正走段迭代的调用方，应写明筛选口径。

### S8 §6.0 与 §6.2 的工件名不一致（`kernel-image` vs `kernel`）

- 位置：§6.0 最小示例（约 1972 行）；§6.2 第一组（约 2012–2013 行）；§4.1（约 1171 行“`[[bin]] name = "kernel"`”）。
- 严重度：低。
- 问题：§6.0 让读者 `readelf -lW .../release/kernel-image`，§6.2 用 `.../release/kernel`，§4.1 说 bin 名是 `kernel`。至少有一处路径是错的，读者复制命令会失败。

- 证据（仅篇内）：三处原文。
- 最小修复：以 §4.1 的 bin 名为准统一，或写成 `<工件名>` 并给一条 `ls` 确认命令。
- 置信度：中（未构建验证，仅篇内不一致）。
- 若我错了：若产物目录里同时存在两个名字（如软链/别名），则只需在 §6.2 注明两者关系。

## 收束

本篇的因果主干（四时刻、符号值/可访问性、建表次序、三种链接形态、三架构跳转）复述稳定，反向推演的方向绝大多数正确。真正会误导读者的是三处：F1（低侧页回收前提与“映射还在/会被丢弃”并存的矛盾）、F2（栈未切换的症状在 §2.3 与 §6.1 相反）、F3（§4.0 小结把“不重建根”写成“在活动根上建根”）。其余为范围限定、编号权威与计数/路径的一致性建议。
