## 一、R1 点名项复核

### 1. §2.5 栈回收假设：不自洽

#### C-01 [FINDING / P2] "恒等映射被移除"与"物理页被复用"被合并成同一种"静默损坏"

- 位置：§2.5 末段（约第 595 行），"假设栈定义落在 `.unpaged_bss`（低一侧）会怎样"整段。
- 严重度：P2。诊断结论会指错方向，不影响主链代码。
- 问题：原文说"等恒等映射在后续切根时不再保留，或该物理页被复用之后，才表现为静默损坏"。这两个触发器的可观察症状不同：恒等映射被移除后，低地址栈访问是没有映射的访问，必然产生页错误；该时刻还没有 IDT/异常处理，现场是停机或三重故障。只有物理页被复用才是静默损坏。原文把两者都归为"静默损坏"，同一句里前后不自洽。
- 影响：读者按 §6.1 第四行排查时，会去查分配器与数据覆盖，而实际现场可能是"第一次低地址压栈就页错误"。反过来，若现场是数据损坏，按"映射被移除"去查页表也查不到。两种故障的修复点不同。
- 证据：
  - §2.5 原句："等恒等映射在后续切根时不再保留，或该物理页被复用之后，才表现为静默损坏。"
  - §2.3 其二明确划了边界："映射还在（`pg_identity` 铺满 4 GiB），所以这里不是页错误，而是静默损坏。"——它把"页错误"与"静默损坏"当成互斥的两类。
  - §4.3 其一也把无映射访问写成"页错误发生在 `enable()` 内部……现场仍是'开启分页后立刻静默停止'"。停止不是数据损坏。
- 最小修复：把这一段拆成两条后果。第一条：切根丢失恒等映射后，低地址取指或压栈产生页错误，没有异常处理时表现为停机/三重故障。第二条：物理页被 `add_memmap` 交回并复用后，栈内容被改写，表现为静默损坏。删掉"第二重后果与第一重同源"，改成"两条后果都源于栈落在被回收的低侧段，但症状与排查路径不同"。
- 置信度：高（0.85）。
- 若我错了：如果 C 侧切根后的新页目录仍保留低侧别名（例如 VM 新建的页目录复制了恒等映射），则"映射被移除"这个分支根本不发生，整句应删掉切根分支，只留复用分支；这不会让"静默损坏"的归并变对，只会让错误变成"多写了一个不存在的触发器"。

### 2. §6.1 症状拆行：有两处缝

#### C-02 [SUGGESTION / P2] 第一行的"三个时刻"不是互斥三分，引用的小节也对不上

- 位置：§6.1 表第一行（约第 2000 行）。
- 严重度：P2。分诊表的第一行会把读者带到错误的小节。
- 问题：行文写"出现时刻三选一：分页开启后立刻／恒等映射被移除时／首次切地址空间后——三个时刻的区分见 §2.4、§2.3、§4.3 与 §4.4 的反向推演"。这里有三个问题。其一，"恒等映射被移除时"与"首次切地址空间后"在低半执行时是同一个事件：切根就是移除低半映射。其二，四个小节对三个时刻，没有给出对应关系。其三，被引用的 §2.3"只切栈不跳"的后果是停机，§2.4"`pg_identity` 排到 `pg_mapkernel` 之后"的后果是高地址取到非内核字节，两者都不是本行症状"低地址取指失败"。
- 影响：读者按引用去 §2.3/§2.4 找"低地址取指失败"的机制，找不到；真正对应的是 §4.3 其一（恒等窗口未覆盖当前 PC）与 §4.4 其一（riscv64 `delta` 缺失后首次切根）。分诊表看似三选一，实际只有两类。
- 证据：§6.0 学习目标列的三个时刻；§2.3 其一/其二；§2.4 的"`pg_identity()` 排到 `pg_mapkernel()` 之后"推演；§4.3 其一；§4.4 其一。
- 最小修复：改成两类时刻——"分页刚开启"与"首次切根后"——每类给一个小节引用。把 §2.3/§2.4 从本行移出；若想保留 C 侧的对应假设，另起一行并注明"C 侧低栈假设见 §2.5"。
- 置信度：中高（0.8）。
- 若我错了：如果"恒等映射被移除"在 C 侧指 VM 换掉内核根、而"首次切地址空间"指用户进程切 CR3，两者确实是不同事件，则应保留三分，但要把两个事件的主语写清（内核根 vs 进程根），并补齐引用对应关系。

#### C-03 [SUGGESTION / P2] 第四、五行的作用域在 C 与 Rust 之间摇摆，第五行的"低地址"在 Rust 高半栈上不可达

- 位置：§6.1 表第四、五行（约第 2003–2004 行）。
- 严重度：P2。读者会按错的作用域选排查路径。
- 问题：第四行的原因写"§2.3 的'只跳不切'，栈仍在低侧别名上"，确认动作却用 Rust 的 `kern_stack_top`。在 Rust v1 接收腿里，如果 `mov rsp` 没执行，SP 仍停在入口 `kernel_boot_stack`，那是高半 `.bss` 里的 64 KiB 栈，不是低侧，也不会静默损坏；只有 riscv64/aarch64 直核腿的入口栈在物理视图下才可能是低地址。第五行"第一次压栈/中断即低地址页错误"与"SP 落进未映射洞"也不自洽：Rust 的高半栈若越出 Step 2 的上界，故障地址是高地址；要得到低地址，得是 `kern_virt_base` 本身被算错或被合成成低值，文中没有给出这条路径。
- 影响：照表排查会把 v1 接收腿误判成"栈没切"，或把高地址页错误当成低地址问题去查低半映射。两类故障的修复点不同。
- 证据：
  - §3.3："换栈的目的，是把 SP 从入口栈（可能仍在物理视图）移到镜像尾的高半栈，而不是笼统的'从低侧换到高侧'。"
  - §4.4 x86_64 的 `mov rsp` 与 §4.5 状态表"入口 RSP = stack_top − 24"。
  - §5.3 `sp_ok = sp >= kern_high`。
  - §4.3 Step 2 只映射 `[kern_virt_base, +kern_size)`。
- 最小修复：给每行加作用域标签（C / Rust 直核 / Rust v1）。第四行拆成 C 的低栈复用与 Rust 直核的入口栈未切；第五行的"低地址"改成"高地址（越出 Step 2 映射上界）"，或补一条"`kern_virt_base` 被填成低值"的独立路径并写清判据。
- 置信度：中（0.7）。
- 若我错了：如果 Rust 的入口 `_start` 栈在所有腿上都是低物理地址（例如 x86_64 v1 的 `_start` 仍在低地址视图执行），则第四行的"低侧"成立；但 §4.5.1 明说 x86_64 接收镜像的 `_start` 在高半 VMA，二者需要对齐。

### 3. §4.0 建根主语：主语本身成立，但"运行期按 VMA 取指"越界

#### C-04 [SUGGESTION / P2] 小结第一条把生产 v1 的取指形态说成所有腿的无条件规律

- 位置：§4.0 小结第一条（约第 1143 行）。
- 严重度：P2。这是章末收束句，读者会把它当成全章结论。
- 问题：原文"构建期选脚本，装载期按 `p_paddr` 摆放，运行期按 VMA 取指；三者必须使用同一套基址"是生产 v1 路径的形态。但同篇 §3.1 的登记表自己列出 riscv64 自引导、aarch64 direct-core、riscv64 测试载体都在物理视图执行，x86_64/aarch64 测试载体的 PC 在低地址。把这些腿概括成"运行期按 VMA 取指"，会让读者以为所有腿在 `enable` 之后都立刻按 VMA 取指。
- 影响：与 §1.1 的"进入"行、§3.1 的表、§4.4 的 `delta`/`ldr` 论证形成表面矛盾。第一次读的读者会拿这条去解释 riscv64 直核腿，得出"不需要 `delta`"的相反结论。
- 证据：§3.1 五行表；§4.4"direct leg……PC 仍留在低地址"；§5.3"x86_64 与 aarch64 用镜像自己的（低）链接地址进入，PC 停在低半"。
- 最小修复：改成"生产 v1 路径在跳转完成后按 VMA 取指；直核与测试载体在 `enable` 之后仍可能按物理地址执行，直到 `jump_to_kmain` 的 `delta`/绝对值跳转"。或把这条从"三者必须"里拆出来，标为"v1 形态"。
- 置信度：中高（0.8）。
- 若我错了：如果"运行期"被作者限定为"`kmain` 之后"，句子成立；但 §4.0 的上下文是"从 `build.rs` 选链接脚本开始，跟到 `kmain` 的第一条指令"，覆盖 `kmain` 之前的整段，读者会按全过程读。

### 4. §1.1 映射主体：两分法漏掉载体形态

### 5. §5.4 证据边界：收尾句与表冲突，M12 的"持续"与一次性证据冲突

#### C-07 [FINDING / P2] 收尾句只点名 M3/M7/M9，表里却有六个"部分覆盖"

- 位置：§5.4 最后一句（约第 1947 行），对照表 1931–1945 行。
- 严重度：P2。证据边界被低报，读者会以为另外三行已经闭合。

- 若我错了：如果 M1/M4/M11 在别处已被重新定义为"已覆盖"，则收尾句正确；但表内文字没有这种重定义，且"部分覆盖"四个字仍然写在它们行里。

#### C-08 [SUGGESTION / P2] M12 的机制是"持续成立"，证据却是一次性手工复跑

- 置信度：高（0.9）。
- 若我错了：如果仓库 CI 已经在跑 `check-layout.sh`，则"不是常驻 CI 断言"本身是事实错误，应改的是证据列而不是覆盖状态；但无论哪种，M12 现在这一行的三列互不支持。

## 二、新矛盾

#### C-09 [SUGGESTION / P2] 生产路径 A 把 U-Boot shim 也写进 `ExitBootServices` 序列

- 位置：§4.5 路径 A（约第 1634–1641 行），对照 §3.6 第一条例（约第 1039 行）。
- 严重度：P2。步骤清单会被读者当成五条腿的共同序列。
- 问题：路径 A 写"生产路径 A（v1 send/receive：UEFI x86_64/aarch64、riscv64 U-Boot）……→ ExitBootServices 配对循环 → enter_kernel_image_v1"。§3.6 却明确写"U-Boot shim 腿没有 EBS，在建表分类之后做同一件事"。同一篇里，U-Boot 腿在路径 A 有 EBS，在 §3.6 没有。
- 影响：读者会以为 U-Boot shim 也调用 `ExitBootServices`，从而高估两条路径的共同点，或在排查 U-Boot 腿时去找不存在的 EBS 日志。
- 证据：§4.5 路径 A 原文；§3.6"U-Boot shim 腿没有 EBS"；§4.5.1 表里 riscv64 U-Boot shim 行只写"shim（`enter_kernel_image_v1` 内的 `enable`）"，没有 EBS。
- 最小修复：在路径 A 的 EBS 一行加脚注"仅 UEFI 腿；U-Boot shim 腿没有 EBS，直接进 `enter_kernel_image_v1`"，或把路径 A 拆成 A1/A2。
- 置信度：中高（0.85）。
- 若我错了：如果 U-Boot shim 的"没有 EBS"是指没有 UEFI 的 `ExitBootServices` 服务，但代码仍走同一个配对循环的空实现，则路径 A 的写法是"共同骨架"，需要补一句"空实现"而不是删步骤；但 §3.6 的"没有 EBS"字面仍与路径 A 冲突。

#### C-10 [SUGGESTION / P3] §3.3 收口填充的清零责任在"装载方"与"自引导面"之间切换，主语没标

- 位置：§3.3 第 883 行。
- 严重度：P3。读慢了能自己补上，但第一次读会以为前后矛盾。
- 问题：前句说"这两段都在 `.bss` 的 `memsz` 内；装载方按 `[filesz,memsz)` 清零，入口汇编清到 `__bss_end`"，后句说"收口填充位于 `__bss_end` 之后，自引导面不保证清零"。读者会问：装载方不是已经清零到 `memsz` 了吗？原因是这里换了路径：v1 的 boot-shim 会清，自引导面的 OpenSBI 只写 `filesz`、入口汇编只清到 `__bss_end`。句子没有标出主语切换。
- 影响：把"收口填充未清零"误读成所有路径都成立，或反过来以为自引导面也清了；这影响"栈首次使用前是否需要预清零"的判断。
- 证据：§4.2"`riscv64.ld` 的注释记录过 OpenSBI 只按 `filesz` 写段体、不写 NOBITS 区"；§4.5"自引导镜像不重拷自己的段，`.bss` 清理由入口汇编完成"。
- 最小修复：改成"v1 的装载方按 `[filesz,memsz)` 清零；自引导面没有这个装载方，OpenSBI 只写 `filesz`、入口汇编清到 `__bss_end`，所以收口填充在自引导面不保证清零"。
- 置信度：中高（0.75）。
- 若我错了：如果自引导面也在 `arch_boot` 之前由 `bootface` 清到 `memsz`，则"不保证清零"是错的，应删；但 §4.5 明说自引导面不重拷段、只靠入口汇编清 `.bss`。

#### C-11 [SUGGESTION / P3] §2.5 把 `bootstrap_start/len` 与 unpaged 段用"即"等同，符号名还与 §2.1 不一致

- 位置：§2.5 第 595 行（"栈所在的物理页属于 `_kern_unpaged_start..end`（即 `bootstrap_start/len`）"）。
- 严重度：P3。假设推演的证据链缺一环，但主线结论不依赖它。
- 问题：§2.1 的链接脚本符号写作 `__k_unpaged__kern_unpaged_start` / `_end`，这里简写成 `_kern_unpaged_start..end`；`bootstrap_start/len` 是 01 篇的记账字段，本节没有给出两者相等的判据，只用"即"带过。整个假设的第二重后果（页被交回空闲链）依赖这个等同。
- 影响：读者无法在本篇内复核"栈页一定在 bootstrap 区间"；若两者边界不同（例如 bootstrap 只覆盖 unpaged 段、或覆盖整个镜像），假设的后果强弱会变。
- 证据：§2.1 的 `__k_unpaged__kern_unpaged_start/end` 摘录；§2.5 的简写；§1.3"bootstrap 资源归 01 篇"。
- 最小修复：把符号名写成 `__k_unpaged__kern_unpaged_start..end`，并加一句"`bootstrap_start/len` 的取值与这两个符号的关系见 01 篇的对应小节；本节只用到'栈页落在被交回区间内'这一条"。
- 置信度：中（0.65）。
- 若我错了：如果 01 篇已明确写 `bootstrap_start = &__k_unpaged__kern_unpaged_start`、`len = end - start`，则"即"只是省略引用，不是事实错误；但本篇作为自包含文档仍应给出指针。

#### C-12 [SUGGESTION / P2] aarch64 direct-core 的入口栈如何立栈没有交代，J3 在这条腿上缺一环

- 位置：§3.3 第 871/881 行；§4.3"入口栈对齐与 SSE"段（约第 1502 行）。
- 严重度：P2。这是三条生产腿之一，不是测试细节。
- 问题：§3.3 列了四条入口序列（x86_64、aarch64、riscv64 direct、riscv64 U-Boot），但讲"物理视图下取到的是低物理地址"时只举 `lea`（x86_64）与 `la`（riscv64），没有说 aarch64 用什么。§4.4 又强调 aarch64 的 `ldr ={kmain}` 取链接期绝对值，适合"已建映射之后"的跳转。读者会问：aarch64 direct-core 在 `enable` 之前用哪条指令立栈？若用 `ldr =kernel_boot_stack_top`，拿到的是高 VMA，而此时高半尚未映射，第一次压栈就会失败。
- 影响：J3 的"进入高半之前栈已映射"在 aarch64 direct-core 上缺一条可复核的因果链。读者只能假设实现用了 PC 相对的 `adrp/add`，但文中没有这句话。
- 证据：§3.3 的四条序列清单；§4.4 aarch64 的 `ldr x1, ={kmain}` 说明；§4.3 Step 1 的直核窗口包含"调用者栈窗口"与"内核 LMA"。
- 最小修复：在 §3.3 或 §4.3 补一句 aarch64 入口立栈的指令形态（PC 相对的 `adrp/add`，或 `ldr` literal 的绝对/相对性质），并说明它在 `enable` 之前取到的是物理地址还是高 VMA；若确实用绝对 `ldr`，要说明高半映射在 `_start` 之前已由谁建立。
- 置信度：中（0.6）。
- 若我错了：如果 aarch64 的 `_start` 在 `enable` 之前根本不切到 `kernel_boot_stack_top`（例如一直用固件栈直到 Step 1 完成），则这条不成立；但 §3.3 说"入口汇编用它立栈"包含 aarch64，需要给出对应指令。

#### C-13 [SUGGESTION / P3] 16 字节对齐断言的位置在 §3.7、§4.4、§5.4 三处说法不一致

- 位置：§3.7 第 1068 行；§4.4 x86_64 代码注释"两条 16 字节对齐断言省略"；§5.4 M13 行。
- 严重度：P3。读者核查 v1 接收路径时不知道该看哪一处。
- 问题：§3.7 说"`boot_validate_and_prepare` 的断言覆盖现算的 `kern_stack_top`"；§4.4 的 x86_64 摘录注释说"两条 16 字节对齐断言省略"（暗示在 `jump_to_kmain` 内）；§5.4 M13 说"三份 `jump_to_kmain` 在生产路径上断言 `kern_stack_top` 16 字节对齐"。三处对"断言在哪"给出三个不同落点。
- 影响：若 v1 接收路径不调用 `boot_validate_and_prepare`，只靠 `jump_to_kmain` 的局部断言才覆盖；读者按 §3.7 去找会找不到。M13 的"生产路径上断言"也因此无法定位。
- 证据：三处原文；§4.5.1"v1 接收 → `arch_boot_resume_v1` → `resume_after_v1_decode` → `resume_additive` → `jump_to_kmain`"（没有提 `boot_validate_and_prepare`）。
- 最小修复：在 §3.7 写清两处断言的分工：`boot_validate_and_prepare` 管 direct 路径的合成值，三份 `jump_to_kmain` 各自管本实现的入口值；或统一说"断言在 `jump_to_kmain`，`boot_validate_and_prepare` 另有同值检查"。
- 置信度：中（0.65）。
- 若我错了：如果两处确实都有断言，三处只是各说一部分，则不是矛盾，但"覆盖"的主语仍需统一，否则读者无法判断 v1 路径是否被覆盖。

#### C-14 [SUGGESTION / P3] §4.3 Step 1 的栈窗口方向词歧义，可能把已用栈排除

- 位置：§4.3 第 1438/1440 行（两条 UEFI 跨镜像腿、两个直核腿的栈窗口）。
- 严重度：P3。方向理解反了会影响"窗口是否覆盖栈"的判断。
- 问题："从当前 SP 向上取整到页、再向下留 4 MiB"没有给例子。若"向上取整"指把 SP 向上对齐到页边界，窗口起点可能高于 SP，把 `[SP, 对齐点)` 这段已用栈排除在外；若指"窗口向上扩展"，起点应在 SP 向下对齐。两条腿用同一句，读者无法判断实现取的是哪一种。
- 影响：这是 `enable()` 之后第一条栈访问能否存活的直接前提。方向读反了，会把"窗口覆盖栈"读成"窗口漏掉栈顶几字节"。
- 证据：§4.3 两条窗口描述；§4.3 其一的反向推演"第一次压栈页错误"。
- 最小修复：给一个数值例子，例如"SP = 0x8000_1234 → 窗口 `[0x7FC0_0000, 0x8000_2000)`"，并明确"页对齐取的是包含当前 SP 的最小页"。
- 置信度：中（0.6）。
- 若我错了：如果"向上取整"在文中是"窗口上界向上取整"的口语，实际实现是向下对齐起点，则只是措辞歧义，补例子即可。

## 四、复核过且没有发现问题的因果链

- §2.3 的四行解码（`mov $k_initial_stktop,%esp` / `push $0` / `push %eax` / `call kmain`）与 §4.4 的六条 asm 对应关系自洽；`mov` 携带绝对值、`call` 携带相对位移、`push %eax` 由 `in("rdi")` 承担的对应关系成立。
- §2.4 的 `961 = 0xF0400000 / 0x400000`、`_kern_offset = 0xF0000000`、`I386_VM_ADDR_MASK_4MB = 0xFFC00000` 的向下取整方向自洽；`pg_identity` 覆盖 `pg_mapkernel` 条目的因果链完整（`pagedir[961]` 从 `0x00400000|…` 变成 `0xF0400000|…`，差 `_kern_offset`）。
- §3.7 与 §4.4 的 x86-64 对齐算式自洽：`stack_top` 16 字节对齐 → `push 0` 后 8 mod 16 → `sub rsp,8` 后 0 mod 16 → `call` 压返回地址后入口 8 mod 16，满足 System V 的 `(RSP+8) % 16 == 0`；"只去掉 `sub rsp,8`"与"只去掉 `push 0`"两种反事实也各自成立。
- §4.4 riscv64 的 `delta` 加法与 §6.2 的断点复算一致：`0x80200144 + 0xffffffbf80000000 = 0xffffffc000200144`；`0xffffffbf7fe00000` 是生产 L4 平移量，`0xffffffbf80000000` 是测试载体按 `kern_phys_base = 0x80000000` 算出的 delta，两个数不是同一个口径但各自成立。
- §4.4 aarch64 的 `ldr x1, ={kmain}` + `br` 在"代码与 literal 同镜像、同视图摆放"前提下取到链接期绝对值，与 §4.3 的 aarch64 `isb` 防御性论证不冲突。
