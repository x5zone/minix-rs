## 二、R1 五项复核

### 2.1 §3.1 三形态：部分解决

现在这一节把“三套坐标”摆出来了：链接脚本形态（三种）、装载路径（v1 交接、直核自举、测试载体）、执行视图（物理、高半、低地址）。五行的登记表把后两套坐标展开，并明确写了“三套分类不是同一件事”（L693）。这比把三形态直接等同于五条腿要好。

残留三个结构问题：

1. 桥接句只说“三套分类”，没有给三套分类起名字。读者要自己从上下文反推是哪三套，而这句话正好是全节最关键的转换点。
2. 五行的登记表里，“链接脚本形态”一列出现三次“生产镜像（带 AT()）”，这一列不是键；真正的键是“形态 × 装载路径”。表的标题与列结构没有把这件事说破。
3. 这张表是五行，§4.5.1 的生产腿表也是五行，但两组五行不是同一组：前者含两条测试载体，后者只列生产腿。两个“五”靠得近，又没有一句话对账，读者很容易把“五条腿”与“五行登记表”当成同一件事。

结论：结构问题被承认了，但还没有被“命名”解决。见 S-01。

### 2.2 §3.2 解析器归属：事实层解决，叙述层未解决

事实层是清楚的：解析器在 `os/libs/minix-elf`，是独立 crate，被五个 crate 依赖，五类消费者逐一列出（L734）。取舍表也把“自建、零堆分配、不用 `repr(C)` 加 `transmute`”讲全了。

叙述层有两个卡点：

1. 节首第一段说“Rust 侧把 C 内联在引导器里的这段解析搬到独立 boot-shim”（L732）。这句话把“解析”与“装载”捆在一起，先说成 boot-shim 的东西，第二段才纠正为共享 crate。第一次读的人会先形成一个错误归属，再被迫改。
2. 同一段说“内核侧一行解析代码也没有”（L732），而同一节的消费者清单里有 `boot.rs` 的 `load_vm_elf`（把用户 ELF 逐页映射进进程地址空间），§4.2 的字段去向表更直接把它称作“内核装载用户 ELF”（L835）。两处并置，读者无法判断“内核侧没有解析代码”是全称还是仅指“内核不解析自己的镜像”。

结论：归属的答案在文中，但到达得太晚，且全称句的范围没有限定。见 S-02。

### 2.3 §5.2 L3 子断言：未解决

L3 的子断言写在 L1895：

- L3a = 首段 VMA/LMA 等于该架构预期基址；
- L3b = 按脚本基址常量算出的预期首段 VMA 与实测首段 VMA 相等；
- L3c = 首段 LMA 等于预期装载基址。

L3a 已经包含 LMA，L3c 又是 LMA；如果 L3a 的原意是“VMA 与 LMA 各自等于预期基址”，那么 L3c 是重复；如果原意是“VMA 等于预期基址”，那么 L3a 里的“/LMA”是笔误。无论哪种读法，这三个子断言都不是一次划分，而 L3 在表体（L1886）里又写成“VMA/LMA = 该架构预期基址”，同一个含混被复制了两遍。一个要按 L3a/L3c 核对门证据的人，无法确定自己该看哪一条。见 B-F2。

### 2.4 §5.4 边界：表体清楚，末段的证书不准确

表体本身是这一篇里少见的“诚实清单”：十三条机制，逐条给覆盖状态与现有证据，M1/M3/M4/M7/M9/M11 标“部分覆盖”，并把“部分覆盖”解释为已登记边界（L1947）。这与第 1 章“J3 没有独立断言”的自我限定是一致的。

问题在最后一段：它只点了 M3/M7/M9 三个“部分覆盖”，而表里实际有六个（还有 M1、M4、M11）。这一段是整节的“证书句”，读者会拿它当结论；漏掉三个，等于把 C 侧 `AT()` 的静态阅读、栈区不重叠的静态阅读、交接寄存器的行为性证据从边界清单里抹掉了。见 B-F1。

### 2.5 §4.0 建根主语：章级解决，节级未解决

章级是解决的：4.0 的术语把“建根”定义成无主语的动作（L1149–L1150），小结句把两条路径的主语点明——“v1 是 boot-shim，直核是内核镜像，接收侧只追加不替换”（L1144）。3.6 的“谁来建根”两条、3.8 的两行表、4.5.1 的五行的“谁建根表”也都在点名。

节级没有解决：4.3 的标题是“自举根的建立与开启”，正文第一个代码块标的是 `os/kernel/src/lib.rs:fn build_bootstrap_root_and_enable`（L1389–L1391），全节没有一句话说这个函数由谁调用。读者从 3.6 带着“v1 是 boot-shim 建根”的记忆走到这里，会立刻卡住：这个位于内核 crate 的函数，是 boot-shim 也链接的共享实现，还是只服务直核面？如果是共享实现，为什么 §4.5.1 又说 v1 的 `enable` 在 `enter_kernel_image_v1` 内？如果是两处同名实现，文中从未声明“同名不同物”。这是 J3 主机制的责任归属，不是措辞小节。见 B-F3。

## 三、新发现条目

### B-F1 · §5.4 的边界证书漏列三个“部分覆盖”

- **位置**：§5.4 末段（L1947），对照表 M1（L1933）、M3（L1935）、M4（L1936）、M7（L1939）、M9（L1941）、M11（L1943）。
- **严重度**：中。
- **问题**：末段写“M3/M7/M9 的‘部分覆盖’是已登记边界”，但表中标“部分覆盖”的还有 M1（C `kernel.lds` 的 `AT()` 只有静态阅读）、M4（栈区不重叠仍靠静态阅读）、M11（交接寄存器约定是行为性证据，无自动断言）。三个被漏掉。
- **影响**：这一段是第 5 章的结论句，也是“零欠账”语境下读者判断边界是否登记完毕的依据。漏列会让读者以为 C 侧 `AT()`、栈区重叠、交接寄存器三处已经有机器证据，或者以为它们不属于边界。对下游 review 的影响是：引用“§5.4 已登记边界”时会少引三条。
- **证据**：表体六行标“部分覆盖”，末段只列三行；同一篇 L1929 的开头又说“反转核对查出三项覆盖缺口……三项均已闭合”，与表体的六个“部分覆盖”并存。两句话用的是“缺口”与“边界”两个词，本来可以并存，但末段的枚举把它们混成了一句。
- **最小修复**：把末段改为“M1/M3/M4/M7/M9/M11 的‘部分覆盖’是已登记边界”，或者改成“表中标‘部分覆盖’的六行均为已登记边界，不再逐条点名”。同时把开头“三项覆盖缺口”改成“三项已闭合的缺口”，避免与六个边界混读。
- **置信度**：高。这是纯文本对照，不依赖源码。
- **若我错了**：如果 M1/M4/M11 在别处（例如 5.1 或 6.2）有机器证据而被有意排除在“部分覆盖”之外，那么末段应写明排除理由；否则按表体读，这三行仍是部分覆盖。

### B-F2 · §5.2 的 L3a 与 L3c 重叠，子断言不构成划分

- **位置**：§5.2 表体 L3 行（L1886）与子断言段（L1895）。
- **严重度**：中。
- **问题**：L3 表体写“首段 `PT_LOAD` 的 VMA/LMA = 该架构预期基址”；子断言又写“L3a = 首段 VMA/LMA 等于该架构预期基址；L3c = 首段 LMA 等于预期装载基址”。L3a 包含 LMA，L3c 也是 LMA。三个子断言不是互斥分解，L3a 与 L3c 至少有一个是重复或笔误。
- **影响**：L3 是“布局常量与链接脚本不符”的主断言。读者按子断言核对 `check-layout.sh` 的输出时，无法判断“L3a PASS”是否已经覆盖 LMA；如果 LMA 实际错了而 L3a 只看 VMA，报告会写成“L3a 通过、L3c 通过”，但两条的含义重叠，证据强度被虚增。反过来，如果 L3a 真的同时看 VMA 与 LMA，L3c 就是冗余项，清单的“三条子断言”是假的。
- **证据**：L3a 与 L3c 的定义字面重叠；§3.1 的反事实只引 L3c（“首段 LMA = 0x200000”，L728），§4.1 只引 L3b（L1197），没有一处同时解释 L3a 与 L3c 的分工。三条引用各取一条，正好把重叠藏住了。
- **最小修复**：把 L3a 改成“首段 VMA 等于该架构预期虚拟基址”，L3c 保持“首段 LMA 等于预期装载基址”，表体的 L3 行改成“首段 VMA 与 LMA 分别等于预期基址（分解见下：L3a/L3b/L3c）”。如果工具实际只有一条合并检查，就删掉子断言段，直接写“L3 一条断言同时比 VMA 与 LMA”。
- **置信度**：高。只依据本篇的字面定义。
- **若我错了**：如果 L3a 的“/LMA”是“VMA 或 LMA 任一不符即失败”的简写，而 L3c 是 LMA 的独立复算，那么应把这句话写出来；否则读者只能按字面读成重叠。

### B-F3 · §4.3 的建根代码块没有主语，与“v1 由 boot-shim 建根”并置时无法判断归属

- **位置**：§4.3 开头与代码块（L1383–L1391）；对照 §3.6 的“谁来建根”（L1037–L1040）、§3.8 的两行表（L1096–L1097）、§4.5.1 的“谁建根表”（L1758–L1764）与 L1770。
- **严重度**：高（对 J3 主机制的理解，不是全文可读性）。
- **问题**：4.3 的代码块标为 `os/kernel/src/lib.rs:fn build_bootstrap_root_and_enable`，正文没有一句说这个函数在两条生产路径上分别由谁调用。3.6 说 v1 是 boot-shim 建根，3.8 说 v1 接收时“根已由 boot-shim 建好”，4.5.1 的表说 v1 的“谁建根表”是 boot-shim、`enable` 在 `enter_kernel_image_v1` 内；而 4.3 展示的函数属于内核 crate。读者无法判断这是同一实现被两侧链接、两处同名不同物，还是 4.3 只覆盖直核面。
- **影响**：J3 的要求是“映射先于进入”，而“谁建根”决定这条要求在 v1 路径上由哪段代码满足。主语不清，读者就无法把 4.3 的 Step 1–3 对应到 v1 的实际执行者，也无法判断 §4.5.1 “跨镜像路径下，`build_bootstrap_root_and_enable` 被 boot-shim 调用一次”（L1770）与 4.3 的代码块是不是同一个函数。这是全篇唯一一处“读者必须靠猜”的主机制归属。

## 四、不建议改动的地方

以下结构是有效的，返修时不要为了“统一”而拆掉：

1. **2.1–2.5 的“先解码、再反事实”单元**。每一节都是“代码摘录 → 逐行解码 → 若去掉某一步会怎样”，三拍完整。这是全篇最可复用的教学结构，尤其 2.1 的 LMA 重叠与 2.3 的三种缺步推演。
2. **1.1 与 1.2 的两张表**。四个时刻与 J1–J4 是全篇的索引；后文每一节都能回指其中一个词，说明坐标系选对了。
3. **3.5 的三档表与 5.3 的架构相关 PC 判据**。前者把“选粒度”的三种结局一次列全；后者把“为什么 x86_64/aarch64 只打印、riscv64 并入 PASS”讲成了可检验的取舍，而不是偏好。
