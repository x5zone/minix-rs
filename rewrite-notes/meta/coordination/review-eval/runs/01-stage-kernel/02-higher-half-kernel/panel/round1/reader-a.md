## 1. 两处说法冲突（必答）

### C1 §3.2 对“内核侧有没有 ELF 解析代码”前后相反

- 位置：第 732 行（同一段内两句）与第 740 行。
- 原文 A（第 732 行）：“因此这些字段由 shim 用本节的共享解析器读，**内核侧一行解析代码也没有**；与 C 的差别不在‘有没有外部装载者’，而在装载者是本仓代码、与内核共用同一份解析器。”
- 原文 B（同一段，紧接其后）：“用途按调用点分五类：……`boot.rs` 的 `fn load_vm_elf` 用它把用户 ELF 逐页映射进进程地址空间；……`vm_server.rs` 的 bootstrap 装载用 `entry_point` 与 `segment_iter` 取入口与段表。”
- 原文 C（第 740 行取舍表）：“换来的是‘读字节数组’这一种接口，**两侧（boot-shim 与内核早期）都不依赖分配器**。”
- 问题：A 说内核侧没有一行解析代码，B 与 C 说内核早期/内核侧代码正在使用同一个解析器。两句的“内核侧”显然不是同一个范围：A 想说的是“内核镜像的装载解析不在内核里”，B/C 说的是“用户 ELF 解析与内核早期映射也用它”。
- 影响：初学者读到 A 会把“内核侧”理解成整个内核镜像，接着读到 B 的 `boot.rs`/`vm_server.rs` 会认为文档自相矛盾，无法判断解析器到底归谁。这也是后文 §4.2 把 `load_elf_into` 放在内核侧讨论时产生“为什么又说内核有解析”的根源。
- 证据：第 732 行两句在相邻位置；第 740 行取舍表；第 734 行五类调用点列表把 `boot.rs`、`vm_server.rs` 都算进来。
- 最小修复：把 A 改成有范围的表述，例如“内核镜像的装载解析不在内核镜像里；内核侧只有用户 ELF 装载路径（`boot.rs` 的 `load_vm_elf`）复用同一解析器”。这样 A/B/C 三处不再互斥。
- 置信度：高。三处文字都在同一节，且 B/C 是同一段与紧邻取舍表，不是跨章转述。
- 若我错了：如果“内核侧”在本项目术语里专指“内核镜像装载路径”而不是“内核代码”，那 A 只是想表达“内核镜像不解析自己的 ELF”；但正文没有给这个限定，第一次阅读无法自行补出。

### C2 §4.3 把 Step 2 的守卫条件写成了 `kern_huge` 选 1 GiB

- 位置：第 1453 行与第 1423、1494–1498 行。
- 原文 A（第 1453 行）：“Step 2 的守卫 `if kern_virt != kern_phys` 记录在注释里：两基址相等时，Step 1 的窗口已经覆盖内核 LMA 段（Step 2 是它的子集），跳过 Step 2 可以避免同一个 VPN[2] 槽位被二次写入。**为什么 `kern_huge` 选中 1 GiB 时不能做 Step 2**，见本节末‘若 `kern_virt == kern_phys` 时照做 Step 2’的推演。”
- 原文 B（代码，第 1423 行）：“`if kern_virt != kern_phys { ... map_huge(..., kern_huge, ...) }`”——Step 2 在基址不等时照做，且用的就是 `kern_huge`。
- 原文 C（本节末推演标题，第 1494 行）：“若恒等映射只覆盖可用内存、或**虚拟基址等于物理基址**时照做第二步（两处）”；第 1498 行结论是 `kern_virt == kern_phys` 时照做 Step 2 会 `AlreadyMapped` 当场 panic。
- 问题：A 的“`kern_huge` 选中 1 GiB 时不能做 Step 2”与 B/C 都不符。B 明确在基址不等时用 `kern_huge` 做 Step 2；C 讨论的条件是“基址相等”，不是“选中 1 GiB”。按 C 的推演，正确条件应是“`kern_virt == kern_phys` 时不能做 Step 2”。
- 影响：读者会得出“只要页尺寸规划选中 1 GiB，Step 2 就必须跳过”的错误结论；而正文后面又说三架构当前都落 2MiB 档，暂时看不出矛盾，一旦读者把 1 GiB 档当作可达状态就会卡住。这是典型的“指路句把原因写错，后文推演对不上”。
- 证据：第 1423 行守卫与 `kern_huge`；第 1453 行指路句；第 1494、1498 行推演条件与结论。
- 最小修复：把第 1453 行那句改成“为什么 `kern_virt == kern_phys` 时不能做 Step 2，见本节末……”。如果确实还想讨论 1 GiB 叶挡住 2 MiB 安装，另起一句，不要与 Step 2 守卫混在同一句。
- 置信度：高。三个位置的条件表达式互斥，不是术语歧义。
- 若我错了：如果 `kern_huge` 在本节有一个未摘录的局部含义（比如“Step 2 只有在 1 GiB 时才被跳过”），那需要正文补一句；但代码摘录的 `if kern_virt != kern_phys` 与后文推演标题已经把条件写死为基址关系。

### F4 RISC-V canonical 段落的“落在低半”与“不是合法 canonical high”自相矛盾

- 位置：第 1254 行（同一段两句）。
- 原文 A：“后两个地址看起来像高地址，但 bit 38 是 0，**符号扩展后落在低半**——它们的 VPN[2] 与恒等映射（覆盖低 4GiB，即 VPN[2] = 0..3）共用同一个顶层槽位。”
- 原文 B（同段下一句）：“`riscv64.ld` 的头注释把这两个地址列为‘**不是合法的 Sv39 canonical high**’的实例。”
- 问题：A 说这两个地址“符号扩展后落在低半”，B 说它们“不是合法的 canonical high”。在 Sv39 里，bit 38 为 0 且高位不全为 0 的地址是**非 canonical**，硬件在页表走查之前就会报异常，并不存在“落在低半并共用 VPN[2] 槽位”的正常执行路径。A 把“按位算出的 VPN[2]=0”说成了“符号扩展后落在低半”，这两件事不是一回事。
- 影响：初学者刚建立“canonical 检查”的概念，会被这句话拉回“非 canonical 地址也能当低半地址用”的错误理解；后面“与恒等映射共用槽位”的推演也会被误读成硬件行为，而不是“如果忽略 canonical 检查、只看 VPN[2] 位段”的软件假设。
- 证据：第 1254 行两句相邻；前一句的 VPN[2] 复算只证明位段相同，不证明地址 canonical。
- 最小修复：改成“后两个地址的 bit 38 是 0，按 Sv39 的 canonical 规则属于非法编码（高位未按 bit 38 符号扩展）；若只看 VPN[2] 位段，它们与恒等映射共用 0 号顶层槽位”。把“落在低半”删掉，或改成“位段上像低半”。
- 置信度：高。canonical 规则与“落在低半”是互斥描述；同段下一句已经承认它们不是合法 canonical high。
- 若我错了：如果作者想表达“链接器/软件按 39 位截断后把它们当低半地址处理”，那需要补“硬件不会走到页表”这一前提；现状没有这个前提，读者只能按硬件语义读。

- 最小修复：加一句“`plan_boot_pages` 是 `arch_boot_impl` 侧的薄包装，粒度选择在 `plan_kernel_mapping`”，或统一成一个名字。

## 4. 必须外部知识（正文假设读者已有，实际会卡）

1. ELF 程序头语义：`PT_LOAD`、`p_vaddr`、`p_paddr`、`p_filesz`、`p_memsz`、`p_flags`。§1.0 只用一行列出，没有讲“LMA 与 VMA 为什么可以不同”。会 C 不等于读过 ELF program header。
2. x86 保护模式与控制寄存器：CR0.PE/PG/WP、CR4.PSE/PGE、PWT/PCD、PDE/PTE 权限位、4MB 大页。§2.0 的前置只要求“段式寻址与分页开关的基本区别”，不足以读 §2.4。
3. 栈对齐 ABI：System V AMD64 的“进入函数时 `(RSP+8) % 16 == 0`”、AAPCS64 与 RISC-V psABI 的 SP 16 字节对齐。§3.7 的算式写得很细，但读者若不知道 ABI 规则，会把 `sub rsp, 8` 当成多余。
4. RISC-V Sv39 canonical 地址与 VPN[2]：§4.1 的基址选择完全依赖它；正文给了复算命令，但没有讲“非 canonical 会在页表走查前异常”。这也是 F4 的根源。
5. AArch64 的 TTBR0/TTBR1、SCTLR、VBAR、`dsb sy; isb`：§4.3 的 Step 2b 与 §4.4 的 `isb` 讨论默认读者知道两套页表基址寄存器的分工。
6. Rust 语言：trait、关联常量、泛型 bound、`unsafe`、`-> !`、`core::arch::asm!`。§3.0 只说“不要求读懂所有实现细节”，但 §3.4 的 `trait HugePages: Paging` 与 §3.7 的安全契约需要这些基础。
7. UEFI、OpenSBI、U-Boot 的角色分工：§3.1/§4.5 反复用“v1 跨镜像”“U-Boot shim”“OpenSBI 只跳转不解析 ELF”，但只给了一句括号。没有这些背景，无法判断“谁读 `p_paddr`”。
8. QEMU 与 GDB 用法：`-s -S`、`target remote :1234`、`$pc/$sp` 与 `$rip/$rsp` 的架构差异。§6.2 默认读者会。
9. BSD make 的 `.for` 语法：§2.2 解释了一句，但“规则名就是输出文件名”这个点仍需要读者熟悉 make 规则；不熟 make 的读者会把 `unpaged_${unpaged_obj}` 当成变量而不是目标名。
10. 帧指针链回溯：§2.3 的第 2 条讲了 `[bp]`/`[bp+1]`，但读者若没写过栈回溯，仍需要“保存的 FP 指向上一个帧的 FP”这一句才能把“终止槽不在链上”读懂。

## 7. 总评（读者 A 视角）

- 全文的骨架是清楚的：四个时刻 → J1–J4 → C 侧双地址/建表五步 → Rust 三形态/解析器/栈顶/大页/收口/建根/跳转 → 实现 → 测试 → 诊断。每章都有导读、最小示例、失败对照、小结、术语，初学者能按图走。
- 最有效的三处：§2.1 的 `AT()` 逐行解码、§2.3 的“绝对值 vs 相对位移”对照、§2.5 的 `k_initial_stktop` 三条证据链。这三处把“链接期符号值”与“运行期可访问地址”的区别讲透了。
- 最需要修的两处冲突：C1（解析器归属）与 C2（Step 2 守卫条件）。前者是范围表述问题，后者是条件写错，都会把读者引向错误结论。
- 最需要补的路径：F1（L3b/L3c/L6a/L6b）与 F5（过程编号）。前者影响“按失败输出定位”，后者影响“判断这是残留还是设计选择”。
- 对“初学者路径”的整体判断：1.0–2.3 可以顺读；2.4 起需要外部硬件知识；3.1–3.2 需要 01 篇的形态背景；4.1 起需要能读 Rust 与链接脚本。若把 §2.4、§3.1、§4.5.1 标成“第二遍再读”，第一遍按 §1、§2.1–§2.3、§2.5、§3.3、§3.5、§4.4、§5、§6 走，能建立完整模型。
