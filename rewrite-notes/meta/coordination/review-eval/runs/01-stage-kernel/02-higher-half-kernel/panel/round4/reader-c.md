## FINDING READER-C-01（P1）

- 位置：§3.2「迭代器在 `next()` 里做类型过滤与范围检查，命中这些条件时 `continue`（不产出该段）」及紧随其后的 `impl Iterator for SegmentIter` 节选；对照 §4.2 `compute_kernel_layout` 的 `while let Some(seg_result) = iter.next()` 与 `let seg = seg_result?;`，以及 §4.2 末段「`filesz > memsz` 已由迭代器拒绝」、§5.1 的 `test_segment_iter_skips_segment_data_out_of_bounds`。
- 严重度：P1。读者无法判断解析器当前对外契约，后续所有「Err 项 / 跳过 / fail-closed」的叙述失去唯一落点。
- 问题：两处给出互斥的迭代器错误语义。§3.2 的代码节选签名是 `fn next(&mut self) -> Option<Self::Item>`，`parse_phdr` 失败走 `Err(_) => continue`；正文说「命中这些条件时 `continue`（不产出该段）」「迭代器不报错、不截断，直接不产出这个段」，并把这条行为当作「当前文档如实记录行为」的 D2-05 缺口。§4.2 的 `compute_kernel_layout` 却写成 `while let Some(seg_result) = iter.next() { let seg = seg_result?; }`，注释明说 a malformed program header is an `Err` item, not a silent skip，末段又写「`filesz > memsz` 已由迭代器拒绝」。同一段链上还有第二处对不上：§3.2 说「`NoLoadSegments` 与四个 `InvalidSegment` 判断点由 `loader.rs` 产生」，把 `filesz > memsz` 记在 loader.rs 一侧；§4.2 说它在迭代器（minix-elf 的 `lib.rs`）里。
- 影响：读者按 §3.2 的节选去读 §4.2，会先卡在 Item 类型上：如果 `Self::Item` 是 `LoadSegment`（节选的 `...` 只省了返回值构造，不能排除这一点），`seg_result?` 就没有 `Result` 可展开，`collect::<Result<Vec<_>, minix_elf::ElfError>>()` 也收不进去；即使 `Self::Item` 是 `Result<LoadSegment, ElfError>`，§3.2 的 `Err(_) => continue` 仍然把解析错误吞掉，与 §4.2 的 `not a silent skip` 相反。两种取值下两节都不能同时成立。更实质的是：D2-05 是「仍开着的已知设计缺口」还是「已由 I-48 / D-084 修掉」，读者得不到答案；而这两句话的时态都写成当前（「当前文档如实记录」「已由迭代器拒绝」）。后面 §5.1 测试名 `test_segment_iter_skips_segment_data_out_of_bounds`（表里注明「越界段被跳过」）又把 §3.2 的跳过语义再确认了一次，使冲突不是单点笔误。
- 证据或推理：§3.2 节选里 `let phdr = match parse_phdr(...) { Ok(p) => p, Err(_) => continue };` 与 `fn next(&mut self) -> Option<Self::Item>` 是同一段代码；§4.2 的 `seg_result?` 与 `collect::<Result<Vec<_>, minix_elf::ElfError>>()?` 要求 `Item = Result<LoadSegment, ElfError>`。若 §3.2 的 Item 也是 `Result`，那么 `Err(_) => continue` 与 §4.2 的 `not a silent skip` 直接相反；若 Item 不是 `Result`，§4.2 的 `?` 不成立。两段代码在错误语义上不能同时为真，类型上也至少有一处需要文档未给出的包装。§3.2 的「调用方看到的是『段比预期少』，而不是『段坏了』」与 §4.2 的「not a silent skip」是同一问题的正反两个答案。
- 最小修复：二选一，并让两节同口径。若 I-48 / D-084 已落地：把 §3.2 的节选换成返回 `Option<Result<LoadSegment, ElfError>>` 的版本，正文改成「畸形表项以 `Err` 项浮出，调用方用 `?` 决定是否中止」，D2-05 段改写为「已修」或「剩余缺口是 X」；把「四个 `InvalidSegment` 判断点由 loader.rs 产生」改成 `filesz > memsz` 在迭代器、其余三个在 loader.rs。若仍是跳过语义：把 §4.2 的 `seg_result?`、`collect` 注释与「已由迭代器拒绝」改回，并说明 `collect` 如何避免把 `Err` 当元素。
- 置信度：高（两段代码在错误语义上互斥；不是措辞差异）。
- 是否需源码核实：是（确认当前 `SegmentIter::next` 的 Item 类型，以及 `filesz > memsz` 守卫在 `lib.rs` 还是 `loader.rs`）。
- 若我错了：有三种可缩小冲突的读法，但正文都没有给出。(1) §3.2 的节选是 I-48 之前的历史版本——正文没有这样标注，且它自称记录「当前」行为。(2) `seg_result` 来自另一个包装迭代器，`compute_kernel_layout` 自己再包一层 `Result`——正文没有给出这层包装。(3) §4.2 的「a malformed program header」只指 `filesz > memsz` 这一类语义错误，而 §3.2 的「表项越界/太小」是另一类、仍按跳过处理——这样两节的字面冲突可缩小为「malformed」一词的范围歧义；但 §4.2 的注释用的是全称「a malformed program header」，§3.2 的「表项越界或太小时跳过」按 ELF 术语也是 malformed program header，读者无法自行确定这个范围。无论取哪种，文档需要把范围写出来。
- 读者验收清单条目：§4.0e 第 4 条（同一主张在概述、设计、实现、小结中的复述一致）＋第 6 条（证据强度与可复算性）。

## FINDING READER-C-04（P2）

- 位置：§6.2 第五组命令的预期输出：「**riscv64 测试载体不是 `nm` 值本身**：它链接在物理地址上，`$rip` = `nm` 值 + `delta`（`delta = kern_virt_base − kern_phys_base`），例如加载基址 `0x80200000` 时 `nm` 给出 `0x80200160`，而 `$rip` 是 `0xffffffc000200160`」；对照 §4.3 riscv64 实现的 `delta` 算式与 §6.2 自己给出的 riscv64 虚拟基址「`0xffffffc0…` 一段」。
- 严重度：P2。§6.2 是全篇唯一带具体数字的 GDB 验收步，按文档复现会得到与预期不符的 `$rip`，读者会把一次正确的跳转判成坏的。
- 问题：把文档自己给的公式与数字代进去，算不出文档给的 `$rip`。按 §6.2，riscv64 的 `kern_virt_base` 是 `0xffffffc0…`（§4.1 明确写 `0xFFFFFFC000000000`）。若把「加载基址 `0x80200000`」当作 `kern_phys_base`，则 `delta = 0xFFFFFFC000000000 − 0x80200000 = 0xFFFFFFBF7FE00000`；再加 `nm` 的 `0x80200160`，结果是 `0xFFFFFFC000000160`，不是文档写的 `0xFFFFFFC000200160`，差 `0x200000`（2 MiB）。要让等式成立，`delta` 必须是 `0xFFFFFFBF80000000`，也就是 `kern_phys_base = 0x80000000`——与「加载基址 `0x80200000`」不同，而文档没有给出这个 `kern_phys_base`。
- 影响：读者按第五组命令断在 `kmain`，读到 `$rip = 0xffffffc000000160`，对照文档的 `0xffffffc000200160` 会以为「少加了 2 MiB」或「`la` 的取值错了」。这条本来是证明 `delta` 路径正确的现场证据，现在会反过来制造一个假故障。它还影响 §5.2 的读数核对：§5.2 说 riscv64 载体的 PC「落在 `kmain` 的高半 VMA」，读者需要知道该 VMA 是 `KernelInfo` 的 `kern_virt_base + (nm − kern_phys_base)`，而不是 `kern_virt_base + (nm − 加载基址)`。
- 证据或推理：文档内三处数字——虚拟基址 `0xFFFFFFC000000000`（§4.1）、`delta = kern_virt_base − kern_phys_base`（§4.3 代码与 §6.2 文字）、加载基址/`nm` 值 `0x80200000`/`0x80200160`（§6.2）。十六进制加法：`0xFFFFFFBF7FE00000 + 0x80200160 = 0xFFFFFFC000000160`（低 32 位 `0x7FE00000 + 0x80200160 = 0x1_0000_0160`，进位 1；高 32 位 `0xFFFFFFBF + 1 = 0xFFFFFFC0`）。文档写的 `0xFFFFFFC000200160` 需要 `delta = 0xFFFFFFBF80000000`，即物理基址 `0x80000000`。
- 最小修复：把 riscv64 测试载体 `KernelInfo` 的 `kern_phys_base` 明确写出来（若是 `0x80000000`，说明它为什么比加载基址低 2 MiB，以及 `kern_size` 如何覆盖 `0x80200000` 起的镜像），或者把例子改成完整三元组（`nm` 值、`kern_phys_base`、`$rip`）并现场复算一行。不要只留「加载基址」这一个量。
- 置信度：高（十六进制加法可复算）；对「测试载体的 `kern_phys_base` 到底是多少」只能从文档内推断，故这一半是中等。
- 是否需源码核实：是（riscv64 测试载体 `KernelInfo` 的 `kern_phys_base`/`kern_size` 常量）。
- 若我错了：若该测试载体的 `KernelInfo` 确实把 `kern_phys_base` 设成 `0x80000000`（比加载基址低 2 MiB），那么文档的 `$rip` 是对的，错的是「加载基址 `0x80200000` 时」这句让人自然把两者当成同一个量；这种情况下最小修复仍是把 `kern_phys_base` 写出来。
- 读者验收清单条目：§4.0e 第 6 条（证据强度与可复算性）。

## FINDING READER-C-05（P2）

- 位置：§4.1「两处通配里各多收了一个族」一条：「x86_64 工件的 `.lrodata.*` 就是未被 `.rodata` 通配收走的孤儿，但它落在收口之前，所以 L5 仍通过」；§6.2 第一组：「5 行依次是 `.text`（RX）、`.lrodata.*`（R）、`.rodata` 含 `.eh_frame_hdr`（R）、`.data`（RW）、`.bss`（RW、NOBITS）」以及「所有 LOAD 行的第三列（VirtAddr）与第四列（PhysAddr）之差一致（L4 断言的这一条）」；§2.1 的无 `AT()` 规则：「不给 `AT()` 的输出段，它的装载地址与虚拟地址相同」。
- 严重度：P2。三处陈述不能同时为真；读者无法判断 `.lrodata.*` 那一行的 `PhysAddr` 是低地址还是高 VMA，也就无法判断 L4 的 PASS 读数是否覆盖它。
- 问题：`.lrodata.*` 是「未被 `.rodata` 通配收走的孤儿」，即链接脚本没有为它写输出段、更没有写 `AT()`。按 §2.1 的规则，无 `AT()` 的输出段 LMA = VMA；它的 VMA 在高半（`0xFFFF8000…` 一段），所以它的 `vaddr − paddr` 应为 0，而其他四个 LOAD 行是 `0xffff800000000000`，L4 的「所有 PT_LOAD 平移量一致」应当在该行上报违例。可是 §6.2 报告 x86_64 工件 5 行 LOAD（含该行）且「所有 LOAD 行的……之差一致」。§4.1 只解释了 L5 为什么仍通过（孤儿落在收口之前），没有解释 LMA 从哪里来。
- 影响：读者拿 §2.1 的规则去核对 §6.2 的 `readelf -lW` 输出，会在第 2 行（`.lrodata.*`）上得到一个与 L4 PASS 相反的预测。若真实情况是 ld 对孤儿输出段另有一套 LMA 继承规则，那么 §2.1 的「不给 `AT()` ⇒ LMA = VMA」需要加「脚本里显式写出的输出段」这个限定；若真实情况不是，那么 §6.2 的「L4 一致」这一条读数就有问题。两种修法都要求文档把机制说出来。
- 证据或推理：三句文档原文构成三段论——(1) 无 `AT()` ⇒ LMA = VMA；(2) `.lrodata.*` 是未收的孤儿（脚本没给它 `AT()`）；(3) 该行仍在 5 个 LOAD 行内且 L4 一致。由 (1)(2) 得该行平移量为 0，与 (3) 矛盾。§4.1 的「落在收口之前」只影响跨度（L5），不影响该行自己的 `p_paddr`。
- 最小修复：在 §4.1 那一条补一句孤儿输出段的 LMA 规则（例如「ld 把孤儿段放在前一输出段之后，并按该段的装载偏移给出 LMA，所以它仍满足 L4；这与脚本里显式写出、又不给 `AT()` 的段不同」），或者直接在 §6.2 报出 `.lrodata.*` 行的 `PhysAddr` 实测值，让读者能自己核对。若该行其实是 `vaddr − paddr = 0`，那么 §6.2 的「所有 LOAD 行一致」需要改成「除 `.lrodata.*` 外一致」。
- 置信度：高（三句按字面不能同时为真）；对真实 ld 行为是中（需要实测）。
- 是否需源码核实：是（`readelf -lW` 看 `.lrodata.*` 那一行的 `PhysAddr`；或 ld 手册里 orphan section 的 LMA 规则）。
- 若我错了：若 ld 对孤儿输出段自动继承前一输出段的 LMA（从而给出低地址），那么 §2.1 的规则只是少了「脚本内的输出段」这个限定，冲突仍在，只是修法变成补限定；若 `.lrodata.*` 根本不是独立的 LOAD 行（§6.2 的 5 行描述有误），则 §6.2 需要改的是 5 行清单。
- 读者验收清单条目：§4.0e 第 6 条（证据强度）＋第 3 条（因果链闭合）。

## FINDING READER-C-06（P2）

- 位置：§3.4 对齐段末「真正会坏的有两种情形：①三者都去掉时……②**只去掉 `sub rsp, 8` 也会坏**」；对照 §4.3 x86_64 三条推演之三末尾「（x86_64 序列里的 `push 0` 终止槽不在这条链上；去掉它改变的是入口栈的对齐，`sp_aligned` 断言会当场失败。）」
- 严重度：P2。两处对「哪几条指令是承重的」给出不同答案，读者会得出「`push 0` 可以拿掉」或「`push 0` 不能拿掉」两个相反结论。
- 问题：§3.4 说真正会坏的只有两种情形，并把 `push 0` 描述成「终止槽」「不在帧指针链上」——读者容易把它读成可删的遗留物；§4.3 却明确说只去掉 `push 0` 也会使 `sp_aligned` 当场失败。按 §3.4 自己给的算式复算：`mov rsp, stack_top`（设 16 对齐）→ `and rsp, -16`（空操作）→ 去掉 `push 0` → `sub rsp, 8` 使 RSP = `stack_top − 8`（8 mod 16）→ `call` 压 8 字节，入口 RSP = `stack_top − 16`（0 mod 16），而 System V 要求入口 `(RSP + 8) % 16 == 0` 即 RSP ≡ 8 mod 16——正好违反。所以「只去掉 `push 0`」是第三种会坏的情形，§3.4 的「两种」枚举不全，且与 §4.3 的明文冲突。
- 影响：这不是纯枚举完整性问题：`push 0` 与 `sub rsp, 8` 是一对（`sub` 补的是 `push 0` 花掉的 8 字节），文档没有把这层配对说透。读者若按 §3.4 的「终止槽不在链上」删掉 `push 0`，会在生产入口留下 0 mod 16 的 RSP；若按 §4.3 保留 `push 0` 又删 `sub`，也会坏。两节合起来才能得到「要么都留、要么都删（若 stack_top 已对齐），不能只删一个」的结论。
- 证据或推理：§3.4 的「真正会坏的有两种情形」是穷举语气；§4.3 的「去掉它改变的是入口栈的对齐，`sp_aligned` 断言会当场失败」是第三例。§4.3 另一句「`sub rsp, 8` 是 x86-64 特有的 psABI 垫片：`push 0` 后 RSP 是 8 mod 16，再减 8 回到 16 边界」直接说明 `sub` 补的是 `push 0`，不是 `call`。
- 最小修复：把 §3.4 的两种改成三种（只去 `push 0`、只去 `sub rsp, 8`、三者都去），并加一句「`push 0` 与 `sub rsp, 8` 必须成对保留或成对去掉；`sub` 补的是 `push 0` 的 8 字节，`call` 的 8 字节由 psABI 的入口约定本身消化」。
- 置信度：高（用文档自己的对齐算式即可复算）。
- 是否需源码核实：否。
- 若我错了：若 §3.4 的「两种」只统计「改变入口 RSP 侧別/16 字节对齐状态」而不含「只去 push 0」，那它的分类标准没有写出来，读者仍应按 §4.3 的明文理解；无论哪种，两节需要统一。
- 读者验收清单条目：§4.0e 第 3 条（因果链闭合）＋第 4 条（跨节复述一致）。

## SUGGESTION READER-C-S05（P3）

- 位置：§4.1「把基址写成 `0xFFFFFC0000000000` 会怎样」整段，尤其末句。
