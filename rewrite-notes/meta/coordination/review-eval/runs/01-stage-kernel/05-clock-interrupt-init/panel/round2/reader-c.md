## FINDING RD05R2-READER-C-01（P2）

位置：§3.7 推演 2（约 1011 行）；对照同节第 2 段的段定义（约 986 行）与三架构门表（约 1000–1004 行）。

主张原文：推演 2 说「只做第一段与第三段、跳过注册。**两级门都开了**，处理器不存在；中断到达后分发器在 `irq_handlers[TIMER_IRQ]` 上找不到链，返回 `IrqError::Spurious`」。

矛盾：同节对第 2 段的定义是「注册：……这一步**同时完成控制器侧的放行**」。跳过注册，控制器侧的门就停留在 `init()` 留下的屏蔽态——两级门里只可能开模块本地门一级。按三架构分开核对（证据都在本篇内）：

- x86-64：控制器侧的门是 IOAPIC 输入 2 的 mask，由 register_hook 的 first-handler 规则解（§4.7 的表，约 1725 行）。跳过注册则 RTE 仍屏蔽，PIT 一次中断都到不了，「中断到达 → 空链 → Spurious」不可达。
- aarch64：控制器侧的门是 `GICR_ISENABLER0` 的 bit 30，同样由 register_hook 解（§4.7）。跳过注册则 PPI 仍屏蔽，同样没有中断到达。
- riscv64：控制器侧「无——定时器是核本地中断，没有控制器线」（§3.7 表），PLIC 对 0 提前返回（§4.9，约 1899 行）。此处根本只有一级门（`sie.STIE`），「两级门都开了」也没有两级可言；但中断确实会经陷阱入口到达并命中空链分支。

也就是说：推演陈述的前提「两级门都开了」在三架构上都无法由「只做第一段与第三段」这个操作产生（x86/aarch64 是一级门关着，riscv64 是只有一级门），而推演的结局（中断到达、空链 Spurious）只在 riscv64 上成立，却被写成无架构限定的普遍结论。同组推演 1 明确限定 aarch64、推演 3 明确列了 aarch64 与 riscv64，唯独推演 2 漏了限定，属于本篇任务定义中「单形态结论写成普遍结论」的实例。

影响：读者拿这条推演在 x86-64/aarch64 上核对三段设计时会卡住——推演给出的机制（中断到达、分发器查空链）在这些形态上不可达，而文档没有任何提示告诉读者该把它收缩到 riscv64。

建议：给推演 2 加形态限定（按 riscv64 陈述），或改写为「跳过注册后，控制器侧的门除 riscv64 外仍关闭——多数形态上根本不会有中断到达；riscv64 无控制器侧门，定时器中断才走空链 Spurious 分支」。

## SUGGESTION RD05R2-RC-S01

位置：§1.4 章末复述（约 129 行）对 §2.6 的引文是幽灵引文。

原文：「注意 §2.6 那句「校准读进程上下文」只是旁证（探针钩子不读进程上下文，见 §2.6 的限定）」。§2.6 的原文（约 612 行）是「校准窗口本身只需要『中断入口与控制器都已经就位』（探针钩子只数 tick，不读进程上下文）」——通篇没有「校准读进程上下文」这句话，且明说的恰恰是相反内容。读者按 §1.4 的引述去 §2.6 核对，找到的是相反陈述，像是对旧稿的清理残留。建议把这句改为直接引 §2.6 现有表述：校准窗口的依赖是旁证，真正的位置依据是调用链与 §2.6 的两条依赖。

## SUGGESTION RD05R2-RC-S02

位置：§2.7 原则 2（约 704 行）把「编程先于放行」写成普遍结论，丢了 §2.6 限定的 PIC/LAPIC 口径。

§2.6 限定（约 537 行）明说：APIC 支路的 LVT 门「在 `init_local_timer` 的编程段就由 `lapic_set_timer_one_shot` 打开」，并写明「『编程段不含放行』对 APIC 形态也不成立；放行与编程的层次要按 PIC/LAPIC 分开说」。§2.7 的「编程先于放行——……任一段提前都会留下一个『源与处理者不匹配』的窗口」没有带这个限定：在 C 的 APIC 形态里，放行发生在编程段之内，原则字面上不成立（§1.1 对应句约 64 行倒是带了 APIC 校准窗口的说明）。建议给原则 2 补口径：该原则按 C 的 PIC 形态与 Rust 的三段分离陈述，APIC 形态下放行与编程同段发生（§2.6 限定）。

## SUGGESTION RD05R2-RC-S03

位置：§3.7 的 C↔Rust 对照表第 3 行（约 1020 行）与第 2 行、同节正文互相打架。

第 3 行把 `TimerIrqGate::enable_timer_irq` 的「C 的对应物」记为「ARM 的 `bsp_irq_unmask`」。但第 2 行已写 `IrqManager::register_hook`「它自己内含控制器侧放行」，正文（约 986 行）说 C 的同一条规则就是 put_irq_handler 末尾的放行；而 §2.5 的 ARM 故事里，`bsp_irq_unmask` 正是控制器侧那次放行（先 `put_irq_handler` 挂链、再 `bsp_irq_unmask` 放行）。也就是说 `bsp_irq_unmask` 在这张表里被数了两次：它对应的是第 2 段内含的控制器侧放行，不是第 3 段的模块本地门——CNTP 的 Enable 位在 C ARM（OMAP INTC + BSP timer）上没有对应物，这正是 `[ARCH: K-1]` 的差异。建议第 3 行改为「无直接对应（CNTP 使能是 K-1 新形态）；C ARM 里占『最后一段』位置的 `bsp_irq_unmask` 属控制器侧放行，对应第 2 段」。

## SUGGESTION RD05R2-RC-S04

位置：§2.5 推演（约 531 行）与 §2.6 推演（约 689 行）的「永久停摆」结论对「对调」情景缺一条前提，且与 §2.6 自己引的 put_irq_handler 尾部行为相顶。

§2.6 的推演是把 `hw_intr_unmask(CLOCK_IRQ)` **移到** put_irq_handler 调用之前——尾部那次放行随之消失，「线被关回且没有代码再打开它」在该情景里自洽。§2.5 的推演则是把两行**对调**（`put_irq_handler` 与 `bsp_irq_unmask` 都还在），却借「§2.6 同一机制」得出「此后无人再打开它」。而对调情景下，伪中断 tick（入口 mask、空链分支 printf 后 return）之后 put_irq_handler 照常执行，其尾部（§2.6 约 653–656 行自引）`irq_actids[irq] &= ~hook->id; if(==0) hw_intr_unmask` 对首个钩子（actids 为 0）会重新放行——文档展示的伪中断分支没有任何写 actids 的动作。要维持「永久停摆」，需要一条文档没写的前提（例如伪中断路径会把 actids 置成非零，或 ARM 侧尾部放行在该时点不生效）；按文档现有材料，结论应弱化为「丢一个 tick 后由注册路径恢复」。建议补前提或改结论。

## SUGGESTION RD05R2-RC-S05

位置：§4.7（约 1779 行）「C 留级联线开着是因为它随后要靠 `put_irq_handler` 打开时钟线」因果挂错对象。

级联线必须开着的理由，§2.3 推演 2（约 357 行）已经给过：从片的 INT 输出走主片 IRQ2，这条线一封，从片 8 条线全部失去通路——这是硬件通路的必然，与「随后打开时钟线」无关；「随后由 put_irq_handler 打开时钟线」解释的是 `0xFB` 里 IRQ0 那一位为什么关着。另外同一句开头称 Rust 的先 `0xFF` 再 `unmask_irq(0)+unmask_irq(2)` 与 C 的 `0xFB`「等价」，但两个结束态在 IRQ0 位上不同（C 的 intr_init 结束时 IRQ0 关着，Rust 的 pic_init 结束时 IRQ0 开着）；文档在约 1783 行（「此刻 CPU 还没有开始取中断」）已给出为何无害的机理。建议把这句改为「最终投递行为等价（差别是 IRQ0 位被提前打开，此刻 IF=0 无害）」，并把级联线的因果改挂到从片通路。

## SUGGESTION RD05R2-RC-S06

位置：§2.4 第二条依据（约 426 行）的受害情景按文档自述的时序不可实现。

原文：「否则重建期间到达的请求会落在一个门刚被改写、钩子还没挂的窗口里」。但 §2.6 限定（约 537 行）说 APIC 校准窗口「随后停 PIT、摘临时钩子、关中断」，而按 §2.4 自己的调用链（约 413–422 行），`apic_idt_init(0)` 与 `idt_reload()` 在校准之后——重建段处于关中断状态，「重建期间到达的请求」没有发生窗口。能落地的害处另有其处：若控制器未屏蔽，是校准那段**开中断**的窗口里会有无主中断进来（§1.2 约 94 行的机制）。建议把受害情景改写为不变量陈述（「门表重建要求控制器处于已定义的屏蔽态」），或把前提换成校准窗口。

## SUGGESTION RD05R2-RC-S08

位置：§3.1（约 734 行）「本篇只用第一组与第二组」与正文对第三组方法 `local_timer_eoi` 的实质依赖矛盾。

`local_timer_eoi` 被分在第三组「AP 与停顿」（约 734 行），但 §4.3（约 1303–1312 行）把它讲成 aarch64 tick 列车的重挂路径（「without the re-arm the tick train stops dead after the first interrupt」），§6.1 的「tick 只来一次就停」诊断行要核它，而 M13「三段 → tick 到达，已覆盖」的载体 PASS（5 个 tick）正依赖这条重挂——本篇的核心证据链用到了第三组。建议把「只用」改为「正文只展开第一、二组的启动用途；`local_timer_eoi` 的每次 tick 重挂作为 tick 列车成立的前提在本篇出现（§4.3）」。

## SUGGESTION RD05R2-RC-S09

位置：§2.6（约 612 行）的 PROBE_TICKS 退化分析停在 [2,9]，按文档自己引的算式，[10,19] 更糟。

原文：「hz ∈ [2,9] 时 `PROBE_TICKS = system_hz / 10 = 0`……采样循环一开就退出、`tsc1` 停在初值」。但同文引用的校准算式（约 421–422、606 行）都带除数 `PROBE_TICKS - 1`：hz ∈ [10,19] 时 `PROBE_TICKS = 1`，除数为 0——x86 上整数除零直接进 #DE，比「tsc1 停在初值」更早、更硬，而 `init_clock` 的 `2..50000` 回退同样放行这个区间。建议补一句 [10,19] 的退化形态，把「合法输入也能打穿校准链」的论证补全。

## SUGGESTION RD05R2-RC-S12

位置：§3.4 推演（约 896 行）与 §4.5 复述（约 1586 行）对「为什么实例不能丢弃」的因果框架与自引证据相顶。

§3.4 推演说「真正的代价落在**实例承载的硬件侧状态**上」，但同一段的依据自己写明「（`claimed` 是参数、不是实例字段）」——GIC 的应答债（active 优先级）记在硬件里，实例上并没有可丢的状态。§4.5 的复述更进一步：「`claim` 与 `complete` 的配对必须在同一个实例上进行」。真正成立的理由是软件侧纪律：身份靠参数在 claim→complete 之间传递，丢弃实例会把这条纪律打散（§3.4 自己的句子「任何一次重构都可能把它丢掉或写错」就是这个意思）。建议把「实例承载的硬件侧状态」改写为「实例边界承载的身份传递纪律」，并给 §4.5 那句加「就本实现的参数传递形状而言」之类的限定。

## SUGGESTION RD05R2-RC-S13

位置：「全屏蔽」的口径在 §1.1/§2.7 比 §1.2/§2.3 粗一档。

§1.1 第 2 条（约 24 行）说控制器要建立「每条线都在屏蔽」的确定状态，§2.7 的表（约 698 行）写「可用 + 全屏蔽」；而 §1.2（约 92 行）与 §2.3（约 352 行）的精确口径是「除级联线外每一条线都在屏蔽」——主片留 IRQ2、从片全关。Rust 侧的 `init()`/`mask_all` 倒是真全屏蔽，粗口径对 Rust 成立、对 C 的 intr_init 不成立。建议给 §1.1 第 2 条与 §2.7 的「全屏蔽」补「（x86 留级联线，见 §1.2）」。

## SUGGESTION RD05R2-RC-S14

位置：§1.1 第 3 条（约 25 行）对 ARM 杂项的列举比 §2.5 少两件。

原文：「ARM 一侧是 TSS 与 PMU」。§2.5（约 473 行）的清点是：栈区赋值与对齐断言、单 CPU 的 `tss_init`、三行 PMU 读写、一行 `bsp_init()`——概述漏了栈区赋值（与 x86 共有）和 `bsp_init`（ARM 独有）；§1.3 的表（约 106 行）对 aarch64 也列了「内核栈指针、TSS、PMU、板级初始化」四件。建议把 §1.1 第 3 条的 ARM 侧补齐为「栈指针、TSS、PMU、板级初始化」。
