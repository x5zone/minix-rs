## 结构重建

我按文档自己的弧线重建，得到的主干是：

1. 第 1 章立命题：RS 是 boot 映像里的普通用户进程，却要给其他 boot 成员授权放行，因此必须自举；Minix3 把自举拆成四步，每一步只依赖前一步已经建立的设施。承重区分是“Step 1 建属性、Step 2 放行”。
2. 第 2 章给 C 证据：`main()` → `sef_local_startup()` 注册回调 → `sef_cb_init_fresh()` 的“前置 + 四步” → `boot_image_info_lookup()` → `table.c` 三表。
3. 第 3 章把隐式全局改成显式输入：`BootTables`、查找结果 `Result` 化、SEF 回调 trait 化、`BootInit` 编排四步、`KernelApi` 五域面、自升级 feature 门控、grant 用 `Option<GrantId>`。
4. 第 4 章按文件落实现：`main.rs`、`lib.rs`、`table.rs`、`boot.rs`、`sef.rs`。
5. 第 5 章用测试收口：四个模块 52 项，全 crate 359 项。

这条弧线在骨架层面是完整的，但有五个断点：

- 第 1 章的 Step 1 定性与第 2 章自己引的 C 代码相反（B1）。
- 第 3 章的五域面契约漏掉第 3、4 章自己使用的两个内核调用（E2）。
- 第 3 章与第 4 章对“生产内核实现是谁”给出互斥答案（H1）。
- 第 4 章章首仍承诺已经删除的 dispatch 节，第 5 章仍引用已经删除的 dispatch 类型（H6、F1）。
- 第 5 章的测试清单与它自己的计数不闭合（G1）。

章级职责重叠的情况是：§1.2 与 §2.0 是同一块内容的两份拷贝；§3 与 §4 在四步序列和外部边界上重叠，§4 的增量主要是文件落点；§5 的测试描述复述 §2 的机制；§6、§7 与 §1.0、§1.3 在“机制归哪一篇”上各写一份且互不相同。

导航骨架的残留状况：header 已经摘掉“导航骨架文档”的自我标签，这一点旧版问题已修。但 §6 仍是带省略号的半截阅读路线，§7 仍把 `plan.md` 写成“写作契约”，`99` 与“§1.3 表”两处引用落空，“第 N 篇”与被引 C 代码混排。此外，章节编号出现 2.4→2.7、3.7→3.9、4.5→4.7 三处断层，是删除导航性小节留下的疤痕。

## SUMMARY

这篇文档的骨架是“概念→C→Rust 设计→实现→测试”的标准五段式，命题清楚，C 证据密度高，设计决策大多能回溯到 §2，这些都是优点。问题集中在三处：

第一，承重事实说反了。Step 1 在概念章被说成“纯本地准备、不向内核提交”，而第 2 章自己引的 C 代码在 Step 1 就对除 RS/VM 外的所有服务调用 `SYS_PRIV_SET_SYS`。这一条错误同时污染了 §1.2 的失败对照与 §2.8 的小结，是 P0 级的概念—证据倒置，必须最先修。

第二，设计与实现的边界没有守住。五域面契约漏掉本篇实际使用的 `get_image` 与 `grant_direct`；生产内核实现同时被写成 `UnimplementedKernelApi` 与 `TrapKernelApi`；`ServiceSlot` 的字段清单被自己的测试反驳；第 4 章章首仍承诺已删除的 dispatch 节，第 5 章仍引用已删除的 dispatch 类型。这些说明“设计章”“实现章”“测试章”是按模板保留的，而不是按内容需要保留的。

第三，改写留下的机械伤痕密集。决策编号被批量替换成主题词后出现“（四链指针）”“错误域二分（）——boot 错误域二分”“本拆分是对 域拆分 原草案”这类病句；`plan`、`todo §11/§13`、`Fix #63`、`NS2`、`I2`、`S2`、`CSSCM` 仍在正文承担论证；章节编号出现 2.4→2.7、3.7→3.9、4.5→4.7 三处断层；§6 仍是带省略号的半截阅读路线。这些单独看是文字问题，合起来说明“从工作笔记转正式稿”的动作完成了一半。

章级职责重叠方面：§1.2 与 §2.0 是逐字复制，§3 与 §4 在步骤与边界上重叠，§5 的测试描述复述 §2 的机制，§6、§7 与 §1.0、§1.3 在“归哪一篇”上各写一份且四种清单互不相同。建议的收敛顺序是：先修 B1 与 E2/H1/H3 四个 P0，再做一次“编号—承诺—归属”三合一对账（S1、H6、F1、N1、E1、S4），最后清理 C1/C2 的语言与过程残留。只做文字清洗而不动 B1/E2/H1，文档会变得更好读，但仍然是错的。
