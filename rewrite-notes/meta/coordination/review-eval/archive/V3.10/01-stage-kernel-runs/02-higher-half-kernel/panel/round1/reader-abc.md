### FINDING RD1-READER-A-01（P2）

- 位置：§2.3“逐行解码”第 2 条（`push $0` 那一条），复述在 §4.3 的 x86_64 六条解码与 §4.3“三条推演”其三。
- 严重度：P2。卡住的是 C/Rust 帧指针链的对比，不是全文主线；但读者无法从文档给出的指令序列判断 C 侧保存槽里到底是什么。
- 问题：文档先说 C 在换栈前把 EBP 清 0，随后又说换栈后 `kmain` 的序言把 `pre_init` 的帧指针保存进槽里。两句话之间只有 `mov $k_initial_stktop, %esp`、`push $0`、`push %eax`、`call kmain` 四条指令，没有任何一条改写 EBP；按文档自己的序列，EBP 在 `kmain` 入口仍是 0，保存槽里应当是 0，而不是 `pre_init` 的帧指针。文档没有给出把 `pre_init` 帧指针送进该槽的指令或路径。
- 影响：读者无法判断 C 侧回溯链到底在哪一帧终止，也就无法理解“两侧到 0 的方式不同”这个结论；§4.3 其三再述同一句话时，读者只能跳过或凭信任接受。
- 证据或推理：原文摘录——“C 侧入口段 `mov $0, %ebp` 只保证换栈前的 EBP 为 0；换栈后调用 `kmain` 时，它的序言保存的是 `pre_init` 的帧指针（跨过换栈点、指向后来会被回收的低侧栈），不是 0。”同一节给出的四行是“`mov $k_initial_stktop, %esp` / `push $0` / `push %eax` / `call _C_LABEL(kmain)`”；四条都不写 EBP。§4.3 复述：“C 在换栈前清 EBP，换栈后调用 `kmain` 时保存槽里是 `pre_init` 的帧指针”。
- 最小修复：二选一。其一，补出真正把 `pre_init` 帧指针留在槽里的指令序列（例如 `mov $0,%ebp` 的实际位置不在换栈前，或 `pre_init` 返回时 EBP 并未被恢复），并把“换栈前清 0”改成与实际序列一致的描述；其二，如果 EBP 确实在换栈前为 0 且 `pre_init` 遵守调用约定，则把结论改成“C 侧 `kmain` 的保存槽也是 0；两侧的差别只在清 0 的位置，不在槽里的值”，并删除“保存的是 `pre_init` 的帧指针”。
- 置信度：中高。矛盾在文档内部可见；具体哪一句对需要看 `head.S` 与 `pre_init` 的编译结果。
- 是否需源码核实：是。
- 若我错了：如果 `pre_init` 使用了非标准约定（不恢复 EBP），或 `mov $0,%ebp` 实际排在换栈之后、`call` 之前，那么“槽里是 `pre_init` 的帧指针”可能成立；但文档必须把这个位置和约定写出来，否则读者无法复现。
- 命中清单：§4.0e 编号不可读（工作流规则在禁读范围）；按类型记为「A-理解路径断裂 / C-因果链缺口」。

### SUGGESTION RD1-READER-A-03

## B 结构编辑

我独立重建的论证骨架是：§1 提出“三件事”（链接布局、装载摆放、成对跳转）；§2 用 C 侧四个决定点（`kernel.lds`、Makefile 改名、`head.S` 四行、`mpx.S` 栈定义）把三件事各走一遍；§3 把 C 的负担逐条翻成 Rust 的五条设计决策（三种脚本形态、自建 ELF 解析器、栈顶改为交接字段、trait 契约、跨距收口）；§4 按同样的顺序落到实现（脚本、解析/摆放、三架构跳转、完整路径、C↔Rust 对照）；§5–§6 给测试与诊断。骨架清楚，三件事的映射在 §1.2、§2.5、§4.5 三处都能对上。结构上的问题主要是“设计章提前讲了实现章的论证”与“同一论证在两章各写一遍”，不是骨架错误。

## C 因果一致性

我追的关键因果主张：①“三件事必须对齐”在 §1.2/§2.5/§4.5 的复述；②C 的“符号值高、段体低、差 `_kern_offset`”在 §2.1/§2.5/§4.5 的复述；③`k_initial_stktop` 高侧在 §2.3/§2.4/§2.5 的复述；④Rust 三种脚本形态的判据在 §3.1/§4.1/§4.5 的复述；⑤`kern_stack_top = kern_virt_base + kern_size` 在 §3.3/§3.5/§4.1/§5.2 的复述；⑥`delta` 只在 riscv64 direct leg 需要，在 §3.1/§4.3/§4.4/§5.2/§5.4 的复述；⑦“`kinfo` 经 `.bss` 副本交接”在 §4.4/§5.4 的复述。①–⑥基本一致，能互相印证；⑦在 §5.4 的摘要里出现了与 §4.4 相反的措辞。另有若干处局部因果链缺口/证据不足，列在下面。

### FINDING RD1-READER-C-01（P2）

- 位置：§5.4 M11 行与 §4.4“两条生产路径在 `kmain` 处合流”段。
- 严重度：P2。不是主线卡住，但两张表/两段正文对同一交接机制给出相反描述，读者无法判断“指针到底经不经过 caller-saved 寄存器”。
- 问题：M11 写“`kinfo` 经 `.bss` 副本交接（不经 caller-saved 寄存器）”，而 §4.4 写“指针本身仍按 ABI 放在 RDI/X0/A0，但它的值不依赖 caller-saved 寄存器的存活”。RDI、X0、A0 都是 caller-saved 寄存器；按 §4.4，交接确实经过 caller-saved 寄存器，只是寄存器里放的是指向 `.bss` 副本的指针。M11 的“不经”与 §4.4 的“仍放在”直接冲突。
- 影响：读者在覆盖表里看到“不经寄存器”，在正文里看到“仍放在 RDI/X0/A0”，无法确定哪一种是实现事实；这会影响对 M11 覆盖状态的理解。
- 证据或推理：原文摘录——M11：“`kinfo` 经 `.bss` 副本交接（不经 caller-saved 寄存器）”；§4.4：“现在全局副本的地址是链接期 RIP 相对常量，不再依赖 shim 栈上的引用；指针本身仍按 ABI 放在 RDI/X0/A0，但它的值不依赖 caller-saved 寄存器的存活”。
- 最小修复：把 M11 改成“载荷经 `.bss` 副本交接；指针仍按 ABI 放在 RDI/X0/A0，但其值指向 `.bss` 副本，不依赖寄存器旧值的存活”。
- 置信度：高。两个短语在同一篇文档内直接对立。
- 是否需源码核实：否（这是文档措辞冲突；实现事实以 §4.4 的详细描述为准）。
- 若我错了：如果 M11 的“交接”专指“载荷的存放位置”而不是“指针的传递方式”，那么“不经 caller-saved 寄存器”可以勉强成立；但当前措辞没有这个限定，读者会按字面读成指针不经寄存器。
