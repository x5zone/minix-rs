## FINDING READER-C-01（P1）

**主张**：I4“校验先于消费”的可观测判据是一条固定的三门链；§3.7 进一步把它说成“载荷先落到存储、再发布，发布前完成校验”。读者要据此回答“在哪一步校验”。

**原文摘录**：

> `| I4 | 校验先于消费 | `validate_before_tables` → `store_kernel_info` → `validate_requiring_sources` | 非法布局进入建表；消费到半提交的表 |` ——§1.2 I4 行

> `I3 与 I4 在实现上是两条相邻的检查：**载荷先落到自己的存储，再发布；发布前完成校验**。` ——§3.7 开头

> ``check_boot_postconditions` 检查派生值（栈顶、用户栈顶、系统调用入口）与镜像/模块区间的半开不重叠` ——§3.7

> `v10（设计裁决）之后只剩一条可被剩余字段证伪的关系——`kern_virt_base` 必须大于 `u32::MAX`……“`syscall_entry` 落在镜像跨度内 / `kern_stack_top` 不越过跨度上界 / 用户栈不越入内核半区”三条读取派生字段的断言随字段一起删除` ——§4.4 第 3 条

> `直核面是 **strict（`validate_requiring_sources`，两个 `bootface` 在调 `arch_boot` 之前显式调用）→ pre-table（2）→ postconditions（3）→ boot_validate（1，`arch_boot_impl` 开头）→ kmain validate**；v1 接收面是 **strict → postconditions（3）→ boot_validate（1）**，且**不经过** pre-table（`resume_additive` 体内没有 `validate_before_tables`）` ——§4.4“腿间实际执行序”

> `store_kernel_info(kernel_info); register_panic_diagnostic(); arch_boot_impl::<A>(kinfo, root_page);` ——§3.6 的 `arch_boot_finish` 引文

**位置**：§1.2 I4 行；§3.7 全节；§4.4 第 3 条、门表与“腿间实际执行序”；§3.6 的 `arch_boot_finish` 引文。

**影响**：这里有四处互相拆台的复述，全部落在读者画像的核心问题“在哪一步校验”上。
其一，§1.2 的链把 `validate_requiring_sources` 放在 `store_kernel_info` **之后**；§4.4 却说两个腿族都在 `store` **之前**跑 strict（直核面在两个 `bootface` 调 `arch_boot` 之前，v1 接收面在 `resume_boot_pt_alloc` 之前），没有任何腿的 strict 在 store 之后。照 §1.2 去查，读者会找不到那一步。
其二，§3.7 说“发布前完成校验”，但 §4.5 明确 `store_kernel_info` 同时“把载荷落到 `.bss` 并把全局副本发布”，而 `boot_validate_and_prepare` 在 `arch_boot_impl` 开头、即 store 之后才跑（§3.6 的引文顺序也是 store → `arch_boot_impl`）。至少 `ks > 0` 与基址页对齐这两条校验发生在发布之后，§3.7 的断言不成立。
其三，§3.7 描述的 `check_boot_postconditions` 是 v10 之前的内容；§4.4 说 v10 后只剩 `kern_virt_base > u32::MAX` 一条，栈顶、用户栈顶、系统调用入口三条随字段删除。设计章与实现章对同一个门的描述直接冲突。
其四，v1 接收面根本不经过 `validate_before_tables`，而 §1.2 把这条门列为 I4 判据的第一步；读者若按 I4 检查 v1 腿，会得出“v1 腿违反 I4”的错误结论。
结论：I4 的**不变量陈述**（校验在消费前完成）仍站得住，但它的**可观测判据**按现在的写法在五条腿上都不成立；读者无法据此判断任何一条腿的校验位置。

**最小修复**：把 §1.2 的 I4 行改成“所有校验在消费（建表/映射/分配）之前完成；各腿门集与顺序不同，见 §4.4”，删掉固定箭头链；把 §3.7 的三门描述替换为 §4.4 的 v10 口径（postconditions 只剩 4 GiB 门；strict 含内核跨度覆盖；v1 腿无 pre-table），并把“发布前完成校验”改为“消费前完成校验”。

**置信度**：高。

## FINDING READER-C-03（P2）

**主张**：§1.1 的“三份数据”表是读者回答“内核拿到什么”的第一张表；它列出的“内核位置记录”与“交接结构”应与 §3.2.1 的 `KernelInfo` 字段一一对应。

> `| 交接结构 | `KernelInfo`（进程内）/ `BootReport` 与 wire（跨镜像） | 内核启动入口、校验门链 | 前三样必须按值深拷，指针不能跨镜像存活 |` ——§1.1 表第 3 行

> `pub struct KernelInfo { pub memmap: …; pub reserved_regions: …; pub source_records: …; pub kern_virt_base: VirBytes; pub kern_phys_base: PhysBytes; pub kern_size: u64; pub boot_modules: …; pub platform_sources: …; pub param_buf: …; pub authority: RamAuthority, }` ——§3.2.1 的字段清单（10 个）

> `装载器另断言 `e_entry == min(vaddr)`（UEFI 与 U-Boot 两条 loader 各一处），直核面由 `KERN_*` 常量提供` ——§4.4 的 `kern_virt_base / kern_phys_base / kern_size` 行

> `BootReport<'a> 只是借用视图；跨镜像发送侧把它序列化进 wire，接收侧在自己的 .bss 重建切片。` ——§3.7

**影响**：

其三，该行“为什么必须交接”一栏写的是“镜像的符号值与装载地址由链接期决定，接收侧只读常量”——这句话恰恰说明接收侧可以自己读链接期常量，不构成“必须交接”的理由。§3.2.1 给出的真实理由是让 shim 解析 ELF、保证“数字与镜像一致”，并明确“两个直核面是例外，用自己文件里的 `KERN_*` 常量”。概述把单形态（三条 v1 腿）的理由写成了普遍理由，且与它自己的“为什么必须交接”栏冲突。

**最小修复**：§1.1 第 2 行只列 `kern_virt_base`、`kern_phys_base`、`kern_size`，把 `entry_point` 移到“装载器对账”脚注（说明它只做 `e_entry == min(vaddr)` 断言）；第 3 行改成“`KernelInfo`（接收侧进程内）/ wire（跨镜像）；`BootReport` 是发送侧借用视图”，并把“为什么必须交接”改成 §3.2.1 的单源一致性理由（并注明两个直核面例外）。

**置信度**：高。

## FINDING READER-C-05（P2）

**主张**：§1.3 用“Rust 的接收侧是另一个镜像，wire 只能传值”来解释 C 与 Rust 的边界；§1.2 的 I1 判据写成“wire 只写固定宽度标量与字节分区”；§3.3 把来源记录的必要性归因于“交接跨镜像”。

**原文摘录**：

> `C 的 `kinfo` 是**同一个二进制里的全局变量**，指针与数组都活在同一地址空间；Rust 的接收侧是**另一个镜像**，wire 只能传值。` ——§1.3

> `| I1 | 值可跨镜像，指针/句柄不可 | wire 只写固定宽度标量与字节分区；接收侧重建切片 | 接收侧读到发送侧堆上的地址；高半切换后读到零 |` ——§1.2 I1 行

> `C 侧没有这个结构：C 的 `memmap` 只有 `base`/`len`，来源隐含在“引导器给的”这个前提里；Rust 把它显式化，是因为交接跨镜像，接收侧无法再问引导器。` ——§3.3

## FINDING READER-C-11（P3）

**主张**：§2.6 用“半开区间的判据是 `start < other_end && other_start < end`”概括 `overlaps`，并据此解释 `-1` 的必要性。

**原文摘录**：

> `区间不重叠由 `overlaps` 检查：内核被临时塞进 `module_list[k]`，于是“内核与模块”“模块与模块”用同一个函数检查。半开区间的判据是 `start < other_end && other_start < end`；把 `-1` 从 `INRANGE` 的第二项去掉，相切的两个模块会被误报为重叠。真重叠时 `panic("overlapping boot modules/kernel")`；相切必须放行。` ——§2.6

> `#define INRANGE(mod, v) ((v) >= mod->mod_start && (v) < mod->mod_end)`
>
> `#define OVERLAP(mod1, mod2) (INRANGE(mod1, mod2->mod_start) || INRANGE(mod1, mod2->mod_end-1))` ——§2.5 引文

> `真重叠时只要有一个方向报出即可（包含关系只在“被包含者作 `cmp`、包含者作 `thismod`”的那一次被发现）` ——§2.5

**位置**：§2.6 第 3 段；对照 §2.5 的宏与“两个方向各检查一次”段。

**影响**：`start < other_end && other_start < end` 是标准的半开区间相交判据，它与 C 的 `OVERLAP` 宏**不等价**：当 `cmp` 完全包含 `thismod` 时，`cmp.start` 与 `cmp.end-1` 都不在 `thismod` 内，宏返回假，而标准判据返回真。C 靠外层对每条记录各调一次 `overlaps`（两个方向）才补上包含关系；这也正是 §2.5 说“包含关系只在‘被包含者作 cmp、包含者作 thismod’那一次被发现”的原因。§2.6 换成标准判据后，`-1` 对相切仍然必要（这一点没错），但读者会以为一次调用就能覆盖所有相交形态，从而无法理解 §2.5 为什么强调“两个方向各检查一次”；也会误以为 C 的宏就是标准判据的实现。

**最小修复**：§2.6 直接写宏的实际判据（“检查对方起点与最后字节是否落在本方 `[start, end)` 内”），再补一句“它与标准半开判据不等价：包含关系只在一个方向命中，靠外层对每条记录各调一次补上”；相切例子保留。

**置信度**：高。

5. **§4.4 的 `source_records` 行与 builder 签名不一致**：表里写“调用方经 builder 参数传入”，但 `build_kernel_info(report: &BootReport, authority: RamAuthority)` 只有两个参数，来源记录是从 `report.source_records` 复制的；建议改成“经 report 传入”。
6. **`RamAuthority::DTB` 与 `DtbBootInput` 两种写法**（§3.2.1 与 §4.4）：前者像 `RamAuthority` 的变体，后者像 `InputObjectId` 的变体；请统一为调用点实际使用的构造形式，并说明 `RamAuthority` 与 `InputObjectId` 的包装关系。
7. **§4.4 的 16 字节对齐门在清单里消失**：门表有“`boot_validate_and_prepare` | `kern_stack_top` 16 字节对齐”一行，但第 1 条防线枚举没有它，引文的省略说明又说该断言被省略；建议在枚举里补一句，避免读者以为这条门不存在。
8. **§4.5 的 `MEMMAP_REGION_STORE_LEN = 128` 来由两说**：§3.2.1 说“UEFI 图常超 40 条”，§4.5 说“直接定居 globals.rs”并转向账本模块删除；建议在 §4.5 补上“因为 UEFI 图常超 C 的 40 条”这半句。
9. **§1.1 的“前三样必须按值深拷”**：表只有三行，第三行就是“交接结构”，读者会问“前三样”是指三行数据还是两类载荷；建议改成“上表三份数据（尤其两张表与模块表）必须按值深拷”。
10. **§2.8 的“四样”**：“四样之间的次序约束共五条（D1–D5）”没有定义“四样”；建议写成“四份交接对象之间”。
