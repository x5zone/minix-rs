# Reader C — 因果一致性（round38）

读者画像：第一次读 Minix-RS 启动链的 Rust/OS 工程师。验收清单（本报告用编号引用）：
R1 判断“引导器把控制权交给内核”是否可信；R2 说出三份交接数据；R3 说出四条不变量。

## FINDING READER-C-01（P1）

- 位置：§2.8 开篇（L997），对照 §1.0 小结（L38）与 §1.1（L52）。
- 严重度：P1。读者验收项 R2 被直接打穿。
- 问题：交接数据的份数在两处冲突。§1.0 与 §1.1 都说“三份数据”，§2.8 却说“四份交接对象之间的次序约束共五条”。
- 影响：读者按验收清单复述“三份数据”时，遇到一个无法命名的第四份；D1–D5 到底约束哪些对象也随之悬空。
- 证据（只引文档内句子）：§1.0 “内核接手时要带走三份数据：可用内存清单、内核位置记录、交接结构。”；§1.1 “内核真正需要‘带走’的东西只有三份数据”；§2.8 “四份交接对象之间的次序约束共五条（D1–D5）”。
- 最小修复：改为“三份交接对象的次序约束共五条”，或明确第四份是什么；若第四份指页表/恒等映射，它们不是交接数据，应改称“三份数据加两组建表步骤”。
- 置信度：高。
- 是否需源码核实：否。
- 若我错了：若“四份”确实指三份数据加页表这一独立交接物，§1.1 必须补一行定义，否则“四份”仍是未定义项。
- 命中验收：R2。

## FINDING READER-C-02（P1）

- 位置：§2.8（L997 与 L1001/L1003），对照 §2.0 小结（L146）。
- 严重度：P1。D1–D5 的证据完整性无法判断。
- 问题：“五条的证据都在本章”与同节 D3/D5 的“证据在 02 篇”直接冲突；§2.0 小结自己说的是“本章与 02 篇”。
- 影响：读者按“都在本章”去找 D3/D5 的证据会找不到，进而无法判断五条次序约束是否都有证据。
- 证据：§2.8 “五条的证据都在本章；下面按编号逐条给陈述与证据锚点”；D3 “语义与证据在 02 篇的 J3”；D5 “覆盖次序的逐数字推演在 02 篇的 J3；本篇只保留这条约束名与调用位置”；§2.0 小结 “证据都在本章与 02 篇的建表节”。
- 最小修复：改为“D1/D2/D4 的证据在本章，D3/D5 的语义与证据在 02 篇 J3；本章只保留调用位置”。
- 置信度：高。
- 是否需源码核实：否。
- 若我错了：若 02 篇 J3 只是“展开”而本章另有等价证据，需在 D3/D5 条目里给出本章锚点；目前没有。
- 命中验收：R1、R3。

## FINDING READER-C-03（P1）

- 位置：§5.1 I3 行（L2608），对照 §5.4（L2633）、§3.1.1（L1118）、§5.2（L2613）。
- 严重度：P1。把单腿/单形态结论写成五条腿的普遍结论。
- 问题：§5.1 写“五条腿都走到 kmain”，但 §5.4 的 riscv64 直核 bootface 门是“故意让模块定位失败以验错误路径”，aarch64 UEFI 的通过判据又包含“DTB preflight failed”这一失败行。
- 影响：I3 的证据强度被高估；读者无法据此判断“所有权/深拷”在五条腿上都被验证。§5.5 “当前没有未闭环的测试缺口”也因此少了支撑。
- 证据：§5.1 “五条腿都走到 `kmain`”；§5.0 小结只说“真机门证明五条链能走到各自终点”；§5.4 “riscv64 直核 bootface … 表址行、`table holds 0x0 entries`、`module placement failed` 的行序（故意让模块定位失败以验错误路径）”；同表 aarch64 UEFI “前两条固定标记 + 第三条变体（`memmap source` 或 `DTB preflight failed`）”；§3.1.1 “该门只验证 DTB 表址与模块定位失败的错误路径（§5.4）”。
- 最小修复：把 I3 的真机证据改为“五条腿都有门覆盖；riscv64 bootface 与 aarch64 UEFI 的 DTB_CFGTABLE 形态验证 fail-closed 错误路径，不证明走到 kmain；走到 kmain 的证据只覆盖 x86 UEFI、aarch64 UEFI 正常形态与 riscv64 U-Boot shim”，并同步 §5.5。
- 置信度：高。
- 是否需源码核实：是（确认 `DTB preflight failed` 是否发生在跳转前；若发生在 kmain 之后，本条减弱）。
- 若我错了：若 aarch64 的失败行只在 kmain 之后出现，且 riscv64 bootface 门另有一次成功启动，则“五条都走到 kmain”可成立；但 §5.4 的“故意让模块定位失败”与 §3.1.1 的“只验证错误路径”直接否定后者。
- 命中验收：R1、R3。

## FINDING READER-C-04（P2）

- 位置：§3.4.1 两条 bullet（L1358、L1359）。
- 严重度：P2。证据锚点错误，D2 的因果链在回查时断掉。
- 问题：说“2.6 里 `kern_phys_start`/`kern_vir_start` 的来源”，但 §2.6 是“模块装载的检查与失败模式”，全节没有这两个名字；本章实际用的是 §2.5 的 `kernbase`/`kernsize` 和链接符号 `_kern_phys_base`/`_kern_vir_base`。第二句又说 `_kern_size` 是“2.5/2.6 引用的那个名字”，§2.6 也没有引用它。
- 影响：D2（内核位置先于清单裁剪）的证据链在读者按锚点回查时断掉；这是把“链接期常量”落到 C 证据上的唯一入口。
- 证据：§3.4.1 “前三个赋值就是 2.6 里 `kern_phys_start`/`kern_vir_start` 的来源”；“随后 `_kern_size = __k_unpaged__kern_size` 把它导出成 2.5/2.6 引用的那个名字”；§2.6 全节只讲装载器次序、条数上限、区间不重叠（L846–L856）；§2.5 用 `kernbase`/`kernsize` 与 `_kern_phys_base`/`_kern_vir_base`（L830）。
- 最小修复：两处“2.6”改为“§2.5”；`kern_phys_start`/`kern_vir_start` 改为文档实际使用的 `kernbase`/`kernsize`（或链接符号名）。
- 置信度：高。
- 是否需源码核实：否（只需本篇内对照）。
- 若我错了：若 §2.6 在未引段落里确实给出这两个名字，则只需补锚点；按本篇现有文字，§2.6 不含它们。
- 命中验收：R3。

## FINDING READER-C-05（P2）

- 位置：§3.2.3（L1303）与 §3.7（L1837），对照 §4.2 注释（L2011）与动作 7（L2046）。
- 严重度：P2。I3 的“单所有者”判据在一条腿上不成立。
- 问题：`BootStorage` 被写成“六类载荷的唯一所有者”，且“发送侧的分类结果同时写进 storage 与 wire”；但同一篇又说 UEFI 腿的 source 记录由分类器直写 wire、storage 的 source 切片为空、不经过 `fill_source_records`。
- 影响：读者无法回答“source 分区归谁所有”，也就无法判断“第二次 fill panic”这条 I3 证据覆盖哪些腿。
- 证据：§3.7 “`BootStorage` 是六类载荷的唯一所有者；`fill_modules`/…/`fill_source_records` 各自在闭包返回时提交计数”与同段“UEFI 腿的 source 记录由分类器直写 wire，不经过 `fill_source_records`”；§4.2 “UEFI 腿的 source 记录由分类器直写 wire；storage 的 source 切片为空”；§3.2.3 “发送侧的分类结果同时写进它自己的 `BootStorage`（调用方持有的定长数组）和 wire”。
- 最小修复：把“六类载荷的唯一所有者”限定为“实际走 `fill_*` 的腿”，并显式写“UEFI 腿的 source 分区由分类器直接写 wire，storage 的 source 切片为空；‘唯一所有者’不覆盖该分区”；同步 §1.2 I3。
- 置信度：高（文档内两面原文直接冲突）。
- 是否需源码核实：否。
- 若我错了：若“分类结果”仅指 memmap/reserved 两表，且“六类载荷”不含 source，则 §3.2.3 可解；但 §3.7 明列 `fill_source_records` 为六类之一，且 §3.2.3 说“六个分区”，冲突仍在。
- 命中验收：R3。

## SUGGESTION

- §1.2 I1 “五条腿共同：接收/消费侧从私有存储重建切片”与 §3.2 “两个直核面的切片由 `build_kernel_info` 的 `&'static` 输入直接给出，没有 wire 解码步骤”并列时，“重建”对直核腿没有 wire 可重建。建议改为“落进私有存储并改指该存储”。
- §1.1 把“框 1 = 可用内存清单（最终形态已排除内核与模块占用区）”与 §3.2.1 “列表不保证已扣除全部占用区”并读，容易以为同一对象有两种状态。建议在 §1.1 补一句“交接的是原材料；框 1 的成品在接收侧扣除后成立”。
- §3.2.1 `reserved_regions` 行写“可用但不可分配”，§3.3 写“已占用/不可分配”。建议统一为“保留但可访问、不可分配”。
- §3.0 术语写“六类 `fill_*` 的唯一所有者”，§3.7 只列五个 `fill_*` 函数（memmap 与 reserved 由 `fill_map_tables` 一次提交）。建议改为“六类载荷（五个 `fill_*` 入口）”。
- §4.4 `authority` 行用 `DtbBootInput`，§3.2 用 `RamAuthority::DTB`，§4.2 用 `InputObjectId::UefiMemoryMap`。三层名字没有对照，读者难以确认是同一值还是三个对象。
- §3.2.1 “v10 起 strict 门改为检查内核物理跨度落在某条 `memmap` 或 `reserved_regions` 区间内”与 §4.4 “strict 门按 `authority` 查 `source_records` 覆盖投影内存图；内核物理跨度落在某条区间内；按位置核对模块名”并读，“改为”像是替换了来源覆盖检查。建议改成“另加（其中内核跨度那一条改为查两张表）”。
- §4.3 的“模块装载层的唯一修剪点在 `loader::load_boot_modules_into`”与 §3.5.1 的“生产者在 `build_shim_table` 里按最后一个 PT_LOAD 的文件尾修剪槽长度；loader 的二次修剪对已在槽内的输入是 no-op”并读，容易被读成两个生效点。建议改为“装载层内唯一的修剪入口；U-Boot 腿的实际生效修剪在 `build_shim_table`，loader 侧对已修剪输入是幂等 no-op”。
