# 12 服务发现：名字查找、身份反查与信息路由

> **目标读者**：已经读过第 11 篇的读者，熟悉纯函数封装。前置知识只需要一样：知道大系统里服务会重启，地址会变，写死地址的程序活不长。

## 1 概念：为什么找人要分三步走

程序想办事，先得知道对方住哪。地址有两层：人读的名字和机器用的端点。名字稳定，端点易变，服务重启一次端点就换了。所以第一步永远是查名字：把名字递给重生服务，拿回当前端点。不缓存，不记忆，每次现查，重启立即可见。这是本组最重要的设计决定，后面两步都是它的陪衬。

第二步是反查：拿着端点问端点背后是谁。进程号、用户号、组号各有各的问法，但形状一样：端点进去，身份出来。问法不同是因为管的表不同：进程号表在进程管理，身份表也在进程管理，问谁都是问它，只是调用号不同。

第三步是路由：杂项信息散在各家手里，问之前先看目标是谁。目标是进程管理就用它的信息调用号，文件系统、重生服务、数据存储各有各的号，目标不是这四家就直接报告不支持，连路都不用跑。路由是纯函数，测试把五家全覆盖：四家有去处，一家被拒绝。

### 1.1 查找模型

记住一句话：每次现查，永不缓存。调用者给名字地址加长度（含结尾零），服务回端点。失败就是失败，没有兜底地址。缓存看起来能省往返，代价是重启盲区：服务换了端点，缓存还指着旧坟。C 版本没有缓存，Rust 版本同样没有，这不是偷懒，是正确性压倒性能。

### 1.2 反查模型

记住另一句话：端点进去，身份出来，要哪个拿哪个。四个身份一次全回，调用者按需取用。C 版本用空指针表示跳过某项，Rust 版本没有空指针的概念，全回元组，调用者忽略不要的。两种表达，同一组数。

### 1.3 路由模型

记住第三句话：先看门牌，再定投递口。端点号就是门牌：0 号进程管理，1 号文件系统，2 号重生服务，6 号数据存储。门牌对不上四家，报告不支持。路由在跑路之前判定，陌生门牌零次往返。

## 2 C 语言源码分析：发现路径上的每个文件在做什么

本章按查找、反查、路由的顺序讲解 C 语言文件。所有行号都针对当前代码库中的 Minix3 源码。

### 2.1 查找：量长填名读端点

打开 `minix3/minix/lib/libc/sys/minix_rs.c` 文件的第 23 行到第 40 行，一共 18 行。第 28 行量名字长度（含结尾零）。第 30 行清零，第 31、32 行填名字指针和长度，第 34 行调协议，目标是重生端点（2 号，通信头文件第 61 行），调用号是查找（请求基址十六进制 700 加 8，见第 463、474 行）。第 34 行到第 37 行处理成功：把回复的端点栏抄给调用者的端点指针，返回成功。第 39 行失败返回负一。请求载荷在通信接口头文件的第 1887 行到第 1896 行：长度、名字长度、端点、草稿地址、名字指针、子类型，回复的端点栏在载荷偏移 8 处（两个长度栏之后）。

### 2.2 反查：三问同形

打开 `minix3/minix/lib/libsys/getepinfo.c`，清零，填端点，空组字段，调服务端协议，失败直接返回负数，成功按需抄四个身份：用户、有效用户、组、有效组，回复的进程号即返回值。回复布局在通信接口头文件的 getepinfo 段：四个 32 位身份加组数，偏移 0、4、8、12。打开 `getprocnr.c`，清零，填进程号，调服务端协议，从回复读端点。三个窄 helper（取进程号、取用户号、取组号）各调一次全量查询再取一栏，组合面手法和第 09 篇的复制函数是同一个思想：老路新用，不新增调用。

### 2.3 路由：门牌定投递口

打开 `minix3/minix/lib/libsys/getsysinfo.c` 文件的第 8 行到第 32 行，一共 25 行。第 18 行到第 25 行按目标端点选调用号：进程管理、文件系统、重生服务、数据存储各一个，默认分支直接返回不支持。第 27 行到第 31 行填事项、地址、尺寸三字段，调服务端协议。调用号：进程管理 47（调用号头文件第 60 行），文件系统基址加 48（第 120 行），重生服务请求基址加 9，数据存储请求基址加 7。事项编号的含义归各家文档，路由层只管投递不管解释。

## 3 Rust 设计决策：为什么查找无缓存路由纯函数

本章解释 `os/libs/minix-sys/src/rs.rs` 文件里的每一个设计选择。先说 C 语言做法带来的问题，再说 Rust 做法如何解决问题，最后说否决掉的替代方案。

### 3.1 用无缓存查找保证重启可见

C 版本每次现查，Rust 版本同样每次现查，不加缓存。加缓存的诱惑是省往返，代价是失效策略：何时过期、谁来通知、过期窗口多长，三个问题每一个都比一次往返贵。重生服务的本职就是登记簿，问它最准。测试断言每次查找恰好一次往返，用调用计数锁死，未来有人加缓存测试会先报警。

### 3.2 用元组代替空指针选择

C 版本的反查用空指针表示跳过某项，四个身份按需抄。Rust 版本没有空指针可传，全量返回进程号加四元组，调用者用模式匹配取要的。窄 helper 不再需要：取一栏就是元组拆一栏，组合面在调用点自然形成，不需要三个函数。回复偏移按 C 布局逐字节核对，测试用四个不同值锁定，防止栏位错位。

### 3.3 用路由纯函数隔离投递决策

C 版本的路由 switch 藏在查询函数体内，测试路由必须跑传输。Rust 实现把路由抽成纯函数：端点进去，服务器加调用号出来，陌生端点直接报不支持错误。查询函数先路由再跑路，路由失败零次往返，测试数着调用次数断言。五家全覆盖：四家有去处，一家被拒绝，查号表逐项对账。

## 4 错误处理：发现路径的失败及其错误号

| Rust 情形 | 处理 | 对应的 Minix 错误号 | 选择理由 |
|-----------|------|---------------------|----------|
| 服务回复负数 | 取反为类型化错误 | 回复的绝对值 | 协议本身，不是映射 |
| 目标非四家 | 直接报告不支持 | `ENOSYS`（值 78） | C 版本默认分支同样报告不支持 |
| 查找失败 | 取反为类型化错误 | 回复的绝对值 | 无兜底地址，失败即失败 |

不支持错误复用共享类型库的现有值，无自创。路由失败在跑路之前判定，零次往返。

## 6 过渡：从找人到对账

服务发现解决的是找人问题：名字去哪查，身份去哪问，杂项信息去哪投。从下一篇开始，视角转向对账：全阶段用过的常量散在十几个头文件里，错误号、信号号、调用号、端点号，个个都要和 C 定义逐项对上。对不上就是 bug，对上了就锁死。

请继续阅读第 13 篇 `13-constants-abi.md`，它把错误号全表、信号全表、调用号全表、端点全表逐项对账，并记录每个常量在家住哪：谁是权威，谁是复述，改谁先改谁后改。
