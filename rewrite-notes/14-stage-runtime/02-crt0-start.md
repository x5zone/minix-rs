## 1 概念：为什么 main 函数不能是第一条指令

初学者常常以为程序是从 `main` 函数的第一行开始执行的。实际上在 `main` 的第一行运行之前，有一大堆准备工作必须完成：环境变量指针要发布成全局变量，程序短名要从完整路径里截出来，C 语言库的内部状态要初始化一遍，编译器和链接器收集的启动函数要按顺序运行一遍，退出时要运行的关闭函数要提前登记好。这些工作不属于任何一个应用程序员的业务逻辑，但是每个程序都需要它们，所以它们被集中放在一个叫做 C 语言运行时启动文件的部件里，传统上简称为启动文件。

启动文件分成两层。最外层是几行汇编代码，它的名字在不同系统里略有差异，在 Minix 的 64 位 Intel 版本里叫做 `__start`，定义在 `minix3/lib/csu/arch/x86_64/crt0.S` 文件里。汇编层的工作非常具体：把栈指针调整到 16 字节对齐，预留 8 字节的影子空间，把三个入口参数搬运到 C 语言调用约定的寄存器里，然后跳转到 C 入口函数。里层是 C 语言函数 `___start`，定义在 `minix3/lib/csu/common/crt0-common.c` 文件的第 144 行到第 192 行，它完成上面列出的全部准备工作，最后调用 `main` 并把返回值交给 `exit`。

这里有一个贯穿全文的关键区别：Linux 和 Redox 把参数个数、参数指针、环境指针直接放在初始栈上，入口汇编从栈里把它们挖出来；而 Minix 把这三样东西打包成一个进程字符串描述结构，只传递一个指向该结构的指针，另外再带两个加载器相关的值。这种差异不是偶然的，它来自不同的历史源头：Minix 的启动文件继承自 NetBSD，而 NetBSD 的进程状态查看工具要求描述结构常驻栈顶，启动文件顺手复用了这个结构。理解了这个源头，就不会对 Minix 为什么多一层间接感到奇怪。

本章剩下的篇幅先建立三个心智模型：入口参数的三元组模型，启动函数列表的有序运行模型，以及静态链接下动态分支消失的模型。下一章再逐行对照 C 语言源码验证这些模型。

### 1.1 入口参数的三元组模型

程序入口收到的不是参数个数和指针数组，而是三个值：清理回调函数、加载器对象描述指针、进程字符串描述结构指针。前两个值只在动态链接的程序里有意义，静态链接的程序里它们永远是空的。第三个值永远有效，指向的结构体里装着参数个数、参数指针、环境指针、环境个数。C 入口函数的第一件事就是检查第三个值是不是空指针，空指针意味着内核或者加载器没有正确布置启动信息，程序没有任何依据可以继续运行，只能立刻退出。

### 1.2 启动函数列表的有序运行模型

编译器允许程序员用特殊标记把函数登记到启动列表里，链接器把这些函数指针收集成连续的数组。Minix 的启动文件处理三个列表：预初始化列表、初始化列表、结束列表。预初始化列表和初始化列表在 `main` 之前按从前到后的顺序运行，结束列表通过 `atexit` 登记，在 `exit` 的时候运行。此外还有一套更老的构造器列表，为了兼容不支持新式数组的老工具链，运行时按从后到前的逆序运行。顺序在这里就是语义：依赖关系靠登记顺序表达，登记在前的先运行。

### 1.3 静态链接下动态分支消失的模型

C 入口函数里有一段检查动态链接器的代码：查看弱引用符号 `_DYNAMIC` 是否为空，再检查加载器对象描述的魔数和版本号。静态链接的程序没有动态段，弱引用符号的值永远是空，整个分支永远不会进入。Rust 实现里干脆不为这个分支建模，因为本运行时只支持静态链接（阶段计划里的架构演进第一项）。保留一个永远走不到的分支只会误导读者，让读者以为动态链接是本运行时的能力之一。

## 2 C 语言源码分析：入口路径上的每个文件在做什么

本章按执行顺序讲解入口路径上的全部 C 语言文件和函数。所有行号都针对当前代码库中的 Minix3 源码。

### 2.1 汇编桩：7 行指令完成的三件事

打开 `minix3/lib/csu/arch/x86_64/crt0.S` 文件的第 43 行到第 49 行：

```
_ENTRY(__start)
    andq    $~15,%rsp
    subq    $8,%rsp
    movq    %rdx, %rdi
    movq    %rcx, %rsi
    movq    %rbx, %rdx
    jmp     ___start
```

第一行是入口符号定义，同时文件第 40 行用别名机制把 `_start` 指向 `__start`，所以链接器无论找哪个名字都能找到入口。第二行的按位与操作把栈指针向下 rounding 到 16 字节的整数倍，这是 64 位 Intel 架构的调用约定要求的：每次执行调用指令的时候，栈指针在减去返回地址之前必须是 16 字节对齐的，函数内部才能安全地使用需要对齐的向量指令。第三行再减去 8 字节，是为了给调用指令即将压入的返回地址预留位置，使得跳转到 C 函数之后的栈依然满足对齐要求。最后三行搬运参数：内核或者加载器把三个入口值放在 `rdx`、`rcx`、`rbx` 寄存器里，而 C 语言调用约定要求前三个参数放在 `rdi`、`rsi`、`rdx` 寄存器里，所以需要三次搬运。最后一行是跳转而不是调用，意味着汇编桩不会再拿回控制权，C 入口函数直接继承了整理好的栈。

读者可能会问：为什么不用调用指令而用跳转指令？因为入口桩不需要返回。调用指令会压入返回地址，而这里根本没有地方可以返回——入口桩是整个进程的第一段代码，它的调用者是内核，内核不会回来取返回值。用跳转指令可以少压一次栈，保持栈的干净。

### 2.2 全局变量：环境指针与程序短名的初始值

打开 `minix3/lib/csu/common/crt0-common.c` 文件的第 77 行到第 81 行：

```c
char       **environ;
struct ps_strings *__ps_strings = 0;
static char     empty_string[] = "";
char        *__progname = empty_string;
```

`environ` 是指向环境指针数组的全局变量，初始值没有显式给出，取决于它所在的编译单元。Minix 还有另一个编译单元 `minix3/minix/lib/libc/sys/environ.c`，它把 `environ` 定义成一个特殊的哨兵值 `0x53535353`，注释里解释了选择这个值的理由：只比较低两个字节，因为不同机器的指针宽度和字节序不一样，所以四个字节都填同样的图案，保证在任何机器上比较结果都一致。启动文件的职责之一就是用描述结构里的真实环境指针覆盖掉这个哨兵值。

`__ps_strings` 是指向进程字符串描述结构的全局指针，初始值是空，入口函数会把它设置成真实地址。`__progname` 是程序短名，初始值指向空字符串，入口函数会把它设置成从第一个参数里截出来的短名。这三个全局变量的共同特点是：它们在入口函数运行之前处于哨兵或者空的状态，入口函数运行之后处于真实状态，后续的库函数和应用程序都可以直接读取它们。

### 2.3 入口函数的完整流程

同一个文件的第 144 行到第 192 行是 `___start` 函数的完整实现。我们按执行顺序逐段讲解。

第 150 行到第 152 行检查描述结构指针是不是空指针。空指针意味着启动信息丢失，函数通过 `_FATAL` 宏输出一行错误信息并退出进程。在 Minix 上 `_FATAL` 宏里的写操作是被禁用掉的（第 89 行把写操作定义成空），所以实际效果是直接退出，退出码为 1。这个细节说明启动早期的报错通道是不可靠的，程序能做的就是尽快停下来。

第 154 行发布环境指针：第 152 行保存描述结构指针到全局变量之后，第 154 行把描述结构里的环境指针复制到全局 `environ` 变量。从这一行开始，标准库里的环境变量查询函数才能正常工作。

第 156 行到第 165 行推导程序短名。代码先把 `__progname` 指向第一个参数的完整路径，然后逐个字符扫描，每遇到一个斜杠就把指针移到斜杠之后，最终停在最后一个斜杠之后的位置。举例来说，完整路径 `/usr/bin/hello` 经过这个循环之后，指针指向 `hello` 的开头。如果参数列表是空的（第一个参数就是空指针），代码保持初始的空字符串。这个循环用字节比较而不是字符解码，所以路径里即使有非文本编码的字节也不会出错，行为和 C 语言的字符串函数完全一致。

第 167 行到第 175 行是动态链接器检查。`rtld_DYNAMIC` 是一个弱引用符号，静态链接的程序里它的地址是零，条件不成立，整个分支被跳过。动态链接的程序里它非零，代码继续检查加载器对象描述的魔数和版本号，任何一项对不上就报错退出，通过之后用 `atexit` 登记加载器提供的清理回调。这个分支是本运行时明确不支持的部分，Rust 实现里没有对应的阶段，文档里保留这一节是为了让读者明白静态链接的程序为什么永远不会走到这里。

第 177 行调用 C 语言库初始化函数 `_libc_init`。这个函数本身在 `minix3/lib/libc/misc/initfini.c` 文件的第 84 行到第 119 行，它用一个静态标志保证只运行一次，依次完成辅助向量定位、栈保护初始化、线程原子操作初始化、线程本地存储初始化、线程库初始化、退出函数互斥锁初始化、环境变量红黑树初始化。其中的线程相关步骤只在多线程构建里编译，单线程的静态程序会跳过它们。

第 179 行到第 181 行运行预初始化列表，第 188 行到第 189 行登记结束列表并运行初始化列表。列表的定义在第 106 行到第 117 行，全部声明成弱引用符号，所以没有任何登记函数的程序也能正常链接，空列表的起始和结束指针相等，循环体一次也不执行。第 191 行调用 `main` 函数并把返回值交给 `exit`。从这一行开始，控制权正式移交给应用程序员的代码，启动文件的使命结束。

### 2.4 构造器兼容层的逆序运行

打开 `minix3/lib/csu/common/crtbegin.c` 文件的第 72 行到第 97 行，可以看到老式构造器列表的运行函数。它用一个静态标志保证只运行一次，注册异常帧信息，注册 Java 类（在 Minix 上永远是空操作），然后从列表尾部向头部逆序调用每个函数。逆序的原因是历史遗留的：老式列表在目标文件里是按逆序存放的，链接器拼接之后需要倒着运行才能恢复登记顺序。新式数组没有这个问题，所以按正序运行。

## 3 Rust 现状与接线时的设计准则

入口链现在完整地住在 `os/libs/minix-rt/src/crt0.rs` 里。`_start` 是一个裸汇编桩：x86-64 上只整理栈对齐（`and rsp, -16`），把内核交来的 `RBX`（`ps_strings` 指针）装进第一参数寄存器，然后调用出生函数。C 版本的三个入口值寄存器（`rdx`、`rcx`、`rbx`，见 2.1 节）里，只有 `RBX` 需要搬运——另两个槽位在静态链接的进程里恒为零，是 C 历史遗留的占位。

出生函数 `rt_birth` 按六个有名字的阶段走完第 1、2 章讲过的全部步骤：描述结构检查（空指针即 `ENOEXEC`，C 的 `_FATAL` 语义）、分配器单次守卫（C `_libc_init` 的角色）、内核信息页查询（失败不致命，`main` 自行裁决）、发布（描述结构与程序短名写入进程级静态量，此后访问器才有真值）、调用 `main`、把返回值交给 `minix_sys::exit`。阶段顺序就是依赖关系，每段在代码里有独立的名字与注释锚点；这条链已经由 `rt-birth` 真机通电验证（argv 接收、内核信息读取、短名扫描都在真机上走过）。

发布之后，应用程序通过一组访问器读进程字符串，它们就是 C 全局变量（`__progname`、`argv`、`environ`）的 Rust 等价物：`progname()` 返回短名字节，`argv_count()`/`argv_bytes(index)` 逐个读参数，`env_count()`/`env_bytes(index)` 逐个读环境，`args()`/`envs()` 一次给出全部字符串的迭代器。所有访问器返回借用的字节切片——不做 UTF-8 检查，不做拷贝，不碰分配器——因为在出生链早期分配器可能尚未就绪，而环境字符串的本质就是字节，直到某个命令决定把它们当文本。迭代器逐槽走 `ps_strings` 的指针数组（与 C 的 `argv`/`environ` 数组同构），空指针槽报告缺失而不是猜测。

消费方进程自己定义入口函数，出生链按符号名把两者接在一起，签名的每一半都各自承载语义。名字必须是 `main` 且以 `#[unsafe(no_mangle)]` 导出：Rust 默认会改写符号名，改名后的定义与出生链的 `unsafe extern "Rust"` 声明对不上，链接器直接报未定义符号——这一半的失败是响亮的。返回类型必须是 `i32`：符号解析只比较名字、从不比较签名，返回 `()` 的定义照样链接成功，但函数体不会写返回寄存器，进程的退出码就是寄存器里的残留值，而且不报任何编译或链接错误——这一半的失败是寂静的。rt-birth（`os/qemu-tests/test-kernels/user/rt-birth/src/main.rs` 的 `main`，三架构真机通电验证）是这份契约的参照实现：入口不收任何参数，参数与环境一律经访问器读取（延续上一段的访问器拆分，而不是 C 的 `main(argc, argv, envp)` 三参形态）；返回值原样成为进程退出状态，经 `minix_sys::exit` 送达 PM。不在乎退出码的程序也必须返回一个具体的 `i32`（通常为 `0`），因为运行它的那一方——shell 也好，init 的 waitpid 也好——无论如何都要读一个。

本仓库曾经有一个专门的 `start.rs` 模块，把这些步骤做成了纯函数和阶段枚举。它在整个工作区里没有任何生产调用方——真实的 `_start` 从未走过它——而且它与 C 真值的偏差在无人察觉的情况下累积（自称保守的最小栈预算连辅助向量表都放不下、声称检测环境哨兵但 C 源里没有检测点）。该模块整体删除，理由是投机性设计与现实脱节的风险大于预先实现的价值：入口代码必须对着真实寄存器 ABI 写，而不是对着一套从未上过机器的纯函数写。今天的 `crt0.rs` 正是按这个教训生长出来的——每个阶段都对着 C 锚点和真机验证落地。

接线时值得保留的是本篇第 2 章的 C 分析和几条已经验证过的设计准则，读入口代码时逐条对照：

- **顺序要有名字**：入口阶段的顺序是语义（依赖靠顺序表达），实现时每个阶段应有独立命名，测试锁定顺序，而不是藏在函数体的行号顺序里。
- **哨兵比较要有名字**：环境哨兵 `0x53535353` 的比较意图（只比低两字节）应写进常量名或函数名，不散落裸十六进制。
- **字节扫描代替字符解码**：短名推导逐字节比较斜杠，保证任何字节序列与 C 行为一致。
- **列表运行器只有一个**：三类启动列表共用一个带方向的运行器，不为每个列表重写循环。
- **单次语义可拥有**：库初始化只跑一次的守卫做成可拥有的类型，测试各自新建，互不污染。
- **入口签名是契约不是习惯**：`main` 的名字、导出方式与返回类型被三个不同环节各自消费——名字被出生链的符号解析消费，返回类型被退出码消费——缺任何一半的失败形态都不一样（一个链接报错，一个静默脏退出码），写消费方时对照 rt-birth 的形状，不靠默认签名碰运气。

Redox 的 relibc 在同样的位置做过同样的事：它的启动代码对着真实的中断与寄存器约定落地，启动列表的运行思想与这里一致。共享思想，不共享代码——静态链接的 Minix 程序不需要动态加载器的重定位表解析。

## 4 错误处理：入口阶段的失败及其去处

C 入口阶段的失败只有一种处理：`_FATAL` 宏输出错误并退出（且在 Minix 上输出被禁用，实际就是直接退出，见 2.3 节），因为启动早期的报错通道本身不可靠。个数非负检查在 C 语言里不存在，因为 C 调用者默认内核不会给出负数。

未来接线的 Rust 入口应当保持同样的形状：描述结构缺失映射到 `ENOEXEC`（没有启动信息就没有合法的进程镜像），个数非法映射到 `EINVAL`（参数向量格式错误），两者的最终去处和 C 一致——尽快退出，退出码可见，路径诚实。当前入口链正是这样做的：`read_process_strings` 在解析层把两种坏描述分别映射到这两个错误号，出生函数在第一阶段遇到解析失败就走 `birth_fail`（渲染一行诊断后 `minix_sys::exit(1)`）。

---

## 5 测试：入口路径的现状

入口的纯逻辑面在 `os/libs/minix-rt/src/crt0.rs` 的测试模块里逐条对应第 2 章的 C 锚点：描述结构的解析往返（宿主内存里构造内核写入的字节布局再解析回来）、空描述的 `ENOEXEC`、负数个数的 `EINVAL`、短名扫描的斜杠边界（末尾斜杠得空名而非崩溃）、指针数组走查器的逐槽语义（`NUL` 终止扫描、空指针槽报缺失）、以及出生前访问器的哨兵契约（未发布时计数为零、迭代器为空、按索引读取返回缺失）。真机路径——裸汇编桩、出生函数的阶段顺序、退出封装——不在宿主测试的覆盖范围，由 `rt-birth` 冒烟内核在 QEMU 里验证（edge E1 的通电验收面）。

## 6 过渡：从程序入口到运行时初始化

程序入口解决的是控制流的起点问题：汇编桩如何整理栈和寄存器，描述结构如何变成环境变量和程序短名，启动函数列表在什么时候运行，主函数的返回值如何变成退出码。下一个问题是运行时状态的发布问题：内核信息页面的指针如何从内核到达用户程序，全局的通信向量表如何从默认的直接陷阱实现切换到内核发布的实现，魔数校验失败的时候全局状态应该是什么样子，错误号全局变量和线程本地存储在 64 位系统上应该如何安排。

这些问题属于进程运行时生命周期的下一个阶段：运行时初始化。请继续阅读第 03 篇 `03-runtime-init.md`，它从构造器函数的三步流程讲起，逐个讲解通信向量表的选择逻辑、错误号模型的演进、线程本地存储的两种形态，并在 Rust 侧给出显式的初始化函数和可拥有的运行时状态类型。
