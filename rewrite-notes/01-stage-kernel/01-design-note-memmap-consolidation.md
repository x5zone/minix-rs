**结论摘要**

1. `MemoryMapSource` 这条 trait 提供了接口约束与静态调用能力，但**没有消费者利用它的「来源可替换」能力**——所有调用点都显式指定具体类型，生产 UEFI 路径根本不经过它（I-28）。**冻结**。

6. **side list 定稿为 shim 内部诊断输出**：不构成跨引导边界的保留协议；成员由分配 × 映射策略决定（I-29-14，v10 修正生命周期表述）。

## 0. 背景

### 0.1 项目与三个目标架构

Minix-RS 是把 Minix3（一个微内核操作系统，内核只负责进程、消息传递、中断与底层内存，文件系统与内存管理都以用户态服务器进程的形式运行）按**语义**重写为 Rust 的实现。重写的定义是：外部可见行为、进程间通信协议、生命周期语义、调度与权限模型保持不变，内部改用 Rust 的类型系统重新表达。目标架构有三个：x86-64、aarch64（ARM 64 位）、riscv64（RISC-V 64 位）。

文中的 Rust 与系统术语，按需解释：

- **trait**：Rust 的接口定义，声明若干方法签名，由类型实现。它提供**三种**不同的东西，本文会用这张表逐条对照：

  | 概念 | 含义 | 本例是否存在 |
  |---|---|---|
  | 接口约束 | 「实现类型必须提供这些方法、签名必须匹配」。写在 `impl Trait for Type` 上，编译器会检查方法是否齐全、签名是否一致 | **存在**。`impl MemoryMapSource for DtbMemoryMap` 受这个检查 |
  | 静态分发 | 编译期确定调用哪个实现。包括以 `T: Trait` 作泛型约束，也包括全限定调用 `<Type as Trait>::method(...)` | **存在**：有两处全限定调用 |
  | 来源可替换性 | 调用方不知道、也不需要知道自己拿到哪个实现，以 `dyn Trait` 或泛型参数接收 | **不存在** |

  因此准确的说法不是「这条 trait 没有被使用」，而是「它提供了接口约束与静态调用，但**没有任何消费者利用它带来的来源可替换性**」——没有一处代码因为这条 trait 而降低了对具体类型的依赖，它也没有统一生产 UEFI 与设备树两条路径（后者见 §1.2）。
- **`'static` 生命周期**：表示这份数据在整个程序运行期内有效。引导阶段常把一块内存「泄漏」成 `'static`，因为引导代码只执行一次、之后不再释放。
- **无标准库（`no_std`）**：代码不依赖 Rust 标准库 `std`，只用 `core` 与本项目允许的组件。`no_std` 本身**不蕴涵**「没有堆」「没有线程」——是否具备动态分配或并发设施，取决于该运行环境是否提供了分配器与相应机制。本项目引导阶段（UEFI 应用）在引导服务存活期间可以分配；内核阶段自建了引导期分配器并在固定阶段后切换。

### 0.2 六条引导路径

「引导腿」指一条从固件到内核入口的具体路径。本项目有五条生产路径加一条辅助路径：

| 编号 | 架构 | 谁在跑引导代码 | 内存图从哪来 |
|---|---|---|---|
| L1 | x86-64 | 独立的引导程序 boot-shim（一个 UEFI 应用） | 读 UEFI 固件内存图并分类 |
| L2 | aarch64 | 同上 | 同上（另有可选的设备树越界校验） |
| L3 | riscv64 | boot-shim 的 RISC-V 变体，由 U-Boot 装载 | 解析设备树的内存节点 |
| L4 | riscv64 | 内核自身（固件直接把控制权交给内核镜像） | 解析设备树的内存节点 |
| L5 | aarch64 | 内核自身 | 解析设备树的内存节点（不裁剪固件前缀） |
| A1 | x86-64 / aarch64 | boot-shim 的一个**辅助**入口，仓库内零调用方 | 读 UEFI 固件内存图并分类（另一份实现） |

「设备树」（device tree，缩写 DTB）是固件交给操作系统的一份二进制数据结构，描述硬件布局，其中 `/memory` 节点列出物理内存区间。UEFI 是 x86 与 ARM 服务器/虚拟机上常见的固件接口标准。

### 0.3 UEFI 的 `ExitBootServices` 与 MapKey

UEFI 固件启动时提供一套「引导服务」（Boot Services），包括读文件、分配内存、输出到控制台。操作系统内核一旦准备好接管硬件，必须调用 `ExitBootServices` 退出这套服务；调用之后这些服务全部失效。

`ExitBootServices` 要求调用方传入一个 **MapKey**。MapKey 由 `GetMemoryMap`（读内存图）返回，它能被固件用来判断内存图是否过期。

准确的规范表述是这样（v2 的写法容易被误读成「MapKey 是内存图内容的哈希」或「两次读图必然不同」，此处按评审意见改写）：

> 分类器必须处理**取得该 MapKey 的同一次 `GetMemoryMap` 所返回的描述符快照**，并把这次读取取得的 MapKey 用于对应的 `ExitBootServices`。若 MapKey 失效，必须重新获取快照、重新分类，再用新 MapKey 重试。**成功退出所对应的那份内存图**才是交接结果的依据。

关键推论（v4 的表述过宽，此处按第四轮评审收窄）：**凡是会导致内存图中某段物理区间的类型或范围发生变化的分配，都不会反映在更早的快照里。** 「一次分配」不等于「一次内存图变化」——`AllocatePool` 可能从既有的池页里切一块出来，那种情况下内存图不变（§2.5.1）。

### 0.4 内存图交给内核之后怎么用

内核拿到内存图后，把它当作两份语义不同的清单：

| 清单 | 语义 | 内核侧消费方 |
|---|---|---|
| 可用表 | 可以自由分配的物理内存 | 物理内存管理器：从这个池子里取页帧，分配给进程 |
| 保留表 | 可以访问、但**不得再分配出去**的物理内存 | 建立「直接映射」（Direct Map，一种把全部物理内存线性映射到内核虚拟地址区的机制）：运行期要能通过它读写这些页，但它们已经被别的用途占着 |

这两份清单最终被放进一个名为 `KernelInfo` 的交接结构，由引导侧交给内核。所有引导腿交付的结构同形：两个列表，语义如上表。

### 0.5 测试的两个层次与持续集成的实际覆盖面

1. **宿主单元测试**：在开发机上直接编译运行，不需要虚拟机，用构造的输入调用纯函数。数量以千计，是主要的逻辑防线。
2. **QEMU 集成测试**：在虚拟机里真正跑一遍固件与内核。又分两种形态：
   - **测试内核**：一个比真内核小得多的 UEFI 应用，调用真内核的若干函数（如建页表、开分页）后打印 `PASS`。仓库里有 39 个这样的测试内核包。
   - **真链路冒烟**：用真实的 boot-shim 加真实内核镜像，起虚拟机，检查串口输出的若干「路标」是否按序出现，直到内核进入调度器。

这两类测试的**分工**在本文里很关键：测试内核检查「内核侧的消费者」，真链路冒烟检查「引导侧到内核的整条通路」。而「分类结果本身对不对」这件事，两类测试都只做了一半——详见 §2.4。

## 1. I-28：一条自称「唯一语义出口」的 trait，生产路径一次也不经过

### 1.1 事实：这条 trait 是什么、谁在用它

trait 定义在 `os/libs/minix-boot/src/memmap_source.rs`，只有一个方法（完整摘录见 §6.1）：

```rust
pub trait MemoryMapSource {
    /// Return the two `'static` tables `(conventional, reserved)`.
    fn collect(&self) -> (&'static [MemoryRegion], &'static [MemoryRegion]);
}
```

该文件顶部的模块注释写着（逐字引文）：

> `MemoryMapSource` — the single semantic exit for the memory map of all three boot chains.

以及：

> every boot chain exposes the **same** shape to the OS semantic layer — two `'static` tables, conventional (the PMM may allocate from it directly) and reserved (touched through the Direct Map at run time but never reallocated).

三个实现：

| 实现 | 位置 | 行为 | 消费者 |
|---|---|---|---|
| `DtbMemoryMap` | `os/libs/minix-boot/src/memmap_source.rs` | 解析设备树 `/memory` 节点的 `reg` 属性，按需裁掉固件常驻区前缀 | L3、L4、L5 三条腿**生产使用**；L2 另有一处调用，用途是拿设备树校验固件快照是否越界，不产出内存图 |
| `UefiMemoryMap` | `os/boot-shim/src/uefi_helpers.rs` | 转调 `build_memmaps()` | 仅 `UefiBootShim::prepare_boot`（辅助入口 A1），该函数**全仓零调用方** |
| `MultibootMemoryMap` | `os/libs/minix-boot/src/memmap_source.rs` | 直接返回 `(&[], &[])`（两个空表） | **无任何引用** |

`MultibootMemoryMap` 的文档注释自己说明了它是占位（逐字引文）：

> Placeholder for the BIOS/Multiboot leg: this repository has no such boot form yet, and the empty-table implementation keeps the trait complete; give it a real implementation when the form appears (do not change contracts early for elegance).

**关于「零调用方」的取证方式**：全仓检索 `UefiBootShim`，命中项全部是文档注释，其中若干出现在三个测试内核的头部注释里，内容恰恰是解释**为什么不用它**——因为测试虚拟机的可启动分区里只有测试内核自己，没有真实内核文件 `/EFI/minix/kernel.elf`，而 `prepare_boot` 的第一步就是去读这个文件。也就是说，这些注释不是调用点，而是「不用它」的理由。

**关于「没有来源可替换性」的取证方式**：全仓检索 `dyn MemoryMapSource`、`T: MemoryMapSource`、`: MemoryMapSource>` 三种写法，零命中。该符号在代码里的全部出现形式是：四处定义与实现（trait 本体加三个实现）、一处库内再导出、四处 `use ... MemoryMapSource as _;`（只为把方法引入作用域）、两处全限定调用 `<DtbMemoryMap as MemoryMapSource>::collect(...)`、一处具体类型的方法调用 `UefiMemoryMap.collect()`。没有任何一处以「不知道自己拿到的是哪个实现」的方式使用它。

### 1.2 事实加推理：为什么生产 UEFI 腿接不进这条 trait

生产 UEFI 入口是 `os/boot-shim/src/main.rs` 的 `fn main`，它调用 `prepare_and_enter_kernel_image`，后者在内存图这一步调用 `ebs_pair::pair_and_classify`，分类逻辑在 `os/boot-shim/src/ebs_map.rs` 的 `fn classify_map`。整条路径不经过 `MemoryMapSource`。

以下是三条结构原因，每条都是代码事实（关键代码见 §6.2、§6.3）：

**原因一：MapKey 配对。** `pair_and_classify` 的签名里显式接收固件入口地址与调用约定，内部流程是：读内存图 → 取得 `map_key` → 分类 → 用**同一个** `map_key` 调 `exit_boot_services`。代码里有一处测试替身把这个配对写死：替身的退出函数会断言传入的键等于最近一次读图得到的键（断言消息为 `EBS must use the current map key`）。§0.3 解释了为什么必须如此。而 `collect(&self)` 既不接收也不返回任何键，也不做退出——这个配对无处安放。

**原因二：分类结果必须直接写进交接区。** 生产路径不返回 Rust 切片，而是把分类结果**直接序列化**进一块固定布局的交接区（arena）的两个分区，写入走 `serializer.push_memmap(...)` / `serializer.push_reserved(...)`，每次调用同时写「线上分区」与「语义工作分区」两份（§6.3）。理由不是 v2 写的那句「两个二进制地址空间不同」——那太绝对：boot-shim 与内核镜像可能共享同一物理地址空间。准确的理由是（按评审意见改写）：

> Rust 切片包含指针与长度，其表示方式与生命周期都不属于稳定的跨镜像协议格式。本项目的 `KernelInfo` 选择固定布局、基址加偏移的交接表示，以避免交接内容依赖 shim 运行期的指针值与 Rust 类型布局。

**原因三：失败面是一个循环。** 读内存图可能因缓冲区不足要求扩容（`BUFFER_TOO_SMALL`），退出可能因 MapKey 过期被拒（`EFI_INVALID_PARAMETER`），两者都要重试，且重试次数有上限、失败一律 fail-closed（不沿用旧的分类结果）；重试前还要清空已写入的两份分区（`reset_map_partitions`）。`collect(&self) -> (两张表)` 是无失败签名，表达不了这个循环。

**推理（可能有别的解释，请评审者判断）**：这三条不是「暂时没接」，而是接口抽象层次选错了——`collect` 抽象的是「值从哪来」（数据来源），而生产路径的约束全在「什么时候能产出、产出到哪去、失败了怎么办」（控制流与存储位置）。后者是固件协议强加的，不随实现变化，因此不适合再抽象一层。

评审补充的一条原则本文采纳并作为 I-28 的设计前提：**UEFI 与设备树的内存图获取机制不同，不是一个需要消除的结构问题**。UEFI 有 MapKey、退出、重试事务；设备树路径没有这些约束。真正应当统一的，是交给内核的内存语义（两张表的形式与含义），而不是固件的获取过程。

### 1.3 事实：这条 trait 现在实际承载了什么

- 一条**文档价值**：模块注释里那段「conventional 可直接分配 / reserved 可访问不可分配」的语义约定，是本文 §0.4 那段话的唯一成文出处，写得准确且有用；
- 一个**具体实现的复用**：`DtbMemoryMap` 一个具体类型服务了 L3、L4、L5 三条腿加 L2 的一处校验。这是真实收益，而且不小；但它属于「同一个结构体加同一个函数」带来的实现复用，**不属于 trait 的多态价值**；
- **trait 的三个实现里，`DtbMemoryMap` 有真实调用方，但调用方均显式指定具体类型；另外两个实现没有真实消费者**（v2 曾写作「三个零多态消费者成员」，容易被误读成连 `DtbMemoryMap` 也没有调用方，此处按评审意见改写）。

也就是说，模块注释承诺的「三条链的唯一出口」，实际兑现的是「设备树那一路的共用实现」。

### 1.4 推理：判据不是「没用到」，而是「来源可替换性无人利用」

v1 曾把「将来可能出现第三种来源」列为保留 trait 的理由。评审指出这条论证是循环的，本文接受，把未来扩展降为次要因素。判断当前状态要分清两种依赖（评审提出的区分，本文采纳）：

| 依赖形式 | 是否存在 | 说明 |
|---|---|---|
| 调用方依赖 trait 作为方法调用接口 | **是** | 两处全限定调用 `<DtbMemoryMap as MemoryMapSource>::collect(...)` 明确依赖这条 trait |
| 调用方依赖 trait 带来的来源可替换能力 | **否** | 没有一处代码可以在不知道具体类型的前提下使用不同实现 |

配合另外两个问题：

1. **抽象是否降低了调用方的类型依赖**：没有。`DtbMemoryMap` 的四个使用点全是具体类型。
2. **抽象是否统一了它宣称要统一的两侧**：没有。生产 UEFI 侧根本不进来，且原因不是工作量（§1.2）。

保留的必要性因此只剩两点：

- **删除动的是已裁记录。** 这条 trait 的引入有编号可查的裁决记录（I-22），记为「代码已落地」。评审建议：不要为了避免触碰它而选择保留，而是**另立一条 superseding 裁决**，写清当时为什么引入、假设的消费者与实现有哪些、哪些假设没有兑现、本次为什么撤销或收窄。本文采纳，把六问写进 §5.1。
- **语义文档不能随代码一起消失。** 见 §1.5。

### 1.5 推荐方向：删除 trait，保留语义契约（方向已由评审批准）

具体动作（作为裁决要素，不是实施指令）：

1. `DtbMemoryMap` 保留为具体类型，`collect` 改为它的固有方法；
2. 删除 `MultibootMemoryMap`；
3. 删除 `UefiMemoryMap`——但以 I-29 对辅助入口 A1 与 `build_memmaps` 的最终处理为前提（若 I-29 决定保留某个测试专用入口，这里的删除范围要相应调整）；
4. 把「可用表 / 保留表」的语义约定搬到真正定义交接协议的数据结构文档里——`KernelInfo` 的两个字段，或一个共享的内存图结果类型；
5. 修正模块注释，不再宣称「所有引导链的唯一出口」。

| 方案 | 做法 | 收益 | 代价与风险 |
|---|---|---|---|
| **A. 删除 trait（已批准方向）** | 见上五步 | 代码与注释不再宣称不存在的能力；读者不会误以为接新来源只需实现一个 trait；少两处无消费者代码 | 需正式 supersede I-22；若将来真出现第二种具备真实消费者的来源，需要重新设计（那时的接口形状多半也不同） |
| B. 保留，重定位 | 保留 trait，注释改为如实描述「它是设备树各腿的实现收敛点」 | 零代码改动；文档与事实一致 | 零载荷抽象继续留在公共 API；`MultibootMemoryMap` 返回空表这一「实现」仍在。已否决 |
| C. 真正接线 | 让生产 UEFI 腿也走 `MemoryMapSource` | 兑现模块注释的承诺 | 需把 MapKey、分区写入、重试循环塞进签名，与 §1.2 三条约束冲突。已否决 |
| D. 折中 | 只删 `MultibootMemoryMap`，按 B 改注释，语义文字下沉 | 去掉最无争议的空占位 | 不解决「来源可替换性无人利用」的根本问题 |

**空表占位的危害要单独说**：一个返回**合法空表**的占位实现，比一个明确「未实现」的实现更危险——它通过类型检查、通过编译，运行起来给出「零可用内存」而不是明确失败，症状会在启动后期以「无处分配页帧」的形式出现。评审的判据本文完全同意：必须预留时，应让未实现状态**显式失败**（panic 或返回错误），而不是返回一个看似合法的空值。

**重新引入 trait 的判据**：当**第二种真实内存来源出现**，且**存在一个实际消费者需要在不依赖具体来源类型的前提下使用它们的共同语义**时，再按真实差异设计。不要为一个尚不存在的引导形态预先冻结接口。

## 2. I-29：内存图分类有两份实现，而测试路径拿到的内存图并不完整

### 2.1 事实：两份实现并存

| 实现 | 位置 | 谁调用 | 输入形态 |
|---|---|---|---|
| `fn classify_map` | `os/boot-shim/src/ebs_map.rs` | 生产路径（L1、L2），经 `pair_and_classify` 调用 | **裸字节缓冲 + 描述符元数据**，自己解析、自己校验 |
| `fn build_memmaps` | `os/boot-shim/src/uefi_helpers.rs` | 辅助入口 A1（零调用方）；14 个测试内核经单数形式 `build_memmap()`（它就是 `build_memmaps().0`） | 第三方 `uefi` 库已解析好的内存图对象 |

两份都做同一件事：在一份固件内存图上按类型标签分流，产出可用表与保留表。分流规则**逐条相同**：

1. 类型为 `CONVENTIONAL`（固件声明的常规可用内存）→ 可用表；
2. 类型为 `MMIO` 或 `MMIO_PORT_SPACE`（设备地址窗口）→ 丢弃；
3. 其余类型且**起点低于 RAM 顶** → 保留表；起点不低于 RAM 顶 → 丢弃。

「RAM 顶」指所有 `CONVENTIONAL` 区间的最大末端地址。计算它需要单独一遍扫描，因为固件返回的描述符不按类型排序。两份实现都这么做。

### 2.2 事实：两份实现的校验与诊断行为不同

| 检查项 | `classify_map`（生产） | `build_memmaps`（测试实际调用） |
|---|---|---|
| 描述符版本 | 拒绝非预期版本（`UnsupportedVersion`） | 无显式检查（解析交给第三方 `uefi` 库） |
| 描述符尺寸 | 拒绝小于最小前缀（`DescriptorTooSmall`）与未 8 字节对齐（`DescriptorSizeNotAligned`） | 无显式检查（同上） |
| 缓冲区边界 | 拒绝图长超出缓冲（`MapSizeBeyondBuffer`）、长度不是描述符步长的整数倍（`MapSizeNotMultiple`） | 无显式检查（同上） |
| 页数为零 | 拒绝（`ZeroPageCount`） | 不判，会产出一条长度为 0 的区间 |
| 乘法与加法溢出 | `checked_mul` / `checked_add`（`LengthOverflow` / `RangeOverflow`） | 直接算 `phys_start + page_count * 4096` |
| 物理地址上限 | 拒绝整段越过 `pa_limit`（`OutOfPhysRange`） | **完全不判** |
| 大块保留段诊断打印（**诊断，非校验**） | 无 | 有（对页数 ≥ 1024 即 ≥ 4 MiB 的条目打印原始类型与地址） |

读这张表有两个口径要说清：

- 右列「无显式检查」指的是**这个函数自身不做**，不等于整条调用链没有校验——`build_memmaps` 消费的是第三方库解析好的对象。但那些校验的判据与归属属于第三方库，与生产路径自建的六项不可比；尤其是「物理地址上限」，第三方库完全不知道本项目的页表能表达多少位物理地址。
- 最后一行是**诊断打印**，不是输入校验，不计入校验项。

表格里最刺眼的一行是「物理地址上限」，配一个位置上的巧合更清楚：`const PA_LIMIT` 就声明在同一个文件 `os/boot-shim/src/uefi_helpers.rs` 里、`build_memmaps` 之后约二十行处，它的文档注释写着「这个常量防止分类器拒绝高地址 DRAM 描述符」——而 `build_memmaps` 自己不使用它，使用它的是生产路径传进 `classify_map` 的那个参数。同一个文件、相邻的两段代码，一个用这个常量、一个不用。

另外，`classify_map` 有一条刻意的不对称：它**只校验将被写出的条目**。代码注释给了理由（逐字引文）：

> a high non-conventional descriptor above `ram_top` is dropped by the filter below; fail-closing the whole map on its geometry would turn a legitimate firmware hole into a boot failure.

意思是：RAM 顶之上的非常规内存段反正会被第 3 条规则丢掉，为一个已知会被丢弃的条目判定整张图非法，会把本来正常的固件空洞变成启动失败。这是一条经过权衡的设计，`build_memmaps` 里没有对应表达。

### 2.3 事实：两条腿的「读图次数」与「分类对应的时刻」不同

v1 把这条写成「MapKey 不配对，两份内存图可能不一致」，并在待验证里承认没读第三方库。第二轮评审要求拆层并核实。本轮读了依赖源码（版本见 §6.4），结论如下。

**事实一：第三方库的退出函数自己会重读一次内存图，并在读之前做一次池分配。** 依赖 `uefi` 0.33.0（`os/Cargo.lock`）的 `exit_boot_services` 流程是：

1. 先建缓冲：`MemoryMapBackingMemory::new(memory_type)`，内部调用 `boot::memory_map_size()` 与 `boot::allocate_pool(...)`——**一次内存分配**；
2. 进入最多两轮的循环，每轮调 `get_memory_map_and_exit_boot_services`，其内部先 `get_memory_map(buf)` 取得**新的** `map_key`，再用这个新键调 `exit_boot_services`；
3. 成功时返回 `MemoryMapOwned`（内含那块缓冲）；两轮都失败则冷复位。

**事实二：因此辅助入口 A1 上至少发生两次 `GetMemoryMap`。** `build_memmaps` 一次（分类所依据的那份），退出前一次（退出所依据的那份）。第二次读之前多了「退出缓冲」这一次池分配。

**事实三：生产路径只有一次读图用于两件事，并且读图与退出之间没有任何分配。** `pair_and_classify` 内读图取得 `map_key` → 分类（只往 arena 写，不分配）→ 用同一个 `map_key` 退出；重试时（`EFI_INVALID_PARAMETER`）重新读图并**重新分类**，先清空已写分区再写。缓冲扩容也发生在读图**之前**（循环顶部就分配缓冲）。

**待验证**：两次读到的描述符内容差多少。可以确定的是至少多出一条 `LOADER_DATA`（退出缓冲）；此外 `build_memmaps` 自己的 `Vec` 分配与两块泄漏出去的切片也发生在它拍快照之后（见 §2.5）。本文没有在真机上比对两次快照的完整差异。

**风险判断**：

- **不会导致退出失败**。旧 MapKey 失效时，退出函数自己会重读，所以这条腿不会因键过期而失败。
- **不能断言「两份内存图不一致」**。调用两次读图函数不等于拿到两张不同的图；且两者之间没有构造性的对应保证，只能说「分类结果与最终退出所用的键之间没有结构上的配对」。
- **真正的后果是可定位的**：分类所依据的快照早于若干次分配，因此那些分配占用的页在分类结果里仍被列为**可用内存**，而它们此刻已被占用。见 §2.5。

**影响范围（v3 已按评审意见收窄）**：

| 路径 | 快照之后的分配 | 是否调用退出 | 准确结论 |
|---|---|---|---|
| L1、L2（生产 UEFI） | **无**（所有 shim 分配都在读图之前） | 是 | 不受影响；分类快照即退出快照 |
| L3、L4、L5（设备树） | 不涉及 | 否 | 不受影响（没有键配对问题） |
| A1（辅助入口） | 输出数组、退出缓冲 | 是 | 潜在问题；目前零调用方 |
| 12 个夹具型测试内核 | 输出数组、根页表页、bump 池、退出缓冲 | 是 | **有实际问题**（见 §2.5） |
| 2 个 `test-memmap` 测试内核 | 输出数组 | 否 | **不是完全不受影响**：分类结果仍可能没有反映输出数组自身的占用；因只做弱性质断言，当前未暴露 |

v2 曾把两个 `test-memmap` 标成「不受影响」，第二轮评审指出这不准确，v3 已按上表改写。

### 2.4 事实：现有测试各测了什么（含持续集成覆盖面表）

v1 曾断言「生产分类器没有真实固件数据流过」，被第一轮评审指出与「持续集成用真实 boot-shim 启动」自相矛盾。经核实，v1 的判断是错的。

逐条核实后的覆盖面：

| 脚本 / 作业 | 架构 | 引导腿 | 是否经过 `classify_map` | 是否断言内存图内容 | 是否在持续集成里 |
|---|---|---|---|---|---|
| `qemu-tests/test-cmd-smoke.sh`（作业 `cmd-smoke`） | x86-64 | L1（xtask 装配真实 boot-shim 为 `BOOTX64.EFI` + `kernel.elf`，OVMF 启动） | **是** | 否（只断言串口路标与命令面） | **是** |
| `qemu-tests/test-cmd-smoke-aarch64.sh`（作业 `cmd-smoke`） | aarch64 | L2（同上，AAVMF） | **是** | 否（同上） | **是** |
| `qemu-tests/test-cmd-smoke-riscv64.sh`（作业 `cmd-smoke`） | riscv64 | L4（OpenSBI 直载，无 UEFI） | 否（走设备树） | 否 | **是** |
| `qemu-tests/run_all.sh`（作业 `qemu-tests`） | 三架构 | 测试内核矩阵，无真实 boot-shim | 否（用 `build_memmap`） | 仅 2 个 `test-memmap` 断言三条弱性质 | **是** |
| `qemu-tests/test-riscv64-uboot.sh`（作业 `qemu-tests`） | riscv64 | L3 | 否 | 否 | **是** |
| `qemu-tests/test-shim-bootmarks-x86.sh` / `-aarch64.sh` | x86-64 / aarch64 | L1 / L2（五路标，含交接后的高半恢复标志） | **是** | 否 | **否**（脚本自陈「不注册进 `run_all.sh`，shell 门手工跑」） |

由此得到三种证据，必须分开计数：

1. **生产分类器是否在真实固件输入上执行过**：**是**（L1、L2 的命令面冒烟门每次持续集成都跑）。
2. **生产分类器的输出是否被直接验证**：**否**。没有任何脚本断言可用表只含常规内存、保留表只含政策允许的类型、MMIO 不进入两表、或区间满足物理上限。
3. **内核消费者是否在真实内存图输入下成功运行**：**是**（能启动到调度器并跑完命令面，说明消费者在真实输入上没炸）。

准确结论：

> 生产分类器有真实固件输入上的**间接集成验证**（能启动、能跑命令面），但**没有对分类结果本身的直接断言**；断言型测试用的是非生产实现，且只验证三条弱性质。

关于最后一道门（评审意见与本文一致）：让一条重要的高半恢复检查永远依赖人工记得执行，不合适。但也不必新增两次独立启动——`cmd-smoke` 已经在真实 UEFI boot-shim 上跑到命令面，可以把五个路标里 `cmd-smoke` 尚未覆盖的项合并进它的断言列表。**待定项**：先比较两边的路标集合，只补缺失项；若确有必须独立成早期门的需求，再安排夜间或发布前运行。

其余测试盘点：

- **（a）14 个测试内核调用 `build_memmap()`**，按用途分两类：

  | 类别 | 数量 | `build_memmap()` 的角色 | 被测对象 |
  |---|---|---|---|
  | 夹具型 | 12 | 提供一份「真实的内存图」作为输入 | 分页开启、高低半切换、保护结构初始化、SMP 关机等内核代码 |
  | 断言型 | 2（x86-64 与 aarch64 各一份，名 `test-memmap`） | 被测对象本身 | 内存图 |

  夹具型的价值是真实的：它们执行生产内核的建页表与开分页代码。**现存的 12 个夹具型测试对内存图没有任何断言**——图里有什么都行，只要能启起来。目标状态见 §2.6.4：在保留「消费者测试」定位的前提下，增加「本测试自身自举分配不进入可用表」的针对性断言。两句话说的不是同一件事，不要混读。

  断言型的三条断言是：非空、总长度大于 0、至少有一条区间起始地址低于 4 GiB。**保留表一条都没测，MMIO 排除没测，RAM 顶过滤没测。**

- **（b）`classify_map` 有 12 条宿主单元测试**，覆盖：常规与保留的区分（含旧 `ram_top` 规则——该规则已判废，§2.5.7.3）、带填充的描述符步长、版本校验、描述符过小、未对齐、图长越界、图长不整除、零页数、页数溢出、地址溢出、超出物理上限、容量溢出。这些是真正的分类测试，但输入是构造的，且覆盖的是待重写的旧判据。
- **（c）消费侧有测试，产出侧没有**：内核侧有一组宿主测试覆盖「保留表如何被用于建立直接映射」（包括一条针对保留表候选取并集的测试），用的是构造输入。所以「保留表的消费者对不对」有测试，「保留表的产出对不对」没有。

### 2.5 核心发现：测试路径拿到的内存图不反映快照之后的分配

这是本文最重要的发现，也是第二轮评审认为比「两份实现重复」更严重的问题。

#### 2.5.1 三类操作发生在快照之后——但只有一类必然改变内存图

先说一个前置区分，v3/v4 在这里混了两种东西：**UEFI 内存图描述的是物理页区间的类型**，不是每个池对象的生命周期。

- `AllocatePages` 直接向页分配器要页，成功后**对应页面的类型必然改变**（常规内存被扣掉，换成请求的类型）。
- `AllocatePool` 从内存池里分配。**只有在池需要扩容时**，固件才从常规内存取页、才产生新的描述符；若池里已有足够的空闲块，内存图完全不变。

按这个区分重新列表：

| 操作 | 必然发生的事情 |
|---|---|
| `AllocatePages`（根页表页、bump 池） | **必然改变内存图内容**（相应页的类型从常规变为请求类型）；**不保证描述符数量增加**——若分配恰好覆盖某条常规描述符的全部区间，固件可以直接改写该条的类型 |
| 输出 `Vec` 的容量增长与 boxed slice 的 backing allocation（`Box::leak` 只是不再释放，本身不分配） | **不一定**改变内存图：可能来自既有池页，也可能触发池扩容 |
| 退出缓冲 `MemoryMapBackingMemory`（`allocate_pool`） | **不一定**（同上） |

v3/v4 曾把三项并列成「三类分配」，v5 收紧为「② 必然、①③ 条件」，v7 再把「必然」的宾语从「产生新描述符」改成「改变内存图内容」——描述符**数量**是否增加取决于分配位置与固件的合并行为，见 §2.5.2。

还有一处 v4 说的不够精确：`Vec::new()` 本身不分配，第一次 `push` 才分配；`into_boxed_slice()` 在容量大于长度时可能收缩（是否重新分配取决于分配器实现）。要回答的最终问题是「输出数组位于哪些物理页、这些页在快照里是什么类型」，而不是「调了几次分配函数」——这需要实测（见 §7）。

#### 2.5.2 机制示意：从常规区间内部取页可能把它分成三段

UEFI 页分配会改写固件内存图。以「从一段常规内存的内部取一页」为例：

```
分类所依据的快照：
  CONVENTIONAL [ A ─────────────────────────────────── Z ]

分配根页表页之后（固件视角）：
  CONVENTIONAL [ A ───── B ]
  LOADER_DATA  [ B ─ C ]        ← 新分配的页
  CONVENTIONAL [ C ─────────────────────────────────── Z ]
```

分类依据的是上面那张图，因此 `[B, C)` 仍然被写进**可用表**。内核的物理内存管理器此后可以从这里取帧——而它此刻正被 shim 当作页表页使用。

**这只是示意，不是断言「一定变成三条描述符」**（第五轮评审的措辞修正）：如果分配发生在区间的头部或尾部，只需要两段；相邻同类型的描述符是否合并，也取决于固件的内存图表示方式。准确的说法是：

> 从常规区间内部进行页分配，可能使原区间在逻辑上分成「分配前、分配区间、分配后」三段；实际描述符条数取决于分配位置以及固件是否合并相邻描述符。

这不影响 §2.5.1 的核心结论：`AllocatePages` 必然更新相应页的类型；`AllocatePool` 是否造成页级变化取决于池是否扩容。

#### 2.5.3 第 ① 类的自指风险是有条件的

第 ① 类不只是「泄漏了两块内存」这么简单。内核最终拿到的 `memmap` 切片，**本身就存放在那份分类输出数组里**；如果这份数组的物理页在交付给内核的那张内存图里被标为「可用」，就形成自指：内核一旦开始从可用表分配页帧，可能覆盖掉它刚读进来的内存图数据。

但按 §2.5.1 的区分，这个自指风险**是有条件的**，必须写清楚三种情形：

| 情形 | 输出数组位于 | 是否自指 | 说明 |
|---|---|---|---|
| 池未扩容，数组落在**已是 `LOADER_DATA`** 的池页里 | 快照中已标记为 `LOADER_DATA` | **否** | 该页会进保留表（若通过类型政策与属性准入），内核不会分配它 |
| 池扩容，固件从 **`CONVENTIONAL`** 取得新 backing pages | 快照中仍是 `CONVENTIONAL` | **是** | 该页进可用表，内核可能分配它 |

**v8 修正**：上表从三行收成两行。v7 的第三种情形（「池扩容，新页取自另一块非常规区域」）**不是规范允许的行为**——UEFI 明确规定 `AllocatePool` 需要扩展池时从 `EfiConventionalMemory` 取页，不存在「扩容取自非常规区域」这个分支。因此风险**更加确定**：只要扩容发生，新 backing pages 必然来自常规内存，必然落在旧快照的可用表里。真正待测的问题收窄为三个：是否扩容、扩了多少页、这些 backing pages 是否落入旧快照之后的变化窗口（第七轮评审的定性，本文采纳）。

也就是说，第 ① 类的危险在「快照之后发生池扩容」时**必然**成立（一旦扩容）。这一点目前**没有实测数据**（见 §7 的探针设计）。

12 个夹具型测试内核今天没有暴露这个问题，原因是它们不跑用户态物理内存管理器——**没有内存分配者，就没有人去踩这块地**。这不代表交接结果正确。

生产路径没有这个问题，原因见 §2.5.4。

#### 2.5.4 生产路径为什么没有这个问题：读图与退出之间零分配

生产路径的顺序（`prepare_and_enter_kernel_image`）：

1. 分配根页表页、bump 池、交接区（arena）、读图缓冲；
2. 读内存图并取得 MapKey；
3. 分类（只往 arena 的两个分区写，不分配）；
4. 用同一个 MapKey 退出；
5. 用 `assert_bootstrap_outside_memmap` 逐条断言自举分配**不在**可用表里；
6. 从 arena 分区构造交接结构，跳转。

关键在第 3 步：分类过程**不分配**，而且更重要的——**在读图与退出之间没有任何会改变内存图的操作**（分类只往 arena 写，写的是 shim 自己早先分配好的页）。因此「分类所依据的快照」与「退出所依据的快照」是同一份。

**但 v3 在这里写错了一句**：v3 说这些非常规区域「全部落进保留表」。这句话不成立——分类规则的第 3 条是「起点**低于** RAM 顶才进保留表」，边界情形见 §2.5.6。

准确的不变量应当拆成两句（第四轮评审建议的限定语已并入）：

- **成立**：所有在最终快照前已形成、并且**被 UEFI 内存图单独表示**的自举页面分配（根页表页、bump 池、arena、读图缓冲），都按固件报告的类型参与分类；且分类所依据的快照就是退出所用的快照。
- **不成立**：这些区域都会进入保留表。`ram_top` 边界会丢掉一部分，而池内部的子分配（`AllocatePool` 的块）从来不被内存图单独表示。

这条不变量是构造性的，不是靠纪律维持的——但它的射程只到「快照是同一次」，不到「保留表内容正确」。第 5 步的断言也只保证「不在可用表」。

#### 2.5.5 断言检查的是什么

`assert_bootstrap_outside_memmap(memmap, base, len)` 遍历**可用表**，只要某条区间与 `[base, base+len)` 相交就 panic。它检查的是「不在可用表」，不是「不在两张表」——这一点决定了它的语义：它防的正是「自举占用的页被交给物理内存管理器」，而不是「这些页是否被列为保留区」。

生产路径对它调用三次：根页表页、bump 池、arena。测试路径**一次都没调**。

#### 2.5.6 `ram_top` 边界：三个必须分开的命题

v4 在这里把两件事混成了一句。按第四轮评审要求拆开：

**代码事实**（§6.2 全文）：第二遍分类对非常规描述符的判断是

```rust
} else if desc.physical_start < ram_top {
```

`ram_top` 由第一遍扫描所有 `CONVENTIONAL` 区间求得，取的是**剩余**常规内存的最大末端。

**命题一：规范可能性。** UEFI 的 `AllocateMaxAddress` 只约束「分配区间的最高地址不超过输入上限」，**不规定分配器在上限之内选哪一块**。因此「根页表页落在某段常规内存的最高端」是规范允许的结果之一。这一条是规范事实，不需要平台证据。

v4 写的「分配器在不超过上限的可用区里从高地址往低取」**不是规范承诺**，是某些固件实现（如 EDK2 一类的池/页分配策略）的取向。v5 已改正。

**命题二：具体固件行为。** 在本项目要跑的 OVMF / AAVMF 上，`AllocateMaxAddress` 究竟把根页表页放在哪里、是否恰好落在某段常规内存的最高端——**需要实测或读对应固件实现，本文没有做**（§7 第 1 项）。这一条是平台事实，与命题一无关。

**命题三：分类规则后果。** 只要出现「起点恰好等于 `ram_top`」的非常规描述符，当前分类器**确实会丢弃它**：它既不在可用表，也不在保留表。这一条是代码事实，已由阅读实现确认。

如果这个形态真的出现：

```
CONVENTIONAL [ A ─────────── B ]      B = 分配起点 = ram_top
LOADER_DATA  [ B ─ C ]
```

第二遍判断 `B < B` → false → 丢弃。三个自举分配（根页表页、bump 池、arena）与读图缓冲都用同一种分配方式，因此都可能落在这个位置。

**为什么现有断言抓不到**：`assert_bootstrap_outside_memmap` 只检查「不与可用表相交」（§2.5.5）。被丢弃的条目本来就不在可用表里，所以断言照样通过。断言防的是「交给 PMM」，不是「被记录」。

**本文核实的影响范围**（第三轮评审要求的那一步，v4 已做，此处保留）：

| 消费方 | 是否依赖「自举分配出现在保留表」 | 核实结果 |
|---|---|---|
| 内核建立直接映射（`dm_coverage` 的 source 4 = `reserved_regions`） | 表面上依赖 | **实际上不依赖 root/bump**：`bootstrap_tree_candidates`（source 2）用另一个来源单独登记根页表页与 bump 池——交接携带的根页表物理地址，加 `boot_alloc` 记录的 bump 区间；跨镜像路径经交接信封的 bump 三元组恢复（§6.8） |
| 同上，arena | 依赖 | **不依赖**：arena 在切根前经恒等通道读取并深拷贝进内核 `.bss`，此后不再访问 |
| 同上，读图缓冲 | 依赖 | **不依赖**：内核从不访问它 |
| 物理内存管理器 | 依赖 | **不依赖**：被丢弃的条目不在可用表里，因此不会被分配出去（这一点反而安全） |
| 任何「按保留表枚举 shim 占用」的未来消费者 | 依赖 | **会漏**：这是真正的风险面 |

**结论（三层）**：

1. **未发现功能性故障**。root/bump 由 source 2 覆盖，arena 与读图缓冲不需要直接映射。
2. **成文不变量是错的**。「非常规且低于 RAM 顶的区间会进保留表」这句话在边界上为假。
3. **现有单元测试没有覆盖这个边界**。12 条宿主测试里有一条覆盖「RAM 顶之上丢掉」，没有一条覆盖「起点恰好等于 RAM 顶」。

**不批准直接的修法**。第四轮评审明确反对把 `<` 改成 `<=`，本文接受，理由：`<=` 只是把「边界上的所有非常规类型」都放进保留表，并没有证明这些地址都是适合建立直接映射的 RAM。在类型语义（§2.5.7）还没定清之前改边界，会把「类型不明」的问题伪装成「地址包含」的问题。

**真正的修法方向（v7 定稿）**：`ram_top` 既不能当准入门槛，也不能当结果裁剪——类型政策落地后**从分类器中删除**，理由与撤回过程见 §2.5.7.3。

##### 2.5.6.1 `ram_top` 的问题比「边界差一位」更深

第五轮评审指出，`desc.physical_start < ram_top` **只检查起点**。它既不证明整个描述符位于常规内存包络内，也不证明它与任何常规区间有实际交集。三种形态足以说明它不是可靠的 RAM 判定：

**形态一（起点等于边界，被丢弃）**

```
CONVENTIONAL [ A ─────────── B )      ram_top = B
LOADER_DATA                 [ B ── C )
```

`B < B` 为假 → 整个描述符被丢弃。这是 §2.5.6 正文讨论的情形。

**形态二（起点在边界内、尾部越界，整段收下）**

```
CONVENTIONAL [ A ───────────────── B )      ram_top = B
LOADER_DATA          [ X ───────────────────── C )    X < B < C
```

判据只看 `X < B` 为真 → **整段 `[X, C)` 都进保留表，包括越过 `ram_top` 的那一段**。当前代码不做任何截断。也就是说，保留表可以包含超出「最高常规末端」的物理地址——这与「只在 RAM 包络内映射」的直觉相反。

**形态三（包络内的非 RAM 类型，被收下）**

```
CONVENTIONAL [ A ────── B )        [ C ────── D )
RESERVED              [ B ──── C )
```

`RESERVED` 的起点低于 `ram_top`，因此进入保留表——尽管它可能代表不应访问的系统保留区。这类问题与边界无关，是「用地址代替类型」的直接后果（§2.5.7）。

结论（第五轮评审的定性，本文采纳）：

> `ram_top` 不是严格的 RAM 包络，也不是实际 RAM 区间集合，而只是一个基于「最大常规末端」的**起点过滤启发式**。

因此两个方向都被排除：既不能改成 `<=`（那只改变形态一的处置，形态二、三依旧），也不能继续把它当可靠的 RAM 判定。「类型政策定案后作为辅助过滤」的方向曾被 v7 考虑，但已由 §2.5.7.3 正式撤回；不属于目标设计（v11 清理此残留）。

##### 2.5.6.2 `AllocateMaxAddress` 只有一种规范读法；当前减法过度保守

v5 把规范写成了「三种可能读法」，这是错的。第五轮评审指出：UEFI 规范对 `AllocateMaxAddress` 的定义只有一条——**分配区间的最高地址（uppermost address）小于或等于输入的 `Memory` 值**。它不是「起点不超过输入值」。

按这一条重新推导。设项目允许的半开区间末端为 `bound`，请求大小为 `size`，返回起点为 `base`：

| 量 | 含义 |
|---|---|
| `bound` | 项目允许的物理区间半开末端（`min(4 GiB 恒等窗口, VM DM 窗口 PA 上界)`） |
| 规范约束 | `base + size - 1 <= Memory` |
| 目标条件 | `base + size <= bound` |

要让目标条件成立，代入规范约束可得最小可行的输入：

```
Memory = bound - 1
  ⇒ base + size - 1 <= bound - 1
  ⇒ base + size <= bound        ✓
```

而当前代码传的是 `bound - size`：

```
Memory = bound - size
  ⇒ base + size - 1 <= bound - size
  ⇒ base + size <= bound - size + 1
```

这个条件**严格强于**目标条件，差额是 `size - 1` 字节。对按页分配而言（`size` 是 4 KiB 的整数倍），相当于在上界附近额外空出接近整个请求大小的空间。

**两个后果，v5 只写了第一个**：

1. **不会越界**（`base + size <= bound - size + 1 <= bound`），所以不是缺陷。
2. **可能造成不必要的分配失败**：如果上界附近恰好有一块刚够容纳请求的空闲区间，按 `bound - 1` 能分配成功，按 `bound - size` 可能找不到合格区域。这是一条 v5 没写出的实际风险。

**需要裁决**——v7 直接裁决选 A（第六轮评审建议，本文同意）：

| 选项 | 做法 | 裁决 |
|---|---|---|
| **A. 改用 `bound - 1`** | 最大化利用界内空间 | **采纳**。`bound` 已是恒等映射与 DM 窗口取最小值后的安全上界，没有理由再损失接近一个请求大小的空间 |
| B. 保留 `bound - size` | 承认这是保守策略 | 否决：没有独立的理由支持这个余量 |

A 案的整数边界证明（四个前提逐条核对）：

| 前提 | 状态 |
|---|---|
| `bound > 0` | 成立：`boot_dm_admissible_end()` 返回两个正的架构常量取最小值（4 GiB 与 `VM_DIRECT_MAP_SIZE`）；实现用 `checked_sub(1)` 兜住零值 |
| 请求大小合法（`size` 为页大小整数倍、非零） | 成立：调用点全部传页数 × 4 KiB 的常量或参数；分配前应保留页对齐校验 |
| 返回地址页对齐 | 成立：`AllocatePages` 按定义返回页对齐区间，故 `base + size - 1` 是该区间最高字节的地址，规范约束恰好落在它上面 |
| 项目的 `bound` 是半开区间末端 | 成立：`BOOT_IDENTITY_MAP_END = 0x1_0000_0000` 与 `VM_DIRECT_MAP_SIZE` 都是「到此为止不含」的常量；而 UEFI 的 `Memory` 输入是**含末字节的最高地址**。两者差一，所以传 `bound - 1`、不传 `bound` |

示意实现（**保留 `size` 参数做请求校验**——v7 的示例丢掉了原 `checked_sub(size)` 顺带提供的校验，v8 修正；工程上也可改为返回错误而非 `assert!`，取决于调用约定）：

```rust
fn bootstrap_alloc_limit(size: u64) -> u64 {
    let bound = boot_dm_admissible_end();

    assert!(size > 0);
    assert!(size.is_multiple_of(PAGE_SIZE));
    assert!(size <= bound);

    bound.checked_sub(1).expect("bound must be non-zero")
}
```

两条约束不能混淆：`size <= bound` 是「请求可满足」的必要前提校验；`bound - 1` 是 UEFI 的最高地址限制输入。规范对 `AllocateMaxAddress` 的定义是分配区间的最高地址不超过输入值。随附两条宿主单测：① `bound` 为页对齐末端时，传入 `bound - 1`；② 分配器返回的实际区间 `[base, base + size)` 满足 `base + size <= bound`。

一个术语统一（评审提出，本文采纳）：`PA_LIMIT` 与 `bound` 都应统一使用**半开末端**语义——`end > pa_limit` 这类检查的语义（「最大可用地址」还是「不可用地址上界」）必须与 `bound` 的定义一致，避免同一个「上界」在两处含义不同。

**与 `ram_top` 边界无关**：改成 `bound - 1` 不会让分配器从最高常规区间的最高端取页，也不消除 §2.5.6.1 的形态一。两者是独立问题——而后者在 v7 已随 §2.5.7.3 一并解决（`ram_top` 整体退出分类判据）。

#### 2.5.7 UEFI 内存描述符的类型、访问属性与生命周期不能压缩成二分分类

当前规则：`CONVENTIONAL` → 可用；`MMIO` / `MMIO_PORT_SPACE` → 丢弃；其余低于 RAM 顶 → 保留。代码里只定义了三个类型常量（§6.2）：

```rust
const CONVENTIONAL_TYPE: u32 = 7;
const MMIO_TYPE: u32 = 11;
const MMIO_PORT_SPACE_TYPE: u32 = 12;
```

其余全部落进 `else` 分支。按 UEFI 2.10 的类型定义（数值见 `uefi-raw` 0.9.0 的 `MemoryType`，§6.10）逐项对照：

| 值 | UEFI 类型 | 退出后的规范语义 | 当前结果 | 问题 |
|---|---|---|---|---|
| 0 | `RESERVED` | 不可用 | 保留表（若低于 RAM 顶） | **语义冲突**：保留表定义是「可访问」，这里规范说不可用 |
| 1 | `LOADER_CODE` | 引导程序代码，OS 可按需使用 | 保留表 | 保守，方向正确 |
| 2 | `LOADER_DATA` | 引导程序数据，OS 可按需使用 | 保留表 | 同上；shim 自己的占用大多在这类 |
| 3 | `BOOT_SERVICES_CODE` | 退出后可作一般用途 | 保留表 | **主动放弃可回收内存**（政策，需成文） |
| 4 | `BOOT_SERVICES_DATA` | 同上 | 保留表 | 同上 |
| 5 | `RUNTIME_SERVICES_CODE` | 必须保留 | 保留表 | 正确 |
| 6 | `RUNTIME_SERVICES_DATA` | 必须保留 | 保留表 | 正确 |
| 7 | `CONVENTIONAL` | 一般可用 | 可用表 | 正确 |
| 8 | `UNUSABLE` | **内存有错误，不得使用** | 保留表 | **语义冲突**：把它当作可访问内存是错的 |
| 9 | `ACPI_RECLAIM` | ACPI 启用前保留，之后可用 | 保留表 | 保守政策，需成文 |
| 10 | `ACPI_NVS` | 必须持续保留 | 保留表 | 正确 |
| 11 | `MMIO` | 设备窗口 | 丢弃 | 正确 |
| 12 | `MMIO_PORT_SPACE` | 设备端口空间 | 丢弃 | 正确 |
| 13 | `PAL_CODE` | 处理器相关代码，必须保留 | 保留表 | 目标平台不出现；如需支持要单独论证 |
| 14 | `PERSISTENT` | 按常规内存工作，但非易失 | 保留表 | 「暂不分配」可接受，但不是 `Reserved` 的必然结果 |
| 15 | `UNACCEPTED` | **必须先被接受才能使用** | 保留表 | **最危险**：见下 |
| `0x10`..`0x6FFFFFFF` | 标准类型之后的保留数值区（**不是** OEM 区） | 保留表 | 可能代表未来标准扩展；不得按 OEM 语义理解 |
| `0x70000000`..`0x7FFFFFFF` | OEM 保留区 | 保留表 | 语义由 OEM 定义，不能默认当 RAM |
| `0x80000000`..`0xFFFFFFFF` | OS loader 保留区 | 保留表 | 需要显式登记项目自己使用的值 |

**v5 在这里有一处事实错误，已改正**：v5 写「≥16 = OEM / OS-loader 区」，把三个不同区间混成一个。UEFI 的实际划分是上面的三段——`0x10..0x6FFFFFFF` 是标准类型之后的保留区，既不是 OEM 也不是 OS loader；OEM 区与 OS loader 区分别从 `0x70000000` 与 `0x80000000` 开始。这个区别影响分类政策：前一段可能承载未来的标准扩展，不能按 OEM 语义理解；后两段则需要项目显式登记自己认识的取值。

**三处必须改的语义冲突**：

1. **`UNACCEPTED`（15）** 是当前规则真正的危险边界。规范明确它表示尚未被接受的内存，必须先执行接受操作才能使用。把它放进「可访问、不可分配」的保留表，等于假设它可以被直接映射读取——在支持机密计算的平台上，读未接受内存会直接触发故障。当前项目没有接受机制，因此正确做法是**显式排除或 fail-closed**。
2. **`UNUSABLE`（8）与 `RESERVED`（0）** 在规范里都是「不可用」。保留表的定义是「可访问但不可再分配」，两者并不等价。把坏内存与固件保留区映射进内核直接映射，可能触发机器检查或读到无意义数据。
3. **三个未知区间**都不能默认进入普通保留表。分类器只应接受已明确支持的类型；未识别类型的默认处置必须是「不进入两张表」，并按策略记录或拒绝。

**两条无争议但需成文的政策**：

- **`BOOT_SERVICES_CODE/DATA`（3/4）与 `ACPI_RECLAIM`（9）被永久排除在物理内存管理器之外**，这是本项目的资源回收政策（早期内核选择简单与安全），不是分类规则的逻辑后果。必须写清，否则读者会以为这是规范要求。
- **`PERSISTENT`（14）** 建议的成文表述是：*当前不将持久内存纳入普通物理页分配器；在项目明确支持其内存属性、持久性与访问语义之前，不把它当作普通可用内存。* 这比「特殊类型，放进保留表」明确得多。

##### 2.5.7.1 四种处置状态，外加两个正交维度

两张表不必构成 UEFI 全部描述符的完整二分：有些区域完全可以**两张表都不进入**——那不是丢失信息，而是它们不属于普通 RAM 映射与分配的范围。

分类结果内部至少分四种处置状态（可以只作为分类器内部策略，不必立刻给 `KernelInfo` 加第三张表）：

| 处置 | 含义 | 进入现有两张表？ |
|---|---|---|
| `Available` | 普通物理内存，可交给 PMM | 可用表 |
| `ReservedMapped` | 必须保留，且项目确认可按既定属性映射 | 保留表 |
| `Excluded` | 已知不应进入普通映射与分配，当前内核无需继续处理 | 两表都不进 |
| `Special` | 必须保留其地址范围等待特殊机制，或当前直接拒绝启动 | 暂不进两表；按政策拒绝或记录 |

**v7 补充：四状态其实是两个正交维度的组合点，不是四种互不相干的内存种类**（第六轮评审指出 `ReservedMapped` 把两个问题压在同一维度）。这两个维度是：

| 维度 | 取值 |
|---|---|
| **分配策略**：这段内存能不能交给 PMM | 可分配 / 保留 / 阶段性回收 / 不可使用 |
| **映射策略**：这段内存要不要建立普通直接映射 | 普通 Direct Map / 特殊映射（如 Runtime 专用虚拟映射、设备路径）/ 不映射 |

四种状态落在这些组合上：`Available` = 可分配 + 普通 DM；`ReservedMapped` = 保留 + 普通 DM；`Excluded` = 不可使用 + 不映射；`Special` 的成员各占不同的组合（例如 `UNACCEPTED` 是保留 + 不映射）。把两个维度分开写，`RUNTIME_SERVICES_*` 这类反例才有地方放（见下）。

**v7 讨论基线政策表**（第六轮评审给出方向，本文采纳；**v8 按第七轮评审补齐 `Special` 各行的失败政策与两维度拆分**——此前 `ACPI_NVS` 一行「按实际消费者决定映射」与 `ReservedMapped` 的定义自相矛盾）：

| 类型 | 分配策略 | 普通 Direct Map | 当前不支持时的处置 |
|---|---|---|---|
| `CONVENTIONAL`(7) | 普通可分配 | 普通 DM（须通过 §2.5.7.6 的属性准入） | — |
| `LOADER_CODE`(1)/`LOADER_DATA`(2) | 保留，不进 PMM | 普通 DM | — |
| `BOOT_SERVICES_CODE/DATA`(3/4) | 保留（不回收是项目政策） | 普通 DM | — |
| `RUNTIME_SERVICES_CODE/DATA`(5/6) | 保留 | **不建普通 DM**（当前不支持运行时服务；未来支持时走 Runtime 专用映射合同） | 普通机器上正常出现——**不得因当前不调用运行时服务就拒绝启动**；保证不进 PMM 即可 |
| `ACPI_RECLAIM`(9) | 保留（第一版不回收） | 普通 DM | — |
| `ACPI_NVS`(10) | 保留，不能交给 PMM | **由是否存在 ACPI NVS 消费者决定**（当前无消费者 → 不建普通 DM；未来内核消费 ACPI NVS 时再映射） | — |
| `RESERVED`(0) | 禁止使用 | 不映射 | `Excluded` |
| `UNUSABLE`(8) | 禁止使用 | 不映射 | `Excluded` |
| `UNACCEPTED`(15) | 禁止使用（接受前） | 不映射 | **当前出现即拒绝启动** |
| `MMIO`(11)/`MMIO_PORT_SPACE`(12) | 不适用 | 设备映射路径 | `Excluded` |
| `PAL_CODE`(13) | 禁止使用 | 不映射 | **当前出现即拒绝启动** |
| `PERSISTENT`(14) | 不进普通 PMM | 不映射 | **保留完整范围信息**（不能只留计数——将来实现持久内存支持时需要范围清单）；当前不分配 |
| 未知类型（三个区间） | — | — | **分类错误** |

四状态标签继续作为这些判断组合后的**文档术语**（`Available` / `ReservedMapped` / `Excluded` / `Special`），但第七轮评审的提醒成立：**不要急着把四状态变成代码里唯一的枚举**。`Special` 本身不是一个具体的分配或映射策略——它把「需要特殊机制」和「当前不支持」压在了一起，有重演 `reserved` 语义混合的风险。代码中真正承载政策的是三个独立判断：分配策略、映射策略、支持状态；四状态只是它们组合后的解释性标签。不需要为此设计多层 trait，把政策表写清楚即可。

与 v7 的三处差别：`ACPI_NVS` 的普通 DM 从「按消费者决定」改为**显式写成由消费者存在性决定**（消除与 `ReservedMapped` 定义的矛盾）；`RUNTIME_SERVICES_*` 明确「普通 UEFI 机器上正常出现，不得因不支持而拒绝启动」（规范要求工作状态与指定睡眠状态下保持，但不必然进项目的普通 DM）；`PERSISTENT` 从裸 `Special` 改为「保留完整范围信息 + 当前不分配」。

「存在即拒绝启动」（`UNACCEPTED` / `PAL_CODE`）与本文 §1.5 对空表占位的批评是同一个原则：在边界处大声失败，好过在深处静默出错。`UNACCEPTED` 出现意味着平台超出项目当前能力——这种事实应当终结启动，而不是被压缩成一个计数。

##### 2.5.7.2 本文的两点判断：一条被第六轮评审推翻，一条需要补前提

**判断一（v6 提出，v7 按评审细化）：`Excluded` / `Special` 必须可观测，且两者可观测的含义不同。**

`Available` 与 `ReservedMapped` 有输出位置（两张表），`Special` 与 `Excluded` 没有——描述符会从输出里消失。但两者的正确处置不一样：

- **`Excluded`（已知可安全排除）**：允许排除并统计。最小返回信息（全部走返回值，零分配，诊断数组用固定容量）：

  ```
  excluded_descriptor_count / excluded_total_bytes
  special_descriptor_count / special_total_bytes
  unknown_type_count
  first_n_diagnostics: [raw_type, physical_start, number_of_pages, attribute] × N
  ```

- **`Special`（等待特殊机制）**：**不能只返回计数**。只统计「发现 3 条 Unaccepted 描述符」会把地址范围丢掉——将来实现了接受机制，也无法从统计数恢复范围。因此 `Special` 要么保存完整范围清单，要么（按 v7 政策表的 `UNACCEPTED`/`PAL_CODE` 行）直接拒绝启动。

- **未知类型**：直接触发分类错误，不为「可观测性」强行允许继续启动。

**判断二（v6 提出，v7 补前提）：穷尽 `match` 的编译保护有前提，v6 的写法不成立。**

v6 说「把 `u32` 转成项目枚举再 `match`，新增标准类型会变编译错误」。第六轮评审指出这有个漏洞：若转换写成

```rust
match raw_type {
    0 => Known::Reserved,
    /* … */
    _ => Known::UnknownStandard,   // ← 新增标准类型落进这里，编译器不会提醒
}
```

那么新增的标准类型仍然落入 `_`，穷尽检查形同虚设。要真正达到目的，需要四个条件一起满足：

1. 对当前支持的标准类型定义明确的 `KnownMemoryType` 枚举（0–15 各一个变体）；
2. 从原始 `u32` **安全地**转换（返回 `Result` 或显式分类），不得把未知数值直接转成枚举；
3. 分类函数对 `KnownMemoryType` 做**无通配分支**的穷尽 `match`；
4. 未知数值单独携带原始值，按拒绝/排除政策处理——并且按 §2.5.7.1 的政策表，未知类型就是分类错误。

这样，更新上游类型定义、把新标准类型加进 `KnownMemoryType` 之后，分类函数里的遗漏才会变成编译错误。另按评审的用词修正：`0x10..0x6FFFFFFF` 应称「**未分配／保留数值范围**」，不要称为「未来标准类型集合」——规范没有承诺这个区间将来一定变成标准类型。

**判断三（v6 提出，v7 撤回）：`ram_top` 改「结果裁剪」不成立。** 撤回与理由单独成节，见 §2.5.7.3。

##### 2.5.7.3 撤回：`ram_top` 既不能当准入门槛，也不能当结果裁剪——应从分类器中删除

**v7 撤回 v6 的判断三。** v6 提议「先按类型得到集合，再用 RAM 包络对结果做区间裁剪」。第六轮评审的反驳成立，而且关键在于：**v6 从来没有说清楚 RAM 包络用什么数据构造**。只有两种可能，两种都错：

**若包络 = Conventional 区间的并集，结果恰恰相反。** 考虑最普通的分配：

```
分配前：  CONVENTIONAL [ A ─────────────────────── Z )

分配后：  CONVENTIONAL [ A ───── B )
          LOADER_DATA              [ B ── C )
          CONVENTIONAL                  [ C ───── Z )
```

把 `LOADER_DATA [B,C)` 归入 `ReservedMapped`，再与 Conventional 并集求交：

```
[B, C) ∩ ( [A,B) ∪ [C,Z) ) = ∅
```

**刚刚分配出来、最需要被正确保留的根页表页，反而被裁掉了。** 这不是边界巧合：`AllocatePages` 本来就会把页从 Conventional 区间移走（§2.5.2），所以「刚分配的自举内存」与「Conventional 并集」天然不相交。v6 的提议在最重要的用例上恰好把要保护的东西毁掉。

**若包络 = `[0, ram_top)`，也不成立。** 两个理由：

1. 它不证明区间内每个地址都是 RAM——形态三（包络内的 `RESERVED`）依旧；
2. 它会丢掉合法的高地址内存：若高地址 RAM 已被固件或引导镜像占用，剩余 Conventional 只存在于低地址，则 `ram_top` 只反映**剩余可用内存**的最高末端，不代表**系统 RAM** 的最高地址。用前者推断后者，两者没有必然等价关系。

**更深一层：UEFI 内存图本身就是比 `ram_top` 更直接的物理区域分类来源。** 规范对 `GetMemoryMap` 的规定区分了两种情况：内存图描述系统中实际存在的物理内存区域；无物理硬件支持的地址空间**不会返回描述符**；有物理硬件支持、但 OS 不应访问的区域，才必须报告为 `EfiReservedMemoryType`。因此分类器只处理实际返回的描述符，按类型政策决定去留——既不需要用 `ram_top` 推断地址空洞，也不应把未报告的地址空间擅自补进普通内存映射。一个数据点上的确认不能推广：QEMU i440fx 的 192 MiB 空洞确实被报告为 `RESERVED`（§2.2），但「所有芯片组空洞都被报告为 `RESERVED`」不是规范保证。

**v7 结论（采纳第六轮评审的建议）**：

> 类型政策定案后，**从 UEFI 分类器中删除 `ram_top`**，而不是把它改造成结果裁剪条件。地址维度只保留一个检查：`PA_LIMIT`（项目能否表达这个物理地址范围）——那是架构能力检查，不是 RAM 语义检查。

若将来发现某个独立、可信的物理 RAM 拓扑来源（不是 Conventional 并集，也不是 `[0, ram_top)`），可以重新评估是否需要地址过滤；在那之前，分类器的地址参数只有 `pa_limit` 一项。

`ram_top` 的历史贡献应当承认：它来自一次真实取证（QEMU i440fx 的 192 MiB `RESERVED` 空洞，§2.2），在「没有类型政策」的年代挡住了设备空洞被恒等映射。但在类型政策落地之后，它保护的东西由 `Excluded` 承接，它引入的三种形态问题（§2.5.6.1）却无人承接。删除是净收益。

##### 2.5.7.4 保留表语义的现状与定义之间的落差

字段文档把保留表定义为「运行期经直接映射可访问、但不得再分配」。对照 §2.5.7 的表，这个定义目前对 `RESERVED`(0)、`UNUSABLE`(8)、`UNACCEPTED`(15) 三类**不成立**，对 `PERSISTENT`(14) 与未知类型**未经论证**。

这不是说现有实现会立刻出错（这些类型在当前 QEMU 平台上未必出现），而是说：**保留表当前的成员集合大于它的语义定义所允许的集合**。补政策表时应当把「不满足定义的类型如何处置」一并写清。

##### 2.5.7.5 描述符的 `Attribute`：解析层事实、映射调用层事实、硬件层未知

第五轮评审指出 v5 的结论超出了证据。v5 说「所有进入直接映射的候选区域统一使用写回缓存属性」——那需要三层证据，v5 只有前一层半。本轮按三层重写，并补了三架构的页表编码事实。

| 层次 | 目前能下的结论 | 证据 |
|---|---|---|
| 描述符解析 | `Attribute` **完全没有被读取** | `RawMemoryDescriptor` 只有 `ty` / `physical_start` / `number_of_pages`（偏移 0/8/24）；偏移 32 从未访问（§6.2） |
| 映射调用 | 调用方**没有显式选择**缓存或设备属性 | 两个窗口用 `PageFlags::kernel_read_write()` / `read_write()`，不含 `NO_CACHE` / `WRITE_THROUGH` / `DEVICE`（§6.11） |
| 最终硬件属性 | **逐架构不同，不能一句话概括** | 见下表 |

三架构的缓存属性落实方式（v6 新增核实，v7 按第六轮评审进一步收紧）：

| 架构 | 机制 | 本仓现状 | v7 修正后的结论 |
|---|---|---|---|
| aarch64 | 页描述符的 `AttrIndx` 选择 `MAIR_EL1` 中的一项；`MAIR` 由内核在 `enable()` 里写成 `0xFF` | Attr0 = `0xFF` = Normal **WBWA**；Attr1 = `0x00` = Device-nGnRnE；AttrIndx 默认为 0 | **基本闭合**，但留一项待查：需确认**所有**实际直接映射叶子描述符的 `AttrIndx` 都是 0，而不是只有某一条默认构造路径如此（§7） |
| x86-64 | 缓存性由 `PAT` + 页表项的 `PCD`/`PWT`，再与该物理地址的 `MTRR` 类型共同决定有效类型 | `flags_to_pte` 从不设 `PCD`/`PWT`；本仓不编程 `IA32_PAT` | **v6 的说法超出证据，已收紧**：「PAT0 复位默认值是 WB」是处理器规范事实，但 boot-shim 运行在 UEFI 固件之后——固件可能已改写 PAT；且有效类型还要与 MTRR 组合。准确表述见下 |
| riscv64 | Sv39 的 PTE 只有 V/R/W/X/U/G/A/D；缓存性由平台级 PMA 决定 | `flags_to_pte` 只写上述权限位 | **v6 的说法过于绝对，已收紧**：Svpbmt 扩展为 Sv39 叶子 PTE 定义了 PBMT 位（62–61），可以覆盖 PMA 属性。准确说法是「**本仓当前的 Sv39 编码不使用 PBMT**」，而不是「PTE 没有缓存位」。PMA 本身是平台相关的，不是「默认 WB」 |

x86-64 的准确表述（替代 v6 的「落回默认 PAT0 = WB」）：

> 当前页表没有显式选择 `PCD`/`PWT`，PAT 选择落在 PAT0；**若** PAT0 保持复位默认 WB，**且**对应物理地址的 MTRR 配置也允许 WB，则该映射表现为 WB。这两个前提都没有被项目声明或校验——固件在交接之前可能改写过 PAT，MTRR 配置也未检查。

RISC-V 需要一条明确的项目合同（第六轮评审提出，**v8 按第七轮评审补 PBMTE 启用条件**）：

- 当前支持的 RISC-V 平台，其普通 RAM 必须具备项目要求的普通内存属性（PMA）；
- 对不满足条件的区域，不允许当作普通 RAM；
- 当前项目不使用 PBMT，普通 RAM 映射**依赖平台 PMA 提供正确的主存属性**；
- 若未来采用 Svpbmt，需要同时验证：① 处理器实现 Svpbmt 扩展；② **`menvcfg.PBMTE` 为 1**——RISC-V 规范规定 S-mode 能否使用 PBMT 由该 M-mode 位控制，为 0 时行为等同未实现；③ 若经 OpenSBI 启动，固件是否已建立相应状态；④ 页表编码与地址转换同步符合规范。不能把 PBMT 当成「强制普通 RAM 用 WB」的通用机制——它的取值只有 PMA（不覆盖平台属性）/ NC（非缓存主存）/ IO（强序 I/O）三种，**没有一个「强制 WB」的取值**，普通 RAM 的缓存性仍然依赖 PMA。

这呼应贯穿本文的原则：**三架构统一的是普通内存的 OS 语义，不是强行让三个架构拥有同一种缓存控制机制。**

对操作系统而言（评审建议，本文同意）：页表建立之前，OS 应当明确建立自己依赖的内存类型环境（读取并按需重设 `IA32_PAT`、检查 MTRR），而不是把固件当前状态当作永久合同。待核清单：① UEFI 交接时读取 `IA32_PAT`；② 读取并分析 MTRR 配置；③ 核实内核是否在某阶段重设 PAT；④ 决定是显式依赖固件状态还是自行初始化。

**因此准确的表述是**：

> 描述符的 `Attribute` 未被读取，映射调用也未显式选择缓存属性；最终硬件属性在 aarch64 上由本仓配置的 `MAIR` 确定为 Normal WBWA；在 x86-64 上**条件成立才为 WB**（PAT0 未被固件改写且 MTRR 允许）；在 riscv64 上由平台 PMA 决定而未被项目声明或校验。

**`Attribute` 不只是缓存性**。UEFI 把它定义为该区域**支持的**属性能力位（`UC` / `WC` / `WT` / `WB` / `UCE` / `WP` / `RP` / `XP` / `NV` / `RUNTIME` / `MORE_RELIABLE` 等），而且它表示「支持什么」，不是「此刻正用什么」。所以不能简单「读出来原样翻成页表标志」。第五轮评审建议的顺序本文采纳：

1. 解析并保留原始 `Attribute`（进描述符视图）；
2. 明确项目会解释哪些属性位；
3. 根据目标架构确定可表达的映射属性；
4. 对无法满足的区域明确排除、拒绝，或采用经过论证的保守策略。

**一处容易忽略的连带**：`EFI_MEMORY_RUNTIME` 是**独立于 MemoryType 的属性**。若将来要使用 UEFI 运行时服务，必须保留相应运行时服务内存，并按运行时映射要求处理带该属性的描述符——这件事无法靠「类型 = `RUNTIME_SERVICES_DATA` 就进保留表」推出。于是有两个不同的问题必须分开回答：

- 是否允许普通 PMM 分配？
- 是否需要被普通直接映射，以及以什么属性映射？

这正是 §2.5.7.1 的四状态策略想解决的：一个 `reserved` 标签回答不了这两个问题。

**本文的判断**：`Attribute` 必须进入描述符视图（第一步），但**不必要求第一版就把全部属性映射做完**。解析、政策识别、页表落实应当分三次裁决，否则这件事会拖住整个 I-29。

##### 2.5.7.6 `Attribute` 的消费决策：方案 A（仅准入校验）为第一版推荐

v6 留了一个未决问题：`Attribute` 读出来之后在哪里被消费？第六轮评审把它收敛为二选一：

| 方案 | 做法 | 对交接结构的影响 |
|---|---|---|
| **A. 仅准入校验（v7 推荐）** | 分类器检查：该区域是否支持项目的普通 RAM 映射方式；是否带项目不支持的特殊属性；是否有运行时映射等独立要求。检查通过后，输出仍然是 `{ base, len }` | **不需要改交接协议**，适合早期阶段 |
| B. 属性影响内核具体映射 | `MemoryRegion { base, len }` 不够，必须经交接协议传递每个区间的映射意图或属性类别 | 需要扩展交接协议，否则 boot-shim 读出的属性没有消费者 |

v7 推荐 A，**v8 按第七轮评审把「检查是否支持普通 RAM 映射」具体化成可写代码的准入政策**：

> 第一版解析并保留描述符 `Attribute`，在 UEFI 来源适配器内部完成准入判断。**凡是进入 `Available` 或 `ReservedMapped` 的描述符，都必须证明支持项目的普通 RAM 映射属性（WB）**——即 `EFI_MEMORY_WB` 位已设置；不得仅凭 `MemoryType` 是 `CONVENTIONAL` 或 `LOADER_DATA` 就认定可以按 WB 建立普通映射。通过准入的描述符仍输出 `{base, len}`；不把原始 UEFI 属性位直接带入 OS 公共交接协议。对不满足普通映射条件的描述符，按对应类型与属性政策排除、保留或拒绝启动。

独立于类型的属性各有各的准入规则（不能只看 `MemoryType`）：

| 属性 | 准入政策 |
|---|---|
| `EFI_MEMORY_WB` | **进入 `Available`/`ReservedMapped` 的必要条件**；未设置则不得按普通 WB 映射 |
| `EFI_MEMORY_RUNTIME` | **独立于 `MemoryType` 判断**——即使类型是 `CONVENTIONAL`，带此位的描述符也不得进 `Available`（它需要 `SetVirtualAddressMap()` 的运行时虚拟映射，不是普通缓存能力位）；当前政策：保证不进 PMM、不建运行时专用映射 |
| `EFI_MEMORY_NV` | 不当作普通可分配 RAM；独立于 `MemoryType = PERSISTENT` 处理（属性和类型可能不一致） |
| `EFI_MEMORY_SP`（Specific Purpose） | 第一版不允许悄悄进入普通 PMM |
| `EFI_MEMORY_RO`/`RP`/`XP` | **这是硬件保护能力，不是当前权限状态**——不得仅因这些位存在就把内存判成只读、不可读或不可执行 |
| `EFI_MEMORY_ISA_VALID` 及 ISA 属性位 | 必须明确目标架构是否理解；不支持的属性**不得静默忽略** |

宿主测试必须覆盖一条属性组合用例：

```
Type = CONVENTIONAL
Attribute = EFI_MEMORY_WB | EFI_MEMORY_RUNTIME
```

这个组合**绝不能**因为 Type 是 Conventional 就进入 `Available`——这是「解析了 Attribute 却仍只用 Type 做最终分类」这类实现错误的最直接检验。

一项未来边界（评审提出，本文登记）：UEFI 另有独立的 `EFI_MEMORY_ATTRIBUTES_TABLE`，用于补充运行时服务内存的保护属性信息。当前不支持运行时服务，第一版不实现；**将来支持时不能认为描述符的 `Attribute` 已包含全部保护布局**。

这不需要一开始就把所有 UEFI 属性映射成三架构页表位。

##### 2.5.7.7 属性政策的穷尽表：每个已知属性位都要有明确处置（v8 新增）

第七轮评审指出 §2.5.7.6 的属性表还不完整——`WP`、`MORE_RELIABLE`、`CPU_CRYPTO` 缺席；`ISA_VALID` 说了「不静默忽略」却没写失败动作；`WB` 缺失时各类描述符的动作没有逐类落地；`RUNTIME` + `CONVENTIONAL` 组合的映射结果没定。本节补成穷尽表，政策目标：**每个已知属性位是参与 WB 准入、改变分配策略、改变映射策略、被明确忽略，还是出现即报错——五者必居其一，不留「识别了却不知道怎么处置」的分支**。

| 属性位 | 处置 | 说明 |
|---|---|---|
| `EFI_MEMORY_UC` / `WC` / `WT` / `UCE` | **能力位，记录**：非 WB 能力不影响准入，但 `WB` 缺失才触发下面的处置表 | 描述符可能同时声明多种缓存能力；关键判断只看 `WB` |
| `EFI_MEMORY_WB` | **WB 准入的必要条件**（缺失走下方逐类处置表） | 普通 DM 的属性前提 |
| `EFI_MEMORY_WP`（v8 补、v9/v11 按规范两度修正） | **缓存性能力位**——UEFI 2.5+ 用法对应 write-protected cacheability policy，与 `RO`/`RP`/`XP`（物理保护能力）不同类。记录该能力；选 WB 时不因 WP 存在而改变映射权限；`WB` 缺失时按 WB 缺失政策处置。**规范背景说明**：2.10 的类型定义中仍保留其历史上的 "Physical memory protection attribute" 标签，同时注明现代用途是缓存策略——保留这一背景，避免读者误以为规范从未把它列入物理保护属性 | 术语纪律：**不得把「保护能力」与「缓存策略能力」混称权限属性** |
| `EFI_MEMORY_RP` / `RO` / `XP` | 记录；**能力位，不是当前权限状态**——不得仅因这些位存在就把内存判成只读、不可读或不可执行 | 第七轮评审确认 |
| `EFI_MEMORY_RUNTIME` | **独立于类型的准入判断**（§2.5.7.6 的表）；对 `RUNTIME_SERVICES_*` 类型的处置见 §2.5.7.1 政策表 | 需要 `SetVirtualAddressMap()` 的虚拟映射，与普通 DM 是两回事 |
| `EFI_MEMORY_NV` | **独立于类型的处置**：不当作普通可分配 RAM（即使 Type 不是 `PERSISTENT`，带此位也不进 PMM）；范围信息保留 | 属性与类型可能不一致 |
| `EFI_MEMORY_SP`（Specific Purpose） | 第一版不允许悄悄进入普通 PMM；范围信息保留 | |

**独立属性的「最终普通映射结果」列（v11 补——第十轮评审指出 v10 只定了分配策略，没把三种独立属性逐类型定完映射策略）**：

| 组合（示意，规则对**普通内存候选类型**适用——排除/设备路径/拒绝启动类型按下方五步裁决顺序先行处置，属性不改变其处置） | 分配策略 | 最终普通映射结果 | 范围去向 |
|---|---|---|---|
| 任意 Type + `RUNTIME`（本项目不支持运行时服务） | 不进 PMM | **不建普通 DM**（统一规则，逐类型同判；例外：将来支持运行时服务时按 `EFI_MEMORY_RUNTIME` 合同另行映射） | side list |
| 任意 Type + `NV`（无论 Type 是否 `PERSISTENT`） | 不进 PMM | **不建普通 DM**——持久内存的访问语义（字节寻址、非易失、磨损）与普通 WB DM 不匹配，第一版没有安全使用它的路径 | side list |
| 任意 Type + `SP` | 不进普通 PMM | **按具体用途裁决，第一版默认不建普通 DM**——特定用途意味着「不该被普通语义使用」，普通 DM 恰是普通语义；除非政策表为某个已知 SP 用途显式放行 | side list（待用途核实后可升级） |
| `CONVENTIONAL + WB + NV` | 不进 PMM | **不建普通 DM** | side list |
| `CONVENTIONAL + WB + SP` | 不进 PMM | **不建普通 DM**（第一版默认） | side list |
| `LOADER_DATA + WB + RUNTIME` | 不进 PMM | **不建普通 DM** | side list |
| `RUNTIME_SERVICES_*`（类型本身） | 不进 PMM | **不建普通 DM** | side list |

统一规则一句话：**三种独立属性（`RUNTIME`/`NV`/`SP`）中任一命中，普通内存候选类型的最终普通映射一律为「不建」、范围一律进 side list**——第一版没有任何「属性命中但仍建普通 DM」的放行路径，所以三种属性的映射去向都是确定的，不存在「分配策略定了、映射策略悬着」的行。这比逐属性逐类型写例外简单，且与「第一版不支持运行时服务、不支持持久内存」的立场一致。「普通内存候选类型」的确切外延由下方五步裁决顺序给出。

| `EFI_MEMORY_MORE_RELIABLE`（v8 补） | 记录；第一版不据此改变分配或映射策略，但**不得静默忽略**——政策表登记「当前不解释」 | 平台固件用于标记更可靠的区域 |
| `EFI_MEMORY_CPU_CRYPTO`（v8 补） | 记录；同上，登记「当前不解释」 | 加密能力标记 |
| `EFI_MEMORY_ISA_VALID` / ISA 掩码位 | **当前出现即分类错误**（fail-closed）：本项目的三架构都不解释 ISA 属性掩码，遇到即拒绝启动。补充（第九轮评审）：`ISA_MASK` 非零而 `ISA_VALID` 为零的组合**同样判为分类错误**——不符合本项目支持的合同 | 第七轮评审要求写出失败动作；第九轮评审补齐组合分支 |

**本表的「已知」以哪个 UEFI 版本为准（v9 新增，第九轮评审要求显式选择）**：**第一版规范基线为 UEFI 2.10**——穷尽表只承诺覆盖 2.10 定义的属性位；2.11 及之后新增的位（如 `EFI_MEMORY_HOT_PLUGGABLE`——表示区域可在运行期被动态移除，OS 应避免把不可迁移的核心数据分配到这类内存）出现时按**未知属性政策**处理（fail-closed），不静默忽略。选 2.10 而不升级的理由：不为「穷尽」把整个 2.11 属性体系引进第一版实现；升级是独立的政策决定（登记 `HOT_PLUGGABLE` 对 PMM 分配与映射的影响），不是随手加一行。**规范版本基线与依赖 crate 的版本一样，应当写成显式承诺**。

**`WB` 缺失时的逐类处置**（v9 重写——v8 的表格有「其余类型不新增后果」一行，违反了本节自己的总原则：凡进 `ReservedMapped` 必须证明 WB。总规则：**类型政策决定描述符原本应进入的分配与映射类别；属性政策可以收窄资格，但不得让缺 WB 的描述符继续进入普通 WB 映射**）：

| 类型 | `WB` 缺失时的处置 | 待明确 |
|---|---|---|
| `CONVENTIONAL` | 不进入 `Available`（不交给 PMM）；**范围进 side list**；记录诊断 | — |
| `LOADER_CODE` | 不建普通 DM；范围进 side list；代码可执行性由恒等映射期（bootstrap 期间本来就在恒等窗口跑）保证 | 切根后是否还需要读取该代码，随恒等窗口拆除消失——待逐腿核实 |
| `LOADER_DATA` | 不建普通 DM；范围进 side list；**是否可行需逐腿核实**——引导数据（含输出数组）可能仍需读取 | 恒等窗口通道是否覆盖；不可行则分类错误 |
| `BOOT_SERVICES_CODE/DATA` | 不建普通 DM；范围进 side list | 内核不消费它们，side list 足够 |
| `ACPI_RECLAIM` | 不建普通 DM；范围进 side list | 未来 ACPI 支持时再决定映射 |
| `RUNTIME_SERVICES_*` / `ACPI_NVS` / `PERSISTENT` | 本就不进普通 DM（政策表），`WB` 缺失不改变处置 | — |

**不存在从属性准入失败绕回普通映射的后门**——这是本表的总原则，v8 版本违反了它（`LOADER_CODE` 未列、`BOOT_SERVICES_*` 与 `ACPI_RECLAIM` 落进「其余」继续进普通保留映射）。

**属性组合的裁决顺序也必须成文**（第七轮评审指出调用点不应碰巧决定 Type 与 Attribute 谁先谁后）。v12 细化为五步（第十一轮终审裁决采纳评审建议：v11 的三步顺序没有写明已知类型的强制处置与独立属性之间的优先级，`RESERVED+NV` 一类组合悬空）：

1. **未知/不支持条件**：未知类型 → 分类错误；`ISA_VALID` 或 ISA 掩码位出现 → 分类错误；`ISA_MASK` 非零而 `ISA_VALID` 为零 → 分类错误。fail-closed 排在最先——无法分类的对象没有后续裁决可言；
2. **存在即拒绝启动的类型**：`UNACCEPTED`、`PAL_CODE` → 拒绝启动。这是明确写进政策的 fail-closed，强度高于一切后续裁决；
3. **类型强制处置**：`RESERVED`/`UNUSABLE` → `Excluded`；`MMIO`/`MMIO_PORT_SPACE` → 专用设备映射路径。**类型胜过独立属性**——这类描述符的属性位记录进诊断，但不改变处置、也不进 side list；
4. **普通内存候选 × 独立属性**：候选类型为 `CONVENTIONAL`、`LOADER_CODE`、`LOADER_DATA`、`BOOT_SERVICES_CODE/DATA`、`ACPI_RECLAIM`、`ACPI_NVS`、`RUNTIME_SERVICES_CODE/DATA`、`PERSISTENT`——`RUNTIME`/`NV`/`SP` 任一命中 → 不进 PMM + 不建普通 DM + 范围进 side list；未命中进入第 5 步；
5. **WB 准入**：通过 → 按类型政策表进入 `Available`/`ReservedMapped`；缺失 → 上方逐类处置表（不建普通 DM + 范围进 side list）。

第 3 步「类型胜过属性」的理由：类型回答「这块区域**是什么**」（固件对区域用途的断言），属性回答「这块区域可以**怎么用**」（能力与用途提示）。`RESERVED` 的排除不是「暂时不映射」的政策选择，而是固件声明 OS 不得触碰——任何属性都无法把「不可触碰」改判成「因政策不映射」；若把它放进 side list，会把「因类型排除」误记成「因属性不映射」，诊断按原因归档的语义随之失真。MMIO 同理：它走专用设备映射路径（非普通 WB 映射），`RUNTIME` 位收窄的是**普通**映射资格，对本来就不建普通映射的类型没有可收窄的对象。

四个此前悬空的组合按此顺序落定：

| 组合 | 落定步骤 | 结果 |
|---|---|---|
| `RESERVED + NV` | 第 3 步 | `Excluded`（类型排除；`NV` 位记录进诊断，不进 side list） |
| `UNUSABLE + SP` | 第 3 步 | `Excluded`（同上） |
| `MMIO + RUNTIME` | 第 3 步 | 专用设备映射路径（`RUNTIME` 位记录进诊断；本项目不调用运行时服务，MMIO 区间不因该位额外要求运行时映射） |
| `PAL_CODE + NV` | 第 2 步 | 拒绝启动（先于一切属性裁决） |

每一类「保留但不映射」的结果统一进 side list——成员由**最终的分配策略 × 映射策略**决定，不是写死三个类型名（第七轮评审指出 side list 成员不应被写死为 ACPI_NVS / RUNTIME / PERSISTENT 三个名字：`WB` 缺失的 `LOADER_DATA` 同样要进）。该五步顺序属**目标合同（冻结）**；§7 的穷测矩阵必须包含上表四个组合作为具名用例，由原型 ① 验证。

**`RUNTIME` + `CONVENTIONAL` 组合的完整结果**（第七轮评审要求写清）：不得进 `Available`（`RUNTIME` 独立判断否决了 PMM 分配资格——运行时映射要求的区域被 PMM 分配后无法履行 `SetVirtualAddressMap` 义务）；项目当前不支持运行时服务，第一版政策为「不进 PMM、不建普通 DM、保留完整范围（进 side list）」，待将来支持运行时服务时按 `EFI_MEMORY_RUNTIME` 合同另行映射。

##### 2.5.7.8 输出缺口：side list 的语义与生命周期（v8 新增、v9 修正生命周期表述）

政策表把分配策略与映射策略拆开后，出现了**既不能分配、也不建普通 DM** 的内存（`ACPI_NVS`、`RUNTIME_SERVICES_*`、`PERSISTENT`，以及 v9 补入的各「WB 缺失」情形）。它们不属于现有两格，需要第三个输出：**side list**。

**v9 修正生命周期表述**（第七轮评审指出 v8 的「为未来保留」不成立）：

> side list 是**第一版引导分类器的内部诊断输出**，用于确认哪些范围因特殊政策没有进入普通两张表。它**不构成跨引导边界的保留协议**——不进 `KernelInfo`、不传给内核；若未来内核要消费这些区域（例如实现持久内存），必须扩展 `KernelInfo` 或建立其他明确的范围交接途径，**不能**依赖这个 shim 内部清单。

成员资格也按第九轮评审修正：**由最终的分配策略 × 映射策略决定**（保留 + 不映射 → side list），不是写死三个类型名。容量由调用方提供（沿用「容量由共同契约提供」原则），分类器零分配。

**这直接影响输出接缝**：sink 需要 `push_unmapped_reserved` 之类的第三种写入（或结果结构返回三种清单），原型阶段定。**在结果形状决定之前，I-29-8 的政策表不能冻结**。

另一项配套澄清（同一评审轮次提出）：**`PA_LIMIT` 与 Direct Map 覆盖是两个合同，必须分开**——

| 合同 | 检查什么 | 在哪层 |
|---|---|---|
| PA representability | 架构页表能否表达该物理地址（半开末端语义） | 分类器的 `PA_LIMIT` 参数 |
| Direct Map coverage | 内核是否**真的**为该区间建立了普通直接映射 | 映射规划与验收层（`dm_coverage` 一侧） |

`PA_LIMIT` 通过不等于 DM 覆盖成立：一个物理地址可以在处理器可表达范围内，却超出项目实际 DM 窗口。`ReservedMapped` 的定义要求普通 DM 可访问——所以**进入保留表的每个区间都必须有独立的 DM 覆盖验收**（当前单窗口则检查其物理覆盖半开范围；多窗口则逐区间检查）。`Available` 有同样问题：可分配性与可访问性不能脱节。§2.5.7.3 说「地址维度只保留 `PA_LIMIT`」指的是**分类器**的输入——分类器不做 DM 覆盖检查，但交接与映射合同必须补上这道独立验收；这句话在此澄清，避免误读。

**还有一个架构分层问题必须说清**（第六轮评审提出，本文采纳）：`MemoryType + Attribute + PhysicalRange` 是 **UEFI 来源适配器的输入**，不是 minix-rs 三架构共同的内存语义输入——RISC-V 当前走设备树，根本不经过这套 UEFI 分类。正确的层次是：

```
UEFI 来源                              Device Tree 来源
MemoryType + Attribute                 /memory + reserved-memory 等
      │                                        │
      ▼                                        ▼
UEFI 类型政策（§2.5.7.1）              DTB 来源政策
      │                                        │
      └──────────────┬─────────────────────────┘
                     ▼
            OS 统一的内存语义
           （两张表 + 四种处置状态）
                     │
                     ▼
              架构映射实现
        x86-64 / aarch64 / riscv64
```

这不是要新增 trait（§3.2 的教训），而是保持职责清楚：UEFI 类型不是 OS 的通用内存类型；设备树也不应该伪造 UEFI 类型；两边各自经自己的政策转换成内核能理解的共同语义；架构层决定这些语义如何落入硬件页表。

**这张图当前处于什么状态，必须区分清楚**（第七轮评审指出，本文核实）：

| 层 | 现状 |
|---|---|
| UEFI 来源适配器（`classify_map`） | **已存在**，但分类只认类型 7/11/12，属性未读；本节的准入政策是它的目标形态 |
| DTB 来源适配器（`DtbMemoryMap`） | **已存在**，但已核实的代码事实只有两条：解析 `/memory` 节点的 `reg`、按 `firmware_reserve_end` 裁剪固件常驻区前缀。**没有** `reserved-memory` 子树处理、`no-map` 属性、DTB 保留区与 RAM 区间重叠检查的证据 |
| OS 统一语义层 | 已有形状（两张表），政策未成文 |
| 架构映射层 | 已存在（三架构 `flags_to_pte`），属性落实未核（§2.5.7.5） |

两点必须写明：**设备树的 `reserved-memory` 不能直接等同于 UEFI 的 `ReservedMapped`**——设备树可能描述需要保留、需要映射、明确不允许普通映射等不同语义的区域，这些都要经 DTB 来源政策判断，不能复制 UEFI 类型分类。这不需要现在开一个大型 DTB 议题，但它是 **I-29-11 的明确验收**：冻结「三架构共同内存语义」之前，DTB 侧已有行为与未覆盖语义必须写成文；若本轮只限定为 UEFI 分类器重构，则 DTB 政策明确登记为后续独立问题，不阻塞 UEFI 侧实现。

#### 2.5.8 反向方向：被释放的池对象，页级结果待验证

§2.5 讨论的都是「已占用却被报成可用」。还有相反方向的一种，但第四轮评审提醒：**不能从 Rust 对象的析构直接推断物理页立刻变成常规内存**。

`build_memmaps` 里第一句是

```rust
let mmap = boot::memory_map(MemoryType::LOADER_DATA).expect("Failed to get UEFI memory map");
```

`boot::memory_map` 返回 `MemoryMapOwned`，其内含的 `MemoryMapBackingMemory` 实现 `Drop`：**若引导服务仍存活，就调用 `free_pool`**（§6.7）。这个 `mmap` 是函数局部变量，函数返回时即被释放。

**能确定的事实**：

1. 取快照时这块缓冲已分配，所以它被标记为 `LOADER_DATA`；
2. 函数返回时 `free_pool` 被调用，池对象被归还。

**不能确定的**：底层物理页是否立刻变回常规内存。固件的池实现通常有共享页与空闲块合并：小块释放可能只是回到池的空闲链表，只有整页（或整组池页）都空闲时才把页还给页分配器。因此这块页在那份快照里是 `LOADER_DATA`，在交接时刻**可能是也可能不是**。

若它确实已变成常规内存，则保留表**多报**了一块实际可用的内存——危害比 §2.5 小（多报 = 少用，不会造成覆盖），但它同样属于「快照类型标签 ≠ 交接时刻真实占用」。

**建议的取证方式**（六步探针，第四轮评审提出，本文采纳）：

1. 取一次 `GetMemoryMap`；
2. 调用 `boot::memory_map(LOADER_DATA)`；
3. 记录返回缓冲的物理地址与长度；
4. 让该对象析构；
5. 再取一次 `GetMemoryMap`；
6. 比较这块缓冲覆盖的页在前后的类型。

三种可能结果分别对应三种结论：立刻恢复为常规内存（保留表多报，应改成不释放或不计入）、仍属 `LOADER_DATA` 池页（当前行为正确）、或部分页变化（需要按页判断）。

**因此本节从「已确认的事实」调整为「待目标验证」**。生产路径不受影响：它的读图缓冲由 `alloc_map_buffer` 用裸 `allocate_pool` 取得、**从不释放**（注释写明「pairing loop 可能需要它直到退出成功」），所以不存在这个不确定性。

#### 2.5.9 两处代码注释需要修正（本文自己的补充）

第五轮评审指出分配器注释写错了，本文核实后同意，并且发现同一条误解还有第二处。

**第一处：`UefiPoolAllocator::dealloc` 的注释**（§6.13 原文）：

```rust
// Pool pages are reclaimed wholesale by the firmware at
// ExitBootServices; boot-stage code never frees individually.
```

「由固件在退出时整体回收」是错的。UEFI 对退出后内存归属的规定是：`LOADER_CODE` / `LOADER_DATA` / `BOOT_SERVICES_*` / `CONVENTIONAL` 等内存交给 OS 或其 loader 接管，**不是**固件自动把它们释放成常规内存。准确的表述应当区分三件事：

- **单个对象释放**：`dealloc` 是空实现，不调用 `FreePool`；
- **页的归属**：这些 `LOADER_DATA` 池页在最终内存图中仍是 loader-owned；
- **谁来回收**：由 OS/内核按自己的内存政策决定，不是退出动作替项目完成。

建议改为：

> Boot-stage allocations are retained until `ExitBootServices`. Their backing pages remain loader-owned memory in the final memory map; the OS loader/kernel is responsible for reclaiming them when no longer needed.

**第二处（本文补充）：`build_memmaps` 的快照顺序说明**。该函数的文档注释把「交接安全」归因于「内核先深拷贝」这一条，读起来像是只要深拷贝就万无一失。按 §2.5.1 与 §2.5.7 的结论，实际成立的是更窄的一句：深拷贝保证「内核读到的内容不会被后续分配覆盖」，但**不保证**「交付的可用表里没有 shim 自己在用的页」。后者要靠「所有自举分配都在拍快照之前」这条顺序，而测试内核违反了它（§2.5）。注释应当把这两件事分开写。

顺带一个连带影响（评审指出，本文确认）：`dealloc` 为空意味着 `Vec` / `Box` 的旧 backing allocation **不会**因为 Rust 对象释放而归还给池。`into_boxed_slice()` 即使触发重新分配，旧 allocation 也会一直占着，直到退出后由 OS 接管。这使 §2.5.1 第 ① 类的「占用时长」比直觉更长——不是「临时分配后立刻释放」，而是「一直占到位图交接」。

### 2.6 目标设计：四段职责与断言分工

评审的核心意见：不要把所有职责塞进一个函数，先划清四段职责；「不是要求做成四个 trait 或四层抽象，而是要求边界清楚」。

| 段 | 职责 | 现状归属 | 是否应当唯一 |
|---|---|---|---|
| ① 获取与退出事务 | `GetMemoryMap`、缓冲扩容重试、MapKey 保存、`ExitBootServices`、键失效后重读重试 | `pair_and_classify`（生产）；第三方库退出函数（辅助与测试） | 不唯一，且**不应该**统一：UEFI 的事务性约束不适用于设备树腿 |
| ② 描述符解析与校验 | 版本、尺寸、步长、缓冲区边界、算术溢出 | 生产路径有**一份项目自有的原始字节解析器**；测试路径用第三方库的解析结果，**尚未复用它**（v2 误写为「当前已唯一」，已改） | 可以唯一，是否需要唯一见 §2.6.1 |
| ③ 项目内存图分类 | 类型政策准入、`Attribute` 准入、常规入库、MMIO 排除、保留判定、`PA_LIMIT` 检查、容量规则（v8：`ram_top` 计算已随 §2.5.7.3 删除） | `classify_map` 后半；`build_memmaps` 里有一份**同义副本** | **必须唯一** |
| ④ 输出与交接 | 生产写固定布局交接区；测试写预分配存储 | 生产：`Serializer`；测试：无（测试拿泄漏切片） | 不唯一，按用途分化 |

一条判据本文完全同意，照录：**「统一的是内存图的语义产出与分类规则，不是强行统一固件获取协议」**。

#### 2.6.1 ② 段：只统一 ③，还是连解析也统一

这是需要裁决的分岔。两个目标：

- **目标一（只收敛分类规则）**：生产用自己的解析器，测试用第三方解析器，两边转换成统一的描述符视图，再共用 ③。可以成立，但必须承认代价：**QEMU 测试不验证生产路径的原始字节解析器**。
- **目标二（连解析一起收敛）**：测试直接取得原始 UEFI 内存图缓冲区与描述符元数据，交给生产路径使用的同一套解析校验与分类逻辑。验证更强，真实固件数据会经过完整的项目自有实现。

本文倾向目标二，理由：现在有真实 UEFI 固件环境，没必要为了让测试接口短一点而绕开项目自己的解析器。可行性取决于测试内核能否方便地拿到原始缓冲与元数据——这一点在 §7 列为待研究项。

#### 2.6.2 ③ 段的输入：必须可重复遍历

分类算法要扫描描述符流。**两遍扫描的旧理由已消失**（v7 删除了 `ram_top`——旧的第一遍就是为算它），**v8 给出新理由：事务性**：

- 第一遍：验证全部将输出的描述符（类型政策、`Attribute` 准入、长度/溢出/`PA_LIMIT`/起点对齐）、统计容量与诊断计数——**不产生任何输出**；
- 第二遍：向输出 sink 写结果。

这样保证「验证完成后才开始产出」，失败时输出容器保持干净（对 EBS 配对循环里「重试前 reset」的现有语义是自然衔接）。若原型阶段证明这个事务性保证不必要，一遍扫描也完全足够——**两遍与否归输出接缝原型决定，不再作为抽象前提**。无论如何，`DescriptorView` 仍必须是可重复遍历的（两次 `iter()`，见下）。

**v8 修正（第七轮评审指出的结构性遗漏）**：`DescriptorRef` 的字段必须包含 `attribute`——§2.5.7.6 的准入政策（`WB` 必要条件、`RUNTIME`/`NV`/`SP` 独立判断）要求分类层读到属性，而 v8 之前的视图只暴露三个字段，等于「解析并保留属性」和「属性准入」两条设计要求没有接起来。数据合同为：

```rust
struct DescriptorView<'a> { /* 校验过的原始描述符缓冲 + 步长 + 条数 */ }

struct DescriptorRef<'a> {
    raw_type: u32,
    physical_start: u64,
    number_of_pages: u64,
    attribute: u64,        // ← 描述符偏移 32 的原始值，由唯一解析器读出并做边界验证
}

impl<'a> DescriptorView<'a> {
    fn iter(&self) -> impl Iterator<Item = DescriptorRef<'a>> + '_;
    // 每条描述符暴露：类型、物理起点、页数、原始 Attribute
}
```

**属性由同一个生产解析器完成字段边界验证**——测试与生产不得各自再解析一次属性（否则「唯一解析器」名存实亡）。`physical_start` 的 4 KiB 对齐校验也在这里完成（UEFI 对描述符字段有明确对齐要求，现有代码只查了 `descriptor_size` 对齐，v8 补上）。

分类器调用两次 `iter()`，不额外分配。这与 `no_std` 环境和引导期分配纪律直接相关：**分类过程必须零分配**，否则就破坏了 §2.5.4 那条生产不变量。

**v9 补齐：两遍扫描的事务性还差一个关键条件**（第九轮评审指出 v8 的推理未闭合）。第一遍**不只是统计描述符数量**——它必须验证**所有**第二遍可能失败的条件：可用表/保留表/side list 的容量、`Serializer` 的 wire 与 semantic 双写分区容量、长度与偏移的整数转换。若这些错误拖到第二遍写入时才暴露，输出仍可能半途留下部分结果——两遍扫描本身并不自动提供事务性。

给接缝原型的验收（sink 示意合同，非强制用 trait 表达）：

```rust
trait ClassificationSink {
    /// Pass 1 末尾调用：按 Pass 1 统计的全部输出条数预检所有容量、
    /// 编码长度与整数转换。失败则整张图作废，不进入 Pass 2。
    fn preflight(&self, counts: OutputCounts) -> Result<(), OutputError>;
    /// Pass 2 调用：写入阶段不得再出现容量或几何验证错误。
    fn push_available(&mut self, range: MemoryRegion);
    fn push_reserved_mapped(&mut self, range: MemoryRegion);
    fn push_unmapped_reserved(&mut self, range: MemoryRegion);  // side list
    /// 完成描述符，返回统计。
    fn finish(self) -> Result<Classification, OutputError>;
}
```

最重要的不是方法数量，而是：**所有可预见的失败在写入前就已排除，Pass 2 具有不可失败的提交合同**。若无法满足（例如 `Serializer` 的 wire/semantic 双写容量无法在 Pass 1 完全预检），必须用暂存结果或显式回滚，不能宣称第二遍天然事务性。

**v11 修正：示意合同里的 `finish(self) -> Result<..>` 与「不可失败」自相矛盾**（第十轮评审指出）。若 Pass 1 已完整预检，Pass 2 的 `push_*` 与 `finish` 就应具有**类型层面可表达**的不可失败合同——比如 `finish(self) -> Classification`（预检通过后返回普通值），或由 Pass 1 产出一个「已验证的提交凭证」（如 `VerifiedPlan` 类型），只有持凭证才能调用写入阶段。两种形态都交给原型比较，但**不能只在注释里承诺不可失败而签名仍返回 `Result`**——那等于把合同留给运行期。

#### 2.6.3 ④ 段的输出：预分配存储，容量由共同契约提供

三种形态比较：

| 方案 | 优点 | 风险与代价 |
|---|---|---|
| 返回两个固定容量结果数组 | 最直观，宿主测试好写 | 结果体积大（当前容量 128 + 256 条，每条 16 字节，合计约 6 KiB）；需确认栈空间；生产侧仍要复制进 `Serializer` |
| 回调 / 接收器闭包 | 不需要中间结果分配；生产可直接写 `Serializer`，测试可写静态数组 | 要处理回调错误、容量溢出、两类结果计数，接口可读性稍弱 |
| 私有 sink trait（静态分发，不导出公共 API） | 两种输出容器各自实现；容量检查与写入错误更清楚 | 多一层接口，需要论证它确实比回调更简单 |

评审倾向「优先比较回调与私有 sink，不优先采用返回两个大型固定数组」，本文采纳。另有一条硬要求：**容量不能复制两份**。当前容量常量（`ARENA_CAP = 16 KiB`、可用表 128 条、保留表 256 条）已经属于交接协议契约，应当由输出容器提供容量并统一处理越界，而不是在测试代码里再写一遍 128 与 256。

关于「要不要用 trait」：这里不反对，但与 I-28 有本质区别——I-28 的 trait 宣称统一多个来源却没有消费者利用；④ 的输出端**确实有两种真实需求**（生产写 `Serializer`，测试写静态数组）。因此私有 sink 若能实质减少分支与重复，就是合理的内部抽象。但它**不应放进 `minix-boot`，也不应被描述成 OS 内存语义接口**——它是分类器内部的输出适配边界，不是跨架构的硬件语义合同。优先静态分发，不用 `dyn`。

**v8 补充（§2.5.7.8 的输出缺口传导到这里）**：三行「保留但不映射」的内存需要落点，sink 的写入动作不再必然只有 `push_memmap` / `push_reserved` 两种。原型阶段要一并决定：

- sink 是两种写入 + 特殊范围走独立 side list（由调用方持有），还是三种写入（`push_special_range` 进 sink）；
- 特殊范围清单的容量归属（沿用「容量由共同契约提供」原则，不在测试里复制常量）；
- 若采用「结果结构返回三种清单」的形态， sink 可能退化为单个写入函数——这会反过来影响回调与 sink 的比较结论。

**因此接缝原型与 I-29-8 的政策表定稿互为前置**：结果形状定了才能写政策表的输出列，政策表批了才能写代码。

#### 2.6.4 断言分工（修正 v2 的内部矛盾）

v2 的 §2.5 要求测试内核加「自举区域不在可用表」的断言，§2.6 却写「夹具型测试保持对内存图零断言」。两句不能同时成立——`assert_bootstrap_outside_memmap` 本身就是一项对内存图内容的断言。v3 按断言**范围**划分，两个要求同时满足：

| 测试类型 | 应承担的断言 | 不承担 |
|---|---|---|
| 12 个夹具型测试 | 检查**本测试自身的自举分配**没有进入可用表 | 不检查完整分类语义（保留表规则、MMIO 排除、类型政策） |
| 2 个专门的分类测试（现 `test-memmap`） | 检查完整分类结果：可用表只含普通内存、保留表只含政策允许的类型、MMIO 不进入两表、区间满足物理上限与边界 | — |
| 宿主分类器测试 | 各类描述符、非法参数、溢出、容量错误 | 不涉及固件 |
| 生产链集成测试 | 真实 UEFI 输入下的启动成功，以及（新增）分类结果内容 | — |

准确表述：

> 12 个夹具型测试**不负责验证完整的内存图分类语义**，但**必须验证本测试自身的自举占用不进入可用表**。完整的分类正确性由专门的分类测试负责。

**测试应当补到什么程度**（v8 按 §2.5.7.3 的定稿重写——`ram_top` 已删除，下面不再有任何以它为准的断言）：

| 性质 | 需要验证的内容 |
|---|---|
| 可用表 | 只有 `CONVENTIONAL` 进入可用表 |
| 保留表 | **只有明确允许普通映射的类型**才能进入保留表 |
| 排他类型 | `RESERVED`、`UNUSABLE`、`UNACCEPTED` 与不支持的未知类型**不得**进入普通保留表 |
| MMIO | 使用专用设备映射路径，不进入普通内存表 |
| 区间安全 | 所有进入两张表的区间都满足长度、溢出与 `PA_LIMIT` 契约；**物理起点 4 KiB 对齐**（§2.5.7.6 v8 新增的解析校验） |
| 类型 × 属性 | 组合结果符合最终项目政策；属性组合用例必须覆盖「`CONVENTIONAL` + `EFI_MEMORY_RUNTIME`」不得进 `Available`（§2.5.7.6），以及 `WB` 缺失时的逐类处置（§2.5.7.7） |

注意「保留表是否非空」要以目标虚拟机的固件实际提供的内存图为准——不要把某个固件布局的偶然性质硬编码成所有平台的要求。

**v8 决定：不再保留 `ram_top` 的 characterization test**（v7 曾提议保留，第六轮评审推翻，本文同意）。

v7 的理由是「固定旧行为、防止无意回归」。但这个理由在 v7 已不成立：`ram_top` 的旧行为（起点恰在边界即丢弃）已被 §2.5.7.3 正式判定为**错误**，不是「待裁决」。保护一个已判定的错误行为需要测试代码保留旧算法或复制旧逻辑，反而增加维护成本。正确的做法是让契约测试直接验证新政策：

| 新 contract test 用例 | 期望 |
|---|---|
| `LOADER_DATA` 起点恰好等于旧 `ram_top` | 按类型政策正常分类（进保留表） |
| `LOADER_DATA` 起点高于旧 `ram_top` | 仍按类型政策分类 |
| `RESERVED` 落在旧 `ram_top` 以下 | **不得**进入普通保留表 |
| 描述符终点越过旧 `ram_top` | 不因这个旧值被截断 |
| 所有进入两张表的区间 | 仍受 `PA_LIMIT` 约束 |

「旧 `ram_top`」在这里只是测试数据的构造参数（用来构造边界形态），不再是分类器的任何输入。

#### 2.6.5 事务协调归 ①，不归 ③

`Serializer::reset_map_partitions()` 的用途是「EBS 重试前清掉上一次失败尝试写下的条目」（§6.3 的注释）。这件事属于**事务协调层**，不是分类器的职责：

- 分类器不该知道 MapKey，也不该知道 EBS 会失败重试；
- 分类器只负责「给定一份快照，把结果写进输出容器，然后 finish」；
- `reset` 由 `pair_and_classify` 在每轮调用分类器**之前**执行（现状已是如此）。

按此归属，③ 段才真正是一段「输入视图 + 输出容器 → 结果」的纯分类逻辑：无分配、无事务状态、可被生产与测试共同调用、可独立宿主测试。验收时应检查分类器的签名里不出现 MapKey、重试计数或「是否是重试」之类的参数。

### 2.7 两条完整修复路径

v2 的「先分配、后拍快照、再断言」只覆盖第 ② 类分配。下面是覆盖三类的两条路径。

#### 路径 A（推荐先研究）：使用退出函数返回的最终内存图

§6.4 的摘录显示，第三方库的退出函数在成功时返回 `MemoryMapOwned`；它内含的缓冲，是**成功退出前最后一次 `GetMemoryMap`** 的结果，且该缓冲本身在读图之前分配。

流程：

1. 提前完成根页表页、bump 池等全部自举分配；
2. 提前准备好分类结果所需的预分配存储（静态数组或复用交接区）；
3. 调用退出函数；
4. **保留**它返回的 `MemoryMapOwned`，不丢弃；
5. 用这份「成功退出所对应的内存图」调用唯一分类器；
6. 分类结果写入步骤 2 准备好的存储；
7. 进入内核，此后不再做需要引导服务的分配。

为什么这条路径能恢复一致性：退出函数内部已经完成了「分配缓冲 → 读图 → 用同键退出」，因此它返回的那张图**就是**退出所用的那张，且包含它自己那块缓冲的占用。分类在退出之后运行，只读那块缓冲、只写预分配存储，不产生新的分配——于是「分类所依据的图」与「退出所用的图」重新成为同一份。

##### 前提一：能否拿到原始字节（已核实，可以）

`classify_map` 的入参是「原始字节 + `map_size` + `descriptor_size` + `descriptor_version` + `pa_limit`」。第三方库 0.33.0 的 `trait MemoryMap` 公开了：

```rust
fn meta(&self) -> MemoryMapMeta;   // 含 map_size / desc_size / desc_version / map_key
fn buffer(&self) -> &[u8];          // ← 原始描述符字节
fn entries(&self) -> MemoryMapIter<'_>;
```

而 `MemoryMapOwned` 实现了 `MemoryMap`（§6.7）。因此路径 A **能**把「退出所用那份图的原始字节与元数据」原样交给生产解析器——**目标二（连解析一起统一）在现有依赖上是可行的**，不需要退回目标一。

一处使用注意：`meta().map_size` 是「实际有效字图长度」，而 `buffer()` 返回的是**分配长度**（比有效长度多若干条冗余，见库内 `EXTRA_ENTRIES`）。因此必须传 `map_size`，不能传 `buffer().len()`；分类器已有 `map_size > map.len()` 的越界检查，方向是对的，但调用点要取对字段。

##### 前提二：退出之后分类失败怎么办（必须定契约）

路径 A 把分类放在退出**之后**，这是它与生产路径的关键顺序差异：生产路径的分类错误（`UnsupportedVersion`、`OutOfPhysRange`、容量溢出等）发生在引导服务仍可用时；路径 A 的这些错误发生在引导服务已失效之后。

必须明确的失败契约（本文建议，待评审确认）：

> 退出成功后，分类只能使用已有内存与已有代码。发生分类错误时进入不依赖引导服务、不依赖动态分配的 fail-stop 路径（裸串口打印 + 停机），不尝试返回 UEFI 环境继续运行。

需要同时核查三件事：

1. **不要走会调用引导服务的日志路径**：见下文「前提三」——已核实安全，但保障是两层的，不能只靠一层。
2. **不要构造会在 `Drop` 里调用 `free_pool` 的对象**：退出后 `free_pool` 必然失败（`MemoryMapBackingMemory::drop` 正是因为「引导服务已退出」才跳过释放）。
3. **退出前释放/清理所有依赖引导服务的临时对象**：路径 A 的顺序本身有利于这一点（分配都在退出前完成），但仍需逐项点清。

##### 前提三：析构路径上的日志（已核实，安全但需知道保障来自哪里）

第四轮评审指出：`MemoryMapBackingMemory::drop` 在「引导服务已退出」的分支里仍然调用 `log::debug!`。本文核对了整条链路，结论是**当前安全**，但保障是两层的：

**第一层：项目没有安装 logger。** `uefi` 库提供 `helpers::init()`，它会调用 `logger::init()` 注册一个写 UEFI 控制台的 `log` 后端。全仓检索 `helpers::init` / `logger::init`，**本项目没有任何调用点**（boot-shim 与测试内核都没调）。没有注册 logger 时，`log::debug!` 走 `log` crate 的空实现，不分配、不输出。

**第二层：退出函数第一步就禁用 logger。** 即使将来有人加了 `helpers::init()`，`exit_boot_services` 的第一句就是 `crate::helpers::exit()`，它的作用是 `logger::disable()`；`Logger::disable()` 把内部输出指针置空，而 `Logger::log()` 在指针为空时直接返回（§6.12）。因此退出之后的任何 `log::*` 都不会碰控制台协议。

**剩下的真实风险**：若有人启用 `log-debugcon`（x86 的 IO 端口 0xe9 后端），它不依赖引导服务，仍会在退出后写端口——但那是无害的调试输出。当前 `boot-shim/Cargo.toml` 对 `uefi` 只开了 `alloc` 特性，不包含 `logger` 与 `log-debugcon`。

**建议写进实现约束**（不是修 bug，是防止将来退化）：

> 退出引导服务之后，`MemoryMapOwned` 的持有、遍历、分类与析构，不得调用引导服务，不得触发依赖引导服务的日志后端或动态分配。

若将来确实需要安装 logger，应确认退出后 `Logger` 已禁用，或让该类资源以不析构的方式保持存活。

##### 前提四：路径 A 依赖的七条前提（v6 把两条从「成立」降级）

| 前提 | 状态 |
|---|---|
| 静态输出数组在镜像加载时已占用内存，因此出现在最终快照里 | 成立（静态数组属于镜像的 `.bss`/`.data`，被固件作为镜像的一部分加载） |
| **静态输出数组在内核消费期间仍可访问、且不进入可用表** | **待验收**（v6 从「成立」降级）：出现在快照里只回答「被记录」，不回答「不被 PMM 分配」与「被内核页表覆盖」。见下 |
| `MemoryMapOwned` 的缓冲在最终 `GetMemoryMap` 之前分配，因此出现在同一次快照里 | 成立（`MemoryMapBackingMemory::new` 先 `allocate_pool`，再读图） |
| 分类过程中不再分配 | 需要实现约束：分类器零分配（§2.6.2、§2.6.5） |
| `MemoryMapOwned` 保持存活至分类结束 | 需要实现约束：不要 `let _ = ...`，要绑定到具名变量 |
| **底层地址在退出后、分类期间可访问** | **待核实**（v6 从「成立」降级）：`LOADER_DATA` 只证明资源归属，不证明该缓冲落在项目自建页表覆盖范围内。见下 |
| `Drop` 在退出后不会释放、也不会写控制台 | **成立**（两层保障，见前提三） |

**降级一：`MemoryMapOwned` 缓冲的可访问性**

`MemoryMapBackingMemory::new` 用的是 `allocate_pool`，**没有** `bootstrap_alloc_limit` 那样的地址上界。因此代码能证明的只有「它是 `LOADER_DATA`」，不能证明「它一定落在项目自建页表的恒等映射或直接映射覆盖范围内」。

必须拆成两个不同问题：

1. **退出后、切换页表之前，分类器能否读这块缓冲？** 第三方 API 既然在退出后返回该对象，就提供了访问接口；但仍需核实项目在「退出完成」到「分类完成」之间没有切换地址空间、也没有破坏该指针依赖的映射。测试内核的实际顺序是「退出 → 分类 → 建表开分页」，中间不切根，因此**大概率成立**——但这是顺序事实，不是结构保证。
2. **切换到内核自建页表之后还需要访问它吗？** 若分类完成即不再访问，则**不需要**把它纳入内核 Direct Map——这正是路径 A 应有的设计。

准确表述：

> 退出后、分类期间的访问路径需要核实；`LOADER_DATA` 证明资源归属，不证明特定页表覆盖。若分类完成后不再访问，则无需将该缓冲纳入内核 Direct Map。

**降级二：静态输出数组的生命周期**

静态数组属于镜像，因此会出现在最终内存图里——这个判断成立。但路径 A 还需要保证：**分类输出的两张表本身，在交接与内核消费期间仍可访问，并且不会被 PMM 当成可用页**。

这里有一处容易被忽略的连带：§2.5.6.1 已证明某些 `LOADER_DATA` 描述符可能因地址过滤而没进保留表。若测试内核的镜像区间恰好落在那个边界上，它的镜像页就可能既不在可用表、也不在保留表——此时「不在可用表」这条断言会通过，但「内核能经直接映射访问它」并不成立。对测试内核而言，镜像页的**取指**走恒等映射，能跑；但**经直接映射读取**（例如把镜像里的静态数组当输出容器）会缺映射。

因此路径 A 的验收要加一条：

| 验收 | 标准 |
|---|---|
| 输出生命周期 | 输出数组所在区间在内核消费期间保持可访问，且不进入可用表；必要时由已知映射来源覆盖，或在切换前深拷贝到内核拥有的存储 |

对测试内核的具体做法：把输出数组的地址范围也纳入自举区域断言与映射覆盖检查，**不要只检查 root 与 bump**。这与 `MemoryMapOwned` 缓冲不同——后者可以在分类完成后不再访问，输出数组是分类结果本身，可能还要被内核读取。

##### 路径 A 的验收，定为六项

| 验收 | 标准 |
|---|---|
| 原始内存图访问 | 使用 `buffer()` 与 `meta().map_size` 作为有效长度，**不能**用 buffer 的分配长度 |
| 分类零分配 | 分类路径没有任何临时堆分配 |
| 输出零分配 | 输出容器指向已准备好的静态存储或交接区 |
| 错误退出 | 退出后分类失败，直接使用裸串口 fail-stop，不返回 UEFI 环境 |
| 析构安全 | `MemoryMapOwned` 析构不调用失效服务、不经不安全日志路径 |
| **输出生命周期（v6 新增）** | 输出数组所在区间在内核消费期间可访问，且不进入可用表 |

这六项通过后，没有必要让 12 个夹具型测试各自实现一套生产 EBS 事务循环——事务配对与重试由 `pair_and_classify` 的专项测试负责。

##### 实现约束（措辞按第五轮评审收紧）

> `ExitBootServices` 成功返回后，分类期间允许持有并读取 `MemoryMapOwned`；其析构不得尝试调用引导服务。分类器、输出容器与 fail-stop 路径不得触发动态分配，也不得依赖引导服务的日志输出。

#### 路径 B：测试也走生产式的配对事务

1. 提前分配全部自举资源、交接区、输出缓冲与读图缓冲；
2. 读最终内存图并取得 MapKey；
3. 用同一份快照运行分类器；
4. 用对应 MapKey 调用退出；
5. 失败则重新读图、清理输出、重新分类；
6. 成功后交给内核。

优点是测试与生产验证同一类事务流程。缺点是测试设施需要更多 UEFI 底层接线，测试内核复杂度上升。

#### 两条路径的分工建议

- **夹具型测试**的目标是「给内核消费者一份可靠的内存图」，用**路径 A** 即可，成本低、语义正确；
- **若要验证退出配对与重试本身**，应当针对 `pair_and_classify` 写专门测试，而不是让 12 个内核各复制一套事务代码。

这也避免把「验证分类器」与「验证固件退出协议」混成同一个测试目的。

## 3. 两条问题的关系

### 3.1 分开裁决，共用一个收敛方向

I-28 的裁决对象是「抽象载体要不要存在」；I-29 的裁决对象是「重复实现怎么合、测试与生产怎么共用同一条数据流」。

- I-28 的删除动作会碰到已裁记录（I-22），需要正式 supersede；
- I-29 的动作是职责切分与测试改造，不需要推翻任何既定设计。

**实施顺序**：先定 I-29 的分类器边界与测试数据流，再清理 I-28 中与辅助路径有关的部分。理由是 I-29 的结论会决定 `build_memmaps` / `build_memmap` 的去留，而 `UefiMemoryMap` 与 A1 的命运取决于那一步。

### 3.2 同类现象：`BootShim`（明确不在本文射程内）

- `os/libs/minix-boot/src/boot_shim.rs` 的 `trait BootShim` 有两个实现：`RiscvUbootBootShim`（L3 生产使用）与 `UefiBootShim`（零调用方，即 A1）。
- 唯一的调用点是 `os/boot-shim/src/uboot_main.rs` 的全限定静态调用 `<RiscvUbootBootShim as BootShim>::prepare_boot(1024)`——同样是具体类型，没有来源可替换性。
- 这条 trait 的文档注释写着「内核接收 `&dyn BootShim` 或泛型 `B: BootShim`」「代码统一使用该 trait，没有条件编译」。这两句都与现状不符：内核根本不接收 `BootShim`，它接收的是 `KernelInfo` 交接结构。

**定性**：`BootShim` 文档的接口形状与实际调用不符，属于另一项**独立的文档与抽象一致性问题**，不并入 I-28 裁决。它与 `MemoryMapSource` 的相似之处仅在「注释宣称了不存在的接口形状」；不同之处是它有一条真实生产实现，因此不应一起删除。

**与 I-29 的关系也需说清**：第四轮评审提醒的一点本文采纳——讨论 I-28 的删除**不是在反对 trait 或静态分发**。§2.6.3 提出的私有 sink 就可能是合理的设计，因为它有两个真实消费者（生产写交接区、测试写静态数组）。两条结论并不矛盾：I-28 的问题是「没有消费者利用它承诺的来源可替换性」，不是「trait 不好」。

## 4. 事实 / 推理 / 待验证

**本文核实过的事实**

1. `MemoryMapSource` 的单方法与三个实现；只有 `DtbMemoryMap` 有真实调用方，且调用方均显式指定类型；另两个实现无消费者。
2. 全仓无 `dyn` 或泛型约束用法；调用点全部是具体类型或全限定形式。
3. `UefiBootShim::prepare_boot` 零生产调用方；提及它的地方都是「为什么不用」的注释。
4. 生产 UEFI 路径经 `pair_and_classify` 与 `classify_map`，不经过该 trait；分类与退出共用同一个 MapKey；重试时重新读图并重新分类；**读图与退出之间没有任何分配**。
5. `classify_map` 与 `build_memmaps` 的三条分流规则逐条相同；六项输入校验与一项诊断打印不同。
6. `PA_LIMIT` 与 `build_memmaps` 在同一文件里相邻，但只有生产路径使用它。
7. 依赖 `uefi` 0.33.0 的 `exit_boot_services` 会先做一次池分配、再重新读图取键、再退出，最多两轮，成功时返回内含该缓冲的 `MemoryMapOwned`；`build_memmaps` 路径把返回值丢弃。
8. 12 个夹具型测试内核的顺序是「快照 → 分配 root → 分配 bump」，且**不调用** `assert_bootstrap_outside_memmap`；2 个 `test-memmap` 不调用退出。
9. `build_memmaps` 的输出 `Vec` 容量增长与 boxed slice 的 backing allocation 发生在它取到快照**之后**；`Box::leak` 本身不分配，只阻止释放。但 `AllocatePool` **不必然**产生新描述符——只有池需要扩容时才从常规内存取页。
10. 持续集成里 `cmd-smoke` 作业的 x86-64 与 aarch64 两条腿用真实 boot-shim 启动，因此真实固件内存图确实经过生产 `classify_map`；但不校验分类结果。
11. `test-shim-bootmarks-x86.sh` / `-aarch64.sh` 自陈未注册进总入口脚本；持续集成工作流列表里也无对应条目。
12. `classify_map` 有 12 条宿主单元测试，输入均为构造数据；**没有一条覆盖「起点恰好等于 `ram_top`」这个边界**（现有那条覆盖的是「起点在 `ram_top` 之上」）。
13. `Serializer::new` 要求缓冲不小于 `ARENA_CAP`（16 KiB）并清零；两份分类分区容量为 128 与 256 条。
14. `assert_bootstrap_outside_memmap` 只遍历**可用表**做相交检查，不检查保留表。
15. `BootShim` 的文档注释描述了一种不存在的接口形状。
16. 三种自举分配（根页表页、bump 池、arena）用 `AllocateType::MaxAddress(bootstrap_alloc_limit(..))`；`bootstrap_alloc_limit` 的界是 `min(4 GiB 恒等窗口, VM 直接映射窗口物理上界)`。
17. 内核侧的直接映射候选里，根页表页与 bump 池由独立来源（source 2）登记，来源是交接携带的根页表物理地址与 `boot_alloc` 记录的 bump 区间，**与 `reserved_regions` 无关**；arena 与读图缓冲不被内核访问。
18. `boot::memory_map` 返回 `MemoryMapOwned`；其 `MemoryMapBackingMemory` 的 `Drop` 只在引导服务仍存活时 `free_pool`，退出后跳过。`build_memmaps` 的局部变量在函数返回时被释放——但**底层页是否立刻变回常规内存未经证实**（池实现可能只归还空闲块）。
19. `uefi` 0.33.0 的 `trait MemoryMap` 公开 `meta()` / `buffer()` / `entries()`；`MemoryMapOwned` 实现该 trait，因此退出后可以取得原始描述符字节加元数据。
20. `meta().map_size` 是有效长度，`buffer()` 返回分配长度（含冗余条目），两者不可混用。
21. `RawMemoryDescriptor` 只有三个字段（类型、物理起点、页数），**不读 `Attribute`**（该字段位于描述符偏移 32）。
22. 分类器只定义三个类型常量（7 / 11 / 12），其余类型——包括 `RESERVED(0)`、`UNUSABLE(8)`、`PAL_CODE(13)`、`PERSISTENT(14)`、`UNACCEPTED(15)` 与三个未知数值区间——全部落进「低于 RAM 顶即进保留表」的分支。
23. 直接映射两个窗口用固定页标志且不含缓存/设备位；硬件层三架构不同：aarch64 由 `MAIR_EL1 = 0xFF` 的 Attr0 定到 Normal WBWA；x86-64 的 `flags_to_pte` 不设 `PCD`/`PWT` 且全仓不编程 `IA32_PAT`——**条件成立才为 WB**（PAT0 未被固件改写且 MTRR 允许）；riscv64 的 Sv39 缓存性由平台 PMA 决定——**本仓 `flags_to_pte` 不编码 PBMT**（Svpbmt 扩展定义了 PBMT 位 62–61，S-mode 可用性受 `menvcfg.PBMTE` 控制）。
24. 本项目没有调用 `uefi::helpers::init()`，因此没有注册 logger；且 `exit_boot_services` 的第一句调用 `helpers::exit()` → `logger::disable()`，把日志输出指针置空，`Logger::log()` 在指针为空时直接返回。
25. `boot-shim` 对 `uefi` 只启用 `alloc` 特性，未启用 `logger` / `log-debugcon`。
26. UEFI 的内存类型数值分四段：`0..15` 标准类型；`0x10..0x6FFFFFFF` 保留数值区（非 OEM）；`0x70000000..0x7FFFFFFF` OEM 保留；`0x80000000..0xFFFFFFFF` OS loader 保留。
27. `AllocateMaxAddress` 的规范约束是「分配区间的最高地址 ≤ 输入值」，不是「起点 ≤ 输入值」。当前代码传 `bound - size`，比规范要求（传 `bound - 1` 即足够）更严格，差额 `size - 1` 字节。
28. `UefiPoolAllocator` 每次 `alloc` 走 `allocate_pool`，`dealloc` 为空实现；其注释「池页在退出时由固件整体回收」与 UEFI 的退出后内存归属规则不符。
29. `ram_top` 判据只检查描述符起点：不证明描述符整体在 RAM 包络内，也不截断越界尾部（§2.5.6.1 形态二）。

**本文的推理（需评审者独立判断）**

1. 生产腿接不进 `MemoryMapSource` 的原因是抽象层次选错（抽象「来源」而非「控制流」）。
2. 两条分类实现的分野不只在校验项数量，更在「分类结果对应哪一刻的内存图」。
3. 零来源可替换性的 trait 的主要危害是误导后续维护者，而非运行期成本。
4. 返回空表的占位实现会把编译期可发现的问题推迟成运行期故障。
5. 若按 §2.6 的接缝收敛，③ 段将获得两个真实消费者，从而满足「值得抽象」的判据。
6. `ram_top` 的严格小于在「最高端自举分配」这个形态上会让保留表漏记，但当前没有功能性后果；保留表作为「完备的占用清单」这一隐含期望是脆弱的。
7. 把 `BOOT_SERVICES_*` 与 `ACPI_RECLAIM` 永久排除是合理的早期策略，但必须成文为政策，否则会被误认为分类规则的逻辑后果。
8. 保留表的成员集合大于它的语义定义所允许的集合（`RESERVED`/`UNUSABLE`/`UNACCEPTED` 三类明确冲突），这是比 `ram_top` 边界更根本的问题。
9. 用地址条件替代类型判断，会把「类型语义不明」伪装成「地址包含」问题；正确的收敛顺序是先定类型策略、再定地址过滤。
10. `Excluded` / `Special` 两种处置必须可观测，且含义不同：`Excluded` 允许统计排除，`Special` 必须保留完整地址范围或拒绝启动（§2.5.7.2）。
11. 「类型 → 处置」的编译保护有前提：`_ =>` 通配会吞掉新增类型，必须 `KnownMemoryType` 枚举 + 无通配 `match` + 未知值单独携带（§2.5.7.2）。
12. ~~`ram_top` 可以保留但应降级为「结果裁剪」~~（v7 撤回）~~→ 改为「结果裁剪」~~（v8 终版）：**从分类器中删除**。撤回理由见 §2.5.7.3（Conventional 并集裁掉自举内存、`[0, ram_top)` 丢高地址内存、类型字段本来就是更直接的分类来源）。
13. 两遍扫描的理由要随 `ram_top` 的删除而更新：旧理由（第一遍算 `ram_top`）失效，新理由是「先验证全部待输出描述符、再写输出」的事务性保证；是否保留两遍由输出接缝原型决定（§2.6.2）。

**本文未核实的边界（待验证）**

### 6.2 生产分类器 `classify_map`（含算术安全的完整证据）

`os/boot-shim/src/ebs_map.rs`：

```rust
fn read_u32(bytes: &[u8], off: usize) -> u32 {
    u32::from_le_bytes(bytes[off..off + 4].try_into().unwrap())
}
fn read_u64(bytes: &[u8], off: usize) -> u64 {
    u64::from_le_bytes(bytes[off..off + 8].try_into().unwrap())
}

fn descriptor_at(map: &[u8], off: usize) -> RawMemoryDescriptor {
    RawMemoryDescriptor {
        ty: read_u32(map, off),
        physical_start: read_u64(map, off + 8),
        number_of_pages: read_u64(map, off + 24),
    }
}

/// Validate `[phys, phys + pages*4096)` and return its byte length.
fn checked_len(desc: &RawMemoryDescriptor, pa_limit: u64) -> Result<u64, MapError> {
    if desc.number_of_pages == 0 {
        return Err(MapError::ZeroPageCount);
    }
    let len = desc
        .number_of_pages
        .checked_mul(PAGE_SIZE)
        .ok_or(MapError::LengthOverflow)?;
    let end = desc
        .physical_start
        .checked_add(len)
        .ok_or(MapError::RangeOverflow)?;
    if end > pa_limit {
        return Err(MapError::OutOfPhysRange);
    }
    Ok(len)
}

pub fn classify_map(
    map: &[u8],
    map_size: usize,
    descriptor_size: usize,
    descriptor_version: u32,
    pa_limit: u64,
    serializer: &mut Serializer<'_>,
) -> Result<Classification, MapError> {
    if descriptor_version != MEMORY_DESCRIPTOR_VERSION {
        return Err(MapError::UnsupportedVersion);
    }
    if descriptor_size < MEMORY_DESCRIPTOR_SIZE {
        return Err(MapError::DescriptorTooSmall);
    }
    if !descriptor_size.is_multiple_of(8) {
        return Err(MapError::DescriptorSizeNotAligned);
    }
    if map_size > map.len() {
        return Err(MapError::MapSizeBeyondBuffer);
    }
    if !map_size.is_multiple_of(descriptor_size) {
        return Err(MapError::MapSizeNotMultiple);
    }

    let entries = map_size / descriptor_size;

    // Pass 1: RAM ceiling from the conventional entries.
    let mut ram_top = 0u64;
    for i in 0..entries {
        let desc = descriptor_at(&map[..map_size], i * descriptor_size);
        if desc.ty != CONVENTIONAL_TYPE { continue; }
        let len = checked_len(&desc, pa_limit)?;
        let end = desc.physical_start + len;     // 已被 checked_add 保证不溢出
        if end > ram_top { ram_top = end; }
    }

    // Pass 2: classify.
    for i in 0..entries {
        let desc = descriptor_at(&map[..map_size], i * descriptor_size);
        if desc.ty == MMIO_TYPE || desc.ty == MMIO_PORT_SPACE_TYPE {
            continue;
        }
        if desc.ty == CONVENTIONAL_TYPE {
            let len = checked_len(&desc, pa_limit)?;
            serializer.push_memmap(MemoryRegion {
                base: PhysBytes(desc.physical_start),
                len: len as usize,
            })?;
        } else if desc.physical_start < ram_top {
            let len = checked_len(&desc, pa_limit)?;
            serializer.push_reserved(MemoryRegion {
                base: PhysBytes(desc.physical_start),
                len: len as usize,
            })?;
        }
    }
    serializer.finish_memmap();
    serializer.finish_reserved();
    Ok(Classification { conventional, reserved })
}
```

**证据闭合说明**（回应「摘录里的加法看起来未经检查」）：`checked_len` 在返回长度之前已经做了两步检查——`checked_mul` 保证 `pages × 4096` 不溢出（否则 `LengthOverflow`），`checked_add` 保证 `physical_start + len` 不溢出（否则 `RangeOverflow`），并额外要求结果不超过 `pa_limit`。因此调用点写 `desc.physical_start + len` 是**已证明不会溢出**的加法；它不是裸加法，而是前面那道检查的后置条件。

### 6.5 自举分配与那道闸

```rust
/// Refuse to boot if a conventional memmap range overlaps the bootstrap
/// allocation `[base, base + len)`.
fn assert_bootstrap_outside_memmap(memmap: &[MemoryRegion], base: u64, len: u64) {
    for r in memmap {                         // 只遍历「可用表」
        let rbase = r.base.0;
        let rend = rbase + r.len as u64;
        assert!(
            base + len <= rbase || rend <= base,
            "conventional memmap [{rbase:#x}, {rend:#x}) overlaps bootstrap allocation [{base:#x}, {:#x})",
            base + len
        );
    }
}

pub fn alloc_root_page() -> PhysBytes {
    let ptr = boot::allocate_pages(
        AllocateType::MaxAddress(bootstrap_alloc_limit(PAGE_SIZE)),
        MemoryType::LOADER_DATA,
        1,
    ).expect("Failed to allocate root page below DM-admissible bound");
    PhysBytes(ptr.as_ptr() as u64)
}

pub fn alloc_bump_region(num_pages: usize) -> (u64, u64) {
    let size = (num_pages as u64) * PAGE_SIZE;
    let ptr = boot::allocate_pages(
        AllocateType::MaxAddress(bootstrap_alloc_limit(size)),
        MemoryType::LOADER_DATA,
        num_pages,
    ).expect("Failed to allocate bump region below DM-admissible bound");
    (ptr.as_ptr() as u64, ptr.as_ptr() as u64 + size)
}
```

### 6.8 内核侧为什么不受保留表漏记的影响：source 2

`os/kernel/src/dm_coverage.rs`：

```rust
/// Source 2: the VM self page-table tree — root page and boot bump region.
fn bootstrap_tree_candidates(kernel_info: &KernelInfo, root: PhysBytes) -> [Option<DmRange>; 2] {
    let in_memmap = |r: &DmRange| memmap_candidates(kernel_info)
        .any(|m| r.base < m.base + m.len && m.base < r.base + r.len);

    let root_range = DmRange::new(root.0, PAGE_SIZE);
    let bump_range = boot_alloc::boot_alloc_region().and_then(|(base, end)| { /* 与 root 去重 */ });

    let mut out = [None, None];
    if !in_memmap(&root_range) { out[0] = Some(root_range); }
    if let Some(r) = bump_range.filter(|r| !in_memmap(r)) { out[1] = Some(r); }
    out
}
```

它的输入是「交接携带的根页表物理地址」与「`boot_alloc` 记录的 bump 区间」，**不经过 `reserved_regions`**。跨镜像接收端在解码信封后调用 `boot_alloc::resume_boot_pt_alloc(bump_base, bump_next, bump_end)` 恢复该区间（`os/kernel/src/lib.rs`）。

因此 §2.5.6 描述的「保留表漏记根页表页/bump 池」在当前实现里没有功能性后果——但这依赖「source 2 恰好存在」这一事实，而保留表的语义本身仍然是残缺的。

### 6.9 自举分配的上界是怎么算出来的

`os/arch/src/lib.rs`：

```rust
/// End of the boot identity-mapped window (C: pg_identity() maps 4 GiB).
pub const BOOT_IDENTITY_MAP_END: u64 = 0x1_0000_0000;

/// Highest PA *end* any bootstrap-tree allocation may use:
/// min(BOOT_IDENTITY_MAP_END, VM DM window PA end).
pub const fn boot_dm_admissible_end() -> u64 {
    if BOOT_IDENTITY_MAP_END < CurrentDirectMap::VM_DIRECT_MAP_SIZE {
        BOOT_IDENTITY_MAP_END
    } else {
        CurrentDirectMap::VM_DIRECT_MAP_SIZE
    }
}
```

`os/boot-shim/src/uefi_helpers.rs`（**当前代码快照**——其注释与 §2.5.6.2 的裁决冲突，见下）：

```rust
/// `AllocateMaxAddress` guarantees the base is at or below the limit, so
/// passing `bound - size` keeps the whole region under the bound.
fn bootstrap_alloc_limit(size: u64) -> u64 {
    boot_dm_admissible_end()
        .checked_sub(size)
        .expect("bootstrap allocation request exceeds the DM-admissible bound")
}
```

**这段快照的解释必须与 §2.5.6.2 的裁决一致**（第七轮评审指出 v7 此处的解释与裁决直接冲突，v8 修正）：

- **当前实现**采用 `bound - size`——那是**比规范所需条件更保守**的限制，不是正确性必需；
- **目标实现**采用 `bound - 1`（§2.5.6.2 已裁决选 A）；
- 真正需要维持的不变量是：实际分配区间 `[base, base + size)` 满足 `base + size <= bound`——**不是**必须使用某一种减法公式。注释里那句「guarantees the base is at or below the limit」是错误的规范读法，随目标实现一并修正；
- 保留这段旧代码摘录的目的是记录裁决时的起点，不是为 `bound - size` 的去留背书。

### 6.10 UEFI 内存类型枚举（`uefi-raw` 0.9.0）

`src/table/boot.rs`：

### 6.11 三架构的缓存属性落实（不读 `Attribute`，但硬件结果各不相同）

**调用层**（两个直接映射窗口，`os/arch/src/arch/boot_dm.rs`）：

```rust
flags: PageFlags::kernel_read_write(),   // kernel DM
flags: PageFlags::read_write(),          // VM DM
```

`os/arch/src/arch/paging.rs`：

```rust
pub const fn read_write() -> Self {
    Self::from_bits_truncate(Self::PRESENT.bits() | Self::WRITABLE.bits() | Self::USER_ACCESSIBLE.bits())
}
pub const fn kernel_read_write() -> Self {
    Self::from_bits_truncate(Self::PRESENT.bits() | Self::WRITABLE.bits() | Self::GLOBAL.bits())

```

两者都不含 `NO_CACHE` / `WRITE_THROUGH` / `DEVICE`——即**调用方没有显式选择缓存属性**。

**硬件层：三架构各不相同。**

aarch64（`os/arch/src/arm64/paging.rs`）：

```rust
// MAIR_EL1 = 0x0000_0000_0000_00FF:
//   Attr0 = 0xFF — Normal, Write-Back Write-Allocate (RAM).
//   Attr1 = 0x00 — Device-nGnRnE (MMIO; `PageFlags::DEVICE`).
const MAIR_EL1_VALUE: u64 = 0xFF;
asm!("msr mair_el1, {}", in(reg) MAIR_EL1_VALUE);
```

描述符的 `AttrIndx` 默认为 0（位全清），因此普通映射选到 `MAIR` Attr0 = **Normal WBWA**。这是**本仓显式配置**的结果，不是默认值。

x86-64（`os/arch/src/x86_64/paging.rs`）：

```rust
fn flags_to_pte(flags: PageFlags) -> u64 {
    let mut pte = X64PteFlags::PRESENT;
    if flags.contains(PageFlags::WRITABLE) { pte |= X64PteFlags::WRITABLE; }
    if flags.contains(PageFlags::USER_ACCESSIBLE) { pte |= X64PteFlags::USER; }
    if flags.contains(PageFlags::GLOBAL) { pte |= X64PteFlags::GLOBAL; }
    if !flags.contains(PageFlags::EXECUTABLE) { pte |= X64PteFlags::NX; }
    pte.bits()
}
```

从不设 `PCD`（bit 4）与 `PWT`（bit 3）；全仓检索 `IA32_PAT` / `0x277` 无编程点。**条件性结论**：若 PAT0 未被固件改写（保持复位默认 WB），且对应物理地址的 MTRR 配置允许 WB，则该映射表现为 WB——两个前提均未被项目声明或校验。

riscv64（`os/arch/src/riscv64/paging.rs`）：

```rust
fn flags_to_pte(flags: PageFlags) -> u64 {
    let mut pte = Sv39PteFlags::V | Sv39PteFlags::A | Sv39PteFlags::D | Sv39PteFlags::R;
    if flags.contains(PageFlags::WRITABLE) { pte |= Sv39PteFlags::W; }
    if flags.contains(PageFlags::EXECUTABLE) { pte |= Sv39PteFlags::X; }
    if flags.contains(PageFlags::USER_ACCESSIBLE) { pte |= Sv39PteFlags::U; }
    if flags.contains(PageFlags::GLOBAL) { pte |= Sv39PteFlags::G; }
    pte.bits()
}
```

本仓当前的 Sv39 编码（`flags_to_pte`）**不使用 PBMT**；Svpbmt 扩展已为 Sv39 叶子 PTE 定义了 PBMT 位（62–61），S-mode 能否使用还受 `menvcfg.PBMTE` 控制。在不使用 PBMT 的前提下，缓存性由平台级的物理内存属性（PMA）决定。因此「保留表区域按写回映射」在 RISC-V 上是**项目假设**，不是编码结果，也没有被任何代码声明或校验。

### 6.13 全局分配器的实际行为

`os/boot-shim/src/uefi_helpers.rs`（12 个夹具型测试内核也用它，见 §6.6）：

```rust
pub struct UefiPoolAllocator;

unsafe impl core::alloc::GlobalAlloc for UefiPoolAllocator {
    unsafe fn alloc(&self, layout: core::alloc::Layout) -> *mut u8 {
        let size = layout.size();
        let align = layout.align();
        let alloc_size = if align > 8 { size + align } else { size };
        match boot::allocate_pool(MemoryType::LOADER_DATA, alloc_size) {
            Ok(ptr) => { /* 对齐处理 */ }
            Err(_) => core::ptr::null_mut(),
        }
    }

    unsafe fn dealloc(&self, _ptr: *mut u8, _layout: core::alloc::Layout) {
        // Pool pages are reclaimed wholesale by the firmware at
        // ExitBootServices; boot-stage code never frees individually.
    }
}
```

三点与此前议题相关：

1. **`Vec` / `Box` 的对象分配确实走 `allocate_pool`**，因此 §2.5.1 说的「池是否扩容」就是这里调用的行为。
2. **`dealloc` 是空实现**：boot 阶段的堆对象永不单独释放。但上面那条注释的**因果说错了**——不是「固件在退出时把池页整体回收」，而是「这些页作为 loader-owned 内存交给 OS」。区别在于：退出之后这些页仍然不是常规内存，不会自动变成 PMM 可分配的页。正确表述见 §2.5.9。
3. **每次 `alloc` 都是一次 `allocate_pool` 调用**，而不是从一块自管 arena 里切片——所以「输出数组会不会导致池扩容」直接取决于固件池的空闲块状况。

**这条注释的修正为什么重要**（本文的判断）：它把「退出后这些页会被回收」写成了事实，而这个错误理解很容易被下游误用——例如认为「shim 占的内存反正会自动还回来」，从而在分类时放心把这些页留在可用表里。§2.5 的整条论证恰好说明相反的事：**没人会自动还回来，必须靠内核对可用表的准确描述才安全。**

| `SP` | 有 / 无 | 同上 |
| ISA | `ISA_VALID` 出现（无论掩码取值）/ `ISA_MASK`≠0 且 `ISA_VALID`=0 / 两者均未出现 | 前两分支 → **分类错误**（§2.5.7.7 政策：出现即 fail-closed）；第三分支 → 正常进入后续裁决（v12 对齐：v11 维度表把 `ISA_VALID=1` 标成「合法」与政策表矛盾） |
| 未支持属性位 | 出现 / 不出现 | 出现 → 记录进诊断、不静默忽略（`MORE_RELIABLE`/`CPU_CRYPTO` 登记不解释；2.11+ 新位按未知属性 fail-closed） |
| **裁决顺序组合** | `RESERVED+NV` / `UNUSABLE+SP` / `MMIO+RUNTIME` / `PAL_CODE+NV` | 按五步顺序落定（§2.5.7.7 四组合表）：`Excluded` / `Excluded` / 设备路径 / 拒绝启动 |

矩阵与全部受影响 `MemoryType` 交叉（`CONVENTIONAL`、`LOADER_DATA`、`RUNTIME_SERVICES_*`、`RESERVED` 等政策相关类型）。不必穷举整个 64 位 `Attribute` 空间，但**政策定义过的组合必须穷尽**——否则「任何组合都有唯一结果」只是设计宣言，不是已验证的合同。

**政策表批准的两个注意点**（沿用并收束）：其一，完整性判据是组合空间无空洞，不是「每个已知属性位都有一行」——五步顺序保证按固定路径走完，任何组合必然落在唯一输出上；其二，三架构 WB 合同是唯一可能**反向修改**政策表的力量——某架构无法表达某类区域所需的映射属性时，对应条目从 `ReservedMapped` 降级 `Excluded`，因此第 4 步批准前政策表保留「待架构核」标记。

**维持非阻塞**：DTB 来源政策（I-29-11）、bootmarks 路标合并。

**样本实验的注意事项**（沿用）：标注为「QEMU + OVMF/AAVMF 目标固件运行样本」；四个时点；每条记录 `Type`、`PhysicalStart`、`NumberOfPages`、`Attribute`；探针使用预分配输出避免自污染。

## 附录 B：术语速查

| 术语 | 含义 |
|---|---|
| UEFI / Boot Services | 一类固件接口标准；Boot Services 是其中的引导期服务集合，退出后失效 |
| `ExitBootServices` | 退出 Boot Services 的调用，需要携带最近一次读内存图得到的 MapKey |
| MapKey | 内存图的版本戳；分类必须处理取得该键的同一次快照，并用同一次读取的键退出 |
| 设备树 / DTB | 固件交给操作系统的二进制硬件描述，`/memory` 节点列出物理内存区间 |
| 可用表 / 保留表 | 本文对两份内存清单的称呼：可自由分配 / 可访问但不可再分配 |
| 物理内存管理器（PMM） | 内核里管理物理页帧分配与回收的组件 |
| 直接映射（Direct Map） | 把全部物理内存线性映射到内核虚拟地址区，便于按物理地址访问 |
| 引导腿 | 本文对「一条从固件到内核入口的具体路径」的称呼 |
| 测试内核 | 比真内核小、调用真内核部分函数后打印 PASS 的 UEFI 应用 |
| 夹具型测试 | 只把某份数据当作输入、不对该数据本身做断言，被测对象是别的代码 |
| 自举分配 | boot-shim 在把控制权交给内核之前自己占用的内存（根页表页、bump 池、arena 等） |
| 交接区（arena） | 跨镜像传递数据的固定布局缓冲，地址以基址加偏移推导，不含进程内指针 |
| 来源可替换性 | 调用方无需知道具体实现类型即可使用不同实现的能力（`dyn` 或泛型） |
| `ram_top`（RAM 顶） | 一次分类扫描中，所有常规内存区间末端地址的最大值。本文 §2.5.6 讨论它作为保留表上界的边界问题 |
| `AllocateMaxAddress` | UEFI 的一种分配方式：只规定分配结果的地址上界，不规定分配器在界内取哪个位置 |
| `LoaderData` / `BootServicesData` 等 | UEFI 的内存类型标签；区分「引导程序自己的数据」与「引导服务的数据」，二者在退出引导服务后的可回收性不同 |
| `AllocatePages` / `AllocatePool` | 两种 UEFI 分配方式：前者直接向页分配器要页（必然改变内存图），后者从内存池取块（只有池扩容时才改变内存图） |
| 描述符 `Attribute` | `EFI_MEMORY_DESCRIPTOR` 的第四个字段，描述缓存属性与运行期属性；本项目当前未读取 |
| `UNACCEPTED` | UEFI 内存类型 15，表示需要先被「接受」才能使用的内存；把它当成普通可访问内存是错误的 |
