## 0. 阅读指引

### 0.1 这件事在系统里的位置

一个操作系统启动时要回答的第一个问题不是「怎么调度」，而是「我手上有哪些物理内存」。机器刚上电时，只有固件知道答案：哪些地址是真正的随机存取存储器、哪些是设备寄存器、哪些被固件自己占着、哪些坏了不许碰。固件把这份答案写成一张**物理内存区间的清单**交给引导程序，引导程序把它翻译成内核能用的形式，再交控制权——此后内核只能靠自己记账。这张清单就是本文说的**内存图**。

翻译这一步做错，后果不在引导期暴露，而在很久之后：一块设备寄存器被当成普通内存映射，内核的内存分配器可能把一个缓冲区放进去，写进去的数据消失、读出来的数据无意义，或者机器直接故障；一块坏内存被当成可用内存，随机位翻转会在几个月后伪装成软件缺陷。因此**分类规则必须唯一、必须可解释**——这正是本组问题的主题。

本项目支持三个处理器架构（x86-64、AArch64、RISC-V 64 位），引导期有两条不同的来源：UEFI 固件给出内存图，设备树（一种二进制硬件描述）给出内存节点。两条来源各自经过自己的政策，汇进内核统一的内存语义。

本文用两个验证层次的专有名词：**真机**=把镜像真正在 QEMU 上启动起来、由判定脚本按行读串口输出判通过/失败的形态（三个架构各有一条腿）；**宿主测试**=在开发机上直接运行、不需要固件或模拟器的单元测试。文中说「需要真机读数」，意思是这件事在宿主测试里无法回答。

### 0.2 UEFI 内存图描述符的形状（规范事实）

每条描述符有四个语义字段，版本 1 的规范长度是 40 字节（另有一个 4 字节的补齐位）：

| 偏移 | 字段 | 宽度 | 内容 |
|---|---|---|---|
| 0 | `Type` | 32 位 | 这块区域**是什么** |
| 4 | 补齐 | 32 位 | 恒为零，只为把下一个字段推到 8 字节边界 |
| 8 | `PhysicalStart` | 64 位 | 物理起点（页对齐） |
| 16 | `VirtualStart` | 64 位 | 运行期虚拟地址，引导期读到的是未转换的原值 |
| 24 | `NumberOfPages` | 64 位 | 页数（每页 4 KiB） |
| 32 | `Attribute` | 64 位 | 这块区域**支持怎么用** |

分类器只用到 `Type`、`PhysicalStart`、`NumberOfPages`、`Attribute` 四个字段；`VirtualStart` 与补齐位属于「结构里有、语义上此刻用不上」。

两个容易踩的形状事实：

- **步长可以大于 40**。固件按「未来可能加字段」的方式排布描述符，实际步长由固件自己报告。因此「缓冲区长度 ÷ 40」推不出条数，任何假设步长等于 40 的实现都可能读到空洞。
- **`Type` 与 `Attribute` 是两个正交的维度**。类型是固件对区域用途的断言，属性是那块区域支持的**能力**位图——它表示「可以做到什么」，不是「此刻正在被怎么用」。把属性读出来原样翻译成页表标志是错的，只按类型分类同样是错的。**这一条是第 7.1 节那个阻断项的根源**：既然属性位是能力位，「某个位是什么含义」完全由规范版本决定，位定义猜错就等于把已知位判成未知位、或反过来。

标准类型有 16 个（数值 0 到 15）：`RESERVED`(0)、`LOADER_CODE`(1)、`LOADER_DATA`(2)、`BOOT_SERVICES_CODE`(3)、`BOOT_SERVICES_DATA`(4)、`RUNTIME_SERVICES_CODE`(5)、`RUNTIME_SERVICES_DATA`(6)、`CONVENTIONAL`(7)、`UNUSABLE`(8)、`ACPI_RECLAIM`(9)、`ACPI_NVS`(10)、`MMIO`(11)、`MMIO_PORT_SPACE`(12)、`PAL_CODE`(13)、`PERSISTENT`(14)、`UNACCEPTED`(15)。数值更高的区段分三段：标准类型之后的**未分配数值区**（`0x10` 到 `0x6FFFFFFF`）、**OEM 保留区**（`0x70000000` 到 `0x7FFFFFFF`）、**OS loader 保留区**（`0x80000000` 到 `0xFFFFFFFF`）——三段语义不同，不能并成一段处理。

属性位图里本文会反复出现的位：**缓存类** `UC`/`WC`/`WT`/`WB`/`UCE`（以及现代用法同属缓存策略的 `WP`）；**保护能力** `RO`/`RP`/`XP`（硬件能做到什么，不是当前权限）；**独立用途属性** `RUNTIME`（需要运行期重新映射）、`NV`（非易失）、`SP`（特定用途内存）；**元信息** `MORE_RELIABLE`、`CPU_CRYPTO`；**ISA 掩码**（一组架构专用位加一个 `ISA_VALID` 有效位）。位定义基线取 **UEFI 2.10**，理由与代价见第 2 节行 1 与第 7.1 节。

### 0.3 分类要产出的东西，以及「映射」这个词的两棵树

内核最终拿到两份区间表，外加一份引导期内部的诊断清单：

| 输出 | 语义 | 是否跨引导边界 |
|---|---|---|
| **可用表** | 普通物理内存，可以交给内核的物理页分配器 | 是，写进交接结构 |
| **保留表** | 运行期可以经「直接映射」访问，但不得再分配出去 | 是，写进交接结构 |
| **side list**（第三份输出） | **保留但不建普通映射**的范围，只用于确认「哪些区间因为政策被挡在两张表之外」 | 否，只是引导壳内部诊断，不进交接结构 |

这里有两个容易混淆的概念，本文必须分开使用：

- **直接映射**（Direct Map）：内核把物理内存线性地映进自己的虚拟地址空间，于是「物理地址加一个固定偏移」就能访问。它决定「内核能不能读到这块地址」。
- **物理页分配器**（PMM）：内核把空闲页分给各个使用者。它决定「这块地址能不能被拿去当普通内存用」。

一个区域可以「必须映射但不许分配」（固件常驻区），也可以「必须保留但不该映射」（运行期服务代码）。用一个 `reserved` 标签同时回答这两个问题，会把「能不能分配」与「要不要映射」压成一位，两类错误因此互相掩盖。

**关键补充（代码事实，也是新增裁决六的由来）**：本仓在这个阶段存在**两棵不同的页表树**，「建不建普通映射」这句话在两棵树上的答案不同：

| 树 | 覆盖范围怎么决定 | 类型政策与设备树政策是否参与 |
|---|---|---|
| **引导根**（内核建立的第一棵树，切到最终根之前一直在用） | 恒等段按大页粒度从地址 0 一路铺到 4 GiB 的上界常量（`IDENTITY_MAP_END`）；只有落在「已知设备窗口清单」里的大块会被拆成 2 MiB 粒度并按片加设备属性，其余一律按普通可读写可执行映射，映射失败（地址无物理内存支撑）直接忽略 | **不参与**。分类结果的可用表、保留表、诊断成员、被排除范围都不进入这段构造 |
| **最终直接映射**（内核正式的物理别名区） | 由四个来源的并集构造：可用表区间、自举页表树、登记的启动模块、保留表区间 | 参与（保留表在这里出现，被排除的范围不进任何来源） |

于是一句「side list 里的范围不建普通映射」在当前实现里只对第二棵树成立；第一棵树会把低 4 GiB 里的一切（包括被排除的区间与设备树 `no-map` 区间）按普通内存映射一遍，直到切根之后才消失。这个不对称同时改变裁决二行 3、裁决三与裁决四的判断，详见第 6 节。

一次分类被拆成三段职责（已冻结）：

1. **解析**：校验固件报告的版本、步长、缓冲区边界，逐条读出四个字段，并检查起点是否 4 KiB 对齐、长度会不会溢出。
2. **裁决**：对每条描述符决定去向（分配 / 保留映射 / 进 side list / 排除 / 走设备路径）。
3. **输出**：**两遍**。第一遍只做裁决和计数，并预检三个输出容器的容量——它是唯一可能失败的一遍；第二遍只写入，不返回错误。第二遍的「不可失败」由类型表达：第一遍产出一个「已验证的计划」凭证，只有持有凭证才能调用写入。

还有两条地址维度的合同，也属于已冻结：

- **架构可表达能力**：分类器检查「这条描述符的末端是否落在本架构页表能表达的物理地址范围内」（半开上界语义）。这是能力检查，不是「是不是 RAM」的判断。
- **映射覆盖验收**：内核是否真的为某个区间建立了直接映射，由另一层的映射规划与验收负责。**通过上界检查不等于覆盖成立**——地址在处理器能表达的范围内，却可能超出项目实际分配的映射窗口。第一轮评审把这条推进一步：覆盖验收必须**指明是哪棵树**，这正是裁决六。

## 1. 裁决一：三个架构的「普通主存语义」最低保证合同

**第一轮结果：选丙（分层最低保证）。** 本节已按评审意见改写措辞与合同；签字仍缺硬件证据。

### 1.1 机制背景：固件声明的属性，和硬件真正给的属性，不是同一件事

冻-8 要求任何进两张表的区间先证明自己支持普通主存语义。目前的证据来自描述符的 `WB` 位。但 `WB` 位是**固件对硬件能力的声明**；一块地址被映射之后究竟按什么缓存策略访问，由**内核自己建立的页表**与**架构的缓存控制机制**共同决定。三架构的机制完全不同：

| 架构 | 谁决定有效缓存属性 | 本项目的现状（代码事实） |
|---|---|---|
| x86-64 | 页表项的 `PCD`/`PWT` 两位选择 `IA32_PAT` 模型专用寄存器里的 8 个表项之一；该表项若写成「跟随 MTRR」，再由该物理地址的 MTRR 范围寄存器决定 | 建立映射时从不设 `PCD`/`PWT`，因此总是落在 `PAT0`；本项目不编程 `IA32_PAT`，也不读 MTRR；`PAT` 是**每个逻辑处理器各有一份**的寄存器，引导处理器写的值不会自动传给从处理器 |
| AArch64 | 叶子页表项的 `AttrIndx` 三位选择 `MAIR_EL1` 里 8 个字节属性之一 | 内核在开启分页前把 `MAIR_EL1` 写成 `0xFF`（Attr0 = Normal Write-Back Write-Allocate），设备区用 Attr1（Device-nGnRnE）；**从处理器的早期入口段也写了同一个值**，这一条已经对称 |
| RISC-V 64 | 页表项（Sv39）**没有缓存属性字段**；普通内存的属性由平台级物理内存属性决定，而物理内存属性归 M 态软件管理 | 建立映射时只写权限位；不使用可选的 Svpbmt 扩展；没有可查询各区间实际策略的通用只读寄存器 |

由此得到三条强度不同的结论（**推理**，前提都是上表的可复核事实）：

- **AArch64 机制上闭合，还差「用到的属性索引」这一层**：`MAIR_EL1 = 0xFF` 只证明 Attr0 是 Normal Write-Back Write-Allocate，**不证明实际建立的每个普通映射叶子都取了 Attr0**。要证的是叶子索引，不是表值。
- **x86-64 是一个条件句，不是事实**：准确表述是「**若** `PAT0` 仍保持复位默认值（写回），**且**该物理地址的 MTRR 允许写回，则映射表现为写回」。这两个前提本项目既没有声明也没有校验。引导壳运行在 UEFI 固件之后，固件有权改写 `IA32_PAT` 与 MTRR。**而且这条依赖已经在本仓被当成前提用了一次**：x86-64 的中断控制器寄存器页（LAPIC / IO-APIC）不靠页表位取「不可缓存」属性（页表没有逐页的设备位），而是靠**固件建立的 MTRR** 拿到。同一份 MTRR 状态把普通 DRAM 判成什么，却没有任何地方声明或检查。
- **RISC-V 64 只能写成平台合同**：可选的 Svpbmt 扩展给页表项加了两位（PBMT），取值只有「跟随物理内存属性」「不可缓存主存」「强序 I/O」三种——**没有一个「强制写回」的编码**；而且 S-mode 能不能用这两位，由 M-mode 侧的 `menvcfg.PBMTE` 控制，该位为 0 时行为等同扩展不存在。本仓另有一条镜像记录：设备窗口的说明里写明「按普通写回缓存映射在模拟器上能用、在真实硬件上不满足设备语义」——模拟器的宽容掩盖了「平台属性没有合同」这件事，同样的掩盖对普通内存也成立。

**措辞修正（采纳第一轮评审）**：本文不再把 RISC-V 的合同写成「保证与 x86、AArch64 相同的写回缓存策略」。三架构统一的是**操作系统所需的普通主存语义**——缓存可用、一致性成立、访问与原子操作符合主存预期；`WB` 是 x86 与 ARM 上表达它的具体属性名称，不是 RISC-V 物理内存属性必须逐字兑现的同一硬件机制。

### 1.2 不写这条合同会具体坏在哪里（反向推演）

- **x86-64**：固件把 `PAT0` 改成不可缓存（例如某个调试配置留下的状态），内核的全部直接映射内存变成不可缓存访问。系统**能正常启动、能跑完所有测试**，只是内存带宽掉到一小部分，且写合并与原子行为的差别只在特定负载下暴露。没有报错，没有日志——因为这条路径上的每一步都「合法」。
- **AArch64**：如果存在一条构造路径把普通内存叶子的 `AttrIndx` 落到 Attr1（Device-nGnRnE），普通内存变成设备内存：非对齐访问直接产生对齐异常，读出未写过的地址返回零字节而不是脏数据。表现为「内核在某些随机点上死掉」。
- **RISC-V 64**：平台把某段 DRAM 的物理内存属性配成非主存属性，内核却把它当普通内存分配出去——页缓存里的数据与设备侧看到的数据不一致，故障形态是数据损坏而非崩溃。

三种坏法共同说明一件事：**「描述符有 `WB` 位」不能推出「内核的映射按普通主存语义访问」**，中间那一跳需要每个架构各自的一条可验收承诺。

### 1.3 选定合同：分层最低保证（丙案），逐架构落成可验收条款

| 架构 | 第一版承诺 | 具体条款 | 验收读数 |
|---|---|---|---|
| x86-64 | **`PAT` 由内核自建，MTRR 只读并分析** | ① 内核建立自己的 `PAT` 表，明确规定一个索引 = 写回、一个索引 = 不可缓存；② 普通内存页表项**显式使用写回索引**，不再依赖「当前页表项恰好落在 `PAT0`」；③ 设备寄存器页**显式使用不可缓存索引**，不再依赖固件 MTRR 恰好把 LAPIC / IO-APIC 判成不可缓存；④ 所有逻辑处理器使用同一份 `PAT` 布局，从处理器上线前完成初始化，改 `PAT` 之后按架构手册处理缓存与转换查找缓冲一致性；⑤ 读 MTRR 并对每个物理区间算出有效类型 | 见 §1.5 第一行；④ 是本仓现状完全缺失的一项（全仓没有 `PAT` 编程点，从处理器路径也没有） |
| AArch64 | **静态审计 + 实际页表遍历，两者都做** | 静态审计证明所有普通直接映射叶子都经过统一的描述符构造路径、索引取 Attr0，设备路径取另一个索引；运行时在切到执行环境之前遍历**实际建立**的叶子，核实普通内存叶子的索引、设备叶子的索引、`MAIR_EL1` 的读回值、以及普通内存页的共享性与本项目的多核合同一致 | 遍历只作为集成验收与调试构建的断言，不进生产启动路径 |
| RISC-V 64 | **平台合同 + 支持平台清单**，不设计通用运行期探针 | 每个受支持平台记录其芯片/平台文档对主存物理内存属性的承诺；用设备树的平台识别信息把启动目标关联到这份承诺；**未列入清单的平台不得仅凭「模拟器能启动」认定符合合同** | 清单、承诺来源、关联方式三项 |

对 MTRR 的分析结果，采纳评审给出的三态处置（**这一条否决了本方上一版的「按区域静默降级」**）：

| MTRR 分析结果 | 处置 |
|---|---|
| 普通内存区间的有效类型是写回 | 允许进入普通映射候选 |
| 某区间有效类型明确不是写回，且该区间不含本次启动必需的对象 | 不进两张表，走诊断 / side list 路径 |
| 重叠配置无法按架构规则确定有效类型，或核心启动对象拿不到它必需的属性 | 判为当前平台不受支持，拒绝启动 |

要点是**「无法分析」与「确定为不可缓存」是两件事**：前者是能力缺失（应当大声失败），后者是政策结论（可以降级）。把它们混成一条「凡异常就降级」会把读不到的配置当成已满足。

### 1.4 请评审人回答（本轮剩余）

1. x86-64 条款 ③（设备页显式取不可缓存索引）会把现有的「x86 设备窗口清单为空」这个事实改掉。它应当与内存图政策同批落地，还是先做 ①②④⑤、把 ③ 单独登记为一条架构属性缺陷？本方倾向同批——理由是本简报已经承认设备侧同样依赖固件 MTRR，分开做等于把一个已知隐式前提留到下一轮。
2. AArch64 的运行时遍历放在「切执行环境之前」还是「切最终根之后各跑一次」？本方倾向前者（此时两棵树的构造都已完成，能同时验证裁决六的作用域）。
3. RISC-V 的支持平台清单第一版到底包含什么？本仓的验证环境只有模拟器形态，**没有任何真实板卡的支持声明**；如果清单只有「模拟器 virt 机器」，那这条合同的实质是「我们在自己控制的平台上验证过」，评审人是否接受这个强度。

### 1.5 需要补的证据（按第一轮意见替换）

| 架构 | 必须提交的证据 |
|---|---|
| x86-64 | `PAT` 初始化代码；各逻辑处理器 `PAT` 一致性的处理位置；MTRR 原始读数与其有效类型分析；设备页取不可缓存索引的实际验证 |

## 2. 裁决二：类型 × 属性政策矩阵的逐行批准

### 2.1 机制背景：五步裁决顺序（已冻结，冻-6）

分类器对每条描述符走同一条路径，任何组合都必须落在唯一的输出上：

| 步 | 判断 | 结果 |
|---|---|---|
| 1 | **未知或不支持的条件** | 类型不在 0–15 之内（即三段未知数值区）→ 分类错误；ISA 属性位出现（无论有效位怎么取）或 ISA 掩码非零而有效位为零 → 分类错误 |
| 2 | **存在即拒绝启动的类型** | `UNACCEPTED`(15)、`PAL_CODE`(13) → 终止引导。前者是「还没被接受的内存」（在支持机密计算的平台上读它会直接故障），后者是处理器相关代码，本项目不支持 |
| 3 | **类型强制处置（类型胜过属性）** | `RESERVED`(0)、`UNUSABLE`(8) → 排除；`MMIO`(11)、`MMIO_PORT_SPACE`(12) → 走设备窗口路径。这两类的属性位**不改变处置**，理由是类型回答「这块区域是什么」，属性回答「能怎么用」；固件声明「不许触碰」不能被任何属性改判 |
| 4 | **普通内存候选 × 独立属性** | 候选类型是 `CONVENTIONAL`、`LOADER_CODE`、`LOADER_DATA`、`BOOT_SERVICES_CODE/DATA`、`ACPI_RECLAIM`、`ACPI_NVS`、`RUNTIME_SERVICES_CODE/DATA`、`PERSISTENT`；只要 `RUNTIME`/`NV`/`SP` 任一位命中 → 不进分配器、不建普通映射、范围进 side list |
| 5 | **普通属性准入** | 满足普通主存语义（写回位存在，并按裁决一的架构合同核对）→ 按类型政策进两张表；不满足 → 走逐类处置表（不建普通映射、范围进 side list），**没有任何绕行通道** |

下面三组组合的结论完全取决于步骤先后，按此顺序落定：`RESERVED + NV` → 排除（属性只记录，不进 side list）；`UNUSABLE + SP` → 排除；`MMIO + RUNTIME` → 设备窗口路径；`PAL_CODE + NV` → 拒绝启动（第 2 步先于一切属性裁决）。

### 2.2 为什么矩阵还没批完

冻-8 说「进两张表必须证明支持普通主存语义」，但**「证明」依赖两件事**：某类区域到底需不需要被映射（取决于内核是否消费它）和某个架构能不能给出所需属性（裁决一）。第一轮评审把前置再加一层：**属性位定义本身的规范来源必须锁定**（第 7.1 节），否则「哪个位算未知」这个问题在实现里是猜的。以下七行按第一轮结论标注状态。

### 2.3 逐行结果

**行 1：基线之外的属性位——失败、记录，还是分级？（第一轮选丙的严格分级版，待位定义核实后才能签）**

当前实现按**分类错误**处理：任何不属于基线掩码的属性位出现，整张内存图作废、引导失败（代码事实：解析层比对「基线已知位掩码」，掩码外有位即报错）。这是把「不静默忽略」实现成了「不容忍」。

第一轮结论采用三类分级，本方同意并补一条实现要求：

| 属性类别 | 第一版处置 |
|---|---|
| 基线已定义、项目明确不解释且不影响安全使用的位（例如标记「更可靠」与「CPU 加密能力」这两位） | 记录，继续；不改变分配与映射资格 |
| 基线未分配 / 保留、项目无法识别语义的位 | 分类错误，fail-closed |
| 后续版本已定义、且会影响分配安全的位（例如「可热插拔」——规范建议操作系统不要把不可迁移的核心代码与数据放进去） | **不得简单记录后继续**：不分配、不建普通映射、进诊断范围；若本次启动必需的对象落在其中，拒绝启动 |

**本方补强**：第三类的判据「核心启动对象落在其中」需要一个可判定的输入，否则会退化成口号。本仓已经有这样一份清单——内核直接映射的来源里包含「登记的启动模块」与「自举页表树」两类候选。建议把这条判据统一表述成一条横切规则：**凡需要「拒绝启动」的属性/类型条件，都写成「该处置的范围与启动必需对象清单相交，且没有安全映射路径」**，并让所有此类判据复用同一份对象清单。这条规则同时服务裁决二行 3、行 5 与裁决四的 `no-map` 验收。

**本方不同意评审人的一点**：第一轮意见里「第二类=保留位 fail-closed」与「第三类=已知但不支持的位」之间的边界，实现上**无法在不知道固件规范版本的前提下判定**——见第 7.1 节。因此在读到固件报告的修订号之前，分级政策的第二类与第三类会塌缩成同一类（都只能按「基线掩码外」处理）。这不是理论问题：本仓当前**从不读取系统表头里的固件修订版本**，也没有把 UEFI 版本记进任何诊断输出。落地顺序应是「先记修订号 → 再分级」。

**行 2：`ACPI_NVS` 的映射资格（第一轮选甲，可签）**

第一版固定为：不进物理页分配器、不建普通直接映射、范围进 side list、**不因存在该类型就拒绝启动**。理由与规范一致：这类内存的定义涉及固件保留用途与睡眠状态下的内容保持，没有 ACPI 消费者时内核没有理由把它放进普通别名区，但也不能交给分配器。

将来 ACPI 支持落地时重开这一行，审真实消费者与睡眠状态合同。**明确否决**第一轮讨论里出现过的「用编译期消费者开关让分类器依赖 ACPI 子系统状态」——那等于把政策表的取值交给另一层的运行时状态，矩阵就失去「任何组合唯一确定结果」的性质。

**行 3：普通属性不满足时的引导镜像区间（`LOADER_CODE`/`LOADER_DATA`）（第一轮选丙的加强版，待映射来源证据）**

逐类处置表把这两类在不满足写回准入时判为「不建普通映射、范围进 side list」。但引导壳自己的代码与数据正落在这两类里：镜像在切到最终页表之前需要被读取（取指走恒等段），切根之后的读取需要直接映射覆盖。

第一轮把这件事拆成两段合同，本方接受，并补上仓库里的事实：**这段覆盖其实已经存在，而且不来自分类结果**。

- **分类资格**：这两类缺写回位时，不进可用表也不进保留表，不因进了 side list 就自动获得普通映射。side list 是诊断，不是映射授权。
- **启动对象覆盖**：对启动仍必须访问的对象（内核镜像、入口代码、栈、交接数据、分类输出数组），必须有明确的专用映射来源，并同时证明五件事——物理区间与实际对象的边界相符、在对应的页表切换阶段仍可访问、所用属性与该区域实际支持的属性一致、**不产生同一物理页的两套缓存属性别名**、不会因此被分配器当成可用页。若无法证明某个缺写回位的引导区间只包含「已被专用映射覆盖且不会被普通映射访问」的对象，则拒绝启动。
- **仓库事实**：引导根的恒等段现在是无差别映射低 4 GiB（§0.3），因此「切根前引导数据可达」这一条**今天就是靠它满足的**——它满足上面第 1、2 条，但**不满足第 3、4 条**（这段映射一律用普通可缓存属性，且与最终直接映射构成同一物理页的别名）。所以这一行不能按「已有覆盖，签」处理，必须与裁决六一起判：要么承认引导根是无差别普通映射、把「不建普通映射」的承诺限定到最终根，要么让引导根按排除清单跳过。本方倾向前者并加一条时限说明（引导根在切根后即拆除，别名窗口只存在于引导期，且本仓已在设备窗口上做过「同页同属性」的处理）。

**行 4：`PERSISTENT`(14)（第一轮维持本方立场，可签）**

不进普通分配器、不建普通直接映射、保留完整范围信息（不能只留计数，否则将来实现持久内存支持时无法恢复范围）、记录数量与总字节数与有限样本；**不因固件报告了持久内存就拒绝整机启动**。该类型在规范里是「可按常规内存工作但非易失」，它不等于坏内存，也不等于未接受内存；项目暂不使用它是资源政策。拒绝启动的触发条件统一成 §2.3 行 1 的那条横切规则：**该范围与启动必需对象冲突且无安全映射路径**。

**行 5：固件服务代码/数据 与 `ACPI_RECLAIM`（第一轮拆成两条，政策可签；实施需本方补一条守卫）**

本方上一版把这两类合并成「永久放弃回收」，第一轮指出这不成立，本方核对后接受拆分，并补一条真实约束。

| 类型 | 第一版结果 | 回收前提 |
|---|---|---|
| `BOOT_SERVICES_CODE`/`BOOT_SERVICES_DATA` | 成功退出引导服务之后**进入可用表** | 不再等 ACPI；需要证明「引导服务依赖已结束」 |
| `ACPI_RECLAIM` | 保留映射，不进分配器 | ACPI 表解析完成、必要数据已复制、引用已解除 |

- **规范依据**：成功调用退出引导服务之后，操作系统加载器可以把这两类当作可用空闲内存——这是规范明确给出的能力，继续留在保留表是项目自行放弃。第三方库自己的文档也逐字写明「内存图中标为这两类的数据会变成空闲内存」，并同时要求调用方保证「不再有指向引导服务数据的引用」。
- **不设地址窗口条件**：「只回收某个地址范围内的部分」被否决。回收是生命周期合同，不是地址猜测。
- **本方补的守卫（这是本行唯一的新增实现要求）**：风险不在规范，而在**我们自己的存活对象**。核查结果对本方有利：引导期堆（池分配）与全部自举分配、读图缓冲都取 `LOADER_DATA` 类型，因此「存活对象恰好落在被回收的 `BOOT_SERVICES_DATA` 里」这一情形在当前代码里不成立。但它是**一条必须被守住的不变量**，不是可以推定的性质：任何将来改用引导服务类型做分配的代码都会静默破坏它。因此落地时要把「引导期一切分配取 `LOADER_DATA`」做成一条守卫（代码检查或宿主测试断言分配类型），并把「退出后不得再触碰引导服务协议对象与池对象」列入实现约束——第三方库文档列的那份检查清单（协议引用、会调用释放的池字符串类型等）可以直接作为验收条目。
- **收益要如实写**：这一行是六项里唯一**增加可用内存**的改动，且随机器内存规模增长；其余各行都是把范围挡在外面。

**行 6：OS loader 自定义类型——不预建注册机制（第一轮否决本方，本方接受）**

本方上一版建议现在就把「项目显式登记的自定义类型」通道留在分类器里，第一轮反对：不要为尚无消费者的场景建通用注册表。本方接受，理由与本仓库的一条既定教训完全同构——一个宣称能承载多种来源、却没有任何消费者利用它的接口，最终会被删掉。将来第一次真正使用该数值区间时，必须同批提供：精确的类型常量、一条明确的分类政策、对应的属性与生命周期处理、以及常量与分类结果的测试；除此之外的该区间数值仍判分类错误，不允许整段通过。这不是「以后再临时改分类器」，而是「每新增一个类型都显式扩充枚举与穷尽匹配」。

**行 7：side list 条目超限（第一轮选乙，可签；必须先改一处术语）**

side list 是引导壳内部诊断，不是内核交接协议，**诊断空间不足不应否决启动**。当前实现却把「装不下」做成预检失败、进而引导失败。采纳的合同：

- 保存前 N 条诊断范围样本；
- 统计全部成员的数量与总字节数（计数饱和时置溢出标志，不失败）；
- 输出显式的截断标志，并记录**哪一类处置**发生了截断；
- 现有的 64 条容量先作为样本容量沿用，不在没有真机读数时凭感觉扩大。

两遍扫描的事务性不受影响：第一遍已经知道总数、容量、样本数与是否截断，它交给第二遍的是一个含「已确定截断」的计划；第二遍最多写 N 条，不可能因诊断容量再次失败。

**必须先改的术语**（否则与冻-5 自相矛盾）：**side list 的政策成员**是所有「保留但不建普通映射」的范围；**实际存储的有界列表**只是这些成员的诊断样本，不承诺保存全部范围。本简报之后凡说「进 side list」，指的都是政策成员；说「样本」才是那个数组。

### 2.4 「政策矩阵不会漏格子」的验收判据（采纳第一轮，替换本方上一版）

本方上一版写的是「五步顺序保证任何组合都落在唯一输出上，因此只要组合空间无空洞就不必逐格检查」。第一轮指出这个推理不够：**固定的执行路线只保证裁决函数一定有返回值，不保证每个返回值对应的政策是有意的**。完整的验收至少需要：

1. 所有标准类型 0–15 都有明确政策；
2. 三段未知类型区间都有明确的失败动作；
3. 基线内每个已知属性位都有明确处置（五者必居其一：参与准入 / 改变分配 / 改变映射 / 记录但忽略 / 出现即报错）；
4. ISA 有效位与掩码的组合完整定义；
5. 未知属性位明确区分 fail-closed 与显式支持的后续属性；
6. 每个类型与独立属性的组合都由五步顺序唯一决定；
7. 所有进两张表的描述符还须通过裁决一的架构准入。

测试不必穷举 64 位属性空间，但要**穷举政策等价类的交叉组合**，并对所有未知位位置做逐位测试；随机采样只作补充。具名用例除原有的四个顺序组合外，第一轮要求补入：`CONVENTIONAL + WB + RUNTIME`、`LOADER_DATA + 可热插拔`、**未知位与强制排除类型的组合**（检验第 1 步与第 3 步谁先，本方上一版漏了这条）、已登记的项目类型与未登记的 OS loader 数值的边界。

### 2.5 需要补的证据（按腿拆开，采纳第一轮对上一版的修正）

上一版本节错误地把三个架构并列成「三个目标的 UEFI 四时点样本」。RISC-V 裸机腿根本不产出 UEFI 内存图（它走设备树，没有类型也没有属性位图），把 UEFI 矩阵强加给它属于本文的错。修正后的采集分工：

| RISC-V（裸机/设备树） | 实际接收到的设备树（或其文本形式）、平台物理内存属性依据、启动前后的相关内存范围证据 |

## 3. 裁决三：退出引导服务之后的端到端验收

**第一轮结果：夹具型腿统一采用路径 A；失败观测采用结构化行；地址空间顺序升级为类型约束。方案可签，输出生命周期待代码证据。**

### 3.1 机制背景：两种顺序，以及我们现在实际站在哪一条上

引导壳必须做一件带有事务性质的工作：读内存图得到一个版本戳，然后用**同一个键**去调用退出函数——中间只要有任何分配改动了内存图，键就失效，必须重读重试。

| 顺序 | 做法 | 关键差异 |
|---|---|---|
| **生产式（路径 B）** | 读图 → 分类 → 用同键退出；键失效则重来 | 分类发生在引导服务还活着时；读图与退出之间**零分配**，所以图不会因为自己的动作而改变 |
| **退出后分类（路径 A）** | 先完成全部自举分配 → 调退出函数 → **保留**它返回的那份最终图 → 分类 | 最终图就是退出所用的图，因此包含所有自举占用（包括读图缓冲自己那一块）；代价是分类发生在引导服务已失效之后 |

**当前实现的准确位置（代码事实，本方上一版没写清）**：生产腿走路径 B（一个用函数指针表达读图与退出的配对循环，可被模拟固件在宿主测试里驱动）。**辅助/测试腿两条都不是**——它在退出之前自己另读一份快照，然后把退出函数返回的最终图**显式丢弃**（那段丢弃的注释理由是「内核已经通过另一个入口拿到了常规内存区间」）。因此路径 A 在本仓**尚未接线**，它的实际改动面是：把取表入口从「自己调读图服务」改成「消费退出函数返回的图」，并让 15 个共用它的测试载体跟着改调用形状。这是裁决三的真实工作量，不只是「跑一遍验收」。

### 3.2 六项验收（已定义，待跑）

| 验收 | 标准 |
|---|---|
| 原始内存图访问 | 用元数据里的**有效图长度**，不能用分配缓冲的长度（缓冲按「留几条余量」分配，长度不是步长的整数倍） |
| 分类零分配 | 分类路径上没有任何临时堆分配 |
| 输出零分配 | 输出容器指向事先准备好的静态存储或交接区 |
| 错误退出 | 退出后分类失败 → 不依赖引导服务的停机路径，不返回固件环境 |
| 析构安全 | 最终图缓冲的持有、遍历、分类、析构都不调用失效服务，也不经依赖引导服务的日志后端 |
| 输出生命周期 | 输出数组所在区间在内核消费期间保持可访问，且不进入可用表 |

其中最后两项是**待验收**。第三项「输出生命周期」的准确判据由裁决六决定（可访问的是哪棵树、以什么属性）。

### 3.3 四个问题及其第一轮结论

**问题 A：输出数组的归属 → 采用「预分配启动对象存储 + 实际覆盖证明」**

不能只因为输出数组是静态变量就认为它安全。采纳的合同：输出缓冲、根页表页、自举区间以及其它跨切根仍需访问的对象，全部在交接之前预分配，并由**同一套启动对象覆盖检查**登记（这条通道本仓已有，就是直接映射来源里的「自举页表树」与「登记的启动模块」两类候选）。若镜像自身的映射来源确实完整覆盖输出数组，可以使用，但必须用实际链接边界与**最终页表**证明，不允许只靠「它在未初始化数据段里」这句推理。

**明确否决**「退出后再拷进刚分配的堆」：退出之后不能分配，复制目的地必须事先存在。

**问题 B：退出之后失败的观测格式 → 采用结构化行，且与裁决五共用字段**

失败只剩裸串口。三个架构在测试环境里的控制台设备各不相同（x86 的 ISA 串口、AArch64 的串口控制台、RISC-V 的 SiFive 串口），而判定脚本是按行读串口输出来判通过/失败的。**采纳的建议：成功与失败都用机器可读的稳定文本格式**，失败行包含固定版本号与失败前缀、稳定的错误码、裁决步骤、处置结果、以及原始描述符四元组（类型、物理起点、页数、属性；没有具体描述符时相应字段留空），形如：

```
BOOT_FATAL v=1 code=CLASSIFY_UNKNOWN_ATTR step=1 type=0x7 base=0x80000000 pages=0x100 attr=0x0
```

流水线解析失败前缀即判失败；人类可读说明可以作为紧跟的一行，但不能是唯一接口。这套字段与裁决五共用，避免出现两份诊断协议。

**问题 C：「退出后到分类结束不切地址空间」→ 升级为类型约束（最小形态）**

现在这条保证靠代码顺序维持。采纳的建议是用阶段对象把它写进接口边界，概念上四条：成功退出才产生「已退出引导服务」对象；分类函数消费它、读最终图并产出「已分类启动」对象；只有拿到后者才能执行页表切换；原始图对象不允许从分类函数逃逸。**约束是不要为此建一个庞大的启动阶段框架**——只在 API 边界表达这一条危险顺序即可。本方补一句实现侧的现实：生产腿的退出是经由项目自有的函数指针循环完成的，不是第三方库的退出封装，因此这套阶段类型要么同时覆盖两条腿，要么明确第一版只约束辅助/测试腿；本方倾向后者并在生产腿用断言过渡。

**问题 D：容量与样本读数 → 一次受控启动全部采集**

两张交接表的容量（128 条、256 条）属于硬合同，**超限即 fail-closed，不截断**；诊断样本按行 7 截断并报告。一次启动里同时记录：各阶段描述符条数、最终图的有效长度与步长、第一遍算出的三类输出条数、诊断样本用量与截断标志、各输出容器的容量与剩余量。不需要为分别测两张表和 side list 跑三次启动。

一个数量级的提醒（**推理**）：路径 A 用的是最终图，条数通常比生产式路径读到的快照多——一次分配可能把一个常规区间切成三段，净增两条描述符。因此「128 / 256 够不够」在两条顺序下的答案不同，需要在各自那条腿上分别取数。

## 4. 裁决四：设备树来源的保留区与不可映射节点政策

**第一轮结果：选丙，但重叠规则必须重写；`no-map` 的验收范围扩大到整张映射规划。待实际设备树样本与映射验收。**

### 4.1 机制背景：两条来源不能共用一套政策

统一的分层是已冻结的方向：UEFI 来源（类型 + 属性）与设备树来源（内存节点、保留区域等）各自经过**自己的来源政策**，汇进同一份操作系统内存语义，再由架构映射层落到页表。UEFI 侧政策是裁决一、二的对象；设备树侧政策是本题。

设备树描述内存的方式与 UEFI 不同：`/memory` 节点用 `reg` 列出系统内存区间；`/reserved-memory` 子树逐条列出被保留的区域，每条可以带一个 `no-map` 标记表示**不得为它建立映射**，也可以带其它提示（为某设备划出、可重用、跨重启保持等）。规范还区分**静态 `reg` 型保留节点**与用 `size`/`alignment`/`alloc-ranges` 表达的**动态分配型节点**——后者要求操作系统按约束自己选址。

已核实的设备树侧行为只有两条（代码事实）：解析 `/memory` 的 `reg`；按固件常驻区的末端裁掉区间前缀。未覆盖：`/reserved-memory` 子树、`no-map`、保留区与内存区的交集处理、被禁用的内存节点、多段 `reg`、地址与长度单元的变体、节点名带 unit-address 的形态。

**来源适用范围的澄清（采纳第一轮第 4 点）**：设备树规范写明，UEFI 启动时系统内存图应来自固件的内存图服务；若同时存在 `/memory`，操作系统必须忽略它。因此本节的政策**只适用于不经 UEFI 内存图的引导腿**，不应变成 UEFI 腿的第二套内存来源。本仓的 UEFI 腿与裸机腿是分开的，这条边界要写进政策文本，防止将来在 UEFI 腿上「顺手」读设备树内存节点。

### 4.2 保留区与 `/memory` 相交是正常表达，不是冲突（本方上一版的实质错误，已改写）

上一版把「保留区与内存区重叠的处理规则」列成需要裁决的冲突问题，第一轮指出这是概念错误，本方核对规范后接受：**`/reserved-memory` 的地址本来就落在 `/memory` 之内**，它表达的正是「这片 RAM 里有一段不要交给普通用途」的切除。真正的错误只可能发生在**来源描述彼此矛盾**时。改写后的第一版规则：

| 情况 | 第一版处置 |
|---|---|
| `/memory` 的有效区间 | 普通内存候选 |
| 静态 `reg` 保留节点与内存区间相交 | 从可用表扣除交集（正常的切除） |
| 静态保留节点没有 `no-map`，且满足普通映射准入 | 进保留表 |
| 静态保留节点带 `no-map` | 同时从可用表与保留表排除 |
| `no-map` 范围与普通映射范围相交 | 必须保证**最终页表没有覆盖该范围的叶子映射**，包括覆盖它的巨大页 |
| 两个保留节点互相重叠、语义相容 | 可以合并为相同处置 |
| 两个保留节点重叠、语义冲突或无法确定 | 分类错误；**不按声明先后顺序裁剪** |

**`no-map` 后果的准确表述（本方上一版过界，已收窄）**：上一版写成「在 AArch64 上会踩到安全监控器或可信执行环境的常驻区，访问产生异常；在 RISC-V 裸机腿上是固件常驻区被映射」，这是把平台可能性写成了必然结论。规范能直接支持的合同只有一条：**不得把它作为标准系统内存映射的一部分，也不得允许非受控的推测访问**；是否表现为某种异常、是否出现缓存不一致，需要平台证据。判定不需要推演异常——映射本身就违反合同。

### 4.3 `no-map` 的验收对象是映射规划，不只是分类输出

这一条第一轮标为「最容易漏」，本方完全接受，并且仓库里已经有一个现成的落点：

- 即使设备树收集器把 `no-map` 范围从两张表里都删掉，如果内核的直接映射构造器随后用一个大范围或巨大页把它重新覆盖，仍然违反规范。
- 因此验收必须查四件事：`no-map` 范围不进入任何普通映射候选；最终页表不存在覆盖该范围的叶子；映射规划不会为使用巨大页而跨过它的边界；其它启动对象映射来源也不会意外覆盖它。
- **本仓有巨大页**：引导根的恒等段按大页粒度铺低 4 GiB，并且已经存在一条判据——某个大块若与「已知设备窗口清单」相交，就拆成 2 MiB 粒度并按片加设备属性。这条判据正是 `no-map` 验收应当扩展的钩子：把它的输入从「设备窗口清单」扩到「设备窗口 ∪ 排除范围（含 `no-map`）」。
- 但注意 §0.3 的事实：**这段大页铺开发生在引导根，且不参与类型政策**。所以「分类器已经排除」在当前实现里确实不等于「没有任何映射覆盖」，`no-map` 的验收不能只写成设备树收集器少输出一条区间的测试。这一层落到裁决六。

### 4.4 第一版的支持边界与被禁用节点

- **只支持静态 `reg` 型保留节点**。使用 `size`/`alignment`/`alloc-ranges` 的动态节点，在项目没有实现对应选址策略时应当明确 fail-closed，或逐条列出经批准可忽略的情形；不能假装已经支持完整的 `/reserved-memory` 语义。`no-map` 与 `reusable` 不能同时出现，也是规范明确写的组合约束。
- **被禁用的内存节点**：`/memory` 标为 disabled → 不纳入普通内存候选；`status` 缺省 → 按规范默认视为可用；`/reserved-memory` 的子节点带 `reg` 但状态为 disabled → **不得当作「保留已解除」的证明**，应保持保留或明确拒绝这种输入，不能静默变成可用表。设备树的 `status` 描述的是设备运行状态，规范没有给出「可不经审查把保留物理区域归还分配器」的通用承诺。

### 4.5 来源不对称是否可以接受？（第一轮接受，本方采纳其文本）

可以。第一版把不对称写进文本，而不是含糊过去：

> 操作系统内存语义的**输出合同**在各来源之间保持一致，但各来源适配器支持的**输入语义范围**不同。UEFI 来源按 UEFI 类型与属性政策分类；设备树来源按 `/memory`、`/reserved-memory` 及其明确支持的属性分类。**未实现的来源语义不得被推断成已支持。**

实施范围据此固定为：静态保留区、`no-map`、以及安全的切除；`reusable`、动态选址、设备用途绑定与更复杂的消费者策略另行处理。

### 4.6 请评审人回答（本轮剩余）

1. `no-map` 与「大页铺开」的冲突在两个地方都可能发生（引导根的恒等段、最终直接映射）。第一版是否两处都验，还是只验最终直接映射、把引导根的例外作为裁决六的一个显式条目记录？
2. 动态选址型节点选 fail-closed 还是「白名单式可忽略」？本方倾向 fail-closed 并把实际遇到的形态记进诊断，等样本说话。
3. 保留节点与内存区间相交后的**切除顺序**是否需要在多段 `reg` 情况下定义（本方认为需要，但要求以「先算交集集合、再一次性排除」实现，避免逐条裁剪造成的边界依赖）。

## 5. 裁决五：被排除描述符的留痕通道

**第一轮结果：采用有界结构化诊断，成功与失败路径都可观测，诊断容量不否决启动。方案可签，字段表已定，待与裁决三的失败行合并成一份协议。**

### 5.1 机制背景：政策里反复出现「记录，不静默忽略」，但记录到哪一层没有合同

政策表里至少三处写着「记录进诊断、不静默忽略」：基线之外的属性位（行 1）、被类型强制排除的描述符的属性位（第 3 步）、当前不解释的元信息位。讨论文档还给出过一份「最小返回信息」的形状：排除与特殊的条数与字节数，外加前若干条的原始四元组（类型、起点、页数、属性）。

当前实现做到的程度（代码事实）——缺口有**两层**：

| 输出 | 记了什么 | 没记什么 |
|---|---|---|
| 可用表 / 保留表 | 区间（起点 + 长度） | 类型与属性（它们只影响裁决，不进输出） |
| side list（诊断样本） | 区间（起点 + 长度） | 类型与属性——所以「命中了哪一位」「缺写回位的是哪一类」无法从输出复原 |
| 排除 / 设备路径 | **什么都不留**：三个计数器（可用、保留、样本）里没有它们的位置，既没有条数也没有范围 | —— |

于是「不静默忽略」目前只兑现到「样本区间可见」这一层，而被类型强制排除的那一类连区间与计数都没有。

### 5.2 受众与字段（第一轮定案）

**受众**：流水线 + 开发者，**不是内核消费者**。诊断仍是引导壳内部产物，不进交接结构，冻-5 不变。流水线能按稳定格式解析，开发者能看同一行记录。

**每条记录的字段**（比上一版的「四元组」多出「为什么」那一半）：

| 字段 | 意义 |
|---|---|
| `step` | 落在五步裁决的哪一步 |
| `disposition` | 可用 / 保留映射 / 诊断成员 / 排除 / 设备路径 / 致命 |
| `reason` | 具体原因，例如类型排除、独立属性命中、缺写回准入 |
| `raw_type` | 原始类型 |
| `physical_start` | 原始物理起点 |
| `number_of_pages` | 原始页数 |
| `attribute` | 完整原始属性字 |

只有四元组无法区分「因为类型被排除」与「因为独立属性要求不建映射」；`step` 与 `reason` 让后续评审能直接追溯到裁决逻辑。**这张表与裁决三问题 B 的失败行是同一套字段**，不产生两份协议。

### 5.3 范围留痕与容量（第一轮定案）

- 同意本方上一版的主张：**类型强制排除的范围也要有诊断记录**，否则第 3 步的判断不可审计。
- 但不要求每条都永久保存在一个大数组里。合同固定为：每种处置都统计条数与总字节数；对「诊断成员」与「排除」至少保存前 N 条原始范围样本；对「设备路径」也记汇总并有限保存样本；**任何致命情形单独保留触发描述符，不得被普通样本挤掉**；输出截断标志与计数溢出标志。这样即使样本被截断，自动化系统也知道发生过截断，而不会误认为没有更多记录。
- 上限沿用现有的 64 条样本容量，不为了避免截断而盲目扩大。
- **术语拆分**与行 7 相同：语义上的成员集合是完整的，数组只是它的有界样本；样本截断不改变分类结果。第一遍统计完整数量与总字节数并确定样本数与截断位，第二遍最多写 N 条，因此不会产生新的写入失败。

### 5.4 请评审人回答（本轮剩余）

1. 成功路径是否也输出诊断摘要（本方倾向输出，且只输出一行汇总，避免每次启动刷数十行）。
2. `reason` 的取值集合是否要与失败行的错误码合并成同一张枚举表（本方倾向合并，理由同裁决三问题 B）。
3. 样本数组的放置：与诊断成员共用一块静态存储，还是各自一块（本方倾向各自一块，理由是截断统计要按类别区分，共用会让「哪一类被截断」变得不可判定）。

## 6. 裁决六（本轮新增）：「不建普通映射」这句话由哪棵页表树兑现

### 6.1 问题从哪来

按第 0.3 节的代码事实：本仓在这个阶段有两棵树。引导根的恒等段**无差别映射低 4 GiB**（只有已知设备窗口的块被拆成 2 MiB 加设备属性），类型政策、诊断成员、被排除范围、设备树的 `no-map` 都不参与它的构造；最终直接映射才按四个来源的并集构造。

于是三条已经写下的承诺，措辞强度并不一致：

| 承诺 | 在引导根上是否成立 | 在最终直接映射上是否成立 |
|---|---|---|
| 「side list 成员不建普通映射」（冻-5） | **不成立**（低 4 GiB 内的成员被按普通属性映射着） | 成立 |
| 「被排除的区域 OS 不得访问」（第 3 步） | **不成立**（同上，且恒等段还给了可执行属性） | 成立 |
| 「`no-map` 不得进入标准系统内存映射」（裁决四） | **不成立** | 成立（前提是把排除范围喂进大页判据） |

这不是实现缺陷的指控，而是一个**合同作用域没有被写下来**的状态。它的另一面同样真实：正因为在引导期有这段无差别覆盖，裁决二行 3 里「引导数据在切根前可达」才成立——同一机制同时是那条行的解药和这几条承诺的漏洞。

### 6.2 为什么它必须由评审人裁决，而不是本方顺手定

选「让引导根也按排除清单跳过」在语义上最干净，但它有一个直接后果：**排除范围需要从分类结果传到内核的页表构造处**——即跨引导边界传一份「不许映射的范围清单」。而冻-5 明确写了 side list 不进交接结构、不构成跨引导边界的保留协议。两条不能同时成立，所以这是一个会触到冻结条目的选择：

| 案 | 做法 | 与冻结条目的关系 | 代价 |
|---|---|---|---|
| 甲 | 把「不建普通映射」在文档与字段说明里**限定为最终直接映射**，并写明引导根存在一段有时限的无差别覆盖，切根后即消失 | 不动冻-5 | 引导期存在一段对 `no-map`/排除区的普通属性别名；对 ARM 这类「同一物理页两套属性为不可预测」的架构，需要论证这段时限窗口可接受 |
| 乙 | 交接结构新增一份「不可映射范围」清单，引导根按它跳过 | **需要修订冻-5**（区分「保留协议」与「映射禁止清单」两种用途） | 一次跨镜像数据契约变更；分类输出与构造判据要加一致性检查 |
| 丙 | 引导根继续无差别，但**排除范围只允许「无副作用」的那些**——即把「必须绝对不映射」的子集（`no-map`、机密计算类区域）在分类阶段就升级为拒绝启动，其余按甲处理 | 不动冻-5，但改变行 4 与第 3 步的强度 | 把「平台超出能力」的判定扩大；需要一份「哪些类型属于绝对不可映射」的清单 |

### 6.3 请评审人回答

1. 三案选哪个？本方立场：**先甲后丙，乙作为例外由评审人推动**。理由是甲与丙都不改跨镜像契约，而乙要改的正是已经冻结的 side list 语义；把契约变更留到有真机证据说明甲不够用时再做，成本最低。若评审人判断引导期别名本身不可接受（尤其在 ARM 上），请直接选乙并批准修订冻-5。
2. 若选甲：这段「无差别覆盖 + 普通可执行属性」是否需要作为一条已知偏差登记（含它的地址范围与时限），并在裁决四的验收里明确「不覆盖引导根」？
3. 若选丙：「绝对不可映射」的子集边界由谁定——类型（如固件保留）、属性（如 `no-map` 标记），还是平台的信任边界？

## 7. 前置阻断项与等待项

### 7.1 阻断项（步 0，先于所有政策批准）：属性位常量的规范来源

第一轮把一个本应更早处理的问题标为最高优先：**在锁定属性位定义之前，属性穷测即使全过，也可能是在测错误的位定义**；尤其不能假设「未知位一定能被正确识别为未知」。

本方按仓库读数核了一遍，结果比担心的要好，但没有消掉问题：

- **一致的部分（代码事实）**：项目自有的属性位常量与所依赖的第三方 `uefi-raw` 0.9.0 的 `MemoryAttribute` 定义**逐位相同**，两者都与 UEFI 2.10 / EDK2 的头文件布局一致（写保护 `0x1000`、读保护 `0x2000`、禁执行 `0x4000`、非易失 `0x8000`、更可靠 `0x10000`、只读 `0x20000`、特定用途 `0x40000`、加密能力 `0x80000`、运行时 `0x8000_0000_0000_0000`、ISA 有效 `0x4000_0000_0000_0000`、ISA 掩码 `0x0FFF_F000_0000_0000`）。也就是说，本仓内部没有「两处常量不一致」这种低级裂缝，基线是明确的 2.10 布局。
- **未消掉的部分**：第一轮指出 UEFI 2.11 的发布 PDF 里，写保护等位的位置与 2.10 的 HTML 及 EDK2 头文件不一致（例如同一位被列为 `0x100` 而非 `0x1000`）。这不是能在文档里判定的勘误，而它一旦为真，「基线掩码外的位=未知」这条判据就会把**已知位误判成未知位**，从而在真固件上触发 fail-closed 拒绝启动。
- **本仓缺的那一步（代码事实）**：全仓没有任何地方读取系统表头里的固件 UEFI 修订版本，诊断输出里也没有它。因此当前无法把「固件实现的是哪一版属性布局」这个事实带进裁决。

因此把这条登记为实现阻断项 **属性位基线核对**，签字前必须交三样东西：逐位常量的权威来源（规范版本 + 头文件）、允许掩码、以及**从固件系统表读出的修订号**（先在引导诊断里打出来，不需要任何政策变更）。第一版仍然按 2.10 实现；若将来要兼容 2.11，先核实正式勘误与实际固件编码，不做猜测式兼容。

### 7.2 登记在案但不属于本批裁决的等待项

列出仅供评审人对全局优先级提意见，不作为签字项：

1. **两遍扫描的接口形态已经被落码单方面选定**。预检产出「已验证的计划」凭证、写入阶段不返回错误——合同是冻结的；但「凭证」与「完成函数直接返回普通值」两种形态本来约定由原型比较后择一，实现直接选了前者。它不是待裁决问题，只是本方要如实记下：若评审人认为应换形态，代价是改代码而不是改文档。
2. **另一份固件内存属性表**：UEFI 还有一张独立表描述运行时服务内存的保护属性。第一版不支持运行时服务，因此不实现；将来支持时不能假设描述符的属性字已经包含全部保护布局。
3. **运行时服务的虚拟地址映射合同**：带运行时属性位的区域若要使用，需要一套与直接映射不同的映射与地址转换约定。目前只保证「不进分配器、范围成为诊断成员」。
4. **池分配释放后的页级归属**：从内存池取出的块在对象释放之后，页是否退回常规内存——规范只保证池分配来自专门的池，不保证页立刻归还。这是待实测事实，不是政策问题（它影响「分类用的图能否反映释放」）。
5. **ACPI 支持落地之后**：`ACPI_RECLAIM` 的回收、`ACPI_NVS` 是否需要映射，都会随行 2、行 5 一起重开。
6. **可信物理内存拓扑来源**：若将来出现独立、可信的 RAM 拓扑来源（不是常规区间并集，也不是地址上界），是否重新引入地址过滤——现在的答案是不引入（冻-2），留待有新来源时重议。
7. **引导路标条目的合并**：属于台账记账工作，不含内存图语义裁决，因此不列为待裁决项。

## 9. 术语表

| 术语 | 含义 |
|---|---|
| 内存图 | 固件交出的物理地址区间清单，每条描述符 = 类型 + 起点 + 页数 + 属性位图 |
| 引导壳 | 由固件加载、负责准备页表与交接数据、然后进入内核的一段独立可执行代码 |
| 描述符步长 | 相邻两条描述符起始地址之差；规范长度是最小值，固件可以用更大的值做向后兼容扩展 |
| 属性位图 | 描述该区域**支持**什么用法的位集合，不是「此刻正被怎么用」的状态 |
| 写回缓存 | 主存的标准缓存策略：写先进缓存、之后回写。普通内存的默认期望 |
| 不可缓存 / 设备属性 | 访问直达地址空间，不经缓存。对寄存器是必需的，对普通内存是灾难 |
| `IA32_PAT` / MTRR | x86-64 上决定有效内存类型的两套机制；前者每逻辑处理器一份、可选 8 种类型，后者按物理地址范围设定 |
| `MAIR_EL1` / 属性索引 | AArch64 的属性表寄存器 / 叶子页表项用来选表项的 3 位索引 |
| 物理内存属性 / Svpbmt / PBMT | RISC-V 的平台级内存属性（归 M 态管理）/ 可选扩展 / 页表项里那两位（只能表达「跟随属性」「不可缓存主存」「强序 I/O」，且需 M 态使能位） |
| 普通主存语义 | 三架构统一的目标：缓存可用、一致性成立、访问与原子操作符合主存预期。它是语义合同，不等于某个具体缓存属性名 |
| 直接映射 | 内核把物理内存线性映进自己的虚拟地址空间，物理地址加固定偏移即可访问 |
| 引导根 / 最终直接映射 | 本文对两棵页表树的称呼：切根之前使用的那棵树（含一段无差别恒等映射）与内核正式的物理别名区 |
| 物理页分配器 | 内核分配与回收物理页的组件 |
| 可用表 / 保留表 | 本文对两份输出的称呼：可自由分配 / 可访问但不得再分配 |
| side list 的成员 / 样本 | 成员=所有「保留但不建普通映射」的范围（语义集合）；样本=实际存储的有界诊断数组内容。二者容量语义不同，不可混称 |
| MapKey | 内存图的版本戳；退出引导服务必须携带取得该键的同一次读取 |
| 退出引导服务 | 结束固件引导期服务的调用；此后固件的分配、控制台、释放接口全部失效 |
| 交接结构 | 引导壳交给内核的固定布局数据块，字段按基址加偏移定位，不含进程内指针 |
| 恒等段 | 引导期把物理地址与虚拟地址等价的映射区间，让还没切页表时代码能继续跑 |
| 切根 | 把页表根从引导期页表切换到内核页表的动作 |
| 夹具型测试 | 只把某份数据当输入、不对该数据本身做断言的测试，被测对象是别的代码 |
| 五步裁决顺序 | §2.1 那张表：未知或不支持 → 拒绝启动 → 类型强制处置 → 普通候选 × 独立属性 → 普通属性准入 |
| 切除（carve-out） | 设备树表达「这片 RAM 里有一段不要用」的方式：保留节点的地址与 `/memory` 区间相交是正常形态 |
| 启动必需对象 | 内核镜像、入口代码、栈、交接数据、分类输出数组等跨切根仍需访问的对象；本文多处「拒绝启动」判据都以它为参照 |

## 12. 本方对第一轮的回应：三处补强、两处不同意

### 12.1 三处补强（本方按仓库读数加进结论的内容）

1. **行 5 的守卫**：第一轮说「必要合同是交接后不得再引用引导服务的数据或其生命周期对象」，本方核查后给出可执行形式——本仓引导期堆与全部自举分配都取 `LOADER_DATA`，所以该不变量**当前成立**；正因如此它更需要一条守卫（断言或宿主测试）而不是依赖代码习惯。
2. **行 3 的定性**：第一轮要求「专用映射来源必须证明五件事」。本方核出这段覆盖**已经存在**且不来自分类结果（引导根的无差别恒等段），它满足前两件事、不满足第三、四件。因此这一行的真实状态不是「等证据」，而是「合同作用域未定义」——由此产生裁决六。
3. **裁决顺序**：本方把裁决五的字段表提前到政策批准之前（§8）。第一轮把裁决五排在矩阵之后，但行 1、行 4、行 5 与裁决三失败行都要引用这份字段，晚定会让多个「不静默忽略」的承诺先签成空话。

### 12.2 两处不同意（请评审人明确裁定）

1. **行 1 的可判定性**。第一轮把「基线未分配的位=失败」与「后续已知但不支持的位=不分配 + 不映射 + 诊断」列为两类，这在语义上正确，但**在当前代码里不可判定**：我们没有读固件报告的规范修订号，也没有任何途径知道眼前这块固件实现到哪一版。本方主张：在 §7.1 落地（打出修订号）之前，两类合并处理，且**默认走第二类的 fail-closed**；落地之后再分裂。如果评审人认为应该反过来（默认继续、按修订号白名单启用），请指出，因为这两种默认在真实固件上的失败方向完全相反。
2. **裁决二行 6 与本方的自我修正**。第一轮否决了「现在就留一条自定义类型通道」，本方接受，并承认这与本仓刚完成的一项结论同构（一个没有消费者的接口最终会被删）。但请把「将来必须同批提供四样东西」写成验收条款，否则第一次使用那个数值区间时，压力会落在「让它先跑起来」上。

### 12.3 一处本方上一版的实质错误（已在正文改写）

把「保留区与 `/memory` 重叠」当成需要裁决的冲突，以及把 `no-map` 的后果写成必然硬件异常。两处都已在 §4.2 按规范合同重写，RISC-V 不采 UEFI 样本的错误在 §2.5 修正。
