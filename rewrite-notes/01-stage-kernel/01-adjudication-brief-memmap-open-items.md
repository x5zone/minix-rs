**本轮（第五轮评审之后）的变化**

两份第五轮意见（一份聚焦缺口、一份通读全文）方向一致：架构方向不再讨论，缺的是几处**数据合同本身**。本方逐条采纳后，正文有八处实质变化：

1. **属性档要有自己的身份**：§2.5 那张表不是任何一份规范出版物的档，而是以依赖库头文件布局为基础的实现兼容档，改称 `MEMATTR_PROFILE_UEFI_RAW_0_9`（身份是项目内部的，不宣称规范归属）。本方核实：钉死的依赖库里**没有**「可热插拔」这一位，而主流实现头文件把它定义为 `0x100000`——所以它在本档里是**档外扩展位**，§2.5 现在把这一行明写出来（此前是漏，不是选择）。
2. **白名单的键与算法补齐**：厂商串与厂商版本都不是构建身份；条目补齐为八个维度（平台身份、架构与启动方式、固件构建身份、证据来源与日期这四维是本轮新增），并给出选档算法（唯一命中→用；零命中/多命中/样本违反该档→拒绝启动）。**样本是验证证据，不是选择器**——某个位没出现在样本里，不能证明固件以后不会给。
3. **归一化阶段产出多个语义集合，不是一个统一禁止集合**（这是本轮最重要的自我纠正）：上一版把「一份集合」写成了统一禁止范围，会把普通静态保留区（允许映射、不许分配）一起禁掉，或者反过来为了保住映射而弱化禁止。改成：唯一的区间数学与页级归一化 + 规划阶段的四行输出（PMM 排除 / 映射禁止 / 按阶段的启动必需对象 / 来源诊断），它们与分类器自己的两类输出合起来共六个集合，相互之间用**五条集合等式**约束（§0.3、§6.7）。
4. **「版本」拆成三个互不相关的字段**：系统表修订、**描述符版本**（读图服务自己返回的、规范单独定义为 1）、属性配置档标识。描述符版本 1 **不**蕴含属性位布局 1；三个都要进诊断。本方核实：本仓已经在校验描述符版本（不受支持即整图作废），但摘要行与致命行都不带它。

## 0. 阅读指引

### 0.1 这件事在系统里的位置

一个操作系统启动时要回答的第一个问题不是「怎么调度」，而是「我手上有哪些物理内存」。机器刚上电时，只有固件知道答案：哪些地址是真正的随机存取存储器、哪些是设备寄存器、哪些被固件自己占着、哪些坏了不许碰。固件把这份答案写成一张**物理内存区间的清单**交给引导程序，引导程序把它翻译成内核能用的形式，再交控制权——此后内核只能靠自己记账。这张清单就是本文说的**内存图**。

翻译这一步做错，后果不在引导期暴露，而在很久之后：一块设备寄存器被当成普通内存映射，内核的内存分配器可能把一个缓冲区放进去，写进去的数据消失、读出来的数据无意义，或者机器直接故障；一块坏内存被当成可用内存，随机位翻转会在几个月后伪装成软件缺陷。因此**分类规则必须唯一、必须可解释**——这正是本组问题的主题。

本项目支持三个处理器架构（x86-64、AArch64、RISC-V 64 位），引导期有两条不同的来源：UEFI 固件给出内存图，设备树（一种二进制硬件描述）给出内存节点。两条来源各自经过自己的政策，汇进内核统一的内存语义。

本文按证据强度分三档称呼，**不再使用「真机」这个词**（本项目目前没有任何物理开发板，把 QEMU 启动叫真机会让读者误以为已有实体硬件验证）：

| 证据档 | 含义 | 能证明什么 |
|---|---|---|
| **宿主单元测试** | 在开发机上直接运行，不需要固件或模拟器 | 纯逻辑：解析、裁决、区间数学、容量预检 |
| **QEMU 整机启动** | 镜像真正在 QEMU 上启动，由判定脚本按行读串口输出判通过/失败（三个架构各一条腿） | 引导链在**该模拟器机器类型 + 该固件构建**下成立 |
| **物理硬件验证** | 真实板卡 | 平台合同、属性与原子能力的最终归属；**本项目目前一格都没有** |

文中说「需要 QEMU 整机启动读数」，意思是这件事宿主单元测试无法回答；说「需要物理硬件验证」，意思是模拟器给出的肯定结果不算证据。

### 0.2 UEFI 内存图描述符的形状（规范事实）

每条描述符有四个语义字段。版本 1 的描述符**总长 40 字节**，其中包含一个 4 字节的补齐位（补齐位不是 40 之外的额外长度）：

| 偏移 | 字段 | 宽度 | 内容 |
|---|---|---|---|
| 0 | `Type` | 32 位 | 这块区域**是什么** |
| 4 | （隐式对齐间隙） | 32 位 | 常见 64 位 ABI 下 `Type` 之后为把下一个 64 位字段推到 8 字节边界而留下的间隙。**规范的结构定义里没有名为它的字段，也没有规定它必须为零** |
| 8 | `PhysicalStart` | 64 位 | 物理起点（页对齐） |
| 16 | `VirtualStart` | 64 位 | 运行期虚拟地址，引导期读到的是未转换的原值 |
| 24 | `NumberOfPages` | 64 位 | 页数（每页 4 KiB），**必须非零** |
| 32 | `Attribute` | 64 位 | 这块区域**支持怎么用** |

分类器用到 `Type`、`PhysicalStart`、`NumberOfPages`、`Attribute` 四个字段；`VirtualStart` 属于「结构里有、语义上此刻用不上」。**那 4 个字节不是描述符的语义字段：解析器不得依赖其内容，也不得因为读到非零就判格式错误**（本方核实现状：解析层只访问偏移 0/8/24/32，从不读偏移 4–7，因此今天没有这种误判，但这条要写成合同而不是靠巧合）。三条几何约束（起点对齐、长度不溢出、页数非零）本仓都已在解析或裁决层实现，其中页数非零是一条独立的错误码（代码事实）。

两个容易踩的形状事实：

- **步长可以大于 40**。固件按「未来可能加字段」的方式排布描述符，实际步长由固件自己报告。因此「缓冲区长度 ÷ 40」推不出条数，任何假设步长等于 40 的实现都可能读到空洞。
- **`Type` 与 `Attribute` 是两个正交的维度**。类型是固件对区域用途的断言，属性是那块区域支持的**能力**位图——它表示「可以做到什么」，不是「此刻正在被怎么用」。把属性读出来原样翻译成页表标志是错的，只按类型分类同样是错的。**这一条是 §7.1 那个阻断项的根源**：属性位的含义完全由规范版本决定，位定义取错就等于把已知位判成未知位、或反过来。

标准类型有 16 个（数值 0 到 15）：`RESERVED`(0)、`LOADER_CODE`(1)、`LOADER_DATA`(2)、`BOOT_SERVICES_CODE`(3)、`BOOT_SERVICES_DATA`(4)、`RUNTIME_SERVICES_CODE`(5)、`RUNTIME_SERVICES_DATA`(6)、`CONVENTIONAL`(7)、`UNUSABLE`(8)、`ACPI_RECLAIM`(9)、`ACPI_NVS`(10)、`MMIO`(11)、`MMIO_PORT_SPACE`(12)、`PAL_CODE`(13)、`PERSISTENT`(14)、`UNACCEPTED`(15)。数值更高的区段分三段：标准类型之后的**未分配数值区**（`0x10` 到 `0x6FFFFFFF`）、**OEM 保留区**（`0x70000000` 到 `0x7FFFFFFF`）、**OS loader 保留区**（`0x80000000` 到 `0xFFFFFFFF`）——三段语义不同，不能并成一段处理。

属性位图里本文会反复出现的位：**缓存类** `UC`/`WC`/`WT`/`WB`/`UCE`（以及现代用法同属缓存策略的 `WP`）；**保护能力** `RO`/`RP`/`XP`（硬件能做到什么，不是当前权限）；**独立用途属性** `RUNTIME`（需要运行期重新映射）、`NV`（非易失）、`SP`（特定用途内存）；**元信息** `MORE_RELIABLE`、`CPU_CRYPTO`；**ISA 掩码**（一组架构专用位加一个 `ISA_VALID` 有效位）。属性位的解释**不取任何笼统的规范版本号**，而由配置档标识决定（§7.1、§2.5）。

### 0.3 分类要产出的东西，以及「映射」这个词的四层含义

内核最终拿到两份区间表，外加一份引导期内部的诊断清单：

| 输出 | 语义 | 是否跨引导边界 |
|---|---|---|
| **可用表** | 普通物理内存，可以交给内核的物理页分配器 | 是，写进交接结构 |
| **保留表** | 运行期可以经「直接映射」访问，但不得再分配出去 | 是，写进交接结构 |
| **诊断成员集合** | **保留但不建普通映射**的范围，用于确认「哪些区间因为政策被挡在两张表之外」 | 否，只是引导壳内部诊断，不进交接结构 |
| **启动映射禁止清单**（第四种输出） | 明确**不许在引导根与最终根里建立映射**的物理页集合 | **是**；不可截断，装不下即拒绝启动（§6.3） |

第四种输出**不是 UEFI 分类器的一种处置结果**。它的产生方式是：

```
UEFI 描述符分类 ──┐
设备树保留语义 ──┼──► 唯一的区间归一化与集合规划阶段 ──┬──► PmmExcludedRanges      （不分配）
前缀阈值 ────────┘    （页级取整、排序、合并、来源记录）   ├──► BootMapDenyRanges     （不许映射，跨边界）
                                                          ├──► StartupRequiredObject  （按启动阶段）
                                                          └──► 来源诊断              （可截断）
```

图上只有两个**区间**输入（UEFI 分类结果、设备树保留语义）加一个**前缀阈值**。上一版这里还画着第三个输入「启动信息保留输入」——本方核查后删除：本仓不存在这样的区间列表（交接结构里的保留区间是分类**输出**；设备树自身的保留映射块属于「设备树保留语义」这一路，且本仓尚未读取）。

**唯一的归一化不等于唯一的集合**（本轮最重要的自我纠正）。上一版把它写成「一份集合」，会把语义不同的范围压成一个对象，两头都错：普通静态保留区（**不许分配、允许映射**）会被连带禁掉映射；或者为了保住映射而弱化 `no-map` 与保留映射块的禁止语义。正确的关系是：

| 集合 | 语义 | 主要消费者 |
|---|---|---|
| `PmmExcludedRanges` | 不得交给普通物理页分配器的页 | 可用表生成、页分配器 |
| `BootMapDenyRanges` | 引导根与最终根都不得建立标准映射的页 | 两棵树的构造判据与覆盖验收 |
| `StartupRequiredObjectRanges(阶段)` | 该启动阶段仍必须访问的对象所在页 | 禁止范围的冲突检查 |
| 来源诊断 | 各来源声明的原始区间、原因与贡献 | 流水线与开发者审计 |

上表是**归一化与集合规划阶段**的四行输出，不是本文提到的范围集合总数。把分类器自己的输出也算上，全文一共牵出六个语义不同的集合（§6.7 逐条列出：可分配的普通内存、可映射但不可再分配的保留区、诊断成员集合、启动映射禁止清单、设备树声明的保留范围、启动必需对象清单），其中前两类在本阶段之上游、后四类是本阶段的输入或输出。**两个数字说的是两件不同的事，不要拿其中一个去改写另一个。**

五条关系必须成立（用它们代替任何「统一禁止集合」的说法）：
```
PmmExcludedRanges ∩ AvailableRanges            = ∅
BootMapDenyRanges ⊆ PmmExcludedRanges          （禁映射的页也不许分配；反向不成立）
ReservedMappedRanges ∩ BootMapDenyRanges      = ∅
AvailableRanges ∩ ReservedMappedRanges        = ∅   （分类器在同一份输入上的两个输出必须互斥）
StartupRequiredObjectRanges(阶段) ∩ BootMapDenyRanges = ∅   除非该阶段有经审的其它安全访问路径
```

前缀阈值不进任何区间集合：它在设备树内存候选成形时作为 `[0, end)` 的裁剪条件参与，**但不得在一个地方当区间、在另一个地方当特判**（第五轮点名要求）。因此参与页级规划时它也必须走同一套取整与溢出规则。

**四层含义必须分开**（第二轮指出此前用「不建普通映射」一句话同时描述四件事，已拆分；本表是全文的统一词汇表）：

| 层 | 含义 | 谁负责 |
|---|---|---|
| L1 不分配 | 不交给物理页分配器 | 分类器（可用表成员资格） |
| L2 不进最终直接映射 | 内核正式的物理别名区不含它 | 映射规划与覆盖验收 |
| L3 不进引导根的恒等段 | 切根之前那棵树也不含它 | **当前无人负责**（见裁决六） |
| L4 不允许非受控访问 | 包括不受控的推测访问 | 平台与固件合同；软件清单只能近似（见裁决六） |

L1 成立不代表 L3 成立：一块内存不该被分配，不等于 CPU 完全不能经其它路径访问它。设备树 `no-map` 在**规范层**要求的是 **L2 + L4**（不得纳入标准系统内存映射；不得允许非受控推测访问），**L3 是本项目额外的加强**——为了避免两棵树的映射行为不一致而把约束推到引导根上。项目加强不等于自动证明了 L4：交接之前那段页表由固件建立，本项目的清单管不到它（§6.4）。

还有两个概念必须分开：**直接映射**（内核把物理内存线性映进虚拟地址空间，决定「读不读得到」）与**物理页分配器**（决定「能不能拿去当普通内存用」）。一个区域可以「必须映射但不许分配」（固件常驻区），也可以「必须保留但不该映射」（运行期服务代码）。用一个 `reserved` 标签同时回答这两个问题，会把两类判断压成一位，错误因此互相掩盖。

**关键补充（代码事实，也是裁决六的由来）**：本仓在这个阶段存在**两棵页表树**，「建不建映射」在两棵树上答案不同：

| 树 | 覆盖范围怎么决定 | 类型政策与设备树政策是否参与 |
|---|---|---|
| **引导根**（内核建立的第一棵树，切到最终根之前一直在用） | 恒等段按大页粒度从地址 0 铺到 4 GiB 上界常量；只有落在「已知设备窗口清单」里的大块被拆成 2 MiB 粒度并按片加设备属性，其余一律普通可读写可执行，映射失败（该地址无物理内存支撑）直接忽略 | **不参与**。可用表、保留表、诊断成员、被排除范围都不进入这段构造 |
| **最终直接映射**（内核正式的物理别名区） | 由四个来源的并集构造：可用表区间、自举页表树、登记的启动模块、保留表区间 | 参与（保留表在此出现，被排除的范围不进任何来源） |

因此「诊断成员不建普通映射」「被排除的区域不许访问」两句，在当前实现里只对第二棵树成立（只满足 L2，不满足 L3）。这段无差别覆盖同时是政策矩阵某一行（引导镜像缺普通属性时仍可达）的解药，与 `no-map` 承诺的漏洞——这就是裁决六。

一次分类被拆成三段职责（已冻结）：

1. **解析**：校验固件报告的版本、步长、缓冲区边界，逐条读出四个字段，并检查起点是否 4 KiB 对齐、页数是否非零、长度会不会溢出。
2. **裁决**：对每条描述符决定去向（分配 / 保留映射 / 成为诊断成员 / 排除 / 走设备路径）。
3. **输出**：**两遍**。第一遍只做裁决和计数，并预检各输出容器的容量——它是唯一可能失败的一遍；第二遍只写入，不返回错误。第二遍的「不可失败」由类型表达：第一遍产出一个「已验证的计划」凭证，只有持有凭证才能调用写入。**容量预检目前覆盖三种输出（可用表、保留表、诊断样本）；裁决六新增的第四种输出（启动映射禁止清单）必须一并纳入，否则该凭证并不覆盖全部写入**（§6.3 第三条）。

还有两条地址维度的合同，也属于已冻结：

- **架构可表达能力**：分类器检查「这条描述符的末端是否落在本架构页表能表达的物理地址范围内」（半开上界语义）。这是能力检查，不是「是不是 RAM」的判断。
- **映射覆盖验收**：内核是否真的为某个区间建立了直接映射，由另一层的映射规划与验收负责。**通过上界检查不等于覆盖成立**。第二轮把这条推进一步：覆盖验收必须**指明是哪棵树、哪一层含义（L2 还是 L3）**。

## 1. 裁决一：三个架构的「普通主存语义」最低保证合同

**状态：方案已定（丙），签字等硬件证据。**

### 1.1 机制背景：固件声明的属性，和硬件真正给的属性，不是同一件事

冻-8 要求任何进两张表的区间先证明自己支持普通主存语义。目前的证据来自描述符的 `WB` 位。但 `WB` 位是**固件对硬件能力的声明**；一块地址被映射之后究竟按什么策略访问，由**内核自己建立的页表**与**架构的缓存控制机制**共同决定。三架构的机制完全不同：

| 架构 | 谁决定有效缓存属性 | 本项目的现状（代码事实） |
|---|---|---|
| x86-64 | 页表叶子项里的 `PAT`、`PCD`、`PWT` **三个位**共同选择 `IA32_PAT` 模型专用寄存器里的 8 个表项之一（4 KiB 页的 PAT 位与大页的 PAT 位位置不同，分别是各自描述符的第 7 位与第 12 位）；选中的表项值与该物理地址的 MTRR 类型再按**架构定义的组合表**合成有效内存类型——不存在一个叫「跟随 MTRR」的表项类型。合成不是取较宽松的一侧：表项选写回而该区间的 MTRR 是不可缓存时，有效类型仍是不可缓存 | 建立映射时三个选择位都为零，因此索引落在 `PAT0`；本项目不编程 `IA32_PAT`，也不读 MTRR；`PAT` 是**每个逻辑处理器各有一份**的寄存器，引导处理器写的值不会自动传给从处理器 |
| AArch64 | 叶子页表项的属性索引（3 位）选择 `MAIR_EL1` 里 8 个字节属性之一 | 内核在开启分页前把 `MAIR_EL1` 写成 `0xFF`（Attr0 = Normal Write-Back Write-Allocate），设备区用 Attr1（Device-nGnRnE）；**从处理器的早期入口段写同一个值**，这一条已经对称 |
| RISC-V 64 | 页表项（Sv39）**没有缓存属性字段**；访问语义由平台级物理内存属性决定 | 建立映射时只写权限位；不使用可选的 Svpbmt 扩展；没有可查询各区间实际策略的通用只读寄存器 |

**RISC-V 那格的措辞按第二轮意见改写**：物理内存属性是**平台定义、由硬件检查**的物理地址属性——一部分由硬件设计固定，只有支持动态重配置的平台才提供 M 态软件接口去改。「缓存性由 M 态软件管理」这句规范话只覆盖缓存相关的那一类属性，不能推广成「所有物理内存属性都由 M 态软件设置」。「平台提供属性信息」与「软件能够修改属性」是两件事，此前混写会让读者以为存在一个可查询、可设置的统一接口。

由此得到三条强度不同的结论（**推理**，前提都是上表的可复核事实）：

- **AArch64 机制上闭合，还差「用到的索引」这一层**：`MAIR_EL1 = 0xFF` 只证明 Attr0 是普通写回写分配，**不证明实际建立的每个普通映射叶子都取了 Attr0**。要证的是叶子索引，不是表值。
- **x86-64 是一个条件句，不是事实**：准确表述是「**若** `PAT0` 仍保持复位默认值（写回），**且**该物理地址的 MTRR 允许写回，则映射表现为写回」。这两个前提本项目既没有声明也没有校验。引导壳运行在 UEFI 固件之后，固件有权改写 `IA32_PAT` 与 MTRR。**而且这条依赖已经在本仓被当成前提用了一次**：x86-64 的中断控制器寄存器页（LAPIC / IO-APIC）不靠页表位取「不可缓存」属性（页表没有逐页的设备位），而是靠**固件建立的 MTRR** 拿到。同一份 MTRR 状态把普通 DRAM 判成什么，却没有任何地方声明或检查。
- **RISC-V 64 只能写成平台合同**：可选的 Svpbmt 扩展给页表项加了两位，取值只有「跟随物理内存属性」「不可缓存主存」「强序 I/O」三种——**没有一个「强制写回」的编码**；而且 S-mode 能不能用这两位，由 M-mode 侧的使能位控制，该位为 0 时行为等同扩展不存在。本仓另有一条镜像记录：设备窗口的说明里写明「按普通写回缓存映射在模拟器上能用、在真实硬件上不满足设备语义」——模拟器的宽容掩盖了「平台属性没有合同」这件事，同样的掩盖对普通内存也成立。

**措辞统一**：三架构统一的是**操作系统所需的普通主存语义**——按主存的方式访问、在共享时保持一致、原子操作按主存语义生效。`WB` 是 x86 与 ARM 上表达它的具体属性名，不是 RISC-V 物理内存属性必须逐字兑现的同一硬件机制。**并且这条语义不隐含「平台必须有物理缓存」**：可缓存性、访问一致性、原子访问能力是相关但不同的三类属性。若项目要把「可缓存的 DRAM」列为平台准入条件，那是需要单独写明的加强约束，不能藏在「普通主存语义」这句话里（本方同意第二轮的判断，正文按此措辞）。

### 1.2 不写这条合同会具体坏在哪里（反向推演）

- **x86-64**：固件把 `PAT0` 改成不可缓存，内核的全部直接映射内存变成不可缓存访问。系统**能正常启动、能跑完所有测试**，只是内存带宽掉到一小部分，且差别只在特定负载下暴露。没有报错，没有日志——这条路径上每一步都「合法」。
- **AArch64**：若存在一条构造路径把普通内存叶子索引落到 Attr1（Device-nGnRnE），普通内存变成设备内存：非对齐访问直接产生对齐异常，读出未写过的地址返回零字节而不是脏数据。表现为「内核在某些随机点上死掉」。
- **RISC-V 64**：平台把某段 DRAM 的属性配成非主存语义，内核却把它当普通内存分配出去——页缓存里的数据与设备侧看到的数据不一致，故障形态是数据损坏而非崩溃。

三种坏法共同说明：**「描述符有 `WB` 位」不能推出「内核的映射按普通主存语义访问」**，中间那一跳需要每个架构各自一条可验收承诺。

### 1.3 选定合同：分层最低保证（丙案），逐架构落成条款

| 架构 | 第一版承诺 | 条款 | 现状缺口（代码事实） |
|---|---|---|---|
| x86-64 | **`PAT` 由内核自建，MTRR 只读并分析**；设备页与主存页**同批**处理 | ① 内核建立自己的 `PAT` 表，明确规定一个索引=写回、一个索引=不可缓存（组合表要求两个索引分别可用，不能靠默认复位值）；② 普通内存页表项**显式使用写回索引**，不再依赖「当前页表项恰好落在 `PAT0`」；③ 设备寄存器页**显式使用不可缓存索引**，不再依赖固件 MTRR 恰好把 LAPIC / IO-APIC 判成不可缓存；④ 所有逻辑处理器使用同一份 `PAT` 布局，上线前完成初始化，改 `PAT` 后按架构手册处理缓存与转换查找缓冲的一致性；⑤ **MTRR 分析器**：读 MTRR 并算出每个相关物理区间的有效类型。它必须是一个有独立输入、独立输出与合成用例的纯计算件，而不是启动代码里临时拼的几条寄存器判断；分析要覆盖：是否启用、默认类型、固定范围区间（处理器支持且启用时）、可变范围区间及其掩码有效性、重叠区间的优先级、物理地址宽度、以及与当前 `PAT` 布局**组合后的最终有效类型**；⑥ **各逻辑处理器的有效内存类型必须一致**——每颗核上线前读取并核对。**注意不要把「寄存器原始值一致」当成「有效类型一致」**：原始读数只是输入证据，要验的是每颗核对每个相关物理区间算出的有效类型都满足项目合同；取不到或不一致时**不得把引导处理器的分析结果当作全机合同** | ①②③④⑤⑥ 全部缺失：全仓没有任何 `PAT` 编程点，从处理器路径也没有；MTRR 从未读取；也不存在任何 MTRR/PAT 有效类型的合成计算件与合成用例 |
| AArch64 | **静态审计 + 实际页表遍历，两者都做；且两棵树分别遍历** | 静态审计证明所有普通直接映射叶子都经过统一的描述符构造路径、索引取 Attr0，设备路径取另一索引；运行时在**引导根与最终根都建好之后**分别遍历两棵树的实际叶子，核实普通内存叶子索引、设备叶子索引、被排除与被禁止范围的覆盖情况；另外**每颗核上线时读回 `MAIR_EL1`**，切到最终根后再确认**实际启用的根**与属性寄存器的解释一致。**遍历不能只统计属性索引**：属性索引选的是内存类型，共享性由叶子项的另一组位决定，两者是不同维度，普通主存叶子的共享性字段必须单独按本项目的多核一致性合同检查 | 索引统计与共享性验收不存在；`MAIR` 只写过、没读回核对过 |
| RISC-V 64 | **平台合同 + 支持平台清单**，不设计通用运行期探针 | 每个受支持平台记录其平台文档对主存访问语义的承诺；用设备树的平台识别信息把启动目标关联到该承诺；未列入清单的平台不得仅凭「模拟器能启动」认定符合合同。**清单要记的不只是「这是什么机器」，还要记到「哪个物理区间有什么能力」**。第五轮把这条从验收细节升为**平台准入合同**：规范把原子性列为按物理地址区域描述的属性，且 **LR/SC 与原子读改写是两类独立能力**（还各有可预约性与最终进展性这类附加条件）。因此「处理器实现了 A 扩展 + 一块受支持的板卡」**推不出**普通主存原子操作成立——某个区域可能只支持其中一类，或两类都不支持。清单至少要记：本 hart 实际实现的原子指令集合、普通内存候选区间的 LR/SC 支持等级、同一批区间的原子读改写支持等级、内核（自旋锁、引用计数、调度器）实际依赖哪些操作及其所需的最低合同、以及上述四项的平台文档或实测出处 | 清单不存在。本仓没有任何真实板卡的支持声明或验证 |

**x86 条款 ⑥ 的意义**：这条由第二轮提出，本方核对后接受，并认为它是本表里最容易被漏的一条——`PAT` 统一了、MTRR 没统一时，同一物理地址在不同核上可能得到不同的有效内存类型，而代码审查看不出这种差异（它只在多核真正跑起来后暴露）。这不要求操作系统接管 MTRR 编程，只要求操作系统**证明它依赖的硬件条件在多核下成立**。

对 MTRR 的分析结果，采用上一轮定的三态处置（**「无法分析」与「确定为不可缓存」是两件事**：前者是能力缺失，应当大声失败；后者是政策结论，可以降级）：

| MTRR 分析结果 | 处置 |
|---|---|
| 普通内存区间的有效类型是写回 | 允许进入普通映射候选 |
| 某区间有效类型明确不是写回，且该区间不含本次启动必需的对象 | 不进两张表，成为诊断成员 |
| 重叠配置无法按架构规则确定有效类型，或核心启动对象拿不到它必需的属性 | 判为当前平台不受支持，拒绝启动 |

### 1.4 本轮已定与剩余问题

上一版本节的三问，第三轮全部给出结论，本方采纳：

| 问题 | 结论 | 采纳后的合同表述 |
|---|---|---|
| x86 设备页取不可缓存索引是否与普通内存同批 | **同一个改动落地，不许分批** | 该改动完成时不得留下「普通内存已显式写回、设备内存仍靠固件 MTRR」的中间合同。实现内部可以分步提交，但分步提交不得进入集成基线 |
| AArch64 的两棵树遍历是永久验收还是一次性 | **调试与集成构建中的永久验收** | 不进生产启动路径；凡是改动属性索引、叶子构造或页表规划的集成测试都必须执行它 |
| RISC-V 支持清单的粒度 | **把「是否支持」与「验证状态」分成三档** | `已验证`（平台/固件组合有证据）、`已识别但未验证`（有识别资料，无平台合同证据）、`不支持`。第一版**只允许第一档启动**；「只是未验证」不得用来绕过主存语义检查 |

**剩余两问，请评审人裁定**：

1. 三档清单归谁持有：代码里的常量表（可在构建期拒绝未知平台）还是平台文档（人工核对）？本方倾向代码常量表 + 一条宿主测试断言「清单外平台不得进入启动路径」，理由是这份清单已经是准入判据，不该只存在于文档里。
2. x86 条款 ②③ 要求普通页与大页**两条构造路径都设显式索引**——本仓的普通页与大页走的是同一个旗标转换函数还是两个不同函数？若是同一个函数内分支，位位置差异要靠测试钉住；这一条属于实现细节，但第三轮指出它是**最容易漏设的位置**，本方认为应当在合同里点名两种粒度各一条验收用例。

## 2. 裁决二：类型 × 属性政策矩阵的逐行批准

### 2.1 机制背景：五步裁决顺序（已冻结，冻-6）

| 步 | 判断 | 结果 |
|---|---|---|
| 1 | **未知或不支持的条件** | 类型**既不是标准类型 0–15，也不是本配置档明确登记的项目扩展类型** → 分类错误（三段未知数值区各自独立处理：未分配区、OEM 区、OS loader 区）；ISA 属性位出现（无论有效位怎么取）或 ISA 掩码非零而有效位为零 → 分类错误 |
| 2 | **存在即拒绝启动的类型** | `UNACCEPTED`(15)、`PAL_CODE`(13) → 终止引导。**这条整机拒绝是本项目第一版不支持这两类内存的保守准入政策，不是规范要求**：规范只说未接受的内存在接受前不得使用、其它已接受区域仍可用，并没有要求因为图上出现这种区域就停止整机启动。前者在支持机密计算的平台上读未接受内存会直接故障，后者是处理器相关代码 |
| 3 | **类型强制处置（类型胜过属性）** | `RESERVED`(0)、`UNUSABLE`(8) → 排除；`MMIO`(11)、`MMIO_PORT_SPACE`(12) → 走设备窗口路径。这两类的属性位**不改变处置**：类型回答「这块区域是什么」，属性回答「能怎么用」；固件声明「不许触碰」不能被任何属性改判 |
| 4 | **普通内存候选 × 独立属性** | 候选类型是 `CONVENTIONAL`、`LOADER_CODE`、`LOADER_DATA`、`BOOT_SERVICES_CODE/DATA`、`ACPI_RECLAIM`、`ACPI_NVS`、`RUNTIME_SERVICES_CODE/DATA`、`PERSISTENT`；只要 `RUNTIME`/`NV`/`SP` 任一位命中 → 不进分配器、不建普通映射、成为诊断成员 |
| 5 | **两级准入，不是一级**（第五轮纠正本方把两个层次混写） | **来源准入**：本来源提供的证据是否足以把该区间当作普通内存候选——UEFI 来源用属性档的写回位作证据，设备树来源用它自己的输入（`/memory` 候选、保留语义、平台合同）；**架构语义准入**：本平台能否兑现普通主存语义（裁决一的逐架构合同）。两级都通过 → 按类型政策进两张表；任一不通过 → 走逐类处置表（不建普通映射、成为诊断成员），**没有任何绕行通道** |

**两处必须写清的类型行**（第五轮抓出的隐式政策，本方核实后确认成立）：

- `RUNTIME_SERVICES_CODE`/`RUNTIME_SERVICES_DATA` **按类型永远不进普通可用表**，第一版也不进普通直接映射（不支持运行时服务）。此前正文只在第 4 步的候选清单里提到它们、没有给出「缺 `RUNTIME` 属性位时怎么办」——本方核实现状：这类描述符会落到逐类处置的兜底分支成为诊断成员，因此**行为是安全的、政策是隐式的**，而 §2.3 的第 1 条判据要求「每个标准类型都有明确政策」。所以这里补显式行，并加一条交叉合同：**类型是运行时服务而属性位没有 `RUNTIME`（或反之，普通类型却带 `RUNTIME`）→ 分类错误**，不允许静默按普通内存继续走。
- 设备树的 `hotpluggable` 提示与 UEFI 的「可热插拔」属性位要有**同一条操作系统语义**（不可迁移的核心数据不落在那段内存上），但**不共用解析器**：两种来源的字段形状不同，为了统一把它们塞进同一个解析入口正是 §6.7 禁止的事（§4.3 已按此写设备树侧政策）。

三组结论完全取决于步骤先后的组合按此顺序落定：`RESERVED + NV` → 排除（属性只记录，不成为诊断成员）；`UNUSABLE + SP` → 排除；`MMIO + RUNTIME` → 设备窗口路径；`PAL_CODE + NV` → 拒绝启动（第 2 步先于一切属性裁决）。

### 2.2 七行的当前状态

**行 1：基线之外的属性位——三类分级（原则可签；**但第四轮起本行整体不能签**）**

三类分级本身成立。真正的阻断在上一层：分类器要能用一张逐位表解释属性字，就必须先知道该用哪一份出版物的表，而第四轮确认表头修订字段区分不了那几份正式文档（§7.1）。所以本行现在的状态是「**等选档机制**」——在白名单落地并至少登记一套已采样本的组合之前，把逐位表接上去等于在猜。

当前实现按**分类错误**处理：任何不属于基线掩码的属性位出现，整张内存图作废、引导失败（代码事实：解析层比对「基线已知位掩码」，掩码外有位即报错）。这是把「不静默忽略」实现成了「不容忍」。采纳三类分级：

| 属性类别 | 第一版处置 |
|---|---|
| 基线已定义、项目明确不解释且不影响安全使用的位（「更可靠」、「CPU 加密能力」） | 记录，继续；不改变分配与映射资格 |
| 基线未分配 / 保留、项目无法识别语义的位 | 分类错误，fail-closed |
| 后续版本已定义、且会影响分配安全的位（「可热插拔」——规范建议不要把不可迁移的核心代码与数据放进去） | **不得简单记录后继续**：不分配、不建普通映射、成为诊断成员；若本次启动必需的对象落在其中，拒绝启动 |

**本方的两条实现级意见**：

- 第三类的判据「核心启动对象落在其中」必须有可判定输入，否则是口号。本仓已有这样一份清单——直接映射来源里的「自举页表树」与「登记的启动模块」。建议把所有「拒绝启动」判据统一成一条横切规则：**该处置的范围与启动必需对象清单相交，且没有安全映射路径**；行 1、行 3、行 4、行 5 与裁决四共用这一条。
- **一处本方自查出的缺陷**：用来测「未知位判为分类错误」的测试哨兵取值是 `1 << 20`，而这个数值正是主流实现框架里「可热插拔」属性位的取值。也就是说，本仓「模拟一个没人认识的位」用的恰好是一个后续版本真的会用的位——该测试通过并不代表分类器能区分二者。第三类分级落地时必须先换掉这个取值，并补一条真正的保留位用例（详见 §7.1 与其现量命令）。

**行 2：`ACPI_NVS`（已签）**：第一版固定为不进分配器、不建普通直接映射、成为诊断成员，且**不因存在该类型就拒绝启动**。理由与规范一致：该类型涉及固件保留用途与睡眠状态下的内容保持，没有 ACPI 消费者时内核没有理由把它放进普通别名区，但也不能交给分配器。**明确否决**用编译期消费者开关让分类器依赖 ACPI 子系统状态——那会把政策表的取值交给另一层的运行时状态。

**行 3：普通属性不满足时的引导镜像区间（与裁决六绑定，待映射来源证据）**

- **分类资格**：`LOADER_CODE`/`LOADER_DATA` 缺写回位时，不进可用表也不进保留表，**不因成为诊断成员就自动获得普通映射**。诊断成员是记账，不是映射授权。
- **启动对象覆盖**：对启动仍必须访问的对象（内核镜像、入口代码、栈、交接数据、分类输出数组），必须有明确的专用映射来源，并同时证明：物理区间与实际对象的边界相符；在对应页表切换阶段仍可访问；**所用属性与该区域实际支持的属性一致**；不产生同一物理页的两套缓存属性别名；不会因此被分配器当成可用页。若无法证明某个缺写回位的引导区间只包含「已被专用映射覆盖且不会被普通映射访问」的对象，则拒绝启动。
- **仓库事实（本方核出，决定了这一行不能按「已有覆盖，签」处理）**：引导根的恒等段现在是无差别覆盖低 4 GiB（§0.3），所以「切根之前引导数据可达」这一条**今天就是靠它满足的**。它满足上面的第 1、2 项，但**不满足第 3、4 项**——这段映射一律用普通可缓存可执行属性，且与最终直接映射构成同一物理页的别名。因此这一行的真实状态不是「等一份证据」，而是「合同作用域未定义」，必须与裁决六一起判。

**行 4：`PERSISTENT`(14)（已签，但承诺范围按第五轮缩小）**：不进普通分配器、不建普通直接映射、记录数量与总字节数与**有界样本**；**不因固件报告了持久内存就拒绝整机启动**。

**本方删掉一句兑现不了的承诺**。上一版写「保留完整范围信息，不能只留计数，否则将来无法恢复范围」——第五轮指出它与本文件自己的诊断模型没有共同载体：样本有界、可截断、且不跨交接边界。100 段持久内存配 64 格样本，剩下 36 段的地址没有任何地方保存，而「语义成员集合是完整的」并不等于那些物理地址被存下来了。两个自洽选项：

| 选项 | 内容 | 本方选择 |
|---|---|---|
| 一 | 第一版**不承诺**将来可直接恢复：只保留总数、总字节与有界样本；将来真做持久内存支持时，另立范围来源与载体 | **选此** |
| 二 | 第一版就承诺完整保存：新增独立的 `PersistentRanges` 存储与其容量合同，**不得复用可截断的诊断样本** | 否：为尚不存在的功能给引导链再加一份范围协议，与本简报的取舍纪律一致地不划算 |

若将来出现真实消费者，必须走二，并把它当作一次跨边界契约变更（同 §6.6 的清单）处理，不能悄悄借用诊断数组。该类型在规范里是「可按常规内存工作但非易失」，不等于坏内存，也不等于未接受内存；暂不使用是资源政策。拒绝启动的触发条件统一走行 1 的横切规则。

**行 5：固件服务代码/数据 与 `ACPI_RECLAIM`（政策已签；第二轮要求加保留区例外，本方核对后确认这条例外在本仓是活的）**

| 类型 | 第一版结果 | 回收前提 |
|---|---|---|
| `BOOT_SERVICES_CODE`/`BOOT_SERVICES_DATA` | 成功退出引导服务之后**进入可用表** | 不再等 ACPI；需证明「引导服务依赖已结束」**且不覆盖任何声明过的保留范围** |
| `ACPI_RECLAIM` | 保留映射，不进分配器 | ACPI 表解析完成、必要数据已复制、引用已解除 |

- **规范依据**：成功退出引导服务之后，操作系统加载器可以把这两类当作可用空闲内存——这是规范明确给出的能力，继续留在保留表是项目自行放弃。本仓依赖的第三方库自己的文档也逐字写明「内存图中标为这两类的数据会变成空闲内存」，并同时要求调用方保证「不再有指向引导服务数据的引用」。
- **不设地址窗口条件**：「只回收某个地址范围内的部分」被否决。回收是生命周期合同，不是地址猜测。
- **存活对象守卫（本方补）**：风险不在规范，而在**我们自己的存活对象**。核查结果对本方有利：引导期堆（池分配）与全部自举分配、读图缓冲都取 `LOADER_DATA` 类型，因此「存活对象恰好落在被回收的引导服务数据里」在当前代码里不成立。但它是**必须被守住的不变量**：任何将来改用引导服务类型做分配的代码都会静默破坏它。落地时把「引导期一切分配取 `LOADER_DATA`」做成一条守卫（代码检查或宿主测试断言分配类型），并把第三方库文档列的那份检查清单（协议引用、会在析构时调用释放的池对象等）作为验收条目。
- **保留区例外（第二轮提出，本方接受并给出落点）**：设备树规范对 UEFI 启动的情形有一条配套要求——静态保留区的范围仍应出现在 UEFI 内存图里，其中 `no-map` 的标为固件保留类型、其它静态保留标为引导服务数据（**评审人引用，本方未取得原文段落，[待验证]**）。若该条成立，「无差别回收引导服务数据」会正好把设备树声明的非 `no-map` 静态保留区交给分配器。**这不是理论风险**：本仓 aarch64 的 UEFI 腿**已经同时持有两份内存来源**（见 §4.4），叠加规则因此有明确插入位置。若规范原文核实不成立，则退化为「不回收与任何声明过的保留范围相交的引导服务数据」这条保守政策——两边不能都不做。

**行 6：OS loader 自定义类型——不预建注册机制（已签）**

不建没有消费者的通用注册表。将来第一次真正使用该数值区间时，必须同批提供：精确的类型常量、一条明确的分类政策、对应的属性与生命周期处理、常量与分类结果的测试；除此之外的该区间数值仍判分类错误。这不是「以后临时改分类器」，而是「每新增一个类型都显式扩充枚举与穷尽匹配」。**第五轮把这条与 §2.1 第 1 步接上了**：第 1 步的判据已改成「既不是标准类型、也不是**本配置档明确登记**的项目扩展类型才算未知」，因此「不预建注册机制」在代码里的形状是**编译期登记的枚举变体 + 穷尽匹配**，而不是运行时可写入的注册表。本方补一句验收强度：那四样东西要写成条款而不是建议，否则第一次使用时的压力会落在「先让它跑起来」。

**行 7：诊断样本超限（上一轮已签为乙；本轮补命名与配额两条）**

采纳「有界样本 + 总量统计 + 显式截断标志」，诊断容量不足不否决启动；两遍扫描的事务性不受影响（第一遍已知总数、容量、样本数与截断位，第二遍最多写 N 条）。两条本轮补充：

- **命名要改**：现有的样本容量常量语义上只覆盖「诊断成员」这一类，而新的诊断模型不止这一类（还有排除、设备路径）。沿用旧名会让读者以为它是所有处置合计的容量。落地时改名或加显式限定。
- **配额按处置独立**：可以共用一块静态缓冲，但每种处置要有独立计数、独立样本配额与独立截断标志；致命触发记录单独存放。否则某一种处置大量出现就会挤掉其它类别，最后无法回答「哪一类被截断」。

**术语统一**（与冻-5 的措辞配套）：**诊断成员集合**是所有「保留但不建普通映射」的范围（语义集合，完整）；**诊断样本**是实际存储的有界数组（不承诺完整）。样本截断不改变分类结果。本文此后凡说「成为诊断成员」指语义集合，说「样本」才指那个数组。

### 2.3 「政策矩阵不会漏格子」的验收判据（上一轮已签）

固定的执行路线只保证裁决函数一定有返回值，不保证每个返回值对应的政策是有意的。完整的验收至少需要：

1. 所有标准类型 0–15 都有明确政策；
2. 三段未知类型区间都有明确的失败动作；
3. 基线内每个已知属性位都有明确处置（五者必居其一：参与准入 / 改变分配 / 改变映射 / 记录但忽略 / 出现即报错）——逐位兑现表见 §2.5；
4. ISA 有效位与掩码的组合完整定义；
5. 未知属性位明确区分 fail-closed 与显式支持的后续属性；
6. 每个类型与独立属性的组合都由五步顺序唯一决定；
7. 所有进两张表的描述符还须通过裁决一的架构准入。

测试穷举**政策等价类的交叉组合**，并对所有未知位位置做逐位测试；随机采样只作补充。具名用例除四个顺序组合外，含：`CONVENTIONAL + WB + RUNTIME`、`LOADER_DATA + 可热插拔`、**未知位与强制排除类型的组合**（检验第 1 步与第 3 步谁先）、已登记的项目类型与未登记的 OS loader 数值的边界。本方补一条：**逐位测试必须把「保留位」与「后续版本已定义位」分成两组**，否则会重复行 1 那个测试哨兵的混淆。

### 2.5 逐位处置表（第三轮要求把验收判据在正文兑现）

§2.3 的第 3 条判据是「基线内每个已知属性位都有明确处置，五者必居其一」。此前正文只按类别写，没有逐位兑现——本轮补齐。**但下表不是按「UEFI 2.10」这个笼统标签兑现的**：第四轮确认 2.10 本身有多份正式发布物且属性位取值并不相同（§7.1），因此每张逐位表都必须绑定一个**配置档标识**才有意义。

**本档的身份（第五轮要求，本方采纳）**：下表既不是 2.10 原始版、也不是勘误版、也不是 2.11，而是**以本仓钉死的依赖库头文件布局为基础的实现兼容档**，标识记为 `MEMATTR_PROFILE_UEFI_RAW_0_9`。这个名字刻意不宣称任何规范归属——按 §7.1 的矩阵，本仓常量里 `WP`/`MORE_RELIABLE` 与原始版一致、`ISA_MASK` 与勘误版一致，**没有任何一份出版物与本档完全吻合**。列名「本档取值」的实际数值由 §7.1 的白名单条目决定，换档就要换整张表与它绑定的用例。

| 属性位 | 本档取值 | 处置 | 说明 |
|---|---|---|---|
| `UC` / `WC` / `WT` / `UCE` | `0x1` / `0x2` / `0x4` / `0x10` | **记录但不改变政策** | 缓存能力声明。一个区域可以同时声明多种能力，准入判断只看是否具备普通主存所需的属性；不具备时才走第 5 步的缺失处置 |
| `WB` | `0x8` | **参与准入** | 进两张表的必要条件之一，且必须与裁决一的架构合同一起看（描述符声明写回不等于内核映射按写回兑现） |
| `WP` | `0x1000` | **记录但不改变政策** | 规范把它归在**物理内存保护属性**一类下，描述「硬件支持把该区域配置为写保护」；同一份规范又说它目前通常被用作缓存属性。所以准确表述是：**它是能力声明，不是当前页表的实际写权限**。第一版记录该位，既不因它存在而修改页表写权限，也不因它存在而改变普通内存准入；规范自身的这两重归类要照写出来，不要只挑其中一句 |
| `RP` / `XP` / `RO` | `0x2000` / `0x4000` / `0x20000` | **记录但不改变政策** | 这三位的含义是「硬件**能够**做该保护」，不是当前权限状态。不得仅因位存在就把区域判成不可读、不可执行或只读 |
| `NV` | `0x8000` | **改变分配 + 改变映射**（第 4 步） | 独立于类型：即使类型是常规内存也不进分配器、不建普通映射，成为诊断成员。属性与类型可能不一致，判断只看属性 |
| `SP` | `0x40000` | **改变分配 + 改变映射**（第 4 步） | **规范说的是提示**：该区域为特定用途预留，建议操作系统不要把不可迁移的核心数据与代码放进来；规范并没有要求所有带该位的区域绝对不得映射。本项目的「不进分配器、也不建普通映射」是**比规范更严的第一版准入政策**，正文与注释都要这样标注，不能写成规范强制 |
| `RUNTIME` | `0x8000_0000_0000_0000` | **改变分配 + 改变映射**（第 4 步） | 需要运行期专用虚拟映射，与普通映射是两回事。**普通机器上正常出现，不得因本项目当前不调用运行时服务而拒绝启动** |
| `MORE_RELIABLE` | `0x10000` | **记录但不改变政策** | 政策表登记「当前不解释」；不得静默忽略。这一位的取值在**不同发布物里不同**（见 §7.1 的四份读数），所以「同一位在不同档里含义相反」的风险是真实的，不是假设 |
| `CPU_CRYPTO` | `0x80000` | **记录但不改变政策** | 加密能力标记，第一版不据此改变任何资格 |
| 「可热插拔」 | **本档未定义**（依赖库布局里没有这一位） | **出现即报错**（第 1 步，按档外扩展位处理） | **第五轮抓出的漏项，本方核实后确认**：主流实现头文件把这一位定义为 `0x100000`，而本档钉死的依赖库里没有它（现量命令见 §10）。所以它既不是本档已知位、也不该被当成「空白保留位」——记录要能区分这两种情况（§7.1 的三组用例第二组）。若将来改绑到含该位的档，它必须作为**已知但不支持**的位进入 §2.2 行 1 的第三类处置，而不是继续按未知位失败 |
| `ISA_VALID` | `0x4000_0000_0000_0000` | **出现即报错**（第 1 步） | 本项目的三个架构都不解释 ISA 掩码 |
| `ISA_MASK` 覆盖的位 | 掩码段（本档为 `0x0FFFF00000000000`） | **出现即报错**（第 1 步） | 掩码非零而有效位为零的组合同样报错——那是不自洽的输入，不是「没有属性」。掩码本身的取值也随发布物不同（§7.1） |
| 本档未分配的空档位 | 配置档之外的任何未登记位 | **出现即报错**（第 1 步） | 「保留位」的判据依赖 §7.1 选出的配置档；**选档失败时根本走不到这一行** |

**为什么这张表不能靠「未知位一律容错」来实现**（第四轮把上一版的例子升级了）：同一个数值位在不同发布物里的身份可以完全不同——按四份读数，`0x10000` 在一份里是「更可靠」、在另一份里是「可热插拔」；`0x1000` 在一份里是写保护、在另一份里是「更可靠」。**两种解释都合法且方向相反**：前者只是提示、后者禁止把不可迁移的核心数据放进去。所以必须先按已核实的固件组合选档或拒绝，再谈逐位处置；把某一张逐位表套到任何版本的属性字上，等价于猜固件读的是哪一份 PDF。

**逐位表的验收方式**：本表每一行都要有一条对应的宿主测试（位单独置位、其余取**该 `AttributeProfileId` 的合法组合夹具**——夹具随档提供，不硬编码某个版本号），加上 §7.1 的三组未知位用例；行与用例的对应关系要能在测试文件里按名字找到，否则「逐位都有处置」仍是文档承诺。

## 3. 裁决三：退出引导服务之后的端到端验收

**状态：路径分工与两遍扫描原则已签；接线与覆盖证明待实现证据。**

### 3.1 机制背景：两种顺序，以及我们现在实际站在哪一条上

引导壳必须做一件带有事务性质的工作：读内存图得到一个版本戳，然后用**同一个键**去调用退出函数——中间只要有任何分配改动了内存图，键就失效，必须重读重试。

**先把事务表述改准确（采纳第二轮纠正）**：规范里退出引导服务这个调用**接收**版本戳、**返回**状态码，它本身不返回一份内存图；内存图是此前由读图服务取得的。「成功退出」的含义是**固件接受了与这个键对应的那次快照**。因此路径 A 的准确流程是：

1. 完成所有自举分配；
2. 调用读图服务，**保留**描述符快照及其版本戳；
3. 用该版本戳调用退出服务；
4. 只有成功后，才把**与成功版本戳配对的那份快照**交给分类器。

本项目自己的退出封装函数可以返回一个含快照的结果对象，但那是**封装层保留下来的读图数据**，不是固件退出调用的返回值。文档层面的意义在于：退出之后**不能**再调用读图服务去取所谓「最终图」——那时读图服务已经失效。这不推翻路径 A，只是让事务合同准确。

| 顺序 | 做法 | 关键差异 |
|---|---|---|
| **生产式（路径 B）** | 读图 → 分类 → 用同键退出；键失效则重来 | 分类发生在引导服务还活着时；读图与退出之间**零分配**，所以图不会因为自己的动作而改变 |
| **路径 A** | 先完成全部自举分配 → 取快照并留底 → 用该键退出 → 成功后用那份快照分类 | 那份快照就是退出所依据的那张图，因此包含所有自举占用（含读图缓冲自己那一块）；代价是分类发生在引导服务已失效之后 |

**当前实现的准确位置（代码事实）**：生产腿走路径 B（一个用函数指针表达读图与退出的配对循环，可被模拟固件在宿主测试里驱动）。**辅助/测试腿两条都不是**——它在退出之前自己另读一份快照，然后把封装函数返回的那份快照**显式丢弃**（那段丢弃的注释理由是「内核已经通过另一个入口拿到了常规内存区间」）。因此路径 A 在本仓**尚未接线**，实际改动面是：把取表入口从「自己调读图服务」改成「消费与成功键配对的留底快照」，并让 15 个共用它的测试载体跟着改调用形状。

### 3.2 六项验收（已定义，待跑）

| 验收 | 标准 |
|---|---|
| 原始内存图访问 | 用元数据里的**有效图长度**，不能用分配缓冲的长度（缓冲按「留几条余量」分配，长度不是步长的整数倍） |
| 分类零分配 | 分类路径上没有任何临时堆分配 |
| 输出零分配 | 输出容器指向事先准备好的静态存储或交接区 |
| 错误退出 | 退出后分类失败 → 不依赖引导服务的停机路径，不返回固件环境 |
| 析构安全 | 快照缓冲的持有、遍历、分类、析构都不调用失效服务，也不经依赖引导服务的日志后端 |
| 输出生命周期 | 输出数组所在区间在内核消费期间保持可访问，且不进入可用表（可访问性要说清是哪棵树：L2 还是 L3） |

### 3.3 四个问题及其当前结论

**问题 A：输出数组的归属 → 预分配启动对象存储 + 构建期**与**运行期两道证明**

不能只因为输出数组是静态变量就认为它安全。采纳的合同：输出缓冲、根页表页、自举区间以及其它跨切根仍需访问的对象，全部在交接之前预分配，并由**同一套启动对象覆盖检查**登记（这条通道本仓已有——直接映射来源里的「自举页表树」与「登记的启动模块」两类候选）。若镜像自身的映射来源确实完整覆盖输出数组，可以使用，但必须证明；**明确否决**「退出后再拷进刚分配的堆」（退出之后不能分配，复制目的地必须事先存在）。

两道证明不可互相替代（第二轮意见，本方接受并撤销上一版「倾向构建期」的表态）：

- **构建期**：核对镜像符号、静态输出区间与预期的段边界——回答「对象在哪里」。
- **运行期**：遍历实际建立的页表叶子，核对这些对象是否被覆盖、属性是否符合合同——回答「实际映射了什么」。

**问题 B：退出之后失败的观测格式 → 结构化行**

失败只剩裸串口。三个架构在测试环境里的控制台设备各不相同（x86 的 ISA 串口、AArch64 的串口控制台、RISC-V 的 SiFive 串口），而判定脚本按行读串口输出判通过/失败。采纳：**成功与失败都用机器可读的稳定文本**——成功路径输出一条摘要行，失败路径输出一条致命行；致命行含固定版本号与失败前缀、稳定的错误码、裁决步骤、处置结果，以及原始描述符四元组（类型、物理起点、页数、属性；没有具体描述符时相应字段留空），形如：

```
BOOT_FATAL v=1 code=CLASSIFY_UNKNOWN_ATTR step=1 type=0x7 base=0x80000000 pages=0x100 attr=0x0
```

流水线解析失败前缀即判失败；人类可读说明可以作为紧跟的一行，但不能是唯一接口。

**成功摘要行必须能回答四件事**（第二轮要求，本方认为这条比格式本身更重要）：每种处置的描述符条数、每种处置的总字节数、保存下来的样本条数、是否发生截断。只报「共排除若干条」不足以判断政策是否误判。

**问题 C：「退出后到分类结束不切地址空间」→ 类型化的阶段对象（本轮补一个中间对象）**

上一版本节给了四条概念约束（成功退出才产生「已退出引导服务」对象；分类函数消费它并产出「已分类启动」对象；只有拿到后者才能执行页表切换；原始快照对象不允许从分类函数逃逸）。第三轮指出**这四条完整描述了路径 A，但与路径 B 直接矛盾**——路径 B 的分类发生在退出之前，按那四条它连产出对象的资格都没有。本方接受，这是措辞问题之外的真实设计缺陷。

修正后的语义要区分**预备分类**与**提交后的分类结果**，两条路径只在后者汇合：

| 路径 | 阶段序列 |
|---|---|
| **A（退出后分类）** | 取得快照并留版本戳 → 用该键成功退出，产生「已退出引导服务」→ 消费快照分类，产生「已分类启动」 |
| **B（退出前分类）** | 取得快照并留版本戳 → 分类并预检，产生**绑定这一份快照与这一份版本戳**的「预备分类结果」→ 用同一版本戳成功退出，才允许把它**提交**为「已分类启动」→ 版本戳失效则丢弃这一份预备结果，重读、重分类、重试 |

于是真正的不变量被表述成一句话：**无论分类发生在退出之前还是之后，只有成功退出之后提交的「已分类启动」才能进入后续页表构造与切根路径**——而不是要求所有分类代码都发生在退出之后。上一版那句「分类完成前不可切根」是这条不变量的特例。

**本方补的仓库事实（说明这不是新增机制，而是把已有机制类型化）**：路径 B 的配对循环今天已经在每一轮调用分类器之前**显式清空交接区里那两份映射分区**（`os/boot-shim/src/ebs_pair.rs` 的重试循环第一句就是重置调用）。也就是说，「上一轮的分类结果不能被这一轮之后使用」这件事当前是靠**运行时重置**维持的；引入「预备分类结果」这个类型之后，同一约束改由**类型不可提交**来表达，重置从「必须记住要做」变成「不做也不会读到脏数据」。这是本条改动的真实收益，应当写进合同而不是当成接口美化。

第三轮同时确认了本方的两点：只有**成功那一轮**才产生「已退出引导服务」对象；阶段类型要**覆盖两条腿**（本方上一版想只约束测试腿，已被否决，理由见 §3.3 前的说明）。本方保留的实现前提仍然有效：路径 B 的读图与退出走项目自有的函数指针循环（为了让宿主测试用模拟固件驱动），所以**模拟固件装置也要产出同样的阶段对象**，否则类型约束在那条腿上只是纸面存在。

**第四轮补的一条硬约束：类型不能替本项目清零内存**（本方接受，这条纠正了本方上一版的一句过度表述）。上一版写「重置从必须记住要做变成不做也不会读到脏数据」——**这个说法过头了**。本项目的分类输出实际写在交接结构的**静态存储**里：类型系统能限制谁能拿到、能不能提交，但一个预备结果被丢弃时，**不会有析构去把那些字节清零**。失败的具体形状是可构造的：

1. 第一轮分类往交接数组写了 5 条；
2. 退出返回「版本戳失效」；
3. 预备结果被丢弃；
4. 第二轮只产出 2 条；
5. 若第二轮没有把长度与计数重新归零，物理上第 3–5 条旧数据仍在，内核侧读到的是**两轮混起来的脏结果**。

所以阶段合同要把不变量写成可检查的形式，而不是靠「类型安全」四个字：

| 不变量 | 含义 |
|---|---|
| **独占有效访问权** | 预备结果独占本轮输出缓冲区的有效写权；未成功退出之前，任何代码不得把它当成有效交接数据读取 |
| **绑定关系** | 预备结果绑定这一份快照与这一份版本戳，提交时校验二者同源 |
| **失败轮次不可提交** | 版本戳失效的轮次，其预备结果在类型上不能进入「已分类启动」 |
| **每轮从零开始** | 新一轮必须以**空计数与空有效长度**开始，不能沿用上轮计数 |
| **只有有效前缀可被消费** | 提交成功后，内核可消费的只是本轮写入的那一段前缀 |
| **清零保留为防御** | 现有的重置继续保留，但它的角色是防御性措施，不是不变量的主要执行者 |

同时本方接受第四轮对 §3.4 遗留问题的裁决（**两条独立用例**，不是同一用例换输入）：路径 A 验「退出后分类消费的是与成功版本戳配对的那份快照」，路径 B 验「预备结果只能由同一版本戳的成功退出提交」——两者踩错的代码位置不同，合并成一条会漏掉其中一半。

**问题 D：容量与样本读数 → 一次受控启动全部采集**

两张交接表的容量（128 条、256 条）属于硬合同，**超限即 fail-closed，不截断**；诊断样本按行 7 截断并报告。一次启动里同时记录：各阶段描述符条数、最终快照的有效长度与步长、**读图服务返回的描述符版本**与表头修订值、第一遍算出的**全部**输出条数（分类三路 + `PmmExcludedRanges` + `BootMapDenyRanges` + 启动必需对象集合 + 诊断样本）、各来源的原始计数与去重后的唯一页数（§5.3 的两种口径）、各处置的样本用量与截断位、各输出容器的容量与剩余量。上一版这里的「三类输出」是漏项：规划阶段的四个集合一个都没列。

一个数量级的提醒（**推理**）：路径 A 用的是与成功键配对的快照，其条数通常比更早的快照多——一次分配可能把一个常规区间切成三段，净增两条描述符。因此「128 / 256 够不够」在两条顺序下的答案不同，需要在各自那条腿上分别取数。

### 3.4 本轮已定

上一版本节的两问，第三轮都给出结论，本方采纳：

| 问题 | 结论 | 采纳后的表述 |
|---|---|---|
| 错误码表与政策原因表要不要合成一套枚举 | **两张表分开，共享命名风格与稳定格式** | 致命行的政策原因字段**不必强制存在**：错误码本身要能说明为什么停止；只有当致命确实由某条描述符的政策判断引发时，才附带一个政策原因。无描述符的错误不允许伪造一个原因字段 |
| 阶段类型覆盖两条腿后，配对循环的重试怎么表达 | **失败的那一轮不产生「已退出引导服务」对象**；路径 B 必须有「预备分类结果」这一中间类型 | 见 §3.3 问题 C 的阶段序列表。中间类型的必要性在于：没有它，「本轮的预备结果」与「本轮的成功退出」之间就没有可表达的绑定关系，重试时无法证明提交的是配对的哪一份 |

**本节的验收形式已定**（第五轮直接签署本方倾向）：**两条独立用例**，不是同一用例换输入——A 验「退出后分类消费的是与成功版本戳配对的那份快照」，B 验「预备结果只能由同一版本戳的成功退出提交」。

**剩余一问（新增，第五轮提出）**：重试阶段的类型要不要再细一层。第一次调用退出服务失败之后，规范警告引导服务可能已**部分关闭**，此后加载程序不应再使用其它引导服务能力。建议引入一个受限阶段：它只提供重试所需的最小能力（重新读图、取新键、再试退出），而不是继续把自己伪装成「引导服务仍完整可用」。本方同意并倾向把 `Plan` 一类的重试动作挂在受限阶段上；请评审人确认粒度：**两个阶段（可用 / 受限重试）**，还是**三个（可用 / 受限重试 / 已退出）**。

## 4. 裁决四：设备树来源的保留区与不可映射节点政策

**状态：方向已定（静态保留区 + `no-map` + 安全切除）；输入边界补齐后才谈签字。**

### 4.1 机制背景：两条来源不能共用一套政策

统一的分层是已冻结的方向：UEFI 来源（类型 + 属性）与设备树来源（内存节点、保留区域等）各自经过**自己的来源政策**，汇进同一份操作系统内存语义，再由架构映射层落到页表。

设备树描述内存的方式与 UEFI 不同：`/memory` 节点用 `reg` 列出系统内存区间；`/reserved-memory` 子树逐条列出被保留的区域，每条可以带 `no-map` 表示更强的约束，也可以带其它提示（为某设备划出、可重用、跨重启保持等）。规范还区分**静态 `reg` 型节点**与用 `size`/`alignment`/`alloc-ranges` 表达的**动态选址节点**（后者要求操作系统按约束自己选址）。

已核实的设备树侧行为只有两条（代码事实）：解析 `/memory` 的 `reg`；按固件常驻区的末端裁掉区间前缀。未覆盖：`/reserved-memory` 子树（**任何腿都没解析**）、`no-map`、保留区与内存区的交集处理、被禁用的内存节点、多段 `reg`、地址与长度单元的变体、unit-address 形态，以及**设备树自身的保留映射块**（文件头之后的独立区间列表，见 §4.3）。

### 4.2 「UEFI 启动时忽略 `/memory`」不等于忽略整个保留语义（第二轮纠正，本方接受）

上一版本节写的是「本节政策只适用于不经 UEFI 内存图的引导腿，不应变成 UEFI 腿的第二套内存来源」。第二轮指出这条划得太宽：规范明确 UEFI 启动时**系统 RAM 应来自固件内存图、`/memory` 节点必须忽略**，但对**静态保留区**规范另有要求——这些范围仍应出现在 UEFI 内存图中（`no-map` 的标为固件保留类型，其它静态保留标为引导服务数据），也就是说 `/reserved-memory` 在 UEFI 启动下**仍是保留语义的输入**，只是不是 RAM 范围的输入（出处：设备树规范 §3.5.4，评审人核实并给出小节号；本方未能逐字核对原文，见 §4.3 的出处表）。

要把两种输入语义分开写：

| 输入 | UEFI 腿 | 非 UEFI 腿（裸机） |
|---|---|---|
| `/memory`（RAM 范围） | **忽略其来源身份**；内存类型与生命周期由固件内存图决定 | 作为普通内存候选 |
| `/reserved-memory` 静态 `reg`（保留范围） | 作为**保留语义的叠加输入**：与固件图做对照，并用于 §2.2 行 5 的回收例外 | 作为保留语义的主输入 |
| 设备树自身的保留映射块 | 规范另要求这些条目反映在固件内存图里（类型为固件保留），因此这条腿也要读它做对照 | **必须处理**，见 §4.3 |

### 4.3 保留来源要分开命名：两个是区间集合，一个是前缀阈值（第四轮再修正）

上一版本节把三样东西并列成「三个保留来源」。第四轮指出**第三样不是同一类东西**：本仓那个所谓「固件常驻区」不是区间声明，而是一个**全局裁剪阈值**，把它与前两者并列会诱使后续代码把它当成普通保留区间、与任意地址的保留范围取并集。本节据此改为「两个区间来源 + 一个前缀阈值」，并给出更合适的名字（`ReservedPrefixEnd`，读作「保留前缀的末端」）。

| 类别 | 实际含义 | 格式与合同（出处见下面的分级表） | 本仓现状（代码事实） |
|---|---|---|---|
| **设备树自身的保留映射块** | 设备树文件头之后的独立保留区间列表，不在节点树里 | 由文件头里的偏移字段指向；每项是两个 64 位大端整数（地址 + 长度）；各项之间不得重叠；以 `{0, 0}` 结束；每项在文件内 8 字节对齐；规范明确**允许设备树本体自己就在这个列表里** | 依赖库**已经提供**遍历这个列表的接口（钉死的 `fdt = 0.1.5` 暴露 `memory_reservations()`），本仓**零调用点** |
| **`/reserved-memory` 子树** | 节点树里的保留区域，带 `no-map`/`reusable` 等属性 | 静态 `reg` 与动态 `size` 两种形态 | **任何腿都没有解析** |
| **`ReservedPrefixEnd`（前缀阈值，不是区间集合）** | 本项目传给内核的一个物理地址上界：低于它的整段当成固件常驻区 | 单一数值，只能表达「低地址前缀」。RISC-V 侧传内核物理基址；引导壳那条腿传零（等于不裁剪） | 存在。**它不是第三个保留列表**，不能与任意位置的保留区间做并集 |

**由此暴露的一个真实局限（本方按读数补）**：把固件常驻区建模成「一个上界」意味着**只能裁掉低地址前缀**——任何位于该上界**之上**的保留区域，本仓当前模型完全看不见。设备树自身的保留映射块恰恰就是一个可以出现在任意地址的区间列表。也就是说，「第三来源」不只是名字问题：它是现有模型表达不了的一类输入。依赖库已经把解析接口送到手边，缺的只是消费它的那几行。

**第三轮给出的规范小节号**（本方未能独立取到规范原文逐字核对，因此按「评审人核实并给出出处」登记，比上一版的「未能取得来源」更精确；其中父节点的单元数与 `ranges` 要求另有一份内核绑定文档佐证）：

| 事项 | 出处（评审人给出） | 内容 |
|---|---|---|
| UEFI 启动时忽略 `/memory` | §3.4.1 | 见 §4.4——本方据此撤回上一版的结论 |
| 静态保留区在 UEFI 图中的类型 | §3.5.4 | `no-map` → 固件保留类型；其它静态保留 → 引导服务数据 |
| `reg` 与 `size` 同时出现 | §3.5.2 | `reg` 优先，`size` 忽略 |
| `no-map` 与 `reusable` | §3.5.2 | 互斥 |
| 保留映射块与 UEFI 图 | §5.3.3 | 条目须反映在 UEFI 内存图中，类型为固件保留 |
| 保留映射块不可访问 | §5.3.1 | 除非启动程序明确说明用途，客户端程序不得访问 |

**保留映射块的处置不能只写「纳入或非空拒绝」，它带的是访问合同**（第三轮要点，本方接受）：规范对客户端程序的要求是**不得访问**这些区域，除非有明确的用途授权。这与「保留但可以经直接映射访问」正好相反——把它塞进保留表是**语义降级**。因此第一版按保守策略写：

| 情形 | 第一版处置 |
|---|---|
| 保留映射块条目，且没有用途授权 | 不进可用表；**不得**作为普通启动对象访问；按项目加强策略一并入**启动映射禁止清单**（与 `no-map` 共用区间传输格式，但来源、原因与审计结果各自独立） |
| 保留映射块条目与启动必需对象相交 | 触发 §6.3 的冲突检查；**不允许「先禁止映射、再指望系统继续跑」** |
| 项目暂时无法表达这项语义 | 遇到非空保留映射块即拒绝启动，**而不是默默塞进保留表** |
| `/reserved-memory` 静态 `reg` 条目 | 按 §4.4 的切除规则处理 |

**这条合同会反咬本项目自己**（第四轮指出，本方核对后认为这是本轮最容易漏的实现问题）：规范**明确允许设备树本体就出现在保留映射块里**，而本仓的裸机腿与 aarch64 的 UEFI 腿都会在引导期持有指向设备树原始存储的指针（解析 `/memory`、平台描述、出界闸都靠它）。于是可能出现：保留映射块禁映射的那段地址，正是本项目还在读的 DTB 缓冲区，或某个启动模块的原始存储。合同要写成可验收的一条，而不是留到失败时才发现：

> 设备树本体以及任何启动模块的原始存储区域若落在保留映射块内，必须明确它的**访问阶段**与**生命周期**：需要在禁止映射生效之后继续访问的内容，必须先复制到允许使用的存储；做不到就启动失败。**禁止一边把该页排除出映射、一边留着指向原始地址的指针。**

本方补一条相关的实现观察：本项目已经有「复制后再用」的先例——交接区在切根前被深拷贝进内核自己的存储，此后不再访问原始地址。这条 MRB 规则应当复用同一种形状（复制到允许存储 + 显式声明原始指针的失效点），而不是新发明一套生命周期机制。

**本方补的两条仓库实测**（评审人看不到代码）：

1. `/memory` 侧**已经**遍历全部 `reg` 对——收集器是 `for region in node.reg()`，且走全树枚举以兼容带 unit-address 的节点名。但**容量只有 8 格，超出部分被静默丢弃**：既没有失败，也没有诊断，也没有计数（`if free_n < 上限 { 写；计数 }`，没有 `else`）。也就是说本简报担心的「只读第一对而丢其余」，在本仓的实际形状是「读到第八对为止，其余无声消失」——在多内存条、多 bank 的机器上表现为少识别一整块 RAM，且没有任何线索指向原因。**登记为缺陷**：超过容量必须失败或至少打诊断（现量命令见 §10）。
2. 区间数学**不需要新写一套**。本仓已有一个同源实现：内核侧按页向外取整、并对末端做饱和处理的纯函数（`os/kernel/src/memmap.rs:cut_memmap`，行为继承 C 原版并有宿主用例）。归一化合同应当与它同源，而不是让引导壳、映射规划与覆盖验收各算一遍——那正是 §6.7 要防的事。

**第一版支持边界**（把上一版「解析不了就拒绝」改成可直接测试的判据，采纳第三轮建议）：

| 输入形态 | 第一版处置 |
|---|---|
| 静态 `reg` 保留节点 | 支持，**且必须遍历 `reg` 里的全部地址/长度对**（规范允许任意多对）。实现若暂时只能处理单对，遇到多对必须明确失败——**只读第一对而丢掉其余是禁止的**（同一要求适用于 `/memory`；本仓现状见下条的实测注记） |
| 同时有 `reg` 与 `size` | 按 `reg`，忽略 `size` |
| 只有 `size`/`alignment`/`alloc-ranges`（需操作系统选址） | **明确失败**（不静默忽略，也不假装支持） |
| `no-map` | 支持，语义见 §4.6；进入启动映射禁止清单 |
| `no-map` 与 `reusable` 同时出现 | 非法组合 → 分类错误 |
| `reusable` **单独**出现 | 范围从普通分配器排除，允许保留普通映射，但**第一版不交给通用分配器、也不实现可回收使用**；诊断里保留该属性。这是**有意放弃一项可用性**，不是把 `reusable` 解释成 `no-map`——它的规范语义是「操作系统可放可再生或可迁移的数据，拥有该区域的驱动必须能收回」，与「禁止映射」是两回事 |
| `/memory` 上带 `hotpluggable`（非 UEFI 腿） | 第一版从普通分配器排除、不进入核心内存分配；允许保留普通映射。若本项目不打算实现这条处理，就**明确拒绝该节点**，不许静默忽略。它与 UEFI 的「可热插拔」属性位共享同一条操作系统语义，但**不共用解析器** |
| `/reserved-memory` 父节点的单元数与 `ranges` | **只接受 `ranges` 存在且为空、且父节点地址/长度单元数与根节点一致**；非空或不一致 → 明确拒绝。这比「地址转换解析不了就拒绝」可直接测得多，也符合最小支持范围 |
| 设备树自身的保留映射块 | 按上表四条处置；本仓需新增消费依赖库已有的遍历接口 |
| `ReservedPrefixEnd`（前缀阈值） | 保留现有裁剪，但**在政策文本与命名里写明它是阈值而不是区间集合**，不参与与其它保留范围的并集运算 |

### 4.4 切除是正常表达；本仓 aarch64 的 UEFI 腿已经存在两份来源

**保留区与 `/memory` 相交是正常的切除表达，不是冲突**（上一轮结论，保持）：`/reserved-memory` 的地址本来就落在 `/memory` 之内，它说的是「这片 RAM 里有一段不要交给普通用途」。真正会出错的只有**来源描述彼此矛盾**。规则：

| 情况 | 第一版处置 |
|---|---|
| `/memory` 的有效区间 | 普通内存候选 |
| 静态保留节点与内存区间相交 | 从可用表扣除交集（正常的切除） |
| 静态保留节点无 `no-map`，且满足普通映射准入 | 进保留表 |
| 静态保留节点带 `no-map` | 同时从可用表与保留表排除，并进入**启动映射禁止清单**（裁决六） |
| 两个保留节点重叠、语义相容 | 可以合并为相同处置 |
| 两个保留节点重叠、语义冲突或无法确定 | 分类错误；**不按声明先后裁剪** |

多段区间建议先算出集合再一次性排除，避免逐条裁剪造成的边界顺序依赖（上一轮本方意见，保持不变）。被禁用的节点：`/memory` 标 disabled → 不纳入候选；`status` 缺省 → 按规范默认视为可用；保留子节点标 disabled → **不得当作保留已解除的证明**，保持保留或明确拒绝，不能静默变成可用表。

**本仓的实际位置（代码事实，决定叠加规则插在哪）**：aarch64 的 UEFI 腿今天已经做了「两份来源」的一半——它读固件内存图，并在镜像盘上存在设备树快照时，解析该快照的 `/memory`，用它给固件图的每个常规区间做**出界闸**（任一常规区间落在设备树 RAM 全景之外即中止启动；注释写明这是为了在引导壳还能打印的时候抓住「固件快照与平台真相不一致」）。同一处注释还记录了为什么第一版**不**用设备树结果替换固件结果：设备树的 RAM 全景包含引导壳自己占用的加载器数据页，直接替换会把这块自占用交给分配器，而自占用的记账「待裁决」。

于是：

- 该腿已经具备解析设备树与两份来源对照的代码位置，`/reserved-memory` 的读取可以插在同一处；
- 「不回收与声明过的保留范围相交的引导服务数据」（§2.2 行 5）在这条腿上是**具体的、可测试的**规则，不是抽象告诫；
- 「不拿 `/memory` 当来源、只当闸门」这条现有语义与规范的「UEFI 启动时忽略 `/memory`」并**不矛盾**（闸门只是校验，不是来源）——**这句结论本方撤回**，见下一小节。

### 4.4.1 出界闸的项目策略：本方撤回上一版的结论（第三轮，本方接受）

上一版宣称「只当闸门不等于违反忽略要求」。第三轮不接受：规范原文是**必须忽略 `/memory` 节点**，而不是「不得用它代替内存图」。本方复述当前行为后同意这个判断——本仓确实让 `/memory` 参与了**启动准入决策**（落在设备树 RAM 全景之外就中止启动），因此不能写成「完全符合忽略要求」。这条撤回与「要不要保留这道闸」是两个问题，必须分开选：

| 案 | 语义 | 代价 |
|---|---|---|
| A | UEFI 腿**完全忽略** `/memory`，只用固件内存图 | 丢掉一类已有告警（固件快照与平台拓扑不一致）；实现最简单，规范关系最干净 |
| B | 保留出界闸，但**明确登记为本项目自己的额外平台一致性检查**，不宣称它是规范的「忽略」行为 | 规范关系诚实了，但准入权仍交给一份来源可疑的输入 |
| C | 只做诊断：报告不一致，不改变准入与内存集合 | 保观测、去掉误中止；但真出现「把非 RAM 当可用内存」时不再被拦住 |

**第五轮结论：选 A，本方撤回自己的 C 路线**（两位评审人共同反对，理由成立，本方接受）。上一版本方主张「先把输入换成固件在同一次启动里交出的设备树、权限停在只做诊断」，并把它当作比 A 更保观测价值的方案。反驳是：既然这条腿本就不该让 `/memory` 参与决策，那么无论它是否改变准入，留着它都要**长期维护一套跨来源一致性判断**，而这不是内存图政策的职责；况且当前输入还是从磁盘镜像读来的、与本机拓扑无证明关系。保观测的收益不值这份持续负担。

本方接受，并补三条落地含义：

1. **删的是这条腿上的 `/memory` 使用**，不是删设备树解析本身——同一份镜像里的设备树快照在 UEFI 腿上仍要读，因为平台描述与 `/reserved-memory` 保留语义都在树里。「忽略 `/memory`」与「读保留子树」不冲突（§4.2）。
2. 因此**出界闸的对照逻辑不能顺手把整段设备树读取一起删掉**——那是 §2.2 行 5 保留区例外的插入位置。
3. 若将来确实需要「固件内存图 vs 平台拓扑」的一致性检查，它作为**独立的平台一致性验证**立项，不重新混进分类政策。

本方保留的一条提醒：删除后，「固件把非 RAM 报成常规内存」这一类故障在本链路上不再有引导期拦截。它并未被本方案解决，只是被移到别的职责层（覆盖验收与后续内存测试），这个残余风险要如实写在这里，不能因为选了 A 就当它消失。

本方倾向的落地顺序是「先 C（一步、无风险、立刻消除误中止）」，把 B 留到输入换成固件产物之后再启用。**请评审人裁定：是否同意「来源可信度」与「权限」分两刀，还是直接按 A 删掉这道闸。** 本方说明为什么不太倾向 A：这道闸抓到的那一类不一致（固件报告的常规内存区间落在平台 RAM 之外）确实存在，删掉它等于把一个已知故障模式变成静默；但如果评审人认为「规范说忽略」应当严格到连诊断读取都不做，本方接受 A。

另外，`/reserved-memory` 与固件内存图的对照**不按描述符逐条相等**验收：一个静态保留区间可能横跨多条固件描述符，固件也可能把一片保留区切成若干相邻描述符。要验的是**覆盖集合与类型**（该保留范围在固件图里是否被全部覆盖，且覆盖它的描述符类型符合 §4.3 表里的要求），不是分段形式。

### 4.4.2 区间数学合同（第五轮要求：原则已定，但还不足以唯一实现）

第五轮指出「唯一的页级坐标归一化」与「所有范围合并成一个集合」是两件事，并列出实现者还需要的一组边界。本节把它们一次写清——这些是可直接编码与测试的条款，不是概念阐述：

| 条款 | 内容 |
|---|---|
| 区间形状 | 一律半开区间 `[start, end)`；长度与末端不得混用同一变量名 |
| 取整 | 起点向下、末端向上取整到 4 KiB；取整只发生在进入规划阶段的那一刻，消费者只见取整后的区间 |
| 溢出 | `start + len` 溢出即拒绝该输入（饱和只允许出现在明确的末端钳制语义里，并要能被诊断看出） |
| 上界重合 | 区间末端恰等于架构可表达地址空间末端时按半空区间处理，不得因为「再加一页会溢出」而失败 |
| 排序与合并 | 归一化后排序，合并相邻与重叠，产出**不相交**集合；合并保留来源证据（多来源用位图，不用单值枚举） |
| 工作缓冲超限 | 归一化过程本身需要临时缓冲；其容量、超限行为（失败并报告，不静默截断）要显式定义 |
| 适用范围 | **所有**参与 PMM 切除的范围都要按页取整，不只 `no-map` 与保留映射块——普通静态保留区即使允许映射，只要与某页相交，该页剩余字节就不许交给分配器 |
| 同源实现 | 与既有的页对齐裁剪纯函数同源，禁止在引导壳、映射规划、覆盖验收三处各写一遍 |

这一条也直接回答第五轮的疑问：**共享唯一的归一化算法，不等于把这些范围合并成一个语义集合**——算法一份，集合各存，关系用 §0.3 那五条集合等式约束。

### 4.4.3 三样保留输入冲突时的判据（第五轮要求机械化，不要用抽象的「相反处置」）

| 关系 | 处置 |
|---|---|
| 任一来源要求禁止普通访问 | 不得进入普通访问路径（禁止优先） |
| 多来源的保留语义一致 | 合并区间，但各自保留独立来源证据 |
| 一方要普通使用、另一方要保留 | **保留优先**，必要时从可用集合扣除 |
| 启动必需对象与禁止范围相交 | 复制、走经审的专用访问路径，或者拒绝启动 |
| 一方给用途授权、另一方明确禁止 | **禁止优先**，除非存在可审计的例外机制 |

第一版**没有**用途授权通道，因此一律按「无授权」处理；本轮明确不为一时无法使用的场景预建授权抽象（与行 6 的「不预建注册机制」同一条纪律），将来出现真实消费者时再经审查加入例外。

### 4.5 `no-map` 的验收对象是映射规划，不只是分类输出

上一轮已定、本轮加强：即使设备树收集器把 `no-map` 范围从两张表里都删掉（满足 L1 + L2），如果内核的直接映射构造器随后用一个大范围或巨大页把它重新覆盖，仍然违反约束。验收必须查四件事：不进入任何普通映射候选；**最终页表不存在覆盖该范围的叶子**；映射规划不会为使用巨大页而跨过它的边界；其它启动对象映射来源也不会意外覆盖它。

本仓有一个现成的落点：引导根的恒等段已经存在一条判据——某个大块若与「已知设备窗口清单」相交，就拆成 2 MiB 粒度并按片加设备属性。这条判据正是禁止清单应当复用的钩子：把输入从「设备窗口清单」扩到「设备窗口 ∪ 启动映射禁止清单」。但注意 §0.3 的事实：这段大页铺开发生在引导根且不参与类型政策——所以「分类器已排除」在当前实现里确实不等于「没有映射覆盖」。这一层落到裁决六。

### 4.6 `no-map` 合同用语的精确化（第二轮意见，本方接受并区分两层）

规范原文的限制是两条：**不得把该区域纳入操作系统的标准系统内存映射**，并且**不得允许不受控的推测访问**（出处见 §4.3 的出处表；本方未能逐字核对原文）；它没有写成「任何时刻、任何用途、任何页表都绝不允许存在映射」。因此要分清两层，否则裁决六的候选会和一个并不存在的强要求打架：

| 层 | 内容 | 性质 |
|---|---|---|
| 规范合同 | 不进标准系统内存映射 + 不允许非受控推测访问 | 必须满足 |
| 项目加强约束 | 在没有经过专门审查的例外时，引导根与最终根**都不得**映射 `no-map` 区间 | **本项目自己的加强政策**，不是规范原句 |

本方同意把加强约束标成加强约束。上一版本方把「`no-map` 被普通映射」的后果描述成必然硬件异常（SError 等），那已经改掉——是否表现为异常、是否出现缓存不一致需要平台证据；判定不需要推演异常，映射本身就违反合同。

按 §0.3 的四层词汇，这条合同现在可以写成一句话：**规范要求 L2 + L4；本项目为加强一致性额外要求 L3；而 §6.4 的交接前窗口使 L4 无法由本项目的软件清单证明**，所以第一版能宣称的是「本项目自己构造的两棵树都满足 L3」，不是「L4 已兑现」。

### 4.7 本轮已定与剩余问题

上一版的第三问（规范出处）已由第三轮给出小节号，本方据此把 §4.2–§4.6 里三处「[待验证]」升级为「评审人核实并给出出处」，同时保留本方的诚实标注：**小节号来自评审人，本方未能逐字核对原文**（规范站点对本方的直接抓取返回拒绝）。第二问也得到答案：`no-map` 的规范合同是 L2 + L4，L3 是本项目加强；因此「引入禁止清单」不能当成 L4 已兑现的证据，交接前那段要作为**平台/固件前提登记进支持清单**（§6.4）。

**剩余一问**（第一问已由第五轮给出判据，见 §4.4.3；本方采纳那张优先级表）：

1. **三样保留输入彼此不一致时的规则**（前几版只问了两方）。现在有三样：设备树自身的保留映射块、`/reserved-memory` 静态 `reg`，以及项目自己的前缀阈值 `ReservedPrefixEnd`（它是阈值、不是区间集合，见 §4.3）。本方倾向：任何两方对同一区间给出**相反**处置（一方要访问授权、一方禁止访问）即分类错误；只做子集关系的（上界裁掉的前缀被某个保留节点覆盖）按切除处理。请评审人确认「相反」的判据够不够精确——本方担心它在用途授权这件事上难以机械判定。
2. **用途授权如何表达**。规范允许「启动程序明确说明用途」时访问保留区域。本仓目前没有任何机制表达这种授权。第一版是「一律按不得访问处理」（保守、可判定），还是现在就设计一条授权通道？本方倾向前者，并要求把「暂无授权表达方式」写进合同，避免将来某次改动顺手放开访问。

## 5. 裁决五：被排除描述符的留痕通道

**状态：方案层已签（有界结构化诊断）；字段表与错误码表需在下一轮回写成两份定稿清单。**

### 5.1 当前实现做到哪里（代码事实，缺口有两层）

| 输出 | 记了什么 | 没记什么 |
|---|---|---|
| 可用表 / 保留表 | 区间（起点 + 长度） | 类型与属性（它们只影响裁决，不进输出） |
| 诊断样本 | 区间（起点 + 长度） | 类型与属性——所以「命中了哪一位」「缺写回位的是哪一类」无法从输出复原 |
| 排除 / 设备路径 | **什么都不留**：三个计数器（可用、保留、样本）里没有它们的位置，既没有条数也没有范围 | —— |

于是「不静默忽略」目前只兑现到「样本区间可见」这一层，而被类型强制排除的那一类连区间与计数都没有。

### 5.2 受众与字段（上一轮定案，保持）

**受众**：流水线 + 开发者，**不是内核消费者**。诊断仍是引导壳内部产物，不进交接结构，冻-5 不变。**每条记录的字段**：

| 字段 | 意义 |
|---|---|
| `step` | 落在五步裁决的哪一步 |
| `disposition` | 可用 / 保留映射 / 诊断成员 / 排除 / 设备路径 / 致命 |
| `reason` | 具体政策原因，例如类型排除、独立属性命中、缺普通属性准入 |
| `raw_type` | 原始类型 |
| `physical_start` | 原始物理起点 |
| `number_of_pages` | 原始页数 |
| `attribute` | 完整原始属性字 |

只有四元组无法区分「因为类型被排除」与「因为独立属性要求不建映射」；`step` 与 `reason` 让后续评审能直接追溯到裁决逻辑。

**但这张字段表以 UEFI 描述符为中心，而诊断现在要承担三类来源**（设备树自身的保留映射块与 `/reserved-memory` 节点都没有 UEFI 的 `Type` 与 `Attribute`）。第五轮要求拆层，本方采纳：

| 字段组 | 字段 |
|---|---|
| 通用诊断 | `source`、`disposition`、`reason`、`physical_start`、`length` |
| UEFI 专属 | `raw_type`、`number_of_pages`、`attribute` |
| 设备树专属 | 节点路径或保留映射块条目序号、原始属性标志（`no-map`/`reusable`/`hotpluggable`） |
| 归一化诊断 | 原始区间、页级归一化后的区间、合并进了哪个目标区间 |

**计数必须分两种口径**，否则日志会自相矛盾：按来源计数时，两个来源声明同一片内存**允许重复计数**（它反映声明次数）；按归一化集合计数时是**去重后的唯一物理页数**。上一版只写了「每种处置的总字节数」，那正是会双倍计算的位置。

### 5.3 范围留痕、配额与致命记录（与行 7 同步）

- **类型强制排除的范围也要有诊断记录**，否则第 3 步的判断不可审计；但不要求每条永久保存在一个大数组里。
- 每种处置统计条数与总字节数；对「诊断成员」与「排除」至少保存前 N 条原始范围样本；对「设备路径」记汇总并有限保存样本；**任何致命情形单独保留触发描述符，不得被普通样本挤掉**；输出截断标志与计数溢出标志（计数饱和而非失败）。
- **配额按处置独立**（§2.2 行 7）：共用一块静态缓冲可以，但每种处置要有独立计数、独立样本配额与独立截断标志。
- **术语拆分**：语义成员集合是完整的，数组只是它的有界样本；样本截断不改变分类结果，也不改变分类输出。

### 5.4 本节的签字条件（第二轮要求，本方接受）

文档里要给出**一份诊断字段稳定表**与**一份错误码表**，而不是让 `reason`、`code`、`disposition` 在各章节自由发挥。字段集合本节已定；错误码表与致命行的取值集合需在下一轮作为独立附录定稿（与 §3.3 问题 B 的成功摘要行共用同一命名体系，但两张表分开——见 §3.4 表首行）。

## 6. 裁决六：「不建映射」由哪棵页表树兑现，以及要不要一个禁止清单

### 6.1 问题（代码事实，不变）

按 §0.3：引导根的恒等段**无差别铺低 4 GiB**，只有已知设备窗口参与拆分；类型政策、诊断成员、被排除范围、设备树 `no-map` 都不参与这段构造。于是三条已写下的承诺在两层含义上强度不同：

| 承诺 | L2（最终直接映射） | L3（引导根恒等段） |
|---|---|---|
| 「诊断成员不建普通映射」 | 成立 | **不成立** |
| 「被排除的区域不进入普通分配器」 | 成立 | 不适用（排除本身不管引导根）；**它不等于「不许访问」**，见下 |
| 「`no-map` 不进标准系统内存映射」 | 成立（前提是把禁止范围喂给大页判据） | **不成立** |

本方上一版把第二行写成「OS 不得访问」，与「未进最终直接映射」混为一谈；第二轮指出不分配、不进最终别名区、不进引导根、不允许非受控访问是四件事（§0.3 的四层表）。**第五轮进一步要求把这句彻底删掉**，本方照办——它与本简报自己的决定直接冲突：既然不把 UEFI 的固件保留类型整批放进映射禁止清单（§6.6），这些范围的实际状态就是「不进可用表、不进最终直接映射、但仍被引导根的恒等段覆盖」，写「不许访问」等于用一个没有任何集合承诺支撑的说法盖住三件不同的事。

准确表述：**被排除的区域不进入普通分配器；是否禁止建立页表映射，由对应来源的映射政策单独决定。** 规范侧也支持这样分——固件保留类型的语义是「不可用」、不可用内存类型的语义是「有错误、不得使用」，两者的「不要用」都不等于设备树 `no-map` 那条页表合同。

### 6.2 三案的最新状态

| 案 | 内容 | 状态 |
|---|---|---|
| 甲 | 把「不建普通映射」在文档里限定为最终直接映射，并承认引导根有一段有时限的无差别覆盖 | **被否**。第二轮的理由：`no-map` 的约束包含「不允许非受控推测访问」，不能仅凭切根后这段映射消失就证明引导期不存在不受控访问。本方接受——推测访问不依赖软件发起的访问，映射存在即可能访问；切根只是终止了那段时间，没有验证那段期间发生了什么 |
| 乙 | 新增一份跨交接边界的「不可映射范围」清单 | **采纳为收窄版**，见 §6.3 |
| 丙 | 只把「绝对不可映射」的子集升级为拒绝启动，其余按甲 | 降级为**退步方案 C′**，见 §6.5 |

### 6.3 收窄版乙：两个对象，四种属性

关键是把「记账用的清单」和「约束页表的清单」彻底分开：

| 对象 | 用途 | 是否跨交接边界 | 容量失败策略 |
|---|---|---|---|
| **诊断样本** | 记录分类结果为什么这样、供流水线与开发者审计 | 否（引导壳内部） | 计数并报告截断，**不影响启动** |
| **启动映射禁止清单** | 明确禁止引导根与最终根映射的区间（设备树 `no-map`，以及经政策升级进来的少量范围） | **是** | **不允许静默截断**；无法完整表达就拒绝启动 |

这不是把诊断清单改造成内核协议，而是新增一个**有明确消费者（引导根的构造判据与最终根的覆盖验收）、有明确语义（映射禁止）、不可截断**的启动约束。它的消费者从第一次落地就存在，与「没有消费者的注册机制」（行 6 被否的理由）不是一回事。

配套要求：

- 引导根的构造判据复用 §4.5 那条现成钩子（大块相交就拆片），输入换成「设备窗口 ∪ 禁止清单」，对禁止清单命中的片段处置为**不映射**——在「一个物理页两套属性不可预测」的架构上，「映射成设备属性」不是可替代方案。
- 交接结构要新增一份有界范围数组，属于跨镜像契约变更：容量常量、布局版本，以及「清单为空」与「清单溢出」必须可区分。
- 覆盖验收要同时跑在 L2 与 L3：最终根不含禁止区间，引导根的恒等段也不含禁止区间。

**第三轮补的三条实现合同**（本方核对后认为三条都成立，且第二条与本方上一版提的横切规则正好接上）：

**一、禁止范围必须按最小页粒度兑现，拆到 2 MiB 不够。** 引导根的构造路径目前只做到「大块与设备窗口相交就降到 2 MiB」。但保留区域完全可以小于 2 MiB，或只与某个 2 MiB 区间的一部分相交——止步于 2 MiB 就意味着禁止范围内仍可能有叶子映射。合同要写成：

- 与禁止范围相交的区间一律继续拆到 **4 KiB 页粒度**；
- 禁止范围覆盖的那些 4 KiB 页**不产生叶子映射**；
- 同一个 2 MiB 区间内**未被禁止的部分可以保留映射**（否则一份小保留会代价高昂地赶走一整块合法映射）；
- 最终根与引导根**两棵树都做这项检查**。

另外必须明确非页对齐输入的处置：禁止区间的起止不是 4 KiB 对齐时，只有两种合法选择——**向外取整到 4 KiB**（代价是牺牲相邻的一点可用空间），或者**明确拒绝这种输入**。不允许「按原始字节区间比较，然后仍然建立一个覆盖它的 4 KiB 映射」——那种写法看起来精确，实际把禁止页的一部分映射了进去。本方选**向外取整**：拒绝合法但不对齐的固件输入会把政策变成可用性风险，而多牺牲一页相邻空间是可计量、可审计的。

**取整之后只能有一份「页级坐标」，但不是只有一个集合**（第四轮补充、第五轮再纠正本方的表述）。向外取整只解决了「映射」这一半；如果可用表的切除仍按**原始字节区间**计算，就会出现同一个物理页一边在禁止清单里、一边在可用表里：

```
禁止范围（原始）    [..................]           100 字节，落在某个 4 KiB 页内
向外取整后          [====================]          整个 4 KiB 页不许映射
若可用表按原始切除  [..][================ 剩余 3996 字节仍可能进 PMM ==]
```

物理页分配器不分配 100 字节，它分配**整页**。所以那种组合直接破坏 L1 与 L3 的一致性——同一个页既「不许映射」又「可以拿去当普通内存」。强制合同：

> **所有参与物理页分配器切除的范围，都必须先完成 4 KiB 向外归一化，再参与可用表生成、集合划分、启动必需对象冲突检查与页表覆盖验收。** 不允许出现「分配侧用原始字节区间、映射侧用归一化页区间」的两套坐标。归一化时的末端相加要做溢出检查，并与架构物理上界比较。

**适用范围不止带禁止语义的范围**（第五轮的纠正）：普通静态保留区即使允许映射，只要它与某页相交，该页剩余字节也不许交给分配器。所以这条覆盖**全部 PMM 排除范围**，映射禁止集合只是它的一个更严子集；同一规则也适用于第一版纳入禁止清单的**保留映射块条目**。

**但唯一的取整不等于唯一的集合**。上一版本方写成「一份区间集合」是过头的：那会把普通静态保留区（不许分配、允许映射）连带禁掉映射，或者反过来为了保住映射而弱化 `no-map` 的禁令。正确模型是 §0.3 的四个语义集合与那五条集合等式；本节的取整规则是它们的**共同坐标**，不是把它们并成一个对象。可编码的区间数学（半开区间、取整方向、溢出、上界重合、排序合并、工作缓冲超限）集中在 §4.4.2，并与本仓既有的页对齐裁剪纯函数同源。

**合并与来源证据要分成两个对象**（第四轮指出 §6.3 内部有矛盾：既要合并相邻/重叠区间，又要每条携带来源与原因）。同一个页可以同时被保留映射块与 `no-map` 节点声明：合并成一条，来源与原因就不再是单值；不合并，又没真正做到归一化，容量计算与页表查询都要额外处理。解法是两个对象：

| 对象 | 保存什么 | 消费者 |
|---|---|---|
| **交接用的禁止范围集合** | 排序、归一化、合并后的**不相交**物理区间；只回答「哪些页不能映射」 | 引导根的构造判据、最终根的覆盖验收 |
| **引导期来源诊断** | 各来源声明的**原始**区间、原因，以及它们各自对最终禁止区间的贡献 | 流水线与开发者审计 |

如果确实要求交接清单也带来源，那来源字段必须是**多值**（来源位图），不能是单值枚举——否则合并操作会静默丢掉一个来源的证据。本方采纳「纯区间 + 独立诊断」的分法：它同时满足 §6.7 的建模纪律（页表消费者只拿区间，不拿政策标签）。

**二、禁止范围与启动必需对象相交时要做冲突检查。** 如果一份禁止映射的范围正好盖住当前入口代码、栈、构造页表时还要读的页表页、跨切根要读的交接区，或者**禁止清单自己的存储**，那么「按清单跳过映射」之后系统不会正常工作——它会以一种很难归因的方式失败。合同：

> 若禁止映射范围与启动必需对象所在的最小页粒度区间相交，且不存在经过审查的其他安全访问路径，则拒绝启动。

本方上一版在 §2.2 行 1 提出的「所有拒绝启动判据统一复用同一份启动必需对象清单」正好在这里落地——**这是那条横切规则的第一个具体消费者**，因此清单的定义必须先于本条实现。清单里要显式包含禁止清单自身的缓冲区：一份把自己也禁掉的清单是可构造的，必须被拒绝而不是被容忍。

**三、清单必须作为第四种输出纳入第一遍预检的硬容量检查。** §0.3 目前写的是「预检各输出容器的容量」——那是按三种输出写的。新增跨边界的禁止清单后，第一遍必须：统计完整的禁止范围集合 → 合并重复、重叠与相邻区间 → 计算输出条数 → 检查清单容量 → **超限直接失败**；第二遍才不可失败地写入。否则「已验证的计划」这个凭证并没有覆盖第四种输出，写入阶段仍可能失败，等于把已冻结的两遍合同悄悄打破。本方补一条：**合并相邻区间要在第一遍做**，否则同一份保留被固件切成三条相邻描述符时会白占三个槽位，容量需求被高估、超限判据也随之失真。

### 6.4 本方补的一条边界：禁止清单管不到交接之前那段时间

在引导壳进入内核之前，执行发生在**固件自己建立的页表**之下（本仓的注释记录了这一事实：引导期由固件把物理 RAM 恒等映射）。这段映射不属于本项目构造的任何一棵树，禁止清单也管不到它；这段时间里固件是否访问过 `no-map` 区域，由固件的行为决定。因此：

- **满足 L3 不等于满足 L4**。L4（不允许非受控推测访问）在交接前的窗口里本方无法用软件清单保证，只能作为平台与固件合同登记。
- **这条局限的准确表述（第三轮收紧）**：它是「**本项目无法通过自身软件证明固件的先前行为**」，不是「已经证明符合 L4」。规范对 `no-map` 的两条限制不会因为新增一份交接结构就消失。因此第一版可以宣称的是「本项目自己构造的两棵树都满足 L3」；L4 的那段窗口要作为**平台/固件前提登记进支持清单**（与裁决一的三档清单合并，不另开一份），否则措辞会超出证据。
- 这条边界应当写进政策的「已知局限」，而不是被禁止清单的成功掩盖。否则读者会以为引入清单就满足了规范的两句话。
- 与裁决三问题 C 相连：正因为这段时间不可控，把「只有成功退出后提交的分类结果才能进入页表构造」写成类型约束才有意义——它至少保证本项目自己构造的两棵树在时序上不错位。

### 6.5 退步方案 C′（如果第一版来不及引入禁止清单）

不是回到甲，而是：**当禁止清单里的范围与当前无差别恒等映射窗口相交、且无法证明安全时拒绝启动**；不相交的范围按最终根政策处理。它比「所有 `no-map` 都拒绝启动」精确，也比「只要切根后消失就行」有依据。本方接受「先 C′、下一批换收窄版乙」的路线，前提是 C′ 的判据使用同一份清单对象（只是处置不同），这样升级时不改数据流。

### 6.6 本轮已定

| 问题 | 结论 | 采纳后的合同 |
|---|---|---|
| 禁止清单第一版的成员范围 | **不把 UEFI 的固件保留类型（`RESERVED`/`UNUSABLE`）整批加入**（本方倾向被采纳），但**要补上设备树自身的保留映射块条目**（第三轮指出，本方核对后接受） | 理由是两类语义不同：UEFI 的类型排除是 L1/L2 层面的类型政策，整批升级为 L3 映射禁令等于把「不该分配」读成「不许映射」。保留映射块则自带**不得访问**的语义（§4.3），不进来才是漏。**交接清单只装规范化后的物理区间**（例如 `{起点, 页数}`），来源与原因**不在条目里**，留在独立的来源诊断中，多个来源对同一页的贡献可以同时存在。上一版这里要求「每个条目携带来源与原因」，与 §6.3 刚拆开的两个对象自相矛盾，第五轮改掉：把来源塞回条目等于把刚分开的对象合并回来；若确实需要交接侧带来源，字段必须是位图而不是单值枚举 |
| 清单容量溢出即拒绝启动 | **采纳**（与诊断样本「超限截断不否决启动」形成明确对照） | 同一个分类器里允许「一类输出超限截断、另一类超限中止」，前提是两类的容量语义在输出结构里可区分；这条差异要写进字段文档，不能只存在于代码里 |
| §6.4 的交接前窗口 | **采纳为已知局限**，并按第三轮要求收紧措辞 | 写「本项目无法证明固件先前行为」，不写「L4 已满足」；该前提进支持清单（§1.4 的三档表），不作为独立承诺 |

**剩余一问**：升级通道的形状。若将来确实需要把某个 UEFI 类型判断升级成 L3 禁令（例如某平台的固件保留区被证明必须完全不映射），应当走**逐条登记**（哪个类型、哪个平台、什么证据）还是走**通用开关**？本方倾向逐条登记，理由是通用开关会让「类型政策」与「映射禁令」重新粘回一处——正是本文前面拆掉的那件事。

### 6.7 范围集合的建模纪律（第三轮的结构性意见，本方认为应写进合同）

到本轮为止，这件事已经牵出**六个语义不同的物理范围集合**：可分配的普通内存、可映射但不可再分配的保留区、诊断成员集合、启动映射禁止清单、设备树声明的保留范围、启动必需对象清单。第三轮的提醒本方完全接受，并把它提炼成一条纪律：

> **不要用「往处置枚举里再加一个值」的方式容纳新集合。** 每个集合都要单独定义它的**输入来源**、**输出形态**与**消费者**，集合之间的关系用区间运算表达（相交、扣除、合并、覆盖检查），而不是用新的标签表达。

理由有两层。第一层是本地经验：本仓刚刚删除过一条宣称能统一多来源、但没有任何消费者利用它的接口（阶段台账里有完整记录），把两个语义不同的东西塞进一个抽象，代价要到很后面才暴露。第二层是这条链路的下游：虚拟内存、物理页分配器、直接映射三层都要消费这些集合；如果它们读到的是「一种新的 `reserved` 变体」而不是「某个集合的区间」，三层会各自重新发明一套彼此不一致的判断——那就是本文那份设计笔记要修的原始病症换了名字回来。

具体推论有三条，都应当在实现时检查：

- **禁止清单不是一种 `Disposition`。** 它是「某些处置结果附带一条映射禁令」的**另一维度**，与去向（分配 / 保留映射 / 诊断成员 / 排除 / 设备路径）正交。用枚举值表达它，就等于把「不分配」与「不映射」重新压成一位（正是 §0.3 那句话要避免的事）。
- **同一区间的多重身份要允许并存**：一块地址可以既是启动必需对象又落在诊断成员里（本仓今天就是这样——恒等段无差别覆盖），这种情况必须能表达，否则「先算集合再排除」的次序会随代码位置漂移。
- **集合运算要有唯一的归一层**：本文出现的合并、取补、覆盖检查若散落在引导壳、内核映射规划与验收层各写一遍，就会有第三份分流规则——那是本文登记要消灭的那类问题。

## 7. 前置阻断项与等待项

### 7.1 属性位的出版物标识与配置档选择（步 0，先于所有政策批准）——本轮把选档机制换掉

本节的历史有三段，写清楚是为了让读者知道每条结论的证据强度：

1. 第二轮，评审人称本仓 ISA 属性掩码比规范多覆盖一个 nibble；本方读取规范网页版、EDK2、Linux 内核头文件与本仓常量四处比对后**否定了那个断言**，当时四处一致（`ISA_MASK = 0x0FFFF00000000000`）。
2. 第三轮，评审人撤回该断言，同时给出 UEFI 2.11 发布 PDF 的另一组数值，本节据此改成「按固件声明的修订版本整体选档或拒绝」。
3. **第四轮（本轮）**，评审人核对了两份 2.10 正式出版物，发现 2022 年原始版与 2024 年 Errata A 的属性常量本身就不同；并指出 `EFI_SYSTEM_TABLE.Hdr.Revision` 无法区分它们。本方接受这两点，并据此**同时撤回上一版的两处结论**（见下）。

**撤回一：本方上一版「2.10 配置档取值已核实」这句话不够严谨。** 本方当时取的是标注为 2.10 的 HTML 页面，而官方规格页把 **UEFI 2.10（2022 年 8 月发布）**与 **UEFI 2.10 Errata A（2024 年 8 月）**列为两份独立文档——本方无法确定那个页面对应哪一份（此点本方核实：两份文档确实并列存在；至于 HTML 属于哪一份，本方未能判定）。因此「与规范一致」当时是一个**没有出版物标识的结论**。评审人也主动撤回了上一轮对本方结论的确认，理由相同。

**撤回二：第三轮定下的选档机制不成立**——它不是缺实现，而是**选择器选不出要选的对象**：

| 事实 | 出处与分级 | 后果 |
|---|---|---|
| 依赖库里最高只到 `Revision::EFI_2_100 = new(2, 100)`，且其文档断言 `EFI_2_100.to_string() == "2.10"` | **本方核实**（钉死的 `uefi-raw 0.9.0`） | 修订值 `2.100` 会被读成「2.10」；本仓连 2.11 的对照常量都没有 |
| 表头修订字段的语义是「该表所符合的规范修订」，而 2.10 Errata A 与 2.11 使用**同一个** `EFI_SYSTEM_TABLE_REVISION`（即 `2.100`） | **评审人核实**；本方对规范站点的直接抓取被拒绝，未能逐字复核，但上一行的观察与之相符 | 读出 `2.100` 既不能证明固件用的是勘误版，也不能据此拒绝 2.11，更区分不了两份 2.10 |

第三轮的原则仍然成立：**门控必须发生在解释之前**，因为同一数值位在不同出版物里的身份可以相反——`0x10000` 在一份里是「更可靠」（记录、继续），在另一份里是「可热插拔」（不得进分配器、不得建普通映射）。按位容错等于猜固件读的是哪一份 PDF。

**四份材料的读数矩阵**（本文不推测哪一份写错；只登记材料、日期与常量，等权威勘误或明确的固件兼容证据。三份 PDF 的数值为**评审人核实**，EDK2 行为**本方核实**）：

| 材料 | 发布身份 | `WP` | `MORE_RELIABLE` | `HOT_PLUGGABLE` | `ISA_MASK` |
|---|---|---|---|---|---|
| UEFI 2.10 原始版 PDF | 2022 年 8 月正式发布 | `0x1000` | `0x10000` | 未定义 | `0x0FFF000000000000` |
| UEFI 2.10 Errata A PDF | 2024 年 8 月勘误发布 | `0x100` | `0x1000` | 未定义 | `0x0FFFF00000000000` |
| UEFI 2.11 PDF | 2024 年 12 月正式发布 | `0x100` | `0x1000` | `0x10000` | `0x0FFF000000000000` |
| EDK2 当前主干头文件 | **实现，不是规范勘误** | `0x1000` | `0x10000` | `0x100000` | `0x0FFFF00000000000` |

按这张矩阵，本仓常量继承 EDK2 布局，而 EDK2 的 `WP`/`MORE_RELIABLE` 与**原始版**一致、`ISA_MASK` 与**勘误版**一致——**本仓的常量组合与任何单一出版物都不完全吻合**。这就是为什么「取一处出处比对」不够，也是 §2.5 的逐位表必须**按配置档标识键控**的直接理由。

**替换机制：以已核实的固件组合为键**（采纳第四轮建议，本方补实现含义）：

| 信息 | 能用来做什么 | 不能用来做什么 |
|---|---|---|
| `EFI_SYSTEM_TABLE.Hdr.Revision` | 记录表接口修订，作为白名单条目的佐证与诊断输出 | **不能单独决定属性配置档** |
| `FirmwareVendor` / `FirmwareRevision` | 识别具体固件产品与版本 | 厂商自定义字段，**不等于规范规定的 UEFI 发行版本**，不是普遍有效的版本选择器 |
| **项目登记的固件组合配置档**（条目内容：固件身份 + 配置档标识 + 逐位取值 + 原始属性样本 + 材料版本与日期 + 文件校验值） | 决定用哪张逐位表解释属性字 | — |
| 未登记的固件组合 | 第一版**拒绝启动**，除非另有明确写下的兼容合同 | 不得仅凭修订值落进某个档就进入分类 |

**白名单条目的字段与匹配算法（第五轮要求把它写成能实现的合同）**。上一版列的键（厂商串 + 厂商版本 + 修订值 + 档标识 + 样本）不够：厂商串只标识厂商、厂商版本是厂商自定义值，**两者合起来都不是不可混淆的固件构建身份**，同一组值可能覆盖不同板卡、不同构建选项与不同平台配置。补齐为：

| 维度 | 作用 |
|---|---|
| `FirmwareVendor` / `FirmwareRevision` | 厂商与厂商版本（必要但不充分） |
| 平台身份 | 板卡、机器类型，或受支持的设备树识别串组合 |
| 架构与启动方式 | 防止把同一固件家族的不同启动路径混成一档 |
| 固件构建身份 | 能取到时记构建号、源码提交或镜像哈希 |
| 表头修订值、描述符版本 | 佐证与诊断，**不作为选档依据** |
| `AttributeProfileId` | 真正决定用哪张逐位表（含逐位掩码与出处） |
| 原始属性样本 | **验证证据**：核对这台固件实际输出过哪些位组合 |
| 证据来源与日期 | 允许日后撤销或升级该条目 |

匹配算法必须四路分明：**唯一命中** → 用该档；**零命中** → 拒绝启动；**多处命中** → 拒绝启动（说明键不够区分，要补维度而不是挑一个）；**样本违反该档约束** → 拒绝启动。未命中时打出的诊断要含上面全部身份维度，使这一例可以直接变成一条新登记项。

本方补的实现含义：白名单是**代码里的数据**，条目要能被宿主测试枚举，匹配是纯函数（输入身份、输出唯一档或三种失败）。**还要明确一点**：某个位没出现在样本里，**不能**证明该固件以后不会给出它——样本是「实际输出过什么」的证据，不是「能力上界」的证据，所以逐位表的兜底分支（未知位失败）不能因为样本干净而被放松。第一版真正能登记的组合只有本仓实际跑过并采到样本的那几套；这与裁决一的 RISC-V 三档清单是同一条纪律。

**测试哨兵：换值的原因要写准确**（第三轮修正本方上一版的表述，第四轮再修正一次）。本仓那个 `1 << 20 = 0x100000` 的哨兵与 EDK2 的「可热插拔」位重合；2.11 发布 PDF 里同一属性的取值是 `0x10000`；而 `0x10000` 在原始版里是「更可靠」、在勘误版里则落进未分配区。也就是说，这个哨兵既不是「任何出版物都不认识」的位，也不是稳定的未知位。用例按性质拆成三组，避免把三种不同的东西混作同一类测试对象：

| 测试组 | 输入位 | 期望 |
|---|---|---|
| 一 | **本配置档内**真正未分配的保留位 | 分类错误（fail-closed） |
| 二 | 实现已定义、但不属于本配置档的扩展位 | 按未知位处理（同样失败），但记录里要能看出它属于「实现扩展」而非「空白保留」 |
| 三 | 将来某个明确支持的扩展配置档里、项目不支持且影响分配安全的位 | 进入行 1 的第三类政策（不分配、不建普通映射、成为诊断成员，必要时拒绝启动） |

**本节结论（第四轮裁决：当前不能签）**：签的**不是**「2.10 可以、2.11 不行」，而是「**先有配置档选择机制，才有逐位表可用**」。在选档机制改成固件组合白名单、且至少登记一套已采到样本的组合之前，§2.5 整张逐位表都缺一个正确的输入前提。本文材料由四项再扩为**五项**：出版物标识与日期、常量来源与出处、允许掩码及其来源、固件身份（厂商串与厂商版本）、实际固件的原始属性样本（连同描述符类型）。

当前缺口（代码事实）：全仓既不读表头修订字段，也不读厂商身份，诊断输出里两者都没有；现量命令：`grep -rn 'revision' os/boot-shim/src os/libs/minix-boot/src --include=*.rs`（读数为零命中）。补这两项读取本身不需要任何政策变更，可以先行落地，作为白名单条目的数据来源。

## 9. 术语表

| 术语 | 含义 |
|---|---|
| 内存图 | 固件交出的物理地址区间清单，每条描述符 = 类型 + 起点 + 页数 + 属性位图 |
| 引导壳 | 由固件加载、负责准备页表与交接数据、然后进入内核的一段独立可执行代码 |
| 描述符步长 | 相邻两条描述符起始地址之差；规范长度是最小值，固件可以用更大的值做向后兼容扩展 |
| 属性位图 | 描述该区域**支持**什么用法的位集合，不是「此刻正被怎么用」的状态 |
| 属性配置档 | 一个有标识的实现兼容档：身份维度组合 + 逐位取值 + 允许掩码 + 出处 + 验证样本。它**不宣称规范归属**，也不能由表头修订值单独选出 |
| 表头修订 / 描述符版本 / 配置档标识 | 三个互不替代的版本概念：系统表所符合的接口修订、内存描述符的结构版本（规范单独定义为 1）、属性字按哪张表解释。**描述符版本 1 不蕴含属性位布局 1** |
| 归一化集合族 | 同一页级坐标下的多个语义集合：`PmmExcludedRanges`、`BootMapDenyRanges`、`StartupRequiredObjectRanges(阶段)`、来源诊断 |
| 写回缓存 | 主存的标准缓存策略：写先进缓存、之后回写。普通内存的默认期望 |
| 不可缓存 / 设备属性 | 访问直达地址空间，不经缓存。对寄存器是必需的，对普通内存是灾难 |
| 普通主存语义 | 三架构统一的目标：按主存方式访问、共享时保持一致、原子操作按主存语义生效。不等于「必须有物理缓存」，也不等于某个具体属性名 |
| `IA32_PAT` / MTRR | x86-64 上决定有效内存类型的两套机制；叶子页表项的 `PAT`/`PCD`/`PWT` 三位共同选择 `IA32_PAT` 的 8 个表项之一（普通页与大页的 PAT 位位置不同），选中的表项值再与该地址的 MTRR 类型按架构组合表合成有效类型（**表项选写回而 MTRR 为不可缓存时，结果仍是不可缓存**）；`PAT` 每逻辑处理器一份，MTRR 按物理地址范围设定，多核下要求各核**有效类型**一致（不是要求寄存器原始值看起来一致） |
| `MAIR_EL1` / 属性索引 | AArch64 的属性表寄存器 / 叶子页表项用来选表项的 3 位索引 |
| 物理内存属性 / Svpbmt / PBMT | RISC-V 的平台定义、由硬件检查的地址属性（部分固定，部分平台支持 M 态重配）/ 可选扩展 / 页表项里那两位（只有「跟随属性」「不可缓存主存」「强序 I/O」，且需 M 态使能） |
| 直接映射 | 内核把物理内存线性映进自己的虚拟地址空间，物理地址加固定偏移即可访问 |
| 引导根 / 最终直接映射 | 两棵页表树：切根之前使用的那棵（含一段无差别恒等映射）与内核正式的物理别名区 |
| L1–L4 四层约束 | 不分配 / 不进最终直接映射 / 不进引导根恒等段 / 不允许非受控访问。四者不等价，本文不再用「不建普通映射」一句话统称 |
| 物理页分配器 | 内核分配与回收物理页的组件 |
| 可用表 / 保留表 | 两份输出：可自由分配 / 可访问但不得再分配 |
| 诊断成员集合 / 诊断样本 | 成员=所有「保留但不建普通映射」的范围（语义集合，完整）；样本=实际存储的有界数组（可截断） |
| 启动映射禁止清单 | 跨交接边界的集合：禁止引导根与最终根映射的页；**不可截断**、装不下即拒绝启动；条目只装规范化区间，来源与原因留在诊断侧 |
| MapKey / 版本戳 | 内存图的版本标识；退出引导服务必须携带取得该键的同一次读取，且只返回状态码 |
| 退出引导服务 | 结束固件引导期服务的调用；此后固件的分配、控制台、释放接口全部失效 |
| 交接结构 | 引导壳交给内核的固定布局数据块，字段按基址加偏移定位，不含进程内指针 |
| 恒等段 | 引导期把物理地址与虚拟地址等价的映射区间，让还没切页表时代码能继续跑 |
| 切根 | 把页表根从引导期页表切换到内核页表的动作 |
| 夹具型测试 | 只把某份数据当输入、不对该数据本身做断言的测试，被测对象是别的代码 |
| 五步裁决顺序 | §2.1 那张表：未知或不支持 → 拒绝启动 → 类型强制处置 → 普通候选 × 独立属性 → 普通属性准入 |
| 切除 | 设备树表达「这片 RAM 里有一段不要用」的方式：保留节点地址与 `/memory` 区间相交是正常形态 |
| 保留映射块 | 设备树文件头之后的独立保留区间列表，与 `/reserved-memory` 子树是两种输入，不能只实现后者；规范允许设备树本体出现在其中 |
| `ReservedPrefixEnd` | 本项目的一个物理地址前缀阈值（低于它的整段当固件常驻区），**不是区间集合**，不参与与其它保留范围的并集 |
| 启动必需对象 | 内核镜像、入口代码、栈、交接数据、分类输出数组等跨切根仍需访问的对象；多处「拒绝启动」判据共用这一份清单 |

### 12.1 采纳（只改正文，无需再讨论）

**第三轮又抓出本方三处**，全部已改：x86 选 PAT 表项被写成 `PCD`/`PWT` 两位（实为 `PAT`/`PCD`/`PWT` 三位，且普通页与大页的 PAT 位位置不同）；「只当闸门不违反忽略要求」是本方替规范做的宽松解释（撤回，改 §4.4.1 三案）；「每个已知属性位都有明确处置」长期只是判据、正文没有逐位兑现（§2.5 补）。另有一条属于**本方写作纪律的失守**：上一版把「2.11 才出现的位按基线外处理」写得很像容错设计，而它实际会让同一位在两个配置档里含义相反的情况静默通过——教训是**凡是「按版本解释位」的地方，必须先拒绝再解释**。

**第五轮又抓出本方五处**，全部已改：① 把「一份归一化坐标」写成「一份区间集合」，会把允许映射的普通保留区连带禁掉；② 数据流图里画了一个本仓并不存在的第三个区间输入；③ §6.6 要求交接条目携带来源，与 §6.3 刚拆开的两个对象自相矛盾；④ 逐位表漏掉「可热插拔」位的定性，并笼统称本档为「2.10 配置档」；⑤ §6.1 保留了一句「被排除的区域不许访问」，与自己「不整批纳入禁止清单」的决定冲突。此外「补齐位恒为零」是**规范没有说的**（那 4 个字节是 ABI 间隙，不是语义字段），「跟随 MTRR」也不是一个 PAT 类型。

十二处错误（第三轮三处、第四轮四处、第五轮五处）有两个共同成因，值得单独记下。**其一是出处问题**：本方把「我读到的一处出处」写成了「规范如此」。评审人在第三轮也犯了同一条，并在第四轮主动撤回对自己结论的确认。因此 §7.1 现在的强制要求是：任何一致性断言都要写明出版物标识、发布日期与取证方式，否则不得写成「已核实」。**其二是抽象层级问题**：本方多次把「同一时刻都为真的一组事实」写成「同一个对象」——补齐位与语义字段、坐标归一化与集合合并、不分配与不许映射、描述符版本与属性位布局，都是这一类的混写。这类错误的共同后果不是文档难看，而是**实现者会照字面写下一个静默过严或静默过宽的对象**。因此第五轮之后，本文新增的每条合同都必须能回答两问：它约束的是哪一类对象，以及违反它时是启动失败还是静默少一块内存——后者一律不接受。
