## 0. 阅读指引

### 0.1 这件事在系统里的位置

一个操作系统启动时要回答的第一个问题不是「怎么调度」，而是「我手上有哪些物理内存」。机器刚上电时，只有固件知道答案：哪些地址是真正的随机存取存储器、哪些是设备寄存器、哪些被固件自己占着、哪些坏了不许碰。固件把这份答案写成一张**物理内存区间的清单**交给引导程序，引导程序把它翻译成内核能用的形式，再交控制权——此后内核只能靠自己记账。这张清单就是本文说的**内存图**。

翻译这一步做错，后果不在引导期暴露，而在很久之后：一块设备寄存器被当成普通内存映射，内核的内存分配器可能把一个缓冲区放进去，写进去的数据消失、读出来的数据无意义，或者机器直接故障；一块坏内存被当成可用内存，随机位翻转会在几个月后伪装成软件缺陷。因此**分类规则必须唯一、必须可解释**——这正是本组问题的主题。

本项目支持三个处理器架构（x86-64、AArch64、RISC-V 64 位），引导期有两条不同的来源：UEFI 固件给出内存图，设备树（一种二进制硬件描述）给出内存节点。两条来源各自经过自己的政策，汇进内核统一的内存语义。

本文用两个验证层次的专有名词：**真机**=把镜像真正在 QEMU 上启动起来、由判定脚本按行读串口输出判通过/失败的形态（三个架构各有一条腿）；**宿主测试**=在开发机上直接运行、不需要固件或模拟器的单元测试。文中说「需要真机读数」，意思是这件事在宿主测试里无法回答。

### 0.2 UEFI 内存图描述符的形状（规范事实）

每条描述符有四个语义字段，版本 1 的规范长度是 40 字节（另有一个 4 字节的补齐位）：

| 偏移 | 字段 | 宽度 | 内容 |
|---|---|---|---|
| 0 | `Type` | 32 位 | 这块区域**是什么** |
| 4 | 补齐 | 32 位 | 恒为零，只为把下一个字段推到 8 字节边界 |
| 8 | `PhysicalStart` | 64 位 | 物理起点（页对齐） |
| 16 | `VirtualStart` | 64 位 | 运行期虚拟地址，引导期读到的是未转换的原值 |
| 24 | `NumberOfPages` | 64 位 | 页数（每页 4 KiB） |
| 32 | `Attribute` | 64 位 | 这块区域**支持怎么用** |

分类器只用到 `Type`、`PhysicalStart`、`NumberOfPages`、`Attribute` 四个字段；`VirtualStart` 与补齐位属于「结构里有、语义上此刻用不上」。

两个容易踩的形状事实：

- **步长可以大于 40**。固件按「未来可能加字段」的方式排布描述符，实际步长由固件自己报告。因此「缓冲区长度 ÷ 40」推不出条数，任何假设步长等于 40 的实现都可能读到空洞。
- **`Type` 与 `Attribute` 是两个正交的维度**。类型是固件对区域用途的断言，属性是那块区域支持的**能力**位图——它表示「可以做到什么」，不是「此刻正在被怎么用」。把属性读出来原样翻译成页表标志是错的，只按类型分类同样是错的。

标准类型有 16 个（数值 0 到 15）：`RESERVED`(0)、`LOADER_CODE`(1)、`LOADER_DATA`(2)、`BOOT_SERVICES_CODE`(3)、`BOOT_SERVICES_DATA`(4)、`RUNTIME_SERVICES_CODE`(5)、`RUNTIME_SERVICES_DATA`(6)、`CONVENTIONAL`(7)、`UNUSABLE`(8)、`ACPI_RECLAIM`(9)、`ACPI_NVS`(10)、`MMIO`(11)、`MMIO_PORT_SPACE`(12)、`PAL_CODE`(13)、`PERSISTENT`(14)、`UNACCEPTED`(15)。数值更高的区段分三段：标准类型之后的**未分配数值区**（`0x10` 到 `0x6FFFFFFF`）、**OEM 保留区**（`0x70000000` 到 `0x7FFFFFFF`）、**OS loader 保留区**（`0x80000000` 到 `0xFFFFFFFF`）——三段语义不同，不能并成一段处理。

属性位图里本文会反复出现的位：**缓存类** `UC`/`WC`/`WT`/`WB`/`UCE`（以及现代用法同属缓存策略的 `WP`）；**保护能力** `RO`/`RP`/`XP`（硬件能做到什么，不是当前权限）；**独立用途属性** `RUNTIME`（需要运行期重新映射）、`NV`（非易失）、`SP`（特定用途内存）；**元信息** `MORE_RELIABLE`、`CPU_CRYPTO`；**ISA 掩码**（一组架构专用位加一个 `ISA_VALID` 有效位）。本文的政策基线取 **UEFI 2.10**——基线之外新定义的位（例如 2.11 表示可热插拔的位）在本文里属于「未知属性位」，是裁决二要讨论的一行。

### 0.3 分类要产出的东西（已冻结的输出形状）

内核最终拿到两份区间表，外加一份引导期内部的诊断清单：

| 输出 | 语义 | 是否跨引导边界 |
|---|---|---|
| **可用表** | 普通物理内存，可以交给内核的物理页分配器 | 是，写进交接结构 |
| **保留表** | 运行期可以经「直接映射」访问，但不得再分配出去 | 是，写进交接结构 |
| **side list**（第三份输出） | **保留但不建普通映射**的范围，只用于确认「哪些区间因为政策被挡在两张表之外」 | 否，只是引导壳内部诊断，不进交接结构 |

这里有两个容易混淆的概念，本文必须分开使用：

- **直接映射**（Direct Map）：内核把物理内存线性地映进自己的虚拟地址空间，于是「物理地址加一个固定偏移」就能访问。它决定「内核能不能读到这块地址」。
- **物理页分配器**（PMM）：内核把空闲页分给各个使用者。它决定「这块地址能不能被拿去当普通内存用」。

一个区域可以「必须映射但不许分配」（固件常驻区），也可以「必须保留但不该映射」（运行期服务代码）。用一个 `reserved` 标签同时回答这两个问题，会把「能不能分配」与「要不要映射」压成一位，两类错误因此互相掩盖。

一次分类被拆成三段职责（已冻结）：

1. **解析**：校验固件报告的版本、步长、缓冲区边界，逐条读出四个字段，并检查起点是否 4 KiB 对齐、长度会不会溢出。
2. **裁决**：对每条描述符决定去向（分配 / 保留映射 / 进 side list / 排除 / 走设备路径）。
3. **输出**：**两遍**。第一遍只做裁决和计数，并预检三个输出容器的容量——它是唯一可能失败的一遍；第二遍只写入，不返回错误。第二遍的「不可失败」由类型表达：第一遍产出一个「已验证的计划」凭证，只有持有凭证才能调用写入。

还有两条地址维度的合同，也属于已冻结：

- **架构可表达能力**：分类器检查「这条描述符的末端是否落在本架构页表能表达的物理地址范围内」（半开上界语义）。这是能力检查，不是「是不是 RAM」的判断。
- **映射覆盖验收**：内核是否真的为某个区间建立了直接映射，由另一层的映射规划与验收负责。**通过上界检查不等于覆盖成立**——地址在处理器能表达的范围内，却可能超出项目实际分配的映射窗口。

## 1. 裁决一：三个架构的「普通写回映射」最低保证合同

### 1.1 机制背景：固件声明的属性，和硬件真正给的属性，不是同一件事

冻-8 要求任何进两张表的区间先证明自己支持普通写回映射。目前的证据来自描述符的 `WB` 位。但 `WB` 位是**固件对硬件能力的声明**；一块地址被映射之后究竟按什么缓存策略访问，由**内核自己建立的页表**与**架构的缓存控制机制**共同决定。三架构的机制完全不同：

| 架构 | 谁决定有效缓存属性 | 本项目的现状（代码事实） |
|---|---|---|
| x86-64 | 页表项的 `PCD`/`PWT` 两位选择 `IA32_PAT` 模型专用寄存器里的 8 个表项之一；该表项若写成「跟随 MTRR」，再由该物理地址的 MTRR 范围寄存器决定 | 建立映射时从不设 `PCD`/`PWT`，因此总是落在 `PAT0`；本项目不编程 `IA32_PAT`，也不读 MTRR |
| AArch64 | 叶子页表项的 `AttrIndx` 三位选择 `MAIR_EL1` 里 8 个字节属性之一 | 内核在开启分页前把 `MAIR_EL1` 写成 `0xFF`（Attr0 = Normal Write-Back Write-Allocate），设备区用 Attr1（Device-nGnRnE） |
| RISC-V 64 | 页表项（Sv39）**没有缓存属性字段**；普通内存的属性由平台级物理内存属性（PMA）决定 | 建立映射时只写权限位；不使用可选的 Svpbmt 扩展 |

由此得到三条强度不同的结论（**推理**，但每条都可复核）：

- **AArch64 基本闭合，但差一步**：机制上内核自己写 `MAIR_EL1`，代码里明确说明「固件可能已经设过自己的 `MAIR`，这里覆盖它」，所以不依赖固件。未核的是「实际建立的**所有**直接映射叶子的 `AttrIndx` 都等于 0」——目前只知道默认构造路径与设备路径的分支如此，不知道是否存在别的构造路径。
- **x86-64 是一个条件句，不是事实**：准确表述是「**若** `PAT0` 仍保持复位默认值（写回），**且**该物理地址的 MTRR 允许写回，则映射表现为写回」。这两个前提本项目既没有声明也没有校验。引导壳运行在 UEFI 固件之后，固件有权改写 `IA32_PAT` 与 MTRR。**更值得注意的是：这条依赖已经在本仓被当成前提用了一次**——x86-64 的中断控制器寄存器页（LAPIC / IO-APIC）不靠页表位取「不可缓存」属性（页表没有逐页的设备位），而是靠**固件建立的 MTRR** 拿到（代码事实，见位置清单里的 `identity_device_windows`）。也就是说，「寄存器区必须由固件的 MTRR 判成不可缓存」已经是既成依赖；同一份 MTRR 状态把普通 DRAM 判成什么，却没有任何地方声明或检查。
- **RISC-V 64 完全依赖平台**：可选的 Svpbmt 扩展给页表项加了两位（PBMT），但它的三个取值是「跟随 PMA」「不可缓存主存」「强序 I/O」——**没有一个「强制写回」的取值**；而且 S-mode 能不能用这两位，由 M-mode 侧的 `menvcfg.PBMTE` 控制，该位为 0 时行为等同扩展不存在。因此普通内存的缓存属性只能写成平台前提。**本仓已经记过一次这个风险的镜像形态**：设备窗口的注释写明「按普通写回缓存映射在 QEMU 上能用、在真实硬件上不满足设备语义」——模拟器的宽容掩盖了「平台属性没有合同」这件事，同样的掩盖对普通 RAM 也成立。

### 1.2 不写这条合同会具体坏在哪里（反向推演）

- **x86-64**：固件把 `PAT0` 改成不可缓存（例如某个图形控制台的调试配置留下的状态），内核的全部直接映射内存变成不可缓存访问。系统**能正常启动、能跑完所有测试**，只是内存带宽掉到一小部分，且写合并/原子行为的差别只在特定负载下暴露。没有报错，没有日志——因为这条路径上的每一步都「合法」。
- **AArch64**：如果存在一条构造路径把普通内存叶子的 `AttrIndx` 落到 Attr1（Device-nGnRnE），普通内存变成设备内存：非对齐访问直接产生对齐异常，读出未写过的地址返回零字节而不是脏数据。表现为「内核在某些随机点上死掉」。
- **RISC-V 64**：平台把某段 DRAM 的 PMA 配成非主存属性，内核却把它当普通内存分配出去——页缓存里的数据与设备侧看到的数据不一致，故障形态是数据损坏而非崩溃。

三种坏法共同说明一件事：**「描述符有 `WB` 位」不能推出「内核的映射按写回访问」**，中间那一跳需要每个架构各自的一条可验收承诺。

### 1.3 候选合同形态

| 案 | 做法 | 代价 | 风险 |
|---|---|---|---|
| **甲：读取并断言** | 引导期读出固件留下的状态（x86：`IA32_PAT` 与 MTRR；AArch64：`MAIR_EL1`；RISC-V：无状态可读，退成平台声明），不满足普通内存前提就让引导失败 | 需要三套架构特定的寄存器读取代码；RISC-V 上「读不到」意味着这条案对它无效 | 把「固件当前状态」当成合同：今天恰好是写回，明天换固件版本就拒绝启动 |
| **乙：自行建立环境** | 内核在交出控制权前**自己写**这些寄存器，不信任固件状态：x86 重设 `PAT` 并把要用的 MTRR 范围显式设成写回；AArch64 已经这么写 `MAIR`；RISC-V 仍然无手段 | x86 上改 MTRR 涉及与固件共存的问题（其它设备的写入类型），风险高；`PAT` 是内核独占的，改它相对安全 | 「自己建立」只对内核独占的寄存器成立，对共享的 MTRR 不成立 |
| **丙：分层最低保证** | 每个架构写一条**各自机制下的最小承诺**，并各配一个验收读数：能自建的架构自建（AArch64 的 `MAIR`、x86 的 `PAT`），不能自建的架构把平台前提写成显式合同并规定不满足时的判据（RISC-V：平台声明 + 出现不满足时判为「该平台不受支持」而不是静默继续），x86 额外补一条「读 MTRR 并分析，不满足则降级或失败」 | 三条承诺形态不同，不能用一句话统一 | 需要评审接受「统一的是语义，不是机制」 |

**本文申请方的立场**：丙。理由是甲把固件状态当合同（脆弱），乙在 x86 的共享寄存器上不可行、在 RISC-V 上根本没有手段；只有丙能让三个架构各自给出**可测试**的承诺，同时不假装三架构有同一种缓存控制机制。

### 1.4 请评审人回答

1. 三架构合同的形态选甲/乙/丙？若选丙，请确认「RISC-V 只给平台前提声明」这一条是否足以支撑「普通内存按写回访问」这个语义承诺，还是必须补一个运行期探针（代价是需要一段只有测试用的寄存器读取代码，而 RISC-V 侧本身没有可读的等价状态）。
2. x86-64 上：`IA32_PAT` 属于**由内核独占、可以安全重设**的寄存器；MTRR 属于**与固件共存**的状态。是否同意「PAT 自行建立 + MTRR 只读只判、判出不满足时按区域降级（该区域不进保留表，改走 side list）」这种混合处理？
3. AArch64 的「所有直接映射叶子的 `AttrIndx` 都为 0」该用什么手段验收：静态穷举页表构造路径（不依赖运行时，可能漏掉未来的新路径），还是切页表前遍历已建叶子做一次断言（运行期成本，但不会漏）？
4. 确认顺序：**这条合同必须先于 §2 的政策矩阵批准**，因为某个架构若无法表达某类区域所需的映射属性，对应政策行要从严（「保留并映射」降级为「排除」）。若评审人认为顺序可以颠倒，请说明降级如何事后不打补丁地回填。

### 1.5 需要补的证据

- 三架构各自「切页表前后」的寄存器读数（x86：`PAT`/MTRR；AArch64：`MAIR_EL1`；RISC-V：平台文档里对 DRAM 的 PMA 声明来源）。
- 一条**故意不满足**的实验：把 x86 的 `PAT0` 手动改成不可缓存，量测启动时间与一段内存拷贝的耗时差别——用来论证「这条合同值多少」。

## 2. 裁决二：类型 × 属性政策矩阵的逐行批准

### 2.1 机制背景：五步裁决顺序（已冻结，冻-6）

分类器对每条描述符走同一条路径，任何组合都必须落在唯一的输出上：

| 步 | 判断 | 结果 |
|---|---|---|
| 1 | **未知或不支持的条件** | 类型不在 0–15 之内（即三段未知数值区）→ 分类错误；ISA 属性位出现（无论有效位怎么取）或 ISA 掩码非零而有效位为零 → 分类错误 |
| 2 | **存在即拒绝启动的类型** | `UNACCEPTED`(15)、`PAL_CODE`(13) → 终止引导。前者是「还没被接受的内存」（在支持机密计算的平台上读它会直接故障），后者是处理器相关代码，本项目不支持 |
| 3 | **类型强制处置（类型胜过属性）** | `RESERVED`(0)、`UNUSABLE`(8) → 排除；`MMIO`(11)、`MMIO_PORT_SPACE`(12) → 走设备窗口路径。这两类的属性位**不改变处置**，理由是类型回答「这块区域是什么」，属性回答「能怎么用」；固件声明「不许触碰」不能被任何属性改判 |
| 4 | **普通内存候选 × 独立属性** | 候选类型是 `CONVENTIONAL`、`LOADER_CODE`、`LOADER_DATA`、`BOOT_SERVICES_CODE/DATA`、`ACPI_RECLAIM`、`ACPI_NVS`、`RUNTIME_SERVICES_CODE/DATA`、`PERSISTENT`；只要 `RUNTIME`/`NV`/`SP` 任一位命中 → 不进分配器、不建普通映射、范围进 side list |
| 5 | **写回准入** | `WB` 位存在 → 按类型政策进两张表；缺失 → 走逐类处置表（不建普通映射、范围进 side list），**没有任何绕行通道** |

下面三组组合的结论完全取决于步骤先后，按此顺序落定：`RESERVED + NV` → 排除（属性只记录，不进 side list）；`UNUSABLE + SP` → 排除；`MMIO + RUNTIME` → 设备窗口路径；`PAL_CODE + NV` → 拒绝启动（第 2 步先于一切属性裁决）。

### 2.2 为什么矩阵还没批

冻-8 说「进两张表必须证明支持写回」，但**「证明」依赖两件事**：某类区域到底需不需要被映射（取决于内核是否消费它）和某个架构能不能给出所需属性（裁决一）。这两件事都没有读数，所以逐行批准一直悬着。以下七行是仍需要评审明确签字的具体判断。

### 2.3 待批准的行

**行 1：基线之外的未知属性位——失败，还是记录后继续？**

当前实现按**分类错误**处理：任何不属于 2.10 基线的属性位出现，整张内存图作废、引导失败。这是把「不静默忽略」实现成了「不容忍」。争议在于：**这是一条会被固件版本单方面改写的合同**。UEFI 2.11 新增可热插拔内存属性位之后，同一份镜像在一个更新的固件上会启动失败，而那块区域对内核来说其实无关紧要（它只是一个提示：不要把这页内存放不可迁移的数据）。

| 案 | 做法 | 后果 |
|---|---|---|
| 甲 | 保持未知即失败 | 最严格；固件演进随时可以打断启动；调试时只能靠属性值定位是哪一位（而当前留痕通道正是裁决五，还没有） |
| 乙 | 未知位一律记录并继续 | 未来若出现一个语义上真危险的位（例如某种必须特殊处理的内存），会被静默放行 |
| 丙 | **分级**：属于「明确未定义/保留」编码空间的位 → 失败；属于「规范已定义但本项目不解释」的位 → 记录并继续；ISA 属性维持失败（架构专用含义，误当普通内存的风险高于新提示位） | 需要维护一份「哪些位是已定义但未解释」的清单，随基线版本更新 |

**立场**：丙。它把「不静默」落实成「看得见但不阻断」，同时不给未编码的空白区留后门。

**行 2：`ACPI_NVS` 的映射资格——按「有没有消费者」还是第一版一律不建？**

政策写的是「是否存在 ACPI NVS 消费者决定要不要映射」。第一版内核不解析 ACPI 表，因此当前没有消费者 → 不建普通映射、范围进 side list。争议：这条判据是**动态的**，将来加了 ACPI 支持就会翻转，而翻转意味着政策表的一行变了。

| 案 | 做法 |
|---|---|
| 甲 | 固定成第一版政策：不建普通映射（进 side list）；把「将来有消费者时再映射」写成一条独立的未来合同，届时重开这一行 |
| 乙 | 政策文本保留「由消费者存在性决定」，但要求这个判据**可机械检查**（例如内核侧一个编译期常量/特性开关，被引导壳读取） |

**立场**：甲。乙等于把政策表的取值交给另一层的运行时状态，矩阵就失去「任何组合唯一确定结果」的性质。

**行 3：`WB` 缺失时的引导镜像区间（`LOADER_CODE`/`LOADER_DATA`）——side list 够不够？**

逐类处置表把这两类在 `WB` 缺失时判为「不建普通映射、范围进 side list」。但引导壳自己的代码与数据正落在这两类里：镜像在切到内核页表之前需要被读取（取指走的是恒等窗口，切根之后的读取需要直接映射）。如果 side list 只是诊断，那么「引导数据在切根后还能不能读」这件事没人保证。

| 案 | 做法 | 后果 |
|---|---|---|
| 甲 | 接受 side list：论证「切根之后不再访问任何 `LOADER_*` 数据」，并把这句话变成断言 | 若将来有引导数据需要跨切根读取（例如交接结构之外还留在镜像里的表），会静默读到缺映射 |
| 乙 | 判为分类错误：`LOADER_*` 缺 `WB` 视为引导环境超出能力，直接失败 | 把一条本可继续的路径变严；在真实固件上这几乎不发生，因此测试难以覆盖 |
| 丙 | 由**已知映射来源**单独覆盖：把引导镜像自身的区间登记进内核的映射覆盖清单（这条通道已经存在，用于内核镜像自己），不依赖内存图的属性判定 | 与分类政策解耦，但多一条「同一块物理地址由两个来源分别声明」的一致性检查 |

**立场**：丙，并要求补一条「两来源区间一致」的验收。请评审人特别看这条：**同一块地址被两个来源分别声明**是否可接受，还是必须让分类器成为唯一权威。

**行 4：`PERSISTENT`(14)——保留范围信息，还是出现即拒绝启动？**

现政策：不进普通分配器、不建普通映射、**保留完整范围清单**（不能只留计数，否则将来实现持久内存支持时无法恢复范围）。替代方案是拒绝启动，理由是本项目对持久内存的属性、持久性与访问语义都没有支持路径，出现它就是「平台超出能力」的明确信号。

争议点是**这条判断的强度**：拒绝启动对用户的代价是一次失败安装；静默保留的代价是一段容量被永久闲置，且没有任何记录说明为什么（在裁决五的留痕通道落地之前尤其如此）。

**立场**：保留范围 + 明确计数并打印原因；如果评审人认为「闲置一段内存却无人知晓」不可接受，就改成拒绝启动。请给出判据。

**行 5：固件服务代码/数据与 `ACPI_RECLAIM` 被永久挡在分配器之外——这是一条项目政策，不是规范要求。**

规范说这三类在退出引导服务之后**可以当一般用途使用**。本项目选择不回收（早期内核要简单与安全）。代价直接可以量化：在大内存的虚拟机上，引导服务数据区往往随内存大小线性增长，被永久放弃的那部分不是零头。

请评审人回答：这条政策是否维持？如果维持，是否需要给它加一个「可回收的最低条件」（例如：只回收位于某个已验收地址窗口之内的部分），还是明确拒绝任何渐进回收（后者实现上简单得多）。

**行 6：三段未知数值区间统一判「分类错误」——要不要为项目自己的类型留一个显式登记通道？**

OS loader 保留区（`0x80000000` 起）是**规范专门留给操作系统的加载器使用的编号空间**。本项目现在对它一视同仁地报错。将来只要给引导产物加一个新区域（例如把内核的某类镜像单独标注），就需要用到它——那时要么临时改分类器（政策被实现倒逼），要么现在就留一条「项目显式登记的自定义类型」通道。

**立场**：现在就留通道，但登记必须是**代码里的常量清单 + 文档里的一行说明**，而不是「凡高位区间都当 loader 自己的」。请评审确认这条通道是否属于范围蔓延。

**行 7：容量与诊断的耦合——side list 条目超限即整张图作废，是否合理？**

side list 按冻-5 只是引导壳内部诊断，但当前实现把「诊断装不下」实现成预检失败 → 引导失败。第 4 步（独立属性命中）与第 5 步（`WB` 缺失）都会往 side list 放条目，而普通机器上带 `RUNTIME` 位的区域不少。**诊断输出的容量不该有否决启动的权力**，可截断又违反「不静默忽略」。

| 案 | 做法 |
|---|---|
| 甲 | 维持失败，但把容量按真机样本定足，并让「超限」成为一条需要重新实测才能改判的信号 |
| 乙 | 超限时降级为「计数 + 前 N 条范围」，并显式打印降级发生（不静默），启动继续 |
| 丙 | 让 side list 不进预检（它不是交接数据），容量策略独立于两张表 |

**立场**：乙，并要求降级必须由输出结构自身携带（一个显式的「已截断」标志），而不是靠人读串口日志。请评审人判断这是否破坏两遍扫描的事务性合同——本文申请方认为不破坏，因为降级发生在写入遍之内且写入遍不允许失败。

### 2.4 请评审人回答（汇总）

对上述七行逐行给「同意哪一案 / 提出第四案 / 需要哪种证据才肯签字」。另外请回答一个结构性问题：**七行批准之后，政策表是否还有可能留下「未定义」的空格**——本文申请方认为不可能，因为五步顺序保证任何组合都按固定路径走完并落在唯一输出上；完整性判据应当是「组合空间无空洞」，而不是「每个已知属性位都有一行」。

### 2.5 需要补的证据

- 三个目标（x86-64 UEFI、AArch64 UEFI、RISC-V 裸机）在四个时点的内存图样本——**读图时、自举分配之后、退出前一刻、退出函数返回的最终图**——每条记录 `Type`、`PhysicalStart`、`NumberOfPages`、`Attribute`。行 1、4、5、7 的结论都依赖真实分布，现在只有推理。
- 政策穷测矩阵的覆盖读数：矩阵里定义过的组合是否每条都有用例，尤其是四个具名顺序组合与「`CONVENTIONAL` + `RUNTIME`」这条最容易被写错的组合。

## 3. 裁决三：退出引导服务之后的端到端验收

### 3.1 机制背景：两种顺序，差别不只是先后

引导壳必须做一件带有事务性质的工作：读内存图得到一个版本戳（MapKey），然后用**同一个键**去调用退出函数——中间只要有任何分配改动了内存图，键就失效，必须重读重试。

于是有两条可选顺序：

| 顺序 | 做法 | 关键差异 |
|---|---|---|
| **生产式（路径 B）** | 读图 → 分类 → 用同键退出；键失效则重来 | 分类发生在引导服务还活着时；读图与退出之间**零分配**，所以图不会因为自己的动作而改变 |
| **退出后分类（路径 A）** | 先完成全部自举分配 → 调退出函数 → **保留**它返回的那份最终图 → 分类 | 最终图就是退出所用的图，因此它包含所有自举占用（包括读图缓冲自己那一块）；代价是分类发生在引导服务已失效之后 |

路径 A 的价值在于：分类所依据的图和真实的物理占用重新变成同一份。它的风险全部来自「引导服务已经不在了」这一条：分配器、控制台、释放接口都失效，任何失败都没有退路。

### 3.2 六项验收（已定义，待跑）

| 验收 | 标准 |
|---|---|
| 原始内存图访问 | 用元数据里的**有效图长度**，不能用分配缓冲的长度（缓冲按「留几条余量」分配，长度不是步长的整数倍） |
| 分类零分配 | 分类路径上没有任何临时堆分配 |
| 输出零分配 | 输出容器指向事先准备好的静态存储或交接区 |
| 错误退出 | 退出后分类失败 → 不依赖引导服务的停机路径（裸串口打印 + 停机），不返回固件环境 |
| 析构安全 | 最终图缓冲的持有、遍历、分类、析构都不调用失效服务，也不经依赖引导服务的日志后端 |
| 输出生命周期 | 输出数组所在区间在内核消费期间保持可访问，且不进入可用表 |

其中最后两项是**待验收**（不是已成立）。「可访问」和「不被分配」是三个不同命题：出现在最终图里 = 被记录；不进可用表 = 不会被分配器拿走；被内核页表覆盖 = 读得到。目前只有第一条有保证。

### 3.3 四个悬空问题

**问题 A：输出数组的归属怎么保证？**

引导壳用来装分类结果的静态数组属于镜像自身，所以会出现在最终图里。但它同时需要「不被分配」与「被覆盖」两条。三种做法：由镜像区间来源单独覆盖（裁决二行 3 的丙案同一条通道）；切根前把结果深拷贝进内核拥有的存储；把输出数组的地址范围也纳入「自举占用不得进可用表」的断言与覆盖检查（过去的断言只查了页表根页与自举分配区两处，漏了输出数组本身）。

**问题 B：退出之后失败，谁能看见？**

fail-stop 只剩裸串口。三个架构在测试环境里的控制台设备各不相同（x86 的 ISA 串口、AArch64 的 PL011、RISC-V 的 SiFive 串口），而真机判定脚本是按行读串口输出来判 PASS/FAIL 的。于是有一个本文没有答案的问题：**fail-stop 的消息格式一旦进入判定脚本，就是一份契约**——它该由谁来读？

| 案 | 做法 |
|---|---|
| 甲 | 失败路径输出固定前缀 + 一段结构化文本（错误种类 + 触发描述符的四元组，若裁决五的留痕通道存在），判定脚本把它算作 FAIL 的一种可读形态 |
| 乙 | 失败只输出人类可读文本，判定脚本继续按「没看到 PASS 就超时」判失败 |
| 丙 | 不为失败路径设计观测接口，只在宿主测试里覆盖错误分支 |

**问题 C：「退出后到分类结束不切地址空间」应该多硬？**

现在这条保证是**顺序事实**（退出 → 分类 → 建表开分页，中间不切根），靠代码顺序维持。要不要升级成结构性保证（例如把「分类期间的访问」包在一个不能被跨越的构造里，或在切根处断言分类已结束）？代价是引导期代码要多一层包装；收益是将来有人调整顺序时不会静默读到未映射地址。

**问题 D：容量合同在路径 A 下要不要重算？**

两张表的容量属于交接协议（可用表 128 条、保留表 256 条），side list 容量属于引导壳内部（64 条）。路径 A 用的是**最终图**，条数通常比生产式路径读到的快照更多（每一次分配都可能把一个常规区间切成三段，从而净增两条描述符）。所以「容量够不够」这个问题在两条顺序下答案不同，需要分别取真机读数。它与裁决二行 7 是同一件事的两个侧面：那边问「装不下该怎么办」，这边问「装得下吗、怎么知道」。

### 3.4 请评审人回答

## 4. 裁决四：设备树来源的保留区与不可映射节点政策

### 4.1 机制背景：两条来源不能共用一套政策

统一的分层是这样画的（已冻结的方向）：UEFI 来源（类型 + 属性）与设备树来源（内存节点、保留区域等）各自经过**自己的来源政策**，汇进同一份 OS 内存语义，再由架构映射层落到页表。UEFI 侧政策是裁决一、二的对象；设备树侧政策是本题。

设备树描述内存的方式与 UEFI 不同：一个 `/memory` 节点用 `reg` 列出系统内存区间；另有一个 `/reserved-memory` 子树逐条列出被保留的区域，每条可以带一个 `no-map` 标记表示**不得为它建立映射**，也可以带其他提示（例如区域是给某个设备用的、或者跨重启保持）。

已核实的设备树侧行为只有两条（代码事实）：解析 `/memory` 的 `reg`；按固件常驻区的末端裁掉区间前缀。未覆盖的语义清单：`/reserved-memory` 子节点、`no-map`、保留区与内存区的重叠、被禁用的内存节点、多段 `reg`、地址/长度单元的变体（`#address-cells`、`#size-cells`）以及节点名带 unit-address 的形态。

### 4.2 为什么不能照搬 UEFI 的类型政策

设备树的「保留」不等于 UEFI 的「保留表」。`no-map` 的语义是**禁止映射**；把它按 UEFI 的 `ReservedMapped` 处理（保留但建普通直接映射），后果是确定的（**推理**，机制清楚）：在 AArch64 上这类区域常常是安全监控器或可信执行环境的常驻区，普通映射会访问到异常内存，产生 SError 或同步异常；在 RISC-V 裸机腿上是 OpenSBI 自己的常驻区，映射之后内核的写回缓存与固件的访问路径会在同一页上给出两种不一致的视图。反过来，把需要映射的保留区（例如为设备划出的共享缓冲区）判成 `no-map` 语义，则驱动读不到它。

同一份地址形状，两种相反的正确处置——这正是「用地址代替类型」的老毛病换了来源又出现一次。

### 4.3 候选方案

| 案 | 做法 | 代价 |
|---|---|---|
| 甲 | 只把「已有行为」成文：明确写「第一版设备树腿只解析 `/memory` 并按固件常驻区裁剪，其余语义未覆盖」，未覆盖项逐条登记为缺口，其中 `no-map` 与重叠检查标为**已知风险** | 「三架构共同的内存语义」这句话在第一版只对 UEFI 腿成立；裸机腿的语义承诺变窄 |
| 乙 | 一次补齐三类政策（`reserved-memory` 解析、`no-map` 禁止映射、保留区与内存区重叠的处理规则）并落码 | 需要在没有真实消费者的情况下设计映射语义；可能设计早了 |
| 丙 | 消费者驱动：只有内核真的需要某类区域时才补对应政策，但先补**最保守的一条**——`no-map` 与重叠检查（这两条的作用是「挡掉错误」，不需要任何消费者） | 政策成文分两批，验收也要分两批 |

**立场**：丙。它比甲多做一条能防真实故障的判据（`no-map` 不许映射、重叠不许同时进两张表），又比乙少做一批没有消费者的设计。请评审人特别判断：**只补「挡错」的那两条、把「给什么语义」留给消费者**，这个切法是否成立。

### 4.4 请评审人回答

1. 第一版接受「UEFI 腿有完整政策、设备树腿只有保守判据」这种不对称吗？如果接受，统一语义的承诺文本该怎么写才不误导读者。
2. 保留区与内存区重叠时的规则选哪条：报错（分类错误）、按后声明者裁剪、还是把重叠部分判为不映射？三条各配一种故障形态，请给出优先级。
3. 被禁用的内存节点（状态为 disabled）该不该从可用表里排除？现政策未覆盖；若按 UEFI 的对应物想，等价动作是把区域判为排除。

## 5. 裁决五：被排除描述符的留痕通道

### 5.1 机制背景：政策里反复出现「记录，不静默忽略」，但记录到哪一层没有合同

政策表里至少三处写着「记录进诊断、不静默忽略」：基线之外的未知属性位（裁决二行 1）、被类型强制排除的描述符的属性位（第 3 步）、当前不解释的元信息属性位。讨论文档还给出过一份「最小返回信息」的形状：排除与特殊的条数与字节数、未知类型条数，外加前 N 条的原始四元组（类型、起点、页数、属性）。

当前实现做到的程度（代码事实）——缺口有**两层**：

| 输出 | 记了什么 | 没记什么 |
|---|---|---|
| 可用表 / 保留表 | 区间（起点 + 长度） | 类型与属性（它们只影响裁决，不进输出） |
| side list | 区间（起点 + 长度） | 类型与属性——所以「第 4 步命中了哪一位」「`WB` 缺失的是哪一类」无法从输出复原 |
| 排除 / 设备路径 | **什么都不留**：三个计数器（可用、保留、side）里没有它们的位置，既没有条数也没有范围 | —— |

于是「不静默忽略」目前只兑现到「区间可见」这一层（side list），而被类型排除的那一类连区间都不留。

### 5.2 形态由受众决定——这是本题真正要裁的东西

已冻结的一条约束把方案空间收窄了：side list 不进内核的统一交接协议（冻-3 与冻-5 共同作用——UEFI 属性不跨界，诊断也不跨界）。所以候选只剩三条：

| 案 | 做法 | 谁能读 | 风险 |
|---|---|---|---|
| 甲 | 引导壳内部固定容量数组，装**被排除/被降级描述符的四元组**，串口打印前 K 条；不进交接结构 | 引导期在场的人、真机判定脚本（如果它按行读） | 打印条数上限 K 之外仍然静默；自动化流水线（CI）想机器解析就得依赖文本格式（与裁决三问题 B 撞在一起） |
| 乙 | 只在**失败**时打印触发那条描述符的四元组，成功路径不留痕 | 只有失败时的读者 | 成功启动里的「一段内存被悄悄排除」仍不可见——而这恰恰是最难复现的故障形态 |
| 丙 | 扩成交互可见：在交接结构里为诊断留一个字段 | 内核与任何后续工具 | 与冻-5 冲突（除非明确区分「诊断字段」与「保留协议」两种用途，而这一区分本身要新裁决） |

### 5.3 反向推演：没有这条通道会怎样

- 一条回归把某段本该映射的固件常驻区误判成设备路径 → 真机表现为「少映射一段地址」，故障在内核消费该区域时出现；出问题时可用的只有两张表的差集，要倒推是哪条描述符被丢，只能重跑并把分类器改成打印一切。
- 固件升级后新增一个属性位，而政策按「未知即失败」（裁决二行 1 的甲案）→ 引导失败，但输出只有一个错误种类，没有当时触发的那一位。这时唯一能定位的手段是把属性值打出来——正是这条通道。
- 反过来，先建一条没人读的旁路也**有代价**：固定数组占引导壳的静态存储，打印消耗引导期串口时间，而字段清单一旦定型，删比加难。

### 5.4 请评审人回答

1. 诊断的**受众**是谁：只有引导期在场的人、由 CI 解析的文本、还是将来的内核消费者？三选一（或明确组合）——它直接决定甲/乙/丙。
2. 要留哪几个字段：最小四元组（类型、起点、页数、属性），还是再加「落在五步顺序的哪一步、哪一种处置」这两个「为什么」字段？本文申请方倾向后者，理由是前者只回答「是什么」。
3. 上限取多少、超限时怎么办（与裁决二行 7 同一个判据，希望一次裁决两处共用）。
4. 是否同意：**被类型排除的区间也必须留范围**（现在连范围都没有），否则第 3 步的判断不可审计。

## 8. 术语表

| 术语 | 含义 |
|---|---|
| 内存图 | 固件交出的物理地址区间清单，每条描述符 = 类型 + 起点 + 页数 + 属性位图 |
| 引导壳（boot-shim） | 由固件加载、负责准备页表与交接数据、然后进入内核的一段独立可执行代码 |
| 描述符步长 | 相邻两条描述符起始地址之差；规范长度是最小值，固件可以用更大的值做向后兼容扩展 |
| 属性位图 | 描述该区域**支持**什么用法的位集合，不是「此刻正被怎么用」的状态 |
| 写回缓存（WB） | 主存的标准缓存策略：写先进缓存、之后回写。普通 RAM 的默认期望 |
| 不可缓存 / 设备内存 | 访问直达地址空间，不经缓存。对寄存器是必需的，对 RAM 是灾难 |
| `IA32_PAT` / MTRR | x86-64 上决定有效内存类型的两个模型专用寄存器机制；前者可选 8 种类型，后者按物理地址范围设定 |
| `MAIR_EL1` / `AttrIndx` | AArch64 的属性表寄存器 / 叶子页表项用来选表项的 3 位索引 |
| PMA / Svpbmt / PBMT | RISC-V 的平台级物理内存属性 / 可选扩展 / 页表项里那两位（只能表达「跟随 PMA」「不可缓存主存」「强序 I/O」，且需 M-mode 使能位） |
| 直接映射 | 内核把物理内存线性映进自己的虚拟地址空间，物理地址加固定偏移即可访问 |
| 物理页分配器（PMM） | 内核分配与回收物理页的组件 |
| 可用表 / 保留表 | 本文对两份输出的称呼：可自由分配 / 可访问但不得再分配 |
| side list | 第三份输出：保留但不建普通映射的范围，只作引导壳内部诊断，不跨引导边界 |
| MapKey | 内存图的版本戳；退出引导服务必须携带取得该键的同一次读取 |
| 退出引导服务 | 结束固件引导期服务的调用；此后固件的分配、控制台、释放接口全部失效 |
| 交接结构 | 引导壳交给内核的固定布局数据块，字段按基址加偏移定位，不含进程内指针 |
| 恒等窗口 | 引导期把物理地址与虚拟地址等价的映射区间，让「还没切页表」时代码能继续跑 |
| 切根 | 把页表根从引导期页表切换到内核页表的动作 |
| 夹具型测试 | 只把某份数据当输入、不对该数据本身做断言的测试，被测对象是别的代码 |
| 五步裁决顺序 | §2.1 那张表：未知/不支持 → 拒绝启动 → 类型强制处置 → 普通候选 × 独立属性 → 写回准入 |
