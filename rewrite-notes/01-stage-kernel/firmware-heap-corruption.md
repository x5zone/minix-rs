# 固件堆腐化：boot 阶段的 `&'static` 数据为何会在内核接管后读回零

> **主题**：一个只在裸机启动链上才会出现的根因——启动早段构造的"整块物理内存布局表"，物理上躺在 UEFI 固件的内存池里；内核换上自己的页表后既不重放那段映射、那些物理页又被逐步回收复用，于是内核晚一点去读时读到的全是零。
> **关联代码**：`os/boot-shim/src/uefi_helpers.rs::build_memmaps`、`os/kernel/src/lib.rs::store_kernel_info`、`os/kernel/src/globals.rs`（`MEMMAP_REGION_STORE` / `BOOT_MODULE_STORE` / `RESERVED_REGION_STORE`）、`os/kernel/src/vm_handoff.rs::classify`、`os/libs/minix-boot/src/kernel_info.rs::memmap`。
> **对照系统**：Minix3 C 的 boot 内存交接、Linux 的 `memblock` / EFI memory map 保留、Redox 的 `RxdPaddr` 早期内存落地。

---

## 1. 现象：一份"内存清单"在关键时刻变成了白纸

一台刚被点亮的机器，CPU 上还没有操作系统，只有一段固件（UEFI）。固件干的第一批事里，有一件是回答"这台机器到底有哪些物理内存、每一块能干什么用"——它把答案排成一张表，叫**内存地址映射表（memory map / memmap）**：每一项是一段物理地址范围加上一个类型（可用、保留给固件、保留给显存……）。

内核要跑起来，第一件事恰恰就是拿着这张表去规划"我能用哪些物理页"。虚拟内存服务器（本仓库里的 VM）从这张表里切出自己的空闲页链表，才有内存可分配给每一个进程。**这张表是全局内存供给的源头**。

这个 bug 的现象是：内核拿着这张表去算空闲内存时，**表上列出的所有条目长度都变成了零**——仿佛这台机器**一点可用内存都没有**。后果极其靠前也极其彻底：VM 因为拿不到任何空闲页，在自己的"诞生"之前就 panic，整台机器连第一个用户态服务都没起来，boot 停在最早期。

诡异的地方在于**同一张表、同一次开机，早一点读和晚一点读结果不一样**：

- 在启动流程较早的一步（Direct Map 覆盖率自检），去读这张表，**还能读出十几条真实的内存范围**；
- 再往后一步，等 VM 真正拿它去切空闲内存时，去读同一张表，**条目全成了零**。

结构体的其它字段（连同另一张同样来源的模块表）此刻仍能正常读出。坏的不是那份"清单"这张纸本身，而是**清单上抄写内容的那几页纸被收走了**。

---

## 2. 背景：一次开机里，"内存的主人"换了三趟

要理解为什么清单会变白纸，必须先理解这段启动链上有三种不同的"内存"，它们各归各家、由不同的页表说话。

| 阶段 | 谁在跑 | 分配内存靠谁 | 这块内存归谁管 |
|---|---|---|---|
| 固件阶段 | UEFI 固件 | UEFI Boot Services 的内存池 | **固件** |
| boot-shim 阶段 | 一个跑在固件之上的 `no_std` 小程序 | 承接固件给的这块池堆（它的 Rust 全局分配器接到 UEFI 池上） | 仍是**固件的池堆** |
| 内核阶段 | 真正的内核 | 内核自己的分配器 | **内核**，且以**内核的页表**为唯一权威 |

关键在第二、三阶段之间那次交接。boot-shim 在固件的池堆上分配、构造出了那张 memmap 表和模块表，然后把它们连同一个"内核信息"结构体一起交给内核。表的数据本体，**物理上坐在固件池堆的若干页里**。

boot-shim 之所以敢把这些数据交给内核继续用，是因为它给这些数据打了 `&'static` 的标签。

---

## 3. 病灶：`&'static` 保证了"不被回收"，却没保证"内核还认得这个地址"

Rust 里 `&'static [T]` 的直觉含义是"这段引用在整个程序运行期间都有效"。在有一整套操作系统、有连续虚拟地址空间的常规程序里，这个直觉是对的。但在裸机启动的语境里，它是一个**危险的错觉**，原因有两条相互独立的机制。

**其一：`'static` 只是编译期的所有权承诺，它管不到页表。** boot-shim 用一个 `Vec` 收集内存条目，再把它 leak 成 `&'static` 切片返回（`os/boot-shim/src/uefi_helpers.rs::build_memmaps`，其签名返回 `(&'static [MemoryRegion], &'static [MemoryRegion])`，并在末尾 `Box::leak(...)`）。`Box::leak` 的作用仅仅是"告诉分配器：这块缓冲区我永远不释放"。它**完全无法保证**：当内核换上自己的页表之后，这个切片所指向的那个**虚拟地址**仍然映射到当初那块物理内存。

内核的页表只映射"内核认识并主动建立"的那些区域。固件池堆这一段，**内核的页表根本没有重放它的映射**——这一点在本仓库早有记录：`os/kernel/src/globals.rs` 里 `RESERVED_REGION_STORE` 的注释就写明了，一块"firmware-pool-backed 的 `&'static` slice，内核页表不重放那段映射，高半区跳转后同一虚拟地址读回来就是零"。也就是说，指针值还在（类型系统让编译器满意），但它指向的地址在内核页表下要么是**未映射**、要么指向了**已经被挪作他用的物理页**。

**其二：底层物理页会在 boot 推进中被回收复用。** 就算某些地址侥幸还能读，那几个物理页也不会一直空着等人来读。在随后加载 VM 的可执行映像、以及撤除 boot 期临时身份映射（boot-identity 驱逐）的过程中，分配器把这段物理内存重新分配给了别的数据。这解释了第 1 节里"早读有、晚读空"的时间线：不是交接那一刻立刻坏，而是**随着 boot 推进、那几页被别人盖掉，渐进地变成白纸**。

把两条合起来看，这个 bug 的本质就一句话：

> 一份需要活过整个内核生命周期的数据，被寄存在了"不属于内核管辖、且内核页表根本不认的地址"上；类型系统对这种跨页表的地址失效毫无感知，`&'static` 照样编译通过。

## 4. 为什么这个根因特别难定位：症状会"伪装"成另一个结论

这类"输入变白纸"的故障有一个共同的坑：**下游拿到空输入后算出荒谬结果，人容易去怀疑下游的算法，而不会怀疑输入本身已经空了。**

具体到这里：VM 的空闲内存分配流程（`os/kernel/src/vm_handoff.rs::classify`）先把 memmap 里标为可用的范围累加，再逐条扣掉内核镜像、根页表、bump 堆等保留项，最后打印 `kernel: vm_handoff free n=`（`vm_handoff.rs`）。当输入 memmap 的条目全 `len==0` 时，这套扣减算出来当然是"一点空闲都不剩"。于是很自然的第一判断是"**扣减扣过头了 / 内存布局的鲁棒性 bug**"——矛头指向 `classify` 的算术，指向 boot 内存布局的边界处理。

但算术是无辜的。真正把它揭穿的，只有一招——**在同一次运行里、在下游计算之前，直接把喂给它的原始输入打印出来看**：探针一 dump，`classify` 时刻读到的 memmap 十几条条目**长度全是零**，而它自己的 23 条扣减数值全部正常。输入已被挖空，计算没错。这一步"回到数据的源头去验真值"，是这类"算法 vs 输入"两可的故障唯一的分水岭。

还有一层迷惑性来自"部分幸存"：内核信息结构体的其它字段仍读得到，让人以为"内存没坏啊"。但这恰恰把病灶精确定位到了**payload 数据页级**（那几页没了），而**非结构体级**（结构本身还在）。"大部分好好的、唯独这一张表空了"这个不对称，是判断"跨页表地址失效"而非"整个内存被写花"的关键特征。

---

## 5. 修复：landing pad——在数据还完好的当口，把它搬进内核自己映射的段

既然病根是"数据寄存在了内核页表不认、且随时会被回收的地盘"，正确的做法就不是去修补那个地址的映射，而是：

> **在页表交接之前、趁固件池里的数据仍然完好的那一刻，把它复制进内核镜像自身一定会被映射进高半区的永久段（本例是 `.bss` 里的定长静态数组），再把引用重新指过去。**

这个"提前把易失数据接到永久存储上"的落脚点，就叫 **landing pad（着陆垫）**。本仓库的落地形态（`os/kernel/src/lib.rs::store_kernel_info`）：

1. 在 `os/kernel/src/globals.rs` 里开好静态存储：
   - `MEMMAP_REGION_STORE`（一段 `[MemoryRegion; MAXMEMMAP]`，`MAXMEMMAP` 与 `memmap` 模块的容量常量同源）承接内存布局表；
   - `BOOT_MODULE_STORE` 加 `BOOT_MODULE_NAME_STORE`（名字落定长字节池）承接 boot 模块表；
2. `store_kernel_info` 在 `arch_boot` 入口——**此刻固件池数据还没被复用、仍是完好的**——把 memmap `ptr::copy` 进那块 `.bss` 静态数组、逐条重建模块表，然后把"内核信息"里那几个切片**重新指向这些 `.bss` 存储**；
3. 因为 `.bss` 是内核镜像的一部分、内核页表**确实把它映射进高半区**，这份拷贝就能在整个内核生命周期里被稳定读到；
4. 容量若超限，用 fail-fast 断言当场崩，而不是静默截断——宁可炸也不留一份"看起来成功、实则残缺"的内存清单；重复调用（kmain 再存一次）有幂等守卫，只落地一次。

修复的判据也是"回到源头看输入"：落地后，`classify` 时刻的 memmap 恢复成十几条真实范围，`vm_handoff free n` 从 0 变成正常条数，VM 拿到空闲页、不再于诞生前 panic，boot 一路越过启动期服务、抵达运行期进程诞生。

这个修复的通用形态，其实本仓库在更早的 `reserved_regions` 上已经用过一次（`RESERVED_REGION_STORE`）。memmap 与 boot 模块表是同一病灶上晚被发现的两处漏网，最终一并纳入同一套 landing pad 纪律。

## 6. 抽象成一条可复用的原则

把上面还原成脱离本仓库也成立的判断：

> 在"页表说了算"的裸机/内核环境里，`&'static` 只保证**不被分配器回收**，**不保证**跨页表切换后该虚拟地址仍映射到同一份物理内容。任何在 boot 阶段（固件 / shim / 临时 boot 页表之下）产生、却需要活到内核运行期的数据，都必须在页表交接前落地到内核镜像自身会映射的段里，否则它的物理页随时会被回收复用。

由此推出两条排查纪律：

- **症状层**：这类故障表现为"某个数据在流程早期还正确、晚期变零/变垃圾"，且常常"结构还在、payload 没了"的不对称。见到这种渐进式、部分幸存的腐化，第一反应应是"它的地址是不是跨了页表边界"，而不是"谁把它写坏了"。
- **归因层**：当"算法给出的结果荒谬"时，先用探针在算法入口打印它真正收到的输入。区分"计算错"还是"输入已经空"，靠的是回源验真值这一个动作，而不是继续盯着算法看。

## 7. 跨系统对照：别人怎么躲开这个坑

这不是本仓库独有的陷阱，而是所有"从固件手里接内存信息"的内核都要正面处理的问题，各家的解法与 landing pad 的思路同构：

- **Minix3（C 基准）**：内核在 boot 期就把物理内存布局接进自己的固定数据结构里，之后所有分配都以内核自有结构为准，不去长期依赖 boot 期临时缓冲。
- **Linux**：UEFI 交下来的 EFI memory map 会被早期解析、拷进内核自管的 `memblock`/`e820` 保留布局；`early_iomap`/`early_memremap` 这类"早期临时映射"有明确的"用完即弃"契约——固件提供的东西绝不当作长期可寻址内存。UEFI 甚至要求调用 `ExitBootServices`：一调用，Boot Services 的代码与内存池区就不再受保护、随时可被内核征用，这与本文"固件池撑不过 boot"是同一条硬事实。
- **Redox**：boot 期从固件（multiboot / UEFI）拿到的内存图，被尽早搬进内核自己映射的 `BootInfo` 结构里，内核全程只读这份搬过的副本，不保留对固件原始缓冲的长期引用。

三家的共同选择，都是**"在交接点把易失的固件数据搬到内核永久映射的结构上"**——这正是本文的 landing pad。差别只在搬到哪、用多大的固定容量。理解了这个共性，本仓库的修法就不是一次孤立的补丁，而是对齐了所有内核都必须遵守的一条启动期铁律。
