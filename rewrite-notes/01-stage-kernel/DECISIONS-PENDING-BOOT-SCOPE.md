# 待裁决：boot 语义边界——恒等映射覆盖与"谁建根/谁开分页"（自包含版）

> 日期：2026-11-09 立档。预计 R23 结束后裁决；**裁决流程有界：一轮代码核实 + 至多一轮第三方意见 + 用户裁决，不做多轮设计轮**（理由见 §7）。
> 性质：这是真分歧（两个方向都自洽），不是执行欠账；但它**不是**开放性设计探索——相邻决策已全部冻结（§5），自由度只剩一个维度。

## 0. 裁决原则（用户原话，作为决策判据记录）

1. **KISS**：ELF 的逻辑边界要清晰。不能指望 boot 逐渐膨胀成一个小 OS。
2. **叙事一致性 = 架构演进纪律**：读者在 Ch1/2 学到的是"boot 完成加载、收集内存图、跳，全完事了"；如果 Ch3/4 与 Ch1/2 对不上，按项目约束这是**必须显式标注的 [ARCH] 架构演进**——静默的架构演进是不允许的。
3. （历史）用户早期曾提出"boot 只建最小页表（128–512MB 量级），工作归 kernel 语义"——**该意见在现有全部记录（设计快照 v1–v3、R13–R22 台账、两份裁决文档、I-29 简报）中零留痕**，属于被淹没的意见；本档即是把它立为正式裁决项，防再次淹没。

## 1. 术语（只列用到的）

- **恒等映射**：`VA = PA` 的低地址映射，切 CR3/satp 后让既有代码继续取指。当前覆盖**低 4GB 全铺**（x86_64：4×1GiB 叶；继承自 C `pg_identity` 的 1024×4MB）。
- **内核高半映射**：内核 ELF 链接在高 VMA（x86_64 `0xFFFF8000_0020_0000` 起），装载地址（LMA）在低位；boot 把 LMA 映射到 VMA，跳转后内核在高地址执行。
- **Direct Map（DM）**：一段固定虚拟窗口到物理地址的线性映射，建一次、覆盖窗口内全部物理内存、永不改。**已裁决归 kernel 建**（`establish_boot_dm`，加法式挂到活动根），不在本档射程内。
- **跨镜像腿 / 直核腿**：跨镜像 = boot-shim 装载独立 kernel.elf 并跳转（UEFI x86_64/aarch64、U-Boot riscv64）；直核 = kernel 镜像自带引导面（riscv64 `bootface`、aarch64 `bootface_a64`），**没有 boot-shim**。

## 2. 现状事实（逐项核实过，带出处）

| 分页工作 | 跨镜像腿谁建 | 直核腿谁建 | 状态 |
|---|---|---|---|
| 恒等映射（低 4GB 全铺） | boot-shim（Step 1） | kernel（`arch_boot_impl` Step 1） | **本档争议点 1**：4GB 全铺是 C 继承，从未重新裁决 |
| 内核高半映射（LMA→VMA） | boot-shim（Step 2） | kernel（Step 2） | **本档争议点 2** |
| 设备窗口（Step 2b/2c） | boot-shim / kernel | kernel | 随争议点 1/2 走 |
| DM 覆盖 | **kernel**（接收侧 `establish_boot_dm`，加法式） | kernel（Step 4） | **已定，不在射程** |
| 分页开启（写 CR3/satp） | boot-shim（跳高入口前） | kernel | 随争议点 2 走 |

- 直核腿（5 条入口中的 2 条）**已经完全符合用户原则**：没有 boot-shim，kernel 自建一切——这是"kernel 建全部"可行性的**在仓实证**（`arch_boot_impl` 就是实现，三架构 QEMU 门在跑）。
- 争议只剩**三条跨镜像腿**：boot-shim 目前建"4GB 恒等 + 内核高半"，并开启分页，然后跳**高地址入口**。
- 4GB 全铺的现行理由（Step 1 注释）：UEFI loader 的代码/数据可能落在低 4GB 任意处，不覆盖则切表后取指失败。另一相关事实：R22 已把"shim 镜像 <4GiB 无守护前提"登记为 P2 观察（§6.3 有行）。

## 3. 裁决问题（唯一决策，两个半选项）

**唯一决策**：三条跨镜像腿上，"恒等映射 + 内核高半 + 分页开启"由谁建、恒等覆盖多大。

### 选项 2a：boot-shim 建**最小窗口**，跳高入口不变

boot-shim 只映射：自己的 footprint（LoadedImage 协议可得）+ 内核 LMA 跨度（ELF 程序头算出）+ arena（shim 自己分配，可控制落点在窗口内）+ 栈。128–512MB 量级。跳高入口、wire、接收侧 additive 全部不变；kernel 继续建 DM。

- 收益：boot 语义最小化（KISS）；**fail-fast**——未映射区的野访问变成页错误（现状 4GB 全铺是 PRESENT，野指针读设备空洞得静默垃圾，C 时代只缓解缓存污染）；Ch1/2 叙事与 Ch3/4 的差距缩小（boot 建的表"小到可以一句话说完"）。
- 代价/风险：窗口内容的**完备性**靠 shim 自己清点（漏一项 = 难查的 boot fault）；恒等映射的 C 继承语义被打破（需 [ARCH] 标注）。

### 选项 2b：五腿统一直核模式——boot 只 load + 交接 + 跳**低入口**，kernel 建全部

boot-shim 退化为纯装载器（读文件、EBS 拿内存图、写 arena、跳 kernel 低入口）；kernel 的 `arch_boot_impl` 建全部（恒等——此时恒等的必要性由 kernel 自己决策、内核高半、DM），然后自行切高半。Ch1/2 叙事与实现**完全一致**："boot 完成加载、收集、跳，全完事了"。

- 收益：boot 语义最小化到极致（KISS 的完全形态）；五腿统一在一个模式上（直核腿已经这么干了）；**分页的全部语义归 kernel**——"内核映射由 VM 重建"在 C 里是 kernel 接管分页的实例，2b 把这个 Minix3 哲学在 Rust 侧找回来了。
- 代价/风险：**x86_64 低入口是新机制**——kernel.elf 链接在高 VMA，需要一个低地址入口 stub（新 section、新跳转路径），riscv64（medany）/aarch64 有直核腿实证，x86_64 没有；additive-resume 合同（D2-07 刚合并的 `resume_additive`）为 UEFI 腿重构为"kernel 自建"；LMA 预订（A+D）的时点与归属重审。

### 选项 2c：现状（4GB 全铺 + boot 建高半）

零改动。代价：boot 语义扩大化固化；Ch1/2 与 Ch3/4 的叙事差距永久存在（需 [ARCH] 显式标注一次了结）；4GB 全铺的静默垃圾访问永久保留。

## 5. 裁决流程（2026-11-09 用户修订：不设轮次上限，锚定问题域）

> 用户修订：上一版的"轮次上限 + 第三方降为挑漏者"过严——**10+ 轮的讨论是允许的，只要能产出更优美的设计**。真正的边界不是轮数，是**问题域**：严格遵守 Minix3 的语义，不肆意扩大化。本项目的既有实践与此一致：偏离 Minix3 语义的地方（独立镜像、wire 协议、DM 窗口模型）都有明确的 [ARCH] 理由在案——"偏离需明确理由"是长期纪律，"轮数"不是。

1. **问题域锚**：本档的问题域 = **boot 的分页职责边界**（恒等映射的覆盖与归属、内核高半映射的建立者、分页开启的时点）。锚 = Minix3 的 boot/prot_init 分工哲学（boot 表是脚手架、kernel 接管分页——`prot_init` 重建在案，01 篇行 1132）。
2. **域内自由**：轮次不设上限。新方案、新约束、对既有选项的实质改进，只要落在问题域内（或以明确理由合法偏离 Minix3 语义），都是有效产出。第三方是**完整的共同设计者**，不是挑漏者——前几轮的 Storage/Report 拆分、内核侧 `.bss` 例外、生命周期三段序，都是共同设计的有效产出。
3. **域外即出界**（两类，同等处理）：
   - 引入 Minix3 语义与已记录项目理由都支撑不了的约束（例如"为了 X 必须要求 bootloader 换内存图交接方式"——I-29 已裁决不要求）；
   - 重开已冻结项（DM 归属、wire 格式、BootStorage 形状、五腿存在性）而无新事实。
4. **事实纪律不变**：容量以 `size_of`/编译期断言为准；证据可重放；冻结项重开需新事实。
5. **终止条件**：连续一轮讨论无新增设计增量（无新约束、无新方案、无对旧方案的实质改进）→ 提交用户裁决。
6. **实施**：按裁决落码；2a/2b 的 [ARCH] 标注与 Ch1/2 叙事回填同批完成。

## 7. 主 agent 倾向（供用户参考；非裁决）

倾向 **2b**，理由：它是唯一让 Ch1/2 叙事与实现**完全一致**的选项（你的第二判据"静默 [ARCH] 不允许"只有 2b 能彻底满足）；直核腿已经证明 kernel 建全部可行；boot-shim 缩成纯装载器后，五腿的"boot 职责"终于统一为一句话。2a 是低风险妥协，但"boot 建页表"的语义残留仍在，Ch1/2 与 Ch3/4 的差距只是缩小不是消失。

**但 2b 有一个必须先核实的硬风险**：x86_64 低入口 stub（riscv64/aarch64 有直核腿实证，x86_64 没有）——这正是 §5 第 1 步要核实的事实，也是本档不需要多轮设计讨论的原因：**唯一的不确定性是工程量核实，不是方向之争**。

同时如实记录你的观察：前几轮（D-1 三轮、D-2 容量辩论）确实发生了扩大化——根因是"评审开放式提案"的框架；本档改用"bounded 问题 + 不在射程清单 + 轮次上限"的框架，这是对扩大化倾向的制度性回应。
