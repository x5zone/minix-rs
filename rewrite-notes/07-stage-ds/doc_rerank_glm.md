## 1. C 真序

### 1.1 阶段类型判定

**服务事件循环型**（本 stage 主体）：DS 是单线程查表服务器，一生 = 启动（注册回调、初始化表、登记 boot 服务）+ 主循环（收信、分派、处理、回信）。按 R 相提示词 §九的服务事件循环型模板组织：服务为什么存在 → 诞生与初始化 → 消息接口 → 核心数据结构 → 按场景分组的请求处理 → 查询与杂项 → 与邻接服务的协议。

**附带集合型特征**（次级）：客户端库 `libsys/ds.c` 是 15 个公开函数的集合（三种打包形状），按"统一框架（`do_invoke_ds`）+ 形状分组 + 代表成员"组织（归 12 篇）。

判定依据：`servers/ds/main.c:42` `while (TRUE)` 事件循环；无自有汇编入口、无链接脚本、不管理硬件。

### 4.1 总判决与理由

**编号 00-12 与 99 全部保持不变；新建 13 一篇；00 与 99 从骨架重写为正文；01-12 按本蓝图契约重建正文（编号、标题语义、边界均不变）。** 不做任何重排、拆分、合并、归档。

理由（三条，均带证据）：

1. **现目录的骨架是对的。** 01-12 的顺序 = 协议 → 数据模型 → 存储原语 → 身份权限 → 初始化 → 写 → 读 → 删 → 订阅 → 镜像 → 客户端，与 R 相提示词 §九服务事件循环型模板逐项对得上（§1.1 判定）；边界声明（每篇"不讲什么/去向"）完整；主讲述点无冲突（§3.3 九条重复里没有一条需要挪篇解决）。真正的病是：**00/99 两篇是占位骨架**、**若干事实已随 2026-09-15 执行轮过时**（§3.2 G1-G11）、**测试与验证面无归属**。这些病的治法是补全与勘误，不是重排。
2. **重排的断链成本在这里不成比例。** 本 stage 被外部引用 52 处（8 个其它 stage 的正式文档 + edge 材料，§8.2），stage 内互引 57 处，代码注释 15 处。重排（例如把通知环从 10 拆出提前）能换来的只是省掉三句"一句自足定义"的补偿（§4.3 D2），却要让 100+ 处引用全部迁移——这正是 01-stage-kernel todo I-14"重编号断链风险大于收益"裁决的同型场景。
3. **只有一处结构性缺口，用追加解决。** 测试与验证面（C 契约、Rust 地图、联调出口）横切全部 handler，塞进任何一篇都违反单篇单语义；13 号空着，追加 `13-ds-verification.md` 零重编号成本。
