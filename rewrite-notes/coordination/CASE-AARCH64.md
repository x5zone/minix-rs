# aarch64 案卷归并

## 一、向量寄存器与巨量分配失败案（已定谳）

**现象（精确）**：aarch64 单进程形态启动（`-smp 1` 也复现）跑到最后阶段确定性崩溃。十二个系统服务器与初始化进程都换装成功，初始化进程进入运行登录脚本的状态，派生并换装出第一个子进程（进程表槽位十二、端点 `0x800c`）；该子进程在启动早期请求一次约四吉比特的堆（长度读数 `0x7ffffffe25c0`，低三十二位 `fffe25c0`），运行时分配器拿不到这么大的堆返回空指针，解引用空指针收到段错误（串口证据 `csig tgt=0xc sig=0xb`），全系统转入空闲，登录标记永不打印。

**关键放大事实**：同一条调用链在 x86_64 上正常——共享的初始化进程源码在 x86_64 单核构建里能一路跑到登录标记、零恐慌；只有 aarch64 的"派生加换装"子进程里出现"把一个栈地址当容量"的读数。这把嫌疑锁定在 aarch64 专属的架构层差异（子进程初始栈、寄存器状态、换装栈镜像布局），而不是共享逻辑。

**定谳的机制**：不在换装栈镜像的字节布局里（那部分两架构逐字节同构），而在**寄存器组保存与恢复的不对称**上。x86_64 把"用户起源的中断必须先保存完整寄存器组，再运行任何调度策略"当作承重不变量（有真机前科与修复记录），aarch64 的同位腿当时没有这道保存。于是恢复时用的是上一次陷入时存下的陈旧寄存器组，其中被调用者保存的寄存器里装着栈上对象地址，活代码把这个陈旧值当长度或容量使用。

**已证伪的假设（不得重提）**：

| 曾提出的假设 | 证伪方式 |
|---|---|
| 发送方消息类型字段跨陷入未物化（编译器级易观测缺陷） | 加易失读屏障后该类读数归零并已修；与本缺陷无关 |
| 派生时父子共享或复用陈旧投递物理页 | 用物理地址对比针排除 |
| 内核延迟投递把"非法消息类型加携带初始化进程栈指针的高位字"写进初始化进程栈、再经写时复制遗传给子进程 | 静态证伪：探针读的那个偏移七十二大于消息体尺寸六十四，是**越界读到了紧邻的内核字段**（那里本就存着用户栈指针）；进程管理的回复正文实为全零。因果链失去支柱 |
| 毒值来自初始化进程的读文件路径 | 用户侧地址探针在崩溃前从未触发，说明该路径根本没被调用 |
| 毒值来自组装换装栈帧时的越界相加 | 该路径全程用带上溢检查的加法并在超限时提前返回错误码，超大长度会先返回错误而不是把毒值递进分配器；且该错误是优雅报错不是段错误 |
| 毒值来自运行时出生例程读参数与环境变量数组 | 那里按终止字节扫描计长，不做指针相减，产不出栈地址量级的长度 |
| 换装参数描述符的计数字段装下了栈指针 | 计数字段是三十二位有符号且入口校验拒绝负数：完整的六十四位栈指针落进该槽会因最高位为一呈负数被拒，产不出"正的大计数" |
| 换装栈顶落位不一致 | 栈顶三处常量一致（内核信息页、调用者算帧内指针、运行时消费端同值），帧落位与帧内指针不会错位 |
| 归因于多核竞态 | 单核也复现，排除 |

**残余的两个候选（当时未定谳，后续各自处置）**：换装初始栈指针的十六字节对齐差（低置信，更像放大器——只有 x86_64 的入口桩自我修正对齐，见 `TODO-LEDGER-OPEN.md` §1）；崩溃映像归属未定（毒值可能在换装之后的 shell 里，符号对账无法区分共享库代码，属定位前置）。

**会再次绊倒人的坑（原文保留，这是本卷的肌肉记忆部分）**：

- **消息体只有六十四字节、八个字**。任何"消息高位字、第九个字、偏移七十二"式读数都是**越界读到相邻内核字段**——上面那条最费时的误判就栽在这（进程表里投递消息紧跟着投递消息的虚拟地址字段，后者存的正是用户栈指针，看起来极像"消息里回音了栈地址"）。核对字段一律以消息体尺寸的编译期值为硬上界。
- **发布构建省略帧指针、泛型增长函数高度内联**：靠扫栈或返回地址链追调用者很可能够不到应用帧；本机反汇编工具还不认 aarch64。别把"扫不到"当成"不存在"。
- **替身特性与测试门控**：诊断分支在某个构建里可能被整段编译剪除，"零次命中"最便宜的解释往往是"代码根本没编进去"，不是"逻辑没走到"。
- **镜像新鲜度**：任何结论必须建立在从当前源码树当场重建的二进制上；用旧镜像跑出的证据一律作废。
- **易观测缺陷陷阱**：探针自身的串口打印会改变时序与寄存器分配，让缺陷时隐时现。判据要两次独立复跑且签名一致。

## 二、执行换根活锁案（已结案）

**本质矛盾一句话**：进程换装上新程序，虚存服务为它建了全新页表，内核却仍拿**旧页表根**去翻译这个进程的虚拟地址。于是该进程每取一条指令都命中"页不存在"，内核向虚存服务要页，虚存服务诚实地把页映射进**新根**并回答成功，中央处理器下次翻译走的还是旧根——同一地址、同一失败、无休止。这是活锁而不是崩溃：系统在不停地"处理"，每一方都在正确地做自己该做的事，却因为一份关键元数据没有同步而永远走不出同一个循环。它会安静地把同一个错误重复七万多次。

**根因**：换装时虚拟文件系统向虚存服务发"清空参数"请求，处理序列对位 C 的清理流程——释放旧地址空间的物理页、清空区域表、销毁旧页表、建立全新页表。页表根此时已从旧根变成新根。**C 的序列在这之后还有最后一步：把新根登记给内核；这条腿恰恰漏了它。** 旧代码还留了一段注释，声称架构层的绑定辅助是"经过验证的空操作"、内核侧登记"由虚存控制通道承载"——没有任何人会在这条路径上发送那条通知。

结果：虚存服务把新镜像映射进新根；内核的段表里的物理根仍停在刚被拆掉的旧根；子进程被调度取指，中央处理器用旧根翻译，页不存在，请求发给虚存服务，虚存服务在新根里映射好并回答成功，重试取指仍走旧根。循环闭合。

**旁证（最强的定位信号）**：同一代码库里另外两条会换页表根的路径——派生子进程后、引导装机时——**都在换根后补发了登记调用**。同一条铁律被遵守了两次、遗漏了一次；"实现不一致"本身就是线索。

**为什么难定位（四层缠绕，每层都是方法教训）**：

1. **换装本身"成功"了**。系统调用返回成功、内存请求回答成功、没有恐慌，所有显性健康指标都是绿的。缺陷藏在不体现在返回值里的元数据同步上——只会盯错误码的排查方法对它完全无从下手。
2. **两个独立失败模式被搅在一起**。当时同时存在本案的确定活锁与第一案的偶发巨量分配失败，两者叠在同一条启动路径上，一个的现场遮盖另一个；且根因彼此独立——修好活锁，分配失败依旧存在，不会"顺手一起好"。
3. **日志本身的陷阱**。含空字节的串口原始流若按默认"二进制安全"方式搜索，命中行会被整段跳过给出假阴性。硬规则：这类日志强制按文本处理，断言"零次"之前必须用显式计数反向复核。
4. **一个"回归"其实是幽灵**。补丁装上后有报告说 x86_64 随即在内核异常分发处触发了页错误异常，看起来像"这个修复把 x86_64 弄崩了"，几乎要推翻整个修复方向。接手者亲手在单核下复现：连跑四轮一次都没出现，登录标记照常打印。追查发现那份报告很可能在多核配置下跑，撞上了与本案完全无关的、早已知的多核早期启动崩溃。

**可迁移的经验清单（七条，原文保留）**：

1. "运行行为异常"比"返回码异常"更早暴露真相：每步都成功却原地打转的系统，错误信息永远为零。要主动看重复模式（同一地址或请求被处理了多少次），而不是只等恐慌。
2. "某个平台跑通了"不等于"逻辑是对的"。本例 x86_64 之所以看起来正常，是因为页表帧分配器恰好把刚释放的物理页立即复用给新根，把错误藏进了实现细节。以架构无关的代码事实为准。
3. 把纠缠的现象拆成独立可证伪的失败模式，分别归因；修好一个不要臆想另一个会一起好。
4. 换根、换元数据这类"两个持有者之间的同步"，要逐条腿核对完整性；同一条不变量实现得不一致，本身就是最强定位信号。
5. 任何外部转来的"你引入了回归"，先亲手在等价条件下复现再下结论。另外立一条铁律：**x86_64 的验证必须在单核下做**。
6. 含空字节的日志搜索强制按文本处理；断言"零命中"前必反向计数复核。
7. 对会"悄悄烂掉"的元数据同步，选择失败闭合而非吞错。C 语言原型丢弃绑定调用的返回值，正是这类缺陷得以藏身的温床；把静默失败改成立即报错，是把疑难杂症转化为可诊断故障的通用手段。

**修复的形态与安全性论证**：在换装清理腿的末尾补发那次登记调用。两个架构都安全的理由是——新根在被登记给内核之前，其内核映射部分已经就位，因此内核不会在自己的地址空间里缺页；这一点在第一案里也独立成立（换装镜像的字节布局两架构同构）。
