# 陷入边界上的陈旧消息：一个跨内核与用户态的寄存器 Heisenbug

> 一个 aarch64 启动死锁，追查十二轮后发现的根因既不在内核，也不在用户程序，
> 而在两者之间那道由汇编指令构成的边界上：用户程序写入消息的 CPU 寄存器，
> 在内核读取消息的时刻还没有落到内存里。

---

## 1. 一个数字改变引起的死锁

Minix-RS 是一个用 Rust 重写 Minix3 微内核操作系统的项目（x86_64/aarch64/riscv64，
`#![no_std]`）。它遵循 Minix3 的微观结构：进程管理、虚拟内存、文件系统、调度器都
运行在用户态服务器上，内核只做 IPC、中断和最小级的内存管理。服务器之间、服务器
与内核之间的一切协作都靠一种定长的消息结构传递。

2026 年 9 月，aarch64 分支卡在一个可复现的死锁上。启动过程推进得比以往任何时候
都远：内核完成自举，十二个系统服务器全部成功装载运行，初始化进程 init 也进入了
运行用户登录脚本的阶段。然后整个系统静止——串口日志冻结在四千余行不再增长，
既不崩溃也不前进。

死锁现场里有两个受害者。init 进程用 `fork` 调用创建了一个待运行用户登录脚本的
子进程；子进程诞生之后，状态标记为"正在等待接收一条 IPC 回复"加"没有调度配额"
（`RECEIVING|NO_QUANTUM`），这两个标记永远不会被清除。init 则阻塞在等待子进程
退出的调用上，陪葬地一起永不推进。

子进程缺的调度配额，要由用户态调度器 SCHED 发放。SCHED 为什么不发？因为它从未
登记过这个子进程。SCHED 为什么从未登记？因为它收到过一条关于这个子进程的申请，
却把申请拒绝了。拒绝的理由是：申请消息的类型字段是 0，不在任何已知请求的取值
范围内。

而发送方进程管理器 PM 发誓自己写的是 `0xF02`。

这就是整个案件的核心矛盾：**同一条 IPC 消息，发送方写入的 m_type 值是 0xF02，
接收方读到的值是 0**。消息在从一个用户进程的内存走到另一个用户进程的内存这条
路上，类型字段被清零了。下面会看到，真正的案发现场比"路上丢失"更离奇：值甚至
没有离开过发送方自己那半边。

## 2. 这类 bug 的本质：同一块内存，三个不一致的世界

要理解这个缺陷，需要先建立一个心智模型。在微内核系统里，IPC 消息不是普通的函数
参数——它是**一块内存加上一个地址**。发送方把自己栈上的一个结构体的地址交给内核，
内核穿过一道汇编陷入边界，按这个地址去读发送方内存里的字节。

于是同一块内存同时活在三个世界里：

1. **程序员看到的世界**：`msg.m_type = 0xF02;` 写完之后，任何人来读这个字段都
   应该得到 0xF02。这是源代码语言（无论 C 还是 Rust）承诺的顺序一致性。
2. **编译器看到的世界**：赋值不必真的写内存。如果编译器判断"这个变量接下来的
   使用还在本函数内、没人能从别处观察到我"，它允许把值留在 CPU 寄存器里，把
   写内存的指令推迟甚至合并掉。这是抽象机语义允许的自由。
3. **内核看到的世界**：内核在陷入之后，按用户给来的地址做内存读。它读到的是
   物理内存（或映射后的虚拟内存）此刻真实的字节。

如果这三者只靠语言的承诺衔接，缺陷就出现了：世界 2 到世界 1 的翻译，由编译器
单方面决定；而世界 3 的观察者是**编译器看不见的人**。当内核隔着陷入边界伸手
读那块内存时，它读到的是世界 2 选择提交的状态——可能还是旧值，可能还是零。

这个缺陷家族在系统软件里有一个实验学名的俗称：Heisenbug——观测行为本身改变
被测行为的 bug。它的三大发作条件在本案例中全部凑齐：

- **优化构建**：只有 `-O2` 级别的寄存器分配和写合并才会让 store（写内存指令）
  滞留；调试构建里每条赋值都立刻落内存，缺陷消失。
- **跨界观察**：必须有一个编译器建模不到的观察者（内核）按地址读这块内存。
- **时序运气**：值是否滞留取决于寄存器压力和指令调度，函数里多加一条打印语句、
  换一个调用点，行为就翻转。这导致它看起来"架构相关"——aarch64 每次都发作，
  x86 每次都不发作，但两者其实都站在悬崖边。

## 3. 机制细节：从 API 形状到缺陷的必然

### 3.1 内核按地址间接读消息

Minix-RS 的 IPC 原语把消息以指针传递。发送一条请求的形式是：把本地消息缓冲区
的地址转成整数，连同目标端点一起交给陷入指令。见
[`os/libs/minix-sys/src/ipc.rs::DirectTrapTransport::send`]：

```rust
let (ret, _status) = unsafe {
    crate::arch_trap::ipc_trap(
        crate::arch_trap::SEND_NR,
        destination.0 as usize,
        (message as *const Message) as usize,   // 地址，不是内容
    )
};
```

陷入指令本身（aarch64 上是 `svc #0`，见
[`os/libs/minix-sys/src/arch_trap.rs::ipc_trap`]）把参数放进寄存器后执行特权级
切换。内核态的处理例程拿到这个地址，在发送者的地址空间里**读内存**取得消息内容，
再投递给接收者。

关键就在"读内存"三个字：内核信任的是那块地址此刻的字节，而不是发送方源代码
逻辑上的最后一次赋值。

### 3.2 编译器为什么敢让写滞留

本案的发送方不是手写赋值，而是一个通用小函数——PM 登记调度器的请求最终走到
[`os/libs/minix-sys/src/syscall.rs::perform_taskcall`]，它的函数体只有几步：
先给消息类型字段赋值，紧接着把同一个消息缓冲的地址交给 `sendrec` 陷入内核：

```rust
pub fn perform_taskcall(
    transport: &impl IpcTransport,
    destination: Endpoint,
    call_number: i32,
    message: &mut Message,
) -> Result<i32, Errno> {
    message.m_type = call_number;                              // 最后一次标量 store
    if let Err(status) = transport.sendrec(destination, message) { // 地址转整数、陷入
        return Err(Errno::from_i32(status.0));
    }
    Ok(message.m_type)
}
```

赋值（把 `SCHEDULING_START`，即 0xF02，定义对照 Minix3 C 的
`minix3/minix/include/minix/com.h:804`）与陷入只隔一行，`message` 是同一个
`&mut` 缓冲。这正是缺陷最锋利的形状：写和读只隔着一次编译器完全不建模的陷入。

在编译器的中间表示里，这条赋值是一条对"本地栈槽"的 store。栈槽的地址虽然被
转成了整数传进汇编块，但**指针一旦被 `as *const _ as usize` 转换，就脱离了
编译器指针别名模型的追踪范围**。对编译器而言，那段内联汇编只是"使用了一个整数
寄存器"，它不知道这个整数将被另一个特权级的代码当作地址去解引用该栈槽。于是
赋值产生的 store 可以合法地滞留：只要在本函数后续没有再从这个地址读的指令，
编译器就认为"晚点写"甚至"合并进后续某次写"都可以。

于是出现了这样的时刻表：

```text
时刻 T1（用户态）  store m_type, 0xF02  → 可能只落到寄存器
时刻 T2（陷入）    svc #0               → 进入内核
时刻 T3（内核态）  按 T2 交来的地址 load → 读到旧值 0
时刻 T4（内核态）  把 0 转发给接收者    → 接收者按"未知类型"拒绝
时刻 T5（之后）    滞留的 store 终于落内存 → 但没人会再去读它
```

### 3.3 Rust 的类型系统为什么拦不住

一个自然的疑问：Rust 不是以类型安全著称吗？为什么编译器不把"传了指针"识别成
逃逸？原因在于 IPC 原语的边界形状。消息指针在进入汇编之前被转成了 `usize`，
这是任何语言里最彻底的"模型盲区开关"——`usize` 不是引用、不是指针类型，编译器的
借用分析和副作用分析都不把它与任何内存关联。`unsafe` 块正确表达了"这里的约定
由人负责"，但编译器能帮忙的部分到此为止。换句话说：**只要 API 用"地址当整数
传过不透明的汇编边界"这个形状，同一块内存在语言层面就同时存在两个互相看不见
的观察者。**

### 3.4 一个补充因素：内核的双次读取

本案还有一个放大复杂度的细节。内核的发送处理腿不是只在陷入那一刻读一次消息：
为了在缺页恢复等路径上拿到新鲜内容，它在投递前会**再次按同一地址读取**
（对位 Minix3 的语义，接收方从自己缓冲取消息见
`minix3/minix/servers/sched/main.c:42` `call_nr = m_in.m_type;` 这一端的对称
关系）。双次读取把"读到陈旧值"的概率窗口扩大了：第一次读可能恰好撞上已提交的
值，第二次读却可能读到被后续写入污染的中间态。追捕过程中一度据此怀疑"地址
翻译错页"，后来用三方对照探针排除了那条路（见 §5）。

## 4. 十二轮追捕：每个阶段都"证明"过一次根因

这个缺陷不是一眼看出来的。它被十七个取证/修复轮次层层剥开，每一轮都用真机
证据杀死一个假根因，同时又给下一轮留下一个更精确的疑点。完整记录在
`rewrite-notes/coordination/NK4C-WORKLOG.md`（§1.119续-7 至 §1.120续-22）。
这里提取对读者有价值的脉络。

### 4.1 第一层假象：错误码与"消息没送到"

最早的现场是：init 向文件系统 VFS 发出的路径查询请求，连续收到五个 EBADF、
一个 ENOENT 的回复，然后往返停摆。当时自然怀疑 VFS 的回复投递腿丢失、或回复
落错槽——这是本项目 IPC 层反复出问题的一个家族。装在内核 IPC 两条腿上的探针
证明了相反的事实：回复确实发了、地址槽解析也正确。停摆的真身挪到了"为什么
请求被拒绝"。

### 4.2 第二层：三个真实的公共层缺陷，但不是主死锁

追捕过程中顺藤摸瓜修掉了三个货真价实的 P0 缺陷，每一个都值得单独记录：

- **零长度拷贝缺前置检查**（§1.120续-5）：内核的跨空间拷贝把"字节数为零"的
  检查排在页表解析之后，导致一个零字节请求带着悬垂地址挂起，最终把文件系统
  服务器炸成段错误。Minix3 的 C 真值把这条检查放在一切地址工作之前
  （内核各 system call 处理腿共用的 `virtual_copy_f`，见
  `minix3/minix/kernel/arch/i386/memory.c:608` 第一条即 `bytes <= 0 → EDOM`）。
  修复按 C 语义前置。
- **窗口满排队的请求无人补发**（§1.120续-6）：VFS 对每台文件系统服务器有
  一个请求窗口；窗口满时新请求进入排队腿，但 C 主循环里负责把排队请求补发出去
  的 `send_work()`（`minix3/minix/servers/vfs/main.c:69-72`）在 Rust 重写中
  只剩排队腿、补发原语没有生产调用方。后果是并发请求一旦重叠，第二条永远
  沉睡。修复是八行接线。
- **回复腿的阻塞与非阻塞之分**（§1.120续-7）：VFS 回复 PM 的那条腿在 C 里是
  阻塞发送加失败即 panic（`minix3/minix/servers/vfs/main.c:912-915`），Rust
  重写时把所有回复统一成了非阻塞发送，把"对端还没到达接收点"的竞态窗口
  交给了调度时序。修复按 C 分叉回两态。

三个修复都让启动过程走得更远，但四千行冻结点始终未破。它们的作用是**排干
了外围的水**，让真正的堤坝缺口露出来。

### 4.3 第三层：PM 发往 SCHED 的申请被 SCHED 用 ENOSYS 拒绝

焦点收敛到一条消息：PM 在启动早期向 SCHED 发出"为 init 启动调度器"的申请。
SCHED 的处理腿对无法识别的消息类型回 ENOSYS（"没有这个服务"）。真机探针抓到
这个 ENOSYS 恰好出现一次，与死锁签名严格对应。往前追：SCHED 的 `from_raw`
判别拿到的类型值无法映射到任何已知请求。再往前：PM 侧发出的类型值在源代码
里是写死的常量 0xF02，且同一条链路上消息的其余字段在接收侧看来时好时坏。

### 4.4 一个插曲：探针把自己骗了一次

中间一轮，调度器专用探针报告"净态下 SCHED 收到零条继承申请"，据此得出的结论
一度被写成定谳。下一轮复核发现：装载该探针的构建配置带 `mock` 特性，
`#[cfg(not(test))]` 一类门控的探针代码**被编译器整段剪除**——"零条"不是消息
没到，是针根本没装。同一轮还确认了另两个取证方法学陷阱：取证所依赖的镜像必须
当场从当前源码树重建（曾有一轮结论建立在旧二进制上），以及探针自身的串口打印
会改变时序（后来改用"内存记录、停机时统一转储"的零扰动方式）。这三条教训被
固化成了项目的探针纪律。

### 4.5 第四层：排除地址翻译，锁进编译器

余下的最后一个强候选是"内核按错误物理地址读"。判别探针同时读取三个来源：
CPU 的活页表基址寄存器、进程表里登记的页表根、内存镜像里的软件备份，再把内核
译文得到的物理地址与直接映射窗口算出的地址逐位对照——三者完全一致，内核确实
在正确的地址上读到了错误的值。翻译嫌疑出局。

决定性的一步是一种在编译器缺陷取证里很经典的针法：把"读一次消息类型字段"的
探针函数标成**禁止内联**，让它的调用本身不改变寄存器分配，只是在陷入之前插入
一次对同一块内存的读取。这条针的效果等于把 §3.2 的时刻表里 T5 提前到 T1：
对滞留中的值做一次无害装载，会迫使编译器先把挂账的 store 落内存。真机结果——
插入这条针之后，0xF02 完整地到达了内核，启动第一次跨过继承登记走到了 shell
程序装载。同一次源码树的有针/无针对照，成了教科书式的定谳证据：

> 唯一成因是：发送方最后一次对 `m_type` 的标量赋值，在陷入指令执行时尚未物化
> 到内核所读的内存里。

## 5. 修复：一道"迫使编译器交还观察权"的屏障

### 5.1 修复的形状

修复加在 IPC 原语库与陷入的接缝处，见
[`os/libs/minix-sys/src/ipc.rs::commit_message_to_memory`]。原理是给消息缓冲区
补上一次编译器无法无视的观察：

```rust
unsafe fn commit_message_to_memory(message: *const Message) {
    let _ = unsafe { core::ptr::read_volatile(message) };
}
```

`read_volatile` 对整个消息对象（`Message` 是 `#[repr(C)]` 的定长结构，尺寸即
内核按该地址读取的窗口）做一次"不可省略、不可重排"的读取，读取地址正是那个
整数转回的指针。编译器要让这次读取成立，就必须先保证该对象此前的所有待办
store 已经落到同一内存——这相当于替内核向编译器出示了一张"有人会来读"的证明。
读取结果本身丢弃，开销是一次寄存器装载。

### 5.2 插入点的选择标准

屏障只插在内核会"读消息内容"的三条腿上：`send`、`sendrec`、`sendnb`
（[`os/libs/minix-sys/src/ipc.rs::DirectTrapTransport`] 的三个实现，插入点均在
`ipc_trap` 调用之前一行）。不需要插的腿有明确的判别理由：

- `receive`：消息是流入方向，调用前缓冲区内容无意义；
- `notify`：参数只是端点编号，内核不读消息体；
- `senda`（异步发送）：发送语义经由另一条内核通道，当前构建形态下未命中
  该缺陷窗口（登记为开放项，见 §8）。

特性门控同样重要：屏障只在 `kernel_trap` 构建（真实陷入语义）且目标是
x86_64/aarch64 时编译——riscv64 的内核 IPC 腿尚未接入，不该假装防护；
宿主测试构建保持原有 `-EIO` 回退。

### 5.3 被考虑过而没有采用的方案

- **在内联汇编里声明 `options(log)` / clobber `memory`**：告诉编译器这段汇编
  读写全部内存，从而禁止任何跨越它的缓存与重排。被放弃的原因粒度过粗：
  一条系统调用的开销预算里，"禁止一切跨边界优化"比"提交一个已知对象"贵得
  多，且会影响同一汇编块承载的其他调用号。
- **让所有调用方自觉"写完后读一次"**：把义务摊给每个用户，必然有人忘。
  修复点选在 IPC 库的边界上，让契约只有一个执行者。
- **回到"按值传参"的 ABI**：从根上消灭"内核按用户地址间接读"（见 §6），
  但那是整个 IPC ABI 的重设计，属于架构演进级别的决定，不该由一个 bug 修复
  顺带通过。

## 6. 为什么 C 版 Minix3 没有这个问题，以及更大坐标系

### 6.1 C 为什么免疫

Minix3 的 C 用户在发送前同样只是"填结构体字段然后传地址"，为什么没发作？
因为 C 的跨界观察契约由 `volatile` 与编译单元边界共同兜底：内核侧的消息类型
判定、库侧的消息构造经由统一的 `message` 联合类型与 `_taskcall` 等非内联的
库函数，`static` 缓冲加显式赋值序列在 -O2 的 C 编译器实践里落内存的时机足够
早；更重要的是，Minix3 的 IPC 库在发送前会经历多次可观察的函数调用边界
（参数拷贝、断言），这些边界在实践上替它做了物化。这是一种**依赖实现惯例
而非语言保证**的免疫——换更激进的优化器，C 同样会翻车。Linux 内核的
`copy_from_user` 场景、以及所有 MMIO 寄存器必须 `volatile` 的历史教训，讲的
是同一件事：**凡是"编译器视角之外的观察者会按地址看你的内存"的边界，就必须
显式告诉编译器。**

### 6.2 其他系统怎么免疫

- **Linux**：系统调用参数走寄存器 ABI，内核需要大块数据时在系统调用内部用
  显式的 `copy_from_user` 拉取——拉取动作发生在内核的编译单元里，用户侧的
  值早在陷入之前就已提交（glibc 封装层不含让 store 滞留的路径，且内核侧
  copyin 有完整的内存序处理）。缺陷窗口窄得多。
- **Redox / seL4 / Fuchsia Zircon**：系统调用 ABI 直接传值或传小结构副本，
  共享内存交互被显式建模为"映射 + 内存序原语"，观察者的存在写进了类型。
  设计层面消灭了"语言看不见的那次读取"。
- **本项目的教训推广**：任何"把指针转成整数塞过汇编/FFI 边界"的 API，都
  应当为编译器提供一份物化证明——要么屏障在使用点，要么 ABI 按值。

## 7. 取证方法学：怎么逼一个 Heisenbug 现形

本案沉淀的几条可复用纪律（细节见 WORKLOG 对应轮次）：

1. **针必须零扰动**。探针自身的串口打印会改变时序与寄存器压力，让缺陷
   时隐时现。后期改用"探针只写内存槽位，系统在停机/超时路径统一转储"的
   方式，才拿到可信的净态数据。
2. **判别针的函数必须禁止内联**（`#[inline(never)]`），否则针本身被优化
   器揉进宿主函数，改变它要观测的那个分配。
3. **先核对镜像新鲜度**。每轮取证前从当前源码树重建全部构件；结论建立在
   旧二进制上时，一切"证据"都自动作废。
4. **核对探针是否真的被编译进去了**。特性门控（`cfg(feature = "mock")` 等）
   会在装载成功、运行静默之间制造完美假象："0 次命中"最便宜的解释往往
   是"针没装上"。
5. **多跑取签名，少跑看单次**。净态复验至少两次独立复跑、逐字节一致才算
   数；单跑通过可能是运气，单跑失败可能是扰动。
6. **用"无害装载反而修复了问题"这种反常信号追踪编译器成因**。当加一行
   与语义无关的读取能改变行为，嫌疑对象就不是协议逻辑，而是优化器的
   可见性模型。

### 8.2 为什么值得单独成文

这个缺陷的教学价值在于它同时踩中三条通常互不相干的线：微内核 IPC 的
"消息即内存"契约、现代编译器"未观察即不存在"的优化模型、以及多架构启动
时序的运气成分。它是"架构无关的代码为什么只在某个架构上发作"这个问题的
标准答案标本：不是 x86 免疫，是 x86 的寄存器分配运气好。任何一个用
`unsafe` 把指针转成整数塞过汇编边界的 Rust 系统程序员，都可能在未来某天
与它重逢——愿这篇文章是那天的路标。
