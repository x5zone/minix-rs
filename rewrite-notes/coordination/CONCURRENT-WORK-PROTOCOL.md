# 多人（多 agent）并发开发同一份代码库的工作协议

## 1. 这套协议要解决的矛盾

一个仓库、多个会话同时开工，而且这些会话**共享同一块磁盘、同一个 Git 工作树**。这不是分布式系统的经典并发问题——没有网络分区可以靠超时判定，也没有事务回滚可以用——它的困难全在三个具体事实里：

- **工作树是唯一的**。任何一次 `git checkout` 或 `git reset` 影响的不是某个会话的临时副本，而是所有人的共同现场。一个会话想换分支，其余会话尚未提交的修改就当场蒸发。
- **文件内容会互相覆盖**。两个会话各自整文件重写同一份待办清单，后写的那个会静默吃掉前一个的改动，而且双方都以为自己是唯一在写的人。
- **判断标准会过期**。待办清单里的行号锚点是扫描那一刻的快照；别人边改码你边读，读到的主张可能三分钟前就不成立了。

所以协议的全部目的一句话：**让并发的收益（多线同时推进）不换来串行的代价（丢工作、假完成、重复劳动）**。下面每一条都能回溯到这三个矛盾之一。

## 2. 所有权分线：把冲突面切到最小

并发之前先切地盘，而不是切任务。这个项目切成四条线，三条干活、一条只做编排：

| 线 | 领地（可独占修改的路径） | 职责 |
|---|---|---|
| 一线（内核面） | `os/kernel/`、`os/arch/`、`os/plat/`、`os/boot-shim/`、`os/qemu-tests/`、`rewrite-notes/01-stage-kernel/`、`rewrite-notes/00-master-plan/` | 内核、架构层、引导与真机测试面 |
| 二线（共享库面） | `os/libs/` 的逐个 crate 枚举、`os/drivers/`、`rewrite-notes/14-stage-runtime/`、`16-stage-drivers/` | 用户态运行时、库、驱动框架；是另外两线的**依赖下游汇聚点** |
| 三线（服务器面） | `os/servers/`、`os/fs/`、`os/net/`、`os/commands/`、`os/etc/`、`os/xtask/`、对应阶段文档 | 各服务、文件系统、网络、命令 |
| 编排线 | 不承载开发条目，只承载规则、锁、跨线状态板、验收阶梯 | 收敛所有人的进度，批量回写权威待办文件 |

三条经验值得单独记住：

**领地要枚举到具体路径，不能写目录通配。** 二线的所有权最初写成"`os/libs/`"，后来发现 `os/libs/minix-boot/` 这个引导契约库的唯一消费者全在一线（`boot-shim`、`kernel`、`arch`、`qemu-tests`），于是经编排线确权把它单独划给一线。目录通配会让人按名字猜归属，猜错就是跨界。

**跨界不是禁止，是先登记。** 清单外的触碰叫"跨界改点"，必须先在编排线的认领板上登记一行：哪条线、哪个条目、想干什么、预计碰哪几个文件。登记之后才许动，动完销账。同一个跨界改点同一时刻只允许一条线持有——这条规矩把"改别人的文件"这种危险动作，换成"在别人知情且让路的情况下改"这种安全动作。

**不许替别人实现他的前置。** A 条目依赖 B 线拥有的 C 条目时，正确做法是等或者先做别的；错误做法是"我看那行很简单，顺手替他改了"。顺手改出来的东西不在对方的验证链里，出了事没人认领。

## 3. 依赖等待与状态可见

条目前置属于别的线时，开工前先读对方文件里那一行的状态列。状态词只有五个，够表达"谁该动、动到哪、能不能接"：

- `☐` 未开工
- `🔄` 进行中（已领取，别人不要再碰）
- `⏸` 等待（必须注明等谁，否则等于隐藏的死锁）
- `✅` 完成（必须带日期与提交号，可复核）
- `🚫` 维持登记但不排期（承认这是缺口，并说明为什么现在不做）

这里有个后来被反复验证的设计取舍：**进度只记在线文件和编排板两处，绝不直接回写权威待办文件**。原因是权威待办文件（跨阶段的那份 `edge_todo.md`、以及每个阶段的 `todo.md`）是所有人共同的读入口，如果每个会话都往里写，写入就会互相覆盖；改成"各线自记 + 编排线在里程碑节点批量收敛"之后，写冲突从 N 个写者降到 1 个写者，代价是权威文件的状态会滞后一段时间——所以读它的人要养成看"最新进度注记"而不是看表头的习惯。

## 4. 领取锁与工作树：把纪律变成机制

这一条是整套协议里唯一用血换回来的。`2026-09-20` 的事故（编号 `C-35`）：一个会话在共享主树里切分支，直接销毁了另外两组尚未提交的在制品。同一天，作为纪律载体的脚本本身和一份线文件也处于未跟踪状态——也就是说，**用来防止丢东西的规则文件，差一点自己也丢了**。

事故之后，"靠自觉"的部分全部改成机制（`tools/claim.sh`）：

```
tools/claim.sh claim <条目ID> <owner>   # 领取：建 claim/<ID>-<owner> 分支 + 建 .wt/<id>-<owner>/ 专属工作树
tools/claim.sh verify                   # 自检位置：主树 → 警告；claim 分支 + 专属树 → 通过
tools/claim.sh list                     # 按日期列全部领取，最旧的那个就是可以回收的僵持条目
tools/claim.sh release <条目ID> <owner> # 销账：合入主线后删工作树；树里有未提交改动则拒绝
```

四条要点：

1. **分支名即排他锁**。`claim/<ID>-<owner>` 全局唯一，第二个人领同一个条目会直接失败，不需要谁去仲裁。工作树之间共享 refs，所以这把锁跨工作树有效。
2. **工作树即隔离壳**。领取之后，本会话只在自己那棵树里改码、构建、测试。共享主树里禁止 `checkout`、禁止 `reset --force`——那正是 `C-35` 的作案手法。
3. **文件头的规则是提示，分支才是锁，工作树才是壳**。写进文档的纪律谁都可能在忙的时候忘掉，而 Git 的分支冲突不会忘。凡是可以机制化的，就不要留在文字里。
4. **在制品即提交**。线文件和纪律载体每次更新后立即提交，不留长期脏状态，更不留未跟踪状态——未跟踪文件是一次 `reset --hard` 的零成本牺牲品。`claim.sh verify` 报出的未提交文件数，就是这个约定的自查信号。

真机验证是唯一必须串行的活动：所有会话共用同一块串口，判定靠抓串口标记，两个 QEMU 同时跑会互相污染读数。跑之前先确认没有别人在用（`claim.sh list` 加上直接问）。

## 5. 修复的三段式与"不许凭记忆改"

这套协议管的是并发，不替代修复本身的守则，两者叠加：

- **动手前读目标行上下各五行**，再用 grep 确认现状。禁止凭报告、凭记忆、凭上一轮的扫描结果改。锚点是快照，行号会漂；符号名才是稳定的坐标。
- **一次只修一条**，修完立刻用同一批 grep 命令复验。
- **先讲清楚再动手**：这是什么、为什么是个问题（带着 C 源的对位依据），然后至少给两个方案并比较（Redox 怎么做、Linux 怎么做、操作系统理论怎么讲），说明取舍之后才实施。
- **新发现的跨线条目**先进自己那线的文件，同时在编排状态板登记一行，收尾时由编排线批量并回权威文件——不要顺手写进权威文件，理由见第 3 节。

## 6. 回归纪律：把"能跑"变成"可比较地能跑"

- 每条改完跑所碰 crate 的测试；每次收工跑一次本线所辖 crate 的全量回归。
- **内存铁律**：构建与测试优先在 Docker 镜像 `minix-ci:1.94` 里跑，限内存 `2g`、单线程 `-j 1`；只有 Docker 不可用才回退宿主，并且要在汇报里明确说明发生过回退。回退方案是 `ulimit -v 3145728`（单位 KB，约 3G）加 `-j 1`。之所以第一优先不是"更快的那个"而是"更稳的那个"：容器隔离的不只是内存溢出——链接期内存峰值能把宿主进程静默杀死，表现为测试莫名消失而不是报错；而任何一次内核测试的 panic 崩溃都会波及宿主系统。
- **禁止整仓 `cargo fmt`**。工具链版本漂移会污染整份 diff，让人无法分辨"这次改了什么"。只对新增代码做单文件格式核验。
- **静态检查要对账基线**：所碰 crate 的告警数量不得高于既有基线，否则改动就没法审查。
- **完成定义是三条同时成立**：所改 crate 测试全绿、静态检查零新增告警、编译检查无新错误。三条缺一不标 `✅`。

## 7. 记账的增量纪律：日志只追加，不复述

`2026-09-20` 的另一场事故：一条线的修复日志被全量重复追加三十二次，膨胀到六万八千五百五十二行，其中约九成是重复内容。不是有人恶意，而是"每次会话都把已知内容再抄一遍以求完整"这个习惯在长会话里必然发生。

约定的做法：

- 日志**只写增量**，一次会话一条，编号连续。
- 追加前自检标题行的数量必须为一（`grep -c` 那一行标题），大于 1 就说明这次是重复追加。
- 历史撞过号的编号，引用时带线名限定词，别靠裸号。
- 扫描、调研类的中间产物一律带作者后缀（例如 `new_todo_{模型名}.md`），并且**互相不引用**。这条看起来浪费，其实是这套协议里最聪明的一条：多个模型独立扫同一份代码，产出的交集是"可信度高"的信号，差集是"需要复核"的信号，矛盾是"必须人来裁决"的信号。一旦让它们互相引用，就退化成一个模型的观点抄了五遍。

## 8. 验收阶梯：并发不能省掉收敛

分线并发只解决"同时干活"，不解决"干完之后系统是不是真的能用"。所以有一张所有人都看得见的阶梯，每一步的判据都是可执行的一条命令：

| 阶 | 内容 | 判据 |
|---|---|---|
| T0 | 三架构能起来 | 引导冒烟通过，回归脚本存量绿 |
| T1 | 三架构用户态门槛 | 用户态陷入与返回腿、运行时诞生链在三架构真机通过 |
| T2 | 服务器通电链 | 各服务的入口不再停在占位循环，端到端联调的对应子项真机通过 |
| T3 | 初始化进程真实运行 | 进入多用户形态，等待子进程与信号端到端可用 |
| T4 | 命令面执行 | 十八个阶段的命令冒烟脚本有可见输出地通过 |
| T5 | 三架构复跑上面全部 + 多核正确性 | 三架构乘全梯次通过，然后进入收尾归档 |

阶梯存在的意义是防止一种典型的自欺：某条线在自己的范围里全绿，但整个系统并没有往前走。所以每一阶的判据必须落在真机或者端到端载体上，而不是单元测试计数上。

## 9. 红线（违反即返工）

- `minix3/` 是原始 C 源码，是外部行为的唯一基准，**只读不改**。结论拿不准时按这个优先序裁决：C 源码的实际行为 > 设计契约 > Rust 实现 > 设计或技术文档 > 任何人的分析。
- **不许假完成**。占位实现、有意推迟的项、暂时守卫，都要如实登记成待办；测试不绿不标完成；"DEFERRED"不算"已修"。
- **不许重开已闭的账**。动手前先 grep 权威待办文件里该条目的最新进度注记。表头普遍滞后，正文注记才是新的。
- **写代码、写文档、改待办都不许逐行直译 C**。C 的对位关系放在注释和锚点里说明，代码与叙述本身必须是 Rust 侧的语义表达。
- 遇到需要人来拍板的语义分歧，登记上交，不代决。协议里所有"待裁决"的队列都是这个出口。

## 10. 归档：临时工具就该有寿终正寝的样子

线文件和编排板都是**临时工具**，条目权威描述始终在原待办文件里。归档规则：

1. 每达成一阶，编排线勾账，并把涉及条目的状态**批量**回写权威文件，按各文件原有体例，消除"两个地方说法不一"的窗口期。
2. 最高阶全绿后：线文件与编排板的条目表冻结，做一次全量对账（回到原文件逐条 grep 复核没有漏领），然后整体并入权威待办文件的归档段；四份临时文件删除，或者在头部标注"已归档"。
3. 多模型独立扫描的产物**合并之后不删**，留作日后对账的证据。
4. 新一轮并行开工时，前轮的线文件加冻结横幅，本轮换新前缀（第一轮 `edge1.md` 至 `edge4.md`，第二轮 `new_edge1.md` 至 `new_edge4.md`），未决行由新板携带并重编号。
