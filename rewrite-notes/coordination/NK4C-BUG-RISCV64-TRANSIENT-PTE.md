## 第 1 章 现象：系统正在做什么的时候崩

### 1.1 先补一课：微内核里"谁来给进程补页"

在开始讲崩溃之前，必须先讲清楚崩溃发生时的**职责分工**，否则后面每个词都看不懂。

本项目是 MINIX 3 风格的重写：内核极小，文件系统、内存管理、进程管理都跑在**各自独立的用户态进程**里，彼此靠消息传递协作。其中"内存管理服务器"（代码里叫 `vm`，本文称**虚拟内存服务器**）负责一件核心工作：**当某个进程访问了一个"暂时还没有对应物理内存"的虚拟地址时，替它找一帧物理内存、建立映射，然后让它把那条指令重跑一遍。**

被服务的那个进程此刻正处于**用户态**，而虚拟内存服务器自己也是**用户态进程**（微内核的核心代价就是：内存管理不再是内核特权代码，而是一个普通进程）。这就带来一个约束，后面所有取证都绕不开它：

> 虚拟内存服务器**没有特权指令可用**。它不能执行 `sfence.vma`（RISC-V 的地址转换缓冲区失效指令，属监管级指令），也不像内核那样能直接读写物理内存——它只能使用内核在启动阶段替它建好的一扇"窗口"（见第 2.2 节）。

### 1.2 崩溃的确切形态

崩溃不是发生在被服务的进程里，而是发生在**虚拟内存服务器自己身上**：它在替别人查页表的过程中，自己访问了一个非法地址，触发加载页故障；而内核看到"故障的是虚拟内存服务器本人"，没有任何人再去补它的页，于是直接判死。

内核的判死点有两个，都写着一样的话：

- 锚点：`os/kernel/src/trap_dispatch.rs:trap_dispatch` 内的 `panic!("pagefault in VM")`（当前实现位于该文件末尾附近的故障转发分支；另一处在设备中断故障分支）
- 串口上的表现（一行字面证据，来自取证日志 `tmp/nk4a/gh72.serial`、`tmp/nk4a/gh103.serial`，多次构建逐字节相同）：

```
sepc 0x3abec stval 0x10bd28cb2c ...  pagefault in VM
```

三个词解释一下，后面反复用：

- `sepc`（Supervisor Exception Program Counter）：出错那条指令的地址。注意它是 `0x3abec` 这种**很低的地址**，说明出错方是虚拟内存服务器这个用户态程序（它的代码段在低地址），不是内核（内核代码在高半区，形如 `0xffffffc0........`）。
- `stval`（Store/Trap Value，RISC-V 也叫 `bad address`）：**访问失败时使用的那个地址**。这个数是本案最重要的物证。
- `pagefault in VM`：项目对 MINIX 3 C 源码 `exception.c:101-118` 的忠实移植——虚拟内存服务器自己缺页即致命。

### 1.3 复现条件（决定后面每个实验的设计）

| 条件 | 实测值 | 锚点 |
| --- | --- | --- |
| 架构 / 机型 | riscv64，`virt` 机型，Sv39 分页 | `os/arch/src/riscv64/paging.rs` |
| 内存大小 | 512 MiB，物理范围 `0x8000_0000`–`0xA000_0000` | 探针常量 `RAM_TOP_PFN = 0x9fb33`，`os/servers/vm/src/alloc_page.rs` |
| 崩溃点 | `sepc = 0x3abec`，`stval = 0x10bd28cb2c` | `tmp/nk4a/gh72.serial`、`gh73.serial`、`gh92` |
| 是否确定性 | **同构建下确定复现**：多次无调试器裸启动，指纹逐字节相同 | `tmp/nk4a/gh72` 与 `gh73` 串口逐位一致 |
| 裸启动到崩 | 约 8 秒（不带 `-S`、不带探针） | `tmp/nk4a/gh96.serial` 时间戳 |

## 第 2 章 机制底座：本案需要的全部背景知识（自包含）

这一章把后面所有论证要用到的机制一次性讲透。读过可以直接跳到第 3 章。

### 2.1 Sv39 三级页表与页表项的位域

RISC-V 的 Sv39 分页把 39 位虚拟地址切成三段，每段 9 位，对应三级表：

```
虚拟地址（Sv39，4 KiB 粒度）
 bit 38 ..... 30 | 29 ..... 21 | 20 ..... 12 | 11 ..... 0
   L2 索引(512)   L1 索引(512)   L0 索引(512)  页内偏移(4KiB)
```

每一级表固定占一整个 4 KiB 物理页帧，里面有 512 个**页表项**（Page Table Entry，本文简称页表项），每项 8 字节。所以：

> **第 i 项的地址 = 表帧物理地址 + i × 8**。这条乘法关系是第 3.4 节"八倍对齐判据"的来源。

本项目对页表项位域的处理集中在三个函数里（锚点均在 `os/arch/src/riscv64/paging.rs`）：

```rust
const PTE_PPN_MASK: u64 = 0x003F_FFFF_FFFF_FC00;   // 物理页号字段：项的 bit[53:10]

fn paddr_to_pte(paddr: u64) -> u64 { (paddr >> 2) & PTE_PPN_MASK }   // 物理地址 -> 页表项字段
fn pte_to_paddr(pte: u64) -> u64   { ((pte & PTE_PPN_MASK) >> 10) << 12 }  // 页表项字段 -> 物理地址
fn pte_is_leaf(pte: u64) -> bool   { /* 读/写/执行三位任一置位即为叶 */ }
```

三个必须记住的性质，本案每一步判断都靠它们：

1. **`pte_to_paddr` 的结果低 12 位恒为 0**。它先把项右移 10 位、再左移 12 位，任何落在低位脏数据都会被"页对齐"洗掉。所以从页表项解出的物理地址**一定是 4 KiB 对齐的**。
2. **叶判定看读写执行位**：只有有效位 V、而读/写/执行三位全 0 的项是"指向下一级表"的中间项；任何一位被置起就是叶（真实页面）。
3. **`PTE_PPN_MASK << 2` 等于 `0x00FF_FFFF_FFFF_F000`**（实测：`python3 -c "print(hex(0x003FFFFFFFFFFC00<<2))"`）。这条算术会在第 4.4 节用来洗清一个"看起来像寄存器被破坏"的嫌疑。

索引取位函数同样简单（`os/arch/src/riscv64/paging.rs:l2_index`/`l1_index`/`l0_index`）：`(vaddr >> 位移) & 0x1FF`，位移分别是 30/21/12。

### 2.2 两扇"直接映射窗"：本案最容易被算错的东西

RISC-V 没有 x86 那种"内核页表天然覆盖物理内存"的免费午餐。本项目给页表项的读写准备了**两扇线性窗口**，把物理地址平移成虚拟地址用：

```rust
// 锚点：os/arch/src/arch/direct_map.rs，impl DirectMapArch for Riscv64DirectMap
const VM_DIRECT_MAP_BASE:      u64 = 0x0000_0010_0000_0000;  // 64 GiB，即 1<<36
const KERNEL_DIRECT_MAP_BASE:  u64 = 0xFFFF_FFC0_4000_0000;
const VM_DIRECT_MAP_SIZE:      u64 = 0x0000_0004_0000_0000;  // 16 GiB
```

对应换算关系（`os/arch/src/arch/direct_map.rs:vm_phys_to_virt` / `kernel_phys_to_virt`）：

```
物理地址 --(+ 窗基址)--> 虚拟地址
  0x9DC377F8  +  0x0010_0000_0000  =  0x10_9DC3_77F8     （虚拟内存服务器窗）
  0x9DC377F8  +  0xFFFFFFC0_40000000 =  0xFFFF_FFC0_DDC3_77F8（内核窗）
```

> ⚠ **本文第 6.1 节会说明：这两个"加法"曾经被算错过一整位数**，代价是误判了一条观测手段不可用。位数这种东西，写文档时最容易骗过眼睛——`1<<36` 是 `0x10_0000_0000`（11 个十六进制位里的"1"在第 11 位），不是 `0x1_0000_0000`。请务必用代码打印验证，不要心算。

### 2.3 页表句柄的"通道"：谁在用哪扇窗

同一份走表代码被两种身份复用，靠一个枚举区分（锚点 `os/arch/src/riscv64/paging.rs:PteChannel`）：

```rust
enum PteChannel { KernelDm, VmDm }
```

- 内核态构造的句柄固定用 `KernelDm`；
- 虚拟内存服务器侧构造的句柄固定用 `VmDm`（因为它是用户态进程，只有那扇窗对它有效）。

所有对页表项的实际读写都过这两个内部函数：

```rust
// 锚点：os/arch/src/riscv64/paging.rs:read_pte_dm / write_pte_dm
unsafe fn read_pte_dm(paddr: u64, channel: PteChannel) -> u64 {
    core::ptr::read_volatile(channel_to_ptr(paddr, channel))       // = paddr + 对应窗基址
}
unsafe fn write_pte_dm(paddr: u64, value: u64, vaddr_for_flush: u64, channel: PteChannel) {
    core::ptr::write_volatile(channel_to_ptr(paddr, channel), value);
    if channel == PteChannel::KernelDm {
        asm!("sfence.vma {}, x0", in(reg) vaddr_for_flush);        // 用户态句柄必须跳过，否则非法指令陷阱
    }
}
```

`write_pte_dm` 里那句通道判断的原因是：用户态执行 `sfence.vma` 会触发非法指令异常（同类“特权级误用指令”的后果在第 5.5 节另有一例）。理解这一点很重要，因为它说明**本案里“用户态与特权级”是一条反复出问题的主线**。

### 2.4 `walk_read`：被崩的那段代码逐行

这是缺陷 (A) 的现场。锚点 `os/arch/src/riscv64/paging.rs:walk_read`，三级只读下降：

```rust
fn walk_read(root_paddr: u64, vaddr: u64, channel: PteChannel) -> WalkResult {
    let i2 = l2_index(vaddr);
    let l2e = unsafe { read_pte_dm(root_paddr + (i2 as u64) * 8, channel) };   // ① 读根表的第 i2 项
    if l2e & V == 0 { return NotPresent; }
    if pte_is_leaf(l2e) {                                                     // 1 GiB 叶
        let paddr = pte_to_paddr(l2e) | (vaddr & 0x3FFF_FFFF);               // ② 物理地址里"或"进了虚拟地址低 30 位
        return Huge1G(...);
    }
    let l1 = pte_to_paddr(l2e);                                               // ③ 中间表帧基址
    let i1 = l1_index(vaddr);
    let l1e = unsafe { read_pte_dm(l1 + (i1 as u64) * 8, channel) };         // ④ 读 L1 表的第 i1 项
    if pte_is_leaf(l1e) {
        let paddr = pte_to_paddr(l1e) | (vaddr & 0x1F_FFFF);                 // ⑤ 同上，2 MiB 叶
        return Huge2M(...);
    }
    let l0 = pte_to_paddr(l1e);
    let leaf_paddr = l0 + (l0_index(vaddr) as u64) * 8;
    let pte = unsafe { read_pte_dm(leaf_paddr, channel) };                   // ⑥ 读叶项
    WalkResult::Leaf(leaf_paddr, pte)
}
```

从这段代码能抽出**三条硬事实**，它们是本案所有"这个地址不可能从哪儿来"推理的依据：

- **事实一**：`①④⑥` 三次访存的地址形状都是 `帧基址(4 KiB 对齐) + 索引 × 8`，因此**低 12 位必然是 8 的倍数**。
- **事实二**：`②⑤` 两条叶分支会把**虚拟地址的低 30/21 位"或"进物理地址**，产出一个非 4 KiB 对齐的"物理地址"返回给调用者。这是全函数里唯一会产生"页内偏移"的地方。
- **事实三**：函数本身不分配、不写表，纯读；任何"写坏了页表"的怀疑都不该落在这个函数上，而应落在它的**写侧同族**（`map`/`remap`/`unmap`/`update_flags`/`walk_alloc`，都经 `write_pte_dm`）。

### 2.5 页表帧从哪来、回到哪去

虚拟内存服务器需要的页表帧由一个注册给架构层的分配器供给：

- 分配：`os/servers/vm/src/alloc_page.rs:vm_pt_alloc` —— 先 `alloc_pfn_reclaiming`（带内存回收重试的物理帧分配，对齐 MINIX 3 C 源码 `pagetable.c:375` 的 `alloc_mem`），拿到帧号后**立刻用 `core::ptr::write_bytes(virt, 0, CLICK_SIZE)` 整帧清零**（`CLICK_SIZE = 4096`）。
- 回收：同文件的归还钩子 `os/servers/vm/src/alloc_page.rs:vm_pt_free`，以及进程退出腿 `os/servers/vm/src/vmproc/vmproc_handle.rs:free_page_table`；架构层分配入口是 `os/arch/src/arch/pt_alloc.rs:alloc_pt_page`（它只调注册进来的分配函数，真正干活的就是上一行的 `vm_pt_alloc`）。

"整帧清零"这四个字后面会救一次场：第 4.3 节用它否证了"新帧带着旧数据上岗"这一整类猜想。

同时，`vm_pt_alloc` 里埋着一组自研检测器（位图 + 串口标记），它们的**可信度分级**是本案方法论的精华之一，见第 4.1 节。

## 第 3 章 把物证拆成数字：现场指纹的逐位解码

本案真正的转折点不是某个新工具，而是**把 `stval` 这个数字拆开看**。拆完你会发现它不是随机噪声。

### 3.1 主指纹 `stval = 0x10BD28CB2C` 的分解

```
0x10_BD28_CB2C
 = 0x0010_0000_0000        ← 虚拟内存服务器的直接映射窗基址（第 2.2 节常量，唯一匹配项）
 + 0xBD28_C000             ← "帧基址"部分：一个物理地址
 + 0xB2C                   ← 页内偏移部分
```

窗口基址这一步没有歧义：RAM 只有 512 MiB（`0x8000_0000`–`0xA000_0000`），内核窗基址是 `0xFFFF_FFC0_4000_0000`，只有 `1<<36` 这个窗基址能把一个 34 位物理地址抬到 `0x10_BD28_CB2C`。而崩溃发生在用户态的虚拟内存服务器里，它只能用这扇窗。

结论一：**这是一次"通过直接映射窗访问物理地址 `0xBD28CB2C`"的读，而 `0xBD28CB2C` 超出物理内存上限**（`0xA000_0000`），所以窗内没有映射，触发加载页故障。

### 3.2 那个"帧基址"到底是什么：差值恰好等于内存容量

```
0xBD28C000 − 0x9D28C000 = 0x2000_0000  = 512 MiB  = 本机 RAM 的大小，也等于 bit29
等价写法：0xBD28C000 = (0x9D28C000 − 0x8000_0000) + 0xA000_0000
                        = "帧在 RAM 内的偏移" + "RAM 顶地址"
```

同一个家族的其他实测样本（都保持这个结构，只有低位不同）：

| 证据文件 | `stval` | 减去窗基址后的"伪帧" | 伪帧 − 合法帧 | 低 12 位（页内偏移） |
| --- | --- | --- | --- | --- |
| `tmp/nk4a/gh72.serial`、`gh73.serial` | `0x10BD28CB2C` | `0xBD28CB2C` | `0x9D28C000` + `0x2000_0000` | `0xB2C`（**不是 8 的倍数**） |
| `tmp/nk4a/gh81` 系（带 `-S` 的漂移变体） | `0x409D28BB20` | 见 3.6（另一种形状） | — | `0xB20`（是 8 的倍数） |

结论二：这里的"高位污染"**不是随机撕裂**。随机翻转的位不会刚好等于内存容量；`真帧地址 + 一整块 RAM 的大小` 或 `帧在 RAM 内的偏移 + RAM 顶地址` 这两种等价读法都指向同一族经典错误：**"相对偏移"与"绝对地址"混用、或基址被加了两次**。这条线索的价值在于：它把怀疑对象从"某个数据踩了页表帧"转向"某个值被用错了单位（偏移当成绝对地址）"，而后者是**纯代码审计能抓到的东西**。

### 3.3 洗清一个假嫌疑：`0x00FFFFFFFFFFF000`

有一段时间，崩溃现场的寄存器里出现 `0x00fffffffffff000`，被读成"某个寄存器被破坏了"。反汇编之后确认：那是 `walk_read` 正常计算的 `PTE_PPN_MASK << 2` 中间值（编译成了 `lui` + `srli` 两步），与第 2.1 节算术性质 3 完全吻合。

教训：**先把自己代码的常量算一遍，再谈"被破坏"**。这条纪律后面又救了一次（3.5 节）。

### 3.4 八倍对齐判据（本案最好用的一把刀）

由第 2.4 节事实一：

> 如果一次访存的地址低 12 位是 8 的倍数 → 它可能是在读某个页表项；
> 如果低 12 位不是 8 的倍数 → 它**不可能**是页表项读取，只能是"页表项解析出的物理地址 + 页内偏移"这种**对被映射页面本身的数据访问**。

`0xB2C % 8 = 4`（`python3 -c "print(0xb2c % 8)"`）。所以：

**崩在 `0x3abec` 的那一次访问，是一个数据访问的形状，而不是页表项读取的形状。**

项目里早就把这条判据写成了代码注释（锚点：`os/kernel/src/trap_dispatch.rs` 中处理 `stval` 低位的诊断分支，判据原文为"槽偏移非 8 倍数 ⇒ 非槽读而是数据访问"）。

### 3.5 一处至今没闭合的矛盾（本文新登记，接手者请先查这里）

把 3.1/3.4 与第 2.4 节合起来看，出现了**互相打架**的三条断言：

1. 现场回栈说：崩在 `Riscv64Paging::query` 内部，调用者是 `minix_vm::cow_exec_pf::sync_slot_pte`（证据：`tmp/nk4a/gh93-gdb.txt` 的 `#0 query+148 / #1 sync_slot_pte+1128`）。
2. `query` 的全部访存都是页表项读取（第 2.4 节事实一），因此**只能产生 8 倍对齐的地址**。
3. 实测 `stval` 的低 12 位是 `0xB2C`，**不是 8 的倍数**。

三条不可能同时为真。可能的出路有两条，都需要复核：

- **出路甲：符号归属不可靠。** `minix-vm` 这个二进制在取证时可能没有行号级调试信息，`query+148` 是"最近符号 + 偏移"的近似。真实崩点也许落在把页表项解析结果当物理地址去访问的**数据访问腿**上——而第 2.4 节事实二正好指认了全函数里唯一会造出非对齐地址的地方（两条大页分支把虚拟地址低位"或"进物理地址）。如果成立，那么"**页表项本身被写坏**"整个大前提都要重估：坏的可能不是页表项，而是**喂给解析器的输入或解析后的用法**（比如把一个非叶项当成 1 GiB/2 MiB 叶用了）。
- **出路乙：确实存在两个不同形状的故障。** 已观测到的两种 `stval` 尾数（`0xB2C` 非对齐 / `0xB20` 对齐）分属两族（3.2 表），也许它们是**两个不同机制**的产物，之前被当成同一个案的两种漂移。

**复核动作（零安装即可做，列为待办 T1）**：取当轮 `minix-vm` 二进制，用带调试信息或至少带完整符号表的方式，把 `0x3abec` 前后各 0x80 字节反汇编（`riscv64-unknown-elf-objdump -d --start-address=0x3a96c --stop-address=0x3ac6c`），逐条确认 `ld` 之前是否有"或页内偏移"的掩码运算（`and`/`or` with `0x3fffffff` / `0x1fffff` / `0xfff`）。若有，出路甲成立，整个"页表帧被写坏"的叙事要重画。

### 3.6 第二族指纹还没有解释

`stval = 0x409D28BB20`（`0x9D28BB20 + (1<<38)`，且低 12 位 `0xB20` 是 8 的倍数）没有落到窗基址上：它既不在虚拟内存窗 `[0x10_0000_0000, 0x14_0000_0000)` 内，也不是内核窗形状。它更像是"一个带 bit38 的地址被当作虚拟地址使用"——而在 Sv39 里 bit38 之上的位必须与 bit38 相同才是合法地址，单独置起 bit38 属于**非法（非规范）虚拟地址**。[待验证：这条解读需要一条能解释 bit38 来源的具体代码路径；目前只能作为观察记录，不能作为结论。]

值得注意的是：这一族只在**带调试器干预**（`-S` 从头挂起）或带额外探针的运行里出现，裸启动的主指纹始终是 `0x10BD28CB2C`。这一现象本身是第 5.2 节"观测者效应"的证据。

### 3.7 三个候选槽地址都对不上现场（接手者优先读这里）

上一节的矛盾可以算得更死。把走表用的虚拟地址 `vaddr = 0x3FFFFDFB2C` 代回第 2.4 节，把三次页表项读取的地址低 12 位**穷举**出来（可复核：`python3 -c "v=0x3ffffdfb2c; print(*[hex(((v>>s)&0x1FF)*8) for s in (30,21,12)], hex(v&0xfff))"`）：

| 读的是哪一级 | 索引 | 索引 × 8 | 该次读的地址低 12 位 |
| --- | --- | --- | --- |
| 根表（L2）第 i2 项 | `255` | `0x7F8` | `0x7F8` |
| L1 表第 i1 项 | `511` | `0xFF8` | `0xFF8` |
| L0 表第 i0 项 | `479` | `0xEF8` | `0xEF8` |
| **现场实测** | — | — | **`0xB2C`** |

三个候选全不中。而 `0xB2C` 恰好等于 `vaddr & 0xFFF`，即页内偏移。结合第 2.1 节性质 1（页表项解出的物理地址低 12 位恒为 0），得到一条形状判断（措辞故意限得很窄，避免越权下结论）：

> 与 `os/arch/src/riscv64/paging.rs:walk_read` 里那三次读取的地址形状（`页框基址 + 索引 × 8`）相比，`stval` 的低 12 位不符合任何一种：因此**不能把这次出错访问解释成一次合法的页表项槽读取**。它的形状是 `窗基址 + 某个页框 + 页内偏移`，即页内容访问的形状。

这句话**不能**推出两件常被误当成它结论的事，证据强度分层写清楚：

| 断言 | 强度 | 理由 |
| --- | --- | --- |
| 出错地址不是一次合法的页表项槽访问 | **硬**（纯算术） | 前提是源码里那三次读取的形状如第 2.4 节所述；不依赖符号、不依赖寄存器快照 |
| 出错指令不在 `query()` 里（即 `sepc = 0x3abec` 的符号归属不对） | **未定** | 两条腿都能解释：① 它确实是 `query()` 代码区里的 `ld`，但喂进去的基址本身已带脏低位（地址坏不等于指令不属于这里）；② `query()` 被内联进了调用者，那个偏移根本不是一个独立函数。区分它们只需看反汇 + 有无调试信息（待办 T1） |
| 已经知道嫌疑页表项是哪一枚 | **未定** | 形状判据只排除一类解释，不指认真靶；真靶位置由第 3.8 节的虚拟地址读法决定 |

这个结论一旦成立，三件事要立即重估：

1. **近期所有实验共同的靶 `0x9DC377F8`（根表第 255 槽）不在嫌疑位置上。** 嫌疑应在一枚**叶项**——若走的是 L0 表，位置是"某张 L0 表帧 + `479 × 8`"。观察点、活体扫描、以及插件骨架的默认参数 `arg=0x9dc377f8` 都在盯错的那一格。
2. **"12 个根帧各 512 槽零命中"这条把缺陷钉成瞬态的关键证据，覆盖层不对。** 它只看了根表（L2）层，从未看过任何 L1/L0 层——如果脏值 durable 地躺在某张 L0 表里，这套扫描是看不见的。证据与结论之间现在是断的（见待办 T1b）。
3. **全内存快照那一次仍可能有效，但要核实它的谓词。** 若它是"对 RAM 每个 8 字节字判定 `pte_to_paddr(字) == 0xBD28C000`"，则覆盖完整（包含 L0 层）；若它是"按原始字节模式搜索某个特定编码值"，则会漏掉"同一物理页框、不同标志位编码"的项。两种谓词的强度差一个量级。

最后一条诚实的限制：这条算术**不区分**"叶项被写坏"与"喂进来的 vaddr 本身就是错的"（第 4.7 节变体一），因为页内偏移永远等于所喂虚拟地址的低 12 位。它区分的是**"合法页表项槽访问的形状"与"页内容访问的形状"**——而这恰好决定了后面一切工具该往哪个地址上看。

### 3.8 页内偏移必须与所喂的虚拟地址自洽（一处还需闭合的算术）

把第 3.7 节的判据反过来用，还能再咬出一层约束：**页面内容访问的页内偏移，等于那次访问所用虚拟地址的低 12 位**。

| 如果崩溃所用的虚拟地址是 | `vaddr & 0xFFF` | 三级索引 `i2 / i1 / i0` | 与现场 `stval` 低 12 位 `0xB2C` 是否自洽 |
| --- | --- | --- | --- |
| `0x7FFFFFFFE000`（子栈顶，页对齐） | `0x000` | `511 / 511 / 510` | **不自洽** |
| `0x7FFFFFFFEB2C` | `0xB2C` | `511 / 511 / 510` | 自洽 |
| `0x3FFFFDFB2C`（第 3.7 节用的那一族） | `0xB2C` | `255 / 511 / 479` | 自洽 |

（可复核：`python3 -c "for v in (0x7fffffffe000,0x7fffffffeb2c,0x3ffffdfb2c): print(hex(v), [((v>>s)&0x1FF, hex(((v>>s)&0x1FF)*8)) for s in (30,21,12)], hex(v&0xfff))"`）

先说一句能稳住结论的话：**无论采用哪一行虚拟地址，三个候选表槽地址都不等于 `0xB2C`**（只可能是 `0x7F8` / `0xFF8` / `0xFF0` / `0xEF8` 这几个值），所以第 3.7 节那条形状判据对两种读法都成立。真正影响下一步工具的是另一件事：**嫌疑表槽落在哪些帧上，取决于采用哪一行。**

两种读法都要检验，不能只挑顺眼的一条：

- **读法甲**：崩溃用的地址其实是 `0x7FFFFFFFEB2C`（栈顶往下 `0xB2C` 字节），先前记录的 `0x7FFFFFFFE000` 是栈基寄存器而不是被访问地址。若成立，则三级索引为 `i2 = 511`、`i1 = 511`、`i0 = 510`，三枚候选页表项地址是**根帧 + `0xFF8`、某张 L1 帧 + `0xFF8`、某张 L0 帧 + `0xFF0`**。注意"根帧 + `0xFF8`"在本案一度被当成"控制位"——它其实是真靶之一。
- **读法乙**：崩溃用的地址确为 `0x7FFFFFFFE000`，而那次访问是"把翻译出来的页基址再加一个与虚拟地址无关的搬运游标"（例如消息拷贝、清零/复制循环里的 `+0xB2C`）。此时低 12 位来自**另一条腿的偏移**。

  读法乙包含一个容易漏掉的子型：`query()` 可能只负责**返回页基址**，而 `0xB2C` 是 `query()` 返回后由**调用者**加上的。此时说"崩在 `query()` 里"与"崩在调用者里"其实是同一件事的两种说法（取决于函数是否被内联），不必另立一种读法——它归在乙下面，证据要求也一样：看那条 `ld` 之前的偏移来自哪个寄存器。

区分方法很省：把当轮串口日志里的 `stval` 与全套通用寄存器原值重读一遍，再看崩点那条 `ld` 之前是否存在"把某个非索引寄存器加进来"的 `add`。读法甲应当能由 `stval & 0xFFF == vaddr & 0xFFF` 直接自证；读法乙则两者必然不等，而那一带指令流里会找到第二个偏移来源。

**对工具的直接后果**：若读法甲成立，嫌疑页表项在**栈链上的 L1/L0 表帧**；只盯"子根帧"去做观察点、活体扫描或插件过滤，得回来的会是一个空结果。所以第 6.3 节给插件补了一层不依赖"先知道帧地址"的宽口径过滤。那些表帧的物理地址已经从插件时间线里开始出来了（待回填，见待办 T12）；在它回填之前，本节给的候选槽号都只能当**候选**用。

> **回填与读法乙子型定案（2026-10-03，权威记录见 WORKLOG §续-266）**：在当前 build 反汇 `query`（起点 `0x3ab58`，与崩点 `0x3abec` 同 build）逐条核对——每条槽读都是 `基址(DM_BASE + pte_to_paddr(父项)，低 12 位恒 0) + 索引×8`、`ld` 立即数恒 0。⇒ **走表读出的地址低 12 位只能是 8 的倍数**。因此：
> - **读法乙子型（"0xB2C 是 query 返回后调用者加上的游标"）不成立**：崩 PC 落在 query 内部的槽读区，那一带没有"query 之后再加偏移"的崩点指令，偏移也不来自任何非索引寄存器（立即数是 0，偏移全来自 4KiB 对齐的基址）。走表的虚拟地址与最终被访问的地址在这一层是**同一件事**，无需另立读法。
> - **裸启动主指纹 `sepc=0x3ac10` 在本 build 解析为非-load 指令 `and a1,a1,t0`**：即 (sepc, stval=…B2C) 这对数字来自**不同 build**（探针改布局），不能合起来当"崩在 query 槽读且 stval 非对齐"用——这是 3.5 节"出路甲：符号归属不可靠"的实锤。
> - **候选末级表帧实测**：插件时间线 + halt dump 出的末级 L0 帧为 `0x9d2ac000`（其 slot 511=0 从未写、全净），栈链 vaddr `0x7fffffffe000` 对应 `i2/i1/i0 = 511/511/510`。上表候选槽按此限宽使用；**"读到的值从未被写过"仅对已 dump 的帧成立，未跑全 512MB 逐字解码扫描**（见待办 T1c）。
> - **连带的结论修正**：此前把 stval 减窗基当"walk 解析出的故障物理"再比"已映射叶"推出的"root 身份错配"，其前提（…B2C 是槽读输出）已被本节算术推翻，故该收敛下调为未证。

## 第 4 章 假设空间：每一条猜想是怎么被处决的

本案先后有过 8 个根因假设。下面按"该假设预言什么 → 用什么判据 → 实测什么 → 结论"四段式重写一遍，**不带时间线**。这张表本身就是最好的排雷地图：接手的人不必再走一遍。

| 编号 | 假设一句话 | 结论 |
| --- | --- | --- |
| H1 | 物理帧分配器把同一帧发给了两个使用者 | **已排除**（可信检测器全零） |
| H2 | 某条映射路径漏记引用计数，回收了仍被引用的帧 | 静态读未坐实（主路径对称） |
| H3 | 新分配的页表帧没清零，带着旧数据上岗 | **已排除**（整帧清零已核对） |
| H4 | 走表算术/掩码写错 | **已排除**（反汇编 + 常量对账） |
| H5 | 陈旧调试探针自己在用户态发超级调用 | **已排除并已成修**（见 5.5 节，另一案） |
| H6 | 帧既当页表又当数据被写，脏值长期驻留在槽里 | **已排除**（活体扫描直接读到零） |
| H7 | 存在一个"只在那一刻可见"的瞬态写者 | **当前主假设**，但观测手段已耗尽 |
| H8 | 根本没有写者：是**读者用错了地址/用错了表根** | **未排除，且被 3.5 节矛盾加强** |

### 4.1 H1（分配器双发）——顺便讲清"检测器的可信度分级"

`os/servers/vm/src/alloc_page.rs` 里为了追本案装了三张位图（`PT_SEEN` 曾作为页表帧、`DATA_SEEN` 曾作为数据帧、`FREED` 曾释放），并在分配点打出四类串口标记：

| 标记 | 判据含义 | 本机可信度 | 为什么 |
| --- | --- | --- | --- |
| `nk4a: ptalloc-DUP pfn=...` | 同一帧被当作页表**两次**发放（位图未清就撞见） | **高** | 只在页表分配路径上判断，语义干净 |
| `nk4a: alloc-reuse-PT pfn=...` | 数据分配撞上了已当过页表的帧 | 高 | 同上 |
| `nk4a: dblfree pfn=...` | 同一帧被释放两次 | 高 | 同上 |
| `nk4a: ptalloc-OOR/BADPFN` | 发出的页号超出 RAM 上限 | 高 | 纯值域判断 |
| `nk4a: ptalloc-reuse-DATA pfn=...` | 页表帧曾经当过数据帧 | **低（歧义）** | 合法复用本来就天天发生；且虚拟内存服务器自己的堆旁路了 `DATA_SEEN` 的置位 |

实测（`tmp/nk4a/gh72.serial`、`gh73.serial`，当前构建）：前四类**全部为零**，只有 `reuse-DATA` 命中 18080 条。

> **方法论要点一：检测器必须分可信/不可信，且"歧义检测器的命中数"不能当证据。** 本案曾两次因为 `reuse-DATA` 这个数字很大而重新怀疑别名方向，都被更干净的检测器拉回来。位图还有一个隐含边界：`PT_SEEN_WORDS = 10_240` 个字 × 64 = 覆盖到页号 `0xA0000`，也就是 2.5 GiB，本机 512 MiB（顶页号 `0x9FB33`）在覆盖范围内——这点要核实，否则"零命中"可能只是"看不见"。

结论：分配器不发双份、不发越界页号、不重释放 → **H1 死**。任何在分配器里加"拒发活帧"的补丁都是空修（确实曾按此方向做过一次，无效，见第 8 章教训）。

### 4.2 H2（引用计数漏计）——静态审计的天花板

MINIX 式内存管理里，一帧物理页被多少条映射引用，由引用计数记账；回收（reclaim）只驱逐计数为 1 的页。审计对象与结论：

| 审计点 | 锚点 | 结果 |
| --- | --- | --- |
| 分叉时逐槽加计数 | `os/servers/vm/src/fork.rs:fork_region` | 与减计数侧对称 |
| 缺页映射加计数 | `os/servers/vm/src/region/page_state.rs:PageSlot::pfn` / `os/servers/vm/src/region/vir_region.rs:map_page` | 加 1 |
| 解除映射减计数 | 同族 `unmap_page` | 减 1，对称 |
| 页缓存驱逐谓词 | `os/servers/vm/src/page_cache.rs:free_pages` | 只驱逐计数 1，与 MINIX 3 C 源码 `cache.c` 对位 |
| 完整性自检 | `os/servers/vm/src/sanity.rs:verify_refcounts` | **对本案无效**：它只统计区域槽里的页号，页表帧不在区域槽里，恒计数 0，别名看不见 |

结论：**主路径上没有"漏加计数"的明面错误**，H2 未被坐实。但也必须诚实：引用计数类缺陷常在**时序交错**中现形，纯静态读码证明不了它不存在。这条正是"需要动态证据"的核心理由之一。

### 4.3 H3（新帧未清零）——一条常量就把整类猜想砍掉

如果新页表帧没被清零，那么"读到旧数据当页表项"是自然解释，而且**值会驻留**。检查：`os/servers/vm/src/alloc_page.rs:vm_pt_alloc` 在返回前执行 `core::ptr::write_bytes(virt.0, 0, CLICK_SIZE)`，`CLICK_SIZE` = 4096 = 一整帧 = 512 个槽。清零量、清零范围都对。

进一步推论（这一步很关键）：**既然分配时整帧被写过零，那么任何非零的脏槽值只能是"分配之后"的另一次写留下的。** 于是要么存在一个分配后的写者（H6/H7），要么那次读根本没读这个槽（H8）。假设空间被压缩成三条，其中一条后来被实验处死。

### 4.4 H4（算术错）——用反汇编自证清白

对 `minix-vm` 的 `query` 起始处反汇编，确认崩溃指令是 `ld a1, 0(a1)`，且 `a1` 由 `srli a1, a2, 0x12`（取 L1 索引）→ `and` → `or a1, a5`（加窗基址）→ `add a1, a6`（加表帧基址与偏移）构成，与 `walk_read` 源码逐位一致；`0x00fffffffffff000` 是 `PTE_PPN_MASK << 2` 的正常值（3.3 节）。

结论：解析与地址算术**照实解码了输入**。输入脏，所以输出脏；算术无责 → **H4 死**。

### 4.5 H6（别名 + 脏值驻留）——被一次"活体读"当场处决

这是本案最漂亮的一次实验设计，也是最有教学价值的一次失败。

**假设预言**：如果某个旧数据持有者把数据字写进了一个正在当页表用的帧，那么该槽会**长期驻留**那个脏值——包括崩溃停机那一刻。

**实验（代号"单槽活体读"）**：正常启动、**不加 `-S`**（第 5.2 节会讲为什么），轮询串口发现崩溃后立即让调试器接入；此时 CPU 停在 panic 处理路径、处于监管态、内核窗有效，于是通过 `KERNEL_DIRECT_MAP_BASE + 物理地址` 直接读目标槽，并读整帧 512 槽。
装置：`tmp/nk4a/riscv_live_read.sh`，证据 `tmp/nk4a/gh102-live.log`。

**实测**：

- 目标槽（子根 `0x9DC37000` + `255 × 8` = `0x9DC377F8`）读出 **全零**；
- 整帧 512 槽只有 8 个非零，且**每一个都解析成内存内的合法页表项**（例如 `0x274AB401` ⇒ 页号 `0x9D2AD`、标志 `0x401`，是栈区那条腿的下一级表指针，完全正确）；
- 没有一个越出 RAM，没有一个非 8 倍对齐。

**升级实验（代号"多根活体扫描"）**：担心"只扫一张表不够"，于是把当时报告出的**全部 12 个进程页表根**各扫 512 槽（装置 `tmp/nk4a/riscv_roots_scan.sh`，根列表与结果在 `tmp/nk4a/gh103-scan.log`），判据同样是"非零且解出的物理地址 ≥ `0xA000_0000`"：**12 × 512 = 0 命中**。

**结论**：**没有任何已知页表根里存在耐久脏槽** → H6 死（"驻留"这一半被证伪）。快照路线的两次独立实验（内存转储全扫 + 停机活体扫）互相印证。

> **方法论要点二：证伪"驻留"不等于证实"瞬态写者"。** 这两者之间还夹着第三种可能：**读的根本不是这个地址**（H8）。本案后来正是在这里翻车（3.5 节的对齐矛盾）。写下这条是因为人在"排除了所有其它可能"时会本能地把剩余选项当结论。

### 4.6 H7（真瞬态写者）——现在的地位与它的麻烦

排除法剩下的主假设：某个写者把越界值写进槽，又在崩溃停机之前被抹掉/或该槽随后被合法写回零。支持它的旁证：`reuse-DATA` 命中帧与页缓存数据帧相邻一簇（`0x9D2A–0x9D2E` 一片）、崩溃时 `0x800c` 那条进程根为 `0x9DC37000`、以及大页分支会造出非对齐地址的巧合。反对它的证据：目前**没有任何观测能看见这个写者**，而且它必须解释"为什么写进来的值是 `真帧 + 512 MiB` 这种结构化形状"（3.2 节）——纯数据踩一脚通常是随机比特，不会恰好等于内存容量。

### 4.7 H8（读者错配）——尚未排除，且被 3.5 节加强

三个具体变体，都可以零成本先验：

- **变体一：喂错虚拟地址。** 崩溃那次走表来自 `os/servers/vm/src/cow_exec_pf.rs:sync_slot_pte`，它这样算地址：
  ```rust
  let vaddr = VirBytes((region.vaddr.0 + offset.0) & !(PAGE_SIZE as u64 - 1));
  let result = match pt.query(vaddr) { ... }
  ```
  实测崩溃走的那个虚拟地址落在 `0x3FFFFDFB2C` 一族（`stval` 低位 `0xB2C` 与现场寄存器 `x2/x5 = 0x3ffffdfbXX` 逐位吻合）。要问的是：**这个值是子进程区域表里的合法用户地址，还是虚拟内存服务器自己的某个调试/窗口指针？** 若是后者，那么"拿子进程的表根去走一个不属于它的地址"就会落到没有映射的槽上，读到那帧上一生命周期留下的东西——不需要任何"写坏内存"的假设。
- **变体二：喂错表根。** 走表用的根是否确为被服务进程当前生效的根（发放/改写根的代码散在 `os/servers/vfs/src/exec_worker.rs`、`os/servers/vm/src/fork.rs`、`os/servers/vm/src/vm_server.rs`）。静态审计里已知端点的根发放都正确，但崩溃那条腿所属的端点未必在其中。
- **变体三：窗自身的翻译不可靠。** 通过窗读一个物理地址，前提是"窗的页表把 `窗基址 + X` 映到 `X`"。如果窗自身的某级表项有问题，读出的值就不属于那个物理帧——这足以同时解释"停机扫描干净"和"崩溃瞬间读脏"，而且把脏值来源换成了**别处的合法数据**（自然解释 3.2 节的结构化形状）。

> **方法论要点三：每当"瞬态"这个词出现，先自问一遍：是值瞬态，还是地址（我认定的地址）不稳？** 本案目前两条都还开着，而区分它们只需要一条断言，不需要任何外部工具（见待办 T1/T2）。

## 第 5 章 观测手段的能力边界（本案最独特的收获）

追到这一步，真正的难点已经不是"想不出假设"，而是**没有一把不改变现场的尺子**。这一章把每种手段的物理限制、实测表现、以及"它的负结果能证明什么、不能证明什么"写清楚。

### 5.1 内存快照与停机活体读

| 手段 | 装置 / 证据 | 能看到什么 | 看不到什么 |
| --- | --- | --- | --- |
| 全内存转储后离线扫 | QEMU 监控命令转储 RAM，再按位解析每个页表根（证据：`tmp/nk4a/ram73.bin`） | 停机时刻是否存在耐久脏槽（实测：0 个） | 停机之前发生过什么 |
| 停机瞬间活体读单帧 | `tmp/nk4a/riscv_live_read.sh`（`gh102`） | 同上，且能定位到具体槽 | 同上 |
| 停机瞬间扫全部已知根 | `tmp/nk4a/riscv_roots_scan.sh`（`gh103-scan.log`，12 根 × 512 槽） | 排除"脏槽藏在别的根里" | 同上 |

**边界所在**：这三者都只能对"驻留"做证伪。它们的负结果是可靠的（三种独立视角互相印证），但它们对"瞬态"只做**间接**推断——前提假设是"我们读的地址 == 崩溃时读的地址"。3.5 节的对齐矛盾正是对这个前提的质疑。

### 5.2 观测者效应：本案实测过的四种干预，四种不同现场

这是本案最反直觉、也最该被后来的读者记住的一节。同一份二进制（缺陷指纹本应确定）：

| 运行方式 | 崩溃指令地址 | 崩溃访问地址 | 指纹族 |
| --- | --- | --- | --- |
| 裸启动（无任何调试通道） | `0x3abec` | `0x10BD28CB2C` | 主指纹 |
| `-S` 从头挂起 + 继续 | `0x3ac1a` | `0x409D28BB20` | 第二族 |
| 正常运行 ~2 秒后接入调试器再继续 | `0x3ac1a` | `0x409D28BB20` | 第二族 |
| 在走表函数里加一次"读回自检"探针 | 崩点与崩因**都变**（该实验已回退） | — | — |

两条硬教训：

1. **暂停/恢复本身改变本案**：崩溃点从一条指令挪到另一条、脏值换一族。合理推测是缺陷与"计时器中断 / 调度"同页表填写交错，任何时基扰动都会换结果。这条推测**未被证实** [待验证]。
2. **在生产代码路径里加读，等于改代码**。第 3 条表格那一行是本案例外：为了抓现场加的一次额外走表检查，把缺陷变成了另一个缺陷（崩溃点、寄存器都不同），实验因此作废并回退。

### 5.3 热路径条件断点的性能墙

尝试在下降过程的多个读点上设带条件的断点（条件里判断解出的物理地址是否越出内存上限），实测在 500 秒内只推进到串口第 11760 行（完整启动约 19694 行）。原因不是调试器坏了，而是**每次访存都要经调试通道回到主机求值条件**，往返开销压垮了模拟速度。装置记录：`tmp/nk4a/riscv_tmux_gdb.sh`、`tmp/nk4a/riscv_gdb_multisite.sh`。

**结论**：热路径上的条件观测必须走"在被观测系统内部完成判定"（插件、代码内台账），不能走"每事件回到外部求值"（gdb 条件）。这条结论直接决定了第 6 章两条主攻路线的形态。

### 5.4 硬件写观察点：现在的"不可行"结论要打上一个问号

既往结论是"在本机 QEMU 8.2.2 的 riscv 软件模拟上，硬件写观察点对裸物理地址和窗口虚拟地址两种写法都不触发"。**这里有一处需要复核的算术**：

```
目标槽物理地址           0x9DC377F8
窗口虚拟地址（正确）      0x10_9DC3_77F8   = 0x0000_0010_0000_0000 + 0x9DC377F8
窗口虚拟地址（内核窗）    0xFFFF_FFC0_DDC3_77F8
既往实验使用的地址        0x1_9DC3_77F8   ← 等于 1<<32 + 物理地址，不属于任何一扇窗
```

证据：`tmp/nk4a/riscv_watch_9dc377f8.sh`、`riscv_watch_auto.sh`、`riscv_watch_dm.sh` 里写着 `DMV=0x19DC377F8  # = 1<<36 + PHY`——注释里的公式对，字面值少了一位零（`1<<36` 是 `0x1000000000`，不是 `0x100000000`）。

这个错误地址足以解释既往两个"负结果"，而**不必**借助"软件模拟不支持"这个更强结论：

- `Cannot access memory at address 0x19dc37ff8`：那个地址本来就没人映射；
- 观察点从不命中：客人压根没访问过那个地址。

复核动作（待办 T3）：用 `0x10_9DC3_77F8` 与 `0xFFFF_FFC0_DDC3_77F8` 两形**同时**设点，并保留一个控制位（`0x10_9DC3_7FF8`，执行链必写的相邻槽）来验证观察点机制本身是否可用。预期：控制位命中即说明机制可用，此时目标位是否命中才成为有效结论。注意软件模拟下的观察点通常按**虚拟地址**匹配，所以"裸物理地址那一形"天然不会命中，那一形需要另一套地址语义（或干脆放弃）。

### 5.5 一条真实修好的弯路：陈旧探针在用户态发超级调用

本案曾长期被一个**假的**崩溃牵着走，值得单独记录，因为它同时解释了"为什么有些日志不可信"。

机制：架构层走表代码被内核（监管态）和虚拟内存服务器（用户态）**共用**。某些本该"用后即滚"的调试探针在打印时走了早期控制台，而 riscv64 的早期控制台后端是超级ervisor 调用接口（SBI）的字符输出——它靠一条从用户态发往监管态的 `ecall` 实现。**用户态发出这条调用，会被内核当成一条进程间通信消息处理**：目的地址字段取到了字符本身，消息指针是空，于是拷贝失败、给用户态进程投递致命信号。结果就是"探针一打，被测对象就被自己打死"。

- 崩溃现场：出错程序计数器处的指令序列是 `li a7,1; li a0,<ASCII>; ecall`；解码出的字符串与探针字面量逐字节吻合。
- 修复：删除两处陈旧探针（成修提交 `f90416cc9`）。
- 后果：这条链一断，原本被它更早杀死的**真实缺陷 (A)** 才裸露出来。也就是说，本案前半程追的那些症状属于幻影。

> 这一节对读者的可迁移价值：**共用代码里的日志语句是行为的一部分**。任何 `no_std` 内核项目都要问一句：这条打印在每种特权级、每种上下文（中断里、空闲循环里、服务进程里）分别做了什么？

### 5.6 记录回放

尝试用 QEMU 的指令计数与时基锁定模式做记录（`-icount` + `rr=record`），希望之后确定性重放、多次反复插桩。实测：本机机型 + 固件 + 模块装载组合下，记录模式启动即退出、无记录文件产出 [待验证：可能需要额外的确定性设备配置]。这条路暂时搁置，是插件路线（6.3）被抬为主攻的直接原因。

| --- | --- | --- | --- |

## 第 6 章 三条往前走的路

### 6.1 路一：零安装的两步复核（先做，成本最低）

1. **复核 3.5 的对齐矛盾（待办 T1）**：反汇编 `minix-vm` 崩点前后各 0x80 字节，确认那次访存到底属不属于 `walk_read` 的页表项读取。若它属于"把解析结果加页内偏移后再访问"的数据腿，整个"页表帧被写坏"叙事要重画，本案立刻从"抓瞬态写者"转成"查谁喂了大页形状的项/错单位地址"——那是纯静态可查的。
2. **复核 5.4 的观察点实验**：用正确窗地址重跑，带控制位判读。

两步都不需要安装任何东西，且都可能直接定根因。

### 6.2 路二：把"谁写了这个槽"变成软件可记录的事件（写者台账）

思路：**放弃从外部抓，改为让被测系统在写下的那一刻自己登记**。与"加读探针"的关键区别是——台账只在**写侧**动（写页表项的路径数量有限，扰动面小），不在读侧新增访存，因此不会像 5.5/5.2 那样把现场改飞。

设计要点：

- **登记点**：`os/arch/src/riscv64/paging.rs:write_pte_dm`（唯一写页表项的漏斗）。增加一个固定容量环形缓冲，每项记 `（序号, 物理地址, 写入值, 通道, 写者标记）`。`no_std` 下没有可靠回溯，因此写者标记由各调用点显式传常量（`map`/`remap`/`unmap`/`update_flags`/`walk_alloc`/根表建立……数量有限，一次改完）。
- **数据写侧的交叉检查**：MINIX 式页缓存与 VM 堆的数据写路径在写前查 `PT_SEEN` 位图（该位图已存在，见 4.1），若"我要写的这帧当前登记为页表帧"则记一条异常事件。**这不需要新位图，只需把已有位图从"分配时查"扩到"数据写时查"**——4.1 表里那个盲区（数据侧写不查 `PT_SEEN`）正是当初检测器漏掉别名的原因。
- **读侧（崩溃那一刻）**：只在已经决定判死的分支里，打印该槽的台账末尾若干条 + 实读值。**只读台账内存，不读客户机页表**，避免新增访存扰动。
- **判读树**（这是台账方案真正的价值：它把三种假设分开）：
  - 台账里该槽最后一次写是**合法页表项**，而实读值越界 ⇒ 存在台账之外的写者 ⇒ 数据腿踩页表帧（别名，H6/H7 的"写者"支）；
  - 台账里该槽**从没被写过**（新帧零初始化后未写），而实读值非零 ⇒ 写者同样在台账之外，但更可能是**读的不是这个地址**（H8）；
  - 台账里出现"数据写命中页表帧"异常事件 ⇒ 别名直接坐实，且事件里带写者标记，可立即归因。
- **门控与代价**：诊断构建专用编译开关（不进生产镜像）；环形缓冲静态尺寸，避免堆分配引入新变量。架构层已有供测试注入的窗口机制（`paging.rs:channel_to_ptr` 的 `runtime-window` 分支），同一形态可让这个台账在**主机单元测试里复现**（不需要真机），这是它比插件更好的地方。

### 6.3 路三：QEMU 插件（需要装东西，见附录 D）

插件是唯一"零暂停、零改客户机码、每访存求值"的外部手段。骨架已在仓库里：`tmp/nk4a/watch_store_plugin.c` + `watch_store_plugin.build.sh`（作者已诚实标注**未编译验证**）。

**符号校准（已对照本机 8.2.2 真实头文件与导出表核实）**

依据：`/tmp/qemu-src/qemu-8.2.2+ds/include/qemu/qemu-plugin.h` 与同源码树 `plugins/qemu-plugins.symbols`（后者是模拟器实际导出的 43 个符号，是最权威的可用面）。

**已实测的运行细节（三条；不注意就会把"没抓到"读成"没人写过"）**

1. **必须带 `-d plugin`。**输出通道函数 `qemu_plugin_outs` 的实现就是按插件日志掩码写日志（锚点：本机 QEMU 8.2.2 源码 `plugins/api.c:qemu_plugin_outs`）。实测对照：同一份 `.so`，带 `-d plugin` 才打得出安装横幅，不带则**全程静默**（可再加 `-D <文件>` 定向输出）。本案最难识别的假阴性就是这种静默。
2. **命令行参数到达插件时长什么样**（锚点：`plugins/loader.c:plugin_add`）：`arg=X` 且 X 内部不含 `=` 时，会被改写成 `"X=on"` 作为**一个**条目，并额外打一句废弃警告；而**逗号在选项解析层就已经切过一刀**，所以"一个 `arg=` 里塞逗号分隔多帧"不会原样到达插件——后一段会被当成独立键、值为空，最后变成 `"0xB="` 这种形状。因此解析侧要同时容忍条目末尾的 `=on` / `=`，并把**解析到的每一帧地址都打回安装横幅**（只报帧数不够——静默丢帧时你看不见）。
3. **先做空载冒烟，再花真实启动的时间**（启动到崩要几十秒到数分钟，而"能不能加载"8 秒就能验）：

```bash
# 空载冒烟：证明 .so 能被加载、符号解析通过、输出通道打得出来
timeout -s INT 8 qemu-system-riscv64 -machine virt -m 16 -display none \
  -serial none -monitor none \
  -plugin file=./watch_store_plugin.so,arg=0x9dc37000 -d plugin
# 期望：一行安装横幅（含逐帧列表）；看不到就先别去 boot 真实镜像
```

**建议的设计调整**（比现骨架更适合本案）：

1. 订阅**读和写**（`QEMU_PLUGIN_MEM_RW`），因为本案要的是"读的那一瞬间"完整时序，不只是写者；
2. 过滤范围放宽到**整个 4 KiB 页表帧**而不是 8 字节槽，避免"写的是相邻槽、越界值来自邻槽"这类漏检；把帧号匹配放在回调最前面（一次位与），命中才继续；
2b. **宽口径层不要做成"大量打印"，要做成"两级记录"**：

   - **第一级（常开、极轻）：按页帧做摘要，不逐条打印。** 命中条件全部满足才计一次：`是写` ∧ `访问长度 == 8` ∧ `虚拟地址 ∈ VM 直接映射窗 [0x10_0000_0000, 0x14_0000_0000)` ∧ `物理地址在 RAM 内`。每个页帧只维护 `（首次写者指令地址, 末次写者指令地址, 末次虚拟地址, 计数）`，用无锁原子更新（多 vCPU 并发下计数与末次值允许轻微竞争，取证够用）。**尺寸可以提前算死**：512 MiB ÷ 4 KiB = 131072 页，每项 32 字节 ⇒ 约 4 MiB 静态表，插件侧完全放得下（内存上限见 `os/servers/vm/src/alloc_page.rs:RAM_TOP_PFN`）。
   - **第二级（建议默认就带）：全局小环形缓冲。** 环形缓冲记最近 N 条（例如 4096 条）命中事件的 `（序号, vCPU, 读或写, 长度, 指令地址, 虚拟地址, 物理地址）`，停机时把与嫌疑页帧相关那段吐出来。这一级解决一个只有摘要解决不了的问题：**"末次写者"很可能恰好是那条合法的写**，真凶在它之前——单靠 first/last/count 会把它盖掉。只有摘要也要得，因为本案复现确定，可以"第一轮找热点页、第二轮展开"；但默认带一条小环形缓冲几乎不额外花成本，一轮就能拿到时间线。
   - **两条过滤条件其实等价，不必都写**：窗基址本身 4 KiB 对齐，所以在窗内 `虚拟地址 % 8 == 0` 与 `物理地址 % 8 == 0` 是同一件事，留一条即可（只有对非窗访问两者才有区分力）。
   - **覆盖面必须写清，不要过调口径**：这层捕获的是**虚拟内存服务器经 `VmDm` 通道**的 8 字节写；**不覆盖内核经 `KernelDm` 通道**的页表写（两条通道见 `os/arch/src/riscv64/paging.rs:PteChannel`，内核窗基址见 `os/arch/src/arch/direct_map.rs:Riscv64DirectMap`）。本案现有证据（崩溃发生在用户态的虚拟内存服务器、回栈指向它自己的函数）把嫌疑压在 `VmDm` 一侧，所以先只开这扇窗是对的；若后续要怀疑内核侧写者，再加一层 `[0xFFFFFFC0_40000000, +RAM)` 的内核窗。
   - **它的完备性来自"不猜帧号"，不是来自"打印得多"**：8 字节对齐的普通数据存储（结构体写入、拷贝循环）同样会命中这一层，所以它是"页帧级摘要台账"，**不是**"页表项写过滤器"。真正的过滤力在第二级展开后与已知页表帧集合求交。这一层本质上就是把第 6.2 节的台账搬到模拟器侧，两者可以各自独立跑，相互对账；
3. 每条命中打印 `（事件序号, vCPU, 读/写, 指令虚地址, 虚地址, 物理地址, 长度）`；本机导出表里还有 `qemu_plugin_insn_disas` 与 `qemu_plugin_insn_symbol`（锚点：`plugins/qemu-plugins.symbols`），可以在插件内直接打印反汇编与符号，省掉事后反查；
4. **插件拿不到写入的具体值**（已核实：本机 43 个导出符号里没有任何取值接口）。缓解办法：插件先定出写者指令，再在对应代码点加一次性台账登记（与 6.2 拼起来正好闭环）；
5. 性能预期：每条访存一次本地函数调用。本机裸启动到崩约 8 秒，即便放大 20–50 倍也在数分钟内，远好于 5.3 的调试通道往返；
6. **自校验**：先用一个控制目标（执行链必写的那一槽 `0x9DC37FF8`）验证插件确实能命中；命中不了控制位就不要相信目标位的负结果。

### 6.4 选择与并行性：插件是最后一张牌，不是第一张

推荐顺序：**T1/T1b（反汇 + 算术定位真靶，半小时，零安装）→ T2（虚拟地址/表根配对）→ T3（用正确地址重做观察点）→ T4（写侧台账）→ 最后才轮到插件**。

上插件的**升级条件写死在此**（四条全满足才值得开专工开发取证基础设施）：

1. T1/T1b 确认现场确实是页表项读取，且靶地址已重新定准；
2. T2 确认喂进走表的虚拟地址与表根配对语义合法（读者错配已被排除）；
3. T3 确认观察点机制本身可用（控制位能命中）而目标位仍抓不到；
4. T4 的客户机内台账跑过一轮，仍无法定位写者。

为什么这个顺序对工具本身也重要：如果靶地址本身错了（3.7 正在质疑这一点），那插件参数 `arg=0x9dc377f8` 只会带回"没人写这一格"的空结果，而这个空结果很容易被误读成"插件也无能为力"——先校准靶地址再上插件，否则工具越精密，误导越便宜。

三条不互斥：一旦真靶定准，插件能给"零扰动的完整访存时序 + 写者指令（本机 8.2.2 还能直接输出反汇与符号）"，台账能给"写了什么值、从哪个调用点"，二者合起来才是完整证据链。

## 第 8 章 方法论沉淀（可迁移到任何内核疑难内存缺陷）

1. **先算自己的常量，再谈"被破坏"。** 本案两次把正常中间值当成内存破坏（掩码值、窗口地址），都靠手算常量翻案。
2. **检测器必须分级，并核对自己的覆盖范围。** "零命中"有三种含义：真的没发生、检测器看不见、检测器边界不足。位图覆盖范围、旁路写入者（比如进程自己的堆）、检查时机（只在分配时查、不在数据写时查）都会造成第三种。
3. **能用不变量判据就别用日志。** "槽偏移必为 8 的倍数"这类算术不变量比任何打印都硬；本案最难解的矛盾（3.5）恰恰是从这条不变量算出来的。
4. **证伪驻留不等于证实瞬态。** 排除法要列全第三选项：值瞬态、地址（我认定的）不稳、观测被扰动。
5. **量化观测者效应。** 把每种干预方式和它产生的现场列成表（5.2），才知道哪个负结果可信。
6. **不要在生产路径里加读来抓 bug。** 读会改布局、改时序、甚至因特权级问题制造幻影（5.5）。要抓就抓"只登记不改行为"的手段（台账、插件）。
7. **未坐实不成修。** 本案曾在分配器里加"拒发活帧"的补丁，事后证明是空修，还差点污染另两个架构的启动。宁可停在"知道工具不够"，也不要用猜测换进度。
8. **症状的形状就是线索。** `0xBD28C000 = 0x9D28C000 + 512 MiB` 这种"恰好等于内存容量"的差值不可能是随机撕裂，它把怀疑空间从"谁踩了内存"收窄到"谁把偏移当绝对地址用了"。
9. **"PTE 有效 + CPU 仍 fault"这类架构上不可能的矛盾，第一步先算地址规范性（canonicality），再怀疑页表、再怀疑模拟器。** 本案用四个版本（8.2.2/8.2.10/9.2.4）同形、以及 Sv39 的位 63:39 判定走完了这一步：地址 `0x7fff_ffff_f000` 之上的一切都在 CPU 可翻译范围之外，与页表无关（§10.11）。
10. **软件走表 ≠ 硬件走表。** guest 侧"我自己走一遍都对"的自证无法替代硬件语义（地址规范性、A/D 位、权限位组合、特权级）；取证时把这些语义差列成清单，逐项问"我这一遍检查了没有"——本案全套 in-guest 自检都漏了规范性，因为软件走表按位取索引、天然不看高位。
11. **跨架构共享的地址常量必须在类型层分架构。** 48 位 LP64 风格的 `0x7fff_ffff_f000` 搬到 Sv39 就是不可寻址的死值；把这类常量收拢成单一权威（`minix_types::USER_STACK_TOP`）是防复发的结构性手段，而不是把字面量改一处。
12. **串口取证解析要容忍行内交织与前导空格。** 本案的决定性一行 `nk4a: fill-root …` 被并发输出切碎成 `"  4a: fillt oo …"`，按整串匹配会把它计成"零输出"，从而漏掉唯一的对账数据（§续-338 侦察段）。
13. **测试的语义边界止于被测模块：它证明「这一条实现路径对该架构的认知正确」，不证明「所有产生同一语义的路径都使用同一权威」。** boot-shim 的 riscv 架构断言测试一直通过，而 VFS exec 的缺省栈顶是错值——两条路径产生同一个语义（用户栈顶），测试只覆盖其一。对症修法是把语义收敛到单一权威常量、全部消费者引用它，再把架构约束以编译期断言钉在权威本身上（§10.12）。

```
控制位（执行链必写）0x9DC3_7FF8 → VM 窗虚地址 0x10_9DC3_7FF8
页表项掩码        0x003F_FFFF_FFFF_FC00；其 <<2 = 0x00FF_FFFF_FFFF_F000
主指纹            sepc 0x3abec, stval 0x10BD28CB2C（低 12 位 0xB2C，不是 8 的倍数）
第二族指纹        sepc 0x3ac1a, stval 0x409D28BB20（bit38 置位，低 12 位 0xB20 是 8 的倍数）
伪帧与真帧之差    0xBD28C000 − 0x9D28C000 = 0x2000_0000 = RAM 容量
崩溃地址候选      0x7FFFFFFFE000（页对齐，偏移 0x000，与现场不自洽；i2/i1/i0 = 511/511/510）

表槽低 12 位候选  0x7F8 / 0xFF8 / 0xFF0 / 0xEF8（永远不等于 0xB2C）
```

## 附录 C 术语表

| 术语 | 含义 |
| --- | --- |
| 微内核 | 内核只做最少量工作（消息传递、调度、中断），文件系统与内存管理都在用户态进程里 |
| 虚拟内存服务器 | 负责替进程补页的那个用户态服务进程（代码里的 `vm`） |
| 监管态 / 用户态 | RISC-V 的两个特权级；部分指令（如地址转换缓冲失效）只在监管态合法 |
| 页表项 | 表里的一格（8 字节），要么指向下一级表，要么描述一个真实页面 |
| 叶 / 中间项 | 叶直接给出页面；中间项给出下一级表的物理地址 |
| 直接映射窗 | 把物理地址平移成虚拟地址的一整段连续映射，用来在没有内核特权时访问物理内存 |
| 页帧 | 一个 4 KiB 物理页面 |
| 启动标记行 | 本文所追踪目标的完成判据：`minix-rs rc: minimal boot script marker` |
| 瞬态 / 驻留 | 脏值只在被读那一刻存在（瞬态），还是长期留在内存里可被事后读到（驻留） |
| 引用计数 | 一帧物理页被多少条映射共同持有，决定它能否被回收 |

| 版本 | 内嵌 OpenSBI | boot 推进 | (A) 判读 |
| --- | --- | --- | --- |

### 10.8 统一机制候选（当前最优解释）

全部症状用「QEMU softmmu 平移缓存与 RAM 内容不一致」统一解释：

| 症状 | 机制 |
| --- | --- |
| (A) walk 崩：VM 读自己页表槽读到越 RAM 值 | QEMU 平移把 VmDm 窗 VA 映到错误物理地址→读到别处数据（自然解释结构化形状：bit38/合法偏移都是**别处的合法数据**） |
| rc refault：PTE 有效但 CPU 反复故障 | QEMU TLB 缓存了 fill 前的 NP 平移；fill 写 RAM 但 CPU 的后续 walk 命中旧缓存 |
| no-region 间歇 | VM 读自身 BTreeMap（region 簿记）时读到错误 RAM 内容→键序/值偶发错乱 |

### 10.11 §续-338 定案（2026-10-04）：rc 循环的根因是**栈顶地址在 Sv39 下不可翻译**——已修复并验证

> 本节是 rc 循环症状（10.2/10.5 里的「(A) 四要素」现场）的终局。它不推翻第 1–9 章的排除结论，但把 10.5/10.8 的解释整体替换掉。

**一句话**：rc 反复 store fault，不是页表坏了、不是根错了、不是 sfence 没生效、更不是模拟器缺陷——**故障地址 `0x7fffffffef90`（以及整个栈 region `[0x7fffffbff000, 0x7ffffffff000)`）超出了 Sv39 的用户地址上限 `0x3f_ffff_ffff`（2^38−1），属于非规范地址；CPU 对它的每一次访问都必然报存储页故障，页表里有什么完全不影响判决**。guest 侧的全部自检（VM 的 `walk_read`、内核 KDM 爬链、VM 的 `pt.query`）都是软件走表，只按位取索引、不做规范性检查，所以现场自洽得「架构上不可能」。

**证据链（可复核）**

1. **判别探针**（本 session 新增于内核 trap 分支，riscv-gated，用后即滚）：26 次循环故障全部 `sepc=0x16d9e`（用户码区）、`sstatus` 低位解析出 **SPP=0（陷阱来自 U 态）**、`sp=0x7fffffffef98`。U 态存储 + 可写 U 叶项（`0x…DF`）+ 根一致 ⇒ 若地址合法就不可能故障。
2. **QEMU 侧判决**：`~/src/qemu/qemu-8.2.10/target/riscv/cpu_helper.c:get_physical_address`（first_stage 分支）第一道门就是规范性：`masked_msbs = (addr >> 38) & 0x3FFFFFF` 必须为 0 或全 1，否则 `TRANSLATE_FAIL`。`0x7fffffffef90 >> 38 = 0x1ff` ⇒ 直接失败——**走表根本不会开始**。
3. **算术复核**（`python3`）：`0x7fffffffef90`、`0x7fffffffe000`、栈 region 两端全部非规范；对照 `0x3ffffc5cc0`（旧 rc 栈）、`0x3fffffefe0`、`0x10bd28cb2c`（VM 窗）全部规范。
4. **代码溯源**：VFS 的 exec 入口把栈顶硬编码为 `0x7fff_ffff_f000`（x86-64 风格；注释自陈读腿未接线、登记 NS5-B），而 boot-shim 的 riscv64 值 `0x3f_ffff_f000` 是对的——**「boot 进程全活、exec 出来的进程死」这个形由此解释**。
5. **干预验证**：修复后单跑（halt-dump p7b）打出 `minix-rs rc: minimal boot script marker`（exec=13 / no-region=0 / kill=0 / panic=0），p5 故障族从 `0x7ffff...` 迁移为 `0x3fffff8/9/a...`（新栈的普通按需填页），全日志 `0x7fffff` 族零命中；正式门 `os/qemu-tests/test-riscv64-boot-full.sh` 报 `PASS riscv64 full boot (marker reached)`。

**修复**（三处、一个单一权威常量）

- `os/libs/minix-types/src/types/boot.rs`：新增 `USER_STACK_TOP`（riscv64=`0x3f_ffff_f000`，其余架构=`0x7fff_ffff_f000`），文档写明 Sv39 规范性与本案史——**跨架构地址常量必须在类型层分架构**。
- `os/boot-shim/src/opensbi_helpers.rs`、`os/boot-shim/src/uefi_helpers.rs`：两处 `build_kernel_info` 改引该常量（值不变者行为不变）。
- `os/servers/vfs/src/main_loop.rs`：exec 的 `DEFAULT_USER_SP` 改引该常量，并写明故障史。

### 10.12 分析者（GPT）三轮意见：定稿句、测试语义边界与地址常量清扫

> 本节收录外部分析者在 §10.11 定案后的意见中可沉淀的三点：结论的定稿表述（采纳为 rc 循环症状的正式表述）、测试的语义边界（补入第 8 章第 13 条）、以及一次机械的地址常量清扫（登记为第 9 章 T13）。

**结论定稿句**（取代「QEMU softmmu 与 RAM 存在分歧」式的表述）：

> guest 生成了 Sv39 非规范用户虚拟地址；硬件翻译在页表遍历开始之前即拒绝该地址。guest 侧的软件页表遍历不执行规范性检查，于是产生「页表项全部有效、硬件却反复报故障」的假象——全链证据都为真，但它们证明的不是取证当时以为的命题。

**两套检查的前置条件不同**（软件自检注定看不见这类缺陷的机制原因）：

```
硬件语义：VA 规范？ ──否──→ 存储页故障（遍历不开始）
                    └──是──→ 页表遍历
软件走表：VA → VPN[2] → VPN[1] → VPN[0] → 读 PTE（无规范性门，直接开走）
```

`0x0000_7fff_ffff_f000` 的 bit 38 = 1 而 bits 63:39 = 0，两族不一致 ⇒ 非规范；Sv39 低半区合法上限为 `0x0000_003f_ffff_ffff`，页对齐栈顶应取 `0x0000_003f_ffff_f000`（权威常量的 riscv64 分支，`os/libs/minix-types/src/types/boot.rs:146`）。同一地址，软件一路走到底、硬件第一步就拒——§10.5「四要素」现场之所以能同时成立，机制即此。

**测试语义边界**：boot-shim 的 riscv 腿带有架构约束测试（§续-338b 评审涉及的两条 `user_sp < 2^39` 断言）且一直通过；但该测试证明的是「boot-shim 这一条实现路径对这个架构的认知正确」，不是「系统中所有产生同一语义的路径都使用同一权威」——VFS exec 的缺省栈顶（`os/servers/vfs/src/main_loop.rs` 的 `DEFAULT_USER_SP`，§10.11 溯源 4）是另一条产生同一语义的路径，测试覆盖不到它。大型系统重写中这类「语义多头」缺陷的对症修法，不是给每条路径各补一个测试，而是把语义收敛到单一权威常量、全部消费者引用它，再把架构约束以编译期断言钉在权威本身上（`os/libs/minix-types/src/types/boot.rs:154-163`）。方法论补入第 8 章第 13 条。

**Sv39 地址语义清扫（登记为 T13）**：同款风险在同一代码库已现身三处——boot-shim 两处 builder 的值正确且有测试；VFS exec 的错误值（本案，§10.11 修复）；`os/servers/vm/src/mmap.rs:212` 的 `MMAP_TOP = 0x0000_0200_0000_0000`（2^41）在 Sv39 下越界，当前不可达（`find_slot` first-fit 先命中栈下缺口，`os/servers/vm/src/mmap.rs:271`；仅当出现大于约 251 GiB 的无 hint 请求才会触及尾缺口）。三处同源说明这不是偶然笔误，而是「x86-64 心智模型的地址常量」这一类别的系统性风险——这类缺陷的危险不在复杂，而在看起来太合理。清扫动作是纯机械的：全库检索字面量族（`0x7fff…`、`0x8000…`、`1 << 47`、`1 << 41`）与全部「用户空间最高地址 / mmap 上限 / 栈顶 / 守卫页 / 地址空间边界」语义的常量，逐个确认从架构定义导出（单一权威常量 + 编译期断言），而非就地字面量。
