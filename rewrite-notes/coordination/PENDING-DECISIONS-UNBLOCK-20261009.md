## U-1 内核包的替身（mock）默认特性：摘除方式与形态对账机制

### 一句话

裁决 `PD-29` 已定方向（从默认特性里摘掉替身），实测直接摘会让 `cargo build --workspace` 在三处类型错误上确定性失败（2026-10-09 于 `65195776b` 后 HEAD 干净 target 复现；哈希勘误：早稿误写 `651957b51`，经 git 核实该名不存在，正确快照为 `65195776b`）；本轮已把根因实验钉死为**成员包自身默认特性**（`minix-arch` 自己 `default = ["runtime-window"]`、`minix-plat` 自己 `default = ["mock"]`），修复方案随之改为"三个包的默认一起摘空"，并已在 scratch 树验证工作区构建与 mock 测试腿双双转绿。待裁决的只剩这个修订版方案的批准。

### 背景（自包含）

本项目的内核包 `os/kernel` 有两个构建形态：

- **宿主测试形态**：体系结构层（`minix-arch`）与平台层（`minix-plat`）走替身实现，让约八百枚内核单元测试能在开发机的 x86_64 宿主上编译运行。替身由特性 `mock` 控制。
- **生产形态**：`--no-default-features`，体系结构与平台走真实实现（riscv64 / aarch64 的 `unknown-none` 目标），这是唯一装机消费者（`os/kernel-image`）使用的形态。

当前 `os/kernel/Cargo.toml:30` 是 `default = ["mock"]`，即**默认构建的是替身形态**。这正是设计债 `SD-30` 的担忧：宿主上测试的二进制与真机上运行的二进制不是同一个形态，"测试全绿"证明的是替身行为而不是生产行为（假绿风险）。裁决 `PD-29` 采了"从默认里摘掉"的方案，并且硬性顺序是先建持续集成双腿（已完成：宿主默认形态测试腿 + x86_64 生产形态交叉编译腿，`.github/workflows/kernel-tests.yml` 两腿常驻）。

**摘除失败的实测现场**（台账 §2 `P-ALL-10` 行原记于快照 `9f752834c`；2026-10-09 GLM 会话在更新后的 HEAD 上以干净 target 复现，docker `minix-ci:1.94`、`cargo check --workspace -j 1`）：把 `default = ["mock"]` 改成 `default = []` 后，工作区构建确定性失败于 `os/kernel/src/lib.rs` 三处——

```text
error[E0308]: mismatched types --> kernel/src/lib.rs:1295
    store_protection(prot)  — expected X86_64Protection, found MockProtection
error[E0308]: mismatched types --> kernel/src/lib.rs:1377
    store_trap_entry(trap)  — expected X86_64TrapEntry, found MockTrapEntry
error[E0599]: no function or associated item named `default` found
    for struct `MockDirectMap` --> kernel/src/lib.rs:1844
    let access = minix_arch::CurrentDirectMap::default();
```

即：内核自己的 `mock` 特性关掉后编译的是生产形态代码体，而它拿到的 `Current*` 别名却是替身类型。单包 `cargo check -p minix-kernel --no-default-features` 则通过（已复跑确认）。

**根因机制（2026-10-09 实验改写，原稿的"开发依赖泄漏"定性被否证）**：

"当前形态"的别名定义在依赖包里、按依赖包**自己的**特性选择。以体系结构层为例（`os/arch/src/lib.rs:118-126`，平台层 `os/plat/src/lib.rs:112-120` 同族但按 `target_arch` 分派、替身影子更淡）：

```rust
// os/arch/src/lib.rs:118-126（节选）
#[cfg(feature = "runtime-window")]
pub type CurrentPaging = MockPaging;
#[cfg(all(not(feature = "runtime-window"), target_arch = "x86_64"))]
pub type CurrentPaging = crate::x86_64::paging::X86_64Paging;
// aarch64 / riscv64 两臂同构；CurrentProtection / CurrentTrapEntry /
// CurrentDirectMap 同款（:139-145、:187-199、:262-267）
```

关键事实链（全部一条命令可复跑，详见"讨论记录"第一轮 GLM 行）：

1. **形态开关藏在依赖包自己的默认特性里**：`os/arch/Cargo.toml` 是 `default = ["runtime-window"]`，`os/plat/Cargo.toml` 是 `default = ["mock"]`。而 `cargo check --workspace` 会把**每个成员包自身当作构建根、按它自己的 default 解析**——`minix-arch` 作为成员根本身就带着替身形态进入这一轮构建，再经特性统一涂满全图，内核的生产代码体便拿到替身类型。
2. **删开发依赖不解决问题**：把 `os/kernel/Cargo.toml` 的 `[dev-dependencies]` 整段删掉后，干净 target 重编仍三处同错（干净 target 排除了旧产物污染）。
3. **单包构建干净的原因**：`-p minix-kernel` 的解析根集只有内核自己，`minix-arch` 退化为纯依赖，而全仓 41 条 `minix-arch` 依赖边全部 `default-features = false`（tomllib 结构化穷举核对过），于是别名落在真实实现上，与生产代码体一致。
4. **激活源定位（消元实验）**：把工作区成员缩到只剩 `arch`/`plat`/`libs`/`xtask`（此时没有任何包依赖 `minix-arch`），`cargo metadata` 的 resolve 里 `minix-arch` 仍是 `["default", "runtime-window"]`——激活者就是"成员根自身默认"，不是任何依赖边。resolver = "2" 在 `[workspace]` 表内在位有效（`os/Cargo.toml:213`），与官方文档"v2 隔离 dev-dependencies 特性"的表述并行不悖——本例的泄漏面根本不是 dev-dependencies。

这不是本项目特有的坑：cargo 的成员根默认语义对"形态开关类特性"天然不友好（任何 `--workspace` 调用都会让形态开关包以替身形态入图）。Linux 内核不存在这个问题，因为 `CONFIG_*` 是单一全局配置、内核自成构建宇宙；Redox 的内核同样单形态构建。

### 为什么现在需要裁决

`PD-29` 的硬序第③步（摘默认）被这三处类型错卡住；测试保障面的两条持续集成腿已经就位（硬序第②步完成），执行线只差这一步。不裁决它，"宿主与真机形态可能不是同一个二进制"这一设计债就永远挂着。

### 方案空间

**方案 A（修订版，推荐）：三个包的默认一起摘空 + 宿主命令显式带形态 + 编译期形态对账点。**

分三小步，各一笔提交：

1. **依赖包默认摘空（真正的修复，2026-10-09 已在 scratch 树验证）**：`os/arch/Cargo.toml` 改 `default = []`、`os/plat/Cargo.toml` 改 `default = []`——成员根自身不再携带形态，"成员根默认"这条激活路径从结构上消失。**验证读数**：同法修改后干净图 `cargo check --workspace` 全绿（`CARGO_EXIT=0`），`cargo check -p minix-kernel --features mock`（宿主测试腿形状）全绿。
2. **内核摘默认（`PD-29` 原方向）**：`os/kernel/Cargo.toml` 改 `default = []`；宿主测试命令显式带 `--features mock`（`mock` 特性定义 `["minix-arch/runtime-window", "minix-plat/mock"]` 保持传递形态，见 `os/kernel/Cargo.toml:31`）；开发依赖里对替身形态的声明（`os/kernel/Cargo.toml:21-22`）随之真正冗余，一并删除；持续集成宿主腿命令同步改（`.github/workflows/kernel-tests.yml`）。
3. **编译期形态对账点（防回归绊线，采纳 GPT 第一轮意见、按其第二轮意见加宽到两包）**：内核不能直接断言依赖的 `cfg` 状态——改用**类型级形态证据**，且必须**同时覆盖 `minix-arch` 与 `minix-plat`**：三处实测错误横跨两包的形态消费面（`store_protection`/`store_trap_entry` 的消费路径涉 `minix-plat` 形态，`CurrentDirectMap::default()` 属 `minix-arch`），只查一包就给另一包留下裸奔面。实现要点：两个依赖包各自提供**能反映其当前 `cfg` 实际选择形态**的类型级标记（两态可用不同标记类型，也可用条件编译选择的 `CurrentForm` 别名——关键是对账对象必须是依赖包当前真正选出的那个形态；不得把两态标记类型都无条件公开、再只要求"任一实现某 trait"，那样证明不了别名当前选中的是哪一态）；内核在对账模块按自身 `mock` 特性**同时**写死对两个包的形态要求，交叉一旦发生报错落在这一处明确的位置。注意它只是绊线不是修复——修复是第 1 步。

- 优点：保持 `PD-29` 方向不变；默认构建路径上的交叉在源头消失（实证，保证边界的准确表述见推荐理由），不再只靠报错集中；对账点让未来任何人再制造交叉时一处定位。
- 风险（比原稿大，须如实入账）：**依赖包自身的宿主测试命令全部要补形态参数**——`cargo test -p minix-arch` 依赖 arch 自己的 `runtime-window` 默认（台账多处引用它，含 `P-ALL-01` 行的 308 枚读数），摘默认后不补参数会在宿主上编译真实实现（别名注释自陈：真实 paging 出 QEMU 即 SIGSEGV）；`cargo test -p minix-plat` 同理补 `--features mock`。文档与台账命令扫描范围因此覆盖 `minix-arch`/`minix-plat`/`minix-kernel` 三家字样。

**方案 B：撤销"摘默认"目标，改裁"默认保留 + 持续集成双腿证明两形态等价"。**

- 优点：零执行成本，两条持续集成腿已经在位（宿主默认形态腿 + 生产形态交叉编译腿）。
- 缺点：等于承认宿主测试与真机可以是不同二进制，`SD-30` 的原始担忧（替身假绿）从"结构上不可能"退化为"靠门禁兜底"；且需要显式记录推翻 `PD-29` 采甲的理由，否则下轮扫描会把"默认带替身"当缺口重报。

**方案 C：把"当前形态"从全局条件编译别名改成显式注入（泛型参数或 trait 对象传递）。**

- 优点：彻底消灭特性交叉这一类问题——形态成为显式参数而非编译期全局状态。
- 缺点：这是架构演进（须按项目三档术语标 `[ARCH: ...]` 三处一致），触及内核所有 `Current*` 消费点（数十处），改动面与风险远超本条需要；且"为漂亮提前改契约"违反项目边界条款。

### 推荐 A 的理由（修订版）

`A` 保留了 `PD-29` 已裁决的方向，且修复已经实验坐实：形态开关从"成员根默认"改为"显式特性参数"后，**默认工作区构建路径**上由成员根默认值引入的形态交叉被消除（不依赖任何人记得什么）。保证边界必须写准：cargo 的特性统一机制本身仍然存在——其他依赖边或命令行 `--features` 仍可显式启用形态特性——所以另设编译期形态对账点作为防回归绊线，把未来的再交叉收敛到一处报错；scratch 树验证的是默认工作区构建与替身测试腿这两条路径，不外推为对一切 cargo 调用组合的保证。`B`（撤销摘默认）的原始动机是"摘不动"，这一动机已被实验消解，只剩"省一次命令扫描"的安逸；`C`（依赖注入）的收益配不上成本，维持原判。原稿"宿主绿=生产绿是结构性保证还是门禁保证"的价值之问，在修订版里有了与实验对应的答案——两者只在内核自身的替身代码轨上有差别，而该轨由 `--features mock` 显式开启、由持续集成双腿分别锁死。

## U-2 调度队列自检设施（`runqueues_ok`）：删、留、还是对位 C 的门控调用点

### 一句话

Rust 侧的调度队列自检函数只被测试调用、没有生产调用方，台账把它登记为"无生产调用方的调试设施、消费者归属需人定"；但 C 真源里它**有**生产调用点——三处断言，全部在调试自检的编译开关门内。所以真正要裁决的不是"删不删这个函数"，而是**要不要把 C 的那三处门控断言一并对位移植**。

### 背景（自包含）

Rust 侧设施：`os/kernel/src/debug.rs:fn runqueues_ok_cpu`（对位 C `minix3/minix/kernel/debug.c:16` 的 `runqueues_ok_cpu`）与 `os/kernel/src/debug.rs:fn runqueues_ok`（对位 `debug.c:121/128`）。功能是遍历调度就绪队列，校验一组不变量：队头队尾成对、尾节点的后继必须为空、队列无环、进程号在界内，违反即向控制台打印具体违反项并返回失败。约三百二十行的模块，除这两个函数外还有同族的转储助手。

Rust 侧现状：全仓 `grep -rn "runqueues_ok" os --include=*.rs`（排除定义文件）的命中**全部在测试代码内**——没有任何生产路径调用它。

C 侧现状（这是关键事实）：`minix3/minix/kernel/proc.c` 有三处生产调用，全部包在调试自检编译开关里：

```c
/* minix3/minix/kernel/proc.c:1656-1658（enqueue 尾部；:1709、:1778 两处同构） */
#if DEBUG_SANITYCHECKS
  assert(runqueues_ok_local());
#endif
```

即 C 的设计是：**设施常驻、调用点常驻、默认不编译**——`DEBUG_SANITYCHECKS` 打开的构建（调试自检形态）里，每次进程入队/出队都全量校验一遍就绪队列不变量，出错立即断言；正常构建里这三处调用被预处理器整体剔除，零开销。另外 `minix3/minix/kernel/proto.h:136` 用宏把 `runqueues_ok_local` 映射到 `runqueues_ok`（单核配置下校验零号核）。

**C↔Rust 调用点对表（2026-10-09 GLM 会话完成，原 [待验证] 已闭合）**：三处 C 调用分别位于 `enqueue` 尾部（`proc.c:1656-1658`）、`enqueue_head` 尾部（`:1707-1709`）、`dequeue` 尾部（`:1776-1778`）——即每次队列变更动作完成、不变量恢复之后校验；Rust 侧对位函数为 `os/kernel/src/sched.rs:88 enqueue_queue_tail`、`:105 enqueue_queue_head`、`:130 dequeue_from_queue`。语义细节：C 的展开是 `runqueues_ok_cpu(cpuid)`，校验的是**当前执行 CPU** 的队列；Rust 移植时每个调用点应校验"被修改队列所属的 CPU"。在本树的单队列设计（`K2`/`S-6.3`：BKL 下就绪队列由锁串行化）里两者应恒等，但须在实现时逐点核实，不得未经核实直接抄 `current_cpu`（GPT 第一轮意见之二）。

Rust 侧没有对位这三处调用点，所以静态扫描看到的就是"只有测试调用"。台账原登记（§8"无生产调用方的调试设施"）把问题表述成"消费者归属需人定"，但没有记录 C 侧这三处门控调用点的事实——这也是本节材料要补的第一件事。

### 为什么现在需要裁决

这是 §8 里最后一个"消费者归属"类开口；而且它有一个隐含的语义保真问题：本项目的外部行为保持原则同样覆盖调试设施（C 的调试自检形态是一个可观察的外部行为面）。不定下来，下一轮死码扫描还会把它捞出来重新讨论一遍。

### 方案空间

**方案 A（推荐）：对位移植——设施保留，三处门控断言一并对位。**

- 给内核加一个编译期特性（如 `sanity-checks`，默认关，与 C 的 `DEBUG_SANITYCHECKS` 默认关同构）；在 Rust 侧三处对位位置（对表已闭合：`sched.rs:88/:105/:130` 三个队列变更函数的尾部）加门控断言调用 `runqueues_ok_cpu(...)`，每个调用点传入"被修改队列所属的 CPU"。
- **失败语义必须符合内核断言惯例**（GPT 第一轮意见之三）：C 侧是 `assert()`（失败即停机）；Rust 侧 `runqueues_ok_cpu` 返回 `bool`，门控调用点对 `false` 必须走内核的 fail-stop 路径（`panic!`/等价机制），不得因"当前处在调试形态"而降级为打印后继续跑——结构不变量破坏后继续调度比停机危险得多。
- 持续集成加一条开该特性的测试腿（宿主形态即可），保证门内代码不烂。
- 优点：与 C 逐点同构（设施、调用点、默认关三要素全对齐）；调试自检形态成为可观察行为面的一部分，未来调度器回归多一层结构性防护。
- 缺点：多一个特性开关的维护面；对表已完成，余量为三行门控代码加一条测试腿。

**方案 B：删除设施，登记为"有意不做"。**

- 优点：消掉死码与"消费者归属"开口。
- 缺点：偏离 C 的调试设施面（C 明确保留它并在调度核心用）；队列不变量回归从"结构性自检"退化为纯黑盒测试；且"有意不做"的理由站不住——移植成本极低，不属于"刻意省略"的正当类。

**方案 C：维持现状（设施在、调用点不移植），把台账行改成"已裁决：仅测试消费"。**

- 优点：零成本。
- 缺点：与 B 同样的语义保真缺口，只是不删而已；下轮死码扫描仍会重捞。

### 推荐 A 的理由

C 真源给了明确答案：设施不是孤儿，它有三处生产调用点，只是门控默认关。重写原则下"保持外部行为"理应覆盖这条面；移植成本是一次小对表加三行门控代码。参照系上，Linux 的调度器自检（`CONFIG_DEBUG_SCHED` 一族）与锁校验（`CONFIG_PROVE_LOCKING`）都是同样的"设施常驻 + 编译开关 + 默认关"形态，方案 A 与业界惯例同构；B/C 都要在台账里写一条"为什么不做"，而那条理由在 C 真源面前站不住。

## U-3 系统信息交换格式的应用二进制接口余量：推迟到首个消费者，还是现在建全

### 一句话

系统信息（MIB）的线上交换格式主体已经锚定（结构体与字节偏移断言全部落库），剩余未建模的是几个**尚无任何消费者**的统计结构（负载平均值、虚拟内存统计族）的**具名客户端结构体**（`NR_VNODES` 选型已由 `bd5c3d008` 解决，见背景节刷新，不再是待裁项）；要裁决的是按"等消费者"推迟，还是现在建全。

### 背景（自包含）

MIB 是 Minix3 的系统信息树（对位 NetBSD `sysctl(9)`：内核态静态树 + 用户态按路径读取）。本项目的 MIB 语义层与执行层已闭环（判定函数逐条对得上 C、执行遍历器落地、一百三十六枚集成测试覆盖全部终态），线上交换格式的主体也已锚定：`os/libs/minix-types/src/types/sysctl_abi.rs` 定义了八个结构体（树节点族 `SysctlNode`/`SysctlNodeData`/`SysctlNodeChild`、描述符 `SysctlDesc`、轻量进程信息 `KinfoLwp`（含信号集 `KiSigset`）、全量进程信息 `KinfoProc2`、时钟信息 `Clockinfo`、时间值 `Timeval`），全部带尺寸与字段偏移断言——交换面从此不会漂移。

剩余未建模的部分，`os/libs/minix-types/src/types/sysctl.rs:429-439` 的注释写得明确：

```rust
// (loadavg/uvmexp2/maxslp/uspace); the rest are A-9 (14's list).
/// Struct loadavg. C: `VM_LOADAVG`.
/// Struct uvmexp (unimplemented). C: `VM_UVMEXP`.
/// Struct uvmexp_sysctl. C: `VM_UVMEXP2`.
```

**2026-10-09 现场刷新（两处事实与本稿初版不同，讨论前必读）**：

1. **`NR_VNODES` 半已解决**：初版写作"`NR_VNODES` 缺定义、实现返回 `EOPNOTSUPP` [待裁决]"——那是 2026-09-15 的旧进度注。实际在 `bd5c3d008`（2026-09-19，"S24——NR_VNODES 裁决落地"）就已按 C 真源落地：C 侧节点在 `minix3/minix/servers/mib/kern.c:341`（`KERN_MAXVNODES`，值 `NR_VNODES`）与 `:346`（`KERN_MAXFILES`，值同为 `NR_VNODES`），均 `_P | _RO`，常量定义于 `minix3/minix/servers/vfs/const.h:8`（`NR_VNODES 1024`）；Rust 侧 `os/servers/mib/src/tree/arena.rs:318-324` 取值表 `"NR_VNODES" => Some(1024)` 带同款锚点，`os/servers/mib/src/subtree/kern.rs:140/:150` 两节点走 `BuildInt("NR_VNODES")`。这一半**不再需要任何裁决**，本节保留其记录只为对账。
2. **loadavg 族的服务端已经实现**：`os/servers/mib/src/subtree/vm.rs` 全文镜像 C `vm.c`（154 行全量）：`VM_LOADAVG`/`VM_UVMEXP2` 已注册为函数节点（`VmFunc::Loadavg`/`Uvmexp2`），负载数学（`LOAD_MINUTES`/`slots_for`/`avg_x100` 等）、`maxslp=20`、`uspace=0`（带理由的零，C `vm.c:138-140`）全部落位；`VM_UVMEXP` 与其余 8 槽在"未支持"清单（对位 C `vm.c:121` 等注释行）。**缺的只是 `minix-types` 里的具名线上结构体**（`struct loadavg`/`struct uvmexp_sysctl` 不在 `sysctl_abi.rs` 的八字段家族中）——服务端行为已按 C 承诺，缺口是"未来客户端命令要用的命名类型"。

所以本节的真实待裁范围收窄为：**给已按 C 实现的已暴露节点（loadavg/uvmexp2）补不补具名客户端结构体，以及"推迟"这个状态怎么登记**。`VM_UVMEXP`（C 自己都标 not-yet-supported 的槽）维持未实现，无争议。

### 为什么现在需要裁决

这是 10 阶段唯一剩下的开口（阶段摘要行："交换格式的应用二进制接口待裁决，执行半已闭"），而它卡住的不是实现——实现已经按"推迟"的假设写完了——卡住的是**这个假设能不能转正成裁决**，让阶段开口清零。

### 方案空间

**方案 A（修订版，推荐）：具名结构体推迟到首个真实消费者，服务端现状转正为裁决。**

- **`loadavg`/`uvmexp_sysctl` 具名结构体**：等第一个真实消费者命令（`ps`/`top`/`vmstat` 之一立项）时再在 `minix-types` 建模，锚定断言同笔到位。服务端节点已按 C 实现并暴露，所以推迟的只是**客户端便利层**，不产生兼容缺口（回应 GPT 第一轮"已暴露接口不能仅凭无仓库内消费者推迟"的划界：本例的接口行为面已按 C 承诺，缺的命名结构体是死码风险面而非兼容面）。
- **前提与验收条件（GPT 第二轮意见）**：上述"客户端便利层，不产生兼容缺口"的判断以**服务端当前响应已满足 C 的线上交换语义**为前提——节点计算逻辑与最终返回的 ABI 字节布局是两项不同的事实。该前提须由现有 ABI/集成测试或明确的 C 对照证据支持（loadavg 的负载计算已有测试；响应长度与字段排列的线上表示验证情况 [待验证]）；若响应布局尚未验证，执行清单须先补齐布局验证再翻状态——但不因此提前建设所有无消费者的客户端类型。
- **`VM_UVMEXP` 等未支持槽**：维持"C 同位即未支持"的现状，属对位而非缺口。
- **登记**：推迟转正为显式裁决写进 10 阶段 `todo.md` 与 `sysctl.rs` 注释指针，防止下轮扫描重捞。
- 优点：零死码风险；阶段开口清零；与"有意不做"台账体例一致。
- 缺点（如实化，GPT 第三轮意见）：主要风险是现有响应布局证据可能不足、需按验收条件补验证；但不因此要求提前建设所有无消费者的客户端类型。（原稿的 `NR_VNODES` 选型一条已完成，不再是本方案的一部分。）

**方案 B：现在建全。**

- 把 `uvmexp_sysctl`（约五十个字段的虚拟内存统计结构）等全部建出并锚定。优点是"交换面一步到位"；缺点是没有任何消费者，纯死码，且这些结构在 C 侧随内核版本漂移，无消费者时建了也无从验证正确性——违背"不为漂亮提前改契约"的项目边界条款。

**方案 C：只裁 `NR_VNODES`，统计结构维持"未登记的空白"。**

- 缺点：空白不登记就会被下一轮覆盖度扫描当缺口重报，等于什么都不解决。

### 推荐 A 的理由

执行半已经按推迟假设写完且全绿，`A` 只是把假设转正；`B` 的死码风险与"无消费者即无法验证"是硬伤；`C` 不解决登记问题。理由放在本项目自身的事实与公理上：没有消费者时不建死类型（设计公理三）；已暴露接口的行为按 C 真源保持兼容（重写原则），且该兼容性以响应布局经验证为前提（见方案 A 的验收条件）——不把"服务端逻辑已实现"默认当成"接口字节布局已全部验证"。

### 裁决栏（已定稿）

| 项 | 内容 |
|---|---|

## U-4 规则集维护批（旧 `OQ-8`）：批量维护会话的范围与基线滚动纪律

### 一句话

门禁脚本的可重跑判据基线与代码现场出现了两处已知漂移，按现行纪律"基线失配是复核后改台账，不是改脚本基线"，漂移就一直挂在每次扫描输出里；需要裁决的是**基线滚动的归属与节奏**——开一次批量维护会话，还是改成"漂移即当轮滚"。

### 背景（自包含）

本项目有一个集中重算机器可判据的只读执行器 `tools/todo-reconcile-scan.sh`：输出四列（判据名、本次读数、台账基线、判定），代码前进而台账基线没跟上时输出"漂移（DRIFT）"。设计意图是让基线失配成为"台账该更新了"的信号，而不是让脚本迁就现状。当前输出里有两条已知漂移（本文写作时点现场）：

1. **"占位传输实现"判据**：基线 5、读数 0（2026-10-09 复核仍为 0）。历史上五个占位传输桩全是文件系统服务的死桩，已在早前批次移除并核实归零；台账行已如实记录，但脚本基线还停在 5。台账原注："脚本基线待维护批"。
2. **"浮点归属相关行"判据**：基线 21、读数 27（2026-10-09 GLM 会话以 python3 字节级复数；**本稿初版写作时是 24，一日之内又漂了 3**）。x86_64 浮点恢复腿合法落地后 `grep -rn "fpu_owner" os --include=*.rs` 的命中数持续上涨——读数上升是代码合法前进，台账原注："按维护纪律交规则集维护批统一滚动，单轮不代改脚本基线"。这个"批量会话还没开、漂移自己又长了"的事实本身就是对"只许批量滚"节奏的实证反证，支持方案 A 里的当轮滚动出口。

这两条的共性：**读数变化都已核实为合法前进，唯一没做的是把脚本里的基线数字改成新值**。而现行纪律明确"单轮不代改"——因为脚本基线是防篡改的锚（如果允许任何一轮顺手改基线，"改基线迁就现状"就会掩盖真回归），所以集中到一个专门的批量维护会话处理。这个批量维护会话就是旧待裁决队列里的 `OQ-8`，它也是旧队列里仅剩的一条真待决（其余全部已裁决完毕，结论在冻结的裁决文件与编排板 §6）。

另有一件同族小事可搭车：`rewrite-notes/coordination/README.md` 与台账索引里"目录内 28 个文件"的计数会随后续新增文件过时（口径类，无判据）。

### 方案空间

**方案 A（修订版，推荐）：按原意开一次批量维护会话，一次性滚动，并把"何时可以当轮滚"写成带证据要求的纪律条文。**

- 会话范围：上面两条基线 + 一次全量判据重算 + 文件计数口径；同笔把维护纪律补成条文（采纳 GPT 第一轮修订）：**已有证据证明基线变化来自合法代码演进时，允许当轮滚动，但必须（a）"核实三件套"齐全——权威定义在 `TODO-LEDGER-INDEX.md` §6：可重跑的核实命令与读数、核实日期、当时的快照提交号，缺任一件视同未核实；（b）基线滚动独立成笔提交，与代码变更分开，让审查者能区分"代码为何变、旧基线为何不再对、新基线怎么来"；（c）通过完整判据重算而非单点改数。**"测试通过"或"读数变了"本身不构成滚动依据；无证据的漂移维持"复核后改台账、不改脚本基线"。
- 文件计数（`README.md`/索引的"28 个文件"）：与机器可重算的门禁基线**解耦**（GPT 意见之五）——优先改成不依赖精确数字的口径描述，确需精确数则自动生成；不值得自动维护的易过时数字不值得记录。搭车处理可以，但不赋予其与门禁基线同等的维护强度。
- 优点：`OQ-8` 清零；扫描输出回归"漂移即异常"的高信噪比；纪律条文有明确的证据门槛，不会滑向"随手改基线"。
- 风险可控，但不为零（GPT 第二轮意见）：基线维护实质上改变门禁的判定结果，错误地把异常漂移认定为合法演进仍可能掩盖真实回归；通过证据门槛（三件套）、独立提交、完整重算与逐行对账把该风险压到可审查的水平。

**方案 B：改成"漂移即当轮滚"的即时刻。**

- 优点：永不积累。
- 缺点：基线失去"防篡改锚"的属性——任何一轮都能顺手改基线，等于取消了"复核后改台账"这道闸；这正是当初立"单轮不代改"纪律要防的。

**方案 C：不滚，接受常驻漂移报告。**

- 缺点：扫描输出的"漂移"变成背景噪音，真回归出现时没人再看——门禁失去信号价值，等于否决了这个判据机制本身。

### 推荐 A 的理由

`A` 就是 `OQ-8` 的原意（批量维护会话），只是补一条"三件套齐全可当轮滚"的出口让机制可持续；`B` 拆掉防篡改闸；`C` 废掉门禁。参照系上，基线滚动与"测试快照更新"同类——工程惯例都是"快照可更新，但更新必须带着证据走显式流程"，`A` 的纪律条文正是这个形态。

## U-5 虚存服务堆供给迁移的收尾参数：调度池分档何时删、统一回哪个值（`SD-11 T4`）

### 一句话

`SD-11`（服务器进程堆接可增长页供给）的实施拆解四步里，前三步已落地（`T1`/`T2` 供给者形态改造与 `VmBreakSupplier`：`65195776b`；`T3` 首迁 DS：`f61639ba2`；`T3b` 迁 SCHED：`b93c8d29a`），只剩 `T4`：把 `minix-rt` 静态池的 x86/非 x86 两档容量删成单值。要裁的是**统一到哪个值、以及删分档排在迁移波的前还是后**。

### 背景（自包含）

静态池的现状是按目标架构分档的双值常量（`os/libs/minix-rt/src/alloc.rs`）：

```rust
// os/libs/minix-rt/src/alloc.rs:165-181（节选，注释压缩）
#[cfg(not(target_arch = "x86_64"))]
pub const GLOBAL_POOL_BYTES: usize = 2048 * PAGE_BYTES; // §续-279c MFS cache 预算轮
/// x86_64 分档——§续-279c 容量轮的 x86 回归修复（真机 gh142 后补验）：
/// 同轮全量 boot 在 x86 上 init runcom 回落 SingleUser（aarch64 同池健康
/// 有真机门读数），x86 侧加载腿对 .bss 膨胀有独立预算约束——
/// **具体限点未坐实**（279e 候选：bootface identity/DM 窗、copy_in_bytes
/// 同源窗口）……落地后删除本分档。
#[cfg(target_arch = "x86_64")]
pub const GLOBAL_POOL_BYTES: usize = 1024 * PAGE_BYTES;
```

三个决定性事实：

1. **两个值各有实证理由**：非 x86 的 2048 页是当年 MFS 缓存预算轮提上去的（出处编号见上方代码摘录的 `alloc.rs` 行内注释）；x86 的 1024 页是真机回归 gh142 后的修复——但**限点本身没坐实**（注释自陈 279e 候选未定），只知道 2048 在 x86 上会把 boot 打回单用户。
2. **迁移进度**：`install_vm_supplier`（出生握手后安装 VM_BRK 供给者）现有生产调用方只有两个服务——`os/servers/ds/src/main.rs` 与 `os/servers/sched/src/main.rs`；`vm` 自身按当初执行图出局（循环依赖）；剩余**约九个服务仍驻留静态池**（`rs`/`pm`/`vfs`/`memory`/`tty`/`mib`/`pfs`/`mfs`/`init`，boot 十二服务表减去已迁三家）。
3. **2048 存在的主要理由（MFS 缓存预算）对应的 `mfs` 仍在池上**——它迁移走之前，把全架构压到 1024 有且回归已知预算的实际风险。
4. **台账 `SD-11` 行（主线迁移后已刷新）对 `T4` 的最新定性**：仍未启动，阻塞于 gh142 真机回归——统一前必须先坐实 279e 的 x86 加载腿限点；且 x86 统一到 2048 ＝ 每服务 `.bss` +4MiB × `load_vm_elf` 对 memsz 的 eager 物化 ＝ 显著物理页增量。本节方案空间已按此事实校准：迁移波先行不豁免 279e 根因坐实——迁移回答"还需要多大池"，279e 回答"为什么 2048 会炸"，两问都要有答案。
5. **静态池的映像驻留是切供给者不消除的（GPT 第三轮意见；已静态核实）**：池存储是零初始化静态数组——`os/libs/minix-rt/src/lib.rs:220-227` 的 `static POOL_STORAGE: PoolStorage(UnsafeCell<[u8; GLOBAL_POOL_BYTES]>)`，即每个链接 `minix-rt` 的服务二进制的 `.bss` 里都驻留一份整池（`lib.rs:549` 自陈"全局实例用 `'static` 的 `.bss` 池"）；且切换后池页不回收（`T2` 语义：界外归还仅计 `foreign_releases`、池页生命周期＝进程生命周期）。因此**迁移改变的是运行时增量供给来源，不减映像驻留**——统一值直接决定每服务 `.bss` 尺寸（1024 页＝4MiB/服务、2048 页＝8MiB/服务）；"服务已迁移所以 2048 的理由消失"这句话必须改为"运行时增量理由消失，驻留成本理由由统一值本身决定"。

### 为什么现在需要裁决

`T4` 是 `SD-11` 验收清单的显式项（"删除分档是本迁移的显式验收项"，`os/libs/minix-rt/src/alloc.rs:179` 注释自陈），且台账 `SD-11` 行写明统一值要"按剩余驻留池服务的预算重定"——这是一个参数＋排序的事实判断，需要人定方向。

### 方案空间

**方案 A（推荐）：分档删除绑下一个迁移波——先把缓存大头迁走，再统一到 1024。**

- 排序：先迁 `mfs`/`pfs`/`vfs`（缓存预算的主要持有者；`mfs` 迁走后 2048 的运行时增量理由消失）→ 同步做 279e 真机取证（见下方结案条件拆分）→ 再删 `cfg` 分档统一为 1024（x86 已证值）→ 验收（具体化，GPT 第三轮意见）：① x86 与 aarch64 全量 boot 门双绿；② **逐服务预算核实**——迁移后每个仍驻池服务的启动期与稳态期分配峰值都在统一容量内（启动成功只证明这一轮没暴露，不证明峰值预算足够）；③ 验收覆盖真实消费路径（池分配或 VM_BRK 增长的关键路径有测试/真机读数），不只 boot 成功；④ `cargo test -p minix-rt` 全绿。
- **279e 结案条件拆分（GPT 第三轮意见，防"调查不结案则 T4 永远不能关"）**：容量变更的必要证据＝迁移后逐服务预算核实＋目标架构全系统门通过（①—④）；历史故障根因结论＝独立取证项，其完成标准另行定义（把限点定位到唯一原因是理想终态，但若长期无法唯一化，允许以"已排除候选＋限点区间收窄到可支撑容量决策"作为根因侧的完成线，与容量决策解耦——理由与边界记入台账）。

- 缺点：分档还要活一段时间（但它是带注释的已知账，不是未知债）。

- 优点：一步到位。

**方案 C：现在就统一到 2048。**

- 缺点：需要先坐实 279e（x86 加载腿的具体限点）才可行——那是另一轮真机取证，未坐实前选它等于把 gh142 已知回归重新引入。

### 推荐 A 的理由

参数裁决的判据是"预算归预算、限点归限点"：1024 在 x86 上是唯一有真机门背书的值，2048 的唯一立得住的理由（MFS 缓存）会随迁移自然消失——所以正确次序是让事实（迁移）消解掉 2048 的理由，而不是在两套预算约束未对齐时赌一个统一值。参照系：Linux 的 `CONFIG_FORCE_MAX_ZONEORDER` 类容量参数从来跟着消费者走，不凭空统一。

## U-6 五十二个空转驱动入口的实装优先级：批次排序原则与第一批名单

### 一句话

`os/drivers` 下 55 个驱动 main 里有 **52 个停在 `loop {}` 空转占位**（16 阶段台账记"二十六个纯占位 crate"——一 crate 可含多 bin，两口径并存），每个实装都是"硬件面＋事件循环＋根服务启动协议"的大件；要裁的是**批次排序原则与第一批名单**，不裁逐驱动设计（每个实施前仍按 todo-fix 单独立项）。

### 背景（自包含）

现状盘点（可重跑：`grep -rln "loop {}" os/drivers --include=main.rs | wc -l` → 52；55 个驱动 main 中仅 3 个真实现：`os/drivers/storage/memory/src/main.rs`、`os/drivers/tty/tty/src/main.rs`、`os/drivers/hid/pckbd/src/main.rs`）。52 个空转入口按硬件族分类：

| 族 | 数量 | 成员 | 直接消费方 |
|---|---|---|---|
| storage | 8 | at_wini、floppy、ahci、virtio_blk、fbd、mmc、filter、vnd | 根文件系统挂载、`E5(f)` 数据存储子面（其真机终态已拿传输链四腿，缺盘上块层） |
| net | 14 | virtio_net、rtl8139、rtl8169、e1000、fxp、lance、dp8390、dpeth、3c90x、atl2、dec21140a、ip1000、lan8710a、vt6105 | `netdriver`/17 阶段（lwip 库 127 测已绿，驱动半未通电） |
| audio | 7 | es1370/es1371、sb16、trident、als4000、cmi8738、cs4281 | 命令面音频工具（无近期消费） |
| bus | 3 | pci、i2c、ti1225 | 其他驱动的枚举依赖（pci 是多数硬件驱动的前置） |
| usb | 3 | usbd、usb_hub、usb_storage | 外设族 |
| power | 3 | acpi、tps65217、tps65950 | 平台发现（acpi 解析库已在 aarch64 用真） |
| system | 3 | gpio、log、random | 杂项 |
| sensors/eeprom | 4 | bmp085、sht21、tsl2550、cat24c256 | i2c 小件（字符驱动模板复用度最高） |
| video | 2 | fb、tda19988 | 显示（QEMU 下串口先行，video 无验收面） |
| tty/pty | 1 | pty | 终端族 |
| clock/printer/iommu/vmm | 4 | readclock、printer、amddev、vbox | 杂项 |

关键事实：**块层（storage 族）是当前验收阶梯的实际阻塞面**——`E5(f)` 数据存储子面的真机门已拿到传输链四腿绿的终态，缺的正是"盘上文件系统服务器 → 块驱动"这最后一截；而网络族的库测试已绿，缺的是驱动通电与 17 阶段设计条目（附录 B 已立）。

### 为什么现在需要裁决

52 个大件若无排序原则，认领板会按"谁顺手领谁"自流——小件（传感器类）先被消费，而真正阻塞验收阶梯的块层迟迟不动；这正是台账 `P-ALL-07` 行"逐个都是大件、非可当轮闭的有界项"需要配套排序裁决的原因。

### 方案空间

**方案 A（推荐）：消费者驱动的三批制。**

- **批 1（块层，单驱动端到端试点）**：只选**一个**先行驱动（GPT 第三轮意见：首款驱动要同时验证设备发现、传输协议、块接口、启动握手、上层真实消费五层契约——若首装就暴露通用接口缺口，提前承诺第二款只会扩返工面；待其依赖边界稳定、复用接口经实测验证后再定第二款）。候选与可达性（静态核实，最终确认留执行首步）：

  | 核实项 | `at_wini`（x86_64 pc 机） | `virtio_blk` |
  |---|---|---|
  | QEMU 机型与架构 | x86_64 pc（`xtask/src/qemu.rs` 默认机型），`-drive file=…,format=raw,media=disk` 落默认接口（`qemu.rs:97-98`） | 同一机型，但需显式加 `-device virtio-blk-pci`（现无） |
  | 设备暴露方式 | 落 pc 机型内建 IDE 控制器，主通道兼容模式旧式端口（任务文件寄存器在固定 I/O 端口，不要求先有 PCI 枚举 [待验证：QEMU pc 的兼容模式归属]） | 设备未暴露；virtio 传输/通知/DMA 依赖需逐项取证 [待验证] |
  | 前置依赖 | `SYS_DEVIO` 端口 I/O（已真，含 `CHECK_IO_PORT` 门与 OQ-N3 特权白名单）＋IDE 中断腿＋RS 启动协议 | PCI 枚举（`bus/pci` 本身仍是空转入口）＋virtio 传输层 |
  | C 真源对位 | `minix3/minix/drivers/storage/at_wini/`（IDE 协议/命令序列） | C 无对位（Minix3 无 virtio），属 `[ARCH]` 面 |
  | 验收终点 | 真盘分区上的 MFS 挂载取代 imgrd ramdisk 场景，直接服务 `E5(f)` 数据存储验收 | 同左，但前置链长一截 |

  按 GPT 三条件（已在目标 QEMU 配置中／前置最少／直接解锁数据存储验收）：**`at_wini`/x86_64 为首选候选**（`virtio_blk` 依赖未备，不应凭名称的跨平台吸引力强推）；执行首步做端口探针真机核实后定案。
- **批 2（网络收敢单 NIC）**：不铺 14 个，收敛到 QEMU 可达的一只（`virtio_net` 或 `rtl8139`），且**先立 17 阶段设计条目**（附录 B 已登记"缺设计条目"），设计先行再实装。
- **批 3（小件批量）**：sensors/eeprom 等真正同质的 i2c 小件，按同一 `chardriver` 骨架批量收，攒模板红利。**音频单列**（GPT 第三轮意见）：音频驱动的数据传输/缓冲/事件需求不同，不因同有字符设备接口就预设骨架高复用，作为后续候选单独登记。
- 优点：排序与验收阶梯对齐，资源花在解锁面上；三批各自有明确判据。
- 缺点：音频/视频等无近期消费者的族排最后（但它们的消费者本来就还没立项）。

**方案 B：难度驱动——小件先行攒模板，块层后置。**

- 真实价值（GPT 第三轮意见，如实承认）：简单字符驱动先行能更早暴露驱动启动协议与公共框架的通用缺口，更早产出可复用模板，为后续所有驱动降本；
- 但这些收益不足以抵消当前块层验收长期被阻塞的成本（`E5` 真机半会持续缺块层；`chardriver` 骨架的复用价值最终也要靠块层/网络层的大消费者兑现）。

**方案 C：不排序，认领板自流。**

- 缺点：批不成系统，`E5` 阻塞面不动，与"驱动实装是移植进度而非齐平差距"的台账定性不匹配。

### 推荐 A 的理由

排序原则只有一个判据：**谁在验收阶梯上被消费，谁先做**。批 1 直接服务 `E5` 真机半（当前最大的待验证族），批 2 服务 17 阶段立项，批 3 用剩余产能收尾——这与"消费者才建模"的公理同构，只是从类型层落到了驱动层。参照系：Linux 驱动子系统的维护现实同样是"SoC 厂商先做平台可达的控制器，通用小件靠社区"。

### A-1 内核引导信息里恒为零的哨兵字段（`OQ-01-A`）

`os/libs/minix-boot/src/kernel_info.rs` 的 `KernelInfo` 有 `bootstrap_start`/`bootstrap_len` 两个字段，在六十四位构建下恒为零（为对称 C `kinfo_t` 的未分页段形状而留）；消费点是一个生产不可达的回收守卫。已有裁决：**临时保留字段加守卫**，按设计公理三推迟。**触发条件**：独立 ELF 自引导（待办 `TODO-02-3`）对未分页段的处置落地时，出现第二个真实使用者则留并真用，否则删字段、守卫、校验条与构造参数。

### A-2 信号集位宽六十四位到一百二十八位（`SD-39`）——**已执行，本条目退役**

**2026-10-09 刷新**：`SD-39` 已在 `07c9517af`（2026-10-09）落地，本条不再存在"等触发"状态。落地内容：内核 `SigSet` u64→u128（repr transparent），新增 `from_bits/bits/to_words/from_words`，`contains/add/remove` 边界拓到 `1..=128`；内核内部信号 `SIGSNDELAY=70`/`SIGKMEM=71`/`SIGKSIG=74` 不再 add 为 no-op（落 word 2，同 C `__sigaddset` 的 `_SYSTEM` 无检查行为）；wire 侧 `MessSigcalls.map` 改 `SigSetBits`（`[u32;4]`，对位 C `ipc.h:1917-1923`，顺带修正旧 `endpt@8` 偏差）；PM 拉取循环 `1..=128` 逐位消费（对位 `sef_signal.c:27-63`）；18 处 mock 同步。GPT 第一轮曾要求"先确认 C 有效信号编号范围与 syscall 边界是否要求 128 位再推迟"——该核验由实现本身完成（C `sigset_t` 即 128 位、内核内部信号已用 70+），结论是拓宽而非推迟。核实读数见 `TODO-LEDGER-OPEN.md` §3 `SD-39` 行（types+sys+pm 1081、kernel 830 全绿）。

### A-3 虚存服务区域映射的防御性回退（`SD-40`）

`os/servers/vm` 的区域映射里有一段"打印三条错误后永久静默"的防御性回退，是内存污染追捕期间加的防御手段。三个选项（删除 / 快速失败 / 保留）都已在设计债台账记录，推荐是**由案卷结案批次点名处置**——因为现在删或改会变动该案的在案取证面。**触发条件**：riscv64 内存污染案卷（裁决 `PD-16`）结案。**结案的定义要写实**（GPT 第一轮意见）：指该案的证据、实验结论与对这段回退的处置理由都已归档可溯，而不是台账状态词从 `open` 翻成 `closed` 就算触发——在写者未定位的调查里，这段防御代码本身可能是在案取证面的一部分。
