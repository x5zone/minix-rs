# riscv 上「只在读的一瞬间出现」的页表崩溃：取证方法论

这份文档记录调试 minix-rs 缺陷 (A) 时得到的几条可迁移知识。它不讨论怎么修（根因尚未坐实），
只讨论**怎么观察**一个特殊的崩溃：它的坏数据在你停机查看时已经消失，只在你不去偷看它的时候才
出现。每条结论都带命令或源码位置作为凭据，读者可以复跑验证。

缺陷 (A) 的现象（锚点：`rewrite-notes/coordination/NK4C-WORKLOG.md` 顶部、串口日志
`tmp/nk4a/gh92f2.serial` 第 19681 行）：riscv64 启动过程中，虚拟内存服务器进程（VM，跑在用户态）
在遍历页表时崩溃，串口打印

```
pagefault for VM sepc 0x000000000003abec stval 0x00000010bd28cb2c
```

随后内核在 `os/kernel/src/trap_dispatch.rs:1991` 停下（`panic!("pagefault in VM")`）。这个崩溃在
同一个二进制上每次都能重现，不需要调试器也会崩。

---

## 知识点一：用户态进程里，物理内存地址是不能直接访问的

要理解为什么这个崩溃难查，先要理解 VM 是怎么读页表的。

页表项里存的是物理地址（内存条上的真实编号）。但 VM 是用户态进程，它的 CPU 每次给出的都是
**虚拟地址**，要经过自己的页表翻译成物理地址才能访问内存。所以 VM 不能直接拿一个物理地址去读
——那个数字在 VM 的虚拟地址空间里要么没意义，要么翻译到别的地方。

minix-rs 用一种叫「直接映射区」（Direct Map）的技巧绕开这个问题：在某个虚拟地址区间里，让
虚拟地址减去一个固定基址就等于物理地址，这样进程想读物理地址 X，就去读「基址 + X」这个虚拟地址。
代码在 `os/arch/src/riscv64/paging.rs:206` 的 `channel_to_ptr`：

```rust
match channel {
    PteChannel::KernelDm => Riscv64DirectMap::kernel_phys_to_virt(PhysBytes(phys)).0 ...
    PteChannel::VmDm     => Riscv64DirectMap::vm_phys_to_virt(PhysBytes(phys)).0 ...
}
```

两个基址（`os/arch/src/arch/direct_map.rs:148-149`，riscv64）：

- 内核直接映射基址 `KERNEL_DIRECT_MAP_BASE = 0xFFFF_FFC0_4000_0000`
- VM 直接映射基址 `VM_DIRECT_MAP_BASE = 0x0000_0010_0000_0000`（即 1 左移 36 位）

**推论**：在用户态崩溃现场，你拿一个物理地址（比如 `0x9DC377F8`）让调试器去读，调试器会按当前
虚拟地址翻译，读不到那块真实内存——这正是我们踩到的 `Cannot access memory at address 0x9dc37ff8`
（`tmp/nk4a/gh93-gdb.txt`）。要读真实物理内存，必须换成「基址 + 物理地址」的写法，而且基址要属于
**当前正在运行的那一方**（内核或 VM）。

### 要点总结
1. 用户态进程的 CPU 只发虚拟地址，物理地址得借直接映射区才能读。
2. 直接映射区有两个：内核的和 VM 的，基址不同（上面两个常数）。
3. 崩溃发生在谁的地址空间，就得用谁的那个基址，否则调试器读不到。

### 灾难预演
如果把 `VM_DIRECT_MAP_BASE` 写成了内核的基址，VM 去「读物理地址 X」时，实际读到的是内核映射
里的那个虚拟位置——在内核态之外那段虚拟地址根本没映射，于是 VM 自己触发一个缺页，本来正常的
页表读取变成「访问页表的访问」崩掉。这就是为什么崩溃信息里 `sepc` 停在读页表项那条指令上。

## 知识点二：在停机时刻，借内核的直接映射区活体读任意物理页

既然用户态读不到物理内存，怎么把出问题的那张页表真正读出来看？答案：不要在崩溃的那一刻读，
也不要开调试器从头拦（下面会讲为什么），而是**让系统自己崩到停机，趁内核接管、坐在内核态的时候
读**。内核停机时，它的页表（含内核直接映射区）是活的，于是「内核基址 + 物理地址」这个虚拟地址
能被调试器正常翻译。

做法（脚本 `tmp/nk4a/riscv_live_read.sh`）：

1. 正常启动，**不加 `-S`**（`-S` 会让调试器一开机就暂停，反而改变时序）。让系统跑到自己崩溃停机。
2. 崩溃后内核停在 `panic` 后的停机循环里。这时用 gdb 连上去（`target extended-remote`）。
3. 内核停机时 `satp`（当前页表寄存器）指向内核页表，直接映射生效。要读物理地址 `0x9dc37000`
   这一页，就读虚拟地址 `0xFFFFFFC040000000 + 0x9dc37000 = 0xffffffc0ddc37000`：

```
(gdb) x/1xg 0xffffffc0ddc377f8    # 子进程根表里第 255 号表项那一格
0xffffffc0ddc377f8: 0x0000000000000000     ← 是零！
```

这一读得到了关键事实：**被怀疑写坏的那一格，在停机时读出来是干净的 0**。整张 512 项的根表里
只有 7 格非零，且全都是合法的页表指针（例如第 511 号 `0x274ab401`，解出物理帧 `0x9d2ad000`，
有效标志位）。用同样方法读另一个候选根（RS 进程 `0x82132000`，`tmp/nk4a/gh102-gdb.txt`）也一样干净。

### 要点总结
1. 想读「真实物理内存」，就趁内核停机、内核页表活着的时刻，用「内核基址 + 物理地址」去读。
2. 不加 `-S`，让系统自然崩，崩了再连调试器读现场，比从头拦更不扰动。
3. 这一读证明了坏页表项**不常驻**：崩溃那一瞬间它是坏的，停机时已经没了。

### 灾难预演
如果内核直接映射基址算错一格（比如多写了两个 `F`，凑成一个 18 位十六进制数），gdb 会报
`Numeric constant too large`（这个坑我们踩过，`tmp/nk4a/gh95-gdb.txt`）。地址看着像，其实位数
超了 64 位，读什么都失败。核对常数一定要用源码里的分组写法 `0xFFFF_FFC0_4000_0000`。

## 知识点三：QEMU 的 riscv 系统模式里，硬件写观察点根本不触发

按常理，「抓住谁在这一刻把这格写了坏值」最正规的办法是硬件写观察点：让 CPU 一旦往那个地址写就
停下。我们照着设计了三套（`tmp/nk4a/riscv_watch_auto.sh` / `riscv_watch_ctrl.sh` / `riscv_watch_dm.sh`），
全部实测失败：

- 观察点**能设上**（gdb 打印 `Hardware access (read/write) watchpoint 1: *(unsigned long*)...`，见
  `tmp/nk4a/gh92f2-gdb.txt`），但**永远不触发**——系统一路跑到崩溃，观察点没停过。
- 无论用「裸物理地址 `0x9DC377F8`」还是「VM 直接映射虚拟地址 `0x19DC377F8`」两种写法，都不触发。
- 想切物理内存模式的 `maintenance packet Qqemu.PhyMemMode:1`，被本机 gdb 直接拒绝，报
  `Invalid argument syntax`（`tmp/nk4a/gh92f1-gdb.txt`）。
- 作为对照，普通的软件断点 `break *0x3abec` **能稳定命中**（同一现场命中 3 次），说明调试器本身没坏，
  是硬件写观察点这条路在这个 QEMU 上不通。

环境：`qemu-system-riscv64 8.2.2`、`gdb-multiarch 15.1`（Debian 打包版）。结论：**在这套工具上，
硬件写观察点不能用来抓页表帧的瞬态写者**。

### 要点总结
1. 「能设上」不等于「能用」：观察点设点成功，触发却可能是空操作。
2. QEMU riscv 系统模式的写观察点 + 物理/虚拟地址语义，实测都不可靠，别把方案押在它身上。
3. 判命中要用对措辞：本 gdb 打的是 `Hardware access (read/write) watchpoint`，不是
   `Hardware watchpoint`；正则写错会把「设点成功」误报成「设点失败」（这个坑 CodeReview 抓过）。

## 知识点四：为什么这类「读的一瞬间才坏」的崩溃，所有动态调试都会失效

前三条叠起来，就是这个缺陷最本质的难点：**你想看它，它就变了；你不想看它，它才出现。**

- 你在读页表的那条路径上**多加一条读**（想提前窥探一下），崩溃点就从 `0x3abec` 挪到 `0x3ae3c`
  （`tmp/nk4a/gh99-live.log`）。加一条读改变了时序，故障躲开了原位。
- 你挂上 gdb **从第一刻暂停再单步**（`-S`），崩溃点挪到 `0x3ac1a`、伴随的坏地址也换了家族
  （`tmp/nk4a/gh101.serial`）。gdb 的暂停/恢复本身就改时序。
- 你**不加任何调试器**、正常启动，故障乖乖停在 `0x3abec`——可这时候你没有观察手段。

这类现象有个名字叫「海森堡 Bug」（观测行为改变了被观测系统），在启动链里尤其常见，因为启动
每一步都依赖内存分配和中断的先后顺序，任何额外指令都会挪动这个顺序。所以：**任何往生产代码里
加的探测指令，都必须当成一次「重新引入不确定性」，实验完要撤销**（本次加的诊断读最后都用
`git checkout` 还原了，保证留在仓库里的是干净二进制）。

### 要点总结
1. 瞬态型崩溃对「代码布局」和「暂停/恢复」都极敏感，加观察手段会把它推离原位。
2. 因此取证顺序应当是：先只读现场（停机借内核映射读，知识点二），再考虑非侵入的动态手段，
   最后才动代码加探针，且探针必须临时、必须还原。
3. 干净的复现值（比如 `sepc 0x3abec`）只能在完全不加调试器的启动里拿到，任何带调试器/带探针
   的数字都不能当作基准证据。

## 由此得到的、可以立刻用的检查思路

即使根因还没坐实，「合法页表项必须解出一个落在物理内存范围内、且按 4K 对齐的物理帧」这条不变量
是恒真的。把这条做成诊断断言——遍历页表时，如果某个非叶子表项解出的物理地址越过了内存顶，就地
报错而不是继续解引用——就能把这类崩溃从「VM 访问非法地址被内核强停」变成「当场指名道姓地报告
哪张根表、哪一格、装了什么坏值」。这也是 WORKLOG 里规划的一条防御性测试方向
（`NK4C-WORKLOG.md` 顶部 §续-247 的下轮候选）。

## 唯一还没试、可能真正能抓到的办法

要抓「读的一瞬间」的瞬态写者，剩下的唯一零暂停手段是 QEMU 插件系统（用插件在每条访存指令上
挂回调，对目标物理地址做写拦截），它不受调试器暂停影响。本机缺 `qemu-plugin.h` 头文件，需要
先装上对应开发包才能编译插件。这一步依赖外部安装，是 (A) 当前受阻的真正原因。
