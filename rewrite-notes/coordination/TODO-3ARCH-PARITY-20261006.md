# 三架构代码面齐平专项：静态扫描待办清单

这份清单只做一件事：把 x86_64、aarch64、riscv64 三个架构在**代码面**（能力实现 + 测试覆盖）上互相欠缺的地方，以及三个架构共同欠着的结构性债务，逐条列成可以被别人独立复算的待办项。它是一次纯静态扫描的产物——没有编译、没有跑测试、没有起虚拟机、没有改任何代码。每一条都附带它可以被核对到的位置（文件与符号，或者一条能重跑的核对方式），给不出处的地方一律写明「待验证」而不是当成事实。

**基准与范围**：以 aarch64 目前的实现状态为终点基准；但「以 aarch64 为基准」不等于「aarch64 已经做完」——aarch64 自己欠着的项（中间页表页回收、浮点状态存取、宿主可发现的架构腿钉住测试等）一并列入。三个架构共有的死代码、未滚除的诊断探针、语义与上游 C 真源不一致的债务，也列入。

**判据**：在写任何一条「某架构缺 X」之前，先自问——如果两个架构在语义上等价、只是机制表达不同，那不是差距；只有一端有行为、另一端没有行为（或者行为不完整）才算差距。文末「排除清单」把按这条判据剔除的正当架构差异逐条列出，它和待办清单同等重要。

**三条终目标现状**（这是判定的地基，不是本报告新发现）：目标① 三架构都启动到最小启动脚本的标记行、目标② 十八阶段命令面走通真实的虚拟文件系统消息通路，均已达成；目标③ 上游自带的自动化测试套件（十八个程序、三十六个用例）在真机跑到终态，在 aarch64 与 riscv64 上均已达成（riscv64 本轮为 34 通过 + 2 跳过 + 0 失败 = 36 个用例全部到终态），**而 x86_64 从未被放进第三类目标的装配白名单**。所以「三架构齐平」这条目标本身就含着一个已知的大缺口——`P-X86-01`。

## 二、排序建议（先做哪几条、为什么是这个顺序）

排序依据三条：挡住终目标判据的优先、能静态定案的优先、会改变后续条目形状的优先。据此分四档。

**第一档（会改变你怎么读整张矩阵，且静态可定案，成本最低）**

1. `P-ALL-01` 架构目录里被目标架构条件门住的 `#[test]` 在宿主永不运行。这条必须先做，因为它决定矩阵里所有「已有测试」格子的可信度——如果 riscv/aarch64 声称的测试覆盖里有约 90 枚根本不跑，那矩阵里「riscv64 已有目标③」这类断言也要用产物读数复核而不是靠绿勾。修法是把钉住测试搬到宿主能发现的 `<crate>/tests/*.rs`，成本小、判据纯静态。
2. `P-A64-02` aarch64 缺宿侧「陷入/返回腿」指令顺序钉住测试。它和第一档同源，是同一个可达性纪律的另一面；而且 aarch64 是基准架构，它自己裸奔最危险。静态可定案。

**第二档（直接挡终目标、或基准架构自欠的硬缺口）**

3. `P-X86-01` x86_64 未进目标③ 套件的装配白名单。这是「三架构齐平」这句话里最大的一块缺口；装配面（把 x86_64 放进 `ATF_BOOT_LEG_READY`、产出对应镜像）可静态铺，但终态判据必须上机。
4. `P-A64-01` aarch64 缺中间页表页回收。基准架构自己欠的项，静态可读码定案缺口存在，修复可参照 x86/riscv 已有分支。
5. `P-RV-01` riscv64 从未在多核配置跑过套件与命令面。它把「riscv 已达成目标③」这个结论限缩成「只在单核下达成」，与第三档的多核欠账联动。

**第三档（改变后续条目形状的多核/SMP 欠账，判据需上机）**

6. `P-A64RV-01` aarch64 与 riscv64 的次级核早期入口汇编体仍是骨架。这是三架构 SMP 能力不齐平的真身：x86_64 有完整的唤醒阶梯，另两端只有骨架加一个契约常量。它挡住「多核真机」这一整类判据，所以先做它能定义后面 SMP 系列条目的形状。
7. `P-ALL-03` 真多核被钳到主核（`SD-24`）、每核运行队列与跨核迁移三件套未通电。与上一条耦合，但范围更广、需上机验证。

**第四档（共有结构性欠账，不挡终目标、但挡代码质量与后续核对可信度）**

8. `P-ALL-04` 未滚除的诊断探针族滚除。它本身是旧债，但因为它压在正被别的会话改动的 `os/kernel/src/*`、`os/servers/vm/*` 上，动它有现场冲突风险，放最后、且必须等那些会话收手。
9. `P-ALL-05` 语义与上游 C 真源不一致的登记（`SD-16` 正/负 errno 交叉、`SD-17` `ps_strings` argc 槽宽 4 与 8、`F10` 正 errno 上线正数、`X-7` 未知 VMCTL 返 `ENOSYS` 而非 C 的 `EINVAL`）。
10. `P-ALL-06` 死代码与手抄结构体错位（`riscv64/paging.rs::switch` 零调用、`ProcInfoStruct` 与 `KProcSnap` 双源、`SI_PROC_TAB` 重复定义）。

## 三、排除清单（判定为正当架构差异，不算差距；与待办清单同等重要）

漏了这份清单，下一轮会有人把设备树和 ACPI 当成「不一致」去修。以下逐条列出被判「不适用 / 正当差异」的东西与理由。

1. **riscv64 无 ACPI，走设备树**。判据二在共享层只逮到 `os/libs/minix-platform/src/acpi.rs` 里 riscv 完全缺席——这是正当差异：x86_64 与 aarch64 从 ACPI 表拿平台事实，riscv64 从设备树拿，两者语义等价（都是「告诉内核有多少内存、哪些中断源」），只是机制表达不同。不算差距。
2. **riscv64 是 Sv39 页表、x86_64 是四级页表、aarch64 是其自身的翻译表格式**。页表层级与索引位是各指令集架构规定的，语义都是「把虚拟地址翻成物理地址」，机制不同不算差距。
3. **`os/arch/src/x86_64/pte.rs` 存在而 aarch64、riscv64 无同名文件**。核对：aarch64 把页表位（`VALID/TABLE/PAGE/AP1/AP2/AF/NG/PXN/XN`，见 `os/arch/src/arm64/paging.rs`）内联在 `paging.rs`，riscv64 把位（`V/R/W/X/U/G/A/D`，见 `os/arch/src/riscv64/paging.rs`）也内联在 `paging.rs`。三架构都有页表项位定义，只是 x86_64 拆成独立文件，且 x86_64 的四级索引计算（`>>39/>>30/>>21/>>12`）确为其专属。语义等价，组织不同，不算差距。
4. **`os/plat/src/x86_64/port_io.rs` 存在而 aarch64、riscv64 无**。端口 I/O 是 x86 独有指令集机制；顶层 `os/plat/src/port_io.rs` 的 `PortIo` trait 注释已写明「在 ARM64/RISC-V 上 I/O 端口不存在——该 trait 实现为空操作，`SYS_DEVIO` 返回 BadCall」。这是正当差异，不是缺口。
5. **aarch64 线程控制块头偏移 `0x10` 需要手动减、riscv64 由链接器把 `TPREL` 折进重定位所以不用减**。两者都是在「让线程指针指向正确的线程局部存储基址」，达成同一语义、机制表达不同，不算差距。
6. **`os/kernel/src/clock.rs`、`os/libs/minix-boot/src/kernel_info.rs`、`os/drivers/tty/tty/src/serial.rs` 被判据二标为「x86_64 完全缺席」**。核对为判据二的假阳性：判据二按字面 token `x86_64`（Rust 目标三元组名）搜索，而这三处用「x86-64」「i386」「16550 端口 I/O」指代 x86，x86 的行为都在（`clock.rs` 有 `rdtsc`/LAPIC/PIT 经 `ClockArch` trait 抽象；`serial.rs` 的 `COM1_BASE = 0x3F8` + `sys_inb/sys_outb` 就是 x86/PC 的默认串口分支；`kernel_info.rs` 是三架构共用的纯数据契约，本就没有「x86 臂」概念）。不算差距。
7. **aarch64、riscv64 的架构专属系统调用一律返回 `BadCall`**（`os/kernel/src/syscall.rs:CurrentArchSyscall` 对 `not(any(x86_64, arm))` 落 `DefaultSyscall` 空实现）。核对代码注释：那些系统调用（如 padconf）在 Minix3 里本就是 i386 专属，对另两端返回 `EBADREQUEST` 是「按真源为正确、不是待实现」。这是正当差异。它附带的注释过期问题另见 `P-X86-04`。
8. **x86_64 不在持续集成 `cross-arch-kernel-build` 任务里**。该任务只为 aarch64、riscv64 建生产形态，因为运行器本身就是 x86_64，再为 x86_64 交叉构建是冗余。不算差距（与 `P-X86-01` 区别开：那条讲的是测试套件上机面，不是构建面）。
9. **大量用户态服务器与文件系统/驱动/网络二进制的生产传输接线尚未通电**（`main.rs` 里空 `loop {}` 占位、`UnimplementedTransport`、客户端协议半靠 `ENOSYS` fail-closed）。这些在**三个架构上同等未完成**，属于「服务功能移植进度」而非「架构间齐平差距」。它不进本齐平矩阵的缺口格，但作为共有结构性欠账，只在 `P-ALL-07` 里以「一条聚合的装配面欠账」登记一次，不逐服务展开。
10. **riscv64 独有的 `os/servers/vm/src/vmdm_bridge.rs` 直接映射旁路**。这是 riscv 为绕开某个虚拟机管理器时序而有的特有机制，另两端不需要。有实现、语义等价，不算差距（反向不对称但正当）。

### P-ALL-12 消息联合有 6 个载荷成员超出本仓自己钉住的 56 字节载荷上限，把 `Message` 撑到 80 字节并留下 16 个不落值的尾部字节【已收口 §续-433：六成员 padding 修复、109 成员严格相等断言链上线、Message 80→64 回到 C 判例，DumpCore 按值名的 44..60 越界写一并消除；三架构门全绿】

- 现状（本轮用一次性探测测试逐个量出来，110 个成员全量）：`MessageUnion` = 72 字节、`Message` = 80 字节（两条断言在 `os/libs/minix-types/src/ipc/message.rs` 的 `test_message_total_size_pinned` 里），而载荷上限常量是 `MESSAGE_PAYLOAD_SIZE = 56`（同文件 :27）。**六个成员超过 56**：`MessLsysGetsysinfo` = 72、`MessageM7` = 64、`MessLsysKrnSysTrace` = 64、`MessLsysKrnSysMcontext` = 64、`MessLsysFiCtl` = 64、`MessLcVmShmUnmap` = 64。直接成因是手算 padding 错：`MessLsysGetsysinfo`（`message.rs:3155-3164`）字段共 4+4+8+8 = 24 字节，要凑 56 只需 `_pad2 = 32`，实际写的是 `[u8; 44]` ⇒ 68 字节再按 8 对齐成 72；它的 doc 注释自己写着“padding to 56 bytes”，与字段矛盾（工具生成行号另判，这句是手写的）。
- 差距：与 C 真源直接相左——`minix3/minix/include/minix/ipc.h` 给每个载荷成员都加了 `_ASSERT_MSG_SIZE`（例：`mess_lsys_getsysinfo` 在 :1071-1072），即**所有成员恰为 56 字节**，整个 `message` 为 64；本仓 :22-26 的头注也说“we keep the same 56-byte payload size for IPC protocol compatibility”。六个越界成员就是对本仓自己那条不变量的违反。附带后果：因为 `union` 被撑到 72，而 `MessageUnion::default()` 只写 `raw: [u8; 56]`（:307/:310-316），第 56..72 字节在任何构造下都不落值；内核两处整块搬运按 `core::mem::size_of::<Message>()` 取长度（`os/kernel/src/ipc.rs:540`、:581、:595），内核→用户方向（`to_kernel = true`，:589-598）就把这 16 个不确定字节搬进用户缓冲。今天无读者（`m_u.raw` 取片均在 56 字节内，如 `os/fs/fs-rt/src/wire.rs:147`、`os/fs/mfs/src/second_level.rs:452`），所以不影响功能，但破坏「两条消息相等⇒字节相等」类对账判据的可复现性；`os/kernel/src/ipc.rs:530-532` 那句 SAFETY 注（“无 padding 读风险（全初始化）”）在此事实上措辞偏强；`test_message_total_size_pinned` 上方那段注释说“largest member is 64 bytes”也与实测 72 不符（本笔已就地改注，结构体不碰）。
- 修法与参照：方案甲，逐成员把手算错的 `_padding` 改回“字段长度之和凑足 56”（先把六个成员的 C `_ASSERT_MSG_SIZE` 逐个对一遍再动手），同时在 `message.rs` 加一条**编译期全量断言**防复发（对每个成员 `assert!(size_of::<T>() <= MESSAGE_PAYLOAD_SIZE)`，可照 `notify.rs:106-109` 的现有写法展开）；方案乙，只改最大那一个（`MessLsysGetsysinfo`），其余 64 字节成员暂时登记——能把 `Message` 从 80 收到 72，但不变量仍不成立，且留下一堆局部修；方案丙，把 `MESSAGE_PAYLOAD_SIZE` 改成 72 承认现状——与 C 的 56/64 判例正面冲突，不采。参照：Linux 的 `union message` 由 `sizeof(message)` 统一定长且字段显式铺满；Redox 的 IPC 走带显式长度的字节串，不存在隐式尾。取舍：甲一次到位且能带上编译期守卫，但改动跨 6 个成员与其所有读写点（需逐处确认没有代码依赖那 16 字节尾部），必带三架构上机对账；乙风险小但欠一个不变量。
- 判据：静态可判（成员尺寸逐个可量，编译期断言本身就是判据）；“不确定值是否真进过用户内存”需上机逐字节对账。
- 影响面：消息线形卫生、尺寸不变量与对账可复现性；不挡三条终目标（两侧同用本类型，自洽）。
- 依赖与顺序：无前置；与 `P-ALL-06`（手抄结构体错位、双源布局）同族，宜并批做；改动会连带 `os/kernel/src/ipc.rs:634`、:704 的 `16+size_of::<Message>()` 异步槽布局约定与 `minix-sys` 镜像，必须整批跑。
- 风险与红线：改 `size_of::<Message>()` 就是改内核↔用户的搬运长度，两侧任一处算错就是踩内存；先加编译期断跑一遍看看还有多少成员报错，再决定批量范围（别先改结构后补断言）。
- 置信级：已坐实（110 成员全量尺寸已量；越界六成员与 `_pad2` 手算错均为直接读数）；未坐实的只有「消费者是否因此看到脏字节」。
