## 〇、这份文件是什么、怎么用

这份文件把散落在多个账本里的**所有需要人拍板、静态分析定不了案**的问题集中到一处。它的读者假设为「没有本仓库代码访问权、只有世界知识的讨论伙伴」（例如网页端大模型）：每条待决项都自带背景、现状锚点、备选方案、成本与我的推荐，不需要读者去翻仓库就能参与讨论。

**本项目的一句话背景**：把 Minix3 微内核操作系统（原版为 C 语言）的语义用 Rust 语言（`#![no_std]`，不使用标准库）重写到三种 CPU 架构上——x86_64、aarch64（ARM 64 位）、riscv64（RISC-V 64 位）。重写原则是「保持对外行为不变」；三条架构线要在真机（QEMU 虚拟机）测试门上「齐平」——同一项能力，三边要么都有、要么明确登记为正当的架构差异。「齐平」里欠缺的每一条登记在待办清单 `TODO-3ARCH-PARITY-20261006.md`（编号 `P-*`），更大的结构债登记在 `STRUCTURAL-DEBT-REGISTER-20260930.md`（编号 `SD-*`），取证过程记录在 `NK4C-WORKLOG.md` / `NK4B-WORKLOG.md`（小节号 §续-NNN / §1.NNN）。

**讨论前需要知道的词汇**：

- **三条终目标**：目标① 三架构都启动到最小启动脚本的标记行；目标② 十八阶段命令面走通真实的虚拟文件系统消息通路（两者三架构均已达成）；目标③ 上游 Minix3 自带的自动化测试套件（Arch Test Framework，简称 ATF，十八个程序、三十六个用例）在真机跑到终态（aarch64 与 riscv64 已达成，x86_64 从未被纳入——见 PD-01）。
- **门（gate）**：`os/qemu-tests/` 下的一族脚本，每种能力一个，起虚拟机跑一次并给出 `RESULT: PASS/FAIL` 读数。
- **微内核服务对象**：进程管理器（PM）、虚拟内存服务器（VM）、虚拟文件系统（VFS）、服务仓库（RS，负责把程序镜像装进内存）、设备管理（devman）、系统事件框架（SEF，用户态服务的事件循环库）。
- **真源优先级链**：Minix3 原始 C 代码 > 设计文档 > Rust 代码 > 其它文档。凡事实争议，以 `minix3/` 目录里的 C 源码为准。
- **`[ARCH: ...]` 标注**：本项目允许偏离 C 原语义，但必须在「设计文档 + 代码 + 台账」三处一致地标注为架构演进。
- **决议列的约定（定稿后的现状语）**：每条头部有「状态」行——**决策状态**（待决 = 方向未定/需继续设计；可冻结 = 推荐已定、证据核验完成，等拍板；已追认 = 代码/既有裁决已替我们做过选择，决议只剩确认）与**实现状态**（未实施 / 部分 / 已实施 / 无需改动）。两个维度分开登记是为了防两类误读：AI 接手者把「已落地」的条目当成「尚未裁决不可动手」，或把「已裁决」的条目当成「代码已完成」。**本文件的元原则：冻结的是裁决规则与政策，不是规则运行后的数据结果**（PD-09/10/16/28 的共同形状，适用全部条目）；执行参数与数据产物（N 的取值、候选表内容、探针逐站归类）不属方向裁决，登记一次后不得临时调整。定稿前各条末尾为「决议：待定」；定稿时逐条替换为最终选择与被否方案（已于第十轮完成，见各条「决议（第十轮定稿）」行）。

## 二、范围与终目标裁决（决定「齐平」二字覆盖什么）

### 1. PD-01：x86_64 要不要补进目标③ 测试套件的上机面

**状态**：决策=可冻结｜实现=未实施

**背景**。目标③ 指把上游 Minix3 自带的自动化测试套件（十八个 C 测试程序、三十六个用例）打包进根文件系统镜像，在 QEMU 虚拟机里真机跑到终态。装配白名单常量在 `os/xtask/src/image.rs:ATF_BOOT_LEG_READY`，当前只含 `"aarch64"` 和 `"riscv64"`；门脚本有 `test-atf-aarch64.sh`、`test-atf-riscv64.sh`，没有 x86_64 版。「三架构齐平」这句话目前对 x86_64 缺一整块。注意 x86_64 并非没有虚拟机门——`os/qemu-tests/run_all.sh` 会为它构建并运行测试内核——缺的只是这套 ATF 套件的「出生腿面」（把测试程序送进虚拟机并让它们跑起来的装配与启动链路）。

### 2. PD-02：「真多核」要不要纳入本轮战役（撤掉主核钳位）

**状态**：决策=可冻结（范围收窄为乙案+子门）｜实现=部分（AP 唤醒/存活与双核门已有，调度未接、钳位保留）

**背景**。内核调度器目前有守卫函数 `os/kernel/src/sched.rs:clamp_cpu_to_bsp`，把所有「把进程安放到哪个 CPU」的请求一律钳到启动核——代码支持多核启动，但实际只有一个核在干活。登记为 `SD-24`（三架构共有）与待办 `P-ALL-03`。三条未还前置：每核运行队列、核间中断（Inter-Processor Interrupt）三架构接线、抢占指令真正下发到别的核。次级核的早期入口汇编体三架构都已落地并可被唤醒（x86_64 一直完整；riscv64 见 `NK4C-WORKLOG.md` §续-403、aarch64 见 §续-405/406，QEMU 串口有次级核到达汇聚点的证据），但唤醒之后被钳位晾在一边。riscv64 的整套 ATF 与命令面门已在双核配置下跑过且读数与单核一致（§续-407）。

**争议点**。甲案：纳入本轮，按「每核运行队列 → 核间中断 → 跨核抢占」三步撤钳，对照上游 C 的 `smp_schedule`。乙案：维持钳位，把「真多核」显式列为下一阶段弧线。

**世界知识与真源参照**。多核的正确性只能来自多核运行，单核绿不能外推（本项目自己登记过的教训）。Linux 与 Redox 的历史都是先单核功能稳定、再接多处理器支持——本项目现在处于「入口已通、调度未接」的阶段，恰是那一步。反向成本：本项目内核是大内核锁 + 自旋锁模型；「撤钳而不先补每核运行队列」会让进程被安到没有队列的核上——从「大声崩溃」退化为「整机静默停摆」，属最难取证的一类故障。

**我的推荐（第二轮改为乙，采纳网页端意见）**。本轮**不**承诺完整 SMP 调度。理由：多核启动基础设施已存在（次级核能起来、能到汇聚点、双核配置下 riscv ATF 照常全绿），真正缺的是 SMP 调度语义——而那不是一根线，是一条新的正确性维度链（每核运行队列 → 远端入队/出队 → 核间中断 → 远端唤醒 → 远端重排 → 抢占 → 亲和/迁移 → 锁序 → 内存序），容易把刚收拢的三架构主线再炸开。允许一个收窄的子项：**「次级核启动 + 基础中断/异常处理存活」作为独立基础设施门**（对应第一版第一步；第九轮改措辞：原「中断存活」易被误读成「核间中断已通」——实际目标只是「次级核可启动且不因基础中断/异常入口立即死亡」，核间中断与远端调度链属完整 SMP 弧线而非本子门），但不把它定义成「真多核战役已开战」，不纳入本轮终目标；完整 SMP 列为下一弧线。第一版推荐的「三步分步撤钳」路线本身成立，保留为下一弧线的实施件。

**决议**（第十轮定稿）：采乙+子门——本轮不承诺完整 SMP；允许「次级核启动+基础中断/异常处理存活」独立基础设施门（不纳入本轮终目标）；任何撤钳子门的前置清单必含 PD-19 登记的投递腿完成屏障+跨核读对账；「三步分步撤钳」路线保留为下一弧线实施件。被否：甲之全量纳入（SMP 调度是新的正确性维度，会炸开刚收拢的主线）。

### 3. PD-06：三架构同样未完成的服务装配接线，算不算「齐平差距」（`P-ALL-07`）

**状态**：决策=可冻结｜实现=无需改动（口径定义，无实施体）

**背景**。几乎所有用户态服务器与文件系统/驱动/网络二进制的「生产传输」还没接线（主函数空循环占位、`UnimplementedTransport`、客户端协议靠 `ENOSYS` 兜底）。关键事实：这些在**三个架构上同等未完成**。「齐平」的判据是「一端有行为、另一端没有行为才算差距」——这条是三端都没有。

**争议点**。甲案：作为「三架构共有欠账」纳入齐平台账主清单。乙案：判定属「服务功能移植进度」而非「架构间差距」，齐平矩阵不计缺口，只在待办清单以一条聚合条目登记一次（现状即乙案做法）。

**世界知识与真源参照**。Linux 内核与 Redox 的里程碑划分里，「架构支持矩阵」与「驱动/服务完备度」是两条正交进度线：前者关注同一功能在不同硬件上的等价性，后者关注功能本身。混在一张表会让「齐平」读数永远绿不了，也掩盖真正的架构差异。

**我的推荐**。乙（排除在齐平之外，维持一条聚合登记）。请决策者确认这个口径即可。

**决议**（第十轮定稿）：口径确认——采乙，服务装配欠账不入齐平矩阵，维持一条聚合登记。被否：甲（三端同缺属移植进度，混表会遮蔽真架构差异）。

### 4. PD-07：三种内核启动入口形态并存，要不要统一；x86_64 要不要迁移（`SD-1`/`SD-2`）

**状态**：决策=可冻结｜实现=部分（riscv 甲案形态已落地；两形态等价断言未做）

**背景**。内核的「被引导」形态目前不止一种：x86_64 走「内联形态」（引导 shim 与内核同一镜像，经 `BootHandoff` 结构传递平台事实）；aarch64 走「独立 ELF 形态」；riscv64 新落了第三种「kernel-image 自引导形态」（不经 BootHandoff）。问题一（`SD-1`）：多形态并存时，共享启动辅助例程里有两处互相假定「对方的 `.bss`（未初始化全局数据段）由自己清零」，已产生过真实时序隐患（从内核镜像侧把已激活的页表根清零）。问题二（`SD-2`）：x86_64 要不要长期迁到独立 ELF 形态。

**已有的用户预裁决（不可绕过，见 `riscv-reviewlog.md` 章 E）**：E.2 规定「riscv 甲案收口前不启动三形态统一；收口后单独立项；终态选型属用户终局裁决」；E.1 规定「aarch64 独立 ELF 稳定满 10 个真机验证轮次、且 x86_64 无在途启动调试战役时，主线程可直接立项迁移评估，终裁仍报用户」。riscv 甲案已收口（riscv 全链 36/36）。

**争议点**。`SD-1`：甲——三架构统一到独立 ELF + BootHandoff；乙——维持多形态，共享启动例程改显式接口（谁清 `.bss` 写进类型签名）并加两形态等价断言；丙——统一到内联（已被真机证伪否决：aarch64 双根页表使内联不可行）。`SD-2`：迁 / 不迁（挂触发条件清单：内联形态再爆一次难以定位的启动缺陷、出现独立内核 ELF 的真实消费方、需要第三个 BootHandoff 消费者验证架构中立性）。

**世界知识与真源参照**。Linux 各架构的自描述入口本就互不相同（每架构自己的汇编头），业界从不为美观统一引导形态；预防性重构（为尚未出现的消费需求付迁移成本）在软件工程公认反面清单上，且每迁一次都要重付全量真机验证。

**我的推荐**。`SD-1` 取乙（显式接口 + 等价断言，形态数记账；**第九轮精确化：断言对象是「进入正式内核后的共同 boot postcondition」**——内存图可得、内核高半映射有效、异常/中断可接、`.bss` 清零责任声明明确等——**不是入口结构本身相等**；「不统一 boot 机制，但统一 boot postcondition」正是 §七.7 公理「统一语义不统一机制」在启动域的现成实例）；`SD-2` 取不迁、维持触发条件清单。合并拍板为一句：「多形态是登记的现实，不统一；统一与否等触发条件」。与债务登记册自身推荐（riscv 落地先行、等价断言随批、统一仅当触发）一致。**第二轮补充（网页端与本文达成共识）**：这个「不统一」不违反 §八.4 的抽象公理——启动链属于**平台把系统送入 OS 的契约**（boot contract），不是 OS 运行时依赖的硬件机制；把三套引导路径强行做成一个 `BootLoader` trait 反而是「抽象了 OS 根本不需要的东西」（公理第 3 条的反例）。**可冻结。**

**决议**（第十轮定稿）：采 SD-1 乙 + SD-2 不迁——多形态是登记的现实，形态数记账；等价断言对象=进入正式内核后的共同 boot postcondition（非入口结构相等）；统一与否等触发条件清单出现再议（E.1/E.2 预裁继续有效）。被否：SD-1 甲（预防性重构重付全量真机验证）、丙（已被真机证伪）。

### 5. PD-14：riscv64 的装机与交棒形态是否就此定为终态（`E.3` 终局裁决）

**背景**。riscv64 没有 UEFI 固件，引导链选型曾三案（`NK4B-WORKLOG.md` M4.4 上交裁决节）：甲——kernel-image 自己当引导体（入口读固件放在 a1 寄存器的设备树指针、自解内存布局、自装载模块）；乙——写一个与 x86/aarch64 同形的独立 boot-shim 装载体；丙——本轮不点电。评审曾裁「丙（本轮）+ 甲（下一弧线方向）」。**今天甲案形态已真机落地**：riscv 从 OpenSBI 到 ATF 36/36、命令面 18 阶段全绿，全部走 kernel-image 自引导 + QEMU 直核装载链（§续-403/406/407 读数）。`riscv-reviewlog.md` E.3 当时写明「终态选型依赖真机数据，显式不预裁，数据出来后与 E.2 合并一次咨询」——数据现在有了。

**决议**（第十轮定稿，追认性）：采甲——「kernel-image 自引导」定为 riscv64 终态（第三形态计入 PD-07 形态账）；真机数据已齐（ATF 36/36+命令面 18 阶段），E.3 等待的合并咨询即本条。被否：乙（为不存在的统一契约付费）、丙（已由 §八.2 核验的读数取代）。

### 6. PD-15：U-Boot 对照测试腿——装不装系统包，这条腿放弃还是补全

**状态**：决策=可冻结｜实现=未实施（裁决为放弃后仅剩台账标注）

**背景**。riscv64 生产链走 OpenSBI。任务书另有一格「对照」：用 U-Boot 装载同一镜像跑一遍（`test-riscv64-uboot.sh`，现 SKIP）。跑它需要宿主系统安装 `u-boot-tools` 与 `u-boot-qemu` 两个包（需 sudo 授权，agent 不能自行安装）。实质障碍：U-Boot 的 `bootelf` 按 ELF 文件头入口地址直接跳转，而生产镜像入口是高半虚拟地址——页表未开状态下直跳必陷。三个方向：(a) 给链接脚本加平坦物理址入口蹦床；(b) U-Boot 腿只装载不跳转（改启动脚本用 `go` 或自写交接）；(c) 放弃 U-Boot 腿，声明 **riscv64 本项目的生产引导契约仅为 OpenSBI → kernel-image 自引导**，U-Boot `bootelf` 属不支持的外部装载契约（第八轮改措辞：原文「三架构统一走 OpenSBI/boot-shim」与 PD-07「不为统一而统一 boot contract」的裁决相冲——三架构的引导契约本就各不相同且均正当）。

**争议点与参照**。生产系统从不为测试给入口加第二种形态（每加一个入口形态，PD-07 形态账多一个要钉住的变量），(a) 与形态收敛方向相反；(b) 让对照腿只证半程，证明不了完整链路；(c) 在「U-Boot 从来不是本系统生产固件路径」的语义下是诚实收敛。Linux 发行版镜像不会为某个引导器的怪癖另做入口。

**我的推荐（第二轮收紧，采纳网页端意见）**：丙（放弃 U-Boot 腿），且**不必装包实测**——本裁决问的是「U-Boot 属不属于本系统的引导契约」，这是范围问题不是技术问题：**riscv64 的生产引导契约仅为 OpenSBI → kernel-image 自引导**（第八轮改措辞，与 PD-07 对齐——不说「三架构统一装载链」，各架构引导契约本就不同且均正当），`bootelf` 的入口跳转语义属于**另一个引导契约**，为证明「不属于本系统契约的东西」再付真机验证成本，本身就是要避免的开销。台账对照格标 `N/A — unsupported loader path` 即可；除非终目标未来明确改为「镜像必须作为通用 ELF 被 U-Boot 装载」，否则不给它预算。

**决议**（第十轮定稿）：采丙——放弃 U-Boot 腿，不装包实测；对照格标 `N/A — unsupported loader path`；除非终目标明确改为「镜像须被通用 U-Boot 装载」，不补预算。被否：(a) 平坦入口蹦床（引入第四入口形态）、(b) 只装载不跳（半程对照）、装包后再裁（为证伪非本系统契约的东西付真机成本）。

### 1. PD-03：架构专属系统调用返回 BadCall——正当差异还是待实现缺口（`P-X86-04`）

**状态**：决策=可冻结｜实现=未实施（注释未改）

**背景**。内核系统调用分派（`os/kernel/src/syscall.rs:CurrentArchSyscall`）里，aarch64/riscv64 对一组架构专属调用（如 padconf，配置内存控制器引脚的 i386 专属调用）返回 BadCall（等价 `EBADREQUEST`，「非法请求」）。代码注释写「aarch64 分派尚未实现，跟踪于待办 B-X」，而 `01-stage-kernel/todo.md` 已把 B-X 标为关闭。**两处对同一事项结论相反**——典型注释腐化：注释里的历史断言，它自己预告的失效条件兑现后无人回看。

**争议点**。甲案：确认正当差异（上游 C 里这些调用本就 i386 专属，对另两端返回错误码是忠实重写），改正过期注释。乙案：确有 aarch64/riscv64 该实现的专属调用，反过来更正待办的「已关闭」标记。

**世界知识与真源参照**。上游真源可判死：`minix3/` 系统调用表中此类调用带架构条件，i386 之外无对应实现；齐平扫描的排除清单第 7 条也按「依真源为正确」处理了行为本身，本条只剩「注释与待办谁改口」的确认。

**我的推荐**。甲。附带纪律：改注释前 grep `minix3/` 全量核对「有没有任何调用是 aarch64/riscv64 有上游实现而我方缺失」，把核对结论写进注释，一次性封口——防止下一轮扫描把过期注释当真缺口去实现一个上游没有的调用。

**决议**（第十轮定稿）：采甲——确认正当差异，改正过期注释并附全量核对结论。被否：乙（上游 i386 之外无对应实现，不为齐平表象发明上游没有的调用）。

### 2. PD-04：缺页地址「三架构都填、只有 x86_64 消费」——删死填位还是补消费臂（`P-ALL-02`/`SD-15b`）

**状态**：决策=可冻结（核验后定性为诊断记录）｜实现=未实施（getter 清理与台账登记未做）

**背景**。发生缺页（页面不在内存、访问触发硬件异常）时，三架构的软件都把出错地址写进进程表的 `p_fault_addr` 字段；但只有 x86_64 在返回用户态前消费它做精确页表刷新（`os/kernel/src/trap_dispatch.rs`、`os/kernel/src/page_fault.rs:set_page_fault_pending`），aarch64 与 riscv64 填而不读（曾实现消费臂后被回滚）。问题：这两端的「填」是无用死代码，还是消费臂缺失的半成品？

**争议点**。甲案：两架构硬件在陷入时把出错地址直接放进专用寄存器（aarch64 的 `FAR_EL1` 配合 `ESR_EL1`、riscv64 的 `stval`），软件不需要经手——「填而不读」是死填位，删掉填位并在文档写明地址来源。乙案：软件路径同样需要这个值（例如跨层传递给 VM 服务器的缺页消息），补齐消费臂。

**世界知识与真源参照**。体系结构手册级事实：ARM64 的 `FAR_EL1` 与 RISC-V 的 `stval` 都由硬件写入出错虚拟地址；Linux 的 arm64/riscv 缺页处理函数直接读硬件寄存器取地址，内核上下文里没有「软件中转填表」这一环。x86_64 之所以要软件填，是因为页故障只把地址压栈在异常帧里、且本仓选择了经进程表传递的形态——那是 x86 臂的实现选择，不是跨架构义务。

**我的推荐（第二轮修正，原「甲/乙」二选一被代码事实推翻）**。核验结果：填位与送达是**同一段共享代码**——三架构都经 `forward_pagefault_to_vm`（`os/kernel/src/trap_dispatch.rs`，注释自证「C exception.c:112-129 尾巴的单点真源」）：错页地址从 `far_el1`（`aarch64_read_far`）/ `stval`（`riscv64_read_stval`）直读后**装进 `VM_PAGEFAULT` 消息送达 VM**——下游已拿到地址；`p_fault_addr` 的填位处注释原文「Rust 侧诊断记录（C 不保留每进程错页地址——地址只随消息旅行）」。该字段的真实读者 = x86_64 返回用户态前的刷页点（`os/kernel/src/lib.rs` 取 `p.p_fault_addr` 执行 invlpg）+ 诊断打印；getter `last_fault_addr`（`page_fault.rs`）零调用。因此：不存在「aarch64/riscv 各自的死填位」这个可删单元（填位是共享代码，x86 有真实消费），也不需要补消费臂（地址已送达，精确刷页可现读硬件寄存器）。**定案形态**：确认字段为诊断记录、删零调用 getter、维持 `SD-15b` 消费臂回滚不动——网页端要求的事实核验完成，**可冻结**。

**决议**（第十轮定稿，追认性）：采核验后的定性形态——`p_fault_addr` 登记为诊断记录、删零调用 getter `last_fault_addr`、维持 `SD-15b` 消费臂回滚不动；错页地址的权威路径=从 far_el1/stval 直读装进 VM_PAGEFAULT 消息（已落地）。被否：原甲案「删死填位」（填位是共享代码且 x86 有真实消费）、原乙案「补消费臂」（地址已送达，硬件寄存器可现读）。

### 3. PD-05：aarch64 模式① 是幻影还是真缺陷；aarch64 浮点状态跨陷入的保存策略（`P-A64-03`/`SD-23`）

**状态**：决策=可冻结（浮点部分追认性）｜实现=已实施（save/restore+懒轮转接线；余上机门背书）

**背景（写作时点的历史扫描快照，已被后续核验更新——浮点部分当前事实见下方「当前核验事实」段；幻影疑案部分仍维持）**。两件事纠缠在一起。其一，aarch64 曾观测到一类间歇性故障（「模式①」：从内存耗尽到运行命令时段错误等症状的演变），案卷 `NK4C-WORKLOG.md` §续-132 曾判「疑为幻影症状、不出博客篇」；至今没有确定性复现。其二，坐实的缺陷：aarch64 浮点/向量寄存器 Q0–Q31 跨陷入从不保存恢复（`os/arch/src/arm64/fpu.rs:save/restore` 与 `enable/disable` 都是空操作；x86_64 走 SSE/AVX 有真存取；riscv64 的懒浮点轮转已在 §续-130 修复）。仓库里存在写好但零调用方的急切保存机制（孤儿原语，`os/kernel/src/proc.rs:KProcess.fpu_state` 有槽位）。

**争议点**。问题一（定性）：甲——把模式① 立为独立缺陷线继续追；乙——维持「幻影疑案」登记不立项。问题二（修法）：甲——接上已建的急切保存（陷入时检测浮点使用即全量存恢复，实现最短）；乙——按 riscv64 懒轮转形状对齐三架构（陷入只记脏标记，切核/切进程才真正搬运，性能好但状态机复杂）。

**世界知识与真源参照**。浮点不存是正确性缺陷而非性能问题——任何用过浮点的程序跨陷入后数据被破坏就是实锤；这一点不需要裁决，需要修。策略选择上：Linux arm64 用惰性所有权跟踪的懒模型，因为通用内核每秒千万次陷入；微内核重写 + 少进程场景里，急切模型（每陷入至多 528 字节存取）正确性最容易钉死，也更贴近上游 Minix3 简单直接的风格。OS 教学的标准建议：先做正确且简单的，性能证据出现后再换复杂的。

**我的推荐**。问题一：乙（模式① 维持登记、不立项——从未在确定性框架下复现，且 riscv 同类症状的教训是「陈旧探针被误当真身」；保留一条复活触发器：任一浮点测试或 ATF 用例在 aarch64 非确定性失败，立即按确定性缺陷排查流程立项）。

**当前核验事实（第二/三轮静态读码，替代上方历史快照中「从不存恢复」的登记；台账滞后声明）**：背景段里的「Q0–Q31 从不存恢复、enable/disable 都是空操作」是扫描时点（§续-422 前后）的台账陈述，**已被当前代码推翻**：`os/arch/src/arm64/fpu.rs` 的 `fpsimd_save_raw/restore_raw` 已存恢复 Q0–Q31 **+ FPSR + FPCR**（状态结构 528 字节 = 32×16+4+4+4，布局对齐 Linux `struct fpsimd_state`；直接回答了网页端「不只存 Q 寄存器」的提醒），且**懒轮转已接线**：`os/kernel/src/trap_dispatch.rs` 有 EC=0x07 陷入的懒恢复段（每核 `fpu_owner`，先存旧归属再恢复新归属再 `enable`），返回用户态路径的 `disable` 建立 FPEN=0b01 门控。问题二的「急切 vs 懒」实际上已被代码选成**懒**——这正是网页端担心的「按硬件形状强行齐平」的反例教学：三架构的 `FpuArch` 各存自己的状态（x86 是 SSE/AVX 形态、arm64 是 FPSIMD 形态、riscv 是 F/D 形态），OS 层只见「这个进程有一个浮点上下文」，不关心里面长什么样（§八.4 设计公理第 2 条的现例）。

**修正后的本条待决面收窄为**：① 确认结案（`SD-23`/`P-A64-03` 台账刷新 + aarch64 浮点测试用例上机门背书；网页端要求的「急切保存只用于真用过 FP 的进程」已由懒模型天然满足——从未碰 FP 的进程 `fpu_state` 保持零值且被归属门控过滤）；② 模式① 定性（仍取乙）。**可冻结**。

**决议**（第十轮定稿，浮点部分追认性）：模式① 采乙——维持幻影疑案登记不立项，保留确定性失败即立项的复活触发器；aarch64 浮点保存采追认——懒轮转+完整 FPSIMD 状态（Q0–Q31+FPSR+FPCR）已在码，本决议只确认结案、刷新 `SD-23`/`P-A64-03` 台账，余上机门背书属执行。被否：模式① 甲（无可复现性不立案——riscv 幻影教训）、急切保存甲（代码已选懒形，且各架构 FP 状态各异正合公理 2）。

## 四、ABI 与接口形态裁决（牵动冻结布局、影响面最大的一类）

### 1. PD-17：x86_64 的 IPC 状态寄存器占用被调用者保存的 RBX——换不换（`SD-14`）

**状态**：决策=已追认（甲案）｜实现=已实施（R10 迁移落地，见第二轮核验）

**背景（写作时点的历史扫描快照，已被后续核验更新——「ABI 选型本身未动」已被 R10 迁移推翻，当前事实见下方「当前核验事实」段）**。进程间通信（IPC）收发消息后，内核用一个寄存器携带「消息来源/状态」返回用户态。上游 C 在 i386 用 `bx`、在 ARM 用 `r1`；**对 x86_64 没有任何定义**。本仓 x86_64 臂选了 RBX——x86-64 System V 调用约定里的被调用者保存寄存器：编译器有权假定它跨函数调用存活，于是 RBX 有三重身份（出生参数、IPC 状态、编译器活值），历史上已造成服务仓库进程 RBX 被踩的真实事故（现靠包装层手工保存/恢复缓解，ABI 选型本身未动）。riscv64 臂选了 a1（调用者保存的参数寄存器），债务登记册评注「已免疫（选型层）」。`NK4B` 的 P2–P6 里程碑硬依赖本裁决。

**争议点**。甲——状态车道换到调用者保存寄存器（r10/r11，与 ARM 的 r1、riscv 的 a1 同哲学：编译器不会跨调用依赖它）。乙——维持 RBX，把状态写入限制在陷入窗口内（需窗口检测机制，脆弱）。丙——状态彻底移出用户寄存器（单独上下文域，不投递给用户可见寄存器；对用户可见的线上语义偏离最大）。

**世界知识与真源参照**。既然 C 对 x86_64 没有定义，就不存在「偏离真源」的顾虑——这是一张自由牌，理当按调用约定常识出牌。Linux 的系统调用返回走 rax（调用者保存），一切跨特权边界的带内状态都放调用者保存寄存器或内存参数块；Redox 的 IPC 返回走显式返回值类型，不用寄存器暗道。占用被调用者保存寄存器等于每次编译器升级重掷骰子，事故史已经付过学费。

**当前核验事实（第二/三轮静态读码，替代上方历史快照中「选型本身未动」的登记）**。甲案**已在当前代码落地**，本条从「选寄存器」改为「追认已定裁决 + 刷新 `SD-14` 台账」：核验——x86_64 的 IPC 状态车道已迁 R10（caller-saved），三处锤点：内核侧 `os/arch/src/x86_64/boot.rs:or_ipc_status_reg`（注释原文「NK4-C Task C A 案（[ARCH]）：x86_64 的 IPC_STATUS_REG = R10」）、陷入帧 `trap_stub.rs`（GP_R10 车道）、用户侧 `os/libs/minix-sys/src/arch_trap.rs:ipc_trap`（从 r10 取状态，注释记录迁移原因是「RBX 被内核状态写摧毁用户 callee-saved 活值：真机 RS `&self.table`=0，NK4A Task C 六轮取证」）。RBX 剩余用途只剩两个身份：出生参数 ps_strings（`boot.rs` 的 `INIT_USER_CONTEXT`）与消息指针入口车道（`push rbx/pop rbx` 手工保护，全仓 6 处：arch_trap/cpu_identity/trap_stub×2/paging×2，均为 LLVM 保留 RBX 所迫）。

**抽象形状核验（§八.4 公理第 1/4 条）**：状态车道已是 arch trait 后的实现选择（OS 层经 `CpuContextArch::or_ipc_status_reg/clear_ipc_status_reg` 调用，内核通用代码不出现寄存器名；三架构各选自己的 caller-saved 车道：x86_64→R10、aarch64→r1 形、riscv64→a1），不存在上层 `#[cfg(target_arch)]` 泄漏——符合网页端「UserReturn 语义接口，寄存器选型留 arch impl」的要求。剩余动作：`SD-14`/`P-X86-05` 台账状态刷新 + `NK4B` P2–P6 里程碑对「ABI 选型未定」的依赖解除。**可冻结（追认性）。**

**决议**（第十轮定稿，追认）：甲案已被代码实施——x86_64 IPC 状态车道=R10（caller-saved，经 `CpuContextArch` 隔离）；本决议确认结案，余下动作=`SD-14`/`P-X86-05` 台账刷新 + `NK4B` P2–P6 对「ABI 选型未定」的依赖解除。被否：乙（陷入窗口检测，脆弱）、丙（移出用户寄存器，偏离线上语义最大）——均已无需选择。

### 2. PD-18：端点编码要不要演进——收窄 / 扩宽 64 位 / 身份与线上值解耦（`SD-18`/`OQ-1`）

**状态**：决策=可冻结（裁决形态=维持冻结、终局不预裁）｜实现=无需改动（冻结即现状）

**背景**。微内核里每条 IPC 消息携带「发送者端点」（endpoint）：进程槽身份 + 代际计数（generation，防止旧回复错发给复用槽位的新进程）。当前线上编码沿用 C 形态。该类型一旦定型，全部消息布局围绕它冻结：登记册纪律是「此裁决未定期间，一切消息布局演进冻结」，防止「先改布局、后改端点」两次破坏性变更。候选（附十个未定小问题 Q1–Q10，清单在 `edge4.md` §6）：甲——收窄位宽；乙——扩到 64 位；丙——进程身份与线上值彻底解耦（身份留内核，线上只过一个不透明票据）。

**争议点与为什么登记册不给推荐**。这是全仓最大的冻结 ABI 决策，三案各牵动槽数上限（进程表规模）、回复路由正确性（代际位数）、以及所有把端点当整数比较的用户代码。债务登记册原文：预裁这个决定本身会制造「空壳断言」失效模式，故只登记不推荐。

**世界知识与真源参照**。世界知识可给方向：Linux 内核的「内部 ID + 命名空间可见 ID」两层分离正是丙案思路——身份与线上表示分离后两边独立演化；seL4（形式化验证微内核）的回复能力（reply capability）也是「不透明票据 + 内核记账」，代际问题由内核对象生命周期解决而非位宽堆叠。乙案（加宽）是最少思想负担的暴力解，但只推迟问题；甲案（收窄）无已知消费需求支撑。Minix3 的端点 = 槽位 + 代际，其防错发机制本身就靠代际位，收窄会削弱它。

**我的推荐（第二轮修正：采纳网页端意见，撤掉「终局丙」的预裁）**。甲乙丙均不在本轮实施；现编码冻结；**终局形态不预裁**。核验支撑这个更保守的裁决：`os/libs/minix-types/src/types/endpoint.rs` 与 C 真源**逐位一致**——C `minix3/minix/include/minix/type.h:22` 定义 endpoint_t 为 int、`endpoint.h:45` 代际移位 15 位，Rust 侧同为 i32 + `ENDPOINT_GENERATION_SHIFT=15`；现进程表 NR_PROCS=256 对槽位域 15 位（上限 32768）余量巨大，代际域 17 位意味着单槽复用 131072 次才回绕，且 C 自带编译期守卫「NR_PROCS 超限即报错要求加大移位」（endpoint.h:61），不存在任何当前终目标被端点编码阻挡。理由（网页端，本处采纳）：「将来最好 opaque ticket」没有现实需求支撑，解耦本身也是 ABI 重设计——本项目当前最大的风险正是**无理由地制造新 ABI 面**；seL4 的 capability 与 Minix 的 endpoint 分属不同设计语境（前者是对象能力模型的本体，后者是 IPC 协议的组成部分），不存在「更先进」的应然方向。**触发条件只有一条**：Q1–Q10 里出现「现有 endpoint 已经挡住当前实际需求」的答案时才重开；PD-20 的纠正性修复不受本条排队牵制（见彼条口径）。

**决议**（第十轮定稿）：采「不预裁」形态——甲（收窄）、乙（扩 64 位）、丙（解耦）均不实施；现编码（与 C 逐位一致：i32、代际移位 15、NR_PROCS=256 对槽域上限 32768）维持冻结；**终局形态不预裁**，唯一触发条件=Q1–Q10 出现「已挡住当前实际需求」的答案。被否：第一版曾推荐的「终局方向丙」（解耦也是 ABI 重设计，无现实压力不预裁——本条即「不为漂亮提前改契约」的定案存证）、乙（加宽只推迟问题）。

### 3. PD-19：跨内核/用户边界消息的三层屏障——用户→内核的编译器物化、内核→用户的完成/可见性、撤钳后的跨核同步（`SD-13`）

**状态**：决策=可冻结｜实现=部分（用户→内核的编译器物化三架构已实施；投递腿今天无新增待插机制，跨核完成/可见性要求已登记为 PD-02 撤钳前置——不存在「今天该插 volatile 而没插」的欠账）

**背景（写作时点的历史扫描快照，已被后续核验更新——「同类边界还有四道没做」已被第四轮收窄为三层屏障，当前事实见本条「当前核验事实」与「第四轮命名核验」段）**。用户进程交给内核的消息可能还躺在 CPU 寄存器/栈缓存里没落到内存，内核却承诺从内存读它。发送侧已用「物化屏障」修好（一次 volatile 读强制回写；注释解释了为什么编译器栅栏不够——只有易失读能迫使驻寄存器的存写回到内存）。同类边界还有四道没做：投递腿（内核把回复写回用户内存后、接收方运行前的完成屏障）、`senda`（异步发送）、内核自调用腿、riscv64 臂。缺陷类别：在弱内存序架构上，次序漂了是静默故障，最难取证。代码对账显示四条缝各自只经过一个汇聚点（内核投递统一走 `delivermsg`，发送统一走 `IpcTransport` 特征），不是几十处散点。

**争议点**。甲——屏障家族补齐四条缝（每条都是已验证形状的复制，小、局部）。乙——按值 IPC ABI：小消息整体按寄存器/内核拷贝传递，指针+内存形态只留大宗传输（从构造上消灭缺陷类，但等于重设计 IPC ABI，是最大的 `[ARCH]` 偏离，且牵动端点编码与冻结的消息布局）。丙——类型系统强制（仿射句柄，未物化的消息在类型层就过不了边界；优雅但在汇编边界依赖不稳定特性）。

**世界知识与真源参照**。Linux 的 copy_from_user 与 `user_access_begin` 纪律、seL4 的收发全部按值传小消息——乙有现实原型且理论最干净；但乙与 PD-18 同时动消息布局面，必须并案。甲对应「缺陷类已知、机制已验证、剩余工作是复制形状」的工程判断——业界对已验证的局部机制优先于伤筋动骨的重设计。

**当前核验事实（回答网页端「证据条件」：屏障到底保证什么、覆盖面到哪）**。屏障本体 = `os/libs/minix-sys/src/ipc.rs:commit_message_to_memory`：对**整个 Message 做一次 `read_volatile`**。它保证的是三者中的 **a）编译器不把消息值留在寄存器/消除先行的标量存写**——注释原话「`compiler_fence(SeqCst)` 只排序访问、不能迫使驻寄存器的 store 落到栈对象；volatile load 能」。证据链不是直觉：同树 A/B 实验（§续-18/22：aarch64 启动 `sched_start` 最后一条 `msg.m_type=0xF02` 存写未物化→内核读到 0→ENOSYS→启动死锁；插屏障后到 SingleUser+/bin/sh exec，且页表镜像三路比对排除地址翻译因素）。覆盖面已**超过背景段的台账陈述**：用户侧 send/sendrec/sendnb 三腿（§续-22）+ `senda`（ipc.rs:653/699 系调用点）+ 内核调用/SYSCALL 腿（`syscall.rs:176`，注释「三架构统一补齐」）**都已插同一屏障**——「四条缝」收窄为：**投递腿（内核→用户方向的完成要求）与 riscv64 腿复核仍在，但跨核可见性风险窗口今天并不存在**：陷返同核时，同一处理器的存写对自身后续读按程序序天然可见（这是缓存一致性保证的不是编译器保证的），而 `SD-24` 主核钳位使当前所有 IPC 的收发双方同核——投递腿屏障的真需求要等 PD-02 撤钳后才打开。因此本条与 PD-02 的耦合关系被核验出来了：**撤钳（任一步）的前置清单里必须加「投递腿完成屏障 + 跨核读对账」**，否则 PD-02 乙案的第一子门也要带上这笔。另按网页端要求补一句诚实边界：本结论基于当前实现与注释中的同树 A/B 实验，未附反汇编级证据（可选加强项：对已发布二进制反汇编 `ipc_trap` 调用点前后，确认 store 先于 svc/int 指令落地——静态可判，不阻裁决）。

**概念钉句（第三轮追加，进设计文档的建议措辞）**：三个概念必须分开，不得互代——**物化屏障（materialization primitive）解决的是「值是否已进入编译器可观测的内存表示」；它不自动等价于 CPU 内存序（memory ordering），更不等价于跨 CPU 同步（inter-core synchronization）**。仓内注释里「编译器栅栏不够、volatile 才行」说的是第一层；投递腿完成屏障与撤钳后的跨核对账说的是第二、三层——这正是 §八.4 公理的又一个应用面：同名不同层的三个机制不该共用一个词。

**第四轮命名核验（回答网页端「投递腿到底需要哪种机制」的三选一）**：选第三项——**今天两者都不需要，且将来需要的也不是物化**。逐项证据：① 投递腿的内核写是真实的内存存写（经每页 walk→物理地址→直接映射窗口的正常指针写，`os/kernel/src/ipc.rs:KernelUserCopy`，续-76 [ARCH: user-copy-via-dm]），不存在「驻寄存器活值被编译器丢弃」的可能——物化问题是**用户侧编译器优化**特有的（用户变量可能被寄存器化/消除，内核经指针写整块缓冲不会），所以「投递腿=再复制一份 volatile 物化」的默认推断不成立；② 同核场景：写与接收方后续读在同一处理器上按程序序天然可见（存储缓冲对自身后续读一致），陷返切换不提供也不要求额外屏障——今天主核钳位（`SD-24`）使收发同核，无窗口；③ 撤钳后的跨核场景：需要的是**完成/可见性屏障（completion，如 DSB/释放序，随入队-唤醒锁的 release/acquire 序落位）**，属第二/三层——手段不是 volatile 读，位置不是 `delivermsg` 单点复制发送腿形状。本条正文原措辞「投递腿物化完成屏障」按此改名为「投递腿**完成/可见性要求**（预登记于撤钳前）」；概念三分的钉句保留，它是这次命名纠错的依据。

**我的推荐（修正为）**。甲立即做，但范围按第四轮核验收窄为两条：① 投递腿的完成/可见性要求登记（今天同核已由程序序保证，无需插 volatile 物化——见上方命名核验；这笔账的落地位置是撤钳时的入队-唤醒锁序，不是 `delivermsg` 里的镜像屏障）；② 把「撤钳前补跨核完成屏障 + 跨核读对账」钉进 PD-02 子门的验收清单。乙（按值 ABI）与 PD-18 同组——PD-18 已改不预裁，乙随之不本轮实施；丙不启用。aarch64 间歇症状线（模式①/PD-05）尚未排他排除投递腿，但 §续-129/130 已把同族症状归因到懒 FPU——投递腿是残余候选而非首要嫌疑。**可冻结（附①②两条登记）。**

**决议**（第十轮定稿）：采甲的收窄版——用户→内核的编译器物化（send/sendrec/sendnb/senda/kernel_call 三架构已落地）维持；投递腿定性为**完成/可见性要求**（今天同核无需动作），随 PD-02 撤钳前作为验收前置落实（手段=锁序/DSB 类，非 volatile 复制）；反汇编证据为可选加强项。被否：乙按值 ABI（与 PD-18 同步不预裁）、丙类型强制（不稳定特性）。

### 4. PD-20：六个消息联合体成员超出自己钉住的 56 字节上限——怎么修、要不要豁免「布局冻结」（`P-ALL-12`）

**状态**：决策=可冻结｜实现=部分（注释面已改；六成员结构与编译期全量断言未动）

**背景**。进程间消息公共结构 =「头部 + 一个联合体（各消息类型的载荷二选一）」。本仓钉住载荷上限 56 字节、整消息 64 字节，头注宣称与上游协议兼容；C 真源对每个载荷成员都有编译期断言钉 56（`minix3/minix/include/minix/ipc.h` 的 `_ASSERT_MSG_SIZE` 族）。Rust 侧全量实测 110 个成员，**六个联合体成员实际超 56**（最大 72），直接成因是手算填充量写错（某成员注释自写「补齐到 56」，实际字段加填充共 68、按 8 对齐成 72）。后果：整 `Message` 被撑到 80；`MessageUnion::default()` 只初始化前 56 字节，第 56..72 字节永不落值；内核两处按 `size_of::<Message>()` 整块搬运，内核→用户方向会把 16 个不确定字节搬进用户缓冲。今天无读者踩到、不挡功能，但破坏「两条消息字节相等才可比」的对账可复现性，且安全注释「全初始化无填充读风险」在此事实上措辞偏强。

**争议点**。甲——逐成员把填充改回「字段和恰好凑足 56」，并加**编译期全量断言**防复发；改动跨六个成员与其全部读写点，必带三架构上机对账。**断言形态已由 C 真源定死为严格相等（第八轮机械锚）**：`minix3/minix/include/minix/ipcconst.h` 的 `_ASSERT_MSG_SIZE` 宏体是 `sizeof(msg_type) == 56 ? 1 : -1`（L17-18，工具生成行号），且 `mess_u8`…`mess_u64` 全族逐个套用（`ipc.h:20/25/30/35` 等）——C 的不变量是「**恰为 56**」不是「不超 56」。因此 Rust 侧新断言必须是 `assert!(size_of::<T>() == MESSAGE_PAYLOAD_SIZE)`；早前措辞「对每个成员断言不超 56」作废——`<=` 会默许「成员被裁到更小而协议不变量静默破坏」这类未来变更（40 字节裁成 32 仍 PASS）。方法论入档：**不让正文的「钉 56」替 C 真源决定语义，让 C 宏本身决定 Rust 断言的比较关系**——本次三处「钉 56/不超 56/凑足 56」措辞不一致正是靠回读宏定义才消除歧义。**断言链完整性由第九轮钉成三层（协议不变量是结构链不是成员集合）**：全部 `MessageUnion` 成员 `== 56` ∧ `MessageUnion == 56` ∧ `Message == 64`（C 真源整消息 64 = 8 字节头 + 56 载荷；代码现钉的 80/72 是违规现状的过渡记录，修复完成后换代为目标三件套）——「每个成员都 56」并不能推出 union 不膨胀：未来引入高对齐成员或改动头部布局都可能使 union>56 或整消息>64，三层都钉才叫机械守卫（不信推导，把不变量写成守卫——本仓自家纪律）。乙——只改最大一个（`MessLsysGetsysinfo`），整消息从 80 收到 72，但不变量仍不成立，留下一堆局部修。丙——把上限常量改成 72 承认现状——与 C 的 56/64 判例正面冲突。

**世界知识与真源参照**。真源立场鲜明：C 用编译期断言把每个成员钉死 56，这是上游的设计不变量不是巧合。Linux 线形结构同样显式定长 + 静态断言；Redox 走带显式长度的字节串、根本没有隐式尾部。丙等于把自己的「协议兼容」声明推翻；乙留下「本仓宣称的不变量为假」的账。

**我的推荐**。甲。附加一条需要显式拍板的口径：**本次修复属「纠正性修复」（回到本仓自己声明并与 C 一致的不变量），不受 PD-18 的布局冻结辖制**——冻结辖制的是演进性变更。若不同意此口径，本条就必须排在 PD-18 之后，代价是把静态可判、有编译期断言兜底的卫生修复挂进最大 ABI 决策的排队。执行顺序：先加全量断言（按第八轮定的**严格相等**形态）跑一遍、让编译器列出全部违规成员（可能多于六个已观测的——若有成员小于 56，`==` 断言同样报出，而 `<=` 会漏），再逐成员修，禁止「先改结构后补断言」。**第二轮：网页端强烈赞成（「甲，纠正性修复」），无新增反对证据，可冻结。**

**决议**（第十轮定稿）：采甲，按第八/九轮定稿形态执行——断言比较关系由 C 宏定为严格相等，断言链三层（全成员==56 ∧ MessageUnion==56 ∧ Message==64）；纠正性修复口径成立，不受 PD-18 布局冻结辖制；先加断言后改结构；修复完成后代码中过渡性 80/72 钉断言换代为目标三件套；必带三架构上机对账。被否：乙（局部修，不变量仍假）、丙（改常量与 C 判例正面冲突）。

### 5. PD-21：内核读写用户内存的安全模型选哪个（`SD-22`，riscv64 `sstatus.SUM` / aarch64 `PSTATE.PAN` / x86_64 未来的 SMAP）

**状态**：决策=可冻结（两层都定）｜实现=大部分（丙案已在 IPC 消息面落地：续-76 [ARCH: user-copy-via-dm]，`copy_msg_from_user` 已改每页 walk→物理地址→DM 窗，与 senda 腿 `copy_via_root_pages` 同源；直引点清册第七轮已跑——用户 VA 裸解引用全仓 grep 违例为零（现存 volatile 命中均为页表自身/内核自有缓冲/DM 别名读）；残余=守卫成文 + 乙案硬件层落地）

**世界知识与真源参照**。Linux 现实是乙+丙并行：拷贝路径走窗口开合；SMAP/PAN 公认是纵深防御标配——单靠软件纪律的「先翻译再访问」在安全审查里不算数，因为它防不住「忘记翻译」的新调用点（本仓现存两处即此形态）。seL4 干脆内核不映射用户内存，是丙案极致形态——它的违例检查同样在翻译层。所以丙不是「不安全」，而是把防线从硬件挪到翻译层。

**我的推荐（第二轮按网页端意见把「三选一」改写成「两层规范」——丙与乙不是互斥方案；方向措辞经第五轮去歧义；保护对象边界经第七轮钉死）**。第一层（现在定）：丙 = **正式的软件访问规范**——**所有内核对用户地址空间的读写（双向：内核读用户页与内核写用户页都算），都必须经统一翻译/验证路径**（与 21 处现实一致，改动只落直接取用户虚拟地址的函数；**第九轮精确化：「统一」指同一套访问规则——目标地址空间的 root → walk → 权限/边界验证 → 物理地址 → DM 覆盖验证 → 访问——入口函数可以有多个**（`copy_msg_from_user`、`copy_via_root_pages`、`cross_space_copy` 各为一入口），但不得绕过这套语义规则——统一语义、不统一机制，本条即 PD-33 在此的应用），并把**禁止项**写成守卫规则：不得新增「拿到用户 VA 后直接解引用」的路径——读与写同禁（静态可判、零新抽象）。第二层（加固批次，与 PD-22 同批）：乙 = **第二层硬件防线**——窗口守卫 + 启用 PAN/SUM/SMAP，作为纵深防御给任何残留/未来的直访上保险。甲（全程开位）否决：把保护变成摆设。

**两层各自的保护对象（第七轮钉死，防硬件防线被神化）**：软件规范（丙）防的是「用户地址未经翻译/验证即访问」，其中**翻译结果本身的正确性由「walk 目标进程自己的页表根 + 逐页 U 位/越界校验 + 物理范围落在 DM 窗口内」三重证明**（代码实证：`copy_via_root_pages` 的 checked_add 半界 + 每页 walk 注入 `CurrentPteWalk::walk`，`kernel/src/ipc.rs`；`cross_space_copy` 的 `resolve_physical` 两端预验 + `physical_range_in_dm_window`，`kernel/src/vm.rs`）；PAN/SUM/SMAP 硬件防线的判断对象是「经**用户映射**（页表项 U=1 的页）的直接访问」——riscv 规范为 SUM=0 时 S 态对 U 页的数据访问陷入，x86 SMAP 同样围绕页表项 U/S 属性（Intel SDM Vol.3A）——它**不替代翻译结果的正确性验证，也不保护经 direct-map 别名对错误物理地址的访问**（`*(direct_map(wrong_pa))` 这类 bug 不触发任何屏蔽位）。两类 bug 不同，两层防线各治一类；本裁决不把乙描述成 direct-map 的万能物理防线。Linux 自身的定位同此（内核自保护文档把这类机制归为「内核不应无预期访问用户态」，不取代 uaccess 语义）。

抽象形状按 §八.4 公理：OS 层只见语义接口（进/出用户访问窗口），寄存器名（PAN/SUM/SMAP 是哪一位、怎么开）留在各架构 impl——上层不得出现 `if arm {…} else if riscv {…}` 式泄漏。**可冻结（两层都定，只是分层排期）。**

**决议**（第十轮定稿）：采两层规范——第一层丙=正式软件访问规范（内核对用户地址空间读写双向同走「目标空间 root→walk→权限/边界验证→PA→DM 覆盖验证」规则，入口函数可多个但不得绕过；禁止新增直接解引用用户 VA 的路径）；第二层乙=窗口守卫+启用 PAN/SUM/SMAP，入安全加固批（与 PD-22 同批）；两层保护对象边界按第七轮钉死句执行（硬件位不替代翻译验证）。被否：甲全程开位（保护变摆设）。

### 6. PD-22：内核地址空间映射是否实行 W^X——运行期内核高阶映射与早期启动恒等窗口的分步收紧（`SD-12`）

**争议点**。甲——装载器按内核镜像段表拆分权限：代码段只读+可执行、数据段可写不可执行（需扩展内核间信息结构 `KernelInfo` 传段表布局）。乙——维持现状，登记为已知安全债。

**世界知识与真源参照**。W^X（写与执行互斥）是现代内核底线配置：Linux 把模块文本设只读+可执行、数据可写不可执行，新 arm64 内核对全部内核内存强制「可写则不可执行」；Windows HVCI 直接拒载违反映射；Redox/hermit 系亦分权限映射。硬件强制的成本只在装载器一次性做对，运行时零开销。

**第二轮核验（先回答网页端的五个生命周期问题，再定修法形状）**。① 低物理恒等窗口的用途是**早期启动**：`os/kernel/src/lib.rs` 页表构建 Step 1 注释写明必须映射整低 4GB（UEFI 装载器代码/数据可能在非 CONVENTIONAL 区）且带 EXECUTABLE（切页表根后的取指）；② **正式内核运行后它在两个架构上已自然消失**：aarch64 的 `switch_address_space` 把 TTBR0 换进程序根 + `tlbi alle1is`，注释原文「identity entry is gone after the first switch」，内核运行期经 TTBR1 钉死高半 + 别名窗口访问物理；x86_64/riscv64 同理：进程根只继承高半内核映射，低半 identity 不进每进程根（x86_64 的 `inherit_supervisor_half` 只拷高半）——运行期仍长存的 RWX 暴露面不是 identity，是 **内核高阶映射整段不分段（Step 2 全范围 `kernel_read_write()|EXECUTABLE` 大页）与直接映射窗口**；③ C 真源对照（网页端未料到的重要事实）：i386 `pg_identity`（`minix3/minix/kernel/arch/i386/pg_utils.c:162-184`）用 **USER|WRITE** 映整 4GB（i386 无 NX 位，等于用户态也能读写执行低 4GB），Rust 侧 supervisor-only **已比 C 更严**——分段 W^X 是 `[ARCH]` 演进而非保真修复；④ 段信息来源：boot-shim/装载器解 ELF 时已有段布局，「按段拆」可在 boot 根构建处先行落地，**不必预设扩 KernelInfo 契约**（网页端的提醒完全成立：安全目标正确 ≠ 扩大交接契约就是最小解；只有当运行期重建进程根确实需要段表时才传）。⑤ **第四轮改错（推翻②/④两处判断；逐项读 `arch/src/arch/paging.rs` 三架构共享的进程页表构建例程 `init_page_table`，592-650 段实测）**：上一段「x86_64/riscv64 进程根只继承高半、低半 identity 不进进程根」的表述**对进程根不成立**——identity 窗口是被**重放进每个进程根**的（fix27 段 4，flags = `kernel_executable_writable()` 整块 RWX，且 x86 切换 CR3 后的第一条取指实测落在它：`IP=CR2=0x1daf0d9d`（真机崩溃现场，fix27e 注有全句；riscv 切换后的首次取指同理，续-103 注））。进程根的真实形状是**已按段拆分**的四段：段 1 内核文本逐页 `kernel_executable_writable()`（RX**W**——文本段有 X 但多一个 W）；段 2 数据段 `kernel_read_write()`（**已 NX**）；段 3 两个直接映射窗口 `kernel_read_write()`/`read_write()`（**已 NX**——网页端问的「direct-map 是否含 EXECUTABLE」核验答案：**不含**，内核窗 `establish_boot_dm` 与 VM 窗都用无 X 标志，故无需新增「DM 设 NX」步骤，目标形态已半）；段 4 identity 整块 RWX。因此运行期长存的 W^X 暴露面精确为两块：**文本段的多余 W** 与 **identity 窗整块 RWX**；而 boot 根的整段大页 RWX 高 map（第二轮所述）仍在，但它不是执行进程的根。收窄 identity 的依赖已写在码注里：「需要装载器的段级来源信息」（[ARCH] 已标注）——即不是拍脑袋扩 KernelInfo，是代码里登记的已知前置。

**我的推荐（第四轮按核验事实重排三步；方向不变、对象精确化；Step 2 验收语义经第五轮钉死）**。Step 1 = 进程根内核**文本段去 W**（RXW→RX，`init_page_table` 段 1 改用 `kernel_executable()`；前置核验：文本页有无运行期写入者——重定位写、探针自改等，静态可判）；Step 2 = 进程根 **identity 去依赖与退出**——安全目标不是「把 identity 按段重新赋权限后继续留着」，而是机械的验收条件：**「切换进程根 → 首跳 → 进入正式高半内核执行路径」这一连续区间完成后，identity 映射不再属于正常进程地址空间**（实现路径：切高半入口或首跳在 identity 内完成后立即拆除该段；依赖装载器段级来源信息——fix27e 注已登记该前置，扩 KernelInfo 与否届时按此判定）。这样定义是为了防止后续执行者把「拆 identity」错误实现成「identity 继续留着、只是权限缩小一点」；Step 3（可选观察）= boot 根高 map 整段 RWX 的同步拆分。判据（作用域随适用范围声明限定，并经第八轮再收窄到子域）：**对正常运行期进程根中的「内核映射子域」**——内核映射部分的执行位只允许出现在内核文本段；内核数据段与内核直接映射窗口均无 X；内核文本段无 W；运行期不保留 identity 映射。**用户地址空间自身的 RX/RW 映射（用户文本段等）不属于本条 W^X 判定对象**——不这样限定，实现者可能写出「全根所有执行位必须属于内核文本」的荒唐断言，把用户程序的文本映射判成错误；严格说「整个进程地址空间的 W^X」是另一个问题（属 VM 对用户段的映射纪律），本条裁的是**内核映射的 W^X**；boot 根不参与该运行期断言（否则验收条件与「boot 根 RWX 属受控残留」的声明自相矛盾）；与 PD-21 乙案同批、不挡终目标。DM 窗已 NX 无需步骤（第二轮核验）。

**适用范围声明（第六轮追加，防术语作用域误读）**：本条裁定的 W^X 适用对象是**正常运行期的进程地址空间根**；**早期 bootstrap 根（boot root）允许存在受生命周期限制的 RWX 映射**（Step 3 是否进一步收紧属后续强化，不构成对本裁决的反例）。完整措辞（第八轮收窄到子域）：**正常运行期进程根中的内核映射子域满足 W^X（内核文本 RX、内核数据/DM NX、identity 去依赖退出）；用户段自身的 RX/RW 不在本裁决射程；早期 bootstrap 环境的 RWX 属启动契约范围内的受控残留**。后人不得以「boot 根仍有 RWX」质疑本裁决未执行，也不得以「实行 W^X」推定「从第一条指令起全地址空间永远无 RWX」。验收断言的作用域与本声明一致——只量运行期进程根（见上方判据句）。

**决议**（第十轮定稿）：采甲的三步版——①进程根内核文本段去 W（RXW→RX，前置=文本页无运行期写入者的静态核验）；②identity 去依赖与退出（验收=切换后区间完成后 identity 不属正常进程地址空间，不得以「留着只缩权限」替代；依赖装载器段级来源，扩 KernelInfo 届时按码注前置判定）；③boot 根高 map 拆分为可选后续。适用范围=运行期进程根的内核映射子域，用户段与 boot 根不在断言射程（与适用范围声明一致）；DM 窗已 NX 无需动作。被否：乙维持现状。

### 7. PD-23：进程管理器的调用号枚举要不要上移到共享类型库（`OQ-2`）

**状态**：决策=可冻结｜实现=未实施

## 五、SEF 服务事件框架批裁决（`P-ALL-08` 的 T 系列余项）

### 1. PD-24：四类拦截（热更新 / 状态搬移 / 覆盖统计 / 故障注入）要不要纳入本轮建模（`T4`）

**背景**。上游 Minix3 的 SEF 库在每次收信前会问内核一组「拦截状态」：RS 热替换自身时挂起的服务状态搬移、故障注入调试、服务覆盖统计（`SYS_STATE_*` 系统调用族）。本仓内核侧实现了部分系统调用，但用户态框架完全不建模这四类（设计文档 `03-stage-rs/20-rs-sef-framework.md` §3.6 T4 明写「未建模，需人裁决」）。

**争议点**。甲——本轮建模（对齐 C 完整事件循环语义）。乙——不纳入，登记 `[ARCH]` 演进项，等消费方出现。

**我的推荐**。乙（登记不纳入）。附加：若将来任何一类被启用，先补「未建模拦截的回归哨兵测试」（SEF 文档 §5.2 第 6 项）再实现，防止「实现了但没人能证明它在拦」。

**决议**（第十轮定稿）：采乙——四类拦截本轮不建模，登记 `[ARCH]` 演进项；任一类启用前先补回归哨兵测试。被否：甲（无消费者，YAGNI；本仓连 RS 完整消息面都未通电）。

### 2. PD-25：同一上游语义的三套回调特征（trait）要不要收敛为一套（`T5`）

**状态**：决策=已追认（第十轮拍板：共享语义词汇与契约，不强制统一 trait 类型；决议见本条末）｜实现=未实施（词汇收敛与被触及轴宿主锚点属实现）

**背景**。服务框架的「事件回调集合」在 Rust 侧有三套平行 trait：`SefCallbacks`（rs/is 用）、`SefHooks`（devman 用，方法面不同）、fs-rt 自有钩子面。上游 C 里它们来自同一组 `sef_cb_*` 函数指针表。三套 trait 意味着「SEF 语义修正」要改三处，且已造成真实断链（PD-26 的 devman 钩子从不被回调正是形态分歧的直接产物）。曾被标注「交代码卓越度评审裁决」，但收敛牵动公共 API 形态，按项目纪律需人确认。

**争议点**。甲——收敛为单一 trait（方法面按 C 的回调表逐一对应）。乙——维持三套，只在文档记录映射。

**世界知识与真源参照**。Rust 生态反面教训是 trait 增殖（每个 crate 自带抽象层）；正面惯例是「协议特征放中央 crate、实现方引用」（与 PD-23 同构的单一真源应用）。上游 C 回调表是唯一真形，一一对应最可审计。

**我的推荐（第二轮改为「不立即裁甲」，采纳网页端意见并升级判据）**。判据不是「它们是不是同一张 C 回调表」，而是「它们是不是同一个 **OS 语义契约**」（§八.4 公理第 1/3 条）——「来源同一张 C 表」≠「Rust 必须只有一个 trait」：三套 trait 完全可能分别服务不同消费者边界而共享同一套语义规范。先建逐方法同构表（首轮草稿已有形状：C `sef_cb_*` 表 11 个 typedef（`minix3/minix/include/minix/sef.h:56-311`）× rs/is `SefCallbacks`（`os/servers/rs/src/sef.rs:92`，全表面含 lu_* 热更族——因为只有 rs 有热更新消费者）× devman `SefHooks`（`hooks.rs:102`，仅 init_server/on_signal 两方法，对应 vtreefs `init_hook`/`got_signal` 的形状）× fs-rt 三态 `SignalAction` 家族钩子），每项标：同语义/同参数/同生命周期时点/同错误模型/同调用者。**已核验的初步信号恰好印证了网页端的担心**：三套不是全表同构——方法集（全集 vs 子集）与参数形状（i32 signo vs 三态判定）都不同。裁定规则：同构轴合并；不同构则**保留多个 trait，但统一每个回调的语义规范与真源文档**（一个回调一份规范，各 trait 只是不同子集视图），绝不为「trait 数量好看」造超级 trait（伪统一 = 把硬件/机制形状当语义抽象，公理第 3 条禁止）；也为统一不强塞空方法——`lu_*` 族只有 rs 有消费者，就让它只存在于 rs 的子集视图里。**预期终态形状（第三轮网页端给出，本处采纳为目标而非约束）**：同构表做完后，最可能出现的是「共享的是语义规范（vocabulary），不一定共享 trait 类型」的三层结构——SEF 语义词汇表在上，RS / devman / fs-rt 各按自己的消费者边界取子集视图；这个结构比「一个超级 trait」更干净，也应作为同构表完成后的默认候选。PD-26（devman 死钩子）仍先行处理，与本条不冲突。

**决议**（第十轮定稿，决策方终审文本）：共享 SEF 信导语义契约与 `SignalAction` 三态词汇表（一份定义，归 minix-sef/minix-types）；`on_signal` 为该语义轴的统一契约名；**但不强制各消费者物理上共用同一个 trait 方法——最终 trait 形状由实现阶段按实际生命周期/副作用决定**；init 族、RS 专属族（init_response/lu_response/signal_manager）保持各自消费者边界不合并；热更五件套随 PD-24 延后不预先建模；devman 死钩子由 PD-26 先行删除。被否：「把统一 trait 方法本身作为冻结目标」（语义统一≠类型统一≠调用点同形，违反 PD-33）、「一张 C 表合一个超级 trait」（不同构轴强行同房）。

### 4. PD-27：补 C 的 `sef_cancel` 逃生门时，库的返回形态（`T2` 通电前置）

**状态**：决策=可冻结｜实现=未实施（逃生门未建，本条是通电硬前置）

**背景**。上游 C 的 SEF 事件循环里，服务的信号处理函数若决定退出，会调 `sef_cancel()`；它把「当前这次阻塞收信」取消，让 `sef_receive_status()` 返回 EINTR（被中断的错误码），服务主循环随即检查标志退出（真源 `minix3/minix/lib/libsys/sef.c:161` 族）。本仓没有这道逃生门：框架把管理器形信号消息吞掉后继续阻塞收下一帧——于是「处理函数想退出、退出决定排在下一帧之后」的服务形状一旦发方链通电就会死锁（已登记红线，见 WORKLOG §续-418）。设计文档 §5.2 第 5 项列了两个候选形态。

**争议点**。甲——返回 EINTR：收信结果携带中断错误，服务循环天然看见（与 C 控制流同形）。乙——新增 `Cancelled` 事件变体：事件枚举多一臂，全部显式 match 的消费点要改。

**世界知识与真源参照**。C 真源形状明确（cancel → EINTR 回报），甲是忠实重写；乙是发明新语义，且本仓对「新增 SefEvent 变体」已有否决先例（变体面扩大击穿 sched/vfs/fs-rt 的显式 match）。Rust 惯例里 EINTR 对应 `ErrorKind::Interrupted`，是重试循环的标准信号，读者不会误解。

**我的推荐**。甲（返回 EINTR）。配套：各服务主循环按 C 形状「收到中断 → 检查退出标志 → 退出」；T2 各站点的死锁注释同步改写为逃生门说明。本条是 T2 发方链通电的硬前置，不定计不得接线。

**决议**（第十轮定稿）：采甲——库层逃生门以返回 EINTR（`ErrorKind::Interrupted` 形状）实现，与 C 控制流同形；配套各服务主循环「收到中断→检查退出标志→退出」；本条是 T2 发方链通电硬前置。被否：乙新增事件变体（击穿 SefEvent 显式 match，发明新语义，否决先例在册）。

### 5. PD-34：`process_init` 六段动作的统一落点（`T3`，勘察后新立）

## 六、内存与容量架构裁决

### 1. PD-28：服务器进程堆的终解——接可增长页供给，还是继续扩静态池（`SD-11`/`SD-8`）

**状态**：决策=可冻结（第五轮升档：冻结「PageSupplier + VM_BRK 终解 + 首迁对象按最小风险机械选择」；候选表属实施阶段产物，不构成方向二次裁决）｜实现=未实施（生产页供给为零）

**背景**。用户态服务器的堆全部是**焊死在 .bss 里的固定大小静态池**。历史上反复上演同一出戏：某程序工作集超池 → 分配失败 → 扩池一轮（512→1024 页）→ 撞上下一个上限 → 再扩；且扩池会平移内存布局、触发「加载器给了没清零的页」另一类问题（WORKLOG §1.55–§1.59 连续五轮皆此家族），还发现「连续多页只能从 bump 区发、已散页无法拼大块」的结构性碎片（扩池解决不了碎片）。对照上游：Minix3 服务进程用 `brk` 系统调用向 VM 服务器要页、堆按需增长（账本记载 libc `brk.c` 走 `VM_BRK`；RS 服务默认要求预映 8 MiB）。对照业界：Redox 用户程序走内核供页上的常规增长堆；Linux 进程堆由内核按需缺页供给——「固定池焊死 .bss」在生产操作系统里不存在。仓里 `PageSupplier` trait（向 VM 要页的接口）已建好，缺的是接到每个服务器初始化的「交换供给者」那一步，以及决定走 brk 还是 mmap 通道。

**争议点**。甲——VM 支撑的增长堆：按既有 `PageSupplier` 缝，配「预 reserve 防重入、出生握手后再装」次序，逐服务器增量迁移（每迁一个，装机前行为不变）。乙——继续静态池容量轮（每爆一次扩一次）。丙——给池加保守上界并修自栈缺页（§1.59 曾用丙止血）。

**世界知识与真源参照**。上面已给：C 真源是 brk 增长堆；Redox/Linux 同型。乙案的问题不只是土：实锤是散页碎片化扩池解决不了，治标都算不上。甲案唯一真风险是**引导期先后**：VM 自己也是用户进程，它出生前向谁要页——所以 VM 这一个服务保留静态池（引导特例），其余服务器接 VM 供给。

**我的推荐（第二轮修正批次次序，采纳网页端意见；终解方向不变）**。甲（与债务登记册推荐一致），通道子裁决选 **brk 风格**（忠实 C 的 `VM_BRK`；mmap 留作演进）。**撤回第一版「第一个迁移对象选 VFS（爆得最狠）」**——理由（网页端）：第一只小白鼠的任务不是解决容量问题，而是验证「分配器 → PageSupplier → VM 请求 → 映页 → 返回」整条闭环；拿最复杂、最容易爆的 VFS 首迁，任何失败都可能是 VFS 自己的问题，诊断价值最差。**VFS-例外条款核验为不成立**：静态读码确认全仓生产 `PageSupplier` 实现**为零**（trait 与 `FailingSupplier`/`FixedPoolSupplier` 两个测试替身同住 `os/libs/minix-rt/src/alloc.rs`，全仓唯一命中文件）；`break_via`（VM_BRK 客户端封装，`os/libs/minix-sys/src/vm.rs:216`）存在但**零生产消费者**（只有自身测试引用）；所有服务共享同一份 `SlabAllocator`（`GLOBAL_POOL_BYTES` 现为一配置 2048 页/另一配置 1024 页，§续-279c MFS 预算轮）——没有任何服务已有现成 brk 链，VFS 也不例外。**修正后的批次**：按「最小风险 + 最强诊断能力」排序，先列候选表（每个用户态服务的：静态池大小、实际工作集、分配器形态、是否依赖 VM 先启动——全部静态可数），首选最小载体（测试载体或最简服务）做 page-supplier 证明活着，链路翻绿后再逐服务迁移，VFS 最后受益、不首当其冲；VM 自身保留静态池（引导特例）。**「机械选择」的固定排序优先级（第九轮钉，消灭「为什么不是 VFS/shell/这个」式人为讨论）**：① 避免 VM 启动循环依赖（VM 自身除外，被 VM 出生所依赖者亦除外）；② 最小实现/依赖面；③ 能完整覆盖「`PageSupplier` → `VM_BRK` → 映页 → 返回」闭环者优先；④ 同分时取工作集更小者。**第五轮重新定性**：本条冻结的是政策——「甲：PageSupplier + VM_BRK；首迁对象按『最小风险 + 最强诊断价值』机械选择」；候选表本身是实施阶段产物，它的产出与排序不再构成架构方向的二次裁决（读者不得把本条误读为「brk 本身未定」）。

**决议**（第十轮定稿）：采甲的政策冻结版——终解=VM 支撑的增长堆，通道选 brk 风格（忠实 C 的 `VM_BRK`，mmap 留演进）；VM 自身保留静态池（引导特例）；首迁对象按第九轮钉死的四级固定排序（避免 VM 循环依赖→最小依赖面→能覆盖完整闭环→同分取工作集小）机械选择，候选表属实施产物不构成二次裁决。被否：乙容量轮（散页碎片化实锤证明扩池治不了）、丙保守界（止血形，非终解）、VFS 首迁（诊断价值最差，且 VFS 例外条款核验不成立）。

### 3. PD-11：用户态线程模型与 futex 归属哪个阶段立项（`SD-32`/`OQ-4`）

**背景**。上游 Minix3 的用户态线程库（libmthread，协程式绿线程）与 libc 线程桩在本仓无对应物；内核也没有 futex（快速用户互斥锁）。已有预裁决 OQ-4：归 14-stage-runtime 阶段立项，但无批次无排期。Minix3 的测试与命令全部单线程，今天不缺它任何功能。

**争议点**。甲——现在就开 `[ARCH]` 线程模型设计文档。乙——维持延期，每个规划周期显式重登记一次（防静默遗忘）。丙——std 上机（宿主机标准库联调面）成为前置目标时再议。

**世界知识与真源参照**。上游自身就是答案：Minix3 的 libc 线程是桩、libmthread 是绿线程——连上游都没做内核级线程。为上游不存在的真消费者提前设计锁原语是教科书式过度设计；「显式重登记」可参照把 unsupported 项做成带检查清单防腐化的做法。

**我的推荐**。乙（与登记册推荐一致）。触发条件写清：出现第一个多线程消费者（真实程序或测试）即升格为 14 阶段立项。

**决议**（第十轮定稿）：采乙——维持延期，每规划周期显式重登记一次；触发条件=出现第一个多线程消费者（真实程序或测试）即升格 14-stage-runtime 立项。被否：甲（为上游都不存在的内核级线程消费者提前设计锁原语=过度设计）、丙（并入 std 前置，无必要）。

### 5. PD-31：全仓严格模式静态检查有存量告警点，合入门怎么定（clippy `-D warnings` 腿）

**状态**：决策=可冻结｜实现=部分（人工棘轮已在执行；CI 机械化与基线元数据未做）

**背景**。xtask 检查的第二腿 `clippy --workspace -- -D warnings`（把任何告警当错误拒绝）实测断裂：共享类型库的一条「枚举变体尺寸差过大」存量告警即整条拒绝，内核单包就有三十余条存量告警。同时本仓每笔改动实际执行的是「与基线文件对账、新增必须为零」的棘轮纪律（仓根的 `clippy_base.txt` 即此先例）。语义修正三选，属编排裁决，已登记上交。

**争议点**。甲——保留 `-D warnings`，批量清完存量后翻绿。乙——降为报告制 + 「新增必须为零」棘轮（与现行人工纪律一致，把它机械化进持续集成）。丙——维护逐条抑制（allow）豁免清单。

**世界知识与真源参照**。Rust 社区对大仓静态检查的通行做法正是棘轮（ratchet）：只卡新增，存量按批次消化；一次性清存量在小团队长仓库里几乎从未成功过，且会把功能改动堵死。豁免清单（丙）腐化风险高——豁免无人回看。

**我的推荐**。乙。存量按「谁改哪块清哪块」的童子军纪律消化，清完的模块从报告名单摘除；全仓存量归零时再议翻回 `-D`。**第二轮追加落地纪律（网页端补充，非新裁决）**：基线文件不得是裸数字，必须绑定五元组元数据——工具链版本、目标三元组、特性开关、包集、clippy 版本（外加可复跑命令与指纹）——否则「今天 37 个告警、明天换工具链变 42 个」会把工具链漂移误判成代码退化。

**决议**（第十轮定稿）：采乙——报告制+「新增必须为零」棘轮机械化进持续集成，基线绑定五元组元数据（工具链/目标/特性/包集/clippy 版本+指纹）；存量按童子军纪律消化，归零后再议翻回 `-D`。被否：甲（一次性清存量在小团队长仓库从未成功且堵死功能改动）、丙豁免清单（无人回看，腐化高）。

### 6. PD-32：分层边界守卫要不要豁免仅供测试编译的代码（`B3` 命令边界守卫）

**状态**：决策=已追认（OQ-N5）｜实现=已实施（豁免已在脚本内；余下 14 处生产违例是待办不是本条实施体）

**背景**。仓里有一条守卫脚本 `tools/check-command-boundary.sh`（检查用户态命令 crate 不许直接触碰 IPC 传输层等下层设施，必须经运行时库）。它报出 40 处违例，分两类：其一，终端控制命令的测试代码（三十余处，全在 `#[cfg(test)]` 门内）直接用共享类型库的类型常量——测试代码不进生产二进制，守卫该不该管它需裁决；其二，三处**生产代码**（init 的两个模块、一个游戏二进制）直接使用 IPC 传输层类型——这是真违例，缺一个顶层封装或按登记转 14 阶段。

**争议点**。甲——守卫只查非测试代码（豁免 `#[cfg(test)]` 门内）。乙——不豁免，测试代码也改走封装。

**我的推荐（第二轮核验后，本条的裁决部分已关闭）**。核验：守卫脚本 `tools/check-command-boundary.sh` **已实现该裁决**——脚本头注原文「Scope ruling (OQ-N5): this boundary guards PRODUCTION layering, so `#[cfg(test)]`-gated modules are stripped before the checks」（awk 逐段剔除 cfg(test) 模块、保留原行号）；本轮实跑命中 14 处 FAIL，抽查确认全部是**生产代码**（`os/commands/bin/shell/src/bin/sh.rs` 直接 import 共享类型库 9 处——该文件无 cfg(test)；init 的 `execve.rs` 直触 IPC 传输层等），台账记录的「termctl 测试代码 30+ 处」已被 OQ-N5 豁免消化。网页端担心「cfg(test) ≠ 全部非生产代码」的精确性问题：当前 os/commands 下**不存在** `tests/` 目录与 `examples/`（find 全量核实），故文本形态剔除与「生产 artifact 依赖边界」今天等价；把网页端的精确化要求登记为**守卫的后续实施纪律**：若未来 commands 下出现集成测试/示例文件，豁免集合必须按「是否链接进生产产物」判定。**剩余的不是裁决而是待办**：14 处生产违例补顶层封装（errno 类走 minix-sys 再导出；DirectTrapTransport 三处按守卫提示登记 14-stage 封装）。**裁决部分可冻结（已落地追认）。**

**决议**（第十轮定稿，追认）：cfg(test) 豁免裁决已由 OQ-N5 落地（守卫脚本已实现，文本剔除≡今日生产边界）；本决议确认该裁决，并采第八轮网页端精确化为后续实施纪律：若出现集成测试/示例文件，豁免按「是否链进生产产物」判定。剩余 14 处生产违例（shell 直用 minix_types、init execve 直触 IPC 层等）为待办非裁决。被否：推翻豁免回到不区分测试的二值守卫（噪声磨掉守卫可信度）。

### 7. PD-33：跨架构抽象设计公理四条要不要写入项目设计宪法；落地节奏选哪种（第二轮新增，源自网页端对「怎么设计不丑」的回答）

**状态**：决策=可冻结（四条措辞经第三轮收紧、第五轮去歧义；网页端第五轮明确「可以入宪」）｜实现=未实施（未入宪，守卫未建）

**背景**。本轮讨论暴露出一个反复出现的判定刚需：面对架构差异（aarch64 的两个页表根、三套 SEF 回调 trait、各架构不同的错页地址寄存器……），到底哪些该用 trait 统一、哪些不该。网页端给出了一条可操作的原则：**不要追求「三架构实现长得一样」，要追求「三架构对 OS 暴露的语义接口一样」**——硬件表示（CR3/SATP/TTBR0+TTBR1、寄存器名、指令名）属于 architecture implementation，不进入 OS 语义接口；一个 OS 逻辑对象（地址空间、浮点上下文、用户访问窗口）允许由不同数量的硬件对象实现。候选例：aarch64 双根不抽象成「假单根」，而是抽象 Minix 需要的逻辑地址空间（用户半/内核半），双根是它的实现细节。

**待决问题一**：以下四条要不要写入设计宪法（`CLAUDE.md` 的关键约束节 + 全局概念文档），作为所有后续裁决的第一层筛子（措辞经第三轮收紧，边界按四层模型划清）：
1. **硬件表示不得泄漏进 OS 语义接口；允许出现在 architecture boundary / arch implementation 内**。本项目的四层模型：OS 语义层（进程、地址空间、消息、用户访问这些概念）→ 架构边界层（仓内已有的 15 个 `*Arch` trait：`FpuArch`/`CpuContextArch`/`TlbArch`/`DirectMapArch`/`PteWalkArch` 等，见 `os/arch/src`——**这一层就是硬件边界接口，出现 TTBR0/CR3/SATP 的语义是它的职责**）→ 各架构实现 → 汇编/控制状态寄存器。真正禁止的是：OS 语义代码直接依赖硬件表示（`if arm { write_ttbr0(..) }`、`match arch {…}`），而不是「整个 trait 世界不能出现硬件名词」——把 arch trait 也压成「不能说硬件名字」的伪纯净层，同样是违反公理的错误抽象。
2. 一个 OS 语义实体可以由不同架构的不同硬件形态实现（「一个逻辑对象」不要求「一个硬件对象」）。
3. 不为消除架构差异而制造伪统一：只有语义确实相同才共享 trait；差异属于 OS 语义本身时保留显式差异。
4. architecture impl 可以复杂；OS 语义层也可以因 **OS 语义本身**（调度器、IPC 状态机、虚存策略、进程生命周期、信号投递）而复杂——但其复杂度**不应来自具体硬件表示**：上层依赖的是统一语义契约，不依赖实现内部表示。（第八轮改措辞：原「OS 层必须简单」会被念成审美型 gate——「这个函数怎么这么复杂？违反公理」，而那不是本公理要拦的东西。）
附带配套三问（每次遇到架构差异先问）：这是 OS 关心的语义还是硬件事实？把硬件名词全删掉还能说清接口吗？有没有两个硬件实现共同满足同一个语义（有→trait 存在的理由）？另附带边界一条（由 PD-07 共识提炼）：**启动契约（boot contract）不在抽象射程内**——它是平台把系统送入 OS 的方式，不是 OS 运行时机制，强行统一反而违反公理第 3 条。

**守卫形态的第六轮修正（防 grep 教条化）+ 第七轮禁面收窄（消除「自己打自己」）**：主守卫原措辞「OS 语义 crate 不得 import 架构专属符号」过宽——会把正当的「OS 语义层 → 架构边界 trait」依赖也误杀（内核通用逻辑依赖 `TlbArch`/`CpuContextArch` 正是四层模型设计出来的关系）。机械定义改为：**OS 语义层允许依赖架构边界接口（仓内 `*Arch` trait）；禁止直接依赖具体架构实现模块、具体架构类型、CSR/汇编原语与 `x86_64`/`aarch64`/`riscv64` 实现符号**——允许：OS→`CpuContextArch`；禁止：OS→`minix_arch::riscv64::…`、`write_ttbr0`、`csrw satp` 类具体操作。这一改完，公理与守卫完全同构，守卫不会反过来杀掉自己的边界层。依赖边界可机检（cargo 依赖图 + 模块可见性），**文本 grep 仍降为辅助线索、不是规范本身**。理由：文档和代码注释里完全可能出现「在 aarch64 中，AddressSpace 的 activate 最终由 TTBR0/TTBR1 完成」——这是**解释实现**，不是泄漏；照文本一刀切会绑住教学面（本书类文档正是本仓的产出物之一）。另登记现状距离（实测，诚实基线段，免后人把公理误读成「已达成」）：`kernel/src` 非 `arch/` 子目录的通用代码现存约 93 处 `cfg(target_arch)` 分支、多处内联汇编（lib.rs 11、trap_dispatch.rs 7、syscall.rs/proc_table.rs/smp.rs 各 2），与第七轮实测的 65 处 `minix_arch::{具体架构}::` 子模块导入同性质——内核通用层今天的部分职责本身就落在架构边界上，公理收敛的射程与逐位归位属**实施工作**（随 PD-02/PD-19/PD-21 等落地逐步收紧），不是裁决本身要一次还清的债。

**冻结前合规实测（第七轮，按收窄后的定义量用户态）**：用户态语义 crate 中存在 **4 处**直接调用具体架构实现模块 `minix_arch::riscv64::paging::vmdm::*`（`os/servers/vm/src/vmdm_bridge.rs` 的 register_read/write/zero 三处 + `alloc_page.rs` 的 zero_page 一处）。处置：**登记为重构待办，不阻裁决冻结**（代码不符合裁决 ≠ 裁决要退回；裁决照冻、形状靠执行收敛——本文件元原则的又一次应用）。守卫建设时先裁射程三选一：① 把 VM 服务器定性为架构边界层成员而豁免（它是页表机制的用户态执行体，C 对位 `arch_do_vmctl.c` 本就是架构代码；豁免写进守卫措辞）；② 把 vmdm 通道收进 `*Arch` 式边界接口（新增一个页表操作特征，VM 不再 import 具体实现）；③ 已知例外白名单（改动最小，但例外清单需定期回看，防成惯例外）。**方法论提醒（第八轮，网页端）**：不要预设「抓到具体架构 import → 必抽一个 `*Arch` trait → 问题解决」——公理真正要问的是「这个承载架构的职责为什么出现在这里、这里是不是它合理的边界」：若结论是「VM 服务器本身就是承载架构的服务实现体」（它既是 OS 语义的一部分，又是物理地址空间/页表机制的实际执行者，与调度器/进程生命周期那类纯内核语义代码不同），则四处 import 应被**重新归类**而非必须消灭；只有结论是「VM 语义层不应知道 vmdm」时方案②才成立，且②不得变成新的抽象冲动（公理第 3 条的反向适用）。后续 PD-21「守卫成文」与本条「守卫建设」一律用收窄后的定义。

**待决问题二（用户提出的落地节奏困境）**：「先跑通再重构」与「初始就按最佳设计实现」哪个对？候选：甲——全部先跑通，设公理达标重构波；乙——一切从初始就按公理最佳设计实现；丙——**契约形状先行、实现允许粗糙**：trait 的语义接口形状（方法名、参数、返回值、禁止泄漏的硬件名词）从第一天就按公理定并钉住（宿主测试 + 守卫脚本），trait 后面的各架构 impl 允许临时、单架构化、甚至丑，后续只改 impl 不改契约。

**世界知识与真源参照**。选丙的论证：① 工程经济学——改动成本不对称：契约破坏波及全部实现者与调用者，实现替换只影响一个模块；先定契约，重构从「伤筋动骨」降为「局部替换」，回归面天然收窄——这止住了用户「先跑通再重构没有足够测试回归」的担心（回归锚点从「行为读数」升为「契约形状断言」，宿主测试可钉）。② 业界先例——Linux 的 file_operations/driver_ops 接口先稳定、各厂商实现千奇百怪互不影响；Rust embedded 生态的 HAL 模式（trait 定语义、各芯片 impl 自便）同构；Minix3 自身的 `FpuArch`/`CpuContextArch` 已是此形状且本轮核验运转良好（PD-05/17：OS 层只见 save/restore/状态车道，不知道 Q0–Q31 还是 XMM，不知道 R10 还是 a1）。③ 甲的风险：实现里的硬件泄漏会长进调用方代码（调用者依赖具体形状后，契约再想改就是 ABI 风暴）——公理违规是会增值的债务；乙的风险：未跑通的链路上谈最佳设计＝造空壳断言，且违反 YAGNI（PD-18 本轮刚因此撤掉终局预裁）。④ 现有裁决已全部在丙的轨道上：PD-17/19 的屏障在汇聚 trait 落一次；PD-21 的「进/出用户访问窗口」接口即用户建议的 `UserAccess::enter/exit` 语义形状（具体 trait 名/层归实施时定，不在待决清单里预设）；PD-25 新判据（语义契约而非 C 表）就是公理第 1 条的应用；PD-04 定性结论（错页地址随消息走单点真源，OS 层不分 FAR/stval/CR2 三套 getter）同构。

**裁决理由·网页端对原则的再表述（第三/四轮复核原文，入档供本条及后续引用为原则的正式措辞）**：
- 关于「优美」的定义（第三轮末）：「优美不是让三个实现的代码长度差不多、看起来一致；而是**同一层的代码拥有同一语义；不同层的差异待在该待的地方**。真正优美的抽象通常不是把所有差异塞进 trait，而是把差异留在实现里，让接口根本看不见它。」
- 关于原则的性质（第四轮末）：「这套原则已经不再是『Rust 封装硬件』的普通硬件抽象层（HAL）思路，而是在明确区分『**OS 语义对象**』与『**硬件承载对象**』。aarch64 的双页表根、不同的浮点状态形态、不同的错页地址寄存器、不同的系统调用返回寄存器、甚至不同的启动契约，都可以用同一套原则自然解释，而不需要一项项打补丁。」
- 关于示范案例的书内措辞（第四轮 §6，比本文件现有表述更精确，定稿时可直接采用）：「**ARM 的两个页表根是硬件事实；Minix 的地址空间才是 OS 语义。正确的抽象不是把两个根伪装成一个根，而是根本不把『根的数量』作为 OS 语义。**」——它应该被叙述成设计原则的实体证明，而不是「为兼容 ARM 做的特殊处理」。
- 关于本清单成熟度的判语（第四轮末，兼作本文件的方法注脚）：「现在这份东西已经明显不一样——**不是代码看起来更一致，而是为什么允许不一致，已经被定义清楚了**。」

这四段不是修辞装饰：它们是本清单多数条目推荐方向的**理由层**——PD-04/05/17/19/21/25 的推荐全部能由「语义对象≠承载对象」这一句推出；后续任何新条目遇「要不要统一三架构写法」之争时，引用这四段即等于引用公理本身（§8.4）。
