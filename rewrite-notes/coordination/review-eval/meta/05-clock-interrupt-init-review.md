## 二、九问问卷

### 1. Detection：以前漏的现在能发现吗？哪些盲区仍漏？

**`PASS`。**

新发现里有实质内容，且都能落到源码：

- **死校准链**：`os/kernel/src/clock.rs:280` 的 `set_tsc_per_ms` 全仓零调用者（`rg -n 'set_tsc_per_ms' os/`
  只命中定义行），因此 `TSC_PER_MS` 恒为 0，所有毫秒换算走 `DEFAULT_TSC_PER_MS = 1_000_000`
  的静默默认（`os/kernel/src/clock.rs:120`、`:155-160`）。这是 C 的 `tsc_per_ms[cpuid]` 校准行为
  在 Rust 侧丢失，不是措辞问题。
- **无范围守卫的截断**：`os/kernel/src/trap_dispatch.rs:1970` 的 `IrqVector::new(id as u8)`
  在 PLIC 源号 ≥ 256 时截断成 `TIMER_IRQ = 0`，会让外部中断走进定时器钩子链。
- **语义层的架构泄漏**：`os/kernel/src/irq_manager.rs` 有 11 个 `cfg(target_arch)` 块，
  其中一个把 QEMU 的 PLIC context 约定 `2*hart+1` 写成语义层函数，另一个导出 ARM 常量名
  `SCHED_SGI_INTID`（`design-d2.md:1124-1130`）。
- **反证轴**：CLAIM 04 用 C 源码推翻了“定时器编程不在 `cstart` 里”的无条件表述，
  证据链 `arch_init → apic_single_cpu_init → lapic_enable(0) → apic_calibrate_clocks`
  与 `apic.c:491`、`:499-512` 对得上（本轮复核见第三节 3.2）；CLAIM 05 用 `min(nr_irq_vectors, 16)`
  推翻了“64 条全屏蔽”的口径表。
- **读者轴**：READER-A-05（`PPI`/`SGI`/`SPI` 三个 load-bearing 术语全篇未定义）、
  READER-A-07（8259A 供向量与 IOAPIC RTE 供向量两种模型互斥）、
  READER-B-06（“跳过注册”推演在 x86/aarch64 上不会产生 `Spurious`）、
  READER-C-07（`PROBE_TICKS = 1` 时 `PROBE_TICKS - 1 = 0` 的除零）都是真实问题。

仍漏的盲区：

- **B-05（假反事实）**：FACT-12 抓到 `sleep(1) → 1.67 秒` 这一处在仓内没有对应机制，但
  B-05 的另一半“反事实前提先证伪”没有形成机械动作；读者 C 的 C-18..C-21 四条“低置信高价值”

  `CNTP_CVAL_EL0` 的复位值在 ARM ARM 里是 UNKNOWN）。
- **B-06（断链渲染）**：锚点门 106/106 只验解析，不验渲染；本轮没有渲染抽样。
- **B-07（端口义）**：没有载体，未测。
- **B-15（公共入口调用方枚举）**：本轮零代码改动，未行使。
- **B-01 的第一遍被削弱**：P-DESIGN 第一遍（只看 C 语义与 Ch1/Ch2）是翻译残留的干净探测器，

### 2. Precision：误报多少？有没有角色或类别模式？

### 3. Design quality：是否发现可删除的抽象、翻译残留、错误建模、多余状态、不合理 trait、多余复杂度？

**`PASS`。**

本轮设计轴不是命名与注释级意见，证据如下（均带可复核锚点）：

- **可删除/已死的抽象**：`ClockArch::read_ticks` 无实现者调用、三个 `CLOCK_*` 静态量零读写、
  `X86_64ArchInit::acpi_tables` 只存不解析、`disable_timer_irq` 无调用者
  （`design-d2.md:947-985` 的 DESIGN-15 逐项核实）。
- **错误建模**：`is_bsp: bool` 加运行期分支，`tick_bsp` 与 `tick_ap` 在 release 下同义，
  `clock_irq_handler` 绕过两个包装直调 `tick_with`（DESIGN-02，`design-d2.md:201-260`）。
- **多余状态**：每 CPU 定时器状态逃逸到全局静态量 `TICK_INTERVAL`×2 与 `LOCAL_TICK_ICR`，
  用 0 当哨兵，`period_ms` 是死参数（DESIGN-07，`design-d2.md:493-561`）。
- **不健全的类型边界**：`IrqVector(pub u8)` 没有范围不变量，管理器按 64 条、x86 只寻址 16 条、
  IOAPIC 写没有引脚上界（DESIGN-12，`design-d2.md:789-841`）；riscv64 的 `id as u8` 是它的
  活路径后果（DESIGN-17）。
- **测试形态**：四个 `os/arch/tests/*` 用 `include_str!` + 字符串包含来钉源码文本，
  改对常量值不会红、改名字会假红（DESIGN-13，`design-d2.md:842-907`）。
- **翻译残留**：`lapic_base` 死字段、`is_bsp` 布尔、两个 0 哨兵、`IrqVector(0)` 双义、
  `assume_held` 妥协（DESIGN-14，`design-d2.md:908-946`）。

不足有两点。第一，18 条设计项 0 条实施、0 条接受，全部转出；设计轴的“找得到”成立，

## 五、面板完整性与可执行性约束

用户要求检查的三件事，逐条回答。

### 5.1 首轮 5 个角色被平台以 `inactive` 回收

`loop.md:19` 写“首轮批量派发 5 个角色时，平台以 `inactive for 600000ms` 回收了 P-FACT、P-DESIGN D1、
P-READER A/B、P-REFUTE；随后改为逐个派发并加‘边查边写盘’要求，全部补齐”。

这是平台的可执行性约束，不是文档缺陷，应该写进工作流：

- **并发上限**：一次最多派发 2–3 个面板 agent，不要 5 个一起发。600 秒的无写盘阈值对“读 2198 行文档 +
  32 个 Rust 文件 + 19 个 C 源”的角色不够。
- **边查边写盘**：每个面板 agent 的 brief 必须要求先建报告骨架、每完成一节就追加写盘，而不是最后一次性写。
  本轮重试时加了这个要求才补齐，说明它有效。
- **重试预算**：每个角色最多重试 1 次；第二次仍被回收就把该角色标成 `MISSING`，在 `loop.md §1`
  写明“本轮该维度无覆盖”，不要让主 agent 用“全部补齐”一句话掩盖覆盖缺口。
- **成本记录**：`metrics.md:8` 的“面板约 3h（含批量 inactive 重试）”应该拆成“有效面板时间”与
  “重试等待”，否则下一轮无法判断并发上限是否值得调整。

### 5.2 读者 A/B 合并

`loop.md:19` 写“读者 A/B 合并为一个两段式 agent（`panel/reader-ab.md`），独立性弱于分角色，
但材料隔离相同”。

合并本身可以接受，但要加两条约束：

- **合并必须记录独立性折扣**：`loop.md §1` 已经写了“独立性弱于分角色”，但没有说这对判定有什么影响。
  下一轮如果 A/B 再合并，应要求 B 段在写之前不读 A 段（同一 agent 内也可以按“先写完 B 段再读 A 段”
  的顺序执行），或者把 B 段交给第二个 agent。
- **合并不能变成默认**：`review-loop` 技能 L1 的默认配置是“500 行及以上：P-FACT、P-DESIGN D1+D2、
  P-READER A、B、C”。本轮是高风险篇目，按配置应该 6 个角色；实际是 5 个 agent（A/B 合并）。
  合并的理由是平台回收，不是成本预算，应该在 `loop.md §1` 写成“VARIANCE”，而不是“缩编”。

### 5.3 D1 用 `grep '^#'` 带出 Ch3 标题

`design-d1.md` 开头自述“为定位章节边界，我对目标文档跑了一次只匹配行首井号的标题检索，
输出里带出了第 3 章以后的小节标题文本（一行标题，无正文）”。`loop.md:21` 判“D1 的‘独立设计’不成立”。

这应该变成材料隔离的可执行约束：

- **禁止 `grep '^#'`**：面板 brief 只允许 `grep -n '^## '`（章级）或由主 agent 提供一份“允许章节的标题清单”，
  不允许面板自己用会匹配到 `###` 的模式。`review-panel.md` §6 应该给出这条命令级的禁令，
  不能只写“不得读 Ch3/Ch4”。
- **污染必须用三档状态**：本轮的“部分污染”是规则外状态，和 D01 的 `PARTIAL-VIOLATION` 是同一类问题
  （B-16 仍 OPEN）。按 B-16 的候选分级，D1 读了 Ch3/Ch4 的标题属于“现有实现或 Ch3/Ch4 正文 = 作废”，
  应记 `INVALIDATED`，不是“部分污染、只作参考”。如果主 agent 认为标题不足以作废，就要在
  `review-panel.md` 里把“标题是否算材料”写成明文，不能每轮临时裁定。
- **污染面板的输出不能被下游当独立输入**：D2 被允许读 D1 报告，这本身是协议允许的；但如果 D1 是
  `INVALIDATED`，D2 的“D1 主张”列就只能当“参考提案”，不能当“独立设计”。本轮 `design-d2.md`
  的 DIFF-TABLE 把 D1 的主张逐条对照，做法是对的；缺的是 `loop.md` 对“D1 无效后设计轴还剩多少独立性”
  的明说。

### 5.4 L4 复验没有在交付前执行

`loop.md:67` 写“待跑：anchor、doc-code-map、doc-ref-check、doc-code-density、doc-style-lint、
eval-trace-check、cargo check”。我在报告阶段重放了其中六项，全部通过（见第 0 节）。这说明产物状态
是好的，但**运行本身没有 L4 证据**：`review-loop` 技能 L4 要求“台账重放：每条‘已修’行给可重放
`grep` 命令与命中输出”，本轮的 `defect-ledger.md` 六条 ① 的“复验”列全写“L4 文档五门重跑”，
没有一条给命令与输出；“修复段回读：由发现该问题的角色或同角色冷启动实例”也没有记录。
这不是“门没跑”的问题，是“轨迹里没有门的证据”的问题，而 `eval-trace-check.py` 不检查这一项。
建议把 L4 的证据要求写进轨迹门（见第七节建议 5）。
