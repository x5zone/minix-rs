- 位置（含原文摘录）：§2.9，L1009–L1013。摘录一（L1009）：「板号在两步里落地，缺名或查表失败**在更早的一步就已经中止**」。摘录二（L1011）：「它执行 `POORMANS_FAILURE_NOTIFICATION`（即 `svc #00`…）——此时还没进 `kmain`，更没到 `intr_init`」。摘录三（L1013）：「因此「板号为 0 导致 `intr_init` 走 `else` 执行 `panic(…)`」这条路，只在**绕过了 pre_init 的情形**下才会走到。反例要说清是哪一种绕过：「全名在 `board` 环境里丢了」对应的是**第二步查表失败、板号保持 0**，`pre_init` 本身并未被绕过——它先通过（短名命中），随后本步才失败；真正绕过 `pre_init` 的是「短名也不在表里」那种情形。两种情形都以 `machine.board_id == 0` 收场，区别只在停在哪一步。」
- 严重度：P2（局部论证无法重建，但小节主论点"板号不是硬件给的"不受影响）。
- 问题：主张句与它自己的展开互相矛盾。按文中事实：短名缺失 = pre_init 失败 = `svc #00` 停机、"更没到 intr_init"，即"绕过（失败于）pre_init"的情形恰恰到不了 intr_init panic；而全名丢失 = pre_init 通过、第二步失败 = board_id 0 = 走到 intr_init panic，即 panic 路径恰恰在"未被绕过"时走到。无论把「绕过」读成"跳过 pre_init 的闸"还是"越过 pre_init 往下走"，摘录三里必有一句反着说；「反例要说清是哪一种绕过」还先预设两种情形都是绕过、随后又否认其中一种（"pre_init 本身并未被绕过"）。
- 影响：读者无法判定"哪种情形会停在 intr_init 的 panic"，摘录一的主题句（"缺名或查表失败在更早的一步就已经中止"）对全名场景也不成立；本段作为"板号为 0 何时 panic"的边界结论不可用。
- 证据或推理：三个摘录并在一段内：A 说失败在更早一步中止；B 说短名缺失时停在 pre_init、到不了 intr_init；C 说 panic 只在绕过 pre_init 时走到。B 与 C 直接冲突（绕过 = 到不了；不绕过 = 能到）。这是纯文内逻辑冲突，与 C 事实无关。
- 最小修复：改写为两场景直陈：「pre_init 自身失败（短名不在表）在 `svc #00` 处停机，到不了 intr_init；pre_init 通过但第二步全名查表失败时 `machine.board_id = 0`，intr_init 走 `else` panic。两种失败都以 board_id==0 收场，区别只在停在哪一步。」并删去「只在绕过了 pre_init 的情形下才会走到」与「反例要说清是哪一种绕过」两句。
- 置信度：高（文内矛盾自成证据）。
- 是否需源码核实：是——修复措辞取决于 `set_machine_id` 是否也写 `machine.board_id`、`get_board_id_by_name` 失败是否返回 0（本次不读源码，按文内自洽性判定）。

## SUGGESTION RD04-RB-S12

- 位置（含原文摘录）：§2.3 L543「这里有一个容易读错的算术：`s` 是 `int`、`sizeof` 是无符号类型，`-1` 在减法前被提升成 32 位无符号数，`(-1 - 36) / 4` 得到的是**正数 1073741814**（不是"负值"）——循环会进入」。
- 严重度：建议。
- 问题：算式隐含 `size_t` 为 32 位（i386）的前提而未注明。按 C 标准做通常算术转换时 `s` 提升到 `size_t` 的宽度随平台变：i386（32 位 size_t）得 1073741814，循环进入；64 位 size_t 下 `(2^64 - 37)/4` 截断进 `int` 后是负值，循环不进入——两种口径结论相反。
- 影响：在 64 位宿主上读此推演的读者会算出不同结果并怀疑自己或文档。
- 证据或推理：C 标准整型提升规则 + LP64/i386 的 `size_t` 宽度；文档的目标 C 树是 i386，结论对其正确，但前提没写。
- 最小修复：句中加括注「（i386 的 `size_t` 是 32 位，本算式按此口径；64 位 `size_t` 下截断结果不同，循环不会进入）」。
- 置信度：高。
- 是否需源码核实：否（C 标准算术 + 目标平台常识）。
- 若我错了：若 Minix3 i386 构建的 `size_t` 另有定义，括注改成实际宽度即可，"未注明前提"这一点不变。
- 命中清单：验10。
