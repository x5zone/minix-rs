## FINDING RD04-READER-C-01（P1）

- 位置：§1.4（L133）vs §4.1（L1584）vs §6.1（L2610）。§1.4：「Rust 侧同一错排会让 `init_clock_and_interrupts` 的第一行 `platform_desc()` 触发 `Frozen` 的读取断言（§4.1）。」§4.1：「Phase B 的第一个动作 `init_protection` 已经无条件读 `platform_desc()`（用于 BSP logical id），所以无论把调用点挪到 `init_clock_and_interrupts` 之后还是 `boot_init_timer` 之后，都会先在 `init_protection` 触发同一句断言」「原本要验证的时钟/中断消费者永远到不了，所以症状只会停在 `init_protection`」。§6.1：「栈顶是 `Frozen::get`，其下是 `platform_desc`、`init_protection`、`kmain`……时钟/中断消费者在这一症状里不会出现——它们永远到不了」。
- 严重度：P1。
- 问题：同一个错排实验（冻结晚于消费）的失败点位，概述章说是 `init_clock_and_interrupts` 的第一行，实现章与诊断章都说是 `init_protection`，并明确断言时钟/中断消费者「永远到不了」。§1.4 的指针还指向 §4.1——被指章节给出的恰是相反结论。
- 影响：按概述建立「谁先炸」模型的读者，到 §6.1 用诊断表核对调用栈时会对不上；两处只能有一处是真，文档没有告诉读者该信哪处。
- 证据或推理：Phase B 内部顺序是 `init_protection` → `init_clock_and_interrupts`（§4.1），而 `init_protection` 无条件读 `platform_desc()`（§4.1 正文与 §4.9 的 `init_protection` 节选都出现 `platform_desc().cpu_topology()`）。因此任何一种错排（挪到 `init_clock_and_interrupts` 之后、`boot_init_timer` 之后、或干脆不调 `init_from_kinfo`）的第一个读取点都是 `init_protection`，不存在能让 `init_clock_and_interrupts` 第一行成为首个读取点的错排。
- 最小修复：§1.4 该句改为「Rust 侧同一错排会让 Phase B 第一个动作 `init_protection` 的 `platform_desc()` 触发 `Frozen` 的读取断言（§4.1）；`init_clock_and_interrupts` 的第一行永远到不了（§6.1）」。
- 置信度：高（0.9）——纯文档内部矛盾，不依赖任何外部事实。
- 是否需源码核实：判定矛盾不需要；判定哪一侧与代码一致需读 `os/kernel/src/lib.rs` 的 `kmain`/`init_protection`。
- 若我错了：若 `init_protection` 实际不读描述符（即 §4.9 节选失真），则方向反转（§1.4 对、§4.1/§6.1 错），不一致本身依然成立。
- 命中清单：自相矛盾；复述漂移（概述未跟上实现章后来加入的 `init_protection` 读取点）。

## FINDING RD04-READER-C-02（P2）

- 位置：§1.4（L133）C 侧半句：「C 侧会撞上 `acpi_phys2vir` 的 `vm_running` 检查——发现函数在 VM 起来之后拒绝工作（§1.3），而消费者（`apic_single_cpu_init`、`discover_cpus`）分散在启动序列的不同位置（SMP 构建下第二处跟在更晚的 `smp_init` 里）」。对照 §1.3（L76）：「发现必须在 `vm_running` 变真之前完成」；§2.1（L296）：「而**真正消费 ACPI 结果的 APIC 初始化在发现之后、同一个函数体内**——`acpi_init()` 与 `apic_single_cpu_init()` 在 `arch_init` 里一前一后」；§2.8（L869）：`acpi_rsdp` 的读者「内核内：`detect_ioapics()`；用户态：ACPI 驱动（经 `SYS_GETMACHINE` 拿一份拷贝）」。
- 严重度：P2。
- 问题：概述断言「省掉第 ④ 段、让消费者各自去读会坏在 vm_running 检查上」，但按文档自身的时间线，两个被点名的内核消费者（`arch_init` 内、`smp_init` 内）全部运行在内核初始化阶段，而文档从未确立任何一个内核消费者运行在 `vm_running` 置位之后；§2.8 给出的内核内读点也只有启动期的 `detect_ioapics()`。据此，「会撞上检查」的确定性失败推不出来，能推出的只是「每个分散位置都必须各自满足 VM 之前」这条约束被放大、`acpi_phys2vir` 的 panic 降级为兜底防线。
- 影响：第 ④ 段（缓存/冻结）在 C 侧的存在理由被表述成一个文档自身证据撑不起的失败机制；读者复述时会传播这个未经证明的因果链。
- 证据或推理：§1.3/§2.4 只确立「VM 起来之后发现函数拒绝工作」与「VM 起来之后固件内存被收走」，没有确立任何内核消费者在 VM 之后运行；§2.1 反而强调发现与消费「在 `arch_init` 里一前一后」（同函数体内相邻）。SMP 的 `smp_init`「更晚」是相对 `arch_init` 而言，不等于晚于 VM 启动。
- 最小修复：把 C 侧半句改写为约束放大式表述，例如「C 侧没有集中冻结点时，『发现只能在 VM 之前』这条约束就从一处（`acpi_init`）扩散到每个消费者所在的位置；§2.1 的相邻结构把它压住——只有当某个消费者被挪到 VM 之后，`acpi_phys2vir` 的 panic 才会兜底」。
- 置信度：中（0.65）——文档内部证据支持我，但「`vm_running` 置位点晚于 `smp_init`」这一前提在本文档内未建立，可能被外部事实推翻。
- 是否需源码核实：是（`vm_running` 在 C 树里的置位点相对 `smp_init`/内核初始化的时序）。
- 若我错了：若 `vm_running` 在内核初始化期间（如 `kmain` 内）就已置位，或存在某个 VM 之后才跑的内核消费者，则 §1.4 的机制成立，本条撤回。
- 命中清单：证据不足；复述与正文的张力（§1.4 的「会坏」强于 §2.1/§2.8 能支撑的程度）。

## FINDING RD04-READER-C-03（P2）

- 位置：§1.3 切分原则表（L83）：「| 解析描述 | 可以在内核里慢慢做 | 解析只依赖那份物理地址指向的字节，只要字节还在 |」。对照 §4.5（L1905）：「`push_platform_windows` 按 `platform_sources` 里每个 source 的 `phys_addr + len` 建窗口，因此 RSDP/DTB **本体**被覆盖；但 ACPI 的表链是 RSDP 内部指针给出的——`rsdt_addr`/`xsdt_addr` 指向 RSDT/XSDT，后者再指向 MADT 等表，这些地址既不在 `platform_sources` 里、也不在任何注册窗口内」「属布局偶然，不是契约。DTB 链没有这个问题（DTB 是单块 blob，长度已在 `len` 里）」；R04-T13（L2597）。
- 严重度：P2。
- 问题：概述把「解析只依赖一份已交接物理地址所指向的字节」当作切分原则的普适依据；这正是 DTB 单块 blob 的形态。对 ACPI 链，解析实际依赖的是从 RSDP 出发的一串**未交接、未注册窗口**的地址，§4.5 明文推翻了该前提的普适性，并把侥幸成立归为 2 MiB 取整的布局偶然（R04-T13）。§1.3 与 §1.4 对此没有任何限定或交叉引用。
- 影响：读者在第 1 章建立「交接一份地址即足以支撑窗口外解析」的模型，直到 §4.5（2400 行之后）才发现 ACPI 链不满足此前提；「解析可以慢慢做」在 ACPI 上目前靠偶然成立，与教学目标 ③（两条硬边界）直接相关。
- 证据或推理：§4.5 自述「DTB 链没有这个问题」即承认该问题对 ACPI 存在；§3.1/§4.2 确立交接物只有「一个地址 + 长度」（x86-64 至多 1 槽、aarch64 至多 2 槽），链上后续表地址不在其中。
- 最小修复：在 §1.3 该表行或其后段落加一句限定：「对单块 blob（DTB）成立；ACPI 链的表体地址不随交接、也不在任何注册窗口内——见 §4.5 与 R04-T13（QEMU 上靠 2 MiB 取整的布局偶然）」。
- 置信度：高（0.9）。
- 是否需源码核实：否（§4.5 已在文档内给出完整证据）。
- 若我错了：若「那份物理地址」被解读为「交接单所指的全部字节（含链上地址）」，则 §1.3 无错——但该读法与交接物只含「kind + len + phys_addr」（§3.6）的事实不符，解读不成立。
- 命中清单：单形态结论写成普遍结论（DTB 形态 → 全部格式）；概述与实现脱节（R04-T13 未回指概述）。

- 命中清单：复述漂移（小结把加法结构说成选择结构）。

## SUGGESTION RD04-RC-S2

- 位置：§4.10（L2352）：「`apic_enabled` | …… | **保留语义**：x86-64 填 1（APIC 路径）；aarch64/riscv64 填 0（C 的 ARM 构建也从未置 1）」。对照 §4.9（L2285-2288）：`let apic_enabled = 1i32;`（`#[cfg(target_arch = \"x86_64\")]`，无条件按架构编译期取值）；§2.1（L347）：失败时「`machine.apic_enabled` 恒为 0」；§2.8（L868）：C 的写入者是 `apic_single_cpu_init()` / `smp_init()` 里的 `machine.apic_enabled = 1`（仅 APIC 路径成功时执行）。
- 严重度：S（建议）。
- 问题：「保留语义」不完全成立：C 的值是运行时条件量（APIC 存在、启用且初始化成功才置 1，失败或缺席保持 0）；Rust x86-64 是编译期无条件常量 1，且 §4.1 表明 Rust 中断投递恒走 APIC、§4.8 表明基址不符是 check-and-reject panic 而非回落 PIC——「APIC 路径失败→0」这一分支在 Rust 中不存在。值的语义从「APIC 是否成功启用」变为「架构是否为 x86-64」。
- 影响：对账表的「保留」分级会让人以为该字段的因果来源未变；追问「什么情况下是 0」时两侧答案不同（C：APIC 缺失/禁用/失败；Rust：仅非 x86-64 架构）。
- 证据或推理：§2.1 明示失败路径返回前不置 1；§4.9 的取值是 `#[cfg]` 常量。
- 最小修复：在 §4.10 该行补半句：「C 在 APIC 缺失/失败时保持 0 并回落 8259；Rust 无非 APIC 路径，故按架构恒填（语义为『arch==x86-64』而非『APIC 成功启用』）」。
- 置信度：中高（0.75）。
- 是否需源码核实：建议核实（`os/kernel/src/misc.rs` 与 `os/arch/src/x86_64` 是否存在任何非 APIC 回落路径；文档口径是无）。
- 若我错了：若 Rust x86-64 存在 APIC 失败仍继续并置 0 的路径，则「保留语义」成立，本条撤回。
- 命中清单：复述漂移（条件结论被写成无条件保留）。
