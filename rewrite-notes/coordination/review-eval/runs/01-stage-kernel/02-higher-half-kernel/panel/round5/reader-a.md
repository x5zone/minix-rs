## FINDING READER-A-01（P1）

**原文摘录**

- §1.1 四时刻表：「| 链接 | 链接脚本与链接器 | 每个符号的 VMA、每个可加载段的 VMA/LMA | 所有 `PT_LOAD` 的 `vaddr − paddr` 相同（J1） |」
- §1.2 不变量表：「| J1 | 平移一致：所有 `PT_LOAD` 的 `vaddr − paddr` 相等 | ... |」
- §2.1 末段：「真正成立的是逐段关系：每个带 `AT()` 的段，装载地址 = 自己的虚拟地址 − 0xF0000000；五处 `AT()` 减的是同一个常量，于是"虚拟地址 − 装载地址"对**每个带 `AT()` 的段**都相等；低侧 `.unpaged_*` 三段不带 `AT()`、平移量为 0——两组各自一致，**不是全表一致**。」

**位置**

§1.1 表格（第 14 行）；§1.2 J1 行（第 27 行）；§2.1 末段（第 99 行）。§2.6 的归纳表（第 514 行）其实已经写成正确的分组版本：「带 `AT()` 的普通段：符号值高一侧、装载地址低一侧，差是 `_kern_offset`；`unpaged_*` 三段的符号值与装载地址都在低侧」。

**影响**

我在 §1 把 J1 记成「任何内核镜像的所有 `PT_LOAD` 平移量相同」，到 §2.1 看 C 的 `kernel.lds` 时得到两个平移量（`.unpaged_*` 为 0，带 `AT()` 的段为 `0xF0000000`），立刻无法判断：是 §1 的 J1 写错了，还是 §2.1 描述的 C 布局其实违反了 J1？这正好落在读者目标的第一时刻「链接」上——J1 是我用来判断「符号值与段体是否错位」的核心判据，现在它和正文对 C 的分析互相冲突。若按 J1 字面去读 C 工件的 `readelf -lW`，我会得出「C 布局不满足不变量」的结论，而 §2.1 和 §2.6 都说 C 的布局是正确的。

**最小修复**

把 J1 改成带范围的两段式定义，并同步 §1.1 与 §1.2：

1. 带 `AT()` 的可加载段：`vaddr − paddr` 等于同一常量（C 的高侧段等于 `_kern_offset`；Rust 生产镜像的全部 `PT_LOAD` 都属于这一组）。
2. 不带 `AT()` 的可加载段：平移量为 0（C 的 `.unpaged_*` 三段）。
3. 在 §1.2 的「可观测判据」里注明：`check-layout.sh` 的 L4 只覆盖 Rust 工件；C 的 `kernel.lds` 要按上述两组分别检查。
4. §1.1 表格的「链接」判据改成同一句话，并把该节概述里「链接脚本把符号值写成高半 VMA、把段体字节的装载地址写成低半 LMA」补一句「C 的 `.unpaged_*` 是低侧 VMA = LMA 的例外」。

**置信度**

高。两处原文直接冲突，且 §2.6 已给出正确版本，说明这是定义处的遗漏而不是我的误读。

## FINDING READER-A-02（P2）

**原文摘录**

§3.7「再算一次对齐这笔账（x86_64）」：「真正会坏的有三种情形：①三者都去掉时，一个非 16 对齐的 `stack_top` 会一路传到 `kmain`；②**只去掉 `sub rsp, 8` 也会坏**——按上面的算式，`push 0` 之后 `and` 不再有作用，`call` 前 RSP 是 8 mod 16；...」

**位置**

§3.7（第 964 行）。相关前提在 §3.3（第 731–732 行）：「`boot_validate_and_prepare` 里有一条断言 `kern_stack_top must be 16-byte aligned`」；以及 §4.4 的 x86_64 asm 序列（第 1347–1358 行）：`mov rsp, {stktop}` / `and rsp, -16` / `xor rbp, rbp` / `push 0` / `sub rsp, 8` / `call {kmain}`。

**影响**

我按 §3.3/§4.4 的前提算：`stack_top` 已经 16 字节对齐，若把 `and rsp, -16`、`push 0`、`sub rsp, 8` 三者都去掉，`call` 仍会压入 8 字节返回地址，进入 `kmain` 时 RSP = `stack_top − 8`，即 8 mod 16，正好满足 System V 的 `(RSP + 8) % 16 == 0`。按 §3.7 的 ① 这却是「会坏」。我无法判断：这三条指令里到底哪几条是入口 ABI 必需、哪几条只是为了补终止槽；这直接影响我复述「进入」时刻的失败症状。

**最小修复**

把 ① 的前提写全，或改写成一个真正会坏的场景：

- 若原意是「连 §3.3 的 16 字节对齐断言也失效」，写成：「① 三者都去掉、且 `stack_top` 本身不是 16 字节对齐时（即 §3.3 的对齐断言也不成立），非对齐值会一路传到 `kmain`；在断言成立时，三者全去仍满足入口 ABI，丢掉的只是终止槽（而终止槽不在帧指针链上）。」
- 若断言只在 debug 构建生效，需要在这一句里注明 release 构建没有这层保证；否则读者会把它当成始终成立的前提。
- 若终止槽其实有消费者，应在此处点名消费者，而不是让 ① 依赖一个未被说明的「非 16 对齐」前提。

**置信度**

算术部分高；作者原意中。若对齐断言只在 debug 生效，① 的结论可能成立，但当前文本没有交代这一点。

## SUGGESTION

**若干小项：数字口径与首次出现的术语。**

- §3.5（第 864 行）标题「三档的判据与后果」，表里却有四行。第四行是「两者都不整除且回退档不受支持」的变体；建议写成「三种主档（第四行是第三档的变体）」，避免读者以为漏了一档。
- §2.2（第 132 行）「名单里的库对象（`klib.o`、`io_inb.o`、`assert.o` 等）」：`klib.o` 与 `io_inb.o` 都在前面「显式列出的 9 个对象」里，不在三个库清单里；把它们当「库对象」举例会让 9+3+13+2=27 的复算对不上。建议改成「名单里的对象（如 `klib.o`、`io_inb.o`、`assert.o`；其中一些来自库清单）」。
- §3.1（第 558 行）「三套分类不是同一件事」：前文刚讲完三种链接脚本形态，这里又出现「三套分类」，我不确定它指哪三套（脚本形态/装载路径/执行视图？）。建议直接点名三个维度。
- §4.4（第 1426 行）与 §4.5.1（第 1615 行）的 `medany`：第一次出现时只说是「`-mcmodel=medany` 下展开为 `auipc` 加 `addi`」，读者若没有 RISC-V 编译器背景，不知道 medany 是什么。建议加一句「medium-any 代码模型：PC 相对寻址，范围约 ±2 GiB」，后文就不必再解释。
