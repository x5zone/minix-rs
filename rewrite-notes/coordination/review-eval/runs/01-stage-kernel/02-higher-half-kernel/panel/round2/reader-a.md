## FINDING RD2-READER-A-01（P2）

- 位置：§3.5「Rust 侧的页尺寸在内核的纯策略层选」段与紧随阶梯代码之后的段落；§4.1「把 `.lbss` 从 `.bss` 的通配里去掉会怎样」段；另引 §3.5 内链接脚本注释。
- 原文摘录（四处）：
  1. §3.5：「（`boot_validate_and_prepare` 只负责采集能力事实与注册分配器）」
  2. §3.5：「`arch_boot` 把 `NoKernelPageSize` panic 成 `arch_boot: page-size policy: no kernel page size satisfies the layout`」
  3. §3.5 链接脚本注释：「boot_validate_and_prepare 按 huge-page 阶梯选映射粒度，kern_size 非 2MiB 对齐即 panic；」
  4. §4.1：「最坏情况是跨距不再是 2MiB 整数倍，L5 判定失败、`boot_validate_and_prepare` 走进 panic 分支。」
- 严重度：P2。局部卡住：这条因果链无法完成，但不阻断全文其余部分。
- 问题：同一件事——`kern_size` 不满足大页粒度时由谁报告——本篇给出了两种互斥的归属。§3.5 正文建立的模型是「`plan_kernel_mapping` 选粒度 → `arch_boot` 把 `NoKernelPageSize` panic 成消息 → `boot_validate_and_prepare` 只采集能力事实与注册分配器」；同一节引用的链接脚本注释与 §4.1 的反推却说 `boot_validate_and_prepare` 选粒度并走进 panic 分支。这不是措辞差异，而是调用链上两个不同的函数。
- 影响：读者读到「2MiB 收口 → 粒度选择 → panic」时必须在句子之间停下来判断哪一句是真的。§6.1 第 5 行的诊断只写「分页还没开启就 panic」，不点名函数；读者若按 §4.1 去 `boot_validate_and_prepare` 找 panic 分支，就会与 §3.5 的「只采集」冲突；若按 §3.5 去 `arch_boot` 找，又会与 §4.1 冲突。因果链「跨距不整除 → 谁报告 → 在任何页表写入之前」因此断在中间，读者只能靠猜继续。
- 证据（只引文档）：上面四处摘录同在本篇；§3.5 的括号明确否定了链接脚本注释与 §4.1 所归给 `boot_validate_and_prepare` 的职责，四处文本不能同时为真。
- 最小修复：在 §3.5 的括号后补一句对账。若正文模型正确，写「链接脚本注释里的 `boot_validate_and_prepare` 是早先写法的统称；阶梯实际在 `plan_kernel_mapping`，panic 在 `arch_boot`」，并把 §4.1 的「`boot_validate_and_prepare` 走进 panic 分支」改成同一个函数；若实现相反（`boot_validate_and_prepare` 内部调用策略并在失败时 panic），则改 §3.5 的括号。两种改法都只动一两句。
- 置信度：高（四处文本在同一篇内互相冲突，不需要源码就能看出）。
- 是否需源码核实：是。需要确认当前实现里 panic 的产生者；文本只能证明冲突，不能证明哪一侧对。
- 若我错了：若 `boot_validate_and_prepare` 确实调用 `plan_kernel_mapping` 并在失败时 panic，那么错的是 §3.5 的括号「只负责采集能力事实与注册分配器」，修复点应改为那句括号；链接脚本注释与 §4.1 反而是一致的。
- 命中清单（§4.0e 编号）：本轮只允许读本篇与读者画像，§4.0e 清单不可读，无法给出编号。按语义归类为「内部自相矛盾（调用链归属）」；请持有规则文件的面板补编号。

## SUGGESTION RD2-READER-A-S02（§4.4「交接路径」的 RDI 机制无法按 ABI 重建）

- 位置：§4.4「两条生产路径在 `kmain` 处合流」长段落。
- 原文摘录：「**交接路径**——早先版本把 shim 栈上的 `&KernelInfo` 经 `noreturn` asm 的 `in("rdi")` 直传给 `kmain`，RDI 是 caller-saved、被调用方覆写后 `kmain` 拿到的是 .rdata 字符串地址（早期版本的读数：`kmain` 收到的指针 `0x1ddda2ee` 与 `.rdata` 里一个字符串常量的地址相合）」
- 问题：按读者已有的 System V ABI 知识，callee 在入口读参数寄存器之前不会「覆写」它；caller-saved 约束的是调用返回之后调用方不能依赖该寄存器。读者无法从这个句子重建「指针怎么变成 .rdata 地址」的机制。紧接着的「第二次根因：形参曾被编译器溢出到内核栈、从被覆写的栈槽读回」又是另一条机制，两条「现场」混在同一句里，读者分不清哪条解释哪次故障。
- 影响：这一段的结论（真正被消费的是 `.bss` 副本）读者能接受，但历史证据无法验证；句子同时承载「载荷存活」「RDI 历史 bug」「.rdata 读数」「spill 第二次根因」四条线，读者要回读两三遍。
- 建议：拆成「结论一句 + 两条历史证据各一句」。RDI 那条改写成可重建的机制（例如「早先版本把指向 shim 栈的指针按值传入，shim 栈在高半切换后不再映射/被覆写，`kmain` 解引用时读到 `.rdata` 字符串；读数为证」——具体以源码为准），或删掉寄存器名与读数，只留「按值传 shim 栈指针在高半切换后不可靠」这个结论。
- 置信度：中（我不确定早先版本的 asm 是否在 `call` 之前自己动过 RDI，还是编译器序言把形参溢出后读回；两种机制在文本里被压成一句）。
- 是否需源码核实：是。
- 若我错了：若早先版本的 asm 在 `call` 前用 RDI 做临时寄存器，句子应直接写这一点；读者就能重建，而不必用 ABI 常识去猜。

## SUGGESTION RD2-READER-A-S03（§1.1 `pg_identity` 的对照读起来像反向结论；间隙方向不明）

- 位置：§1.1 第三段（内核为什么在高半）。
- 原文摘录：
  1. 「`pg_mapkernel` 写内核映射时不置 `I386_VM_USER`……而 `pg_identity` 的恒等映射置了它——内核所在的这一段对用户态不可访问。」
  2. 「用户栈与数据被往下挪，既空出这段"越界就能撞上"的间隙，也让内核段与用户段在地址上不连续。」
- 问题：第一句的「而 `pg_identity` 置了它」与结论「内核所在的这一段对用户态不可访问」方向相反。读者会读成：既然恒等映射置了 USER 位、而它覆盖的物理内存里就有内核字节，那么内核在低地址反而是用户可访问的；「这一段」到底指 `pg_mapkernel` 写的高半映射，还是 `pg_identity` 写的恒等映射，句子里没有说。第二句的「越界就能撞上」也没有说方向：用户栈向下增长，0xF0000000–0xF0400000 在用户栈顶之上，向下溢出撞不到；能撞上这段间隙的是从 0xF0400000 向下增长的内核栈。
- 影响：这是全篇唯一解释「为什么内核在高半」的理由段。第一句读反了，读者会怀疑前面的地址划分；第二句读错方向，读者会把源码注释里的「catch kernel stack overflow」理解成用户栈溢出，而后的「0xe.. 对 0xf..」讨论就接不上。
- 建议：把「这一段」写成「内核的高半映射（`pg_mapkernel` 写的那一段）」；把间隙写成「内核初始栈从 0xF04xxxxx 向下增长，越过 0xF0400000 就落进这段未映射间隙」。若 `pg_identity` 的 USER 位另有用意（例如只在引导期短暂存在），补半句说明它为什么不推翻结论。
- 置信度：中高（文本层面；`pg_identity` 的实际覆盖范围与 USER 位效果需源码确认）。
- 是否需源码核实：是（`pg_identity` 是否覆盖内核物理页、USER 位在用户态是否真的可达）。
- 若我错了：若「这一段」在原语境里已明确指高半映射，补「高半」两字即可；若 `pg_identity` 不覆盖内核页，第一句的对照本身没有问题，只需说明覆盖范围。

## SUGGESTION RD2-READER-A-S10（§2.3 承诺「保留 `push 0` 的理由见 §4.3」，§4.3 没有给出理由）

- 位置：§2.3 第 2 条解码末句；§4.3 x86_64 asm 解码段与三条推演其三。
- 原文摘录：
  1. §2.3：「压进栈的这个 0 槽不在帧指针链上（Rust 侧保留它的理由见 §4.3）。」
  2. §4.3：「`push 0` 仍是初始栈的终止槽（C 注释 `Terminate stack`），不在帧指针链上。」
  3. §4.3 三条推演其三：「（x86_64 序列里的 `push 0` 终止槽不在这条链上；去掉它改变的是入口栈的对齐，`sp_aligned` 断言会当场失败。）」
- 问题：读者按指针到 §4.3，得到的是「它仍是终止槽、不在链上」（重申）和「去掉它入口对齐会变」（后果），没有「为什么保留」的理由。而且对齐可以由 `sub rsp, 16` 单独完成，读者自然会问：既然这个槽不在帧指针链上，保留它的语义理由是什么，还是纯属 C 栈形的遗留？
- 影响：一个明确的承诺指针没有兑现；读者在「保留 / 删除这个槽」之间没有判据。§4.3 的「多出来的三条各有理由」只覆盖 `and rsp`、`xor rbp`、`sub rsp,8`，`push 0` 不在其中，读者更会去找那个理由。
- 建议：在 §4.3 的 `push 0` 句后补一句真实理由（例如「保留它是为了与 C 的初始栈形一致，给手工回溯一个终止值；16 字节调整由 `push 0` 与 `sub rsp, 8` 共同完成」），或把 §2.3 的承诺改成「后果见 §4.3」。
- 置信度：高（文本层面）。
- 是否需源码核实：否（理由属设计意图，可由作者补）。
- 若我错了：若 §4.3 的「去掉它改变的是入口栈的对齐」就是作者心中的理由，把这句直接写成「保留理由」即可；读者不会再找一个不存在的语义解释。

## SUGGESTION RD2-READER-A-S11（§2.3 解一条 `push $0` 插入了六句回溯器实现，主线被打断）

- 位置：§2.3 第 2 条解码。
- 原文摘录：「它是初始栈底的终止槽，与回溯链的终止点是两件事：本仓两侧的回溯器都沿**帧指针链**走（C 侧 `libsys/stacktrace.c` 的 `util_stacktrace` 从 `get_bp()` 出发 `while(bp)` 逐帧读 `[bp]` 与 `[bp+1]`；内核侧 `i386/exception.c` 的 `proc_stacktrace_execute` 与 Rust 侧 `stacktrace.rs` 的 `walk_frames_from` 同形），正常情况下链走到保存帧指针槽里的 0 才停。C 侧入口段 `mov $0, %ebp` 在换栈前清零；`pre_init` 是普通 C 函数，EBP 是 callee-saved，`pre_init` 返回时把它恢复成 0……两侧回溯器另有 `saved_fp <= fp`（C 写作 `hbp <= bp`）的防环终止……」
- 问题：解一条 `push $0` 用了六句回溯器实现细节（C 侧入口、`pre_init` 的 callee-saved、Rust 侧 `xor rbp` 的位置、`-C force-frame-pointers` 的边界、防环终止），主线「一次跳转里的两种寻址」在这里中断。读者要么跳过，要么被 C/Rust 帧指针差异带走。
- 影响：主线理解路径被打断；后面的「这个 0 槽不在帧指针链上」本来一句就够，读者却要先处理三段回溯器实现。对本篇的教学目标（§2.3 的两种寻址）来说，这些细节是旁支。
- 建议：保留「这个槽是 C 的 `Terminate stack`，不在帧指针链上」一句，把回溯器实现与 `-C force-frame-pointers` 的边界移到 §4.3 的清帧指针推演，或放进一个「边栏」段；在 §2.3 只留一句「理由与两侧差异见 §4.3」。
- 置信度：高（结构偏好，不影响事实）。
- 是否需源码核实：否。
- 若我错了：若这段是为 §4.3 的 `xor rbp` 做铺垫，至少在段首写「这里先记住结论，理由见 §4.3」，让读者知道可以跳过细节。

## SUGGESTION RD2-READER-A-S13（「视图」是全篇判据列，但没有定义）

- 位置：§2.3 首次出现；§3.1 登记表表头与取值；§4.4 表头。
- 原文摘录：
  1. §2.3：「于是这两条指令对"执行视图"的敏感度不同」
  2. §3.1 表头：「| 链接脚本形态 | 装载路径 | 进入/执行视图 | 跳转完成时 PC |」

- 问题：「视图」是 §3.1 登记表和 §4.4 表的判据列，但篇内没有定义。读者只能从三个取值反推它是「当前 PC 相对链接地址的位置关系」。§4.3 的「第三种执行形态」直到后文才把「符号值与执行地址之间没有平移差」说出来，而 §3.1 的表已经要求读者用这个区分去读每一行。

- 若我错了：若「视图」在 01 篇已有定义且读者画像保证读者记得，补一句回指即可；本篇仍需要它，因为 §3.1 的表把它当判据列。

- 置信度：高。
- 是否需源码核实：否。
- 若我错了：若项目文风允许 MB 表示 MiB，至少全文统一一种写法；读者不会在同一段里看到两种。
