## 1. 术语表（只列后文用到的）

- **UEFI**：现代 PC/ARM 服务器上的固件接口。固件提供“启动服务”（读文件、分配内存、取内存图），内核接手前要调用 `ExitBootServices` 退出这些服务。
- **boot-shim**：夹在固件和内核之间的一个小程序。它负责读内核文件、分配内存、建立最初的页表，然后跳到内核。
- **LMA（加载地址）**：ELF 可执行文件里每个段有两个地址——运行时虚拟地址（VMA）和应当被装载到的物理地址（LMA）。boot-shim 按 LMA 把内核段直接写进物理内存。
- **UEFI 内存图 / conventional memory**：固件维护的一张物理内存清单。`EfiConventionalMemory` 表示“空闲可用”；`EfiLoaderData` 表示“被引导程序占用”。`AllocatePages` 只会从空闲页里发。
- **bump 分配器**：只前进不回收的简易分配器。给一段物理区间和一个游标，每次分配把游标往前推。
- **BootFileTable**：U-Boot 路径下，shim 自己建的一张表，记录“内核文件和 12 个模块文件被放在物理内存的哪个地址、多长”。表项是固定宽度结构体。
- **v1 交接（BootHandoffV1）**：shim 和独立内核镜像之间的协议。shim 把内存图、模块列表、参数等打包进一块九页的“arena”，把 arena 物理地址交给内核；内核解码后继续启动。
- **G8**：本项目的收敛规则——连续两轮“零新增发现”才允许标记 CONVERGED。
- **P0–P3（本文的严重度口径）**：P0 阻断——事实错误或代码缺陷，不修不可交付；P1 严重——重大事实错误或会误导结论；P2 一般——应当修复但不阻塞收尾；P3 可读性/指针类——可登记为已知债。

## 2. 裁决项一：BootForm 注册表保留、删除，还是接到真实入口？

### 事实

代码里有一个 `BootForm` 枚举，登记了五种“内核启动形态”：

| 代号 | 形态 | 现状 |
|---|---|---|
| (a) | x86_64 UEFI 内联：内核直接链进 boot-shim 的 PE 镜像，在同一进程里执行 | 已退役。现在 x86_64 也走“独立内核镜像 + v1 交接” |
| (b) | aarch64 UEFI 跨镜像：shim 建 arena，跳独立内核镜像 | 在用 |
| (c) | riscv64 OpenSBI 自引导：内核镜像自己就是引导面 | 在用 |
| (d) | aarch64 QEMU 直核：QEMU `-kernel` 直接装载内核镜像 | 在用 |
| (e) | riscv64 早核停车邮箱 | 实际是“次级 CPU 的早期入口 stub”：没有注册的后续入口就永久 `wfi` 停车。它不是主启动形态 |

这个模块原本声称提供两样东西：

1. **一处记账**：五种形态都登记在枚举里，数量测试守住“家族不会悄悄长大”。
2. **等价断言电池**：对每种形态跑同一组“启动后置条件”（例如内核栈顶必须落在镜像跨度内、系统调用入口必须在镜像内），证明五种形态的后置条件等价。

实际代码是：

- 数量测试只比较“枚举长度 == 5”。在任何别处新增一条真实启动路径、不改这个枚举，测试不会红。
- 断言电池对五种形态各跑一次，但每次构造的都是**同一份合成数据**（`canonical_higher_half_info()`），循环变量只用来取一个标签字符串。它没有构造任何形态真实的 `KernelInfo`，也没有经过任何形态的入口。
- 形态 (a) 的 `source_path()` 指向 `os/boot-shim/src/main.rs`，但那个文件已经不实现这个形态；(e) 指向的是次级 CPU 的 stub，不是启动入口。

评审已经把注释改成诚实版本（“注册表不追踪真实入口”“电池只证明谓词与形态无关”），但结构问题没解决：这个模块的宣传价值（“已经有防线”）大于它实际提供的东西。

### 选项

**A. 删除注册表、电池和数量测试。** “有哪些启动入口”交给文档里的一张表 + 真实入口清单（内核镜像 crate 的 `main.rs` 按架构分道）。代码更少，不会给人假安全感。代价：失去“跨形态后置条件等价”这个概念；但当前它本来就没被真正执行。

**B. 保留注册表，但把它做成真的。** 每个形态提供一个真实的 `KernelInfo` 构造器或入口探针；断言电池跑真构造器；数量从真实入口清单派生。代价：退役形态 (a)/(e) 没有真实入口，只能标历史；在用形态 (b)–(d) 的构造器会与现有 builder 重复，容易再次变成“测试自己造数据、自己通过”。

**C. 保留为纯文档清单。** 把模块改名为“历史形态清单”，明确写“不追踪生产入口、不是防线”，数量测试只守枚举自身。代价：保留一个价值有限的模块；未来读者可能仍误以为它是 guard。

### 我的倾向

A 或 C。这个模块目前不承重；如果教学上想保留“五种形态”的清单，C 的成本最低且诚实；如果目标是减少代码和误导，A 更干净。B 的工作量最大，且很难避免“假等价”。

### 裁决（2026-11-08，用户）：采纳 A——删除

删除注册表、等价断言电池与数量测试；五种形态的历史对照留在教学文档（§3.1/§4.8 的表已承担该解释）。实施随 code-excellence 批次，与 F04/F05（BootShim trait、PagingWithId）同族同批；实施时 `grillme-code-review` 的对照副本不受影响（它是独立单技能目录）。

## 3. 裁决项二：内核镜像的物理区间，要不要向固件“预订”？

### 事实

UEFI 路径下，boot-shim 把内核 ELF 的每个段直接写到它的 LMA（例如 x86_64 上常见 `0x200000..0x400000`）。**固件不知道这些页已经被内核占用**：在 UEFI 内存图里它们仍然是 `EfiConventionalMemory`（空闲）。

后果：之后任何一次 `AllocatePages`（给 12 个模块找落地页、给页表、给 arena、给 UEFI 池分配）都可能返回与内核镜像重叠的页。一旦重叠，shim 的拷贝会静默覆盖内核正文。

当前已有的防线：

1. 内核装载后，把内核物理跨度记进两个原子变量。
2. 模块落地页分配器在 `AllocatePages` 返回后、**拷贝模块字节之前**检查是否与内核跨度重叠，重叠就 panic。
3. 两条 UEFI 入口在模块装载后，再按页取整复查模块、root 页、bump 区（这是检测，不是预防：root/bump 在装载内核之前分配，如果真重叠，内核拷贝可能已经覆盖了它们）。
4. arena 分配后立即复查。
5. ELF 段拷贝前检查“源缓冲区”与“所有目标跨度”不相交，避免拷贝 UB。

按时间窗分这五条：防线 2、5 在“拷贝之前”（预防）；防线 1 是记录、3、4 在“分配之后”（检测——挡不住已经发生的覆盖）。所以真正的残余窗口只有两处：内核跨度被记录之前的分配，与 **UEFI 池分配**（`AllocatePool`，通过全局分配器）——把模块文件读进 `Vec`、参数落地区、DTB 拷贝缓冲区。这些分配若落进内核跨度，读文件/写缓冲会直接改坏内核正文，而现有的模块落地页检查发生在之后，来不及。

**证据状态要诚实标注**：选项 C 的前提（“碰撞概率很低”）目前**没有任何地址数据支撑**——未统计过 OVMF/AAVMF 上 `AllocatePool` 的实际返回区间与本仓内核跨度（x86_64 常见 `0x200000..0x400000`，2MB）的重叠率。现有唯一地址读数是深拷探针页（`pa=0x5e9b000`），但它是指定上界 `MaxAddress(4GiB−4KiB)` 分配的单页，不代表池分配行为。若要量化“低概率”，需先在门链上打印池分配地址直方图。

**为什么现在这样设计（前因）**：现有交接协议把两本账分开——“固件说什么是空闲”由 UEFI 内存图在 EBS 时刻定稿（conventional 列表），“内核说自己占用了什么”由接收侧的 classify 从自由清单里扣除（`kern_phys_base..+kern_size` 进 deduction record，VM 侧再复核 `LiveBootstrap ∩ VM-free = ∅`）。内核镜像的占用因此**不在固件账上**。选项 A（`AllocateAddress` 预订）等于把内核占用提前写进固件账，改变的就是这条分账语义；选项 B/D 不动它。这也是 A 会牵动分类模型、文档与真机行为的原因。

### 选项

**A. 向固件预订内核区间。** 解析 ELF 得到 LMA 跨度后，用 UEFI 的 `AllocateAddress`（指定地址分配）把这段标成 `EfiLoaderData`。这样固件不会再把它发给任何人，模块、arena、池分配都自动安全，现有的一堆防御断言可以简化。代价与风险：固件可能拒绝精确地址分配（跨多个描述符、地址不空闲等）；这会把内核镜像从“conventional（可用表）”变成“LOADER_DATA（保留表）”，改变内存分类模型和文档；需要在拷贝之前完成，且与模块装载的次序要重排。

**B. 包一层全局分配器。** 在 boot-shim 的 `GlobalAlloc` 外面加守卫：任何落在内核跨度内的分配都拒绝。覆盖模块文件 `Vec`、参数、DTB 拷贝。内核 ELF 自己的 `Vec` 在跨度记录之前分配，不能靠它；但 ELF 段拷贝已有“源/目标不相交”断言。代价：多一层分配器包装；panic 发生在分配处，错误信息要清楚；不改变内存分类模型。

**C. 维持现状，只补文档和检测。** 认为内核跨度（几 MB、低地址）与 UEFI 池通常在高地址，实际碰撞概率很低；把残余风险写进文档，并对参数/DTB 缓冲做分配后检查。代价：模块文件 `Vec` 的破坏发生在检测之前，属于“已知但接受”的风险。

**D. 调整装载顺序。** 先读内核 ELF、记录跨度，再分配 root/bump、再读模块。能缩小窗口，但模块文件 `Vec` 仍要等全局分配器守卫（B）才能真正防住。

### 我的倾向

**修订后的倾向（采纳第三方意见 + 代码复核）**：主修改为 **A + D**——解析 ELF 后按页取整用 `AllocateAddress` 预订 LMA 页，再调整装载次序；B 降为“诊断与第二道检查”，C 不可接受。原倾向（B 为主）低估了 pool 元数据写入发生在守卫之前的时序。A 的代价（分类模型变化、真机成功率未测）成立，但“目标页不可分配时拒绝启动”是正确的失败行为，比“启动成功后被池分配静默覆盖”安全得多。

### 裁决（2026-11-08，用户）：确认 A + D 实施

方向定案：主修 A + D；B 降为诊断（`R8-FU-01` 重新定级，不再排期为“第二道防线”）；C 不可接受。状态为**已裁决、待实施**——“待实施”不等于“已解决”：闭案需通过四道验证（预订次序与失败关闭的代码复审、最终 UEFI 内存图实测核对、`classify`/VM 消费者相交假设审计、OVMF/AAVMF 真机探针读数）。

### 实施合同（2026-11-08 确认生效；R13 前完成）

**预订范围怎么算**：按每个 `PT_LOAD` 的完整内存占用 `R_i = [LMA_i, LMA_i + MemSize_i)`（必须含 `p_memsz > p_filesz` 的 BSS 部分）：checked arithmetic 算末端 → 按 4 KiB 向外取整 → 全部目标页做并集去重 → 合并连续页成若干连续区间 → 对每个区间执行 `AllocateAddress`，类型 `EfiLoaderData`。**不要**预订 `min(LMA)..max(LMA)` 整个大跨度（段间空洞不占）。

**次序**：读取必要 ELF 元数据（尽量用固定暂存区读 ELF header 与 program headers，避免 `Vec` 抢先占据 LMA 页）→ 算出全部目标页 → 预订 LMA → 分配 root/bump → 读取与分配模块及其它缓冲 → 拷贝内核段 → 后续交接。读取完整 ELF 的 `Vec` 若恰好占住待预订页，`AllocateAddress` 会失败——按失败处理，**不得为追求成功率静默退回未预订模式**。

**失败语义与账本**：任一目标页预订失败 → 拒绝启动；多段预订只要有一段失败 → 整个启动终止，不允许带部分预订继续。最终 UEFI 内存图必须真实反映这些页已变为 `EfiLoaderData` 并进入保留投影。`startup_objects` 仍登记内核对象；第二跳 `deducted` 的消费语义要核对，**不能暗中假设每条扣减记录都必须与原 Conventional 可用表相交**。

补一条现状：B 的“全局分配器守卫”曾以 `R8-FU-01` 登记为“完整守卫排给 code-excellence”。按第三方意见与上文时序分析，这个登记需要**重新定级、重新定义范围**：外层守卫不构成内存安全保证；若保留，只能叫“事后诊断或早停机制”，不能称为“第二道安全防线”，也不得与 A+D 并列成两个看似等价的实施任务。

**第三方质疑的核对（2026-11-08，已按代码复核）**：B 的“外层守卫”按原描述**不能作为主防线**——固件 pool 在 `AllocatePool` 返回之前就会在目标页里写自己的分配器元数据（EDK2 的 `POOL_HEAD`/`POOL_TAIL`），外层守卫拿到指针时损坏已经发生，只能算诊断。代码侧事实：`main.rs` 的全局分配器是 `uefi = "0.33"` 的 `uefi::allocator::Allocator`（所有 `Vec`/`Box` 都走固件 pool）；九步表第 1 步先分配 root/bump、第 2 步才读内核与模块，模块页分配有拷贝前拒绝，但**模块文件 `Vec`、DTB 拷贝、param 缓冲的 pool 分配没有任何拦截**。另：`AllocateType::Address` 与现有 `MaxAddress` 同属 uefi 0.33 的同一枚举，A 有实现路径；实施时“读 ELF 的 `Vec` 可能先占住 LMA 页”——现有 `first_source_destination_overlap` 会把这类重叠变成 halt（安全失败），A 落地应在解析 ELF 后、拷贝段前预订 LMA，预订失败即拒绝启动，不静默退回。两本账设计不必合并：固件账记录“这些页已被 loader 占用”（`LOADER_DATA`→保留投影），对象账记录“这些页属于哪个存活对象”（`startup_objects`/deduction record）。

## 4. 裁决项三：riscv64 直核面的 `a2` 取表通道，补证据还是删掉？

### 事实

riscv64 的“直核”形态（QEMU `-kernel` 直接装载内核镜像）需要拿到 `BootFileTable`，才能找到 12 个模块文件。代码支持两条候选通道：

1. **DTB `/chosen/opensbi,boot-file-table` 属性**：设备树里写一个物理地址。
2. **`a2` 参数**：镜像入口的第三个参数（RISC-V 调用约定里 `a0`/`a1` 之后）。

核查结果：

- 仓库内**没有任何代码或脚本给 `a2` 写值**。六个真机脚本全部用 `fdtput` 把表地址注入 DTB。
- QEMU 的 `-kernel` 直载约定只保证 `a0 = hartid`、`a1 = DTB 物理地址`；没有 `a2 = 表地址` 的约定。
- U-Boot shim 腿是**另一个入口**：`a0`/`a1` 是 `(extra_argc, extra_argv)`，DTB 地址在 `argv[0]`；它不经过这个 `a2`。
- 文档早先写“U-Boot 腿的 a2 约定”，后来改成“直核面的备用 a2 通道，仓内没有生产者；已跑通的是 DTB 通道”。

也就是说，`a2` 是一条**没有生产者、没有门链验证过**的备用路径。

### 选项

**A. 删掉 `a2` 通道。** 只留 DTB `/chosen`。代码和文档都简化；与所有已跑通的路径一致。风险：如果将来某个外部 loader 真的用 `a2` 传表，功能就没了（但当前不存在这样的 loader）。

**B. 保留为“备用通道”，明确标注无生产者、未验证。** 当前状态。诚实，但保留一条会腐烂的未测代码路径。

**C. 保留并补真机证据。** 例如：在 QEMU 直载运行中打印 `a2` 原值；或者写一个注入脚本/小 trampoline，故意把表地址放进 `a2`，再让门链实际走这条通道。需要额外工具工作（QEMU `-kernel` 不直接支持设置 `a2`，可能要 `-device loader` 或自定义装载器）。

### 我的倾向

如果没有明确的外部消费方，选 A（删）。如果这条通道是给未来某个 loader 预留的接口，选 C（补证据），不要长期停在 B。

### 裁决（2026-11-08，用户）：采纳 A——删除

删除 `a2` 备用通道：入口 asm 的第三参数通道注释、`bootface` 的 a2 合法性分支与 §3.7/§4.8 的“备用通道”表述同步清除；DTB `/chosen/opensbi,boot-file-table` 为唯一生产通道。将来确有外部 loader 需求时，以明确 ABI 合同重新引入。实施随批次。

- 删除它会不会破坏与某个外部引导器的兼容性？从公开的 RISC-V/QEMU 约定看，`a2` 有标准含义吗？

## 5. 裁决项四：CI 要不要加一条“内核镜像交叉构建”作业？

### 事实

评审发现过一个真实编译错误：riscv64 的 `kernel-image` 里，两处对返回 `u64` 的函数取了 `.0`（当成新类型），导致两个 riscv64 变体都编译失败。这个错误存在了很多轮，因为：

- 本机默认 `cargo check -p kernel-image` 只编译宿主 x86_64，riscv64 专属文件被 `cfg` 掉；
- CI 的 QEMU 作业只构建内核和测试载体，不构建 `kernel-image`；
- 最后是评审面板跑了 `cargo build --target riscv64gc-unknown-none-elf --features fw-riscv64-{none,uboot}` 才发现。

错误已修，两个变体现在都能构建。但同类回归仍然没有门拦。

### 选项

**A. CI 加作业**：构建 `kernel-image` 的 riscv64 两个 feature 变体（可选加 aarch64）。成本：一条 CI 作业 + 交叉工具链（CI 已经在构建 riscv64 QEMU 镜像，工具链大概率已有）。
**B. 只加本地脚本/文档**：便宜，但不会强制执行。
**C. 在宿主构建里强制解析 riscv 文件**（例如给 CI 一个 `cargo check --target` 的脚本步骤）。本质仍是 A 的一种实现。

### 我的倾向

A。这是纯基础设施决定，技术上没有争议；唯一成本是 CI 时间。

### 裁决（2026-11-08，用户）：采纳 A——加 CI 作业

CI 增加 `kernel-image` 的 riscv64 双 feature（`fw-riscv64-none` / `fw-riscv64-uboot`）构建作业，并纳入 aarch64 生产 target；发布脚本/本地文档不替代强制 CI 检查。实施随批次（`R10-FU-01` 落地）。

## 附录 A：§4.9 与 §4.3 “同一不变量口径未合并”的原文与代码事实

> 第三方（GPT）指出：若两处只是表达不同，P3 定级合理；若公式、适用范围或失败语义实际不同，则是内容合同冲突，应重新定级。为便于独立判断，附上原文与代码事实。

**文档 §4.3 的原文**：

> 装载前还有一道跨段防线：所有段的文件字节区间与所有目标 LMA 区间两两不相交（`first_source_destination_overlap`），跨段重叠同样 halt。

**文档 §4.9 的原文（函数对照表行）**：

> `overlaps(mod, n, cmp_mod)` → `fn first_overlapping_pair`｜改型｜检查对象从“模块 + 内核”变成“内核镜像自身的 PT_LOAD 段”。

**代码事实**（`os/boot-shim/src/loader.rs`）：装载路径有**两个**断言函数——`first_source_destination_overlap` 检查“每个段的文件字节区间 × 每个段的目标 LMA 区间”的任意交叉（src-vs-dst），`first_overlapping_pair` 检查“目标 LMA 区间两两不相交”（dst-vs-dst）；**两者都不检查文件字节区间之间（src-vs-src）的重叠**。

**据此的判断**：§4.3 的“两两不相交”按字面覆盖了 src∪dst 的并集，范围**宽于**代码（src-vs-src 未查）；但 src-vs-src 重叠对只读拷贝无害，代码是对的，宽的是文档措辞。据此该行属**措辞类 P3**（修复方式是把 §4.3 的句子收窄为“每段的文件字节区间与该段及所有段的目标 LMA 区间不相交，且目标 LMA 区间两两不相交”），不是内容合同冲突。
