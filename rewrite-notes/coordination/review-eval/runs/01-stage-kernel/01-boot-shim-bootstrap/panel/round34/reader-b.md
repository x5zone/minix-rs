## 结构重建（我读出的论证骨架）

1. **§1.1–§1.2 立问题**：引导器交棒时机器状态没有可依赖的外部约定，于是自举必须自己凑齐四样东西（内存清单、内核位置、页表、交接结构），并满足五条次序约束 D1–D5。D1–D5 是"约束名"，不是执行序，也不是第 3 章的设计提纲（§1.3 明说）。
2. **§1.3–§1.4 定读法与边界**：本篇到 `pre_init` 返回／控制权交给 `kmain` 为止；越界内容（换栈、高半、Direct Map、ELF 段拷贝、DTB/ACPI 解析等）逐条登记下游归属。
3. **§2 以 C 代码顺序验证第 1 章的四样东西**：引导协议（2.1）→ 第一跳（2.2）→ 参数收集与参数表（2.3）→ 内存账的建与裁（2.4–2.5）→ 页表与建表之后的下游（2.6）→ 跨架构同名函数对照（2.7）→ 调用树与 D1–D5 证据锚点（2.8）。
4. **§3 逐项说明 Rust 为什么换掉或保留 C 的做法**：引导协议（3.1）→ 入口与取件（3.2）→ crate 边界（3.3）→ 交接结构（3.4）→ 可回收段退役（3.5）→ 大页能力（3.6）→ 三种交接形态（3.7）→ 页表页分配器（3.8）→ 借槽机制退役（3.9）→ 选读对照（3.10）。
5. **§4 按调用链落实**：入口（4.1）→ UEFI 顺序与描述符分类（4.2）→ 共用装载（4.3）→ 两条构造入口与校验门链（4.4）→ 内核侧七个落地区（4.5）→ 建根与开分页（4.6）→ 分配器换手（4.7）→ 跨镜像/直核分道（4.8）→ C 函数对照（4.9）。
6. **§5 从机制反推证据**：M1–M17 各需证明什么 → 三层证据覆盖现状 → TODO 交接 → 写不出可观测断言的机制。
7. **§6 诊断**：路标读法（6.1）→ panic 路径（6.2）→ 失败模式表（6.3）→ 可复制命令（6.4）。
8. **§7 参见**。

结构判断：主链完整，第 2 章与第 3/4 章通过 §1.2 的 D1–D5 与 §3.10 的对照表扣合；计数与状态都指定了唯一权威（§3.7 生产腿、§5.2.3 门链、§4.5 交接容量、§5.1 TODO 状态）。职责重叠集中在 §3.4 对 §4.4/§4.5、§3.7 对 §4.8、§3.8 对 §4.7，但三处都以"→"与"不重复"声明做了分工，未形成双权威。章节边界混淆集中在 §2.4.1.4、§3.4.1、§4.6 尾部、§6.1 标题。下面只报清单内的阻断项（FINDING）与非阻断项（SUGGESTION）。

- 最小修复：把审计句改成点名对象与字面量的形式，例如"Rust 侧 `os/kernel` 与 `minix-boot` 对 `BOARD`/`board`（大小写两种拼写）检索均零命中；C 内核的 `get_value` 读 `board=` 属 C 侧消费者，不在本审计范围"，并附检索命令。
- 置信度：中（"kernel"可能本意就是 Rust 侧 `os/kernel`；审计可能实际做了大小写不敏感检索，只是没写出来）
- 是否需源码核实：是（确认 `os/kernel`/`minix-boot` 是否存在读 `BOARD` 或 `board` 的代码，以及当时检索的字面量）
