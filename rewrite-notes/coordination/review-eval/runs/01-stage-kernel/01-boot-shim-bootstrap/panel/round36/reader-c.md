## FINDING READER-C-04（P3）

- 位置：§4.3 装载循环的 `num_pages` 解释：“写小了（加数 A ≤ 4094）时，只有余数 r 满足 `r > 4096 - A` 才会少一页——反例：`data.len()=4095`（r=4095）、`A=4094` 时 `(4095+4094)/4096 = 1`，仍是一页。所以 A=4095 是让「任何非零余数都进位」成立的最小加数，写成「只要余数非零就会少一页」是不成立的强结论。”
- 严重度：P3
- 问题：这段话给出的“少一页”条件写反了。设 `x = q*4096 + r`（`0 ≤ r < 4096`），公式 `(x+A)/4096` 在 `r > 0` 且 `r + A < 4096` 时才会比 `ceil(x/4096)` 少一页，即条件是 `r < 4096 - A`，不是 `r > 4096 - A`。文中自己举的反例（A=4094、r=4095）满足 `r > 2`，却没有少一页——它恰好推翻了文中刚给出的条件，而不是推翻“只要余数非零就会少一页”这句弱结论。
- 影响：我按文中条件去验证其他加数时会得到相反结论；要判断 A=4095 为什么是最小加数，必须自己重新推一遍。这正好落在“每个因为/所以有前提”的验收点上：结论对，前提错。
- 证据或推理：文中例子本身即证据：`(4095 + 4094) / 4096 = 8189 / 4096 = 1`，而 `ceil(4095/4096) = 1`，没有少一页；但 r=4095 大于 4096−4094=2。若把条件改成 `r + A < 4096`，则 A=4094、r=4095 不满足（不欠），A=4094、r=1 满足（`(4097+4094)/4096=1`，而 ceil=2，欠一页），与例子和结论都一致。
- 最小修复：把“只有余数 r 满足 `r > 4096 - A` 才会少一页”改为“只有余数 r 满足 `r > 0 && r + A < 4096`（即 `r < 4096 - A`）才会少一页”；例子保留。
- 置信度：高
- 是否需源码核实：否
- 若我错了：也许文中的 `r` 指“距下一页的剩余量”而不是除法余数，但例子把 `data.len()=4095` 的 r 写成 4095，说明就是普通余数；没有第二种读法能让 `r > 4096 - A` 与例子同时成立。
- 读者验收清单条目：第 2 条（因果主张的证据/推导自洽）；同时命中第 3 条（“所以”的前提写错）。

## FINDING READER-C-06（P3）

- 位置：§3.4.2 “不做深拷、把 `KernelInfo` 的切片按原指针存进内核的全局槽会怎样”段：“不重建根——重建会清零活动根、下一条取指页错误，见 §3.7 反向推演”

- 严重度：P3
- 问题：同一机制在概述与详述里给出两种故障时点：§3.4.2 说重建活动根后“下一条取指页错误”，§3.7 说 TLB 残留可能让 CPU 先跑几条，故障落在下一个冷取指。前者是即时失败，后者是一段静默窗口；这正是 §3.7 用来说明“故障点与根因隔得更远”的关键因果。
- 影响：我会把“重建根会立刻在下一条取指出错”当作结论记住，从而低估 §3.7 描述的静默窗口；排查时也会以为串口一定在紧接着的位置停住，而不是可能在几条指令之后才以不相关的位置出现。

- 最小修复：把 §3.4.2 的“下一条取指页错误”改为“下一个冷取指页错误（TLB 残留可能让它先跑几条，见 §3.7）”。
