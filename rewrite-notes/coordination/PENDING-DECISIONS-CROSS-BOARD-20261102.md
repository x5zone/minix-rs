## 零、评审方法与证据约定

### 0.1 三条基本判断原则

本项目的总体目标是「用 Rust 重写 Minix3 内核与用户态，不改变外部可观察行为」。由此派生三条与本次裁决直接相关的判断原则：

1. **C 真源优先**：Minix3 的 C 源码行为是事实基线，高于任何设计文档与 Rust 现状。凡 C 与 Rust 在报文、退出码、输出字节上分叉，默认视为 Rust 需要修正，除非有明确理由裁决为「登记的已知差异」。
2. **缺陷形例外**：当 C 的可观察行为来源于**未定义行为或明显缺陷**（越界读、除零崩溃、无限循环、截断数据），照抄它会把缺陷固化进新实现。这类情形必须逐条裁决：是「缺陷兼容」（照抄，保证任何脚本的可移植性），还是「理性修正」（背离 C，登记为已知差异）。本材料第 2.8 节整族属于这一原则的适用对象。
3. **平台真值**：有些差异的「真值」取决于 Minix 自己的系统调用与文件系统语义，而不是 Linux 宿主的 glibc 行为。用 Linux 宿主上编译的参照程序测出来的现象，只能当候选证据，不能直接当结论。第 2.6 节是这一原则的适用对象。

### 0.2 证据等级

材料中的事实按证据类型分四级，每条事实都注明它属于哪一级：

| 证据类型 | 含义 |
|---|---|
| 源码锚点 | 可定位到具体 C/Rust 代码（`文件路径:行号` 形式） |
| 可重跑读数 | 给出命令、夹具、环境和预期输出，任何人可复现 |
| 内部批次读数 | 有项目内部批次记录，但参照件为宿主自建，外部评审者无法独立复现 |
| 待取证 | 需要 Minix/QEMU 真机结果，目前不能下结论 |

补充约定：宿主读数只证明宿主构建的具体表现，不单独证明 Minix 目标环境的信号、退出状态或系统调用语义；凡依赖平台语义的条目，目标实测列为待取证。

### 0.3 编号与命名约定

材料中的「登记号」（例如 `CUT-EMPTY-BYTE-LIST-RUNAWAY`）是项目台账用的稳定标签，便于跨会话追踪；每个登记号在本材料中都配有完整的中文解释，读者不需要记住它们。工作板 A、B、C 分别对应命令面、库与驱动、内核与引导三条工作线。

### 0.4 本轮的盘点口径

- **覆盖面**：三块工作板（A/B/C）的全部条目状态列、三块板的「需人裁决」专节、结构债台账的开放行、两份历史待决清单（三架构齐平专项与阻塞解除批）的决议状态、作用域登记板的待决队列。

## 一b、第一轮评审裁决总览

> 外部评审（网页端，无代码访问）对 §一 总表十三项的逐条裁决（评审日期见头部创建行）。裁决文本的要点、补证要求与执行状态记录在本章；各议题详解（§二）开头另有该条的裁决块，正文保留裁决前的分析原文作为取证材料。

### 1b.1 统一裁决原则（采纳）

评审建议固定下来的判断方法，本项目采纳为后续同类争议的默认口径：

| 情形 | 应采用的策略 | 本材料中的例子 |
|---|---|---|
| C 有明确定义的正常行为 | 优先兼容 | fortune `.dat`、正常 fold 参数 |
| C 的缺陷导致崩溃或挂死 | 修正并登记 | fortune 空库、cut 空列表、fold 参数缺陷 |
| C 的实现机制偶然产生错误副作用 | 不复制机制 | colrm 缓冲吞错误 |
| C 的未定义行为恰好产生稳定边界 | 不凭单次读数决定，先确认目标平台 | nl 短定界符 |
| C 的行为依赖底层操作系统语义 | 必须在 Minix 环境验证 | comm/cmp 目录操作数 |
| C 与 Rust 的实现机制不同，但外部语义可等价 | 保持语义，允许机制不同 | fbd 拷贝转发 |
| 没有实际使用者且成本较大 | 明确登记，暂不建设 | wtf 外部程序调用、九台网卡占位 |

## 二、议题详解

### 2.1 fortune 的磁盘格式：`.dat` 与定界串

**第一轮裁决**：**通过（方案甲）**。实施要求：① 实现 `.dat` 读取器，按 C 的索引读取文本；② 正确处理定界串与 rot13；③ 对索引版本、字节序、长度、偏移范围做严格校验；④ 没有 `.dat` 时保持 C 的错误行为，不偷偷切换成文本模式；⑤ 损坏索引给明确错误，不越界读取。`strfile` 不必同批移植——先保证能读取 C 的 `strfile` 生成的标准文件，并把 C 生成的 `.dat` 作为测试夹具；将来若要求在 Minix-rs 内部创建新数据库，再单独决定是否移植 `strfile`。

**背景**。`fortune` 是打印随机格言的命令。C 原版的实现方式分两层：一个纯文本数据文件（格言之间用一行 `%` 分隔），加一个**二进制索引文件**（后缀 `.dat`）。索引文件由配套工具 `strfile` 生成，里面记录格言条数、每条的偏移量、以及一串标志与定界串。`fortune` 启动时先打开 `.dat` 索引，按索引里的偏移直接跳读文本文件，从而不必扫描整个文本。

C 真源的相应位置：

- 索引文件的打开与缺失处理：`minix3/games/fortune/fortune/fortune.c:1064-1068`（`open_dat`）。
- 判定「一条格言结束」用的是索引里携带的定界串：`fortune.c:268-269`（读到定界串为止的循环）。
- 索引里的条数与时长的使用：`fortune.c:1253`（`Fort_len = maxlen_in_list(...)`）；随机抽取的取模点见第 2.2 节。

Rust 现状与 C 是两种不同的设计：`os/commands/games/text-games/src/fortune.rs` 用一个「格言数据库」抽象（`QuipDb`，提供按序号取格言、总数、是否为空三个操作），`os/commands/games/text-games/src/bin/fortune.rs` 从命令行给出的路径读入**纯文本**、按行切分成格言列表、再均匀抽取。它既不需要 `.dat` 索引，也不认识 C 的定界串。模块注释里明确写着「数据文件在 `datfiles/` 目录」是作为真源参照，而不是运行时读取索引。

**问题**。要不要把 Rust 的 fortune 改成与 C 相同的两文件（文本 + `.dat`）模型？

**候选方案**：

- **甲：实现 `.dat` 格式**。解析二进制头（标志、条数、字符串表、定界串、偏移表），按索引跳读；同时保留对无索引文件的处理（C 在缺 `.dat` 时给出「Cannot open」类错误，具体见锚点 `fortune.c:1064-1068`）。优点：任何用 `strfile` 生成过的数据文件都能直接使用，这是 fortune 最外层的可观察行为。成本：一个二进制格式解析器加配套测试；索引格式有字节序与版本细节要逐项对表。
- **乙：保留重设计（纯文本按行切分）**。优点：实现简单、无二进制格式面；缺点：与 C 的数据文件生态不兼容——用户拿 C 的 `.dat` 文件给新实现，会得到无法预期的输出（把二进制当文本）。这是**已登记但未裁的差异**。
- **丙：双模**。有 `.dat` 就按索引读，没有就按文本行切分。折中，但「同一文件在两种模式下产出不同结果」会让行为面更难界定，且 C 并无此形态。

**C 真源行为分析**。C 的 fortune 对数据文件是强依赖 `.dat` 的（先打开索引再按偏移读文本）。索引里还带旋转（rot13）标志与定界串，这两项都会改变输出内容。也就是说，「文本按行切分」与「C 的读取模型」不只是格式差异，还有「旋转是否应用」「定界规则是否一致」两个语义差异。

**后果推演**。选乙或丙，意味着 fortune 的数据兼容性永远与 C 分叉；选甲，工作量大但一次到位。需要注意的是：本项目当前镜像里 fortune 是否被播种、是否真有 `.dat` 数据文件，本身就是「是否有真实使用者」的问题；如果镜像只带内置格言，甲的价值目前主要体现在「格式承诺」而非「即时可用」。

**项目侧推荐**：**甲（实现 `.dat`）**。理由：数据文件格式是外部行为里最硬的一种；且 C 的定界串与旋转语义只有走索引才能完整复刻。若评审认为当前无真实数据文件使用者、不值得先付出成本，可退为「丙（双模）+ 把 `.dat` 解析列为首个真实使用者出现时的前置」——请评审在这两种取舍中给一个方向。

**执行说明（第一轮裁决后）**：方案甲已选定；`strfile` 不必与读取器同批移植——先保证能读取 C 的 `strfile` 生成的标准文件，创建侧待未来有真实需求再单独裁决。

### 2.2 fortune 空库的错误腿

**第一轮裁决**：**通过（方案乙）**。错误分两类，不得混同：有效索引但格言数量为零 → `no fortunes in database`；索引损坏或结构不合法 → `invalid fortune database`。不复刻除零崩溃，也不通过主动发送信号 8 模拟 C 的崩溃。

**背景**。这是第 2.1 节的直接下游：如果索引里记录「零条格言」，C 的 `fortune` 会怎样？

**当前事实（[内部批次读数] + [源码锚点]）**。用宿主自建的 `strfile` 处理一个只含一枚 `%` 的文件，`strfile` 报告 `There were 0 strings`；随后运行宿主自建的 `fortune`，shell 报出 `Floating point exception (core dumped)`，**退出码 136（即 128+8，对应信号「浮点异常」）**，标准输出与标准错误都是空的。该读数证明了当前宿主构建的具体表现，**不单独证明 Minix 目标环境的信号与退出状态**。机制在 C 源码里可以定位：随机抽取时对「条数」取模——`minix3/games/fortune/fortune/fortune.c:956` 的 `random() % Noprob_tbl.str_numstr` 与 `:1007` 的 `random() % parent->tbl.str_numstr`。条数为零时，这两处取模即除以零。另有一个 C 语言层面的细节：整数取模的除数为零属于未定义行为，信号 8 是具体编译器、指令与运行环境下的表现，不是 C 语言标准保证的结果。这不影响已批准的裁决——空库仍选择给诊断而非复刻崩溃——但事实表述必须准确。

Rust 现状（[源码锚点]）：按行切分的重设计下，「空数据库」是一个普通的空列表；实现里有一个「空数据库」的构造（`os/commands/games/text-games/src/fortune.rs:44` 附近，注释写明「every pick misses」），不会崩溃，但输出与退出码也未按 C 的「空输出 + 崩」对齐。

**问题**。空数据库时，新实现应当：(甲) 照抄 C 的崩溃（无报文、退出码 136）；(乙) 给一条可读诊断并非零退出（例如 `fortune: no fortunes in database`）；(丙) 什么都不做、退出 0？

**C 真源行为分析**。C 的崩溃是缺陷（对零取模），不是设计意图；没有任何脚本会依赖「空库时进程被信号杀死」这一具体形态。但它确实是可观察行为：退出码 136 与「无任何报文」是可测的。

**后果推演**。照抄崩溃意味着新实现也要在空库时自杀式退出，这会与项目「不引入可避免的崩溃」的一般工程直觉冲突；给诊断则与 C 分叉一个角落。第三种（退出 0）既不符 C 也不合理。

**项目侧推荐**：**乙（可读诊断 + 非零退出），并登记为已知差异**。理由：信号崩溃属于第 0.1 节定义的「缺陷形」；复刻崩溃没有可移植性收益，反而把一个会触发 core dump 的路径引入新系统。不复刻崩溃、不通过主动发送信号 8 模拟——该分支已经第一轮裁决关闭，不再作为可选方案保留。

### 2.3 colrm 的输出缓冲与错误归属

**第一轮裁决**：**通过（方案乙）**。不采纳候选丙作为默认方案——若 Rust 已及时发现写失败，丙的「读坏时归因 stdin」必须继续读取输入、推迟输出错误才能模仿 C 的延迟归因，等于重新引入缓冲与错误优先级模拟，没有实际收益。固定规则：读取失败报 `stdin`；输出失败报 `stdout`；不以输出量决定错误是否可见；不延迟报告。**同时发生读写错误时的规则：对独立错误按上述归因；若两种故障同时存在，按 Rust 实际首先观察到的错误终止，不得为了模仿 C 的错误归因而继续读取或推迟报告——该策略不保证同时故障时与 C 的错误优先级一致，这一边界单独登记。**现有实现若能区分两种独立错误，只需固化测试，不必重构。

**背景**。`colrm` 从标准输入删除指定列后写到标准输出。C 原版用 stdio 的 `putchar` 逐字符输出，并在读失败/写失败时分别报 `stdin`/`stdout`。stdout 在 C 里是有缓冲的：小量输出攒在用户态缓冲里，直到缓冲满或进程退出才真正写到底层文件描述符。这个「什么时候真正写」的机制，决定了「写失败被归因到哪里、甚至是否被报出来」。

**当前事实（[可重跑读数]——探针在册；Minix libc 侧 [待目标实测]）**。项目里有一个专门复现该行为的探针脚本 `tools/atf-c-compat/probes/colrm_leg_order.py`，矩阵是「读腿干净/读腿先给字节后失手」×「输出小/输出大」，写洞一律用 `/dev/full`（一个写入必失败的特殊设备）。读数结论：

- 读坏且输出还没攒满缓冲：那次写根本没落到文件描述符上，只有读错可见 → C 报 `stdin` 并退出 1；Rust 现状报 `stdout` 并退出 1。
- 输出攒满过：刷缓冲撞「设备已满」，`putchar` 返回失败 → C 报 `stdout`；Rust 同形（报 `stdout`）。
- **读干净而写坏（小输出）**：C 的 `check(stdin)` 看到「已到文件末尾」就 `exit(0)`，退出时 stdio 静默刷缓冲，写错误根本不报、退出码 0；Rust 现状报 `stdout` 并退出 1。

C 真源锚点：`minix3/usr.bin/colrm/colrm.c:99`（`case EOF: check(stdin)`）、`:117-119`（`putchar(ch) == EOF` 时 `check(stdout)`）。

**问题**。命令层要不要复刻 libc 的 stdio 缓冲策略？也就是说：

- (甲) 复刻：Rust 侧也实现「用户态缓冲 + 退出时刷 + 写错误按缓冲状态归因」。这样第三条矩阵形态（读干净写坏 → 退出 0、无报文）与 C 一致。
- (乙) 保留现状：写失败一律报 `stdout` 并退出 1。行为更「正确」，但与 C 分叉一个角落。
- (丙) 只复刻归因、不复刻静默：读坏时归因 `stdin`（与 C 一致），写坏一律报错。

**C 真源行为分析**。C 的这个行为不是 colrm 自己的逻辑，而是「用 stdio 逐字符输出」这个选择的副产品。宿主探针证明了 C stdio 缓冲可能产生这些错误归因和静默行为；Minix 的 libc 是否在相同探针下产生完全相同的读数，当前材料未提供目标实测。由于本次裁决选择不模拟该缓冲机制，这一平台差异不构成实施阻塞。

**后果推演**。复刻缓冲策略会把「写错误的可见性」与「输出量」绑定在一起：小输出时写错误被吞掉。这可以说是缺陷（吞错误）也可以说是「完全兼容」。从使用者角度，`colrm ... > /dev/full` 这种场景极少；从可移植性角度，脚本若依赖退出码判断成败，C 在小输出时会给出误导性的 0。

**项目侧推荐**：**乙（保留现状，登记已知差异）**。理由：① 分叉只在「输出未满缓冲且写失败」这个病态角落出现；② 复刻 libc 缓冲策略需要在新实现里模拟「缓冲何时满」，等于把 C 的内存布局细节变成契约；③ 项目内有一条同类裁决先例：文档里明确写过「不把缺陷写成契约」。如果评审倾向绝对兼容，则建议采丙（归因对齐、静默不复刻），把「吞写错误」这一条单独登记。

### 2.4 VM 服务器跨重启状态

**第一轮裁决**：**暂不批准方案选择，列为补证项（最高优先级）**。先厘清三个不同概念并分别给出状态承载方式：① `VmServer` 对象重新构造但 VM 进程仍存活；② VM 服务进程被服务管理器重新执行但底层内核状态保留；③ VM 进程崩溃、内存映像丢失后由新进程替换。条件性判断：若只是同一进程内重建对象，静态存储可以成立；若是真正的进程重新执行，静态变量不可能保存上一进程的状态；若状态依赖内核仍持有的页表、物理映射等资源，必须识别谁才是真正的状态所有者。补证清单见 §1b.4。方案丙（响亮拒绝）可保留为临时过渡，不作最终设计。

**背景**。项目的系统结构里有一个「虚存服务器」（VM），负责管理各进程的地址空间。C 原版的 VM 服务器有一个特殊行为：它靠一组**进程全局变量**（BSS 段里的静态变量）记录「本次启动是不是第一次」。**「当 VM 被服务管理器重启时，这些静态变量仍然保留上一次的值」是项目原有的设计假设——第一轮评审未予采信，待补证**（`is_first_time()` 查询 `RTS_BOOTINHIBIT` 这一个事实，不能单独证明 BSS 在服务重新执行后仍然存在；三种重启情形的区分见本节开头裁决块）。

### 2.5 wtf 的三级退化查找与跨程序调用口径

**第一轮裁决**：**通过（方案乙），附触发条件**。当前不为 wtf 实现跨程序调用。未来当命令面建立正式的进程创建、等待与输出捕获能力，或 `whatis`/`pkg_info`/`make` 进入镜像时，重新检查三级退化查找；不得永久写成「wtf 不支持外部调用」。验收条件：确认三个命令确实不在最终镜像及可执行路径中，并对照 C 脚本在同样环境下的最终输出与退出码——结果一致，环境差异的论证才闭合。

**背景**。`wtf` 是查询缩写词含义的小工具。C 原版其实是一个 shell 脚本，它先查本地缩写词库；查不到时**依次调用三个外部程序**：

1. `whatis`（手册页索引查询）；
2. `pkg_info`（软件包信息查询）；
3. 如果当前目录在 pkgsrc 软件包树里，调用 `make help` 查询软件包帮助。

C 真源锚点（[源码锚点]）：`minix3/games/wtf/wtf:83-104`（三段依次尝试，失败则落到下一段）；三个被调程序在镜像中的缺席情况 [待目标实测]（验收命令见本节裁决块）。

**问题**。命令层要不要具备「调用外部程序」的能力与口径？三种可能：

- (甲) **实现调用**：给命令运行时补一个「启动外部程序并收集输出」的原语，wtf 逐级调用、失败则降级。优点：与 C 脚本语义一致；成本：需要一个进程创建/等待/管道设施，这套设施在当前命令运行时里是否存在需要确认（这是本条真正的成本项）。
- (乙) **不实现调用，登记环境差异**：当前镜像里 `whatis`、`pkg_info`、`make` 三个程序**都不存在**。C 的脚本在一个没有这三个程序的环境里运行时，三级查找会全部失败（`command not found` 被 `2>/dev/null` 吞掉，`$?` 非零）——也就是说，**在相同环境下，C 的行为与 Rust 现状（只查本地库）的可观察结果相同**。差异只在「将来这些程序出现了」时才会显现。
- (丙) 只实现 `whatis` 一级（自己实现手册页索引查询），跳过包管理两级。

**C 真源行为分析**。C 脚本的三级查找是「尽力而为」：每一级失败都静默落到下一级。因此「环境里没有这些程序」本身就是 C 脚本支持的一种正常状态。这一点很重要：它让「不做调用」在当前环境下并不产生可观察差异。

**后果推演**。选甲，要先有进程创建设施，且三个被调程序仍不存在，短期收益为零；选乙，零成本，但要在台账登记「当被调程序出现后需补齐」；选丙，只做一级且要自实现手册页索引，投入与收益都不匹配。

### 2.6 comm/cmp 的目录操作数：平台真值

**第一轮裁决**：**通过（方案丙），补证（高优先级）**。分别测 comm 与 cmp，不得用一个命令的结果代替另一个——两条命令的 C 代码形状不同（comm 走 `fopen`/`fgets`，读错误被当作文末；cmp 走 `open`/`fstat`/`fdopen`+`getc` 并显式检查 `ferror`，读错误经 `errmsg` 报告退出 2），逐条记录：打开是否成功、第一次读取的返回值、是否设置读错误标志、`errno`、最终 `stderr`、退出状态；同时确认两条命令的 C 原始实现如何处理读取错误。读数到手前，维持 Rust 现有的目录错误并退出 1 作为临时行为，不冻结为最终裁决。

**背景**。`comm` 与 `cmp` 都是「两个输入文件比较」类命令。当其中一个操作数是**目录**时，行为应当是什么？

**当前事实（[内部批次读数] + [源码锚点]；Minix 真值 [待目标实测]）**。在 Linux 宿主上编译的 C 参照件里，`comm <目录> <文件>` 的观察是：`fopen(目录, "r")` **成功**，随后 `fgets` 返回空（把「是目录」错误当作文末），于是参照件**退出 0**，并打出一段看似正常的比较输出。Rust 现状则报错 `comm: …: Is a directory` 并退出 1。

但项目在复核时发现这条「参照件退 0」是**宿主 Linux 的偶然**：C 真源 `minix3/usr.bin/comm/comm.c:181-182` 只在 `fopen` 返回空指针时才报错；`fopen` 对目录是否成功，取决于操作系统自己的「打开目录」语义。Linux 允许以只读方式打开目录（`open` 系统调用对目录成功，`read` 才返回「是目录」错误）；Minix 的对应语义需要查证——而查证的场所是 Minix 真机（本项目在模拟器里跑的镜像），不是 Linux 宿主。

**`cmp` 的代码形状与 `comm` 不同，必须分开测**。`cmp` 不走 `fopen` 打开输入：它用 `open(2)`（`minix3/usr.bin/cmp/cmp.c:102`、`:115`，打开失败 `warn` 后退出 2），随后 `fstat`（`cmp.c:135-143`）——**非普通文件**（目录正是这种）会置 `special` 标志、走 `c_special()` 特殊文件路径（`minix3/usr.bin/cmp/special.c:50`）：`fdopen` 之后用 `getc` 逐字节比较，循环退出后**显式检查 `ferror`**，读错误经 `errmsg` 报告并退出 2（`minix3/usr.bin/cmp/misc.c:50-56`）。也就是说，在宿主上 `cmp <目录> …` 的预期形状是「报错退出 2」，与 `comm` 的「静默退 0」**结构性地不同**——一条命令的读数不能推及另一条。两命令的 Minix 真机读数都要单独取。

**问题**。目录操作数的行为：(甲) 维持报错退出 1；(乙) 照宿主参照件退出 0 并输出「空比较」；(丙) 先取得 Minix 真机读数，再按平台真值决定。

**C 真源行为分析**。C 的 `comm` 没有对目录做任何特殊处理：它的行为完全由「`fopen` 对目录返回什么」「`fgets` 在目录上返回什么」决定。这正是第 0.1 节「平台真值」原则的教科书案例：同一份 C 代码在 Linux 与 Minix 上可以有不同的可观察行为，因为依赖了平台的打开/读取语义。

**后果推演**。选乙会把 Linux 宿主的偶然固化成语义；选甲可能与 Minix 真值相反；选丙最稳，但需要一次真机读数（项目已有真机门设施，成本可控）。

**项目侧推荐**：**丙（先取 Minix 真机读数，再定）**。在读数到手之前，维持现状（甲）不作最终裁决；读数到手后，若 Minix 的 `fopen` 对目录失败，则甲即与 C 一致（可关闭）；若 Minix 允许打开目录，则按 `fgets` 的返回行为决定。

### 2.7 宽字符腿：rev 的非法序列报错与 cut 的字符位

**第一轮裁决**：**部分通过**。`rev` 通过：实现非法多字节序列的报错腿（不再静默输出空内容并返回成功）；`rev` 的宽字符读取同样依赖 locale——现有探针用单枚 0xFF 验证了非法序列错误路径，但不足以说明所有非 ASCII 字节序列在目标 locale 下的处理方式，实现时须同时明确 `rev` 自己的解码契约。`cut -c` 列补证（高优先级）：不直接冻结为「固定按 UTF-8 码位计数」——C 的宽字符分支与 locale 相关，默认 C locale 下字符处理未必等价于 UTF-8 码位处理。做法：查明 C 的 `setlocale` 调用与目标环境默认 locale——已核实两处调用都是 `setlocale(LC_ALL, "")`（`minix3/usr.bin/rev/rev.c:67`、`minix3/usr.bin/cut/cut.c:82`，即从环境变量取 locale；未通过环境变量设置其他 locale 时，程序回落到 C locale）。C locale 使用单字节字符编码，ASCII 范围内的字符按单字节处理；**但不能据此推导所有 0x80–0xFF 高位字节都能作为合法字符处理**——某些输入可能被宽字符转换函数判为非法多字节序列，其具体处理需要结合 Minix libc 的宽字符转换实现与目标环境探针确认。C locale、UTF-8 locale、非法高位字节是三个不同的测试维度，不能合并成一个结论——再加上 Minix 镜像默认 locale、Rust 运行时是否提供 locale、C 宽字符实现实际采用的编码。若项目明确把运行环境固定为 UTF-8，可选 UTF-8 码位语义，但必须在环境契约中说明，不能称其为无条件复制 C 的宽字符行为。

**背景**。C 的这两个命令都有「宽字符」实现分支：`rev` 按**宽字符**（wchar）读写，`cut -c` 按**字符位置**而不是字节位置计数。

C 真源锚点：

- `rev`：`minix3/usr.bin/rev/rev.c:94-104` 用 `fgetwln`（宽字符行读取）读入；遇到非法多字节序列时，读取函数置错误标志，随后 `warn("%s", filename)` 打出 `stdin: Invalid or incomplete multibyte or wide character` 并退出 1。
- `cut -c`：`minix3/usr.bin/cut/x_cut.c:52-57` 用 `getwc`/`putwchar` 做字符级读写（文件里有一对编译期分支：宽字符分支与字节分支）。

Rust 现状（[源码锚点] + [内部批次读数]）：`rev` 按字节反转，遇到非法 UTF-8 时**静默返回空输出、无报文、退出 0**；`cut -c` 按**字节位置**计数，对多字节字符（例如中文）切出来的位置与 C 不同。项目里的探针读数：给 `rev` 一枚单独的 0xFF 字节，参照件打出空标准输出加一句错误（退出 1），本实现打出空输出、无报文、退出 0。

**问题**。两条宽字符腿是否实现？可拆成两个子问题：

- (甲) 实现：`rev` 增加「非法序列 → 报错退出 1」的腿；`cut -c` 改为按字符（UTF-8 解码后的码位）计数。成本：一个 UTF-8 解码器（或复用标准库的字符迭代），以及把所有现有「按字节」的测试期望按族翻正。
- (乙) 维持字节语义，登记两条已知差异。成本：零；缺点：对中文等多字节文本，`cut -c` 的列位置与 C 不同，这是**用户可直接观察**的差异。
- (丙) 只做 `rev` 的报错腿（安全性与可诊断性收益），`cut -c` 维持字节（登记差异）。

**C 真源行为分析**。C 的宽字符分支是按区域设置（locale）启用的；在默认的 C locale 下，宽字符函数实际上按单字节工作。这一点很重要：C 的 36 个测试用例与默认环境里，`cut -c` 与按字节可能在多数场景下一致；只有多字节 locale 才显出差异。`rev` 的错误报文则只在真遇到非法序列时出现。

**后果推演**。选乙，多字节文本的 `cut -c` 行为分叉，且 `rev` 在坏输入上「静默成功」会掩盖数据问题（这是可诊断性缺陷）；选甲，成本中等，但测试期望需要成族翻正；选丙是折中。

**项目侧推荐**：**甲（两条都实现）**，理由：`cut -c` 的字符语义是外部行为的一部分（列选择对文本处理工具是核心语义），`rev` 的报错腿是坏输入下的基本可诊断性。若评审担心成本，可退为丙并明确 `cut -c` 的字节语义登记为差异。

**开放问题（请评审回答）**：`cut -c` 的字符计数是否应严格按 C 的宽字符路径（含 locale 依赖），还是可以固定按 UTF-8 码位（项目的运行环境固定，简化实现）？

### 2.8 C 的缺陷形是否照抄：四种情形

**第一轮裁决**：**逐项裁决完成，实施与测试待验收（情形二推翻项目侧推荐）**。

- **情形一（cut 空列表）：修正，不挂死。** 保留「每个输入行输出一个空行、不输出任何被选择的数据字节」的 Rust 行为；明确这是经过选择的 Rust 语义，不是 C 兼容。
- **情形二（nl 短定界符）：不批准「拒绝短参数」。** 逐长度核对 C 代码的实际行为：长度 0 时第二次判断读 `optarg[1]` 已越界；长度 1 时第三次判断读 `optarg[2]` 已越界；长度 2 时三次读取都合法（`optarg[2]` 是终止空字节）；长度大于 2 触发拒绝。**因此「接受 0–2 字节」不能说成 C 赋值逻辑已经证明的正常行为**——空串与单字符两种输入都触发了越界读。Rust 选择接受 0–2 字节，是依据 C 注释 `/* at most two delimiter characters */` 与两个定界符字段作出的**项目语义选择**，不是从 C 对空串/单字符的实际行为推导；不复制 `optarg[2]` 的检查机制，更不得把宿主上某次越界读的结果固化成目标行为。边界按**字节**计（C 的 `char *` 下标按字节；测试夹具若只覆盖 ASCII，写成「0–2 字节（ASCII 夹具）」）。空串、单字节、双字节三种输入必须分别测试。
- **情形三（fold 数字位）：修正解析器。** `-b80` 正常解释为宽度 80，不依赖下一个参数得到宽度 0；缺少参数产生正常参数错误，不是空指针崩溃。
- **情形四（paste/comm 的 NUL 截断）：保留完整字节，登记差异。** C 用字符串输出 API 遇 NUL 停止；Rust 用字节向量保留后续数据；既然 I/O 模型能完整表达字节，就保留完整数据。
- **最终政策：** 无限循环、崩溃与数据静默丢失不作为必须兼容的契约；确定的正常输入边界尽量与 C 对齐；由未定义行为引出的偶然读数先证明目标环境稳定性，再决定是否兼容。

**背景**。前面第 2.2 节已经出现一个「C 的缺陷产生可观察行为」的案例。本节把同族的四种情形集中裁决。每种情形都给出：C 的行为、机制、当前 Rust 行为、以及「照抄」与「修正」的后果。这一族的共同问题是第 0.1 节原则二的直接适用：**缺陷兼容还是理性修正**。

**情形一：`cut` 的空列表（`CUT-EMPTY-BYTE-LIST-RUNAWAY`）**

- C 行为：`cut -b ''` 或 `cut -c ''`（给空的选择列表）时，C **无限输出**（不终止）。
- 机制：C 的字节剪切路径按位置表逐行输出；空表时循环的推进条件失效，导致对同一行无限循环（项目读数：参照件挂死不返回）。
- Rust 现状：每行打印一个空行后退出 0（这是当前测试 `an_empty_list_is_not_an_error_and_prints_a_blank_line_per_input` 钉住的行为）。
- 照抄后果：新实现在空列表时挂死。**这是不可接受的工程后果**（命令永不返回，占用终端）。
- 修正后果：与 C 分叉；需要登记。
- 项目侧倾向：修正（不挂死），登记差异。

**情形二：`nl` 的定界符长度（`NL-DELIM-LENGTH-RULE`）**

- C 行为：`nl -d` 给**不足两个字符**的定界符（`:`、`x`、空串）时，参照件报 `nl: invalid delim argument -- <值>` 并退出 1；给两个字符（`::`、`ab`）时接受。
- 机制：`minix3/usr.bin/nl/nl.c:157-167` 判断「超过两个字符」写的是 `if (optarg[2] != '\0')`——当用户的字符串只有 0 或 1 个字符时，这个下标**越过字符串末尾**读下一个字节。参数在内存里紧邻存放，该字节通常非零，于是实际效果变成「长度不足 2 也拒绝」。这是未定义行为产生的**稳定可观察后果**（在这类实现上总是拒短）。
- Rust 现状：接受短定界符（只取前两个字符）。
- 照抄后果：拒绝短定界符——但这本身是一条**合理的输入校验**（定界符必须正好两个字符）。可以不用越界读、以显式检查实现同样的接受/拒绝边界。
- 修正后果：接受短定界符，与 C 分叉。
- 项目侧倾向：照抄判决（拒绝短定界符），但用显式长度检查实现，不复制越界读。这样「判决」与 C 同，「机制」健康。**（第一轮评审推翻此倾向并进一步更正论证：0–2 字节接受是项目语义选择——空串/单字符在 C 里越界，不能作为「C 已定义正常接受」的依据——>2 字节拒绝；见本节开头裁决块。）**

**情形三：`fold` 的数字位（`FOLD-DIGIT-NOT-FIRST-IN-CLUSTER`）**

- C 行为：`fold` 的宽度选项有一个古怪的解析分支。当数字不是紧跟短横线后的第一位时（例如 `-b80`，`b` 是选项字母、`8` 是数字），C 去读**下一个命令行参数**的第二个字符（`minix3/usr.bin/fold/fold.c:88-96` 的 `atoi(argv[optind] + 1)`），并且那个参数随后被当作文件名跳过。三个实测形态：
  - `-b9`：下一个参数不存在（空指针），参照件**当场段错误**（退出码 -11 / 139）。
  - `-b80`：读到的字符串是 `b80`，`atoi` 得 0，参照件按宽度 0 一行一个字输出。
  - `-b9 80`：把 `80` 当档名，报「找不到文件」退出 1（与 Rust 现状同形，因为开档失败先触发）。
- Rust 现状：把聚簇里的数字继续累加宽度（`-b80` 按宽度 80 处理）。
- 照抄后果：复制一个会段错误的解析分支，或复制「宽度 0 一行一字」的怪异结果。
- 修正后果：Rust 的处理更符合直觉；与 C 分叉。
- 项目侧倾向：修正（绝不复制段错误），登记差异。`-b80` 的宽度解释可以单独讨论是否要贴近 C 的 0。

**情形四：`paste`/`comm` 的空字节截断（`PASTE-COMM-NUL-TRUNCATES-PRINT-LEG`）**

- C 行为：`paste` 与 `comm` 的输出腿都以「字符串末尾是空字节」的方式发送（`%s`/`%.*s`），于是**行内如果含值为 0 的字节，C 在那里截断**。两台各自有锚点与读数：`paste` 的发送腿在 `minix3/usr.bin/paste/paste.c:180`（换行改写为串尾）；`comm` 的行缓冲在 `minix3/usr.bin/comm/comm.c:209-211` 写串尾、输出走 `%s`。实测：给 `paste` 一行 `61 00 62 0a`（字节 a、NUL、b、换行），参照件输出 `61 0a`（只到 NUL 前）；给 `comm` 含 NUL 的输入，参照件同样在 NUL 处截断（读数 `tmp/comm-409/`，输出含 `09 09 61 0a 63 0a 09 7a 0a` 形状）。
- 机制：C 把行内容当以空字节结尾的字符串打印；NUL 是串的结束符。这是「用字符串 API 处理二进制数据」的经典缺陷。
- Rust 现状：按字节向量输出，NUL 原样保留（未截断）。
- 照抄后果：与 C 完全一致，包括「二进制数据被静默截断」。对于文本工具这通常无害；对于含 NUL 的二进制输入是数据丢失。
- 修正后果：与 C 分叉；含 NUL 的输入输出不同。
- 项目侧倾向：修正（保留完整字节），登记差异。理由：静默截断是数据丢失，属于第 0.1 节原则二里应当修正的类别。

**整族问题**。请评审在以下两种政策中选择一种，或给出更细的分档：

- **政策甲（缺陷兼容优先）**：凡可观察行为都照抄，包括崩溃、截断；唯一底线是「不引入无限循环/挂死」这类会让工具不可用的形态。
- **政策乙（安全与可诊断优先）**：凡缺陷形一律修正并登记差异；「照抄」只保留给确定性、无害的判决（如情形二的拒绝短定界符）。
- **政策丙（逐情形裁决）**：本材料已给出的四个倾向（情形一修正、情形二「判决照抄但机制健康」、情形三修正、情形四修正），评审逐条确认或修改。

**项目侧推荐**：**政策丙**，并按上表逐情形执行。理由：四种情形的「可观察性」「危害度」「照抄成本」差异太大，用一条政策覆盖会顾此失彼。同时建议把「判决照抄、机制健康」这种中间形态（情形二）确立为一条通用做法：**保留 C 的接受/拒绝边界，但不复制产生该边界的缺陷机制**。

**执行说明（第一轮裁决后）**：四种情形的处理方式均已裁决（见本节开头裁决块），进入实施与测试验收；情形二按「0–2 字节接受是项目语义选择」的新论证实施，情形四按保留完整字节实施并登记差异。

### 2.9 chown 的名换号：口令库腿

**第一轮裁决**：**通过（方案乙），附错误语义修正**。不实现用户名/组名解析，不在命令层直接解析口令文件；继续接受数字 UID/GID。**名字形输入改为走 C 的 unknown user/group 类错误**（当前数据库缺失的环境下，C 的报文语义是「这个名字不存在」而非「这个功能不支持」），不再报 `NamedUnsupported`。等口令数据库真正出现时，再补 `getpwnam`/`getgrnam`。

**背景**。`chown`（改文件属主）与它的别名 `chgrp`（改文件属组）接受两种形式的参数：数字编号（`100`、`100:200`、`#100`）与名字（`root`、`wheel`）。名字形式需要查**口令数据库**（用户数据库与组数据库），也就是 C 里的 `getpwnam`/`getgrnam` 两个库函数。

C 真源锚点：`minix3/sbin/chown/chown.c:169`（`uid_from_user` 解析用户名）、`:256`（`getgrnam` 解析组名）、`:269`（`uid_from_user` 的回落路径）。解析失败时报「未知用户/组」类错误并退出。

Rust 现状：`os/commands/bin/fileops/src/chown.rs` 的解析层只接受数字编号；遇到名字时返回一个明确的「名字不支持」错误（枚举值 `ChownError::NamedUnsupported`），并在注释里写明这是已登记的缺口。也就是说，**当前实现不会假装解析名字，而是响亮拒绝**。

**当前事实（[可重跑读数] `ls os/etc/` + [源码锚点] `chown.rs` 注释）**：项目镜像的 `/etc` 目录里只有 `rc` 与 `ttys` 两个文件，**没有 `passwd` 与 `group`**（可复核：`ls os/etc/`）。也就是说，即使实现了 `getpwnam`/`getgrnam`，镜像里也没有可供查询的数据。

**问题**。名换号腿：(甲) 实现口令数据库查询（需要先有 `/etc/passwd`、`/etc/group` 与对应的解析函数）；(乙) 维持数字编号、响亮拒绝名字，登记已知差异；(丙) 在命令内部直接解析一个约定路径的口令文件（不经过库层）。

**C 真源行为分析**。C 的 chown 依赖系统口令数据库；在数据库缺失的环境里，C 同样会报「未知用户」。所以「镜像没有口令库」这个事实本身让 C 与 Rust 在**当前环境**下的可观察行为接近（都拒绝名字），差异会在口令库出现后显现。

**后果推演**。选甲，需要先建设口令库基础设施（数据文件 + 库函数 + 镜像播种），是一次跨板工程；选丙，把「口令文件格式」直接固化进命令，层次不干净；选乙，零成本，但要在台账登记「口令库出现后必须补齐」。

**项目侧推荐**：**乙（维持数字编号，登记差异）**，并把「口令库基础设施」作为一条独立的前置议题（与登录、用户管理相关命令一起考虑），不在 chown 一个命令里单点突破。

**验收要求（第一轮评审后由开放问题转为验收）**：无口令数据库时，名字形输入（如 `chown root file`）产生与 C 的 unknown user/group 类错误相符的报文和非零退出状态，不得再返回 `NamedUnsupported`。

### 2.10 九台网络变体驱动的去留

**第一轮裁决**：**有条件通过（方案丙）**。保留九个占位壳，但必须显式标记不可用：① 源码明确标注 placeholder/unsupported；② 不伪造芯片识别结果；③ 不向服务管理器或设备发现层报告自己可以驱动真实设备；④ 若有人尝试启动，明确报告未实现，而不是静默运行空循环；⑤ 构建文档明确区分 46 个实现驱动与 9 个占位。发布状态按四个层面分开要求，**「镜像里有二进制」不等于「系统可以把它当已实现驱动启动」**：1) 源码与构建——占位源码保留，二进制可按需要进入镜像；2) 设备注册——没有真实设备匹配时，不得注册成可用驱动；3) RS 生产启动配置——未实现占位不得进入正常生产启动流程，除非 RS 启动链能安全识别并处理其未实现状态；4) 显式启动——主动请求启动占位驱动时返回明确的未实现错误。若当前构建配置会把它们当成正式可启动驱动发布，应从生产部署清单排除但保留源码骨架。补证（高优先级）：确认这九台是否被实际加入默认镜像与 RS 启动配置——这决定是只加标记，还是必须从可用驱动清单剔除。

### 2.11 存储代理族下游转发的形态（fbd 与 filter）

**第一轮裁决**：**方向支持（方案甲），filter 部分补证（最高优先级）**。fbd：优先采用 C 已有的拷贝转发路径；若数据内容、长度、错误返回与调用方可观察结果一致，可直接实施。filter：**「逐元素请求与聚集/分散请求语义等价」的论断不被接受**——多段请求中途失败时，已写入的字节范围、部分成功状态、两个镜像后端之间的状态差异、请求顺序、失败报告位置都可能不同，属于可观察行为而非纯性能差异。先补部分失败语义分析（① C 的 vector 请求多段中途失败的处理逻辑；② 两个镜像后端的调用先后与错误传播；③ Rust 单段接口如何报告部分完成；④ 逐段请求后失败位置与后端最终状态是否与 C 相同）。若不能证明等价，可考虑给块设备接口补最小 vector 能力，而不是马上建设通用授权模型。

**背景**。存储代理族里有两个「在真实块设备之上再加一层」的驱动：

- `fbd`（块设备代理）在 C 里有两条数据通路：**直接转发**用「间接授权」原语（`cpf_grant_indirect`，`minix3/minix/drivers/storage/fbd/fbd.c:205`、`:230-250`）把调用方的内存授权原样转给下游驱动，零拷贝；**拷贝转发**（`fbd_transfer_copy`，`fbd.c:275`）先把数据拷进自己的暂存区再转发。
- `filter`（镜像过滤）在 C 里用「聚集/分散」的输入输出向量数组转发（`minix3/minix/drivers/storage/filter/driver.c:905-935`：一次请求携带最多 `NR_IOREQS` 个不连续段，镜像开启时对两个后端各发一份）。

Rust 侧（[源码锚点]）：没有「间接授权」原语（授权对象不能转手），所以 fbd 的直接转发不可用；同时，Rust 的块设备框架当前只支持单段请求（项目登记为 `E-BLK-VEC` 缺口），所以 filter 的聚集/分散数组也不能原样表达。两者共同的问题是：下游转发腿用什么形态落地。

**问题**。下游转发腿用哪种形态：

- (甲) **fbd 采用拷贝通路；filter 候选采用逐段单请求**。fbd 的拷贝通路按核对清单验证后实施；filter 的逐段请求只是候选实现形态，其与 C vector 请求的外部语义等价性尚未证明，未经补证不得实施为等价替换。每台设备具名登记这一取舍。
- (乙) 自建「间接授权」原语：补上 Rust 侧缺失的授权转手能力，恢复零拷贝直接转发。成本：一个跨层级的授权模型设计，风险高。
- (丙) 先补「聚集/分散」框架缺口（`E-BLK-VEC`），再按拷贝通路实现。

**C 真源行为分析（第一轮评审对下述等价主张作了区分，filter 一侧撤回）**。两条通路要分开看，不能混成一句「语义等价」：

| 子问题 | 当前结论 |
|---|---|
| fbd：C 的直接转发与拷贝转发是否等价 | 可以按拷贝通路推进，但仍需核实数据内容、长度、错误返回等外部可观察结果一致 |
| filter：C 的 vector 请求改成 Rust 逐段请求是否等价 | **尚未证明，当前禁止据此实施为等价替换** |

fbd 的两条通路（直接、拷贝）是 C 自己为同一语义写的两种实现，等价性有较强的源码依据，但仍须按上表核对数据、长度与错误返回。filter 的情况不同：把一次携带多段的聚集/分散请求改成多次单段请求，在多段中途失败时的已写入字节范围、部分成功状态、两个镜像后端之间的状态差异、请求顺序、失败报告位置上都可能不同——这些是可观察行为，不是纯性能差异。第一轮裁决已撤回「逐元素请求与聚集/分散请求语义等价」的主张。

**后果推演（按第一轮裁决改写）**。fbd 选甲（拷贝通路）：可落地，等价性仍须按核对清单确认；filter 的逐元素请求：**在部分失败语义补证完成前不得实施**；若补证后仍不能证明等价，可考虑给块设备接口补最小 vector 能力，而不是马上建设通用授权模型。

**项目侧推荐（已被第一轮裁决修正）**：fbd 采用拷贝通路（核对通过即可实施）；filter 待部分失败语义补证后另定，原「拷贝通路 + 逐元素请求」的整体推荐不再有效。「间接授权」作为未来优化项登记（不阻塞）。

**调查问题（随最高优先级补证一并回答，不是开放裁决）**：逐元素请求带来的多次往返，在镜像设备的错误处理（部分成功）上是否需要与 C 的批量请求保持一致的语义？此问已并入 §1b.4 最高优先级补证的第四项（逐段请求后失败位置与后端最终状态是否与 C 相同），随该补证一并交回读数。

### 2.12 `KernelInfo` 的引导哨兵字段

**第一轮裁决**：**通过（方案乙）**。保留 `bootstrap_start`/`bootstrap_len` 与现有协议形状，`(0,0)` 哨兵语义受守卫保护。关闭条件写清：保留至明确的跨镜像协议演进或结构重设计时重新评估；「第二个真实使用者出现」可作为重新评估的触发条件，但不是届时必须删除。

**背景**。内核与引导程序之间有一个共享的数据结构 `KernelInfo`，里面有两个字段 `bootstrap_start` 与 `bootstrap_len`，描述「引导阶段临时使用的内存区段」（C 原版有这样一个概念：内核启动早期使用的一段内存，启动完成后回收）。

在 64 位架构下，本项目的内核**不使用**这个概念（内核从第一条指令起就在高半区，不存在单独的临时区段），所以这两个字段在生产代码里恒为 `(0, 0)`；「回收这段内存」的守卫代码因此永远不可达。这两个字段保留的唯一理由是「与 C 的 `kinfo_t` 结构保持对称」。

**问题**。(甲) 删除字段与守卫（要改公共数据结构，波及 40 多个测试内核的构造点）；(乙) 保留，加守卫注释（现状，临时裁决）。

**C 真源行为分析**。C 的 `kinfo_t` 有这两个字段，且 C 的内核确实使用它们。Rust 侧「不使用」是架构差异（高半启动 vs 低址启动），属于第 0.1 节意义上的「语义等价、机制不同」——字段的存在与否本身不改变任何外部行为，只影响内核与引导程序之间的结构对称性。

**后果推演**。删：公共 API 变更、大量测试构造点同步修改、风险是漏改；留：两个死字段，但零风险。

**项目侧推荐**：**乙（保留）**。理由：外部行为零差异；删除的成本与风险不对等。若评审倾向「宁删勿留」，可以接受，但需要一次全仓构造点同步与三架构真机复验。

**执行说明（第一轮裁决后）**：关闭条件已定——保留至明确的跨镜像协议演进或结构重设计时重新评估；「第二个真实使用者出现」是重新评估的触发条件，不是届时必须删除。

### 2.13 x86_64 客态测试腿的 A/B 两案

**第一轮裁决**：**通过（方案乙），附文案修正**。追认 picolibc 非 TLS 客态方案，不开展内核级 FS 基址保存/恢复。文案修正：36/36 是「全部 36 个用例到达终态」，具体读数是 34 通过 + 2 跳过，不能写成「36 项全部通过」；这条腿是测试基础设施，不是内核 TLS 支持能力的验收。未来需要 glibc 或真正使用 TLS 的用户态程序时另立项，不为当前 ATF 提前做内核功能。

**背景**。项目用上游的 C 测试套件（ATF，18 个程序、36 个用例）做三架构真机验收。x86_64 这一腿需要把 C 测试程序编译成可在项目镜像里运行的形态。之前有两条路：

**当前事实**。乙案已经落地并在真机通过：`tools/vendor-picolibc-x86_64.sh` 本地构建 picolibc 1.8.6（显式 `-Dthread-local-storage=false`），`build-libatf-c.sh`/`build-atf-test.sh` 的 x86_64 腿改链 picolibc，并补了 x86_64 的启动桥（`startup-minix.c` 的 `_start`、`sys-bridge.c` 的 `syscall` 与 `int 0x21` 桥）；门读数 `test-atf-x86_64.sh` 36/36 到终态（34 通过 + 2 跳过），证据件 `suite_sha256=866e091d66d1…`。当时没有等到 A/B 两案的明确裁决，按乙案这个「可逆默认」落地。

**问题**。追认乙案，还是切到甲案？

**C 真源行为分析**。这一条不是「C 行为 vs Rust 行为」的问题，而是「测试基础设施怎么搭」的问题：C 的 ATF 测试程序本身不依赖 TLS（picolibc 非 TLS 形态已证 36/36），所以乙案不改变测试语义。

**后果推演**。追认乙案：零额外工作，测试腿保持绿色；切甲案：需要内核新功能（FS 基址保存/恢复），且测试语义与乙案相同，收益是「通用 glibc 兼容性」而不是测试本身。

### 2.15 关键机制原文摘录

以下三段 C 原文对应本材料中最需要「看清机制」的三处判断（评审者可据此独立判断「缺陷形」的定性是否成立）：

**摘录一：`nl` 的定界符长度检查**（`minix3/usr.bin/nl/nl.c:156-167`）

```c
case 'd':
    if (optarg[0] != '\0')
        delim[0] = optarg[0];
    if (optarg[1] != '\0')
        delim[1] = optarg[1];
    /* at most two delimiter characters */
    if (optarg[2] != '\0') {
        errx(EXIT_FAILURE,
            "invalid delim argument -- %s",
            optarg);
        /* NOTREACHED */
```

注释说「最多两个字符」，但检查写的是「第三个字符必须为空」。逐长度看：长度 0 时第二次判断读 `optarg[1]` 已越界；长度 1 时第三次判断读 `optarg[2]` 已越界；长度 2 时三次读取都合法；长度大于 2 触发拒绝。越界读是未定义行为；实测越界字节通常非零，于是效果变成「不足两个字符也拒绝」——但这只是宿主上某次越界读的偶然结果，不是可移植语义。

**摘录二：`fold` 的数字位解析**（`minix3/usr.bin/fold/fold.c:88-96`）

```c
case '0': case '1': case '2': case '3': case '4':
case '5': case '6': case '7': case '8': case '9':
    if (width == -1) {
        p = argv[optind - 1];
        if (p[0] == '-' && p[1] == ch && !p[2])
            width = atoi(++p);
        else
            width = atoi(argv[optind] + 1);

    break;
```

正常形态是 `-b80`：`p` 指向 `-b80`，`p[2]` 非空，于是走 `else` 分支，去读**下一个参数**的第二个字符。下一个参数不存在时 `argv[optind]` 是空指针，`atoi` 前就已崩溃（实测段错误）。

## 附录 B：术语表（面向无代码读者的最小词汇表）

- **C 真源**：Minix3 的原始 C 实现。项目以它的可观察行为为事实基线。
- **登记号**：项目台账给每个待办/债务起的稳定标签（如 `CUT-EMPTY-BYTE-LIST-RUNAWAY`），仅作追踪用。
- **宿主 vs 真机**：宿主是开发机的 Linux 环境；真机是项目自己的镜像在模拟器里运行的环境。凡依赖操作系统语义的观察，两者可能不同。
- **stdio 缓冲**：C 标准库对输出流的用户态缓冲。小量输出会攒着，直到缓冲满或进程退出才真正写到设备。
- **退出码与信号**：进程正常结束返回 0 至 255 的退出码；被信号杀死时，shell 报 128+信号编号（如 136 = 128+8，信号 8 是浮点异常）。
- **宽字符**：C 的 `wchar_t` 字符族。按宽字符处理意味着把多字节序列解码成字符再计数，而不是按字节计数。
- **未定义行为**：C 标准允许实现任意处置的程序行为（越界读、对零取模等）。它在特定实现上可能有稳定的可观察结果，但不可移植。
- **BSS**：程序数据段里存放「初值为零的全局/静态变量」的区域。它在同一进程内跨函数调用存活。
- **服务器（server）**：项目里承担系统服务职责的独立进程（如虚存服务器、服务管理器）。服务器崩溃后可被重启。
- **块设备镜像**：在真实块设备之上做一层的逻辑设备，例如把写入同时发往两个后端。
- **聚集/分散（gather/scatter）**：一次输入输出请求携带多个不连续的内存段，而不是一段连续内存。
