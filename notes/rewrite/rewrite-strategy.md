# 重写策略：语义冻结

> **核心原则**：将重写与重构设计严格分层 —— 先建立行为等价性，再改进设计。

---

## 1. 两阶段方法

### 1.1 阶段分离

```
阶段 1：Rewrite（语义等价）
阶段 2：Redesign（语义改进）
```

**避免常见错误**：

```
Rewrite + Redesign + 优化 + 重构 → 一锅炖 → 爆炸
```

### 1.2 为什么这很重要

在 OS 级别，重写时同时改变语义会导致：

- 无法区分：
  - 你引入的 bug
  - 原本的设计决策
- fork 语义变化
- wait 语义变化
- RS 行为变化
- VFS 同步问题
- IPC 时序变化

---

## 2. 语义冻结

### 2.1 允许改变的内容

| 类别 | 允许的变化 |
|------|-----------|
| 架构 | 32位 → 64位 |
| 语言 | C → Rust |
| 硬件抽象 | 直接硬件操作 → trait 抽象 |
| 内存安全 | 裸指针 → 安全抽象 |

### 2.2 禁止改变的内容

| 类别 | 限制 |
|------|------|
| 语义 | 必须与 Minix3 行为一致 |
| 时序 | IPC 顺序必须保留 |
| IPC 协议 | 消息格式不变 |
| 进程关系 | parent/child 语义保留 |

### 2.3 不变量

```
Invariant: 行为必须等价于 Minix3
```

---

## 3. 标注设计缺陷

### 3.1 标注而非修复

在重写阶段，显式标记设计问题：

```rust
/// DESIGN NOTE:
/// 此字段承担双重职责：
/// 1. Unix 父子关系（用于 wait()/SIGCHLD）
/// 2. 系统进程的启动初始化链接
///
/// 这两种语义并不等价。
/// 详见 redesign 文档中的分离方案。
parent: Pid,
```

### 3.2 Hack 标注

```rust
/// HACK (继承自 Minix3):
/// 此调用作为 PM 和 VFS 之间的同步屏障。
/// 它与 setuid 在语义上无关。
///
/// 除非重新设计 IPC 协议，否则不要删除。
fn setuid_barrier() { ... }
```

### 3.3 为什么这很重要

> 重写 ≠ 盲目复刻
> 重写 = 带注释的保真复制

---

## 4. 接受的技术债务（保留）

在重写阶段，以下问题**有意保留**：

| 问题 | 位置 | 原因 |
|------|------|------|
| parent 语义混乱 | `mproc.mp_parent` | 保留 Unix 兼容性 |
| `setuid(0)` hack | RS-VFS 同步 | 保留 IPC 时序 |
| `do_fork` / `do_srv_fork` 不对称 | PM fork | 保留服务 fork 语义 |
| PM / VFS 耦合 | 多处 | 保留同步机制 |

## 6. 何时开始 Redesign？

### 6.1 判断标准

> 当你可以**完全预测 Minix3 行为**时

### 6.2 准备就绪的指标

- [ ] 知道所有路径：fork → VFS → VM → RS
- [ ] 知道哪里会发生 SUSPEND
- [ ] 知道哪里可能死锁
- [ ] 知道哪里依赖 hack

### 6.3 心态转变

```
阶段 1：理解系统
阶段 2：设计系统
```

很多人失败于：

```
没有理解 → 立即重构 → 崩溃
```

正确的路径：

```
先理解 → 再重构
```

---

## 7. 总结

| 原则 | 描述 |
|------|------|
| **语义冻结** | 重写期间保留所有 Minix3 行为 |
| **标注复刻** | 标记设计缺陷，暂不修复 |
| **阶段分离** | 先重写，后重构 |
| **行为等价** | 重写版本必须是"可信基准" |

> **核心洞察**：克制设计冲动，优先建立语义确定性。
