## 1. 概念：被驱动的服务器

### 1.0 章节引言

目标读者是已经理解微内核基本划分的读者：内核做调度与消息传递，文件功能放在用户态的服务进程里。前置知识只需要两条：进程之间用消息通信，一次文件操作对应一次请求与一次回复。

本章先建立心智模型，再进入源码。模型回答三个问题：文件服务器的工作从哪里来（请求来源），工作如何被路由到正确的处理函数（请求分发），服务器的生命从何开始到何结束（挂载状态与退出条件）。

### 1.1 文件服务器是一间只接订单的厨房

想象一家餐厅的后厨。厨师不招待客人，不点菜，不结账。后厨只做一件事：从传菜口接到订单小票，做菜，把成品连同小票编号一起送回去。小票编号至关重要，因为多个订单同时在做，服务员靠编号认领自己的菜。

Minix3 的文件服务器就是这间后厨。虚拟文件系统服务（Virtual File System，后文简称虚拟文件系统服务）是前台：它接待应用程序的打开、读写、关闭请求，把每个请求翻译成一张小票（消息），递给对应的文件服务器。文件服务器只管做，做完把结果连同小票编号送回。应用程序长什么样、文件描述符表怎么管，文件服务器一概不关心。

这个比喻直接对应三处真实机制：

1. **小票就是消息**。每条消息的类型字段同时携带两样东西：要做什么操作（请求编号），以及这是第几号订单（事务编号）。做完之后，回复消息原样带回事务编号，发送方靠它配对请求与回复。
2. **传菜口只有一个**。文件服务器一次只处理一条消息，处理完才接下一条。这就是贯穿本框架的单线程事件循环假设：任何时刻最多一个请求在执行，因此不需要锁。
3. **后厨有营业状态**。没挂载文件系统时，后厨拒绝一切点菜，只接受开业请求（挂载）。打烊请求（卸载）之后，如果老板还要求继续营业，后厨空转等待下一次开业；只有老板明确关店并且已经打烊，后厨才下班。

### 1.2 请求编号：三十三张标准小票

虚拟文件系统服务与文件服务器之间只说三十三种话，从挂载、查找、读写，到改权限、读目录、同步刷盘。每个编号是基址 `FS_BASE`（数值 `0xA00`）加上一个从一到三十三的小索引。索引一保留给一个历史上存在、如今标明应当删除的获取节点请求，分发表里没有它的位置；索引二到三十三各有归属。

为什么编号要这样设计？因为消息类型的低十六位已经被事务编号占用。发送方把请求编号放在高十六位，事务编号放在低十六位，拼成一个三十二位整数发出去。接收方先拆出事务编号留着回执用，再把高十六位减去基址，得到分发表下标，查表调用。这套拼装与拆分就是头文件里的三个事务宏：取编号、加编号、删编号。

这里有一个值得停留的细节：高位部分是带符号数，减法按无符号回绕语义执行。也就是说，即使收到的类型字段看起来是负数，减法依然能得到正确的下标，随后的范围检查会挡住非法下标。这是 C 语言里典型的"用回绕代替分支"的写法，Rust 实现里用带回绕的减法完整保留了它。

### 1.3 分发表：三十二个槽位

分发表是三十四个槽位的数组（下标零到三十三），其中下标零从不使用，下标一空着（对应那个应当删除的请求），其余三十二个槽位各指一个适配函数。收到请求时查表：下标越界或者槽位为空，回答"功能未实现"；查到函数，就调用它。

分发表的意义在于把"路由"与"处理"分开。路由只认编号，不认内容；处理函数只管自己的请求，不管别人。这种分离让增加一种文件系统变得便宜：实现一组回调函数，填进同一张表，主循环一行不用改。后文的 Rust 设计把这张函数指针数组变成 trait 加匹配分支，路由依然只认编号。

### 1.4 挂载状态：营业中还是打烊

文件服务器记三样全局状态：当前挂载在哪个设备上，文件系统的根节点是几号，以及到底挂没挂载。外加一个运行标志，表示老板（启动框架）是否还要求营业。

消息分发的门禁规则只有一条：**没挂载时，只受理挂载请求**。其他请求一律回答"无效参数"，连表都不查。这条规则保护了尚未准备好的服务器：它的缓存是空的，根节点未知，任何文件操作都没有意义。

退出条件是运行标志与挂载状态的组合：**只要还在要求营业，或者还挂载着，就继续收消息**。于是关闭流程自然分成两步：先请服务器终止（运行标志清零），它继续服务直到卸载请求到来；卸载完成后两个条件同时为假，循环结束，进程退出。这就是为什么终止函数只做两件事：清运行标志，取消当前阻塞的接收调用，让循环有机会重新检查条件。

### 1.5 非请求消息：不属于后厨的敲门声

不是每条消息都是订单。内核通知（比如进程状态变化的通告）和其他服务进程发来的消息也会到达同一个接收口。规则是：凡是不来自虚拟文件系统服务的消息，一律交给服务器自定义的通用处理函数，并且**不发送回复**。因为对方没下单，自然没有小票可回。

这个"收到但不回复"的分支是新人的第一个陷阱：直觉上每个接收都该有个发送与之配对，但通知机制的设计恰恰是单向的。Rust 实现里用一个独立的枚举分支表达它，类型上就不允许为它构造回复。

### 1.6 能力协商：开业时互相通气

挂载成功时，服务器可以报告自己的能力：是否支持多线程，是否支持窥视（把文件页直接暴露给虚拟内存而不复制），是否支持六十四位文件大小。框架还帮服务器做一件事：如果服务器同时实现了文件窥视和块窥视，或者它根本没有后端设备（无盘服务器可以用读来模拟窥视），框架自动点亮窥视能力位，服务器自己不用操心。

多线程能力位值得单独说明：本框架只实现单线程事件循环，因此基于本框架的服务器永远不置该位。这不是缺功能，而是有意的设计选择，理由在第 3 章展开。

### 1.7 与其他系统的对照

Linux 把类似的职责拆成四组操作表：超级块操作、索引节点操作、文件操作、地址空间操作，分别挂在不同的对象上。Minix3 的选择恰恰相反：一张大表按请求编号组织，不按对象组织。原因在于通信方式不同：Linux 是函数调用，调用点知道自己手里拿的是什么对象；Minix3 是消息传递，收到的只是一个编号，必须先路由再谈对象。理解了这个差异，就理解了为什么 Rust 设计保留整张表而不是拆成四个 trait：拆表省不掉路由，反而让"某个请求没人处理"的错误从查表时的显式拒绝，变成编译期难以发现的缺方法。

Redox 的方案（Scheme 特征）更接近 Minix3：一组 open、read、write、close 方法，路径形如"方案名冒号路径"。区别在于 Redox 用统一资源标识符风格的路径字符串做路由，而 Minix3 用数字编号。数字编号的好处是路由开销固定且可表驱动，代价是可读性差——这正是 Rust 侧用枚举把每个编号重新命名回人类语言的原因。

### 1.8 本章小结

文件服务器是被驱动的：虚拟文件系统服务发请求，它做事并回复。三十三种请求编号加事务编号拼成消息类型，分发表做路由，挂载状态做门禁，非请求消息走旁路且不回复，能力在挂载时协商，退出发生在"不再要求营业并且已经卸载"的那一刻。下一章进入 C 源码，逐段验证这些机制的真实形状。

## 2. C 源码分析

### 2.1 文件清单与全局状态

框架的 C 源码只有两个文件，外加两个头文件：

| 文件 | 行数 | 内容 |
|------|------|------|
| `minix3/minix/lib/libfsdriver/fsdriver.c` | 九十七行 | 主循环、逐消息分发、终止函数 |
| `minix3/minix/lib/libfsdriver/table.c` | 四十行 | 三十二个槽位的分发表 |
| `minix3/minix/include/minix/vfsif.h` | 八十四行 | 请求编号、标志、事务宏、特殊错误码 |
| `minix3/minix/include/minix/fsdriver.h` | 一百二十七行 | 回调表结构、节点描述、数据抽象 |

全局状态在 `fsdriver.c` 开头五行：挂载设备号、根节点号、是否已挂载三个库内变量，外加一个文件私有的运行标志（`fsdriver.c:5-9`）。注意运行标志是静态的，外部只能通过终止函数修改它，这是刻意的封装：退出条件只能由框架自己推进，服务器实现碰不到它。

### 2.2 逐消息分发 `fsdriver_process`（`fsdriver.c:17-62`）

分发函数 `fsdriver_process` 接收四个参数：回调表指针、收到的消息、内核报告的接收状态、是否异步回复。函数体按顺序做五件事：

1. **旁路判断**（`fsdriver.c:26-31`）。如果是内核通知，或者发送方不是虚拟文件系统服务，就调用通用处理函数（如果服务器提供了的话），然后直接返回，不发送任何回复。
2. **拆事务编号**（`fsdriver.c:34-35`）。用取编号宏留下低十六位，用删编号宏（算术右移十六位）得到请求部分。
3. **门禁检查**（`fsdriver.c:39`）。已挂载，或者请求正好是挂载请求，才能继续；否则结果记为无效参数。
4. **查表调用**（`fsdriver.c:40-45`）。请求部分减去基址（注释明确写了回绕是有意的），下标合法且槽位非空就调用，否则记为功能未实现。
5. **发送回复**（`fsdriver.c:50-58`）。回复类型是结果码加上原事务编号；异步标志决定用异步发送还是普通发送；发送失败打印一行日志；最后调用请求后钩子（如果有）。

特别注意第 5 步的回复是无条件发送的：即使结果是错误码，也要把错误码连同事务编号送回去，让发送方知道这单失败了。唯一不发送回复的是第 1 步的旁路。

### 2.3 终止 `fsdriver_terminate` 与主循环 `fsdriver_task`（`fsdriver.c:64-97`）

终止函数 `fsdriver_terminate`（`fsdriver.c:67-74`）只有两行有效代码：运行标志置假，取消阻塞中的接收。取消接收会让主循环的接收调用以"被中断"错误返回，主循环看到这个特定错误就继续下一轮（`fsdriver.c:88-90`），重新检查循环条件。

主循环 `fsdriver_task`（`fsdriver.c:79-97`）的结构：

```
运行标志置真
当（运行标志为真，或者已挂载）时循环：
    阻塞接收任意来源的消息
    如果接收返回被中断：继续下一轮
    如果接收返回其他错误：宕机（框架认为接收失败是不可恢复的）
    分发这条消息（同步回复模式）
```

宕机分支值得注意：接收失败在框架看来不可能是 transient 的。与其带着未知状态继续服务，不如立刻停下。这是一种 fail-stop（故障即停）哲学：宁可整个服务器进程崩溃重启，也不让可疑状态污染文件系统。

### 2.4 分发表 `fsdriver_callvec`（`table.c:1-40`）

分发表 `fsdriver_callvec` 用了一个小技巧定义下标：`CALL(请求编号)` 展开成 `(请求编号减基址)`，于是每一行字面上就是"某某请求对应某某适配函数"，不需要人工计算下标。三十四槽数组里填了三十二个函数，缺的是下标零（保留）和下标一（获取节点请求，头文件标注应当删除）。缺失的槽位保持空指针，分发时的空检查会把它们变成"功能未实现"回答。

三十二个适配函数的声明集中在库内头文件 `minix3/minix/lib/libfsdriver/fsdriver.h`（第四到第八十四行），每个函数签名相同：回调表指针、输入消息、输出消息，返回整数结果码。签名统一是故意的：分发表数组的元素类型只有一个，不统一就填不进同一张表。

### 2.5 请求编号与事务宏（`vfsif.h:41-81`）

三十三个请求编号从基址加一排到基址加三十三（`vfsif.h:41-73`），总数常量是三十四（`vfsif.h:75`）。判定宏 `IS_FS_RQ` 检查"除低八位外是否等于基址"（`vfsif.h:77`），这是粗筛：连基址前缀都不对的消息根本不是文件请求。

三个事务宏（`vfsif.h:79-81`）：取编号是按位与上十六个一，加编号是左移十六位再或上编号，删编号是带符号右移十六位。删编号用带符号移位是有意的：请求部分可能是负数（基址本身是 `0xA00`，本是正数，但回复码可能是负的错误码，同一套宏要同时服务请求与回复两条路）。

### 2.6 标志与特殊错误码（`vfsif.h:7-38`）

挂载标志两个：只读挂载、根文件系统挂载（`vfsif.h:8-9`）。查找控制标志两个：要求保留末尾符号链接不解析、要求附带完整用户凭证（`vfsif.h:12-18`）。能力标志三个：多线程、有窥视、六十四位（`vfsif.h:20-23`）。

特殊错误码三个，都是负三百开头：进入挂载点（负三百零一）、离开挂载点（负三百零二）、绝对符号链接（负三百零三）（`vfsif.h:26-28`）。它们不是失败，而是查找过程的重定向信号，详细语义在 `03-fsdriver-utility.md` 的查找章节展开，本篇只记录它们的存在与数值。

用户凭证结构（`vfsif.h:33-38`）含用户标识、组标识、附加组数量、附加组数组。查找请求在置了凭证标志时用授权携带它，否则只带用户标识与组标识两个数字。

### 2.7 回调表结构（`fsdriver.h:52-105`）

回调表是三十多个函数指针的集合，外加挂载后钩子与通用消息钩子。数量上它比三十一个请求多，因为有些回调被多个请求共享（读与块读共享读写族参数，删除文件与删除目录共享删除族参数），而查找回调不直接对应任何请求（它被查找适配器内部调用）。共享签名的几组请求用额外的调用标识参数区分：读族用读、写、窥视三值，删除族用删除文件、删除目录两值（`fsdriver.h:45-50`）。

节点描述结构（`fsdriver.h:9-16`）是六个字段：索引节点号、模式、大小、用户标识、组标识、设备号。挂载回复、新建回复、创建回复都复用这个形状。

数据抽象结构（`fsdriver.h:19-26`）是端点加联合体：远端调用者用授权标识，本地调用者用指针，外加一个仅用于完整性检查的总长度。目录项抽象结构（`fsdriver.h:29-36`）是通道加容量加偏移，配 staging 缓冲区。两者都在 `03-fsdriver-utility.md` 展开，本篇只记录它们的字段。

### 2.8 与 C 一千零一十三步的差异说明

本篇的 C 分析覆盖主循环与分发共约一百三十七行。Rust 实现与 C 的步骤差异只有两处，且都不是语义差异：

| 差异 | C 做法 | Rust 做法 | 分类 |
|------|--------|-----------|------|
| 查表方式 | 函数指针数组下标访问 | 枚举匹配分支 | 设计决策：用穷尽检查代替空指针检查，行为一致 |
| 异步回复 | 分发函数接受异步标志并分支发送 | 框架只描述回复内容，发送留在服务进程 | 已知缺口：多线程异步回复超出单线程框架范围，见第 3 章 |

## 3. Rust 设计决策

> 本章解释为什么这样设计。每个决策先给依据（第 1 章的概念或第 2 章的源码位置），再给替代方案与取舍。

### 3.1 请求编号做成枚举（依据：第 1.2 节、第 2.5 节）

C 用整数常量表示三十三个请求，类型系统看不出"一"和"三十四"的区别：前者是保留请求，后者根本不存在。Rust 用枚举 `RequestNumber` 把每个合法索引变成一个变体，非法索引在解码时就被拒绝。解码函数对零和大于三十三返回空，调用方把空映射成"功能未实现"，与 C 的空槽位行为一致。

替代方案是保留整数常量加一组范围检查函数。那样调用方每次都要记得检查，漏一次就是一次把非法请求送进分发的漏洞。枚举把"记得检查"变成"不解码就拿不到值"，非法状态在类型层面不可表达。

保留请求的取舍：头文件说获取节点请求应当删除，分发表也没有它。Rust 保留枚举变体但标记它没有分发槽位，而不是直接删掉。这样做的好处是解码索引一时得到的是一个有名字的"保留请求"，而不是匿名的"未知请求"，排错日志可读；行为上两者都回答功能未实现，与 C 一致。

### 3.2 事务编号做成独立类型（依据：第 1.2 节、第 2.5 节）

C 的三个事务宏是裸的位运算，分散在分发函数里。Rust 把它们收成 `TransactionId` 类型上的编解码函数：解码做算术右移（保留符号，与 C 的删编号宏一致），编码做左移加或。测试里用负错误码走一遍编解码，锁定"负数能活着回来"这个 C 语义。

### 3.3 标志做成新类型而不是裸整数（依据：第 2.6 节）

挂载标志、能力标志、查找标志在 C 里都是八进制整数掩码。Rust 给每组一个单字段结构，配命名常量与谓词方法。这样 `MountFlags` 的值永远传不到要 `CapabilityFlags` 的地方，C 里混用两组掩码的错误在编译期就被抓住。每组的值与 C 头文件逐位一致，注释里写明八进制原值以便对照。

### 3.4 回调表做成整体 trait（依据：第 1.3 节、第 1.7 节、第 2.7 节）

这是本篇最核心的设计决策。C 的回调表是三十多个可空函数指针，Rust 把它变成 `FsDriver` trait，三十多个方法各对应一个回调。必须实现的方法只有一个（挂载），其余都有默认体：返回结果的方法默认报功能未实现，纯通知的方法默认什么都不做。这完整保留了 C 的"空回调等于未实现或跳过"规则（`call.c` 里每个适配函数开头的空检查），只是把三十多处分散的空检查收成 trait 默认体，一处写明。

为什么不拆成四个小 trait（对照 Linux 的四组操作表）？第 1.7 节已经给了理由：消息路由只认编号，一个请求进来必须有唯一的归属。拆成小 trait 后，一个服务器可能实现了数据组却忘了命名空间组，编译器不会抱怨，运行时某个请求才突然报功能未实现。整体 trait 加默认体的方案里，"支持什么"一目了然：看实现里重写了哪些方法。

Redox 的对照：Redox 的 Scheme 特征也是整体 trait（open、read、write 等全在一组），理由相同：一个挂载点对应一个实现，拆分没有收益。不同之处在于路由键：Redox 用路径字符串，Minix3 用数字编号。数字编号路由更快更固定，但可读性差，所以 Rust 侧用枚举把编号翻译回名字，两全其美。

### 3.5 挂载三元组做成枚举（依据：第 1.4 节、第 2.1 节）

C 用三个独立变量记录挂载状态，理论上可以出现"已挂载为真但设备号没填"的矛盾组合。Rust 用 `MountState` 枚举：要么未挂载，要么挂载且同时携带设备号与根节点号。矛盾组合在类型层面不存在。服务器状态 `ServerState` 再把运行标志和挂载状态绑在一起，循环条件做成谓词方法，C 主循环里的复合条件有了唯一定义。

### 3.6 分类结果做成枚举（依据：第 1.5 节、第 2.2 节）

分发函数开头的三向分支变成 `Route` 枚举：旁路、未挂载拒绝、未知拒绝、可分发。旁路分支在类型上就不携带回复（`Handling::NoReply`），想给通知发回复的代码写不出来——编译器直接拒绝。这比注释"记得别回复"可靠得多。

分类函数 `classify` 把发送方端点做成参数而不是硬编码常量，测试可以传入任意端点验证"非虚拟文件系统服务来源一律旁路"。生产代码传入常量 `VFS_ENDPOINT`（数值一，与 `com.h` 一致）。

### 3.7 单线程假设写进文档而不是类型（依据：第 1.1 节）

用户态文件服务器是单线程事件循环：一次处理一条消息，不存在并发。本框架的类型（trait 方法拿可变借用）天然适配这个模型：同一时刻只有一个请求持有服务器的可变借用。但框架没有用线程标记在类型层面锁死单线程，因为那会堵死未来的多线程演进（能力位里本来就预留了多线程）。取舍是：文档明确声明单线程假设，类型保持中立，异步回复明确标为已知缺口。

### 3.8 空服务器作为协议测试对端（依据：第 2.2 节旁路与门禁）

`NullDriver` 只实现挂载，其余全用默认体。它存在的理由很实际：分类、门禁、挂载状态机这些框架逻辑，需要一个" server 实现没问题、纯测框架"的对端。没有它，框架测试就必须搭一个完整文件系统，问题定位会混在一起。这是测试替身（test double）思想的正常应用，不是多余抽象。

### 3.9 设计决策与替代方案汇总

| 决策 | 依据 | 替代方案 | 为何不选 |
|------|------|----------|----------|
| 请求编号用枚举 | 第 1.2 节、第 2.5 节 | 整数常量加检查函数 | 漏检查即漏洞；枚举让非法值不可表达 |
| 事务编号独立类型 | 第 1.2 节、第 2.5 节 | 裸位运算散落各处 | 语义（算术移位保符号）只应实现一次 |
| 三组标志各自新类型 | 第 2.6 节 | 裸整数掩码 | 混用两组掩码的错误编译期可抓 |
| 回调表用整体 trait | 第 1.3 节、第 1.7 节、第 2.7 节 | 拆四个小 trait | 路由只认编号，拆分掩盖缺实现 |
| 挂载状态用枚举 | 第 1.4 节、第 2.1 节 | 三个独立变量 | 矛盾组合可表达；枚举消除整类错误 |
| 分类结果用枚举 | 第 1.5 节、第 2.2 节 | 整数结果码加注释 | 旁路误发回复的错误类型层面可防 |

## 4. Rust 实现详解

> 本章解释代码如何落地。每个小节先一句话说清思路，再给出位置与关键行为。

### 4.1 协议模块（`os/libs/minix-fs/src/protocol.rs`）

常量 `FS_BASE`（`0xA00`）与 `VFS_ENDPOINT`（数值一）是全框架共享的唯二魔数，各自注释了 C 出处。`REQUEST_TABLE_SIZE`（三十四）只用于文档与断言，分发本身走枚举匹配，不需要数组。

`RequestNumber` 枚举三十三个变体，每个变体的判别值就是表索引。`from_index` 是常量函数，零与超界返回空；`is_dispatched` 唯独对获取节点请求返回假，对应分发表的空槽。`message_type` 方法算出不带事务编号的完整类型，供测试与未来的发送端使用。

`TransactionId` 是对十六位整数的包装。解码先取低十六位做编号，高位算术右移做请求部分；编码分回复与请求两路（位运算相同，名字不同以便阅读）。预过滤函数 `is_file_request` 实现判定宏的字面语义。

`LookupRedirect` 枚举把三个负三百开头的特殊码变成具名变体，配常量断言锁住数值（负三百零一到负三百零三），头文件漂移会在编译期暴露。

`FileNode` 是六字段结构，字段名是英文全称（索引节点号、模式、大小、属主、属组、设备），与 C 结构体的六个字段一一对应。构造函数要求六个字段全给，不存在"填一半"的中间态。

### 4.2 驱动模块（`os/libs/minix-fs/src/driver.rs`）

`FsDriver` trait 按五组组织方法（挂载组、数据组、命名空间组、元数组、块组），每组内部按请求编号顺序排列，每个方法注释写明对应的 C 回调名与到达它的请求。读写相关的方法用闭包传递数据（`&mut dyn FnMut(&[u8])`），而不是直接拿通道类型：trait 保持传输无关，授权通道的细节留在第 02 篇与第 03 篇的交界处。

`classify` 函数是门禁的实现：通知或外来发送方直接判旁路；解码索引；挂载请求或已挂载才看分发槽；保留请求与未知索引判未知。减法用回绕减法，与 C 注释"回绕是有意的"一致。

`handle_header` 把分类结果变成处理意见：旁路无回复，未挂载拒绝报无效参数，未知拒绝报功能未实现，可分发则把请求交还给调用方（调用方再进第 02 篇的适配器）。这个两段式不是多余：头部规则不需要服务器参与，提前处理让适配器只操心真正的请求。

`Server` 结构把状态与实现绑在一起，提供终止、记录挂载、记录卸载、是否继续四个操作。终止只清运行标志（发送取消由服务进程的接收原语完成，框架只描述状态变化）。记录挂载与记录卸载是常量函数，一次把设备号与根节点号同时写好，不存在只写一半的时机。

### 4.3 与 C 一千零一十三步的差异说明（实现侧）

第 2.8 节列的两处差异在实现侧的落点：枚举匹配覆盖了分发表的全部三十二个槽位加两个空位（保留与未知），编译器的穷尽检查保证没有漏掉的编号；异步发送没有实现，`handle_header` 只产出"回复什么"，不产出"怎么发送"，注释里标明这是已知缺口。

## 6. 过渡：从骨架到血肉

本篇搭好了文件服务器的骨架：消息从哪里来（虚拟文件系统服务），到哪里去（三十二个槽位之一或旁路），服务器处于什么状态（运行标志加挂载状态），什么时候下班（不再被要求营业并且已经卸载）。

但骨架还不会干活：挂载请求里的设备号与标签怎么取，读写请求里的位置与长度怎么验，创建请求里的点名字符怎么挡，这些"每个请求内部的翻译"还没讲。下一篇 `02-fsdriver-call.md` 逐个展开三十一个适配器：每种请求带什么字段、做什么校验、调哪个回调、回什么内容。

阅读建议：先读第 02 篇的挂载组（五个适配器），它把本篇的挂载门禁与状态更新连成完整闭环；再读数据组（六个适配器），它是读写路径的主干；命名空间组与元数组可以按需查阅。
