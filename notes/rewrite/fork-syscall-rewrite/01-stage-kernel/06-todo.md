## 1. 项目背景

**Minix-RS** 是一个把 Minix 3（微内核操作系统）的 C 代码**语义等价重写为 Rust** 的项目：

- **上游源码（ground truth）**：Minix 3 的 C 源码，位于 `minix3/` 目录，**只读不改**。
- **Rust 实现**：位于 `os/` 目录下的各 crate（`os/kernel` 内核、`os/arch` 架构层、`os/servers/vm` VM 服务等）。
- **重写原则**：不是逐行翻译（translation），而是**语义重写**（semantic rewrite）——保持外部行为、IPC 协议、生命周期语义与 Minix3 一致，但用 Rust 类型系统重新表达内部结构。

项目的关键约束（与本文档强相关）：
- **`#![no_std]` + boot 期无堆**：内核代码除 `#[cfg(test)]` 外不依赖标准库；且 kernel **boot 阶段堆分配器尚未建立**（注意：`no_std` ≠ 没有 allocator——no_std 环境可以自带分配器，这里的原因是 boot 期未建立），因此核心表必须用固定容量静态存储（`static [T; N]`）而不是 `Vec` / `Box`。这是本文档方案的核心动因之一，完整三层因果链见 §10.5。
- **执行模型分层**：用户态服务器是单线程事件循环；**内核是 SMP + BKL（Big Kernel Lock）**，跨 CPU 共享数据需要 `Atomic` / 锁，进程表的 `p_rts_flags` 在 Rust 侧是 `AtomicU32`。
- **文档体系**：`notes/rewrite/fork-syscall-rewrite/01-stage-kernel/` 下按「阶段 + 功能」组织 32+ 篇概念文档，每篇对应一组 Minix3 内核 C 源码 / Rust 实现。用**启动主线**串联整个内核启动流程（阶段 A–F）。

## 3. 06 现状与问题

### 3.1 现状

- **篇幅**：2192 行，远超 `01-stage-kernel` 的常规体量（多数文档 400–900 行；全目录最长为 `05-clock-interrupt-init.md` 2253 行，暂不在本次范围）。
- **结构**：Ch1 概念（§1.1–1.7）→ Ch2 C 源码分析（§2.0–2.9）→ Ch3 Rust 设计决策（§3.0–3.15）→ Ch4 实现详解（§4.0–4.8）→ Ch5 测试 → 附录 A libexec 详解 → Ch6 参见。
- **内容覆盖**：进程本质、CPU 四问、三类运行态实体、进程表/特权表/RTS 三件套、boot image、VM 鸡生蛋、阶段 C 执行节拍、`proc_init`、`arch_proc_reset`、boot 循环、`get_priv`/`set_sendto_bit`、`arch_boot_proc`、`arch_proc_init`、`libexec_load_elf`、`bsp_finish_booting`、KPriv 8 子结构、CapabilityTemplate、RTS 16 位、ProcKind/EntrySpec、CpuContextArch trait、FPU 演进、SMP 预留、错误处理、fork 对照、测试矩阵。

### 3.2 问题诊断

**问题 1：单个文档混入了太多概念（v2.1 修订：行数只是症状，概念混杂才是病根）。**

- **行数本身不是问题**——如果 06 只承载一个确实很难的独立概念，2000 行甚至更长都可接受。真正的问题是 06 同时承载了：进程本质教学、三件套存储、boot image、VM 鸡生蛋、运行时字段用法、FPU 演进、fork 对照、libexec 详解……**每个概念都没讲好，因为每个都没讲透就切换到了下一个**。
- 2192 行（约为其他文档的 2–3 倍）与信息密度不均（入门级概念与论文级细节混杂，如 CPU 断点续传 vs KPriv 子结构字段表/libexec 回调签名）都是概念混杂的**症状**。改造的验收对象是**概念边界**（A1），不是行数。

**问题 2：把「存储布局」和「运行时字段用法」揉在一篇里，职责越界。**

- 06 既讲了「`struct proc` 有哪些字段、进程表怎么存」（存储层），又展开了「字段在 fork/exec 里怎么改、RTS 怎么联动调度队列」（运行时用法）。
- 后者的正确归属是后续功能文档（17/11/12/22）——它们已经存在且内容覆盖完整。06 的展开是**重复讲述**，且把文档拉长。
- 这正是用户最核心的反馈：**「启动的过程遇到了 proc table，把所有字段的讲解全部融入到一篇文档中，这就有点过大从而难以讲好了。」**

**问题 3：内核「必须讲清楚 table 怎么存」这一点被淹没。**

- 用户指出：用户态程序存一个表可以用 `Vec::new()`，一句话带过；但内核 **no_std + boot 期零堆**，进程表、特权表怎么存（静态数组 / 指针数组 / 容量常量）是**硬约束驱动的设计决策**，必须讲清楚。
- 06 现有 Ch2/Ch3 确实覆盖了 `static [KProcess; N]` 等设计，但**没有以「存储」为主线组织**——存储决策散落在逐函数分析中，读者很难抓住「为什么是这种存储形态」的因果链。

### 3.3 一句话总结（v2 修订：主从关系锁死）

> **06 是「阶段 C 启动主线」文档：解释 Minix3 如何在阶段 C 建立第一个可运行的进程运行环境——先建立 proc/priv/RTS 等核心表的存储模型（怎么存、为什么这么存），再沿 `proc_init → boot image → ELF load → wakeup` 展示这些结构如何被初始化并最终交给后续运行时；字段按分组建立导航，运行时细节引用后续文档。** 篇幅预期 ~800–1000 行（**纯参考值，不作为 pass/fail 指标**——行数不是问题，概念边界才是，见 §9 A1）。

**主从关系**：阶段 C 启动主线是**第一主线**，存储模型是为理解启动而服务的**支撑**——但支撑部分（内核为什么这样存）必须讲透，不得浅尝辄止（见 §4.4 两条红线）。

## 4. 决策过程：为什么拆又为什么不拆

### 4.1 最初方案：拆成 5 篇（已否决）

在分析早期，对照 `02-stage-vm/` 的拆分模式（vmproc struct / vmproc table / acl 各一篇），曾考虑把 06 拆成：

- `06a-proc-table.md`（进程表）
- `06b-priv-table.md`（特权表）
- `06c-rts-bitmap.md`（RTS 位图）
- `06d-boot-image.md`（boot image）
- `06e-vm-elf-load.md`（VM ELF 加载）

**否决理由**：
1. **阶段 C 是一个完整主题**，不是三件独立数据结构的堆叠——它的主线是「清空 → 填充 → 唤醒」的**启动节拍**，拆分会把主线打散。
2. **后续功能文档已存在且覆盖完整**（11/12/17/22 等）。拆出 06a/06b/06c 会把「存储布局」和「运行时用法」**都各拆一遍**，反而增加文档间跳转成本，且与已有功能文档构成重复。
3. **拆分会破坏编号**：06 是启动主线上的固定锚点，下游文档（07/08/10/12 等）大量引用「06 §X.Y」；拆成 06a/06b… 会让所有交叉引用失效或歧义。

### 4.2 最终方案：不拆，瘦身 + 分组引用

**核心判断**：06 的「大」和「讲不好」不是因为它装了 6 个概念，而是因为它**把存储、设计、运行时三条线全部展开讲了一遍**。解法不是拆文档，而是**重划职责边界**：

| 层 | 谁负责 | 06 的职责 |
|----|--------|----------|
| **存储布局**（字段定义、容量、索引、共享策略、no_std 约束） | **06** | ✅ 本文档改造后重点 |
| **Rust 设计**（类型、trait、子结构分组） | **06 + 22** | 06 讲「存储形态」的设计决策；22 讲「权限语义」的设计 |
| **运行时字段用法**（fork 怎么改字段、enqueue 怎么用 p_nextready、IPC 怎么用 p_caller_q） | **17 / 11 / 12 / 22 / 19 / 20 / 21 / 23 / 24** | ❌ 06 只给引用 |
| **启动主线**（proc_init → boot 循环 → bsp_finish_booting） | **06 保留骨架** | ✅ 保留但不展开细节 |

**核心原则（用户原话，纳入正式需求）**：

> - 讲解 proc table，可以列出 `proc` struct 的整体布局，甚至列举所有字段，**但不展开整体讲解**，仅给出后续文档的引用。
> - 不讲解字段 ≠ 完全不讲解。**字段应该分组**，然后讲解**每个分组具体完成什么操作系统的语义**；具体完成细节归属到后续某个文档（以及 Rust 关于该语义、该分组如何设计）。
> - **priv 表同理。**

### 4.3 为什么「内核必须讲怎么存」是 06 存在的最大理由

用户的关键洞察（正式纳入需求）：

> 「`[]struct` 就是 table……但牵涉到在内核中如何存储，**std 下完全不用讲 `vec::new()` 就完事，内核必须讲清楚这个 table 怎么存**。」

对照表（06 必须写的存储决策 vs 用户态微不足道的等价物）：

| 内核存储决策 | 用户态等价 | 内核必要性 |
|-------------|-----------|-----------|
| `static [KProcess; NR_TASKS + NR_PROCS]` | `Vec::new()` | boot 期无堆分配器 → 必须静态数组 |
| `ppriv_addr: [Option<NonNull<KPriv>>; NR_PROCS]` | `HashMap<u32, &Priv>` | O(1) 索引 + 零堆 + 无 unsafe |
| `priv[NR_SYS_PROCS = 64]` 固定容量 | `Vec<Priv>` | 编译期容量已知 → `const fn new()` |
| `p_rts_flags: AtomicU32` | `u32` | SMP 跨 CPU 原子读 |
| `Endpoint(pub i32)` newtype | `type Endpoint = i32` | 跨 FFI 边界 + 类型安全 |
| `[T; N]` 用 `RTS_SLOT_FREE` 位表达「空」 | `Option<T>` 或 `Vec` | 零堆 + 无 Option 包装的静态数组 |

06 的 Ch2（或改造后的对应章节）必须把这些「为什么是这种存储形态」写清楚。

### 4.4 心智模型锁死：Stage C 是第一主线，存储是支撑（v2 新增）

**06 是「Stage C 的文档」，不是「proc/priv/RTS 的总文档」。** proc/priv/RTS 只是阶段 C 为了建立第一个可运行环境而操作的三类核心状态——不能写成四个主题的拼盘：

```
06：阶段 C —— 建立第一个可运行的进程运行环境
        │
        ├── 需要什么数据结构？          → proc table / priv table / RTS / boot image
        ├── 这些结构如何组织、为什么？    → 存储因果链（Ch2/Ch3 讲透）
        └── 如何用它们完成启动节拍？      → 清空 → 填充 → 加载 → 唤醒（Ch1 §1.5 + Ch4）
```

**两条红线**（防摆向任一极端）：

1. **不得让字段/结构喧宾夺主**：字段分组是导航，启动节拍（清空→填充→加载→唤醒）是叙事主线——读者读完应能独立回答「阶段 C 做了什么、这些表为什么长这样」。
2. **不得把存储讲浅**：用户核心洞察「内核必须讲清楚这个 table 怎么存」依然成立——存储因果链在 Ch2/Ch3 内**完整论证**（这是 06 区别于用户态文档的存在理由），只是不展开运行时字段用法。

```markdown
#### 2.1.1 标识组：进程的身份

字段：`p_nr` / `p_endpoint` / `p_name` / `p_magic`（以 proc.h 为准）

**OS 语义**：内核需要一个稳定、O(1) 可寻址的标识把「进程」与「系统消息、调度、信号」关联起来。

**C 中的结构关系**：
- `p_nr`：slot 索引偏移（负数=内核 task，非负=用户进程），`proc_addr(n)` 宏用数组下标 O(1) 定位——「身份即索引」，这是 C 静态数组方案的基石。

- `p_magic`：slot 完整性哨兵（如有，待对照 proc.h 确认）。

**阶段 C 中的作用**：`proc_init` 清空时重排 p_nr；boot 循环按 p_nr 落槽。

**运行时细节**（哪些操作会改这些字段、endpoint 代际怎么递增）：详见 [17-syscall-process.md §1.1–1.2](./17-syscall-process.md)。

```

**C 结构**：`p_nr: int` + `p_endpoint: int`（裸 int，二者可混淆）。

**Rust 表达**：`ProcNr(i32)`、`Endpoint(i32)` 两个 newtype（`repr(transparent)`），类型层面无法混淆。

**特权表「存储」必须单独讲的部分**（§2.2.0）：

- **分治策略**：进程表有 `NR_PROCS`（数百）个槽，但特权表只有 `NR_SYS_PROCS = 64` 个槽。只有系统进程需要独立特权，普通用户进程**共享单一 `USER_PRIV`**。如果把 31 字段平铺到每个进程，内存浪费巨大。`p_priv` 指针（进程表）→ 所属特权槽。
- **双表索引结构**：`priv[NR_SYS_PROCS]`（实体数组）+ `ppriv_addr[NR_PROCS]`（指针数组，`priv_addr(i) = ppriv_addr[i]`），进程号 → O(1) 找特权槽。两表长度不同、以指针数组桥接。
- **零堆的存储形态**（C 侧）：`priv[NR_SYS_PROCS]` 静态数组 + `ppriv_addr[NR_PROCS]` 指针数组在编译期固定大小。Rust 端 `PrivTable` 的具体表达（`[KPriv; NR_SYS_PROCS]` + `const fn new()`）属 Ch3 §3.2，本节（Ch2）只论证「为什么必须静态数组」。**这是「内核必须讲怎么存」的特权侧体现。**
- **boot 期静态分配 vs 运行时动态分配**：boot 期只为内核 task + RS + VM 分配静态特权（`NR_STATIC_PRIV_IDS` 段）；运行时 `get_priv()` 从动态段（`[NR_BOOT_PROCS.. NR_SYS_PROCS)`）分配。

### 6.3 RTS 位图存储（可并入 6.1 生命周期控制组，或独立一节）

- **为什么位图而非枚举**：进程可同时因多个原因不可运行（无特权 + 等 VM 建页表 + 被停止），位图支持多原因叠加。
- **16 位全集全部列出**（`SLOT_FREE`/`NO_PRIV`/`NO_QUANTUM`/`VMINHIBIT`/`BOOTINHIBIT`/`PROC_STOP`/`SENDING`/`RECEIVING`/`SIGNALED`/`SIG_PENDING`/`P_STOP`/`NO_ENDPOINT`/`PAGEFAULT`/`VMREQUEST`/`VMREQTARGET`/`PREEMPTED`）。
- **不变量**：`p_rts_flags == 0 ⟺ runnable`；`rts_set`/`rts_unset` 联动 enqueue/dequeue（06 只讲不变量，联动细节 → 11）。
- **存储决策（v2 修订：现存已验证设计，非预设）**：`RtsFlags` 为 `AtomicU32` + bitflags 宏（已实现于 [os/kernel/src/proc_table.rs](file:///os/kernel/src/proc_table.rs) / [os/kernel/src/sched.rs](file:///os/kernel/src/sched.rs)）。**并发协议论据必须写实，分三段**：

  1. **概念结论**：BKL 串行化所有写者；`AtomicU32` 支撑跨 CPU 无锁读。
  2. **具体代码证据**（写侧）：
     - `p.p_rts_flags.set(RtsFlagsBits::NO_QUANTUM)` — [sched.rs:366](file:///os/kernel/src/sched.rs#L366)
     - `p.p_rts_flags.clear(RtsFlagsBits::NO_QUANTUM)` — [sched.rs:408](file:///os/kernel/src/sched.rs#L408)
     - `table.rts_set(ProcNr(0), RtsFlagsBits::PROC_STOP)` — [sched.rs:503](file:///os/kernel/src/sched.rs#L503)
     这些都通过 `rts_set`/`rts_unset` 封装（[sched.rs:329-410](file:///os/kernel/src/sched.rs#L329-L410)），被调度器在持 BKL 期间调用。
  3. **代码中的实际对象**（无锁读模式参考）：**注意**——`p_rts_flags` 本身在代码里**不直接**暴露 `load(Relaxed)`（bitflags 宏的 `.is_set()` 包装了 load）。同表上的 `p_nextready` 才是显式 `AtomicI32` + `load(Ordering::Relaxed)` 模式（[sched.rs:153, 167](file:///os/kernel/src/sched.rs#L153, #L167)），用于调度器跨 CPU 扫描就绪队列（idle-steal 路径）。**RTS 自身的「跨 CPU 读」是通过 bitflags API（`.is_set()`）间接表达**，调用方通常在持 BKL 内使用，因此 `Relaxed` 序不是 RTS 字段本身的硬约束，而是 `p_nextready`（队列链接）的硬约束。
  4. **结论**：BKL 串行化与 Atomic 是两个维度——前者管写互斥（防止并发修改 `p_rts_flags`），后者管**同表相邻字段**（如 `p_nextready`）的读可见性/借用模型。RTS 字段本身在持 BKL 临界区内使用 `AtomicU32` 是防御性设计（编译期杜绝裸 `u32`，并为 `SyncUnsafeCell` 包裹的全局 `PROC_TABLE` 提供安全读侧）。**不得写成「SMP → 所以 Atomic」的口号**——必须区分「写侧 BKL 串行化」与「读侧无锁 / 跨字段链接原子性」两个不同维度。
- **boot 期涉及的 6 位**（阶段 C 视角）：`SLOT_FREE`/`NO_PRIV`/`NO_QUANTUM`/`VMINHIBIT`/`BOOTINHIBIT`/`PROC_STOP`，说明每位的设置时机。

### 6.4 boot image 存储（保留精简版）

- `image[]`（`NR_BOOT_PROCS = NR_TASKS + NR_BOOT_MODULES = 5 + 12 = 17`）是编译时硬编码清单，**不是 ELF**，编译进 kernel 二进制。
- proc 号编号表（DS=6, RS=2, PM=0, …）——boot image 顺序 ≠ proc 号顺序，决定槽位落点。Rust 侧 `BOOT_MODULE_PROC_NRS[i]`。

- 详情指向 01 §1.5、08 §1.3、09 §1.2。

## 10. 约束与注意事项

1. **ground truth 优先**：字段名、容量、数值以 `minix3/minix/kernel/proc.h`、`priv.h`、`param.h`、`com.h` 为准，不得凭记忆写。行为不确定的标注「待确认」。
2. **文档不得出现进度式表述**（已实现/待实现/✅❌🚧）——教学文档只描述系统行为（§2.11 风格约束）。
3. **引用必须是后续文档真实存在的小节**：先确认目标小节号再写「详见」。后续文档引用以相对路径（`NN-xxx.md`）格式，不写绝对路径。
4. **保持阶段 C 锚点地位**：06 是 07/08/10/12 等文档引用的「阶段 C」入口。章节编号（Ch1/Ch2…换层后）可调整，但文档定位不变——它是「Stage C 主线 + 存储支撑」，不是「字段百科」。
5. **存储因果链必须三层展开**（v2 修订）：第一层，Minix 模型本身是编译期固定容量（`NR_PROCS`/`NR_SYS_PROCS` 是常量）；第二层，kernel **boot 阶段堆分配器尚未建立**（注意 `no_std` ≠ 无 allocator——是 boot 期未建立，不得写「no_std 所以必须静态数组」）；第三层，因此 Rust 表达 `[KProcess; N]` / `[KPriv; 64]` 是自然选择。所有「为什么这么存」的论证落到这三层，不得写成用户态可用的泛泛理由。
6. **SMP/BKL**：进程表、RTS 位图涉及多 CPU 时，讲清 `Atomic`/BKL 保护；禁止在跨 CPU 场景使用 `Rc`/`RefCell` 的说法。**并发协议论据以真实代码为准**（v2 修订）：BKL 串行化所有写；Atomic 支撑跨 CPU 无锁读（如调度扫描 `load(Relaxed)`）。`p_nextready: AtomicI32`、`RtsFlags: AtomicU32` 是**现存已验证设计**（proc_table.rs/sched.rs），可直接写，但「为什么」必须落到真实访问协议，不得写成「SMP → 所以 Atomic」的口号。
7. **不新增文档**：本次重构**不新建** 06a/06b/… 文档；所有内容收敛在 06 单文档内，或下放**到已有**的后续文档。
8. **文风**：中文，面向「理解 Minix3 微内核基本结构」的开发者；图表必要才用；代码块注释用中文。
9. **主线与存储并重**（v2 新增）：本次改造的重心是「分组 + 下放」，但**不得把阶段 C 启动主线砍薄**——Ch1 §1.5 执行节拍与 Ch4 的 清空→填充→加载→唤醒 主流程必须完整保留（验收 A15）；同时不得让字段分组喧宾夺主（验收 A14）。06 的最终质量标准：**读者能从 06 独立回答「阶段 C 做什么、为什么需要 proc/priv/RTS、这些结构怎么存、boot image 如何进入 proc table、最终如何形成第一个可运行环境」**。
