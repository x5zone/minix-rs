# 16 — 进程表快照：先把三家的表拿过来，再建索引

> **分类**: 进程信息之首 / 跨服务整表拷贝
> **源码**: `minix3/minix/servers/mib/proc.c:1-40`（三张表与四个常量）、`:46-137`（拿表的函数 `update_tables`）、`:143-158`（按进程号查槽的函数 `get_mslot`）、`:163-172`（滴答换算时间的函数 `ticks_to_timeval`）、`:185-216`（写等待原因文字的函数 `fill_wmesg`）
> **说明**: 进程信息五篇的第一篇。系统信息服务自己不存任何进程信息，每次有人问，先把内核、进程管理、文件服务三家的整张表拷贝过来，再回答。本篇讲拷贝时的三条规矩、进程号怎么查、滴答数怎么换算成秒、等待原因那句话怎么写。表里每一行的具体含义归三家管，本篇不管。

## 1 概念

### 1.1 目标读者与前置知识

面向要实现 17 到 20 的人。前置知识：06（拷贝出去时按长度截断）、10（查询函数在分发里是终点）。"拿表"就是跨服务整表拷贝：一次把别家服务内存里的整张进程表复制过来。"失败标记"就是拿失败之后记下来，后面不再试的意思，下面会展开讲。

### 1.2 本章不讲什么

- 表里每一行的含义——内核、进程管理、文件服务各管各的内存布局，跨阶段的约定，本篇只拿表，不解释表的内容。17 到 20 用到哪一行再引用对方服务的文档。
- 轻量线程、第二套进程格式、进程参数、Minix 进程快照四种输出格式——17、18、19、20。
- 拷贝出去——06。

### 1.3 为什么拿表要有规矩

系统信息服务回答任何进程问题之前，都要先拿到三张表：内核的进程表（有调度状态和寄存器）、进程管理的进程表（有进程号、用户号、状态）、文件服务的轻量表（文件相关的轻量行）。三张表一次拿过来要几百 KB（`proc.c:62-64` 注释写了大小），拿的动作是跨服务的消息调用，并不便宜。所以拿表有三条规矩，每一条都是拿一次代价高换来的：

第一，同一个时钟滴答里最多拿一次。用户能忍受一 tick 的旧数据（`:60-69`），服务就用缓存的数据回答，不重复拿。

第二，拿失败就记下来，后面永远不再试（`:53-58`，注释原话是"基本不可能自己好"）。这个决定看起来狠，其实是算过账的：拿表失败说明对方服务出了问题，重试一次又要花几百 KB 的拷贝，而对方自己好的可能性极小。服务宁可每次都报上次那个错，也不再重复拿。注意这个判断写进了代码，不是写在运维手册里：错了就是错了，不再指望它自己好。

第三，拿之前先把"已失效"记下来，再开始拿（`:72`）。这样拿的过程中任何一步失败，表都停在失效状态，不会有人读到半新半旧的表。

三张表拿回来，还要建一个按进程号查槽位的哈希索引（`:121-134`）。槽位数是表大小的四分之一（注释说这是"期望的在用进程数"，`:33`）。进程号小于等于零的不进索引（内核任务没有进程号）。冲突的用链条连起来。按进程号查槽的函数就顺着链条比进程号（`:152-157`）。这个思路和 NetBSD 里按进程找槽的函数一样，注释没写，但行为对得上。

### 1.4 小结

拿表有三条规矩：同一个滴答里不重复拿，拿失败就记下来不再试，拿之前先记失效。表拿回来之后建一个进程号索引，槽位数取表大小的四分之一。滴答数换算成秒、等待原因写成一句话，是后面两节的事。表的内容归三家管，17 到 20 只管把拿到的行翻译成输出格式。

## 2 C 源码分析

### 2.1 三张表与四个常量（`proc.c:18-39`）

| 符号 | 位置 | 值和形状 | 说明 |
|------|------|------|------|
| 内核表 | `:18` | 进程数组，长度是内核任务数加进程数 | 内核的全表，连内核任务也在里面 |
| 进程管理表 | `:19` | 进程管理结构数组，长度是进程数 | 进程管理服务的那张表 |
| 文件轻表 | `:20` | 轻量文件结构数组，长度是进程数 | 文件服务的轻量行 |
| 余量 | `:31` | 8 | 分两步读时的预留（`:22-30` 注释：先问大小再拿数据，两步之间可能有新进程出生，多留八个位置） |
| 哈希槽数 | `:33` | 进程数除以四 | 期望的在用进程数 |
| 找不到标记 | `:34` | 负一 | 查不到这个进程号 |
| 上次拿表的时间和有效标记 | `:38-39` | 滴答数和真 | 节流用的钟加上面的失败标记 |

进程总数是构建配置（`config.h:31`），本篇不固定具体数字——哈希槽位数用参数算，§4 会讲。

### 2.2 拿表的函数（`proc.c:46-137`）

| 步骤 | 位置 | 行为 |
|------|------|------|
| 看失败标记 | `:57-58` | 以前失败过，直接返回失败 |
| 看时间 | `:66-69` | 和上次拿表是同一个滴答，直接用缓存（第一次拿表除外） |
| 先记失效 | `:72` | 把有效标记先置成假再开始拿，下面任何一步失败都会停在失效 |
| 拿内核表 | `:75-87` | 调系统调用拿全表，逐行检查魔数 `PMAGIC(0xC0FFEE1，const.h:164)` |
| 拿进程管理表 | `:90-103` | 调系统信息接口拿表，逐行检查魔数 `MP_MAGIC(0xC0FFEE0，mproc.h:106)` |
| 拿文件轻表 | `:106-112` | 调系统信息接口拿轻表（轻量行没有魔数字段，所以不检查） |
| 记有效 | `:114-115` | 有效标记置真，记下当前滴答 |
| 建索引 | `:121-134` | 槽清零，只有在用且进程号大于零的才连进链条（从头插入，`:131-132`） |

魔数是每行开头的一个固定标记，用来检查这一行是不是有效数据。内核表和进程管理表的每一行都有，文件轻表的行没有，所以第三步不检查。

源码里有一处待办（`:119`）："建索引的时机是否可以推迟到要用的时候"，如实记下来。这不是本篇的缺口（索引已经建了），是优化方向的讨论。

### 2.3 按进程号查槽（`proc.c:143-158`）

进程号小于等于零（零是内核，调用的人自己处理，`:148`）直接返回找不到标记。剩下的算出槽位，顺着链条比对进程号，找到返回槽号，找不到返回找不到标记。

### 2.4 滴答换算成秒和微秒（`proc.c:163-172`）

秒等于滴答数除以频率，微秒等于余数乘一百万再除以频率（中间用六十四位算，`:171`）。频率从系统调用拿，本篇只规定"拿到频率之后怎么算"，不规定"频率从哪来"。

### 2.5 写等待原因的文字（`proc.c:185-216`）

三种特殊端点直接写名字（任意端点、自己、无端点，`:191-200`）。剩下的从端点号算出槽位（`:202`）：内核任务的槽一直有效，普通进程的槽要看是不是在用（`:203-204`），名字从内核表里那一行的名字字段拿（`:205`），拿不到就空着。有名字就按"名字加括号"的格式写（直接通信，`:210-212`），没名字就按端点号写（`:213-215`）。三个特殊端点的值是相对端点算出来的（`endpoint.h:54-56`），本篇不固定具体数字。

## 3 Rust 设计决策

| # | 决策 | C 做法 | Rust 做法 | 为什么 |
|---|------|--------|-----------|--------|
| D1 | 拿表规矩变成枚举 | 一串判断加全局标记位 | 三种拿表结论的枚举（失败过不再试、本滴答用缓存、现在就拿，`os/servers/mib/src/proc/tables.rs`）加一个判断函数 | "失败过、用缓存、拿"三种结论就是本篇的全部规矩。枚举让调用的人必须把三种都处理，漏掉失败标记那个分支编译不过 |
| D2 | 配置数字变成参数 | 构建宏 | 哈希槽数函数取进程总数做参数（`tables.rs`） | 进程总数是构建配置，可以调。把具体数字写死（比如 256）是编造可移植性 |
| D3 | 链条查找变成纯函数 | 全局数组加指针 | 切片版本的链条查找（`tables.rs`） | 指针链是内存管理的实现细节。"算槽位、顺链条、比进程号"这个逻辑本身是纯计算，可以单独测。链条过期指向数组外面时返回找不到，而不是崩溃 |
| D4 | 特殊端点的值不变枚举 | 直接用宏值比 | 四种端点情况的枚举加调用的人自己比值（`tables.rs`） | 三个特殊端点的值是相对端点算出来的，端点编号规则变了就全错。比对的逻辑值得测，具体的值不值得固定 |

替代方案及否决：把三张表的内存布局直接复制——否决。布局归三家管，复刻就是越界。17 到 20 用到哪一行就去引用对方服务的文档。

和别的操作系统对照着看：Linux 的进程信息是现查现算的（读 `/proc` 时去进程表里找），NetBSD 是系统调用里填快照。Minix 的做法是第三种：整表拷贝加缓存。整表拷贝一次贵，但拷贝完之后十个查询都能用，平均到每个查询就便宜了。Redox 的进程方案（`proc:`）走的是按路径查单个进程的路子，和 Minix 整表拷贝正好是两个极端：Redox 省内存，Minix 省重复查询。本篇的 Rust 设计站在 Minix 这一侧：拿表的规矩（什么时候拿、什么时候不拿、什么时候放弃）才是要保留的语义，表存在哪、怎么存都可以换。

## 4 实现详解

### 4.1 模块结构

```
os/servers/mib/src/proc/
├── mod.rs    — 重导出
└── tables.rs — 本篇：找不到标记、余量、哈希槽数、两个魔数、魔数检查、

                 链条查找、滴答换算、端点分支加括号规则
```

### 4.2 核心符号表

| 符号 | 来源 | Rust 位置 | 行为 |
|------|------|-----------|------|
| 三张表和四个常量 | `proc.c:18-39` | `tables.rs` 头部 | 余量 8、找不到是负一、槽数取参 |
| 魔数 | `const.h:164` 加 `mproc.h:106` | 魔数常量加检查函数 | 整表逐行检查 |
| 拿表规矩 | `proc.c:53-72` | 判断函数 | 死了、用缓存、拿 |
| 拿表顺序 | `proc.c:74-113` | 顺序常量 | 内核、进程管理、文件轻表 |
| 哈希 | `proc.c:121-134,143-158` | 槽位函数加链条查找 | 取模、顺链条 |
| 换算 | `proc.c:163-172` | 滴答换算函数 | 秒和微秒 |
| 写等待文字 | `proc.c:185-216` | 端点分支加括号规则 | 四种分支加括号 |

### 4.3 不变量

| 不变量 | 谁保证 | 证据 |
|--------|------|------|
| 失败过就不再试 | 判断函数先看失败标记 | `proc.c:57-58` |
| 同一滴答用缓存 | 缓存分支 | `proc.c:68-69` |
| 一行坏整表坏 | 逐行魔数检查（调用的人负责调） | `proc.c:81-87,97-103` |
| 过期链条返回找不到 | 越界检查 | 防御性的：C 用全局数组不会遇到，Rust 用切片要守住 |

### 4.4 和 C 不一样的地方

§2 有五节，§4 是一个模块：拿表的执行动作、读时钟、表布局按 §1.2 移交出去。过期链条的防御是切片建模顺带的好处（C 用全局数组走不到这条路，合法输入下两边结果一样）。类别：边界移交加建模附带的好处，已经声明。
