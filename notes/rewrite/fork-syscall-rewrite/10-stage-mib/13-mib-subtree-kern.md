# 13 — 内核通用子树：操作系统的自我介绍、十个现场计算的查询和一棵占位子树

> **分类**: 子系统子树 / 内核通用查询
> **源码**: `minix3/minix/servers/mib/kern.c`（全文 508 行）
> **说明**: 第一棵完整的函数子树：两个带检查函数的可写节点、十个现场计算的查询函数、四十五个填好值的表项，以及一棵假装支持 System V 进程间通信、实则等真正服务来接管的占位子树。三十九个空着的编号位置不是没写完，是写进数据的排除约定。

## 1 概念

### 1.1 目标读者与前置知识

面向第一次实现系统信息查询处理函数的人。这是三棵子系统子树里的第一棵，后面的 14（虚拟内存与硬件）、15（Minix 扩展）照同一个写法做，所以本篇会把写法本身讲透：表是什么形状，函数节点和常量节点怎么分工，向别的服务要数据的代码为什么先不写。

前置知识：03（节点有哪几种形状）、09（普通数据节点怎么读写，本篇的函数节点是它的对照）、10（函数节点在分发里是终点，走到就没有下一层了）、12（远端挂载能把一棵子树整个覆盖，本篇的占位子树就是等着被覆盖的那个例子）。

系统信息查询是什么不需要预习：把它理解成"按名字读写系统信息"。比如用户在终端里敲 `sysctl kern.ostype`，想知道操作系统叫什么名字，答案从本篇的表里来。敲 `sysctl kern.cp_time`，想看每个处理器花了多少时间在用户态和内核态，答案由本篇的函数现场算出来。

### 1.2 本章不讲什么

- 进程相关的三个查询（进程快照、进程参数、轻量线程列表）——那是 17、18、19 的事，本篇的表里只给它们登记三个名字，指向那三篇。
- 向别的服务要数据到底怎么执行（怎么向内核要时钟频率、怎么向进程管理服务要根设备名、怎么向文件服务要驱动表）——那是向别的服务要数据的代码的事，本篇只写"拿到数据之后怎么算"的那一半。
- 另外两棵子树——14、15。

### 1.3 操作系统的自我介绍：三类节点

打开终端敲 `sysctl kern.ostype`，回车，屏幕上出现 `Minix3`。这短短一行背后，是内核通用子树在回答问题。这棵子树的节点分三类。下面逐个讲，后面两棵子树的每一行，都能按这三类对应上。

**第一类是常量叶子。** 操作系统叫什么名字、版本号是多少、同时最多跑多少个进程、一次系统调用最多能带多少个向量——这些数字在编译的时候就定了，或者在构建系统里写死了，运行时不会变。读它们不需要计算，查表返回就行。表里四十五个已填位置里的大多数是这种节点。其中四个可写（主机名、域名、主机标识、实时钟偏移），两个带检查函数（安全级别、进程创建失败时的等待时间），其余只读。

**第二类是函数节点。** 有些问题不能靠查表回答，因为答案每一秒都在变：当前时钟频率折算成微秒是多少、系统启动了多久、每个处理器的各类时间花了多少、有多少驱动在运行、控制台设备号是多少。这些问题必须请求到了才现场计算：请求到了，函数才去问内核或者别的服务要原始数据，算完返回。本篇有十个这样的函数。

**第三类是占位子树。** `kern.ipc` 下面挂着四个节点，号称能回答 System V 风格的进程间通信信息。但它的查询函数永远返回"不支持"。这不是偷懒，是占位：真正的进程间通信服务启动之后，会用远端挂载把整棵占位子树覆盖掉（12 讲的覆盖机制），以后凡是问到 `kern.ipc` 的请求都转交给真正的服务。在服务上线之前，占位子树保证"问了有回答"（回答是"不支持"，而不是"没有这个节点"）。带着"等真正的服务来接管"往下读，12 的挂载逻辑会好理解得多。

还有三十九个空着的编号位置。NetBSD 传下来的编号一共八十四个位置，Minix 只实现了四十五格，剩下三十九个在源码里是注释（"还没实现"、"已经废弃"、"和我们的设备节点方案不兼容"）。本篇把这三十九个编号写成一张清单：问到空位置，查找直接失败，返回"没有这个节点"，而不是"以后再说"。空位置是约定，不是没写完。后人想启用一个位置，必须先从清单里删掉它，表和清单互相排斥，启用了不该启用的（比如把明确不兼容的位置当成能实现）测试会直接变红。

### 1.4 和别的操作系统对照着看

NetBSD 是这套编号的来源：`kern.ostype`、`kern.hostname`、`kern.cp_time` 这些名字和编号都从 NetBSD 的手册页抄来，行为也尽量对齐（比如进程创建等待时间的取值范围直接写着"NetBSD 的规则"）。Linux 走的是另一条路：`/proc/sys/kernel/` 下的文件树做读写，`sysctl` 系统调用后来被弱化，`sysctl` 命令行工具变成读写 `/proc/sys` 文件的壳。名字不同，形状相通：都是"按层级名字读写内核参数"。

Redox 的做法值得多看一眼，因为它和本项目的思路最接近。Redox 把系统信息做成系统方案：用户态程序打开系统方案下的路径读数据，每个方案实现统一的方案接口，路径分发、权限检查、数据生成分层。它的核心分层思想和本篇的 Rust 设计是同一个：**分发只管找地方，计算只管纯逻辑，向别的服务要数据是独立的一块代码**。本篇把"要数据"（向内核和别的服务要原始数据）和"算"（拿到数据之后怎么算、怎么截断、怎么选模式）拆开，算的那一半先写成纯函数，要数据的那一半等后续实现。这正是 Redox 方案接口把"路径语义"和"数据来源"分开的思路在系统信息树上的应用。

### 1.5 小结

回头看，这棵子树只有四种东西。查表返回的常量叶子，其中四个可写，两个带检查函数。现场计算的函数节点，一共十个。永远回答不支持的占位子树，它在等真正的服务来接管。以及三十九个空着的位置，问到就是没有这个节点，空位置是约定，不是没写完。下一棵子树照这个顺序数：先数清有几种东西，再看每种东西怎么读写。

## 2 C 源码分析

### 2.1 两个带检查函数的可写节点

表里只有两个节点写了检查函数，它们长得很像，但规则完全相反。

安全级别（`mib_kern_securelvl`，`kern.c:17-30`）的规则只有一句话：**新值不许比旧值小**。初始值是负一，第一次写零可以通过，写完零再想写回负一就不行。注释直接承认：这是假实现，真正的安全级别支持还没做（`kern.c:26-28` 的注释原话加待办事项）。只升不降的用意不难理解：安全级别是系统的自我约束，允许运行时调高（收紧），不允许调低（放松），否则任何能写这个节点的程序都能先把锁打开再干坏事。实现是假的，方向是对的。

进程创建等待时间（`mib_kern_forkfsleep`，`kern.c:208-217`）的规则也是一句话：**零到两万毫秒之间**。上限两万来自最大睡眠二十（`sys/param.h:447`），乘一千换算成毫秒，注释注明"NetBSD 的规则"。语义是：进程创建因为数量到顶失败时，父亲睡这么多毫秒再重试。零表示不睡，两万表示最多睡二十秒。超出范围的写直接拒绝。

### 2.2 十个现场计算的查询函数

下表按源码顺序列出十个函数。每个函数都遵循同一个形状：向某个服务要原始数据，算一下，通过拷贝原语返回。读表时注意"输入源"这一列，它标的是数据从哪来，这正是 Rust 侧要拆出去的那一半。

| 函数 | 位置 | 输入源 | 关键行为 |
|------|------|--------|-----------|
| 时钟参数 | `kern.c:36-58` | 内核时钟频率 | 微秒节拍等于一百万除以频率，四项频率回显同一个值。每节拍能校正的微秒数直接照填节拍数（注释写着"我觉得"，外加一个问内核的待办，`:52-55`） |
| 性能分析 | `kern.c:64-71` | 无 | 永远返回不支持（Minix 有自己独立的性能分析接口，这是有效的约定，不是没写完） |
| 硬时钟滴答 | `kern.c:77-90` | 内核滴答计数 | 单调递增的滴答数就是开机时长（注释 `:83-86` 把"硬件时钟滴答"和"单调时钟滴答"是同一回事讲清楚了） |
| 根设备 | `kern.c:96-114` | 进程管理服务的根设备名环境变量 | 问不到返回参数错误。名字按缓冲区长度减一截断并补零（`:111`）。返回长度含结尾零 |
| 处理器衰减值 | `kern.c:120-129` | 调度器的衰减值 | 直接拷贝一个整数 |
| 处理器时间 | `kern.c:136-187` | 内核的每处理器滴答 | 名字超一层返回参数错误。带处理器号查单个，不带则按接收区大小决定求和还是逐个返回（见下） |
| 控制台设备 | `kern.c:193-203` | 主次设备号合成 | 直接合成设备号返回。注释说不支持三十二位旧请求，但代码里并没有长度检查（注释和代码的细微出入，见 §4.4） |
| 驱动列表 | `kern.c:222-281` | 文件服务的驱动映射表 | 问不到返回参数错误。只列运行中的。伪终端驱动在需要时多列一行别名（见下） |
| 启动时间 | `kern.c:287-299` | 内核开机时间 | 问不到返回参数错误。时间值结构直接拷贝 |
| 进程间通信信息 | `kern.c:306-316` | 无 | 名字不是一层返回参数错误，否则返回不支持（占位子树：等真正的服务覆盖） |

其中三处值得展开讲。

**处理器时间有三种返回形状。** 调用的人可以在名字后面跟一个处理器号（比如"零号处理器的各类时间"），也可以不跟。不跟的时候，函数看接收缓冲区的大小决定：没给缓冲区（只问长度），回答"求和结果的长度"。给了缓冲区，而且长度恰好装得下一份，返回所有处理器的总和。给了更大的缓冲区，逐个处理器依次写入，返回总字节数。这个看大小决定的逻辑在 Rust 侧被提炼成三种情况的枚举（§3、§4），测试把三种形状各执行一遍。

**驱动列表里藏着一个兼容性别名。** NetBSD 的用户态工具认准伪终端驱动叫 `pts`，Minix 的驱动标签不一定叫这个。代码里有一段专门处理：如果伪终端驱动在运行但名字不是 `pts`，就在列表最前面加一行：名字写 `pts`，块设备主号写负一，字符设备主号写真号（`kern.c:246-255`）。块主号负一的意思是"这行是别名，没有对应的块设备"。读到这种兼容性补丁很正常：系统信息树的消费者是现成的用户态工具，树的一端连着历史，迁就历史是它该做的。

**根设备名字的截断只有一行，但值得细读。** `name[MIN(vallen, sizeof(name) - 1)] = '\0'`（`:111`）：进程管理服务说名字有多长就信多长，但绝不超过自己的缓冲区减一，然后亲手补一个零。返回值是名字长度加一，把结尾零也算进长度。调用的人按这个长度分配缓冲区，下次一定装得下。这就是 01 篇讲的"收尾换算"在单个函数里的样子：长度语义是调用的人和服务之间的约定，差一个字节就会错。

### 2.3 数据表：四十五个已填位置

内核通用表（`kern.c:332-498`）按编号顺序摆了四十五个位置。按形状数一遍：操作系统三个字符串（类型、发行版、版本，值归构建系统）、构建期整数（一批最大值和特性开关，值归头文件里的宏）、四个可写（主机名、域名两个字符串，主机标识、实时钟偏移两个整数，主机标识带十六进制显示标志）、检查函数双星（安全级别初值负一、等待时间初值零）、函数节点（上表十个，再加三个指向进程信息三篇的登记节点）、占位子树（`kern.ipc` 一棵，`kern.c:318-329`：查询函数加三个常数零）。

三个登记节点（进程快照、进程参数、轻量线程列表）值得单独说一句：它们登记在本篇的表里，但函数体在 `proc.c`，行为在 17、18、19。本篇只认"表里有这三个名字"，不讲它们怎么算。这是按函数清单切文档的自然结果：表按编号归属，行为按源码文件归属。

### 2.4 空着的三十九个位置：注释里的排除约定

散落在表里的注释（`kern.c:361-363` 等三十多处）把三十九个编号分成四类：还没实现（二十多格）、已经废弃（七格）、和 Minix 设备节点方案不兼容（两格）、NetBSD 内部使用（性能分析那格除外，其余照单全列）。问到这些编号，查找直接失败，调用的人拿到"没有这个节点"。注意这个错误码选得很有讲究：不是"没实现"，是"没有这个节点"。调用的人分不清"NetBSD 有但 Minix 没做"和"根本不存在"，而这正是目的：排除约定不需要解释历史，只需要稳定回答。

### 2.5 初始化：一行

初始化函数（`kern.c:503-508`）只有一行：把整张表挂到传入的节点上。这是 04 讲的四行挂载序列里的第一行，本篇不展开，只认"线的这一头在本篇的表"。

## 3 Rust 设计决策

| # | 决策 | C 做法 | Rust 做法 | 为什么 |
|---|------|--------|-----------|--------|
| D1 | 表变成数据 | C 数组加宏，编译期铺开 | 四十五行常量切片（`os/servers/mib/src/subtree/kern.rs:114`）加按编号查找（`:361`） | 八十四位置的稀疏表按编号索引是 C 的内存布局习惯。Rust 侧表很小，线性查找加排序断言就够了。布局不值得复刻，位置值得固定 |
| D2 | 构建期值只记名字 | 宏值（最大虚拟节点数等） | 只记宏名字的变体（`kern.rs:70` 起） | 写具体数字是编造数字。构建宏的值归构建系统，表里只记名字。后人接线时按名字搜索，不猜数字 |
| D3 | 空位置变成数据 | 注释（"还没实现"） | 三十九个编号的清单（`kern.rs:355`）加互斥测试（四十五加三十九等于八十四） | 注释会撒谎（填了位置忘了删注释）。表和清单互相排斥，"填一格"变成两处一起改，改漏了测试变红 |
| D4 | 向别的服务要数据的部分先不写 | 直接调用（问频率、问滴答、问驱动表） | 只写纯计算的部分（微秒除法、三种情况、截断长度、别名条件） | 要数据是另一块代码的事。本篇的函数是"算"的部分，不是"要"的部分。判断和执行分开，正是 Redox 方案接口把路径语义和数据来源分开的思路 |
| D5 | 占位子树变成枚举变体 | 子表加函数（行为恒为不支持） | 占位表变体加查询函数变体（`kern.rs`） | 占位子树的存在意义是"被覆盖"（12）：变体名让 12 的覆盖逻辑能按名字搜索到终点 |

**和 Redox、Linux 的对照。** Linux 把"表"做成控制表数组，把"算"做成处理函数回调，表和回调登记在一起，和 Minix 的宏表是同一路数。Redox 更进一步：方案接口按路径分发，每个路径背后是一个方法，路径表和数据来源彻底解耦。本篇的 Rust 设计站在 Redox 这一侧：表项只记"编号、名字、形状"，形状是枚举（常量、构建值、可写、带检查、函数、占位表），函数背后的纯计算是独立的小函数。C 的宏把"形状"和"初值"挤在一行里，Rust 把它们拆成"形状枚举"加"计算函数"，非法的形状在类型层面就写不出来。

替代方案及否决：静态竞技场建表（八十四位置一次建成，真正的节点复刻）——否决。竞技场的事 04 已经说过，但三棵子树表齐（13、14、15）之前建一半，是没完工的工程。本篇计算加数据先行，竞技场在 15 统一建（§4.4 声明）。

## 4 实现详解

### 4.1 模块结构

```
os/servers/mib/src/subtree/
├── mod.rs  — 子树重导出（内核子树先生效）
└── kern.rs — 本篇：函数枚举、检查枚举、形状枚举、表项结构、
               表、编号清单、查找函数、检查函数、时钟计算、

```

### 4.4 和 C 不一样的地方

§2 有五节，§4 是一个模块：向别的服务要数据的执行、竞技场、初始化按 §1.2 移交出去（类别：边界移交）。控制台设备注释"不支持三十二位旧请求"但代码无长度检查的细微出入如实记录（§2.2 表行：注释声称、代码未做，不判设计问题，等要数据的代码复核。类别：注释和代码细微出入，已声明）。

## 6 过渡

内核通用子树这一站讲完了。你现在知道了：表里四十五个填好的位置分别是什么形状，两个可写节点为什么各有一道检查，十个查询函数拿到原始数据之后分别怎么算，以及那棵占位子树为什么宁可永远回答不支持也要占着位置——它在等真正的进程间通信服务来接管。三十九个空着的位置为什么一个都不能问——因为它们是排除约定的一部分，问到就是没有这个节点。

在服务启动顺序里，这对应初始化函数登记的第一棵子树。此后任何问到 `kern.` 开头名字的请求，分发都会落到这张表上。下一站是 14，虚拟内存与硬件两棵小表：同样的查表加现场计算、同样的表加清单，题材换成负载、内存和机器信息。
