# 09 — DS 删除：主人才能删，删标签带级联

> **分类**: 数据面 handler / 删除
> **源码**: `minix3/minix/servers/ds/store.c:583-651`
> **说明**: 删除是检索的"破坏版"：前三步（键门、查找）一样，但权限更严（只认主人，不认门），收尾更重（label 删除带级联，串/存要释堆）。本文讲清这三处不同。

---

## 1 概念

### 1.1 目标读者与前置知识

面向要实现或调用删除的读者。前置知识：08 的检索流程（前三步同构），04 的释放，03 的堆指针。级联删除的概念现场解释。

### 1.2 本章不讲什么

- 订阅者怎么被唤醒——删末尾调 `update_subscribers(dsp, 0)`，但那是 10 的事。
- 堆分配器选哪个——A-3 未决，本篇只讲"删时把缓冲交还给谁"。
- 客户端删除函数的包装——那是 12 的事。

### 1.3 删除和检索的三处不同

| 步骤 | 检索（08） | 删除（本篇） | 为什么不同 |
|------|-----------|-------------|-----------|
| 权限 | `PRIV_RETRIEVE` 门：没设门谁都可读 | **只认主人**：`owner == source`，门一律不看（`:606`） | 读是"看"，删是"毁"——毁不设"公开可毁"选项；C 连 `check_auth` 都不用，直接比名字 |
| 类型分支 | 四臂各回各的 | 四臂各清各的：`U32` 无事、`LABEL` 级联、`STR`/`MEM` 释堆、未知 `EINVAL` | 读是解释，删是 teardown，每种形状的善后不同 |
| 收尾 | 无 | 先过通知环（`set=0`，`:642`），再清旗（`:645`） | 订阅者存的位图下标是条目序号——条目没了，旧位必须清，否则下次取 `check` 会读到野位 |

### 1.4 级联：删一个标签，带走它名下的一切

删 `LABEL` 条目（即删一个服务，如 `"vfs"`）时，C 做三件事（`:613-636`）：

1. 清订阅表里 owner 是该服务名的**所有订阅**（`:616-621`）——服务都没了，它的订阅自然作废。
2. 清条目表里 owner 是该服务名的**所有条目**，每清一个先过通知环（`:624-631`）——它发布的东西一起下架，下架也要告诉订阅者。
3. 最后清标签条目自己（`:642-645`，通用收尾）。

顺序是先订后条：订阅是"等通知的人"，条目是"被看的东西"——人先散，东西再撤，不颠倒。

### 1.5 堆缓冲交还（A-3）

`STR`/`MEM` 条目删时 `free(data)`（`:635`）。Rust 还没有全局分配器（A-3），所以 `apply_delete` 不直接释，而是把缓冲描述符装进调用方给的暂存数组、计数返回——"谁分配谁释放"的权责不变，只是释放动作延迟到分配器落地。这叫"交还"，不是"泄漏"：每个缓冲都有去处，去处可数（`heap_buffers`）。

### 1.6 小结

删三异（主人制、按型善后、先环后旗），签删级联（先订后条再己），堆交还（可数延迟释）。下一站 10——订阅与取阅：DS 的"消息推送"半（次主线核心）。

## 2 C 源码分析

### 2.1 主流程（`store.c:593-648`）

源（`:593-595`，无名→`EPERM`，注意检索的无名是门设才拒，删是直接拒——删连"门没设"这条路都没有）→ 键（`:598`）→ 查（`:602`，无→`ESRCH`）→ 主（`:606`，`strcmp(owner, source)`，不等→`EPERM`）→ 按型善后（`:609-640`）→ 环（`:642`）→ 旗清（`:645`）→ `OK`。

### 2.2 按型善后（`:609-640`）

- `U32`（`:610`）：无事——数字无堆、无级联。
- `LABEL`（`:613-636`）：清同名订阅（`:616-621`，调 `free_sub_slot`，含 `regfree`）→ 清同主条目（`:624-631`，逐个先 `update_subscribers(…,0)` 再 `flags = 0`）。
- `STR`/`MEM`（`:634-636`）：`free(data)`。
- default（`:637-639`）：`EINVAL`——注意它在善后**之后**、通知环**之前**：未知类型不跑环、不清旗，表不动（读 08 的 `:423` 同位，都是"臂错则停"）。

### 2.3 收尾二步（`:642-645`）

`update_subscribers(dsp, 0)`（`:642`，清位 + 通知，10 细讲）→ `flags = 0`（`:645`）。先环后旗：环要读条目的类型和键（定"谁匹配"），旗清了就没法读了。

## 3 Rust 设计决策

| # | 决策 | C 做法 | Rust 做法 | 为什么 |
|---|------|--------|-----------|--------|
| D1 | 主人制直写 | `strcmp(owner, source)`（`:606`） | `plan_delete` 内 `key_eq(owner, source)`，不用 `check_auth` | 删不用门是语义（不是疏忽），复用 `check_auth` 会把"门没设可删"这种错语义带进来；`key_eq` 复用 NUL 止规则（04 D4） |
| D2 | 级联变计划位 | `switch` 内联（`:613-636`） | `DeletePlan { slot, cascade_label }`（`delete.rs`） | verdict 定"要不要级联"，apply 定"怎么级联"——调用方（测试/上层）对级联可见、可断言 |
| D3 | 堆交还 | `free(data)`（`:635`） | `apply_delete(…, heap_out)` 回填 + 计数 | 无分配器（A-3）不硬释；交还可数，不丢不漏 |
| D4 | 清位等价化 | 逐受害者 `update_subscribers(…,0)`（`:628,642`） | `clear_notify_bit` 直清下标 | 位只在匹配时置（10），直清该下标全表 == 逐个匹配清的效果；省掉 verdict 依赖，删模块不碰匹配引擎 |

## 4 实现详解

### 4.1 模块结构

```
os/servers/ds/src/
├── delete.rs  — 本篇：DeleteReject / DeletePlan / plan_delete / DeleteEffect / apply_delete
├── slots.rs   — 04：查找（verdict 的 instrument）
├── publish.rs — 07：check_key_len（键门共享）
└── notify.rs  — 10：通知环（收尾调它，本篇只声明调用点）
```

### 4.2 核心符号表

| 符号 | 来源 | Rust 位置 | 行为 |
|------|------|-----------|------|
| 五拒 | `store.c:593-638` | `delete.rs`（`DeleteReject`） | 源/键/空/主/型→errno |
| 落法 | `store.c:602-636` | `delete.rs`（`DeletePlan`） | 槽位 + 级联位 |
| 删 verdict | `store.c:593-638` | `delete.rs`（`plan_delete`） | 五步（C 序）：源→键→查→主→型 |
| 删执行 | `store.c:609-648` | `delete.rs`（`apply_delete`） | 级联（先订后条）→ 堆交还 → 环位清 → 旗清 |

### 4.3 不变量

| 不变量 | 守卫 | 证据 |
|--------|------|------|
| 删只认主 | `key_eq(owner, source)`，无门 | `store.c:606` |
| 级联先订后条 | apply 内顺序 | `store.c:616-631` |
| 先环后旗 | 清位→清旗顺序 | `store.c:642-645` |
| 堆交还可数 | `heap_buffers` 计数 | `store.c:635` |
