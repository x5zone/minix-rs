## 1. 构建与工具链

### 1.1 宿主测试一律 docker 限内存单线程执行，并警惕构建产物目录的属主污染

链接期内存峰值能把宿主进程静默杀死（表现为测试莫名消失而非报错），并行编译则会崩；此外容器默认以 root 身份写 `os/target/`，此后宿主与容器复用同一目录时双方都假失败——宿主报权限拒绝，容器报找不到编译产物。docker 隔离的不只是内存：任何 panic 崩溃都会波及宿主系统，所以 docker 是第一优先，直跑只是回退。

正确做法：`cd os && docker run --rm -v "$PWD:/work" -w /work -m 2g minix-ci:1.94 cargo test -j 1 -p <包名>`；确需宿主直跑时挂 `-u $(id -u):$(id -g)` 并回退 `ulimit -v` 限内存。怀疑产物目录属主已脏：单包构建通过后再用容器内干净 `CARGO_TARGET_DIR` 复跑对照，两个环境结论不一致即属主问题。评审线或审计线需要独立的容器化验证环境时，用独立的 `CARGO_TARGET_DIR`（勿与主线共享 target），收尾先在容器内修正属主再清理；有复用价值的对账与验证脚本不进临时目录（随会话蒸发且重写代价高），把重写要点写进交付物并推动固化为仓内标准工具。

> 来源：`NK4A-TODO.md` §5 第 1 条；`NK4B-WORKLOG.md`「M3.4 根因取证节」；`NK4A-HANDOFF-STATUS.md` §6 环境与陷阱清单；`new_edge4.md` §1 规则 9

### 1.2 镜像组装必须验证退出码与产物新鲜度，陈旧镜像会制造假进展

组装失败时启动脚本仍会拿上一次的镜像点火，串口照样有输出，看起来"跑过了"实际什么都没验证；改链接脚本不会触发重链，陈旧内核会混进新镜像。

正确做法：组装命令后检查 `IMG-EXIT=0` 才起 QEMU；怀疑镜像陈旧用 `strings BOOTX64.EFI | grep <新符号>` 验证产物里确有新符号；改 `os/kernel-image/x86_64.ld` 后 `touch os/kernel-image/src/main.rs` 强制重链。真机取证前再做一层"构建-产物-运行"三方对账：看构建日志确有重编动作（秒级"未重编"完成行是陈旧工件的信号）、扫产物二进制确认预期字符串在或不在（源码有而串口还在打，跑的是旧工件）；复用既有工件跳过重建前（如为对比基线而跳），先确认工件确实含目标改动，必要时反汇编关键函数验证——跳过重建复用旧工件会把已修缺陷复现成假回归。

> 来源：`NK4A-TODO.md` §5 第 2、3 条与 §7 常用命令；`NK4C-WORKLOG.md` §1.120续-88/续-106（陈旧工件假信号与跳过重建假回归两案例）

### 1.3 整仓格式化禁止，格式核验走 nightly rustfmt 单文件加差分口径

整仓 `cargo fmt` 会在无关文件里制造大规模格式差异，淹没真正的改动审查；宿主 stable 工具链的 rustfmt 不认 let-chains 语法，核验结论本身不可信。两个补充形态各有真机判例：对基线漂移存量大的包漏掉 `--check` 直接裸跑格式化，会一次性重排该包全部文件（一次靠及时检查版本库状态才复原）；代码评审通过后追加的格式修正本身又会引入新的折行漂移，需要再核对一遍，否则提交进版本库的代码与验证过的代码不是同一份。

正确做法：单文件核验用 `rustup run nightly rustfmt --edition 2024 --check <文件>`；判定口径用差分——统计本次改动文件的新增格式块数，与改动前基线在同一工具同一命令下的块数对比，持平即通过（"全绿零差异"口径会被工具链自身的存量漂移淹没）；新增行自己写合规，存量格式漂移不碰；任何导致产物字节变化的追加修改（格式修正、评审意见落实）之后重建并复跑验证。

> 来源：`NK4A-TODO.md` §5 第 11 条；`NK4C-WORKLOG.md` §1.119续（裸跑格式化重排整包的事故记录）；`NK4C-WORKLOG.md` §1.120续-38/续-51（差分口径与评审追加修改的再污染）

### 1.4 三架构共用路径上的架构专属代码必须带 target_arch 门，交叉形态要有结构性构建门

x86 专属汇编与寄存器字段若只带测试形态门而不带 `target_arch` 门，宿主检查与 x86_64 镜像构建都编译不到 aarch64 形态，断裂一路无人发现，直到 aarch64 载体构建才集中爆发。这类事故在该仓发生过两轮，第二轮里还包括上一里程碑自己埋下的三条。

正确做法：共用路径上的探针与取证代码用 `#[cfg(all(not(feature = "mock"), target_arch = "x86_64"))]` 形态；结构性收口是把三个架构目标（x86_64、aarch64、riscv64）的内核构建检查设为持续集成常驻门，让这类回归在机制上无法合入。门控不止编译属性一种：构建脚本的架构分支（`build.rs` 的架构目录扫描）同样会漏新架构——新架构静默退到空列表、无错误无警告，只在真机标志行失败时现形；新架构接线清单里要逐一过所有形态门（编译属性门、构建脚本架构门、共享特性门），分支收编用穷举匹配而非逐个列举，漏列即在编译期报错。

> 来源：`NK4B-WORKLOG.md`「P3 M3.1」；`NK4-REGRESSION-REVIEW-20260922-PART2.md`；`NK4C-WORKLOG.md` §1.120续-89（构建脚本架构门静默缺架构）

### 1.5 docker 镜像缺 UEFI 目标工具链：UEFI 载体走宿主限存构建（"docker 第一优先"的已核实例外）

两套 CI 镜像都没装 x86_64/aarch64 的 UEFI 目标，UEFI 载体（页错误循环、用户陷阱、boot-shim 等）在容器内直接报找不到编译目标，无镜像可回退；宿主工具链齐全，历史 UEFI 产物均为宿主构建。

正确做法：UEFI 载体走宿主 + `ulimit -v 3145728` + `-j 1`（铁律的宿主回退条款），汇报注明"宿主构建（docker 缺 UEFI 目标）"；宿主跑 cargo test 仍坚持 docker。

> 来源：跨会话记忆 `minix-rs-uefi-carrier-host-build.md`（见 6.3）

### 1.6 worktree 内 docker 构建的 target 只能落树内；共享 target 卷会喂进他线的中间态工件

给容器挂载尚不存在的宿主目录，docker 守护进程先以 root 创建它，随后非 root 构建进程权限拒绝且宿主侧无法修复；更隐蔽的是并发会话挂共享 target 卷时，他线在同一树内构建一半的中间态源码会以指纹恰好命中的工件喂进你的构建，产生"符号明明在源码里却报找不到"的假错。

正确做法：target 落工作树自身路径（gitignored，销账不受影响）；误建的 root 属主目录用容器内 chown 修复（`docker run --rm -u 0 -v <目录>:/work minix-ci:1.94 chown -R $(id -u):$(id -g) /work/target`）；假错判别三步——符号 grep 源码存在、单独 check 该依赖通过、只有依赖它的 crate 挂——成立即换树内 target 重跑，勿改源码。

> 来源：跨会话记忆 `minix-rs-worktree-docker-target-perms.md`（见 6.3）

### 1.7 Cargo 特性统一以单次调用为界：显式混形态同命令必炸，多包同图构建撞重复定义

根包启用某特性会把共享类型切到替身分支，而消费方以关默认特性方式消费内核——同一条 cargo 命令里出现"内核按生产编译、底座按替身编译"的类型错配（三处类型不匹配）。同族：init 与其他命令包放进同一次构建时，运行时底座的特性并集触发入口符号重复定义——是命令形态陷阱而非代码回归，验证矩阵里误判会制造假发现。

正确做法：引导载体与 qemu 测试内核单独 invocation；多包合跑用不含载体的固定组；guest 工件逐包独立构建；评审先把"命令形态陷阱"与"代码回归"分流再进发现清单。工作区裸检查门已实测全绿，但全仓 clippy 严格模式仍有存量拒点（已登记待裁决），勿以 clippy 全绿作为合入前置。

> 来源：跨会话记忆 `minix-rs-cargo-feature-unification-trap.md`（见 6.3）；`NK4A-REVIEW-REPORT.md`（多包同图构建节）

### 1.8 工具链升级的两类静默陷阱：宿主入口签名失效与未引用依赖的 rlib 整体丢弃

新版编译器不再为整数返回值的 main 实现终止 trait——宿主形态 `fn main() -> i32` 直接编译错误，而裸机侧 crt0 契约恰恰要求该签名，单一签名两头不能兼得。另一条：可执行包不经依赖引用任何符号时，该依赖 rlib 被整体丢弃，启动符号、panic 处理器、全局分配器齐消失，报错却是"需要全局分配器"而非"缺启动符号"，极具迷惑性。

正确做法：入口按 cfg 拆双形（照服务器包的既有双形模板）；freestanding 可执行包显式 `extern crate` 引用运行时底座保住三件套；遇到入口/分配器类编译错误先查这两条，勿去改签名或加分配器。

> 来源：跨会话记忆 `minix-rs-rustc194-termination-and-rlib-drop.md`（见 6.3）

### 1.9 跨架构编译验证必须固化生产特性配方，裸默认特性的错误爆发是方法伪影不是回归

按特性组合选择目标形态的仓库里，裸跑默认特性的编译检查会引入需要标准库的代码路径（如调试覆盖模块），在无标准库目标上连锁爆出数百个错误；这些错误与代码健康无关，但拿它当回归信号会把真回归淹没在噪声里，反向也会把伪影误报成断裂。同一伪影被两条独立工作线各自撞见并各自登记为"方法伪影"，是"命令形态问题而非代码问题"的交叉印证。

正确做法：riscv（推广到一切无标准库目标）的编译性检查与持续集成门固化生产配方命令（关默认特性加形态特性），验证链里记录"配方告警集与基线持平"这类口径；见到错误爆发先核配方再看错误内容。同族反面：权威宿主基线用显式包列表跑，会把包列表之外成员的编译断裂藏成盲区（集成测试面静默烂掉数月无人见）——包列表是必要的（全工作区会牵进存量烂尾测试污染基线），但要配一个低频的"全工作区全目标编译检查"兜底，大目标（如测试套件上机）开工前先跑一次；对账任何测试计数前先确认该数字的包列表口径，同一提交两个计数可以都对。

> 来源：`riscv-reviewlog.md` §A.0；`NK4B-WORKLOG.md`「M4.4」（同命令独立得到同批错误并登记方法伪影）；`NK4C-WORKLOG.md` §1.120续-77a（配方告警集口径）、§续-190 交接（包列表基线）、§续-197d（全工作区断裂修复）

### 1.10 固件交接不负责清零镜像的数据段：入口序列第一步清 .bss，垃圾读出会伪装成"启动在前进"

引导固件只负责把控制流递到入口，不负责初始化镜像的无初值数据段。放在 .bss 里的分配游标若不清零，首次分配返回垃圾地址；更隐蔽的是读到的脏字节可能恰好通过校验，让启动看起来在前进（假就绪）。仓内唯一真机跑到用户态的载体入口汇编带清零并注释自证，而生产内核镜像的入口序列没有清零循环。

正确做法：生产镜像入口序列第一步清无初值数据段（或链接脚本断言加启动自检覆盖）；把它列为引导形态变更的共同前置，配判别性断言。

> 来源：`riscv-reviewlog.md` §A.1、§C 坑对账表

### 1.11 汇编尾声远跳用取址加寄存器间接跳，不用直接跳：重定位范围在分节布局下构成链接悬崖

对远处符号的直接跳转指令生成幅值受限的重定位（riscv 直接跳转重定位可表达范围仅正负一兆字节），逐函数分节的链接布局下符号间最终距离可能超限，链接时悬崖式失败；取地址到寄存器再间接跳用相对取址，全范围可达。

正确做法：无标准库汇编尾声跳转到注册入口或重调度入口一律用"取地址加间接跳"；新增跨节跳转后查重定位表确认。

> 来源：`NK4C-WORKLOG.md` §1.120续-75

### 1.12 装机与引导的工具链版本事实必须写进脚本：镜像装载器语义、设备树编译器选项、盘形工具单位都是版本敏感的

装机面每个工具的版本行为都是事实而非常识：QEMU 的 loader 设备装载 ELF 按程序头虚拟地址放置（多模块低地址互相重叠即整体拒装；要按指定地址放原始字节必须开 `force-raw=on`）；U-Boot 的 bootelf 按可执行头入口地址直跳（生产内核入口是高半虚拟地址，在分页关闭时必陷——入口适配是裁决级工程而非小修）；镜像组装工具新版把旧选项转成新语义（FIT 语法）；设备树编译器新版删了类型选项；盘工具的偏移参数单位是字节不是扇区；发行版引导器只认带分区表的盘（整盘文件系统直接拒执行）。这些事实错一个就是一轮"启动即退"或"串口零行"。

正确做法：把每个工具的版本与实测行为注释进装机脚本，新机换版本先复测这几条；多模块注入用原始字节加显式地址；riscv 走固件直载腿，U-Boot 腿单独立项；手建盘一律分区表加分区内文件系统。

> 来源：`NK4C-WORKLOG.md` §1.120续-89（改动面 3 与装机面取证链）；§1.120续-77f 环境线

### 1.13 发行版交叉编译器的默认加固对裸机目标是双毒；架构取址伪指令对绝对符号不可靠

发行版交叉 C 编译器默认开启两级加固，对裸机用户态目标都是毒：分支保护指令（编译器辅助代码以带保护指令开头）在低版本架构上是未定义指令；栈保护器把初始化钩子塞进初始化数组、其模板写走异常路径野写内存——真机死在 C 库初始化数组阶段。另一处：自制启动代码里用 GOT 两跳取绝对地址符号不可靠（实测槽位落零洞或无关内容，线程指针寄存器拿到两条空指令拼出的值），取地址型符号用页基址加低位偏移、取值型符号用字面量池；对齐伪指令与标签的顺序错位会让重定位落到填充指令上。

正确做法：库腿与测试腿的构建脚本同步加"关分支保护、关栈保护"（只改一侧会目标文件间引用不一致）；裸机入口代码的符号取址按符号类型选寻址模式；标签放对齐伪指令之后；初始化数组阶段崩溃先用两枚标记二分定位是哪一枚钩子。

> 来源：`NK4C-WORKLOG.md` §续-277（交付 7 与取证链 gh123–129）

### 1.14 可复用资产台账必须带健康度标注：陈旧工具静默产出"像新缺陷"的假线索

取证工具与其派生物（指纹表、索引、快照）绑定被测物的一次布局；被测物重建后旧派生物错位，工具不报"我过期了"而报一个像新缺陷的错误（"指纹表不是有效镜像"）——接手者拿陈旧工具的输出当新线索就浪费一轮。资产清单只列名字不标健康度时，这个坑对每个接手者重挖一次。

### 2.1 起跑前清理 QEMU 残留进程，进程匹配模式用方括号防自匹配

### 2.2 调试探针四条纪律：形态门控、限次上限、过滤去重、裁决删除标注

宿主测试形态下控制台对象是真实端口写，不带形态门的路标会让测试进程直接段错误；不限次的探针在重复事件里刷爆串口与计数配额；配额若不按目标事件过滤，会被启动前段的高频重复事件耗尽——该仓曾连续两轮把配额耗在崩溃点之前，崩溃现场反而拿不到；探针是临时件，不标注归属就没人敢删。

正确做法：全部探针带 `#[cfg(not(feature = "mock"))]` 门；内核侧用 `crate::ipc::probe_mark`（全局共享上限），VM 侧用 `crate::bootmark::mark`（独立计数）；配额按"目标事件预期重复次数"设定，并按目标进程过滤、按重复组合去重，或只在异常值上打印；门控条件从"事件类型"收窄到"目标信号独占的通道或来源特征"——按宽事件类型设门的配额会被无关路径烧掉两轮才收紧到位（页表游走探针被本进程自根游走和重启重装载两条无关腿烧穿，终门按调用通道收窄才稳）；注释标注归哪个裁决流程删除。探针只许读寄存器与立即数——缺页等异常处理路径内严禁页表遍历与内存读取，会沿同一路径递归触发。这条铁律有量化边界与一条配套区分：少量页表游走可以侥幸返回，全量扫描必然撑爆内核栈（现场签名是进入哨兵完整存活、紧随其后的登记哨兵零命中、原始字节为取指缺页加全一返回地址）；"仪器测不了"与"候选被证伪"是两个命题，仪器不可用时该候选保持开放而非关闭，需要页表信息就挪到正常上下文预采。崩溃已发生的现场（栈或堆可能已毁）探针约束更紧：在任何调用指令之前取返回地址寄存器、线性扫描限制在代码段地址窗内、禁止任何进程间通信/堆分配/帧链解引用；探针自身静默时改读崩溃现场邻域的既有路标行做身份判定。定位"哪条语句干的"用语句间步进针——在嫌疑函数各语句之间插纯串口写，首尾针夹出区间再对半细化，比全量重建帧指针链便宜且不扰动分配时序。门控条件不能用端点号猜槽号（端点空间与进程号空间重叠），按进程号或先打一张对照表写门控；带配额的采样探针必须按进程号去重，否则单进程的重试风暴会刷爆配额、把目标事件挤掉。

### 2.3 时序敏感的修复必须两次独立复跑，单次通过不算数

可编程间隔定时器（PIT）的抢占时机让同一份代码两轮运行走不同路径——同一现象一轮出现、下一轮消失有实录。单轮通过可能只是时序运气；反过来，为单轮现象做过度设计同样是错。

正确做法：每个修复真机复跑两次、两轮现象同形才算验证；只在单轮出现的现象登记为时序敏感未决项，不主动追。四条补充判据。其一，瞬态失败（首轮失败、同镜像复跑即绿）的处置是同镜像复跑一次再定性，登记不立案、再现才升格追查。其二，宣布"现象消失"前过两道门：本轮是否到达原触发深度（串口行数、相位计数、事件量对齐历史崩溃点），连续合格轮数是否足够——只跑到触发深度一半的"零命中"是"未触达"不是"未复现"；"家族清零"类结论单轮不宣布（扣减只修一个实例时，下一轮即复发的实录在案）。其三，验证类复跑要求独立轮次：串口逐字节相同不算独立证据（同一次运行），跨配置多轮签名稳定加改动前基线对照才构成"彻底修复"。其四，跨战役交接列"新武器/新变量"清单：已修的共享缺陷会让旧现场读数作废、从未走过的配置面（新容量分档、新桩腿）是首轮异常读数的先验排除项。

### 2.4 崩溃现场定位分两路：模块可离线符号化，内核本体只能探针自报

服务器与命令模块是未剥离符号的 ELF 且链接地址即执行地址，可以离线反汇编定位；内核本体是无符号表的 PE 载体，且 UEFI 每次加载的基址不同——按固定基址换算的思路已被实测证伪。

正确做法：模块用 `objdump -d <模块 ELF> | grep -B8 "<地址>:"` 离线定位；内核侧上限次探针自报位置；恒等映射的测试内核可离线 `nm`。四个方法层扩充。其一，崩溃打印行同时打崩溃指令指针与一个已知符号的运行时地址，两者同基，差值消去加载基址得到模块内偏移——但差值法只在同一二进制内合法；多个模块共享同一份库代码时，符号对账无法区分归属（返回地址落在共享区间，两份镜像都包含该符号），必须补"崩溃进程文本段区间对两份镜像代码段区间"的判别打印，且镜像必须当场重建。其二，寄存器文件整批变成机器码字节时的内容级溯源法：把每个寄存器按小端展开成字节，相邻寄存器边界若能拼出连续合法指令流即"整块码被灌入"；对该字节流在全部涉案二进制里做唯一性扫描，命中者即污染源；再经段表映射回虚拟地址、反汇编钉死到具体函数与具体拷贝指令，拷贝长度与目标结构尺寸吻合是非巧合级强信号——这套方法不加任何探针就能把"谁拷的、多长、从哪来"钉到函数级。其三，判读前先问"硬件出口到底恢复哪些字段"：只恢复段寄存器五元组的出口上通用寄存器整批变码字节，只能是保存区被批量覆写（逐字段搬运不可能整文件齐变）；只有指令指针坏则查控制流与栈内容。其四，历史串口产物当语料库：统计同签名出现次数与配对差值，多轮差值恒定即"确定性同一条指令"；首轮崩溃与异常终止打印腿的递归二次崩溃分开统计。其五，崩溃带精确指令指针且镜像未剥符号时，第一动作是区间反汇编加算式对账而非探针轮：把故障指令的地址计算链逐条重建（全局符号、结构体字段偏移、立即数），与故障地址寄存器逐字核对——设备控制器认领寄存器这类"读即消费"的内存映射读，反汇编直接给出答案，比探针轮快且不扰动现场。其六，反汇编逐条对账源码可以处决"算术写错"类假设：崩溃点指令流与源码逐位一致即算术无辜，嫌疑转向"输入数据被污染"或"喂错了输入"。其七，两种"崩溃地址与崩溃行对不上"的形态要分清：信号投递型死亡里，指令指针只是信号送达时恰好停在的位置（无辜旁观者，死因在投递方——先问"信号是谁、为何投递"再看指针）；发布构建内联归属偏移则表现为"该行静态上不可能产生此崩溃"的自相矛盾——矛盾本身就是归属偏移的指纹，改为检索该函数体内被内联进来的全部索引点。

### 2.5 取证循环节奏：静态定性优先、探针定性兜底、三轮无定性即停

固定循环防乱枪打鸟；停手铁律防沉没成本——一起连续六轮未定性的案例里，正当产出只有决定性实证与被证伪的假说，任何"顺手改动"都是制造推进感的假动作。修了一个真实的相邻缺陷、但实证表明它不是本案根因时，必须如实记"假设对该案证伪"，不得记成进展。

正确做法：八步循环——读串口尾部（排除采样行）→ 位置符号化 → 读对应源码列出全部出口 → 静态可定性直接修，否则限次探针复跑读数 → 修复附一段 C 源对位论证 → 改动前读目标行上下文并 grep 确认 → 宿主测试全绿再提交 → 真机复跑两次。同一问题三轮无定性即转阻塞状态，宣布"本轮不做无定性修复"。八条补充：每轮取证先在当前分支头部重建复跑、确认旧签名仍然存在再追——靶心可能一直在追已被更早改动消灭的症状；探针从嫌疑腿移到所有腿的汇合口（统一回复出口），才能读到真实的回复码面；同一区域连续绕圈时强制回到原始 C 源码做静态对账、直接补那个被反复点名却从未对照 C 原文的缺口，而不是继续加探针；已提交的"无条件必打"路标行本身就是免费仪器——路标缺失可作否定证据，对状态字段按常量表做位解码、对状态机事件做计数比，能不开探针就把死锁定位到两条腿之间；死锁或饿死类的第一探针是全进程状态快照（按计数阈值触发遍历进程表打印每进程状态），断言"某值只可能来自某条路径"必须穷举全部写点坐实；静默冻结的标准作业是粗二分、细步进、静态读码修正语义三段——零输出冻结没法靠日志尾行定步，先在父/子两侧锁区间，再进嫌疑函数锁到语句，收尾读码修正归因模型（表层的可睡眠调用实为走文件系统进程间通信的轮询，归因随之改写）；一次性挂死与反复空转用限次计数判别——入口探针只打一次即静默是单向前进后停（非空转），再对嫌疑函数按阶段前后插标记二分；连续多轮定向探针零命中不是"仪器差"而是"崩溃点模型有系统性偏差"的信号——给自己定阈值（连续三轮零命中即触发模型偏差检查），列出已证伪与未覆盖路径重新枚举，超出文本探针能力的瞬态写者问题登记成可直接执行的调试器处方转专项，同时把会话杠杆转给未启动的目标；阻塞类定位沿消息因果链向前追而非停在最后一条日志——最后可见活动可能只是上游断点的下游余波，对"某消息从未发出"先用全量捕获探针区分"没发"与"发了丢失"；假说未处决前不动生产代码，排查期补丁只进诊断构建，环境故障（测试台空日志）时宁可回滚备好的改动挂账，也不投未验证的生产改动。

### 2.6 观测通道本身会撒谎：阴性结论必须先验证通道，洪流下打印不可作执行证据

aarch64 用户态的诊断打印不落到串口文件，只有走内核诊断通路的系统调用可见——据"计数为零"判"分支没走"整轮定性作废（分支探针直证系统调用真返回了权限错误）。诊断洪流下同一探针一轮打十几行、下一轮零行，串口行数对"是否执行"不构成证据；日志含空字节时 grep 计数同样不可靠。

正确做法：取证前先用一条必然经过的探针验证观测通道在吐字；洪流场景改用"回复码哨兵分区"——把分支编号加错误码塞进回复消息类型读回，每次稳定回传，不靠打印；统计日志先做字节级预处理（空字节会让文本工具漏计）。三条同族扩充，各有真机判例。其一，对串口原始流的文本检索必须强制按文本处理——内含空字节的流会被检索工具按二进制降级、静默漏报命中行，凡要下"命中零次"的排除性结论必须用显式计数方式复核，假阴性会把取证方向整个翻转。其二，多核并发写同一串口会逐字节交织、伪造出寄存器值（读出的 64 位值按 ASCII 解开恰是另一输出行的碎片即证据），多核环境打结构化日志用同一字符串冗余重复加事后计数定位，关键结论布哨兵链而非单哨兵。其三，真机探针的消息必须是固定前缀加纯整数列——无标准库运行时的 panic 消息渲染器对复合格式串不输出消息体，探针"零输出"与"没命中"从此不可区分（两轮实验实锤：复合格式串零输出，改纯整数列稳定打印）。其四，用户态诊断通路的载荷有硬上界（十六字节），超限静默丢弃——三枚超限探针全程零输出的实录在案；进程创建与装载风暴窗口内用户态诊断打印非确定丢弃，关键结论要么多轮命中要么改内核侧探针，可用格式用压缩前缀换关键载荷。其五，本机环境的 grep 实为另一个实现（ugrep），对含无效 UTF-8 字节的文件静默吞掉全部输出、连计数模式都不出数且退出码无异样——取证与对账的文本处理一律走脚本语言按字节读入，不信文本工具的计数。

### 2.7 探针的两种不可信：自身伪影与扰动源

伪影类实证五起：键缺判别维度会跨进程误报（两进程栈地址同域）；配额按错误频度设置会被启动期耗尽；报文超长被接收端静默丢弃；内存转储的层级命名凭直觉写错（把页目录当页表），整条根因白推一轮；把"故障时读数为零"过度推理成"曾被写后清除"。扰动类：探针装入引起的代码布局位移本身就能翻转缺陷是否复现；长期驻留的带前缀探针每秒数百行刷爆串口，把真死锁的信号淹没——清噪之后真阻断才现形。

正确做法：探针键取判别维度全集；配额按目标事件频度设定并按目标进程过滤去重；报文长度与接收端上限常量对账；转储探针先对照页表遍历定义自证层级命名；"读数为零"只记快照、历史推断要哨兵回读佐证；对布局敏感嫌疑做三方对质（干净基线镜像对照加探针有/无双跑），常驻探针跑完即回滚。扰动的强度谱系上限是"让缺陷整体消失"：挂上用户态探针的轮次里，生产缺陷可以完全不再发生（探针把首次出错位置挪走）——因此一切"修好/改坏"判据必须建立在零用户态探针的纯净基线上并量化复现率；取证基线的操作定义是"最小探针集加同配置多轮运行逐字同形"，多轮不同形即判扰动、换非扰动手段。同时单腿零命中只对被探测的那条腿有效、不外推到邻近腿（探测执行腿的针零命中的真实含义可能是"事件从未发起"，与"回复腿断裂"是两个命题）。两条设计侧对策：时钟中断热路径禁打印型探针（打印本身扰动时钟时序，该轮比对照轮冻得更早——只能作定性佐证不能当定量证据，必须观测就用内存静态记录加事后读回）；读侧探针改布局即可作废现场，改用写侧台账替代——只在写路径的唯一漏斗登记（调用点数量有限、扰动面小），判读树按"台账写过而实读值不符/台账从未写而实读非零/写命中表页事件"三分支天然分离假设。

### 2.8 金丝雀与毒化是"保存之后有无写者"类假说的终审判据

向目标上下文注入哨兵值再观察交付值——若交付的正是哨兵，证明保存与恢复之间无人写过（一次判决）；无条件毒化后读数只在毒化后的第一个陷阱窗口内有效，毒值会级联扩散（毒指针被解引用、被写进对象），越跑越脏。

正确做法：终审用金丝雀一次判决；毒化读数限第一窗口；写生产寄存器上下文的诊断代码判决后立即摘除——判决工具本身就是污染源（哨兵被当真实交付值污染用户态有实录）。对照实验本身也要过判别力审查："做了某操作后现象消失"必须排除其它能产出同一结果的通路（该操作让真正出错的那条路径提前走完、纯时序扰动），目标假设是唯一分叉点的对照才算数；有两条以上旁路解释的对照实验不构成坐实，随后的直接修复未消除失败会反证对照证据无效。

### 2.9 调试器批处理模式可全自动硬件取证；观察点零命中不可作阴性证据

调试器批处理加脚本能在冻结启动的虚拟机上自动设断点、设观察点、读物理内存，全程无人值守——"硬件观察点必须人工交互"的前判被推翻，正是这条路线抓到多核间特性寄存器差异。但同一调试桩对目标虚拟地址的观察点可能连续三轮零命中而机制自测全部正常——零命中当阴性证据会错杀整条路线。

正确做法：模板为"虚拟机冻结启动 + 批处理脚本"（自动断点→观察点→物理内存读，物理读免受分页影响）；观察点零命中前先做翻译与写入自测，自测通过而目标零命中即判工具不可靠，改走软件探针时序对账。硬件观察点在多核内核上另有一份结构性不可行判据清单：写者跑在另一处理器上且页表把同一物理页映射到不同线性地址时观察点不触发；被观察物理地址逐轮漂移且调试器无页表遍历能力时无处设点；无调试符号时只能裸地址工作；被观察结构每次陷入都被写、写频率使条件断点不可持续——四条任一不满足就改走内核探针或全量异常日志取证，"值得一试"与"结构上受困"要分清。

### 2.10 "未知写者"类悬案用大排除法：先列全集再布网，逐网三元组对账

一起十几轮的悬案靠三张独立检测网系统性证伪——每网覆盖一类写路径，按（标签、物理地址、长度）或（虚拟地址、页表根、物理地址）三元组去重对账，全部零命中后嫌疑收敛到唯一一类路径（当前调用同步直写陈旧地址）；与崩溃签名同虚拟地址重合的写点是最高优先线索。

正确做法：清零/覆盖类悬案先枚举全部可能写者再逐类布网，不做无网猜测试；判定写者身份用配对节奏（成对出现的设置与使用日志）而非单点打印；修复后用独立真机复跑对账，关键计数逐字一致才算闭合。排除法另有四条边界纪律。第一，枚举的完备性没有内保证——"全部候选探针阴性，故收敛到唯一剩余机制"只在本方枚举空间内成立，成修前强制做一遍权威源码终审：该机制在 C 源里是否存在、C 靠什么保证同类一致性（一个"缺失跨处理器翻译缓存刷新"的收敛结论，被 C 源里根本没有这个机制一行推翻，真根因在完全不同的维度——闲置副核没停本地定时器）。第二，宣布"结构上不可能"前核对检测集合是否覆盖实际参与事故的结构的物理帧——只测几类代表性符号的检测网会漏掉具体的别名对，被推翻的"关闭"要敢于复活重查。第三，探针族连续阴性到一定数量，停止"再加一枚"，改画"探针覆盖面对可能破坏者位置"的矩阵，主动找让整族探针结构性失明的盲区象限（破坏发生在所有探针点之后、且根本不经内核写腿时，一切写腿守卫与恢复点检查都看不见）。第四，证伪的有效范围等于扫描窗覆盖范围——扫描窗按段表或镜像边界实测而非凭印象取整，窗外部分要么补扫、要么把结论降级为"未完全证伪"。两个加分手段：构造"嫌疑机制前提不存在"的最简复现场景（不含任何跨进程态的父进程复现同字同值损坏，整族跨进程解释一次出局）；对"页别名或共享页"类假说在嫌疑写入点埋物理地址对比针——同虚拟地址从涉事各方页表根各走一遍，多次全不等即结构性排除别名论。再补四条。第五，体内守卫优于调用点前置探针：在共享函数体内对每次指针跟随做合法性检查、命中记静态计数后按错误返回，覆盖全部调用者与全部跟随点，零命中即可洗清整个机制；但发布构建的内联副本与重排可能让个别读点绕过守卫分支——"守卫零命中却仍崩"的残余矛盾不能推出"不经此函数"，用反汇编核内联副本或直接上硬件观察点。第六，路径级探针只覆盖被探的那条调用边：共享函数有多个调用者时，"A 路径插针全干净却仍崩"的矛盾唯一消解是检索全部调用点、按调用边分配探针覆盖（一个"VM 填页越界"悬案的真凶路径是另一个调用者——写时拷贝保护的全表扫描——探针从未盖到）。第七，排除法定论必须附前提清单（尤其"仪器覆盖完备性"这类未验证前提），换镜像或换构建后重跑最便宜的对账（反汇编崩溃指针）而非沿用旧结论；每次写出"瞬态"二字强制三选一：值真的瞬态、我认定的地址不稳、观测本身被扰动——区分三者的最便宜断言（如故障地址页内偏移自洽校验）优先于任何新观测手段。第八，判死一个故障家族要用正证据而非多轮未复现：构造"如果它发生必留痕"的探针位并取全量判定序列（每条回执的裁决值），"四十五条全部正常"才是"症状从不在此"的证明。

### 2.11 可复现判据体系：确定性测试台、量化计数、归一化签名、控制实验

多核噪声下同一镜像两次运行发散、连基线控制组也崩，无法归因；单核多次运行逐字相同才构成无歧义测试台。构建产物敏感：增量构建的陈旧工件让某些结论无法从干净重建复现。环境文件同样敏感：换全新固件变量文件会改变模块装载落点，曾被误判为缺陷复现。物理地址每轮漂移而用户虚拟地址稳定，跨轮对账比物理地址必错。

正确做法：归因用单核确定性测试台；活锁类修复的判据取"同一故障地址的重复缺页计数归零"而非行数增减；多轮回归用归一化地址后的运行签名做双跑一致性门；常量矩阵实验配控制组全新重建；固定环境文件（累积的虚拟机变量文件）；跨轮对账只比虚拟地址。四个补充判据。模拟器全量异常日志（记录每次中断与异常的完整寄存器现场）是多核崩溃取证的第一仪器：两轮逐字复现同一崩溃即证确定性而非随机竞态，且拿到无探针的全寄存器现场，解读前先弄清该日志的记录盲区（"日志里没有"不等于"没发生"）。只在单一核数下复现过的问题先做核数扫描——多核现象若在两核复现、单核健康，竞态面缩到成对关系，且"单核与双核的唯一差异"直接指向缺失的每核行为。判定"真死锁而非慢"用双时长对拍：两次时长悬殊的采样逐字节相同即静止态。确定性缺陷与时序竞态用签名漂移性判别：崩溃点随运行速度或布局漂移是竞态特征，多轮逐字同签名指向确定性缺陷（两者可叠加——确定性缺陷被诊断布局移动落点）。再补四条。跨轮对账只能比形状与签名、不能比具体数值：物理帧每轮重新分配，两个轮次的"根地址不一致"曾造就一桩假定谳——两个数字来自不同运行轮次；探针入库后一切判读须同轮对账。引用旧轮探针数据前先回读原始串口逐项对账（标签、门控、寄存器语义）——一次"两棵页表树共享物理页"的惊悚结论实为"同一进程同树读两遍"的标签误读；同构镜像进程布局相同使虚拟地址无法区分属主，属主判别用页表根不用虚拟地址。对寄存器值立疑前先读该架构的入口约定（哪条腿传什么号），有信息量的是差分（有/无某类陷入）而非绝对值。交接或跨战役时列"新武器/新变量"清单：已修的共享缺陷令旧现场读数作废、从未走过的配置面是首轮异常读数的先验排除项。

### 2.12 QEMU 真机轮的 shell 退出码 124 是收尸超时的常态，判据只看串口签名

panic 后 guest 停机但 QEMU 进程仍活着，靠外层 timeout 收尸，shell 退出码恒为 124——把退出码当过/挂判据会把所有 panic 轮误读成"原因不明的失败"（与 1.2 的镜像组装退出码是两层不同的事）。

正确做法：真机轮产物是串口日志，判据取串口签名（标志行/panic 签名/异常向量行）；退出码仅记录不作裁决；QEMU 参数照配方原样跑（自行追加机器参数会启动即退）。

### 2.14 探针零命中与可疑读数的归因清单：先排除仪器自身，最后才轮到目标行为

取证探针是一个自身可能出错的小程序，它的"零命中"与"可疑读数"各有一组无辜解释，归因顺序错了会把仪器缺陷读成系统事实。零命中的无辜解释有八类：特性门控把探针代码整段剪除（观测所用构建形态与探针的编译形态不一致）；镜像陈旧（增量构建未重编，产物修改时间早于末次源码修改）；配额被启动期高频事件耗尽；门控守卫恒假（地址空间宽度写错使比较永假、比较键跨了虚拟与物理两个量纲）；门控条件本身错（拿端点号猜进程号，两个空间重叠）；观测通道丢弃或消息渲染器不支持该格式（含载荷超上限静默丢弃）；短字面量被编译器内联进指令流使字符串检索查无（检索不到不等于码没编进，用符号表查）；打点代码的形态门控根本不含目标架构（跨架构对比串口签名前，先确认每个路标在目标架构有没有对应打点——"缺席"只证明没打点）。可疑读数的假象有六类：越界读——按偏移读消息结构越过尺寸上界，读到相邻内核字段而那里恰好存着同域值（用户栈指针），凭一个字节的位置能撑起贯穿数轮的自洽假因果链；打印值的进制或字段标签混淆，语义不明的两个字节足以让读者编出一条假根因链；判据覆盖面小于数据存放面（只校指令指针不校通用寄存器保存区），读数为真而推论为假；栈回溯符号归属是"窗内相似地址"的概率匹配，必须配直证复核；诊断打印自身的字段宽度不够，读数被截断成歧义形态（计数上界四位被按两位打），误导"预算与泄漏"二分方向；封顶型探针的尾部重复是"窗口截断"不是"无限循环"——拿封顶常数的倍数当洪流证据，是把探针机制误读成系统行为。

正确做法：把清单当检查单正向走。凡要下"某事件未发生"的结论，依次核对：探针在该构建形态里真实存在（配置形态匹配、产物里有符号）、镜像是当场重建的、配额没被别的事件耗尽、守卫条件用已知会命中的地址冒烟过、门控键查过对照表、通道活着且消息格式是渲染器支持的、打点在目标架构有定义。凡读数异常，先查自己（尺寸上界、进制标签、比较键量纲、判据覆盖面、打印宽度、封顶常数），再查系统。探针按偏移读结构以类型的整体尺寸为硬上界，逐偏移核对，越界字段一律不打；读数与假说"意外吻合"时第一反应是查"读的是不是紧邻字段、该字段正常语义下装什么"。栈扫描或地址换算归因之后，必须在被归因函数内装直证探针并先证明其活性，命中才算数，零命中而现象仍在即推翻归因；哨兵与特殊常量表（任一端点、无端点）先解码再判垃圾值；带封顶的采样探针必须按进程号去重，判读时先查封顶常数。

> 来源：`NK4C-WORKLOG.md` §1.120续-32（越界读伪影翻案）、§1.120续-16/续-24（镜像陈旧与守卫恒假）、§1.120续-15（进制混淆自造假象）、§1.120续-29（直证复核推翻栈扫描归因）；`notes/rewrite/fork-syscall-rewrite/trap-boundary-message-materialization.md` §4.4（配置剪除造成假零命中）；`NK4C-BUG-AARCH64-VEC-CAP.md` §7（会再次绊倒人的坑）；`NK4C-WORKLOG.md` §1.120续-93（打点形态门不含目标架构）、§续-142（诊断通路十六字节上界）、§续-115（封顶误读为洪流）、§续-278c（打印宽度截断）

### 2.15 连续证伪要靠判据链收敛，不靠轮次堆叠：每轮证伪留一条判据，假设复活设证据门槛

一族假设被连续证伪时，"又试了一发没中"与"收紧了搜索空间"的区别在于每轮是否留下可复用的判据。一条间歇性内存腐蚀弧线的判据链范本：毒值跨多轮独立扰动恒定、仅随对齐余量平移过一次——指向确定性数据流而非翻译层残留（若是陈旧翻译导致写错物理帧再读残留，内容应随时序漂移）；毒值平移量恰等于某次修复引入的对齐余量——证明该修复已生效但不是根因；不含任何跨进程态的进程复现同字同值损坏——把整族跨进程解释一次出局；抓到出错指令后按"该指令能写出什么值"做范畴论证——写常量填充模式的指令产不出栈地址，源寄存器来自内存的指令把问题转化为"源头是谁"；对整类指令做全量枚举（对真实加载的镜像反汇编全部向量存储并统计目标寄存器）才能彻底关闭"某类寄存器污染"假设族——抽样排除只是部分排除，两种证据强度不同。同一观测可由多条通路产出时，探针只能证明"槽里是什么"、不能证明"怎么进去的"：下结论前做判别力边界分析，列出所有能产出同一观测的通路，不能二选一的登记为独立假设并配独立判别针，判别手段按成本升序排队。

正确做法：每轮证伪必须产出一条判据（值恒定性、平移量、最简场景、指令能力边界、全量统计），判据连续否证同族假设后把整族永久关闭并写进账本防后来者走回头路；低置信候选升级为实施前必须有新观测支撑（仅以"修复形态"复活就消耗整轮实施预算并全部回滚的教训）；修复落点必须与受害数据的构造点重合——实施前先回答三个问题：受害数据结构在哪块栈或哪个堆上、由谁构造、构造点的布局来源是否受本修复控制（打在消费侧或交接侧的修复注定无效）；与当前案无关的真发现按 5.26 处置，不并入因果链。

> 来源：`NK4C-WORKLOG.md` §1.120续-38/续-39/续-40/续-41/续-42/续-43/续-44（四轮证伪判据链弧线）、§1.120续-34b（判别力边界分析）

### 2.16 确定性复现不等于根因证明：症状可能只是布局敏感的表现，正解是修那个"时隐时现"的真缺口

往一个无关模块加几十字节探针，就能让同一二进制上"确定性复现"的症状翻转成另一种症状——若该症状是确定性根因，无关模块的字节位移不该翻转它；它实为启动期排序或未初始化竞争的布局依赖表现。布局敏感不是拒绝修复的理由，而是定位提示：真正的保真缺口（一条回复码从未被校验的登记腿）会在不同布局下时隐时现，修掉它才第一次得到不依赖探针扰动的稳定签名。配套纪律：任何新探针都改变布局，所以布局敏感场景的正解是零扰动取证——盘点并复用已提交构建里内置的路标、一次性触发的快照（按计数阈值触发全表快照而非逐事件打印）、关机时才转储的内存环形记录；把加针后的运行当"净态证据"引用，是多轮反复翻案的根源。

正确做法：把"确定性复现"只当候选证据、不当根因证明；用"扰动无关模块是否翻转症状"做廉价判别；症状随布局翻转时回到权威源码逐行对账，找那个时隐时现的真缺口修掉而不是修症状；每轮取证先检索仓里已提交的探针与路标清单，证据标注来自净态运行还是加针运行，引用结论时核对它当初的观测条件。

> 来源：`NK4C-WORKLOG.md` §1.119续-6/续-7（确定性症状降级与真修复）、§1.119续-2/§1.120续-21（零扰动通道三类）

### 2.17 新停点先判"是否本改动引入"：对照实验必须验证对照条件真的生效

新崩溃签名出现时第一反应易是"刚改的代码引入回归"；判定靠同配置重建基线镜像对照。两个实证细节。其一，对照镜像与当前镜像逐字同签名即预存而非引入，且能顺带定性新旧形态关系（旧的随机形态被新布局取代成确定态）。其二，对照操作本身可能静默失败——用暂存回退做的对照，实际因路径与暂存异常没有回退，所谓对照镜像仍是同码，结论全部无效；改用检出基线提交重建才完成真对照。

正确做法：新停点出现，检出基线提交（或确认无歧义的等价基线）同配置重建、跑足轮数、逐字比对串口签名；对照完成后必须验证对照状态真的生效（版本库状态确认回退到位、用镜像指纹区分两份镜像），对照结论入档前注明"对照已验证生效"；能用检出固定提交就不用可能静默失败的暂存回退。

> 来源：`NK4C-WORKLOG.md` §1.120续-76/续-77a（对照定谳与"对照未生效"的纠正）

### 2.18 同一架构并存多个失败模式时先按签名分流分桶，修好一个不臆想另一个"顺手一起好"

两个正交缺陷（确定性的换根活锁与间歇性的巨量分配崩溃）叠加时，后者的发作会遮盖前者的现场，混查会把两条独立因果线搅在一起越查越乱；且两条根因彼此独立——修好其一，另一依旧存在。

正确做法：多现象叠加先按"确定性或偶发""发作前置条件"分桶；交接件给每个模式一段串口签名判别式，接手第一动作先跑签名分流、再按分流结果进对应配方；一个修复落地后对其它现象做独立复验。墙的数量多到逐个试探不经济时，建"轮次×首墙"矩阵表：同一镜像不同轮命中的首墙不同（时序敏感族的常态），按"复现频率×阻挡深度"排修墙顺序——连续多轮确定性首挡的先修、非必现的后排；每轮判读与"本轮命中的墙"对账，不同轮的证据不混用；且墙序本身对探针敏感（加一枚探针即换首墙），改一行代码视为新布局。

> 来源：`NK4C-AARCH64-EXEC-REBIND-LIVELOCK.md` §6（纠缠现象分桶）；`notes/rewrite/fork-syscall-rewrite/NK4C-MIGRATION-20260930.md` §4.A（签名分流判别式）；`NK4C-WORKLOG.md` §续-137/续-141/续-148（多墙轮转矩阵与确定性首墙优先裁决）、§续-220（墙序探针敏感）

### 2.19 零改动诊断仪：按包开启调试断言，让既有不变量在真机精确行崩溃

发布构建里休眠的不变量断言（重复释放、引用计数下溢、一致性检查）本身就是一套现成仪器：按包开启调试断言（用后即滚）能让违反点在真机精确崩溃，零代码改动绕开"处理路径内不许再搭仪器"的禁区。两个前置与一个产出：先盘点已知良性记账不对称触发的断言并临时放行（否则诊断仪死在良性点上、拿不到真崩点）；有效观测是"零内存安全断言触发"加崩溃点漂移性；崩溃点随运行速度漂移指向时序窗竞态。

正确做法：宿主测试覆盖不到的路径，优先考虑"开调试断言"这类零改动诊断仪再考虑写探针；用前盘点已知良性断言并准备放行；观测结论与构建形态绑定记账，用后即滚。

> 来源：`NK4C-WORKLOG.md` §1.120续-64

### 2.20 观测手段能力矩阵：每种仪器的扰动性、能给出什么、当前状态列成表，负结果可信度由此判读

疑难缺陷推进到假设收敛期时，"还剩什么牌、哪个负结果可信"取决于一张能力矩阵。七种典型手段的边界实录：全内存快照与停机活体读是零扰动的，但只能证伪"脏值驻留"、不能证明"瞬态"；静态审计零扰动，能排除结构性错误但证明不了时序问题；调试器条件断点每命中一次都要回宿主求值，往返开销在热路径上不可用（实测五百秒只推进六成串口行）；硬件观察点在特定模拟器与架构组合上可以设点成功但永不触发（物理与映射两种地址形皆然，软件模拟模式下观察点按虚拟地址匹配）；生产路径加一条读就换布局，曾产出幻影指纹，禁用；客户机内写侧台账扰动面小，待实测验证；模拟器插件零暂停零改码、每访存回调本地求值，是热路径观测的最后一张牌，但接口事实必须对照本机导出符号表校准（骨架与上游片段都会骗人，且插件拿不到写入的具体值——只能定"哪条指令写的"，值与语义要靠客户机内台账闭环）。记录回放等高级特性在本机加固件组合下可能启动即退，死法要归档失败原因与复现命令。

正确做法：假设收敛期强制列手段能力矩阵（零扰动？/产出类型/当前状态三列），路线选择从矩阵推导而非从习惯推导；热路径的条件观测一律走"被测系统内部求值"（插件回调或代码内台账），外部调试器只用于冷路径与停机后取证；写任何模拟器插件前先对照本机导出符号表逐个打勾，接受"插件定指令、台账定值"的分工；环境限制类结论必须有干净对照实验背书（对照组证明工具链本身健康），且结论绑定环境版本。

> 来源：`NK4C-BUG-RISCV64-TRANSIENT-PTE.md` §5（手段能力矩阵全章）、§6.3（符号校准表）；`NK4C-WORKLOG.md` §续-241/续-242/续-247（观察点两形不触发与记录回放死路）；`riscv瞬态页表崩溃取证方法论.md` 知识点三（对照组定性）

### 2.21 观测者效应有谱系：暂停与恢复这类零代码干预也换指纹族；零语义变化的拖慢实验是竞态判别器

观测者的干预强度远不止"加探针改布局"一档。实测谱系：生产路径加一条读——崩点与崩因全变、实验作废；调试器从头挂起或运行数秒后接入——不改任何代码也把指纹换族（推测与定时器中断和调度的交错有关）；对全窗做零语义变化的均匀拖慢——竞态型缺陷因窗口交错被改变而不再触发，耐久损坏型照崩。这意味着不同"轮次"采到的指纹可能根本不同族，跨轮拼签名的做法天然危险；带干预的运行读数不可当基准证据。

正确做法：把"干预方式对现场指纹"列成量化表作为一切判读的先决背景，比较任何两次观测前先核对两者运行方式相同；只有零调试器零探针启动拿到的复现值可作基准证据，带干预的数字一律不得当基准；对疑似竞态先做一次"零语义变化的拖慢实验"定性——拖慢后消失即竞态、仍崩即耐久损坏，一步定缺陷类型；取证手段按侵入度递进：先只读现场（停机借内核映射活体读，零扰动），再非侵入动态手段（插件），最后才动代码加探针，探针用后即还原；侦查执行模型的结构性事实（单线程组件内部不存在并发竞争、多核加全局大锁的调度层才有交错）可与速度扰动响应交叉，把嫌疑面收窄到"组件生命周期×内核切换时机"的交互带。

> 来源：`NK4C-BUG-RISCV64-TRANSIENT-PTE.md` §5.2（干预方式与指纹族量化表）、§3.6、§8 条 5；`NK4C-WORKLOG.md` §续-270（拖慢实验定竞态）、§续-246（生产路径加读漂崩点）、§续-226（挂起时机换指纹族）；`riscv瞬态页表崩溃取证方法论.md` 知识点四（取证顺序与基准纯净性）

### 2.22 崩溃地址与寄存器现场先做算术判读再消费：八倍对齐、页内偏移自洽、差值等于容量、语义坐标逐层换算

页表遍历类崩点的故障地址自带结构信息，四条纯算术判据不依赖符号与快照。其一，槽读形状判据：走表读的地址形状恒为"对齐页基址加索引乘槽宽"，故障地址低位必为槽宽倍数；不符即是"页内容数据访问"的形状——一步二分"走表还是走数据"。其二，页内偏移自洽判据：页内容访问的低位恒等于所喂虚拟地址的低位，与全部候选虚拟地址对账，自洽者才有资格当"崩溃所用地址"，不自洽的记录值要怀疑是基址寄存器值而非访问地址。其三，差值判据：越界值与合法值的差恰好等于内存容量或窗尺寸这类有语义的常量，指向"相对偏移当绝对地址、基址加了两次"的单位混用族（纯代码审计可抓），随机位翻转不会恰好等于容量。其四，语义坐标换算：把坏值在每一层"应该是多少"建链（页表项位、物理页号位、物理地址位、帧号位），逐层求差，残余位形与已知常量（窗基址、容量、位图字位）对表，单层看是模糊结论、逐层对齐后残余形状直接指向写入者的值来源类别。配套纪律：寄存器现场消费前先做自校验（零号寄存器恒零，转储里它非零即布局错位，整套寄存器代数作废）与语义锚定（哪个寄存器是栈指针、哪个是系统寄存器——把栈指针当遍历地址、把本进程页表基址当目标进程被遍历的根，都曾把四轮观测引到错的靶位）；"同一数据两次读不一致"先上三级排除（单次求值合并、函数内埋点、强制真实加载），三级全过才允许归因内存层——编译器指纹是必要表现不是充分判据；跨构建的指令指针与故障地址禁拼合判读（探针改布局会移动指令指针，拼出的"崩在槽读且地址不对齐"是假前提），判读前用镜像指纹双验两者同构建；同一构建内"指令算术恒对齐而硬件报非对齐"的矛盾穷尽真实访问解释后，把"模拟器报告语义"列为正式候选，并按故障地址低位分族统计形态分布防单轮以偏概全。

> 来源：`NK4C-BUG-RISCV64-TRANSIENT-PTE.md` §2.4/§3.2/§3.4/§3.7/§3.8/§3.3（四判据与回滚块）；`NK4C-WORKLOG.md` §续-153（转储自校验位）、§续-238/续-257（语义锚定与靶位翻案）、§续-156~158（三级排除杀编译器理论）、§续-163/续-164（跨轮数值假对账）、§续-256/续-266（同构建矛盾与模拟器报告语义候选）；跨会话记忆与提交 `80c23e9dc`（形态分族统计）

### 2.23 物理内存取证两件套：全量快照离线分析加停机活体读，判据谓词的语义层级决定覆盖度

模拟器监视器可以把整机物理内存转储落盘，离线按物理地址分析（走目标进程页表根逐级映射、与模块镜像逐字节比对），一轮裁决多轮探针悬案；对转储字段的判读有两条纪律。其一，判据谓词语义层级：按"解码后判值域"的语义谓词扫描（对每个字判解码结果），同一物理帧配任何标志位编码都能命中、覆盖完整；按"原始字节模式"扫描则同帧异编码全部漏掉——两种都叫"扫了全内存"，证据强度差一个量级，归档时必须同时归档谓词原文。其二，覆盖层矩阵：多级页表每一级都是独立覆盖层，"扫了全部根表零命中"不覆盖中间层与叶层——宣称"某层零命中"前先画覆盖矩阵（扫了哪些层级×哪些帧×什么谓词），嫌疑层级未定时负结果只许写"该层该谓词下零命中"，不得写成"缺陷必为瞬态"。第二条腿是停机活体读：不加挂起参数正常启动、轮询串口发现崩溃后立即接入调试器——此时处理器停在崩溃处理路径、处于高特权态、内核直接映射窗有效，可经映射窗直读任意物理帧且零改动；判据谓词必须是语义谓词（解码后判值域）而非字节模式。两个工具细节：监视器转储命令的文件路径要带引号否则被当表达式解析；调试器里手输长常数先用源码的分组写法核对位数（超位宽的常数会让所有读取失败，易误判成目标不可读）。直接映射窗有两套基址（内核一套、用户态服务器一套）且分属两套页表——在谁的地址空间读就用谁的基址，用错基址读到的不是目标物理内存；停机后内核页表接管，统一用内核基址。

> 来源：`NK4C-WORKLOG.md` §续-144/续-145/续-154（转储配方与判别实验）、§续-187/续-188（快照双事实）；`NK4C-BUG-RISCV64-TRANSIENT-PTE.md` §3.7/§4.5/§5.1（谓词语义层级、停机活体读、覆盖层重估）；`riscv瞬态页表崩溃取证方法论.md` 知识点一/二（双基址归属与常数位数）

### 2.24 工具负结果先归因自己的参数，再归因工具缺失；宣告"手段不可用"要有对照组背书

观察点"设点成功却永不触发"的负结果，曾有一轮把根因归到"软件模拟不支持观察点"这个更强也更难验证的结论上；重审发现实验脚本里的地址常量抄错一位（注释公式对、字面值少一位零），错误地址同时解释"读不到内存"与"从不命中"两个负结果——无需借助工具缺能论。同族形态：调试器接入时机的三个坑（不带挂起参数启动则崩溃早已发生、接入即错过；残留实例占着单客户端调试端口；从头挂起会换指纹族，晚接入才保时序）；命中判定正则与工具实际输出措辞不匹配（不同版本措辞不同），会把"设点成功"误报成"设点失败"诱使后续追错方向；"本工具环境不可用"的结论曾因没做干净对照（残留进程未清、接入时机错）被两轮误判，用户纠正后实测脚本化流程完全可用。

正确做法：负结果归因顺序写死——先用代码打印常量、逐位核对自己设的地址与参数（不信注释和心算），再考虑工具能力缺失；重设观察点时两种地址形（两个映射窗）同时设点，并保留一个"执行链必写的相邻槽"作控制位，控制位命中后目标位的负结果才有效；宣告"某手段不可用"前先跑一个已知能命中的对照组（如软件断点）证明工具链健康；判定脚本的正则以本机工具实际输出串逐字核对、结论绑定工具版本；环境限制类结论必须有干净对照实验（全新端口、精确清场、正确接入时机）背书。

### 2.25 假设处决用四段式排雷地图：预言、判据、实测、结论，不带时间线；被推翻的结论单独立"降级台账"

把每个根因假设的处决过程按统一四段式重写并汇成编号表（假设编号加一句话结论），接手者一眼看清哪条已死、死于什么证据、哪条还开着——不带时间线是关键，时间线属于流水账层，蒸馏层只留机制与判据。静态审计的天花板要诚实标注："未坐实"与"已排除"是两个状态，混写会让接手者把未证结论当已证。姊妹件是"结论降级台账"：比死路清单更致命的是"曾写进文档的结论后来被推翻"——每个被推翻的结论单独立条（原结论、证伪证据、错在推导哪一步、波及哪些后续动作作废），不下调则后续会话继续在被废结论上盖楼。长链疑难的每版根因叙事标注证据等级与判别实验编号；证据强度分层——纯算术结论标"硬"（不依赖符号与快照），依赖符号归属或快照的标"未定"，硬结论的确定性不得传染给未定结论，且每条硬判据写明"它能区分什么、不能区分什么"；多症状同灭时优先找单一根因归并是恰当的克制，但要登记"若再现不同源同形症状则重开"的观察项，防止"缺陷已除"被推定成"所有同形路径已定谳"。归并解释之外，排除法收敛不等于定谳：必须有特征值反证（恒定毒值、恒定签名是把误归因翻案的钥匙）与指令级钉死。

正确做法：每个疑难缺陷文档配一张假设编号表，结论统一措辞分级（已排除/未坐实/当前主假设/未排除）；已被处决的假设不删，留作排雷地图；与死路清单并列维护降级台账；布置在未定结论上的实验互相引用，前提倒掉时批量作废。

### 2.26 检测器与自检的可信度要分级：位图有覆盖、旁路、时机三因，歧义判据的高命中数不是证据

数据结构型检测器（位图、影子账、自检函数）与打印探针是两套独立的假阴性来源。位图型检测器零命中的三种结构性原因：覆盖范围不足（位图只到某个上限，更小的机器上"看不见"不等于"没发生"）；旁路写入者（被检进程自己的堆绕过置位路径，别名写恰好漏过）；检查时机错位（只在分配时查、不在数据写入时查）。自检函数同理：完整性自检只统计某类槽位时，对"页表帧被别名占用"这类缺陷结构性失明——它给的不是安心是虚假安心；检测器自身还有"查询时机与置位时序错位"的坑，其指纹是"误报计数恰好等于全量事件数"。判据语义的干净度要分级：只在可疑路径触发、纯值域判断的检测器高可信；"合法复用本来就天天发生"类的歧义判据，命中数再大也不进证据链——曾有一案两次因歧义检测器的大数字重新怀疑别名方向，都被四类干净检测器的全零拉回。环形窗口型去重器的容量必须大于窗口期事件交错速率，否则同址复发被无关项挤出窗口，"零复发"是窗口太小的伪影。

正确做法：启用检测器前核对覆盖范围（位图容量对物理内存上限）、旁路（谁绕过置位）、时机（查与置的先后）；给每个检测器标可信级，歧义检测器的命中数不进证据链；"恒定计数等于事件总数"的输出先怀疑检测器时序而非被测系统；活锁判别用累计计数或饱和直方，不用定长环形窗；启用既有自检前核对其统计范围与被检缺陷的作用域是否相交，不相交就扩范围或明写"该自检对此类缺陷无效"。

> 来源：`NK4C-BUG-RISCV64-TRANSIENT-PTE.md` §4.1/§4.2/§8 条 2（检测器分级与自检盲区）、§6.2（数据写侧交叉检查）；`NK4C-WORKLOG.md` §续-110/续-111（环形窗漏判活锁）、§续-153（误报计数等于全量事件数）

### 3.1 页表位标志逐层 AND：新建中间层必须从叶子派生 USER 位

x86 的用户/特权位与读写位在地址翻译时逐层相与：中间层只填"存在+可写"时，用户页即使叶子齐全也会被中间层屏蔽，用户态首次访问即触发页错误；而纯软件的页表遍历只读叶子，完全看不到中间层缺位。同一机理在该仓两条独立代码路径各爆发过一次。

正确做法：新建中间层时从叶子派生——叶子含 USER 则中间层补 USER（Linux 的 `_PAGE_USER` 处理同型）；沿路径改动后刷新对应线性地址的翻译缓存。可写位无条件保留；禁执行位任一层生效即生效，无需传播。

### 3.2 把 IPC 状态寄存器放在被调用者保存寄存器上是三重身份冲突的高危移植决策

原版 C 只有 32 位 x86 与 ARM 形态的定义，32 位 x86 能安全复用 bx，靠的是用户侧封装宏在窗口内自行保存恢复。移植到 x86_64 后该寄存器同时承担三种身份——进程出生参数、IPC 状态寄存器、编译器活跃值载体（如对象引用）——内核任何在窗口外的写入都会摧毁用户活跃值，并被封装的保存恢复动作固化。真机曾实证内核交付零值导致整个调用期的对象引用失效、进程段错误。状态车道迁移到调用者保存寄存器后，"内核写污染旧寄存器"假说被正式证伪，但迁移本身引入新风险：一处同步函数漏改（仍写旧寄存器）被"该寄存器值普遍为零"的探针读数掩盖了两轮，通知位投递失败才暴露；同族第二例是次级返回车道与状态车道在 C 里共用同一寄存器、按调用互斥，拆开后漏同步一处。

正确做法：寄存器调用约定差异（调用者/被调用者保存）属架构级裁决，须多方案对比、配存活缝测试；车道迁移落地必须检索审计全部读写站点，并同步手编测试载荷的机器码字节；守卫测试用双干扰值（目标车道钉真值、被迁离寄存器钉毒值），断言交付后两边各归其位。判据一般化：跨特权边界存活的状态车道必须选"调用约定上本就不保证存活"的寄存器（新架构选调用者保存的参数寄存器天然免疫，是同一判据的反向应用）；每核专用寄存器的所有权必须唯一或有明确仲裁——一个寄存器被两个子系统当不同语义使用时，先裁决所有权再接任何新功能。

> 来源：`NK4B-WORKLOG.md`「P1」（三方案对比）；`NK4C-WORKLOG.md` §1.40/§1.49/§1.54（迁移落地与漏点审计）；`.review/zcode/edge1/FIXLOG.md` 迭代 22 补记（方案落地与假说证伪）；`minix3/minix/include/arch/i386/include/ipcconst.h:IPC_STATUS_REG`；`os/arch/src/x86_64/trap_stub.rs:sync_status_register_to_frame`；`os/libs/minix-sys/src/arch_trap.rs:ipc_trap`；`notes/rewrite/fork-syscall-rewrite/riscv-reviewlog.md` §C 坑对账表（状态车道判据与寄存器所有权行）

### 3.3 错误码符号域分家：跨界传输必须显式折算，成功值与错误码不可同槽混读

C 服务器按特定宏构建时错误码自带负号上线；Rust 内部用正号常量原样放进回复字段，用户侧就把每次报错读成了成功值（打开设备失败被当成拿到了描述符）。而成功返回值与错误码共用同一消息槽——读到的正数可能是字节数也可能是错误码，不折算就无法区分。内核调用层另有"正错误码原样上线"的既有约定，与 C 的负值约定不同。装载失败的正值错误码被上层"非负一律当成功"吞成笼统失败，真实原因（如执行格式不支持）永不上浮。

正确做法：在回复边界统一折算（正错误码转负上线），折算收拢在公共边界单个入口（幂等取负包装，已为负的直通，不动各条已正确的腿）；成功值与错误状态分开车道传输（专用带值收尾函数）；改返回值语义前先 grep 调度层既有对账；测试断言跟随线上契约的符号约定。同族第三面是"吞错三张面孔"，治理靠分流而非一刀切：接口签名直接返回单元类型，把错误在类型层面抹成无事件；回复腿按契约给兜底值本身对位 C，但真实失败码不落任何诊断面，把调试成本转嫁给下一轮取证；内部错误枚举转出的正值错误码走成功车道被吞成笼统失败。分流三问——吞的是硬失败还是尽力而为、是否在启动必经路径上、C 对位是否真的检查返回值——逐一过堂后只修硬失败点与启动路径点；尽力而为的 C 惯例形态原样保留，但真错误码必须落诊断面。机械防线两级：新类型包一层错误码专型（回复位上出现正错误码直接成类型错误，编译期拦住整族）；静态检查开"下划线吞 must-use 值"的强制告警做全仓机械门。

### 3.4 通知与挂起语义存在反直觉特例：超范围信号号恒空、状态机应答有严格次序

编号超出 64 位信号集的内核通知，其信号集永远为空，消费方只能按消息来源分类路由，不能读信号号；请求-应答走严格状态机（挂起→取件→应答→恢复执行），状态不符即拒绝。这些特例散落在 C 源里，凭直觉写就会错。

正确做法：涉足通知/挂起语义前先 grep 既有对账与 C 对位；消费方按消息来源路由而非信号号；状态机每个转换点逐一核对前置状态。

### 3.5 哨兵常量必须从权威定义派生并加绝对值钉死测试

`SELF`、`ANY` 这类特殊端点值是端点空间推导出来的特定数值。手写字面值一旦与权威推导值偏差——比如恰好撞上某个系统任务的真实端点号——宿主的罐头应答替身不校验端点语义、测试恒绿，真机上消息永不命中。

### 3.6 消息字段位次必须按 C 结构体逐格核对，不许拿"长得像"的另一族推断

C 消息是联合体，不同消息型的字段序不同（块设备族首格是文件偏移量，后续字段整体后移一个字长）。凭直觉猜位次后编译、宿主测试全绿，只有真机驱动收到垃圾字段（次设备号为零、授权失效）才暴露。

正确做法：位次表收敛到 `minix-types` 的单一权威点（`*_off` 常量族）；编码收拢成自带形状测试的函数；逐格钉值测试锁字节。

### 3.7 64 位地址经过 32 位消息车道必截断，宿主替身测不出，只有真机可见

用户空间链接基址与栈顶都在 4 GiB 之外，任何按 32 位承载的指针与长度字段都会静默截断；而 C 头文件的消息尺寸断言把载荷钉在 56 字节（只有 32 位形态），"照 C 布局加宽字段"这条路从根上不存在。宿主的罐头应答替身不校验地址语义，截断只在真机暴露。

正确做法：指针与长度走统一的 64 位车道（仓内判例链的既定裁决），以 `minix-types` 单一权威结构加编译期尺寸断言落地；编码解码双侧读同一车道图；测试钉入 4 GiB 以上的值，判别断言按"32 位截断下必失败"的地址设计。

### 3.8 状态机查"两半"：阻塞半与唤醒半、应答与清旗必须成对出现

C 用宏把置位与出队绑成一个原子动作，Rust 把引擎原语与进程表拆开之后就容易出现只做一半：被挂起的进程留在就绪队列被空转挑中上万次、或两个进程互等死寂、或清了页错误旗但进程永不复跑。回复载荷同理——统一收尾会无条件写回空结果，臂内已入队的带载荷回复会被覆盖，用户拿到零值。拆腿后还会出两类新病：同一挂起被两条路径各入链一次，请求队列自指成环、唤醒条件恒不触发（签名是"队列空判断恒为假"，后续请求者全部跳过唤醒）；交付完成臂漏清某个挂起标志位，残留位让进程被停车腿永久停住（C 在交付尾部无条件清理）。

正确做法：每个挂起点核对四件套——阻塞出队、唤醒入队、返回码写入、通知发送；C 里捆绑动作带前置断言（"已挂起则拒绝再次挂起"），拆腿后每条腿只许执行一次；对照 C 判断：凡出现"向输出消息写字段"的臂必须自己入队回复，收尾守卫按先入队者生效；用空转挑选计数、队列空判断恒假等签名取证。同族第三形态：进程就绪状态旗标的置位与清位必须走带出入队半的封装函数——裸清旗让进程看似可运行却不在任何调度队列里，永不被调度；评审对状态旗标的裸位操作单独标注。同族第四形态：完成臂的"不回执"是 C 里的合法第三态（C 真源对每个内核调用判断"等于不回执哨值才交付"），注释断言"本腿不会出现不回执"的分支，第一个真机 C 程序的兜底退出腿就把它证伪成内核恐慌——三架构同步补上不回执臂（语义为不写返回寄存器直接返回）。

### 3.9 照抄 C 位运算公式前先核两侧存储约定与运算符优先级

C 侧某权限掩码字段存的是反码（初值全 1），公式 `mode & 字段` 等价于标准语义"按反掩码过滤"；Rust 侧按自然语义存原始掩码后照抄公式，位运算不报错、静默给错值——默认掩码为零时新建文件的权限位全空。手工移植的移位表达式另有优先级陷阱：加法结合紧于左移，`基址 + 序号 << 位移` 会解析成对已加偏移的整体左移，非零基址直接算出越界物理地址。

正确做法：见到 C 位运算先核两侧"存的是掩码还是反码、初值是什么"；移位表达式写显式括号，并配能区分两种解析结果的判别测试；与手工耦合的常量在同轮补编译期断言；臂测试要覆盖入口计算段，不许直接摆放计算结果当现场（否则臂的前半段成为无覆盖区）。

### 3.10 失败与不可服务路径的三件事：补偿资源、给出应答、显式收口

失败臂漏掉资源补偿会累积耗尽全局配额（描述符表最终回满报错）；漏掉应答会让对端永远挂起等待；页故障的"不可服务"出口若只返回错误而不清挂起旗、不发信号，系统静默死锁，掩盖下游真实缺陷。收口补上之后，同一个空指针解引用会变成可见的段错误崩溃——这是缺陷被暴露，不是收口引入的回归。

正确做法：资源补偿抽成所有失败臂共用的单个函数；跨设备应答设计成续接体（等设备关闭回复落地才算收尾）；页故障不可服务终局统一走共用收口函数（发段错误信号+清页错误旗），与 C 对应路径逐行对位；每个错误臂配"零副作用+有应答"断言。

### 3.11 设计判读先分"防御性缓解"与"结构性消除"：直接映射判读为例

判读一段 C 机制是本质要求还是历史遗迹，方法是找它的物理根因。VM 的用户态与内核态两份直接地址映射指向同一物理页、仅特权位不同——这不是冗余，因为一个页表项的特权位不可能同时取两个值，是特权级硬件的必然；而 C 里围绕 32 位地址短缺诞生的页表借用与备用队列机制，在根因（物理地址到稳定虚拟地址的换算）被直接映射结构性消除后，可以整体删除。多位外部评审独立收敛到同一判读，交集判读可作为设计定稿的置信依据。

正确做法：设计演进区分"防御性缓解"（保留）与"结构性消除"（根因消除后机制降级为历史文档）；架构差异压缩为常量抽象（分叉留在底层，上层保持统一）。

> 来源：`AI-chats/cross-review.md`（三位外部评审的独立判读节）

### 3.12 停车-唤醒窗口内对陈旧调用帧的同步直写是跨路径状态撕裂的典型形态

内核完成调用的路径会对调用者消息缓冲做同步回执直写；进程被虚拟机代为停车、恢复回用户态继续事件循环后，旧调用帧已死——下一次同类调用的同步完成写到陈旧地址，恰好砸中自引用槽（真机实证：自引用槽清零→进程段错误）。C 对位：该直写只存在于系统调用腿，陷阱腿的状态经寄存器返回从不写调用者缓冲。配套陷阱：同一上下文存在两条保存路径（缺页转发保存与陷阱保存）且无互斥，停车-唤醒间隙陈旧帧可覆盖活跃帧。

正确做法：给挂起上下文增加"恢复时跳过同步回执"的门标记随上下文保存恢复，直写腿按门分道；多段挂起重派时门标记必须从旧上下文继承（漏继承会复发）；双保存路径加互斥断言；判定写者身份用全量日志的配对节奏（设置与使用成对出现）。

### 3.13 自旋锁的比较交换失败无法分辨"继承本 CPU"与"他人持锁"，两步原子写再埋一致性窗口

中断入口用比较交换试锁，失败被当作"继承被中断上下文的锁"，但它无法区分本 CPU 内核帧持锁（应继承）与另一 CPU 持锁（必须自旋）——把后者当前者，两个 CPU 同时可变访问进程表撕裂指针（单核永不复现）。改为锁标志与持有者两个分离原子后，两次写之间又有一致性窗口：开中断瞬间被打断的处理者读到"已锁但持有者非己"，自旋等待一个永不登记持有者的持锁者。

正确做法：根治是单字所有者（原子整数，负值空闲、非负为持有 CPU）：获取=单条比较交换、释放=单条写空闲、继承=读出等于自身，语义对位 C 的关中断自旋锁；所有中断与陷阱入口统一走"继承或自旋"入口。

> 来源：`NK4C-WORKLOG.md` §1.50/§1.52；`os/kernel/src/smp.rs`（单原子大内核锁）

### 3.14 只认直接映射窗口的虚拟转物理函数对窗口外地址产出伪值——内核自身地址的拷贝必须走真页表

虚拟转物理函数只识别两个直接映射窗口，内核镜像高半区地址（内核栈、静态数据、堆分配）落入兜底分支产出野值，再以"物理地址"名义直传、不经页表遍历——一段"多核竞态"嫌疑被证伪为确定性换算错误。

正确做法：内核自身高半区地址的拷贝站点统一改走"进程地址引用"（每进程页表都映射高半区，真遍历得正确物理地址）；回栈诊断同理禁用"虚拟转物理再转回虚拟"的往返，直接读已映射地址。姊妹形态：跨地址空间访问用户内存时，用户虚拟地址绑定的是当前地址空间——在接收者的陷入上下文里直接解引用发送者 VA 会落到错误空间（通用保护故障实锤）；统一走"发送者页表根翻译→物理地址→内核直接映射窗口"的通道，页内偏移由翻译函数带出、不再二次叠加。本通道的覆盖面（续-76a 定格）：senda 读写腿、跨空间拷贝、以及 IPC 消息本体拷贝 `copy_msg_from_user`/`copy_msg_to_user`（`os/kernel/src/ipc.rs`，`[ARCH: user-copy-via-dm]`）均已并入——特权态直接解引用用户 VA 的形态在三架构上全部退场，riscv 不再依赖 sstatus.SUM、x86 SMAP/aarch64 PAN 的同型隐患一并消灭。

> 来源：`NK4C-WORKLOG.md` §1.51；`NK4C-RESUME-PROMPT.md` §3.2；`os/arch/src/arch/direct_map.rs:DirectMapArch::virt_to_phys`；`os/kernel/src/ipc.rs:copy_via_root_pages`

### 3.15 内存耗尽诊断必须区分"记录表满"与"池字节尽"；抬静态常量会平移布局触发缺页服务者自缺页

耗尽打印是十六进制计数——"大块配额用尽"实为记录表满而空闲页充裕（过早报耗尽）；抬表后换签名：大块分配只从连续游标发页、从不查已释放单页的回收栈，数百个已释放单页永久搁浅；再把常量抬大一档（静态区随之增长）平移了虚拟机栈基址、越过唯一预物化的帧页——虚拟机（缺页服务者）对自己启动的缺页递归恐慌。三个前置缺一不可，单修任何一个都不够。

正确做法：耗尽诊断先分"表满"与"游标尽而回收栈有货"两类；单页请求走单页供给（与逐页归还对称，Linux/Redox 的零阶分配同构）；静态数组尺寸配编译期不变量断言；真前置是启动栈跑道不足（对位 C 的保留映射队列），与常量同轮同修并用多档实验矩阵验证。同族判据：临时缓解的边界是布局敏感的启发式（常量在剃刀边缘布局上翻转崩溃形态），原则解（启动前把缺页服务者自身的工作内存整片预映）不依赖布局——临时缓解必须文档化为"已评估的临时形态"并警示布局敏感，防止被误当终态。

> 来源：`NK4C-WORKLOG.md` §1.59–1.61、§1.92–1.95；`os/libs/minix-rt/src/alloc.rs:alloc_big/supply_pages`；`os/arch/src/arch/boot.rs:VM_STACK_SIZE`；`notes/rewrite/fork-syscall-rewrite/riscv-reviewlog.md` §D.6（自举内存预映缺件与临时形态定性）

### 3.16 不可执行位生效后，区域模型必须承接可执行语义且两条填充腿组位一致

装载器每段按"读写执行"全开装载（对位 C——32 位没有该位，无害）；区域旗标转换只消费写位丢弃执行位，缺页填充按"可写→读写"派生——不可执行生效下读写即不可执行，可执行文本被判死，取指缺页每轮按同旗标"成功"重映射成活锁。修一处后同族病灶在同文件的另一条填充腿复发（重复缺页计数 7 万降到 15 量化实锤）。

正确做法：区域旗标加可执行内部位、转换对称消费执行位、缺页填充腿与预填充腿同规则承接（按段属性派生）；同时注意 C 忠实边界——对外查询接口有意不外泄执行位（C 从不报该位），注释钉死"勿在此补"。

> 来源：`NK4C-WORKLOG.md` §1.74–1.78；`os/servers/vm/src/mmap.rs:to_vr_flags`；`os/servers/vm/src/cow_exec_pf.rs:sync_slot_pte`

### 3.17 指令合法性取决于异常级与栈选择器的当前状态

两个真机实证：栈选择器指向当前异常级自己的栈指针时，写"另一视图栈指针"寄存器是未定义指令——三处保存恢复舞步全部踩雷（签名是同步异常）；无第二阶段地址转换的体系里，"全部一级转换失效刷新"指令同时作用于不存在的一级，同为未定义。

正确做法：被异常入口汇编接管的活动栈切换在宿主函数里做诚实空操作（普通函数里手改栈指针会让尾声从孤儿帧读返回地址）；整根切换用"全量刷新"的安全变体并补同步屏障；每遇到"从未观测到"的指令，先查它对当前异常级/栈选择器组合是否合法。

> 来源：`NK4C-WORKLOG.md` §1.109、§1.115；`os/arch/src/arm64/protection.rs`；`os/arch/src/arm64/tlb.rs`

### 3.18 切换地址空间前必须确认执行流不在被切换的映射里；跨镜像续跑只许追加式初始化

内核以库形式内联进引导载体、代码全落低半恒等映射时，"跳向高半"实际没离开低半——首次切换页表根加全量刷新后恒等映射消失，下一条取指即未定义（签名：切换前置打印有、后置打印永远没有）。续跑路径复调完整初始化则会对已启用的页表根清零，当场摧毁自身映射与设备映射；两个镜像各有独立静态副本，漏掉根地址登记会让下游读空。

正确做法：独立内核 ELF 链接高半基址，引导载体经引导信息块交接后绝对跳入高半入口，执行流全程不依赖将被切换的映射；续跑初始化拆成纯追加阶段（校验不触页表→补登记→交接→建直接映射→跳转）；分配游标用续跑构造跨镜像接续；跨界结构补 C 布局标注与尺寸编译期断言。第三架构同族判例补一条：为目标进程临时新建的页表根若未铺内核高半映射，写基址寄存器切换后的第一条内核取指即落入未映射区——且此时向量基址已随切换失效，表现为彻底静默（无异常码、无恐慌打印、任何路标都出不来）。遇到"切址后全静默"先转储目标根、静态检查其是否含内核映射，而不是怀疑恢复汇编；为其他进程建根的构造点与为引导进程建根的构造点共用同一段映射铺设代码，缺铺设即结构性缺陷。

> 来源：`NK4C-WORKLOG.md` §1.114、§1.115；`os/boot-shim/src/main.rs`；`os/libs/minix-boot/src/handoff.rs:BootHandoff`；`os/kernel/src/lib.rs:arch_boot_resume_high_half`；`NK4C-WORKLOG.md` §1.120续-98（第三架构进程根缺内核映射的全静默签名）

### 3.19 异常分类必须逐类别处置；架构的读写位位置凭直觉平移必错

缺页被当致命异常直接恐慌打死时，延迟填充的正常缺页被静态误诊为"映射覆盖缺口"（次轮翻案）；把 32 位 x86 页错误码的读写位位置（低位）平移过来取位，实际该位在指令 syndrome 的固定第 6 位——取错位让写时拷贝首写被报成读、只读重映射、无限重缺页活锁。

正确做法：异常入口按异常类别门控分道（系统调用/取指缺页/数据缺页/外部中止），分类谓词集中一个架构无关函数并配全量编码期望表；读写位从 syndrome 固定位取；段错误臂先存帧再发信号，末尾必须走重调度出口（否则出队后回到已死进程单核空转）。

> 来源：`NK4C-WORKLOG.md` §1.116；`os/kernel/src/trap_dispatch.rs:classify_abort_disposition`

### 3.20 每次陷入由硬件重装内核栈的体系换成单次装载体系后，阻塞路径必须"弹帧后再切换"

32 位 x86 每次陷入由任务段硬装内核栈，aarch64 的当前异常级栈只在启动时装一次——阻塞式接收从调度路径退出时从不弹出进入序言帧，栈指针逐轮下行踩穿静态数据直到间接跳转垃圾地址。配套：给进程登记写线程指针寄存器的副作用被内核库的占位初始化用零覆盖真实栈基，首次系统调用把帧存到负偏移静默中止（一度误判中断覆盖）。

正确做法：阻塞决策走专用返回值通道（继续/重调度/停车三态），汇编尾声按三态分别精确弹帧后转重调度入口；每 CPU 栈基写线程指针寄存器，回用户态前显式重装；带副作用的初始化加"非零哨兵"校验防占位值覆盖。

> 来源：`NK4C-WORKLOG.md` §1.113；`os/arch/src/arm64/trap_stub.rs`

### 3.21 OS 层禁止硬编码架构私有寄存器表偏移与无条件发射特权指令

内核按"字节偏移 80"写用户寄存器——该偏移在 x86_64 恰是返回值寄存器，在 aarch64 映射里是第 7 参数寄存器，而恢复代码读的是第 0 寄存器，唤醒接收者的返回码整个写丢（停车机制落地前该路径不可达，宿主替身看不见）。同族：页表直写函数无条件发射特权刷新指令，虚拟机经用户态直映射通道调用即同步异常（x86 同名函数早有通道门控）。

正确做法：上下文抽象增加按语义命名的返回值寄存器访问器（各架构自实现）；特权指令按调用通道门控并加调试断言；新增跨架构路径时 grep 全部既有硬编码偏移。该形态在第三架构上原样复发过一次，补充了组合缝形状：通道枚举与按通道选窗口的逻辑早已存在，唯独刷新指令没随通道门控——"修复所需的抽象骨架已在，新语义只接到了一半调用点"是这类缺陷的固定形状，编译器与类型系统都不拦"枚举参数用了一半"。修通道类缺陷时对枚举的每个消费点过一遍门控清单，三架构保持同构形态便于审计；删掉无条件刷新必须给出不变量论证（启动期只写不存在到存在的映射、值为零的项不进缓存）并显式登记残余缺口。

> 来源：`NK4C-WORKLOG.md` §1.111、§1.113；`os/kernel/src/proc.rs:CpuContextArch`；`os/arch/src/arm64/paging.rs`；`NK4C-WORKLOG.md` §1.120续-77a（riscv 刷新指令通道门控闭合）；`notes/rewrite/fork-syscall-rewrite/riscv-reviewlog.md` §A.5；`NK4C-WORKLOG.md` §续-164（登记的残余缺口兑现：只读到可写升级时跳过刷新的前提不成立，旧译文存活使填充永不生效——内存已写而翻译未生效，两层判据缺一不可；登记在案的残余缺口在主线成修时顺手关闭，或至少让触发形态出现时能立刻对号）

### 3.22 "调用方看到成功、字节没落地"的静默失败家族

四例同族：授权表被碎片成每组件一张、后注册者整体覆盖内核侧单表（C 不变量是每进程一张全局表），一次性组件销毁后内核持悬垂地址读到陈旧槽；授权请求的发送方字段填了哨兵值（非法端点），内核解析必败而调用侧用"let 下划线"吞掉错误，读到全零缓冲仍返回成功；状态查询回执填好局部结构后从不拷回用户授权，模式位恒零；授权越界是硬失败非截断，手写窗口小于用户结构体被整块拒绝。

正确做法：共享单表全局唯一，组件只借注入引用；哨兵值永远不当真实端点参数（用具体端点常量）；传输层禁止静默吞拷贝错误；回执腿配"拷出"断言；窗口尺寸统一从类型尺寸派生并用布局钉值测试。

> 来源：`NK4C-WORKLOG.md` §1.23–1.24、§1.64–1.65、§1.106；`os/kernel/src/grant.rs:verify_grant`；`os/libs/minix-sys/src/grant.rs`

### 3.23 线上槽步长必须从类型派生：编译期断言是常量的来源，不是事后证明

一笔在制品同时带两缺陷入仓：拷贝腿两臂方向与契约相反（读腿把清零缓冲写进用户表，一条消息都投不出去）；槽步长手写常量与同文件尺寸断言自相矛盾，越界读构成未定义行为并成为后续启动死锁真根因。而取证探针只验证了"范围检查通过"，没验证读到的字节内容——检查通过不等于数据正确。

正确做法：槽步长用类型尺寸表达式直接当常量消费，编译期断言锁一致性；线上读写腿逐臂与文档契约对拍；取证读数必须含原始字节值，不只报"通过/失败"。

> 来源：`NK4C-REVIEW-REPORT-20260927-R3.md`（自审发现节）；`os/kernel/src/ipc.rs:WireAsyncSlot`

### 3.24 每 CPU 架构不变式必须内核自持，不依赖固件遗留

引导处理器经固件启用了不可执行位、应用处理器早入口汇编只置长模式位——同一访问主核成功、副核风暴（页错误错误码恒为同一保留位违例值），叠加每次启动两种内存布局形态交替，构成"崩溃点逐轮漂移"之谜的完整答案。修复首版写错位（置了保留位）仍风暴，实证正确位才是开关。

正确做法：副核早入口显式置位 + 主核页表启用处显式置位（不依赖固件遗留）；每 CPU 初始化收口加特性位断言，把非法态从静默风暴变快速失败。

> 来源：`.review/zcode/edge1/FIXLOG.md` 迭代 27–29；`os/arch/src/x86_64/ap_early_entry.rs`

### 3.25 C 的有界循环换成 Rust 全量迭代即越界选座

C 对负载表按"处理器计数"循环、全死回落引导核；Rust 侧账本是定长 32 元素数组且初始化为"全员零负载"，次级核标记死亡后重选扫到从未存在的"幽灵座"（仍是零负载、最轻）→ 选中越界编号 → 内核校验拒绝 → 错误码折算成权限拒绝 → 初始化进程活锁。单核验证恒选零号故免疫，多核才暴露。

正确做法：迭代一律以拓扑计数封顶（取计数与账本长度的较小值）；回落基准同步封顶；回归测试构造"账本长于拓扑+次级核全死"场景断言回落零号，断言对含缺陷实现必失败。该案补三条定性纪律：区分"触发器"（谁让缺陷显形）与"根因"（哪行代码违约）——次级核未就绪只是触发器，无界扫描才是缺陷；实现注释承诺"超出的槽位永远不会被触碰"而实现做不到时，文档承诺与实现行为的矛盾处本身就是信号；单核口径的验证让按核数选座位的缺陷天然隐形，多核缺陷的回归要单核多核双口径。

> 来源：`NK4C-WORKLOG.md` §1.118；`os/servers/sched/src/cpu.rs:pick`；`os/kernel/src/sched.rs:validate_cpu_param`；`NK4C-WORKLOG.md` §1.118（修复）（触发器与根因分层、注释承诺矛盾、双口径回归设计）

### 3.26 C 的三态返回值压缩成 Result 二态会把"无结果"变永真

C 的非阻塞收尸调用返回正 PID（有退出）、零（有活子）、负（无子）三态，循环以"大于零"为继续条件；译成"结果正常即继续"后，零也是"正常"——收尸环退化成每秒数千次的无界忙等（真机实测数万圈），洪流掩盖下游一切诊断。根子在上层把"消息类型非负一律当成功返回"。

正确做法：翻译 C 三态返回值时用带谓词的匹配（成功且载荷大于零才继续）；同族调用点逐一对位 C 原文；各加"零值出口"回归测试（喂单个零值即应退出，含缺陷实现会二次调用）。两点扩充。其一，同族缺陷一次枚举修净：修一处后全仓检索同型环（结果类型为"成功即继续"的收尸环与排空环），另两处同型变体同轮修掉或登记结构债，不留给下一轮。其二，"零值出口"回归测试的设计手法——喂单个零值返回即应退出，含缺陷的实现会对替身发起超额调用，天然判别，不需要观察业务结果。

> 来源：`NK4C-WORKLOG.md` §1.117；`os/commands/sbin/init/src/runcom.rs`；`os/servers/rs/src/trap_api.rs`；`NK4C-WORKLOG.md` §1.117（修复）（同族枚举修净与回归设计）

### 3.27 C 的 OR 位标志被互斥枚举替换时，谓词必须覆盖整个位窗口

C 的生命周期字段是位集，僵尸化只置僵尸位、退出位留给清理阶段；Rust 换成互斥枚举后僵尸化把"退出中"整体替换为"僵尸"——"是否退出中"谓词对每个正常退出的进程返回假，父进程管理器直接恐慌（真机按槽实锤）。

正确做法：互斥枚举覆盖 C 位测试语义时，谓词写成全死亡窗口并集，调用点逐一对位 C 位读；建模前先审"这个枚举替换是否丢失了位并行语义"。

> 来源：`NK4C-WORKLOG.md` §1.63；`os/servers/pm/src/mproc/lifecycle.rs:is_exiting`

### 3.28 无显式判别值的枚举做整型转换得到的是序数不是线路号

字符设备请求枚举没写显式判别值，"按整型发送"得到 0..6 的序数；线路号本应是"基址+序数"。驱动侧解码按"收到的类型减基址"查表落空归入未知 → 分派置空、既不回复也不报错 → 发送方永久等待。修两处即打通追了多轮的控制台链（真机标志行首次出现）。有显式判别值标注的同族枚举转换则合法，不能一刀切。

正确做法：线上消息类型一律走"取线路号"方法；回归钉三件事——线路号等于基址、驱动解码往返成立、载荷逐字节回读；按枚举家族穷举检索裸整型转换清理同类。

> 来源：`NK4C-WORKLOG.md` §1.104–1.105；`os/servers/vfs/src/cdev.rs:open_request`；`os/libs/minix-chardriver/src/driver.rs:classify`

### 3.29 一个字段两种口径（容量与累加）在基址非零的架构上必炸

物理页按绝对页号索引位图，内存基址非零的架构上页号从数十万起，而按"可用页合计"建的位图容量只有几千——分配释放全越界。C 里本就是两个量：位图容量覆盖地址空间、记账合计只累加可用页；把容量式新值仍喂记账会凭空抬高统计总量（评审拦下）。

正确做法：两个字段各自命名、各自文档与校验断言、构造点同步；位图容量取"区域上界页号"，记账合计单列专供统计。

> 来源：`NK4C-WORKLOG.md` §1.111；`os/servers/vm/src/boot.rs:total_pages`

### 3.30 每 CPU 化不是单点修复：闲置副核必须真正安静，共享的全局镜像与单怠速进程都是同类残留

多核启动的失败族有一条共同病根——每核化只做了一半。三个真机坐实的残留。其一，闲置副核的"停车"名不副实：空闲函数按核分支里"副核停掉本地定时器"的那一半没搬进来，一次性定时器每 tick 自我重装，使停止调度的副核仍高频收时钟中断、在已切换的地址空间下重入内核，与主核竞争并腐蚀虚拟机用户栈；十四轮取证、十二枚探针全阴性的统一解释就是破坏者是这条行为路径，不在任何内核写腿上。其二，所有核共用一个怠速进程槽（C 为每核初始化独立的怠速结构、各自带停止状态），各核记账并操作同一份上下文。其三，当前页表根用全局原子变量做软件镜像（C 读的是每核硬件寄存器，天然每核独有），闲置核经空闲切换写入即污染其它核的跨地址空间拷贝。修掉一处后启动推进到新阶段，新失败大概率是同类残留。

正确做法：修掉一处每核化缺口后主动审计整个每核面（怠速进程、当前根、每核指针）的全局共享残留，C 源里"仅多核步骤省略"式的自陈注释就是现成的审计清单；对位 C 的空闲路径整块搬运 if 分支而不是单条语句；判定"副核真安静"查定时器是否真停而非调度器名义状态；全局镜像变量在多核下的正确性等价物是硬件寄存器，注释自陈"将来要每核化"的全局变量当定时炸弹登记，迁移时找已完成的同类迁移做模板；每核访问器分容错档（返回可选值带回落，用于可能早于状态安装的路径）与断言档；启用副核跑用户进程前补齐配套三件套（中断入口清怠速并重装定时器、入队唤醒的跨核中断、调度亲和守卫），补不齐就用过渡守卫并按 4.6 登记移除条件——声明的多件套修复不允许只落其一直接上真机评估（一次实测：只补唤醒半使进程跑起来，恰好撞进尚未根治的跨核腐蚀，净效果劣于不修，回滚）。

### 3.31 大内核锁的串行化不等于每核数据结构的语义：锁外使用使"共享队列等价于全局队列"的论断为假

设计冻结文档自辩"共享就绪队列加大内核锁串行化，行为等价于单一全局队列"。等价性为假：锁串行化的是改队列的写操作，但挑进程是不移除队首的读，且锁在进程无锁跑用户态之前就已释放——处理器甲挑中进程并放锁进用户态，处理器乙再取锁挑中同一队首进程，该进程的入口风格字段已被甲的首次恢复清掉，乙的恢复读到空即崩溃。C 真值是每核一套就绪队列（源注释明言"总用本地处理器的队列"），这是承重正确性而非可合并的负载均衡优化——把每核结构类比成"可合并的优化"是范畴错误。单核验证恒选零号核故免疫。

正确做法：审计冻结设计决定的等价性论证时，检查锁保护的对象集合是否覆盖全部读写——不出队的读加锁外使用等于串行化无效；引用冻结文档论断前先对 C 源码验证，错误论断显式翻案登记；修复选型触及被冻结的设计决定属架构裁决级，上报用户选型；多核串口不可得时，结构性代码分析是合法且高效的替代取证通道。

> 来源：`NK4C-WORKLOG.md` §1.120续-53/续-54（论断翻案与每核队列落地）；os/kernel/src/sched.rs

### 3.32 跨持有者的元数据同步逐腿核对：换页表根必须通知内核，"某平台没炸"可能是资源复用的巧合正确

微内核里页表内容由用户态虚拟机构造、页表根由内核装载且内核从不主动读虚拟机的数据结构，于是"换根必须补发通知"是跨持有者铁律。执行清理腿漏发通知后，内核手里的根指针停在已拆除的旧根上，处理器对首文本页无限重复缺页。两个放大因素。其一，x86 平台销毁页表时把页表页归还分配器、新建时大概率复用同一物理页——新旧根恰为同一页，缺陷被巧合掩盖；不归还页表的架构必然新旧根不同页，立刻暴露。"逻辑上应无条件成立的不变量只在部分平台成立"时，不信那个看起来对的平台，以架构无关的代码事实为准——x86 的免疫毫无设计保证，分配器策略一变同样爆发。其二，C 源码丢弃绑定函数的返回值，通知失败也照样回答成功——静默陈旧的温床；重写时改为失败闭合（失败即内部错误向上抛），把"悄悄烂掉"变成"当场报错"。定位线索的结构值得记：同一铁律在代码里被遵守了两次、遗漏了一次，二比一的不一致本身就是最强定位信号。

正确做法：对"谁建、谁用"跨持有者的元数据，枚举全部实现站点做完整性核对，发现实现分歧优先怀疑缺失的一边；对"名字温和、职责关键"的 C 对位函数做语义注释升格；注释声称"会自动发生"的通知必须有代码事实支撑；通知或登记类调用的返回值逐处过堂，C 丢弃返回值的站点在重写时显式决定失败闭合或注释论证吞错理由；修复自身做时序影响论证（新调用在什么条件下波及谁）并写进修复说明。

> 来源：`notes/rewrite/fork-syscall-rewrite/NK4C-AARCH64-EXEC-REBIND-LIVELOCK.md` §2/§4/§5/§7/§8；`NK4C-WORKLOG.md` §1.120续-35/续-36；os/servers/vm/src/exit.rs:handle_procctl_clear

### 3.33 陷入边界上的消息必须显式物化：用户态最后一次写对编译器建模不到的观察者不可见

同一块消息内存活在三个世界——语言承诺顺序一致、编译器允许把写滞留寄存器或推迟合并（只要本函数后续没人从该地址读）、内核是编译器建模不到的按地址读物理内存的观察者。三个发作条件：优化构建（调试构建每条赋值立刻落内存，缺陷消失）、跨界观察（内核按用户地址读）、时序运气（寄存器压力与指令调度决定写是否滞留——加一条打印即翻转，造成"架构相关"假象，实为两架构都站在悬崖边、一个寄存器分配运气好）。接口形状使缺陷从可能变必然：消息指针被转成整数塞过内联汇编边界后，借用分析与副作用分析都不再把它与任何内存关联——"指针转整数塞过汇编或外部接口边界"就是缺陷存在的充分形状。判别针法：把"读一次消息类型"的探针函数标为不内联（否则针被优化器揉进宿主函数、改变它要观测的寄存器分配），这一次无害装载把滞留的写逼落内存——同源码树的有针无针对照成为定谳证据，"无害读取改变行为"本身就是编译器成因的指纹。修复是一道读屏障：对整个消息对象做一次不可省略、不可重排的读取并丢弃结果，替内核向编译器出示"有人会来读"的证明，开销仅一次寄存器装载；插入点只选内核会读消息内容的腿且每条腿写明插或不插的理由（纯出参方向不需要、内核只读端点号的通道不需要、当前形态未命中窗口的登记开放项——不插不等于忘），特性门控只覆盖真实接入的架构（未接入的不假装防护）。被拒方案各有理由：汇编级整块内存破坏提示粒度过粗；把义务摊给每个调用方必然有人忘（修复点收口到库边界使契约只有一个执行者）；按值传参属架构演进、不该由单个缺陷修复顺带通过。

正确做法：审查所有"指针转整数塞过汇编边界"的接口形状；跨界入参缓冲在陷入前用一次整体读取物化，出参方向不需要；移植 C 代码时把"C 恰好没炸"依赖的实现惯例（volatile、统一联合体、非内联库函数边界）逐处显式化，不做"C 没问题所以照抄结构就安全"的假设；对编译器行为的成因注释禁止超出观测支撑的断言（反例可推翻过度断言时降级为诚实表述），未复现的同形路径登记开放项而非顺手加针。

> 来源：`notes/rewrite/fork-syscall-rewrite/trap-boundary-message-materialization.md` §2/§3/§5/§6/§7；`NK4C-WORKLOG.md` §1.120续-21/续-22（栈中性判别针与成修）；os/libs/minix-sys/src/ipc.rs:commit_message_to_memory；`NK4C-WORKLOG.md` §续-156~158（指纹的必要非充分：强制真实加载后读数仍不一致即内存真被改写，编译器层被排除——"同一数据两次读不一致"按单次求值合并、函数内埋点、强制真实加载三级递进，全过才归因内存层）；`STRUCTURAL-DEBT-REGISTER-20260930.md` §SD-31（逐陷阱点手工插屏障脆弱，汇编级整块内存提示更原则化，登记未决）

### 3.34 C 对位移植的三类结构性漏项：检查顺序即契约、每轮排水原语必须有人调用、阻塞与非阻塞按调用点分叉

三例同源——"语义等价"直觉替代了逐处对账。其一，C 把零长度检查放在一切地址工作之前（返回域错误），重写版排在页表解析之后：零字节请求带着空集合的悬垂哨兵指针走完整个地址解析，未映射即挂起，下游连锁冻结到全系统；语言层还有个配合陷阱——零长集合的数据指针是悬垂哨兵值而非可解引用地址。其二，C 主循环每轮调用一次排水原语补发排队请求，重写版排队腿在、补发原语在、生产调用方为零——每个组件局部看都正确，系统级静默吞工作且无任何错误码暴露。其三，C 里对同一对端的两种回复语义各有机理（关键回复阻塞加失败即崩溃，普通回复非阻塞），重写版统一成非阻塞，把竞态窗口交给调度时序；"看起来健康"的架构可能只是靠时序运气通过——一个缺陷只在单架构显形时，先问另一架构是真免疫还是时序运气。

正确做法：翻译时对"检查顺序、排水或补发原语是否有生产调用方、阻塞与非阻塞"三类做逐腿对账表；为零长这类第一守卫配"顺序钉死"测试（不可解端点加零字节仍是域错误，而非成功）；对每个入队原语检索其配对排水原语的生产调用方，为零即缺陷；用装针扰动或多跑分布检验"另一架构是真免疫还是时序运气"；启动推进但冻结点未破时，把已修项理解为排干外围的水——排除法证据而非失败。

### 3.35 C 在分支之前无条件执行的副作用必须保持在分支之前；跨函数不变量要枚举全部实施点

C 在发送接收调用的发送半之前无条件置"回复挂起"标志（注释明言使通知不能打断该调用）；重写版把置位搬进了某一条阻塞分支且晚于发送——而走哪条分支取决于目的地此刻是否停车，这本身是调度时序，正是布局敏感翻转的机制来源。漏置的后果链很长：通知扫描腿不被跳过、挂起通知可冒充回复被抢先消费、上层误判失败、用户收到权限错误。同一不变量还有投递侧另一翼（补投通知前必须检查目标是否挂起回复），两翼对位 C 同一处语义、缺一即漏；置位前提修好后，新可达路径上的清理对称性（各完成路径都要清标志）要专门补查。

正确做法：翻译 C 时凡"分支前无条件执行"的副作用保持在分支之前，绝不搬进某条分支；识别这类跨函数不变量后主动枚举其全部实施点（消费侧检查加投递侧门）逐点对账；改动使新路径可达时，让评审专门检查新路径上的清理对称性。

> 来源：`NK4C-WORKLOG.md` §1.119续-2/续-3；os/kernel/src/ipc.rs（交付清挂起位）

### 3.36 "相同则跳过"类优化必须比较硬件实时寄存器，软件镜像与硬件可以合法地分叉

切换地址空间前先比较软件镜像"当前根与目标根相同则跳过装载"；但镜像与硬件在两条路径上会合法分叉——续跑路径单独写镜像不写硬件；虚拟机为未运行进程改页表根既不写硬件也不更新镜像。比较镜像即假阳性跳过，处理器跑在错误的页表树上、读到错误内存。x86 从未显形，因为读硬件寄存器的指令总返回实际值。

正确做法：凡"缓存态对硬件态"双记账的跳过优化，判据读硬件寄存器（三架构各一条读指令实现），相等时防御性同步镜像；续跑与交接路径上镜像与硬件的每个写入点对账（谁写硬件、谁写镜像、是否成对）；修复后用三方对照（硬件值、登记值、镜像值）验证闭合；后续证据推翻归因时回改工作日志定性，多个修复不笼统记成"修好了同一个缺陷"。

> 来源：`NK4C-WORKLOG.md` §1.120续-18/续-21/续-22；os/arch/src/x86_64/tlb.rs:get_active_root（三架构同型）

### 3.37 进程外代写页表的服务器，写完页表项必须按变更类型刷新地址翻译缓存

用户态虚拟机在自己的缺页处理里对子进程页表做三路写——同帧改权限、换物理帧、新建映射——全程零翻译缓存失效（对整个服务器目录做检索、命中为零是结构性证据）。体系结构要求存在到存在的权限变更显式失效；换物理帧不失效旧译文，则用户态重执行的写命中缓存的旧译文、写进父帧而读自新帧，恰好产出"单字陈旧而邻字正常"的签名。它与内核恢复点的刷新缺口是两条不同的腿（权限变更腿对换帧腿），混同会修错地方。

正确做法：任何代写他人页表的组件按变更类型刷缓存：权限变更显式失效、换物理帧失效旧译文；跨架构审计先用全量文本检索建结构性证据（命中为零即整族缺口），再上真机判别针（换帧前后打物理帧号、同一物理帧经不同映射各读一次，区分"写进错帧"与"写丢失"）。

### 3.38 riscv 栈切换寄存器的生命周期是一条显式清单：哨兵初值、停车重固定、向量基址恒描述即将运行的模式

riscv 没有可占用的每核栈交换专用槽之外的余裕，内核栈基只能放内存格（单核成立，多核要改每核数组，注释钉死）；初始化需要零基址的一次性哨兵——否则交换寄存器被清零，第一个用户态陷阱把栈指针换成零直接毁内存；恢复到用户态的腿必须在返回前重新固定交换寄存器——停车机制打破"每次陷阱都原路返回"的不变量后，交换寄存器里停着被停车进程的用户栈指针，不重固定则下一个用户态陷阱把内核帧建在用户栈上。向量基址同理：内核腿尾声按保存的特权模式重选向量基址，使其恒描述"即将运行的模式"——否则内核态定时器中断进到用户态入口约定里，交换毁内存（这是停车机制落地时新发现的缺口）。配套结构前置：阻塞式接收需要陷入汇编尾声支持"内核决策不返回调用者"的分派返回值（分派函数返回单元类型在结构上无法表达阻塞语义），这是移植的真正工作量所在，而非业务逻辑。

正确做法：把"谁写它、停车期间停着什么值、恢复腿是否重置"作为独立清单核对；写不变量注释时写明"由哪两条路径的什么指令对维持"，新增第三条控制流路径时逐条核对不变量的成立范围是否被悄悄缩窄；按来源模式选入口约定的地方（向量基址、交换寄存器、内核栈基）以"即将运行的模式"为准绳做状态机核对，跨模式嵌套返回列为必测路径；移植阻塞系统调用先核对陷入尾声有无决策分支通道。

### 3.39 跨架构异常语义不可直译：写判别按本架构原因码重写，系统调用指令的返回点步进是本架构义务

两处直译陷阱。其一，写缺页判别用"错误码低位与一"——这是 x86 页错误码语义；riscv 无错误码，写语义要从原因码数值本身判（取指、载入、存储三类），按数值与一判会把载入缺页误判成写，沿写时拷贝路径造成只读重映射活锁。其二，系统调用指令不自动步进返回点寄存器（x86 的系统调用语义自动保存返回点），内核必须显式步过指令长度，否则服务完原样返回、重捕同一条指令死循环。归一化是正解：每架构把原因码归一成统一的车道值（配纯函数），跨架构等值测试用函数对函数比较而非抄写字面量——抄字面量的等值测试在一边修改时另一边不会变红。

正确做法：缺页路由腿按本架构原因码重写分类，不沿用错误码位判别；系统调用腿保留步进并在契约注释钉死；多架构归一化函数之间用函数对函数等值断言，常量带来源注释，车道语义写明"本约定与各架构位定义的对应关系"防误读。

> 来源：`notes/rewrite/fork-syscall-rewrite/riscv-reviewlog.md` §A.6/§A.8；`NK4C-WORKLOG.md` §1.120续-76b（归一化纯函数与等值测试）；os/kernel/src/trap_dispatch.rs:riscv64_pf_error_code；os/arch/src/riscv64/exception.rs:is_write_fault

### 3.40 零初始化是分配请求的显式契约，不是分配器行为的隐式不变量；"死代码"可能是缺口的最后一块拼图

C 对每个非豁免内存区置"缺页即清"请求位、后端见位清零；重写侧请求位在、三个后端全实现、翻译函数已写好但带死代码豁免标注——唯一断点是按缺页分配的漏斗不传该参数。把"新帧恰为全零"押在"今天没有页回收所以帧天然干净"上，是以隐式不变量替代显式契约：页回收或缓存一上线，复用帧的残留（很可能是上一任的栈页，栈地址）就变成隐蔽数据污染——"某长度字段读到栈地址"类毒化的一个现实来源。

正确做法：见到死代码先查它是不是缺口的最后一块拼图（翻译函数的死，恰因漏斗没接）；零初始化语义显式随请求传递并配判别性测试（毒化假帧加豁免区不清）；对"清零或不清"的 C 内存语义逐条对账，发现带死代码豁免的语义函数追问"谁该调它而没调"；长程取证中穿插落地这类"与当前假设无关、可独立证真"的真偏离，真实前进且不污染当前因果链，但修完必须真机对照并诚实记录"对目标缺陷无效"。

> 来源：`notes/rewrite/fork-syscall-rewrite/riscv-reviewlog.md` §D.10（管线建成、漏斗一个接头未插）；`NK4C-WORKLOG.md` §1.120续-45（清零腿落地与对目标无效的诚实记录）

### 3.41 有固件特权层的架构上，"内核以为属于自己的资源"要逐项实测归属；x86 的端口输入输出概念不存在于 riscv

监督模式的世界是固件的：时钟比较器在物理内存保护下从监督模式直访即访问例外；写保护寄存器本身即非法指令；riscv 没有端口输入输出概念——设备协议层能跑完全流程，但每一条硬件访问都拿回"不支持调用"，字符永远出不了串口（"协议通了、链路不通"）。同一机制一刃一柄的入口陷阱：按可执行入口地址直跳生产镜像（高半虚拟地址）在分页关闭时即陷；而中等地址无关代码模型的取址被松弛为按实际执行位置解析的相对寻址，所以高半入口能在分页关闭时执行——这解释了为什么简单样例载体能过而生产形态不能。

正确做法：移植到有固件特权层（固件接口、可信固件、统一可扩展固件接口）的架构时，逐项盘点内核以为属于自己的资源并实测归属，实测教训直接写进代码注释；端口输入输出驱动的通道要重设计为内存映射代写或映射直访，不假设协议通了链路就通；新引导形态的入口地址模型（入口是物理还是虚拟地址、代码模型的取址如何松弛）作为共同前置核实。

> 来源：`notes/rewrite/fork-syscall-rewrite/riscv-reviewlog.md` §A.1/§A.3/§A.4

### 3.42 长持有可变借用的路径上，回调回同一单元的点一律用尝试借用并显式降级

整条分派期间持有可变借用时，审计回调点在特性开启时对同一单元二次可变借用直接崩溃；降级为尝试借用、失败即丢弃该次审计，必须有文档化契约背书（哪些丢失可容忍），不可静默。

正确做法：长持有借用的路径上凡可能回调回同一单元的点用尝试借用；"丢失可容忍"写成模块文档契约；新增贯穿性参数时重审其借用在全路径上的重入点。

> 来源：`NK4C-WORKLOG.md` §1.120续-36/续-37

### 3.43 aarch64 对栈指针做按位运算必须经暂存寄存器中转：同一编号寄存器的语义随指令组分裂

三十一号寄存器在加减立即数组里读作栈指针、在逻辑立即数组里读作零寄存器，所以"栈指针按位与做对齐"直接写即非法或语义错误；必须取入暂存寄存器、运算、再写回。用同义汇编改写做对照实验前先确认汇编器的改写行为，避免把汇编器等价误判为行为差异。

### 3.44 内核自身运行区必须进直接映射覆盖集：身份映射在场不代表别名映射在场，"某配置才崩"先判竞态还是扰动因子

直接映射的候选集三源并集全部面向虚拟机可用的物理内存及其引导配套，内核自身运行区（镜像、栈）不在任何一源里；身份映射补偿了直接寻址访问，没有补别名访问（按物理地址换算虚拟地址再走直接映射窗口的路径）。固件分配器落位随启动时序漂移：栈落在已映射段内就正常跑，落在洞里则第一个经别名访问栈页的跨空间拷贝即崩——崩溃地址等于映射基址加崩溃帧自身栈页物理地址是决定性证据。"多核配置才崩"是多核扰动分配与时序的表象：同轮内崩溃指令确定性（差值恒定）判它是扰动因子，逐轮签名漂移才是竞态。旁证形态：引导侧早已交付的保留区清单，内核侧建表路径对该字段零消费——"管道在、阀门没开"用检索消费者发现。

正确做法：审计覆盖完整性用存量探针输出的全覆盖清单做程序化区间判定，不靠猜；身份映射与别名映射两条访问路径独立审计；"某配置才现"的间歇缺陷先分确定性部分（覆盖缺口）与随机部分（落位漂移），随机源要有物理解释再谈修；交付方与消费方之间的字段做消费者存在性检查。同族对偶面：接受方帧分配器的空闲表必须扣除全部自占帧——自身页表根恰好落在引导分配池基址、而整个池区间仍留在空闲表内时，装载压力下的普通帧发放会覆写自身页表根，该进程全部地址翻译间歇腐坏（键序错乱、容器异常、遍历走设备洞三症状一次统一解释）；扣减粒度一次到位（整池与全部模块区），按症状逐实例补扣的两轮都因"家族清零"实为运气未进窗口而复发；交接契约应写成"交接方先扣除全部自占区间再交付空闲表"，双侧防护（分配器上下界检查）兜底。

> 来源：`NK4C-WORKLOG.md` §1.120续-48/续-49（覆盖缺口坐实与间歇机制）；os/kernel/src/dm_coverage.rs:kernel_dm_pa_end；§续-167a/续-168/续-175（根页覆写家族与全池扣减成修）

### 3.45 架构间的承重不变式不可照搬：先证明目标架构存在该不变式要防的场景

甲架构因存在指令边界任意抢占，必须在中断腿把现场帧存进上下文（有真机前科的承重不变式）；乙架构的同位腿把整份现场帧压在异常栈上、中断臂只查时间片、返回腿从同一份现场帧原样弹回，全程不读上下文——两套设计各自自洽。按甲模板给乙补存帧腿是搅浑两套设计的错误修复，需真机对账针（保存行与恢复行的五元组自动对账）才证伪。

正确做法：跨架构移植"不变式"前先证明目标架构确实存在该不变式要防的场景（抢占点、切换点在哪里）；"某腿没做某事"不等于缺陷，可能是其设计不需要；寄存器通路类假设的终审用保存恢复对账针：任一恢复行不是任何保存行的后继即坐实，每次恢复都等于最近一次保存即排除。

> 来源：`NK4C-WORKLOG.md` §1.120续-36/续-37（对账针配方与通路证伪）

### 3.45 MMU 关闭的物理视图阶段，字面量活着、静态引用是雷：跨视图的数据一律走纯字节池

分页未开启的引导阶段，唯一能解引用的是"调用点直接物化的字面量"（编译器把短字面量用相对取址内联进指令流）；而静态字符串引用、匹配跳转表这类"经数据段的胖指针"，其指针字段是链接期写入的高半虚拟地址——物理视图解引用即加载异常，固件复位域重启，表现为横幅重打、探测值归零的"热重入"假象。三轮翻案才定谳：先误疑镜像短读、再疑字面量、终定位跨视图引用。同一问题在跨视图名字传递上的正解是纯字节池：定长字节二维数组，基址经调用点相对取址物化，先拷进物理名字池再拼引用；凡在物理视图腿要被读的字段必须递物理地址后备。

正确做法：引导的物理视图阶段不传任何含静态引用的结构跨分页使能边界；跨视图名字用纯字节池加相对取址基址；物理名字页同时服务物理视图读与内核高半加恒等低半两视图；见到"启动横幅重打、探测值归零"先查跨视图引用，不先查装载。

> 来源：`NK4C-WORKLOG.md` §1.120续-88（装机面真机取证链，三轮翻案）

### 3.46 Sv39 页表操作铁则：非叶项权限位必须全零、拆大页后全局刷新、优先级加显式括号、位表先对特权规范

四条铁则各有真机或评审判例。其一，规范规定中间级表项的读写执行与用户位必须全零、权限只由叶子决定——按 x86 直觉给中间层清用户位是多余动作（riscv 的按叶遍历验证天然只读叶子），过度授权反而是错。其二，大页拆分后多个虚拟地址的旧大页译文仍存活，局部刷新不足，必须全局刷新（等价 x86 重载基址刷新、arm64 全域刷新）。其三，加法与移位的优先级陷阱三架构都踩过同款，含移位的地址算式一律写显式括号。其四，自建页表项标志结构前先对特权规范位表——本仓的访问位与脏位定义与规范有出入（按位复制不受影响），留档待核；另一族：单独置高位的虚拟地址是非规范形，见到即怀疑"带位污染的地址被当地址用"，挂观测嫌疑标签不进主证据链。

正确做法：实现页表操作按上述四条核对；新架构页表标志结构先对特权规范位表再动手；非规范地址检查做成故障地址判读的固定一步。

> 来源：`NK4C-WORKLOG.md` §1.120续-90（改动面与评审）；`NK4C-BUG-RISCV64-TRANSIENT-PTE.md` §3.6（非规范地址记录）

### 3.47 固件保留区的拒绝形态是访问异常而非缺页：每个启动腿自建保留面，削空闲内存图是唯一有效闸

物理内存保护拒绝访问的表现是与缺页不同的访问异常码——页表映射存在、物理禁区才是原因。固件常驻区若未从内存图的传统内存段剔除，帧分配器的位图初始化会把元数据刷进固件区、首次触碰即异常。修保留面有两个死路：只进内核直接映射、虚拟机账本不吃内存图段——都拿不掉虚拟机那一段；唯一有效闸是把固件段从空闲内存图里削掉。前提要诚实：削界逻辑带适用声明（固件段严格落在内存基址与载荷入口之间），换板若载荷入口下沉应改走保留内存解析。

正确做法：每个新启动腿自建保留面（统一可扩展固件接口腿本有保留区表、固件腿此前没有，新腿是第一个保留者）；诊断"映射在、访问炸"先查物理保护而非页表；削界纯函数配编译期断言把关（无独立测试跑道的交叉编译模块，常量断言是宿主面上唯一可跑的判别器）。

> 来源：`NK4C-WORKLOG.md` §1.120续-91（保留面三判例与削界函数）

### 3.48 控制状态寄存器位域写前对规范位表：顶层使能位与完成位差一位，闲置核就睡死

闲置暂停例程置"中断使能"写错了位——写成的是"上一次使能状态"位（仅由特权返回指令消费拷回），真正的内核态中断使能是另一个低位。后果链完整：用户态忙期正常（特权返回把上一次状态拷进使能位），内核闲置循环睡死——待决中断挂起却不被投递、运行时长冻结、可睡眠调用超时永不到期、整机静默。诊断签名是"待决位与使能位都显示就绪却不投递"——第一怀疑对象就是顶层使能门。

正确做法：写控制状态寄存器位域前对照特权规范位表，位域表钉进注释或断言；遇到"待决加使能俱全却不投递"先查顶层使能；用户态忙期正常而内核期停摆的差分本身就是位域写错的指纹（用户态的使能位是特权返回从旧值拷回的）。

> 来源：`NK4C-WORKLOG.md` §1.120续-109（闲置定时器停摆单行成修，串口四千行推至两万五千行）

### 3.49 内核禁用浮点是一条注入防线：目标特性门、编译期报错门、布局检查三重把守；确需浮点的汇编局部提升

编译器不保证不产浮点指令（自向量化给内核镜像注入数百条浮点指令的实录在案），汇编器也不拦（内联汇编默认不含浮点扩展，浮点存取被拒收只是表象）。内核态执行浮点指令会踩用户浮点寄存器活值，是浮点状态未保存族缺陷的注入源之一。三重防线：构建命令按架构显式注入"减浮点、减向量"目标特性；关键模块放编译期报错门；镜像布局检查加全架构"浮点指令数为零"断言。真正需要浮点的全局汇编函数用局部特性提升包裹，并在注释里论证安全前提（内核无存活浮点状态，恢复例程覆写全部寄存器不违反调用约定）。

正确做法：三重门照抄落地；给全局汇编的局部提升函数写安全前提注释；跨架构对照这类缺陷时注意 ISA 差异——同构代码在另一架构无毒可能只是编译器选了通用寄存器装载常量（架构间的"免疫"无设计保证）。

> 来源：`NK4C-WORKLOG.md` §1.120续-129（浮点踩消息头定谳与修复）、§续-133（riscv 注入缺口与三重门）

### 3.50 懒浮点门控的位值三样对表：常量名、规范位值、消费谓词的触发值必须闭合

懒浮点轮转的守门谓词要求状态位等于"关闭"值才把非法指令判成浮点陷阱；而移植代码给非持有者的上下文打补时写成了"初始"值——初始值恰恰放行首条浮点指令（不陷阱），轮转腿成了不可达死代码，用户态对用户态的浮点互踩全无保护。三处放大因素：架构文档里的错误认知是错误常量的诱导源；同名常量的位值与语义名不符（"脏"值实为"干净"值）；浮点状态位住在状态寄存器帧内的架构上，陷阱出口对状态寄存器的整体回装会把函数体内的活写冲销——门控写进帧、收尾统一落帧才行。姊妹坑：汇编恢复例程若把被调用者保存浮点寄存器列入破坏集，编译器会在恢复序列之后插入序言寄存器的回装，覆盖刚恢复的用户值——恢复型汇编的破坏集必须有意豁免这一段，豁免的安全性前提（全内核禁浮点）用门钉死。硬件策略寄存器还要单点所有：两处代码对同一策略寄存器各写各的归属策略，后者覆盖前者，整个机制静默休眠、骗过全部静态审查。

正确做法：跨架构移植任何位态门控，建立"常量名→规范位值→消费谓词要求的触发值"三样对表并用交叉检索闭合；常量名与规范语义冲突即使暂无功能问题也要改名（它误导下一个读者）；状态位住帧内的架构，门控写进帧、收尾统一落帧；恢复型汇编破坏集做调用约定级审查、豁免配安全前提门；策略寄存器单点所有，跨层归属在设计文档钉死；改门控实验先推演"自陷阱零恢复"类次生洞并对照 C 的持有者分支。

> 来源：`NK4C-WORKLOG.md` §1.120续-129 修复 3（破坏集豁免）、续-130 经验（策略寄存器单点所有）、§续-133（帧内位冲销与万能异常码）、§续-197（初始值放行的死门控）；`NK4C-RETRO-AUDIT-20261001.md` §11.1/§11.6（三样对表条目）；`os/arch/src/riscv64/fpu.rs`

### 3.51 跨架构设备臂清单与线上编码双侧同源测试：单边后端静默全灭、零消费者包装首用必暴双错

跨架构驱动排查的新形态：后端实现清单单边——串口驱动只实现了一个架构的端口访问模型，另一架构的内存映射设备根本没有端口车道，用户态全部控制台写静默失败，而启动链照常（内核早期控制台直写掩盖症状）；头注文档只描述已实现架构，读起来完全自洽，缺的是"另一架构怎么办"这一整面。零消费者的线上包装潜伏双错：请求编码与回复解码各错一处，旧测试脚本化了错误的线上形态、一直绿到真机首用才炸——零消费者等于零真实验证。附带：线上车道宽度对宽类型静默截断，超界必须显式拒绝而非截断。

正确做法：把"某架构单边后端、端口车道消费方全量盘点"列为跨架构移植评审检查项；补臂对位 C 生态惯用法（设备映射加寄存器直驱），按目标架构分派；客户端编码与服务器解码配一对同源测试（引用同一联合体臂常量，两端不得各自手写偏移）；零消费者包装首用前先做线上形态对账而非信任既有测试；宽类型超界显式拒绝。

> 来源：`NK4C-WORKLOG.md` §1.120续-131（tty 单边）、续-132（零消费者双错与同源测试）、续-133 顺路件

### 3.52 判定谓词禁用带默认值字段的模式匹配，用语义标志位

区域类型判别曾写成对参数形状的模式匹配——而匿名区域的参数默认值恰好与真设备映射同形状，探针门控把全部匿名区域误杀、净态计数三轮异常。"参数的枚举默认值"与"语义上真的是该类型"不是一回事；同一课在评审线与回溯审计两处独立踩中。

正确做法：区域与对象类型判别一律走语义标志位；凡结构体带默认值字段，判别逻辑禁用该字段的形状匹配；为探针写过滤谓词前，先核该参数在全部构造点的默认值分布。

> 来源：`NK4C-WORKLOG.md` §1.120续-132 评审（形状匹配误杀匿名区）；`NK4C-RETRO-AUDIT-20261001.md` §2.3（同款第二例）

### 3.53 未知消息类型的静默臂是乒乓放大器：对位 C 的缺省臂语义要带行号锚定，移植期反射类回程改静默丢弃

带上站标识的失败回复泄漏进错误车道后，接收端对未知消息类型静默处理，又把它原样发回，乒乓不收敛——C 对位的缺省臂语义本该是熔断器（回不支持的错误码），静默吞掉让故障从一次崩溃降级成无限循环。移植期还要防两级语义漂移：对位 C 时口口相传会把"回不支持的错误码"漂成"恐慌"（引用 C 对位必须带行号锚定）；而在车道不可信、确有垃圾实存的移植期，把垃圾反射回车道的回程（不支持错误码、原值回）应统一改静默丢弃。

正确做法：服务器分派的未知类型臂逐一与 C 源带行号对齐；移植期对错误来源的反射类回程一律静默丢弃并打丢弃标记；车道恢复可信后再回 C 语义。

> 来源：`NK4C-WORKLOG.md` §续-136（带上站标识消息泄漏解码）、§续-148（乒乓放大器归纳）、§续-153（C 对位行号纠偏）

### 3.54 有序容器点查失败而遍历可见，即键序不变量已破坏：防御性重建必须配打点留痕

同一个键、同一个结构、同一地址，点查失败而沿链遍历可见——内存字节没变、编译器被排除后，唯一自洽解释是有序容器的内部节点不变量被破坏（就地改键或节点字段被覆写使二分落错分支）。防御性处置两级：点查失败而遍历可见时按遍历结果放行并打兜底计数；点查与写操作同判时做全量重灌使结构合法化并打修复计数——重建后树再坏即腐坏源仍在逃，兜底不掩盖判据，计数入库让腐坏源可继续追捕。

正确做法：有序映射类容器出现"点查失败而遍历可见"先怀疑键序不变量而非内存腐坏；防御性重建必须配打点计数，让兜底行为可观测、腐坏源可追捕；对"统一解释多症状"的漂亮定谳保持下轮可证伪姿态。

> 来源：`NK4C-WORKLOG.md` §续-159/续-160（区域表兜底与重建落地）

### 3.55 VM 区域语义的 C 直译两例：拆分两半必须继承内存类型；堆顶指针只是槽位提示，断点由用户态持有

两处"语义等价"直觉翻车的真源对账。其一，区域拆分的两半必须继承原区域的内存类型——重写侧用新建构造丢掉了类型，任何缺页落进残段即因无类型而投递段错误；C 真源拆分时两半都带原类型。母区无类型时拒绝拆分（防御增量，C 无此形），调整大小的能力谓词对无类型区走新建腿而非原地扩展（扩展产出的新页会同型缺类型而死）。其二，堆顶指针只是区域槽位的放置提示，不是程序断点——断点变量由用户态 C 库持有、变化时才向虚拟机发绝对地址请求；虚拟机侧的全部"缩减语义"就是覆盖即成功、不缩。把提示当断点用，派生污染引导区、请求全拒。同族"纯阅读侦察"产出的补腿地图（认为 C 靠某条腿做堆预分配）被全树检索零命中直接否决——继承来的事实性断言先 grep 复核再落地。

正确做法：区域拆分两半继承内存类型加防御门加回归测试；堆断点语义按 C 直译（绝对断点、前驱单点、扩展或新建双臂由内存类型能力决定）；插腿处给提示指针补设置点并注释钉死"提示非断点"；笔记与计划里的"代码事实类断言"落地前全树检索核调用点存在性。

> 来源：`NK4C-WORKLOG.md` §续-279m/续-279m-b（拆分缺类型与断点直译）；`minix3/minix/servers/vm/region.c:split_region/vm_region_top`；`os/servers/vm/src/brk.rs`

### 3.56 跨 libc 布局翻译层：内核固定写自己布局等于砸调用者返回地址；逐字段赋值让编译器推导目标侧

同一逻辑结构在不同 C 库里布局不同（字段数、对齐、大小全可能不同）：内核侧按自己的固定布局直写调用者栈上的对象，超界部分正好砸坏帧链与返回地址——症状是返回到垃圾地址的全零跳转，极难归因。正解是两段式翻译层：先写进内核侧的原始缓冲，再逐字段赋值进调用者对象——目标侧的偏移与宽度全部由编译器按目标 C 库推导，多架构共用零手抄。配套防线：内核侧原始布局的每条字段偏移用宿主对账测试逐条断言到布局元数据，任何一侧漂移即红；编译期静态断言在重构中易被删，防线必须落到持续集成测试。

正确做法：跨 libc 边界结构一律两段式翻译（原始缓冲加逐字段赋值）；内核侧布局配宿主对账测试（逐字段偏移断言）；防御性收紧引发既有测试红时，先查测试夹具形状是否取了真源不存在的形，再查产品码。

> 来源：`NK4C-WORKLOG.md` §续-277/续-277b/续-277c（布局翻译层与宿主对账测试）；`os/libs/minix-types/src/types/stat.rs`

### 3.57 外来 libc 符号接管三定律与边界契约：命令行对象抢占、裸名引用必须裸名定义满足、宏转发先于一切头文件

为上机 C 测试接管库函数的三条链接定律。其一，链接器按"命令行目标先于归档"解析，把接管实现做成命令行对象即可抢占库成员（既有先例同形）。其二，裸名引用必须由裸名定义满足：用别名或独名实现不满足裸名引用，链接器把裸名解析回库成员，其内部引用再拽入库内另一个同名成员，触发强符号双重定义——正解是取改名后的规范符号名做 C 名定义，配合在一切头文件之前做宏转发，让库头里的声明被一并改名、与自定义同形；GNU 风格调用法（解引用返回值）在此通道是未定义行为，要登记负向契约并自给零外呼实现。其三，接管前先用真机探针测目标库的实际行为面（含边界与极端值）：目标库对越界码可能永不产生预期输出形态，"校准常量数值"这条路从根上不成立，必须整族接管。边界契约：上界常量是"表项数"不是"任意上界"（合法区间按真源公式取，边界差一让成批用例翻车）；探针取证清单必须覆盖边界双侧（上界本身与上界减一）。另一个假象：半实现桩的堆增长"成功"其实是推进自己数据段里的指针、长进未映射页——堆行为疑点先用反汇编定"符号到底解析到谁"再决定在哪层修，修完同步删掉不再被引用的死桩（符号表零引用核实）。

正确做法：接管库函数按三定律落地（命令行对象、裸名裸定义加宏转发前置、真机定谳目标行为面）；边界常量按真源公式取、判据按半开区间；探针覆盖边界双侧；桩的调用链用反汇编定谳；死桩用符号表核零引用后删除。

> 来源：`NK4C-WORKLOG.md` §续-279n（strerror 族接管与边界差一）、§续-279m（假桩堆增长）、§续-279n 提交（随机数真源直译）；`os/xtask/src/image.rs`（兼容层装配）

### 3.58 共用架构层代码里的打印是行为的一部分：用户态打印经固件调用即是陷入，被内核当消息处理即自戕

内核与用户态服务器共用的架构层代码里，诊断打印的后端若是"经固件的字符输出调用"，从用户态执行即是一条陷入；内核若把这条调用的寄存器当进程间通信处理（目的地址取到字符本身、消息指针为空、拷贝失败投致命信号），结果就是"探针一打，被测对象被自己打死"——更早杀死了真缺陷，前半程追的症状全是幻影。判读实录：崩点指令序列与打印字面量逐字节吻合才定谳。

正确做法：无标准库内核对每条打印问一句"它在每种特权级、每种上下文分别做了什么"；共用架构层代码中的日志纳入行为审查而非当作无害观测；用户态可达路径上的诊断必须走专用诊断通道而非通用控制台；陈旧探针用后即滚并登记技术债，成修后用"穷举该通道全部使用者"确认删的是唯一可达源再闭合。

> 来源：`NK4C-WORKLOG.md` §续-191~193（陈旧探针成修与闭合）；`NK4C-BUG-RISCV64-TRANSIENT-PTE.md` §5.5（固件调用误投递机制）

### 3.59 启动路径关键算术一律显式检查：发布构建的溢出检查关闭不是正确性论据

启动算式若为负，发布构建下静默回绕成巨正数、跳转到荒谬地址、启动静默死——调试断言与构建档案依赖都不能作为正确性论据。用显式检查加硬失败把不变量写成启动期快速失败（行为逐位中性：高半基址恒高于物理基址）。评审对"显式化破坏集"类建议先写最小编译实验验证可表达性（返回不返回的汇编选项禁止输出操作数，某些"更严格"的写法在语言层面不可表达），不可表达即在注释记死结论并关闭，不硬改。

> 来源：`NK4C-WORKLOG.md` §1.120续-124/续-125（显式检查入库与不可表达判定）

## 4. 测试与防回归

### 4.1 判别性断言三招：毒化读回、反向验证、变异实测

测试与实现一起错时，绿是复述不是证据：现场参数让两种实现得到同一结果、断言照着错误实现写死期望值、替换与否都返回同值的用例，全部测不出目标缺陷。

正确做法：一、毒化+读回——先把目标槽位钉上干扰值，操作后断言读回的是正确值，含缺陷的实现会原样吐出毒值；二、反向验证——修完把实现改回含缺陷写法再跑，相关断言必须变红，否则断言没有判别力；三、变异实测——对校验逻辑做注入矩阵（注入漂移应失败、还原应通过，加固与回退各实测一遍），量出加固的真实能力，反向实测只覆盖契约一侧时，推理出的加固可能被量出有害；四、断言对照 C 源核，不对着现有实现核。五、不变量不能从数组长度反推：帧槽总数含保留填充槽，把总长钉成活寄存器数的断言能编译能过、却固化了错不变量——写不变量断言前读结构体定义处的权威注解，按"活成员数"断言而非按总长。

> 来源：`NK4A-TODO.md` §6.2 示例（毒化读回判别断言）；`NK4B-WORKLOG.md` M3.3（注入矩阵）；`.review/zcode/edge1/FIXLOG.md`「SELF 哨兵权威化」条目（判别补强）；`.review/zcode/edge3/FIXLOG_archive.md`「反向验证」条目；`NK4C-WORKLOG.md` §1.120续-75 评审（帧槽活数断言）

### 4.2 测试会把偏离固化成契约，替身会掩盖生产缺陷：测试必须与真值双向对账

实现偏离 C 语义后，把偏离行为写成期望值的测试会让偏离获得背书；手工伪造输入的替身让模块清单与内核契约的多重不一致长期潜伏；恒定失败的替身把"永不通电"固化成期望行为。测试绿只证明现状被复现，不证明现状正确。

正确做法：审测试做双向对账——测试描述对照 C 源与设计，不只对照实现；修行为偏离必须连固化它的测试一起改；替身的输入从真实来源派生，不许手编；通电批次预留"翻转诚实失败断言"的动作，防止把信号误判为回归。

> 来源：`notes/rewrite/fork-syscall-rewrite/new_todo_HY4.md`（执行门偏离被测试固化的发现）；`new_todo_muse.md`（替身伪造模块清单的发现）；`new_todo_deepseek.md`（恒失败断言固化的发现）——三份独立诊断中两份以上命中同一机制

### 4.3 替身全绿不能证明线上语义正确：宿主可达边界要诚实拆分

宿主传输替身按自己的符号约定应答时，与线上符号约定相反的缺陷在宿主下全部假成功，直到真实冒烟才暴露；罐头替身按调用次数逐个吐出备好的回复，首轮失败可能只是"回复耗尽"而非业务失败。替身只验证决定逻辑，不验证线上语义；假成功比诚实失败危险，因为它消灭了报警。

正确做法：传输替身缺席时按失败关闭（pin 一个 EIO 测试定格行为）；线上语义以 C 头文件导出的绝对值 pin 测试为准；每条修复声明"宿主可达边界"，宿主测不到的缺口如实登记挂真机验证，不许顺手修也不许假装完整；通电是唯一终审，通电前的宿主结论全部标注为"决定半"（只证明逻辑决定正确，不证明线上语义正确）。多架构扩展面同理：某架构上新增代码根本没被执行（空输入使新循环空转）时，"多轮无回归"只证明没坏、不证明跑过；为"新代码被执行过"找直接签名（诊断计数非空、新腿触发），拿不到就诚实标注该架构对该改动是零信号，不冒充覆盖。分流器用法：真机诡异数据损坏先把核心构造逻辑提成宿主可跑断言（加严到逐消息粒度）——宿主全过即在逻辑层洗清，把嫌疑域收窄到"代码生成、布局、池交互"的运行期面，省掉在逻辑层继续找的时间；顺手把宿主暴露的预存失败经版本对照确认后交对应线，不混入本轮归因。

> 来源：`notes/rewrite/fork-syscall-rewrite/edge_todo.md` 头部登记（系统调用符号冲突判例）；`.review/zcode/edge3/FIXLOG.md`「NS7」「NS7-A」两条；`.review/zcode/edge2/FIXLOG.md` 批A/批B 的如实登记段；`NK4C-WORKLOG.md` §1.120续-51（零信号架构的诚实标注）

### 4.4 收尾验证三件套：测试计数基线只增、静态检查基线对账、格式存量漂移不动

多会话共享仓库，没有基线对账就分不清"我引入的"与"预存的"；交叉编译时 `cargo check` 会静默放过内联汇编里的部分错误，只有真正构建才报；普通 `cargo build` 不编译 `#[cfg(test)]` 代码，批量改动测试代码后只看普通构建会假通过。

正确做法：每批改动在 docker 内逐包跑测试并给出具体计数（基线加新增，只许增长）；静态检查用改动前后对比证明零新增；包名用连字符（`-p minix-sys` 而非下划线）；交叉形态以内联汇编相关代码的 `cargo build` 为门；测试代码的批量修改必须跑测试形态编译。配套一条："提交进版本库的字节即被验证的字节"——格式修正、评审意见落实这类后置修改都改变最终产物，沿用修改前镜像的验证结果等于验证了别的东西；任何后置修改之后重建镜像复跑，"彻底修复"的判定取跨配置多轮签名稳定加改动前基线对照计数。

> 来源：`.review/zcode/edge3/FIXLOG.md` 过程教训两条（批量补法与对账范式）；`.review/zcode/edge1/FIXLOG.md` 迭代补记追记（持续集成构建门的由来）；`NK4C-WORKLOG.md` §1.120续-36（后置修改后重建复跑）

### 4.5 历史日志变机械防回归门：三问分流、内容指纹基线、变异负例

对数万行历史日志逐条问三个问题——在几份独立日志出现过、当时怎么发现/修的、能否用检索或脚本机械拦截——能拦的落成机械检查清单，不能的归流程纪律；与既有评审模式库逐条对照避免重复立条。基线键若用行号会随文档漂移失效。

正确做法：基线键用"检查名+路径+行内容指纹"（对行号漂移免疫、对内容改动敏感）；每项检查配正反样例自测矩阵，真树注入违规验证必报、还原后复绿；判据必须看最终工件而非构建通过（构建检查不覆盖内联汇编、特性不满足时静默跳过产物）。

> 来源：`PATTERN-SCAN-REPORT-20260923.md`；`tools/pattern-gate.sh`

### 4.6 验证通过不等于架构正确：偏离 C 本形的架构内自洽补丁终会被结构性取代

某停车机制在自身架构内真机验证通过，仍属错误设计——接收方用"自己收过的每个消息源"覆写停车发送方的期望来源字段，两个不同来源先后经过时字段被覆写错位，真实回复到达时对不上号（真机两轮取证实锤）。对照 C 原文才发现 C 的对应路径根本不代做这件事。

正确做法：动手前先对照 C 锚点质疑"为什么这里要代做"——验证绿只证明补丁在该架构内自洽；评审对"偏离 C 本形的架构"单独标注，即使全部测试通过也列为架构演进观察项。过渡性偏离（守卫、钳制、掩蔽）必须在同一提交里登记对位 C 的锚点与移除条件清单——哪些后续件落地才拆守卫；只写"这是过渡偏离"的注释防不住永久化。多架构共享代码（页表分配、引用计数、回收）的改动负论证义务：提交说明必须写清"为什么其余架构不受影响"——一条未坐实的"防御性"改动曾差点破坏另两个架构的启动；验收分层照七层表打勾（根因证据、症状消失、独立稳定轮次、其余架构无回归、宿主全绿、布局与静态检查零新增、探针不残留生产路径）。

> 来源：`NK4C-REVIEW-REPORT-20260927-R3.md`（自审发现节）；`os/kernel/src/ipc.rs`；`NK4C-WORKLOG.md` §1.120续-73（过渡守卫登记）；`notes/rewrite/fork-syscall-rewrite/NK4C-MIGRATION-20260930.md` §5（真多核未还债与守卫移除条件）

### 4.7 宿主可链接面逐服务器不同：不可链接的就退回 wire 契约互证

PM/VFS/DS 都有宿主可跑的真代码面（公开的 fork、处理器、解码入口，或架构在两个小 trait 上）；VM 的库只导出服务器与引导类型、内部全部 crate 私有，无法在宿主链接——这是结构性事实不是缺陷。另：集成测试目录的包根就是目录本身，Cargo 自动发现不覆盖，每个测试文件要手写测试注册表条目。

正确做法：领相关子项先核实公开面；不可链接就退回 wire 契约（用共享类型包的消息结构与对端真编码器互证）并在边界账本登记缺口，不为"跑起来"改他人领地的导出面；每加一个集成测试文件同步补注册条目。

> 来源：跨会话记忆 `minix-rs-e5-host-half-linkable-surface.md`（见 6.3）

### 4.8 共享冒烟判据是单向棘轮：标志行冻结，判据只许扩展不许放松

rc 标志行与冒烟分阶段判据被多条弧线的"全绿"结论引用；改动标志行之前的内容或放松既有阶段判据，会让前序弧线的证据失效、旧结论变假绿。

正确做法：`os/etc/rc` 只允许在标志行之后追加，标志行及之前一字节不动；冒烟脚本允许加新判据（如命令执行标记），禁止放松或删除既有判据。

> 来源：`NK4B-TODO.md` §2.2–2.3 与 §8；`NK4B-OPENING-PROMPT.md` 铁律节

### 4.9 健康签名与病态签名靠量级分档区分；"无报错但不前进"的现场唯一信号是重复计数

修复后同一地址出现四次（四个进程文本段各一次性按需缺页）与改动前同页重复数万次的活锁签名，若只按"该地址是否出现"判回归，会把健康当未修。另一形态：活锁现场每一环单看都健康（调用返回成功、应答正常、零崩溃），缺陷藏在"元数据没同步"这种不体现在任何返回值里的地方，唯一异常信号是同一请求被处理了几万次的重复计数。

正确做法：为每个已知失败模式登记病态计数阈值与健康基线计数，回归判定按量级档位而非有无；对"无报错但不前进"的现场主动统计同地址同请求的重复次数并设基线（修复后同一地址只出现个位数次，与数万次泾渭分明），健康基线的量级本身就是断言。

> 来源：`NK4C-WORKLOG.md` §1.120续-36（量级分档）；`NK4C-AARCH64-EXEC-REBIND-LIVELOCK.md` §3/§9（重复计数定谳）

### 4.10 静默丢弃止血三件套：丢弃打印、白名单收窄、双向钉子测试；止血落地后重审完整消息流

为掐断乒乓环加的"未知来源静默丢弃"止血，因无丢弃打印且条件过宽，把合法调用号一并吞掉——装载腿的普通调用号被吞、整条链下游全部断掉，三轮才定位。终修三件套：丢弃分支前打打印（否则副作用不可观测）；条件按"已注册调用号谓词"白名单式收窄（负值与超界仍丢，止血不变）；补两枚边界钉子测试（合法值穿透必有回复、非法值静默零发送）。任何静默丢弃类止血落地后，重审完整消息流确认没有吞掉其它合法消息。

正确做法：静默丢弃止血必须同时带丢弃打印、白名单收窄、穿透与丢弃双向钉子测试；止血合入后全量重审消息流；把"合法值穿透"钉成判别性断言（含缺陷实现会对替身超额调用）。

> 来源：`NK4C-WORKLOG.md` §续-149/续-150/续-151/续-153（止血吞调用号与三件套终修）

### 4.11 套件门与判据串纪律：终集定案、期望数唯一真源、镜像陈旧防线、夹具取真源存在的形

测试套件门的判据设计有五条实证纪律。其一，终集定案：按计划文件的期望数收齐全量结果行再裁决——首个通过即跳出会掩盖后续失败；停滞检测盯总进度（无新结果行）而非通过计数。其二，期望数唯一真源是工具落盘的计划文件，不手抄。其三，镜像陈旧防线：最新模块文件不得比镜像新；容量不足让格式化工具在装配时前置拦下（防线有效而非事后爆炸）。其四，判据串设计要预判"可被哪些无关路径产出"：同一标志行在串口里出现两次——一次是命令真实输出（新后端成立的证据）、一次是文件回显（与后端无关）——裸计数把两者混为一谈；解析按形态（引号、行上下文）分类计数，只让目标形态计入判据；全文检索改取标志行之后的窗口再判。其五，夹具必须取真源存在的形：防御性收紧引发测试红时，先查夹具是否在用生产不存在的形状（无类型区域、宏被做成返回零的函数——循环零次执行的假绿），夹具同步取真形。配套两条：脚本判据加管道失败传播选项时，"生产者大输出加消费者早退"的组合会以假失败收场（最小复现一行命令坐实）——轮询断言直读文件不走跨进程管道；收尾判定只认当前轮实测读数，门红先对账已知台账（真失败不被掩盖恰是门在正确工作），显式论证后才许解释为"门的正确行为"。

正确做法：套件门按五纪律搭；轮询脚本不用跨进程管道判据；收官对账只引用本轮读数；门红先对台账再定性。

> 来源：`NK4C-WORKLOG.md` §续-277/续-277b/续-277c/续-278/续-278b（套件门四道防线与终集定案）、§续-277 提交（管道假失败）、`NK4C-RETRO-AUDIT-20261001.md` §5（标志行双形态）；`NK4C-接续PROMPT-20261002.md` §七（兼容桩取真形）

### 4.12 编译与单测门全绿不等于运行期可达：探针零命中等于"腿未通"，真机正证据验收加孤儿原语扫描

一条门控谓词写错位值的运行期分支，在宿主单测与布局检查里全绿——宿主测试根本不跑那条腿，编译期门只看静态属性。绿灯给了不可达缺陷假信心。推论链两条：其一，运行期可达性只能靠真机正证据坐实（探针命中计数大于零、命中日志），"探针零命中"的语义是"这条腿没通"，进入可达性排查而不是记平安；其二，"有代码、有测试、有注释"三绿灯俱全的设施可能是孤儿原语——浮点保存恢复汇编与其宿主槽全部建成测过，但全仓调用者计数为零，字段注释还写着"陷阱入口会更新"的承诺式描述，让它在评审里一直像已接通。把"公开接口全仓调用者计数"做成周期性扫描，孤儿即现形（同一判例：队列补发原语零生产调用方）；凡注释声称的接线，用调用者检索验证而不是读注释。补一个宿主面的姐妹件：无测试跑道的交叉编译模块，常量求值断言是宿主面上唯一可跑的判别器——把纯函数不变量写成编译期断言，任何目标的编译检查都会执行它。

正确做法：新增运行期门控腿的验收标准必须含一条真机正证据；零命中进可达性排查；周期跑公开接口调用者计数，孤儿入台账；承诺式接线注释用检索验证；无跑道模块的关键不变量落成编译期断言。

> 来源：`NK4C-RETRO-AUDIT-20261001.md` §11.1/§11.6（门禁遮蔽运行期可达条目）、§4 家族 2（孤儿原语）；`STRUCTURAL-DEBT-REGISTER-20260930.md` §SD-23（浮点孤儿）；`NK4C-WORKLOG.md` §1.120续-91（常量断言把关）

### 4.13 管道失败传播加早退消费者等于假失败：轮询判据直读文件

打开管道失败传播的判定脚本里，"大输出生产者加命中即退的消费者"组合会让生产者死于断管、管道返回一百四十一、轮询永判不中——三轮真失败实为脚本假信号。最小复现一行命令可坐实。

正确做法：轮询类断言直读落盘文件，不走跨进程管道；同类风险面是全部"生产者输出大加消费者早退"组合；给判定脚本配最小复现自检。

> 来源：`NK4C-WORKLOG.md` §续-277（三轮假失败与最小复现）

## 5. 流程与协作纪律

### 5.1 修复纪律"读现状、单条修、grep 验证"的价值由批量脚本事故背书

违反单条修复的事故全部源于批量变换脚本自身带缺陷：批量插方法的两版脚本各错一处（漏多行函数体、插到实现块外还误删声明行），批量字符串手术在"编译已绿"之后又引入多文件语法损坏——爆炸半径从一条扩大到一批。

正确做法：修前读目标行上下文并 grep 确认现状，一次只修一条，修后 grep 验证；批量变换必须单管线推进、每片验证，损坏即整体回退重做；批量补测试代码后必须跑测试形态编译。

> 来源：`.review/zcode/edge3/FIXLOG.md`「过程教训」「过程事故」两条；`.review/zcode/edge4/FIXLOG.md` 头部执行协议备忘

### 5.2 修复日志只追加：全量复述曾让日志膨胀几十倍，编号撞车靠先落主线裁决

会话收尾时把整份日志重复追加，文件膨胀到九成以上是重复行，历史不可检索，只能归档重组；gitignore 的共享日志被并行会话同时追加时必然编号撞车。

正确做法：只写增量，一次会话一条；追加前自检文件头计数必须为 1，非 1 即停手排查全量复制；受跟踪文档只引用提交哈希、绝不引用 gitignore 日志里的条目序号（既不可移植又会撞号）；历史条目发现错误不追改，就地追加更正节。

> 来源：`.review/zcode/edge3/FIXLOG.md` 头部归档重组注记与追加更正节；`new_edge4.md` §1 规则 5（FIXLOG 增量纪律）

### 5.3 多会话并发靠认领锁与专属工作树隔离；未跟踪的在制品等于不存在

共享工作树同时承载多线的未提交改动，任何换分支/重置动作都会销毁别人的工作——曾有一次重置同时摧毁两组已过评审、测试全绿的在制品；而分支引用跨工作树共享，使认领分支天然成为全局排他锁。刚写出的守卫脚本与规则文档本身若处于未跟踪状态，同一次重置会连保护机制一起摧毁。

正确做法：领取条目用认领脚本（自动建专属工作树并打印路径），只在自己的树内改码、构建、测试；开工前跑位置自检；共享主树内禁换分支/强制重置；纪律载体必须被 git 跟踪且改完即提交；完成后合入主线再释放（树内有未提交改动则拒绝回收）；真机串口验证全仓同一时刻只允许一方执行。对未提交在制跑 `git checkout <引用> -- <路径>` 会无条件覆盖工作树、静默冲掉改动（自伤版踩踏）——对账前先提交，或用 stash/临时工作树跑基线。并行只读线（扫描、评审、对账）对共享工作树的已跟踪文件改动一律不动、只上报——观测到的"异常改动"很可能是主线在制品；判"异常"前先对照主线工作日志的在途主题。

> 来源：`new_edge4.md` §1 规则 7/8 与 §2 工作树踩踏判例行；`.review/zcode/edge2/FIXLOG.md` STTY-G 批（主仓落账卷入陈旧暂存内容的事故）；跨会话记忆 `minix-rs-baseline-diff-no-checkout.md`（见 6.3）；跨会话记忆 `nk4c-riscv-scan-thread-state.md`（见 6.3，只读线程纪律）

### 5.4 账本状态列会滞后：前置是否满足以代码实证为准

多起判例显示状态列未回勾而交付物已在主线存在且全绿——按账本等待会互相卡死，按账本回写会制造假状态；允许各线直写权威账本又会引入并发写冲突。

正确做法：对状态有疑义时以最新进度注记加代码/测试实证为准；禁止各线直写权威账本，由编排线在里程碑批量收敛回写；前置核验结论（"前置在代码中已满足"）写进自己的登记行留痕。

### 5.5 否定式与全称断言：范围词必须与检索实参一字不差，归因必须附可复跑命令

一轮评审的全部新发现同源一条根因——先写结论再补命令。"全仓只有三处"的检索根目录漏掉了载体目录，反例就在同一链路的真机代码里；把行计数（提及数）当成调用方数、把两个统计口径混成一个归因，都是范围词与实参脱节的表现。

正确做法：先跑命令抄输出，再写断言；范围词与检索实参一致，不许靠括号收窄；行计数只担保"提及"不担保"调用"；凡写"A 造成 B"必须附可复跑命令；修正错误措辞用同义转述，避免原文引用打坏自己的防回归检索。

> 来源：`NK4B-WORKLOG.md`「锚点自查记录」（写完当场重跑全部引用）与载体侧更正各节

### 5.6 受阻条目交付三件套：字段级缺件清单、多方案对比、推荐序；拿不出判别性断言的修复不做

"缺交接协议"式的抽象缺件无法裁决也无法开工；拆成字段级清单后才发现仓内已有真机跑通的对位实现，方案代价随之改判。已定性的缺陷若当前路径不读受影响对象，修了没有可观测差异——用改动制造推进感是假交付。

正确做法：受阻节交付三件套——字段级缺件清单（文件与符号级）、方案对比表（做法/代价/风险）、推荐序并明示不自行定案；动手前先回答"判别性断言是什么、缺了它含缺陷的实现是否也通过"，答不出就只登记不修。

### 5.7 收敛判据缩水与"接受现状"式回填会掩盖结构性缺失；流程修复的验收判据是行为改变

收敛标记的语义从"产物完整且评审通过"缩水成"评审通过"后，缺设计文档的条目被逐个"接受现状"并照常标记收敛，问题顺延给下一会话无限循环；同时规则文件被小修五十多处而行为模式不变——工具只打印建议而不阻断退出，条文写了不等于行为发生。

正确做法：收敛以产物完整为前提并由工具核验；见到缺失要么阻断要么取得明示知情，禁止顺手回填；门禁类规则必须配非零退出的严格模式，启动协议固化为"必跑工具、按退出码分叉"；规则修改以"下次同类缺失是否被阻断"为验收判据，并定期做全流程元层体检。

### 5.8 局部豁免不能成为后续会话的默认

正确做法：豁免逐条限定对象与次数，跨文档复用须重新请求决策；规则修订后全链检索旧表述清零。

### 5.9 多模型独立评审：隔离是交集可信的前提，重合度即置信度

多份独立诊断各自命中同一组阻断时，重合点成为高置信真相；差异点暴露各自盲区——某缺陷只有一个模型命中，恰恰证明单份扫描不可全信。允许互引时，交集会被第一个模型的框架污染。

正确做法：并行评审以作者后缀命名隔离（`new_todo_{名字}.md`）、头部声明互不引用；由第三方按"交集必信、并集覆盖"收敛进权威账本；扫描产物留存备查。委托外部模型做静态分析时的输出契约决定产出可用性：候选必须写成四元组——精确定位（文件与符号）、两架构的具体差异、该差异下什么值会落进哪个槽位、一条能二选一判别的真机探针（含两种读数形态各对应哪个结论）；同时禁下根因定论、禁改代码、禁提波及全系统的大改，要求候选显式声明与已证伪清单的接触面。外部候选与既有证据的关系分四类对账：正交未覆盖、机制形态不符、已被真机证据覆盖、论据修正互相印证，逐条给理由，冲突处以真机证据为准。

### 5.10 评审依据与评审对象必须分离；锚点会腐烂

拿设计过程的产物去核"设计与代码是否一致"是循环论证——被审对象不能自证；判断会随提交推进而过期（"某汇编不存在"的结论两次失效）；手工行号引用在文档重排后整表漂移。

正确做法：评审依据只来自独立源，按"原始 C 源码、设计文档、代码"的优先级排序；执行账本条目前重读目标现状；引用一律用章节与符号锚点，不用手工行号。锚点腐烂有四种具体形态：编号漂移（不同稿次编号不一致）、引用计数加错、锚点行落在前向声明而非定义、符号名凭印象写错——拿到任何转述型产物先跑四条机械检查：编号分布抽查自洽、分布表逐行相加对账、锚点首命中行核返回类型、可疑符号全仓逐字检索取定义。第五种形态是整份交接件或会话摘要的叙述过时：交接件称"有未提交改动待补验证链"，实际该改动早已提交入库；摘要对同一事实留下两说矛盾。处置：引用任何转述（交接件、摘要、开场指令里的"未完成项"）前先对版本库现状取证（提交历史与工作树状态），矛盾处用一次新鲜净态复跑定标；写新交接件时逐条点名旧件的过时点并声明权威优先序，旧件留档不改。

### 5.11 自洽的假说最危险：巧合数据能编出完整叙事，撤回时须声明净结论

全帧取证抓到"长度寄存器恰等于目标指针值"的巧合，可自洽推出"失控清零覆盖堆池"的完整叙事——一条更正即撤回（该清零是分配器对新页的合法操作）。同弧线内"游标回卷""越界清零"两个中间假说也被逐轮读数修正；假说撤回若连带淹没本轮已实证的部分，净成果反而变模糊。

正确做法：假说叙事必须能被所引数据的原始读数否证；撤回就地追加更正、不改写原条目，并同条声明"本轮仍成立的净结论"；每个中间假说标注当前证据等级（猜想/有佐证/已证伪）。姊妹形态：排除结论成立不等于排除论据成立。一条"该路径不可能收到大值"的排除论据建立在"异常值会触发溢出类防护"上，而"把指针当长度"这类毒值在 64 位量级下恰好不触发回绕检查——结论对、论据错，错误论据会当"已证事实"被后续轮次继续引用。引用任何排除结论前复核其论据里的界是回绕界还是绝对界；发现论据错误时就地更正论据并声明结论不变。

> 来源：`.review/zcode/edge1/FIXLOG.md` 迭代 24（提出与撤回）；`PATTERN-SCAN-REPORT-20260923.md`（更正纪律节）；`NK4C-WORKLOG.md` §1.120续-33/续-34（排除论据被推翻而结论维持）；`NK4C-BUG-AARCH64-VEC-CAP-GLM.md` §2（论据修正节）

### 5.12 声明-事实机械对账：逐笔提交按 diff 核对 message 声明

对两百多笔提交逐笔用版本工具的统计输出核对"声明改了什么"与"diff 实际动了什么"：绝大多数一致，唯一实锤违规是全量暂存把依赖目录卷进版本库（忽略清单无条目）；两笔初判违规经全文核实是评审脚本正则误报。体量异常（单笔新增数千行）是最高效的筛查信号。注意口径标注：某复证结论须注明架构与核数口径，否则与另一弧线的"未达成"表述构成假性矛盾。

正确做法：对账判据四条——纯文档声明不得含代码文件、"探针全回滚"声明对应提交本体应为纯文档、保护文件清单（原始 C 源禁改、构建产物与依赖目录禁入）、单笔体量阈值；忽略清单补条目加缓存清理（盘面保留）；结论必带架构/核数/形态口径。

> 来源：`NK4C-REVIEW-REPORT-20260927-R3.md`；`.review/zcode/edge1/REVIEW-R3-STATE`（评审进度账）；`STRUCTURAL-DEBT-REGISTER-20260930.md` 附录 B（高价值台账为每条承重主张配可重放的验证命令与判定结果——"台账是否过期"从人工记忆问题变成可脚本检查的问题，一次复审即揪出十条失真锚点）

### 5.13 开放项收拢账+已闭环防重领：四层收进一页，双向对账防漂移

多智能体并发下开放项散落在账本行、弧线工作日志、修复日志登记节与仓级杂项四处，导致已修项被重复领取、未修项丢失。全系统审计后按四层收进一节：里程碑表（带阻塞点与接手入口指针）、协作账本只留指针、未修发现表（每项带级别与最近复核日期）、专设已闭环节。

正确做法：领取按"认领→专属树作业→合入→销账→本节划掉"闭环；未修发现与修复日志双向对账（修复侧销账时同步划掉）；每项标最近复核日期让陈旧项显形。

> 来源：`edge_todo.md`「NK4-OPEN」节；`STRUCTURAL-DEBT-REGISTER-20260930.md` §0（台账状态六态受控词表——开放、临时方案已落地、部分修复、已实现后证伪回滚、已裁决未实施、已收敛——每个状态自带行动指引，中间态压进二值会让续做者要么重做已做之事、要么误以为已彻底解决）

### 5.14 标注"架构级待裁决"之前先查权威源码

一处多核中断控制器解析被钉成"缺字段、三方案待裁决"；实读模拟器源码钉死：该场景下固件必发独立子表、旧解析代码从错误偏移读的其实是另一个寄存器组——不是该不该放宽安全检查，是解析器少实现一个标准子表。三方案裁决问题消失，变成一个普通补全任务。

正确做法：把问题升级为"架构裁决"前，先读该行为的权威实现（模拟器/固件/规范源码）确认现象是设计意图还是实现缺口；故意拒绝畸形输入的检查原封保留，缺的是解析分支；启动参数差异属引导契约还是调优旋钮，分别归位。同族形态：下"本树无 X"类否定结论前，检索范围必须覆盖 ground truth 全树——只搜内核半树漏掉系统头半树，曾造成"ABI 不可钉死"的边界条目误判（类型实际定义在 sys 子树头文件里）。

### 5.15 认领板销账三坑：先于合并强删分支、删自身工作目录毒杀全会话、选择性提交丢弃暂存删除

三个实证坑。其一：销账内部是强删分支，把合并与销账串成一条管道时，管道尾部命令的零退出码会掩盖合并失败，销账抢跑销毁含未合入提交的分支——合并与销账必须拆成两次调用且合并不加管道，销账前核对自身提交已进主线祖先。其二：销账删除专属工作树后若持久工作目录仍在树内，会话每次 spawn shell 都以失效目录为工作目录即告失败，子代理同样继承坏死目录，本会话无法恢复，且残留分支与注册未清——销账一律先回到主树目录执行；已中招只能新会话补注册清理。其三：对"索引已暂存删除、工作树已重建为未跟踪"的路径做选择性提交会按工作树内容取语义，删除被静默丢弃——纯索引删除落库前先核对暂存清单。

> 来源：跨会话记忆 `minix-rs-claim-release-before-merge.md`、`minix-rs-claim-release-cwd-hazard.md`、`minix-rs-pattern-gate-c61.md` 销账判例（见 6.3）

### 5.16 长程自主任务靠外部记忆交接：账本顶部状态即权威，接手用定点读、只记事实不评价前棒

长程会话随时可能被收尾或上下文压缩，脑内状态不可靠；接手者通读全史代价高且易被前棒的自我评价带偏（评审实测抓到过自报盲区延伸的漏报）。

正确做法：交接协议——每次提交前更新账本顶部状态（当前断点编号+一句话现象+下一手第一动作，具体到命令），收尾前三自查（顶部最新、无未提交改动、每节有新停点）并另写交接文件，上下文逼近耗尽时先落记录再做里程碑；接手协议——开工只读版本库现场、账本头部与尾部、路线图当前单元，其余用检索定位补读；接手核账只记事实清单（现场抄录、测试计数实测、冒烟实跑、账本提炼），不写评价，保留独立重判权；纯诊断轮也用专用前缀提交固化探针与结论（修复与探针分开提交）。四点扩充。在途生产改动的双向纪律：验证链未走完的生产改动显式标注"已实施未接线"留在工作树不提交（丢弃等于白做，硬提交等于跳过验证链），交接件写明缺口清单与接手第一动作——核对在途改动完整在位后补验证链，不重写不硬提。死路清单是交接件里最重要的节：已证伪假设逐条编号（假设内容、证伪方式、与当前问题关系），否则接手的独立分析会重提死路帮倒忙。长程任务的"一直迭代"靠机制不靠语气：持续执行依赖外部目标注入（每轮重注入加"目标不得缩小"约束），开场必须确认进入该模式，并显式写明"禁止以完成单个取证轮为交付停止"。单轮任务书固定四件：本轮唯一目标、明确不修清单（附与目标的正交性说明）、已定谳方向勿推翻的声明、完成判据在总目标中的位置——没有不修清单，接手者面对多个可修缺陷会自选方向耗散预算。

### 5.17 全量落盘是杂物入库的高发点：暂存永远用明确路径

停止令触发的全量落盘一次入库 543 个文件 35.7 万行，含临时目录、会话配置、聊天归档等非仓库物；git status 长期显示他人遗留的已改私人文件，全量暂存会静默卷入提交。

正确做法：永远 `git add <明确路径>`，禁 `-A` 与 `git add .`；用户私人文件任何情况不动；落盘后用缓存移除分流杂物；评审把"落盘杂物"单列为流程级发现。忽略清单本身要按"放行规则"审计：一条目录级放行规则会让其下所有无后缀规则的大体积产物（磁盘镜像、固件镜像、串口原始日志、中间目标目录）全部裸奔，一次全量暂存即把数百兆二进制卷进版本库；而超大对象一旦进了提交历史，后续删除无效，只能重写历史才能恢复推送。新增产物类型时同步补忽略规则并验证放行规则的作用域。

> 来源：`NK4A-REVIEW-REPORT.md`（危险面节）；`NK4C-RESUME-PROMPT.md` §1.1/§9；跨会话记忆 `git-forensics-handoff-20260930.md`（见 6.3；放行规则裸奔与超大对象阻断推送）

### 5.18 账本行内日期与文风门的结构性冲突：按文件分流看检查结果

文风检查的正文日期规则面向读者向的 stage 文档；协作账本的体例又强制每条完成记录带日期，且历史行全带日期——两者结构性冲突，工具没给账本豁免。

正确做法：按文件分流——stage 文档必须零命中；账本文件的日期命中照惯例保留并在交付说明点明，不为清零删日期或给日期加反引号（与既有行不一致）；真要清零须先给检查工具加账本豁免（涉工具改动，走账本登记）。

### 5.19 多模式 grep 的负结论：按模式拆分计数，且禁止出自被 head 截断的输出

一条 `grep -rE "a|b|c"` 把多个语义不同的模式合并计数，任一模式的子串噪声（如未锚定的 `dc `/`ic ` 命中 2960 行无关文本）会把真实命中淹掉，叠上 `head -N` 截断，就会对「零命中」下出假负结论——直到外部复核才由反例推翻（riscv 静态扫描第 4 轮「全仓 fence.i 零命中」误判，第 5 轮翻案：实有 2 行活指令）。

正确做法：负结论（「X 不存在/从未入账」）必须**逐模式分开计数**（每个模式单跑一条命令、各自看命中数），不得从多模式合并输出反推；**禁止对被 `head`/管道截断的输出下负结论**——截断处未验即「零命中」不成立；下负结论前至少对关键模式跑一次不截断的全量计数并留可复跑命令（与 5.5 「归因附可复跑命令」同源）。全称断言的检索实参要与断言范围词一字不差。

> 来源：`notes/rewrite/fork-syscall-rewrite/riscv-reviewlog.md` §D.11 自审段（债⑩ fence.i 散点翻案的完整因果链：未锚定模式噪声 2960 行＋`head -8` 截断＋截断处未验证即下负结论）

### 5.20 交接声称与里程碑声称都要亲跑复现并绑定确切配置：启动器默认值是隐形变量

三类实证。其一，交接方声称的回归崩溃，接手方在受控配置下多轮复现不出——报告极可能撞上与本案无关的已知多核早期崩溃（启动器默认多核是无命令行选项的硬编码默认值），"已知无关崩溃在非等价条件下伪装成新缺陷"，差点否掉一个正确修复。其二，"里程碑已达成"的前提仅在手改启动命令的单核配置下成立，标准配置下实未达成——声称与配置脱节让目标状态被高估。其三，确定性反证要读日志行号序：标志行在崩溃行之前证明"到过"。

正确做法：收到回归或崩溃报告，第一动作在等价配置下亲手复现，复现不出走幽灵分支并补静态安全面分析，结论要能解释报告为何产生；声称任何里程碑必须写明确切启动命令与配置，审计以项目预定义的标准配置复跑为准；真机验证按已知问题选默认隔离配置（如已知多核问题的架构默认单核）；读崩溃日志先看行号分形态、重建"到没到过"的时序。

> 来源：`NK4C-AARCH64-EXEC-REBIND-LIVELOCK.md` §6/§9；`NK4C-WORKLOG.md` §1.120续-36/续-46（幽灵证伪与前提纠正）；`notes/rewrite/fork-syscall-rewrite/NK4C-MIGRATION-20260930.md` §3（启动器默认值）

### 5.21 "外部已完成修复"类前件用固定证据清单核查：不存在的提交不编造评审

用户指令反复以"缺陷已由外部修复，评审其提交后继续"下发，而证据显示不存在对应的新提交。风险两面：编造一个对不存在提交的评审（幻觉），或原地空转等待（停滞）。同一套证据清单可机械裁决：全量拉取远端引用、按提交时间排序看全部分支、检查暂存区与工作树状态、对未跟踪文件核对修改时间与自陈边界（自陈"禁下结论禁改代码"的静态分析件不是补丁）。

正确做法：对"外部已完成修复"类指令前件执行固定证据清单核查并编号累计次数；结论诚实上报（不存在的提交不编造评审），随后按总目标继续推进真正前沿；真正由外部落地的修复走本地独立验收（验证链全绿加代码评审）后才销账，不重复审查已验收结论。

> 来源：`NK4C-WORKLOG.md` §1.120续-40/续-44/续-48（多度核查清单）；`NK4C-GLM53-PROMPT.md` §4（外部在制件的边界声明样例）

### 5.22 跨机器迁移的抢救面：远端同步第一、易失资产三处置、环境依赖可重建、恢复顺序分层

版本库只保已跟踪内容；评审进度账、修复日志、临时目录里的对账表原件、助手记忆目录都在机器本地，报废即失；更大的单点故障是本地领先远端的大量未推送提交——迁移不先同步远端或整目录拷贝（含作为真值源的原始 C 源子树），全部工作丢失。环境依赖同样易失：容器镜像、夜间工具链、固件变量文件、引导工具链都不随仓库走。

正确做法：迁移交接件固定四表——迁移即刻快照（当前提交、分支、领先远端笔数、复现刚需文件是否被跟踪）；环境依赖清单（容器镜像导出导入或按分层重建、工具链、固件与引导工具按前沿补装）；不会随版本库迁移的本地状态处置表（逐项三处置：折叠入正式文档、抢救入仓库固定路径、确认可弃并写明关键结论已有副本）；新机恢复顺序（按线分层：主线权威件、评审线件、账本顶部）。迁移第一动作是对账并同步远端。

> 来源：`notes/rewrite/fork-syscall-rewrite/NK4C-MIGRATION-20260930.md` §0/§3/§7；`NK4C-REVIEWER-SESSION-RECORD-20260930.md` §3/§4；跨会话记忆 `git-forensics-handoff-20260930.md`（见 6.3）

### 5.23 跨架构移植把已付学费钉成同型位点表：实施轮从"探索"降级为"对账"

同一缺陷族（特权指令通道门控、栈切换寄存器生命周期、监督态访问用户内存、引导形态并存）在已落地架构各付过学费；新架构线的做法是把同型位点全部钉到文件与符号的对照表，按三档判定（已免疫、中招、条件不足需真机），再配三判定语义（已就绪为静态可证的必要条件、有缺口钉位置与形状、需真机判定的单列交接表）——静态结论与真机判据的边界由此清晰，"已就绪"永不替代真机判据。量化收益：已免疫档全部来自架构中立修复的免费继承（公共腿不动、架构差异进底层），且风险集中在"未完成的部分"与"完成部分之间的组合缝隙"，没有一处"已实现但语义错了"。

正确做法：开新架构前先出同型位点对照表，实施轮只对账该表不重新探索；已裁决的路线不复议；修复尽量落在架构中立层使后续架构免费继承；每引入一条新控制流路径，用旧架构的评审清单当验收单；跨架构"同构造同源"推论只作假设登记，一侧证伪后另一侧必须独立复判（两侧并发条件可能根本不同）；叙述与当前代码冲突时以代码为准并标注翻案。

> 来源：`notes/rewrite/fork-syscall-rewrite/riscv-reviewlog.md` §0/§C 表汇总/§A.11；`NK4C-WORKLOG.md` §1.120续-77a（对账闭环实例）；§1.120续-89/续-90（延后缺口到达即精确路标：静态判于早期、登记附"消费点加先例锚点加到达条件"三要素，真机推进到该点直接镜像补齐一次通过）；§续-95（立"架构间语义差异"假设前先逐字比对两架构同名路径，读起来像不是证据——一步逐字比对即可证伪并诚实撤销）

### 5.24 挂起裁决设条件式预裁：预裁不是终裁、显式不预裁、修订须本人同意

挂起裁决项的真正成本不是裁决本身，而是"要不要开始想"这类低信息量打断反复落在执行路径上。预裁制度自身有三条防腐烂纪律：依赖尚未产生的真机证据的裁决一律不写死（预裁不是终裁）；与正文冲突时预裁章单向优先，勘误以补注追加、不回改正文（保留审计轨迹）；候选取舍依赖未来实测的，显式声明"不预裁"并写明判据落位时间点——现在写死就是在制造空壳断言（与"裁决前置的文档拖着执行不落最后留下空壳"的已登记病灶同源）。

正确做法：为挂起裁决设可观测的触发条件（如"真机稳定运行若干轮次且无在途相关战役"）；预裁文本与被预裁的分析文本物理分离、冲突单向优先、修订权单点（本人同意才可修订或撤销）。

> 来源：`notes/rewrite/fork-syscall-rewrite/riscv-reviewlog.md` §E（用户预裁决章）

### 5.25 注释与账本里的设计论断是可失效命题：写明依据链，通道语义变更时重扫全部既有论断

三类实证。"真实固件布局互不相交"的注释断言被证伪（固件自身交付的段与保留集必然自重叠），据此写的整段丢弃逻辑留下未覆盖尾块。"零调用者是有意设计"的论断，其依据（每次页表项写自带刷新）被同批修复在另一通道上打破——依据失效，但注释与账本不会自动失效；且"直接映射保持翻译恒定"只覆盖页表页自身的翻译，不覆盖被修改目标页在目标进程缓存里的旧翻译，单核下靠调度事实自然闭合的窗口，在多核或惰性切换路径上重开。同族两态：把设计行为（命中停车接收者时延迟投递）误标为"失败回退"，会让下一轮去追不存在的问题；"防御深度"叙述与实测路径不一致（实际靠固件内存类天然排除而非显式扣除）会误导后续重构。

正确做法：注释与账本中对系统行为的断言（尤其对外部系统的断言）当可检验命题要求证据；每条"有意设计"写明完整依据链（依赖哪个调度或硬件事实）；任何通道语义变更后重扫该通道上全部既有论断；被证伪的注释改为诚实披露开放项；给代码路径定性"回退或失败"前先读设计注释与 C 对位段；叙述与实测冲突以实测为准并就地更正。

> 来源：`NK4C-WORKLOG.md` §1.120续-51（注释断言证伪）；`notes/rewrite/fork-syscall-rewrite/riscv-reviewlog.md` §D.12（设计论断依据被自家修复打破）；`NK4C-WORKLOG.md` §1.120续-29/续-66（设计行为误标与防御叙述修正）；§续-153（C 对位口口相传漂移：缺省臂语义被传成恐慌，引用 C 对位必须带行号锚定）

### 5.26 取证副产品中的独立真缺陷：独立坐实、全量因果判别、独立立项，不顺手修

长弧取证常顺带坐实与本案无关的真缺陷（如某架构浮点状态跨陷入不保存恢复）。处置错误的两端：顺手修会吃掉剩余预算且制造"已修未愈"的混淆；只做抽样排除就归因会错杀——抽样的"未排除"与全量的"彻底排除"是两种证据强度，直到对真实加载镜像做整类指令的全量统计，才彻底证明该缺陷产不出本案毒值。

正确做法：副产品三步——独立证据链坐实；与当前缺陷的因果判别做到全量而非抽样；据此决定独立立项（单独实现加独立评审、按架构隔离）还是登记不动；不在取证轮顺手修、不并入当前因果链。

> 来源：`NK4C-WORKLOG.md` §1.120续-42/续-43/续-44（浮点缺陷的独立坐实与全量否证）；§1.120续-129~续-133（该登记项三个月后升格为主犯：消息头被写脏的悬案定谳为浮点寄存器跨陷阱不保存，孤儿设施独立立项修复并落地全部三架构——"登记时保留独立立案结构"使升格顺畅：证据链现成、无需重查、不与原案因果纠缠）

### 5.27 任务书的演化形态：活体权威冲突铁律、差量结构、阻塞加解锁条件、诚实边界节

系列任务书（接续任务书）沉淀出五个结构约定。其一，活体权威冲突铁律：任务书是快照、写完即开始过时，开头显式声明"与工作账本冲突以账本为准"，并给接手者就地修正义务（发现文档过时就改或标注，不为修文档另开任务）。其二，差量结构：系列任务书显式声明前作哪些条款仍然有效、本文件只写差量；被取代的条款显式标注闭合，不静默消失（静默删条款等于纪律丢失）。其三，阻塞显式化：卡死的缺陷写明阻塞状态加阻塞条件一句话加解锁条件编号清单（每条可验证、任一满足即可的或语义），把"什么时候值得再来"变成客观判据；已用掉的旁路执行完毕后显式标注闭合，防下个会话把它当退路重入。其四，诚实边界节：收尾专设一节逐条列"没做什么"——未坐实结论（嫌疑面都是候选不是结论）、名实不符的中间态（链路打通不等于上机跑通）、残留物与滚除义务归属、未验证变量；每条标责任方。其五，迭代协议写到无歧义：纯文档提交记"无代码可审"（评审协议对零代码轮次也闭合）、每轮收官核对"账本前沿指针、正文节、版本库头三方一致"（活体权威自身的自校验）、评审给出必须修的发现则必开修复轮（评审有牙齿）。

正确做法：系列任务书按五约定搭骨架；快照类文档一律声明活体权威与自身时效；卡点写阻塞与解锁条件，不用情绪判断。

> 来源：`NK4C-接续PROMPT-20261002.md`/`NK4C-接续PROMPT-20261003.md`/`NK4C-接续PROMPT-RISCV-20261003.md`（三份任务书的活体权威节、差量声明、阻塞与解锁、诚实边界节、迭代协议节）

### 5.28 回溯审计的隔离架构：分离工作树加只读已提交对象加子代理结论逐条复验

对过往提交做追溯审查时，主线在同一工作树活跃推进、有未提交在制品且共享构建产物目录——在主树上跑验证读到的是脏树而非快照态。隔离架构四件：一律在分离工作树（固定在某提交）复核；读某提交的文件一律走版本库的已提交对象读取（工作区文件会混入未提交内容）；主线的在制品不触碰、不暂存、不提交；子代理可扩吞吐但只做初筛，承重结论（缺陷定级、探针遗留、幻影判定）由审计者本人逐条读已提交对象重放复验——不盲信子代理，也不轻信提交说明。验证链对账用三列表（提交自述/独立复跑结果/精确命令）；复现有物理下限时（主线占着构建产物目录，无法重启到快照态）显式声明局限并换证据源——对已提交时段的原始串口做独立解析重放，证据从"我能重跑"降级为"我能重放原始记录"，仍是独立验证；"审计区间内的回归"与"区间外既有"分开标注，混写即误报。C 锚点未命中不等于锚点造假：先全树按符号换路径重搜再判，"路径直觉错"与"锚点假"是两种结论，行号级锚点允许±1容差但要登记。

正确做法：回溯审计按隔离架构四件套执行；验证链三列表；无法复跑的项写局限声明与替代证据源；区间内外分开标注；锚点复核失败先全树重搜。

> 来源：`NK4C-RETRO-AUDIT-20261001.md` §0/§1/§5/§10/§11（隔离架构、三列表、局限声明、锚点复核）

### 5.29 结构债的十家族分类学与批次经济学：实现成本很少是约束，稀缺的是裁决节奏与真机批次

结构债盘点把全部债条按共性归为十族——双份事实源（编译器不管的两处声明）、组合缝（各自验收都过、风险在件与件之间）、错误类型级擦除（结果类型被抹成无事件）、架构分叉双维护、承诺注释当实现（"以后会自动"式注释）、环境运气不变量（"新帧恰好是零"）、容量上限被逐轮救火拖延、静默无操作层（占位实现返回成功）、无移除条件的过渡守卫、阻塞语义在现有接口下结构性不可表达。关键洞见有二。其一，每族在仓内都已有成功治法先例（表驱动门、编译期断言交叉检查、失败关闭验证器、过渡偏离登记移除条件），新缺陷入库前先归族、归族后直接套该族先例，实现成本很少是约束。其二，真正稀缺的是裁决节奏与真机验证批次：最高杠杆批次的判据是三维乘积——已裁决（零协商延迟）×单批债密度×能否打开新的真机证据通道；伴生的复利投资是契约测试折叠——把一项仅真机可验的验收改写成宿主测试可验，此后这笔债永远不再消耗真机轮次。

正确做法：新债入库先归十族再套先例；排批次按三维乘积打分；每修一笔债问一句"验收能否从真机折叠到宿主"，能折叠的优先。

> 来源：`STRUCTURAL-DEBT-REGISTER-20260930.md` §4（十家族与先例）、§6（稀缺资源论与契约测试折叠）

### 5.30 先校准靶位再上精密工具：工具越精密，误导越便宜

重型取证基建（模拟器插件、定制观测）动工前，若靶位本身是错的（嫌疑表项的层级与槽号未定谳），插件只会带回"没人写这一格"的空结果，而这个空结果极易被误读成"插件也无能为力"、错杀最后一张牌——精密工具的空结果有两义（没人写/盯错了地方），只有先钉死靶才有单义。本案实录：观察点、扫描、插件默认参数曾在错误靶位上全部空转数轮。升级顺序写死：零安装复核（反汇编加算术定靶、读者错配排除）永远排在基建前面，插件升级条件逐条写进文档、全部满足才开专项。

正确做法：精密工具动工前先做零安装复核定靶；升级条件四条（靶位唯一、判据谓词语义干净、对照位命中、预算到位）写进文档；"工具也无能为力"的结论必须排除"盯错地方"后才许下。

> 来源：`NK4C-BUG-RISCV64-TRANSIENT-PTE.md` §6.1/§6.4（升级条件与插件降级为最后一张牌）、§3.7（靶位重估）

### 5.31 竞态嫌疑先做源码级先后顺序对账表：同序阶段之上的重排类修法全部不采纳

竞态类嫌疑（数据竞争、窗口交错）的第一张表是"源码级先后顺序对账"：把涉案流程逐阶段钉出 C 与重写侧的行号，逐阶段标注谁先谁后。对账同序的阶段，其上的"重排优化"类修法直接出局（C 亦如此且能跑，说明该顺序不构成缺陷）；偏离只可能藏在两侧不同序的阶段，或共享分配器与并发层的交互里。同族：对"目录类文档"继承来的下一步处方，落地前先对处方的事实性前提做一次检索级复核（一张全靠"以为 C 有某腿"的补腿地图被全树零命中直接否决）。

正确做法：竞态嫌疑先建两侧行号级顺序对账表；同序阶段排除重排类修法；继承的处方先验事实前提再执行。

> 来源：`NK4C-WORKLOG.md` §续-272（五阶段逐字同序对账）、§续-279m（堆预分配腿地图被否决）
