# 一次只在真机上出现的随机内存改写：riscv64 非确定性内存污染

> **本文追的是一条尚未定位写者的缺陷。** 它的登记名是「riscv64 非确定性内存污染」，取证记录里也称作「腐蚀」。目标读者是**第一次接触这件事的人或模型**，包括被请来给独立意见的外部审阅者。
>
> **当前状态**：头号候选仍然是两条线之争——**内核代客做跨空间拷贝时，走页表返回了错的物理地址**，以及**陷入与返回用户态的那几条路径把用户上下文保存或恢复错了**。但这两侧「有没有被实验测过」都已经填上读数：拷贝线有专门针对它的双走表对账探针，累计四次点火零不一致（这个读数能封住什么、封不住什么，写在第 7 章实验戊，务必连着读）；陷入与返回线则上线了进入计数遥测，**把每一条路径在一个开机周期里被走了多少次量了出来**——同族的三处缺陷由此被静态坐实并修复，而量级读数把其中「返回用户态之路上、中断还开着的那段窗口」压到「每个开机周期只武装 1 次、被时钟踩中的概率约 1.6×10⁻⁵」，也就是真实存在但几乎走不到的加固；同一份读数把「用户态那条路上的异步时钟中断」抬成计算窗内暴露面最大的一条（读数与口径限制见 3.8，候选排序见 6.2）。
>
> **另一件事是挡在目标③前面的东西已经清掉了。** 那处停摆与那张「往地址 0 写」的脸**各自定谳到一个确定性根因并修复**：停摆断在信号管理器自己的退出链上（取证记录 §续-383，机制见 §1.1），往地址 0 写断在测试程序的出生例程没有初始化线程指针（取证记录 §续-384）。目标③ 的 riscv64 腿随后跑到「36 个用例全部出结论：34 个通过 + 2 个跳过 + 0 个失败」，且把诊断探针族滚除之后复跑仍然全过（取证记录 §续-384、§续-385）。
>
> **而本文追的那条非确定性污染本身仍未结。** 它不再挡任何一条终目标，写者也没有被现场抓获——修好那两个确定性缺陷不能反证它消失了，因为它们的机制与「静默改几字节」根本不同类。这恰好就是本文继续存在的理由。
>
> 完整的九类候选与它们的当前评价在第 6 章。判据侧新增一条纪律：**凡反推出来的门槛数字一律当场用脚本算一遍、把式子写在旁边，不得从任何文档抄表**；第 8 章给出按式子现算的门槛表，并说明抄表这个动作本身为什么会成为缺陷温床。
>
> 承诺三件事：**自包含**（读完不需要再翻别的文档就能明白现场与证据形状）、**可复核**（每条事实断言都带文件与符号锚点，或取证存档路径；所有位运算与计数都由脚本算出，标注为「工具生成」）、**诚实**（哪些已坐实、哪些只有支持但未坐实、哪些结论的证据基础其实不成立，分开写清楚）。

## 第 1 章 现象：一条指令都没有执行错，内存内容却变了

一台机器上同时跑着一个内核与一批用户态服务进程（启动期由引导装载件加载的模块共 12 个，口径见 `os/qemu-tests/test-cmd-smoke.sh` 的开篇注释）。其中有个测试进程做了一件极其实诚的事：它先算出一串伪随机字节，把它们搬进两块缓冲区，再把两块缓冲区的每一个字节喂进一个摘要函数，最后把摘要结果与**源码里硬编码的一串十六进制常数**比对（常数出处 `minix3/tests/lib/libc/string/t_memcpy.c`，第 54 行，工具生成）。

它的算术全对。搬运函数全对。摘要函数全对。把完全相同的程序放到另一个环境里裸跑，结果与常数逐位相同。

**可是在这台机器上跑，最后那串摘要就经常是别的值。** 而且每次开机得到的那个「别的值」都不一样：这次是 `9f2e1c56`，下次是 `25f4881b`，再下次是 `0ecef203`。同一个二进制、同一个磁盘镜像、同一份内存布局，只因为重新开了一次电源，答案就换了一个。

这就是本案的全部麻烦所在：**缺陷不在任何一段计算里，而在计算所用的数据于两次采样之间被悄悄改掉。** 没有人写了坏值，没有硬件故障报警，也没有异常抛出——只有事后核对时发现，某一小块内存的内容不再是它刚才的样子了。

它露出水面的面孔不止一张。下面这张表按「现场长什么样」列出目前记录到的全部形态，逐行带来源；行数本身不做维护，以表为准。它们被认为可能出自同一个机制，但**这个「同一个」始终是假设，不是已证事实**。

**为什么「拷贝长度先导」与「爬行」这两行重要**：`kdst copy` 就是**内核代客跨空间拷贝**的诊断行——三次响亮失败全部由它先导，而爬行也被归到同一个拷贝路径的挂起重试。也就是说，**同一嫌疑路径已经用自己的遥测碰了两次门**。另有一处仓内历史记录可作旁资：栈回溯代码里就写着曾经因为这类拷贝写坏目标而级联出野值（`os/kernel/src/stacktrace.rs` 的注记，工具生成行号 L259 附近）。

**为什么这类缺陷比崩溃难得多**：崩溃会自己报到，并把出错位置递到你手上；静默改写不会。你唯一能确定它存在的办法，是事先设计一个「内容必须一直正确、且一旦有任何一字节变动就会立刻显形」的观测装置。本案的整个进展史，本质上就是不断制造更好的观测装置的历史。

### 1.1 最后两张脸分别属于哪条线（两张都已定谳，而且都不是那条静默改写）

这两条很容易被并成「又出事了」，然后一起拿去追写者。但判别的问题应该是：**它有没有改变内存的内容？** 答案不同，追查线就完全不同，混在一起会整轮白费。回头看，这两张脸**一张也没在改内存内容**，于是两张都不是本案。

**其一：整机不再推进——已定谳并修复，断点在信号管理器自己的退出链上。** 死前的顺序是：某个测试程序执行完成 → 它写虚拟地址 0 → 该次写被判为非法地址 → 信号 11 正常投递（这一步行为是对的）→ **同一个已经处在退出流程里的进程又报了一次页故障** → 内存服务按「这个端点我认不出来」那个出口回一个错误 → 串口到此不再增长。

最初读出来的因果是「内存服务拒服务之后没人解除那次缺页等待」（取证记录 §续-382）。**那只是表象**：内核确实只在内存服务主动下发清位命令时才解除等待，但真正的断点更上游——信号管理器自己把那个进程退掉了，只是**退的时候把信号号弄丢了**。完整链条是：段错误属于要转储内存核的信号 → 进入退出流程；退出流程第 8 步向文件系统发「转储核」通知时，载荷里的终止信号号取自退出码，而退出码所在的对象要到第 10 步才建立 ⇒ **信号号恒为 0**（上游 C 真源是先写终止状态再走退出，`minix3/minix/servers/pm/signal.c:sig_proc_exit`，工具派生行号 L552）；文件系统对信号号为 0 的转储请求回一个错误（守卫本身正确，是上游喂了个 0）；而信号管理器对回复的识别不认负的 errno，这条消息落进静默丢弃臂 ⇒ 重启流程永不执行 ⇒ 僵尸化、清槽、告知内存服务全部不发生 ⇒ 父进程永久等待，且**静默丢弃本就不出声**，所以没有任何崩溃文案。

这里的普遍价值比那个缺陷本身大：**一个拒绝服务的出口必须同时回答「谁负责解除等待」**。如果只把「杀掉服务进程」换成「回一个错误」，而没有把发出等待的那一侧一起收尾，错误处理就比原来礼貌、后果却比原来致命。而修法的红线也由此得出：**只补解锁、不补终止，会把「永久挂住」变成「反复缺页的活锁」**（上游 C 在这里是大声失败：端点校验不过就直接 `panic`，`minix3/minix/servers/vm/pagefaults.c:handle_pagefault`，工具派生行号 L85-L86；全仓解除缺页等待的唯一入口是 `os/kernel/src/syscall.rs:dispatch_vmctl` 的清位分支）。本重写选择的是「补终止语义」：`os/servers/pm/src/exit.rs:exit_proc` 增加一个终止状态参数（工具派生行号 L338、L342，并在 L446 把它填进通知），与 C 的 `mp_sigstatus` 对位（取证记录 §续-383）。

**其二：往虚拟地址 0 写——已定谳为线程指针未初始化，从本案样本集移出。** 当时把它归回「指针字段被改」这一族的推理是：同一个二进制在 64 位 ARM 的同类门上全部通过，而被切断的那串字符串处理函数与上游真源逐行同形（`tools/atf-c-compat/posix-stubs.c:232` 对 `minix3/lib/libc/string/stresep.c`，已核）——既然被测代码不是新的，一个指针变成 0 就只能是被改掉的。**这条推理的漏洞在于它默认了「只有内存内容会变错」**：还有一整类可能是**寄存器被换了**。本例就属于后者，而且不是随机换——测试程序的出生例程根本没给线程指针赋值，而错误码变量在本工具链里是线程局部存储，它的写入形式就是「以线程指针为基址、偏移 0 存一个字」（`sw a4, 0(tp)`）。线程指针为 0 ⇒ 每一回都落在地址 0。

两条定谳证据把这件事钉死。第一条是**反汇编上三个独立的死亡指令地址全是向错误码写**（取证记录 §续-384）；第二条是**另一架构上出现过同族形态**：同一个出生文件的 64 位 ARM 那条臂上写着一条真机取证注记——标签如果写在地址对齐指令**之前**，低位地址重定位就会落在填充用的空操作上，取到的线程指针是两枚填充指令拼成的垃圾值，后果同样是「错误码写变成野地址写」（`tools/atf-c-compat/startup-minix.c`，工具派生行号 L137-L141）。同一种故障在两个架构上都由「线程指针没设好」导致，而且都只在**碰错误码的用例**上发作——这正好解释了为什么本案曾有一段时间「12 个不碰错误码的用例全绿、只有一个用例族全灭」。**修法**：riscv 那条臂补上 `la t0, __tls_base` + `mv tp, t0`（同文件工具派生行号 L162-L163），与 64 位 ARM 那条臂同形；两臂为何一个要减线程控制块头偏移、另一个不用，也按链接脚本与符号类型对过（取证记录 §续-384）。

**于是本案真正剩下的脸只有一张**：上面那行「内核自己的打印缓冲被局部改字节」。它至今没有被解释，也仍与概率性改写的形状兼容。

⚠️ **这张脸对本文第 6 章的立论前提构成张力，必须点明。** 第 6 章整章建立在「测试进程算数据的那段时间里，内核侧看不到任何活动」上面（见 3.1 与取证记录 §续-343）。而现在这一处字节改写**发生在内核自己的打印路径上**。两种读法都还活着：要么两处改写不同源（一处落在用户页、一处落在内核缓冲，是两个写者）；要么「无内核参与」这个前提本身漏了一类活动——比如内核在自己被打断的时候改了自己的缓冲。**[待验证：被空字符盖掉的那次现场是否落在被计数遥测划定的计算窗内；本文未把该跑与 3.8 的窗口起终读数对齐]** 在对齐之前，第 6 章那张清单的适用范围要按「用户数据被改」这一族读，不能当成全部污染的共同前提。

## 第 2 章 那个测试为什么正好是观测装置

先讲清一个概念。本文反复提到「自动化测试套件」：它是 MINIX 3 自带的一批 C 语言测试程序，每个程序里声明若干「用例」，用例通过断言判断被测函数的行为对不对。本文的主角是其中一个用例，叫 `memcpy_basic`，出处 `minix3/tests/lib/libc/string/t_memcpy.c:memcpy_basic`。

### 2.1 它为什么灵敏：摘要链的雪崩性质

把一块数据算成摘要，就像把几十种颜料反复调和：任何一滴颜料在任意时刻掺进去，最终颜色都会改变，而且改变是全局的、无法从结果反推掺了哪一滴。摘要函数的这个性质是设计目标，不是副作用。

这个用例还把灵敏度推到更高：它用的是**一个持续累积的摘要上下文**。整个用例从头到尾只有这一个上下文，中间不断喂数据，最后一次取值。所以中途任何一次内存改动，都会被后面所有数据一起放大，绝不会出现「改了但改在没人看的地方」。

### 2.2 它到底跑了多少数据（下面的数字全部由脚本算出，标注「工具生成」）

源码骨架（`minix3/tests/lib/libc/string/t_memcpy.c`，行号由工具派生）：

- 三四个宏：对齐种类数 16、长度种类数 4、缓冲区类型数 4（L39-L41，工具生成）；
- 一块测试缓冲区的大小 = 16 × 4 = **64 字节**（L45，工具生成）；
- 两块放在只读/初始化数据段，另两块放在函数栈上（L47、L87，工具生成）；
- 摘要上下文 `mc` 是一个全局数组，一个元素（L43，工具生成）；
- 期望值是硬编码的 32 位十六进制串 `7b405d24bc03195474c70ddae9e1f8fb`（L54，工具生成）；
- 核心循环：对 16 × 16 种偏移组合，先给两块缓冲区各重填 64 个随机字节，再做一次搬运，再把两块缓冲区依次喂进摘要（L62-L75，工具生成）；
- 用例正文对 4 种缓冲区类型两两配对、跳过自己配自己，于是得到 **12 个有序对**；每对内部有 256 种偏移组合（L94-L97，工具生成）；
- 全用例**只有一处断言**：比较最终摘要与期望值（L99，工具生成）。

由上面这些数字可以算出：

| 量 | 值（工具生成） |
|---|---|
| 摘要检查点总数（= 偏移组合数，即当时设计的逐组校验粒度） | 12 × 256 = **3072** |
| 搬运函数调用总次数 | 12 × 13 784 = **165 408** |
| 由随机流写入的字节总量 | 21 172 224 字节 ≈ **20.2 MiB** |
| 送进摘要函数的数据总量 | ≈ **20.2 MiB** |

于是这个用例的品性就很清楚了：**它是全套件里唯一在长时间里对全部内容做一致性核对的用例**。其余三十五个用例几乎都只检查返回值是否为指针非空、字符串是否等于某个短常量——改一个字节它们可能毫无反应。而这里，20 MiB 数据流过一条累积链，最后只有一句比对。

### 2.3 灵敏的代价：能感知，不能定位

单点断言意味着「知道被改了」和「知道被改在哪」是两件事。这个装置能告诉你「这一跑被击中了」，但它给不出时刻、给不出地址、也给不出改写者。本案取证的主要工作量都花在把这一个比特位的信号，逐步升级成能定位字节位置的装置：先在每个检查点打印累积摘要（第 3 章的「分歧对」），再把每个偏移上的 64 字节全量打印（第 3 章的「全量转储」）。每升级一次，定位精度就细一层，但**插桩本身也在改变被观测程序的执行时序**——第 4 章会用一整节说明这个副作用如何误导了取证方向。

### 3.2 真机上「完全正确」是可达的

**读数**：一次真实开机里，逐检查点校验的 **3072 个内层块全部对账无差异**，最终摘要与裸机参考**逐位一致**，串口日志完整跑完约 1.5 MB，测试报告 `passed`（取证记录 §续-363）。

**这条为什么关键**：它把「我们的实现有系统性错误」这个解释彻底掐掉了。既然同一套代码同一套镜像可以一分不差地跑完，那么历次错值只能是**每次开机是否被击中**的差别。缺陷从「必现的算法错」重定性为「概率性的内存改写」。

### 3.3 命中概率随暴露时长增加而增加（目前还不能称「正比」）

同一缺陷在三种暴露时长下的读数（取证记录 §续-340、§续-364）：

| 暴露时长 | 读数 | 结果 |
|---|---|---|
| 短启动（只做启动与几条命令） | 常规通过 | 常常不被击中 |
| 中窗（420 秒 / 1800 秒） | 9 个用例出终态 / 23 个用例出终态 | 恰好 1 个失败，即本用例 |
| 长窗（36 个用例全量、3600 秒） | **0 个用例出终态** | 在第一个结果行打印出来之前，内核就因 5 章那条野地址停住了 |
| 同样的长窗，但换成三处陷入/返回路径都修好后的内核 | **24 个用例出结论**（22 通过 + 2 跳过 + **0 失败**） | 跑到第 13 个测试程序时整机不再推进（即 §1.1 那条停摆）；本案的金丝雀的两个用例都在通过之列（取证记录 §续-378） |
| 同样的长窗，两个确定性缺陷都修好、诊断码族滚除之后 | **36 个用例全部出结论**（34 通过 + 2 跳过 + **0 失败**） | 整套跑完至进入多用户态；本案的金丝雀全绿（取证记录 §续-384，滚除后复跑见 §续-385）——**这一行是当前最新的长窗读数** |

**强度限定【重要】**：这组数据支持的是「暴露越久越容易命中」这个**单调上升**关系，**不支持**「命中概率与时长成正比」这个更强的断言。最自然的累积模型是参数为 λ 的指数分布形状：时长 T 内至少命中一次的概率为 1 − e^(−λT)；只有在 λT 远小于 1 的低命中区间，它才近似等于 λT。本案样本量远不足以区分这两种形状。

**还要排除一个误读**：上表第三行（0 个终态）**不能**当作「命中率更高」的统计点——它不是被同一类静默改写打穿的，而是被一条**另外的响亮故障**提前截断了。它能支持的结论只有一个：长时间跑这套件会被各种形态打断，因此「靠重跑碰运气」这条路不可行。

**第四行与第三行不是同一个观测装置，不能直接相减当作改善幅度**。它们差的不仅是内核里那三处修复，还差着探针形态（有无进入计数读数行）与启动镜像（是否重新播种）——具体的分组见 3.8 末尾。这一行能支持的结论是：**同一个长窗负载现在能跑过 24 个用例而零失败**，而截断它的那条故障已经不再是野地址 panic。

### 3.4 与处理器模拟器的版本无关

两条不同世代的模拟器版本（8.2.2 与 9.2.4）跑出同一族面孔（取证记录 §续-346）。这条证据把「模拟器的软件内存管理有缺陷」这个诱人的解释削弱到很低的位置——但注意，它没有完全否证：同一族的两个版本仍可能共享同一段有问题的代码路径。**[待验证：只换版本、不换后端（例如改用支持硬件虚拟化的加速器）的对照未做]**

### 3.5 只有这一个架构有现象

同一个内核、同一套虚拟内存服务、同一套测试套件，在 64 位 ARM 上 36 个用例全部到达终态且零失败（取证记录 §续-286；门脚本 `os/qemu-tests/test-atf-aarch64.sh`，判据见附录 A）。这条把嫌疑面从「共用的上层逻辑」推到「RISC-V 独有的那部分」，也就是分页实现与架构相关的陷入路径。

### 3.6 改写是「小而准」的，不是整页覆盖

**读数**（取证记录 §续-349）：在命中那一跑里，两条输入缓冲全程未被破坏、随机数表全程未被破坏，只有摘要上下文变了。而**摘要上下文与随机数表在同一个 4096 字节页内**。

**本文作者独立复核了这条的算术**：摘要上下文起始 `0x80200108`，随机数表起始 `0x80200000`，相差 **264 字节**，同一页（页号 `0x80200`）；摘要上下文的尺寸 = 4 个 32 位状态字 + 2 个 32 位比特计数 + 64 字节残留输入缓冲 = **88 字节**，占到 `0x80200108`–`0x80200160`。

**因此**：一次页级清零、一次页级拷贝、或者一次「整页错位写」都不可能产生这个读数——那会顺手毁掉同一页里的随机数表。被改的是**几字节到几十字节量级的精准写**，落点在 88 字节的摘要上下文里。（摘要上下文被改而输入缓冲未改，本身就足以让最终值面目全非，因为状态字和比特计数都在链上。）

**[待验证：264 字节的间隙里住着哪些全局量，本文未逐项核对目标文件的符号布局]**

### 3.7 面孔清单：被击中的对象不固定

已观测到的被击中对象有四类：测试进程的数据段、进程间共享页上的记录结构、内核启动期使用的模块镜像、内核交接数据（取证记录 §续-363 的画像终稿）。改的具体位置逐次开机不同。

**强度限定【重要】**：能说的只是「**目前每次取证只观测到一个污染对象**」。这**不等于**「每次开机只发生一次写」。两种很容易发生的屏蔽机制都会让第二处写看不见：其一，第一处写一旦破坏控制流，程序就异常终止，后面的写根本来不及发生或被打印出来；其二，现有探针只保存第一处差异。因此「单次一处」目前**不能当判别依据**使用。

### 3.8 每条陷入与返回路径在一个开机周期里被走了多少次（已实测）

这一条把第 6 章的排序从「谁读起来更合理」换成「谁在这个负载下真的被走到、走多少次」，是本文目前最硬的一条新事实。

**装置长什么样（注意：这套计数器已随诊断码族滚除，下面的读数作为历史记录保留，代码里已不存在）**：当时用七个计数器（`os/kernel/src/trap_dispatch.rs` 里的 `NK4C_LEG_COUNTS` 数组），每走一条路径做一次原子加一；槽位用命名常量而不是裸数字，以免接错对象；「中断还开着就进返回路径」这一项由一个直读状态位现行使能位的辅助函数判定。读数挂在测试探针已有的两条魔术串上（`os/kernel/src/syscall.rs:nk4c_legs_report`），**在计算窗的开头与结尾各打一行**，所以「窗内增量」是两次累计值相减得到的；每开机一次只多两行串口（+295 字节），不会因插桩本身改变被测时序。**现在要重跑这套读数必须先把探针加回**（滚除见取证记录 §续-385；本文其余部分引用它的地方都是在引用当时那份读数，不是在描述现行代码）。

| 路径 | 整开机累计 | 计算窗内增量 |
|---|---|---|
| 内核态那条陷入路径（被打断的是内核自己的指令） | **8** | **+0** |
| 用户态那条路径 · 异步时钟中断 | **26 189** | **+68** |
| 用户态那条路径 · 环境调用 | **73 893 934**（约 7389 万） | **+733** |
| 用户态那条路径 · 页故障 | **3 094** | **+0** |
| 返回用户态那条路径 | **6 131** | **+0** |
| 其中「进来时中断还开着」的那段窗口（被武装） | **1** | **+0** |
| 用户态那条路径被内核态来源走过的次数（哨兵） | **0** | **+0** |

原始读数以十六进制记在取证记录 §续-375、§续-376；上表已由本文用脚本重新换算成十进制并对齐差值（复核命令在本节末）。

**量级换算（工具生成，假设已标出）**：时钟周期由「整开机约 26 200 次用户态时钟陷入 ÷ 开机约 330 秒」反推得 **12.6 毫秒**；窗口长度取「约 50 条指令」按 1 GHz 量级估 **0.2 微秒**；两者相除得**单次武装窗口被踩中的概率 ≈ 1.6×10⁻⁵**，而每个开机周期只有 1 次这样的武装窗口 ⇒ 预期命中次数 ≈ 1.6×10⁻⁵ / 开机。

**这三条读数各自封掉或打开什么**：

1. 「返回用户态的路上有个中断窗口」是**真实缺陷**，但在这个负载下它每开机只被武装一次、踩中概率约 1.6×10⁻⁵。**一个每 boot 命中 30-40% 的写者不可能只以这个频率碰运气**，所以它从候选首位退到「正确但与本案无关的加固」；它继续存在的理由是正确性与三架构对齐（64 位 ARM 的同族入口第一句就是屏蔽中断）。
2. 计算窗内**唯一在高频动的是用户态那条路径上的异步时钟中断**（68 次）。本案最强的统计指纹——随暴露时长上升、几字节量级的精准改写、应用不主动调用服务时也能发生——与它同向：**每次进入都要把 34 个寄存器搬进搬出**，只要其中一条搬错，就正好是「指令完全合法、地址不对」的形状（机制图见 6.1）。
3. 「内核态那条陷入路径」整开机只有 8 次、窗内 0 次，与「窗口内内核侧看不到活动」这个旧观测一致，所以它也撑不起高频命中。

**口径限制（两条，漏一条就会把这个表读过头）**：

- 异步中断 / 环境调用 / 页故障三项**不是用户态那条路径进入次数的全量普查**。浮点惰性陷阱（陷入原因码 2）与其他同步异常不计入任何一项。漏计只会**增加**用户态路径的暴露面，因此第 2 条结论只会变强；但**不要把这三项相加当作总进入次数**。
- 计数器是**跨 hart 的全局聚合值**；「由中断次数反推时钟周期」隐含单 hart 计时假设——本案的点火命令是 `-smp 1`（见 4.3 第一条），所以成立；接上多核之后这个反推失效，计数本身仍可用。
- 计数在魔术串被认出时就已经累计，所以「窗内 0 次」只对**计算窗**成立，不能外推到整个测试程序的执行期（执行程序链与首次命页都在窗口之前）。

**这组读数回答不了什么（不粉饰）**：它只回答「哪条路径被走到、走多少次」，**不回答「被保存的寄存器值对不对」**——后者只能靠陷帧逐字段校验（见第 7 章实验丁的子件二，仍开放）。另外，修前没有计数器，因此**没有**「同一个开机里既有寄存器被踩又有腐蚀」的现场抓获；上面是量级论证加前后统计对照。要现场抓获，便宜的做法是加一个特性门把三处修复同时关回旧形状**而保留计数器**，让旧形状与计数同 boot 对照（取证记录 §续-376 列为收口后的可选坐实项，不是阻塞项）。

**与采样计数的对应关系（第 8 章要用到这两个不同的口径）**。取证台账把每次点火的内核摘要与启动镜像摘要并列登记（`tmp/nk4a/tmemcpy_bisect/sample_ledger.txt`），所以「哪些全绿开机用的是同一个二进制」是可以直接查的。按内核摘要分组，三处修复后的全绿开机构成是这样的（工具生成）：

| 内核摘要 | 启动镜像摘要 | 全绿开机次数 | 对应取证记录 |
|---|---|---|---|
| `2ec60d7b` | `2b8d8c52` | **12** | §续-373（三处修复，无计数器） |

两个必须分开的结论：

1. **同一个内核二进制、同一个启动镜像的连续全绿最多 12 次**。这是能当作单一独立同分布样本代入统计判据的上限。
2. 计数器上线之后，内核二进制换了三次、启动镜像换了一次，所以这部分全绿是**跨二进制的累计**。取证记录按口径把它记作「19 次」（§续-375 的 17 加 §续-376 的 2）；而台账里这一组实际共有 **21 次全绿**——差的那 2 次是 §续-374 那个内核（`e63b5244`）的两次点火，它们未进入累计。**[这条出入属于台账记账口径，不是读数矛盾；本文只登记，不替取证记录改数]** 无论是 19 还是 21，它们都跨了多个二进制，**不能当作单一同分布样本**：跨二进制的累计可以当方向上的支持，不可以单独拿去满足统计判据。

## 第 4 章 已排除的假设，以及每条排除手段的分辨力边界

这一章是本文对外部审阅者最有价值的部分。原因很直白：**一个排除结论的价值，等于它所用手段的分辨力**。下面每条都写明「手段覆盖了什么」和「手段看不见什么」。

| 编号 | 假设 | 排除手段 | 手段的盲区（重要） |
|---|---|---|---|
| 排除-1 | 交叉编译代码生成、随机流、memcpy、摘要实现有错 | 3.1 的裸机对账 | 只证明「不经我们内核与加载器时正确」。若缺陷需要我们的内核参与才出现，本手段无覆盖 |
| 排除-2 | 物理帧分配器把同一页发给两个使用者 | 在分配时刻判定的位图检测器，真机全零命中 | 只能得出「**分配那一刻，没检测到已登记的重复所有权**」。它既不能排除「事后被某条错误路径改接给另一个使用者」，也不能排除「某些页从来没进过这份账本」。要真正排除需要运行期的物理页所有权不变量，见 4.3 |

### 4.1 排除-6 需要重做：判据本身是探针自己造的假象

时间顺序是这样的：某段时间里，所有实验都以「客机在串口输出第 245 699 字节处停滞」为观测点。回退走页表改动、回退内核侧改动，**两条臂都停在同一个字节数**，于是得出「内核侧与本缺陷无关」（排除-6）。

随后发现：**这个停滞点是打印插桩自己造出来的**。把测试探针换成打印量较小的那个形态（从每个检查点都打一行，退回只打十二行），同一份内核镜像**一路跑完、不再停滞**（取证记录 §续-361）。也就是说停滞不是内核行为决定的，而是「探针打了多少字」决定的——打印本身改变执行时序，时序决定何时撞上某个资源边界。

**如果这个定性成立，那么排除-6 的两条臂都带着同一个混杂变量，对这个假设没有分辨力**：两条臂用的是同一个高打印量探针，本来就都会停滞，与内核代码对不对无关。

本文作者另外注意到一处内部不一致，可作为佐证（也说明这条线值得重跑）：取证记录 §续-352 记「关掉一处页表项检查后，客机越过了 245 699 停滞点」，说明**同一探针下改内核行为确实能移动停滞点**；而 §续-358 又记「把那处检查重新打开后仍停在 245 699」，两读数互斥。并且回退到本次审计之前的源码树时，那份代码里本来就**没有**那处检查，按 §续-352 的读法它不该停滞。

**这条不是「内核侧有罪」的证据，而是「内核侧清白尚未证明」的说明。** 第 7 章的实验甲就是为此设计的：判据从「是否停滞」换成「是否逐次开机恒定」，后者不受打印量影响。

**本项的现状（与主线程已收敛）**：后续取证已把走表线**重新打开并列为头号候选**，但用的是另一个理由：我们的走表**变更**已被排除（因为原始走表同样出此症），而**走表本身从未被排除**（取证记录 §续-366）。这与 4.1 以方法学理由提出的质疑方向一致。

### 4.1.1 对那四份停滞日志的逐字节复核（本文作者独立取证）

停滞点被记作「第 245 699 字节」，直觉上这是一个极强的确定性信号。本文作者把四份同尺度的停滞存档逐字节比了一遍，**结论是它没有看起来那么硬**：

| 存档（`tmp/nk4a/tmemcpy_bisect/`） | 字节数 | 与其他份的差异 |
|---|---|---|
| `machine_fix1.log` | 245 699 | 基准 |
| `machine_fix2.log` | 245 699 | 与基准不同 **966 字节**，首个不同在第 **163 363** 字节 |
| `machine_hard1.log` | 245 699 | 与基准不同 **58 字节**，首个不同在第 143 635 字节 |

### 4.2 已经被买到的教训：观测手段自己就会造出读数

下面几条不是修辞，是本案真实踩过的坑，任何外部审阅者给出的实验建议都应当先过这几关。

**教训一：打印不能消费被测数据流。** 最早的探针版本为了「验流」，在入口处打印了前五个随机数值——**而没有重新播种**。结果摘要链被推进了五个值，跑出**一个可复现的错误值**，而且在这个架构和宿主机上错得逐位一致。一个假的必然错，差点被当成真结论。修正 = 打印之后立即重新播种。（取证记录 §续-342）

**教训二：去重键可能跨进程共享。** 一个用于「同一地址被填多次」判定的探针，其去重键是（位置，页内虚拟地址，页内物理地址）三元组，**全局共享**。于是「同一虚拟地址先后对应不同物理帧」这一现象——对进程更替（每次执行程序换栈帧）而言完全正常——会被读成「重复填充」的实锤。该判据必须按进程分开。（取证记录 §续-342）

**教训三：一个「关掉 X」的臂，必须先证明 X 真的被关掉了。** 这条不是修辞：本案确实有一次以「关掉中断后现象不变」为凭的推论，后来发现那个臂根本没关上任何东西（见 4.4 与排除-8）。它的代价不只是浪费一轮：一个假的「已降权」会把后继实验的候选排序带偏一整串。**判据应该是一行可以核的读数（「窗内该类陷入次数 = 0」），而不是一个旗标被置上了。**

**教训四：同一个现象在每一轮真机门里都出现在同一位置、而另一个架构上同一份二进制全绿——那是确定性指纹，先按确定性缺陷排查。** 本案把一条确定性缺陷（线程指针没初始化）在「非确定性内存污染」的框架里挂了好几轮：那个测试程序的四条用例在已观测的每一轮全量门里全灭（取证记录 §续-378、§续-382、§续-383 三轮同脸），而同一份二进制在 64 位 ARM 上全部通过。**这两件事同时成立时，该被怀疑的是「概率性」这个框架本身。** 可操作的判据是一句话：**先问「它有没有哪怕一次成绿过」。** 从未成绿 ⇒ 按确定性查（读码 + 反汇编 + 只装那几个用例的最小诊断镜像，本案实测迭代周期约三分钟一轮）；偶尔成绿 ⇒ 才轮到概率性框架与统计判据。代价也可以量出来：换到确定性框架之后，那条缺陷是**一轮**拿下的（取证记录 §续-384）。

### 4.3 本轮新核出的三条结构性事实（直接改变某些假设的优先级）

这三条是本文作者在核对环推与配置时实测得到的，它们要么直接排除一类机制，要么把一类机制重新打开。

**其一：出问题的点火是单核配置。** 跑套件的门脚本与启动门都写 `-machine virt -smp 1 -m 512M`（`os/qemu-tests/test-atf-riscv64.sh` 的点火行，工具派生行号 L202；`os/qemu-tests/test-riscv64-boot-full.sh` 同形，L144）。因此：

> **跨核转译缓冲卸载（一个核改了页表、另一个核手里仍是旧映射）这一整类机制，在所有污染观测里结构上不可达。**

（多核只在一个专门的中断转发测试里出现，那个测试不跑套件。）但请注意：**单核只否掉「跨核」那一半，同核陈旧表项仍然完全可能**，所以 4 章的排除-4 并未因此变强。

**其二：地址空间标识符根本没启用。** 写入 `satp` 寄存器的值是「模式位左移 60 位，再或上根表物理地址右移 12 位」，**没给地址空间标识符留位**（`os/arch/src/riscv64/tlb.rs:86`，工具生成）。两个直接推论：

- 「标识符滥用导致旧进程表项被新进程复用」这类经典缺陷**结构上不存在**（标识符恒为 0）；
- 第 7 章的守护设计可以更简单：只需保证守护对象与被测对象**在同一个虚拟页内**（不需考虑标识符匹配）。
- ⚠️ **代价**：因为没有标识符，每次切地址空间**必须**做一次全量失效，否则整个系统的表项全部混淆。仓内曾存在两处写法不一致：运行期切根入口 `os/arch/src/riscv64/tlb.rs:set_active_root` 确实配套了全量失效（先写 `satp` 紧接不带操作数的 `sfence.vma zero, zero`，工具派生行号 L88-L89），而 `os/arch/src/riscv64/paging.rs` 里另一个**只写 `satp`、不跟任何失效指令**的切换入口。**该项已彻底收掉**：它先在 RISC-V 生产路径上被核为零调用方（仅架构内模拟测试使用，取证记录 §续-367），随后连同它在 `trait` 里的契约面被整面移除（`trait` 成员与三个架构的实现一起拿掉，取证记录 §续-390），所以现在连「待清理的死代码」也不是了。生产切换全部经 `set_active_root_tracked` 走上面那个带失效的入口。**但仍要说清边界：洗清一个已知入口不等于「所有改写页表的入口都配对了失效」已经穷举完**，那句仍挂在排除-4 上。

**其三：这台虚拟机里没会自主写内存的设备。** 点火命令里只有一个写内存入口：`-device loader,addr=…,force-raw=on`（12 个模块 + 启动表 + 根盘镜像），加上 `-serial file:…` 与 `-display none`。**没有 virtio、没磁盘控制器、没有网卡。** 因此本文第 6 章里「外设直接存存取取（DMA）改写内存」这一整类**被配置结构性排除**（不是被环推排除）——`loader` 设备只在客机开始执行**之前**写内存，不可能在测试窗口内动手。

**另外一条作者自查但未成立的可疑点（负结果）**：返回路径上有一处把保存的程序计数器直接加 4 的代码（`os/kernel/src/trap_dispatch.rs:1829`，工具生成）。若被跳过的指令是 2 字节压缩编码，这就会让用户从错位置继续执行，形状上非常契合本案。但本文核对后确认它只在**用户态环境调用**（`ecall`）分支上执行，而 **`ecall` 在 RISC-V 里没有压缩编码形式**（只有压缩的 `c.ebreak`，不是 `ecall`），所以「加 4 字节」在此处成立。**该可疑点已自行消。**写出来是为了给外部审阅者划清「已经有人看过、结论是清白」的区域。

### 4.4 一次「关掉中断」的实验为何两个臂各自独立失效（排除-8 的展开）

这一小节的价值在于：**一个设计正确、但两处都默默失效的实验，比一个设计错的实验更难发现**，因为它的「现象不变」看起来像一个读数。本案那次削减实验（取证记录 §续-368 提出，§续-374 与 §续-375 分别查出两处死因）想问的问题是「把计算窗内的时钟投递关掉，腐蚀会不会消失」。它的两处死因彼此独立，任意一处单独存在就足以让整个臂无效：

**死因一（内核侧）**：那个实验臂所做的，只是在返回用户态之前**跳过「把返回后的使能位置 1」那一条指令**。但硬件本来就保证那一位是 1：陷入发生时，处理器把陷入前的使能状态存入那个「返回后恢复用」的位，而返回指令又会把它置 1。**跳过一条置 1 的指令，面对的是一个已经是 1 的位**——净效果什么也没改变。（现在的代码把顺序改成「先无条件清掉，再按旗标决定是否置回」，那个旗标才名副其实。）

**死因二（探针侧）**：读数行根本没有出现过。测试探针自己手抄了一份消息头结构体，**少了一个发起者字段**；真布局是发起者在 0 号位置、类型在 4 号位置（`tools/atf-c-compat/kmsg.h:struct kmsg`，工具派生行号 L13-L15），于是内核按 4 号位置读到的是 0，那条内核调用从来没被认成预期的魔术串——**开关命令从未抵达内核**。（该头文件自己的注释就写着：两处手抄的结构体今天逐字节一致，但 C 链接层不做跨编译单元的类型检查，一侧改槽序就静默错位。）

**由此得到的可复用规律（两条）**：

1. **一个「什么也没发生」的读数比错读数更值钱**——它同时否证了两条推论链，而它只能由「本该出现却没出现」发现。如果当时只盯着「腐蚀在不在」而不盯「读数行在不在」，这两处死因都不会暴露。
2. **关闭类实验必须自带一个阳性对照**：「关掉 X」的臂里应该同时报一个「X 确实被关住」的量（本案中就是窗内的时钟陷入次数应当为 0）。没有这个对照，「现象不变」永远不能等同于「X 无关」。现在的进入计数遥测（3.8）正好提供了这个对照所需的那个读数。

| gate1 | `0x1bfffe61e730` | 44 | 0 | `0x3ffe61e730` | 形状 B |
| bit38 族 | `0x4000000000` | 38 | 0 | `0x0` | 形状 B |

取证记录 §续-365 把前两行归为同一形状，理由是「高位连续置起，像 64 位 long 模式下的栈指针」。这里给两点本文作者独立复核后的补充，请外部审阅者判这个归类是否成立。

**其一：era_323 不能用作本缺陷的证据。** 它比栈顶常数改正所针对的那个错误值低正好 **112 字节**（`0x70`，工具生成）。也就是说它就是那个错误栈顶常数往下偏移后的形态（为何恰好是 112 字节，本文未取证，**[待验证]**），而且它是改正**之前**采集到的观测。拿改正之前的样本去支撑「改正之后仍有路径在产生同形状的值」这个假设，逻辑上不成立。

**其二：关于那个余数 6，本文上一版的推论跨了界。** 我当时写「余数不为 0 ⇒ 它不是一个栈指针」，这是错的：**页故障报告的是出错的那次访问的地址，不是参与地址计算的那个寄存器的值**。举例：只要指令是「以 sp 加 6 为地址存一个八字节字」，即使 `sp` 本身按 16 字节对齐，报告地址也会是余 6。

所以正确的表述只能弱到这一步：**run8 与「未经偏移直接使用的、按调用约定对齐的栈指针」不相符**，而不是「run8 不可能来自栈」。两者差别很大：前者只说明「不是整个旧值被原样当作指针写入」，后者才会排除掉「旧值参与了一次带偏移的访问」。

仍然站得住的部分：run8 最高置位 50、比 era_323 高出四位，且**无法由 era_323 经过一次移位或一次掩码得到**（右移四位后形态仍不符，工具生成）。所以「两个样本同源」这个假设至少**还缺少一个能写出算术过程的生成器**。

**其三：形状 B 我复核通过。** gate1 的 38 位以上置位集合是 {38,39,40,41,43,44}，与取证记录记的逐位一致；它掩掉 38 位以上之后落在合法用户半区内，所以「合法低 38 位 + 高位散布置起」这个描述成立。

### 5.1 形状 B 的三种候选生成器，按可信度排序

「高位散布置起」这个形状至少有三种成因，**上一版本文把「按位或」排得太前**，这里改排序并给出可计算的判据。记 `C` = 观测到的坏值，`A` = 期望值或当前合法值，`B` = 另一个候选源值。

| 序 | 生成器 | 为什么排这里 | 能区分它的指纹 |
|---|---|---|---|
| 1 | **部分覆盖 / 复合字**：一个 64 位字里，低位来自当前值、高位某几个字节来自旧值（一个陷帧或栈上对象被盖了半截） | 它比严格的「按位或」更贴合「几字节量级精准写」这个已实测特征 | 逐字节看：变化集中在**连续的几个高位字节**，且那几字节能在旧主人内容里逐字找到 |
| 2 | **跨页边界的写**：一条宽度 8 的存落在页内偏移 4089–4095 附近 | 形状 B 的低 38 位合法、高位像被拼接，与跨页拆分的存非常兼容 | 强指纹：一处变化靠近页尾 **且** 下一页页首同时变化 **且** 变化长度等于某个合法存宽度 **且** 内容能与某个源缓冲前后对接。特别地，「偏移 4092 + 宽度 8」几乎一眼可认 |
| 3 | **真的按位或** | 不是不可能，但要两个候选源同时对得上才能立项 | 需同时满足 `C == A \| B`、`A & ~C == 0`、`B & ~C == 0`，**且在多个样本上反复成立**。只出现一次不够 |

**另有一种最硬的陈旧指纹，与上面三种共用**：若能证明「当前对象所在物理帧 = 帧 B，帧 B 内容未变，而旧主人帧 A 恰好含有那段坏内容」，那几乎就是直接证据（它同时区分了 1、2 与「算错地址的写」）。本案已有的全量物理内存快照工具（附录 A 里的两份 512 兆字节快照）正是为了做这种比对而存在的。

**本文的判断【有支持、未坐实】**：所谓「形状 A」目前只剩 run8 **一个改正之后的样本**，而它既不能由那个旧栈顶常数经一次移位或掩码得到，也不具备「原样写入的指针」该有的低 4 位形态。把 run8 与 era_323 捆成一个族，风险是为两种不同来源追一个共同写者。建议把 era_323 从本缺陷的证据集中移出（标注「已由栈顶常数改正解释」），把 run8 单列为第三种形状。

**复核**：
```bash
python3 -c "
for n,v in (('era_323',0x7fffffffef90),('run8',0x7ffff48b124e6),('gate1',0x1bfffe61e730),('bit38',0x4000000000)):
    print(n, hex(v), 'msb',v.bit_length()-1, 'mod16',v%16, 'low38',hex(v&(2**38-1)), 'legal38',(v&(2**38-1))<2**38)
print('era_323 与旧栈顶常数差', 0x7ffffffff000-0x7fffffffef90)"
```

## 第 6 章 能在「无内核参与」窗口里改几字节的机制清单

第 3 章有一条很强的时序证据：在命中那一跑里，测试进程算完整段数据的期间，**内核侧看不到任何活动**——没有系统调用、没有探针行（取证记录 §续-343）。能在这段时间里改动客机内存的机制，理论上只有以下几类。把它列全，是为了让外部审阅者直接指认「哪一类我看来最像、以及用什么一次判定」。

### 6.1 第一名是用户态那条陷入路径：它是唯一被计数证实「计算窗内高频」的候选

把四个已实测特征摆在一起看：

> 只在 RISC-V 上出现 + 随暴露时长上升 + 几字节量级的精准改写 + 应用不主动调用服务时也能发生

这四条同时成立时，**一次陷或中断把用户上下文弄脏**比「某次走页表偶然返回错物理地址」更贴脸。理由是一个具体到令人不安的机制，**它不需要任何地址算术出错**：

```text
用户程序：
    …
    sd  t0, 0(a0)        ← 存一条指令，本身完全正确
    …
陷进入 → 保存寄存器 → 计时器处理程序运行 → 返回前恢复寄存器 → sret
                                  ↑
                    若这里少恢复了一个寄存器（或恢复错了内容）
用户程序：
    sd  t0, 0(a0)        ← 指令仍完全正确，但 a0 已经不是被陷前的那个值
```

**这种机制下，所有页表代码、所有走表算法、所有地址掩码都可以是彻底清白的**，而现场表现就是「程序自己执行了一次合法存储，只是落在了另一个地址」。而且它**天然带随机性**：不是每次中断都出事，只有当某个具体寄存器当时恰好承担着关键地址时才会。这正好解释了 3.7 「位置随机」与 3.3 「随暴露时长（即中断次数）上升」。

**为什么这个候选项在本仓不是空想**：本内核**确实会在返回前修改被保存的用户上下文**——至少有两处活动写入点：浮点惰性轮转的处理程序会改写保存下来的状态寄存器里的浮点状态字段（`os/kernel/src/trap_dispatch.rs:riscv64_fpu_trap_body` 内对 `frame.sstatus` 的位域赋值，工具派生行号 L2644），而上下文切换路径上也会对即将返回的上下文里的同一字段作修正（`os/kernel/src/lib.rs` 内关于「为非拥有者修正 `ctx.sstatus.FS`」的段落，工具派生行号 L3643 附近）。也就是说，「内核写用户返回上下文」不只是一个假设，它是已经存在于代码里的一类动作。

**并且这一族在本仓不是假想敌：已经静态坐实并修好了三处同一形状的缺陷**（都是「寄存器当暂存的次序错」或「该屏蔽中断的那段没屏蔽」）：

| 出问题的路径 | 缺陷形状（一句话） | 后果形状 |
|---|---|---|
| 内核态那条陷入路径（`os/arch/src/riscv64/trap_stub.rs:riscv64_kernel_trap_vector`，工具派生行号 L252） | 拿 t0 当暂存去算被打断的栈指针，早于把 t0 存进自己的槽 ⇒ 出口把一个**栈地址**还给被打断的内核指令 | 无异常、无日志、页表也没错 |
| 用户态那条陷入路径（同文件 `riscv64_user_trap_vector`，L363） | 返回前把**用户的 t0** 换成了它自己的栈指针 | 异步中断打进来时等于偷走一个寄存器值（同步环境调用则合法，因为调用约定本来不要求它存活） |
| 返回用户态那条路径（`os/arch/src/riscv64/trap_return.rs:restore_to_user`，工具派生行号 L117） | 换向用户态向量之后还有约 50 条指令跑在内核态，而中断此刻是开的 | 一拍时钟落进这段窗口，就把 34 槽陷帧盖到调度器的活栈上 |

三条都由宿主端的文本级钉住测试守着（形状判定 `os/arch/tests/riscv64_trap_leg_shape.rs`，返回路的次序与位定义 `os/arch/tests/riscv64_return_leg_pin.rs`），并且各配了**正控制**——故意把缺陷写回去，测试必须当场翻脸。这不是装饰：形状判定最初只核了「保存侧」，第二行那个发生在「恢复侧」的同形缺陷正是靠补上的规则与正控制才被扩出来的。**如果一组静态判据只检查一半的流向，它给出的「清白」也只覆盖一半。**

**但 3.8 的计数把这三条分成了两档**，这是本节最需要外部审阅者看的地方：用户态那条路径在计算窗内被走 68 次（整开机 26 189 次），是三处里唯一「窗内高频」的；内核态那条整开机只 8 次、窗内 0 次；返回路径的中断窗口每开机只武装 1 次、踩中概率约 1.6×10⁻⁵。**所以「陷帧这一族」作为整体仍然是首要嫌疑，但嫌疑的具体落点已经收窄到「用户态那条路径上的异步时钟中断」这一条**——它同时具备机制贴合、窗内高频、以及本仓实证过的同形缺陷三项。

**并且这一带本仓确实交过一次学费**：浮点门控曾把「不会陷入」的字段值当成「会陷入」来设（字段值与判据不匹配），导致那段浮点轮转处理实际上从不执行，而且它通过了两轮代码审阅仍未被拦下。**[待验证：上述两处写入点当前的位域值与语义是否完全正确，本文未重新逐项对规范核]**

### 6.2 完整候选项清单（按计算窗内的实测暴露面排序）

排序的判据现在只有一条：**该机制在计算窗内的暴露面**（3.8 实测），机制本身的贴合度作为第二判据。「窗内暴露面」列写「未量」的那些行，意思是**还没有可用读数**，不表示它清白。

| 序 | 机制类 | 窗内暴露面 | 当前评价 |
|---|---|---|---|
| 1 | **用户态那条陷入路径把用户上下文保存或恢复错**（包括被保存的寄存器被处理程序踩、少恢复一个、陷帧本身被覆） | **68 次/窗**，整开机 26 189 次 | **第一嫌疑**，且是唯一同时具备「机制贴合 + 窗内高频 + 本仓已实证同形缺陷」三项的候选（见 6.1 表第二行）。三处同形缺陷修好之后，同一个内核二进制连续全绿 12 次、门跑到 24 个用例零失败——方向上支持，不构成证明 |

**一条被量级移出本清单的**：「返回用户态之路上、中断还开着的那段窗口」。它是一处真实缺陷（6.1 表第三行）且已修好，但每开机只武装 1 次、踩中概率约 1.6×10⁻⁵，**与每开机 30-40% 的命中率差三个数量级以上**。它留在代码里的理由是正确性与多架构对齐（64 位 ARM 的同族入口第一句就是屏蔽中断），不再占用写者嫌疑位。

**一条读法警示（在这一节很容易把 3.8 读错）**：「内核态那条陷入路径在窗内 +0」**不等于**「计算窗内内核没有活动」。前者只统计「内核正在执行时被打断」这一种进入方式；而窗内那 733 次环境调用是**由用户态发起、在内核态执行**的工作——内核在替服务搬数据、改页表、做拷贝，全都计入环境调用那一行。因此第 2、3、4 类机制**都没有**被这张计数表洗清，它们只是暂时无法用这张表排序。要真给它们排序，需要的是**在拷贝入口本身加计数**，而不是在陷入入口加计数。**[待验证：本文未核对内核代拷贝在窗内的调用次数有没有现成读数]**

**顺带一个必须考虑的可能**：本缺陷可能不止一个写者。本案的证据只支持「单一机制多面孔」（取证记录 §续-342 判决 2），但样本量很小——命中次数的总量在个位数到十几之间。上面那张暴露面表还提醒另一种更可能的形状：**同一个机制在不同地点由不同路径执行**——比如 §1.1 那条「内核自己的打印缓冲被盖字节」发生在内核态，而用户页被改发生在用户任务运行期间；两者可能是同一个缺陷的两张脸，也可能根本不是同一个写者。

## 第 7 章 能一次判定方向的实验组，与它们该拼成的判别矩阵

都优先选**不依赖真机长时间运行**的设计，因为 3.3 那张表说明长时间暴露既慢又不可靠。

### 实验甲：把内核侧清白这件事重新测一遍（针对 4.1）

固定**低打印量探针**（消除停滞点混杂），两臂：当前内核、走页表改动之前的内核。判据换成 **第一次缓冲对上的累积摘要是否逐次开机恒定**（3.7 与取证记录 §续-361 已经给出这个摘要三跑三值，它本身就是个不受打印量影响的传感器）。

- 两臂的该摘要都逐次变动 ⇒ 内核侧确实清白，排除-6 才算真正成立，此后所有分页层再审计都可以停；
- 某一臂恒定而另一臂变动 ⇒ 内核侧出局作废，立刻回到第 6 章第 3 类。

成本：两次开机，且不需要长窗。

### 实验丁：陷帧完整性校验（仍开放）+ 中断暴露面测量（已由进入计数完成）

这一组包含两个子件，它们的现状不同：一个已经拿到读数并换了一个更可靠的做法，另一个至今未做。

**子件一：测清「计算窗内到底有多少中断打了进来」——已完成，但用的不是「关掉它们」**。原设计是直接在测试窗口内禁用当前核的监管态中断投递（不是「减少控制台输出」，而是让计时器中断不再进来）。这一臂的实际执行结果值得当成方法学样本留下：它有两处彼此独立的死因，一次也没真的关上中断（展开见 4.4，降权结论已在排除-8 作废）。

**为什么换成计数更划算**：要回答「中断是不是写者」，先得知道窗内到底进来了多少次；而「关掉它看现象变不变」为了这个读数必须牺牲整个窗口的工作状态，还要额外证明你真的关上了。计数只读不删：**窗内该类陷入次数 = 0 就是「这条路未被走到」的直接证据，窗内次数高而腐蚀仍在，就是降权的直接证据**，两种读数都不需要改动被观测对象。4.2 教训三说的就是这个：关闭类实验必须自带一个阳性对照，而计数天然带着它。

读数已在 3.8：整开机 26 189 次用户态时钟陷入，其中落在计算窗内的是 **68 次**。

**子件二：给陷帧加守护值——仍开放，且因为计数拿到了读数而价值上升**。在保存完用户寄存器后立即对陷帧算一次校验值，在 `sret` 前再算一次并逐字段比对，重点盯看栈指针、返回地址、前七个参数寄存器、临时寄存器、保存寄存器、以及保存的程序计数器与状态字。不是为了永久保留这个校验，而是为了**抓一只现行犯**：最希望看到的证据形状是「第 18 342 次中断：入口 a0 = 某值，出口 a0 = 另一个值，栈指针未变」。

**为什么计数回答不了子件二要问的问题**：计数只回答「哪条路径被走到、走多少次」，**不回答「被保存的寄存器值对不对」**。前者只能把嫌疑收窄到「用户态那条陷入路径上的异步时钟中断」这一族（6.2 第 1 类），后者才是坐实。所以这一步不可省。

**设计约束（新读数给出的一个硬提醒）**：窗内只有 68 次时钟陷入、另有 733 次环境调用。这意味着「抓现行犯」的抽样面比看上去小得多：如果校验只在若干抽检上做，很可能一次也没碰到被踩的那一次。因此校验必须**逐次进入都做、只在字段不一致时打印**（同 4.2 教训一：校验不能消费被测数据流），并且打印量要封顶。**[待验证：本文未核实现有探针是否具备「逐次进入都校验」的低开销能力；若开销不可忽略，需先量开销再定抽检还是全检]**

四种可能结果与对应结论（按计数与校验两个轴重写）：

| 读数形状 | 结论 |
|---|---|
| 陷帧校验报出「入口某寄存器 = A，出口 = B」，而 A 正是那次访存用的地址 | 直接坐实 6.2 第 1 类，本案基本结束 |
| 校验一直完整、窗内中断计数不低（与 3.8 同量级）、腐蚀照旧 | 第 1 类大幅降权。注意措辞：这是「被校的那几个字段在那几次进入里未变」，**不是排除**——转「跨空间拷贝错物理地址 + 同核陈旧表项」 |
| 校验一直完整、且腐蚀不再再现 | 三处修复生效的正面支持；仍要过第 8 章的双判据才能说修好 |
| 加上校验之后腐蚀率本身变了 | 该装置把被测时序扰动掉了（4.2 教训一那一类），需改成不消费数据流的形状重做 |

### 实验乙：守护对象（注意：不要做成「守护页」）

上一版本文建议放「几页守护数据」，**那是错的布局**。关键约束是：架构上**不存在**「保证两个不同虚拟页共用同一条转译表项」的条件；转译缓冲的匹配语义是按虚拟页（以及地址空间标识符或全局位）走的，而不是「地址相邻就共享」。因此**跨页的守护对被「同核陈旧表项」这类机制完全不敏感**——它只能测出错址写，测不出陈旧映射。

**本仓的实际情况让这件事更简单**：4.3 第二条已确认地址空间标识符恒为 0，所以「同页」就是全部条件，不需再管标识符匹配。

正确布局：守护对象与可疑对象**同住一个 4096 字节页**。本案已有现成的天然条件——摘要上下文与随机数表本来就在同一页内（3.6）而且相隔 264 字节：

```text
同一个物理页
+0x000  随机数表（已知内容，不断自校验）
+0x108  摘要上下文（被测对象）
其他间隙  填充已知魔术值的守护变量，多个尺寸与对齐
```

**把它做成一个主动判别器（而不只是被动报警）**，可执行步骤：

1. 先访问热点与守护对象，建立转译表项；
2. 把该虚拟页改映射到**另一个内容不同、守护魔术值也不同**的物理页；
3. **不发失效指令**，再读守护对象：读到旧页的魔术值 ⇒ 抓到陈旧转译；
4. 补一条只针对该地址与当前标识符的失效指令，再读：应该落到新页魔术值。

如果第 3 步能稳定复现陈旧读，就拿到了「不失效会怎样」的已知良好基线——接下来只要看真实腐蚀现场能否命中这个基线形状。校验一律放在被测计算之外，避免重踩 4.2 的教训一。

### 实验丙：把它做成 2×2，而不是单向削减

上一版本文只写了「削减控制台流量看命中率」。这个设计有一个先天缺陷：**控制台流量不是一个自变量**，削减它会同时改变调度、改变中断时刻、从而改变缺陷命中概率——混杂变量与被测变量搅在一起。

因此它的**逻辑上限**必须先说清：「关掉控制台流量后命中率不下降」最多否定「控制台代写流量是必要触发因素」，**不能否定内核或中断仍是写者**。

升级后的 2×2 布局（行：控制台流量高/低；列：中断投递正常/受控）：

| | 中断正常 | 中断受控 |
|---|---|---|
| **高控制台** | A | B |
| **低控制台** | C | D |

三种读数形状分别指向不同结论：

- `A ≈ C`、`B ≈ D`、`A ≠ B` ⇒ 主要变量是**中断暴露**，控制台流量无关；
- `A ≈ B`、`C ≈ D`、`A ≠ C` ⇒ 更像**控制台与内核代写流量**；
- 四格差不多 ⇒ 两者都不是主触发因素（这同样是有价值的结论，它一次性关掉两整类假设）。

### 实验戊：双走表对账探针（**已在运行；请审阅它的判据强度**）

针对 6.2 第 2 类的直判探针已在跑：同一个虚拟地址做**两次走表**，物理地址不一致就打印（根表地址，虚拟地址，两个物理地址）。探针本体是 `os/kernel/src/vm.rs:nk4a_walk_reconcile`（工具派生行号 L37），目前有两个调用点：

1. 内核代客查一段区域时的那次走表：`os/kernel/src/vm.rs:lookup_range_in_table`（函数定义在 L296，对账调用在 L310）。
2. **回执直写**（每次内核调用返回时把结果写回发起者自己的内存）：`os/kernel/src/syscall.rs:kernel_call_finish_ipc_door`，对账调用在工具派生行号 L3689。

第二个调用点在本轮新增，而它恰好接上了 6.2 那条「窗内 733 次环境调用」的暴露面：回执直写是**每次内核调用都要做一次**的用户内存写，与 3.8 测到的环境调用次数同量纲。也就是说这条线不再只在「拷贝帧」那种低频事件上对账，而是进入了高频路径。

本文**不把它当建议提**，而是请外部审阅者评它的**判据强度与遗漏**，具体四点：

1. **它能证什么、不能证什么**：两次走表一致 ⇒ 只能排除「同一个入口重复调用会得到不同结果」，**不能**排除「两次都错到同一个错物理地址」（确定性错译）。也就是说：**探针不报 ≠ 走表清白**。这个逻辑上限必须在结论里写死，否则一次零命中会被误读为排除。**本探针已跑过首轮：全程零不一致，而腐蚀照旧（取证记录 §续-367，21 个用例通过 + 腐蚀仍在）**；到三处修复后的采样里累计四次点火也是零命中（按同一上限读）。另注意一个容易被名字误读的点：两个臂调的是**同一个函数**（`os/kernel/src/pte_walk.rs:walk_x86_64`，L183；该函数不按架构分支，名字里的架构只是历史遗留），所以它测的是「同一个函数重复调用稳不稳」，连「两套不同实现之间是否一致」都不测。
2. **去重容量的两侧风险**：上限 32 条。噪声跑满 32 条会静默丢弃后续事件（低估）；而去重本身会把「同一三元组反复发生」压成一行，丢掉频率信息。
3. **建议补的第三个臂**：除「同一个入口内两次走表」之外，再加**写后回读对账**（写完立刻经直接映射窗口读回，比对源内容）。前者测「算得稳不稳」，后者测「算对了但没落到位」，两者合起来才能把第 2 类整族包起来。
4. **计数口径的盲区（与 6.2 的读法警示同源）**：两个调用点盖的是「查表入口」与「回执直写」，而 6.2 第 2 类真正的现场——帧内容的收帧与落帧拷贝——并不在这两个点上。因此「累计零不一致」不能当作「拷贝路径已洗清」读；它洗清的是另外两处入口。要覆盖拷贝路径，需要把同一对账放在 `os/kernel/src/vm.rs:cross_space_copy`（工具派生行号 L482）的目标地址解析处。**[待验证：本文未核对该函数内部是否已有等效的二次走表]**

## 第 8 章 什么才算修好了

对一个概率性缺陷，「跑了一次、绿了」不构成证据。本案已经付过一次这个学费：同一镜像四次点火里两次以不同方式崩、另外两次的测试结果还各不相同（取证记录 §续-342）。项目自己的判据纪律是：**症状消失不等于根因清除；两次逐字节相同的输出不等于独立稳定验证。**

需要一个可算的验收形状。设观测到的命中率为 p（按 3.3 的修正：p 是暴露时长的函数，形状暂按 1 − e^(−λT) 建模，而不是常数也不是严格正比），要求连续 k 次独立点火全部正确才宣布修复，那么「缺陷仍在但 k 次全对」的概率是 (1-p)^k。要让这个逃逸概率低于 1%，**k 必须由式子当场算出来，不能从任何文档抄**——下面这张表就是用 `math.ceil(log(0.01)/log(1-p))` 现算的（工具生成）：

| 改动前命中率 p | 逃逸率 < 1% 所需的连续全绿次数 k | k−1 次的逃逸率 |
|---|---|---|
| 0.5 | **7** | 1.56% |
| 0.4 | **10** | 1.01% |
| 0.3 | **13** | 1.38% |
| 0.2 | **21** | 1.15% |

**为什么要把「不许抄表」写进判据而不只是写进提醒**：抄来的数字不会报错，它只会沉默地把结论说硬。本案里 p = 0.4 那一档曾被按 p = 0.5 的行写成 k ≥ 7（`0.6^7 = 2.80%`，离 1% 差三倍），而同一句里 p = 0.2 的「22」是照抄一份独立审查文档的保守值（按定义是 21）。两个错的方向还不一致：前者把门槛说松（原本不够的读数会被当成够了），后者把门槛说紧。所以规则得是「凡反推类数字一律现算并把式子写在旁边，引用别人的数字同样复算」。

**p 越小、需要的 k 越大，而这正是长窗测试不可行的原因**——p 小的那一端恰恰是短启动，那里本来就不容易命中。

**判据必须分两个口径写（这是 3.8 那张分组表带出来的新约束）**：

1. **单二进制口径**：同一个内核摘要、同一个启动镜像摘要下的连续全绿。本案目前这个口径的最大值是 **12**。按现算的表：对 p = 0.4 是 `0.6^12 = 0.22%`（**达线**），对 p = 0.3 是 `0.7^12 = 1.38%`（未达线），对 p = 0.2 是 `0.8^12 = 6.9%`（远未达线）。
2. **跨二进制累计口径**：取证记录把它记作 19 次全绿（台账里同组实际有 21 次，分组见 3.8）。**这个口径只能作为方向上的支持，不能单独满足统计判据**，因为它混合了多个内核二进制与两个不同的启动镜像。而且基线那一侧（约 7 次里出 3 次坏，≈ 43%）本身跨镜像、还把一次「停滞」与两次「腐蚀」混计成同一个分子（取证记录 §续-379 已把这条写进限制）。把 43% 当 p 代进去，等于先假设了不同分布的样本同分布。

**[待验证：单二进制口径若要真正达到 p = 0.2 那一档，需要 21 次同一个内核二进制的连续全绿；本文未核实按单轮约 5 分钟的采样成本，这是否排得进当前阶段]**

**还有一条判据是前两条都替代不了的**：可达性，也就是进入计数（3.8）。**全绿样本本身不证明被修的那条路径真的跑过**——本案已经拿到一个实例：如果只看那 12 次全绿，很容易以为返回路径的中断窗口被反复检验过，而它每开机只武装 1 次。所以验收报告里必须同时列出「窗内各类进入次数」那一行读数。

**一个必须防的统计陷阱**：不能把 3.3 表里「0 个终态」那一跑当作高命中率证据去推 k；它是被另一条响亮故障截断的，不属于同一事件族。

因此本文建议的验收形态是**三判据**：
1. 一个不受时长影响的**确定性判据**（实验甲那种「逐次开机恒定」的形状，用固定低打印量探针），并且要覆盖第 6 章各类机制各自最可能命中的地址区域；
2. 一个**统计判据**：以单二进制口径跑足 k 次（k 由上面的式子按期望逃逸概率现算，写成文档要求而不是口头保证）；跨二进制的累计只当方向支持；
3. 一个**可达性判据**：同一批采样里的进入计数读数（3.8）必须显示被修或被嫌疑的那条路径真的在窗内被走过。

三条缺任何一条都不能说「修好了」。**目前已到的位置**：单二进制 12 次全绿（达 p = 0.4 那一档的线）+ 跨二进制累计 19 或 21 次 + 可达性已拿到读数并且正好把一条嫌疑路径洗清了量级；而门已经跑到 **36 个用例全部出结论、零个失败**（取证记录 §续-384；把诊断探针族滚除之后复跑仍全过，§续-385）。

**但「门全绿」不等于「修好了」，这两件事必须分开写。** 全量门跑完只说明「这几轮开机没被那条静默改写击中」，而本案的写者从未被现场抓获（见 3.8 末段与第 9 章）。还有一个具体的判据空白：**可达性判据在全量门那一轮上没有配对读数**——腿计数靠测试探针自己发的两条魔术串界定计算窗，全量门用的是标准用例二进制、不带那对串，所以那轮的 `nk4c: legs` 命中为零。计数读数曾在专门采样轮里单独拿到过（取证记录 §续-375、§续-376），**但两者不是同一轮，写结案时得注明**。

单靠门脚本变绿不足以宣布修复。现状的门判据是「终集计数」：把通过、失败、损坏、跳过四种行都算作到达终态，凑齐清单上的期望条数才定案，任何失败或损坏一票否决（`os/qemu-tests/test-atf-riscv64.sh`，行号由工具派生：期望数取自清单文件 L90-L91，终集计数与一票否决在 L213-L230；窗口长度默认 3600 秒在 L43）。这套判据本身是对的——它把「跳过」这种合法终态也算入，不会因为用例自己选择跳过而误报停滞——但它对概率性缺陷没有免疫力。**另需补一条：停滞（串口连续多轮无增长后由门自己停掉模拟器）必须与「失败」分开计**，因为 §1.1 那条停摆不是被测代码的错，把它当成一条测试失败会掩盖真正的写者读数。

## 附录 B 术语（给零背景读者）

- **微内核与用户态服务**：内核只留最少的机制，程序加载、文件系统、内存管理都由独立进程承担。好处是一个服务写坏了不会直接拖垮内核；代价是它们之间必须靠消息往来协作。
- **页表与按需补页**：程序看到的地址是虚拟的，需要一页页表格换算成物理地址。表格还没建到某一页时，处理器报「页故障」，由负责内存的服务进程补上——这就是「按需补页」。
- **Sv39**：64 位 RISC-V 的一种三级页表格式，可寻址范围由此受限；超出该范围又不符合符号扩展规则的地址称为「非规范地址」，处理器对它的访问必然故障。
- **直接映射窗口**：内核把整段物理内存按固定偏移映进自己的地址空间，于是「物理地址 P」可以像普通指针一样被内核读写，不必为它建页表。
- **地址转译缓冲**：处理器缓存最近的「虚拟地址 → 物理地址」换算结果。改了页表却忘了让对应表项失效，后续访存就会继续用旧映射——本案第 6 章第 3 类。
- **陷入路径与返回路径**（本文说「用户态那条 / 内核态那条 / 返回用户态那条」时指的是这个）：处理器发现异常或收到中断时，会跳到软件事先放好的入口去执行——这一段入口叫陷入路径；它处理完之后把现场交还给被打断的那一侧，这一段叫返回路径。**「用户态那条」与「内核态那条」的区别是被打断的是谁**：前者从用户程序跳进来，后者从内核自己的指令跳进来（更危：它把陷帧建在内核栈上）。本案的三条路径与它们的缺陷形状列在 6.1 的表里。
- **陷帧**：陷入时为了事后能原样恢复，把三十多个寄存器逐个存起来的那块内存（本案是 34 个槽、共 272 字节）。它的落点由栈指针与「换栈用的备份指针」决定，所以这两个寄存器一错，整块陷帧就写到别人正在用的地方上。
- **计算窗**：测试程序自己算数据的那段时间，由探针在开头与结尾各发一条魔术串界定。**窗内增量 = 结尾累计 − 开头累计**，这就是 3.8 那张表右列的算法。注意它只界定「这段时间」，不代表这段时间里只有用户代码在跑（见 6.2 的读法警示）。
- **武装窗口**：本文特指「返回用户态的那段路上、中断还开着」的那段时间。窗口存在不等于被踩中——踩中需要一个时钟中断恰好落在那几十条指令里，这就是 3.8 里那个 1.6×10⁻⁵ 的出处。
- **正控制**：故意把缺陷写回去、验证测试会当场失败的测试。没有它，一个全绿的测试可能只证明了自己根本没在看。**钉住测试**：用源码文本或反汇编形状而非行为来断言的测试，目的是拦住「改回去了但行为看上去还对」那一类回归。
- **处理器模拟器与软件模拟（TCG）**：用软件逐条翻译并执行客机指令。功能上等价于真处理器，但性能与时序特性差异很大，而且**任何统计性时序缺陷的观测都受它影响**。
- **半主机**：客机通过一条特殊指令请求模拟器替它做输入输出，从而脱离被测试操作系统的栈。
- **ATF**：MINIX 3 使用的自动化测试框架；一个测试程序声明若干用例，由运行器逐个调用。用例可以主动声明「跳过」（例如需要某个架构条件时才跑）。
