## 第 1 章 现象：一条指令都没有执行错，内存内容却变了

一台机器上同时跑着一个内核与一批用户态服务进程（启动期由引导装载件加载的模块共 12 个，口径见 `os/qemu-tests/test-cmd-smoke.sh` 的开篇注释）。其中有个测试进程做了一件极其实诚的事：它先算出一串伪随机字节，把它们搬进两块缓冲区，再把两块缓冲区的每一个字节喂进一个摘要函数，最后把摘要结果与**源码里硬编码的一串十六进制常数**比对（常数出处 `minix3/tests/lib/libc/string/t_memcpy.c`，第 54 行，工具生成）。

它的算术全对。搬运函数全对。摘要函数全对。把完全相同的程序放到另一个环境里裸跑，结果与常数逐位相同。

**可是在这台机器上跑，最后那串摘要就经常是别的值。** 而且每次开机得到的那个「别的值」都不一样：这次是 `9f2e1c56`，下次是 `25f4881b`，再下次是 `0ecef203`。同一个二进制、同一个磁盘镜像、同一份内存布局，只因为重新开了一次电源，答案就换了一个。

这就是本案的全部麻烦所在：**缺陷不在任何一段计算里，而在计算所用的数据于两次采样之间被悄悄改掉。** 没有人写了坏值，没有硬件故障报警，也没有异常抛出——只有事后核对时发现，某一小块内存的内容不再是它刚才的样子了。

它露出水面的面孔至少有五张，而它们被认为出自同一个机制：

| 面孔 | 现场 | 来源 |
|---|---|---|
| 测试摘要错 | 上面那串每次不同的摘要值 | 取证记录 §续-342、§续-361 |
| 内核读到当成数值用的字符串 | 内核启动期把一段扣除区间算成 `[0x0, 0x6d636e797361)`，末值换出来是可读文本 "asyncm" | 取证记录 §续-342 |
| 内核自己 panic 后报「无法再派生子进程」 | 一个取不到值的可选类型解包失败 | 取证记录 §续-342 |
| 加载器越界访问 | 报出「长度为 3 却索引第 3 格」，而边界检查在算术上封死了这种输入 | 取证记录 §续-346 |
| 页故障打出一个不可能合法的地址 | 处理器报告的出错地址远大于本页表格式允许的用户地址上限 | 取证记录 §续-364、§续-365 |
| 先导签名：拷贝长度读到腐值 | 三次不可达的越界 panic **全部以 `nk4a: kdst copy len=1` 为先导**（健康跑为 0x2f）——长度字段本身就是被腐蚀的源 | 取证记录 §续-346 |
| 爬行（没崩但慢一千倍） | 执行程序链卡住、每步极慢，一小时窗内零个终态 | 取证记录 §续-366 第 2 次采样 |

**为什么这两行新增面孔重要**：`kdst copy` 就是**内核代客跨空间拷贝**的诊断行——三次响亮失败全部由它先导，而爬行也被归到同一个拷贝路径的挂起重试。也就是说，**同一嫌疑路径已经用自己的遥测碰了两次门**。另有一处仓内历史记录可作旁资：栈回溯代码里就写着曾经因为这类拷贝写坏目标而级联出野值（`os/kernel/src/stacktrace.rs` 的注记，工具生成行号 L259 附近）。

**为什么这类缺陷比崩溃难得多**：崩溃会自己报到，并把出错位置递到你手上；静默改写不会。你唯一能确定它存在的办法，是事先设计一个「内容必须一直正确、且一旦有任何一字节变动就会立刻显形」的观测装置。本案的整个进展史，本质上就是不断制造更好的观测装置的历史。

## 第 2 章 那个测试为什么正好是观测装置

先讲清一个概念。本文反复提到「自动化测试套件」：它是 MINIX 3 自带的一批 C 语言测试程序，每个程序里声明若干「用例」，用例通过断言判断被测函数的行为对不对。本文的主角是其中一个用例，叫 `memcpy_basic`，出处 `minix3/tests/lib/libc/string/t_memcpy.c:memcpy_basic`。

### 2.1 它为什么灵敏：摘要链的雪崩性质

把一块数据算成摘要，就像把几十种颜料反复调和：任何一滴颜料在任意时刻掺进去，最终颜色都会改变，而且改变是全局的、无法从结果反推掺了哪一滴。摘要函数的这个性质是设计目标，不是副作用。

这个用例还把灵敏度推到更高：它用的是**一个持续累积的摘要上下文**。整个用例从头到尾只有这一个上下文，中间不断喂数据，最后一次取值。所以中途任何一次内存改动，都会被后面所有数据一起放大，绝不会出现「改了但改在没人看的地方」。

### 2.2 它到底跑了多少数据（下面的数字全部由脚本算出，标注「工具生成」）

源码骨架（`minix3/tests/lib/libc/string/t_memcpy.c`，行号由工具派生）：

- 三四个宏：对齐种类数 16、长度种类数 4、缓冲区类型数 4（L39-L41，工具生成）；
- 一块测试缓冲区的大小 = 16 × 4 = **64 字节**（L45，工具生成）；
- 两块放在只读/初始化数据段，另两块放在函数栈上（L47、L87，工具生成）；
- 摘要上下文 `mc` 是一个全局数组，一个元素（L43，工具生成）；
- 期望值是硬编码的 32 位十六进制串 `7b405d24bc03195474c70ddae9e1f8fb`（L54，工具生成）；
- 核心循环：对 16 × 16 种偏移组合，先给两块缓冲区各重填 64 个随机字节，再做一次搬运，再把两块缓冲区依次喂进摘要（L62-L75，工具生成）；
- 用例正文对 4 种缓冲区类型两两配对、跳过自己配自己，于是得到 **12 个有序对**；每对内部有 256 种偏移组合（L94-L97，工具生成）；
- 全用例**只有一处断言**：比较最终摘要与期望值（L99，工具生成）。

由上面这些数字可以算出：

| 量 | 值（工具生成） |
|---|---|
| 摘要检查点总数（= 偏移组合数，即当时设计的逐组校验粒度） | 12 × 256 = **3072** |
| 搬运函数调用总次数 | 12 × 13 784 = **165 408** |
| 由随机流写入的字节总量 | 21 172 224 字节 ≈ **20.2 MiB** |
| 送进摘要函数的数据总量 | ≈ **20.2 MiB** |

于是这个用例的品性就很清楚了：**它是全套件里唯一在长时间里对全部内容做一致性核对的用例**。其余三十五个用例几乎都只检查返回值是否为指针非空、字符串是否等于某个短常量——改一个字节它们可能毫无反应。而这里，20 MiB 数据流过一条累积链，最后只有一句比对。

### 2.3 灵敏的代价：能感知，不能定位

单点断言意味着「知道被改了」和「知道被改在哪」是两件事。这个装置能告诉你「这一跑被击中了」，但它给不出时刻、给不出地址、也给不出改写者。本案取证的主要工作量都花在把这一个比特位的信号，逐步升级成能定位字节位置的装置：先在每个检查点打印累积摘要（第 3 章的「分歧对」），再把每个偏移上的 64 字节全量打印（第 3 章的「全量转储」）。每升级一次，定位精度就细一层，但**插桩本身也在改变被观测程序的执行时序**——第 4 章会用一整节说明这个副作用如何误导了取证方向。

## 第 3 章 已坐实的事实

每条都给锚点与复核方式。标「本文作者独立复核」的，是指我这次不信任二手记录、自己算过或自己读过原始文件的。

### 3.1 计算层完全清白

**做法**：把编译产物原封不动搬到另一个执行环境里去跑——用处理器模拟器直接加载这个测试二进制，让它使用自己自带的 C 运行库启动例程，通过半主机方式把输出打回宿主机。这条路上**不经过我们重写的内核，也不经过我们写的程序加载器**，因此内核与加载器整体不在嫌疑范围内。半主机的意思是：客机程序发一条特殊指令请求模拟器替它做输入输出，而不是走我们操作系统的系统调用。

**结果**：逐位相同，三次都是 `7b405d24…`（取证记录 §续-342；存档 `tmp/nk4a/tmemcpy_bisect/bare_1.txt`、`bare_2.txt`、`bare_3.txt`，另有参考态 `reference_baremetal.txt`）。

**因此排除的**：RISC-V 交叉编译器的代码生成、BSD 风格伪随机数算法的实现、C 运行库里逐字节搬运的 memcpy 实现、我们自己补的那份摘要函数实现（`tools/atf-c-compat/md5.c`，签名与 `minix3/sys/sys/md5.h:MD5_CTX` 同形）。

**复核**：
```bash
ls tmp/nk4a/tmemcpy_bisect/ | grep -E 'bare|reference'
python3 -c "
L=open('minix3/tests/lib/libc/string/t_memcpy.c',encoding='utf-8',errors='replace').read().split(chr(10))
print(chr(10).join(f'{i+1}: '+L[i][:90] for i in range(38,55)))"
```

### 3.2 真机上「完全正确」是可达的

**读数**：一次真实开机里，逐检查点校验的 **3072 个内层块全部对账无差异**，最终摘要与裸机参考**逐位一致**，串口日志完整跑完约 1.5 MB，测试报告 `passed`（取证记录 §续-363）。

**这条为什么关键**：它把「我们的实现有系统性错误」这个解释彻底掐掉了。既然同一套代码同一套镜像可以一分不差地跑完，那么历次错值只能是**每次开机是否被击中**的差别。缺陷从「必现的算法错」重定性为「概率性的内存改写」。

### 3.3 命中概率随暴露时长增加而增加（目前还不能称「正比」）

同一缺陷在三种暴露时长下的读数（取证记录 §续-340、§续-364）：

| 暴露时长 | 读数 | 结果 |
|---|---|---|
| 短启动（只做启动与几条命令） | 常规通过 | 常常不被击中 |
| 中窗（420 秒 / 1800 秒） | 9 个用例出终态 / 23 个用例出终态 | 恰好 1 个失败，即本用例 |
| 长窗（36 个用例全量、3600 秒） | **0 个用例出终态** | 在第一个结果行打印出来之前，内核就因 5 章那条野地址停住了 |

**强度限定【重要】**：这组数据支持的是「暴露越久越容易命中」这个**单调上升**关系，**不支持**「命中概率与时长成正比」这个更强的断言。最自然的累积模型是参数为 λ 的指数分布形状：时长 T 内至少命中一次的概率为 1 − e^(−λT)；只有在 λT 远小于 1 的低命中区间，它才近似等于 λT。本案样本量远不足以区分这两种形状。

**还要排除一个误读**：上表第三行（0 个终态）**不能**当作「命中率更高」的统计点——它不是被同一类静默改写打穿的，而是被一条**另外的响亮故障**提前截断了。它能支持的结论只有一个：长时间跑这套件会被各种形态打断，因此「靠重跑碰运气」这条路不可行。

### 3.4 与处理器模拟器的版本无关

两条不同世代的模拟器版本（8.2.2 与 9.2.4）跑出同一族面孔（取证记录 §续-346）。这条证据把「模拟器的软件内存管理有缺陷」这个诱人的解释削弱到很低的位置——但注意，它没有完全否证：同一族的两个版本仍可能共享同一段有问题的代码路径。**[待验证：只换版本、不换后端（例如改用支持硬件虚拟化的加速器）的对照未做]**

### 3.5 只有这一个架构有现象

同一个内核、同一套虚拟内存服务、同一套测试套件，在 64 位 ARM 上 36 个用例全部到达终态且零失败（取证记录 §续-286；门脚本 `os/qemu-tests/test-atf-aarch64.sh`，判据见附录 A）。这条把嫌疑面从「共用的上层逻辑」推到「RISC-V 独有的那部分」，也就是分页实现与架构相关的陷入路径。

### 3.6 改写是「小而准」的，不是整页覆盖

**读数**（取证记录 §续-349）：在命中那一跑里，两条输入缓冲全程未被破坏、随机数表全程未被破坏，只有摘要上下文变了。而**摘要上下文与随机数表在同一个 4096 字节页内**。

**本文作者独立复核了这条的算术**：摘要上下文起始 `0x80200108`，随机数表起始 `0x80200000`，相差 **264 字节**，同一页（页号 `0x80200`）；摘要上下文的尺寸 = 4 个 32 位状态字 + 2 个 32 位比特计数 + 64 字节残留输入缓冲 = **88 字节**，占到 `0x80200108`–`0x80200160`。

**因此**：一次页级清零、一次页级拷贝、或者一次「整页错位写」都不可能产生这个读数——那会顺手毁掉同一页里的随机数表。被改的是**几字节到几十字节量级的精准写**，落点在 88 字节的摘要上下文里。（摘要上下文被改而输入缓冲未改，本身就足以让最终值面目全非，因为状态字和比特计数都在链上。）

**[待验证：264 字节的间隙里住着哪些全局量，本文未逐项核对目标文件的符号布局]**

**复核**：
```bash
python3 -c "
mc=0x80200108; rt=0x80200000; sz=4*4+2*4+64
print(mc-rt, (mc>>12)==(rt>>12), sz, hex(mc+sz))"
python3 -c "
t=open('tools/atf-c-compat/md5.h',encoding='utf-8',errors='replace').read()
i=t.find('MD5Context'); print(t[i-20:i+260])"
```

### 3.7 面孔清单：被击中的对象不固定

已观测到的被击中对象有四类：测试进程的数据段、进程间共享页上的记录结构、内核启动期使用的模块镜像、内核交接数据（取证记录 §续-363 的画像终稿）。改的具体位置逐次开机不同。

**强度限定【重要】**：能说的只是「**目前每次取证只观测到一个污染对象**」。这**不等于**「每次开机只发生一次写」。两种很容易发生的屏蔽机制都会让第二处写看不见：其一，第一处写一旦破坏控制流，程序就异常终止，后面的写根本来不及发生或被打印出来；其二，现有探针只保存第一处差异。因此「单次一处」目前**不能当判别依据**使用。

## 第 4 章 已排除的假设，以及每条排除手段的分辨力边界

这一章是本文对外部审阅者最有价值的部分。原因很直白：**一个排除结论的价值，等于它所用手段的分辨力**。下面每条都写明「手段覆盖了什么」和「手段看不见什么」。

| 编号 | 假设 | 排除手段 | 手段的盲区（重要） |
|---|---|---|---|
| 排除-1 | 交叉编译代码生成、随机流、memcpy、摘要实现有错 | 3.1 的裸机对账 | 只证明「不经我们内核与加载器时正确」。若缺陷需要我们的内核参与才出现，本手段无覆盖 |
| 排除-2 | 物理帧分配器把同一页发给两个使用者 | 在分配时刻判定的位图检测器，真机全零命中 | 只能得出「**分配那一刻，没检测到已登记的重复所有权**」。它既不能排除「事后被某条错误路径改接给另一个使用者」，也不能排除「某些页从来没进过这份账本」。要真正排除需要运行期的物理页所有权不变量，见 4.3 |
| 排除-3 | 页表项被逐出后又被复用（缓存所有权判别缺陷） | 两份全量串口存档里逐出事件行数 = 0（取证记录 §续-343） | 准确表述应当是「**未观察到逐出或复用是这两次运行的触发因素**」，而不是「逐出假设已排除」。后者强得多，而现有证据只到前者；逐出路径自身的缺陷仍作为登记性缺陷留账 |
| 排除-4 | 改页表后缺地址转译缓冲失效指令 | 该路径已改为经内核直接映射窗口直写并紧随失效指令（取证记录 §续-343 引 `os/arch/src/riscv64/paging.rs`） | ⚠️ **本案目前最危险的「看起来已排除」**。已证明的只是「某一条写入路径后面跟了失效指令」，需要证明的是「**所有**改写页表的入口、**所有** hart、**所有**地址空间标识符与全局映射情形下都跟了正确的失效指令」。本轮新增的三条结构性事实见 4.3 |

| 排除-6 | 内核侧（含走页表返回错物理地址）整体清白 | 两次回退实验：把走页表改动整体回退、再把内核侧回退到本次审计之前的源码树，都仍然在同一个字节数处停滞 ⇒ 判内核侧清白（取证记录 §续-359、§续-360） | ⚠️ **这条排除的证据基础不成立，见 4.1** |

### 4.1 排除-6 需要重做：判据本身是探针自己造的假象

时间顺序是这样的：某段时间里，所有实验都以「客机在串口输出第 245 699 字节处停滞」为观测点。回退走页表改动、回退内核侧改动，**两条臂都停在同一个字节数**，于是得出「内核侧与本缺陷无关」（排除-6）。

随后发现：**这个停滞点是打印插桩自己造出来的**。把测试探针换成打印量较小的那个形态（从每个检查点都打一行，退回只打十二行），同一份内核镜像**一路跑完、不再停滞**（取证记录 §续-361）。也就是说停滞不是内核行为决定的，而是「探针打了多少字」决定的——打印本身改变执行时序，时序决定何时撞上某个资源边界。

**如果这个定性成立，那么排除-6 的两条臂都带着同一个混杂变量，对这个假设没有分辨力**：两条臂用的是同一个高打印量探针，本来就都会停滞，与内核代码对不对无关。

本文作者另外注意到一处内部不一致，可作为佐证（也说明这条线值得重跑）：取证记录 §续-352 记「关掉一处页表项检查后，客机越过了 245 699 停滞点」，说明**同一探针下改内核行为确实能移动停滞点**；而 §续-358 又记「把那处检查重新打开后仍停在 245 699」，两读数互斥。并且回退到本次审计之前的源码树时，那份代码里本来就**没有**那处检查，按 §续-352 的读法它不该停滞。

**这条不是「内核侧有罪」的证据，而是「内核侧清白尚未证明」的说明。** 第 7 章的实验甲就是为此设计的：判据从「是否停滞」换成「是否逐次开机恒定」，后者不受打印量影响。

**本项的现状（与主线程已收敛）**：后续取证已把走表线**重新打开并列为头号候选**，但用的是另一个理由：我们的走表**变更**已被排除（因为原始走表同样出此症），而**走表本身从未被排除**（取证记录 §续-366）。这与 4.1 以方法学理由提出的质疑方向一致。

### 4.1.1 对那四份停滞日志的逐字节复核（本文作者独立取证）

停滞点被记作「第 245 699 字节」，直觉上这是一个极强的确定性信号。本文作者把四份同尺度的停滞存档逐字节比了一遍，**结论是它没有看起来那么硬**：

| 存档（`tmp/nk4a/tmemcpy_bisect/`） | 字节数 | 与其他份的差异 |
|---|---|---|
| `machine_fix1.log` | 245 699 | 基准 |
| `machine_fix2.log` | 245 699 | 与基准不同 **966 字节**，首个不同在第 **163 363** 字节 |
| `machine_hard1.log` | 245 699 | 与基准不同 **58 字节**，首个不同在第 143 635 字节 |

### 4.2 已经被买到的教训：观测手段自身的两类污染

这两条不是修辞，是本案真实踩过的坑，任何外部审阅者给出的实验建议都应当先过这两关。

**教训一：打印不能消费被测数据流。** 最早的探针版本为了「验流」，在入口处打印了前五个随机数值——**而没有重新播种**。结果摘要链被推进了五个值，跑出**一个可复现的错误值**，而且在这个架构和宿主机上错得逐位一致。一个假的必然错，差点被当成真结论。修正 = 打印之后立即重新播种。（取证记录 §续-342）

**教训二：去重键可能跨进程共享。** 一个用于「同一地址被填多次」判定的探针，其去重键是（位置，页内虚拟地址，页内物理地址）三元组，**全局共享**。于是「同一虚拟地址先后对应不同物理帧」这一现象——对进程更替（每次执行程序换栈帧）而言完全正常——会被读成「重复填充」的实锤。该判据必须按进程分开。（取证记录 §续-342）

### 4.3 本轮新核出的三条结构性事实（直接改变某些假设的优先级）

这三条是本文作者在核对环推与配置时实测得到的，它们要么直接排除一类机制，要么把一类机制重新打开。

**其一：出问题的点火是单核配置。** 跑套件的门脚本与启动门都写 `-machine virt -smp 1 -m 512M`（`os/qemu-tests/test-atf-riscv64.sh` 的点火行，工具派生行号 L202；`os/qemu-tests/test-riscv64-boot-full.sh` 同形，L144）。因此：

> **跨核转译缓冲卸载（一个核改了页表、另一个核手里仍是旧映射）这一整类机制，在所有污染观测里结构上不可达。**

（多核只在一个专门的中断转发测试里出现，那个测试不跑套件。）但请注意：**单核只否掉「跨核」那一半，同核陈旧表项仍然完全可能**，所以 4 章的排除-4 并未因此变强。

**其二：地址空间标识符根本没启用。** 写入 `satp` 寄存器的值是「模式位左移 60 位，再或上根表物理地址右移 12 位」，**没给地址空间标识符留位**（`os/arch/src/riscv64/tlb.rs:86`，工具生成）。两个直接推论：

- 「标识符滥用导致旧进程表项被新进程复用」这类经典缺陷**结构上不存在**（标识符恒为 0）；
- 第 7 章的守护设计可以更简单：只需保证守护对象与被测对象**在同一个虚拟页内**（不需考虑标识符匹配）。
- ⚠️ **代价**：因为没有标识符，每次切地址空间**必须**做一次全量失效，否则整个系统的表项全部混淆。本文曾指出两处写法不一致：运行期切根入口 `os/arch/src/riscv64/tlb.rs:set_active_root` 确实配套了全量失效（先写 `satp` 紧接不带操作数的 `sfence.vma zero, zero`，L88-L89），而 `os/arch/src/riscv64/paging.rs:switch()` **只写 `satp`、不跟任何失效指令**（L772-L777，工具生成），配对与否取决于调用点。**本项已核完（取证记录 §续-367）：后一个方法在 RISC-V 生产路径上零调用方（仅架构内模拟测试使用），属于陷阱死代码，已登记待清理；生产切换全部经 `set_active_root_tracked` 走上面那个带失效的入口。因此本条不再构成第 2 类的候选依据，但“所有入口是否都配对失效”仍需逐个核（只核这一个入口不够）。**

**其三：这台虚拟机里没会自主写内存的设备。** 点火命令里只有一个写内存入口：`-device loader,addr=…,force-raw=on`（12 个模块 + 启动表 + 根盘镜像），加上 `-serial file:…` 与 `-display none`。**没有 virtio、没磁盘控制器、没有网卡。** 因此本文第 6 章里「外设直接存存取取（DMA）改写内存」这一整类**被配置结构性排除**（不是被环推排除）——`loader` 设备只在客机开始执行**之前**写内存，不可能在测试窗口内动手。

**另外一条作者自查但未成立的可疑点（负结果）**：返回路径上有一处把保存的程序计数器直接加 4 的代码（`os/kernel/src/trap_dispatch.rs:1829`，工具生成）。若被跳过的指令是 2 字节压缩编码，这就会让用户从错位置继续执行，形状上非常契合本案。但本文核对后确认它只在**用户态环境调用**（`ecall`）分支上执行，而 **`ecall` 在 RISC-V 里没有压缩编码形式**（只有压缩的 `c.ebreak`，不是 `ecall`），所以「加 4 字节」在此处成立。**该可疑点已自行消。**写出来是为了给外部审阅者划清「已经有人看过、结论是清白」的区域。

## 第 5 章 野地址样本的位形，与一处可疑的归类

页故障会报告出错的地址。本案攒下四个超出合法用户地址范围的样本。64 位 RISC-V 的 Sv39 页表格式下，用户地址半区是 `[0, 2^38)`，权威常数与推导都写在 `os/libs/minix-types/src/types/boot.rs:USER_VA_LIMIT`（行号由工具派生：该常数在 L173-L179，L183-L184 有两条编译期断言把栈顶常数钉在用户半区内并要求页对齐）。

下面每一行的所有派生量都由脚本算出（工具生成）：

| 样本 | 值 | 最高置位 | 除以 16 的余数 | 低 38 位掩码后 | 归类 |
|---|---|---|---|---|---|
| era_323 | `0x7fffffffef90` | 46 | 0 | `0x3fffffef90` | 旧叙事里的「形状 A」 |
| run8 | `0x7ffff48b124e6` | **50** | **6** | `0x3f48b124e6` | 「形状 A」 |
| gate1 | `0x1bfffe61e730` | 44 | 0 | `0x3ffe61e730` | 形状 B |
| bit38 族 | `0x4000000000` | 38 | 0 | `0x0` | 形状 B |

取证记录 §续-365 把前两行归为同一形状，理由是「高位连续置起，像 64 位 long 模式下的栈指针」。这里给两点本文作者独立复核后的补充，请外部审阅者判这个归类是否成立。

**其一：era_323 不能用作本缺陷的证据。** 它比栈顶常数改正所针对的那个错误值低正好 **112 字节**（`0x70`，工具生成）。也就是说它就是那个错误栈顶常数往下偏移后的形态（为何恰好是 112 字节，本文未取证，**[待验证]**），而且它是改正**之前**采集到的观测。拿改正之前的样本去支撑「改正之后仍有路径在产生同形状的值」这个假设，逻辑上不成立。

**其二：关于那个余数 6，本文上一版的推论跨了界。** 我当时写「余数不为 0 ⇒ 它不是一个栈指针」，这是错的：**页故障报告的是出错的那次访问的地址，不是参与地址计算的那个寄存器的值**。举例：只要指令是「以 sp 加 6 为地址存一个八字节字」，即使 `sp` 本身按 16 字节对齐，报告地址也会是余 6。

所以正确的表述只能弱到这一步：**run8 与「未经偏移直接使用的、按调用约定对齐的栈指针」不相符**，而不是「run8 不可能来自栈」。两者差别很大：前者只说明「不是整个旧值被原样当作指针写入」，后者才会排除掉「旧值参与了一次带偏移的访问」。

仍然站得住的部分：run8 最高置位 50、比 era_323 高出四位，且**无法由 era_323 经过一次移位或一次掩码得到**（右移四位后形态仍不符，工具生成）。所以「两个样本同源」这个假设至少**还缺少一个能写出算术过程的生成器**。

**其三：形状 B 我复核通过。** gate1 的 38 位以上置位集合是 {38,39,40,41,43,44}，与取证记录记的逐位一致；它掩掉 38 位以上之后落在合法用户半区内，所以「合法低 38 位 + 高位散布置起」这个描述成立。

### 5.1 形状 B 的三种候选生成器，按可信度排序

「高位散布置起」这个形状至少有三种成因，**上一版本文把「按位或」排得太前**，这里改排序并给出可计算的判据。记 `C` = 观测到的坏值，`A` = 期望值或当前合法值，`B` = 另一个候选源值。

| 序 | 生成器 | 为什么排这里 | 能区分它的指纹 |
|---|---|---|---|
| 1 | **部分覆盖 / 复合字**：一个 64 位字里，低位来自当前值、高位某几个字节来自旧值（一个陷帧或栈上对象被盖了半截） | 它比严格的「按位或」更贴合「几字节量级精准写」这个已实测特征 | 逐字节看：变化集中在**连续的几个高位字节**，且那几字节能在旧主人内容里逐字找到 |
| 2 | **跨页边界的写**：一条宽度 8 的存落在页内偏移 4089–4095 附近 | 形状 B 的低 38 位合法、高位像被拼接，与跨页拆分的存非常兼容 | 强指纹：一处变化靠近页尾 **且** 下一页页首同时变化 **且** 变化长度等于某个合法存宽度 **且** 内容能与某个源缓冲前后对接。特别地，「偏移 4092 + 宽度 8」几乎一眼可认 |
| 3 | **真的按位或** | 不是不可能，但要两个候选源同时对得上才能立项 | 需同时满足 `C == A \| B`、`A & ~C == 0`、`B & ~C == 0`，**且在多个样本上反复成立**。只出现一次不够 |

**另有一种最硬的陈旧指纹，与上面三种共用**：若能证明「当前对象所在物理帧 = 帧 B，帧 B 内容未变，而旧主人帧 A 恰好含有那段坏内容」，那几乎就是直接证据（它同时区分了 1、2 与「算错地址的写」）。本案已有的全量物理内存快照工具（附录 A 里的两份 512 兆字节快照）正是为了做这种比对而存在的。

**本文的判断【有支持、未坐实】**：所谓「形状 A」目前只剩 run8 **一个改正之后的样本**，而它既不能由那个旧栈顶常数经一次移位或掩码得到，也不具备「原样写入的指针」该有的低 4 位形态。把 run8 与 era_323 捆成一个族，风险是为两种不同来源追一个共同写者。建议把 era_323 从本缺陷的证据集中移出（标注「已由栈顶常数改正解释」），把 run8 单列为第三种形状。

**复核**：
```bash
python3 -c "
for n,v in (('era_323',0x7fffffffef90),('run8',0x7ffff48b124e6),('gate1',0x1bfffe61e730),('bit38',0x4000000000)):
    print(n, hex(v), 'msb',v.bit_length()-1, 'mod16',v%16, 'low38',hex(v&(2**38-1)), 'legal38',(v&(2**38-1))<2**38)
print('era_323 与旧栈顶常数差', 0x7ffffffff000-0x7fffffffef90)"
```

## 第 6 章 能在「无内核参与」窗口里改几字节的机制清单

第 3 章有一条很强的时序证据：在命中那一跑里，测试进程算完整段数据的期间，**内核侧看不到任何活动**——没有系统调用、没有探针行（取证记录 §续-343）。能在这段时间里改动客机内存的机制，理论上只有以下几类。把它列全，是为了让外部审阅者直接指认「哪一类我看来最像、以及用什么一次判定」。

### 6.1 排序的第一名不是页表，而是陷帧本身

上一版本文把「陷与中断上下文」只当作一个普通候选项，这是低估了。把四个已实测特征摆在一起看：

> 只在 RISC-V 上出现 + 随暴露时长上升 + 几字节量级的精准改写 + 应用不主动调用服务时也能发生

这四条同时成立时，**一次陷或中断把用户上下文弄脏**比「某次走页表偶然返回错物理地址」更贴脸。理由是一个具体到令人不安的机制，**它不需要任何地址算术出错**：

```text
用户程序：
    …
    sd  t0, 0(a0)        ← 存一条指令，本身完全正确
    …
陷进入 → 保存寄存器 → 计时器处理程序运行 → 返回前恢复寄存器 → sret
                                  ↑
                    若这里少恢复了一个寄存器（或恢复错了内容）
用户程序：
    sd  t0, 0(a0)        ← 指令仍完全正确，但 a0 已经不是被陷前的那个值
```

**这种机制下，所有页表代码、所有走表算法、所有地址掩码都可以是彻底清白的**，而现场表现就是「程序自己执行了一次合法存储，只是落在了另一个地址」。而且它**天然带随机性**：不是每次中断都出事，只有当某个具体寄存器当时恰好承担着关键地址时才会。这正好解释了 3.7 「位置随机」与 3.3 「随暴露时长（即中断次数）上升」。

**为什么这个候选项在本仓不是空想**：本内核**确实会在返回前修改被保存的用户上下文**——至少有两处活动写入点：浮点惰性轮转的处理程序会改写保存下来的状态寄存器里的浮点状态字段（`os/kernel/src/trap_dispatch.rs:riscv64_fpu_trap_body` 内对 `frame.sstatus` 的位域赋值，工具派生行号 L2644），而上下文切换路径上也会对即将返回的上下文里的同一字段作修正（`os/kernel/src/lib.rs` 内关于「为非拥有者修正 `ctx.sstatus.FS`」的段落，工具派生行号 L3643 附近）。也就是说，「内核写用户返回上下文」不只是一个假设，它是已经存在于代码里的一类动作。

**并且这一带本仓已经交过一次学费**：浮点门控曾把「不陷」的状态值当成「会陷」来设（字段值与判据不匹配），导致轮转腿成为死代码，而且该缺陷通过了两轮代码审阅仍未被拦下。这类事实是本文把它排第一的主要理由。**[待验证：上述两处写入点当前的位域值与语义是否完全正确，本文未重新逐项对规范核]**

### 6.2 完整候选项清单（按当前可信度排序）

| 序 | 机制类 | 当前评价 |
|---|---|---|
| 1 | **内核代客跨空间拷贝的走表返回错物理地址**（具体入口已钉：exec 帧拷贝——文件系统服务收帧与落帧两处各自请求一次内核代拷贝；帧字节包括参数、环境变量与栈布局） | **主线程当前的头号候选**（取证记录 §续-366）。它能一笔同时解释三件事：随机位置的数据段腐蚀（帧池复用使任何对象的 .data 都可能被击中）、野地址（帧里的地址字段本身被错放）、以及 1 章那两行新面孔（`kdst copy len=1` 先导与爬行）；aarch64 干净可归为「同一逻辑、不同走表实现」 |
| 2 | **陷与中断的上下文保存恢复出错**（包括被保存寄存器被处理程序踩、少恢复一个、陷帧本身被覆） | 本文作者与外部审阅意见共同推荐的前选，**尚未被任何实验测过**。它能解释全部四条统计特征，且本仓已有同类缺陷先例（见 6.1）。它比第 1 类多一个好处：**完全不需要任何地址算术出错** |
| 3 | **同核陈旧转译表项 / 失效指令不完备** | 强候选。跨核那一半已被 4.3 第一条排除；曾疑的一处「只写根寄存器不失效」入口已查为死代码（见 4.3 第二条），**但「所有改写页表的入口是否都配对失效」仍未逐个核完** |
| 4 | **某个服务经自己的直接映射窗口算错地址写** | 微内核结构下必须认真怀疑；错址只要落在内存内就不会报错。与第 1 类在「内核代拷贝」这个入口上是**重叠**的，不一定需要分开建模 |
| 5 | **未对齐 / 跨页访存**（不是软件模拟出错，而是真发出了这类访问） | 模拟链已被 4 章排除-7 关掉；残余版本可静态审 |
| 6 | **物理帧复用时的残留内容 + 按需填充边界** | 与 3.6 的「小而准、同页其他字节未损」相冲，排位靠后 |
| 7 | **并发与内存顺序**（读改写无屏障、无锁结构的发布与订阅顺序） | 必须列入。但本文配置是单核（4.3 第一条），**真正的多处理器内存顺序问题不可达**；单核上仍可能有「中断在两条指令之间插入」造成的非原子 |
| 8 | **外设直接存取与缓存一致性** | 被配置结构性排除（4.3 第三条：虚拟机里无会自主写内存的设备） |
| 9 | **模拟器自身的缺陷** | 被 3.4 两代同形压低，但未否证（同一族的两个版本可能共享同一段代码） |

**其中 1 / 2 / 3 是现在真正应该争第一嫌疑的三条线。**

**顺带一个必须考虑的可能**：本缺陷可能不止一个写者。本案的证据只支持「单一机制多面孔」（取证记录 §续-342 判决 2），但样本量很小——命中次数的总量在个位数到十几之间。

## 第 7 章 能一次判定方向的实验组，与它们该拼成的判别矩阵

都优先选**不依赖真机长时间运行**的设计，因为 3.3 那张表说明长时间暴露既慢又不可靠。

### 实验甲：把内核侧清白这件事重新测一遍（针对 4.1）

固定**低打印量探针**（消除停滞点混杂），两臂：当前内核、走页表改动之前的内核。判据换成 **第一次缓冲对上的累积摘要是否逐次开机恒定**（3.7 与取证记录 §续-361 已经给出这个摘要三跑三值，它本身就是个不受打印量影响的传感器）。

- 两臂的该摘要都逐次变动 ⇒ 内核侧确实清白，排除-6 才算真正成立，此后所有分页层再审计都可以停；
- 某一臂恒定而另一臂变动 ⇒ 内核侧出局作废，立刻回到第 6 章第 3 类。

成本：两次开机，且不需要长窗。

### 实验丁：陷帧完整性校验 + 测试窗口关中断（信息量最大，建议先做）

这一组是本文最推荐先做的，**不是因为它的修复可能性最高，而是因为它一次开机就能同时回答两个大问题**。两个子件：

**子件一：在测试窗口内禁用当前核的监管态中断投递。** 注意不是「减少控制台输出」，而是直接关投递（计时器中断不再进来）。由于 4.3 第一条已经确认当前就是单核配置，这里不需要额外准备「专用核」，直接在唯一那个核上做即可。超时由宿主机负责（现有门脚本已经是宿主机轮询循环，天然具备）。

**子件二：给陷帧加守护值。** 在保存完用户寄存器后立即对陷帧算一次校验值，在 `sret` 前再算一次并逐字段比对，重点盯看栈指针、返回地址、前七个参数寄存器、临时寄存器、保存寄存器、以及保存的程序计数器与状态字。不是为了永久保留这个校验，而是为了**抓一只现行犯**：最希望看到的证据形状是「第 18 342 次中断：入口 a0 = 某值，出口 a0 = 另一个值，栈指针未变」。拿到这样一行，案子基本就结了。

**这个设计的干净之处在于**：它切掉的是一整个机制族（陷与中断路径），而不是只减少某类流量，所以它不受「改动本身会改变时序」这个噪声的干扰——因为两侧都在跑，只是中断不再投递。

四种可能结果与对应结论：

| 结果 | 结论 |
|---|---|
| 关中断后永远正确 | 陷与中断路径进入第一嫌疑（第 6 章第 1 类坐实方向） |
| 关中断后仍随机污染，陷帧一直完整 | 保存恢复路径大幅降权，全力转「同核陈旧表项 + 走表错地址」 |
| 关中断后仍随机污染，但陷帧出现异常 | 几乎就是突破（说明写者不止一个入口） |
| 关中断后仍随机，陷帧正常，而强制全量失效后消失 | 同核陈旧表项与失效指令浮出水面（第 6 章第 2 类） |

### 实验乙：守护对象（注意：不要做成「守护页」）

上一版本文建议放「几页守护数据」，**那是错的布局**。关键约束是：架构上**不存在**「保证两个不同虚拟页共用同一条转译表项」的条件；转译缓冲的匹配语义是按虚拟页（以及地址空间标识符或全局位）走的，而不是「地址相邻就共享」。因此**跨页的守护对被「同核陈旧表项」这类机制完全不敏感**——它只能测出错址写，测不出陈旧映射。

**本仓的实际情况让这件事更简单**：4.3 第二条已确认地址空间标识符恒为 0，所以「同页」就是全部条件，不需再管标识符匹配。

正确布局：守护对象与可疑对象**同住一个 4096 字节页**。本案已有现成的天然条件——摘要上下文与随机数表本来就在同一页内（3.6）而且相隔 264 字节：

```text
同一个物理页
+0x000  随机数表（已知内容，不断自校验）
+0x108  摘要上下文（被测对象）
其他间隙  填充已知魔术值的守护变量，多个尺寸与对齐
```

**把它做成一个主动判别器（而不只是被动报警）**，可执行步骤：

1. 先访问热点与守护对象，建立转译表项；
2. 把该虚拟页改映射到**另一个内容不同、守护魔术值也不同**的物理页；
3. **不发失效指令**，再读守护对象：读到旧页的魔术值 ⇒ 抓到陈旧转译；
4. 补一条只针对该地址与当前标识符的失效指令，再读：应该落到新页魔术值。

如果第 3 步能稳定复现陈旧读，就拿到了「不失效会怎样」的已知良好基线——接下来只要看真实腐蚀现场能否命中这个基线形状。校验一律放在被测计算之外，避免重踩 4.2 的教训一。

### 实验丙：把它做成 2×2，而不是单向削减

上一版本文只写了「削减控制台流量看命中率」。这个设计有一个先天缺陷：**控制台流量不是一个自变量**，削减它会同时改变调度、改变中断时刻、从而改变缺陷命中概率——混杂变量与被测变量搅在一起。

因此它的**逻辑上限**必须先说清：「关掉控制台流量后命中率不下降」最多否定「控制台代写流量是必要触发因素」，**不能否定内核或中断仍是写者**。

升级后的 2×2 布局（行：控制台流量高/低；列：中断投递正常/受控）：

| | 中断正常 | 中断受控 |
|---|---|---|
| **高控制台** | A | B |
| **低控制台** | C | D |

三种读数形状分别指向不同结论：

- `A ≈ C`、`B ≈ D`、`A ≠ B` ⇒ 主要变量是**中断暴露**，控制台流量无关；
- `A ≈ B`、`C ≈ D`、`A ≠ C` ⇒ 更像**控制台与内核代写流量**；
- 四格差不多 ⇒ 两者都不是主触发因素（这同样是有价值的结论，它一次性关掉两整类假设）。

### 目标产物：一张写者判别矩阵（不是更多日志）

本案已经不适合「再跑一次、再打印一点、再看看崩在哪」这种推进方式。上面三组实验拼起来应得到这样一张表：

| 实验 | 污染？ | 陷帧异常？ | 旧物理帧被读到？ |
|---|---|---|---|
| 正常 | 是 | ？ | ？ |
| 关中断 | 否 | 否 | ？ |
| 强制全量失效 | ？ | 否 | 否 |
| 不失效（实验乙第 3 步） | 是 | 否 | 是 |

**一旦某一行填得特别干净，根因会一下子收缩一个量级。** 当前配置下最值得先填的是「关中断」与「不失效」两行。

### 实验戊：双走表对账探针（**已在制，无需重建；请审阅它的判据强度**）

针对 6.2 第 1 类（也是主线程当前的头号候选）的直判实验已经存在：同一段地址做**两次独立走表**，物理地址不一致就打印（根表地址，虚拟地址，两个物理地址）。入口在 `os/kernel/src/vm.rs:nk4a_walk_reconcile`，调用点在跨空间拷贝路径内（工具生成行号 L71 与 L354；去重容量 32 条）。本文**不把它当建议提**，而是请外部审阅者评它的**判据强度与遗漏**，具体三点：

1. **它能否证什么**：两次走表一致 ⇒ 只能排除「同一次拷贝内部走表不确定」，**不能**排除「两次都错到同一个错物理地址」（确定性错译）。也就是说：**探针不报 ≠ 走表清白**。这个逻辑上限必须在结论里写死，否则一次零命中会被误读为排除。**本探针已跑过首轮：全程零不一致，而腐蚀照旧（取证记录 §续-367，21 passed + 腐蚀仍在）**——按上面那条上限读：它只排除了「同一次拷贝内走表不确定」，**第 1 类整体未被排除**。
2. **去重容量 32 条的两侧风险**：噪声跑满 32 条会静默丢弃后续事件（低估）；而去重本身会把「同一 (虚拟地址, 物理地址1, 物理地址2) 反复发生」压成一行，丢掉频率信息。
3. **建议补的第三个臂**：除「同一次拷贝内两次走表」之外，再加**写后回读对账**（写完立刻经直接映射窗口读回，比对源内容）。前者测「算得稳不稳」，后者测「算对了但没落到位」，两者合起来才能把第 1 类整族包起来。

## 第 8 章 什么才算修好了

对一个概率性缺陷，「跑了一次、绿了」不构成证据。本案已经付过一次这个学费：同一镜像四次点火里两次以不同方式崩、另外两次的测试结果还各不相同（取证记录 §续-342）。项目自己的判据纪律是：**症状消失不等于根因清除；两次逐字节相同的输出不等于独立稳定验证。**

需要一个可算的验收形状。设观测到的命中率为 p（按 3.3 的修正：p 是暴露时长的函数、形状暂按 1 − e^(−λT) 建模，而不是常数也不是严格正比），要求连续 k 次独立点火全部正确才宣布修复，那么「缺陷仍在但 k 次全对」的概率是 (1-p)^k。要让这个逃逸概率低于 1%，在 p = 0.5 时需 k ≥ 7；在 p = 0.2 时需 k ≥ 22；**p 越小、需要的 k 越大，而这正是长窗测试不可行的原因**——p 小的那一端恰恰是短启动，那里本来就不容易命中。

**一个必须防的统计陷阱**：不能把 3.3 表里「0 个终态」那一跑当作高命中率证据去推 k；它是被另一条响亮故障截断的，不属于同一事件族。

因此本文建议的验收形态是**双判据**：
1. 一个不受时长影响的**确定性判据**（实验甲那种「逐次开机恒定」的形状，用固定低打印量探针），并且要覆盖第 6 章各类机制各自最可能命中的地址区域；
2. 一个统计判据：以本文第 3.3 节那张表的长窗形态跑足 k 次（k 由上面的式子按期望逃逸概率反推，写成文档要求而不是口头保证）。

单靠门脚本变绿不足以宣布修复。现状的门判据是「终集计数」：把通过、失败、损坏、跳过四种行都算作到达终态，凑齐清单上的期望条数才定案，任何失败或损坏一票否决（`os/qemu-tests/test-atf-riscv64.sh`，行号由工具派生：期望数取自清单文件 L90-L91，终集计数与一票否决在 L213-L230；窗口长度默认 3600 秒在 L43）。这套判据本身是对的——它把「跳过」这种合法终态也算入，不会因为用例自己选择跳过而误报停滞——但它对概率性缺陷没有免疫力。

**复核**：
```bash
python3 -c "
import math
for p in (0.5,0.2,0.1):
    k=math.ceil(math.log(0.01)/math.log(1-p)); print('命中率',p,'→ 需连续',k,'次全对才把逃逸率压到 1% 以下')
print('Sv39 用户地址上界 2^38 =',2**38)"
```

### A.2 一条与本案相邻、但**不属于**本案根因的未决登记项

`os/servers/vm/src/memtype.rs` 里判断「某类内存能否就地改尺寸」的 `supports_resize`，对「物理连续匿名内存」与「块缓存内存」两类**继承了默认为真**；而 C 里这两类的对应回调虽然存在，函数体却是**无条件返回内存不足**（`minix3/minix/servers/vm/mem_anon_contig.c:anon_contig_resize` 打印「cannot resize physically contiguous memory」后返 `ENOMEM`；`mem_cache.c:cache_resize` 同理）。净效果：一次堆增长落到这两类区域上时，C 拒绝、本重写会同意。**可达性未坐实**，与本案污染是否相关亦未知；它已连续多轮被报，登记在此以防再次丢失。

## 附录 B 术语（给零背景读者）

- **微内核与用户态服务**：内核只留最少的机制，程序加载、文件系统、内存管理都由独立进程承担。好处是一个服务写坏了不会直接拖垮内核；代价是它们之间必须靠消息往来协作。
- **页表与按需补页**：程序看到的地址是虚拟的，需要一页页表格换算成物理地址。表格还没建到某一页时，处理器报「页故障」，由负责内存的服务进程补上——这就是「按需补页」。
- **Sv39**：64 位 RISC-V 的一种三级页表格式，可寻址范围由此受限；超出该范围又不符合符号扩展规则的地址称为「非规范地址」，处理器对它的访问必然故障。
- **直接映射窗口**：内核把整段物理内存按固定偏移映进自己的地址空间，于是「物理地址 P」可以像普通指针一样被内核读写，不必为它建页表。
- **地址转译缓冲**：处理器缓存最近的「虚拟地址 → 物理地址」换算结果。改了页表却忘了让对应表项失效，后续访存就会继续用旧映射——本案第 6 章第 4 类。
- **处理器模拟器与软件模拟（TCG）**：用软件逐条翻译并执行客机指令。功能上等价于真处理器，但性能与时序特性差异很大，而且**任何统计性时序缺陷的观测都受它影响**。
- **半主机**：客机通过一条特殊指令请求模拟器替它做输入输出，从而脱离被测试操作系统的栈。
- **ATF**：MINIX 3 使用的自动化测试框架；一个测试程序声明若干用例，由运行器逐个调用。用例可以主动声明「跳过」（例如需要某个架构条件时才跑）。
