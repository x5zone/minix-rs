# RS (Reincarnation Server) 跨层污染分析

> 本文档记录 Minix3 中 RS 机制的架构问题，以及未来重新设计的方向。

---

## 1. 核心问题：跨层污染 (Cross-Layer Pollution)

### 1.1 现象描述

RS (Reincarnation Server) 及其相关的特权位、内核端点机制，像**"全局变量污染"**或**"横向切面入侵"**一样渗透到各个 Server 中：

- **PM** 中的 `do_fork` 需要处理 RS 特权位
- **VM** 中的 `vmproc` 需要标记 `VMF_VM_INSTANCE`
- **VFS** 中的文件描述符管理需要考虑特权进程

### 1.2 本质：逻辑的"露点"

在理想的微内核架构中，每个 Server 应该是**黑盒**。但 Minix3 为了实现"不死之身"的容错，让 RS 的触角伸到了每一个角落：

| 问题 | 表现 |
|------|------|
| **侵入性 (Intrusiveness)** | 在 PM 里处理进程关系时，RS 的逻辑像倒刺一样扎在 `do_fork` 中。不仅要处理业务，还要照顾"监工"的情绪 |
| **强制性耦合 (Forced Coupling)** | 不是作为可选插件存在，而是系统运行的**前置条件**。每个模块都要为它的存在修改数据结构（如 `mproc` 里专门为特权位留出的字段） |
| **无法回避的可见性** | 这种"每个模块都能看见它"的感觉，就是代码审美报警的根源 |

## 2. 理想 vs 现实

### 2.1 美的逻辑（理想架构）

```
┌─────────┐     ┌─────────┐     ┌─────────┐
│   PM    │────→│   RS    │←────│  Kernel │
│(进程管理)│     │(重启服务)│     │(端点分配)│
└─────────┘     └─────────┘     └─────────┘
     │                                │
     └──────────────┬─────────────────┘
                    ↓
              事件通知（松耦合）
```

- **关注点分离**：PM 管进程，RS 管重启
- **PM 不知道 RS 的存在**：进程退出时发个信号，谁爱接谁接
- **无侵入性**：各 Server 的数据结构保持纯净

### 2.2 丑的现状（Minix3 实现）

```
┌─────────────────────────────────────┐
│              PM                     │
│  ┌─────────┐  ┌─────────┐          │
│  │ do_fork │──→│ RS逻辑  │ ← 倒刺  │
│  │  业务   │  │ 特权位  │          │
│  └─────────┘  └─────────┘          │
└─────────────────────────────────────┘
              ↓
        强制同步 RS 数据
```

- **卑微的同步**：PM 必须主动去同步 RS 需要的数据
- **数据结构污染**：`mproc` 中散布着 RS 相关的字段
- **横向切面**：RS 逻辑像 AOP 一样横切各个模块

## 3. 具体污染点记录

### 3.1 PM 层

| 位置 | 污染内容 | 理想状态 |
|------|----------|----------|
| `do_fork` | 特权位继承、RS 通知 | PM 只创建进程，RS 自己监听 |
| `mproc` 结构 | `mp_priv` 等特权字段 | 纯净的进程管理字段 |
| `SYS_PRIVCTL` 调用 | 内核特权控制 | 由 RS 直接处理 |

### 3.2 VM 层

| 位置 | 污染内容 | 理想状态 |
|------|----------|----------|
| `vmproc` 标志 | `VMF_VM_INSTANCE` | VM 不需要自识别标志 |
| `do_fork` | 特殊处理 VM 实例 | 统一处理所有进程 |

### 3.3 VFS 层

| 位置 | 污染内容 | 理想状态 |
|------|----------|----------|
| `fproc` | 特权进程标记 | 无特殊标记 |
| 文件描述符 | 特权进程特殊处理 | 统一处理 |

## 4. 重新设计方向

### 4.1 目标架构

```rust
// 理想的关注点分离

// PM：纯净的进程管理
pub struct Process {
    pid: Pid,
    parent: Option<Pid>,
    state: ProcessState,
    // 没有特权位！没有 RS 相关字段！
}

// RS：独立的重启服务
pub struct ReincarnationService {
    watched_processes: HashMap<Endpoint, ProcessWatch>,
    privilege_table: HashMap<Endpoint, Privilege>,
}

impl ReincarnationService {
    // RS 自己监听进程事件，不侵入 PM
    fn on_process_exit(&mut self, event: ProcessExitEvent) {
        if let Some(watch) = self.watched_processes.get(&event.endpoint) {
            self.restart_process(watch);
        }
    }
}
```

### 4.2 关键改进

| 方面 | 当前 | 改进后 |
|------|------|--------|
| **耦合方式** | PM 主动调用 RS/内核特权接口 | RS 监听事件，被动响应 |
| **数据结构** | 特权字段散布在各结构体 | 特权信息集中在 RS 管理 |
| **可见性** | 每个 Server 都知道 RS | Server 不知道 RS 存在 |
| **容错机制** | 硬编码的特权位和重启逻辑 | 可插拔的重启策略 |

### 4.3 实现路径

1. **事件总线**：引入进程生命周期事件，RS 订阅而非被调用
2. **特权隔离**：将特权信息从 `mproc`/`vmproc` 移到 RS 的独立表中
3. **内核解耦**：内核只提供基础端点，特权控制由 RS 通过标准 IPC 完成

## 6. 总结

> **"不美"的感觉 = 理想主义被现实妥协强行摩擦产生的火花**

RS 的跨层污染是 Minix3 为了容错能力而做出的架构妥协。当前阶段需要：

1. **忍辱负重**：完整记录现有实现
2. **标记路标**：在文档中标注重构候选点
3. **保持审美**：清楚知道什么是美的，什么是为了兼容性而保留的丑

未来的重新设计应该让 RS 成为一个真正的**独立服务**，而不是一个**侵入式的架构元素**。
