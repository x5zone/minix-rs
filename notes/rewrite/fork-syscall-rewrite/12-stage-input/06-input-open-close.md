## 1. 概念：开门三问与关门打扫

### 1.1 打开设备时，服务依次问三个问题

用户进程想读键盘，先要打开设备节点（比如 `/dev/kbd0`）。打开请求经过前台门卫（第 02 篇：重起后没开过的窗，非开门信一律丢掉）到达打开处理函数，函数按固定顺序问三个问题，任一答案不对就拒绝，连后面的问题都不问：

```
问题一  有这个门牌号吗？（换算查得到槽位吗？）
         |-- 查不到 → “查无此设备”（通信错误号 ENXIO）
         v
问题二  这扇窗营业吗？（有驱动在背后，或者是多路器？）
         |-- 不营业 → “查无此设备”（同一个错误号，故意的：不告诉调用者
         |   是“没这个门”还是“门后没人”，见 1.2 节）
         v
问题三  里面已经有人了吗？（槽位被占了吗？）
         |-- 有人 → “正忙”（EBUSY）
         v
       三个都通过 → 记下“有人了”，回答“好”
```

三个问题的顺序是承诺：调用者收到"查无此设备"时，知道问题出在前两个之一，绝不会是"里面有人"。顺序即接口，改顺序就是改接口。

### 1.2 为什么两种失败共用一个错误号

问题一和问题二失败时，服务回答同一个错误号。这不是偷懒，是刻意的信息隐藏：调用者不需要区分"门牌号写错了"和"驱动还没来"——两种情况的正确反应一模一样（等驱动来了重试，或者检查设备名）。区分它们只会诱惑调用者写两套重试逻辑，而两套逻辑的行为完全相同。Rust 一侧用两个枚举变体（`UnknownMinor` 与 `DeviceNotActive`）记住内部原因、用同一个错误号对外回答——对内精确，对外克制（第 03 篇 3.4 节的"两种原因一个号码"，此处是它的第一次实际使用）。

### 1.3 一间房只接待一位客人：独占打开

问题三确立的政策是独占：一个设备同时只服务一个打开者。第二个打开者收到"正忙"，而不是排队。为什么不定成共享？因为输入是"消耗性"资源——按键读出来就没了，两个读者抢同一队列，事件会被随机分给两人，谁都读不全。与其让两个读者读到残缺的流，不如让第二个直接知道"有人了，你去读多路器或者等"。多路器（"任意键盘"）的存在让独占政策不苛刻：读具体键盘被拒，读多路器通常能进（多路器永远营业，第 03 篇）。

### 1.4 关闭：打扫三间房，C 漏了两间

关闭的职责是"恢复到没人用过的样子"：记下"没人了"，清空队列（读位置和计数归零——不清的话，下次打开会读到上次的剩菜）。C 打扫了这三间（`opened`、`tail`、`count`），但漏了两间：挂起的读（`suspended` 一家）和记录的选择者（`selector`）。漏掉的后果是真实的：挂起的读带着上一位客人的联系方式留下来，下一位客人进门后读操作会被旧挂起挡住（读函数看到"已挂起"就拒绝，第 07 篇），而取消旧挂起需要旧客人的身份，新客人拿不出来——房间被上一位客人的幽灵永久占住。这不是理论推演：文件系统关闭字符设备时不先取消挂起的读（证据见 2.3 节），进程退出或另一线程关闭时，挂起的读就这样被留下来。本篇的 Rust 实现把漏的两间也打扫了（第 3 章），是全阶段第一个修正性偏离，值得读者停留。

### 1.5 本章小结：三问一扫，外加一次修正

读完本章，读者应该能不假思索地回答：打开三问是什么顺序、为什么前两个共用错误号、为什么独占；关闭打扫哪几间、C 漏了哪两间、漏掉的后果是什么、Rust 为什么多打扫。下一章（第 07 篇）讲房间里最重要的活动：读。

## 2. C 源码分析

> 本章逐段对照原始 C 代码。所有行号以工作区当前 `minix3/` 为准。

### 2.1 打开：三问三答（input_open，input.c:85-102）

```c
static int
input_open(devminor_t minor, int UNUSED(access), endpoint_t UNUSED(user_endpt))
{
        struct input_dev *input_dev;

        if ((input_dev = input_map(minor)) == NULL)
                return ENXIO;

        if (!input_dev_active(input_dev))
                return ENXIO;

        if (input_dev->opened)
                return EBUSY;

        input_dev->opened = TRUE;

        return OK;
}
```

注意两个"不用"的参数：访问方式和用户身份。打开时不看调用者想读还是想写（键盘反正只读），不看调用者是谁（独占政策下，谁第一个来谁得，不记名）。参数表里留着它们是因为前台统一传这些参数（第 02 篇搬运函数的约定），处理函数用 `UNUSED` 标记"我知道有，但我不需要"——标记本身就是文档：后人看到标记就知道"不是忘了用，是故意不用"。

三问的顺序在代码里是自上而下的三个 `if`，和 1.1 节的图逐行对应。成功路径只有两行：记下有人了，回答好。打开不碰队列、不碰灯、不碰挂起——开门只是登记，不动房间里的任何东西。

### 2.2 关闭：打扫三间，漏掉两间（input_close，input.c:107-125）

```c
static int
input_close(devminor_t minor)
{
        struct input_dev *input_dev;

        if ((input_dev = input_map(minor)) == NULL)
                return ENXIO;

        if (!input_dev->opened) {
                printf("INPUT: closing already-closed device %d\n", minor);
                return EINVAL;
        }

        input_dev->opened = FALSE;
        input_dev->tail = 0;
        input_dev->count = 0;

        return OK;
}
```

换算失败同样回答"查无此设备"（和打开一致：门牌错了永远是这个答案）。关闭没人持有的设备是"无效参数"，附带一行日志（日志是服务的自言自语：正常流程里不应该发生，发生了说明调用者（文件系统）的记账和服务对不上，值得留一句）。打扫三间：`opened` 复位、`tail` 与 `count` 清零——队列清空的理由见 1.4 节（不给下次留剩菜）。

漏掉的两间（`suspended` 一家四口与 `selector`）在代码里表现为"不存在"：函数体里根本没有它们。这种"缺席"需要证据链才能定性为 bug 而不是"故意"（2.3 节），否则就是过度解读。

### 2.3 定性为 bug 的证据链：关闭前没有取消

文件系统关闭字符设备的代码（`filedes.c:453`）只有一行：直接调关闭，吃掉错误。不存在"先取消挂起读再关闭"的步骤（取消函数 `cdev_cancel` 只在管道与工作线程场景被调用，`pipe.c:542` 与 `cdev.c:381` 定义处可查，与关闭路径无关）。于是以下场景真实可达：进程发起阻塞读（服务记下挂起），进程退出（文件系统直接关闭），挂起带着死者的联系方式留在槽位里。此后：新打开者读→因"已挂起"被拒；新打开者取消→身份对不上被忽略；事件到来→回答发给死者（异步发送失败，只记日志）。房间永久半死不活，直到驱动重起（断开连接会清理挂起，第 11 篇）或服务重起。三条证据（关闭不清、关闭前不取消、清理路径缺失）合在一起，"漏打扫"的定性才成立——单看关闭函数，只能说"没清"，不能说"错了"。这是本篇教给读者的第二个方法：bug 的定性需要跨文件的证据链，单函数视角下很多 bug 看起来像风格。

## 3. Rust 设计决策

> 本章解释"为什么这样设计"。每个决策先说备选方案，再说选择的理由。

### 3.1 判断与执行分开：decide 只看，apply 只改

每个处理函数拆成判断（`decide_*`，纯函数，只读状态）与执行（`apply_*`，只写状态）。理由：判断需要测试全部的分
支（打开三问有四条路：三拒一准），执行只有一条路；混在一起，测试执行时不得不顺带满足判断的前置条件（比如测"清空队列"必须先构造"已打开"），测试意图被前置条件淹没。分开后，判断的测试只摆状态不断言副作用，执行的测试只做动作不操心前置——测试意图一行就能看懂。更深层的理由在第 07 篇：读的判断与执行之间隔着一次跨进程内存拷贝（拷贝失败不能 advance），判断与执行天然不在同一时间发生，拆开是物理现实的要求，不是风格偏好。

备选方案是保留 C 的"判断执行一体"（一个函数又查又改）。拒绝的理由：一体函数在拷贝失败时需要"回滚改过的状态"，回滚逻辑是新的 bug 温床；拆开后，执行只在 transport 成功后调用，不需要回滚。

### 3.2 关闭多打扫两间：全阶段第一个修正性偏离

`apply_close` 在 C 的三间之外，多清挂起一家与选择者。分类是修正性偏离（C 有 bug，Rust 改），三处标注齐全：代码注释里的 `MINIX3 BUG`（含源码位置、触发场景、修复内容）、本文档 2.3 节的证据链、差异表本节。偏离的安全性论证：正常流程（关闭时无挂起）下，多清的是本来就空的东西，线缆行为与 C 逐字节相同；只有 C 出错的场景下行为不同，而那个场景下 C 的行为是"房间半死不活"，任何把房间打扫干净的行为都比它好。测试 `test_close_clears_parked_reader_and_selector` 直接构造"带挂起带选择者的关闭"，断言两者皆空——回归测试锁死修正，C 的旧行为回不来。

备选方案是忠实复刻（只清三间）。拒绝的理由：复刻一个已证伪的行为不是"保真"，是"保 bug"；且触发场景（进程退出时有挂起读）是常规操作，不是边角——退出时阻塞在读键盘上的进程随时可能被杀。

### 3.3 取消只清标志：与关闭修正的刻意不对称

`apply_cancel` 只清 `suspended` 标志，不碰联系方式——和关闭的多打扫形成不对称。理由：取消之后，联系方式字段不可达（所有使用处都先查标志，标志已倒），下次挂起会整体覆盖；关闭之后，标志本身（`suspended`）可达（下次打开的读会查它），不清就中毒。不对称的背后是对称的原则：清不清，看的是"下次使用者能不能到达"，不是"字段脏不脏"。代码注释把这条原则写明，读者看到两处不同的清理力度时，能找到同一把尺子。

### 3.4 错误变体复用既有词汇，不新增

打开关闭用到的三个错误（查无门牌、门后没人、正忙、关没人持有的）全部命中 `error.rs` 既有变体（`UnknownMinor`、`DeviceNotActive`、`DeviceBusy`、`NotOpened`），本篇零新增。值得记录的原因：第 03 篇设计错误词汇时"超前"声明了当时用不上的变体，本篇是第一次兑现——超前声明的合法性由兑现证明，兑现时不需要改错误模块一行。这种"先声明后兑现"的节奏是阶段内协作的常态，读者在后续篇章会反复看到。

## 4. 实现详解

> 完整代码在 `os/servers/input/src/handlers.rs`（打开关闭两节）。本章按"打开、关闭"的顺序展开，每个小节标注对应的第 3 章决策。

### 4.1 打开：`decide_open` 与 `apply_open`（对应决策 3.1）

```rust
pub fn decide_open(device: &InputDevice) -> Result<(), InputError> {
    if !device.is_active() { return Err(InputError::DeviceNotActive); }
    if device.opened { return Err(InputError::DeviceBusy); }
    Ok(())
}

pub fn apply_open(device: &mut InputDevice) {
    device.opened = true;
}
```

判断按 C 顺序先活跃后独占（换算查不到是调用者的事，返回 `UnknownMinor`，不在这两个函数里——换算在分发层，第 03 篇的 `map_minor_to_index`）。注意 `decide_open` 不是 `const fn`：它调用的 `is_active` 含端点比较，非常量——诚实地用普通函数，不为了 `const` 而重写判断（第 03 篇的 `is_active` 归第 03 篇所有，本篇只调用）。

### 4.2 关闭：`decide_close` 与 `apply_close`（对应决策 3.1、3.2、3.3）

判断只有一条（没人持有就拒），执行打扫七项（`opened`、`tail`、`count` 加挂起一家四口加选择者）。C 的关闭日志行（"正在关没人持有的设备"）归传输层——`decide_close` 返回错误，分发层记日志再回答，判断函数不碰日志（判断是纯函数，纯函数不写日志）。

### 4.3 与 C 的差异说明

| C 行为 | Rust 对应 | 差异分类 |
|--------|----------|---------|
| 打开三问顺序与错误号 | 同序同号 | 无差异 |
| 关闭三间打扫 | 七项打扫 | 修正性偏离（MINIX3 BUG，见 2.3/3.2 节） |
| 关闭日志行 | 归传输层（判断只返错） | 设计决策：判断执行分离的自然结果 |
| 其余 | 逐项对应 | 无差异 |

## 6. 过渡：门开了，开始读书

本篇结束时，设备能打开能关闭，关闭的幽灵也被超度了。但打开之后最重要的事还没讲：读。读是输入服务最复杂的动作——它有三种回答（给、等、不给），"等"背后是一整套挂起与唤醒机制，"给"背后是环形缓冲的几何。下一篇（第 07 篇）讲读：调用者说"我要 N 个事件"之后，服务如何决定给几个、什么时候给、给不了时怎么优雅地等。
