## 1. 概念：输入服务是整个系统的"事件汇"

### 1.1 它解决什么矛盾

键盘和鼠标是全系统最"吵"的设备：任何一个进程都可能想听，但硬件中断只有一次。如果把"谁来听"的决定交给每个驱动或每个读者，就会出现三个没人想看到的结果——两个读者抢同一个键、没有读者时按键丢失、驱动为了路由逻辑互相耦合。输入服务给出的答案是把矛盾收拢到一处：**驱动只管把事件报上来，服务决定事件去向谁**；读者拿到的永远是同一种语言（20 字节的事件格式，第 04 篇），不问事件来自哪块硬件。

这个角色有一个准确的比喻：输入服务是一间**传达室**。快递员（设备驱动，比如 pckbd）把包裹送进传达室，登记在册；收件人（打开 `/dev/mouse0` 的进程）来取自己的包裹；收件人不在家的包裹，按规矩转交一个默认代理人（终端驱动，键盘事件最终变成控制台上的字符）。传达室还代管一件小事——键盘上三个指示灯的状态它记得住，换一个快递员来（驱动重启），灯该什么样还是什么样。

### 1.2 它不是什么：三条边界

第一，它**不碰硬件**。中断、端口、扫描码都是驱动的世界（pckbd 属驱动阶段，第 14 篇只讲契约面）；输入服务收到的已经是翻译成统一语言的事件。第二，它**不解释按键含义**。"0x2C 是空格"这样的翻译发生在终端驱动的键盘映射里（第 13 篇契约面）；服务只做路由、缓冲与唤醒，不认字。第三，它**不服务块状数据**——它是字符设备框架上的一个普通字符驱动（第 02 篇），与磁盘、网络无涉。

### 1.3 启动主线：一个进程怎么跑起来

输入服务不在内核启动镜像里，由重启动服务（RS）按配置加载（`system.conf:400-403` 的 `service input` 条目）。启动之后的执行链是严格线性的，这条链就是本套文档的目录结构：

```text
RS 运行时加载 input（不在 boot 镜像，RS 加载组）
  ▼  main（input.c:696-704；Rust: main.rs，第 01 篇）
  ├─ 登记首次启动回调、执行四步初始化                ← 第 01 篇（init.rs 的 init_plan）
  │    清十槽位表 → 订阅驱动到来事件 → 向文件系统宣告 → 向终端握手
  ▼  进入字符驱动框架主循环（chardriver_task；Rust: dispatcher.rs 的判决 + 传输层执行）
       ├─ 字符设备请求（开/关/读/控/取消/查询）        ← 第 06、07、08 篇
       ├─ 驱动上报事件（INPUT_EVENT）                  ← 第 09 篇
       ├─ 终端灯令（INPUT_SETLEDS，仅终端来源）        ← 第 10 篇
       └─ 数据存储通知（驱动来了/走了）                ← 第 11 篇
```

主循环分两半：**裁决的一半**（一次到达进来，状态变化与效应清单出去）已在本阶段 Rust 代码中就位（`dispatcher.rs`，第 01 篇 4.5 节）；**机械的一半**（收信、发信、授权拷贝）是传输层，按跨阶段清单 E-INWIRE 落地——在此之前服务进程诚实停车，不假装能收信（`main.rs` 的空转注释）。

### 1.4 次主线一：一次事件的旅程

驱动上报一次按键，事件走这样一条路（第 09 篇是主线，这里只给全景）：

```text
pckbd 中断 → 扫描码翻译成事件（页/码/值）→ 驱动经客户端库发 INPUT_EVENT
  ▼  服务校验：槽位号合法？发送方是这槽的主人？（input.c:383-390）
  ├─ 目标设备被打开 → 入队（满了挤掉最旧的，input.c:338-346）
  │     → 叫醒挂起的读者（恰好给一个事件，input.c:361-364）
  │     → 或通知在查询的进程"有货了"（input.c:366-369）
  ├─ 目标没开但总机（键盘mux/鼠标mux）开着 → 进总机队列（input.c:404-407）
  └─ 谁都没开 → 原样转交终端驱动（TTY_INPUT_EVENT，input.c:408-421，第 13 篇）
```

### 1.5 次主线二：驱动的一生，与灯的记忆

驱动的一生是另一条线（第 11、12 篇）：驱动启动后在数据存储里发布一条"我来了"（键名 `drv.inp.<label>`，值是要键盘还是要鼠标，`inputdriver.c:23-34`）；服务收到通知，核对 label，分给它槽位号并回发配置（`input.c:475-528`）；之后事件流淌；驱动死了，存储里的键消失，服务发现后把该槽挂起的读者以"输入输出错误"叫醒（`input.c:533-553`）。灯是跨这条生命线的记忆：终端要求点灯，服务把掩码记在槽位上再发给驱动（`input.c:227-234`）；驱动换了一代，新驱动一连接，服务立刻把记住的灯态补发一遍（`input.c:525-527`，第 10 篇）。

## 3. 设计原则（全阶段通用，各篇引用不重复论证）

1. **判决皆纯函数，出口皆数据**。每个判决（路由、门卫、回信、叫醒、广播）是只读输入的纯函数；对外的动作收拢成效应清单（第 02 篇 4.5 节），传输层照单执行。测试因此不需要传输在场——86 个单元测试全部这样跑（2026-09-15 实测）。
2. **复制 C 的顺序纪律，升级为类型纪律**。C 靠"程序员记住先后"保证正确的地方（拷贝失败不推进、先救挂起读者），Rust 用只读规划加按值提交、用枚举变体顺序来表达，让调换顺序变成编译错误或 review 可见的结构变化。
3. **C 崩溃处，Rust 显式报错**。四处"不可能路径"的崩溃（反向映射坏下标、存货不足、违规赊账、登记簿满）全部改为显式错误返回，调试与发布构建行为一致（架构演进 A-7/A-11，各篇分别标注）。
4. **诚实占位**。传输未落地就是空转停车加注释指路（edge 清单 E-INWIRE），不用看似能跑的代码掩盖。
