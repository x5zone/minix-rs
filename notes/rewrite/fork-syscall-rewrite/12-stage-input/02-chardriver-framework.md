## 1. 概念：为什么十几个驱动共用同一个"前台"

想象一家有十几个窗口的办事大厅。每个窗口办不同的业务（键盘、鼠标、终端、打印机……），但大厅的前台是同一个：取号、叫号、告诉你"这个窗口今天没开"、把办了一半需要等的业务先挂起来——这些事每个窗口都一样，没必要每个窗口摆一个前台。字符驱动框架就是这个前台：它是 Minix3 源码树里一个独立的库（`libchardriver`，字符驱动的"字符"指"按字节流读写"的设备，区别于按块读写的磁盘），输入服务、终端驱动和十几个硬件驱动都调用它的主循环，把自家业务登记成一张回调表就行了（第 01 篇的 `input_tab` 就是这样一张表）。

### 1.1 前台只做三件事，多一件都不做

前台收到每一封信之后，按固定顺序做三个判断。记住这三个判断，就记住了本章的全部内容：

```
第 1 问  这封信是什么性质？（分类）
         |-- 通知类（有人敲门，不是来送信的）：按送信人分三路，答复一律没有
         |-- 块设备开门信（送错了大厅）：直接退回“查无此设备”，不打扰窗口
         |-- 字符设备请求信：进入第 2 问
         |-- 其他信：转交窗口的“其他信箱”，前台不再管
           |
第 2 问  这扇窗今天开过门吗？（重起门卫）
         |-- 开过：进入第 3 问
         |-- 没开过，但是来开门的信：记下“这扇窗开了”，进入第 3 问
         |-- 没开过，又不是来开门的：悄悄丢掉，不回信、不告诉窗口
           |
第 3 问  窗口的答复要不要现在寄出？（回信纪律）
         |-- 普通答复：按信的种类装好信封寄出
         |-- “先别回，我稍后自己答”：只允许读、写、控制、取消四种信；
         |   开门、关门、查询三种信不许赊账
         |-- “我重起过，之前的客人请另想办法”：一律不回
```

三个判断互相独立：分类只看信封，门卫只看登记簿，回信纪律只看窗口的答复和信的种类。这种独立性是本章 Rust 设计的直接依据（第 3 章）。

### 1.2 门卫的存在理由：崩溃会留下"上一代"的客人

门卫（第 2 问）是三个判断里最需要解释的一个。正常情况下，每个设备第一次被使用前一定会先收到开门信，门卫的登记簿和现实永远一致，门卫形同虚设。门卫真正工作的是服务崩溃重起之后：调用者手里还拿着崩溃前拿到的请求编号，服务却已经失忆（第 01 篇解释过，输入服务重起后忘记一切）。如果没有门卫，重起后的服务会拿着上一代的编号去回答这一代的客人——答非所问，还可能把数据送错地方。门卫的做法简单粗暴：重起时烧掉登记簿（宣告时清空，见 2.5 节），重起后没开过门的设备一律假设"来信的都是上一代的幽灵"，只放行开门信。幽灵信被丢掉后，调用者会超时重试，重试时先开门，一切恢复正常。

### 1.3 回信纪律的存在理由："稍后再答"是挂起读的基石

第 3 问里的"先别回"值得单独解释。读键盘是一个"等"的动作：进程想读按键，但用户还没按键，服务不能干等（干等会卡住整个服务进程，后面的消息都处理不了），也不能直接回答"没有"（那样进程就得不停地问，空转浪费处理器）。正确的做法是：服务记下"谁在等、等到的数据送到哪里"，然后告诉前台"这封信先别回"。前台在登记簿上记一笔，等按键真的到了，服务再通过另一条秘密通道把答案寄出（第 07 篇讲这条通道）。"先别回"这个赊账许可，就是挂起读机制的法律基础——没有它，输入服务不可能同时服务"正在等的读者"和"源源不断的新消息"。

### 1.4 信封的格式：请求七种，回信三种

调用者和驱动之间用固定格式的信封通信，格式定义在源文件开头的注释里（`chardriver.c:1-44`， Programmer's manual 式的表格，本章 2.1 节逐行解读）。请求信有七种（开门、关门、读、写、控制、取消、查询），回信有三种（普通回信、查询的当场回信、查询的事后通知）。信封上关键的几个栏位：次设备号（找哪扇窗）、内存授权（数据送到调用者的哪块内存）、请求编号（调用者同时办多件事时靠它认领回信）。

### 1.5 本章小结：前台是所有字符驱动的共同契约

读完本章，读者应该能不假思索地回答：前台收到信后做哪三个判断；门卫烧掉登记簿的时机和理由；哪四种信允许赊账、哪三种不允许；请求七种回信三种各自的编号。下一章（第 03 篇）解释窗口背后的房间结构——十个设备槽位和两种编号；第 06 至第 08 篇解释七个处理函数各自认领信之后做什么。

## 2. C 源码分析

> 本章逐段对照原始 C 代码。行号以工作区当前 `minix3/` 为准。框架源码 600 行全部在本篇语义范围内（输入服务使用面），无裁剪死角，2.8 节有逐项核对表。

### 2.1 信封格式：源文件头注释就是协议说明书（chardriver.c:1-44）

源文件开头44行的注释是整个字符驱动协议最权威的说明书，建议读者先读注释再读代码。注释定义了两张表。

请求表（注释第 7-22 行）：每一行是一种请求，列是信封栏位。开门信带次设备号、访问方式、用户身份；关门信只带次设备号；读写信带次设备号、内存授权、字节数、标志、位置、编号；控制信带次设备号、授权、用户、标志、编号、控制码；取消信带次设备号和编号；查询信带次设备号和操作掩码。记住"读写信的栏位最多"——读写是唯一搬运数据的请求（第 07 篇）。

回信表（注释第 26-33 行）：普通回信带状态和编号；查询的当场回信带次设备号和状态；查询的事后通知带次设备号和状态。注意普通回信用编号认领（因为读写控制取消都可能同时办多件），查询回信用次设备号认领（因为查询从不赊账，当场问当场答，不会认错）。

### 2.2 消息编号：七个请求，三个回答（com.h:915-937）

```c
#define CDEV_RQ_BASE    0x400
#define CDEV_RS_BASE    0x480
#define CDEV_OPEN     (CDEV_RQ_BASE + 0)   /* 0x400 */
#define CDEV_CLOSE    (CDEV_RQ_BASE + 1)   /* 0x401 */
#define CDEV_READ     (CDEV_RQ_BASE + 2)   /* 0x402 */
#define CDEV_WRITE    (CDEV_RQ_BASE + 3)   /* 0x403 */
#define CDEV_IOCTL    (CDEV_RQ_BASE + 4)   /* 0x404 */
#define CDEV_CANCEL   (CDEV_RQ_BASE + 5)   /* 0x405 */
#define CDEV_SELECT   (CDEV_RQ_BASE + 6)   /* 0x406 */
#define CDEV_REPLY      (CDEV_RS_BASE + 0) /* 0x480 */
#define CDEV_SEL1_REPLY (CDEV_RS_BASE + 1) /* 0x481 */
#define CDEV_SEL2_REPLY (CDEV_RS_BASE + 2) /* 0x482 */
```

请求和回答各占一个以 `0x00` 结尾的基址，请求是否属于字符设备用掩码判断：`IS_CDEV_RQ(type)`（`com.h:922`）把类型号的低 7 位抹掉后看等不等于 `0x400`。这种"基址加偏移"的编号方式意味着：看到 `0x402` 就知道是"字符设备请求组第 2 号"，不需要查表。Rust 版本把这组编号逐字搬运（`framework.rs` 的 `CharacterRequest`），测试把每个数值锁死。

同一区域还定义了栏位里出现的标志位（`com.h:939-957`）：打开时的读写许可能力位（`CDEV_R_BIT`/`CDEV_W_BIT`/`CDEV_NOCTTY`），传输标志（`CDEV_NOFLAGS`/`CDEV_NONBLOCK` 不许赊账位），查询的操作掩码（读`CDEV_OP_RD`、写`CDEV_OP_WR`、错`CDEV_OP_ERR`、事后通知`CDEV_NOTIFY`），以及打开回答里的克隆和控制终端标志（`CDEV_CLONED`/`CDEV_CTTY`）。这些标志的消费者是各处理函数（第 06 至第 08 篇），本章只登记它们的存在和数值。

### 2.3 主循环：等信、分发、回信，永不停（chardriver_task，chardriver.c:549-570）

```c
void chardriver_task(const struct chardriver *cdp)
{
        int r, ipc_status;
        message mess;

        running = TRUE;
        while (running) {
                if ((r = sef_receive_status(ANY, &mess, &ipc_status)) != OK) {
                        if (r == EINTR && !running)
                                break;
                        panic("chardriver: sef_receive_status failed: %d", r);
                }
                chardriver_process(cdp, &mess, &ipc_status);
        }
}
```

主循环是全框架最短的核心：标记运行中，然后永远循环"收一封信、处理一封信"。收信时愿意收任何人的信（`ANY`），并且要求传输层告诉自己"这封是通知还是普通消息"（`ipc_status` 参数，第 2.4 节用它）。唯一的退出路径是`running` 被清掉之后又恰好被信号打断——对应 `chardriver_terminate`（`chardriver.c:537-544`，把 `running` 置否并取消阻塞中的收信）。收信本身失败只有两种下场：是退出信号就 break，否则整个驱动崩溃（收不到信的服务没有任何存在价值，和第 01 篇订阅失败就崩溃是同一个逻辑）。

### 2.4 分发：先看性质，再看门卫，最后看窗口（chardriver_process，chardriver.c:455-532）

分发函数是本章最长的函数，按 1.1 节的三问严格分段：

**第 1 问：通知优先（第 464-482 行）。** 先看是不是通知（`is_ipc_notify`）。通知和普通信的最大区别：通知永远不回信。通知再按送信人分三路：硬件中断送信人（`HARDWARE`）走中断钩子，时钟送信人（`CLOCK`）走闹钟钩子，其他所有人走"其他信箱"。输入服务的中断和闹钟钩子都是空的（第 01 篇 2.3 节），所以输入服务实际只收到第三路——数据存储服务用通知告诉它"有个驱动来了/走了"（第 11 篇）。

**送错大厅的信（第 488-492 行）。** 块设备的开门信（`BDEV_OPEN`，`0x500`）如果送到字符驱动这里，框架自己回答"查无此设备"，不打扰窗口。注释解释了理由：如果不回答，调用者会永远卡在等待回信上——一个进程因为打开了一个不存在的设备节点就永远卡死，是不可接受的。这条分支是框架层面"宁可报错也不沉默"原则的体现。

**第 2 问：门卫（第 494-514 行）。** 字符设备请求先提取次设备号（提取失败直接返回，连门卫都不经过——信封上连窗号都写错了的信，前台直接扔掉，见 `chardriver_get_minor`，2.7 节）。然后查登记簿：没登记过的窗，非开门信一律悄悄丢掉（不回信、不告诉窗口），开门信先登记再放行。这里的"悄悄"很重要：丢掉幽灵信时不回错误，因为回错误也送不到正确的客人手里（客人已经是上一代了），沉默是最安全的。

**第 3 问的前半：分派到窗口（第 517-529 行）。** 七种请求各进各的窗口（`do_open` 到 `do_select` 六个搬运函数，2.6 节），七种之外的类型号进"其他信箱"，分派完直接返回（"其他信箱"和通知一样，前台不回信，回信是窗口自己的事——输入服务的"其他信箱"就是第 09、第 10、第 11 篇的事件、灯光、驱动生命线）。

### 2.5 回信纪律：三种下场，一种 crash（chardriver_reply，chardriver.c:195-274）

窗口的答复送到回信函数，这里决定答复的下场：

**下场一：赊账（第 203-223 行）。** 答复是"先别回"（`EDONTREPLY` 伪码，`sys/errno.h:199`）时，只允许读、写、控制、取消四种信。注意代码里有意思的细节：读、写、控制三个分支没有任何语句，直接掉进取消分支一起返回——注释写明这是故意的（fall-through）。而开门、关门、查询三种信赊账会触发崩溃（`panic`）：这三种信没有"稍后回答"的通道，赊了就永远还不上，还不如当场崩溃让问题暴露。

> 符号约定：`errno.h` 里赊账码写作 `_SIGN 203`，其中的符号前缀在系统组件编译时是负号、用户侧编译时是空（`sys/errno.h:188-193`），即系统侧看到 -203、用户侧看到 203。Rust 一侧统一用 `minix-types` 的用户态正数（203），与重起服务等其他服务一致；比较的是数值含义而非符号形式。

**一个诚实的 FIXME（第 208-216 行）。** 代码里有一段被 `#if 0` 关掉的检查：本想验证"非阻塞的读写不许赊账"（调用者说了不等，服务还赊账就自相矛盾），但注释承认现实中好几个驱动没写对——有的根本不走这条回信路径（比如终端），有的非阻塞实现是错的（比如音频）。于是检查被关掉，留下一句 FIXME。这个细节值得读者记住：框架的正确性有时要向现实中写得马虎的驱动让步，"理论上应该"和"实际上做得到"是两回事。第 06 至第 08 篇实现处理函数时必须记得这条让步：框架不会替处理函数检查非阻塞赊账，每个处理函数要自己守住这条线。

**下场二：重起沉默（第 232-233 行）。** 答复是"我重起过"（`ERESTART`）时，一律不回信。注释解释：唯一的调用者是虚拟文件系统，而它还没准备好处理"服务重起"这种错误——回一个对方处理不了的错误，不如沉默，让对方通过别的渠道（超时、重连）自己发现。

**下场三：正常寄出（第 235-273 行）。** 按信的种类装信封：开门关门的回信带状态和编号，读写控制的回信带状态和编号，取消的回信带状态和编号（注意是取消信自己的编号，取消信是替原来那封信要说法的），查询的当场回信带状态和次设备号。装好后按送信方式寄出（`send_reply`，2.6 节末尾）：如果是请求回答式的交互就尝试非阻塞直送，否则走异步通道，寄不出去只记日志不崩溃（信寄丢了调用者会超时，这是调用者的恢复责任，不是前台的）。

### 2.6 六个搬运函数：窗口的迎宾员（do_open 到 do_select，chardriver.c:279-433）

每个搬运函数做同样的三件事：钩子没登记就按默认回答（开门关门默认"好"，读写的默认回答是"输入输出错误"，控制的默认回答是"不懂这个控制"，取消的默认回答是"先别回"即让原来的请求继续，查询的默认回答是"坏文件描述符"）；钩子登记了就从信封里拆出参数、调用钩子、原样返回钩子的答复。输入服务的七个钩子全登记了（第 01 篇），所以这些默认回答输入服务一个都用不上——但它们是框架契约的一部分：将来某个驱动只登记部分钩子时，默认行为就是它的行为。本篇登记它们的存在，各处理函数的行为在第 06 至第 08 篇。

开门搬运有个额外动作（第 297-302 行）：如果钩子的回答里带了"克隆"标志，说明窗口把客人领到了另一扇窗（伪终端类设备会这样），前台把新窗号也登记到门卫簿上。输入服务从不克隆（它的打开回答只有成功和错误码，第 06 篇），这条分支对输入服务永远走不到，但它是理解门卫簿"登记的不一定是开门信上的窗号"的关键。

### 2.7 次设备号提取：信封阅读器（chardriver_get_minor，chardriver.c:575-598）

按信的种类从正确的栏位读窗号：开门关门读开门关门栏，取消读取消栏，查询读查询栏，读写控制读读写栏，其他类型号返回"无效参数"。两个断言（消息指针和输出指针非空）是防御性编程：这个函数被分发路径信任，信任但验证。

### 2.8 宣告：重起的三件事（chardriver_announce，chardriver.c:99-124）

宣告函数在第 01 篇已经露过面（`input_init` 第 3 步调用它），这里看它的三件事：请内核放行卡在上一代服务上的调用者（`sys_statectl`，失败则崩溃——连"松开旧客人"都做不到的服务没法干活）；查出自己的名字并发布"某某字符驱动起来了"的标记（发布失败同样崩溃）；清空门卫登记簿（1.2 节的烧簿动作）。前两个失败崩溃、第三个不可能失败——和第 01 篇的失败哲学完全一致。

## 3. Rust 设计决策

> 本章解释"为什么这样设计"。每个决策先说备选方案，再说选择的理由。

### 3.1 三个判断写成三个纯函数，而不是一个分发大函数

C 的 `chardriver_process` 是一个 78 行的函数，三个判断（分类、门卫、分派加回信）按顺序写在一起，中间共享局部变量。直译成 Rust 会得到一个同样 78 行的函数——能用，但三个判断的边界藏在语句顺序里，测试想单独验证"门卫认不认识这扇窗"时，必须先伪造一封完整的信。Rust 版本把三个判断拆成三个纯函数：`classify_request`（只看类型号和通知位）、`gate_character_request`（只看请求种类和登记簿）、`decide_reply`（只看请求种类和答复值）。每个函数只读输入、不碰全局状态、不发消息，测试用几个整数就能覆盖全部的分
支（`framework.rs` 的分类测试、门卫测试、回信测试）。

备选方案是保留一个 `process` 大函数。拒绝的理由：大函数需要伪造完整的消息结构体才能测试，而消息结构体的完整定义属于第 05 篇（协议面）——本篇如果为了测试去构造完整消息，就提前拥有了不属于自己的知识。拆成纯函数之后，本篇的测试只用整数（类型号、状态码），消息结构体的知识完整地留在第 05 篇。

### 3.2 七种请求写成带数值的枚举，而不是整数比较

C 用整数比较判断信的种类（`switch (m_ptr->m_type)` 配 `case CDEV_OPEN`）。Rust 版本用带显式数值的枚举（`CharacterRequest::Open = 0x400` 等）。枚举的好处在第 01 篇 3.2 节已经论证过（编译器检查穷举），这里补充数值的作用：`as i32` 得到的值就是信封上的类型号，测试把七个值逐个锁死（`framework.rs` 的 `test_message_numbers_match_c`）。将来传输层把类型号变成枚举只需要改一处转换函数，所有使用方自动跟上——而整数比较的写法会在每个 `switch` 里重复"这个数是什么意思"的知识。

### 3.3 门卫登记簿用定长数组加线性查找，不用哈希表

C 的登记簿是 256 个元素的数组加线性查找。Rust 版本原样保留（`OpenDeviceSet`：`[i32; 256]` 加长度）。有人可能觉得 2026 年了应该用哈希集合，但三条理由支持保留数组：第一，256 个整数的线性查找在现代处理器上是几次缓存行访问，比哈希计算加随机内存访问更快；第二，哈希表需要哈希算法和内存分配器，`no_std` 环境下每个依赖都要审查，数组零依赖；第三，也是最重要的，登记簿的内容必须在重起时整体清空，数组清空是一个长度置零，哈希表清空涉及逐个释放——简单的结构有简单的清空语义，而"重起时一定能清空"是门卫正确性的前提（1.2 节）。

唯一的诚实改动是溢出处理：C 在 256 个槽位用完时崩溃（`panic("out of slots")`），Rust 的 `record` 返回布尔值表示"记下了/没记下"。崩溃和返回错误的 wire 行为有差异吗？没有——C 崩溃后重起服务会重新拉起服务，效果等价于"这次没服务成"；Rust 返回错误让调用方（将来的打开路径）回答调用者一个错误码，效果同样是"这次没服务成"，但少一次进程崩溃。差异分类是架构演进（崩溃改显式错误），wire 可观察行为一致，测试覆盖两种结果。

### 3.4 赊账许可写成请求的方法，而不是回信函数的分支

C 在回信函数里用 `switch` 判断"这种信让不让赊账"。Rust 版本把"让不让赊账"写成请求的方法（`CharacterRequest::may_park`），回信纪律函数（`decide_reply`）只问方法要答案。这个拆分的理由是知识归属：赊不赊账是请求种类的内在属性（读天生能等，开门天生不能等），应该跟请求定义住在一起，而不是散落在回信逻辑里。`decide_reply` 因此只有三行判断：赊账 sentinel 加允许赊账就是挂起，赊账 sentinel 加不允许就是违规，重起 sentinel 就是沉默，其他一律寄出。读者读 `decide_reply` 时不需要记住七种请求各自的性质——那是 `may_park` 的事。

### 3.5 违规赊账命名而不崩溃，但保持 wire 沉默

C 对"开门信赊账"的回答是崩溃。Rust 版本定义 `ReplyDecision::InvalidParking` 这个变体，让主循环（传输落地时）记日志并回答调用者一个错误，而不是让整个服务进程陪葬。wire 行为有差异吗？C 崩溃后调用者超时重试，Rust 回答错误后调用者立刻知道错了——调用者看到的都是"这次没办成"，且 Rust 版本让调用者知道得更快。这是一个有意的架构演进：框架的 bug（窗口不该赊而赊）不应该用整个服务的命来偿，记日志足够让开发者发现，调用者不应该为框架的 bug 等一次超时。测试把"开门关门查询赊账得违规"锁死，保证这条纪律永远不会被悄悄放宽。

## 4. 实现详解

> 完整代码在 `os/servers/input/src/framework.rs`。本章按"判断一、判断二、判断三、数据结构"的顺序展开，每个小节标注对应的第 3 章决策。

### 4.1 判断一：分类（对应决策 3.1、3.2）

`CharacterRequest` 枚举七个变体各带信封上的数值，`from_message_type` 把整数翻译成枚举（不是字符请求就是 `None`）。`Incoming` 枚举表达分类结果的三种去向：进门卫的字符请求、框架代答的块开门、转交其他信箱的其他信。`classify_request` 是纯函数：通知直接返回 `None`（通知按送信人分类，不归这个函数管，见 2.4 节）。

```rust
pub const fn classify_request(message_type: i32, is_notify: bool) -> Option<Incoming>
```

`const fn` 意味着分类逻辑可以在编译期求值——分类规则是刻在契约里的，不是运行时算出来的。

### 4.2 判断二：门卫（对应决策 3.1、3.3）

`GateVerdict` 三个变体（放行、登记并放行、悄悄丢掉）对应 2.4 节门卫的三个分支。`gate_character_request` 是纯函数：登记了就放行，没登记且是开门就登记并放行，没登记又不是开门就丢掉。`OpenDeviceSet` 是登记簿：定长数组、长度、包含查询、记录、清空。记录满时的布尔返回值是 3.3 节的诚实改动。

### 4.3 判断三：回信纪律（对应决策 3.1、3.4、3.5）

`ReplyDecision` 四个变体（寄出、挂起、重起沉默、违规赊账）对应 2.5 节的三种下场加一种违规。`decide_reply` 先问赊账 sentinel（配 `may_park`），再问重起 sentinel，最后默认寄出——判断顺序和 C 的 `if` 链顺序一致，逐行可对照。

三个回信数据结构（`TaskAnswer`、`SelectAnswer`、`SelectNotification`）各带自己的消息类型方法：普通回信用请求编号认领（`0x480`），查询当场回信用次设备号认领（`0x481`），查询事后通知走异步通道（`0x482`）。为什么普通回信和查询回信的认领方式不同，2.1 节已经解释（赊不赊账决定会不会认错）。

### 4.4 宣告三效果（对应 2.8 节）

`AnnounceEffect` 三个变体按 C 的执行顺序排列，`announce_effects` 返回同样顺序的数组——和第 01 篇的 `init_plan` 是同一个设计手法（顺序写成数据，见第 01 篇 3.1 节）。第 01 篇的 `announce_effects_for_init` 函数把两处连起来，测试断言它们永远一致：一处改了顺序，另一处必须跟上。

### 4.5 与 C 的差异说明

| C 行为 | Rust 对应 | 差异分类 |
|--------|----------|---------|
| 登记簿满时崩溃（chardriver.c:90） | `record` 返回 `false`，调用方答错误 | 架构演进：崩溃改显式错误，wire 可观察行为一致（调用者都看到"没办成"） |
| 违规赊账时崩溃（chardriver.c:220-221） | `InvalidParking` 变体，主循环记日志并答错误 | 架构演进：见 3.5 节 |
| `#if 0` 关掉的非阻塞赊账检查 | 未实现（沿用 C 的关闭状态） | 无差异：C 关掉了，Rust 也不做；若将来打开，需同步更新本文档 |
| 其余分类、门卫、回信、宣告逻辑 | 逐分支对应 | 无差异 |
