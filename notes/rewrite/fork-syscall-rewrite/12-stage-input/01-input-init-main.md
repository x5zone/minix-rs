# 01-input-init-main: 启动入口与初始化序列

> **状态**: 已改写（2026-09-04，首版完整文档）

## 1. 概念：一个服务进程的诞生需要回答哪几个问题

想象一台刚加电的机器。内核先起来，然后有一个叫作重起服务的管理者负责把其余的系统服务一个个拉起来。输入服务就是被拉起来的其中之一。读者第一次接触这段代码时，最容易产生的误会是把它当成"键盘驱动"——它不是。键盘背后的硬件中断由另外的驱动进程处理（第 14 篇），输入服务只做三件事：向全系统宣告"我在这里"，向数据存储服务订阅"我关心的驱动什么时候到"，然后坐下来等消息。

### 1.1 输入服务不在启动镜像里，它是被运行时加载的

Minix3 把一小部分关键进程直接打进启动镜像，内核引导时就把它们摆好（这张表在 `minix3/minix/kernel/table.c`，可以用命令验证输入服务不在其中）：

```sh
rg -i "input" minix3/minix/kernel/table.c   # 无输出：启动镜像里没有输入服务
```

输入服务由重起服务在运行时加载，依据是系统配置文件中的服务声明（`minix3/etc/system.conf:400-403`）：

```
service input
{
        ipc             SYSTEM pm vfs rs ds tty vm;
        priority        1;
};
```

这两行声明了两件事。第一，输入服务允许和谁说话：内核体系调用、进程管理、虚拟文件系统、重起服务、数据存储服务、终端驱动、虚拟内存服务——注意键盘驱动不在名单里，输入服务从不直接接触硬件驱动进程，它只和数据存储服务谈"谁来了谁走了"（第 11 篇）。第二，它的调度优先级是 1，和终端驱动同级：按键从按下到回显的延迟，取决于这条链路上的每个进程都不被饿死。

### 1.2 启动框架只做一件事：把"第一次"和"以后每次"分开

系统事件框架（System Event Framework，简称 SEF，见 `minix3/minix/include/minix/sef.h:1` 的文件头注释）是所有系统服务共用的启动脚手架。它解决的问题很具体：同一个服务进程二进制文件，会在两种场合被运行——第一次诞生（fresh boot），以及崩溃后被重起服务重新拉起（restart）。两种场合需要的准备工作不一样：第一次要从零建表，重起时也许想保留状态。SEF 让服务在 `main` 里先登记"我是哪种场合该干什么"，再调用统一的启动入口，框架负责在正确的时机调用正确的回调。

输入服务的选择是全部场合中最简单的那一种：只登记第一次诞生的回调。重起之后，它心甘情愿地忘记一切——打开设备的进程会重新打开，驱动进程会重新宣告，挂起的读请求会收到错误（第 06、第 07、第 11 篇分别解释这三条恢复路径）。这个"忘记一切"的决定，是理解整个输入服务设计的关键：正因为重起不需要保留状态，设备表的初始化才可以是一个无条件的清零循环，不需要区分"新建"和"恢复"两条路。

### 1.3 启动完成之后，进程把自己交给主循环，永不返回

`main` 的最后一行调用字符驱动框架的主循环之后，`main` 函数在逻辑上就结束了——主循环不返回，进程余生都在"收消息、分发、回消息"里度过（第 02 篇）。所以启动代码和服务代码的边界非常干净：`main` 之前是"我是谁、我准备好了什么"，`main` 的最后一行之后是"我如何服务"。本篇只讲边界之前的事。

启动时序全图（箭头表示"完成后进入下一步"，缩进表示调用关系）：

```
重起服务按 system.conf 加载输入服务进程
  |
  v
main()（input.c:696-704）
  |-- input_startup()：登记“第一次诞生”回调，启动框架
  |     |
  |     v
  |   input_init()：四步初始化（见 1.4 节）
  |
  v
chardriver_task(&input_tab)：进入框架主循环，永不返回（第 02 篇）
```

### 1.4 四步初始化：先摆好桌子，再请客人

`input_init` 的四个步骤顺序不能乱，每一步都依赖前一步的结果：

```
第 1 步  清空十个设备槽位，逐个填回各自的次设备号
           |
           v
第 2 步  向数据存储服务订阅“输入驱动到了或者走了请告诉我”
           |
           v
第 3 步  向虚拟文件系统一侧宣告“我这个字符设备起来了”
           |
           v
第 4 步  给终端驱动发消息：“我起来了，你可以把灯的状态发给我了”
```

为什么必须是这个顺序？如果第 3 步跑到第 1 步前面，虚拟文件系统会立刻开始转发打开设备的请求，而设备表还是垃圾——请求会被送到未初始化的槽位。如果第 4 步跑到第 2 步前面，终端驱动收到"我起来了"之后可能立刻开始查询驱动状态，而订阅还没建好，查询结果会漏掉已经存在的驱动。顺序即正确性，这是启动代码最常见的形态。

### 1.5 本章小结：启动只回答三个问题

读完本章，读者应该能不假思索地回答：输入服务是谁拉起来的（重起服务按配置文件加载，启动镜像里没有它）；它诞生时按什么顺序准备（清表、订阅、宣告、握手）；准备好之后它去哪里了（交给框架主循环，永不返回）。下一章回答主循环收到消息之后如何分发，第三章解释设备表里每个槽位的结构。

## 2. C 源码分析

> 本章逐段对照原始 C 代码。所有行号以工作区当前 `minix3/` 为准，可用 `sed -n '起始,结束p' 文件` 独立验证。

### 2.1 进程入口：三行代码，两个动作（`main`，input.c:696-704）

```c
int
main(void)
{
        input_startup();

        chardriver_task(&input_tab);

        return 0;
}
```

`main` 只有两个动作：`input_startup()` 完成登记和初始化（2.2、2.3 节），`chardriver_task(&input_tab)` 进入主循环（第 02 篇）。`return 0` 永远执行不到——主循环不返回，它的存在只是让编译器相信 `main` 有返回值。这三行是全篇的锚点：之后几十节文档讲的每一个处理函数，都是主循环通过 `&input_tab` 这张表找到的。

### 2.2 登记启动回调：只登记"第一次"（`input_startup`，input.c:685-694）

```c
static void
input_startup(void)
{
        sef_setcb_init_fresh(input_init);

        sef_startup();
}
```

两行。第一行告诉启动框架："当确认这是第一次诞生时，请调用 `input_init`"（`sef_setcb_init_fresh` 的声明在 `sef.h:60`）。注意没有 `sef_setcb_init_restart` 之类的调用——对照 1.2 节的讨论，这是深思熟虑的省略，不是遗漏：重起后忘记一切，恢复路径由各个客户端的重做动作承担。第二行 `sef_startup()`（`sef.h:9`）是统一的启动入口，框架在内部完成和重起服务的握手，然后在合适的时机调用已登记的 `input_init`。

### 2.3 回调注册表：七个槽位，一张名片（`input_tab`，input.c:31-42）

```c
static struct chardriver input_tab = {
        .cdr_open     = input_open,
        .cdr_close    = input_close,
        .cdr_read     = input_read,
        .cdr_ioctl    = input_ioctl,
        .cdr_cancel   = input_cancel,
        .cdr_select   = input_select,
        .cdr_other    = input_other
};
```

这张表是输入服务递给框架的名片："这七种消息我认领，剩下的按你的默认规矩办"。框架的回调结构一共有十个槽位（`chardriver.h:9-23`：打开、关闭、读、写、控制、取消、选择、中断、闹钟、其他），输入服务只填了七个。空着的三个同样是设计：

- 写槽位空着：向输入设备写没有意义（键盘是只读的），框架对"没有写处理函数"的默认回答是输入输出错误（第 02 篇解释这条默认路径）。
- 中断槽位空着：输入服务不拥有任何硬件，硬件中断由键盘驱动进程处理（第 14 篇）。
- 闹钟槽位空着：输入服务不维护任何定时器。

读者可以把这张表当作全阶段的目录：打开和关闭在第 06 篇，读在第 07 篇，控制、取消和选择在第 08 篇，其他消息在第 05、第 09、第 10、第 11 篇。

### 2.4 初始化本体：四步，每步都有失败预案（`input_init`，input.c:646-683）

```c
static int
input_init(int UNUSED(type), sef_init_info_t *UNUSED(info))
{
        message m;
        int i, r;

        /* Initialize input device structures. */
        for (i = 0; i < INPUT_DEV_MAX; i++) {
                devs[i].minor = input_revmap(i);
                devs[i].owner = NONE;
                devs[i].tail = 0;
                devs[i].count = 0;
                devs[i].opened = FALSE;
                devs[i].suspended = FALSE;
                devs[i].selector = NONE;
                devs[i].leds = 0;
        }

        /* Subscribe to driver registration events for input drivers. */
        if ((r = ds_subscribe("drv\\.inp\\..*", DSF_INITIAL)) != OK)
                panic("INPUT: can't subscribe to driver events (%d)", r);

        /* Announce our presence to VFS. */
        chardriver_announce();

        /* Announce our presence to TTY. */
        memset(&m, 0, sizeof(m));

        m.m_type = TTY_INPUT_UP;

        if ((r = ipc_send(TTY_PROC_NR, &m)) != OK)
                printf("INPUT: send to TTY failed (%d)\n", r);

        return OK;
}
```

逐段解释：

**第 1 步：清表循环（第 652-662 行）。** 十个槽位逐个复位：次设备号按槽位反查填回（反查函数在第 03 篇），拥有者设为"无"，环形缓冲的读写位置和计数清零，打开和挂起标志复位，选择等待者设为"无"，指示灯掩码清零。注意这个循环没有失败分支——内存清零不可能失败，这是把它放在第一步的另一个理由：先完成绝对不会失败的事。

**第 2 步：订阅驱动事件（第 664-666 行）。** `ds_subscribe("drv\\.inp\\..*", DSF_INITIAL)` 向数据存储服务订阅"名字以 `drv.inp.` 开头的数据项发生变化请通知我"。C 字符串里的双反斜杠是转义，真正的订阅模式是正则表达式 `drv\.inp\..*`。标志 `DSF_INITIAL`（`ds.h:26`，含义是"立即检查一次订阅"）保证在订阅之前就已经存在的驱动也会被发现，而不是只等未来的变化。失败预案是 `panic`——进程直接崩溃。看起来粗暴，实则是诚实的：如果连"我关心的驱动什么时候到"都问不出来，这个服务不可能正确工作，早崩溃比带病运行好，重起服务会把它重新拉起（对照 1.2 节）。

**第 3 步：向文件系统一侧宣告（第 668-669 行）。** `chardriver_announce()` 做三件事：请内核放行那些还卡在上一代服务上的调用者，发布"我这个字符设备起来了"的标记，清空"上次重起前打开过谁"的记录。细节在第 02 篇，这里只需要记住它的位置：必须在清表之后（否则宣告会引来读写未初始化表格的请求），必须在终端握手之前（否则终端可能在服务还不可达时就开始对话）。

**第 4 步：向终端握手（第 671-679 行）。** 组装一条类型为 `TTY_INPUT_UP`（`com.h:879`，含义是"输入服务起来了"）的消息，用阻塞发送发给终端驱动（`TTY_PROC_NR`，`com.h:64`）。失败预案和第 2 步相反：只打印一行日志，不崩溃。为什么区别对待？订阅失败意味着"我永远聋了"，握手失败只意味着"终端这次没听见"——终端驱动有自己的重起和重连逻辑，漏掉一次通知不会造成永久失联（终端一侧的完整反应在第 13 篇）。"哪些失败值得崩溃"和"哪些失败值得容忍"，是这段代码教给读者的第一课。

## 3. Rust 设计决策

> 本章解释"为什么这样设计"。每个决策先说备选方案，再说选择的理由，最后指出去哪里验证。

### 3.1 启动顺序写成数据，而不是写成四个函数调用

C 的 `input_init` 是四个动作排成一串的函数体。直译成 Rust 会得到一个同样四个动作排成一串的函数——能用，但读者想回答"启动分几步"时必须通读函数体。Rust 版本把顺序写成数据（`init.rs` 的 `init_plan` 返回四个步骤的数组），执行顺序和"一共几步、哪几步"变成同一个东西：数数组长度就知道几步，读数组内容就知道顺序，改顺序就是改数组。

备选方案是保留 C 形态的 `run_init()` 函数。拒绝的理由：顺序信息藏在语句先后里，测试想断言"宣告必须在握手之前"时，只能把函数跑一遍并观察副作用——而副作用需要真实的数据存储服务和终端驱动，测试写不出来。写成数据之后，测试直接比较数组（`init.rs` 的 `test_init_plan_follows_c_order`），不需要任何外部进程。这是从 Redox 的实践里借来的思路：Redox 的方案管理代码把"系统起来需要哪些服务、按什么顺序"同样写成可检查的数据，而不是藏在启动脚本的执行过程里。

### 3.2 七个回调写成枚举，而不是函数指针表

C 的 `input_tab` 是七个函数指针的结构体。Rust 里最省事的对应物是同样七个函数指针的结构体，但这只是换了语言的直译。Rust 版本用七个变体的枚举（`init.rs` 的 `HandlerSlot`）列出"我认领哪七种消息"，分发时用 `match` 穷举。好处是编译器参与检查：将来第 06 篇落地打开处理函数时，如果有人新增了第八种消息却忘了教分发器，`match` 缺分支会编译失败；C 版本里同样的遗漏只会静静地走默认路径。

备选方案是保留函数指针表（Rust 允许结构体里放 `fn` 指针）。拒绝的理由有两条：第一，函数指针表把"有哪些处理函数"和"它们分别是什么"混在一起，读者数槽位要一个个数；第二，空着的写、中断、闹钟三个槽位在 C 里是"没写就是默认"，在枚举方案里必须显式写出"这三个我故意不要"并注明框架默认是什么——把省略变成显式的决定，正是文档驱动设计想要的效果。

空槽位的默认行为不是本篇编造的：第 02 篇逐条验证了框架对缺失处理函数的回答（写请求答输入输出错误，中断和闹钟通知直接丢弃）。

### 3.3 只登记"第一次诞生"，用单变体枚举把政策写死

C 用"只调用一次登记函数"表达"只有第一次诞生需要准备"。Rust 版本用只有一个变体的枚举（`init.rs` 的 `StartupRegistration::FreshBoot`）表达同样的政策。单变体枚举看起来奇怪——它永远只能是那一个值。但这正是它的价值：类型签名在说"这个服务没有第二种启动方式"，而不是"碰巧这次只用了一种"。将来如果有人想给输入服务加"重起保留状态"，他必须先给这个枚举加变体，而加变体的动作本身就会提醒他：清表循环、宣告语义、挂起读的恢复路径（第 06、第 07、第 11 篇）都要重新设计。

备选方案是用布尔值或字符串表示启动方式。拒绝的理由：布尔值需要读者记住"真表示第一次还是重起"，字符串在编译期不检查拼写，都是把政策藏进约定而不是写进类型。

### 3.4 订阅模式字符串逐字节保留，不过度"清洗"

C 的订阅字面量 `"drv\\.inp\\..*"` 在 Rust 里原样保留为 `"drv\\.inp\\..*"`（`init.rs` 的 `DRIVER_EVENT_PATTERN`），包括双反斜杠。有人可能想"清洗"成更可读的正则写法，但清洗会引入风险：万一清洗前后的模式匹配范围有细微差别，服务会漏掉驱动或收到无关通知，而这类问题只在驱动恰好晚到时才暴露，极难调试。正确的做法是逐字节保留，并用注释解释双反斜杠是 C 字符串转义、真正的模式是 `drv\.inp\..*`，再用测试把字面量锁死（`init.rs` 的 `test_driver_pattern_matches_c_literal`）。

### 3.5 终端握手的消息编号不属于本篇

C 的 `input_init` 里出现了 `TTY_INPUT_UP` 和 `TTY_PROC_NR` 两个常量。Rust 的 `init.rs` 里故意没有它们对应的常量，只有一个 `NotifyTerminal` 步骤。这不是遗漏：消息编号的所有权属于第 05 篇（协议面），终端一侧的反应属于第 13 篇。如果本篇定义一遍、第 05 篇再定义一遍，两个定义 drift 的时候读者不知道信谁（跨文档重复定义的教训，见各篇统一的引用规则）。本篇的诚实做法是：在文档里引用编号、在代码里只记录"这一步发生了握手"，并明确指向拥有编号的篇章。

## 4. 实现详解

> 本章解释"怎么做"。每个小节先一句话说清思路，再给代码位置，最后说明和第 3 章哪个决策对应。完整代码在 `os/servers/input/src/init.rs`（启动顺序与回调清单）和 `os/servers/input/src/main.rs`（进程入口）。

### 4.1 四步初始化：`InitStep` 与 `init_plan`（对应决策 3.1）

```rust
pub enum InitStep {
    ClearDeviceTable,      // 对应 input_init 第 652-662 行：清表循环
    SubscribeDriverEvents, // 对应第 665 行：订阅驱动事件
    AnnounceToFileSystem,  // 对应第 669 行：向文件系统一侧宣告
    NotifyTerminal,        // 对应第 672-677 行：向终端握手
}

pub const fn init_plan() -> [InitStep; 4] { ... }  // 按 C 顺序排列
```

枚举变体按 C 的执行顺序排列，`init_plan` 返回同样顺序的数组。`const fn` 意味着这个顺序在编译期就固定了——启动顺序不是运行时算出来的，是写死在二进制文件里的，和 C 的语句顺序地位相同。每个变体的文档注释标出对应的 C 行号，读者可以逐行对照。

### 4.2 回调清单：`HandlerSlot` 与 `handler_slots`（对应决策 3.2）

七个变体按 `input_tab` 的字段顺序排列（`init.rs`）。变体注释里写清三件事：对应的 C 回调字段名、处理函数名、完整语义在哪一篇。空着的写、中断、闹钟槽位不在枚举里——枚举只收录"我认领的"，认领之外的归属由第 02 篇的框架默认行为覆盖，两处互相引用，不重不漏。

### 4.3 启动登记：`StartupRegistration`（对应决策 3.3）

```rust
pub enum StartupRegistration {
    FreshBoot,  // 对应 sef_setcb_init_fresh(input_init)，input.c:688
}

pub const fn startup_registration() -> StartupRegistration {
    StartupRegistration::FreshBoot
}
```

`startup_registration` 永远返回唯一的变体。测试（`init.rs` 的 `test_startup_registers_fresh_boot_only`）断言这个唯一性——看起来像在测一句废话，实际测的是政策："这个服务没有第二种启动方式"一旦被打破，测试会第一个知道。

### 4.4 进程入口：`main.rs`（对应 2.1 节）

入口二进制文件只做登记、列计划、交出控制权三件事，主循环落地之前用空转等待，并注释说明空转是故意的（不能服务的服务器不许假装在服务）。这种"诚实的占位"和第 3 章的风格一致：没实现的部分显式标出来，而不是用看似能跑的代码掩盖。

### 4.5 与 C 四步的差异说明

| C 步骤（input.c） | Rust 对应（init.rs） | 差异分类 |
|------|------|------|
| 清表循环（652-662） | `ClearDeviceTable` + `structs.rs` 的 `InputTable::fresh` | 设计决策：顺序归本篇，表格构造归第 03 篇 |
| 订阅（665，失败则崩溃） | `SubscribeDriverEvents` + 模式常量 | 无差异（崩溃政策在文档 2.4 节说明，传输落地时实现） |
| 宣告（669） | `AnnounceToFileSystem` + `framework.rs` 的 `announce_effects` | 设计决策：步骤归本篇，三个子效果归第 02 篇 |
| 握手（672-677，失败只记日志） | `NotifyTerminal`（编号归第 05 篇） | 设计决策：见 3.5 节（所有权归属） |
