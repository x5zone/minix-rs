## 1. 概念：全系统只讲一种输入语言

### 1.1 为什么需要统一语言：三种键盘，一种描述

想象三种键盘：个人电脑键盘、笔记本键盘、未来可能接上的 USB 键盘。它们的硬件nodes各不相同：扫描码不同、鼠标协议不同、媒体键的位置不同。如果每种硬件都用自己的语言向系统报告，系统里每个想读输入的程序都要学三种语言——再来三种硬件就要学六种。统一语言解决这个问题：所有驱动先把自家硬件的报告翻译成系统统一的事件格式，再送到输入服务；所有读者（终端、将来的窗口系统）只学这一种语言。新增硬件只需要写"硬件到统一语言"的翻译，新增读者只需要学统一语言，两边解耦。

头文件开头的注释把这层意思说透了（`input.h:17-22`）：输入服务大量借用 USB 人机接口规范的事件词汇，每个驱动应该把自己的事件码转换成这个格式；键盘事件用美国键盘布局；到本地化布局的映射在别处做（终端、图形服务）。三句话分了三层责任：词汇归规范，翻译归驱动，本地化归读者——本章只讲词汇这一层。

### 1.2 一个事件是二十个字节：两看、一值、两路由、两保留

统一语言的一句话是二十个字节，六个字段（`input.h:25-32`）：

```
字节   0-1     2-3     4-7        8-9       10-11      12-19
       页      码      值         标志      来源设备   保留（将来放时间戳）
       哪一类  哪一个  按下还是   绝对还是  哪个设备
               事件    松开/位移  相对      产生的
```

- **页**（2 字节）：事件属于哪个家族——通用桌面（指针移动、电源键）、键盘、指示灯、按键、消费类（媒体键）。页是最高层的分类，读者先看页，再看码。
- **码**（2 字节）：页内的具体事件——哪个键、哪个灯、哪个按钮。码的含义只在页内有效：键盘页的 4 表示字母 A，消费类页的 4 毫无意义。
- **值**（4 字节）：按键和按钮用 1 表示按下、0 表示松开；指针移动用这个字段装坐标或位移量（这就是注释说"值不完全列举"的原因——坐标有无数种）。
- **标志**（2 字节）：值是绝对位置还是相对位移。触摸屏报的是手指在哪里（绝对），鼠标报的是移动了多远（相对），读者必须看标志才知道怎么理解值。
- **来源设备**（2 字节）：哪个物理设备产生的事件，由服务在转发时填写，驱动不用填。
- **保留**（8 字节）：将来放时间戳，现在恒为零，读者不许解读。

### 1.3 页码为什么是 1、7、8、9、12：借来的号码不连续

初次看到五个页码（1、7、8、9、12）会疑惑：2 到 6、10、11 去哪里了？答案是这些号码是从 USB 规范的使用页码表里借来的，借的时候只借了需要的五页，没借的不在系统里出现。号码不连续不是疏漏，是"只借需要的"的证据。读者不需要记住 USB 规范的全文，只需要记住：页码的权威定义在 USB 规范，系统的权威定义在本章，两者数值一致，不一致时以系统头文件为准。

### 1.4 键盘码为什么有 215 个：把整张美国键盘编号

键盘页的事件码最多（215 个），因为它要给整张键盘的每个键一个编号：26 个字母、10 个数字、12 个功能键、小键盘区、修饰键（左右 Ctrl、Shift、Alt、徽标键）、多媒体区的一部分。编号从 `0x04` 开始（字母 A），`0x00` 到 `0x03` 留空——留空的原因同样来自 USB 规范（那里是保留区）。编号里有三段明确的保留空隙（`0xA5-0xAF`、`0xDE-0xDF`、`0xE8` 以上），这些空隙没有键，将来 USB 规范加新键时从这里取号。空隙的存在意味着"码是否合法"不能靠区间判断（比如"小于 0xE8 就合法"是错的，0xA5 就不合法），只能靠查表——Rust 一侧的 `is_defined` 方法正是查表实现（第 3 章）。

### 1.5 系统段：只有系统组件能看到的三个名字

头文件第 6-15 行被条件编译包起来：只有定义了系统标记的编译单元才能看到键盘设备类型、鼠标设备类型和"非法设备编号"三个名字。普通用户程序看不到它们——用户程序只需要读写事件，不需要知道"键盘"和"鼠标"在系统内部是两种设备类型。这种"同一头文件、不同可见性"的做法，是微内核系统里常见的分层：协议的公共部分人人可见，系统内部的管理词汇只给系统组件。

### 1.6 本章小结：词汇表备好，翻译和使用在别处

读完本章，读者应该能不假思索地回答：统一语言解决什么问题（三层责任划分）；二十字节的六个字段各自是什么；页码为什么不连续；键盘码为什么 215 个、空隙在哪里、为什么合法性只能查表；系统段三个名字的可见性规则。下一阶段（第 05 篇）讲这些事件如何装进消息，第 09 篇讲服务收到事件后做什么。

## 2. C 源码分析

> 本章逐段对照原始 C 代码。所有行号以工作区当前 `minix3/minix/include/minix/input.h` 为准（共 333 行）。

### 2.1 事件结构：六字段二十字节（input.h:24-32）

```c
struct input_event {
        uint16_t page;                  /* event page (INPUT_PAGE_) */
        uint16_t code;                  /* page-specific event code */
        int32_t value;                  /* event value */
        uint16_t flags;                 /* event flags (INPUT_FLAG_) */
        uint16_t devid;                 /* identifier of source device */
        uint32_t rsvd[2];               /* reserved for a future timestamp */
};
```

字段宽度值得细读：页和码是 16 位（页最多几十个，码最多几百个，16 位绰绰有余）；值是 32 位有符号（坐标和位移量可正可负，32 位装得下任何屏幕）；标志和来源是 16 位；保留是两个 32 位（时间戳需要 64 位）。总长度 2+2+4+2+2+8 = 20 字节，各字段自然对齐，无填充——在任何字节序和对齐规则下都一样长，这是它能当"线上传输格式"的物理基础。Rust 版本用 `repr(C)` 保证同样的布局，并用测试把总长度锁死为 20（`event.rs` 的 `test_event_layout_matches_c`）。

注释只解释了保留字段的未来用途（时间戳），其余字段的注释是"是什么"而不是"为什么"——"为什么"在文件头的三层责任注释里（1.1 节）。

### 2.2 事件页：五个借来的号码（input.h:34-39）

```c
/* Event pages. */
#define INPUT_PAGE_GD           0x0001  /* General Desktop page */
#define INPUT_PAGE_KEY          0x0007  /* Keyboard/Keypad page */
#define INPUT_PAGE_LED          0x0008  /* LED page */
#define INPUT_PAGE_BUTTON       0x0009  /* Button page */
#define INPUT_PAGE_CONS         0x000C  /* Consumer page */
```

五个页：通用桌面（指针和系统控制）、键盘、指示灯、按键、消费类（媒体和应用快捷键）。英文原名值得记住：General Desktop、Key、LED、Button、Consumer——终端驱动过滤事件时只看键盘页（第 13 篇），"消费类"这个名字解释了为什么音量加减和计算器键在这里：它们是"消费者"（使用者）层面的按键，不是打字层面的按键。

### 2.3 事件值与标志：按下松开与绝对相对（input.h:41-47）

```c
/* Event values.  Not exhaustive. */
#define INPUT_RELEASE           0
#define INPUT_PRESS             1

/* Event flags. */
#define INPUT_FLAG_ABS          0x00    /* absolute value (the default) */
#define INPUT_FLAG_REL          0x04    /* relative value */
```

"Not exhaustive"（不完全列举）是整份头文件最诚实的注释：值字段对按键只有两种取值，对指针有无数种取值，所以它拒绝给出完整的表。标志只有一位有效（`0x04`，借自 USB 规范的"相对"位），绝对是默认值零——"默认零"意味着驱动不填标志时事件自动是绝对的，少填不错的设计（但鼠标驱动必须记得填相对，否则位移会被当成坐标，第 14 篇）。

### 2.4 通用桌面码：五个（input.h:50-57）

```c
enum {
        INPUT_GD_X = 0x0030,
        INPUT_GD_Y,

        INPUT_GD_SYSTEM_POWER_DOWN = 0x0081,
        INPUT_GD_SYSTEM_SLEEP,
        INPUT_GD_SYSTEM_WAKE_UP
};
```

横轴 `0x30`，纵轴靠自动递增得 `0x31`；电源、睡眠、唤醒三个系统控制从 `0x81` 起排。注意 Y 没有手写值——C 的枚举自动递增在这里是安全的（X 和 Y 在规范里就是连号），Rust 版本把两个值都手写出来（`event.rs` 的 `GeneralDesktopCode`），让每个数值都能独立审查，不依赖"上一个加一"的心算。

### 2.5 键盘码：215 个（input.h:59-290）

键盘码表是文件的主体（232 行），从 `INPUT_KEY_A = 0x0004` 开始，到修饰键 `0x00E0-0x00E7` 结束，中间经过字母、数字、回车转义退格制表、小键盘区、功能键 F1 到 F24、编辑键区、数字小键盘第二区。三个保留空隙在表中清晰可见：`0xA5-0xAF`（注释写明保留）、`0xDE-0xDF`（注释写明保留）、`0xE8` 以上（注释写明保留）。显式写出值的只有四个位置（起始 `0x04`、小键盘第二区起始 `0xB0`、修饰键起始 `0xE0`），其余靠自动递增——232 行里只有三个数字是手写的，其余都是顺序。这个写法对人类友好（读起来是整张键盘），对机器验证不友好（想确认某个键的值要从上一个手写值数下来），Rust 一侧的机械生成（3.2 节）正好补上机器验证。

抽查三个值供读者验证：字母 A 是 `0x04`（表头），回车是 `0x28`（从 `0x04` 数 36 个），左 Ctrl 是 `0xE0`（手写值）。验证方法：`sed -n '60,64p;280,290p' minix3/minix/include/minix/input.h`。

### 2.6 系统段：三个内部名字（input.h:6-15）

```c
#ifdef _SYSTEM

/* Device type. */
#define INPUT_DEV_KBD           0x01    /* keyboard device */
#define INPUT_DEV_MOUSE         0x02    /* mouse device */

/* Known-invalid input device ID. */
#define INVALID_INPUT_ID        (-1)

#endif /* _SYSTEM */
```

键盘类型 1，鼠标类型 2（位掩码，可组合——一个驱动可以同时是键盘和鼠标，比如笔记本的键盘加指点杆，第 14 篇），非法编号 -1（注意是负数，而设备编号都是非负的，所以 -1 不可能和真编号撞车——哨兵值选负数的经典理由）。这三个名字只在系统编译时可见：驱动用类型掩码宣告自己是什么（第 12、第 14 篇），服务用非法编号表示"还没分到号"（第 11 篇）。Rust 一侧三个常量已在本篇模块定义（`event.rs` 的 `DEVICE_TYPE_KEYBOARD`、`DEVICE_TYPE_MOUSE` 与 `INVALID_INPUT_ID`，值与测试见第 5 章），使用方在第 11、第 12、第 14 篇——定义权归本篇（头文件是本篇的依据），使用权归各使用篇。

### 2.7 指示灯码、按键码、消费类码（input.h:292-331）

指示灯三个（数字锁、大写锁、滚动锁，从 1 开始排）；按键一个（主按键 1——头文件只给第一个按键命名，更多按键用同页更大的码直接表示，和键盘码"每个都命名"不同，因为按键数量不固定）；消费类十九个（上一曲、下一曲、停止、播放暂停、静音、音量加减、媒体选择、邮件、计算器、浏览器、搜索、主页、后退、前进、停止刷新、刷新、书签），显式值八处（`0xB5`、`0xCD`、`0xE2`、`0xE9`、`0x183`、`0x18A`、`0x192`、`0x194`、`0x221`、`0x22A`），其余自动递增。消费类码的分布（`0xB5`、`0xCD`、`0xE2`、`0xE9`、`0x18x`、`0x19x`、`0x22x`）来自 USB 规范的消费类页分区，本章不展开分区含义（那是 USB 规范的书，不是输入服务的书），只登记数值。

## 3. Rust 设计决策

> 本章解释"为什么这样设计"。每个决策先说备选方案，再说选择的理由。

### 3.1 页、值、标志写成枚举，码在键盘页写成新类型加常量

五个页、两种值、两种标志，取值集合都很小（5、2、2），写成枚举是最自然的：`from_u16`/`from_i32`/`from_flags` 把线上的数翻译成含义，未知的数翻译成空（调用方丢弃，见 3.3 节）。键盘码 215 个，写成 215 变体的枚举技术上可行，但代价是 `from_u16` 要写 215 个分支——和常量表加一个成员检查函数效果一样，代码量却翻倍。所以键盘码用新类型包 16 位整数（透明传输，任何数都能走），215 个已定义的码各一个具名常量，未定义的判定用一个成员检查函数。这种"小集合用枚举、大集合用新类型加常量表"的分界，是按集合大小选择表达方式的实例：枚举的优势（编译器检查穷举）在 215 个分支时变成负担（没人能读完 215 分支的 `match`），常量表的优势（对照头文件逐行验证）在大集合时压倒一切。

备选方案是全部统一成枚举（包括 215 个键盘码）。拒绝的理由：215 分支的 `match` 无法人工审查，只能信任生成器；常量表同样由生成器产生，但每一行都可以和头文件左右对照——可审查性在大集合场景下比形式统一更重要。

### 3.2 键盘码表机械生成，生成器进仓库，测试锁死每个值

215 个常量和 215 个成员检查分支由脚本从 C 头文件生成（`tools/gen-input-keycodes.py`），生成器本身提交进仓库。理由有三条：第一，手抄 215 个值一定会抄错几个，机器不会；第二，头文件将来加新键时，重新跑脚本加跑测试就是完整的更新流程，不需要人工比对；第三，生成器的解析逻辑（显式值设起点、其余自动递增）本身就是对"C 枚举语义"的可执行文档——读者读生成器就知道 C 的自动递增是怎么回事。

备选方案是手写常量表。拒绝的理由：手写 215 个十六进制数，审查者需要逐个核对，审查成本和抄写成本一样高，等于把机器能做的事交给人做。备选方案二是生成但不提交生成器（只提交结果）。拒绝的理由：结果无法追溯来源，将来头文件变了没人知道怎么重新生成——提交生成器是"可重复"的底线。

成员检查函数（`is_defined`）的 215 个分支是生成器写的，测试（`key_codes.rs` 的 `test_key_code_defined_set_matches_c_gaps`）把 215 个已定义值和 6 个保留空隙代表值全部断言——"定义的都在，不该在的都不在"，双向锁死。

### 3.3 未知的页和码翻译成空，调用方丢弃，不猜测

`from_u16` 对五个页之外的数返回空，各小表的 `from_u16` 对未命名的值返回空。备选方案是"最接近猜测"（比如把未知页当成键盘页）或"透传未知值"。拒绝猜测的理由：猜错页意味着把鼠标位移当成按键，错误会扩散到读者程序；拒绝透传的理由：本章的类型承诺"这个值含义明确"，透传未知值会打破承诺。丢弃是唯一诚实的处理——而丢弃的决定在类型层面可见（调用方必须处理空），不是静默的。服务收到未知页事件时的丢弃路径在第 09 篇，终端过滤非键盘页在第 13 篇，本章只保证"未知能被表达为无"。

### 3.4 保留字段建模为数组并要求全零，而不是忽略它

C 的保留字段是两个 32 位，将来放时间戳。Rust 版本把它建模为 `[u32; 2]` 数组（而不是跳过不建模），并提供 `reserved_is_zero` 检查。建模的理由：跳过会让结构体变成 12 字节，和线上的 20 字节对不上，将来时间戳落地时整个结构要重排；建模为数组现在就把 20 字节钉死，时间戳落地时只改数组的解读，不改结构体的形状。要求全零的理由：现在写非零的发送方和读非零的接收方都是 bug，早暴露比晚暴露好（发送方清零在第 09 篇，零检查在测试里）。

### 3.5 指示灯"码"和指示灯"掩码"是两种东西，本章只拥有前者

读者可能混淆：指示灯页的三个码（哪个灯）和置灯请求的掩码（灯开还是关，第 10 篇）是两种编码。本章只拥有"哪个灯"（`LedCode`），掩码的定义权在第 10 篇，本章不提前定义、不引用、不假设。这是第 01 篇 3.5 节"编号所有权"原则的又一次应用：一个概念只属于一篇，别的篇章引用时指过去，不抄过来。

## 4. 实现详解

> 完整代码在 `os/servers/input/src/event.rs`（格式与小表）和 `os/servers/input/src/key_codes.rs`（键盘码表，机械生成）。本章按"结构、页与值、小码表、大码表、系统段常量"的顺序展开，每个小节标注对应的第 3 章决策。

### 4.1 结构：`InputEvent`（对应 2.1 节、决策 3.4）

```rust
#[repr(C)]
pub struct InputEvent {
    pub page: u16,          // 页：见 EventPage
    pub code: u16,          // 码：页内编号
    pub value: i32,         // 值：按下松开或坐标位移
    pub flags: u16,         // 标志：绝对或相对
    pub source_device: u16, // 来源设备：服务填写
    pub reserved: [u32; 2], // 保留：恒零，将来放时间戳
}
```

字段顺序和 C 一致，`repr(C)` 保证内存布局一致，`zero` 构造函数对应 C 的清零习惯，`reserved_is_zero` 对应决策 3.4。字段名 `source_device` 比 C 的 `devid` 更长——C 的缩写在这里没有保留价值（`devid` 省三个字母，读者每次都要反应一下），这是全 crate 命名风格的一次说明：省掉的字母如果不能自解释，就不省。用户的这条写作要求（不许缩写黑话）在代码命名上同样生效。

### 4.2 页、值、标志：三个小枚举（对应 2.2、2.3 节、决策 3.1、3.3）

`EventPage` 五个变体各带 USB 页码值，`from_u16` 未知返回空（决策 3.3）。`PressState` 按下松开，`from_i32` 对位移值返回空（位移不是按下，类型上分开）。`ValueMode` 绝对相对，`from_flags` 只看相对位（和 C 的位测试逐字对应）。三个 `from` 函数都是 `const`，翻译规则编译期固定。

### 4.3 小码表：四个枚举（对应 2.4、2.7 节）

`GeneralDesktopCode`（5 个）、`LedCode`（3 个）、`ButtonCode`（1 个）、`ConsumerCode`（19 个）。消费类枚举把 C 的自动递增值全部手写出来（`0xB6`、`0xB7`、`0xEA` 等），每个数值独立可审查——这是 2.4 节"显式优于递增"原则在消费类表的应用。按键表只有一个变体：看起来单薄，但它诚实地反映了头文件的现状（只命名了一个），更多按键走"同页更大的数"，和键盘码的透明传输一致。

### 4.4 大码表：`KeyCode`（对应 2.5 节、决策 3.1、3.2）

```rust
pub struct KeyCode(pub u16);  // 透明传输：任何数都能走
impl KeyCode {
    pub const A: KeyCode = KeyCode(0x0004);       // 215 个具名常量之一
    pub const NUM_1: KeyCode = KeyCode(0x001E);   // 数字键加前缀（标识符不能以数字开头）
    pub const fn from_u16(raw: u16) -> Self { ... }
    pub const fn is_defined(self) -> bool { ... } // 查表判定，非区间判定
}
```

数字键的 `NUM_` 前缀是 Rust 标识符规则逼出来的（标识符不能以数字开头），注释写明，前缀只出现在 Rust 一侧，线上的数不变。`is_defined` 用 215 分支的匹配实现查表判定——1.4 节解释过为什么不能用区间判断，代码是那段论述的可执行版本。

### 4.5 系统段常量：定义归本篇（对应 2.6 节）

```rust
pub const DEVICE_TYPE_KEYBOARD: u16 = 0x01;  // 键盘类型位
pub const DEVICE_TYPE_MOUSE: u16 = 0x02;     // 鼠标类型位，可与键盘位组合
pub const INVALID_INPUT_ID: i32 = -1;        // 未分配设备编号
```

三个都是无类型宏的直接搬运（类型按用途选择：类型位是 16 位掩码，非法编号是有符号 32 位，负值才有意义）。定义放在本篇模块是因为头文件是本篇的依据；使用它们的连接、宣告、驱动代码在第 11、第 12、第 14 篇，到时直接引用，不再重复定义。

### 4.6 与 C 的差异说明

| C 行为 | Rust 对应 | 差异分类 |
|--------|----------|---------|
| 枚举自动递增值（Y、睡眠、唤醒等） | 全部手写显式值 | 无差异（数值一致），可审查性改进 |
| 保留空隙无名 | `is_defined` 对空隙返回否 | 无差异（集合一致） |
| `devid` 缩写字段名 | `source_device` | 命名改进：线上布局不变 |
| 其余结构、页码、标志、码值 | 逐项对应 | 无差异 |
