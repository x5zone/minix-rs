## 1. 概念：广播、记住、恢复

### 1.1 置灯是广播，不是一对一

调灯命令带一个地址：键盘多路器（"所有键盘"）或某个具体键盘。服务把地址翻译成目标集合：多路器地址对应四个键盘槽，单个地址对应一个槽，鼠标地址对应空集（鼠标没有灯，命令蒸发）。然后对集合里的每个槽做两件事：记住新掩码（无论如何），发送新掩码（有驱动才发）。记住与发送分离，是全章的核心：记住面向未来（驱动还没来），发送面向现在（驱动正在跑）。

### 1.2 为什么记住：驱动会死，灯不能闪

键盘驱动是普通进程，会崩溃、会被重起。驱动死的时候，它控制的物理指示灯停在最后的状态；新驱动起来，如果没人告诉它"灯应该是什么样"，它默认全灭——用户正在大写锁定的状态下打字，灯却灭了，"灯"与"状态"脱节。服务记住每个槽的掩码，新驱动一到就先把灯调成记住的样子（第 11 篇连接时恢复），脱节的时间只有一个连接过程那么长。记忆是服务替驱动保管的"状态遗嘱"：驱动可以死，遗嘱不丢（遗嘱存在服务进程里，服务死了才是另一回事——服务死了重起后遗嘱清零，一切重来，第 01 篇的忘记一切政策）。

### 1.3 为什么广播：四个键盘与一个多路器

四个物理键盘各有各的灯，但用户只按一种"大写锁定"——四个键盘的大写锁定是同一个逻辑状态，灯必须一起亮一起灭。多路器地址（"所有键盘"）就是干这个的：终端不知道也不关心有几个键盘，它说"大写锁定灯亮"，服务广播到四个槽。单个地址留给"只调某一个"的场景（极少用，但协议保留）。广播的实现是循环四个槽、逐个匹配地址——循环范围写死在键盘区，鼠标天然收不到（1.1 节的空集是循环范围的自然结果，不是一句 `if` 特判）。

### 1.4 先记住后发送：顺序即语义

同一槽位，先保存掩码，再发送（如果有驱动）。顺序不能反：先发后记，发送成功但进程在"记"之前崩溃，记忆丢了；先记后发，任何时点崩溃，记忆都不比已发送的旧。崩溃可以在任意两条语句之间发生——这是系统编程的基本假设，顺序设计必须对"任意位置崩溃"都正确。先记后发满足：记是本地内存写（不失败），发是异步发送（失败只记日志，见 1.5 节）。

### 1.5 发送失败只记日志：灯不值得崩溃

发给驱动用异步发送（fire-and-forget，单向协议没有回答，第 05 篇），失败（驱动刚死）只记一行日志，请求照样算成功。为什么失败不算失败？灯是"状态同步"，不是"事务"：同步可以下次再做（驱动重连时从记忆恢复，1.2 节），事务失败必须让调用者知道。把同步做成事务（失败就报错），调用者（终端）收到错误也不知道该干什么——重发一遍？还是告诉用户"灯没亮"？都不对：重发可能还是失败（驱动死了），告诉用户更是添乱。正确的失败语义是"记一笔，靠恢复机制兜底"，这正是代码做的。

### 1.6 为什么只有终端能调灯：来源过滤的理由

第 05 篇记录了"置灯只认终端"的分发规则，这里的理由是：灯是共享输出设备（四个键盘的灯反映同一个逻辑状态），必须有一个唯一的写入者，否则两个写入者打架（终端说亮、某驱动说灭，听谁的）。终端是"大写锁定"逻辑状态的主人（它解释按键、维护锁定状态，第 13 篇），主人调灯，天经地义。来源过滤（第 05 篇 2.7 节）是这条理由的可执行版本。

### 1.7 本章小结：记住是灵魂，广播是身体

读完本章，读者应该能不假思索地回答：置灯发给谁（目标集合三种情况）、为什么记住（驱动会死）、为什么广播（逻辑状态唯一）、为什么先记后发（任意位置崩溃）、发送失败为什么不算失败（同步非事务）、为什么只有终端能调（唯一写入者）。下一章（第 11 篇）讲驱动的来去：连接时从记忆恢复，断开时叫醒等待者。

## 2. C 源码分析

> 本章逐段对照原始 C 代码。所有行号以工作区当前 `minix3/` 为准。

### 2.1 置灯：循环、匹配、记住、发送（input_set_leds，input.c:204-240）

```c
static void
input_set_leds(devminor_t minor, unsigned int mask)
{
        struct input_dev *dev;
        message m;
        int i, r;

        /* Prepare the request message */
        memset(&m, 0, sizeof(m));

        m.m_type = INPUT_SETLEDS;
        m.m_input_linputdriver_setleds.led_mask = mask;

        /*
         * Send the request to all matching keyboard devices.  As side effect,
         * this approach discards the request on mouse devices.
         */
        for (i = FIRST_KBD_DEV; i <= LAST_KBD_DEV; i++) {
                dev = &devs[i];

                if (minor != KBDMUX_MINOR && minor != dev->minor)
                        continue;

                /* Save the new state; the driver might (re)start later. */
                dev->leds = mask;

                if (dev->owner != NONE) {
                        if ((r = asynsend3(dev->owner, &m, AMF_NOREPLY)) != OK)
                                printf("INPUT: asynsend to %u failed (%d)\n",
                                    dev->owner, r);
                }
        }
}
```

先组装消息（清零、填类型、填掩码——组装一次，循环复用：四个目标收到的消息一字不差，组装一次是自然的）。注释点出循环的副作用（"顺带丢弃鼠标设备的请求"）：循环范围是键盘槽，多路器地址全匹配（`minor != KBDMUX_MINOR` 不成立则不跳过），单个地址只匹配自己的次设备号，鼠标地址谁也匹配不上——三句话讲清 1.1 节的三种情况，且"鼠标蒸发"明确标注为副作用（作者知道，读者也要知道：副作用写进注释，就不是暗坑）。

循环体内先记住后发送（1.4 节），发送只发给有主人的（1.1 节），失败记日志（1.5 节）。函数无返回值（`void`）：置灯没有失败的概念——记住了、能发的都发了，函数的工作就完成了。`void` 在这里是语义声明，不是偷懒（对比打开关闭读控制个个有返回值：那些都有"办不成"的情况，置灯没有）。

## 3. Rust 设计决策

> 本章解释"为什么这样设计"。每个决策先说备选方案，再说选择的理由。

### 3.1 目标规划返回定长数组，而不是变长集合

`plan_light_targets` 返回四个槽位的数组（没选中的是空），而不是"选中的名单"。理由：键盘永远四个槽，目标集合是"四个槽的子集"——定长数组让"没选中"可见（空位），变长集合让"没选中"不可见（缺席）。可见的缺席可测（测试断言"第 0、2、3 位是空"，`test_single_minor_addresses_itself`），缺席的缺席只能数个数。四个是小常数，定长数组零成本——"子集"用"定长数组加空位"表达，是小全集场景的标准做法。

备选方案是返回集合（Vec）。拒绝的理由：Vec 需要分配器（`alloc` 有，但没必要），且"鼠标地址得空集合"与"单个地址得一元集合"在类型上无法区分"空是因为没选中"还是"空是因为没东西"——定长数组里，空位的位置本身就是信息（第几个槽没被选中）。

### 3.2 所有权装进目标，而不是第二次查表

`LightTarget` 带 `owned` 标志（有没有驱动），传输层凭它决定发不发。备选方案是传输层拿到目标槽位后自己再查一次主人。拒绝的理由：规划与发送之间没有交错（单线程事件循环，规划完立刻发，没有别的消息插进来改主人），第二次查表查的和第一次一样——重复查询是"以防万一"的防御性编程，而"万一"在单线程里不存在。防御性代码防的是不存在的情况，等于没防，还多一次查表。单线程的确定性要用足：一次查询的结果管全程。

### 3.3 记忆读写是两个函数，不是字段直访

`apply_light_save`（写）与 `remembered_lights`（读）是两个函数，尽管它们各只有一行。理由：读写各有各的注释位置（写注释讲"无条件记住"，读注释讲"连接时恢复"），字段直访把两处的理由混在一起。更重要的是，第 11 篇读记忆时不需要知道记忆存在哪（字段名），只需要"给我当前灯光"——函数是稳定的接口，字段是易变的实现。今天记忆存在 `leds` 字段，明天想存时间戳附带，改函数体就行，调用方不动。一行函数不是浪费，是接口与实现的分界线画在了稳定的地方。

### 3.4 鼠标蒸发无分支：循环范围即过滤器

规划函数没有"如果是鼠标地址就返回空"的特判——循环只走键盘槽，鼠标地址自然匹配不上。理由：特判是"用代码写注释"（"鼠标没有灯"这句话，循环范围已经说过了），重复说一遍等于承认"循环范围可能改"——范围是常量（四个键盘槽），改不了，特判的防御对象不存在。C 同样没有特判（注释说"副作用"，不是 `if`），Rust 延续：范围即过滤器。

## 4. 实现详解

> 完整代码在 `os/servers/input/src/setleds.rs`。本章按"规划、记忆"的顺序展开，每个小节标注对应的第 3 章决策。

### 4.1 规划：`LightTarget` 与 `plan_light_targets`（对应决策 3.1、3.2、3.4）

```rust
pub struct LightTarget {
    pub index: DeviceIndex,  // 哪个槽
    pub owned: bool,         // 有没有驱动（发不发）
}
```

循环四个键盘槽：多路器地址全选（`Minor::is_keyboard_multiplexer`，第 03 篇本轮新增的方法——03 篇的快照与测试已同步，见 scan），单个地址选自己的次设备号相等的槽。注意比较的是"槽的次设备号等于地址"，不是"地址换算成槽"——换算（第 03 篇正查）在这里不适用：换算把鼠标地址也换算出槽，而广播必须让鼠标地址落空。用"相等"而不用"换算"，是 3.4 节"范围即过滤器"的另一面。

### 4.2 记忆：`apply_light_save` 与 `remembered_lights`（对应决策 3.3）

写无条件，读纯返回。第 11 篇连接时调用读（恢复），本章调用写（记住）——读写成对出现但分属两篇，配对关系在两篇的"参见"里互相指认（跨文档配对不断线）。

### 4.3 与 C 的差异说明

| C 行为 | Rust 对应 | 差异分类 |
|--------|----------|---------|
| 组装一次循环复用 | 目标规划（组装归传输层，见 1.1 节） | 设计决策：规划发送分离（组装是发送的一步） |
| 循环匹配三情况 | 同三情况（数组空位表达） | 无差异 |
| 先记后发 | 同顺序（记在本章，发在传输层） | 无差异 |
| 失败记日志 | 目标 `owned` 标志（传输层记） | 无差异（职责划分） |
| 无返回值 | 规划返回数组（纯函数需要返回值） | 表达差异：C 的 void 是"无失败"，Rust 纯函数用返回值交付结果 |
