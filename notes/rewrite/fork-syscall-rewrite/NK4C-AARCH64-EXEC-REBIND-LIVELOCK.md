# 一次成功的 exec，一个永远取不到指令的子进程：aarch64 页表换根未通知内核的活锁复盘

> 这是一篇面向读者的独立复盘：不需要读过其它文档，也能明白这个 bug 的现象、本质、为什么它极其难查、以及最终如何修好。所有事实断言都带代码符号锚点（`路径::函数名`），可在当前仓库核对。

---

## 1. 一句话的本质矛盾

一个进程调用 `exec` 换上了全新的程序，内存服务器为它建了一张全新的页表，可内核却依然拿旧的页表根地址去翻译这个进程的虚拟地址。于是这个进程每取一条指令都命中"页不存在"，内核向内存服务器要这一页，内存服务器诚实地把这一页映射进新页表并回答"好了"，可 CPU 下次翻译时走的还是那张旧页表——同一地址、同一失败、无休止。

这就是活锁（livelock）：系统在不停地"处理"，每一方都在正确地做着自己该做的事，却因为一份关键的元数据没有同步，整体永远走不出同一个循环。它不像崩溃那样会停下来给你一行错误，它会安静地把同一个错误重复七万多次。

---

## 2. 背景：微内核里"页表根地址"是谁的财产

要理解这个 bug，必须先理解 minix-rs（MINIX3 微内核的 Rust 重写）的一个基本分工。

在宏内核里，页表由内核自己维护，一切都在内核掌控之中。但在微内核里，**管理进程虚拟内存的不是内核，而是一个跑在用户态的"内存服务器"（VM server）**。在 minix-rs 里它就是 `os/servers/vm`。它决定每个进程的地址空间里哪些页有效、把物理内存页分配给谁、处理缺页请求。页表的实际构造与写入都发生在 VM server 这一侧。

可是 CPU 翻译虚拟地址时用的页表根地址（x86_64 上是 CR3 寄存器指向的页目录物理地址，aarch64 上是 TTBR0 寄存器指向的页表根物理地址）是由**内核**在切换进程时装载的。内核并不参与页表内容的构造，它只持有每个进程"页表根的物理地址"这一份**副本**，存放在进程表项的 `p_seg.phys_root` 字段里。

关键就来了：**内核怎么得到这份根地址副本？** 在 minix-rs 里，内核自己从不主动去读 VM server 的数据结构。VM server 建好或换了一张页表之后，必须显式地通过一条内核调用把新根地址"告诉"内核。这条调用就是 `VMCTL SetAddrSpace`，对应 `os/servers/vm/src/kernel_gateway.rs::KernelGateway::sys_vmctl_set_addrspace`，内核侧的处理函数是 `os/kernel/src/syscall.rs::vmctl_set_addr_space`——它是除了启动引导之外，**唯一**会写入 `p_seg.phys_root` 的入口。

于是形成一条铁律：**只要 VM server 换了一个进程的页表根，就必须补发一次 `SetAddrSpace`，否则内核继续用旧根。** fork、boot、exec 三条换根的腿都必须遵守。

在原始的 MINIX3 C 代码里，这条通知内嵌在建页表例程的最后一步。C 的 `exit.c` 在清理旧地址空间、建新页表的序列末尾会调 `pt_bind`（`exit.c:137`），`pt_bind` 的实质就是这条根地址的内核登记（对位 `sys_vmctl_set_addrspace`）。记住这个 `pt_bind`，它就是整个故事的主角，也是最容易被忽略的一步——因为它的名字听起来只是"把页表绑个指针"，实际上它是"让内核看见新页表"的唯一通道。

## 3. 现场：exec 之后的 0x200000 无限缺页

现象出现在 aarch64 的真机（QEMU）启动流程里。系统正常走到 INIT 进程进入单用户态、`fork` 并 `exec` 出一个 `/bin/sh` 子进程。`exec` 系统调用本身返回成功——注意这一点，`exec` 是"成功"的。

但紧接着，串口日志里出现一行内存请求，然后是第二行、第三行……最终重复了七万四千零一十五次：

```
memreq target=<子进程> start=0x200000 len=0x1000 ok=1
```

`0x200000` 是子进程新程序镜像的第一个代码页（文本段起始）的虚拟地址。`ok=1` 表示内存服务器每次都成功地授权了这一页。可子进程拿到"授权"后立刻又对同一个 `0x200000` 再次缺页。每次缺页都被成功满足，每次满足后都立刻重演。系统就卡在这个"取第一条指令→缺页→授权→再取→再缺页"的死循环里，永远执行不到程序的第一条真正的指令，启动再也前进不了，预期的 `minix-rs rc: minimal boot script marker` 永远打不出来。

这里有一个极具迷惑性的细节：**每一环单看都是"成功"的**。内存请求的返回值是 `ok=1`（不是错误码），缺页处理函数正常返回，VM server 事件循环健康运转。如果你只看"有没有报错""有没有 panic"，一切正常。唯一的异常信号是**同一个地址被重复请求了几万次**——这是一个"量级"异常，而不是"状态"异常。要发现它，你得去数一行日志重复了多少次，而这份日志有数万行、是含二进制空字节的串口原始流。数错一次方向就偏了（一个反复踩到的坑：对含空字节的日志做文本搜索必须强制按文本处理，否则命中行会被当成二进制而静默漏报，让人误以为"从没发生过"）。

## 4. 根因：换了新根，却没人告诉内核

把第 2 节的铁律对照 exec 路径的代码，问题一目了然。

`exec` 时，VFS 向 VM server 发一个"清空参数"请求（`VMPPARAM_CLEAR`），VM server 的处理函数是 `os/servers/vm/src/exit.rs::handle_procctl_clear`。它做的事对位 C 的清理序列：释放旧地址空间的物理页、清空区域表、`free_page_table()`（销毁旧页表）、`init_page_table()`（建一张全新页表）。

到这里，这个进程的页表根已经从"旧根 A"变成了"新根 B"。C 的序列在这之后还有最后一步 `pt_bind`——把新根登记给内核。**而 minix-rs 的这条 `handle_procctl_clear` 腿，恰恰就没有这一步。** 旧代码在这里留了一段注释，声称架构层的绑定辅助函数是一个"经过验证的空操作"、内核侧的根登记"由 VMCTL SetAddrSpace 通道承载"——意思好像是这条通知会自动发生。但它不会。没有任何人在这条路径上发送 `SetAddrSpace`。

结果就是第 1 节描述的分裂：

- VM server 把新的 `/bin/sh` 程序镜像映射进**新根 B** 的页表里；
- 内核 `p_seg.phys_root` 仍停在**旧根 A**——而 A 刚刚被 `free_page_table` 拆掉了；
- 子进程被调度起来取指，CPU 用内核装载的旧根 A 翻译 `0x200000`，A 里没有这一页的映射（它甚至是被清零/回收的空页表）→ 命中"页不存在" → 内核发缺页请求给 VM server；
- VM server 在自己的新根 B 里把这一页映射好，回答 `ok=1`；
- 子进程重试取指，CPU **还是用旧根 A** → 再次"页不存在" → 回到上一步。

循环闭合，永不跳出。

旁证能坐实"这就是漏了一步"：同一份代码库里，另外两条同样会换页表根的路径——`os/servers/vm/src/fork.rs::do_fork`（给子进程建页表后）和 `os/servers/vm/src/vm_server.rs::exec_bootproc`（引导装机时）——**都在换根后补发了 `sys_vmctl_set_addrspace`**。三条腿里两条做了、唯独 exec 的清理腿跳过了。一条铁律在代码里被遵守了两次、遗漏了一次，这种"不一致"本身就是最强的定位线索。

## 5. 为什么同一份代码在 x86_64 上"看起来"是对的

这是整个 bug 最难查的一层，也是最值得写下的一条经验。

同样的漏发 `SetAddrSpace`，在 x86_64 上却一路正常跑到 rc marker，从不缺页活锁。乍看会让人怀疑"根因是不是别的"，从而被引向歧途。真相是：x86_64 是被一次**内存分配器的巧合**给"蒙混过关"了，而 aarch64 没有被蒙混。

区别在拆页表时的"归还"行为：

- 在 x86_64 上，销毁一张页表会把页表本身占用的物理页**归还给分配器**。紧接着建新页表时，分配器按后入先出的空闲栈取页，**大概率把刚还回去的那一页又原样分了出来**。于是"新根 B"和"旧根 A"往往是**同一个物理页地址**。内核手里那个"没更新的旧根 A"，实际上正好就是新根 B——错误指针恰好指向了正确页表，bug 被巧合掩盖。
- 在 aarch64 上，销毁页表（`os/arch/src/arm64/paging.rs` 的页表 `destroy`）只是把根清零，**从不把页表页归还分配器**。于是新根 B 必然是另一个物理页，与内核手里的旧根 A 不相等——巧合不复存在，bug 立刻暴露。

这就是"一个平台是对的、另一个平台是错的"最阴险的一种情形：**缺陷是架构无关的逻辑遗漏，能否发作却取决于一个平台特定的、纯属偶然的资源回收顺序。** x86_64 上那个"看起来正确"的行为根本不是设计保证的，它只是恰好还没被拆穿。如果哪天 x86_64 的页表分配器策略变了（不再复用同一页），同样的活锁会在 x86_64 上原样爆发。

可迁移的判断是：当"逻辑上应当无条件成立"的不变量（换根必通知内核）只在部分平台成立时，别急着相信那个"看起来对"的平台——它很可能只是把错误藏进了巧合里。要拿架构无关的**代码事实**（"这条腿到底发没发 `SetAddrSpace`"）作准，而不是拿"某平台跑通了"作准。

## 6. 为什么这个 bug 反复迭代了很多轮才定谳

除了第 5 节的平台巧合，还有几层互相缠绕的干扰，让定位变得极其缓慢。把它们逐层剥开，正是这篇复盘想留档的地方。

**第一层：`exec` 本身"成功"了。** 系统调用返回成功、内存请求回答 `ok=1`、没有任何 panic。所有显性的"健康指标"都是绿的。缺陷藏在"元数据没同步"这种不体现在返回值里的地方。一个只会盯错误码的排查方法，面对这种 bug 完全无从下手——你必须去观察"运行行为"这一更高层，注意到"同一页反复缺"这个反常模式。

**第二层：两个独立的失败模式被搅在一起。** aarch64 当时其实同时存在两个毛病。一个是本文讲的 exec 换根活锁；另一个是一个偶发的内存耗尽问题——子进程某个长度值间歇性地取到了一个陈旧栈地址，导致一次约 4GiB 的巨量分配失败而崩溃。后者发作时子进程根本还没走到 exec 成功那一步，前者只有在 exec 成功之后才现形。两者叠在同一条启动路径上，一个的现场会遮盖另一个。花了很多轮把"偶发崩溃"和"确定活锁"这两种现象分离成两个独立失败模式、分别归因，才把活锁这条线单独拎清楚。而且值得记一笔：这两个毛病**根因彼此独立**——修好了换根活锁，那个偶发内存耗尽依旧存在，并不会"顺手一起好"。这说明把纠缠的现象拆成独立可证伪的模式，比指望"找到一个万能根因"更靠谱。

**第三层：日志本身的陷阱。** 如前所述，含二进制空字节的串口原始流，如果用默认的"二进制安全"方式做文本搜索，命中行会被当作二进制而整段跳过，给出"从没出现过"的假阴性。有好几次排查方向就差点被这种假阴性带偏。硬规则是：对这类日志做搜索要强制按文本处理，并且在断言"某事件发生了 0 次"之前，一定要用能显式计数的方式反向复核一遍。

**第四层：一个"回归"其实是幽灵。** 当修复补丁第一次装上后，有报告说 x86_64 随即在内核 trap 处理处（`os/kernel/src/trap_dispatch.rs` 的异常分发）触发了页错误异常（向量 14），看起来像是"这个修复把 x86_64 弄崩了"。这几乎要把整个修复方向推翻——毕竟第 2 节说的那条"新页表若没有内核映射就提前交给内核，内核自己会缺页"的担忧，听起来逻辑自洽、极具说服力。所幸接手者没有直接接受这份"回归报告"，而是**亲手在单核下复现**：x86_64 连跑四轮，一次都没有复现出那个异常，rc marker 照常打出。追查下去，那份报告极可能是在 xtask 默认的多核配置（`-smp 4`）下跑的，撞上了一个与本案完全无关的、早已知的多核早期启动崩溃。教训凝成两条铁律：**x86_64 的验证必须在单核下做；任何外部转来的"崩溃报告"必须亲手复现，否则可能就是幽灵。** 一个未经复现的"回归"，差点否掉了一个真正正确的修复。

把这四层合起来看，这个 bug 之难，不在于修复本身有多复杂（最终就是补发一次内核调用），而在于**它把"哪里错了"这件事，藏在了"每一处看起来都对了"之下**：返回值对、单平台对、日志读起来对、连"回归"都是假的。难的是穿透这一层层表象，抓住那个唯一的、架构无关的代码事实。

## 7. 修复：补上那条腿——以及为什么它两个架构都安全

修复本身很小，就是让 exec 清理腿和 fork/boot 腿一样，在换根后补发那条内核通知。

核心改动在 `os/servers/vm/src/exit.rs::handle_procctl_clear`：函数新增一个内核网关参数（`gateway: &mut dyn KernelGateway`），在 `init_page_table()` 建好新页表之后，取出新根的物理地址并通知内核：

```rust
let new_root_phys = <PageTable as Paging>::root_paddr(proc.page_table_mut()).0;
gateway
    .sys_vmctl_set_addrspace(endpoint, new_root_phys, 0)
    .map_err(|_| VmProcctlError::InternalError)?;
```

第三个实参 `0` 是"内核可见的页表根虚拟别名"，在 minix-rs 的直接映射（Direct Map）设计下这个别名没有意义，内核一律从物理根出发遍历，所以传 `0`（等价于"无虚拟别名"）——这与 fork、boot 两条腿的写法完全一致。配套地，`os/servers/vm/src/ipc/dispatcher.rs::dispatch_procctl` 从上下文里解出网关并把它穿进清理腿。

真正的"这里会不会又引入新问题"的担忧，是那个幽灵回归逼出来的问题：**换了一张刚建好的页表根就立刻交给内核去用，安全吗？** 静态核对下来，答案是肯定的，有三重独立的理由，恰好也解释了为什么这个补发在两个架构上都不会让内核自己踩空：

1. **新根本来就带着内核映射。** `init_page_table` 在非测试分支里建根时就调用了 `map_kernel`，把内核代码/数据段、直接映射窗口一并映进了这张新页表（这是 x86_64 页表的一个基本不变量：每个用户进程页表都共享同一份内核映射）。所以"新根只有用户映射、内核会踩空"的前提根本不成立。
2. **这条通知不会立即改写当前 CPU 的页表根寄存器。** `os/kernel/src/syscall.rs::vmctl_set_addr_space` 只有在"被设置的目标进程恰好就是当前正在运行那个进程"时，才顺手重载 CR3/TTBR0。而在 exec 清理这一刻，目标是被 exec 的子进程，当前运行的是发起这次调用的 VM server 自己——两者不同，于是内核只是安静地把 `p_seg.phys_root` 记成新根，绝不提前切换正在跑的地址空间。真正的装载发生在本该发生的时候：等调度器要运行这个子进程时。
3. **子进程不会因为这次解除抑制而提前入队。** `vmctl_set_addr_space` 会顺带清掉目标的一个"内存抑制"标志（VMINHIBIT），但此刻子进程正持有一个"等待接收回复"的状态，清除抑制并不会让它被错误地排进可运行队列——它仍在等 exec 的回复，调度时序不受这条通知干扰。

有了这三重保证，"补发通知"就只是把一份早已存在的正确元数据递到内核手里，不改变任何时序，两个架构一律安全。

**回归验证**（三件套全绿，作为定论的证据）：

- 主机侧单元测试（VM server / 内核 / 架构三包）全部通过，其中新增一条断言：exec 清理确实发出了一次 `SetAddrSpace`，且目标 endpoint 正确、虚拟别名为 0、根地址非 0。测试用可记录的模拟网关替代真实内核调用（真实的直连传输在测试构建里无法服务这条调用）。
- aarch64 真机：修复前那行 `start=0x200000` 的重复缺页从基线的 74015 次降到 **0 次**；被 exec 的子进程真正取指运行起了新程序镜像；多次独立复跑、甚至四核配置下，签名逐字稳定。
- x86_64 真机（单核）：rc marker 照常打出，零 panic，那个"回归异常"确认不复存在。作为健康基线，x86_64 上 `start=0x200000` 只出现个位数次——那是若干进程各自的代码段正常地按需缺页各一次，与修复前的"同页重复几万次"在量级上泾渭分明。

代码评审阶段还追加了一处顺带发现的健壮性修复：`os/servers/vm/src/audit.rs` 里一条审计写出从"直接可变借用"改成"尝试可变借用"。原因是 exec 清理在整段分发期间会一直持有网关的借用，而清理路径里某个文件描述符关闭的审计点会再次借同一个引用计数单元，在启用审计特性时会造成二次借用而 panic；按模块约定"丢一条审计记录远不及 panic 拖垮事件循环严重"，改成借用失败即丢弃。这条与本 bug 无关，却是把网关穿进清理腿后自然暴露的并发借用隐患。

## 8. 一个来自 C 语言原型的隐患：静默的陈旧

值得单独记一笔的是：这个 bug 之所以能在原型语义里"合法地"隐藏，部分要怪 C 代码本身的态度。

C 的 `exit.c` 里那句 `pt_bind` 的返回值是被丢弃的——即便这次内核登记调用失败，C 也会照样回答"成功"。这是一种"静默陈旧"的设计：换根通知如果没送达，系统不会报错，只会悄悄留下一个指向旧根的指针。minix-rs 在结构上对位了这个序列，却又把绑定步当成"空操作"删掉了注释里承诺的自动通知，两者叠加，让"漏发通知"在代码读起来像是有意的、且即便漏了也不会以错误形式暴露。

因此 Rust 修复里有一个刻意与 C 不同的姿态：这条 `SetAddrSpace` 一旦失败，就**向上抛出错误**（映射为内部错误），而不是像 C 那样吞掉。这是"失败闭合"（fail-closed）：宁可让这次 exec 明确失败并留下痕迹，也不留一个静默陈旧的页表根。把一类会"悄悄烂掉"的缺陷，变成会"当场报错"的缺陷——对微内核这种一处元数据不一致就能让整机活锁的系统，这个选择几乎是必须的。

## 9. 可迁移的经验清单

把这次多轮排查沉淀成几条能复用到别处的判断：

1. **"运行行为异常"比"返回码异常"更早暴露真相。** 一个每步都返回成功却原地打转的系统，错误信息永远为零。要主动去看重复模式（同一地址/同一请求被处理了多少次），而不是只等 panic。
2. **"某个平台跑通了"不等于"逻辑是对的"。** 当一条应当无条件成立的不变量只在部分平台显现，被掩盖的那个平台多半只是把错误藏进了某个偶然的实现细节（这里是页表分配器恰好复用同一物理页）。以架构无关的代码事实为准。
3. **把纠缠的现象拆成独立可证伪的失败模式。** 一个偶发崩溃和一个确定活锁混在一条路径上时，先分离、分别归因；修好一个不要臆想另一个"会顺手一起好"（本例两者根因独立）。
4. **换根、换元数据这类"两个持有者之间的同步"，要逐条腿核对完整性。** 这里 fork、boot 都补了通知、唯独 exec 漏了——同一条不变量在代码里被实现的不一致，本身就是最强的定位信号。
5. **任何外部转来的"你引入了回归"，先亲手在等价条件下复现再下结论。** 本例那个几乎否掉正确修复的"崩溃回归"，单核复现四次的结果是幽灵；多核配置下的已知无关崩溃伪装成了新 bug。
6. **二进制/含空字节日志的搜索要强制按文本处理，断言"零命中"前必反向计数复核。** 假阴性曾数次险些误导方向。
7. **对会"悄悄烂掉"的元数据同步，选择失败闭合而非吞错。** C 丢弃 `pt_bind` 返回值正是这类 bug 得以藏身的温床；把静默失败改成立即报错，是把一类难以复现的疑难杂症转化为可诊断故障的通用手段。
