# 07-lwip-pktsock：包共享层

> **分类**：协议族第 2 篇（两家共用一套收发，容量不够丢包）
> **源码**：`minix3/minix/net/lwip/pktsock.c`（一千二百三十六行的包共享实现）
> **Rust 模块**：`os/net/lwip/src/pktsock.rs`（缓冲默认与容量门）
> **前置**：`notes/rewrite/fork-syscall-rewrite/17-stage-net/06-lwip-ipsock.md`（网际公共层，建户缓冲语义）、`notes/rewrite/fork-syscall-rewrite/17-stage-net/05-lwip-util-addr.md`（公共工具，池尺寸对照）
> **说明**：包层是数据报原始两家的亲妈：建户转发、收发复用、组播感知，两家只填协议细节。本篇讲默认缓冲、容量门、头标志。队列存储与包搬运在服务层，本库只定默认与门限。

> **本篇不讲什么**：
> - 网际选项语义（见 `06-lwip-ipsock.md`，选项另讲）
> - 数据报原始具体协议（见第 09 到 10 篇，两家各归其位）
> - 队列存储搬运（本篇只讲默认与门限，存储在服务层）
>
> 本篇只回答一个问题：**两家共用的收发是什么规矩**。

## 1. 概念：合租的厨房

### 1.0 章节引言

目标读者是读完网际公共层的读者。前置知识只需要两条：建户存缓冲数，池片五百一十二。本章解释包层为什么存在：两家收发长得一样，各起一套灶太浪费。

### 1.1 建户只转发

包层建户三件事：队头清空、队长清零、组播复位，然后转交网际建户。注释写得实在：本体不分配资源，失败无析构。转发即全部：转发之外无一物。

### 1.2 容量门按总量算

收包先问门：队里已有加新包总长，超接收缓冲不让进。算的是总长不是块数（大包按大包算，小包按小包算），六万四千误丢的前车之鉴写进注释。门只看数不看人：谁的包都一样。

### 1.3 默认缓冲两家不同

默认缓冲两家各表：数据报发送八千一百九十二接收三万二千七百六十八，原始发送最大载荷接收三万二千七百六十八。发送超缓冲直接拒，接收下限取池片尺寸。默认可调（上下限卡死），系统控制表敞开读。

### 1.4 头标志三位

包头标志三位：第六版位、组播位、广播位。输入时按包类型打标记（第六版打第六版位，组播广播各打各的），端口存入（原始传零）。标志只标记不决策：决策在上层。

### 1.5 原始多三步

原始比数据报多三步：先廉价估算（含头预留，不够直接丢），再去头校验（第六版去头验头，映射转版），再自拷贝（不断他家路，不吞别家包，存控制信息）。三步是原始的税：免税的是数据报。

### 1.6 本章小结

包层四件事：建户转发，容量看门，默认两表，原始多税。下一章进入 C 语言源码验证。

## 2. C 语言源码分析

### 2.2 建户转发（`pktsock.c` 第五十二行到第七十七行）

结构首字段必须是网际户（头文件第六行到第十五行注释强调），队头空队尾指头长度零在第六十三行到第六十五 行，组播复位在第六十七行，源地址接口号清零在第六十九行到第七十行。本体转发网际建户在第七十七行，注释称不得分配资源失败无析构在第五十二行到第五十六行。

### 2.3 容量门（`pktsock.c` 第八十四行到第一百三十一行）

可收判定 `pktsock_may_recv` 在第八十四行到第八十五 行（组播感知在第九十二行到第九十四行，容量检查在第一百零七行到第一百零八行，注释称用总长不用块数在一百零六行）。试输入 `pktsock_test_input` 在第一百一十六行到第一百一十七行（仅原始用，先廉价估算在一百二十一行到一百二十六行，返头预留在一百二十八行到第一百三十一行）。

### 2.4 输入复写（`pktsock.c` 第一百三十八行到第二百四十二行）

入口 `pktsock_input` 在第一百三十八行到第一百四十行（独占断言在一百五十六行到一百五十七行，注释称数据报靠库拷贝原始靠自拷贝在一百四十九行到第一百五十五 行）。拒绝即丢（第一百六十行到第一百六十四行）。头复写在一百六十六行到第一百七十二行（第六版在一百七十三行到一百八十七行，第四版在一百八十八行到第二百零四行，断言头够长在一百八十三行与第一百九十九行）。接口标志在第二百一十一行到第二百二十六行（端口存在第二百二十六行）。入队加唤醒在第二百二十八行到第二百四十二行（尾插加长度累加在第二百三十八行到第二百四十行，事件唤醒在第二百四十二行）。

### 2.5 默认缓冲（`udpsock.c` 第二十七行到第三十四行，`rawsock.c` 第四十八行到第五十五 行）

数据报：最大载荷六万五千五百三十五（第二十七行），发送最小一默认八千一百九十二最大载荷（第二十九行到第三十一行），接收最小池片默认三万二千七百六十八 最大六万五千五百三十六（第三十二行到第三十四行）。原始：最大载荷六万五千五百三十五（第四十八行），发送最小一默认最大载荷最大载荷（第五十行到第五十二行），接收最小池片默认三万二千七百六十八 最大六万五千五百三十六（第五十三行到第五十五 行）。注入在建户（数据报第一百三十八行到第一百三十九行，原始第三百一十行到第三百一十一行），发送限流即发送缓冲（数据报第二百七十九行，原始第四百七十三行）。

## 3. Rust 设计决策

> 本章解释为什么这样设计。每个决策先给依据，再给替代方案与取舍。

### 3.1 默认做成常量（依据：第 1.3 节、第 2.5 节）

两家四数写死，发送限流即发送缓冲。替代方案是运行时读配置，不选的理由是：默认值是编译期契约，读配置多一次错的机会。

### 3.2 容量做成纯函数（依据：第 1.2 节、第 2.3 节）

队里已有加新包总长对接收缓冲比大小，一测就是全部。替代方案是容量散落在输入口，不选的理由是：纯函数让两家共用一套门。

### 3.3 标志做成常量（依据：第 1.4 节、第 2.4 节）

三位各一值，成员检查纯函数。替代方案是裸数字散写，不选的理由是：常量让错位编译不过（类型是八位）。

### 3.4 设计决策汇总

| 决策 | 依据 | 替代方案 | 为何不选 |
|------|------|----------|----------|
| 默认常量 | 第 1.3、2.5 节 | 运行时读配置 | 编译期契约 |
| 容量纯函 | 第 1.2、2.3 节 | 容量散落入口 | 两家不能共用 |
| 标志常量 | 第 1.4 节 | 裸数字散写 | 错位不响 |

## 4. 错误处理

| 场景 | C 行为 | Rust 表达 | 说明 |
|------|--------|-----------|------|
| 容量超限 | 丢包 | 门限返回假 | 门外不进 |
| 发送超缓冲 | 拒绝 | 调用方比大小 | 超限不发 |
| 头不够长 | 断言崩溃 | 调用方保证 | 头短必崩 |
