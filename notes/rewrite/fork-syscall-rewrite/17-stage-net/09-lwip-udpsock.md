## 1. 概念：不需要连接意味着检查更少但边界同样严格

### 1.0 本章的读者与阅读方法

本章假设读者已经理解第 06 篇的地址种类与选项边界，知道套接字创建时保存发送与接收缓冲区尺寸。本章不需要读者了解用户数据报协议的报文格式，只需要带着三个问题来读：创建时允许哪几个协议号，发送之前必须通过哪几道长度与标志检查，新建套接字的组播相关初始值是什么。读完本章，读者应当能够说出协议号的两种通过取值，发送标志的唯一允许位，以及组播生存时间与环回的默认值，即使遮住所有函数名字也不影响理解。

### 1.1 协议号检查只接受通配与本协议号

创建用户数据报协议套接字时，调用者给出协议号。只接受两种取值：通配 0，或者用户数据报协议号 17。轻量校验和变体的协议号即使底层协议栈支持，也会被明确拒绝，源文件第 128 行的注释说明参照系统不支持该变体。其余协议号一律返回协议不支持错误。这种严格检查的意义在于防止调用者误用：用户数据报协议套接字只能承载用户数据报协议，传输控制协议号 6 或者控制报文协议号 1 都应当在创建时就被拒绝，而不是等到发送时才暴露。

### 1.2 创建流程复用共享层并设置组播初始值

创建时先调用数据包共享层的创建函数，传入发送默认值 8192 与接收默认值 32768，再创建底层协议控制块并挂接输入回调。新建控制块的组播生存时间设为 1，组播环回标志置起。生存时间 1 表示组播数据包默认只在本地链路传播，不会被路由器转发，这是一种保守的默认：需要跨网段组播的程序必须显式调大该值。环回开启表示本机发送的组播数据包会回送给本机的接收队列，便于单机测试。管理树同时公布校验和开关、发送空间、接收空间三个只读节点，供查询工具读取。

### 1.3 输入路径全部委托给共享层

底层协议栈收到数据报后调用输入回调，回调不做任何协议特有的处理，直接把数据包、源地址与端口转交给共享层的输入函数。共享层负责容量判断、头部改写、入队与唤醒。这种委托的意义在于复用：用户数据报协议与原始套接字的接收队列机制完全相同，分别实现只会制造两份需要同步的代码。Linux 内核同样把数据报与原始套接字的接收队列分开但共享辅助函数，Redox 的网络栈把无连接协议的接收路径实现为同一个队列类型加不同的协议标记，思路一致。

### 1.4 发送之前有两道长度检查与一道标志检查

发送标志只允许绕过路由表位，其余位出现即返回操作不支持。目的地址检查要求未连接套接字必须给出目的地址，否则返回需要目的地址错误。长度检查分两段：发送前比较载荷长度与套接字发送缓冲区，超出返回消息过长；发送时在已知头部长度后比较头部加载荷与最大载荷 65535，超出同样返回消息过长。分段的原因是发送前尚不知道头部长度，只能做粗检，发送时头部确定后再做精检。两段检查缺一不可：只有粗检会漏掉头部带来的超长，只有精检会让明显超长的请求走得太远才被拒绝。

### 1.5 选项设置覆盖组播生存时间、环回与校验和

选项设置包括组播生存时间、组播环回开关、组播成员管理、单播生存时间与服务类型等。组播成员的加入与离开委托给第 12 篇的成员管理模块，本文只说明选项分发的入口位置。读取路径把内部标志转换为 0 或 1 的字节值返回，保证用户程序看到的永远是规范化的布尔量，而不是内部位掩码的原始值。

### 1.6 本章小结

用户数据报协议解决四件事：创建时只接受两种协议号，发送前检查标志、地址与长度，新建时组播生存时间取 1 且环回开启，输入全部委托给共享层。下一章进入 C 语言源码的逐项验证，确认每个数值与每个分支都有源码依据。

## 3. Rust 设计决策

> 本章解释每个设计选择的原因，先给出依据，再列出考虑过的替代方案与放弃理由。

### 3.1 协议号采用白名单函数，而不是范围判断（依据：第 1.1 节、第 2.3 节）

只有两个离散值通过，用相等比较列出。替代方案是用数值范围判断。放弃的理由是范围判断会误接受两者之间的无效值，例如 6 与 136，而白名单精确表达了语义。

与 Redox 的对比：Redox 的协议分发同样用枚举加匹配，而不是数值范围。与 Linux 的对比：Linux 在套接字创建时用 switch 语句列出支持的协议，本文的白名单函数是同一思路的纯函数形式。

### 3.2 发送标志采用掩码取反判断（依据：第 1.4 节、第 2.5 节）

允许的位取反后与输入相与，结果为 0 即通过。这种写法在新增允许位时只需要改掩码，不需要改判断结构。替代方案是逐位比较。放弃的理由是逐位比较在标志增多时容易遗漏。

### 3.3 长度检查拆成两个函数（依据：第 1.4 节、第 2.5 节）

粗检比较载荷与发送缓冲区，精检比较头部加载荷与最大载荷。拆分的依据是调用时机不同：粗检在头部未知时调用，精检在头部已知后调用。替代方案是合并成一个函数。放弃的理由是合并后的函数需要同时接受三个参数，调用者容易传错，且测试无法分别覆盖两个时机。

### 3.4 组播默认值采用具名常量（依据：第 1.2 节、第 2.3 节）

生存时间 1 与环回开启各有一个名字，测试逐个断言。替代方案是在创建函数中手写数字。放弃的理由是手写数字无法区分 1 是生存时间还是其它含义，重构时容易改错。

### 3.5 设计决策汇总

| 决策 | 依据章节 | 考虑过的替代方案 | 放弃理由 |
|------|----------|------------------|----------|
| 协议白名单 | 第 1.1 节、第 2.3 节 | 数值范围判断 | 误接受中间无效值 |
| 标志掩码判断 | 第 1.4 节、第 2.5 节 | 逐位比较 | 标志增多时易遗漏 |
| 长度拆分两函数 | 第 1.4 节、第 2.5 节 | 合并成一个 | 调用时机不同，测试难覆盖 |
| 默认值具名常量 | 第 1.2 节、第 2.3 节 | 创建处手写数字 | 含义不清，重构易错 |

## 4. 错误处理

| 场景 | C 语言行为 | Rust 表达 | 说明 |
|------|------------|-----------|------|
| 协议号非 0 且非 17 | 返回协议不支持 | 白名单返回假，调用者转换为协议不支持 | 创建时拒绝 |
| 发送标志含多余位 | 返回操作不支持 | 标志函数返回假 | 多余位不支持 |
| 未连接且无目的地址 | 返回需要目的地址 | 服务主程序返回对应错误 | 规则已文档化 |
| 载荷超过发送缓冲区 | 返回消息过长 | 长度函数返回假 | 粗检不通过 |
| 头部加载荷超过 65535 | 返回消息过长 | 边界函数返回假 | 精检不通过 |
