# 14 — SCHED 与 RS 的交互

本文介绍 RS 如何替系统进程向 SCHED 申请调度、退出时如何取消。首先，系统进程和用户进程生的地方不一样：系统进程生在 RS，申请先行（生下来就有调度）；用户进程生在 PM，申请后到（生下来再申请）。然后，RS 的申请带两个断言、6 个参数直达，取消按位置分两种处理：清理时失败打警告继续走，改槽时失败带码返回。需要注意的是，RS 申请的父亲恒为 RS 自己，不存在继承。

前置阅读：`02-sched-message-surface.md`（5 种消息的版面）、`13-pm-interaction.md`（PM 的申请，本文的对照）。

分工声明：RS 槽配置的细节（`r_*` 4 个值的来源、system.conf 怎么装载）归 `../03-stage-rs/08-rs-slot-config.md`，Live Update 全流程（`update_service`/`clone_slot` 怎么迁）归 `../03-stage-rs/16-rs-live-update.md`，那两篇是主权文档。本文只取申请点 `type.h:92-95` 和取消两处（`manager.c:461`、`request.c:342`），配置的来源本文只引用，不重复。

> 本章不讲什么：
> - RS 槽配置细节（`r_*` 4 个值的来源、system.conf 怎么装载）——见 `../03-stage-rs/08-rs-slot-config.md`（本文只取引入点 `type.h:92-95`）
> - Live Update 全流程（`update_service`/`clone_slot` 怎么迁）——见 `../03-stage-rs/16-rs-live-update.md`（本文只取取消的两处）
> - 服务端检查（`accept_message`/槽位填充）——见 `06-start-scheduling.md`（本文只讲申请的形状）

## 1 概念

### 1.0 引言与前置

本文回答三个问题：第一，RS 的孩子和 PM 的孩子有什么区别；第二，RS 的申请长什么样（两个断言、6 个参数）；第三，取消失败时两种位置怎么处理。本文假设读者已经知道 5 种消息的版面（见 02）和 PM 的申请（见 13），只讲"RS 的申请"。

### 1.1 为什么生的地方不一样

生的地方有两个：系统进程生在 RS（申请先行，生下来就有调度，调度跟着生一起到），用户进程生在 PM（申请后到，生下来还没调度，调度随后申请）。分生的道理：系统进程的参数 RS 自己知道（槽里 4 个值都在 RS 表里，知道就直达，不用再问）；用户进程的参数 PM 才知道（nice 在 PM 表里，不知道就发继承问，见 13 的继承）。生的地方定申请的时机（源头在 RS，调度定在生前，槽位生前已定；源头在 PM，调度定在生后，生后发消息申请）。

### 1.2 申请前的两个断言

申请的门是两个断言，先分域（`utility.c:371-372`）：用户进程无主（`is_usr_proc` 则 `r_scheduler == NONE`，用户进程归 PM 管，RS 无权申请）；系统进程有主（非用户进程则 `!= NONE`，系统进程的参数在 RS 表里，有主才申请）。断言即分域的边界（边界两侧各有各的主，越界（用户有主/系统无主）就是构建错（`assert` 直接死），不是运行错）。先分域、后直达，域没分清就没法申请。

### 1.3 六个参数直达

申请的形状（`utility.c:375-381`）：6 个参数直达（调度器/被调度者/父亲=RS/队列/时间片/CPU，`sched_start` 的完整形状，一个不少）→ 失败返回错误码（`378`：申请失败就返回，不瞒着）→ 成功主即定（`&r_scheduler` 读回复定主，和 13 §1.4 的照收同一个道理）。直达即约有三明：父亲明（恒为 RS，生在谁家写谁的号，没有例外）、数值明（4 个值跟着走，队列时间片 CPU 都从槽里来，没有缺省值）、主明（回复是谁主就是谁，不瞎猜）。没有继承（RS 的孩子不抄父亲，父亲就是 RS 自己，抄自己即直达；和 PM 抄父亲的 INHERIT 对照，见 13 §1.3）。

### 1.4 取消失败按位置分两种处理

取消的两条路（同样是 `sched_stop != OK`，处理跟着位置走）：清理服务时（`manager.c:461-463`：失败打警告继续走，拆台时槽位已经没了，返回也没用，继续走是唯一诚实的做法）→ 改槽时（`request.c:342-345`：失败带码返回，改之前还能停（槽位没动，返回保住不变），返回是事务的守法）。同样的错、不同的处理（同样的取消失败，不同的处理（继续/返回），错的代价跟着位置走：没位置可回就继续，有槽位可保就返回）。

### 1.5 生在 RS 的三个结果

结果有三：父亲即 RS（生在谁家写谁的号，`com.h:61` 的 `2` 作父亲（`376`）→ 守土 BSP（05 的判断经 10 的选择，RS 的孩子生下来就在 BSP 上））→ 申请先行（生下来就有主，申请在生时（boot 第二步），不是生后申请）→ 取消两条路（清理拆台/改槽返回，取消的两种处理，见 §1.4）。要点：父亲栏的号（`parent == RS_PROC_NR`）是系统进程的证明（证明在父亲栏，服务端验父亲即知是系统进程，不用别的证明）。

### 1.6 和 PM 的申请对照

| 差别 | RS 的申请（本篇） | PM 的申请（13） |
|----|----------------|--------------|
| 生的地方 | RS 的孩子（系统进程） | PM 的孩子（用户进程） |
| 申请时机 | 申请先行（槽位生前已定） | 申请后到（生后发消息问） |
| 申请形状 | 新建 START（6 参数直达） | 抄父亲 INHERIT（3 字段抄时间片） |
| 申请门 | 双断言（分用户和系统） | 双断言在别处（INIT 自己当父亲/抄谁的辨别） |
| 取消形状 | 两种处理（继续/返回） | 打警告继续 + 主记回空（单来回） |
| 主记录 | 槽主（r_scheduler） | 表主（mp_scheduler） |

同一个函数（都是 `sched_start`/`sched_stop`），不同的路（生的地方不同，形状跟着变）。

### 1.7 和其他 OS 的对照

用大白话对照一下：

- **Linux**：内核线程由 `kthreadd` 生（申请先行，生下来就定调度，`sched_fork` 直达，和 §1.3 的直达对应）；用户进程 `clone` 后抄父亲（抄的形状，和 13 的继承对应）。`do_exit` 的 `sched_exit`（取消的对应，主记回空的意思）。
- **Redox**：服务监管者生服务（配额先行，调度在生前，直达的意思）；服务死了监管者收（取消的对应，两种处理的意思：能重启就继续，不能就返回）。
- **seL4**：系统进程在集成时生成（调度集成时定死，没有运行时的申请）；RS 的申请取消都是运行时（申请在 boot 第二步，取消在清理和改槽）。区别就是一个静态、一个动态：集成时定死，还是运行时商量。

### 1.8 小结

生（RS 的孩子申请先行）定源头，申请（双断言、6 参数直达）定交接，取消（同样的错、不同的处理）定收尾。三节合起来就是一句话：生的地方定申请的时机，源头在 RS 则调度在生前、申请在当时、取消分两种处理。

## 2 C 源码分析

### 2.1 申请的双断言（`utility.c:364-372`）

先声明局部变量（`364-367`：槽指针、返回值、是不是用户进程）→ 算域（`370`：非 `SYS_PROC` 即用户，域的算法）→ 双断言（`371-372`：用户无主/系统有主，域的边界，见 §1.2）。

### 2.2 六个参数直达（`utility.c:375-381`）

直达（`375-377`：6 个参数（调度器/被调度者/父亲=RS/队列/时间片/CPU）+ 回执定主（`&r_scheduler`））→ 失败返回（`378`：申请失败就返回）→ 成功即定（`381`：返回 `s`（成功即 `OK`），主已定在回执里）。注意：用户进程到这里断言已经死了（见 §2.1），直达的前提是域已分清。

### 2.3 槽里的 4 个值（`type.h:92-95`，概念引用）

调度器（`92`：`r_scheduler`，问谁）→ 队列（`93`：`r_priority`（负值另有含义，保留））→ 时间片（`94`：`r_quantum`）→ CPU（`95`：`r_cpu`）。4 个值的来源归槽配置（`../03-stage-rs/08-rs-slot-config.md` 的范围，本节只列 4 个值的名字，来源的细节移交）。

### 2.4 清理服务时的取消（`manager.c:455-465`）

分叉（`456`：detach 就跳过取消，recovery 的范围，附着另迁、不取消）→ 拆台先讲（`457-460`：拆台的打印）→ 取消（`461`：`sched_stop(主，号)`）→ 失败继续（`461-463`：失败打警告**继续走**，见 §1.4）→ 灭迹（`466` 续：`srv_kill`，取消后接着灭，灭不因取消失败而停）。

### 2.5 改槽时的取消（`request.c:335-345`）

先同步（`336-340`：`sys_getpriv` 先行，改前先同步）→ 取消（`342`：`sched_stop(主，号)`）→ 失败返回（`342-345`：失败打警告**带码返回**，见 §1.4）→ 改槽（`347` 续：`edit_slot`，取消成了才改，改在取消后）。取消和改槽的顺序：先取消、后改（取消失败改就不做，顺序即事务）。

### 2.6 生源的号（`com.h:61`，概念引用）

`RS_PROC_NR = 2`（生在谁家的号，见 §1.5 的证明）。号的用处：父亲栏（`376` 的 `parent`）+ 守土的判断（05 的 `is_system_proc` 经 10 的选择）+ 白名单的名字（04 的 `accept_message` 认 RS 的名字），一个号三处用，三处一源。

## 3 Rust 设计决策

Rust 改写不是把申请取消两函数照抄一遍，而是在吸收 Linux 直达和"处理跟着位置走"的做法后做的取舍。下面 D0–D3 每条都附 C 证据和 Rust 落点。

### D0 申请的判断沿用既有实现（确认）

- **C**：双断言（`371-372`）+ 6 参数直达（`375-381`）。
- **Rust**：`SchedulerConfig` + `sched_decision`（`os/servers/rs/src/sched.rs:30-141` 既有范围，4 个测试既有：`test_sched_decision_sys_proc_starts/user_proc_none_skips/passes_full_config/boot_defaults_match_c`）。
- **为什么**：确认即决策（既有的已经对了，再建模就是影子机器，和 13 的 D4 同一个道理）。本篇 §2.1–§2.2 作概念分析，§5.2 复用既有 4 个测试（只引名字、不重列，重复即多余）。

### D1 取消两种处理做成枚举

- **C**：清理失败打警告继续走（`manager.c:461-463`）对改槽失败带码返回（`request.c:342-345`）。
- **Rust**：`StopSite::{CleanupService, EditSlot}` + `StopOutcome::{Continue, Abort(i32)}` + `on_stop_result(site, result)`（`os/servers/rs/src/sched.rs` 新增，位置见 §4.2 符号表）。
- **为什么**：同样的错、不同的处理（处理跟着位置走，见 §1.4）；成功都是继续（`OK` 即成，两路都继续，成了就不用选）。有名可测（两种处理一个名字，5 个测试可锁，没有名字两个 `if` 散在各处，各管各的）。备选方案（调用处各写 `if != OK`）被否决了：处理散在两处（同样的错的处理应该有一个名字）。

### D2 生源的号复用一源

- **C**：`RS_PROC_NR = 2`（`com.h:61`）作父亲（`376`）。
- **Rust**：复用 `Endpoint::RS` 一源（不造新号，`SchedulerConfig::from_slot` 既有 `parent: Endpoint::RS`（`os/servers/rs/src/sched.rs:67`）；05/10 同源）。
- **为什么**：一源三用（05 的判断/10 的选择/14 的生，三处用一个源，改号改一处，Proposal #12 的惯例）。本篇不造新号（新号即副本，副本即漂移的来源）。

### D3 清理和改槽只描述、不扩写

- **C**：detach 跳过取消（`456-465`，recovery 的范围）+ 失败拆台（PM 的范围，见 13 §2.6）。
- **Rust**：只描述、不扩写（`CleanupDecision` 既有 detach 的判断；本篇不加新码，§2.4–§2.5 作概念分析）。
- **为什么**：判断已有主人（recovery 持有跳过取消的判断，再写即复述）；拆台的主人在 PM（13 既有，跨阶段不引代码）。

| ARCH | 落点 | 三处一致标注 |
|------|------|-------------|

## 6 过渡

本篇在 13（PM 交互）之后、99（全局概念）之前，是"申请取消"的归属层：13 讲用户进程的申请，本篇讲系统进程的申请取消；没有本篇，生源没名字（系统进程没证明），取消没两种处理（同样的错只能同样处理，就错了）。

```
13-pm-interaction: 申请三路 → 新建继承组装 → 回复照收 → 主跟着生死（用户进程的申请）
   │
   └─► 本篇：生源分域 → 双断言直达 → 清理继续走 → 改槽带码返（系统进程的申请取消）
           │                              │
           └─► 99-global-concepts：总表（5 种消息汇总，申请取消归位）
```

阅读顺序提示：如果关心"5 种消息三路申请的总表"，下一站 `99-global-concepts.md`（总表，申请取消归位）。
