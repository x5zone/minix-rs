# 11 — init_scheduling 与 balance_queues 队列平衡

本文介绍 SCHED 服务端的队列平衡机制。首先讲为什么需要恢复：时间片用完就降一级（08 的事），只降不升的话所有进程最后都会沉到底。然后讲恢复的节奏：每 5 秒一轮，每轮升一级，升到上限就停——降得快、升得慢，这个不对称就是为了防止振荡。最后讲定时器循环本身：启动时设一次闹钟，闹钟响了做恢复，做完再设下一次，循环往复。

前置阅读：`02-sched-message-surface.md`（主循环怎么收时钟通知）、`05-priority-timeslice-model.md`（优先级上限的含义）。

> 本章不讲什么：
> - 时钟中断的内核侧（滴答从哪里来、通知怎么投递）——见 `../01-stage-kernel/15-clock-timer.md`（本篇从"闹钟响了"之后开始讲）
> - `sys_setalarm` 的内核实现——调用语义见 §2.2/§2.3，实现归内核侧
> - 恢复之后怎么下发——见 `09-schedule-process.md`（本篇只讲恢复的判断）
> - 降级的完整流程（时间片用完降级是怎么走的）——见 `08-noquantum-nice.md`（本篇只拿降级做对照）

## 1 概念

### 1.0 引言与前置

本章回答三个问题：恢复什么（降得快、升得慢，为什么速率不对称）、什么时候做（5 秒一轮，定时器怎么定）、什么时候停（升到上限就停，谁是天花板）。本章假设读者已经知道主循环收通知的环（见 02）和上限的含义（见 05），只讲"平衡"这一个动作。

### 1.1 为什么要做队列平衡

只降不升，队列最后会整体下沉：时间片用完降一级（08），降了的再降，久了用户进程全沉到底，队列分层就名存实亡了——恢复就是下沉的反方向。但恢复不能无节制：如果恢复一步到位（一次直接升回上限），忙进程每轮都是"用完降、用完升"，在上限和降级位之间来回跳，恢复量等于降级量，等于没恢复——节制就是振荡的刹车。解决办法是降得快、升得慢：降级按时间片触发（用完立刻降），恢复按轮次触发（5 秒才升一级），两种不同的尺子一配，忙进程沉下去上不来、闲进程慢慢升回去，各归其位。

### 1.2 降级和恢复的不对称

降级（`schedule.c:99-101`，细节见 08）：`priority < MIN_USER_Q` 才加 1——时间片用完立刻降，不用等轮次，有下限（最低到 `MIN_USER_Q`，沉不到更低）。恢复（`schedule.c:360-362`）：`priority > max_priority` 才减 1——轮次到了才升，没轮次不升，有上限（最高到 `max_priority`，升不过上限）。两者的区别有三条：降级由事件触发（时间片用完），恢复由时间触发（5 秒一轮）；降级一次降完（一个时间片对应一级），恢复逐级回升（一次只升一级）；降级的底是 `MIN_USER_Q`，恢复的顶是各自的 `max_priority`（上限各不相同）。三条归成一句：速率不对称——不对称就是为了防振荡（见 §1.1）。

### 1.3 设闹钟、响铃干活、再设闹钟的循环

循环有三节：启动时设闹钟（`init_scheduling`，`334-343`：超时时间等于 5 秒乘时钟频率，调 `sys_setalarm` 设下去，闹钟没响之前什么都不做）→ 闹钟响了干活（CLOCK 通知到了，主循环 `45-51` 判断是通知就调恢复函数，环本身见 02，本篇只用它）→ 干完再设闹钟（`367-368`：恢复完重新设一次，不设的话闹钟只响一次、恢复只做一次，循环就断了）。循环的关键不在干活而在"再设"：设了之后就是"响铃→恢复→设闹钟→响铃→恢复"，自己续下去才停不下来。两次设闹钟写法一样、失败处理也一样（失败就 panic，`340-341` 对 `367-368`，函数没有返回值，失败就没有中间状态）。

### 1.4 恢复下发只动优先级和时间片

恢复时的下发是局部下发：`schedule_process_local` 就是 `PRIO|QUANTUM`（`32-33`），只动优先级和时间片，不动 CPU——恢复不重新选核（选核归第 10 篇，出生时选定，恢复时不再选）。局部有两层意思：语义上局部（恢复只管队列，CPU 位置是出生时定的，不因为恢复而迁移）；掩码上局部（和 `SCHEDULE_CHANGE_ALL` 的区别见 09，恢复用的掩码是全集的子集，和 `MIGRATE` 正好互补）。如果恢复时动 CPU，每 5 秒就全局重排一次位置，第 10 篇的台账每轮乱一次——局部就是不乱的保证。

### 1.5 默认策略和将来可换的位置

C 注释自己写了"这个默认策略以后会换"（`348-352`：英文原文说降下去、升回来，默认策略以后会改）。这句注释有两层意思：一是"策略可换"（默认两个字：逐级恢复是当前的选择，不是唯一的解）；二是"位置已留"（会换两个字：将来换哪里换——就是本篇 D2 的恢复判断函数）。策略的三个问题（恢复什么、何时恢复、何时停）里，"恢复什么"（逐级回升）可换，"何时"（5 秒一轮）可调，"何时停"（升到上限）不可换（上限是 05 定的界，换策略不换界）。Rust 的转述办法：策略写成默认的结构体，替换位置用注释标出来（D4，S-9）。

### 1.6 和其他 OS 的队列平衡对照

- **Linux**：周期均衡（`rebalance_domains` 逐级拉负载，闲核从忙核拉任务——和 5 秒一轮是同一个思路，只是粒度是运行队列不是优先级）和 CFS 的收敛（用完时间片权重下沉、周期性恢复——和"降得快升得慢"同一个思路，只是形式是累计运行时间不是升降队列）。防振荡是 SMP 的通用做法：恢复太勤快就会乒乓迁移（`balance_interval` 指数退避就是干这个的）。
- **Redox**：平衡做在调度器内部（时间片轮转加优先级，核内自己平衡），没有用户态的恢复循环。因为 Minix 的策略面在用户态，所以闹钟和循环都在服务端。
- **seL4**：内核定死策略（固定优先级轮转），没有用户态策略面——没有闹钟也没有恢复（策略定了就不需要恢复）。SCHED 的恢复是用户态策略面的自我修正：策略是活的，才需要平衡。

### 1.7 小结

降得快升得慢定下防振荡的节奏，设闹钟响铃干活再设闹钟保证循环不停，局部下发保证不乱换核，可替换位置留好将来可变。总结成一句话：超上限才恢复、恢复不过上限，这就是本篇的全部内容。

## 2 C 源码分析

### 2.1 超时时间的三个数（`schedule.c:16-18` + `sysutil.h:60`）

静态变量（`16`：`balance_timeout`，超时时间的本体）→ 人读的单位（`18`：`BALANCE_TIMEOUT 5`，5 秒，人的单位）→ 时钟频率（`sysutil.h:60`：`sys_hz()`，每秒多少滴答，时钟的单位）。超时时间等于人读的数乘时钟频率（`338`）：把秒换算成滴答数，闹钟才知道什么时候响。

### 2.2 启动时设闹钟（`schedule.c:334-343`）

函数开头（`334-336`：变量声明加返回值）→ 算超时（`338`：5 秒乘时钟频率，单位换算）→ 设闹钟（`340`：`sys_setalarm(balance_timeout, 0)`，相对时间的一次性闹钟，`0` 表示不是绝对时间，新闹钟替换旧闹钟）→ 失败就 panic（`340-341`：不是 `OK` 就直接 panic，函数没有返回值，失败没有中间状态）。调用点在出生时（`main.c:133`：`sef_cb_init_fresh` 最后调 `init_scheduling`，见 01）。

### 2.3 恢复函数的函数体（`schedule.c:348-369`）

英文注释（`348-352`：每 N 轮恢复一次、降下去升回来、默认策略以后会换，见 §1.5）→ 全表扫描（`358`：`NR_PROCS` 全扫，一个不落）→ 在用检查（`359`：只有 `IN_USE` 的表项才处理，04 的检查）→ 恢复判断（`360`：`priority > max_priority`，超上限才恢复，见 §1.7 的停止条件）→ 升一级（`361`：减 1，一次只升一级，见 §1.2）→ 局部下发（`362`：`schedule_process_local`，见 §1.4，**返回值不检查**，和 `103`/`284` 检查返回值的做法不一样，见 D3）→ 再设闹钟（`367-368`：和启动时同写法同失败处理，见 §1.3，循环的续接点）。

### 2.4 局部下发的掩码（`schedule.c:32-33`）

局部下发（`32-33`：`LOCAL = PRIO|QUANTUM`，只动优先级和时间片）→ 迁移下发（`34-35`：`MIGRATE = CPU`，只动 CPU）→ 全量下发（`22-30`：三个标志位全拼上是 `ALL`，见 09）。恢复用局部不用全量：恢复只管队列，不管核（见 §1.4），掩码本身就是语义的边界。

### 2.5 闹钟响了调恢复的链路（`main.c:44-51`，概念引用）

认出是通知（`45`：`is_ipc_notify`，认通知的环）→ 按来源分发（`46`：`switch(who_e)`）→ 闹钟响了调恢复（`47-48`：来源是 `CLOCK` 就调 `balance_queues()`）→ 其他不管（`50-51`：`default` 空分支，不是时钟就不恢复）。环本身归 02（本节只确认"铃响就恢复"这一点，恢复的函数体在 §2.3）。

### 2.6 降级的对照（`schedule.c:87-109`，概念引用）

取表项（`98`）→ 降一级（`99-101`：小于 `MIN_USER_Q` 才加 1，用完立刻降，有下限）→ 局部下发（`103`：同样局部下发但**检查返回值**，失败就返回，和 `362` 不检查的做法不一样）→ 返回成功（`106`：返回 `OK`）。本节只确认"降得快"这一点（降级的完整流程见 08，降和恢复对称的两半，一半在这里、一半在 §2.3）。

## 3 Rust 设计决策

Rust 改写不是把两个 C 函数逐行翻译，而是在参考 Linux 周期均衡和"降快升慢"这个通用思路之后做的取舍。下面 D1–D4 每条都给出 C 的证据和 Rust 的落点。

### D1 超时时间做成值对象

- **C**：`static unsigned balance_timeout`（`16`）+ `BALANCE_TIMEOUT 5`（`18`）+ `5 * sys_hz()`（`338`）。
- **Rust**：`BALANCE_TIMEOUT_SECS`（`os/servers/sched/src/balancer.rs:23`：人读的数，恒为 5）+ `Balancer::init(hz)`（超时时间用饱和乘算出来）+ `timeout_ticks()`（取值）。
- **为什么**：超时时间是算一次、读多次的值对象，不是服务；设闹钟和失败 panic 都归调用者（闹钟是环（02）的事，持表和下发分离见 06/09 的同样分法，本模块不碰闹钟、不决定生死）。饱和乘：正常频率下和 C 的值完全一样；离谱频率下钳住不绕回（10 的 D3 同样道理：绕回成 0 等于闹钟密不间断，那是 C 的意外，不是 C 的约定）。备选方案（`init` 里直接调 `sys_setalarm`）被否决了：算值和设闹钟混在一起（模式 A），设闹钟是环的事，不是值的事。

### D2 恢复判断做成纯函数

- **C**：`if (priority > max_priority) { priority -= 1; schedule_process_local(rmp); }`（`359-362`，返回值不检查）。
- **Rust**：`rebalance_one(max: Priority, current: Priority) -> Option<Priority>`（`balancer.rs:73`：超上限就返回高一级，否则返回 `None`）。
- **为什么**：判断（该不该恢复）和执行（扫表、下发、再设闹钟）分开——判断是纯逻辑，执行是持表人的事（04 的 D2、10 的 D1 同样思路：表在服务端，下发在边界，闹钟在环）。`Priority` 复用 `schedproc.rs` 的同一份（上限检查 `>= 16` 在构造时已经拦掉，见 06，所以恢复判断永远超不过上限）。`None` 就是"已到上限、没事可做"（C 用空 else 分支表示停止，Rust 用 `None` 表示停止，意思一样、说法不同）。备选方案（`fn rebalance(&mut SchedProc)` 读写一体）被否决了：判断和执行混在一起（读表项即改表项，模式 A）。

### D3 扫表、下发、设闹钟三件事分开

- **C**：`balance_queues` 把扫表加局部下发加再设闹钟写在一个函数里（`353-369`）。
- **Rust**：扫表归持表人（IN_USE 检查，见 04），下发归 09 `aggregate` 的调用者（PRIO|QUANTUM 的组合，见 09），再设闹钟归主循环（见 02）；本模块只给超时时间的值和恢复的判断。
- **为什么**：三件事三个主人（C 写在一起是单文件的写法，分开是服务端的写法，各持各的表、各干各的事）。返回值不检查的转述：恢复是尽力而为的周期纠偏（这次失败下轮再恢复，判断不因失败而改）；检查还是不检查是调用者的策略，本模块不替调用者定（返回 `Option` 两种策略都容得下：检查的人看 `Some` 的下发结果，不检查的人不管）。备选方案（三事一体 `balance_queues(&mut Table)`）被否决了：一体就得本模块持表（表在 04，那样就是模式 C 的重复）。

### D4 策略写成默认结构体

- **C**：注释写"默认策略以后会换"（`348-352`）。
- **Rust**：显式的 `Balancer` 默认策略结构体 + S-9 替换位置注释（第二套策略到了再立 trait）。
- **为什么**：C 的注释说了"可换"没说"已换"，忠实转述就是留位置不定型（结构体加注释标出替换位），不是提前抽象（只有一套实现的 trait，模式 25：一种行为不需要多态）。备选方案（`QueueBalancer` trait 加一套默认实现）被否决了：只有一种行为的多态（模式 25），新策略到了那天再立 trait，不早一天。

### ARCH 决策总表

| ARCH | 落点 | 三处一致标注 |
|------|------|-------------|
| S-9 队列平衡策略可替（默认结构 + 替换位） | `Balancer` + 替换位注释 | `balancer.rs` + 本文档 D4/§1.5 + plan §4/S-9 行 |

## 6 过渡

本篇在 10（选核）之后、12（内核契约）之前，解决的是"平衡"这一层：10 讲了出生时放在哪个核，本篇讲队列沉了怎么升回来；没有本篇，降了没人升（队列整体下沉），升了没节奏（来回振荡）。

```
10-pick-cpu-smp: 单核短路 → 系统进程放启动核 → 普通进程选最闲的 → 选中记账（选核这一层）
   │
```
