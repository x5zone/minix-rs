# 13 — SCHED 与 PM 的交互

本文介绍 PM 如何替进程向 SCHED 申请调度、退出时如何取消。首先，申请调用按调度器的身份分三路：没有调度器直接返回，内核调度直接调 `sys_schedctl`，用户态调度器才真正发消息。然后，新建进程（START）和 fork 子进程（INHERIT）带的内容不一样：新建带 4 个字段（含时间片），继承带 3 个字段（不带时间片，时间片从父进程来）。需要注意的是，回复里的调度器可能和你问的不是同一个，PM 照单全收，以回复为准。

前置阅读：`02-sched-message-surface.md`（5 种消息的版面）、`04-schedproc-table.md`（槽位有没有人的检查）。

分工声明：PM 侧 nice 系统调用的用户面（`do_getsetpriority`/`get_nice_value` 权限检查）归 `../04-stage-pm/16-scheduling.md`，那是主权文档。本文只取 `sched_nice` 服务端消息面：PM 把 nice 换算成优先级后如何组装消息。PM 表（`mproc`）本身的实现细节本文只引用，不重复。

> 本章不讲什么：
> - PM nice 系统调用用户面（`do_getsetpriority`/`get_nice_value` 权限检查）——见 `../04-stage-pm/16-scheduling.md`（本文只取 `sched_nice` 服务端消息面）
> - RS 调用面（`sched_init_proc` 系统进程的申请）——见 `14-rs-interaction.md`（本文只讲 PM 的申请）
> - 服务端检查（`accept_message`/槽位填充/EBADCPU 重试）——见 `06-start-scheduling.md`（本文只讲申请的形状）
> - `_taskcall` 投递机制的细节——那是调用者传输层的话题，本文只约定组装的内容

## 1 概念

### 1.0 引言与前置

本文回答三个问题：第一，按调度器的身份不同，申请走哪条路，哪些路不需要发消息；第二，新建和继承两种消息，内容有什么区别；第三，回复里的调度器写谁，PM 怎么处理。本文假设读者已经知道 5 种消息的版面（见 02）和槽位检查（见 04），只讲"PM 如何申请"。

### 1.1 为什么 PM 要申请和取消

新建的进程只有一个 endpoint，没有队列位置（priority）也没有时间片（quantum），没有这两样就跑不起来，所以生前必须先申请（申请就是"给个队列位置、给份时间片"的意思）。退出的进程队列位置还占在表里（槽位还是 `IN_USE`），不取消就腾不出位置给后来的进程，所以死前必须先取消（取消就是"把位置销掉"的意思）。申请和取消是生死两道门：生了要进门（`sched_start`/`sched_inherit` 登记），死了要出门（`sched_stop` 注销）；两道门缺一不可（只登记不注销表会满，只注销不登记表永远是空的）。

### 1.2 申请按调度器身份分三路

申请先看调度器是谁，分三路走（`sched_start.c:58-76` + `sched_stop.c:16-17`）。第一路是没有调度器（`NONE`：没人管，`58-59`/`16-17` 直接返回 `OK`，不用发消息）；第二路是内核调度（`KERNEL`：内核自己管，直接调 `sys_schedctl` 传参数（`70-76`），不走消息）；第三路是用户态调度器（发消息申请（`80-96`），消息里带 4 个值）。三路的区别：第一路是"完了"（没事可做），第二路是"直达"（参数直接给内核，不走消息），第三路是"发消息"（写信给 SCHED）。三路里有两路不发消息：短路的就是不发消息的路，消息只是第三路的形状。

### 1.3 新建和继承带的内容不一样

新建（START）带 4 个字段（`81-84`：endpoint/parent/maxprio/quantum，时间片跟着走）；继承（INHERIT，fork 出来的孩子）带 3 个字段（`25-27`：endpoint/parent/maxprio，时间片空着，从父进程继承）。两种消息用同一个消息体（`mess_lsys_sched_scheduling_start`，先 `memset` 清零（`24`/`80`）），继承的时间片栏恒为零（零就是"没有时间片"的线上形状，06 的 INHERIT 分支本来就不读时间片，读零和不读是一个效果）。内容的有无是生和死的差别：新建没有可继承的所以自己带（时间片没来源，带着就是来源），继承有父进程可抄所以不带（父进程就是来源，再带就多余了）。

### 1.4 回复里的调度器照单全收

注意注释里的提醒（`33-39`/`90-96`）：回复的调度器"可能不是你问的那个"（你问的 SCHED 可能把申请转给了另一个 SCHED 再回你）。申请方没法预知转发链的终点（注释明写了 "might have forwarded"，问的时候写的名字不是最终的名字）；最终的名字在回复栏里（`scheduler`），PM 照着写（`*newscheduler_e = 回复`，`39`/`96`）。回复是谁，主就是谁（`mp_scheduler` 存的就是回复的值，主跟着回复走）。

### 1.5 主记录跟着生死走

主记录存在 `mproc.h:78` 的 `mp_scheduler` 里，走一个来回：空（刚 fork 还没申请：`forkexit.c:101` 先断言是空）→ 有（生了就申请：`PRIV_PROC` 的孩子默认主是 `SCHED_PROC_NR`（`101-102`），回复是谁主就是谁）→ 空（死了就取消：`sched_stop`（`425`，失败只打印警告、不拦着退出）→ 主记回空（`441`））。主跟着生死走（活着就有主，死了就没主，主是生死的影子）。初始值分两种（`main.c:199,213`）：INIT 生下来就是内核调度（`KERNEL`，第一个进程特殊），系统进程生下来是空（`NONE`，RS 的孩子，PM 不管，见 14）。

### 1.6 INIT 是个特例

系统刚启动时的形状（`pm/schedule.c:20-50`）：把表扫一遍（`IN_USE` 且不是 `PRIV_PROC` 的，也就是除系统进程外，系统进程归 RS 管），断言两件事（`34`：在场的只有 INIT；`36`：它的父进程是自己（`parent == self`），第一个进程没有父亲，自己当自己的父亲），按通用流程申请（`37-43`：`sched_start(SCHED_PROC_NR, self, self, USER_Q, USER_QUANTUM, -1)`，流程是通用的，值是特殊的：父亲是自己，队列是缺省的 `USER_Q`（见 05），时间片是缺省的 `USER_QUANTUM`（见 05），CPU 传 `-1` 表示"不动"），失败只打印警告（`44-47`：申请失败不拦着启动，警告一句了事）。特例即源头（后来的 fork 全是抄 INIT 的时间片，源头在 INIT，后面的全是它的后代）。

### 1.7 和其他 OS 的对照

用大白话对照一下：

- **Linux**：进程创建时调 `sched_fork` 抄父进程的策略，和这里的继承（时间片从父进程来）是同一个意思；进程退出时调 `sched_exit` 销掉位置，和这里的取消对应；`SCHED_DEAD` 状态（死了但位置还没腾出来）说明"取消"这一步省不掉。`sched_setscheduler` 改策略（主记录跟着变）和"回复是谁主就是谁"对应。
- **Redox**：进程生死都在内核里（`create_process` 直接给队列位置，申请在内核内部，没有发消息这一步）；Minix 的申请是用户态策略面的形状（策略在 SCHED，所以申请要发消息，消息即申请）。
- **seL4**：调度上下文在系统集成时配好，运行时不再申请；SCHED 的申请和取消都是运行时消息（生了就申请、死了就取消）。区别就是一个静态、一个动态：集成时定死，还是运行时商量。

### 1.8 小结

申请（按调度器身份分三路，短路的不发消息）选走哪条路，内容（新建 4 个字段、继承 3 个字段、同一个消息体）定消息的形状，主记录（回复是谁主就是谁、生死来回）守住名字。三节合起来就是一句话：申请是生死的门，生了登记、死了注销，主记录跟着生死走。

## 2 C 源码分析

### 2.1 三个申请函数（`sched_start.c:11-97` + `sched_stop.c:9-29`）

继承函数（`11-41`：5 个断言（`18-22`：三个 endpoint 非负、上限在界内、指针非空）→ 清零（`24`）→ 填 3 个字段（`25-27`）→ 发送（`30`：`SCHEDULING_INHERIT`）→ 读回复（`39`））；新建函数（`46-97`：选路（`58-76`，见 §2.2）→ 清零填 4 个字段（`80-84`）→ 发送（`87`：`SCHEDULING_START`）→ 读回复（`96`））；取消函数（`sched_stop.c:9-29`：短路（`16-17`）→ 2 个断言（`20-21`）→ 清零只填 endpoint（`23-24`）→ 发送（`25`：`SCHEDULING_STOP`））。三个函数同一个套路（断言/清零/发送/读回复，取消没有读回复，因为取消不产生新的主）。

### 2.2 选路检查（`sched_start.c:58-76` + `sched_stop.c:16-17`）

新建的短路（`58-59`：`NONE` 直接 `OK`，不发消息）；内核直达（`70-76`：`KERNEL` 就调 `sys_schedctl(FLAG_KERNEL, ...)`（`71-72`）→ 失败返回错误码（`73`）→ 主记为内核（`75`：`*newscheduler_e = KERNEL`））；发消息（`80-96`：走消息，见 §2.3）；取消的短路（`sched_stop.c:16-17`：`KERNEL` 或 `NONE` 直接 `OK`，内核管的退出时自己了结，没人管的本来就没什么可取消的）。取消短路有两个条件（内核管的退出即了结，另有接管或进程即死，见 `14-15` 的注释；没人管的无可取消）。

### 2.3 新建和继承的内容与回复（`sched_start.c:24-39,80-96`）

继承填 3 个字段（`25-27`：endpoint/parent/maxprio，时间片空着）→ 新建填 4 个字段（`81-84`：上面 3 个 + quantum，时间片跟着走）→ 转发注释（`33-38`/`90-95`：回复可能和问的不一样，"might have forwarded"）→ 照着回复写（`39`/`96`）。类型的差别：继承的 `maxprio` 是 `unsigned`（`12`），新建的 `maxprio`/`quantum` 是 `int`（`49-50`，断言 `>= 0`/`> 0`（`64`/`66`）），新建的内容有下界，继承的没有下界（继承的界在父进程的时间片，不在消息栏里）。

### 2.4 PM 的申请面（`pm/schedule.c:20-112`）

首次申请（`20-50`：扫表（`IN_USE` 非 `PRIV`）→ 双断言（`34` 只有 INIT 在场/`36` 父亲是自己）→ 按通用流程申请（`37-43`：`USER_Q/USER_QUANTUM/-1`）→ 失败打警告（`44-47`））；fork 后申请（`55-83`：nice 换算成队列（`59-61`，换算规则见 05）→ 继承来源二选一（`67-76`：`PRIV_PROC` 的父亲就抄 INIT（`73`，附父亲无主的断言 `72`），否则抄亲生父亲）→ 发继承消息（`79-83`））；改 nice（`89-111`：内核管的拒绝（`98-99`：`KERNEL`/`NONE` 返回 `EINVAL`，内核管的队列不能这么改，想改走内核的门，13 不设这个门）→ 换算（`102`）→ 发消息（`105-108`：endpoint/maxprio 两个字段（`mess_pm_sched_scheduling_set_nice`）））。

### 2.5 生死来回（`forkexit.c:101-102,425,438-441`，概念引用）

默认主（`101-102`：`PRIV_PROC` 的孩子默认 `SCHED_PROC_NR`（附无主的断言 `101`），RS 生的孩子 PM 给个默认主（RS 不管非系统进程，见 `97-99` 的注释））→ 死时取消（`425`：`sched_stop(主，号)`，失败打警告（`426-433`：取消失败的麻烦在后头（同一个位置再登记新人会搞混），警告一句了事））→ 主记回空（`438-441`：`mp_scheduler = NONE`，死了就没主）。本节只讲来回的三节，表的实现归 PM，见 D4。

### 2.6 主记录的初值与申请失败（`pm/main.c:199,213,372-380`，概念引用）

初始两条路（`199`：INIT 的孩子（就是 INIT 自己）记为内核（`KERNEL`）→ `213`：系统进程记为空（`NONE`））→ 生后申请（`372-373`：不是内核管、不是空，就调 `sched_start_user`（在 VFS 回复之后先生后申请，先生、后申请））→ 申请失败拆台（`376-380`：申请失败主记回空（`380`：不用再取消）+ 拆掉刚生的进程（`exit_proc`）+ 告诉父亲失败（`reply -1`），申请失败的进程不留，留下来就是没主的孤儿）。本节只讲初值和失败策略，表的实现归 PM，见 D4。

## 3 Rust 设计决策

Rust 改写不是把三个函数两百行照抄一遍，而是在吸收 Linux"生了登记、死了注销"和"按身份选路"的做法后做的取舍。下面 D1–D4 每条都附 C 证据和 Rust 落点。

### D1 申请三路做成枚举

- **C**：`NONE → OK`（`58-59`）/ `KERNEL → sys_schedctl`（`70-76`）/ 其余发消息（`80-96`）；取消是 `KERNEL||NONE → OK`（`sched_stop.c:16-17`）。
- **Rust**：`SchedulerSel::{None, Kernel, Server(Endpoint)}`（`os/servers/sched/src/client.rs:28`）+ `route_start`（`client.rs:74`）/ `route_stop`（`client.rs:103`）（短路做成 `Done` 变体）。
- **为什么**：短路是选路的结果（调用者 match 三路全覆盖，每路都有归宿，不会漏）；C 的提前返回是单函数的写法（返回后没有值，"完了"和"直达"的区别湮没了）。`None` 和 `Kernel` 是两条不同的路（完了不发消息，直达带参数走 `sys_schedctl`，参数即 12 的组装形状）。备选方案（`if sel == NONE return Ok` 直译）被否决了：捷径不是路由，返回后调用者不知道去哪了。

### D2 新建和继承做成两个包

- **C**：新建 4 个字段（`81-84`）对继承 3 个字段（`25-27`，时间片空着）；同一个消息体（`MessLsysSchedSchedulingStart`，`memset` 清零）。
- **Rust**：`StartPack`（`client.rs:115`：4 个字段）/ `InheritPack`（`client.rs:148`：3 个字段）+ `wire()` 组装同一个消息（继承的时间片置零，06 的 INHERIT 分支本来就不读时间片，读零和不读是一个效果）。
- **为什么**：内容的有无是生和死的差别（新建没处抄所以自己带，继承有父进程可抄所以不带，时间片的来源不同，消息的形状不同）；两个包让"继承带时间片"写不出来（类型即约定）。备选方案（一个包 + `quantum: Option`）被否决了：继承必无、不是可选（Option 是说可有可无，实际继承必无，语义比现实弱）。

### D3 回复照着收

- **C**：`*newscheduler_e = 回复.scheduler`（`39`/`96`）+ 转发注释（`33-38`/`90-95`）。
- **Rust**：`read_scheduler(reply)`（`client.rs:196`：回复是谁主就是谁）。
- **为什么**：申请方没法预知终点（转发链终点不可预知，收自己问的即瞎猜，收回复的即事实）；写回 PM 表的事（`mp_scheduler` 的写是 PM 表的事，init/fork 本来就有），SCHED 这一侧只给读、不给写，读写分开（和 12 的 D3 同一个道理）。备选方案（读完检查"回复 == 问的"）被否决了：检查即否定转发（转发是合法形状，检查即拒绝合法）。

### D4 生死来回只描述、不建模

- **C**：`NONE → SCHED → NONE` 的来回（`101-102`/`425`/`441` + 初值 `199`/`213` + 失败拆台 `372-380`）。
- **Rust**：只在文档里讲清楚（本章 §2.5–§2.6 是来回的全分析；不建状态机，这是本决策定的）。
- **为什么**：来回的表在 PM 那边（三处持表本来就有实现，SCHED 这一侧再建模就是影子机器，和 12 的 D4 同一个道理：第二个主即死代码的来源）。备选方案（建一个 `MpLifecycle` 枚举状态机）被否决了：影子机器，约定用文档立，不用代码复述。
