# 10 — pick_cpu 与 SMP CPU 选择

本文介绍 SCHED 服务端怎么给进程选 CPU。首先按固定顺序走三条规则：机器只有一个 CPU 就直接用启动 CPU，是系统进程就放在启动 CPU，其他情况选负载最低的可用 CPU。然后讲负载计数器这本台账是怎么记的（选中加一、释放减一、坏核标死亡）。需要注意的是，单核机器和"系统进程"这两条短路规则是有优先级的，顺序不能换。

前置阅读：`01-sched-init-main.md`（机器信息从哪里来）、`05-priority-timeslice-model.md`（怎么判断是不是系统进程）。

> 本章不讲什么：
> - 内核 SMP 迁移机制（运行中进程怎么换核）——见 `../01-stage-kernel/16-smp.md`（本篇只讲 SCHED 这边第一次选核）
> - 选好之后怎么下发——见 `09-schedule-process.md`（本篇只给出选中的值）
> - EBADCPU 重试循环的细节——见 `06-start-scheduling.md`（本篇只讲"标死亡"这个动作本身）

## 1 概念

### 1.0 引言与前置

本章回答三个问题：选 CPU 的三条规则各管什么（分别对应哪种进程）、负载台账跟着谁增减（选中、释放、标死亡）、单核情况和编译开关是怎么处理的。本章假设读者已经知道机器信息怎么取到（见 01）和系统进程怎么判断（见 05），只讲"选核"这一个动作。

### 1.1 为什么要选核

单核机器没什么好选的，选出来的永远是 CPU 0，选核函数退化成常量。多核机器必须选：新进程出生时还没有位置，要么全挤在一个核上（启动核独扛全局，其他核闲着），要么按负载分摊到各个核上。选核就是干分摊这件事的：以每个核的负载计数器为依据，负载最低的核中选。另外还有一条独立的规则：从 RS 出生的系统进程固定放在启动核上——这不是偏心，而是"在哪出生就在哪跑"，和 06 里"新建进程暂时固定"的处理是同一个原因（内核侧不随便迁核）。

### 1.2 三条规则的顺序

三条规则按固定顺序匹配，命中第一条就返回：第一，机器只有一个 CPU 就用启动核（单核世界里没有选择，直接短路）→ 第二，是系统进程就用启动核（用 05 的判断，系统进程优先于负载均衡）→ 第三，普通进程选负载最低的可用非启动核（负载最低者得；负载一样取编号小的，因为比较用的是严格小于，先到的最小值一直留着；如果没有比启动核更优的，就回退到启动核，回退不是特例，而是初值本来就设成了启动核）。顺序不能换：单核时连系统进程都不用判断，结果一样但少一次判断；系统进程不能进第三条，因为"固定放启动核"优先于"均衡"。

### 1.3 负载台账记哪三件事

台账记三件事：选中就加一（`cpu_proc[cpu]++`，选中即记账）→ 释放就减一（进程退出时减，见 07，退出即销账）→ 坏核标死亡（重试循环里标上 `CPU_DEAD`，见 06，只标不增减）。记账要收支相符（07 讲过这种"两边各记一本"的思路）；账记错了选择就偏了（比如释放时漏减，某个核的计数永远偏大，以后就再也选不中它）。

### 1.4 "死亡"的两种写法

C 里"死亡"有两种写法：一个是 `CPU_DEAD` 标记（重试循环标上的真死亡），另一个是 `cpu_is_available` 宏（写的是 `>= 0`，但计数器是无符号数，这个比较恒为真，所以它 guard 的 `continue` 永远触发不了）。第二个宏不是 bug，而是个没写完的抽象：真正的死亡过滤其实发生在后面的负载比较里（死核的计数值被标成无符号最大值，严格小于的比较永远选不中它）。两道门一明一实，起作用的是后面那道。Rust 取了起作用的那道：`None` 就是不可用（见 D2）。

### 1.5 编译开关退化成运行时判断

C 里有两套写法：编译期（`#ifdef CONFIG_SMP`，有这个开关才走三条规则，否则直接返回 0）和运行时（`processors_count`，开关变成了一个数：单核走第一条，多核走三条）。这是一种演进（S-5：编译开关变成运行时检测，架构层面的 trait 见 01-stage-kernel/16，本篇只讲 SCHED 这边的数字）。另外注意区分：非 SMP 编译直接返回 `cpu = 0`（连核的概念都没有），SMP 单核返回 `bsp_id`（有一个核的位置，值多半也是 0，但意思不一样）。

### 1.6 和其他 OS 的选核机制对照

- **Linux**：`select_task_rq` 做的事和这里的三条规则是对应的：按调度域选空闲核（和"选负载最低"同一个思路），再用亲和性掩码限制可选范围。Linux 有亲和性掩码所以有限制范围的概念，SCHED 没有实现那套（见 D 位的讨论），所以没有。`cpu_proc[]` 这本台账对应 Linux 每个运行队列的进程数（都是按核记数，一个记在服务端数组里，一个记在队列结构里）。
- **Redox**：选核做在调度器内部（按亲和性和负载自己选），没有一张独立的负载表。因为 Redox 的策略面和执行面在同一层，不需要像 Minix 这样在服务端单独记一本台账。
- **seL4**：线程绑哪个核由 TCB 的亲和性配置决定（配好就不变，是静态配置，没有动态均衡）。SCHED 这边是动态均衡（每次新建都看当前负载），一个静、一个动，这是微内核两种不同分工的体现：均衡放用户态做，还是配置放内核里定。

### 1.7 小结

三条规则按顺序定位置（单核短路、系统进程放启动核、普通进程选最闲的），负载台账记增减标死亡，死亡的真过滤在负载比较里，编译开关退化成运行时数字。总结成一句话：选择读台账做决定，台账错了选择就错，所以记账必须收支相符，这就是本篇的全部内容。

## 2 C 源码分析

### 2.1 负载表和哨兵（`schedule.c:37-46`）

死亡标记（`37`：`CPU_DEAD=-1`）→ 可用性宏（`39`：`>= 0` 的恒真比较，见 §1.4）→ 缺省时间片（`41`：`DEFAULT_USER_TIME_SLICE`，含义见 05，这里只列位置）→ 系统进程判断（`44`：`is_system_proc`，含义见 05，这里只管调用）→ 负载表（`46`：`cpu_proc[CONFIG_MAX_CPUS]`，台账本体）。

### 2.2 三条规则的函数体（`schedule.c:48-78`）

函数开头（`48-52`：两个局部变量 `cpu/c`，负载初值设为无符号最大值 `cpu_load = (unsigned)-1`）→ 单核短路（`54-57`：`count == 1` 就用启动核）→ 系统进程短路（`60-63`：从 RS 出生的就用启动核）→ 初值设为启动核（`66`：`cpu = bsp_id`，回退的初值）→ 选最闲的循环（`67-75`：跳过死核（`68-70`：68 行注释，69 行判断，70 行 `continue`，恒真宏守的其实是这里）→ 跳过启动核（`71` 行前半）→ 严格更闲才替换（`71` 行后半，平局时留小编号））→ 选中并记账（`76-77`：写进表项、计数器加一）。

### 2.3 编译开关的两套写法（`schedproc.h:14-16` + `schedule.c:78-80`）

缺省单核（`schedproc.h:14-16`：没有 SMP 配置时 `CONFIG_MAX_CPUS = 1`）→ 非 SMP 直接返回 0（`schedule.c:78-80`：`#else` 分支里 `cpu = 0`，没有核的概念）。

### 2.4 机器信息的结构（`type.h:122-125`）

核数（`123`：`processors_count`，运行时读到的数，见 S-5）→ 启动核（`124`：`bsp_id`，系统进程的固定位置）→ 后面还有 apic 等字段（`125` 起，和本篇语义无关）。

### 2.5 标死亡的联动（`schedule.c:227-230`，概念引用）

标死亡（`229`：`cpu_proc[cpu] = CPU_DEAD`）→ 重新选（`230`：再调一次 `pick_cpu`，循环本身见 06）→ 本节只确认"标死亡"这个动作存在（标死之后再选，死核在负载比较里天然落选，不需要额外判断）。

## 3 Rust 设计决策

Rust 改写不是把 C 函数逐行翻译，而是在参考 Linux 选最闲核的做法和台账已有的结论之后做的取舍。下面 D1–D4 每条都给出 C 的证据和 Rust 的落点。

### D1 三条规则做成纯函数

- **C**：`pick_cpu(proc)`（`48-78`：读表项、做判断、写回核号，一体）。
- **Rust**：`pick(is_system: bool, topo: &MachineTopology, loads: &[CpuLoad]) -> u32`（`os/servers/sched/src/cpu.rs:69`：是不是系统进程由调用者传进来，拓扑显式传参，负载只读一个视图）。
- **为什么**：系统进程的判断在 05 已经有了，调用者传结论进来就行，重判一遍就是两处真相来源；拓扑显式传参（S-5：运行时数字做参数，不读全局，读全局就是隐式参数，隐式参数不好测）；负载传切片视图（调用者持有表，04 的 D2 同样思路，`&[Option<u32>]` 能表示任意核数，不需要定长泛型）。备选方案（传整个表项和机器结构、照 C 直译）被否决了：判断和选择混在一起（读表项等于重判系统进程，模式 A）。

### D2 死亡用 `None` 表示

- **C**：`CPU_DEAD=-1`（`37`）+ 恒真宏（`39`，永远触发不了）+ 负载比较里的真过滤（`71`）。
- **Rust**：`CpuLoad = Option<u32>`（`cpu.rs:37`）+ `is_available`（`cpu.rs:47`：`is_some` 就是真过滤）+ 选择时跳过 `None`。
- **为什么**：取起作用的那道门（恒真宏是个没写完的抽象，留着它后人会信错门）；哨兵收进类型（S-4：`-1` 变成 `None`，和 05 的 D5 同一个道理）；负载比较天然拒绝死核（跳过 `None` 和"C 里最大值选不中"效果一样，路不同、果同，06 的 D3 同样思路）。备选方案（保留 `CPU_DEAD: u32 = u32::MAX` 常量）被否决了：哨兵进类型就是模式 17 的问题。

### D3 计数用饱和加减

- **C**：`++`（`77`）/`--`（07 的 `130`）无符号直接算，溢出会绕回。
- **Rust**：`add_load`/`release_load`（`cpu.rs:112,124`：饱和加减） + `mark_dead`（`cpu.rs:100`：置 `None`）。
- **为什么**：正常路径（每次选中都有一次释放配对）和 C 的结果完全一样；非正常路径（比如释放了两次）停在 0，不会绕回成极大值——绕回成极大值会被负载比较误读成死核（见 §1.4 的比较），那是 C 的意外，不是 C 的约定；标死亡就是置空（什么时候标由 06 的重试循环决定，这个函数只执行标记）。备选方案（用 `wrapping_add/sub` 逐行贴着 C 写）被否决了：逐行贴合保住的是意外（模式 65），不是语义。

### D4 编译开关改成运行时参数

- **C**：`#ifdef CONFIG_SMP`（`50/78`：两套写法）+ `CONFIG_MAX_CPUS`（`schedproc.h:14-16`）。
- **Rust**：`MachineTopology{processors_count, bsp_id}`（`cpu.rs:24`：对照 `type.h:122-125`）+ 单核短路（`count <= 1` 就用启动核，非 SMP 直接返回 0 是这个式子的特例，见 §1.5）。
- **为什么**：开关变成数字（S-5：编译开关改运行时检测；`bsp_id` 越界就钳进视图范围，只钳不 panic）；空视图返回 0（约定：调用者永远传真实表，到不了这个分支，不断言）。备选方案（`#[cfg]` 写两套实现）被否决了：行为差别应该体现在值上，不应该体现在编译配置上（模式 14）。

### ARCH 决策总表

| ARCH | 落点 | 三处一致标注 |
|------|------|-------------|
| S-4 CPU 负载追踪（哨兵类型化） | `CpuLoad` + `is_available` + `mark_dead` | `cpu.rs:37,47,100` + 本文档 D2 + plan §4/S-4 行 |
| S-5 SMP 编译期开关（运行时化） | `MachineTopology` + 单核短路 | `cpu.rs:24` + 本文档 D4 + plan §4/S-5 行 |
