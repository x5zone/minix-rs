# 09 — schedule_process 参数下发与内核对接

本文介绍 SCHED 服务端如何把调度参数下发给内核。首先用掩码决定"哪些字段要下发"，然后把没选中的字段填成 `-1`（表示保持不变），再算出 `niced` 备注并打包成一条消息发出去。需要注意的是，内核收到后会做三道检查，检查通过才真正写入进程表。本文还会讲清楚容易混淆的一点：SCHED 这边的 `schedule_process` 和内核那边的 `sched_proc` 是两个不同的函数，只是名字像而已。

前置阅读：`05-priority-timeslice-model.md`（参数的来源和 `niced` 的含义）、`06-start-scheduling.md`（新建进程时全量下发的用法）。

> 本章不讲什么：
> - 调度器注册语义（`p_scheduler` 是怎么确定的）——见 `12-kernel-interface.md`（本篇只用到"调用者必须是该进程的调度器"这一条检查）
> - CPU 选择策略（`pick_cpu` 怎么看负载、怎么读 `cpu_proc[]`）——见 `10-pick-cpu-smp.md`（本篇只用到"先选好 CPU 再下发"这个顺序）
> - 各个 handler 什么时候调下发（新建、退出、降级、改优先级各自的时机）——见 `06-start-scheduling.md`/`07-stop-scheduling.md`/`08-noquantum-nice.md`（本篇只讲下发本身的实现）

## 1 概念

### 1.0 引言与前置

本章回答三个问题：下发时带哪些字段（掩码说了算）、没带的字段怎么办（填 `-1` 表示保持）、内核收到后做什么（先检查、再写入）。本章假设读者已经知道参数从哪里来（见 05）和新建进程时全量下发长什么样（见 06），只讲"下发"这一个动作是怎么实现的。

### 1.1 为什么下发要分成两层

SCHED 知道"参数应该是什么"，内核知道"参数现在是什么"，两层之间没有共享内存，只能靠发消息沟通。下发的完整链条是：在 SCHED 侧按掩码挑出字段、打包（调用 `sys_schedule` 发消息）→ 内核侧检查 endpoint、检查权限、检查取值范围 → 内核把数值逐个写入进程表。打包在服务端、写入在内核，中间的消息体（`mess_lsys_krn_schedule` 的五个字段）就是两层的分界面。如果没有这条消息，两边就各记各的账，对不上；有了它，每发一次、内核确认一次，两边就一致了。

### 1.2 掩码决定带哪些字段

掩码一共有四种形状：全带（`ALL`：优先级、时间片、CPU 三个都下发，新建进程时用）→ 只带数值（`LOCAL`：下发优先级和时间片，不动 CPU，进程还在册期间的常规操作）→ 只带 CPU（`MIGRATE`：只下发 CPU，不动数值，迁移 CPU 时用）→ 空掩码（什么都不带，代码里留着这个形状，但实际没人发）。掩码的好处是见名知意：读到调用点写着 `LOCAL`，就知道这里肯定不会动 CPU，不用再去翻函数体确认。

### 1.3 `-1` 表示"保持不变"

这里有一个约定：掩码没选中的字段填 `-1`（对应 `schedule.c` 的 `307/312/317` 三处），内核看到 `-1` 就跳过这个字段（对应 `system.c` 的 `680-688`）。两边用同一个哨兵值，一处约定、两处遵守。需要注意的是，这个 `-1` 和 05 里缺省 CPU 的 `-1`（`USER_DEFAULT_CPU`）长得一样、意思完全不同：那边是"没选就用默认值"，这边是"没带就不改"。读代码时不要把两者搞混。

### 1.4 `niced` 备注跟着每条消息走

还有一条规则：只要进程的优先级上限超过了默认队列（`niced = max > USER_Q`，见 `319` 行，定义复用 05 的结论），这条备注就跟着消息一起发。这个备注不属于掩码管的字段，所以即使是空掩码也会带上。内核用它来决定置不置 `MF_NICED` 标记（`692-694`）：它只是一个记录，不会导致参数被拒绝，不影响检查的结果。

### 1.5 内核先做三道检查，再分四步写入

内核收到消息后，先检查、再写入，顺序不能反（如果先写了再检查，不合法的值就已经污染进程表了）。三道检查是：endpoint 是否合法（`isokendpt` 失败就返回 `EINVAL`，见 `do_schedule.c:14-15`，endpoint 都对不上就不知道往哪写）→ 调用者是不是该进程的调度器（`caller != p_scheduler` 就返回 `EPERM`，见 `20-21`，调度器身份就是权限本身）→ 取值范围检查（优先级和时间片的范围见 `system.c:645-650`，CPU 合法性见 `652-655`，越界就拒绝）。检查全过之后分四步写入：先把进程置上 `RTS_NO_QUANTUM`（让它先出队，见 `674-678`）→ 逐个写入非 `-1` 的字段（`-1` 的跳过，见 `680-688`）→ 按 `niced` 置或清 `MF_NICED`（见 `692-694`）→ 清掉 `RTS_NO_QUANTUM` 让进程重新入队（见 `697`），最后返回 `OK`。

### 1.6 `schedule_process` 和 `sched_proc` 的命名对照

这里有个容易混淆的地方：`schedule_process`（SCHED 服务端，负责按掩码挑字段、打包）和 `sched_proc`（内核，负责检查、写入），名字只差一个后缀，但住在完全不同的两层。前者只读调用者传进来的表项值，不直接碰内核进程表；后者只读从消息里拆出来的四个参数，不知道掩码的存在。分工也很清楚：掩码用错了（比如该带的没带）是服务端的问题，写入时越界是内核检查要拦的问题，查问题时先看分层对照表（见 §2.6）就知道该看哪边。

### 1.7 和其他 OS 的下发机制对照

- **Linux**：`sched_setattr` 做的就是"检查加写入"这两件事，和这里的三道检查加四步写入是对应的。Linux 没有 `-1` 保持位，调用者想只改一个字段，得先把旧值读回来、改一项、再整体下发（读-改-写），效果一样，只是多一次往返。Linux 改运行中进程的参数时同样要先出队、改完再入队，和这里先置 `RTS_NO_QUANTUM` 是一个思路。
- **Redox**：调度器和进程表在同一层，改参数就是直接改内存，没有跨层消息。所以 Redox 没有"打包下发"这个动作——正是因为 Minix 把策略面（SCHED）和执行面（内核）分成了两层，才需要这条消息。
- **seL4**：系统调用靠 capability 鉴权（没 capability 就 fault），相当于把"endpoint 合法"和"有没有权限"两道检查合成一道。而 Minix 是分开的两道门：endpoint 对不上返回 `EINVAL`，不是调度器返回 `EPERM`，分开返回的好处是调用者能分清失败原因（这和 04 的 D2 是一样的思路）。

### 1.8 小结

掩码决定下发哪些字段，`-1` 约定解决"没带的字段怎么办"，`niced` 备注每条消息都带上，内核先做三道检查再分四步写入。总结成一句话：打包在服务端、写入在内核，消息体就是分界面，这就是本篇的全部内容。

## 2 C 源码分析

### 2.1 掩码常量的定义（`schedule.c:22-35`）

三个标志位（`22-24`：`SCHEDULE_CHANGE_PRIO/QUANTUM/CPU`，值分别是 `0x1/0x2/0x4`）→ 全集（`26-30`：`SCHEDULE_CHANGE_ALL` 是三个标志位的或）→ 局部掩码（`32-33`：PRIO 和 QUANTUM 的组合，08 用的就是这个形状）→ 迁移掩码（`34-35`：只有 CPU 标志位）。

### 2.2 按掩码挑字段的函数体（`schedule.c:297-319`）

函数开头（`297-301`：返回值 `err`，三个新值 `new_prio`/`new_quantum`/`new_cpu`，加上 `niced`）→ 先选 CPU（`302`：调 `pick_cpu`，选 CPU 的细节见第 10 篇）→ 三个字段各按标志位决定取表项值还是填 `-1`（`304-317`，三个字段写法相同）→ 算 `niced` 备注（`319`：`max > USER_Q`，定义来自 05）。

### 2.3 发消息的过程（`schedule.c:321-327` + `sys_schedule.c`）

调发送函数（`321-322`：`sys_schedule(endpoint, prio, quantum, cpu, niced)`，五个参数组成一条消息）→ 失败就打印日志（`323-324`：失败提示里写着 "PM:"，这是从 PM 时代留下来的字符串，不影响语义）→ 返回内核给的返回值（`327`：成功失败都原样返回给调用者）→ 装消息（`sys_schedule.c`：五个字段逐个填进消息体，再调 `_kernel_call(SYS_SCHEDULE)` 发出去，消息体有 endpoint/quantum/priority/cpu/niced 五个字段）。

### 2.4 内核入口的权限检查（`do_schedule.c:8-29`）

函数开头（`8-13`：进程表指针、进程号、四个新值）→ endpoint 检查（`14-15`：`isokendpt` 失败就返回 `EINVAL`）→ 调度器身份检查（`20-21`：`caller != p_scheduler` 就返回 `EPERM`，见 §1.5）→ 拆消息（`24-27`：四个值直接取出，`niced` 用 `!!` 压成 0/1）→ 转交（`29`：调 `sched_proc`，拆消息的人不写表，写表另有其人）。

### 2.5 内核写入的顺序（`system.c:642-699`）

函数开头（`642`）→ 优先级和时间片的范围检查（`645-650`：队列号上溢拒绝、时间片小于 1 拒绝，`-1` 是这唯二的例外）→ CPU 检查（`652-655`：只在 SMP 编译配置下检查）→ 出队（`674-678`：运行中和非运行中两条路径都置 `RTS_NO_QUANTUM`）→ 逐个写入（`680-688`：等于 `-1` 的字段跳过）→ 写 `niced` 标记（`692-694`：置或清 `MF_NICED`）→ 重新入队（`697`：清掉 `RTS_NO_QUANTUM`）→ 返回成功（`699`：返回 `OK`）。另外注意一个细节：内核这里队列上溢的判断用的是 `>` 而不是 `>=`，所以 16 能通过内核检查，而 06 在服务端用 `>= 16` 就拦掉了——服务端严、内核宽，内核是最后一道闸，不是第一道门。

### 2.6 命名对照表

| 维度 | `schedule_process`（服务端，`schedule.c:297`） | `sched_proc`（内核，`system.c:642`） |
|------|------------------------------------------|----------------------------------|
| 位置 | 用户态 SCHED 服务 | 内核 `system.c` |
| 输入 | 表项值 + 掩码 | 四个参数 + 备注（已经从消息里拆出来） |
| 检查 | 不做检查（组好就发） | 做三道检查（endpoint、权限、范围） |
| `-1` | 负责填（掩码没选就填 `-1`） | 负责认（看到就跳过） |
| 备注 | 负责算（`319` 行） | 负责记（`692-694` 行） |
| 返回 | 内核返回什么就返回什么 | 成功返回 `OK` |
| 背锅划分 | 掩码用错归服务端 | 越界归内核检查拦 |

## 3 Rust 设计决策

Rust 改写不是把 C 函数逐行翻译，而是在参考 Linux 的检查加写入分工和内核 `SchedParams` 结构之后做的取舍。下面 D1–D5 每条都给出 C 的证据和 Rust 的落点。

### D1 掩码做成 flags 类型

- **C**：`unsigned` 的三个位，加上 ALL/LOCAL/MIGRATE 宏（`schedule.c:22-35`）。
- **Rust**：`ChangeMask: bitflags<u8>`（`os/servers/sched/src/kernel_api/schedule.rs:32`：PRIO/QUANTUM/CPU 三个位，加上 ALL/LOCAL/MIGRATE 三个具名组合）。
- **为什么**：调用点写 `LOCAL` 比写 `0x3` 好读，一眼就知道带了什么；常用组合只拼一次，各处不再手拼，就不会漏掉某个位。备选方案（用三个 `bool` 参数）被否决了：三个布尔一共有 8 种组合，其中一些非法组合也能表达出来，而且 `ALL` 这样的名字就没地方放了（模式 16）。

### D2 保持位用 `None` 表示

- **C**：没选中的填 `-1`（`307/312/317`），内核看到 `-1` 就跳过（`680-688`）。
- **Rust**：`Fanout{priority: Option<u8>, quantum_ms: Option<u32>, cpu: Option<u32>}`（`schedule.rs:83`：`None` 就是保持）+ `KEEP = -1`（`schedule.rs:54`：线上值只在这里定义一次）+ `wire_*()`（`schedule.rs:121-151`：`None` 转成 `KEEP`）。
- **为什么**："保持"本质上是"没有值"，`Option` 把这个意思直接写进了类型；C 的 `-1` 哨兵还得解释"负数是什么意思"（和 05 的 D5 是同一个道理）。内核的 `SchedParams` 也是同样的三个 `Option` 加一个 `niced: bool`，两个 crate 在线上形状一致（03 的 D3 提过这种"同形"做法）。备选方案（直接传 `i32` 的 `-1`）被否决了：哨兵进类型就是模式 17 的问题。

### D3 `niced` 的判断复用 05 的谓词

- **C**：`niced = (max > USER_Q)`（`319`，在函数里直接算）。
- **Rust**：`aggregate` 里面调 05 的 `is_niced`（`schedule.rs:105-119`：公式只用、不重写）。
- **为什么**：公式只有一份，放在 05，09 只管调用；如果两边各写一遍，将来 05 改了分界、09 没跟着改就错了（模式 A）。备注在 `aggregate` 最后一步直接赋值，和掩码无关，所以空掩码也会带上（见 §1.4）。备选方案（在本模块再写一遍 `max > 7`）被否决了：两份一样的公式就是两处真相来源。

### D4 检查留在内核，服务端只在文档里讲

- **C**：三道检查加四步写入全在内核（`do_schedule.c` + `system.c:642-699`）。
- **Rust**：本模块没有检查函数（检查规则在 §2.4/§2.5 讲全，代码实现在内核 `sched_proc`，见 `os/kernel/src/sched.rs:321`）。
- **为什么**：检查是内核的主权，服务端再写一遍就是两处真相来源（内核改了范围、服务端没跟上）。文档里讲全规则，代码权威留在内核：读本文知道检查长什么样，改检查去内核改。备选方案（加个 `validate_fanout()` 预检）被否决了：预检通过不代表真正下发时还能通过（TOCTOU 问题），而且同样是两处真相来源。

### D5 打包和发送分开

- **C**：服务端打包（`297-329`）→ 发消息（`sys_schedule`）→ 内核检查写入。
- **Rust**：`aggregate`（只管挑字段）+ `wire_*`（只管转线上值）；发消息（`_kernel_call`）和选 CPU（`pick_cpu`）都归调用者（选 CPU 见第 10 篇，拿消息发出去是调用臂的事）。
- **为什么**：挑字段是纯计算，发消息是 IPC 副作用，两者分开，纯函数才好测（06 的 D5 和 07 的 D3 是同样的分法）；表项的五个值由调用者组好传进来（04 的 D2 同样思路）。备选方案（一个 `fanout()` 函数把打包加发送全包了）被否决了：纯函数里藏 IPC 副作用，既不好测也讲不清。

### ARCH 决策总表

| ARCH | 落点 | 三处一致标注 |
|------|------|-------------|
| （本篇无 ARCH 行为变更） | — | 纯表达层演进（掩码 flags 类型/保持位 Option/`niced` 复用/检查只述不写），无需 ARCH 标注 |

## 6 过渡

本篇在 08（进程中途的动作）之后、10（选 CPU）之前，解决的是"下发"这一层：06/07/08 讲了新建、退出、降级这些动作什么时候发生，本篇讲这些动作最终怎么把参数送到内核；没有本篇，参数就留在服务端，内核收不到。

```
08-noquantum-nice: 时间片用完降级 + 改优先级事务（进程还在册期间的动作）
   │
   └─► 本篇：掩码挑字段 → 保持位转线上值 → 内核检查写入（下发这一层）
           │                              │
           ├─► 10-pick-cpu-smp：选 CPU（下发之前先选好去向）
           └─► 12-kernel-interface：调度器注册（权限的来源）
```

阅读顺序提示：如果关心"下发之前 CPU 是怎么选好的"，下一站看 `10-pick-cpu-smp.md`；权限（注册）的去向见 `12-kernel-interface.md`。
