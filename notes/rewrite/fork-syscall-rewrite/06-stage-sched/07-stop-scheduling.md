# 07 — do_stop_scheduling 停止调度

本文介绍 SCHED 怎么把一个进程从调度表里释放掉：先过两道检查（发送者白名单、槽位确实被占用），然后做两件事（SMP 下 CPU 负载计数减一、占用标记清零）。释放是登记的逆操作：进程退出了槽位还占着，表满了新进程就没地方登记；负载计数不减，选 CPU 的账就永远对不上。释放不问出身：什么进程来了都一样处理，没有特例。

前置阅读：`02-sched-message-surface.md`（STOP 消息的名字和分发）、`04-schedproc-table.md`（表检查规则）、`06-start-scheduling.md`（登记流程，对称的来源）。

> 本章不讲什么：
> - 客户端调用面（`sched_stop` 的短路逻辑与三个调用点） —— 见 `13-pm-interaction.md`/`14-rs-interaction.md`（本篇只讲服务端收到之后怎么办）
> - 下发与选 CPU 的细节 —— 见 `09-schedule-process.md`/`10-pick-cpu-smp.md`（释放不下发，原因见 §1.4）
> - 登记流程 —— 见 `06-start-scheduling.md`（本篇只引用对称关系）

## 1 概念

### 1.0 引言

释放流程要回答三个问题：什么消息能进这个入口、释放到底释放哪两样东西、释放和登记有什么不一样。答完这三个问题，两道检查、两项释放、四处不同就全清楚了。本章默认你已经知道消息的名字（见 02）、表检查规则（见 04）、登记流程（见 06），只讲"释放流程本身"。

### 1.1 为什么要释放槽位

有生就有死：名册有进就得有出——进程退出了槽位不腾出来，表满了新进程就没地方登记（`NR_PROCS` 有限，06 的空检查会一直拒绝）；CPU 负载有加就得有减——进程退出了计数不减，负载数字只涨不落（10 的选 CPU 会越来越偏，全是历史旧账）。释放就是登记的逆操作：登记记一笔（置标记加负载），释放销一笔（清标记减负载）——账实相符，调度器名册的会计学。

### 1.2 检查的顺序

检查有两道，顺序本身就是诊断信息：发送者白名单（`118-119`：只有 PM 和 RS 能进，其他一律 `EPERM`）→ 槽位确实被占用（`121-125`：`sched_isokendpt`——占着才能释放，空槽位和名字对不上都拒绝）。顺序和 06 一样（先验发送者、再验槽位），检查方向和 06 相反（06 验空 `isemtyendpt`，本篇验占用 `isokendpt`）：释放验有没有、登记验空不空，各用各的检查（04 的 §1.4 讲过这两个检查是一面镜子的两面，这里各就其位）。

### 1.3 释放的两样东西

释放做两件事：减负载（`cpu_proc[cpu]--`，`130`：CPU 的账减一——只在 SMP 构建里减，单核没有这笔账，见 §2.3）→ 清标记（`flags = 0`，`132`：槽位的命清零——直接赋零而不是 `&= ~IN_USE`：全表只有一个标记位，清标记就是清零，04 的 §1.3 讲过一表一标记）。释放顺序是登记顺序的反向（登记：交接之后置标记；释放：清标记就是最后一步——没有可逆的交接，死人不用交接）。

### 1.4 释放没有的东西

和登记比，释放有四个"没有"：不验边界（上限字段用不上——消息里根本没这个字段，`ipc.h:1440-1444` 是单字段消息）→ 不调交接（内核不用认可谁的离开——进程已经死了，没调度可交）→ 不下发（不调 `schedule_process`——死人不用调度）→ 不填回复字段（`scheduler` 不填——`OK` 照常经分发回复回去，回复里没有新归属可告）。四个没有让释放很轻：登记八步，释放五步（两道检查取一道、两项释放、一个成功返回）——轻是因为死人的事本来就少，不是因为偷工减料。

### 1.5 对称表

| 操作 | 登记 `do_start_scheduling`（06） | 释放 `do_stop_scheduling`（本篇） |
|------|-------------------------------|-------------------------------|
| 消息 | 两种（INHERIT/START） | 一种（STOP） |
| 白名单 | `accept_message`（`150`） | `accept_message`（`118`） |
| 验槽位 | 验空 `isemtyendpt`（`154`） | 验占用 `isokendpt`（`121`） |
| 验边界 | `max >= 16 → EINVAL`（`164`） | 没有（消息里没这个字段） |
| 特例 | init 临时值（`171-188`） | 没有（释放不问出身） |
| 交接 | `sys_schedctl`（`218`） | 没有（死人不用交接） |
| CPU 账 | 选 CPU（`226`，10 的细节） | 减负载（`130`，SMP 才减） |
| 标记 | 置 `IN_USE`（`223`） | 清零（`132`） |
| 下发 | `schedule_process` 全量加重试循环 | 没有（死人不用调度） |
| 回复 | `scheduler`（`246`） | 无回复字段（`OK` 照常回去，回复里无归属） |

对称是刻意保持的：两个臂检查顺序一样（先发送者后槽位）、错误码同一套（`i32`）、管线形状一样（`Request` 进、`Seed`/`Release` 出）——对称写进了代码（06 的 D4 和 07 的 D4 同构），不只写在表里。

### 1.6 exit 的三条来路

来路有三条（调用面归 13/14，本篇只讲收到之后怎么办）：PM exit（`forkexit.c:425`：儿子死了就给它停调度）→ RS 终止（`manager.c:461`/`request.c:342`：服务死了就给它停调度）→ 短路（`sched_stop` 里面 `KERNEL`/`NONE` 直接返回 `OK`——内核自己调度的不用 SCHED 收尾，连消息都不发）。来路不同，入口同一个（06 的 §1.1 讲过同样的道理：登记的两种消息如此，释放的三条路亦然）。

### 1.7 其他系统的同类设计

- **Linux** 用 `sched_exit`/`put_task_struct` 对应这里的两项释放：`sched_exit` 脱离运行队列（清标记的意思）和 `put_task_struct` 释放引用（减负载的意思）——"脱离"和"释放"分开，两个系统都有。`flags = 0` 的直接赋零对应 Linux 的 `__set_task_state(TASK_DEAD)`（Linux 状态多所以设值，本篇只有一个标记位所以清零——标记数量不同）。
- **Redox** 进程退出是整块回收（上下文、地址空间、调度项一起收走），没有"减负载、清标记"这种分步动作——分步是 Minix"表驱动加用户态调度器"的形状（Redox 内核自己调度，释放就是回收）。
- **seL4** 的线程结束对应 TCB 对象回收（能力删了名字就没了——名和实是一体的，所以没有"验占用"这道检查）；`flags = 0` 的清零对应 seL4 的对象复位（槽位回到初始状态的两种写法）。SMP 减负载在 seL4 里没有对应物（亲和性是配置不是负载账——这笔账是 SCHED 负载策略自己的形状）。

### 1.8 小结

检查（白名单加验占用两道且有序）管能不能释放，释放（减负载加清标记）销两笔账，四个没有守住轻量，对称表把登记释放贯穿起来。贯穿始终的一条要求：释放是登记的逆操作——登记记一笔，释放销一笔，账实相符。

## 2 C 源码分析

### 2.1 白名单与验占用（`schedule.c:112-125`）

开头（`112-115`：一个槽位指针、一个编号——`rmp`/`proc_nr_n`，没有父进程编号：释放不问出身）→ 白名单（`118-119`：PM/RS 之外一律 `EPERM`）→ 验占用（`121-125`：`sched_isokendpt`，名字对不上就 `EBADEPT` 加一条警告）。

### 2.2 取槽位（`schedule.c:128`）

取槽位（`128`：`rmp = &schedproc[proc_nr_n]`——释放动作从这里开始）。

### 2.3 减负载（`schedule.c:129-131`）

构建开关（`129,131`：`CONFIG_SMP` 的开关——单核没有这笔账）→ 减一（`130`：`cpu_proc[rmp->cpu]--`——CPU 的账减一，10 的表就是这张）。

### 2.4 清标记与返回（`schedule.c:132-134`）

清零（`132`：`flags = 0`，注释 `/*&= ~IN_USE;*/`——等价写法的意思：全表只有一个标记位，清零就是清标记，04 的 §1.3 讲过）→ 返回成功（`134`：`OK`——释放一定成功：检查过了后面就没有失败点了）。

### 2.5 消息的形状（`ipc.h:1440-1444`）

单字段（`1441`：`endpoint`——死人的名字而已）→ 填充（`1443`：52 字节补齐——消息定长的要求）→ 结构体结束（`1444`）。

### 2.6 来路的发送端（`sched_stop.c:9-29` + 三个调用点）

短路（`sched_stop.c:16-17`：`KERNEL`/`NONE` 直接 `OK`，连消息都不发）→ 组装消息（`sched_stop.c:24-27`：填端点、发 `SCHEDULING_STOP`）→ 三条路（`forkexit.c:425`/RS `manager.c:461`/`request.c:342`——调用面归 13/14，本节只说明收到端的检查存在）。

## 3 Rust 设计决策

Rust 改写不是把一个函数五步照抄过来，而是参考 Linux 的脱离/释放区分和 06 的管线经验之后再取舍。决策编号 D1–D4，每条都给出 C 依据和 Rust 落点。

### D1 消息形状单字段

- **C**：`mess_lsys_sched_scheduling_stop{endpoint}`（`ipc.h:1440-1444`：单字段）。
- **Rust**：`Request{child: Endpoint}`（`os/servers/sched/src/scheduling/stop.rs:25`：单字段形状）。
- **为什么**：死人没有数字（上限时间片父进程全都没有——形状里没地方放就等于没有这个语义）；单字段形状就是在说"释放只问是谁"。备选方案（复用 06 的 `Request` 四字段）被否决了：两种消息形状不同，合成一个就把形状抹掉了（STOP 的消息里如果有个 quantum 字段，那个值没有任何含义——有含义的位置不能放没含义的值）。

### D2 检查顺序照抄

- **C**：白名单 → 验占用（`118-125`，顺序不能换）。
- **Rust**：`admit(sender_ok, slot)`（`stop.rs:53`：`EPERM` → 表检查码的顺序直译，和 06 的 `admit` 同形——两个臂检查顺序一样是刻意对称）。
- **为什么**：顺序就是诊断信息（06 的 D2 同理）；管线同形（两个臂同一个顺序同一套码——对称写进代码，不只写在表里，见 §1.5）。备选方案（释放臂自己另写一套检查顺序）被否决了：两套顺序就是两种诊断（同一种诊断写两遍，早晚写岔）。

### D3 释放的两样东西

- **C**：减负载（`130`，SMP 构建里）+ 清标记（`132`，直接赋零）。
- **Rust**：`Release{endpoint, cpu}`（`stop.rs:38`：释放的形状）+ `plan_stop`（`stop.rs:72`：检查过了就释放，没有分支没有循环）+ SMP 开关留给调用者（单核跳过减负载——`Release` 照样带 CPU，规则一份、开关一处读，10 消费这个约定）。
- **为什么**：释放是执行（减负载清标记都要改表——纯函数改不了表，形状归调用者）；构建开关在调用者（编译期开关改运行时是 S-5，10 的范围）；清零不进代码（`flags = 0` 就是调用者写个零——代码里没东西可判断，判断止于检查）。备选方案（`Release` 里加 `clear_flags: bool` 开关）被否决了：恒为真的开关就是摆设（释放一定清标记，没有不清的时候）。

### D4 对称写进代码

- **C**：登记释放对照十行（§1.5 的表：消息/检查/槽位/边界/特例/交接/账/标记/下发/回复）。
- **Rust**：两个臂同形（`Request` 进 → `Seed`/`Release` 出 → 错误码 `i32`；`admit` 同名同序；测试同构：顺序/填值-释放形状/循环码-往返）。
- **为什么**：对称是个约定（以后改登记的人一定会想到释放——同形就是互为镜子）；`flags = 0` 的直接赋零对 `IN_USE` 的置位（代码之外的对称在 §1.5 的表里，不在代码里——代码里的对称止于管线形状）。备选方案（释放臂另起一套管线形状）被否决了：形状不同镜子就碎了。

### ARCH 决策总表

| ARCH | 落点 | 三处一致标注 |
|------|------|-------------|
| （本篇无 ARCH 行为变更） | — | 纯表达层调整（检查顺序直译、两项释放归调用者），无需 ARCH 标注 |

## 6 过渡

本篇在 06（登记）之后、08（降级调整）之前，是"释放"的归属：06 定登记的流程，本篇定释放的流程；没有本篇，表满了新进程没地方登记（槽位腾不出来），负载账永远对不上（计数只加不减）。

```
06-start-scheduling: 两种消息 → 四道检查 → 三种填值 → 交接置标记 → 死 CPU 重试 → 回复归属（登记流程）
   │
   └─► 本篇：一种消息 → 两道检查 → 两项释放（登记的逆操作，释放流程）
           │                              │
           ├─► 08-noquantum-nice：降级调整流程（在册进程的去向）
           └─► 10-pick-cpu-smp：减负载的表（账的去向）
```

阅读顺序提示：关心"在册进程的去向"，下一站 `08-noquantum-nice.md`（降级调整流程）；账的去向见 `10-pick-cpu-smp.md`。
