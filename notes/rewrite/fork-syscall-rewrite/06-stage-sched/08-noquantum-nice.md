# 08 — do_noquantum 与 do_nice

本文介绍在册进程的两种优先级变化：时间片用完内核通知降级（当前位置降一级，到底就停），和管理员调 nice 值改上限（上限和当前位置一起改成新值，下发失败就回滚）。降级是时间给出的裁决（时间片用完了的结果），改上限是人的裁决（管理员的意思）；降级只动当前位置，改上限连上限一起动；降级没有发送者检查（信的是内核的标记），改上限有全套检查（验发送者验槽位验边界）。

前置阅读：`02-sched-message-surface.md`（耗尽消息的检查与分发）、`04-schedproc-table.md`（表检查规则）、`05-priority-timeslice-model.md`（上限和当前位置的分工）。

> 本章不讲什么：
> - 下发的细节（`schedule_process` 参数聚合） —— 见 `09-schedule-process.md`（本篇只用局部下发的名字）
> - accounting 七个字段的含义 —— 见 `12-kernel-interface.md`（本篇只讲耗尽通知这条消息）
> - PM 改上限的调用面（`sched_nice` 的短路逻辑与 nice 折算） —— 见 `13-pm-interaction.md`（本篇只讲服务端收到之后怎么办）
> - 降级之后的恢复（`balance_queues` 逐级升回来） —— 见 `11-balance-queues.md`

## 1 概念

### 1.0 引言

在册进程的变化要回答三个问题：时间片用完谁降级、改上限改哪两个值、谁有资格改上限。答完这三个问题，降级（内核通知、降一级、到底停）、改上限（上限当前位置一起改、失败回滚）、改上限资格（PM 能改、内核通知不能改）就全清楚了。本章默认你已经知道耗尽消息的检查（见 02）、表检查规则（见 04）、上限和当前位置的分工（见 05），只讲"在册进程的变化"。

### 1.1 为什么在册进程的优先级会变

登记定初始值（06），退出销名字（07）——但登记和退出之间很漫长：在册进程时而时间片用完（降级），时而管理员改主意（改上限）。如果数字在登记那一刻就钉死，时间片用完的进程永远占着高队列（低队列饿死），管理员也没手段（nice 系统调用成一纸空文）。变化是调度的呼吸：降升循环（本篇降、11 升）和改上限的权力（本篇改）——不动调度器就僵了（队列僵化），动了才活。

### 1.2 信任不对称

四个 handler 里三个验发送者，只有耗尽处理不验：`do_noquantum` 里没有 `accept_message`（`92` 直接读 `m_source`）——检查不在这个函数里，在主循环那道关（`main.c:68-84`：验内核标记，伪造的消息打回去 `EPERM`，02 的 §2.4）。不对称是权力决定的：说"某人时间用完了"就能改调度（伪造就等于夺权）——权力越大，检查越严（检查上移到分发，函数里反而没检查）。其他 handler 都是白名单（PM/RS 能进）——请求可以验名单，耗尽通知只验内核标记（标记伪造不了，名单可以列——检查强度跟着权力走）。

### 1.3 降级怎么做

降级三条规则：收到耗尽通知才降（通知到了）→ 降一级（`priority += 1`，`100`：数字加一就是优先级降一级——数字越小权越高，反着读，05 的 §1.2）→ 到底就停（`< MIN_USER_Q` 才降：钉在底的进程不再降——底是降级的尽头，尽头之外没有队列）。降级只动当前位置（上限不动——降级是状态往下沉，不是约束变了；恢复时有上限可回，11 的内容）。降级之后必须下发（局部下发：`schedule_process_local`——改了数字不下发，内核那边还是旧的）。

### 1.4 改上限怎么做

改上限四步：验发送者验槽位验边界（白名单 → 验占用 → `>= 16` 拒绝——06 的 D2 那套顺序在这里复用，两个臂同一套）→ 快照（存下旧上限旧当前位置——改之前留退路）→ 一起改（`max = priority = new`，`282`：上限当前位置取同一个新值——改上限改的是"约束加状态合一"，不是只改一个数）→ 失败回滚（下发失败就恢复旧的两个值——事务性：改不成，就当没改过）。改上限和降级的区别：改上限动上限（约束可以换），降级不动（约束不能降）——上限动不动，是改和降的分水岭。

### 1.5 局部下发

下发分两种：全量（`SCHEDULE_CHANGE_ALL`：数字 CPU 全下——登记的大动作，06 的内容）和局部（`SCHEDULE_CHANGE_PRIO | SCHEDULE_CHANGE_QUANTUM`：只下数字——在册进程变化的日常）。局部不迁 CPU（`CPU` 位是空的——降级改上限都不动 CPU 归属，CPU 是 10 的范围）；局部下发的名字就是个宏（`schedule_process_local`，`32-33`——名字即标记组合，细节归 09）。降级改上限都用局部下发：动数字不动 CPU，这是本篇下发的全部形状。

### 1.6 其他系统的同类设计

- **Linux** 用 CFS 的 `vruntime` 增长和 `sched_setscheduler` 对应降和改：CFS 时间片用完权值往下沉（降级的同构，只是形状是累计执行时间而不是降队列）和 `sched_setscheduler` 换策略（上限当前位置一起改的意思）；事务回滚对应 Linux 的"先验后置"（`__sched_setscheduler` 验完参数再写——验和写分离，失败就不写，和本篇"快照后写、失败回滚"路不同果相同）。
- **Redox** 调度域嵌在进程里（降和改都是改整块的域，没有独立的两个臂）——Minix 一条消息一个臂，Redox 一块结构统管，分合不同。
- **seL4** 用 `TCB_SetPriority` 改优先级对应改上限（改的同构，只是上限当前位置不分家——seL4 没有两个数，所以没有"一起改"这个形状）；降级在 seL4 里没有对应物（MCS 预算用完线程就停，不是降级——停和降是时间片用完的两种答案）。

### 1.7 小结

降级（内核通知、降一级、到底停）是时间的裁决，改上限（过检查、快照、一起改、失败回滚）是人的裁决，资格（PM 能改、内核通知那条路不能改）是权力的边界，局部下发（动数字不动 CPU）是下发的形状。贯穿始终的一条要求：上限动不动——降级不动上限，改上限两个一起改。

## 2 C 源码分析

### 2.1 耗尽检查与降级（`schedule.c:87-109`）

开头（`87-90`：一个槽位指针、一个编号——`rmp`/`rv`/`proc_nr_n`，没有新旧值的变量：降级不做快照）→ 验占用（`92-96`：`sched_isokendpt(m_source)`，名字对不上就 `EBADEPT` 加警告——没有白名单那道检查，见 §1.2）→ 取槽位（`98`）→ 降一级（`99-101`：`< MIN_USER_Q` 才 `+= 1`，到底停）→ 局部下发（`103-106`：`schedule_process_local`，失败就返回错误码）→ 返回成功（`106`：`OK`）。

### 2.2 改上限的检查与快照（`schedule.c:254-282`）

开头（`254-259`：一个槽位指针、一个编号、三个新旧值——`rmp`/`rv`/`proc_nr_n`/`new_q`/`old_q`/`old_max_q`）→ 白名单（`262-263`）→ 验占用（`266-271`：名字对不上就 `EBADEPT` 加警告）→ 取消息值（`274-275`：`new_q = maxprio`）→ 验边界（`276`：`>= 16` 就 `EINVAL`）→ 快照（`278-279`：存旧上限旧当前位置）→ 一起改（`282`：`max = priority = new`）。

### 2.3 改后下发与回滚（`schedule.c:284-291`）

局部下发（`284-286`：`schedule_process_local`）→ 回滚（`287-288`：失败就恢复旧的两个值）→ 返回下发的码（`291`：返回下发的返回码——成功失败都透传，失败时槽位已恢复旧值）。

### 2.4 局部下发的名字（`schedule.c:32-35`）

局部（`32-33`：`PRIO | QUANTUM`——数字的两个标记）→ 迁 CPU（`34-35`：`CPU` 标记，本篇不用——列在这里是为了说明"局部的反面是什么"，细节归 09）。

### 2.5 内核标记检查（`main.c:68-84`）

耗尽消息分支（`68`）→ 验标记（`70-71`：`IPC_FLG_MSG_FROM_KERNEL`）→ 执行降级（`72-77`：失败只警告不回复——`continue` 的意思就是不回复，02 的 §2.4）→ 伪造斥回（`78-83`：伪造就 `EPERM` 再记一笔）→ 分支结束（`84`）。

### 2.6 改上限的消息与来路（`ipc.h:1822-1827` + `pm/schedule.c:89-112`）

消息的形状（`1822-1827`：endpoint/maxprio 两个字段——改上限的消息带谁带多高）→ 来路（`sched_nice`，`pm/schedule.c:89`：KERNEL/NONE 短路 → nice 折算队列 → 组装消息发 `SET_NICE`——调用面归 13，本节只说明收到端的检查存在）。

## 3 Rust 设计决策

Rust 改写不是把两个函数六十行照抄过来，而是参考 Linux 的验写分离和三个臂的管线经验之后再取舍。决策编号 D1–D5，每条都给出 C 依据和 Rust 落点。

### D1 发送者检查在外面

- **C**：`do_noquantum` 里没有 `accept_message`（`92` 直接读 `m_source`）；检查在 `main.c:68-84`。
- **Rust**：`admit(slot)`（`os/servers/sched/src/scheduling/noquantum.rs:38`：没有发送者参数——函数签名就是信任模型）。
- **为什么**：检查上移了，函数里就没有检查（检查在循环层、硬说在函数层，那是形状作假）；签名里没有发送者就验不了发送者（调用者想验发送者都找不到入口——误用在编译期就暴露）。备选方案（`admit(sender_ok, ...)` 和三个臂统一）被否决了：统一的形状掩盖了真实的不对称（四个 handler 三个验发送者、一个验内核标记——形状应当说出不同，不应当抹掉不同）。

### D2 降级做成纯函数

- **C**：`if (priority < MIN_USER_Q) priority += 1`（`99-101`）。
- **Rust**：`demote(Priority) -> Option<Priority>`（`noquantum.rs:52`：饱和加一、到底封顶，`None` 防御性保留）。
- **为什么**：降级是个算术（无表可查、无检查可验——纯了才好测）；到底封顶就是全函数（`None` 防常量漂移，05 的 `to_priority` 同例）。备选方案（调用者内联 `+1`）被否决了：到底的判断散开（到底在各处各写一遍，以后改了一处漏一处）。

### D3 改上限分三段

- **C**：验检查（`262-276`）→ 快照写值（`278-282`）→ 下发回滚（`284-291`）。
- **Rust**：`admit`（`nice.rs:53`：EPERM→表检查码→EINVAL，和 06/07 同序）+ `regrade`（`nice.rs:80`：两个数一起改、一个构造）+ 回滚就是写回去（调用者拿着 `before: Current`，`Copy` 就是快照——没有回滚函数）。
- **为什么**：快照就是值（`Current` 把一对数绑在一起就是事务性——拆开以后某次调用可能只写一半，见 §1.4）；回滚不需要函数（拿着就是快照、写回去就是回滚——函数将无事可做）；检查顺序三个臂统一（06 的 D2、07 的 D2 同理）。备选方案（`rollback(before) -> Current` 函数）被否决了：恒等函数就是摆设（返回它的输入而已）。

### D4 边界检查双向拒绝

- **C**：`new_q >= 16 → EINVAL`（`276`：没写下界）。
- **Rust**：`< 0 || >= 16 → EINVAL`（`nice.rs:63-73`，`as u8` 旁边有守卫注释——06 的 D3 那套写法的跨臂复用）。
- **为什么**：对外表现一致（06 的 D3 同理，不再证明）；三个臂同一套（边界双向拒绝在 06/08 两处同形——以后改一处一定会想到另一处）。备选方案（`u32` 线值绕回）被否决了：翻译腔（模式 65）。

### D5 局部下发只讲意思

- **C**：`schedule_process_local`（`32-33`：PRIO|QUANTUM）。
- **Rust**：本臂没有标记符号（局部下发的名字归 09；降和改都只说"局部下发"，执行归调用者）。
- **为什么**：标记组合是下发的语义（09 的范围——08 复述标记值就是两份定义）；臂里只讲局部的意思（动数字不动 CPU），不列标记的值。备选方案（本臂复刻 `LOCAL_PRIO|LOCAL_QUANTUM` 常量）被否决了：两份定义的隐患。

### ARCH 决策总表

| ARCH | 落点 | 三处一致标注 |
|------|------|-------------|
| （本篇无 ARCH 行为变更） | — | 纯表达层调整（检查上移签名化、降级纯函数化、快照即值），无需 ARCH 标注 |
