# 01 — 进程间通信服务器的启动入口与主循环：消息从哪里来，到哪里去，什么时候不回信

> **状态**: 已改写（2026-09-05，依据 plan.md 阶段 1 边界从零写作）
> **定位**: 阶段 1 启动入口与主循环（后面所有处理函数篇章的锚点）
> **源码**: `minix3/minix/servers/ipc/main.c`（284 行，本篇覆盖第 12 行到第 25 行的分发表、第 124 行到第 142 行的启动包装函数、第 216 行到第 284 行的主函数；第 27 行到第 122 行的管理信息库子树与信号处理移交 03 与 10，第 144 行到第 214 行的进程事件处理移交 09）
> **Rust 模块**: `os/servers/ipc-server/src/server.rs`（事件循环）、`os/servers/ipc-server/src/dispatch.rs`（消息分类与分发判决）
> **说明**: 进程间通信服务器（IPC server，Inter-Process Communication server）是 Minix3 里面负责管理 System V 信号量与共享内存的用户态服务。它的主循环一生只做四件事情：等一封消息、判断这封消息属于哪一个类别、把属于自己的请求交给对应的处理函数、按规则决定要不要回信。本文讲清楚这四件事情、启动时的回调注册，以及一次请求进门时要经过的完整路径。

## 1 概念

### 1.1 目标读者与前置知识

面向第一次阅读 Minix3 用户态服务代码的读者。前置知识只需要两样：C 语言的基本阅读能力，以及操作系统里面"服务器循环收取消息"这个基本想法。System V 信号量与共享内存是什么不需要预习——可以把它们理解成"进程之间协调与共享数据的两种操作系统对象"，细节在用到的时候用一句话解释。内核提供的收信原语（`sef_receive_status`，带状态的接收函数）的名字会在正文里面出现，语义同样现用现讲。

### 1.2 本篇不讲什么

- 七种请求里面每一种请求的**字段含义**——那是 02 的事情（协议面）。
- 管理信息库子树长什么样、注册时发生了什么——那是 03 的事情。
- 信号量与共享内存的处理函数内部怎么做——那是 05 到 08 的事情。
- 进程事件的订阅与处理——那是 09 的事情。
- 收到终止信号之后怎么清理退出——那是 10 的事情。

本篇只讲骨架：启动时注册了哪几个回调，主循环收到消息之后先问哪几个问题，最后怎么决定回信还是不回信。

### 1.3 为什么主循环长成这个样子

进程间通信服务器的本质是一个**单线程的按编号分发请求的用户态服务器**：它不管理硬件，不调度进程，不碰页表。它的一生就是：等一封消息，看消息头上面的调用编号，要么把消息交给某一个处理函数并回信，要么因为消息不属于自己而跳过。因为逻辑是线性的，主循环不需要线程，也不需要锁——同一时刻只处理一封消息。这和系统信息库服务（MIB，10-stage-mib 的 01 篇讲的三条路径循环）是同一个形状：接收、分类、分发、回复。微内核的用户态服务器大多长成这样（Redox 操作系统的方案服务、seL4 的用户态服务器同理：单线程收取消息是默认形状，多线程是例外）——不是 Minix3 的特殊癖好，而是"一次只回答一封信"这个约束的自然结果。

整个循环可以画成下面这样：

```
        ┌──────────────────────────────────────────────┐
        │ 启动包装：登记三个回调，然后交出控制权        │
        │ 全新启动回调 / 重启回调 / 信号回调             │
        │ main.c 第 124 行到第 142 行                   │
        └──────────────────────┬───────────────────────┘
                               ▼
┌───────────┐   ┌──────────────────────────────┐   ┌───────────────┐
│ 等待消息   │──▶│ 按类别分流                   │──▶│ 决定回信      │
│ receive   │   │ 内核通知则跳过 / 进程事件另走 │   │ reply         │
│ 主循环    │   │ / 管理信息库请求另走 / 其余   │   │ 主循环        │
│ :228      │   │ 按编号查表分发 :234-261      │   │ :264-276      │
└───────────┘   └──────────────────────────────┘   └───────────────┘
                                                          │
                                   查表分发后收尾：刷新共享内存引用计数并销毁符合条件的段
                                   update_refcount_and_destroy :279（本体在 08；
                                   三个专用分支的 continue 绕过它）
```

分流的第一层值得停下来多看一眼：**同样是"不属于自己的消息"，内核通知与进程事件、管理信息库请求的处理方式各不相同**。内核通知（`is_ipc_notify`，`com.h` 第 92 行）是内核顺手告知"刚才那是一次异步通知，不是请求"，直接打印一行日志然后等下一封信。进程事件（来源是进程管理器，类型是 `PROC_EVENT`）与管理信息库请求（来源是管理信息库服务）则各有一条专用处理路径。所以主循环的分流不是一层判断，而是三层：先问是不是通知，再问是不是进程事件，再问是不是管理信息库请求，最后才查表。这是读这个主循环时最容易看漏的结构：**查表分发只是最后一层，前面还有三层专用分流**。

### 1.4 一次请求进门时走过的完整路径

假设一个用户进程调用了 `semget`（创建一个信号量集合），这封信到达之后发生的事情如下：

```
1. 等待：sef_receive_status 在任意来源上阻塞，直到这封信到达（:228）
  → 2. 通知检查：内核状态不是通知，继续往下走（:234）
  → 3. 进程事件检查：来源不是进程管理器，继续往下走（:241）
  → 4. 管理信息库检查：来源不是管理信息库服务，继续往下走（:248）
  → 5. 查表：调用编号减去基址得到下标，下标合法且表项非空，调用 do_semget（:255-259）
  → 6. 回信判决：处理函数返回的不是挂起标记，填写结果码并发送回信（:264-276）
  → 7. 收尾：刷新共享内存引用计数并销毁符合条件的段（:279），回到第 1 步
```

第 6 步里面的"挂起标记"（SUSPEND，数值负 998）是全文最反直觉的一个设计，值得现在就记住：**处理函数返回 SUSPEND 的意思是"这次先不回信，调用者继续等着，以后再补一封回信"**。信号量等待操作（`semop`，06 篇）在条件不满足时会让调用者挂起，服务器先返回 SUSPEND，当条件满足或者等待被取消时再补发回信。主循环看到 SUSPEND 就跳过回信，直接做收尾工作。把 SUSPEND 读成"出错了"会在 06 篇里面处处误判，先在这里钉住：**SUSPEND 不是错误码，是"稍后回复"的约定**。

### 1.5 小结

启动时登记三个回调（全新启动、重启、信号），主循环分四个步骤（等待消息、按类别分流、查表分发、决定回信），分流有三层专用路径（内核通知直接跳过、进程事件与管理信息库请求各走专用函数，且三条专用路径都绕过收尾钩子），查表分发覆盖七个调用编号，回信只有一条规则（不是挂起标记就回信），查表分发之后运行一次共享内存引用计数收尾。记住这张图，后文 02 到 10 的每一篇都是往这个骨架里面填充具体内容。

### 2.2 启动序列逐项核对（`sef_local_startup`，第 124 行到第 142 行）

| 步骤 | C 位置 | 行为 |
|---|------|--------|

| 登记全新启动回调 | 第 128 行（`sef_setcb_init_fresh`） | 挂 `sef_cb_init_fresh`（注册管理信息库子树，见 03） |

| 登记信号回调 | 第 132 行（`sef_setcb_signal_handler`） | 挂信号处理函数（清理退出，见 10） |

### 2.3 主循环逐项核对（`main`，第 227 行到第 280 行）

| 步骤 | C 位置 | 行为 |
|---|------|--------|
| 等待消息 | 第 228 行（`sef_receive_status(ANY, &m, &ipc_status)`） | 在任意来源上阻塞；失败则终止整个服务（`panic`），因为收不到消息说明循环本身已经无法工作 |

| 通知检查 | 第 234 行到第 238 行（`is_ipc_notify`） | 是通知则打印来源后继续等待，不回信，且跳过收尾钩子（`continue` 在收尾之前） |
| 进程事件检查 | 第 241 行到第 245 行 | 来源是进程管理器且类型是 `PROC_EVENT` 则调用 `got_proc_event`（09），然后继续等待，且跳过收尾钩子 |
| 管理信息库检查 | 第 248 行到第 252 行 | 来源是管理信息库服务则调用 `rmib_process`（03），然后继续等待，且跳过收尾钩子 |
| 查表分发 | 第 255 行到第 261 行 | 下标等于调用编号减去基址；下标越界或者表项为空则结果为"功能未实现"（ENOSYS，数值 78） |
| 回信判决 | 第 264 行到第 276 行 | 结果不是挂起标记则填写结果码并发送；发送失败只打印不终止（对端可能已经退出） |
| 收尾 | 第 279 行（`update_refcount_and_destroy`） | 只在查表分发路径执行（三个专用分支的 `continue` 都绕过它）；刷新共享内存引用计数并销毁符合条件的段（本体在 08）；注释写着"一定有更好的办法"，意思是每轮全表轮询开销大 |

收发失败的不对称处理值得记住：**收不到消息则终止服务，发不出消息只记录日志**（第 229 行对比第 275 行）：收不到说明循环本身无法接收，无可挽回；发不出多半是对端已经退出，不值得为此终止本服务。轻重分明，和管理信息库服务的主循环是同一个道理。

### 2.5 回信规则（第 264 行到第 276 行）

| 处理结果 | 条件 | 动作 |
|-------------|------|--------|
| 结果是挂起标记（SUSPEND） | 信号量等待操作让调用者挂起（06） | 不回信，直接做收尾工作，调用者继续等待 |
| 其他一切结果 | 包括成功与各种错误码 | 把结果码填入回复消息的类型字段后发送；发送失败只打印 |

回复消息复用收到的消息缓冲区（`m`），处理函数已经填好的其他字段保留（第 269 行到第 272 行的注释）。这个"复用缓冲区"的习惯在 Minix3 的用户态服务器里面很常见：省一次清零与拷贝，结果码覆盖类型字段即可。

### 2.6 启动链位置证据

进程间通信服务器**不在启动映像里面**：内核的启动表（`kernel/table.c`）没有登记它。它由重生服务器（RS，Reincarnation Server）在运行时加载，特权面由 `ipc.conf` 定义（能收哪些端点的消息、能向虚拟内存服务发哪几种请求，见 02）。进程间通信服务器与输入服务、设备管理服务同属重生服务器加载组，在启动链上位于虚拟内存服务与进程管理服务之后（README 的启动链位置图）。

内核启动时对除虚拟内存服务之外的所有用户进程设置"虚拟内存抑制"标志（`kernel/main.c`，虚拟内存建好页表之前谁也不许运行），抑制解除之后进程间通信服务器才真正可被调度——这条抑制链在 `01-stage-kernel` 的虚拟内存启动协议篇。

## 3 Rust 设计决策

| 编号 | 决策 | C 做法 | Rust 做法 | 为什么这样做 |
|---|------|--------|-----------|--------|
| D1 | 调用编号变成枚举 | 裸整数做减法查表（第 255 行），非法下标靠运行时判断 | `IpcCall` 枚举加 `from_raw` 返回 `Option`（`ipc_server.rs`） | 非法编号不可表达：`None` 就是越界分支；加第八个编号时编译器逼迫补充分支；与虚拟内存服务的 `VmCall` 枚举同款做法 |
| D2 | 到达消息分成五类 | 四个 `if` 加一个下标判断散写在循环体里面 | `Incoming::{Notify, ProcEvent, Mib, Dispatch, Unknown}` 加 `classify` 纯函数（`dispatch.rs`） | 通知拒绝、进程事件分流、管理信息库分流、查表分发、未知编号是五件不同的事情，五个名字让日志和测试能区分；`classify` 只做判断不做事，可单测 |
| D3 | 未知编号变成纯函数 | 越界或者空槽返回"功能未实现"内联在循环里面（第 257 行到第 261 行） | `unknown_call_result() -> i32` 返回 `ENOSYS`（`dispatch.rs`） | 规则一句话，值得一个名字；以后调用编号空间变化只改一处 |
| D4 | 回信规则变成纯函数 | `if (r != SUSPEND)` 内联（第 264 行） | `should_reply(result: i32) -> bool`（`dispatch.rs`） | 与管理信息库服务的 `should_reply` 同款判决层：规则与循环体解耦，循环体以后长什么样都不影响它；挂起标记的语义由测试钉住 |
| D5 | 循环体拆成单步函数 | 死循环里面混着接收、分发、回信、收尾 | `run_once` 处理一轮（`server.rs`），`run` 只负责无限循环与收尾钩子 | 虚拟内存服务同款拆分：测试可以一次驱动一轮，不用启动无限循环；接收失败计数与连续失败上限放在 `run` 里面 |
| D6 | 传输层抽象成特征 | 直接调用 `sef_receive_status` 与 `ipc_sendnb` | `IpcTransport` 特征（`server.rs`）：`receive` 与 `send` 两个方法，生产实现与测试替身各一个 | 收发原语依赖内核落地之前，业务逻辑可先测；虚拟内存服务的 `IpcTransport` 同款做法；Redox 的方案服务同样把传输与业务分开 |
| D7 | 接收失败只计数不终止（架构演进） | 接收失败直接终止服务（第 229 行 `panic`） | 接收失败计数加一并继续循环，连续失败达到上限才终止（`server.rs`，标注 `[ARCH: IPC-01-01]`） | 用户态服务器不应该因为一次传输抖动就退出；虚拟内存服务同款演进（连续失败上限后终止，避免无限空转消耗处理器）；行为差异在文档与代码注释两处一致标注 |

微内核对照（类比，不是移植依据）：单线程收取消息的循环是 Minix3、Redox、seL4 用户态服务器的共同默认形状，本篇的"分类、分发、应答"三段对应 Redox 方案服务的"解析请求、分发到文件系统操作、写回响应"三段；Redox 按路径字符串分发，进程间通信服务器按整数编号分发——都是"名字到处理者"的查表，只是这里的名字是连续整数，所以可以用减法得到下标。对照的结论只有一个：循环骨架不值得发明，保持三段式，把心智花在"五类到达与挂起语义"上面。

替代方案及否决：把七个处理函数也搬进本篇的 Rust 代码——否决，因为处理函数分属 05 到 08，本篇只定义分发判决与循环骨架，处理函数以特征方法的形式预留接口（05 到 08 落地时实现）；现在搬只能搬空壳，违反一次只做一件事的原则。

## 4 实现详解

### 4.1 模块结构

```
os/servers/ipc-server/src/

```

### 4.2 关键类型与函数

**消息分类**（`dispatch.rs`）：

- `Incoming` 枚举：`Notify`（内核通知，直接跳过）、`ProcEvent`（进程事件，交给 09）、`Mib`（管理信息库请求，交给 03）、`Dispatch(IpcCall)`（查表命中，交给 05 到 08）、`Unknown`（未知编号，回功能未实现）。
- `classify(is_notify: bool, source: Endpoint, call_type: i32) -> Incoming`：按主循环第 234 行到第 261 行的顺序做判断，纯函数，无副作用。
- `should_reply(result: i32) -> bool`：结果不等于挂起标记就回信（挂起标记数值负 998，见 02）。
- `unknown_call_result() -> i32`：固定返回"功能未实现"（数值 78）。

**事件循环**（`server.rs`）：

- `IpcTransport` 特征：`receive() -> Result<(Message, IpcStatus), ()>` 与 `send(dest: Endpoint, msg: &Message) -> Result<(), ()>`。生产实现对接内核收发原语（待内核落地），测试替身用队列预置消息。
- `IpcServer` 结构：持有传输层句柄、已初始化标志、丢弃计数。单线程事件循环，不需要锁（与虚拟内存服务同款 single-threaded 模型，`RefCell` 合理）。
- `run_once() -> RunStep`：处理一轮（接收、分类、分流或者分发、回信判决）。测试直接调用它，一次驱动一轮。
- `run() -> !`：无限循环调用 `run_once`，连续接收失败达到上限（32 次）则终止，避免传输损坏时无限空转。

### 4.3 关键不变量

- 分类顺序不可调换：通知检查必须在进程事件与管理信息库检查之前（通知没有合法的来源与类型，先排除）。
- 挂起标记永不进入回信路径：`should_reply` 返回假时，分发结果不得再被编码成回复消息（由测试钉住）。
- 收尾钩子只在查表分发路径运行：通知、进程事件、管理信息库三个分支的 `continue` 都绕过它（与 C 一致，由三个分支的测试分别钉住零次运行）。

## 6 过渡

本篇讲完了骨架：启动时登记哪三个回调，主循环收到消息之后先问哪几个问题，什么时候回信，什么时候不回信。但是还有三个问题没回答：第一，七个调用编号各自长什么样，消息里面带了哪些字段（02 回答）；第二，启动时注册的那棵管理信息库子树长什么样，主循环里面那句 `rmib_process` 到底做了什么（03 回答）；第三，每个处理函数内部怎么做（05 到 08 回答）。下一篇先回答第一个问题：协议面。

在启动时序里面的位置：本篇是阶段 1，主循环是所有处理函数篇章的锚点。05 到 08 的每一篇开头都会回到本篇的这张分流图，指认自己是第 5 步查表命中的哪一个表项。
