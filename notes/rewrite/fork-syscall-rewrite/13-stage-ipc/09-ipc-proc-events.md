# 09 — 进程事件：有人死了，告诉等他的人

> **状态**: 已改写（2026-09-05，依据 plan.md 阶段 5 事件面边界从零写作）
> **定位**: 阶段 5 跨服务协作（主循环收到进程管理器 `PROC_EVENT` 时发生什么）
> **源码**: `minix3/minix/servers/ipc/main.c` 第 3 行（订阅掩码常量）、第 4 行（事件掩码全局）、第 144 行到第 214 行（订阅更新与事件处理）；`minix3/minix/include/minix/syslib.h` 第 289 行到第 294 行（事件位）
> **Rust 模块**: `os/servers/ipc-server/src/events.rs`（订阅状态机与事件应答）
> **说明**: 信号量等待者挂起后，如果等待的进程死了或被信号打断，挂起不能留着——进程管理器把"谁出什么事"告诉本服务，本服务取消对应的等待。本篇讲订阅什么时候开、什么时候关，事件来了怎么分诊。取消等待的内部实现是 06 的事情，本篇只讲事件的送达与应答。

## 1 概念

### 1.1 目标读者与前置知识

面向已经读过 01、05、06 篇的读者。前置知识：01 篇的进程事件分支，05 篇的订阅开关调用点，06 篇的取消函数。订阅是什么不需要预习——"告诉进程管理器：这两种事发生时通知我"。

### 1.2 本篇不讲什么

- 等待记录的结构、取消计数的调整——那是 06 的事情（本篇只调用取消函数）。
- 订阅掩码的内核侧实现——那是进程管理器的事情（本篇只讲调用契约）。
- 共享内存为什么不用订阅——08 已讲（轮询对照），本篇只注记结论。
- 服务退出与重启——那是 10 的事情。

### 1.3 为什么订阅是开关式的

一个刚接触实现的读者最容易犯的错误，是以为"订阅了就一直订着"。其实订阅是个开关：第一个信号量集合诞生时打开（05 篇创建），最后一个消失时关闭（05 篇删除），平时没人用信号量时处于关闭状态。开关而不是常开有两个原因。第一，事件是有成本的：进程管理器每次进程退出或信号都要给订阅者发信，没人用信号量时收这些信是纯开销——注释第 153 行到第 159 行把账算得很细：只在"有人用"时订阅。第二，开关只有两种状态变化才值得调一次：从"零需求"到"有需求"、从"有需求"到"零需求"——需求在非零之间波动（两个集合变三个）不值得再调一次。Redox 操作系统的 interest 掩码是同款思想：只订阅关心的事件，关心集合变化时才重设。

### 1.4 一次事件的完整旅程（以等待者被信号打断为例）

```
1. 用户进程甲挂起等待（06 篇），用户进程乙给甲发信号
  → 2. 进程管理器：把"甲被信号"事件发给本服务（本服务订着）
  → 3. 主循环：来源进程管理加类型事件，走事件分支（01 篇）
  → 4. 事件处理：读出端点与种类（非退出即信号），调 06 的取消函数
  → 5. 取消函数：释放等待记录，补发中断回信（06 篇）
  → 6. 回执：原样回一封"收到"给进程管理器（无论第 5 步发生什么都回）
```

注意第 6 步的"无论如何都回"：回执是对"信收到"的确认，不是"事办成"的报告——即使事件端点根本没在等（陌生事件），回执照发。这是从 01 篇继承的规矩：专用分支的信都要有交代（通知除外，它连类型都没有）。

### 1.5 小结

事件面由四部分组成：掩码常量、订阅开关、事件分诊、回执。记住这四部分，05 篇的两个调用点（开与关）与 06 篇的取消函数（分诊的去向）就有了归宿。

## 2 C 源码分析

### 2.1 掩码与全局逐项核对（`main.c` 第 3 行到第 4 行，`syslib.h` 第 289 行到第 294 行）

| 符号 | 位置 | 内容 |
|------|------|------|
| `SEM_EVENTS` | `main.c:3`（`0x01`） | 信号量模块的订阅需求位（注释写明"目前只有信号量用"——为消息队列预留扩展位） |
| `event_mask` | `main.c:4`（全局） | 当前总需求掩码（各模块需求位或起来） |
| `PROC_EVENT_EXIT` | `syslib.h:292`（`0x01`） | 退出事件位 |
| `PROC_EVENT_SIGNAL` | `syslib.h:293`（`0x02`） | 信号事件位 |

需求位（`SEM_EVENTS`）与事件位（`EXIT`/`SIGNAL`）是两套东西：前者记"本服务想要什么"，后者记"发生了什么"。订阅时把两个事件位一起订（或全不定），不挑——注释第 153 行到第 159 行解释为什么不定单个进程：订阅"正在投递信号的过程中"建会漏事件导致死锁，宁可全订。

### 2.2 订阅开关逐项核对（`update_sub`，第 144 行到第 170 行）

| 步骤 | C 位置 | 行为 |
|---|------|--------|
| 变化判断 | 第 148 行（零与非零互异） | 老掩码与新掩码一个为零一个非零才动作；非零之间波动不动作 |
| 打开 | 第 163 行到第 164 行 | 订阅退出加信号两事件 |
| 关闭 | 第 165 行到第 166 行 | 退订（掩码零） |
| 登记 | 第 169 行 | 更新全局掩码 |

退订后的遗留事件（注释第 160 行到第 161 行）：退订后还可能收到几封之前订阅期的遗留事件，必须正确回执（不能因"已退订"而拒收）——回执逻辑不看订阅状态，只看信。这是 2.4 节"无论如何都回"的依据。

### 2.3 需求位开关逐项核对（`update_sem_sub`，第 176 行到第 189 行）

| 步骤 | C 位置 | 行为 |
|---|------|--------|
| 清位 | 第 180 行 | 先清信号量需求位，保留其他位（消息队列扩展位） |
| 置位 | 第 181 行到第 182 行 | 需要则置位 |
| 下沉 | 第 184 行 | 调总开关（2.2 节） |

05 篇的创建与删除调的就是这个函数（传真与假）。注释第 141 行到第 142 行写明扩展意图：消息队列落地时加需求位，总开关不动——本篇的 Rust 实现保留"或起来"的结构（`events.rs` 的掩码类型可扩展位）。

### 2.4 事件分诊逐项核对（`got_proc_event`，第 191 行到第 214 行）

| 步骤 | C 位置 | 行为 |
|---|------|--------|
| 读信 | 第 196 行到第 197 行 | 端点取自消息端点字段，退出标志取自事件等于退出位 |
| 分诊 | 第 203 行到第 204 行 | 需求位里有信号量位则调 06 的取消函数（无则跳过——退订后遗留事件走这里直接去回执） |
| 回执 | 第 207 行到第 210 行 | 原样回"收到"类型；发送失败只打印（对端进程管理器不可能消失，失败仅记日志） |

分诊的注释（第 199 行到第 202 行）写明"目前只有信号量需要知道进程被信号与退出"——共享内存不需要（08 的轮询对照）。陌生端点（没在等）调取消函数，取消函数内部直接返回（06 篇 2.6 节"未挂起则返"），回执照发。

## 3 Rust 设计决策

| 编号 | 决策 | C 做法 | Rust 做法 | 为什么这样做 |
|---|------|--------|-----------|--------|
| D1 | 掩码变类型 | 裸整数掩码加全局变量（第 3 行到第 4 行） | `Subscription{want_sem: bool}` 加 `sync() -> Option<SyncAction>`（`events.rs`） | 需求位目前只有一位，布尔足矣；扩展位加字段（注释记消息队列位）；全局变量变服务层持有值 |
| D2 | 开关边沿变返回值 | 变化判断内联（第 148 行） | `sync` 只在零与非零互异时产出动作，否则空（`events.rs`） | 边沿语义独立可测（三测：关闭保持、打开动作、波动无动作）；调用进程管理器的效应由服务层执行 |
| D3 | 事件变枚举 | 端点加整数事件（第 196 行到第 197 行） | `ProcEvent{endpoint, kind: EventKind::{Exit, Signal}}`（`events.rs`，02 的解码已备） | 退出与信号是两种东西，枚举让分诊分支穷尽；未知事件值归信号（C 的等值判断语义：只有退出位算退出，其余都当信号） |
| D4 | 回执变常量 | 原样回类型（第 207 行） | `ack_type() -> i32` 回"收到"类型（`events.rs`） | 与 01 篇的回执类型函数同款；发送失败记数（01 篇循环已有计数器） |

微内核对照（类比，不是移植依据）：Redox 的进程退出通知同样走订阅制（只订自己关心的），且回执与办理分离——与本篇 D2/D4 同构。seL4 的坏访问错误是同步异常（无订阅），形状不同，不适用这里（进程事件天生异步）。

替代方案及否决：常开订阅（省掉开关）——否决，因为事件有成本且注释算过账；开关逻辑是 C 的显式设计，不是偶然。

## 4 实现详解

### 4.1 模块结构

```
os/servers/ipc-server/src/
  events.rs       — 订阅状态机、事件类型、回执（本篇 D1 到 D4 的落地）
```

取消等待调 06 的 `WaiterTable::cancel`，由服务层在分诊后执行（本模块只产出"去取消谁"的分诊结论，不直接碰等待表——与 05 篇 D3 同款效应分离）。

### 4.2 关键类型与函数

**订阅**（`events.rs`）：

- `Subscription { want_sem: bool, synced: bool }`：需求与已同步状态。
- `SyncAction::{Subscribe, Unsubscribe}`：服务层要调进程管理器的动作。
- `set_sem_want(want: bool) -> Option<SyncAction>`：2.3 节的清位、置位、下沉；只在边沿产出动作（2.2 节语义）。

**事件**（`events.rs`）：

- `EventKind::{Exit, Signal}`：退出与信号；`from_raw(event: u32)` 非退出值归信号（C 等值判断语义）。
- `ProcEvent{endpoint, kind}`：分诊输入（02 的 `ProcEventIn` 已解码端点与退出标志，本模块做枚举化）。
- `needs_cancel(kind) -> bool`：恒真（两类事件都进取消函数，06 内部分流）——函数存在是为了把"C 无条件调用"写成可测的真值。
- `ack_type() -> i32`："收到"类型常量。

### 4.3 关键不变量

- 边沿触发：非零波动不产出动作（测试三态钉住）。
- 回执无条件：分诊结果不影响回执（测试陌生端点仍回执——服务层语义注记）。
- 非退出即信号：未知事件值归信号（C 等值判断的直接后果，测试钉住）。
