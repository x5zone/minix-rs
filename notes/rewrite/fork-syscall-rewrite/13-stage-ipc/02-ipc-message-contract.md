# 02 — 进程间通信的协议面：七个调用编号、七种消息结构、一张特权清单

> **状态**: 已改写（2026-09-05，依据 plan.md 阶段 2 协议面边界从零写作）
> **定位**: 阶段 2 协议面（后面所有处理函数篇章的前置依赖）
> **源码**: `minix3/minix/include/minix/com.h` 第 785 行到第 796 行（调用编号）、第 610 行到第 619 行（进程事件编号）、第 1151 行（挂起标记）；`minix3/minix/include/minix/ipc.h` 第 355 行到第 422 行（七种消息结构）、第 1802 行到第 1813 行（进程事件消息）；`minix3/minix/servers/ipc/ipc.conf`（特权面）；`minix3/sys/sys/ipc.h`、`minix3/sys/sys/sem.h`、`minix3/sys/sys/shm.h`（System V 常量）
> **Rust 模块**: `os/libs/minix-types/src/ipc/ipc_server.rs`（语义层：调用编号枚举与每种消息的请求响应类型）、`os/libs/minix-types/src/ipc/message.rs`（传输层：七种消息的二进制布局）
> **说明**: 协议面回答一个问题：用户进程发来的那封信，信封上写了什么，信纸上每个格子是什么意思。本篇把七个调用编号、七种消息结构的每个字段、进程事件消息、挂起标记的特殊语义、特权配置文件，一次讲全。处理函数收到信之后怎么做是 05 到 08 的事情，本篇只讲信本身。

## 1 概念

### 1.1 目标读者与前置知识

面向已经读过 01 篇的读者。前置知识：01 篇的主循环分流图（知道"查表分发"是第几步即可）。C 语言的结构体语法需要会读，八进制数字（比如 `001000`）在用到的时候会解释。消息传递的底层原语（内核怎么把一封信从一个进程搬到另一个进程）不需要预习——那是 `01-stage-kernel` 的进程间通信原语篇的事情，本篇只关心信的内容。

### 1.2 本篇不讲什么

- 主循环收到信之后先问哪几个问题——那是 01 的事情（骨架）。
- 权限检查怎么做（读、写、管理三种权限位怎么比对）——那是 04 的事情。
- 每个处理函数内部的流程——那是 05 到 08 的事情。
- 标识符与序号的编码细节、错误码的完整表格——收口在 99，本篇只讲协议面用到的部分。

### 1.3 为什么协议面要单独成篇

一个刚接触 Minix3 的读者最容易犯的错误，是把"信封"和"信的内容"混在一起：看到 `do_semget` 里面读了 `m_lc_ipc_semget.key`，就以为这个字段的含义属于 `do_semget`。其实不是。这个字段的含义属于协议：C 库函数 `semget` 在用户进程里面按这个布局填信，服务器按这个布局读信，两边的布局由头文件 `ipc.h` 共同约定。处理函数只是协议的使用者，不是协议的定义者。

把协议面单独抽出来有三个好处。第一，七种消息结构一次讲全，05 到 08 的每一篇都不用再解释字段含义，只引用本篇。第二，传输层（56 个字节的二进制布局）与语义层（每个字段是什么意思）可以分开演进：Rust 侧用类型安全的方式重新表达语义，但二进制布局必须和 C 一字不差，否则用户进程发来的信就读错了。第三，特权配置文件（`ipc.conf`）是协议的一部分：它规定了谁有资格给本服务写信，本服务有资格向虚拟内存服务提哪几种要求——这些都是通信契约，不是业务逻辑。

类比一下：协议面相当于邮政系统的"信封规范与邮路规定"，处理函数相当于"收信之后怎么办事"。规范先行，办事在后。Redox 操作系统的方案服务也是这个分层：方案的请求格式（路径、偏移、长度）先定死，具体文件系统的实现各写各的。

### 1.4 一封信的完整旅程（以创建信号量集合为例）

用户进程调用 C 库函数 `semget`，到服务器返回标识符，中间经过下面这些步骤：

```
1. 用户进程：C 库把键、数量、标志填入 mess_lc_ipc_semget 结构（信纸），
   信封上写调用编号 IPC_SEMGET（0xD01），收件人是进程间通信服务器
  → 2. 内核：把 64 个字节（8 字节信封加 56 字节信纸）从用户进程搬到服务器，
     顺手在信封上盖一个"发件人"章（m_source，内核填写，无法伪造）
  → 3. 服务器主循环：按 01 篇的分流图走到查表分发，调用 do_semget（05 篇）
  → 4. 服务器：把新建集合的标识符填入 retid 格子，把结果码填入信封类型字段，发回信
  → 5. C 库：从回信的 retid 格子取出标识符，作为 semget 的返回值交给用户进程
```

注意第 2 步里面的"发件人章"：调用者的身份（`m_source`）是内核填写的，不是用户进程自己声称的。所以语义层的请求类型里面，调用者字段一律来自信封，不来自信纸——这是防伪造的关键。02 篇的 Rust 设计里面，每个请求类型都有一个 `caller` 字段，它的解码来源是 `m_source`，这一点由测试钉住。

### 1.5 小结

协议面由五部分组成：七个调用编号（信封上写什么）、七种消息结构（信纸上每个格子的含义）、进程事件消息（进程管理器发来的特殊信）、挂起标记（"稍后回复"的约定）、特权配置文件（谁能写信、能向谁提要求）。记住这五部分，后文 04 到 09 的每一篇都会引用本篇的字段名，不再重复解释。

## 2 C 源码分析

### 2.1 调用编号（`com.h` 第 785 行到第 796 行）

| 调用编号 | 值 | 说明 |
|------|------|------|
| `IPC_BASE` | `0xD00` | 基址，七个编号都是基址加偏移 |
| `IPC_SHMGET` | 基址加 1（`0xD01`） | 创建共享内存段（07） |
| `IPC_SHMAT` | 基址加 2（`0xD02`） | 挂接共享内存段（08） |
| `IPC_SHMDT` | 基址加 3（`0xD03`） | 脱离共享内存段（08） |
| `IPC_SHMCTL` | 基址加 4（`0xD04`） | 控制共享内存段（08） |
| `IPC_SEMGET` | 基址加 5（`0xD05`） | 创建信号量集合（05） |
| `IPC_SEMCTL` | 基址加 6（`0xD06`） | 控制信号量集合（05） |
| `IPC_SEMOP` | 基址加 7（`0xD07`） | 操作信号量（06） |

七个编号连续，顺序是先共享内存后信号量（历史原因，和实现顺序无关）。主循环用"编号减基址"得到数组下标（01 篇第 2.4 节）。调用编号总数是七个，没有空洞。

### 2.2 七种消息结构逐项核对（`ipc.h` 第 355 行到第 422 行）

每种消息结构都是 56 个字节（不够的部分用填充字节补齐，C 用 `_ASSERT_MSG_SIZE` 宏在编译时断言长度）。下面按调用编号的顺序列出每个字段：

**信号量创建请求**（`mess_lc_ipc_semget`，对应 `IPC_SEMGET`）：

| 字段 | C 类型 | 含义 |
|------|--------|------|
| `key` | 键类型 | 查找或者创建的键；零表示私有键（只能由创建者使用，见 2.5 节） |
| `nr` | 整数 | 集合里面信号量的数量 |
| `flag` | 整数 | 创建标志（是否新建、是否独占，见 2.5 节） |
| `retid` | 整数 | 回信格：新建或者找到的集合标识符 |

**信号量控制请求**（`mess_lc_ipc_semctl`，对应 `IPC_SEMCTL`）：

| 字段 | C 类型 | 含义 |
|------|--------|------|
| `id` | 整数 | 集合标识符 |
| `num` | 整数 | 集合内的信号量序号（从零开始） |
| `cmd` | 整数 | 控制命令（取值、设值、删除等，见 05 篇） |
| `opt` | 用户空间地址 | 命令的附加参数（按命令不同解释为整数或者指针） |
| `ret` | 整数 | 回信格：命令的返回值 |

**信号量操作请求**（`mess_lc_ipc_semop`，对应 `IPC_SEMOP`）：

| 字段 | C 类型 | 含义 |
|------|--------|------|
| `id` | 整数 | 集合标识符 |
| `ops` | 用户空间指针 | 操作数组的首地址（数组在用户进程的地址空间里面，服务器通过内核拷贝逐个取出，见 06 篇） |
| `size` | 无符号整数 | 操作数组的元素个数（上限 100，见 2.5 节） |

注意 `ops` 是一个指针，不是数组本身：消息只有 56 个字节，装不下整个数组。服务器收到信之后，用内核的数据拷贝原语把数组从用户进程搬过来。这个"信里面装指针"的模式在共享内存控制请求的 `buf` 字段同样出现。

**共享内存创建请求**（`mess_lc_ipc_shmget`，对应 `IPC_SHMGET`）：

| 字段 | C 类型 | 含义 |
|------|--------|------|
| `key` | 键类型 | 查找或者创建的键；零表示私有键 |
| `size` | 长度类型 | 请求的段大小（字节数） |
| `flag` | 整数 | 创建标志（同信号量创建） |
| `retid` | 整数 | 回信格：新建或者找到的段标识符 |

**共享内存挂接请求**（`mess_lc_ipc_shmat`，对应 `IPC_SHMAT`）：

| 字段 | C 类型 | 含义 |
|------|--------|------|
| `id` | 整数 | 段标识符 |
| `addr` | 用户空间常量指针 | 希望挂接到的地址（可以为空，表示由系统选择） |
| `flag` | 整数 | 挂接标志（只读、地址取整，见 08 篇） |
| `retaddr` | 用户空间指针 | 回信格：实际挂接到的地址 |

**共享内存脱离请求**（`mess_lc_ipc_shmdt`，对应 `IPC_SHMDT`）：

| 字段 | C 类型 | 含义 |
|------|--------|------|
| `addr` | 用户空间常量指针 | 要脱离的挂接地址（全消息只有一个有效字段） |

这是七种消息里面最简单的一种：整封信只有一个地址。脱离操作不需要段标识符，因为地址本身就能定位到挂接记录（08 篇展开）。

**共享内存控制请求**（`mess_lc_ipc_shmctl`，对应 `IPC_SHMCTL`）：

| 字段 | C 类型 | 含义 |
|------|--------|------|
| `id` | 整数 | 段标识符 |
| `cmd` | 整数 | 控制命令（删除、读取状态、设置属性，见 08 篇） |
| `buf` | 用户空间指针 | 命令的附加数据区（同 `semctl` 的 `opt`，信里面装指针） |
| `ret` | 整数 | 回信格：命令的返回值 |

### 2.3 进程事件消息（`ipc.h` 第 1802 行到第 1813 行，`com.h` 第 610 行到第 619 行）

| 项目 | 值与位置 | 说明 |
|------|------|------|
| `PROC_EVENT` | 通用请求基址加 3（`com.h` 第 610 行） | 进程管理器发给订阅者的事件通知类型 |
| `PROC_EVENT_REPLY` | 通用回复基址加 0（`com.h` 第 619 行） | 订阅者回给进程管理器的回执类型 |
| `endpt` | 端点类型（消息第 1 个字段） | 发生事件的进程的端点 |
| `event` | 无符号整数（消息第 2 个字段） | 事件种类：退出（数值 1）或者信号（数值 2），定义在 `syslib.h` 第 289 行到第 294 行 |

进程事件消息不是用户进程发来的，而是进程管理器发来的（01 篇主循环的专用分流）。它的处理在 09 篇，本篇只登记它的信封与信纸。

### 2.4 挂起标记（`com.h` 第 1151 行）

| 项目 | 值 | 说明 |
|------|------|------|
| `SUSPEND` | 负 998 | 处理函数返回这个值表示"先不回信，调用者继续等待" |

挂起标记不是错误码：错误码都是正数（`errno.h`），挂起标记是负数。主循环看到它就跳过回信（01 篇第 2.5 节）。目前只有信号量等待操作会返回它（06 篇）。回复抑制的另一个标记（`EDONTREPLY`，数值 203）属于管理信息库服务的回信规则，本服务不用。

### 2.5 特权配置文件（`ipc.conf`，18 行）

| 段 | 内容 | 含义 |
|------|------|------|
| 系统特权 | `UMAP`（14）、`VIRCOPY`（15） | 本服务可以使用内核的地址映射与跨地址空间拷贝原语（处理函数拷贝用户数据时需要，见 05 到 08） |
| 用户标识 | `uid 0` | 本服务以超级用户身份运行 |
| 可接收端点 | 系统任务、普通用户进程、进程管理器、重生服务器、日志服务、终端服务、数据存储服务、虚拟内存服务 | 谁有资格给本服务写信：用户进程（七种请求）、进程管理器（进程事件）、管理信息库服务（管理信息库请求） |
| 虚拟内存请求 | `REMAP`、`REMAP_RO`、`SHM_UNMAP`、`GETPHYS`、`GETREF` | 本服务有资格向虚拟内存服务提的五种要求：重映射、只读重映射、解除共享内存映射、查询物理地址、查询引用计数（07 与 08 的跨服务契约） |

### 2.6 System V 常量（`sys/sys/ipc.h`、`sem.h`、`shm.h`）

**通用键与标志**（`ipc.h` 第 85 行到第 116 行）：

| 常量 | 值（八进制） | 含义 |
|------|------|------|
| `IPC_R` | `000400` | 读权限位 |
| `IPC_W` | `000200` | 写或者修改权限位 |
| `IPC_M` | `010000` | 修改控制信息权限位（只有创建者与超级用户能改属性） |
| `IPC_CREAT` | `001000` | 键不存在则创建 |
| `IPC_EXCL` | `002000` | 与创建标志合用时键已存在则失败 |
| `IPC_NOWAIT` | `004000` | 需要等待则直接返回错误，不阻塞 |
| `IPC_PRIVATE` | 键值零 | 私有键：每次创建都得到新对象，不与任何键关联 |
| `IPC_RMID` | 0 | 删除标识符 |
| `IPC_SET` | 1 | 设置属性 |
| `IPC_STAT` | 2 | 读取状态 |
| `IPC_INFO` | 500 | 读取模块信息（Minix3 扩展，供 `ipcs` 命令使用） |

**信号量常量**（`sem.h`）：读权限 `SEM_R`（八进制 `0400`）、改权限 `SEM_A`（八进制 `0200`）、已分配标志 `SEM_ALLOC`（八进制 `01000`，第 154 行）；单次操作上限 `SEMOPM`（100，第 184 行）；信号量最大值 `SEMVMX`（32767，第 93 行）；集合数上限 `SEMMNI`（10，第 164 行）、系统信号量总数上限 `SEMMNS`（60，第 166 行）；`SEM_UNDO`（八进制 `010000`，第 76 行）本服务明确不支持，op 篇会把"遇到就返回参数错误"写进行为契约（plan 的 A-7 项）。

**共享内存常量**（`shm.h`）：只读挂接 `SHM_RDONLY`（八进制 `010000`，第 76 行）、地址取整 `SHM_RND`（八进制 `020000`，第 77 行）；段数上限 `SHMMNI`（1024，第 218 行）、每进程挂接数上限 `SHMSEG`（32，第 219 行）；延迟销毁标志 `SHM_DEST`（`0x0400`，第 222 行，08 篇的核心语义）；私有标志 `SHM_ALLOC`（`0x0800`，07 篇）。

**标识符编码**（`ipc.h` 第 110 行，`inc.h` 第 41 行到第 42 行）：标识符的高 16 位是序号、低 16 位是数组下标（`IXSEQ_TO_IPCID` 宏）。完整编码规则收口在 99，本篇只登记"标识符不是数组下标"这个事实——05 与 07 的查找函数都要先解码。

## 3 Rust 设计决策

| 编号 | 决策 | C 做法 | Rust 做法 | 为什么这样做 |
|---|------|--------|-----------|--------|
| D1 | 调用编号变成枚举 | 裸整数宏（`com.h`），查表靠减法 | `IpcCall` 枚举加 `from_raw` 返回 `Option`（`ipc_server.rs`） | 非法编号不可表达；七个变体与七个表项一一对应，加编号时编译器逼迫补充分支；与虚拟内存服务的调用枚举同款做法 |
| D2 | 每种消息拆成请求与响应两个类型 | 一个共用结构体既当请求又当响应（`retid` 格子平时空着） | `IpcSemgetIn` 与 `IpcSemgetOut` 分开（`ipc_server.rs`） | 请求与响应的有效字段本来就不同：请求填键与标志，响应只填标识符；分开之后"响应里面带键"这种错误写不出来；与虚拟内存服务的 `VmMmapIn` 与 `VmMmapOut` 同款拆分 |
| D3 | 调用者身份来自信封 | 约定俗成（读 `m_source`），无类型保证 | 每个请求类型都有 `caller` 字段，解码函数从 `m_source` 填写（`ipc_server.rs`） | 内核填写的发件人章无法伪造，信纸里面的地址字段反而可能来自不可信的用户进程；把"身份来自信封"变成构造约束，-Trusted 来源与非受信来源在类型层面分开 |
| D4 | 二进制布局与语义分层 | 一套结构体既是布局又是语义 | 传输层（`message.rs` 的七种定长布局）与语义层（本模块的请求响应类型）分开，解码函数连接两层（`ipc_server.rs`） | 布局必须和 C 一字不差（否则读错信），语义可以用 Rust 的类型系统重新表达；与虚拟内存服务的传输层加语义层同款分层；Redox 的系统调用层同样把线格式与语义分开 |
| D5 | 指针字段变成地址加长度 | 裸指针（`void *ops`），长度另放一个字段 | `operations_address`（64 位地址）与 `operation_count`（个数）两个字段，配上限断言（`ipc_server.rs`） | 裸指针在 Rust 侧没有意义（两个地址空间的指针不能直接解引用）；地址加个数的形式逼迫调用者走内核拷贝；个数上限（100）在解码时检查，超限直接返回参数错误 |
| D6 | 特权面变成常量表 | 配置文件（`ipc.conf`），运行时由重生服务器解析 | `ALLOWED_CALLERS` 与 `VM_REQUESTS` 常量数组（`ipc_server.rs`），逐项注释来源 | 特权面是协议的一部分，应该进代码审查的视野；常量数组可被测试枚举（"七个编号全在表里"）；与数据存储服务的标志表同款做法 |
| D7 | 消息缺口显式标注（架构演进） | 无（C 不缺，缺的是 Rust 侧） | 模块头注释标注 `[ARCH: IPC-02-01]`：七种消息类型在共享类型库里面是新增的，此前不存在 | 按审查规则，新增的协议类型必须三处一致标注（行为对照点、设计文档、代码注释）；本篇即行为对照点，代码注释引用本篇 |

微内核对照（类比，不是移植依据）：Redox 的方案请求把"路径、偏移、长度"作为请求头，本篇的七种消息结构是同样的"请求头"角色；seL4 的用户态服务器用能力令牌标识调用者，本篇用内核填写的端点标识调用者——都是"身份来自可信第三方"的思想。分层（线格式与语义分开）是三个系统共同的选择：线格式为了兼容不能动，语义为了安全值得重写。

替代方案及否决：直接复用 C 结构体的逐字段翻译（每个字段一对一搬运，保留 `opt` 这种多义字段）——否决，因为 `opt` 按命令不同有时是整数有时是指针，一对一搬运会把 C 的含糊原样搬过来；本篇按命令把 `opt` 解释成明确的类型，含糊在解码层解决，不漏到处理函数里面。

## 4 实现详解

### 4.1 模块结构

```
os/libs/minix-types/src/ipc/
  ipc_server.rs   — 语义层：调用编号枚举、七组请求响应类型、进程事件类型、
                    特权面常量、解码函数（本篇 D1、D2、D3、D5、D6 的落地）
  message.rs      — 传输层：七种消息的 56 字节定长布局（本篇 D4 的布局一半）
  event.rs        — 已有：进程事件掩码与事件枚举（本篇复用，不重复定义）
  mod.rs          — 模块声明：新增 ipc_server 子模块并重导出
```

### 4.2 关键类型与函数

**调用编号**（`ipc_server.rs`）：

- `IPC_BASE`（`0xD00`）、`IPC_SHMGET` 到 `IPC_SEMOP`（基址加 1 到加 7）、`NR_IPC_CALLS`（7）。
- `IpcCall` 枚举：七个变体（`Shmget`、`Shmat`、`Shmdt`、`Shmctl`、`Semget`、`Semctl`、`Semop`），`from_raw(i32) -> Option<IpcCall>` 与 `to_raw() -> i32` 双向转换。
- `SUSPEND`（负 998）与 `should_reply` 的配合在 01 的分发模块，本篇只登记数值来源。

**请求响应类型**（`ipc_server.rs`，七组）：

- 信号量创建：`IpcSemgetIn { caller, key, count, flag }` 与 `IpcSemgetOut { id }`。
- 信号量控制：`IpcSemctlIn { caller, id, number, command, option }` 与 `IpcSemctlOut { value }`。
- 信号量操作：`IpcSemopIn { caller, id, operations_address, operation_count }`（无响应类型：成功时回成功码，挂起时不回信，见 06）。
- 共享内存创建：`IpcShmgetIn { caller, key, size, flag }` 与 `IpcShmgetOut { id }`。
- 共享内存挂接：`IpcShmatIn { caller, id, address, flag }` 与 `IpcShmatOut { attached_address }`。
- 共享内存脱离：`IpcShmdtIn { caller, address }`（无响应类型：成功只回成功码）。
- 共享内存控制：`IpcShmctlIn { caller, id, command, buffer }` 与 `IpcShmctlOut { value }`。
- 进程事件：复用 `event.rs` 的 `ProcEvent` 与掩码类型，本模块只提供 `ProcEventIn { endpoint, event }` 的解码（来源是进程事件消息）。

**传输层布局**（`message.rs`，七种）：

- `MessLcIpcSemget`、`MessLcIpcSemctl`、`MessLcIpcSemop`、`MessLcIpcShmget`、`MessLcIpcShmat`、`MessLcIpcShmdt`、`MessLcIpcShmctl`：每个 56 字节，字段顺序与 C 一致，联合体新增七个成员。32 位 C 发送者的整数字段在 64 位接收侧零扩展（与虚拟内存服务的消息布局同款处理）。

**解码函数**（`ipc_server.rs`）：每个请求类型一个 `decode_message(&Message) -> Self`，调用者字段取自 `m_source`，其余字段取自对应的传输层布局。操作个数超过上限（100）时解码函数不截断，留给 06 篇的处理函数按参数错误拒绝（本篇只定数据形状，不定拒绝规则）。

### 4.3 关键不变量

- 布局断言：七种传输层结构体的大小都等于 56（编译时断言，与 C 的 `_ASSERT_MSG_SIZE` 对应）。
- 身份来源：任何请求类型的 `caller` 字段只能来自 `m_source`，测试用伪造的信纸字段验证（信纸里面填一个假端点，解码结果不受影响）。
- 编号覆盖：`from_raw` 对七个编号返回 `Some`，对其他一切值返回 `None`（由测试枚举全部 16 位整数空间的关键边界：基址减 1、基址加 0、基址加 8）。

本篇讲完了信：七个调用编号、七种消息结构的每个字段、进程事件消息、挂起标记、特权配置。但是还有两个问题没回答：第一，启动时注册的那棵管理信息库子树长什么样，`ipcs` 命令查到的信号量与共享内存信息从哪里来（03 回答）；第二，每个处理函数收到信之后怎么做（05 到 08 回答）。下一篇先回答第一个问题：管理信息库注册。
