# 08 — 挂接与引用计数：映射、脱离、惰性数数

## 1 概念

### 1.1 目标读者与前置知识

面向已经读过 04 与 07 篇的读者。前置知识：04 篇的挂接掩码，07 篇的段表与物理地址快照。内存映射是什么不需要预习——可以把它理解成"让一块物理内存在某个进程的地址空间里有个地址"。引用计数是什么不需要预习——"数数还有几个使用者"。

### 1.2 本篇不讲什么

- 段的创建、查找、表结构——那是 07 的事情（本篇假设段已经在表里）。
- 权限判断的内部规则——那是 04 的事情（本篇只引用掩码结论）。
- 虚拟内存服务内部怎么做映射——那是 `02-stage-vm` 的事情（本篇只讲调用契约）。
- 管理信息库子树的结构——那是 03 的事情（本篇只讲组装函数交什么数据）。

### 1.3 为什么引用计数是惰性的

一个刚接触实现的读者最容易犯的错误，是以为"挂接数"是个记账字段：挂接时加一、脱离时减一。其实这里反过来：挂接与脱离都不碰这个数，每轮循环收尾时全表问一遍虚拟内存服务"这页现在被几个地址空间引用"，减掉自己那一份就是挂接数。删除标记（`SHM_DEST`）的段要等这个数归零才真正销毁——标记删除与真正销毁之间可能隔很多轮循环。

用惰性而不用记账有两个原因。第一，挂接与脱离发生在别的进程地址空间里，进程崩溃、被杀、地址空间重建都不会通知本服务——记账会漏，只有现查是准的。第二，删除语义因此是"延迟销毁"：标记先立，销毁等数归零——这正是 System V 要求的"删了名、不断连"（删标识符不断已有挂接）。Redox 操作系统的共享内存引用计数是记账式的（内核统一管理映射，崩溃时内核代收），Minix3 把映射散在各进程、由服务轮询——两种形状各有利弊，本篇不评判，只把轮询语义讲准（plan A-3 记为决策点：轮询保留）。

### 1.4 一次挂接与一次延迟销毁之旅

```
挂接：
1. 用户进程：发起挂接请求（段标识符、希望地址、标志）
  → 2. 地址取整：未对齐且无取整标志则回参数错误，有则向下取整
  → 3. 按标识符找段（找不到回参数错误），按标志查权限
  → 4. 请虚拟内存服务把段的物理页映射到调用者地址空间（失败回内存不足）
  → 5. 刷新访问时间与最后进程，回实际地址（挂接数不动，惰性）

延迟销毁：
1. 用户进程：发起删除命令 → 所有者身份通过 → 立删除标记（段还在）
  → 2. 每轮收尾：查引用数；只要还有人挂着就不销毁
  → 3. 某轮查到零挂接：解映射、清分配位、收缩水位
```

注意挂接第 4 步的映射方向：源是本服务自己的地址（段内存驻在本服务地址空间），目标是调用者地址——跨地址空间的重映射，五个特权之一（02 篇的 `REMAP`）。脱离是反向：调用者地址解映射。

### 1.5 小结

挂接由六部分组成：地址取整、权限掩码、重映射、脱离认亲、控制命令、惰性刷新与延迟销毁。记住这六部分，09 篇的订阅（共享内存不用）与 10 篇的空表判断（高水位归零）就有了依据。

## 2 C 源码分析

### 2.1 挂接逐项核对（`do_shmat`，第 130 行到第 170 行）

| 步骤 | C 位置 | 行为 |
|---|------|--------|
| 地址取整 | 第 141 行到第 146 行 | 未按页对齐且无取整标志则回参数错误；有则向下取整到页边界 |
| 找段 | 第 148 行到第 149 行 | 按标识符查找，找不到回参数错误 |
| 查权限 | 第 151 行到第 157 行 | 只读标志则读位，否则读加写位（04 篇掩码表），不过回访问拒绝 |
| 重映射 | 第 159 行到第 162 行 | 源本服务地址、目标调用者地址、长度整段；失败回内存不足 |
| 记时间与进程 | 第 164 行到第 165 行 | 刷新访问时间与最后进程（挂接数不动，注释第 166 行写明惰性） |
| 回地址 | 第 168 行 | 回实际映射地址 |

映射长度用段的原始大小（`shm_segsz` 存原文，第 160 行直传；页取整是映射原语内部的事。销毁解映射时显式取整，第 192 行到第 193 行）——07 篇记了两个数，这里用的是记账侧。

### 2.2 引用计数刷新逐项核对（`update_refcount_and_destroy`，第 173 行到第 206 行）

| 步骤 | C 位置 | 行为 |
|---|------|--------|
| 逐槽问数 | 第 178 行到第 187 行 | 只扫到高水位，跳过空槽；问本服务地址上该页的引用数；问不到（返回 255）则警告并跳过该槽 |
| 换算挂接数 | 第 187 行 | 引用数减一（自己占一份）：`nattch = rc - 1` |
| 延迟销毁 | 第 189 行到第 196 行 | 挂接数为零且立了删除标记：解映射（长度取整）、清分配位 |
| 收缩水位 | 第 203 行到第 205 行 | 尾部连续空槽回落高水位 |

三个细节值得记住：第一，问不到引用数（255）时不断言、不销毁，只警告——页面失踪是虚拟内存侧的问题，本服务不擅自删段。第二，`nattch` 是 `short` 类型（`shmatt_t`），引用数是字节——256 个以上挂接会绕回，实际挂接上限三十二，够不着。第三，销毁只清分配位不碰序号——序号保留语义与 05 篇同款（空闲槽留序号）。

调用点三处：主循环每轮收尾（01 篇）、脱离末尾（2.3 节）、删除命令与状态查询前（2.4 节）。状态查询前也刷新——读到的挂接数必须是新鲜的（注释第 276 行到第 279 行写明：刷新可能释放槽位，所以先刷新后找槽）。

### 2.3 脱离逐项核对（`do_shmdt`，第 209 行到第 242 行）

| 步骤 | C 位置 | 行为 |
|---|------|--------|
| 问物理地址 | 第 218 行到第 219 行 | 问调用者地址的物理地址；问不出（零）回参数错误 |
| 按物理认亲 | 第 221 行到第 235 行 | 只扫到高水位，跳过空槽；物理快照相等即命中；刷新访问时间与最后进程；解调用者侧映射；跳出 |
| 找不到 | 第 236 行到第 237 行 | 只打印一行日志，不回错误（返回码照样成功） |
| 收尾 | 第 239 行到第 241 行 | 刷新引用计数（认亲解映射后数变了），回成功 |

"找不到不算错"是全文最反直觉的一句，值得现在就记住：脱离一个没挂接的地址，C 只打印日志，返回成功。理由是脱离的调用者经常"宁可多脱一次"（退出路径的清理逻辑），报错反而添乱。08 篇的 Rust 实现保持同样行为（行为契约，非演进）。

### 2.4 控制命令逐项核对（`do_shmctl`，第 261 行到第 371 行）

先刷新（状态查询两命令，2.2 节的顺序要求），再找段（三路：信息查询无段、状态查询按槽下标、其余按标识符），再走命令：

| 命令 | 值 | 行为 |
|------|------|------|
| `IPC_STAT` | 2 | 读权限检查，把描述符拷贝给调用者 |
| `SHM_STAT` | 13 | 同上（按槽下标找段），另回标识符 |
| `IPC_SET` | 1 | 所有者身份检查（否则回操作不许可），从调用者拷回草稿，只收所有者、组、模式低九位，刷新改属性时间 |
| `IPC_RMID` | 0 | 所有者身份检查，立删除标记（段不立即消失），刷新引用计数（零挂接则当场销毁） |
| `IPC_INFO` | 500 | 填概要信息并拷贝，另回最高在用槽号（空表回零） |
| `SHM_INFO` | 14 | 填聚合信息（在用段数、总页数、常驻等于总数、交换三项零）并拷贝，另回最高在用槽号 |
| 其他 | — | 回参数错误 |

删除与信号量的对照：信号量的删除当场清槽叫醒（05 篇），共享内存的删除只立标记、销毁等数归零——"删名"与"销毁"分离是本篇的核心差异，记住它。

概要填充（`fill_shminfo`，第 248 行到第 258 行）：最大值、每进程段数、总页数三项填全一（不限或未知），最小值一，标识符上限一千零二十四。

### 2.5 管理信息库组装与空表判断

**组装**（`get_shm_mib_info`，第 379 行到第 444 行）：与 05 篇同款三段式（概要捷径、断言、空指针报尺寸、逐项拷贝），每项八个字段（权限快照用 04 的搬运、大小、两进程、四时间、挂接数），数组长度恒等于标识符上限（`ipcs` 契约，注释第 399 行到第 404 行）。

**空表判断**（`is_shm_nil`，第 465 行到第 469 行）：高水位为零即空（10 篇的退出判定用）。

**死代码**（第 446 行到第 462 行 `#if 0`）：调试打印函数，不编译，plan 已记排除。

## 3 Rust 设计决策

| 编号 | 决策 | C 做法 | Rust 做法 | 为什么这样做 |
|---|------|--------|-----------|--------|
| D1 | 取整变纯函数 | 未对齐分支内联（第 141 行到第 146 行） | `align_addr(addr, flag) -> Result<u64, ShmError>`（`attach.rs`） | 对齐规则独立可测（对齐、未对齐无标志、未对齐有标志三测）；页大小具名 |
| D2 | 刷新变纯扫描 | 全表轮询加原地销毁（第 173 行到第 206 行） | `sweep(table, counts) -> SweepPlan`（`refcount.rs`）：引用数由调用者查好传入，产出销毁名单与解映射请求 | 轮询是跨服务查询（虚拟内存侧），判断是纯逻辑；与 04 篇 D1 同款分离；名单顺序即销毁顺序，测试可断言 |
| D3 | 销毁效应显式 | 解映射直接调（第 191 行到第 193 行） | `UnmapReq{addr, len}` 名单（`refcount.rs`），服务层执行 | 解映射是内存管理效应；255 警告变名单里的跳过项（可观测，不打印） |
| D4 | 认亲变纯查找 | 物理问询加线性比对交织（第 218 行到第 235 行） | `find_by_phys(table, phys) -> Option<usize>`（`attach.rs`）；问询留边界 | 比对逻辑可单测；找不到回成功（2.3 节契约）在服务层表达 |
| D5 | 控制命令变枚举 | 裸整数分支（第 283 行/第 301 行） | `ShmctlCommand` 枚举加 `from_raw`（`attach.rs`） | 与 05 篇 D5 同款：三处分支一致性编译器监督 |
| D6 | 状态查询刷新顺序变类型 | 注释约束顺序（第 276 行到第 281 行） | 服务层序列在 `attach.rs` 的 `stat_sequence()` 文档函数里钉死：刷新→找段→拷贝 | 顺序是正确性的一部分（先找段会拿到释放前的槽）；文档函数即检查清单，落地时照单执行 |

微内核对照（类比，不是移植依据）：Redox 的内存映射引用计数由内核记账，进程退出时内核代收映射——集中式；Minix3 的惰性轮询是分布式——服务不信任任何通知，只信现查。两种形状各有利弊：集中式实时准确但内核复杂，分布式简单但销毁延迟。本篇保留分布式（plan A-3 决策：轮询保留），只把"查"与"判"分开。

替代方案及否决：改记账式（挂接加一、脱离减一）——否决，因为进程崩溃与地址空间重建不经过本服务，记账会永久漏数；且这是行为级变更（销毁时机改变），plan A-3 已定保留轮询。

## 4 实现详解

### 4.1 模块结构

```
os/servers/ipc-server/src/shm/
  attach.rs       — 取整、认亲查找、控制命令枚举与执行（本篇 D1、D4、D5 的落地）
  refcount.rs     — 引用计数刷新扫描（本篇 D2、D3 的落地）
```

07 的 `segment.rs` 管表与创建，本篇两模块管使用与销毁——创建与使用在 `ShmTable` 上会合。

### 4.2 关键类型与函数

**挂接与控制**（`attach.rs`）：

- `align_addr(addr: u64, flag: u32) -> Result<u64, ShmError>`：页对齐则原样，未对齐有取整标志则向下取整，否则参数错误。
- `find_by_phys(table, phys: u64) -> Option<usize>`：扫到高水位、跳空槽、物理快照相等即命中。
- `ShmctlCommand` 枚举：六个变体（删除、改属性、查状态、按槽查状态、概要、聚合），`from_raw(i32) -> Option`。
- `authorize(cmd, perm, caller) -> Result<(), ShmError>`：状态查询读位、删除改属性身份、信息放行（调 04 决策）。

**引用计数**（`refcount.rs`）：

- `RefQuery { slot, count: Option<u8> }`：调用者查好的引用数（`None` 表示问不到，对应 255）。
- `UnmapReq { addr: u64, len: u64 }`：服务层要执行的解映射。
- `SweepPlan { unmaps: Vec<UnmapReq>, freed: Vec<usize>, skipped: Vec<usize> }`：销毁名单、释放槽位、跳过槽位。
- `sweep(table, queries) -> SweepPlan`：2.2 节的逐行对应（换算、销毁条件、跳过、水位收缩在本函数末尾）。

### 4.3 关键不变量

- 刷新顺序：状态查询先刷新后找段（D6 文档函数，服务层照单执行）。
- 找不到不算错：脱离认亲失败回成功（服务层表达，测试钉住）。
- 名单顺序：销毁与解映射按槽序（与 C 的从低到高一致），测试断言顺序。
- 序号保留：释放槽留序号（与 05 篇同款，07 的构造即遵守）。
