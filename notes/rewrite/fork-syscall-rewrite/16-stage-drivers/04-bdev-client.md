## 1. 概念：电话总机

### 1.0 章节引言

目标读者是已经读完第二篇的读者。前置知识只需要一条：块请求有七种，编号是基址加索引。本章站在马路另一边看同一个十字路口：驱动侧是接电话的，客户端是打电话的。

### 1.1 客户端库是一台电话总机

想象一栋大楼的电话总机。分机想打电话，不用知道外线怎么走：拿起话筒说找谁，总机接通，通完计费。驱动端点表就是总机的通讯录：主设备号对应哪条外线（驱动端点）。打开计数是通话记录：哪个分机正在通话中。异步调用表是留言本：对方忙时先记下，通了再回拨。

这台总机有三本账：通讯录（驱动表，十六个主设备号各记一个端点），通话记录（打开计数，最多四个不同的次设备），留言本（异步调用表，最多二百五十六条未完成的调用）。三本账的上限各不相同，因为用途不同：通讯录按系统里的驱动个数定，通话记录按文件服务器同时打开的设备数定（文件服务器同时只用几个盘），留言本按并发请求数定。

### 1.2 同步调用：拿起话筒就说

同步打开的流程是：查通讯录找端点，找不到在本地拒绝（不打扰任何人）；组装打开消息（次设备号、访问方式、同步标识）；发出去等回复；回复的标识必须原样返回，类型必须是通用回复，否则视为坏回复；状态成功才记通话记录，失败不记。

同步关闭的流程多一道本地门：通话记录里没有这个设备，直接在本地拒绝，连消息都不发。这个门防止调用方关一个从没打开过的设备去骚扰驱动。记录里有才发关闭消息，驱动说成功才销记录，驱动说失败保留记录（关闭没成功，通话还在继续）。

读写与向量读写走同一条路，只是操作码与材料不同。设备控制多一个用户端点参数（控制操作可能涉及调用应用程序的授权）。所有同步调用共用一个回复检查函数：标识对上才认，类型不对报无效参数，发不出去报输入输出错误。

### 1.3 异步调用：先留言再回拨

同步调用是打电话等接通，异步调用是发短信等回拨。调用方把请求登记进留言本（分配调用槽），发出去就干别的事，回复到了由分发函数按标识找到原槽，记下状态，等调用方来取。等待函数是调用方取留言的动作：本实现里是非阻塞收集（有结果拿走，没结果稍后再来），生产环境由服务层的事件循环驱动。

留言本的槽位有两本预算：驱动重启重试十次，传输错重试五次。发不出去扣驱动预算，扣完还没发出去就判输入输出错误；传输报输入输出错误扣传输预算。其他错误直接完成调用，不重试（重试一个被拒绝的请求没有意义）。

刷新函数是把留言本里发给某个设备但还没发出去的请求全部发一遍，用于驱动刚回来时的补发。回调是留言本的高级用法：调用方登记时留一个函数，回复到时自动调，本实现把回调留在服务层，只管状态机可测试的部分。

### 1.4 驱动重启：总机重拨

驱动重启是总机最忙的时候。正在飞的请求分两类：同步调用在发送处卡住，返回发送失败，调用方决定重试；异步调用扣驱动预算，预算还有就重发，预算没了判错。已经打开的设备要重开：按通话记录里记的次数，一次一次重发打开请求（打开两次的设备重开两次，保持计数对得上）。

重开有个 honesty 注释：如果重开中途遇到非传输错误，之前已经重开好的次设备可能永远关不掉（源码里的 FIXME 原话）。Rust 实现把这个诚实注释保留在文档里，不假装问题不存在：恢复流程尽力而为，失败时返回错误让上层决定，不静默丢状态。

### 1.5 传输抽象：总机不碰电话线

C 语言直接调内核消息原语发消息，这让库函数在没有内核的环境里无法测试。Rust 实现把发消息收回复收进一个行为定义：生产环境用内核原语实现，测试用回环与录制替身。行为定义只过四个整数（端点、类型、次设备号、标识）加回复三元组，内核的端点类型、消息结构体一律不进本库。这是硬件抽象原则在用户态的对应：调用策略与传输机制分离，策略可测，机制可换。

回环替身模拟健康驱动：标识原样返回，状态按配置来，外加一次性的错标识模式专测坏回复路径。录制替身按剧本回放：预先排好成功失败序列，测重试逻辑时看发了几次、每次发给谁。门禁要求行为定义至少有两个行为不同的实现，这两个替身满足。

### 1.6 与驱动侧的镜像关系

驱动侧七种请求，客户端七种操作，编号必须一致。本实现在测试里锁死编号（打开 `0x500`，收集 `0x504`，分散 `0x505`，控制 `0x506`），框架侧改编号这里立刻变红。这是刻意放的绊线：两边由不同的人维护时，编号漂移是最常见的闭环断裂，测试里的硬编码就是防漂移的钉子。

### 1.7 本章小结

客户端库是电话总机：通讯录找驱动，通话记录管打开，留言本管异步，重启时重拨。同步调用直来直去，异步调用登记等待分发收集。传输抽象让策略可测。下一章进入 C 语言源码验证。

### 2.2 常量：三本账的上限

调用上限二百五十六（`const.h`），同步标识负一（`const.h`，同步请求不用分发所以标识固定），数据存储查询一百次间隔五十微秒（驱动发现时的轮询预算），驱动重试十次（`const.h`），恢复容忍两次重启，传输重试五次（`const.h`），打开跟踪四个不同次设备（`const.h`）。

### 2.3 驱动端点表（`driver.c`）

表里每项记端点加标签。初始化全填未知，绑定写标签并清端点（清掉旧端点，强制重新通过数据存储解析，保证拿到的是新驱动的端点），查询返回端点或未知，清除忘掉绑定，更新走数据存储查新端点并处理驱动重启（重启时触发重开流程）。

### 2.4 打开计数（`minor.c`）

数组每项记设备号、计数、访问位累积。增加时同设备计数加一并累积访问位，无空槽打印太多打开设备并丢掉记录（打开本身已成功，只影响重启恢复）。删除时计数减一，到零销项。查询告诉调用方设备是否打开过。重启重开按记录逐次重发打开：打开两次的设备重发两次，保证计数对得上。源码里的 honesty 注释（重开中途失败则已重开的次设备可能永远关不掉）是真实的设计缺口，本实现保留语义：恢复函数返回第一个错误，不假装全成功。

### 2.5 同步发送与异步发送（`ipc.c` 第一百零二行到第二百六十八行）

驱动上线更新先查数据存储拿端点，查不到按轮询预算重试（查询一百次、每次间隔五十微秒是上限，不是每次必查满）。异步发送组装消息发出去不等回复，调用标识用调用槽索引；同步发送发出去等回复，标识固定负一，回来先验类型再验标识最后取状态，三验缺一即坏回复。

重试预算藏在发送循环里：驱动重启十次内重发，传输错五次内重发，恢复中途再重启容忍两次。预算数字全在 `const.h`，测试里锁死，改预算测试变红。

### 2.6 回复分发与等待（`ipc.c` 第二百六十九行到第三百四十六行）

回复分发按标识找调用槽，找到记状态，找不到打日志丢掉（游离回复）。等待函数按标识阻塞到回复到。回调在分发时调，参数原样递回。刷新函数把某设备名下所有没发出去的异步请求发一遍。

## 3. Rust 设计决策

> 本章解释为什么这样设计。每个决策先给依据，再给替代方案与取舍。

### 3.1 设备号做成值类型（依据：第 1.1 节、第 2.3 节）

主设备号透明包装，完整设备号高位主设备号低八位次设备号，打包解包为常量函数。日志里的数值与 C 语言一致，排错时两边对得上。替代方案是裸整数到处传，不选的理由是：主次传反编译器不吭声，而这是客户端最常见的调用错误。

### 3.2 驱动表做成常量泛型宽度（依据：第 1.1 节、第 2.3 节）

默认十六与 C 表同宽，测试可缩小。未知端点用负一标记，与 C 的未知标记同值。绑定即覆盖，清除即忘掉。替代方案是动态表，不选的理由同驱动侧：宽度是系统常量，编译期定死。

### 3.3 打开计数做成定长数组（依据：第 1.1 节、第 2.4 节）

四个槽位，同设备累积计数与访问位，满了返回失败。查找删除计数三个操作全是线性扫描，四项上限下足够快。替代方案是哈希表，不选的理由是：无标准库环境下哈希表是额外依赖，四项线性扫描更快更简单。

### 3.4 调用表做成槽位数组加两本预算（依据：第 1.3 节、第 2.5 节）

二百五十六槽，驱动预算十，传输预算五。收集即释放，槽位永不泄漏。发送失败扣驱动预算，传输错误扣传输预算，其他错误直接完成。设备归属查询供重启重发用：重发时按设备找槽，不用翻整个表。替代方案是链表加动态分配，不选的理由是：上限固定，数组加状态机最简单，且收集即释放的规则让泄漏在类型层面不可能（没有分配就没有泄漏）。

### 3.5 传输做成行为定义（依据：第 1.5 节、第 2.5 节）

请求四元组（端点、类型、次设备号、标识）进，回复三元组（类型、标识、状态）出，外加三种传输错误。回环替身模拟健康驱动，录制替身按剧本回放。两个行为不同的实现满足门禁，也覆盖了测试的两种需要：状态配对测试用回环，重试计数测试用录制。替代方案是直接依赖内核传输，不选的理由是：那样全部测试都要进内核环境，策略逻辑测不起。

### 3.6 同步客户端组合三件套（依据：第 1.2 节、第 2.5 节）

驱动表加打开计数加传输，一个结构体装三样。打开只记成功，关闭先查本地记录，错误码按回复检查函数统一翻译。替代方案是三个全局单例，不选的理由是：全局单例测起来互相污染，一个测试的绑定漏到下个测试里。组合结构体让每个测试new一个干净的，天然隔离。

### 3.7 设计决策汇总

| 决策 | 依据 | 替代方案 | 为何不选 |
|------|------|----------|----------|
| 设备号值类型 | 第 1.1、2.3 节 | 裸整数 | 主次传反无检查 |
| 驱动表泛型宽度 | 第 1.1、2.3 节 | 动态表 | 宽度是系统常量 |
| 打开计数定长数组 | 第 1.1、2.4 节 | 哈希表 | 四项线性更快更简单 |
| 调用表槽位加预算 | 第 1.3、2.5 节 | 链表加分配 | 固定上限下数组最简单 |
| 传输行为定义 | 第 1.5、2.5 节 | 直连内核传输 | 策略测不起 |
| 同步客户端三件套 | 第 1.2、2.5 节 | 全局单例 | 测试互相污染 |

## 4. 错误处理

| 场景 | C 行为 | Rust 表达 | 说明 |
|------|--------|-----------|------|
| 无驱动绑定 | 本地拒绝 | `open` 报无效参数 | 不打扰任何人 |
| 关未打开设备 | 本地拒绝 | `close` 报无效参数 | 不骚扰驱动 |
| 发不出去 | 输入输出错误 | `check_reply` 映射发送失败 | 传输错即输入输出错 |
| 坏回复 | 无效参数 | `check_reply` 映射标识类型错配 | 三验缺一即坏 |
| 驱动消失 | 恢复或报错 | `TransportError::DriverGone` 映射忙 | 上层决定重试或放弃 |
| 调用表满 | 负标识 | `CALL_TABLE_BUSY`（无内存） | 调用方稍后重试 |
| 重试耗尽 | 判错 | 槽内记输入输出错误 | 预算归零即放弃 |
