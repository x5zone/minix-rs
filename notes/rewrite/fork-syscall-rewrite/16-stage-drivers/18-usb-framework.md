# 18-usb-framework：通用串行总线框架

> **分类**：通用串行总线第 1 篇（请求包编号与枚举顺序，包格式只定编号）
> **源码**：`minix3/minix/lib/libusb/usb.c`（二百五十五行的客户端库）、`minix3/minix/drivers/usb/usbd/base/usbd.c`（一百八十四行的守护启动）、`minix3/minix/drivers/usb/usbd/hcd/hcd.c`（一千三百一十四行的通用枚举与传输状态机）、`minix3/minix/drivers/usb/usbd/hcd/hcd_common.c`（七百六十一行的设备管理）、`minix3/minix/drivers/usb/usbd/hcd/hcd_ddekit.c`（四百八十四行的设备套件桥接）、`minix3/minix/drivers/usb/usbd/hcd/hcd_schedule.c`（三百零五行的请求包调度）、`minix3/minix/drivers/usb/usbd/hcd/musb/musb_core.c`（九百四十八行的控制器核心）与 `musb_am335x.c`（七百六十三行的芯片初始化）、`minix3/minix/include/minix/com.h` 第八百一十三行到第八百四十行（请求常量与消息字段）、`minix3/minix/include/minix/usb.h`（一百五十八行的请求包结构）
> **Rust 模块**：`os/drivers/usb/usbd/src/protocol.rs`（请求编号与解码）、`os/drivers/usb/usbd/src/enumerate.rs`（枚举顺序）、`os/libs/minix-usb/src/urb.rs`（请求包跟踪）
> **前置**：`notes/rewrite/fork-syscall-rewrite/16-stage-drivers/00-drivers-overview.md`（驱动子系统全景，本框架在其中的位置）、`notes/rewrite/fork-syscall-rewrite/16-stage-drivers/04-bdev-client.md`（块设备客户端库，客户端库思想对照）
> **说明**：通用串行总线框架是请求包赛道：驱动与主机守护之间不读写扇区，只交换编号的包。本篇讲包编号是什么、设备上电先说什么后说什么。控制器寄存器与数据包流量在服务层，本库只定编号与顺序。

> **本篇不讲什么**：
> - 海量存储与集线器驱动（见 `19-usb-storage-hub.md`，批量传输与端口管理另讲）
> - 块语义怎么消费通用串行总线（见 `19-usb-storage-hub.md`，海量存储挂靠块框架）
> - 控制器寄存器细节（本篇只讲唯一硬件后端存在，寄存器在服务层）
>
> 本篇只回答一个问题：**驱动与主机守护之间的包怎么编号，设备插上后按什么顺序说话**。

## 1. 概念：邮局的挂号信编号

### 1.0 章节引言

目标读者是读完存储批的读者。前置知识只需要一条：驱动是独立进程，靠消息与别的进程说话。本章解释通用串行总线为什么不直接读写设备：中间隔着主机守护，所有事都得写成编号的包。

### 1.1 主机守护是邮局，请求包是挂号信

想象邮局：寄信人（驱动）不直接找收信人（设备），只把挂号信（请求包）交到邮局（主机守护），邮局投递并把回执送回来。每封挂号信有个编号（请求类型），邮局按编号分拣。驱动寄出的有五种：报到、注销、交一封请求包、撤回一封请求包、报信息。邮局送回的有四种：通用回执、请求包办结、设备出现、设备消失。

编号是框架的全部契约：报到是基址加零，注销加一，交包加二，撤回加三，报信息加四，回执加五，办结加六，出现加七，消失加八。编号错一位，邮局就分错拣。

### 1.2 枚举是新生报到流程

设备插上像新生报到：先体检复位（端口复位），再交身份证复印件（取短设备描述符），再领学号（分配总线地址），再交完整档案（取全部配置描述符建成树），最后选宿舍入住（激活默认配置）。档案交齐才能宣布入学（向驱动宣布设备出现）。

五步顺序是枚举的全部怪癖：发现、描述、编址、读配置、配制、完成，错一步重来。失败回发现态重新复位，不带病往下走。

### 1.3 客户端库是代写书信的秘书

驱动不自己封包，有秘书（客户端库）代写：交包时填好端点与包标识，包办结时按标识找到等回执的那位并叫醒它（完成回调），设备出现消失时转告上下线回调。秘书手里有本花名册（待办包链表），标识为零等于查无此人。

### 1.4 调度是邮局的投递班次

邮局投递能力有限：同时在飞的请求包最多十六个。内外部请求包统一排队，办结一个放行一个。调度器线程与设备线程分工：设备线程管一台设备的生老病死，调度器线程管所有包的投递班次。

### 1.5 硬件后端是唯一的投递员

控制器后端只有一家（贝格尔骨板上的导师图形控制器），启动时按板型初始化九个回调（建设备、复位设备、建阶段、收阶段、发阶段等）。换板子换投递员，邮局分拣规则不变：硬件相关封在后端里，枚举顺序与包编号与板子无关。

### 1.6 本章小结

通用串行总线框架三件事：五加四的包编号，新生报到五步走，秘书代写加邮局投递。下一章进入 C 语言源码验证。

| `minix3/minix/include/minix/usb.h` | 一百五十八行 | 请求包结构、驱动回调表 |

### 2.2 请求编号（`com.h` 第八百一十三行到第八百四十行）

基址 `USB_BASE` 是十六进制一千一百（第八百一十三行）。驱动发往守护的五个请求占基址加零到加四：`USB_RQ_INIT` 报到、`USB_RQ_DEINIT` 注销、`USB_RQ_SEND_URB` 交包、`USB_RQ_CANCEL_URB` 撤回、`USB_RQ_SEND_INFO` 报信息（第八百一十六行到第八百二十行）。守护回执 `USB_REPLY` 占加五（第八百二十一行），守护发往驱动的三个通知占加六到加八：`USB_COMPLETE_URB` 办结、`USB_ANNOUCE_DEV` 出现、`USB_WITHDRAW_DEV` 消失（第八百二十五行到第八百二十七行）。消息字段映射在第八百二十九行到第八百四十行（授权标识、包标识、结果、设备标识等各归哪个消息字）。

### 2.3 客户端四个发送函数（`usb.c` 第二十行到第二百五十五 行）

`usb_send_urb` 交包在第二十行到第七十五行（填请求类型、授权、进程间发送接收、等回执、包标识入待办链表 `pending_urbs`）。`usb_cancle_urb` 撤回在第八十行到第一百一十六行（原名拼写如此）。`usb_init` 报到在第一百二十一行到第一百五十二行（先经设备目录服务查守护端点）。`usb_send_info` 报信息在第二百三十一行到第二百五十五 行。消息处理 `usb_handle_msg` 在第一百九十七行到第二百二十五行（办结调完成回调，出现消失调上下线回调），完成路径经 `_usb_urb_complete`（第一百五十七行到第一百九十二行）。

### 2.4 守护启动（`usbd.c` 第三十六行到第一百五十一行）

主函数按序做四件事：守护初始化、主机控制器初始化、设备管理初始化、启动（第三十六行到第六十九行）。启动建服务线程（第一百二十九行）、初始化调度器（第一百三十五行）、阻塞等退出即主循环（第一百三十九行）。服务线程只调设备套件服务初始化（第一百七十九行到第一百八十三行），内建无限接收循环。

### 2.5 枚举五步（`hcd.c` 第四百七十三行到第八百九十行）

总入口 `hcd_enumerate` 在第四百七十三行到第五百六十二行（复位、定最大包长、取设备描述符、回写包长、设地址、睡五毫秒、取描述符树、设配置）。取设备描述符 `hcd_get_device_descriptor` 用标准请求读描述符（第五百七十八行到第五百七十九行），设地址 `hcd_set_address` 用设地址请求（第六百三十一行到第六百三十二行），取描述符树 `hcd_get_descriptor_tree` 取短取全两遍，设配置 `hcd_set_configuration` 用设配置请求（第八百一十四行到第八百一十五 行）。设备线程每台设备一个（第二百五十行到第二百八十行）：先枚举，再连回调，再无限等包事件。

### 2.6 请求包结构（`usb.h` 第二十四行到第一百零四行）

驱动回调表 `struct usb_driver` 三成员（第二十四行到第二十八行）：完成、接设备、断设备。请求包结构 `struct usb_urb` 在第六十五 行到第九十六行（设备标识、类型、端点、方向、状态、错计数、长度、实长、包标识等），无效包标识 `USB_INVALID_URB_ID` 为零（第六十三行）。传输类型四种（第五十二行到第五十八行）：同步、中断、控制、批量。控制请求八字节（第九十八行到第一百零四行）。

## 3. Rust 设计决策

> 本章解释为什么这样设计。每个决策先给依据，再给替代方案与取舍。

### 3.1 编号做成枚举（依据：第 1.1 节、第 2.2 节）

驱动请求五值与守护消息四值各一枚举，数值写死（基址加偏移），解码函数双向验号，陌生号返回空。替代方案是裸常量加手工比对，不选的理由是：枚举让漏判分支编译不过，裸常量漏了也不响。

### 3.2 枚举做成阶段机（依据：第 1.2 节、第 2.5 节）

发现描述编址读配制配制完成六态，成功推进一步，失败回发现态，完成后宣布。替代方案是布尔三元组，不选的理由同存储篇：阶段机让非法转移不可能。

### 3.3 跟踪做成查表（依据：第 1.3 节、第 2.3 节）

待办包数组加按标识查找，零标识直接拒，端点号超十五判无效。替代方案是链表加回调散写，不选的理由是：数组查找贴合花名册心智，测试不用起消息循环。

### 3.4 设计决策汇总

| 决策 | 依据 | 替代方案 | 为何不选 |
|------|------|----------|----------|
| 编号枚举 | 第 1.1、2.2 节 | 裸常量比对 | 漏分支不响 |
| 枚举阶段机 | 第 1.2、2.5 节 | 布尔三元组 | 非法转移可能 |
| 跟踪查表 | 第 1.3、2.3 节 | 链表散写 | 测试要起循环 |

## 4. 错误处理

| 场景 | C 行为 | Rust 表达 | 说明 |
|------|--------|-----------|------|
| 陌生请求号 | 不分拣 | 解码返回空 | 编号错不受理 |
| 陌生守护号 | 不处理 | 解码返回空 | 编号错不受理 |
| 零包标识 | 查无此人 | 查找返回空 | 无效不查表 |
| 端点号超十五 | 非法端点 | 有效性返回假 | 十六端点是顶 |
| 完成后推进 | 无下一态 | 成功返回假 | 到头了 |
| 枚举中失败 | 重复位 | 回发现态 | 带病不往下 |

## 6. 过渡：框架搭完用存储

通用串行总线框架是请求包赛道的第一篇：编号定完，顺序定完，下一篇海量存储与集线器是第一次完整消费（批量传输跑在批量端点上，集线器管端口上下线）。读存储之前，建议重温本篇的枚举五步：集线器宣布设备出现之后，主机守护走的正是这五步。
