## 1. 概念：只接订单的厨房

### 1.0 章节引言

目标读者是已经理解微内核基本划分的读者：内核只做调度与消息传递，设备功能放在用户态的服务进程里。前置知识只需要两条：进程之间用消息通信，一次设备操作对应一次请求与一次回复。

本章先建立心智模型，再进入源码。模型回答三个问题：字符驱动的工作从哪里来（请求来源），工作如何被路由到正确的处理函数（请求分发），驱动的生命从何开始到何结束（上线宣告与退出条件）。

### 1.1 字符驱动是一间只接订单的厨房

想象一家餐厅的后厨。厨师不招待客人，不点菜，不结账。后厨只做一件事：从传菜口接到订单小票，做菜，把成品连同小票编号一起送回去。小票编号至关重要，因为多个订单可能同时在做，服务员靠编号认领自己的菜。

Minix3 的字符驱动就是这间后厨。虚拟文件系统服务是前台：它接待应用程序的打开、读写、关闭请求，把每个请求翻译成一张小票（消息），递给对应的字符驱动。字符驱动只管做，做完把结果连同小票编号送回。应用程序长什么样、文件描述符表怎么管，字符驱动一概不关心。

这个比喻直接对应三处真实机制：

1. **小票就是消息**。每条消息的类型字段说明要做什么操作（请求编号），外加一个请求标识（小票编号）。做完之后，回复消息原样带回请求标识，发送方靠它配对请求与回复。
2. **传菜口只有一个**。字符驱动一次只处理一条消息，处理完才接下一条。这就是贯穿本框架的单线程事件循环假设：任何时刻最多一个请求在执行，因此不需要锁。
3. **后厨有开业宣告**。驱动启动后先向数据存储服务宣告自己上线，然后清空已打开设备记录，从一张白纸开始服务。重启后的驱动不信任任何旧状态：没经过新一轮打开的设备，一律视为陌生设备。

### 1.2 七种请求：标准小票只有七张

虚拟文件系统服务与字符驱动之间只说七种话：打开、关闭、读、写、设备控制、取消、轮询。每种话有一个编号，是基址（数值 `0x400`，也就是十进制的一千零二十四）加上一个从零到六的小索引。判定一条消息是不是字符请求，只需要看一件事：把消息类型除了低七位之外的部分拿出来，是不是等于这个基址。这就是头文件里的判定宏，用一次掩码代替七次比较。

为什么编号要这样设计？因为同一个消息类型字段还要区分块请求、网络请求、时钟请求。每个家族占一个基址，家族内部用小索引区分。路由的第一步永远是看基址认家族，第二步才是看索引认具体操作。这种两层路由让新增一种请求变得便宜：在家族内部加一个索引，主循环的家族判断一行不用改。

消息里除了类型，还带着操作需要的全部材料。打开带着次设备号、访问方式、出资进程；读写带着次设备号、位置、授权、字节数、标志、请求标识；设备控制带着控制码；取消带着要取消的那个请求的标识；轮询带着关心的事件集合。回复则简单得多：普通回复带状态码加请求标识，轮询回复带状态码加次设备号，延后的就绪通知用单独的回复形状，好让轮询服务分清立即回答与稍后通知。

### 1.3 回调表：十个挂钩

框架本身不碰硬件。它定义十个挂钩，具体驱动实现其中几个，填进一张表，主循环照表调用：打开、关闭、读、写、设备控制、取消、轮询，外加中断、定时器、通用消息三个旁路挂钩。

十个挂钩里有七个对应七种请求，三个对应通知。每个挂钩都可以空着，框架给每种空挂钩规定了默认行为：空的打开与关闭视为成功，空的读写视为输入输出错误，空的设备控制视为不合适的控制操作，空的取消视为让原请求继续跑完，空的轮询视为坏文件描述符，空的通知挂钩视为忽略。这套默认行为不是随意定的：它让最简单的驱动（比如只读一个固定内容的设备）只实现读一个挂钩就能工作，其余全部走默认。

### 1.4 挂起与取消：先欠着，稍后再还

读、写、设备控制这三种请求可能需要等：终端等用户敲键，串口等硬件就绪。框架允许这三种请求的挂钩回答一个特殊标记，意思是请求我收下了，回复稍后送到。驱动稍后用专门的延后回复函数把答案送回去，函数内部检查状态码，拒绝用特殊标记再调自己（防止无限欠账）。

取消请求就是为这种欠账准备的：调用方等不及了，发取消请求请驱动放弃之前欠下的那一笔。驱动的取消挂钩决定是放弃（随后给原请求发取消确认）还是让原请求继续跑（回答不回复，让原请求自然完成）。如果驱动根本没有取消挂钩，框架直接回答不回复，等于默认让原请求继续。

这里有一个值得停留的细节：挂起回答只允许出现在四种请求里（读、写、设备控制、取消）。打开、关闭、轮询回答挂起是驱动的错误，框架在 C 语言里直接让进程停下，在 Rust 实现里把它翻译成无效参数回复。宁可报错，不可含糊，这是框架对待协议违反的一贯态度。

### 1.5 重启门：陌生设备一律先开门再干活

驱动可能重启：崩溃后被系统服务重新拉起，或者版本升级。重启后的驱动失去了所有内存状态，但调用方可能还拿着旧的打开句柄继续发读写请求。框架用一张已打开设备表挡住这种陈旧请求：宣告上线时清空表格，之后每个打开请求登记一个次设备号，非打开请求先查表，查不到就静默丢弃，不发送任何回复。

静默丢弃而不是报错，是深思熟虑的选择。陈旧请求的发送方（虚拟文件系统服务）会通过驱动上线事件自己恢复，它不需要也不想要一堆错误回复。框架在这里选择少说话，让恢复流程走专门的通道，而不是在请求通道里吵架。

还有一处类似的守卫：如果有人给字符驱动建了一个块设备节点，打开那个节点会发来块打开请求。字符驱动对块打开一律回答没有此设备，否则虚拟文件系统服务的对应线程会永远卡住。这是一种跨家族的礼貌：认出不是自己的信，立即退回并说明原因。

### 1.6 通知：不属于订单的敲门声

不是每条消息都是订单。硬件中断通知与时钟定时通知也会到达同一个接收口。规则是：凡是通知，一律交给对应的旁路挂钩，并且不发送回复。因为对方没下单，自然没有小票可回。

这个收到但不回复的分支是新人的第一个陷阱：直觉上每个接收都该有个发送与之配对，但通知机制的设计恰恰是单向的。Rust 实现里用独立的枚举分支表达它，类型上就不允许为它构造回复。想给通知发回复的代码写不出来，编译器直接拒绝，这比注释里写记得别回复可靠得多。

### 1.7 与其他系统的对照

Linux 把类似的职责拆成多组操作表：文件操作、轮询操作、内存映射操作，分别挂在不同的对象上。Minix3 的选择恰恰相反：一张大表按请求编号组织，不按对象组织。原因在于通信方式不同：Linux 是函数调用，调用点知道自己手里拿的是什么对象；Minix3 是消息传递，收到的只是一个编号，必须先路由再谈对象。理解了这个差异，就理解了为什么 Rust 设计保留整张表而不是拆成多个小行为定义：拆表省不掉路由，反而让某个请求没人处理的错误从查表时的显式拒绝，变成编译期难以发现的缺方法。

Redox 的方案（方案特征）更接近 Minix3：一组打开、读取、写入、关闭方法，路径形如方案名加冒号加路径。区别在于 Redox 用统一资源标识符风格的路径字符串做路由，而 Minix3 用数字编号。数字编号的好处是路由开销固定且可表驱动，代价是可读性差，这正是 Rust 侧用枚举把每个编号重新命名回人类语言的原因。

### 1.8 本章小结

字符驱动是被驱动的：虚拟文件系统服务发请求，它做事并回复。七种请求编号加请求标识拼成消息，回调表做路由，已打开设备表做重启门，通知走旁路且不回复，挂起的请求稍后用延后回复函数作答，退出发生在终止函数清掉运行标志的那一刻。下一章进入 C 语言源码，逐段验证这些机制的真实形状。

## 2. C 语言源码分析

### 2.1 文件清单与消息布局

框架的 C 语言源码只有一个文件，外加两个头文件：

| 文件 | 行数 | 内容 |
|------|------|------|
| `minix3/minix/lib/libchardriver/chardriver.c` | 六百行 | 主循环、逐消息路由、回复构造、七个适配器 |
| `minix3/minix/include/minix/chardriver.h` | 四十行 | 十个回调的函数指针表、框架函数声明 |
| `minix3/minix/include/minix/com.h`（第九百一十九行到第九百五十六行） | 约四十行 | 请求基址、七个请求编号、三个回复编号、判定宏、标志位 |

文件开头的注释（第一行到第四十四行）画出了完整的消息布局表：每种请求占用哪些字段，回复有哪三种形状。这是全框架最值得细读的注释，它是后面六百行代码的地图。

### 2.2 上线宣告与打开集合（`chardriver.c` 第五十二行到第一百二十四行）

运行标志是一个文件内静态整数，打开集合是一个最多存二百五十六个次设备号的数组加一个槽位计数。三个小函数管理这张表：清空（把计数归零）、查找（线性扫描）、登记（满了就让进程停下）。线性扫描在最多二百五十六个条目的控制路径上完全够用，这是典型的用简单换可靠。

上线宣告函数做三件事：请内核解除可能卡住的调用方（重启时有人正等着旧驱动回复），向数据存储服务发布驱动上线事件（键名是驱动名前加字符前缀），清空打开集合。发布失败与取标签失败都让进程停下：宣告不上线就服务，等于黑车上路，框架宁可停下。

### 2.3 延后回复与选择通知（`chardriver.c` 第一百二十九行到第一百七十二行）

两个延后回复函数分别服务挂起的任务请求与轮询请求。两者都先检查状态码：回答挂起标记或旧式暂停标记一律让进程停下，因为那意味着驱动在已经要回答的时候又说再等等。然后清零整个回复消息（防止旧栈内存泄漏到回复里），填类型、状态、标识，用异步发送发出去，发送失败只打印一行日志，不重试。发送失败不重试的理由是：对方可能已经不在乎这个答案了（比如已经取消），为一条可能没人等的回复去阻塞整个驱动不值得。

### 2.4 回复构造（`chardriver.c` 第一百七十七行到第二百七十四行）

发送辅助函数看本次接收是同步调用还是异步通知：同步调用用非阻塞发送，异步用专门的异步发送。回复主函数先处理三个特殊标记：挂起标记只允许出现在读、写、设备控制、取消四种请求上（其他请求用它就是驱动错误，直接停下）；旧式暂停标记一律停下（旧同步协议早在二零一三年退役）；重启标记直接吞掉不回复（调用方通过其他渠道知道重启）。

然后按请求种类填回复：打开关闭一类，读写控制一类，取消比较特殊（取消的回复是给原请求的，不是给取消请求本身的），轮询用自己的两种回复形状。默认分支是未知请求，直接停下。清零、填表、发送，三步走完，一次请求的生命周期结束。

### 2.5 七个适配器（`chardriver.c` 第二百七十九行到第四百三十三行）

每个适配器都是从消息里拆字段、调挂钩、返回结果的三段式：

- 打开适配器：挂钩空着直接成功；否则拆出次设备号、访问方式、出资端点去调挂钩；如果返回值带着克隆标志，把新次设备号也登记到打开集合（伪终端的主从复制就靠这个机制）。
- 关闭适配器：挂钩空着直接成功；否则拆出次设备号去调。
- 读写适配器：两个方向共用一个函数，用方向参数区分；挂钩空着返回输入输出错误；否则把次设备号、位置、端点、授权、长度、标志、标识七样材料全部递给挂钩。
- 设备控制适配器：挂钩空着返回不合适操作；否则递七样材料（控制码代替方向）。
- 取消适配器：挂钩空着返回不回复（让原请求继续）；否则递次设备号、端点、标识。
- 轮询适配器：挂钩空着返回坏文件；否则递次设备号、事件集合、端点。

### 2.6 路由与主循环（`chardriver.c` 第四百三十八行到第五百七十行）

块打开守卫先把误投的块打开请求挡回去（回答没有此设备）。然后是通知分支：硬件中断走中断挂钩，时钟走定时挂钩，其他走通用挂钩，全都不回复。然后是字符请求的重启门：取出次设备号（取不出就静默返回），没登记过的设备只有打开能进，其余静默丢弃。最后按类型调七个适配器之一，拿结果去调回复主函数；未知类型走通用挂钩且不回复。

终止函数只有两行有效代码：运行标志置假，取消阻塞中的接收。主循环的结构是：运行标志置真，当运行标志为真时循环，阻塞接收任意来源的消息，接收被中断且运行标志已清就退出，接收出其他错误就停下（框架认为接收失败不可恢复），否则路由这条消息。接收失败直接停下的哲学是故障即停：宁可整个驱动进程崩溃重启，也不让可疑状态污染设备。

### 2.7 次设备号提取（`chardriver.c` 第五百七十五行到第六百行）

`chardriver_get_minor` 按消息类型从对应的字段里取出次设备号：打开关闭从打开关闭字段取，取消从取消字段取，轮询从轮询字段取，读写控制从读写字段取，其他类型返回无效参数。开头两个断言保证指针非空。七个分支正好对应七种请求，一个不多一个不少，这是审阅时数分支的土办法：分支数对不上七，必有遗漏或多余。

| 非阻塞、克隆、控制终端标志 | 第 2.1 节 | 协议常量 | 已覆盖 |

### 2.9 与 C 六百行的差异说明

| 差异 | C 做法 | Rust 做法 | 分类 |
|------|--------|-----------|------|
| 分发表 | 按类型 switch 分发 | 枚举解码加匹配 | 设计决策：行为一致 |
| 空挂钩 | 运行时判空走默认 | 行为定义默认体 | 设计决策：行为一致 |
| 满表 | 进程停下 | 插入返回失败 | 设计决策：策略上移服务层 |
| 消息收发 | 库内直调传输原语 | 状态机不管传输 | 设计决策：传输在服务层 |
| 旧式暂停 | 进程停下 | 映射为无效参数回复 | 设计决策：不停进程，报错代替 |

## 3. Rust 设计决策

> 本章解释为什么这样设计。每个决策先给依据（第 1 章的概念或第 2 章的源码位置），再给替代方案与取舍。

### 3.1 请求编号做成枚举（依据：第 1.2 节、第 2.1 节）

C 语言用整数常量表示七种请求，类型系统看不出九百九十九和一千零二十四的区别：前者根本不存在，后者是打开。Rust 用枚举 `CdevRequest` 把每个合法索引变成一个变体，非法索引在解码时就被拒绝。调用方把空映射成无效参数或走通用挂钩，与 C 的行为一致。

替代方案是保留整数常量加一组范围检查函数。那样调用方每次都要记得检查，漏一次就是一次把非法请求送进分发的漏洞。枚举把记得检查变成不解码就拿不到值，非法状态在类型层面不可表达。

### 3.2 请求标识做成独立类型（依据：第 1.1 节）

C 语言的标识是裸的无符号整数，在回复里原样带回。Rust 把它收成 `RequestId` 包装，不解释内容，只负责携带与回显。测试里用标识配对请求与回复，锁定原样带回这个语义。

### 3.3 打开集合做成定长数组加计数（依据：第 1.5 节、第 2.2 节）

上限二百五十六与 C 语言一致。插入幂等（重复登记同一设备不占新槽），清空即复位计数。C 语言满表时停下，Rust 返回失败，由服务层决定策略：测试替身直接断言，生产服务可以打日志或停下。替代方案是动态数组，不选的理由是：上限是协议常量，动态只会引入分配失败的新错误，毫无收益。

### 3.4 驱动行为做成整体行为定义（依据：第 1.3 节、第 1.7 节、第 2.5 节）

这是本篇最核心的设计决策。C 的回调表是十个可空函数指针，Rust 把它变成 `CharDriver` 行为定义，十个方法各对应一个回调，全部带默认体。默认体完整保留空挂钩规则，只是把七处分散的空检查收成一处写明。

为什么不拆成多个小行为定义？第 1.7 节已经给了理由：消息路由只认编号，一个请求进来必须有唯一的归属。拆分后，一个设备可能实现了数据组却忘了轮询组，编译器不会抱怨，运行时轮询请求才突然报坏文件。整体行为定义加默认体的方案里，支持什么一目了然：看实现里重写了哪些方法。

### 3.5 分类结果做成枚举（依据：第 1.5 节、第 1.6 节、第 2.6 节）

路由函数的五向分支变成 `Route` 枚举：通知、块误投、陈旧、合法请求、通用。通知与通用分支在类型上就不携带回复，想给通知发回复的代码写不出来。陈旧分支由调用方静默丢弃，不构造回复。

分类函数把通知来源与次设备号做成参数而不是硬编码，测试可以传入任意端点验证来源门禁。生产代码传入真实的端点常量。

### 3.6 单线程假设写进文档而不是类型（依据：第 1.1 节）

用户态字符驱动是单线程事件循环：一次处理一条消息，不存在并发。本框架的类型（行为定义方法拿可变借用）天然适配这个模型：同一时刻只有一个请求持有设备的可变借用。但框架没有用线程标记在类型层面锁死单线程，因为那会堵死未来的演进。取舍是：文档明确声明单线程假设，类型保持中立。

### 3.7 空设备作为协议测试对端（依据：第 2.5 节空挂钩）

`SilentDevice` 只用默认体，它存在的理由很实际：分类、重启门、回复决策这些框架逻辑，需要一个设备实现没问题、纯测框架的对端。没有它，框架测试就必须搭一个完整终端，问题定位会混在一起。这是测试替身思想的正常应用，不是多余抽象。门禁要求行为定义至少有两个行为不同的实现，空设备加回声设备满足。

### 3.8 设计决策汇总

| 决策 | 依据 | 替代方案 | 为何不选 |
|------|------|----------|----------|
| 请求编号用枚举 | 第 1.2、2.1 节 | 整数常量加检查函数 | 漏检查即漏洞 |
| 请求标识独立类型 | 第 1.1 节 | 裸整数到处传 | 配对语义只应实现一次 |
| 打开集合定长数组 | 第 1.5、2.2 节 | 动态数组 | 引入分配失败，毫无收益 |
| 整体行为定义 | 第 1.3、1.7、2.5 节 | 拆小行为定义 | 路由只认编号，拆分掩盖缺实现 |
| 分类结果用枚举 | 第 1.5、1.6、2.6 节 | 整数结果码加注释 | 误发回复的错误类型层面可防 |

## 4. 错误处理

| 场景 | C 返回 | Rust 表达 | 说明 |
|------|--------|-----------|------|
| 无读写挂钩 | 输入输出错误 | `NO_TRANSFER_HOOK` | 设备不能搬字节 |
| 无控制挂钩 | 不合适操作 | `NO_IOCTL_HOOK` | 同控制语义 |
| 无轮询挂钩 | 坏文件 | `NO_SELECT_HOOK` | 不能轮询的设备 |
| 无取消挂钩 | 不回复 | `NO_CANCEL_HOOK` | 让原请求继续跑完 |
| 块打开误投 | 没有此设备 | `BLOCK_OPEN_MISMATCH` | 跨家族的礼貌退回 |
| 无可用次设备号 | 无效参数 | `BAD_MINOR` | 取不出设备的消息 |
| 挂起非法请求 | 进程停下 | `reply_decision` 报无效参数 | 打开关闭轮询不许挂起 |
| 旧式暂停标记 | 进程停下 | `reply_decision` 报无效参数 | 旧协议已退役 |
| 重启标记 | 吞掉不回复 | `ReplyDecision::SwallowedRestart` | 调用方另有渠道知道重启 |
| 延后回复用哨兵 | 进程停下 | `ReplyPlan` 构造器返回空 | 构造时拒绝，永不断言 |

## 6. 过渡：从框架到设备

本篇搭好了字符驱动的骨架：消息从哪里来（虚拟文件系统服务），到哪里去（七个适配器之一、旁路或静默丢弃），设备处于什么状态（运行标志加打开集合），什么时候下班（终止函数清掉运行标志的那一刻）。

但骨架还不会干活：内存盘的七个设备号各自是什么语义，终端的行规则与 termios 如何工作，伪终端的主从对如何复制，日志驱动的诊断捕获如何流动，这些每个设备内部的翻译还没讲。第五篇 `05-memory-driver.md` 先讲最简单的内存驱动：它同时是字符与块的双面设备，是理解双面驱动的最好入口；第六篇 `06-tty-driver.md` 讲最复杂的终端驱动。

阅读建议：先读第五篇的设备表（七个次设备一目了然），它把本篇的打开登记与克隆机制连成完整闭环；再读第六篇的读写路径，它是挂起与取消机制最重的用户。
