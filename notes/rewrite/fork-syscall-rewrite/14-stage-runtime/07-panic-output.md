# 07 诊断输出：绕过文件系统的喊话通道与恐慌梯子

> **目标读者**：已经读过第 05 篇的读者，理解系统调用协议。前置知识只需要一样：知道程序出错时要留下诊断信息，而出问题的时候恰恰是平时好用的工具最不可靠的时候。

## 1 概念：为什么喊话不能走寻常路

程序平时说话走文件系统：打开标准错误，写入字节，关闭。这条路要经过三个环节：文件描述符表是好的，文件系统服务是活的，磁盘或者终端是通的。程序恐慌的时候，坏掉的很可能正是这三个环节里的一个：堆损坏了，服务死锁了，驱动没响应了。对着一条可能已断的路喊救命，等于没喊。

Minix 给系统服务和驱动准备了另一条路：诊断通道。字符先攒在一个固定大小的 staging 缓冲区里，攒满或者遇到结尾标记就通过一条直达内核的控制消息递出去，全程不碰文件系统。内核收到后写进自己的环形日志，操作员用专门的工具查看。这条路的依赖只有内核还活着，而内核是全系统最后才倒下的东西，所以它是遗言最可靠的去处。

这里有三个贯穿全文的心智模型。第一个是攒后发的缓冲模型：逐个字符攒，整块发出，减少陷入次数，结尾标记和满缓冲是唯二的发送时机。第二个是层层兜底的恐慌梯子：先报身份，再报消息，再报调用栈，然后跑钩子，然后试正常退出，再试信号自杀，再试非法跳转自杀，最后原地打转。每一步都是上一步失败后的退路，梯子一路向下，情况一路变糟。第三个是分阶段落地的演进模型：先原地打转保平安，再把格式化做出来，再把通道接上内核，最后接上退出。每一阶段都可测试，每一阶段都不破坏上一阶段的行为。

### 1.1 缓冲模型

记住一句话：零字节是句号，满缓冲是换页。调用者逐个字符喂进来，缓冲区别攒着，遇到零字节就把攒下的发出去（零字节本身不存），缓冲满了先发再存新字符。空缓冲遇到零字节是什么都不做：没有内容，发什么呢。这条规则简单到不可能误解，实现它的函数也简单到不可能写错。

### 1.2 恐慌梯子模型

记住另一句话：梯子只往下走，从不往上爬。身份报不出来不影响报消息，消息报不出来不影响跑钩子，退出失败就自杀，自杀失败就打转。每一级都不假设上一级成功，每一级的失败都由下一级接住。设计恐慌路径的人必须假设一切都会坏，包括恐慌路径自身。

### 1.3 演进模型

记住第三句话：先保平安，再求好用。第一阶段原地打转：行为和以前完全一样，格式化逻辑先在测试里长大。第二阶段格式化进栈缓冲：恐慌信息落在内存里，输出端还是打转。第三阶段接内核通道：信息真正递出去。第四阶段接退出：善后完整。每一步都保留退路，通道不通就退回打转，绝不在没把握的时候换路。

## 2 C 语言源码分析：诊断路径上的每个文件在做什么

本章按从字符到数字再到恐慌的顺序讲解全部 C 语言文件。所有行号都针对当前代码库中的 Minix3 源码。

### 2.1 字符累积与发送时机

打开 `minix3/minix/lib/libsys/kputc.c` 文件，开头的注释先讲清这条路的定位：服务偶尔要打印消息，用系统库里的简化打印函数，打印走内核调用，不走文件系统，只能服务和驱动用，内核和日志驱动各有自己的版本。第 12 行的 staging 缓冲区大小是诊断缓冲常量，值在 `minix3/minix/include/minix/com.h` 文件的第 416 行：一屏文字，80 列乘 25 行，2000 字节。内核那边的接收缓冲同样大，发送长度超过会被内核拒绝，所以发送方永远发不超过这个数的块。

第 17 行到第 32 行的函数体是缓冲模型的原文：第 22 行的发送条件是结尾零且缓冲非空，或者缓冲已满；先发送再清零计数；第 26 行起非零字符才存入。注意判断在存储之前：满缓冲时先把旧的发出去，再存新字符，新字符永远有位置。空缓冲遇到零字节时两个条件都不成立，函数直接返回，什么都不做。

### 2.2 诊断控制消息的四种操作

打开 `minix3/minix/lib/libsys/sys_diagctl.c` 文件的第 5 行到第 27 行，一共 23 行。第 9 行把操作码写进消息。第 11 行到第 25 行按操作码填不同的字段：打印诊断带缓冲地址和长度，打印调用栈带目标端点，注册和注销不带额外参数， unknown 操作码直接恐慌。第 27 行走内核调用发出去。操作码的四个值在通信头文件的第 412 行到第 415 行：1 打印诊断，2 打印调用栈，3 注册诊断信号，4 注销。头文件 `minix3/minix/include/minix/syslib.h` 的第 164 行到第 171 行给四个操作各包了一个便捷宏，调用者不用记数字。

### 2.3 恐慌函数的梯子

打开 `minix3/minix/lib/libsys/panic.c` 文件的第 21 行到第 67 行，是梯子的原文。第 34 行到第 37 行先报身份：能查到自己名字就打印名字加端点，查不到就打印查找失败说明，身份总有一款。第 39 行到第 46 行报消息：有格式字符串就格式化打印，没有就打印无消息。第 48 行到第 49 行打印调用栈标记并输出调用栈。第 51 行跑钩子，钩子默认是空函数，弱别名机制允许用户覆盖它而不改库。第 54 行试正常退出，退出码 1。第 57 行试信号自杀。第 62 行到第 63 行把函数指针设成非法地址再调用，用一次注定失败的跳转自杀，注释写明动机：发给进程管理器的消息可能因死锁失败。第 66 行原地打转，注释写明这是最后一招。

### 2.4 断言与数字和标准错误

打开 `minix3/minix/lib/libsys/assert.c` 文件的第 12 行到第 22 行，断言失败先打印文件名、行号、失败的表达式和函数名，再调恐慌函数，注释标注永不返回。打开 `minix3/minix/lib/libc/gen/itoa.c` 文件的第 9 行到第 35 行，整数转文本用静态 8 字节缓冲：负数先写减号再取反，零单独写零，否则从一万开始逐位试除，前导零跳过。读者注意除数的起点是一万：超过五位的数字在这里走不通，缓冲也装不下，这是 C 版本的真实局限，Rust 版本在第三章修正它并明确标注。打开 `minix3/minix/lib/libc/gen/stderr.c` 文件的第 6 行到第 12 行，标准错误输出先量长度再一次写完，保证一行完整发出。

## 3 Rust 设计决策：为什么是自有缓冲加栈上格式化加输出端抽象

本章解释 `os/libs/minix-rt/src/diag.rs` 文件里的每一个设计选择。先说 C 语言做法带来的问题，再说 Rust 做法如何解决问题，最后说否决掉的替代方案。

### 3.1 用自有缓冲代替静态全局

C 语言的 staging 缓冲和计数器是静态全局，所有测试共享，互相污染。Rust 实现把缓冲和计数装进自有类型，方法全走可变借用，每个测试新建自己的缓冲。发送时机逐字复刻 C 版本：先判断再存储，零字节不存，空缓冲遇零无动作。额外提供一个写完刷尾的便利方法，因为 C 版本在程序转场时会落下一段没刷的尾巴，调用者需要显式收尾，方法名字就把这层意思说清楚。

替代方案是保留全局加锁，理由是和 C 语言结构一致。这个方案被否决了，理由是用户态单线程用不上锁，而测试隔离用自有值免费得到，全局加锁是花钱买不需要的东西。

### 3.2 用调用者内存代替静态数字缓冲

C 语言的数字缓冲是 8 字节静态数组，嵌套调用互相覆盖，五位以上输出错字。Rust 实现把结果写进调用者给的内存，返回写了几个字节，装不下就截断高位并如实报告全长，调用者能发现截断。符号、零、多位数的处理逐项测试，全 32 位范围用边界值覆盖：最小值、最大值、五位分界上下。这是对 C 局限的修正性改进，代码注释按项目规范标注了原始位置和修正内容，文档这里也如实记录，不藏着。

### 3.3 用输出端抽象分离格式化与发送

恐慌时格式化必须永远安全（只用栈内存），发送可能需要内核（可能正坏着）。Rust 实现用输出端 trait 隔开两者：旋转输出端原地打转（当前生产行为，观察不到变化），捕获输出端记进固定数组供测试断言。trait 有两个行为不同的实现，并被恐慌梯子用作约束，抽象有打底，不是装饰。恐慌处理函数先格式化位置加消息进 256 字节栈缓冲，再交给输出端，最后打转。行为和以前一样，但格式化层已经可测试，通道接通时只换输出端实现，不动格式化。

Redox 的做法和这个思路相通：Redox 的恐慌处理同样先保证最小可用（输出寄存器状态），再谈丰富输出。区别在于 Redox 的输出端是串口和显示帧缓冲，而这里是内核诊断通道。两种系统都认同一句话：恐慌路径的每一行代码都必须能在最坏情况下跑通，本模块的无分配、无系统调用、全栈内存就是这句话的落实。

## 4 错误处理：诊断层的失败及其错误号

| Rust 情形 | 处理 | 对应的 Minix 语义 | 选择理由 |
|-----------|------|-------------------|----------|
| 未知控制码 | 调用者决定（构造时拒绝） | C 版本直接恐慌 | 库版本把是否致命还给调用者 |
| 数字缓冲装不下 | 截断并报告全长 | C 版本静态缓冲溢出（未定义） | 如实报告代替静默错字 |
| 捕获输出端满 | 丢弃并计数 | 无对应（测试设施） | 测试能断言溢出本身 |
| 恐慌梯子走到底 | 原地打转 | C 版本同样打转 | 最后一招跨语言一致 |

诊断层不发明错误号：控制码合法性用有无表示，数字截断用长度表示，溢出用计数表示。需要错误号的地方（比如参数错误）沿用共享类型库的现有值。

## 6 过渡：从终局骨架到服务分组

诊断输出解决的是遗言通道的问题：字符如何攒，数字如何写，恐慌梯子如何走，演进如何分阶段。从下一篇开始，视角从终局回到日常：程序活着的时候办的每一件事，都是向某个服务进程发一次请求。进程管理管生死，文件系统管读写，往后每组一篇，每篇都是第 05 篇协议的一次套用。

请继续阅读第 08 篇 `08-pm-syscalls.md`，它从创建进程讲起，逐个讲解生命、信号、执行三族调用的封装。诊断通道本身会在第 07 篇的后续阶段里接上内核调用，届时走的也是第 05 篇的协议。
