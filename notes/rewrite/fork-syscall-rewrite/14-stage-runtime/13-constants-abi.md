## 1 概念：为什么常量需要审计与归属

常量是系统里最安静的 bug 来源。数字写错一位，编译器不拦，测试不一定覆盖，错的是行为。Minix 的常量散在十几个头文件里：错误号一张表，信号号一张表，调用号按服务分段，端点号按启动顺序排。对账要做两件事：第一，逐项核对 Rust 侧的值和 C 定义一致；第二，给每个常量定一个权威的家，家里存一份，别处只引用，不各存一份。

权威归属的理由很实际：同一个数字存两份，改了一处忘另一处就是定义矛盾。前面十二篇的实践已经立下规矩：端点号住在使用它的调用组模块里（进程管理住进程组，文件系统住文件组），错误号住共享类型库，信号号住共享类型库。本篇把规矩写成表：谁住哪，为什么住哪，改谁先改谁后改。

### 1.1 对账模型

记住一句话：机器数一遍，人工逐项认。脚本数 C 头文件里有几个定义，人工把 Rust 侧的值逐个对到行号。数对了不算完，值也要对：名字对上值错了同样是 bug。对账表里名字、值、行号三列齐全，缺一列就是没对完。

### 1.2 归属模型

记住另一句话：一处权威，到处引用。权威的家是数字第一次落地的模块：错误号的家是共享类型库，调用号的家是各调用组，端点号的家是各调用组。复述只许引用，不许重定义。改数字先改权威家，再看引用处要不要跟，顺序不能反。

## 2 C 语言源码分析：常量表的出处与规模

本章列出各常量表的原始位置与规模。所有行号都针对当前代码库中的 Minix3 源码。

### 2.1 错误号全表

错误号在 `minix3/sys/sys/errno.h` 文件里，共 115 个独立编号。1 到 86 是通用错误（第 42 行起），200 到 217 是 Minix 特有错误（第 196 行起），符号约定是用户态正数、内核态负数（同一文件第 185 行起的符号开关）。96 号有两个名字（协议错误与最大号标记），值相同，这是 C 语言有意为之的别名，不是重复定义。

### 2.2 信号号全表

信号号在 `minix3/sys/sys/signal.h` 文件的第 52 行到第 84 行：1 到 32 共 32 个信号，33 到 63 是内核专用不对用户态开放。上界 64 在第 45 行。给自己发信号的范围检查认 0 到 63，0 号是存在性探针，不投递。

### 2.3 调用号分段

调用号在 `minix3/minix/include/minix/callnr.h` 文件里：进程管理基址 0（第 9 行），用 1 到 47；文件系统基址十六进制 100（第 68 行），用加 0 到加 63，其中套接字族占后段（排除项，归网络阶段）。管理信息、重生服务、数据存储的调用号在通信头文件里按各自基址排：管理基址加 0 是查询，请求基址十六进制 700 加 8 是查找，加 9 是查信息。

### 2.4 端点号排序

端点号在 `minix3/minix/include/minix/com.h` 文件的第 59 行起，按启动顺序排：0 进程管理，1 文件系统，2 重生服务，3 内存驱动，4 调度，5 终端，6 数据存储，7 管理信息，8 内存服务，9 管道文件系统，10 根文件系统。用户程序最常用的四个（0、1、2、8）权威家在各调用组模块，7 号在杂项模块，6 号在服务发现模块。

### 2.5 大族现状

终端控制常量在 `minix3/sys/sys/termios.h` 文件里，共 304 行 116 个定义。文件控制、状态、输入输出控制、等待、资源、时间、系统名各族散在各自系统头文件里。这些大族的逐项移植按需进行：调用组需要哪个常量，验证哪个，搬运哪个，测试锁定哪个。本轮搬运了文件组必需的三个（创建标志、复制命令、段数上界），其余见第 5 章规则。

## 3 Rust 设计决策：为什么错误号补全信号新建其余登记

本章解释本轮常量工作的三个决定。先说问题，再说做法，最后说否决掉的替代方案。

### 3.1 用脚本 diff 定位错误号缺口

人工数 115 个编号不现实，脚本提两边名字加值一比，22 个缺口自动现形：87 到 96 十个通用尾巴，202 与 205 到 214 十二个 Minix 特有。逐行核对原始行号后补进共享类型库，注释带行号。补完再跑一遍脚本：115 对 115，零值差。以后错误号表有变，同样的脚本再跑一遍，缺口无处藏身。

替代方案是人工逐项抄，理由是简单直接。这个方案被否决了，理由是 115 项人工抄一定错，机器比对才可靠。对账的方法和对账的结果一样重要，方法写进复查报告，可复现。

### 3.2 用新模块收容信号全表

信号 32 个加范围规则，体量够一个模块，归属共享类型库。范围检查函数和调用组的自发检查共用一套：调用组删掉自己的副本，改调共享函数，单点定义，全库一致。测试锁定六个代表值加边界四则：0 放行，31 放行，负一拒绝，64 拒绝。

替代方案是信号常量散在调用组里，理由是用哪放哪。这个方案被否决了，理由是信号是跨组概念（发信号在进程组，终端控制将来也要用），跨组概念住共享库，这是第 12 篇定下的规矩的自然延伸。

### 3.3 用登记表管理大族

终端、文件控制、状态等大族本轮不逐项搬运，理由有三：调用组当前需要的三个已经搬运验证；大族逐项搬运是体力活，出错率高；没有使用者的常量是死代码，违反最小接口原则。登记表记录每族的位置、规模、状态、归属规则：需要时验证搬运，搬运时测试锁定。本轮的三个（创建标志、复制命令、段数上界）就是按这条规则搬运的先例。

## 4 错误处理：本篇无新增失败

本篇是审计篇，不新增运行时行为。错误号补全的值经脚本验证零值差，信号范围与调用组行为一致（调用组改调共享函数后重测通过）。大族登记无代码变更，无需错误分析。

## 5 测试与对账：脚本 diff 加模块测试

错误号对账用脚本 diff（115 对 115，零值差），命令与输出见复查报告的门禁证据。信号模块 2 个测试：六个代表值与上界，范围四则。调用组改调共享函数后全量重测通过（`cargo test -p minix-sys` 110 个通过）。大族按需搬运规则：调用组需要哪个常量，验证哪个（原始行号），搬运哪个（注释带行号），测试锁定哪个（值断言）。终端等大族当前无使用者，保持登记不搬运。

测试统计截至 2026 年 09 月 05 日：`cargo test -p minix-types` 共 167 个测试通过，其中错误号模块含新增缺口断言，信号模块 2 个。`cargo test -p minix-sys` 共 110 个测试通过（调用组改调后无变化）。
