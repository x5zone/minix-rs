# 01 内核交付：内核如何把新进程需要知道的一切交给用户程序

> **目标读者**：学习过 C 语言和基本操作系统概念，知道进程是什么，但是没有读过 Minix 内核源码的读者。前置知识只需要两样：知道指针是指向内存的地址，知道栈是函数调用时存放局部变量和返回地址的那块内存。
> **本文在进程运行时生命周期中的位置**：诞生时刻。内核刚刚完成可执行文件的加载，还没有跳转到程序的第一条指令。本文回答新进程在睁开眼睛之前，内核替它准备了哪两样东西：内核信息页面的地址，以及初始栈顶的位置。
> **前置依赖**：`00-runtime-overview.md` 对运行时生命周期的整体介绍，以及 `../01-stage-kernel/09-vm-boot-protocol.md` 对内核启动协议的讲解。
> **本篇不覆盖的内容**：程序入口汇编桩如何把控制权转交给 C 函数（那是第 02 篇的主题），运行时初始化构造器如何查询并安装通信向量表（那是第 03 篇的主题），系统调用如何陷入内核（那是第 04 篇和第 05 篇的主题）。

## 1 概念：新进程睁开眼睛之前需要知道的两件事

想象你搬进一套新公寓。房东不会只给你一把钥匙就消失，他至少还要告诉你两件事：第一，这把钥匙是真的，能打开这扇门；第二，你的家具应该从哪个电梯口搬进来，大件物品走哪条通道。操作系统内核在启动一个新进程的时候，扮演的正是房东的角色。

新进程在诞生的那一刻一无所知。它的地址空间是刚刚建立的，它的栈是空的，它甚至不知道自己要和哪些内核服务打交道。内核在跳转到程序入口之前，必须把两样东西放在新进程伸手就能够到的地方：

第一样东西叫做内核信息页面。它的 C 语言类型名字是 `struct minix_kerninfo`，定义在 `minix3/minix/include/minix/type.h` 文件的第 214 行到第 244 行。这个结构体的第一个字段是一个魔数，也就是一个固定的、精心挑选的 32 位整数 `0xfc3b84bf`。魔数的作用和公寓钥匙上的防伪标记一样：程序拿到页面指针之后，第一件事就是检查这个数字对不对。如果数字不对，说明页面指针是坏的，或者内核和用户程序对内存布局的理解不一致，这时候程序绝对不能继续相信页面里的其他字段。魔数之后是一个标志字，告诉程序页面里哪几个指针是有效的；再往后是两个对用户程序真正有用的指针，一个指向通信向量表，一个指向用户信息结构。页面里其余的指针指向机器描述、内核日志缓冲、负载统计这些只供系统服务使用的结构，普通用户程序不应该触碰它们。

第二样东西是初始栈顶的位置。新进程的栈是从高地址向低地址生长的，内核必须告诉程序栈顶在哪里，程序才能在栈上布置参数和环境变量。这个地址存放在用户信息结构里的 `kui_user_sp` 字段中。为了照顾那些在用户信息结构出现之前就已经编译好的老程序，内核还保留了一条后备路径：老的内核信息结构里偏移 2440 字节处有一个同样含义的字段，新程序优先读新位置，读不到再回头读老位置。

这里有一个贯穿本文的核心设计问题：内核以后可能会给用户信息结构追加新字段，老程序在新内核上运行的时候，怎么判断某个字段到底存不存在？Minix 的答案非常朴素：用户信息结构的第一个字段记录了整个结构的总长度，程序用总长度减去目标字段的偏移和大小，大于等于零就说明字段存在。这个规则在 C 语言里写成一个宏 `KUSERINFO_HAS_FIELD`，本篇后面会逐行讲解它，Rust 实现里则把它收敛成一个单独的、可测试的函数。

把这两样东西放在一起，内核交付的完整画面就是这样的：内核加载完可执行文件，根据可执行文件的参数和环境变量算出初始栈镜像需要多少字节，从内核选定的栈顶地址向下留出这段空间，把参数字符串、环境字符串、进程字符串描述结构依次填进去，然后带着内核信息页面的指针和栈顶地址跳转到程序入口。从程序的视角看，它醒来的时候，寄存器或者约定的内存位置里放着页面指针，栈指针寄存器指向一块已经布置好的栈，它要做的就是验证魔数、读出栈顶、解析栈上的内容。

## 2 C 语言源码分析：每一行关键代码在做什么

本章逐个讲解内核交付涉及的全部 C 语言定义和函数。所有行号都针对当前代码库中的 Minix3 源码，读者可以用文本编辑器打开对应文件逐行对照。

### 2.1 用户信息结构与版本探测宏

打开 `minix3/minix/include/minix/type.h` 文件的第 205 行到第 212 行，可以看到用户信息结构的定义（第 202 行到第 204 行是它上面的注释）：

```c
struct kuserinfo {
    size_t kui_size;        /* 整个结构的总长度，用于接口版本探测 */
    vir_bytes kui_user_sp;  /* 新进程的初始栈指针 */
};
```

这个结构体只有两个字段，但是注释里写了一句非常重要的话：这个结构体以后只允许追加新字段，永远不允许调整现有字段的位置。这句话是整个版本兼容策略的基石。因为偏移永远不变，老程序用老偏移去读新内核发布的更大的结构，读到的依然是正确的字段；新程序用 `kui_size` 去探测老内核发布的更小的结构，发现长度不够就知道新字段不存在，从而走后备路径。

紧跟在结构体下面的第 211 行到第 212 行是版本探测宏：

```c
#define KUSERINFO_HAS_FIELD(kui,f) \
    (kui->kui_size >= offsetof(struct kuserinfo, f) + sizeof(kui->f))
```

这个宏读起来可能有点绕，我们把它拆开。`offsetof` 是 C 语言标准库里的一个运算符，它回答这样一个问题：某个字段从结构体开头数起偏移了多少字节。对于 `kui_user_sp` 字段，偏移量就是第一个字段 `kui_size` 的宽度。`sizeof(kui->f)` 是该字段本身的宽度。两者相加就是容纳该字段所需要的最小结构长度。如果内核报告的实际长度大于等于这个最小长度，字段就存在；否则字段不存在。这个判断完全不依赖版本号数字，只依赖长度，新增字段的时候不需要分配版本号，不会烧掉版本号空间，这就是它比版本号比较更耐用的原因。

### 2.2 内核信息页面的完整字段

同一个文件的第 214 行到第 244 行是内核信息页面的定义。为了阅读方便，我们把它的字段分成三组：

第一组是身份和状态字段。第 230 行的 `kerninfo_magic` 是前面提到的魔数，合法值是第 229 行定义的常量 `0xfc3b84bf`。第 231 行的 `minix_feature_flags` 记录内核具备哪些特性，第 232 行的 `ki_flags` 记录页面里哪些指针是有效的，后面三个 `flags_unused` 是预留的填充字段，目前没有使用。

第二组是用户空间接口指针，也就是用户程序可以合法使用的两个指针。第 240 行的 `minix_ipcvecs` 指向通信向量表，第 241 行的 `kuserinfo` 指向上一节讲的用户信息结构。注释里明确标注这两个指针属于用户空间接口，意味着它们的含义和布局是稳定的，内核升级不能悄悄改变它们。

第三组是服务专用指针，包括第 236 行的 `kinfo`、第 237 行的机器描述、第 238 行的内核消息缓冲、第 239 行的负载信息、第 242 行的手臂架构时钟、第 243 行的时钟信息。这些指针指向的结构体本身可能随时变化，只有系统服务才能使用它们。普通用户程序应该把它们当作不存在。

第 246 行和第 247 行定义了两个标志位：最低位表示通信向量表指针有效，次低位表示用户信息指针有效。程序在使用指针之前必须先检查对应的标志位，再检查指针本身是不是空指针，两个条件同时满足才能使用。这个双重检查在后面的运行时初始化代码里还会出现一次。

### 2.3 内核信息页面的访问函数

打开 `minix3/minix/lib/libc/sys/kernel_utils.c` 文件，全部 62 行都很重要，我们逐段讲解。

文件开头的注释（第 1 行到第 10 行）声明了这组函数的设计边界：它们既可以被普通用户程序调用，也可以被系统服务调用，它们的访问行为被视为用户空间接口的一部分。注释还立下一条规矩：不要往这个文件里添加与用户信息字段检索无关的函数，尤其是时钟信息这类内容。换句话说，这个文件是内核交付信息的只读窗口，不是杂物箱。

第 25 行到第 32 行的 `get_minix_kerninfo` 函数返回全局变量 `_minix_kerninfo` 里保存的页面指针。函数体的第一行是一个断言，要求指针不能为空。这个断言的意思是：如果运行时初始化阶段没有成功安装页面指针，那么任何试图读取页面内容的行为都是编程错误，应该立刻停下来，而不是带着空指针继续运行。Rust 实现里把这个断言翻译成一个显式的错误变体，调用者必须处理它，效果相同但是不需要终止整个进程。

第 39 行到第 62 行的 `minix_get_user_sp` 函数是初始栈顶的选择逻辑。它的执行顺序值得逐行品味：先调用 `get_minix_kerninfo` 拿到页面指针，然后检查标志字里是否设置了用户信息有效位，同时用版本探测宏检查用户信息结构是否大到足以容纳栈指针字段，两个条件都满足才返回新位置的 `kui_user_sp`。否则函数回退到老位置的 `kinfo->user_sp`。注意回退路径没有任何版本检查，因为老位置的偏移是历史遗留的固定值，老程序和老内核都认这个位置，不需要探测。

### 2.4 初始栈镜像的计算与填充

打开 `minix3/minix/lib/libc/sys/stack_utils.c` 文件。这个文件的作者在文件开头的注释里画了一张栈布局图（第 28 行到第 60 行），我们把它翻译成从低地址到高地址的顺序来讲解。栈的底部是进程字符串描述结构，往上是参数指针数组和环境指针数组，再往上是填充对齐用的空隙，最顶部是所有的参数字符串和环境字符串本身。字符串放在顶部、指针放在底部的理由是：字符串的长度各不相同，先把字符串一个一个紧挨着放好，再回头填写指向它们的指针，这样指针的值只需要做一次加法就能算出来。

第 76 行到第 114 行的 `minix_stack_params` 函数负责计算整个栈镜像需要多少字节。它的输入是可执行文件路径、参数指针数组、环境指针数组，输出是总字节数、是否溢出、参数个数、环境个数。函数体的逻辑分成三步：先把总数设为固定最小值，这个最小值包括参数个数本身、两个空指针终止符、辅助向量数组、可执行文件名缓冲、进程字符串描述结构；然后遍历参数数组和环境数组，每个字符串贡献一个指针槽位加上字符串本身的长度（含结尾的零字节），每次加法之后都检查总数是否反而变小了，变小就说明整数回绕了，标记溢出；最后把总数向上 rounding 到机器字宽的整数倍。溢出检查是这个函数最容易被忽略的细节：如果参数和环境变量的总长度接近地址空间上限，加法回绕会得到一个很小的总数，后续代码会据此分配一块过小的栈，导致内存越界。C 代码用比较运算捕捉回绕，Rust 实现里用带溢出报告的加法，意图完全相同。

第 119 行到第 172 行的 `minix_stack_fill` 函数负责把栈镜像真正填好。它的输入包括前面算好的总数和一块调用者准备好的缓冲区。函数先用 `minix_get_user_sp` 减去总数得到新地址空间里的栈指针值，然后从缓冲区的开头依次写入参数个数、指向各个字符串的指针（指针的值是栈指针加上字符串在缓冲区内的偏移）、空指针终止符、环境指针、空指针终止符，接着做字对齐填充，最后在当前位置构造进程字符串描述结构，把参数指针位置、参数个数、环境指针位置、环境个数填进去。读者注意指针值的计算方式：缓冲区在当前地址空间里的位置和它在新进程地址空间里的位置是不一样的，所以代码里用 `*vsp + (fp - frame)` 把缓冲区内偏移换算成新地址空间里的虚拟地址。这个换算只做一次加法，不需要查页表，因为栈镜像是连续的一块内存。

### 2.5 进程字符串描述结构与历史遗留字段

打开 `minix3/sys/sys/exec.h` 文件的第 104 行到第 116 行，可以看到进程字符串描述结构的定义：参数指针、参数个数、环境指针、环境个数，一共四个字段。进程状态查看工具和程序自身都用这个结构来定位字符串，而不需要重新解析整个栈。

同一个目录下的 `minix3/minix/include/minix/param.h` 文件第 35 行有一个名字很像的字段 `user_sp`，它属于内核启动参数结构，是内核在引导阶段记录自己希望用户栈放在哪里的位置。这个字段和用户信息结构里的 `kui_user_sp` 语义相同，但是存放的位置不同：前者是内核内部的启动记录，后者是发布给用户程序的正式接口。新程序应该读后者，前者只作为理解内核意图的参考。

## 3 Rust 设计决策：为什么这样建模

本章解释 `os/libs/minix-rt/src/handoff.rs` 文件里的每一个设计选择。阅读方法是：先说 C 语言做法带来的问题，再说 Rust 做法如何解决问题，最后说还有哪些替代方案以及为什么没有采用它们。

### 3.1 用构造即校验的类型代替裸的魔数比较

C 语言的做法是在每次使用页面之前写一遍 `if` 判断，判断散落在各个调用点，漏写一处就会埋下隐患。Rust 实现引入了一个新类型 `ValidatedKernInfo`，它的构造函数的唯一工作就是比较魔数：魔数对了就交出包装好的值，魔数错了就返回携带实际值的错误。拿到这个值的后续代码不再需要重复检查，因为类型系统保证了凡是能拿到这个值的地方，检查一定已经通过。这种手法在类型系统文献里叫做把非法状态变得不可表达，意思是把运行时的检查提前到构造的那一刻，此后用类型来记住检查的结果。

替代方案是保留 C 风格，在每个函数开头重复检查魔数。这个方案被否决了，理由是检查逻辑一旦需要修改（比如以后魔数变成两个字段联合校验），所有调用点都要跟着改，而新类型只需要改构造函数一处。

### 3.2 把版本探测宏收敛成一个函数

C 语言的版本探测是一个宏，它在每个使用点展开成一次长度比较。宏的问题是它没有类型，也没有独立的测试入口：你没法单独为宏写一个单元测试，只能通过调用它的函数间接覆盖。Rust 实现把宏体翻译成 `user_info_has_field` 函数，参数是结构总长度、字段偏移、字段大小，返回值是字段是否存在。偏移和大小用两个公开常量表示，分别对应宏里的 `offsetof` 部分和 `sizeof` 部分。这样做的好处是探测规则有了一个唯一的、可测试的家，任何字段的探测都走同一条路，行为不可能在不同调用点之间悄悄分叉。

### 3.3 把栈顶选择做成纯函数

C 语言的 `minix_get_user_sp` 直接读写全局变量和指针，单元测试没法在不启动内核的情况下驱动它。Rust 实现把选择逻辑抽成 `select_initial_stack_pointer` 纯函数：输入是可选的已校验页面、可选的用户信息、后备的老栈顶值，输出是选中的栈顶地址。真正的指针解引用被推迟到运行时初始化模块里唯一的一处，纯函数只负责做决策。测试可以用构造好的结构体覆盖全部三种情况：新位置可用、新位置不可用所以回退、页面指针缺失所以报错。这种分离在操作系统文献里叫做把机制和策略分开：解引用指针是机制，选择用哪个值是策略，策略应该是纯的、可测试的。

Redox 的做法和这个思路是一致的。Redox 的启动信息也来自内核发布的结构体，区别在于 Redox 把参数个数和指针直接放在初始栈上，而 Minix 传递的是一个描述结构的指针。两种做法在信息论上是等价的，都是把不定长的数据用指针加长度来描述。Rust 实现没有照搬 Redox 解析栈的代码，而是针对 Minix 的描述结构建模，这正是语义重写和逐行翻译的区别：保留外部行为，内部表达服从目标系统的类型习惯。

### 3.4 用显式溢出报告代替回绕比较

C 语言的栈大小计算用加法之后的比较来发现回绕，这种写法依赖读者知道无符号整数回绕的语义，第一次读到的人很容易错过。Rust 实现用带溢出报告的加法，每次加法都返回结果和是否溢出两个信息，最后汇总成一个布尔字段。调用者看到溢出标志为真就拒绝构造栈镜像，不会拿到一个回绕后的小数字去分配内存。两种写法的数学含义完全相同，但是 Rust 版本把检查意图写在了类型里，而不是藏在比较运算符里。

### 3.5 用范围检查的构造器包装进程字符串描述结构

C 语言的进程字符串描述结构用有符号整数存放个数，理论上可以出现负数。直接把负数 cast 成 Rust 的无符号长度类型会得到一个巨大的正数，后续代码会据此分配巨量内存。Rust 实现的 `ProcessStrings::from_raw` 构造器在转换之前先检查两个个数是否非负，负数映射到参数错误。这种检查在 C 代码里是不存在的，因为 C 调用者默认内核不会给出负数；Rust 版本把这份信任显式化，宁可多一次比较，也不要一次隐式的回绕。

## 4 错误处理：每个错误对应哪一个 Minix 错误号

项目规则要求错误类型必须映射到 Minix3 的错误号，不允许自创错误码。本模块有两个错误类型，它们的映射关系如下：

| Rust 错误 | 含义 | 对应的 Minix 错误号 | 选择理由 |
|-----------|------|---------------------|----------|
| `HandoffError::BadMagic` | 页面魔数不匹配 | `ENOEXEC`（值 8） | 页面来自可执行文件加载路径，魔数错误说明镜像或者发布步骤损坏，最接近的可执行文件格式错误 |
| `HandoffError::NullPage` | 页面指针缺失 | `ENOEXEC`（值 8） | 与上一行同理：没有页面就没有合法的进程镜像，属于同一类故障 |
| `ProcessStrings` 个数为负 | 参数向量非法 | `EINVAL`（值 22） | 调用者传入的参数向量格式错误，C 语言库对这类故障统一使用参数错误 |

负数个数的检查对应 C 语言里隐式的信任假设，错误号选择遵循 C 语言库对 malformed 参数向量的一贯做法。魔数错误的检查对应 C 语言里把全局指针清零的做法，Rust 版本把它变成显式错误，调用者可以用问号运算符向上传播，也可以在入口处把它变成进程退出码。

## 6 过渡：从内核交付到程序入口

内核交付解决的是新进程的知识问题：页面指针在哪里，栈顶在哪里，栈镜像如何布置，版本如何探测。下一个问题是控制流问题：程序的第一条指令执行之后，控制权如何一步一步走到 `main` 函数，参数和环境变量如何变成 `main` 的参数，启动函数列表和关闭函数列表在什么时候运行，动态加载器的分支为什么在静态链接的程序里永远不会走到。

这些问题属于进程运行时生命周期的下一个阶段：程序启动。请继续阅读第 02 篇 `02-crt0-start.md`，它从 7 行汇编桩讲起，逐段讲解 C 语言入口函数的完整流程，并在 Rust 侧给出显式的启动阶段枚举和函数列表运行器。
