# 03 运行时初始化：内核信息查询与通信向量表安装

> **目标读者**：已经读过第 01 篇和第 02 篇的读者，理解内核信息页面、初始栈、程序入口的概念。前置知识只需要一样：知道函数指针是可以存放在结构体里的回调地址，调用结构体里的函数指针就相当于调用它指向的函数。
> **本文在进程运行时生命周期中的位置**：初始化阶段。程序入口已经完成描述结构检查和环境变量发布，接下来要在调用主函数之前，把和内核打交道的两样全局状态准备好：内核信息页面的指针，以及进程间通信向量表。本文回答查询以什么顺序发生，校验失败时全局状态是什么样子，错误号和线程本地存储在 64 位系统上应该如何安排。

> **本篇不覆盖的内容**：通信原语的陷阱指令实现（那是第 04 篇的主题），系统调用消息协议的封装（那是第 05 篇的主题），内存分配器的实现（那是第 06 篇的主题），诊断输出与恐慌处理（那是第 07 篇的主题）。

## 1 概念：为什么需要一次全局的初始化

程序入口把环境变量和程序短名准备好之后，程序看似已经可以运行了。但是它还缺两样东西：第一，它手里还没有内核信息页面的地址，不知道通信向量表和用户信息结构在哪里；第二，它手里的通信向量表还是链接时填好的默认值，内核发布的新版本还没有安装。这两样东西有一个共同特点：它们是全局的，整个进程只有一份，而且必须在主函数的第一行运行之前就绪。任何一个库函数都可能在主函数运行期间读取它们，所以它们的初始化不能推迟到第一次使用的时候，而必须在启动序列里显式地完成一次。

C 语言的解决方案是一个构造器函数 `__minix_init`，链接器保证它在程序入口完成之前运行。构造器做三件事：向内核查询信息页面指针，校验页面里的魔数，条件满足时把内核发布的通信向量表复制到全局变量里。三件事的顺序是固定的：查询失败就清空指针，魔数不对也清空指针，只有查询成功而且魔数正确，才会走到安装向量表的那一步。这种顺序不是随意的，它保证了程序永远不会拿着一个来历不明的页面去安装向量表。

这里有两个贯穿全文的设计问题。第一个是全局状态的管理问题：C 语言用两个可变全局变量保存页面指针和向量表，任何代码都可以读写它们，测试没法隔离它们。Rust 实现把同样的信息装进一个可拥有的状态值，真正的二进制程序在启动时持有唯一的全局实例，单元测试在每个测试里新建局部的实例，测试之间互不干扰。第二个是错误号模型的问题：C 语言用一个全局整数和取地址函数来传递错误原因，Rust 用返回值里的结果类型来传递错误原因，全局可变状态从此消失。这两个问题在下一章的源码分析里有具体的出处，在第三章的设计决策里有完整的论证。

### 1.1 查询、校验、安装的三步顺序

初始化的三步顺序可以用一句话记住：先问内核要地址，再看地址里的内容对不对，最后才把内容里附带的函数表拿来用。每一步失败都回到同一个安全状态：页面指针为空，向量表保持原来的默认值。程序的主函数可以通过检查页面指针是否为空来判断初始化是否成功，而不需要知道具体是哪一步失败的。具体的失败原因通过返回值告诉调用者，调用者可以把它记录下来或者转换成退出码。

### 1.2 通信向量表的双重条件

安装向量表需要同时满足两个条件：标志字里声明向量表有效，向量表指针本身非空。只满足其中一个是不够的：标志位设置了但是指针是空，说明内核的声明和实际内容不一致；指针非空但是标志位没设置，说明内核不希望用户程序使用这个指针。C 语言用逻辑与把两个条件连在一起，Rust 实现保留了完全相同的双重检查。这种冗余不是多余的，它是内核和用户程序之间的契约：双方必须同时点头，交易才能成立。

### 1.3 错误号与线程本地存储的背景

C 语言的错误号是一个全局整数，库函数失败时返回负一并把原因写进这个全局变量，调用者读全局变量就知道发生了什么。这种设计在单线程程序里工作得很好，在多线程程序里需要每个线程一份独立的副本，否则两个线程会互相覆盖对方的错误原因。Minix 继承的 NetBSD 代码在 32 位 Intel 上没有用户态的线程本地存储，所以退化成整个进程共享一个。64 位 Intel 处理器提供了专门的段寄存器来支持线程本地存储，Rust 运行时可以提供真正的按线程隔离。错误号本身也可以顺便演进：既然 Rust 函数可以直接返回结果类型，就不再需要全局变量来旁路传递错误原因，全局状态从此少了一个。

## 2 C 语言源码分析：构造器与周边的每个文件在做什么

本章逐个讲解运行时初始化涉及的全部 C 语言定义和函数。

### 2.1 构造器函数的三步流程

打开 `minix3/minix/lib/libc/sys/init.c` 文件，全部 32 行都很重要。

第 6 行定义全局页面指针 `_minix_kerninfo`，初始值是空。第 8 行声明构造器函数 `__minix_init`，链接器属性保证它在程序入口完成之前自动运行，调用者不需要显式调用它。第 10 行到第 18 行定义全局向量表 `_minix_ipcvecs`，初始值是七个直接陷阱函数：发送并接收、发送、通知、异步发送、非阻塞发送、接收、内核调用。这些默认值指向的函数直接执行陷阱指令，不经过任何间接层，所以即使内核从不发布新的向量表，程序依然可以用这套默认值和内核对话。

第 20 行到第 32 行是构造器的函数体，三步顺序非常清晰。第一步调用 `ipc_minix_kerninfo` 查询页面指针，返回值非零说明查询失败。第二步比较页面里的魔数和期望的魔数，不相等说明页面内容不可信。两个条件用逻辑或连在一起，任何一个成立都把全局指针清零并结束函数。第三步检查标志字里的向量表有效位和向量表指针本身，两个条件同时成立才把内核发布的整张表复制到全局变量里。注意复制的是整张表而不是单个函数指针：七个函数指针要么一起换成新版本，要么一起保持旧版本，不会出现新旧混用的中间状态。

### 2.2 通信向量表的类型定义

打开 `minix3/minix/include/minix/ipc.h` 文件的第 2786 行到第 2795 行，可以看到向量表结构体的定义（第 2798 行是引用它的全局变量声明）：七个函数指针，分别对应发送、接收、发送并接收、非阻塞发送、通知、内核调用、异步发送。每个函数指针的签名和它包装的陷阱函数完全一致，调用者通过向量表发起的调用和直接调用陷阱函数的效果完全相同，区别只是多了一层间接。间接的好处是内核可以在不重新编译用户程序的情况下更换陷阱实现：只要发布一张新表，用户程序下次初始化的时候就会自动用上。

同一个文件的第 2800 行到第 2834 行是一组内联包装函数，每个包装函数都只有一行：从全局向量表里取出对应的函数指针并调用它。举例来说，`_ipc_send` 取出 `send` 字段并调用，`_ipc_sendrec` 取出 `sendrec` 字段并调用。这种写法把全局变量的读取收敛到一处，调用者不需要知道全局变量的名字，只需要调用包装函数。如果以后向量表的存放位置发生变化，只需要修改这组包装函数，调用者不需要跟着改。

### 2.3 错误号全局变量与取地址函数

打开 `minix3/lib/libc/gen/_errno.c` 文件的第 44 行到第 55 行，可以看到取地址函数的实现：非多线程构建直接返回全局整数的地址，多线程构建先检查线程系统是否启动，未启动返回全局地址，已启动返回线程私有的地址。这个函数的调用者是 C 语言的 `errno` 宏，宏把它返回的地址解引用成左值，库函数往这个左值里写错误号，用户程序从这个左值里读错误号。整个机制依赖一个全局整数和一个返回其地址的函数，读写没有任何锁保护，在单线程程序里是安全的，在多线程程序里依赖线程私有地址的切换。

### 2.4 程序短名的读写函数

打开 `minix3/lib/libc/gen/getprogname.c` 文件的第 50 行到第 57 行，读函数只有一行：返回全局指针 `__progname`。打开 `minix3/lib/libc/gen/setprogname.c` 文件的第 53 行到第 65 行，写函数的主体被条件编译关闭了，注释里写着在 NetBSD 系统里程序名由启动文件设置，不允许覆盖。这个设计的意思是程序短名是只读的：启动文件在入口处设置一次，之后任何代码都只能读不能改。Rust 实现保留了这个只读语义，短名推导函数是纯函数，调用者拿到结果之后自行保存，没有全局的可写变量。

### 2.5 环境变量哨兵的定义

`minix3/minix/lib/libc/sys/environ.c` 文件只有一行有效代码，把全局环境指针初始化成哨兵值 `0x53535353`。注释里解释了选择这个值的理由：只比较低两个字节，因为不同机器的指针宽度和字节序不一样，所以四个字节都填同样的图案。这个哨兵和第 02 篇讲的启动文件配合使用：启动文件用描述结构里的真实环境指针覆盖掉哨兵值，覆盖之前的值是哨兵，覆盖之后的值是真实地址，库函数可以通过比较来判断环境是否已经发布。

## 3 Rust 设计决策：为什么初始化是一个纯函数加一个可拥有的状态

本章解释 `os/libs/minix-rt/src/init.rs` 文件里的每一个设计选择。

### 3.1 用显式的查询 trait 代替直接的陷阱调用

C 语言的构造器直接调用陷阱函数查询页面指针，测试没法在不启动内核的情况下驱动它。Rust 实现引入 `KerninfoSource` trait，把查询抽象成一个方法：真实实现执行陷阱，测试实现返回预设的结构体。初始化函数只依赖这个 trait，不依赖具体的陷阱指令，所以测试可以传入预设成功、预设查询失败、预设魔数错误的三种测试替身，覆盖构造器的全部三个分支。这种手法在操作系统文献里叫做把硬件边界抽象成 trait：硬件相关的代码只出现在 trait 的实现里，决策逻辑只依赖 trait 的接口，测试替身和真实实现可以互换。

有人可能会问：只有一个真实实现和一个测试替身的 trait 是不是过度抽象？项目规则要求 trait 至少有两个行为不同的实现，这里的真实陷阱和预设数据恰好满足这条规则：一个访问硬件，一个不访问硬件，行为完全不同。而且 trait 被用作初始化函数的泛型约束，调用者传入不同的实现会得到不同的行为，抽象不是装饰品，而是测试能力的来源。

替代方案是把查询写成普通函数，用条件编译在测试构建里替换它的实现。这个方案被否决了，理由是条件编译的替换是隐式的，读者必须同时看两份代码才能理解行为，而 trait 的替换是显式的，调用点一眼就能看出传入的是真实来源还是测试替身。

### 3.2 用可拥有的状态值代替两个全局变量

C 语言用两个全局变量保存页面指针和向量表，任何代码都可以读写它们，测试之间会互相污染。Rust 实现把同样的信息装进 `RuntimeState` 结构体：一个可选的已校验页面，加上一个向量表选择枚举。初始化函数是纯函数，输入是查询来源和调用前生效的后备向量表选择，输出是新的状态值和结果，函数体内不读写任何全局变量。真正的二进制程序在启动时把返回的状态值存进唯一的全局实例，单元测试在每个测试里使用局部的状态值，测试之间互不干扰。这种分离在软件工程里叫做把状态的所有权显式化：谁拥有状态，谁负责传递它，而不是让所有人共享一块谁都能改的内存。

向量表选择枚举只有三个值：无、内核发布、测试替身。它没有复制 C 语言的七个函数指针，因为函数指针的复制是机制，记录选择结果是语义。真正的消息发送是通信机制模块的工作，那里会根据选择结果决定调用哪张表。这里只记录决策，不复制指针，避免了在 Rust 代码里搬运裸函数指针。

### 3.3 保留三步顺序和双重条件，一个都不省略

初始化函数的函数体严格复刻 C 构造器的顺序：先查询，查询失败清空状态并返回查询失败错误；再校验魔数，魔数不对清空状态并返回魔数错误；最后检查标志位和指针的双重条件，满足则选择内核发布的表，不满足则保留调用者传入的后备选择。顺序和条件一个都没有省略，省略任何一步都会改变外部可观察的行为。测试对每一步都有覆盖：查询失败、魔数错误、标志位缺失、指针为空、四种情况各有一个测试，断言状态和返回值完全符合预期。

Redox 的运行时初始化也是显式函数调用，而不是链接器构造器。Redox 的入口函数在调用主函数之前显式调用初始化函数，初始化函数把通信句柄作为参数传递，而不是从全局变量里拉取。本模块采用了相同的形状：初始化是显式调用的函数，输入和输出都写在签名里，没有隐藏的构造器魔法。区别在于 Redox 传递的是文件描述符和命名空间句柄，而这里传递的是页面查询来源和后备向量表选择，差异来自两个系统不同的内核接口，而不是设计思想的不同。

### 3.4 用结果类型代替全局错误号

C 语言的错误号是全局整数，库函数用返回值负一表示失败，用全局变量表示原因。Rust 实现用 `Result` 类型同时携带成功值和失败原因，不需要全局变量。边界上需要和 C 语言互相调用的地方，`errno_to_negative` 函数把类型化错误转换成 C 语言的负数约定，`negative_to_errno` 函数把 C 语言的负数返回转换回类型化错误，零和正数统一视为成功。转换逻辑只有这两处，转换规则有独立的测试覆盖，读者不需要在每个调用点重新推导正负号的方向。

### 3.5 用枚举说出线程本地存储的两种形态

C 语言在 32 位 Intel 上没有用户态的线程本地存储，错误号是整个进程共享的。64 位 Intel 处理器提供了专门的段寄存器，运行时可以提供真正的按线程隔离。Rust 实现用 `ThreadLocalModel` 枚举说出这两种形态：共享单元和线程指针。枚举目前只用于文档和决策记录，真正的段寄存器设置是后续阶段的工作，但是把选择写成枚举有两个好处：第一，读者一眼就能看出 32 位和 64 位的区别在哪里；第二，以后的代码在匹配这个枚举的时候，编译器会强制处理两种情况，不会漏掉任何一种。

## 4 错误处理：初始化阶段的两种失败及其错误号

| Rust 错误 | 含义 | 对应的 Minix 错误号 | 选择理由 |
|-----------|------|---------------------|----------|
| `InitError::KerninfoQueryFailed` | 内核查询返回非零状态 | `EIO`（值 5） | 通信层不可达属于输入输出错误，C 语言库对这类故障统一使用输入输出错误 |
| `InitError::BadMagic` | 页面魔数不匹配 | `ENOEXEC`（值 8） | 与第 01 篇的魔数错误同类：页面来自可执行文件加载路径，内容不可信属于可执行文件格式错误 |

查询失败在 C 语言里把全局指针清零，魔数错误同样把全局指针清零，Rust 版本把两种清零翻译成空状态加显式错误，调用者可以用问号运算符向上传播，也可以在入口处把错误转换成进程退出码。错误号选择遵循 C 语言库对同类故障的一贯做法，没有引入新的错误码。

|----------|-----------|-------------------|
| `test_successful_init_installs_kernel_table` | 查询成功且标志和指针齐备时安装内核发布的表 | `init.c` 安装分支 |

| `test_wrong_magic_discards_page` | 魔数错误时状态清空并返回魔数错误 | `init.c` 魔数比较分支 |
| `test_direct_trap_source_reports_unreachable_in_hosted_tests` | 真实陷阱来源在宿主测试环境里显式失败 | 硬件边界抽象 |

## 6 过渡：从运行时初始化到系统调用机制

运行时初始化解决的是全局状态的发布问题：页面指针如何到达用户程序，向量表如何从默认值切换到内核发布的版本，校验失败时状态是什么样子，错误号和线程本地存储应该如何安排。下一个问题是通信机制问题：进程间通信的发送、接收、发送并接收、通知、非阻塞发送、异步发送这六种原语分别对应哪条陷阱指令，陷阱指令的参数放在哪些寄存器里，通信状态码如何编码，异步发送的批量表如何组织。

这些问题属于进程运行时生命周期的下一个阶段：系统调用机制。请继续阅读第 04 篇 `04-ipc-primitives.md`，它从陷阱指令的寄存器约定讲起，逐个讲解六种原语的语义和状态编码，并在 Rust 侧给出通信 trait 和状态类型。第 05 篇 `05-syscall-mechanism.md` 则在它的基础上讲解消息协议的封装：调用号如何放进消息类型字段，失败时消息类型如何变成状态码，负数如何变成错误号。
