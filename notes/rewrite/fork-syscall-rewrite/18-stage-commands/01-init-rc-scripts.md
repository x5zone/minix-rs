## 1. 概念：内核工作结束之后，第一个用户进程如何把系统带到可用状态

### 1.0 本章说明

本章回答一个问题：内核引导完成、第一个用户进程开始运行之后，系统是怎样一步一步变成"可以登录、可以使用"的样子的。

> **本章不讲什么**：
>
> - 服务管理命令 `service` 与 `minix-service` 的具体用法（见 `02-service-scheduler.md`）
> - 终端登录程序 `getty` 与 `login` 的内部流程（见 `03-login-passwd.md`）
> - 每个启动脚本各自的业务细节（挂载、网络、日志等，分散在 `04` 与 `14` 到 `19` 各篇）
> - 进程创建原语与可执行文件加载机制（见 `14-stage-runtime`）
>
> 本章只讲"第一个进程的职责"与"启动脚本体系的设计思想"这两个地基概念。

### 1.1 为什么必须有一个"第一个用户进程"

内核引导的终点，是中央处理器（Central Processing Unit，简称 CPU）已经切到受保护的运行环境、内存管理与中断都已就绪。但这个时候系统还处在一个很尴尬的状态：所有代码都运行在内核态，没有文件系统可用视图，没有终端，没有网络，没有任何用户程序。内核自己不能"变成"一个多用户系统，因为内核的职责是提供机制（创建进程、收发消息、读写设备），而不是决定"开机之后先做什么、后做什么"这种策略。

于是需要一个交接点：内核创建出第一个用户态进程，然后退居幕后。这个进程在传统上拿到的进程标识符（Process Identifier，简称进程编号）是 1，名字就叫 `init`，即启动初始化进程。它是整个用户世界的"祖先"：之后每一个用户进程，要么是它直接创建的，要么是它的后代创建的。

可以用一个类比理解：大楼主体施工完成（内核引导），之后需要一家物业公司进场（启动初始化进程），按一份入住手册（启动脚本）逐项开通水电、电梯、门禁，最后打开大门迎客（多用户登录）。施工队不会自己决定物业流程，物业也不会去浇筑混凝土，职责边界非常清晰。

第一个进程的特殊性体现在三个方面，缺一不可：

1. **它是所有孤儿进程的收养者**。任何进程退出时，如果它还有活着的子进程，这些子进程就成了孤儿。内核把孤儿进程的父进程改记为启动初始化进程，由它负责回收这些进程退出时留下的退出状态（在 Unix 传统中称为"收割"，即反复等待子进程结束并取走其退出码）。如果没有这个收养机制，孤儿进程退出后会变成无人回收的"僵尸"进程，越积越多。
2. **它是运行级别的持有者**。系统当前处于"单用户维护模式"还是"多用户服务模式"，由启动初始化进程的状态机记录和切换。别的程序可以请求切换（例如关机命令），但真正执行切换的是它。
3. **它是终端会话的派生者**。每个可登录的终端上运行的登录准备程序，都是启动初始化进程直接创建的子进程。这样设计保证了：无论终端上的程序如何崩溃，启动初始化进程都能发现子进程死亡，并重新派生一个新的，保持终端永远有人值守。

### 1.2 运行级别：单用户维护模式与多用户服务模式

"运行级别"这个词听起来抽象，其实就是回答"系统现在允许多少人在上面做事"：

- **单用户维护模式**：只开一个管理员控制台，不启动网络服务，不接受远程登录。这种模式是给系统管理员修系统用的——比如根文件系统损坏时，先以最小形态启动，修好再进入完整状态。
- **多用户服务模式**：正常对外服务的状态：文件系统全部挂载，网络配置好，各个终端上都有登录提示，定时任务与守护进程各就各位。

Minix 的启动初始化进程用一个状态机在这些形态之间流转。状态机的输入是信号（Signal，即操作系统投递给进程的异步通知）与子进程的生死事件，输出是"执行一段启动脚本"或"派生一批终端会话"。把"开机"理解成一次从单用户形态出发、经过执行启动脚本、最终稳定在多用户形态的状态迁移，后面读源码会轻松很多。

### 1.3 启动脚本为什么分三层：配置变量、函数库、脚本目录

开机要做的事有几十件（检查磁盘、挂载文件系统、配置网络、启动日志服务、打开终端……），如果把顺序硬编码在一个程序里，每增删一件事项都要改程序、重新编译，这显然难以维护。NetBSD 系统一脉相承的做法（Minix 直接继承）是把启动过程拆成三层：

1. **配置变量层**（`/etc/rc.conf` 与 `/etc/defaults/rc.conf`）：只写"做什么、不做什么"。文件内容几乎全是"变量名等于 YES 或 NO"的赋值行，例如是否允许远程登录、是否启动某个守护进程。管理员定制开机行为时只改这一层，不碰任何逻辑。
2. **函数库层**（`/etc/rc.subr`，1300 多行）：提供一套启动脚本共用的 shell 函数，例如"按配置决定是否执行""执行并记录结果""等待依赖"。这是启动体系的"标准库"，保证 32 个脚本写法统一。
3. **脚本目录层**（`/etc/rc.d/`，32 个脚本）：每个脚本只负责一件事（挂载关键文件系统、配置网络、启动日志……），脚本头部用注释声明"我提供什么能力、我依赖什么能力、我在什么场合跳过"。

三层之间由两个程序串起来：主脚本 `/etc/rc` 负责总体流程（读配置、调排序、逐个执行、记日志），排序工具 `rcorder` 负责读每个脚本头部的依赖声明，算出一个满足所有依赖的执行顺序。这种"声明依赖、自动排序"的思想，和 Linux 世界的 systemd 用 `After` 与 `Requires` 声明服务顺序是同一个设计源头，只是实现载体不同（一组 shell 脚本加一个排序工具，对比一个常驻的服务管理器）。

### 1.4 启动与关机是一枚硬币的两面

关机不是"直接断电"，而是启动的逆过程：通知所有进程终止、把内存中的文件数据写回磁盘、卸载文件系统，最后才停机或重启。`shutdown` 命令负责"通知与等待"的体面部分，`reboot` 命令负责最后的"请求内核重启"动作，而启动初始化进程负责在收到关机信号后把系统状态机带回单用户形态。可以说，读懂了启动链，就读懂了一半的关机链。

## 2. C 源码分析

### 2.1 启动初始化进程：一个七状态的状态机

`minix3/sbin/init/init.c`（1902 行）是本篇最核心的源码。它的主函数在第 230 行附近开始，主体流程可以概括为：确认自身身份（我是第一个进程吗）、创建新会话、探测关键设备、解析启动参数、注册信号处理、清理标准输入输出、探测安全级别，然后进入状态机循环。状态机的状态用单字符表示（第 133 到 139 行），一共七个：

| 字符 | 状态 | 含义 |
|------|------|------|
| `d` | 死亡（Death） | 进程即将退出，系统停机前的最后形态 |
| `s` | 单用户（Single User） | 单用户维护模式，在控制台开一个管理员 shell |
| `r` | 执行启动脚本（Runcom） | 执行 `/etc/rc`，从单用户形态走向多用户形态 |
| `t` | 重读终端表（Read Ttys） | 重新读取终端配置文件，更新会话清单 |
| `m` | 多用户（Multi User） | 多用户服务模式，值守所有终端会话 |
| `T` | 清理终端（Clean Ttys） | 终端配置变化后，关闭多余会话、补齐新增会话 |
| `c` | 紧急（Catatonia） | 异常僵持形态，等待外部干预 |

状态之间用 `transition` 函数（第 624 行附近）切换，切换请求可以来自信号处理函数（例如收到挂起信号要求重读配置），也可以来自子进程回收逻辑（例如执行启动脚本的子进程结束了）。特别值得注意的是初始转移：第 195 行把"请求转移"变量预置为"执行启动脚本"，也就是说，只要没有特殊情况，开机就走"单用户准备 → 执行启动脚本 → 多用户"的标准路径；只有在启动参数要求或控制台设备缺失时，才停在单用户维护模式。

### 2.2 执行启动脚本：`runcom` 状态做了什么

`runcom` 状态的处理函数在第 975 行附近。它创建一个子进程，在子进程里执行 `/etc/rc autoboot`（第 899 行附近把 `autoboot` 参数拼进启动参数表），父进程等待子进程结束。等待期间回收到的任何子进程结束事件都由统一的回收函数处理（第 828 与 933 行附近两次调用 `collect_child`，分别对应正常等待与异常打断两种路径）。

这里有一个细节：第 866 行在某种异常路径下把启动模式改成快速启动（FASTBOOT）。快速启动的含义是"跳过耗时的文件系统检查"，适用于"刚刚正常关机、磁盘大概率干净"的情形。这个决策点说明状态机不仅管"走哪条路"，还管"用多快的速度走"。

### 2.3 终端会话管理：`read_ttys`、`multi_user`、`clean_ttys`

多用户形态的核心工作是管理终端会话，围绕 `/etc/ttys` 这个终端配置文件展开（文件格式与解析细节见 `03-login-passwd.md`，本篇只讲启动初始化进程这一侧的行为）：

- **`read_ttys` 状态**（启动脚本执行成功后在第 968 行附近返回该状态）：重读终端配置文件，建立"应该有哪些终端、每个终端运行什么程序"的期望清单。
- **`multi_user` 状态**：按期望清单派生会话。每个会话对应终端表中的一行"启用"记录，启动初始化进程为它创建子进程、运行指定的终端服务程序（通常是 `getty`），并把会话记入会话表。会话表用显式的增加与删除函数维护（第 191 到 192 行的 `add_session` 与 `del_session`），会话结构体里记录了终端表下标、在终端表中是否存在、要运行的程序与预解析好的参数表（第 157 到 165 行）。
- **`clean_ttys` 状态**：当终端配置文件变化（收到挂起信号）时进入。逐行对比"已知会话"与"文件现状"，区分四种处置：保留、发挂起信号后关闭、新增派生、撤销（对应的纯决策逻辑在 Rust 侧被提炼为 `clean_ttys.rs` 的 `diff_line` 函数，见第 4.3 节）。

单用户形态（`single_user`，第 695 行附近）则简单得多：在控制台上显示"输入管理员口令，或按 Control-D 进入多用户"的提示，根据输入决定停留还是继续走向多用户。这就是开机会先看到的那一行提示的来源。

### 2.4 信号面：关机、重启、掉电的三条信号线

启动初始化进程用信号处理函数把外部请求翻译成状态转移（第 315 行附近注册，第 517 到 538 行是 Minix 特有的两个处理函数）：

- 收到中止信号（Signal Abort，编号 6）：创建子进程执行 `/sbin/shutdown -r now`（重启）。
- 收到用户自定义信号一（编号 10，在部分架构是 30）：创建子进程执行 `/sbin/shutdown -p now`（断电停机）。
- 注意：处理函数里只做"创建子进程执行关机命令"这一件事，真正的"通知进程、等待退出、卸载文件系统"由关机命令完成。信号处理函数保持极简，是 Unix 编程的一条铁律（信号随时可能打断主流程，处理函数里做复杂事极易出错）。

Rust 侧把这张"信号编号到关机请求的映射"提炼成了纯函数 `request_for`（见第 4.3 节），映射关系与这两处源码逐项对应。

### 2.5 主启动脚本 `/etc/rc`：总体流程

`minix3/etc/rc`（468 行）是开机时实际跑起来的第一个脚本。它的流程体现了"总体调度与具体事项分离"：

1. 设置基本环境（家目录、命令搜索路径、文件默认权限），加载函数库与配置文件（第 20 到 30 行附近），检查"系统是否已配置"开关——如果管理员还没有确认配置，直接报错退出，避免在一台没准备好的机器上稀里糊涂进入多用户。
2. 收集 `/etc/rc.d` 下的脚本清单，用 `rcorder -s nostart` 算出执行顺序（第 141 到 152 行），然后逐个执行。
3. 执行输出一路记入启动日志（`/var/run/rc.log`），同时设立元数据标记，把"脚本自己的输出"和"调度器元数据"区分开（第 50 行附近的长标记串注释解释了为什么标记必须又长又唯一：防止与某个脚本的正常输出撞车）。

### 2.6 依赖排序工具 `rcorder`：注释即契约

`minix3/sbin/rcorder/rcorder.c`（771 行）读取每个脚本头部的依赖声明注释，关键词在第 78 到 90 行定义：`PROVIDE`（我提供什么能力）、`REQUIRE`（我依赖什么能力，也有复数拼写 `PROVIDES` 与 `REQUIRES`）、`BEFORE`（我必须排在谁前面）、`KEYWORD`（场景关键词，例如只在特定场合运行）。然后它做一次拓扑排序，输出满足所有约束的脚本顺序。

验证：32 个启动脚本中有 30 个以上含有 `PROVIDE` 声明（用 `rg -c PROVIDE minix3/etc/rc.d/` 逐个计数可复现，见第 7 节的验证记录）。这说明依赖声明不是摆设，而是每个脚本必须履行的契约。

### 2.7 关机、重启与首次配置：`shutdown`、`reboot`、`setup`

- `minix3/sbin/shutdown/shutdown.c`：体面关机的执行者——向所有进程发终止通知、等待退出、必要时强制杀死，最后调用系统停机或重启。启动初始化进程的信号处理函数最终都是 fork 出它来干活。
- `minix3/sbin/reboot/reboot.c`：短小直接的收尾工具，请求内核重启或停机。
- `minix3/minix/commands/setup/setup.sh`：首次启动时的交互式配置脚本（设时区、设管理员口令等），跑完后把"系统已配置"开关打开，后续开机 `/etc/rc` 的配置检查才能通过。可以把它理解成新机器的"开箱向导"。

### 2.8 配置文件面：`rc.conf`、`defaults`、`boot.cfg.default`

- `minix3/etc/rc.conf`（22 行）： thin 的本地覆盖层——先加载 `/etc/defaults/rc.conf` 的全部默认值，再在下面写本地修改。Minix 出厂默认把"系统已配置"设为 YES，保证首次启动直达多用户（见文件尾部的注释）。
- `minix3/etc/defaults/`：所有启动变量的默认值集中地，升级系统时覆盖此目录不影响本地的 `rc.conf`。
- `minix3/etc/boot.cfg.default`：内核引导加载器的默认配置面（等待时间、默认启动项），属于引导阶段与启动阶段的交界，由启动初始化进程读取执行（Rust 侧 `entry.rs` 的启动参数解析与之对应）。

## 3. Rust 设计决策

### 3.1 为什么用枚举状态机代替 C 的函数指针状态机

C 源码用"状态处理函数指针"（`state_func_t`，即返回下一个状态处理函数的函数指针）表示状态：当前状态就是一个函数地址，转移就是返回另一个函数地址。这种写法紧凑，但有两个代价：第一，状态集合是隐式的——想知道一共有几个状态，必须把所有返回语句找齐；第二，状态没有名字，想打印当前状态、想做状态覆盖测试，都无从下手。

Rust 实现（`state_machine.rs`）把七个状态收拢为一个枚举 `StateKind`，并配上 `as_char` 与 `from_char` 两个方向的转换函数，与 C 的单字符状态记号逐项对应。这样做的好处是编译器替我们检查完备性：任何按状态分派的 `match` 一旦漏掉某个状态就编译失败，而 C 语言里漏掉一个函数指针分支只会在运行时表现为莫名其妙的行为。

这个取舍参考了两边生态的通行做法。Linux 内核里大量的状态机仍然用函数指针或数值编码（历史包袱与性能惯性），而 Redox 的用户态服务更倾向用枚举加 `match` 表达状态（例如它的驱动状态管理），因为用户态程序的首要目标是可读与可验证。启动初始化进程是用户态程序，选枚举是顺势而为，不是对 C 源码的逐行翻译。

### 3.2 为什么把纯决策逻辑抽成独立函数

通读 `init.c` 会发现，很多逻辑其实不依赖操作系统：判断"这一终端行该保留还是关闭"只需要三个布尔值（会话是否已知、该行是否还在文件里、该行是否启用）；判断"这个信号对应哪种关机请求"只需要信号编号；判断"开机走单用户还是直接走启动脚本"只需要启动参数与控制台是否可用。

Rust 实现把这些逻辑抽成纯函数（输入确定、输出确定、不碰任何系统调用）：`session_db.rs` 的会话增删、`clean_ttys.rs` 的 `diff_line`（三个布尔值到四种处置的映射）、`contracts.rs` 的 `request_for`（信号编号到关机请求的映射）与 `shutdown_argv`（拼出关机命令的参数表）、`entry.rs` 的 `decide_entry`（启动参数加设备状况到初始状态的映射）。每个纯函数都可以直接单元测试，不需要伪造进程、信号与终端。这正是 89 个测试能全部在普通开发机上跑通的原因。

这种"纯决策下沉、系统交互上浮"的分层，与 Redox 用户程序的组织方式一致：解析与决策放在普通库里充分测试，真正执行系统调用的薄层尽量小。本篇的三个新 crate（见 `02`、`03`、`04` 各篇）沿用同一分层，只是走得更远——它们是完全不依赖操作系统的 `no_std` 库。

### 3.3 会话表：从 C 链表到哈希表

C 源码用侵入式链表维护会话（Unix 老程序的常见手法：结构体里直接嵌链表指针）。Rust 实现用标准库的哈希表（`HashMap`）存放会话，键是终端表下标。这样、查找与删除都是平均常数时间，更重要的是所有权清晰：会话的创建与销毁只发生在明确的函数里，不存在"链表节点忘记摘除"的整类错误。性能上两者没有可感知差别（会话数量就是终端行数，几十个的规模），可读性与安全性是选择哈希表的全部理由。

### 3.4 重大决策记录：启动脚本体系保留还是重写（架构演进候选 A-6）

计划中的架构演进项 A-6 提出一个重大问题：Minix-RS 最终是保留 shell 脚本启动体系（要求先实现一个兼容的 shell，见 `05-shell-family.md`），还是改用编译期静态配置（用 Rust 数据结构描述启动顺序）？

本篇不拍板，只记录决策现状与两边的代价：

- **保留 shell 脚本**：与现有 32 个脚本、`/etc/rc.subr` 函数库、`rcorder` 排序语义完全兼容，管理员的既有知识全部有效；代价是启动链依赖 shell 先就绪，启动顺序的实施排在 `05` 之后。
- **改用静态配置**：启动链可以很早独立验收，不依赖 shell；代价是 32 个脚本的语义要逐个翻译成静态数据，翻译过程本身可能引入行为差异，且与上游脚本演进脱钩。

Rust 当前实现（`runcom.rs` 记录执行意图、`sysctl.rs` 与 `ttys.rs` 解析配置面）刻意只建模"执行什么、按什么顺序"，不绑定"用什么语言执行"，为两种结局都留了门。这个悬置是诚实的：在 shell 就绪之前，任何"已决定"的宣称都是虚假的。

### 3.5 与 Linux 服务管理器的对比：相同的依赖思想，不同的执行载体

Linux 的 systemd 用单元文件声明依赖（`After` 对应"在我之前启动谁"，`Requires` 对应"我需要谁"），由常驻的服务管理器求解启动顺序。Minix 的 `rcorder` 方案用脚本头部注释声明同样的关系（`REQUIRE` 对应需要谁，`BEFORE` 对应排在谁前面，`PROVIDE` 给能力命名以便引用），由一次性的排序工具求解顺序，然后由 shell 逐个执行。

两种方案的依赖语义是同构的，差异在执行模型：systemd 常驻并持续监管服务（崩溃重启、按需激活），Minix 的启动链是一次性的（执行完就退出，之后的值守交给启动初始化进程的终端会话管理）。理解了这个差异，就理解了为什么 Minix 不需要一个常驻的"启动管理器"——值守职责本来就在第一个进程手里。

## 4. 实现详解

### 4.1 模块结构

`os/commands/sbin/init`（程序包名 `minix-init`）共 15 个源文件，每个文件对应 C 源码的一个职责面：

| Rust 文件 | 对应 C 源码位置 | 职责 |
|-----------|----------------|------|
| `main.rs` | `init.c:229-367` | 入口流程：解析参数、探测设备、决定初始状态 |
| `entry.rs` | `init.c:229-367` | 启动参数解析（`parse_boot_args`）与初始状态决策（`decide_entry`）；设备探测接口 `DeviceProbe` 带两个行为不同的实现（测试用 `FakeDeviceProbe` 与生产用 `FsDeviceProbe`，后者查真实文件系统） |
| `state_machine.rs` | `init.c:130-146`、`624-640` | 七状态枚举、信号枚举、转移表 |
| `single_user.rs` | `init.c:692-760` | 单用户会话：口令提示与 Control-D 转移 |
| `runcom.rs` | `init.c:860-1013` | 执行启动脚本子进程的监护逻辑 |
| `multi_user.rs` | `init.c:multi_user` 相关段 | 多用户会话派生 |
| `read_ttys` 相关（在 `ttys.rs`） | `init.c:read_ttys` 相关段 | 终端表重读与期望清单构建 |
| `clean_ttys.rs` | `init.c:clean_ttys` 相关段 | 已知会话与文件现状的逐行对比（`diff_line`） |
| `session.rs` | `init.c:157-165` | 会话结构体（终端表下标、存在标志、程序与参数表） |
| `session_db.rs` | `init.c:190-192` | 会话增删（`add_session`、`del_session`） |
| `ttys.rs` | 终端表解析 | 终端表行解析（格式细节见 `03-login-passwd.md`） |
| `utmp.rs` | `init.c:197-208` | 登录记录（`session_utmpx`、`make_utmpx`、`utmpx_set_runlevel`） |
| `contracts.rs` | `init.c:517-538` | 外部契约：关机信号映射（`request_for`）与关机参数表（`shutdown_argv`） |
| `shutdown.rs` | 关机流程 | 关机状态流转 |
| `sysctl.rs`、`log.rs` | `init.c:176-189`、`188-189` | 安全级别探测与日志通道 |

### 4.2 关键类型与不变量

- **状态枚举 `StateKind`**：七个变体与 C 的七个单字符记号一一对应（`as_char`/`from_char` 互为逆函数，往返测试覆盖全部七个）。不变量：任何时刻有且仅有一个当前状态，转移只能发生在信号处理与子进程回收两个明确位置。
- **会话记录**：键为终端表下标的哈希表。不变量：下标唯一；`clean_ttys` 对比时"已知但文件已无"的会话必须先发挂起信号再撤销，不能直接丢弃（否则终端上的进程永远收不到挂起通知）。
- **关机请求映射**：信号编号 6（中止）映射到重启，编号 10 或 30（用户自定义信号一）映射到断电停机，其余信号返回"无请求"（由别处的状态处理接管）。不变量：映射函数永不崩溃，未知信号一律放行。

### 4.3 纯决策函数一览

| 函数 | 输入 | 输出 | 对应 C 行为 |
|------|------|------|------------|
| `diff_line(已知, 在文件, 启用)` | 三个布尔值 | 保留、发挂起后关闭、新增、撤销 | `clean_ttys` 的逐行处置 |
| `request_for(信号编号)` | 整数 | 重启、断电、无请求 | `minixreboot` 与 `minixpowerdown` 的分派条件 |
| `shutdown_argv(关机请求)` | 重启或断电 | 关机命令参数表 | 两处 `execl("/sbin/shutdown", ...)` 的参数 |
| `decide_entry(启动参数, 控制台可用)` | 参数与设备状况 | 从启动脚本走还是停单用户 | `main` 到 `transition` 之间的决策段 |

## 5. 测试要点

`cargo test -p minix-init`：**89 个测试，全部通过**（截至 2026-09-06）。

测试按模块组织，重点行为如下（以下函数名均可用 `rg "fn 测试名" os/commands/sbin/init` 复现）：

- **状态机**（`state_machine.rs`）：七个状态字符往返、非法字符返回空、转移表覆盖（单用户收到挂起信号重读终端表、多用户收到终止信号走向清理等）。
- **终端清理决策**（`clean_ttys.rs`）：`test_known_on_keeps`（已知且启用则保留）、`test_known_off_shutdowns`（已知但关闭则发挂起后关闭）、`test_unknown_creates`（未知则新增）、`test_missing_retires`（文件已无则撤销）——四个测试恰好覆盖 `diff_line` 的四种输出。
- **关机契约**（`contracts.rs`）：信号编号 6 映射重启、编号 10 与 30 映射断电、其余信号无请求、参数表拼装包含正确的 `-r` 或 `-p` 标志。
- **入口决策**（`entry.rs`）：控制台缺失时 fallback 到单用户、快速启动标志解析、设备探测失败的处置；`test_fs_probe_sees_live_filesystem`（真实文件系统探针见得到根目录、见不到虚构路径）与 `test_probes_are_interchangeable_as_trait_objects`（两探针同一接口调用）。
- **会话数据库**（`session_db.rs`、`session.rs`）：增删往返、重复增加的幂等性、删除不存在会话的安全无操作。

尚未覆盖、随后续阶段补齐的：真实派生终端会话（依赖进程管理原语）、真实执行 `/etc/rc`（依赖 shell 就绪，即架构演进候选 A-6 落定之后）。这两项在代码里显式走"记录意图"的降级路径，不静默失败。

## 6. 过渡：从启动链走向服务与登录

本篇走完了交付因果链的第一步：内核把控制权交给启动初始化进程，它执行启动脚本、把系统带到多用户形态、并在每个启用的终端上派生值守程序。

但启动脚本执行起来之后，第一个需要回答的问题是："启动的那些常驻服务，谁来日常管理（启停、查状态）？"——这是 `02-service-scheduler.md` 的职责（服务管理命令与定时调度）。而终端上被派生的值守程序 `getty` 一旦跑起来，它如何初始化终端、如何交棒给 `login`、口令数据库又长什么样——这是 `03-login-passwd.md` 的职责。阅读顺序上请先走 `02`，再走 `03`：先理解"服务"这个概念，再看"登录"这个最特殊的服务现场。
