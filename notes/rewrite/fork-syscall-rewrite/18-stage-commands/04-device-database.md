## 1. 概念：设备是文件，名字是契约

### 1.0 本章说明

本章讲两件事：`/dev` 下的设备文件从哪里来，以及系统里各种"名字对数字"的对照表由谁维护。

> **本章不讲什么**：
>
> - 设备驱动的内部实现（见 `16-stage-drivers` 各篇）
> - 口令数据库（见 `03-login-passwd.md`）
> - 网络协议栈如何使用主机表（见 `18-network-config.md`）
>
> 本章只讲用户侧看得见的三件事：建设备节点、写目录规范、查系统数据库。

### 1.1 一切皆文件在设备侧的体现

Unix 把设备抽象成文件：`/dev/console` 是控制台，`/dev/c0d0p0s0` 是某块硬盘的某个分区，读写这些"文件"就是读写设备。应用程序不需要知道硬盘控制器的端口地址，只需要打开路径、读写、关闭——与操作普通文件同一套动作。这就是"设备是文件"：内核把设备驱动藏在文件接口后面。

但文件接口解决的是"怎么用"，没解决"从哪来"：`/dev` 目录本身不会凭空长出几百个设备文件。有人必须在系统安装时（以及 governance 变化时）按"设备类型、主设备号、次设备号、属主、权限"的清单把节点一个个建出来。这个"有人"就是本篇的主角之一：静态建设备脚本（`MAKEDEV`）加单节点创建命令（`mknod`）。

主设备号与次设备号需要解释：主设备号表示"哪一类驱动"（例如音频类是 13，见 `MAKEDEV.sh` 第 210 行 `makedev audio c 13 0`——字符设备、主号 13、次号 0），次设备号表示"这类里的第几个"（混音器是同类 13 的次号 1）。应用程序打开设备文件时，内核取出这两个号，就知道把读写请求转交给哪个驱动的第几个设备。设备文件就是"两个号加权限"的物化形态。

### 1.2 建设备节点的两种输出：真建与只说

`MAKEDEV.sh` 的核心 `makedev` 函数（第 56 行起）接受统一的七个参数（设备名、类型、主号、次号、属主用户名、属组名、权限，可选第八个链接目标），然后按两种模式输出：

- **真建模式**：直接执行 `mknod 设备名 类型 主号 次号`，再 `chmod` 设权限、`chown` 设属主；链接类型则执行 `ln`。这是安装时真实创建 `/dev` 的路径。
- **只说模式**（`MTREE` 开关打开）：不执行任何命令，只打印目录规范行（`./dev/音频设备 类型=字符 属主=… 权限=… 设备=本地,13,0`）。打印出来的文本可以直接喂给目录校验工具，核对"建出来的对不对"。

"真建"与"只说"共用同一套参数解析，是深思熟虑的设计：校验标准与创建动作不可能脱节，因为它们是同一段代码的两种输出。很多系统的"文档说一套、程序做一套"问题，根子就在于标准与实现是两份独立维护的文本。

`mknod` 命令是"真建"能力的单点版本：一次建一个节点。`MAKEDEV.sh` 里列出的标准设备集合（`STD_DEVICES`，含内存盘设备、终端、传感器、音频等上百项）本质上就是循环调用单点能力。理解了 `mknod`，就理解了 `MAKEDEV` 的每一行。

### 1.3 设备数据库：给设备建索引

`/dev` 下文件上百之后，"按名字找设备号"成了高频操作。`dev_mkdb` 命令的做法是遍历 `/dev`（用文件层次遍历接口，第 214 行），把每个设备文件的"设备号、类型、相对路径"逐条写进一个常量数据库（第 56 到 98 行的写入器：打开写器、逐条放入、落盘时打上版本标记）。之后查询设备不再扫描目录，而是查索引。这与 `03` 篇口令库"文本编译成哈希"的思想是同一个：读多写少的数据，离线建索引、在线查索引。

### 1.4 系统数据库：十三张对照表，一个查询入口

系统里散落着十几张"名字对照表"：组名对组标识（`group`）、主机名对地址（`hosts`）、服务名对端口（`services`）、协议名对协议号（`protocols`）、合法 shell 清单（`shells`）、终端能力（`gettytab`，见 `03` 篇）等等。每张表格式不同、消费者不同，但查询动作相同："给我这个名字对应的那一行"。

`getent` 命令（`getent.c` 第 98 到 118 行的数据库表登记了 13 个名字，各自绑定一个查询回调，其中远程过程调用库一项仅在非 Minix 时编译，Minix 上实际 12 项；主函数第 120 到 136 行：参数不足直接打印用法，按第一个参数的名字分派回调，名字对不上就报"未知数据库"并打印用法）把十余种查询收敛成一个入口：`getent 数据库名 键…`。管理员排错时不用记十余种查法，脚本里解析输出格式也统一。这种"多表一门"的收敛，与 `service` 命令收敛启动脚本、`UserDatabase` 接口收敛用户查询，是同一设计品味的三次出现。

各配置文件的分工（以 `etc/` 实例为准）：`group` 管组（`wheel:*:0:root`——组名 wheel、口令占位星号、组标识零、成员 root）；`shells` 列合法登录 shell（登录程序据此拒绝陌生 shell）；`hosts` 管主机名；`services` 管服务名与端口；`protocols` 管协议名；`motd` 是登录后显示的每日信息（纯文本）；`nsswitch.conf` 决定"先查文件还是先问网络"（名字解析的策略开关）；`utmp` 记录当前登录会话（谁在系统上，由登录链写入、用户查询命令读取）。

## 2. C 源码分析

### 2.1 `makedev` 函数：七个参数，两种输出（`MAKEDEV.sh` 第 56 到 110 行）

函数先做参数个数检查（7 个或 8 个，否则返回 1），再把类型字母翻译成单词（块、字符、链接，其他字母返回 2）。类型决定后续分支：链接类型忽略主次设备号、记下链接目标；块与字符类型走设备分支。然后按 `MTREE` 开关二选一：打印规范行，或执行创建命令。注释第 56 行把参数顺序钉死在函数头上，调用处传错顺序一眼可见。

实例行（第 210 行附近）：`makedev audio c 13 0 属主 属组 666`——音频设备、字符类型、主号 13 次号 0、所有人可读写。传感器行展示了"主号随总线变化"的写法（`bmp085b总线号s77`），磁盘行展示了"同一前缀加分区后缀"的展开（`c0d0`、`c0d0p0`、`c0d0p0s0` 三级）。读这些实例行，是理解"主次设备号如何编码真实硬件拓扑"的最短路径。

### 2.2 `mknod`：单节点创建的参数面（`mknod.c` 与 `pack_dev.c`）

`mknod` 命令行接受"路径、类型、主号、次号"，外加属主、属组、权限选项。它把主次设备号打包成内核的设备号表示（`pack_dev.c` 的职责：按目标系统的位布局拼装，NetBSD 系的打包规则），然后调用创建设备节点的系统调用。与 `MAKEDEV.sh` 的关系：脚本负责"知道建什么"（清单），`mknod` 负责"动手建"（动作），两者通过命令行衔接——脚本里那句 `mknod 设备名 类型 主号 次号`就是明证（第 96 行）。

### 2.3 `dev_mkdb`：遍历与建库（`dev_mkdb.c` 第 56 到 98 行、第 178 到 220 行）

主函数（第 178 行起）打开数据库写器，物理遍历（不跟随符号链接，防循环）目标目录（第 214 行的文件层次打开），每遇到一个设备文件就调写入条目函数（第 88 行起：拼装"设备号加类型"键与"相对路径"值，放入写器），最后落盘并在文件头打版本标记。常量数据库的特性是"建成后只读"，查询端无需加锁——这是它敢被高频查询的底气。

### 2.4 `getent`：数据库表驱动的分派（`getent.c` 第 98 到 136 行）

数据库表是"名字加回调"的数组（组、主机、服务、协议、shell 等 14 项，远程过程调用库一项仅在非 Minix 时编译，注释写明了条件）。主函数逻辑三段：参数不足打印用法；线性扫描表找名字，命中即调回调并返回其退出码；扫完没命中，警告"未知数据库"再打印用法。每个回调内部再调 C 库的对应查询函数（如查组调按名查组、查服务调按名查服务，见第 274 与 809 行附近的调用点）。表驱动的好处：加一种数据库只加一行表项，主函数纹丝不动。

### 2.5 目录规范：`etc/mtree/` 与 `mtree` 命令

`etc/mtree/` 下是多份层次规范（基础发行版、兼容层、不同架构各一份），每行"路径加 `键=值` 属性"（类型、权限、属主等）。`mtree` 命令（`usr.sbin/mtree/`）做两件事：按规范创建目录树（安装时），或按规范校验现有目录树（审计时，报出权限被改、文件缺失之类的问题）。与 `MAKEDEV` 的"只说模式"输出格式一致，两者可以互相喂——创建清单即校验标准，见 1.2 节。

## 3. Rust 设计决策

### 3.1 为什么查询接口按"数据库"而不是按"行格式"组织

直觉的做法是"解析器大一统"：组行、服务行都是文本行，写一个通用行解析器。但 `getent` 源码展示的真相是：分派发生在"数据库名"这一级（十三选一），而不是"行格式"这一级。调用方永远先说"我要查组"，再说"键是 wheel"。Rust 实现（`lookup.rs`）于是定义 `LookupTable` 接口（按名查行），`GroupTable` 与 `ServicesTable` 各自实现，共享的查无处理收拢进 `getent` 函数（空键判参数无效、查无判不存在）。接口的划分与 C 的分派表同构，只是把"函数指针数组"换成了"接口加实现"——Rust 类型系统能表达时，就不用函数指针表。

### 3.2 为什么服务查询认别名而组查询不认

这是两种数据库的本质差异，不是实现偷懒：服务天然有多个名字（`http`、`www`、`www-http` 同指 80 端口，见测试用的真实行样），组名则一对一。`ServicesTable` 的查找同时比对主名与别名表（与 C 库按名查服务解析别名的行为一致），`GroupTable` 只比对主名。接口相同、行为不同——这正是"一个接口、两种实现"要表达的：调用方统一，语义各从其库。如果未来接入主机表（别名更多），再加第三个实现，调用方依然不动。

### 3.3 为什么解析上限是显式常量

组员上限 16、别名上限 8、能力上限 32、属性上限 16——这些数字是拍脑袋定的吗？是，但拍得诚实：无标准库环境没有可增长数组，栈上固定数组必须有个大小；超限判错（而不是静默截断），保证"解析成功即完整"。常量全部公开命名（`MAX_MEMBERS` 等），调用方与评审者都能看到边界在哪里。Linux 与 Redox 的同类解析器在内核侧同样用固定上限（附带截断或报错策略），思路一致，只是本库选择"报错"而非"截断"——截断会撒谎（丢了成员还说解析成功），报错不会。

### 3.4 为什么坏行跳过而不是整库报错

三个表的查找都遵循"单行解析失败就跳过、继续找下一行"（`find_map` 加 `ok` 转换）。理由来自运维现实：系统数据库是人维护的文本，偶尔混入一行坏格式（升级脚本 bug、多人编辑冲突）不该导致整个登录或查询链瘫痪。C 库的逐行扫描同样是"坏行继续"，行为一致。但"跳过"不等于"无视"：解析函数本身对坏行返回明确错误，调用方若做"全表校验"（如 `mtree` 审计模式）仍可逐行收集错误——查找与校验是两个场景，共用解析、各取所需。

## 4. 实现详解

### 4.1 模块结构

`os/commands/sbin/devdb`（库包名 `minix-devdb`）共 5 个源文件：

| Rust 文件 | 对应 C 源码位置 | 职责 |
|-----------|----------------|------|
| `lib.rs` | — | 错误类型（`DevDbError`，22 对应参数无效、2 对应键不存在）与模块组织 |
| `group.rs` | `etc/group` 格式 | 组行四字段解析（`parse_group_line`，成员上限 16） |
| `services.rs` | `etc/services` 格式 | 服务行解析（`parse_services_line`，井号注释、端口冒号协议、别名上限 8） |
| `mtree.rs` | `etc/mtree/` 行格式 | 规范行解析（`parse_mtree_line`，斜杠指令跳过、属性查询 `attribute`） |
| `lookup.rs` | `getent.c:98-136` 分派思想 | `LookupTable` 接口、`GroupTable` 与 `ServicesTable`、`getent` 查无处理 |

### 4.2 关键类型与不变量

- **组条目 `GroupEntry`**：组名、组标识数字、成员表。不变量：四字段不多不少；成员可空（无成员组合法）；成员名字符规则与登录名一致。
- **服务条目 `ServiceEntry`**：服务名、端口号、传输协议、别名表。不变量：端口列必含斜杠；协议只认传输控制协议与用户数据报协议两个词；端口号不溢出 16 位；井号之后全是注释（含行首井号的整行跳过）。
- **规范条目 `MtreeEntry`**：路径加属性表。不变量：路径之后每个词必含等号；斜杠指令（`set`、`unset`）不是条目，由校验器（调用方）处理；`attribute` 查询按名精确匹配。
- **查询接口 `LookupTable`**：关联行类型加按名查找。不变量：坏行跳过；首个命中获胜（与 C 库"文件在先者胜"的顺序语义一致）。

### 4.3 解析与查询函数一览

| 函数 | 输入 | 输出 | 对应 C 行为 |
|------|------|------|------------|
| `parse_group_line(行)` | 文本行 | 条目 | `group` 文件四字段语义（实例 `wheel:*:0:root`） |
| `parse_services_line(行)` | 文本行 | 条目、无（注释空行）、错 | `services` 文件列语义与井号注释 |
| `parse_mtree_line(行)` | 文本行 | 条目、无（注释空行与斜杠指令）、错 | `mtree` 规范行语义 |
| `getent(表, 键)` | 接口对象与键 | 行或查无 | `getent.c` 主函数的分派加查无语义 |

- **规范解析**（`mtree.rs`，5 个）：`test_directory_entry`（路径加类型权限双属性、缺席属性查无）、`test_directives_skipped`（两斜杠指令跳过）、`test_comment_and_blank_skipped`、`test_bare_word_rejected`（无等号词）、`test_empty_line_rejected`（纯空白行视为空行跳过）。
- **查询接口**（`lookup.rs`，5 个）：`test_group_lookup_by_name`（命中与落空）、`test_services_lookup_by_alias`（别名命中主行）、`test_services_lookup_skips_comments`（注释行不干扰）、`test_getent_maps_miss`（查无与空键的两错误）、`test_tables_are_interchangeable_by_shape`（两表同式调用）。

尚未覆盖、随后续阶段补齐的：其余十种数据库（Minix 上实际 12 项，已实现组与服务两项；每种加一个解析模块加一个表实现，接口不动）、真正创建设备节点（依赖设备号系统调用）、常量数据库的构建与查询（`dev_mkdb` 的读写两端）。解析与查询层是全覆盖的，执行层是显式留白的。

## 6. 过渡：地基就位，迎接 shell

本篇走完了交付因果链的地基层：设备节点有人建（静态脚本列清单、单点命令动手建）、设备索引有人编（遍历建库）、系统名字有人管（十三表一门查）、目录层次有人验（规范即标准）。

至此，交付因果链的第一环（`01` 启动、`02` 服务、`03` 登录、`04` 设备与名字）全部闭合：启动初始化进程能派生会话，因为终端设备存在；登录程序能验人，因为口令库存在；服务能被管理，因为名字解析存在。下一站是 `05-shell-family.md`——登录链交棒的 shell 本体：命令解释器的三副面孔（精简 shell、Korn 风格 shell、C 风格 shell）与环境变量语义。地基篇到此结束，交互篇正式开始。
