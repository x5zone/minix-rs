### 1.1 什么是"保护"——为什么要保护（NEW — WHY 地基）

**目标**: 建立"保护"的直觉，不靠术语堆砌。让初学者先理解"保护"在保护什么、从谁那里保护。

**内容要点**:
- **信任边界**：内核可信，用户进程不可信。这是操作系统存在的根本前提之一。一句话建立前提，不展开成哲学讨论。
- **具体例子**（GPT4-2 简化版）：用户程序执行 `*((int*)0)=0`（写空指针）或 `sys_kill_all_processes()`（试图直接调用内核功能）。为什么不能成功？
  - 不是因为"用户"二字有魔法
  - 而是因为 CPU 硬件 + OS 配置协同阻止：用户态特权级低 → 该地址在页表里无权限（或该功能需 syscall 入口）→ CPU 触发缺页异常 → 跳到内核 handler → 内核杀掉进程
  - **为什么用这个例子而非 `*(0xffffffff80000000)=0`**：避免初学者分心"为什么这个地址是内核地址"。空指针更直观，权限拒绝的核心机制相同。
  - 这个例子预告了三件事：特权级、页表权限位、异常处理——正是后文要展开的三个机制
- **"保护"的定义**：让不可信代码不能破坏可信代码（内核）和其他不可信代码（别的进程）。保护 = 特权级 + 内存权限 + 异常处理 的协同。
- **过渡**：这种保护靠 CPU 硬件特权级实现。引出 1.2。

### 1.2 硬件特权级——保护的地基（NEW — WHAT 是特权级，不讲页表权限位）

**目标**: 讲清特权级是 CPU 内建的权限等级，是所有保护机制的根基。三架构对照建立统一心智模型。**本节只回答"特权级是什么"，不讲"如何落地为内存保护"（后者移到 1.4 第一问，避免重复）**。

**内容要点**:
- **三架构特权级对照**（GPT4-3 严谨版，RISC-V SPP 表述修正）:

| 架构 | 内核特权级 | 用户特权级 | 当前特权级存放 |
|------|-----------|-----------|---------------|
| x86-64 | ring 0 | ring 3（ring 1/2 不用） | CPL（CS 低 2 位） |
| aarch64 | EL1 | EL0（EL2/3 留给虚拟化/固件） | PSTATE.M |
| riscv64 | S-mode | U-mode（M-mode 留给固件） | CPU 当前状态（trap 来源由 sstatus.SPP 记录） |

- **CPU 如何知道当前特权级**：简述 CPL / PSTATE.M / sstatus 的角色——CPU 每条指令执行时都隐含知道自己在哪个特权级，这是硬件强制的，软件无法伪造。
  - **RISC-V 严谨表述（GPT4-3 必改）**：RISC-V 当前运行级别是 CPU 当前状态（S-mode 或 U-mode），**不是**靠 sstatus.SPP 表示。SPP 只在 trap 发生时记录"trap 来自哪个特权级"（0=U-mode, 1=S-mode），供 sret 返回时决定降回哪级。即：SPP 是"来源记录"，非"当前状态"。当前状态由 CPU 内部硬件状态机维护，软件不可直接读取一个"当前 mode"寄存器（需通过 sstatus.SPP 间接推断仅在 trap 入口时有效）。
- **特权级切换的两种触发**（概念点到，细节延后）:
  - **被动**：异常（除零/缺页/未定义指令）→ CPU 自动切到内核态
  - **主动**：系统调用（syscall/svc/ecall）→ 用户主动请求进入内核
  - 两者都涉及特权级跨越，都需要 CPU 硬件配合
- **过渡**：特权级是地基，但光有"当前在哪个特权级"不够——CPU 在异常/系统调用时还需要回答几个运行时问题。引出 1.3 流程，1.4 CPU 视角三问。

### 1.3 跨特权级的统一流程（NEW — 共性模型，syscall/exception 分叉，三架构统一抽象+返回闭环）

**目标**: 用一张图建立"用户态↔内核态"的整体心智模型，三架构共性。这是 GPT 强调的"真正的架构抽象"。**syscall 和 exception 分叉表示**（GPT 第二轮第三处），因为对初学者是两个不同概念。**流程图用三架构统一抽象层**（GPT 第三轮第二处）——不写"CPU 自动切栈"，因为 RISC-V 是软件切栈，写"自动"会让 1.4c 推翻流程图。**加返回闭环**（GPT 第三轮第四处）——保护结构是双向门非单向门。

**内容要点**:
- **统一流程图**（分叉版+三架构统一抽象+返回闭环+顺序修正+保存现场统一）:

```
用户态运行
    │
    ├──→ syscall / svc / ecall   （用户主动请求服务）
    │
    └──→ exception               （CPU 被动发现错误：除零/缺页/未定义指令）
            │
            ▼
    CPU 进入更高特权级（ring3→ring0 / EL0→EL1 / U→S）
            │
            ▼
    跳到异常入口 + 切换到可信内核栈
    （x86/aarch64：CPU 读向量表时原子完成跳入口+切栈；riscv64：跳到 stvec 后软件第一条指令交换 sscratch 切栈）
            │
            ▼
    保存现场（cs/rip/ss/rsp/rflags 等；由硬件、软件或两者协作完成，具体机制因架构而异）
            │
            ▼
    内核 handler 执行
            │
            ▼
    返回指令（iretq/eret/sret）：恢复现场 + 切回用户栈 + 降特权级
            │
用户态继续运行
```

- **关键点 1（顺序修正，自评3）**：x86 读 IDT 门描述符时，CPU **同时**完成切栈（从 TSS.sp0 加载 RSP）+跳入口（加载门描述符里的 handler 地址），是原子操作，非"先跳再切"。aarch64 类似（EL0→EL1 时硬件切 SP_EL1 并跳 VBAR_EL1 指向的入口）。riscv64 不同：CPU 只负责跳到 stvec，切栈由 handler 第一条指令 `csrrw sp, sscratch, sp` 软件完成。流程图抽象层把"跳入口+切栈"合并为一步，三架构都成立，1.4c 再分架构展开硬件 vs 软件。
- **关键点 2（保存现场统一，GPT4-4）**：三架构"保存现场"也不统一——x86 CPU 硬件自动压入 SS:RSP:RFLAGS:CS:RIP，其余寄存器软件保存；aarch64 大部分寄存器软件保存；riscv64 全部软件保存。流程图用"保存现场"抽象表述，加注"由硬件、软件或两者协作完成，具体机制因架构而异"，1.4b/1.4c 不展开细节（留 ch13）。
- **syscall vs 异常的本质区别**（概念点到，细节延后 ch12）：
  - 异常 = CPU 被动发现错误，用户进程"不想"进入内核
  - syscall = 用户主动、受控请求服务，是合法的特权级跨越
  - 两者在"切栈+保存现场+跳入口"的硬件机制上相同，区别在触发意图和返回后用户态是否继续原指令
- **返回闭环（GPT 第三轮第四处，必须建心智模型）**:
  - 保护结构不是单向门（只管"用户→内核"），而是双向门（"内核→用户"返回同样重要）。
  - 返回时 CPU 必须能：恢复用户现场 + 切回用户栈 + 降特权级——这三件事由返回指令原子完成。
  - **返回指令对照表**（不展开，只建模型）:

| 架构 | 返回指令 | 完成动作 |
|------|---------|---------|
| x86-64 | `iretq` | 弹出 RIP/CS/RFLAGS/RSP/SS，CS 低 2 位决定降回 ring3 |
| aarch64 | `eret` | 恢复 PCSP_EL0，PSTATE.M 降回 EL0 |
| riscv64 | `sret` | 恢复 PC，sstatus.SPP 决定降回 U-mode |

  - 细节（swapgs、sscratch 二次交换、用户态恢复后的指令位置）留给 ch12/ch13。
- **为什么这个流程需要 CPU 预先配置**：切栈要知道切到哪个栈，跳入口要知道跳到哪个地址——这些答案 CPU 不会自己生成，必须 OS 预先填好。引出 1.4 CPU 视角三问。

### 1.4 CPU 视角三问（NEW — 核心框架，替换原 OS 资源三问）

**目标**: 从 CPU 运行时视角提出三个问题，prot_init 的全部工作就是给 CPU 配置这三个答案的数据结构。**这是本章核心**——概念（三问）与实现（prot_init）的统一性极强。

#### 1.4 引子：CPU 视角总领（GPT 第二轮第六处+第三轮第一处纯化）

**内容要点**:
> 从 CPU 的角度看，保护结构就是回答三个运行时问题：
> 1. 当前什么特权级？
> 2. 异常/syscall 发生时跳到哪里？
> 3. 陷入内核时用哪个栈？
>
> `prot_init()` 的全部工作，就是给 CPU 配置回答这三个问题的数据结构。后文三问逐一展开，每问对应 prot_init 的一类配置。
>
> **注**：第一问"特权级"是核心，它进一步决定可访问的内存范围（见 1.4a）——但内存访问控制是特权级的"后果"，不是与特权级并列的独立问题。特权级是地基，页表权限位是落地手段。

#### 1.4a 第一问：当前什么特权级？（+ 特权级如何落地为内存访问控制）

**目标**: 三问第一问纯化为"当前什么特权级"（GPT 第三轮第一处），内存访问控制作为特权级的"后果"展开，不作为独立问题。这样三问维度更纯（都是 CPU 视角），且不丢耦合知识点。把"特权级定义"（1.2）和"如何落地为内存保护"（本节）分开讲，避免重复。

**内容要点**:
- **特权级如何落地为内存访问控制（作为特权级的"后果"展开，耦合点必须讲透；删去"WHY 特权级本身"段——1.2 已讲，避免重复）**:
  - 特权级本身只是个"标签"（1.2 讲过），不能直接阻止访问。真正阻止访问的是**内存管理数据结构里的权限位**——而哪些权限位生效，由当前特权级决定：
    - x86 页表 PTE 的 U/S 位（0=Supervisor only, 1=User 可访问）；段描述符 DPL
    - aarch64 页表 PTE 的 AP 位、UXN/PXN
    - riscv64 页表 PTE 的 U 位 + R/W/X
  - **耦合关系（层次清晰）**：特权级决定"能不能"，页表权限位"执行能不能"。两者缺一不可。**特权级是核心，页表权限位是落地手段（后果），非并列**。回到 1.1 的例子：`*((int*)0)=0` 失败，正是因为 ring3 + PTE.U=0 协同阻止——ring3 是"为什么不能"，PTE.U=0 是"如何阻止"。
  - **边界声明**：保护结构不"做"内存管理，但依赖内存管理的数据结构落地权限。页表组织（多级/TLB）是内存管理文档的事，本文只讲权限位这一耦合点。
- **小图（GPT4-5 推荐改，本节最难理解，必须加）**:

```
特权级（为什么不能）
    │
    ▼
CPU 发起内存访问
    │
    ▼
检查页表权限位（如何阻止）
    │
    ├── 允许 → 访问成功
    └── 拒绝 → 触发异常（阻止后的动作）
                    │
                    ▼
                跳到内核 handler（见 1.4b）
```

  - 这张图建立三层层次：特权级（为什么不能）→ 页表权限位（如何阻止）→ 异常处理（阻止后动作）。是本节核心教学价值。
- **prot_init 的职责（三架构不对等，必须点明，自评2）**:
  - **x86**：prot_init 配置 GDT 段描述符 DPL（初始代码段/数据段描述符），是 x86 特权级检查的依据。
  - **aarch64/riscv64**：prot_init 在第一问**几乎不配置**——特权级是 CPU 固定的（EL0/EL1、U/S 是硬件定义），页表权限位由 arch_boot_impl 建立（02 文档），不归 prot_init。
  - **点明不对等**：1.4 引子说"每问对应 prot_init 一类配置"，但第一问只在 x86 有 prot_init 配置（GDT DPL），aarch64/riscv64 在第一问 prot_init 几乎不干活。这是 x86 历史包袱（段描述符 DPL）导致的，非三架构共性。读者需理解：第一问的"答案"在 aarch64/riscv64 由 arch_boot_impl（页表权限位）+ CPU 硬件（固定特权级）共同提供，prot_init 只在 x86 补充段描述符 DPL。

#### 1.4b 第二问：异常/syscall 发生时跳到哪里？（异常入口）

**目标**: 讲清异常向量表的存在原因和三架构实现。

**内容要点**:
- **WHY**：CPU 发现异常或收到 syscall 时，自己不知道该执行哪个函数——必须有一张表告诉它"向量号 X → handler 地址 Y"。无有效入口 → triple fault（x86）/ 异常嵌套失控。
- **HOW（三架构）**: x86 IDT / aarch64 VBAR_EL1 / riscv64 stvec。一句话流程：CPU 发现异常 → 查向量表 → 找到 handler → 跳转。
- **嵌套异常用哪个栈（概念点到，细节延后 ch13）**:
  - x86-64：同特权级不切栈（用当前 RSP）；NMI/double-fault/MCE 用 IST（TSS 里 7 个专用栈）避免依赖可能已损坏的内核栈。
  - aarch64：EL1 再陷异常仍用 SP_EL1，需小心保存/恢复。
  - riscv64：sscratch 在内核态时存的是用户 sp，必须检测 sstatus.SPP 判断"来自用户还是内核"再决定是否交换——RISC-V trap 处理已知复杂点。
- **prot_init 的职责**：填充异常向量表元数据（IDT 门描述符的 DPL/IST/门类型；VBAR/stvec 指向汇编定义的向量表）。注意：handler 地址在本文阶段仍为 0，真正加载推迟到 ch13 set_handler() 之后。

#### 1.4c 第三问：陷入内核时用哪个栈？（跨特权级栈切换）

**目标**: 讲清栈切换的 WHY 和三架构 HOW，强调 RISC-V 软件切栈特色。

**内容要点**:
- **WHY**：若 user→kernel 继续用用户栈保存上下文（cs/rip/ss/rsp/rflags），用户能把栈顶设在只读页或构造畸形栈帧 → 篡改陷入上下文或内核栈溢出。必须切到可信内核栈。CPU 进入内核第一件事不是执行 handler，而是"找个安全地方保存现场"——这就是栈。
- **HOW（三架构，核心知识点）**:

| 架构 | 栈切换方式 | 关键寄存器/结构 |
|------|-----------|----------------|
| x86-64 | CPU 硬件自动：ring3→ring0 从 TSS.sp0 加载 RSP，压入 SS:RSP:RFLAGS:CS:RIP | TSS.sp0 |
| aarch64 | CPU 硬件自动：EL0→EL1 切到 SP_EL1 | SP_EL1 |
| riscv64 | **硬件不切**：软件 `csrrw sp, sscratch, sp` 交换；sscratch 存内核栈顶 | sscratch |

- **RISC-V 特色必须强调**：三架构里唯一软件切栈的，trap handler 第一条指令就是交换。sscratch 在用户态时存内核栈顶，在内核态时存用户栈顶——一个寄存器两种用途，靠 sstatus.SPP 区分。
- **prot_init 的职责**：配置内核栈顶到 TSS.sp0（x86）/ SP_EL1（aarch64）/ sscratch（riscv64）。

### 1.7 x86 为什么还保留 GDT（= 原 1.6 独立子段，后移作补充，标题改为疑问式）

**定位**: GDT 不是 OS 概念的必要组成，是 x86 实现特权级+栈切换的**载体**。aarch64/riscv64 没有 GDT 照样实现同样功能。回应 GPT"GDT 在第一章被赋予过高重要性"。

**内容要点**:
- **GDT 承载的两个功能角色**（强调 TSS 是核心知识，GDT descriptor bit 是实现细节）:
  1. 段描述符 DPL：CPU 在控制转移（far call/jump、中断）时检查 DPL，是 x86 特权级检查的依据。
  2. TSS 描述符：TSS 存 sp0（ring3→ring0 内核栈指针）和 IST（嵌套异常专用栈）。**TSS 是核心知识**（1.4c 第三问的答案），**GDT descriptor bit 格式是实现细节**（留给 §2）。
- **为什么 x86 还保留 GDT（回答标题疑问）**:
  - 64-bit 下段式内存隔离已废弃（flat segment），但 x86 架构规定 TSS 必须通过 GDT 描述符引用——所以 GDT 不能完全去掉。
  - 即：GDT 存在是因为 x86 架构要求 TSS 描述符必须挂在 GDT 里，不是 OS 概念需要 GDT。
  - aarch64/riscv64 用 CSR/系统寄存器直接存内核栈指针（SP_EL1/sscratch），不需要 GDT 这种间接表。
- **历史遗留一句话带过**: 64-bit 用 flat segment（base=0, limit=max），段式内存隔离已废弃，内存保护交给页表。Minix3 代码涉及 GDT 是因为 x86 架构要求，不是 OS 概念需要。
- **不要讲**: GDT 段描述符位级格式（留给 §2）、LDT（32-bit 遗留）。

#### 5.6.2 因果链编造错误（P0 级，补入 §2.0 Claims-Evidence）

**问题**：§2.1 第 2 条解释 `memcpy(&kinfo, local_cbi, sizeof(kinfo))` 时，原版写：

> `local_cbi` 是 `kmain` 的参数，位于调用者栈帧中。`kmain` → `cstart()` → `proc_init()` 调用链推进后，原调用者栈帧会被覆盖。将启动信息拷贝到全局变量 `kinfo`，后续代码才能读到有效值而非被覆盖的垃圾。

**错误**：嵌套调用链中，只要 `kmain` 还在栈上没返回，它的栈帧一直存在，`local_cbi` 指向的内容不会被覆盖。"调用链推进后栈帧被覆盖"是想当然的因果链，技术上错误。

**正确解释**：`local_cbi` 作为 `kmain` 的局部参数，作用域受限于 `kmain` 调用链。拷贝到全局 `kinfo` 是为了让**非 `kmain` 调用链的代码**（中断 handler、其他子系统）也能访问启动信息。

**错误模式**：为了解释某个操作的目的，编造看似合理但技术上错误的因果链。特征：解释里出现"因为…会被覆盖/失效/丢失"，但实际机制并非如此。

**根因**：§2.0 Claims-Evidence 没严格执行——每条 C 代码解释都应该能对回源码验证。`local_cbi` 的生命周期用栈帧语义一推就知道原解释错。

**规则补丁**：Ch2 每条 C 代码解释，必须满足以下之一：
- 直接引用源码行作为证据（`file:line` + 代码片段）
- 用 C 语言语义可验证的因果链（如"局部变量作用域限于函数内"是 C 标准保证的）
- 标注"推测，待验证"——不得作为确定知识陈述

违反 → P0（正确性问题，非可读性）。

#### 5.6.3 x86 偏向叙述（补入 §1 概念准确性）

**问题**：§1.8 "为什么 cstart 必须先于后续所有阶段"段，原版只讲 x86 的 GDT 约束（"段寄存器依赖 GDT 描述符"），未点明这是 x86 特有。读者会误以为是三架构统一约束。

**修正**：保留 x86 视角的 GDT 约束叙述，追加"架构差异注记"明确：
- "段寄存器依赖 GDT 描述符"是 x86 特有约束
- aarch64/riscv64 没有 GDT/段描述符
- 三架构都强制 `cstart` 先于 `proc_init`，但强制点不同（x86=GDT，aarch64/riscv64=异常向量+内核栈）

**规则补丁**：当某段叙述只适用于部分架构时，必须显式标注架构范围。未标注 → 读者默认理解为三架构统一 → 误导。这属于 §1 概念准确性，P1。

**判定**：叙述中出现"x86 特有机制"（GDT/段描述符/TSS/IDT 门描述符）但未标注架构范围 → P1。

#### 5.6.4 附录化展开（补入 §3.5 教学性）

**问题**：§1.4c "WHY 必须切到内核栈"一句话带过安全论证，读者想深入理解时无去处。

**修正**：主文保持简洁（一句话建心智模型），文末新增"附录 A：为什么必须切到内核栈"展开完整安全论证（威胁模型 + 4 类攻击向量 + 切换机制如何逐一失效 + 对应表 + 总结）。主文加链接 `[附录 A](#附录-a…)`。

**教学收益**：
- 主线不被攻击细节打断，概念流保持
- 想深入的读者有归宿（附录可跳过，不影响主线理解）
- 攻击向量与防御机制对应表让读者看到闭环

**规则补丁**：当某个 WHY 的完整论证会打断概念流时，主文一句话建模型 + 文末附录展开。附录必须有：
- 威胁模型/前提条件
- 具体机制（攻击向量/失败模式/因果链）
- 机制如何对应到防御
- 一句话总结

附录不是"补充知识"，是"深度展开"——删掉附录不影响主线理解，但保留附录让想深入的读者有完整闭环。
